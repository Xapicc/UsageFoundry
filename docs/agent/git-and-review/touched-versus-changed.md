# What a run touched against what it changed

[← git-and-review index](../git-and-review.md)

Read before editing `src/lib/runTouches.ts`, `src/lib/runTouchScan.ts`, `src/lib/touchReplay.ts`, `src/lib/touchedMap.ts`, `src/lib/pathMap.ts`, `RunTouches.tsx`, `RunTouchNotes.tsx`, or anything under `src/app/runs/[id]/touched/` and `/api/runs/[id]/touched`.

**What a run *touched* is a different fact from what it changed, and the three ways of having none of it are three different sentences.** The Files tab draws both halves: `diff.ts` says what came out of the branch, and `runTouchScan.ts` says what the run's `kind: "tool"` events named, so an operator can read the set difference — a file changed by something that names no file (a `Bash` running `sed -i`, a formatter, a codegen step), a file read and never written, a file touched outside the checkout at all. **Two modules, and the split is load-bearing rather than tidy:** `runTouches.ts` holds the reconciliation and reaches nothing — no database, no `node:fs`, no `git` — because `RunTouches.tsx` is a `"use client"` file and imports it, which is `apiTypes.ts`'s own reason one module over; `runTouchScan.ts` holds the query. Reconciling on the server instead would mean a second `runDiff` — several more git processes for the file list the tab has already fetched — which is the whole reason the changed set arrives as a prop rather than as a fetch. **The scan is `readCountsFor`'s `CASE` and must stay it**: keying on `repo_root` rather than `COALESCE(work_dir, folder)` then `folder` returns an empty result for every worktree-isolated run and looks exactly like a working query. Two differences from that one, both deliberate — it is not filtered to `$.name = 'Read'`, and it **keeps** the rows that query drops at its `ELSE NULL`, which are the touches outside the checkout and are a group of their own. The path fields come from `TOOL_FILE_FIELDS` in `logLine.ts`, a subset of `HEADLINE_FIELDS` typed as one, so a field renamed there fails to compile instead of leaving this reading `NULL` for every row; `path` is deliberately not among them, because on `Glob` and `Grep` it is the directory a search ran in. **There is a second reader over the same rows and it is a second function rather than a flag on the first.** `scanTouchSequence` answers the map's replay — one row per *call*, uncollapsed, `ORDER BY e.id` — where `scanTouches` answers the Files tab, one row per file. Neither derives from the other: a count has no positions in it, and a list of positions is the wrong payload for a table drawing one row per file. A flag would have joined them anyway at the caller that does not want the other's shape, which is why the ordering rides on `/api/runs/[id]/touched/sequence` and not on `touched`: that route is fetched by every run page's Files tab and folding the sequence in would multiply its payload by however many times the busiest file was read. What the two *do* share is the relativising `CASE`, which is now the `TOUCH_ROWS` subquery both read — one copy, because a second would be a second thing to get right and the one that drifted would be the one nobody read. **Ordered by `e.id` and never by `ts`**: `id` is `AUTOINCREMENT` and so ascending in emit order, where `ts` is a millisecond clock several calls routinely share, and a tie broken by the planner is a replay drawing a plausible order that did not happen. The derivation over those rows is `touchReplay.ts`, beside `runTouches.ts` and under the same rule for the same reason — the page that scrubs is a `"use client"` file — and it is **never** derived in the browser from the run page's event array, which is the newest 2,000 events inside 4 MB and would describe the tail of a long run as the whole of it. **No row may carry a success or failure mark**, and that binds the sequence harder than the table: a mark advancing file to file reads as progress. A tool call is recorded when it is made and a result only when it *failed* (`orchestrator.ts:7343-7344`), and the failure row carries no `tool_use` id joining it back — only a whitespace-flattened 160-character command string, which is wrong exactly inside a retry loop. So the header says once that a touch is an *attempt*, and that is where the hedge stays. **An absent diff is an *unknown* changed set, not an empty one**, and only `kind: "range"` is present. `none` is a branch deleted after the run finished or never had; `worktree` is a run in the operator's own checkout, whose `files` are empty by construction, so reading it as known filed every edit under "not changed". For both the card still renders, because its two figures and its three empty states are facts about the events rather than about the branch, and an old run whose branch was deleted is exactly the one whose events are most likely to have been swept. What it drops is the two groups whose *labels* make a claim about the diff: "changed, never named" and "named, and not changed" over a file nobody can say was not changed is the reconciliation asserting the thing it exists to check. `changedSetOf` in `runTouches.ts` is the one place either surface decides this, and `worktree` gets its own sentence there. A range's `uncommitted` lines are git's quoted porcelain, decoded by `uncommittedPaths`, and a touched file among them is "named, and left uncommitted": never "not changed", and never "in the diff", because a land leaves it behind. A rename's old name is the committed twin of that case: a run that read a file before committing a rename of it touched a path the branch no longer has, so it is changed rather than "not changed". It is matched through `changedSetOf`'s `renamedAway` list rather than folded into `changed`, because "changed, never named" iterates the latter and would claim a file no tool call named — a path that was never there under that name. A copy's source is the opposite and stays out of `renamedAway`: it still stands on the branch, unchanged, which the uncommitted side's own `R`/`C` split already decides for its case. **Nothing may render as an empty list.** `run_events` is swept at `eventRetentionDays` while a checkout is kept on its own clock, so a run old enough has a diff and no touches: `touchesFor` answers `swept`, `empty` and `none` as three `kind`s and the component gives each its own sentence, because all three otherwise read as a run that touched no file. The horizon is checked **after** the scan and not instead of it — a run past the horizon whose sweep has not run yet still has its rows, and announcing the policy over data that is sitting there would be a readout describing the schedule instead of the database. And the header prints the **distinct touched-file count** and the **work-cycle count**: they are the measurement that decides whether a file-by-cycle grid has an axis short enough to draw, which `proposals/SessionFlow/` deferred for want of them.

**The map at `/runs/[id]/touched` draws the same rows and is allowed to claim less than the table, never more.** The operator read the landed card on a real run — 39 distinct files across one work cycle — and asked for the picture `proposals/SessionFlow/` had turned down; that call is made and is not to be relitigated, but the survey's *findings* are facts about the stored data and every one of them still binds. Four rules, and each fails silently by drawing something plausible. **The node set is files and the arrangement is the path hierarchy** (`touchedMap.ts`): tool → file is a bipartite star at every size — a dozen hubs with nearly everything hanging off `Read`, which the mockup's own fake run put at degree 321 — and it draws one fact the header already states. Tool identity is therefore an *attribute*, `TouchedFile.tools` on the node and the union of them on a directory, and a line on the canvas means **is in** and never *was called by*. A tool node here would have to earn its place against that, and none has. **Nothing on it says a touch succeeded**: the fill says read, written or both, which is what the call asked for, and the sentence saying a recorded call is an *attempt* is shared with the table through `RunTouchNotes.tsx` rather than written a second time. **No file is ever dropped**, and the rule lives in `pathMap.ts` — the arrangement, over any per-file payload — rather than beside the touches, because the next map laid out this way inherits it instead of pasting it. Over budget, the tree folds at a **depth** — deepest directories first, so the top level of the repository survives — and each folded node carries the count behind it and the surface says the total out loud; opening a directory opens its ancestors, or the next plan closes one over the top of the click. `capGraph` is deliberately not reused: it prunes by degree largest-first, which over this graph keeps the directories and discards the files. And **`changedKnown` withholds the changed ring**, on the same grounds as the two groups the card drops: a mark meaning "the branch changed this" over a file nobody can speak for is the reconciliation asserting the thing it exists to check. The one place the map says *more* than the table is a run whose events are `empty` and whose diff is not: it wrote through `Bash` alone, and those files have paths and therefore positions, which is exactly the group the survey recorded a tool → file graph as structurally unable to show.
