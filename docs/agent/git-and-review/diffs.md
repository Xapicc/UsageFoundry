# Diff flags, budgets and ranges

[← git-and-review index](../git-and-review.md)

Read before editing `DIFF_FLAGS`, `selectForPatch`, `splitPatches`, `diffRange` or `targetMergeOn` in `src/lib/diff.ts`, `src/lib/patch.ts`, `conflictedFiles` in `src/lib/land.ts`, or adding any `git diff` call.

**Diffing runs repository-controlled code unless it is told not to.** Every `git diff` that reads a file's *contents* carries `--no-ext-diff --no-textconv`, through the one `DIFF_FLAGS` array in `diff.ts` (`--no-color` and `-M` with them): `diff.external` and a `diff.<driver>.textconv` reached through `.gitattributes` are both *commands git runs*, configured by the repository being rendered. Same class as the `core.fsmonitor` clearing that already applies to every call. The one call site outside that array is `land.ts`'s `conflictedFiles`, `["diff", "--name-only", "--diff-filter=U"]`, and its exemption is written here rather than left to be re-derived: `--name-only` emits paths and never opens a blob, so neither driver is invoked. That is an argument about *that* call's arguments and not a relaxation of the rule — a `--name-only` that grows a content flag, or any new `diff` call, takes `DIFF_FLAGS`. The same site passes `NO_CLOCK`, so a driver invocation there would also run unbounded, which is the second reason not to let one become reachable. Paths that come back from git and go out again as pathspecs are pinned with `:(top,literal)`, or a filename containing `*` would be read as a glob.

**A diff that was shortened says so.** The file *list* is always complete; patch bodies are budgeted (`selectForPatch`), and what the budget leaves out is counted and rendered as "N files listed without contents" rather than dropped. The budget is in **bytes as well as lines**, because the selected patches are one `git diff` read that fails whole at `MAX_DIFF_BYTES`: a minified bundle is one line of megabytes, and charged in lines it took every other file's patch with it. A file's byte cost is both sides' `ls-tree -l` blob sizes plus a marker per changed line — a bound, so a small edit to a very large file is charged the whole file and listed without contents, which the count says. `splitPatches` matches chunks to files **by position**, never by parsing the header path — git re-quotes odd filenames there — and a count mismatch yields no patches at all rather than hunks filed under the wrong name. The one ordinary way the two lists part is a type change (a file that became a symlink, or the reverse): numstat counts it once and the patch writes it as two chunks under an **identical** header, so a repeated header is folded into the chunk before it — measured on git 2.39.5, where one type change cost every file in the diff its patch. **A read that failed is not a change that was too large**: when no patch could be read, every file counts as listed without contents and `patchFailure` says why, and the per-row sentence gives no reason at all, because a row cannot tell the budget's omission from a failed read.

**An isolated run's diff is measured from the target as the branch contains it, not always from its base.** `worktree_base` never moves, and a conflict resolution merges the *target into the branch* — so from then on `<base>...<branch>` holds every commit the target gained before that merge, and "What changed", the review a person pays for (`review.ts` reads the same `runDiff`) and the Files tab's "changed, never named by a tool call" all present other people's work as this run's. Measured on git 2.39.5: one run commit and one unrelated `main` commit, `main` merged in, gave 4 files where the run had changed 2. `diffRange` measures from the newest first-parent merge's **second** parent when `merge-base --is-ancestor` puts that parent on `worktree_base_branch` — the first parent is the branch before the merge, and measured from there the run's own commits vanish — and the card says which commit it measured from, because a count that is not base-to-branch reads as wrong beside the operator's own `git diff <base>`. The same happens when an agent merges the target itself, and the same rule covers it. `targetMergeOn` walks the first-parent merges newest first, up to `MAX_MERGES_WALKED`, and takes the first whose second parent is on the target, so a merge of some other branch on top no longer hides an older merge of the target; a branch with no such merge, or a legacy row with no `worktree_base_branch`, stays measured from `base`, and the card then says nothing, which is true. A validation and a review each record the commit it was measured from as their `base_sha`, since that is what the child was shown.
