# Reviews, resolutions and validations: the assist child

[← git-and-review index](../git-and-review.md)

Read before editing `startReview`, `startAssist`, `AssistRequest`, `reviewEnv` or `parseReviewOutput` in `src/lib/review.ts`, `resolveConflicts` or `resolvePrompt` in `src/lib/land.ts`, `resolveAllowedTools` in settings, or the `$.assist` filter in `src/lib/runTouchScan.ts` and `src/lib/fileCostNotice.ts`.

**Reviewing a diff is not a work cycle and is never automatic.** `startReview` exists only behind a POST; nothing in the run loop reaches it. It refuses when the operator's *own* configured ceiling is already spent (`guardFraction >= 1` on either window) rather than going through `evaluateBudget` — there is no per-run fraction for a review and inventing a threshold would be a limit nobody set. The reviewer is given the diff, the run's task and how the run ended, but **not** the event log: the log is the process rather than the outcome, and a reviewer that reads how the agent got there reviews the journey. A large diff is cut at a file boundary and the omitted files are *named* in the prompt, because a reviewer handed a third of a change with no marker writes a confident review of a change that did not happen.

**A conflict resolution may check its own merge only where a toolchain can exist, and only where an operator named the command.** `resolveConflicts` pins `acceptEdits`, which auto-approves file edits and read-only shell and holds everything else for a human — and a `-p` child has nobody to ask. So the resolver could edit the conflicted files and could not run one command against the result: 19 of 58 completed resolutions, $109.94 of $233.85, say in their own report text that they could not compile or test what they had merged, across the whole recorded window. `AssistRequest.allowedTools` is the same door `ISOLATED_GIT_TOOLS` opens for a work cycle and the same flag — additive, so everything not named still follows the mode. **The reviewer passes no command and must keep passing none**: it is `--permission-mode plan` precisely so that nothing it does can write, and a command granted through that field would be the one hole in that. What the flag now always carries underneath the operator's list is `SEARCH_TOOLS` — `Grep` and `Glob`, which is why the emptiness guard is gone, since the list can no longer be empty. That is a bound by capability rather than by count, and the difference is the whole of what makes it not a hole: the pinned CLI drops both tools from the tool list whenever `Bash` is present unless something names one of them, so naming them buys their existence and not a permission. Measured on this install — zero of 469 recorded `system:init` events ever carried `Grep`, and every one of the five `Grep`/`Glob` calls an agent attempted came back "No such tool available" — and measured the other way on the pin, where adding the two to `--allowedTools` puts them back and changes nothing else in the list. `settings.resolveAllowedTools` is **empty by default and that is not timidity** — this app runs against whatever repository is mounted, so there is no command it could ship that is right for one, and `npm run typecheck` means nothing in a Go or Python tree. It is granted only on `resolveCheckout`'s **reuse** branch, where the run's own worktree was clean and standing on the branch and therefore has a dependency tree; the other branch cuts a fresh `git worktree add` with none, where a check fails for a reason that is not the merge and an agent reading a missing-module error as its own bad resolution will "fix" code that was right. `resolvePrompt` takes the granted list rather than assuming one, so the prompt cannot ask for a command the argv did not allow — an agent told to verify and then refused reports the refusal as a finding about the merge, which is how nineteen reports came to carry a limitation instead of a result. **It is not a gate and its name no longer says it is.** It was `resolveVerifyTools`, one line from `landVerifyCommand` in the same interface, which made it read as the install-wide answer to "what must pass before code lands" — and it is read in exactly one place, `resolveConflicts`, where it becomes the assist's `allowedTools` and decides no land at all. The cost of the old name was an operator setting this one believing they had set the gate, which leaves the gate off and looks identical to having set it. Stored settings are the non-default keys only and carry no version, so `getSettings` reads the old key when the new one is absent: without that the rename is somebody's grant silently becoming `[]`, and `saveSettings` drops the dead key the next time anything saves because it rebuilds the blob from `SETTINGS_KEYS`.

**`AssistKind` has a third member and it is the one that is not a person's press.** A review and a merge-conflict resolution are each started by somebody pressing something; a **validation** is started by a run asking to close a task, and `docs/agent/taskboard.md` carries what it decides and why. What belongs here is what it does to this module. It is on the same table, the same lifecycle and the same boot reconciler, which is the reason a third `kind` was chosen over a fourth table. It takes the review's clock rather than the resolution's absence of one, and more sharply than the review needs it: a run is waiting at its cycle boundary for the answer, holding its folder and one of `maxConcurrentRuns`, so a verdict that never arrives is a slot that never comes back — where a resolution is unbounded precisely because there is no length of time after which reconciling somebody's work becomes the wrong thing to do. It is the only kind that passes `maxBudgetUSD`, and `AssistRequest` carries that as an optional field rather than a constant here so the two a person starts keep the behaviour they had. `after` is the hook it settles through, exactly as a resolution commits its merge through it, and the verdict reaches `run_reviews.verdict` as a `Partial<AssistResult>` — this module never parses one and must not learn to, because what a verdict *means* is the other file's subject. Three new columns ride along: the task the claim was about, and the base and head it read, written at the **start** rather than at the settle, because what they record is what the child was shown and a branch that moved while the validation ran would otherwise be recorded as the thing that was judged.

**An assist streams, and every tool call it makes is on the run's log wearing its own name.** The three kinds spawned here ran `--output-format json` until 2026-09-09, which prints one object when the child exits: a validation therefore showed as the `complete_task` that claimed the task, then a minute of nothing while a billed child read the branch, then a verdict — and the half an operator needs in order to decide whether to believe that verdict, which files it opened before deciding the work was there, existed nowhere at all. `stream-json` plus `--verbose` is the pair the CLI gates streaming on, `chat.ts` carries the same two for the same durability reason one file over, and the shape was measured against the pin before the change rather than assumed (`docs/verification.md`, 2026-09-09). Two things follow and neither is optional. **Only `tool_use` blocks are taken**: the assistant's own text belongs in `run_reviews.text`, where the page draws it as a verdict or a review, and the same words on the run's log would read as the run's report about itself. **And every one of those rows carries `assist`**, which is what `describeEvent` turns into the `check ›` / `review ›` / `resolve ›` prefix — attribution is load-bearing here in a way it is not even for a sub-agent, because a check reads the branch while the run that asked for it is still mid-cycle, so its calls land *interleaved* with the run's own rather than after them, and an unlabelled `Grep` between two of the run's lines reads as the run's.

**That field is also a filter, and two readers had to grow it in the same change.** A `tool` row is not only a log line: `runTouchScan.ts` reduces them into "what did this run touch", which the Files tab draws and the touched-versus-changed reconciliation reads, and `fileCostNotice.ts` counts the `Read`s in a folder to tell the next agent what is expensive to keep re-reading. Both would have silently absorbed the assist's reads — files nobody edited appearing as the run's work, and a reviewer's single pass over a file being reported back as a habit — so both now require `json_extract(payload, '$.assist') IS NULL`. That is the whole reason the marker is a field on the row rather than a prefix baked into `name`: a string that only the renderer understands cannot be filtered on in SQL, and these two readers are SQL.

**`parseReviewOutput` reads the `result` event and refuses anything else, including the last line that happens to parse.** A stream's final complete line is an ordinary `assistant` event whenever the child was killed, and read as the result it reports a turn that never finished as one that finished with no text having cost nothing — with the stderr that says what actually happened dropped. So the scan is for `type === "result"` and the fall-through to a whole-string parse is taken only when no such event arrived *and* the one object printed does not name itself as some other kind of event, which is what keeps the older one-object shape readable.
