# Parking, refusals and the rate-limit ladder

[← run-lifecycle index](../run-lifecycle.md)

Read before editing how `src/lib/orchestrator.ts` parks a run, answers a refusal, a transient API error or a 429, and reconsiders a paused run in `sweepPaused`.

**A run parks on two triggers, and only one of them needs configuring.** Our own guard is the first: `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume`, which needs both a per-run fraction *and* a numeric 5-hour ceiling — and ceilings default to `null` by design, so on a stock install that trigger never fires. The provider's own refusal is the second, and it needs neither — **including the enforcement mode**, which it used to need and must not again. That gate read `limited && policy.enforcement === "live-resume"`, and the default is `between-cycles` in all three places one is set, so the ordinary run met the shared account's wall and was written `failed`: terminal, with the only way back an HTTP request a person makes, and at twenty-five runs sharing one allowance that is the steady state rather than the exception. The two facts were never related — `enforcement` is the operator's answer to *when guards are read*, where a 5-hour window refilling on its own is a fact about the provider and the one quantity this app already reasons about as waitable — and nothing on that control said it was also deciding whether a wall is survivable. `refusalDisposition` is that decision now, pure and unit-tested, and it takes no enforcement argument at all: there is nothing left to gate on. What still bounds it is `MAX_PAUSES_PER_RUN` — counted on `runs.refusal_pauses`, never on `pause_count`; see the next paragraph — and the run's own worked minutes, which `evaluateBudget` checks ahead of the window at the pre-cycle guard and `sweepPaused` checks again, ending a parked run on a verdict that can never clear rather than leaving it holding a folder. **Worked** minutes rather than wall clock, and that changed: `maxDurationMinutes` is now measured against the span since `started_at` less every park, so the hours a run spends waiting for the window no longer count against it — see `budgets-and-guards.md` for why that is still a terminus. The consequence here is that the second bound has stopped bounding how long a parked run may *exist* — the sweeper's own check now only ever ends a run that was already out of time when it parked, and `MAX_PAUSES_PER_RUN` bounds the refusal path rather than this one, so on the guard path `maxIterations` is what is left. The run failed at that cap says it ran out of *waits* rather than out of allowance, because by then the allowance may well have refilled and the operator's next move differs. Claude Code reports API-level refusals as an assistant turn whose `message.model` is the literal `<synthetic>` (the marker `transcripts.ts` already keys on to keep an all-zero record out of the unpriced warning); `isUsageLimit()` decides whether that refusal is an exhausted allowance. Nothing parses a reset instant out of the message: the CLI renders a *formatted local time*, and the `usage limit reached|<epoch>` form every community wrapper keys on appears nowhere in the shipped binary. The refusal test sits **before** the exit-code test *and* before the `DONE` test — a refusal exits non-zero, so the exit code would file the provider's decision as the agent crashing, and a refusal that exits 0 would otherwise match nothing and re-spawn straight back into the wall.

**The refusal allowance is its own count, and only a refusal spends it.** `MAX_PAUSES_PER_RUN` reads `runs.refusal_pauses`, which the `paused` branch of `startRun`'s ending advances only when the park is waiting out a refusal (`refusalPark`); `pause_count` beside it counts every park of either kind. They used to be one column, so a `live-resume` run that had stepped aside three times at its own 5-hour guard was failed `pauses-spent` at its first real refusal — out of waits it never took — and the refusal ladder started a rung up for parks that were not refusals in a row. `reopenRun` zeroes `refusal_pauses`, because a run the cap ended and the operator then picked up is the fresh attempt the cap was not meant to span: carried, the pick-up failed at the next wall without waiting once, saying it had already waited out three windows. It does **not** zero `pause_count`, which `ensureWorktree` reads as "has worked before": a cycle the live guard cut is refunded, so a run parked in its first cycle is back at `iterations === 0` with its branch very much existing, and a zeroed `pause_count` would send it past the orphaned-branch guard. The column was added with a backfill from `pause_count`, because an existing row cannot say which of its parks were refusals and counting them all keeps exactly the allowance it had. `parksAndRefunds.test.ts` drives both halves through the real loop.

**A refused run backs off; it does not trust the window boundary.** `refusalResumeAt` reads the end of the last block with real spend in it — not `session.endsAt`, because the refusal's own zero-token `<synthetic>` record opens a block of its own that reads as a window five hours out. Even that boundary is approximate in both directions: it runs late by the opening turn's latency, and early whenever the window was really opened by work this app cannot see — claude.ai, Desktop and Cowork spend the same allowance and write no local transcript. A boundary still in the future is waited for; one already passed falls through to a 20/40/60-minute backoff, stepped by `refusal_pauses` so a guard park between two refusals does not lengthen the second wait, floored so nothing re-spawns immediately and capped at six hours. `MAX_PAUSES_PER_RUN` bounds the whole thing, because unlike the guard path — where worked minutes are checked ahead of the window and terminate the run — a refusal is someone else's claim about someone else's counter, and a misread one must not park forever.

**…and every run's answer is spread, because every input to it is shared.** All of the above is a statement about *one* run. The ladder is a module constant and the boundary comes from a `currentSnapshot()` whose file scan is coalesced across concurrent callers, so twenty-five runs refused inside the same minute read one block boundary and, with nothing randomised anywhere, computed **one** `resume_at` between them — measured, not reasoned. They woke in one sweep, spawned in one turn, met the same approximate boundary and re-parked together, three times, at which point the cap ended the fleet inside two hours with no operator input. `jitterMs` is the one design for that, shared with the transient ladder below: uniform over `[0, width]` where `width` is half the wait, floored and capped, and **never negative** — jitter may only delay, because both callers have a floor underneath them (`MIN_REFUSAL_WAIT_MS`, and the ladder's own rung) that a shortening spread would quietly undo. It is applied *after* `refusalResumeAt`'s floor and cap and clamped again, so neither moves; the band collapses only at `MAX_REFUSAL_WAIT_MS`, which a real 5-hour boundary cannot reach. The randomness is a **parameter** rather than a `Math.random` inside, which is what keeps the ladder, the floor and the cap pinned at the numbers they had — those cases pass `() => 0` and read exactly as before. The floor is `3 × SWEEP_MS` and it is the sweeper's property rather than the jitter's: a parked run wakes at the first sweep *after* its `resume_at`, so a band narrower than a tick is invisible. `MAX_RESUMES_PER_SWEEP` is the other half, and it is the half no spread can reach — a fleet parked before this existed, or bunched against the floor, or carrying a null `resume_at`, is due in one tick, and the sweep used to flip every one of them and hand the lot to a single `promoteQueued()`, which starts everything startable in one synchronous turn. Four per tick, and a run over the cap simply keeps its `paused` row and its already-past `resume_at`: nothing is written, so nothing is rewritten every 60 seconds, which is `FOLDER_TAKEN_REASON`'s rule one branch over. The cap belongs here and not in `promoteQueued`, which must stay the one owner of FIFO order, the folder claim and the concurrency cap — the last of which is `settings.maxConcurrentRuns`, **4** in `DEFAULTS` since `8651bcd` and nullable only as an explicit opt-out, so a stock install is bounded twice over and an install that has taken that opt-out is bounded here and nowhere else.

**A `<synthetic>` turn is not by itself a refusal — the cycle's own outcome decides.** When a stream drops after some blocks have been yielded, Claude Code finalises the partial response with an ordinary `end_turn` and carries the cycle on (`tengu_streaming_partial_finalized`, and the watchdog/stale-connection retries beside it). The `API Error: Connection closed mid-response` turn it leaves behind is then a warning *about a completed cycle*, followed by a clean `result` and exit 0 — but `apiError` latches on first sight, so the marker alone was ending runs whose work cycle had finished. `recovered` requires the CLI's own verdict (a `result` event, a success subtype, a zero exit) — never anything inferred from the text — and excludes an allowance refusal by name, because a wall that exits 0 must still stop the run rather than re-spawn into itself, which is the reason this whole test sits ahead of the exit-code test.

**A refusal has three answers, not two, and the third one is not a park.** A cycle can also die because the connection dropped mid-response or the upstream was briefly overloaded — `isTransientApiError`, matched on the five stream-truncation sentences read out of the shipped binary, on the statuses and `error.type` names the provider documents as retryable, and on the socket errors that never reach a status. That is neither the wall nor the agent failing, so the loop retries it in place: 5/20/60 seconds of backoff and another spawn into the same session. Retried rather than parked because `resume_at` exists to wait out a five-hour window and a run that parks yields its folder — for a fault measured in seconds, on a run whose session is intact. `MAX_TRANSIENT_RETRIES` is **consecutive**, reset by any cycle that gets through and held in `startRun`'s frame rather than on the row (a restart hours later is not "in a row"), so a long run meeting one blip an hour is never terminated by the total while a dead upstream ends the run in ~85s and names the attempt count. The retried cycle is refunded to `iterations` *and* to `cyclesThisSegment` — the first for the reason a parked cycle is, the second because that counter means "no cycle in this segment has completed yet", which is what lets `looksLikeResumeFailure` still recognise a retry that cannot resume the truncated session. The order of the tests is load-bearing: `isUsageLimit` first, because a wall can arrive as a 429 and no backoff refills an allowance. `refusalInStderr` deliberately does **not** consult this — an agent's own build output says "connection error" constantly, and a run must not re-spawn because its test suite could not reach a registry.

**…and a rate limit is a transient failure that is not the same transient failure, so it has its own ladder and its own ending.** `isRateLimited` is a **strict subset** of `isTransientApiError` — both patterns already match there — so it widens nothing about what is retried; all it decides is which ladder and which sentence, and `refusalKind` asks it after the wall and before the general blip, because the wider predicate matches every 429 too. The distinction is what the two faults *are*. A dropped socket clears in seconds whatever this app does, and 5/20/60 is generous for it. A 429 at twenty-five concurrent runs against one account is the provider describing this app's own steady-state request rate: it lasts as long as the fleet keeps asking, so the three fast retries became three twenty-five-wide waves into the condition that caused them and the fleet was `failed` inside ninety seconds, every dependent chain `blocked` behind it, with an 85-second tolerance against a limit the concurrency itself produced. `RATE_LIMIT_BACKOFF_MS` is minutes rather than seconds for that reason — 30 seconds, 2 minutes, 5 and 10, so four retries and five attempts in a row, about 17 minutes of tolerance at the floor of the jitter band and about 26 at its ceiling — and the wait is the back-pressure: a run that is sleeping is a run that is not asking. What that costs is paid in occupancy rather than in spend, and it is a deliberate trade rather than an oversight: the cycle is retried **in place**, so the run holds its folder, its worktree slot and one of `maxConcurrentRuns` for the whole ladder. Parking instead would yield the folder — which is the right answer for a five-hour window and the wrong one here, because the run queued behind it meets the same 429 and the session this run would have to resume is intact. It is bounded on the other side by the run's own time limit, since a retry re-enters the loop at the top and `evaluateBudget` reads `maxDurationMinutes` before every re-spawn — and this wait does count against that limit where a park does not, because the run sleeps in its own frame and never writes `paused_at`, which is the column the worked-minutes arithmetic subtracts. It bounds the tolerance and does not promise the fleet survives, which is why the ending says so: `rate-limited` is a separate `RefusalCause` from `retries-spent`, because "the upstream is down" and "we were rate limited and gave up" call for opposite responses, and the sentence names `maxConcurrentRuns` — the N this whole failure is proportional to — rather than telling the operator to wait. `transientBackoffMs` is the schedule, pure and taking the attempt index and a randomness source, where it was `TRANSIENT_BACKOFF_MS[transientRetries]`: a constant lookup on a per-run counter that starts at 0 for every run, so twenty-five runs meeting one failure retried at exactly the same instants. It shares `jitterMs` with the refusal path above, additive and half a rung wide — half being what keeps the ladder *strictly* climbing, each rung's floor above the one below it at the top of its band — and passes no floor, because this wait is slept in-process rather than served by the 60-second sweeper, so any spread at all is real.

**A paused run is reconsidered, not trusted.** `resume_at` decides *when to look*; `evaluateBudget` decides *whether to run*. `sweepPaused` (60s, lazily started and stopped) re-evaluates from a fresh snapshot and re-queues through `promoteQueued` rather than calling `startRun` directly — that is what keeps FIFO order, folder reservation and the concurrency cap in one place. A verdict that can never clear ends the run instead of leaving it holding a folder — except the one verdict that is not about this run at all: `no_ceiling` reads as clear, through the same `RUN_ENFORCEABLE_CODES` the pre-cycle guard reads, because ending every parked run 60 seconds after the pre-cycle guard ended every running one is the same wrong answer twice. `pauseVerdictClears` is that one rule and it has two readers: the decision, and the occupancy read that feeds it — a verdict that clears without asking who is in the folder is the two-agents-in-one-working-tree collision arriving through the one door allowed to un-park a run. A cleared verdict is still not enough on its own: a run whose folder was taken while it waited stays `paused` and re-checks next tick, because the alternative is a `queued` row that a restart would close out.
