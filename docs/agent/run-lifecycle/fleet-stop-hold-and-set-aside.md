# The fleet stop, the new-work hold and set-aside

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `src/lib/fleet.ts`, any reader of `settings.newWorkPaused`, or `runs.set_aside_at` and the bulk pick-ups in `src/lib/orchestrator.ts`.

**There is one install-wide stop, one install-wide hold, and neither is a new way for a run to end.** Every stop was per run or per workflow instance, so halting twenty-five unattended runs was twenty-five requests through twenty-five pages and the only real alternative was stopping the container — which discards every in-flight cycle's spend accounting. `src/lib/fleet.ts` is the three missing controls and it *composes* them: `stopFleet` walks every `started` instance through `stopInstance` — the one door, which closes its orchestrator blocks before it signals anything, so a block left `thinking` cannot emit into a fleet being taken down — and then every run outside one through `stopRun` and `stopWaitingRun`, choosing between them with the very same `haltSteps` a workflow halt uses. `memberSteps` became that generic exported function for exactly this reason: a second copy of "which rows does this take down" is a second chance to rewrite a `completed` row as stopped, or to miss a member that then goes on spending. Waiting rows are closed out **before** any live run is signalled, `walkMembers`' ordering for `walkMembers`' reason, and the whole walk is synchronous. They are written `stopped`, as Stop on each one's page writes them, where a workflow halt writes its waiting members `blocked`: a halted member is kept from revival by its instance's `stopping` (`HALTED_MEMBERS`), and a run outside a workflow has nothing like it, so a `blocked` row was woken by `reviveBlockedDependents` the moment anybody picked up the run in front of it, undoing the stop of a run nobody had picked up. `stopWaitingRun` releases nothing, which is what keeps the ordering: the live runs' own stops release afterwards. The cause is a third `HaltCause` kind rather than `operator` with different words, because once the sentence has scrolled off the stored cause is the only thing distinguishing a workflow somebody stopped from one that went down with everything else.

**The hold is a settings row of its own, and nine separate call sites read it.** `settings.newWorkPaused` suppresses `promoteQueued` (through `selectPromotable`), `releaseDependents` (through `releasableRuns`, the release half only — a chain that can never start is still ended, because `blocked` costs nothing and holding it back would leave a dead chain nobody can end), `tickSchedules` (through `decideSchedule`'s own `paused`, so the cursor stays put and the windows that pass are recorded as missed rather than made up — and asked once more after a fire's snapshot, because a hold pressed while that was awaited is not in the decision, where `releaseWindow` gives the cursor back), an orchestrator block's deciding turn (at its claim, in the paragraph below), a review block's reviews and the merge queue's conflict resolutions (in the paragraph after that), `emitBlockRuns` (at its door, beside the two refusals that are already facts about the machine rather than about the specs), and the two parks the sweeper un-parks: `sweepPaused`'s resume branch and `releaseStackWaits`. Those two leave the row in its park rather than queued, and that is the whole of their reason: a restart keeps a `paused` row inside its grace and a `waiting-for-stack` row whatever its age, but closes every `queued` row out, and the hold kept the row in the queue — so a park whose wait ended while new work was held was ended by the very restart the operator held the fleet for. A verdict that ends a parked run still ends it, because that is recording rather than starting. It suppresses *starting*, never recording: a press of Run on a workflow still writes its graph out, the rows simply never leave the queue. Persisted rather than a process variable because the usual reason it gets set is the restart it has to survive, and deliberately **not** a key of `Settings` — the settings page sends the whole object on Save, so a field in that blob is one an unrelated edit from a stale tab would silently clear, which for a preference is a nuisance and for the fleet's kill switch is the failure it exists to prevent. Clearing it calls `releaseDependents` then `promoteQueued`, in that order and for `sweepPaused`'s reason; without that pair the queue would sit still until the next terminal transition, which on a fleet that has just been stopped is never. Then `sweepPaused`, for the parks the hold kept, whose own timer is a minute. It is stated on the dashboard in words, because a held fleet and a quiet one are otherwise identical there. The bulk pick-up takes an **explicit list of the ids the page displayed**, `POST /api/chat/[id]/approve`'s rule and its reason, with one budget for all of them — **laid over each run's own stored blob rather than substituted for it**, because `reopenRun` writes `budget=?` wholesale, so handing it the sheet's two fields would rewrite every limit a run was started with to the two the sheet happens to expose and silently drop the rest: a time limit, a token limit, an enforcement mode chosen per run, gone on a press aimed at the cycle cap. Spreading the wire over the stored blob keeps an explicit answer explicit — a blank cycle cap arrives as `null` and means "no cycle limit" here exactly as it does anywhere else — while a field the sheet never asked about keeps the value that run was started with, and `permissionMode` is untouched by the merge because it rides on the stored blob, `normalizePolicy` drops it and `reopenRun` reads it back off the row. The ids are picked up **in dependency order**, not the page's newest-first order: a dependent that never started goes back to `waiting` and is decided on the spot, and if the run it waits on through `on-finish` is in the same press and not yet picked up, that run still reads as a finished cycle, so the dependent is admitted and both work at once. It is `topologicalOrder` over the `run_deps` rows among the ids rather than a `created_at` sort, because a chain is created inside one millisecond often enough that the tie would fall to a random id. It is deliberately narrower than `reopenRun` accepts: `completed` is what a run that used up its cycle cap is written as *and* what a run that reported DONE is written as, so a fleet control that swept it in would restart everything that worked, and that decision keeps its own button on its own page.

**An orchestrator block's deciding turn is held at its claim, not refused at its emission.** Until 2026-10-06 the hold reached a block only at `emitBlockRuns`, so a held install still spawned the turn — on `0effa73`, `startWorkflow` under the hold returned ok and a stub CLI was invoked with `-p decide`, exactly as without it — and the turn was billed for a decision it was then told nothing could act on. The other answer, naming the turn as deliberately outside the hold, was weighed and refused: the operator presses the hold to stop new spending, the turn is spending by a child nobody is watching, and under the hold its only possible outcome is a refused emission — after which the block has emitted nothing, which blocks everything behind it, so the workflow was paid for and lost. So both claim loops, `advanceInstance`'s and a pass's in `stepPass`, ask `newWorkPaused()` beside `assistBudgetFull()` and `isShuttingDown()` and leave the block `waiting`: the budget-full shape, a shortage rather than a decision about the work, and never `blocked`, which would end the branch behind it for a condition the operator will clear. `startBlockTurn` asks once more after its window and transcript awaits, `tickSchedules`' reason, and hands a claim the hold overtook back to `waiting` with `started_at` cleared, since nothing started. `emitBlockRuns`' refusal stays, for a turn already deciding when the hold is pressed. Lifting needs no call of its own: `setFleetPaused(false)` calls `releaseDependents`, which ends by advancing every instance. **A restart under the hold is the other half.** `reconcileBlocksOnBoot` closed out every `waiting` block of an instance no member survived, on the premises that nothing would wake it and that re-deciding unattended is spend nobody wants — and with the turn held, the restart the hold is usually pressed for wrote off exactly the held turns, where the run half keeps a `waiting` run that is ready and held. Under the hold neither premise is true: the lift wakes the block, and a person presses it. So `bootBlockPlan` leaves an instance's blocks, `looping` ones included, for the lift when new work is held and the restart closed out **none** of its members (`restart_closed`); one with such a member is closed out as before, because a block behind a run the restart ended would be released by `on-finish` on a cycle that died with the container, which is the queued-run rule's case held or not. A review block is held the same way and a merge block is not, in the paragraph below.

**A review block is held at its claim and at each review's door, and a merge block only at its conflict resolution.** Decided 2026-10-06 on the deciding turn's argument: a review is a billed child nobody is watching, a resolution is one too, and the operator presses the hold to stop new spending. So both claim loops ask `newWorkPaused()` before claiming a review block and leave it `waiting`, for the reason above. `startReviewBlock` asks again after its snapshot await and hands the claim back through `releaseBlockClaim`, since nothing is seeded yet. `driveReviewItem` waits the hold out at each review's door, beside a full assist queue, for a block already reviewing when the hold is pressed: its next review would otherwise start the moment a slot freed or a fix round ended. Its fix runs needed nothing, since they go through `createRun` and sit in the queue. The lift needs no call of its own: `releaseDependents` advances a waiting block, and the door's poll notices. A merge block is not held at its claim, because a merge with no conflict spends nothing, and holding it would leave free work unlanded for a limit about spending. Only the resolution is refused, at the queue's two doors, with `HELD_RESOLUTION_REFUSAL` at both so the row reads the same. `processOne` asks after `landState` and before any checkout, through `planItem`'s `resolutionsRefused`. `resolveConflicts` asks once more, for a queue asker, after its last await, and rolls the merge back as its markerless refusal does. The row fails as it would in a batch without auto-resolve, rather than waiting in the queue, because a waiting row holds its repository's one drain for as long as the hold lasts, and every land the operator queues there behind it. The merge block that fails is one `pickUpsOf` already offers. The answer is not cached with the window's in `resolutionsRefused`: asking costs nothing, and the branch behind should see a lift. It reaches every queue batch, the operator's own included, for `promoteQueued`'s reason — queued work, drained by a worker nobody is watching — while the run page's Resolve button passes no asker and is not held, a chat turn's reason. `bootBlockPlan`'s held rule needed nothing. A review block held at its claim is a `waiting` block of an instance the restart closed none of, which it already leaves for the lift; one already reviewing is `thinking`, and the boot fails it as it fails any review a restart cut off.

**A control that acts on a set needs a per-run way to say no, and `runs.set_aside_at` is it.** There are two bulk pick-ups — the restart notice, over every `restart_closed` row a restart ended `failed` or `stopped`, and the fleet's own, over every terminal run the page is displaying — and neither had anything an operator could say about one run in the set. So a run somebody had deliberately stopped was started again by a press aimed at the twenty-four beside it: an agent that accepts edits, back at work in a folder that was finished with, under limits nobody re-read, and nothing anywhere recording that it had been held back. The alternative was to stop pressing the button, which at twenty-five runs is worse than the one-page-at-a-time state the button replaced. `setRunAside` writes **only** that column — status, `stop_reason` and `restart_closed` are left exactly as the ending wrote them, which is what makes putting the run back an undo rather than a fifth way for a run to end, and it is why the two readers *filter* on the column instead of clearing anything. The three doors are deliberately not the same mechanism, and there is a fourth that is not a pick-up at all: `reviveBlockedDependents`, which `reopenRun` calls for whatever the picked-up run's ending blocked, leaves a set-aside row out of its candidate set. Both bulk presses reach it, so without that a set-aside run behind one they picked up was put back to waiting and then started, and the walk went on through it to whatever was behind it. `restartClosedRuns` filters the query, so the notice's count and the press that reads that list are the same answer and cannot disagree. `reopenFleet` checks the column **against the row**, at the moment of the write, because the ids it is given are a list the page rendered earlier and a run set aside since is exactly the stale case the check exists for — refused by name, never silently skipped. And `reopenRun` does not read it at all: it **clears** it, because picking one run up by name on its own page is the decision being taken back, and a mark that survived would go on excluding a run that had since been picked up and worked again. Clearing it before the revive is also why a by-name pick-up of a set-aside run still wakes what is blocked behind it. Setting aside a *live* run marks it **before** `stopRun` signals anything, `stopFleet`'s ordering for `stopFleet`'s reason: stopping first leaves the row terminal and unmarked for as long as the loop takes to notice, which is precisely the set a bulk pick-up sweeps, so the press meant to hold a run back could hand it to one instead. The route composes the two rather than `setRunAside` doing its own stopping, so a stop is still a stop with its own audit line.

**A refused run is still in the restart notice's count, so the answer to a press is drawn beside the button, never in place of it.** `reopenRestartClosed` refuses per run and only a successful `reopenRun` clears `restart_closed`, so after a press that refused anything the count is still above zero — and `RestartClosed` used to draw its answer only at zero, which put the same notice and the same button back and never showed which runs were refused or why. Some refusals are permanent (a run of a stopped workflow, a run whose work cycles are used up), so each further press met the same refusal with nothing said and `/api/status`'s `restartClosedOutstanding` stayed above zero for good. The decision is `restartClosedView` in `src/lib/`: the answer to the last press is drawn whenever there is one, naming each refused run by its short id, linked to its page, with `reopenRun`'s own sentence — and saying that picking it up or setting it aside there is what takes it out of the count, since pressing again will not. The offer beside it is drawn whenever runs are waiting **unless one of them is a run that press just refused**, because the offer's sentence says they "can resume where they left off" and its button only asks again, which for a permanent refusal is false for ever. Withheld whole rather than drawn for the runs that were not refused, because the press takes no list — it reads `restartClosedRuns` like `/api/status` does — so its button would ask the refused runs again and the sheet's count would under-state what one press may start; the list read straight after a press is exactly what it refused, so the two mix only when a run joins in between, and that run is offered on the next load. A failed press is the same shape: the error is drawn beside the button rather than instead of it, because the button was the only thing that cleared the error, and the list is read again after the failure, because a request that never reached the server may still have been carried out and the count is what the failure message tells the operator to check.
