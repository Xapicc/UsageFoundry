# The prior-read pointer and its holdout

[← run lifecycle index](../run-lifecycle.md)

Read before editing `priorReads.ts`, `priorReadsNotice` or the `priorReads` slot in `nextPrompt`, before changing what an `iteration` event carries, and before analysing the holdout.

**A run's first prompt names the files earlier runs on its repository opened most, on half of all runs, as a fact rather than an instruction.** `priorReadsFor` ranks the main-thread `Read` calls of the 100 most recent earlier runs on the run's repository (`folder_repo`, falling back to `repo_root`), weighted ×0.9 per run back. `priorReadsNotice` then sends the top 20 that still exist in the run's tree. The rule is the one `proposals/ContinuousImprovement/` measured: 45.0% prequential coverage of a new run's opening eight reads, against 42.3% by raw frequency and 39.2% by distinct runs, over 294 runs to 2026-08-21. The re-measure gate in `19-remeasure-2026-10.md` was applied to those figures because no run could read the install's database. The header says *these are the files earlier runs opened most … not an instruction to read any of them*, and it has to: `02-what-already-tries.md` measured `continuedWorkNotice`'s one named command copied by 85% of the runs it reached, while CLAUDE.md's "read this first", in the same message, was declined by 101 of 112. A list worded as a reading assignment is the second kind of sentence, and its files are then paid for on every turn. The text is generated, never a `DEFAULT_*`, so that a Save cannot pin a sentence that describes the list beside it. Each path carries the number of earlier runs behind it.

**Its slot is the last orientation before the task, on the session-less branch only.** It comes after `continuedWorkNotice` and `priorWorkNotice`, which are about work already under the agent, and directly ahead of `o.task`. That is where the proposal measured from, and nowhere after the task, where `COMPLETION_NOTICE` and `NEEDS_REVIEW_NOTICE` must stay last. A resumed conversation already holds the block from the turn that opened it. The ranking is built from runs created before this one, so a restart that loses its session is sent the same list again, and nothing re-sends it per cycle.

**It is resolved once per segment, synchronously, beside `githubTokenFor` and after `ensureWorktree`.** That is the once-per-run class constraint 9 names: the input cannot change while the run works. Nothing is added to `createRun`, so the no-`await` window there is untouched. The query reaches `run_events` through `idx_run_events_run` from the run ids `runs` gives it, not by scanning the table. The 100-run bound is on the query, not on the answer, because at ×0.9 a run 100 back weighs 0.003% of the newest. Every path is proved at use time: it must resolve, by `realpath`, to a regular file inside the run's own root (the checkout, or the repository for a run with isolation off). This is `resolveInMount`'s before-and-after rule, and it buys existence in the same call. A path that is gone, a symlink out of the tree, another checkout's copy, a sub-agent's read and anything with a control character never reaches the prompt. The candidate that fails loses its place rather than leaving a hole.

**Who is never considered, so is in neither arm.** A folder not in a repository has no "this repository" to have history, and every such folder shares one bucket. A Codex or local-model run is excluded because the measurement and the arms are Claude Code's. Codex reads through shell commands the log does not record as a `Read`, so its compliance could not be scored. A local model is a different reader whose runs would add variance to both arms. Dreaming's writer (`origin_ref` `dreaming:…`) is excluded because its task, folder and corpus are fixed by the feature, and a list of what earlier writer runs opened is a nudge toward re-reading notes it is meant to judge afresh. A run with no earlier reads on its repository *is* considered and gets its arm, with nothing to show. Recording it keeps the arms' populations the same when they are read back.

**The arm is `inHoldout(runId)`, a function of the id and nothing else, and it must never change.** It is the first 32 bits of SHA-256 over `prior-read-pointer:<id>`, held out below 2³¹. `runs.id` is a random UUID, so half of all runs are held out. The arm is the same on every cycle, after a restart, after a pick-up and in any query later, which is why no column records it. The experiment name is in the preimage so that a second experiment on the same ids draws a different split; two on bare ids would put the same runs in the same arm of both, confounded for good. Changing the name or the hash re-deals the arm of every run already logged, which is what `priorReads.test.ts`'s four pinned ids exist to catch. The arm is decided before anything about the run's history is known. Whether there was anything to show is recorded beside it and never decides it.

**Every session-less cycle the pointer considered records `priorReads: { arm, paths }` on its `iteration` event, in both arms.** `paths` is how many files the block named, or would have named. The arm is recomputable for ever. Whether there was anything to show is not, once the logs it was ranked from are swept at `eventRetentionDays`. The treated arm's prompt carries the block itself, which the run page's *Prompt* fold shows. The held-out arm's cycle row says the list was held back whenever there was one to hold, so two runs on one repository do not read as one simply having had a shorter prompt. Reading the arms back — compliance, displacement and outcome, as `17-implementation-sketch.md`'s Phase 4 separates them — is not built. It needs about a fortnight of runs, and `03-experiment-holdout.md` sizes it.

**There is no setting.** The holdout is the off switch for half the install, and a toggle would be a third arm nobody randomised. Turning it off means reverting the commit that added it. If one is ever added, it goes through all four doors of constraint 1: the interface member, `DEFAULTS`, `SETTINGS_KEYS` and the `PUT /api/settings` arm.
