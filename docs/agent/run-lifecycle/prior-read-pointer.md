# The prior-read pointer and its holdout

[← run lifecycle index](../run-lifecycle.md)

Read before editing `priorReads.ts`, `holdoutExport.ts`, `priorReadsNotice` or the `priorReads` slot in `nextPrompt`, before changing what an `iteration` event carries, and before analysing the holdout.

**A run's first prompt names the files earlier runs on its repository opened most, on half of all runs, as a fact rather than an instruction.** `priorReadRanking` ranks the main-thread `Read` calls of the 100 most recent earlier runs on the run's repository (`folder_repo`, falling back to `repo_root`), weighted ×0.9 per run back, and `priorReadsNotice` sends the top 20 that still exist in the run's tree — from **a ranking fixed per repository** (below), not one built per run. The rule is the one `proposals/ContinuousImprovement/` measured: 45.0% prequential coverage of a new run's opening eight reads, against 42.3% by raw frequency and 39.2% by distinct runs, over 294 runs to 2026-08-21. The re-measure gate in `19-remeasure-2026-10.md` was applied to those figures because no run could read the install's database. The header says *these are the files earlier runs opened most … not an instruction to read any of them*, and it has to: `02-what-already-tries.md` measured `continuedWorkNotice`'s one named command copied by 85% of the runs it reached, while CLAUDE.md's "read this first", in the same message, was declined by 101 of 112. A list worded as a reading assignment is the second kind of sentence, and its files are then paid for on every turn. The text is generated, never a `DEFAULT_*`, so that a Save cannot pin a sentence that describes the list beside it. Each path carries the number of earlier runs behind it.

**Its slot is the last orientation before the task, on the session-less branch only.** It comes after `continuedWorkNotice` and `priorWorkNotice`, which are about work already under the agent, and directly ahead of `o.task`. That is where the proposal measured from, and nowhere after the task, where `COMPLETION_NOTICE` and `NEEDS_REVIEW_NOTICE` must stay last. A resumed conversation already holds the block from the turn that opened it. The ranking is built from runs created before this one, so a restart that loses its session is sent the same list again, and nothing re-sends it per cycle.

**The list is one object per repository, taken once, and no pointer's reads are in it (2026-10-31).** Until then each run's list was ranked afresh from the last hundred runs, which included the reads of runs the pointer had shaped, so an effect on one run leaked into the next run's treatment and "the treatment" was a different list per run with a hundred-run memory. `snapshotFor` ranks a repository's top 60 the first time a run on it asks, from reads no pointer reached — runs created before `PRIOR_READS_SHIPPED_AT`, and runs recorded in the holdout arm — stores it in `prior_read_snapshots` with the instant it was taken, and every later run in both arms is shown the first 20 of it that still exist. The existence filter is the only thing that varies it. A repository with fewer than `SNAPSHOT_MIN_RUNS` runs of such reads has no snapshot yet and shows nothing in either arm (`treatment: "snapshot-pending"`); nothing is written, and the next run asks again, so a poor list is never frozen for the whole experiment. What it costs is freshness: a file a repository stops touching stays until the filter retires it. The other design — ranking from holdout-arm reads alone — was passed over because it keeps the hundred-run memory in the treatment. Changing `SNAPSHOT_ENTRIES`, the untreated test or deleting rows from `prior_read_snapshots` is a change to the treatment, and a run's `treatment` field is how a read-back tells the two periods apart.

**It is resolved once per segment, synchronously, beside `githubTokenFor` and after `ensureWorktree`.** That is the once-per-run class constraint 9 names: the input cannot change while the run works. Nothing is added to `createRun`, so the no-`await` window there is untouched. The query reaches `run_events` through `idx_run_events_run` from the run ids `runs` gives it, not by scanning the table. The 100-run bound is on the query, not on the answer, because at ×0.9 a run 100 back weighs 0.003% of the newest. Every path is proved at use time: it must resolve, by `realpath`, to a regular file inside the run's own root (the checkout, or the repository for a run with isolation off). This is `resolveInMount`'s before-and-after rule, and it buys existence in the same call. A path that is gone, a symlink out of the tree, another checkout's copy, a sub-agent's read and anything with a control character never reaches the prompt. The candidate that fails loses its place rather than leaving a hole.

**Who is never considered, so is in neither arm.** A folder not in a repository has no "this repository" to have history, and every such folder shares one bucket. A Codex or local-model run is excluded because the measurement and the arms are Claude Code's. Codex reads through shell commands the log does not record as a `Read`, so its compliance could not be scored. A local model is a different reader whose runs would add variance to both arms. Dreaming's writer (`origin_ref` `dreaming:…`) is excluded because its task, folder and corpus are fixed by the feature, and a list of what earlier writer runs opened is a nudge toward re-reading notes it is meant to judge afresh. A run with no earlier reads on its repository *is* considered and gets its arm, with nothing to show. Recording it keeps the arms' populations the same when they are read back.

**The arm is `inHoldout(id)` of the run's own id, or of its chain, and `inHoldout` must never change.** It is the first 32 bits of SHA-256 over `prior-read-pointer:<id>`, held out below 2³¹. `runs.id` is a random UUID, so half of all runs are held out. **A run that continues another (`continues_run`) is dealt its parent's arm instead (2026-10-31)** — `holdoutArmFor` takes the nearest ancestor that recorded an arm, an `iteration` event or an exported row logged `priorReads.arm`, and only if none did the arm the chain's head would draw — because a continuation carries on the parent's branch and work, and dealt by its own id it put one piece of work in both arms. A recorded arm wins over a re-derived one so that a chain straddling the change stays coherent, and the event records `basis`, `id` or `parent`. A run before that change was dealt by its own id and its event says nothing, which the export reads as `id`. The vault pointer's arm is still each run's own. The experiment name is in the preimage so that a second experiment on the same ids draws a different split; two on bare ids would put the same runs in the same arm of both, confounded for good. Changing the name or the hash re-deals the arm of every run already logged, which is what `priorReads.test.ts`'s four pinned ids exist to catch. The arm is decided before anything about the run's history is known. Whether there was anything to show is recorded beside it and never decides it.

**Every session-less cycle the pointer considered records `priorReads: { arm, paths, files, basis, treatment }` on its `iteration` event, in both arms.** `paths` is how many files the block named, or would have named, and stays a count so that a row from before the list was logged reads the same way; `files` is the list, `[{path, runs}]` (2026-10-31). The arm is recomputable for ever. Whether there was anything to show is not, once the logs it was ranked from are swept at `eventRetentionDays`. The treated arm's prompt carries the block itself, which the run page's *Prompt* fold shows. The held-out arm's cycle row says the list was held back whenever there was one to hold, so two runs on one repository do not read as one simply having had a shorter prompt. Reading the arms back — compliance, displacement and outcome, as `17-implementation-sketch.md`'s Phase 4 separates them — is built (below), and **its evidence is kept (2026-10-31)**: `holdoutExport.ts` copies it to `holdout_runs`, `holdout_cycles` and `holdout_tool_events` ahead of every event sweep (`retention/tables.md`), with each run's arm and whether it was logged or derived, the hundred preceding and the overlapping runs with their arms, `runs.live_siblings` (the runs `running` on the repository when it started, written once by `recordLiveSiblings`), every call that names a file, and the paths its prompt named with the pointer's block kept apart from the brief's. The list a run was held back from is `holdout_runs.prior_read_ranking`, `logged` for a run started since the list was logged and `recomputed` — from the events that survive, without the existence filter — for one before. The compliance join in `03-experiment-holdout.md` is reproduced over these tables for both arms by `holdoutExport.test.ts`.

**The holdout is read back from the export tables, as three questions that share no figure (2026-11-08).** `holdoutReadback.ts` serves `/api/holdout-readback` and the *Does the prior-read pointer change what runs do* band, which is on `/usage` (it was on the dashboard until the analysis regions moved there, also on 2026-11-08). It reads `holdout_runs`, `holdout_cycles` and `holdout_tool_events`, never `run_events`, so it answers the same after the sweep; and `runs.ending_code`, which the export does not copy and a permanent row has no sweep to lose. *Compliance* scores each (cycle, listed path) pair in both arms by one rule — a call on that path at or after the cycle began, any thread, `03-experiment-holdout.md`'s — over the list the cycle logged: the block the pointer arm was sent and the list the held-out arm was withheld. A file the task's own brief also names is set aside in both arms, since a run opens it whatever any list said, and the error is taken over runs because a run's pairs move together. A held-out cycle whose list was not logged is counted and left out, never rebuilt, so one arm is not scored against an exact list and the other against a guess. *Displacement* is distinct main-thread `Read` paths before the first main-thread edit and in the whole run. It is deliberately not `03`'s count of paths the prompt never named, which falls by construction in the arm whose prompt names twenty more. *Outcome* is the share reaching a second cycle, the `ending_code` counts and `runs.spent_usd`, the one spend source, named on the card and never added to a transcript or telemetry reading. **A run is read only when** its arm was logged, its list was one of the fixed snapshots, it does not continue another run (a chain is one draw, not several), it is settled, and a cycle's list held a file. Every other considered run is counted under the first of those reasons that applies, per arm, so a difference in what each arm lost shows. The earlier rolling list is a different treatment and is not read. Each section says how many each arm needs, from `03`'s table, before a difference is significant; the intervals are normal-approximation and unadjusted, except the primary's (next paragraph). The plan's covariate-adjusted regression is not computed; its other three parts are. Nothing here is a guard.

**The plan's primary, interference check and two looks are computed beside those, by `holdoutInference.ts` (2026-11-08).** Pure and deterministic, so one set of export rows is always one set of figures and a reload is never a fresh draw. *The primary* is the whole-run main-thread `Read` count, **stratified by repository**: each repository weighted by its share of the runs, variance `sum w² (v1/n1 + v0/n0)`, which is Lin's estimator with the repository dummy as the only covariate. A repository where either arm holds fewer than two runs has no variance and is set aside and counted. This is the plan's first honest version and **not its pre-registered primary**: the treatment-by-covariate interactions with HC2 errors, and the repository's pre-period mean, prompt length, `max_iterations`, model and `continues_run`, are not built, because the plan's own simulation puts their gain at a factor of 0.83 to 0.88 only at a raw correlation near 0.3 to 0.4, and that correlation is unmeasured here. Its p-value is a two-sided *studentised* permutation test that re-deals arms within each repository, exact when there are 20,000 assignments or fewer and otherwise 4,000 seeded draws, `(1 + at least as extreme) / (1 + draws)`. *The two looks* are the plan's O'Brien-Fleming boundaries, `z` of 2.797 then 1.977 on the stratified `z`, at half and all of `PLANNED_RUNS_PER_ARM` (410, the plan's thirty-day row, a fall of about 26% in files read). They are counts of runs read, not dates, because the read population (settled, fixed list, not a continuation, a list to name) arrives slower than the fleet the plan counted; 410 is a number to change before a look is taken, never after one. **A look is the data as it stood when the smaller arm first held that many runs**, ordered by `finished_at` (else `finalized_at`), so loading the card again is not another look and runs that settle later are the descriptive "to date" line. A boundary crossed at the interim ends the test there. *The interference check* regresses each held-out run's whole-run reading on the treated share of its neighbours whose arm is known, for three definitions of neighbour: the hundred preceding runs (`preceding_runs`), the overlapping ones (`overlapping_runs`) and the ones live at its start (`live_siblings`, null before 2026-10-31 and then counted as not recorded, never as none). Both sides are centred by repository, the interval is HC2, and the p-value is the conditional randomisation test: every neighbour re-dealt 400 times by the real `inHoldout` on the id `<replicate>:<id>`, held-out readings held fixed. The re-deal gives a continuation's neighbour its own id's arm, not its parent's, and the treated share of a hundred runs hardly varies (the card prints how little), so a wide interval is the absence of evidence and is labelled so. The 400 draws are the readback's cost, about 0.6 s of hashing at fifteen hundred runs on a repository. Not computed: the covariate-adjusted regression, the plan's secondary estimands (ratio of totals, log ratio, trimmed difference, the two-part split), the rolling-list period (a different treatment, and an operator decision whether to read it as its own), and the compliance target's re-pricing (`complianceOf` sets the brief's pairs aside, so the 62.3% baseline it was sized for is wrong until the first reading gives the held-out share).

**There is no setting.** The holdout is the off switch for half the install, and a toggle would be a third arm nobody randomised. Turning it off means reverting the commit that added it. If one is ever added, it goes through all four doors of constraint 1: the interface member, `DEFAULTS`, `SETTINGS_KEYS` and the `PUT /api/settings` arm.
