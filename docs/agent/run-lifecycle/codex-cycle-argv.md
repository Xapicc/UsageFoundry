# What a Codex cycle's argv carries

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `codexWritableRoots` in `src/lib/orchestrator.ts`, or the network and reasoning-effort arguments `buildCodexArgs` adds in `src/lib/cycleInvocation.ts` (`settings.codexNetworkAccess`, `settings.codexRunEffort`, `CODEX_PERMISSIONS`). The rest of what a cycle's argv carries is [cycle-argv-and-notices.md](cycle-argv-and-notices.md). What a Codex cycle loads from its checkout's `.codex/config.toml`, and why that turns on `--ignore-user-config` and the cycle's trust write, is [../security/cycle-settings-env.md](../security/cycle-settings-env.md).

**A Codex cycle is handed the run's write set in the shape Codex's sandbox can build, and none of Claude Code's sandbox preparation.** Measured on the first real Codex run (2026-10-07, `docs/verification/other-providers.md`): Codex's bwrap makes `.git`, `.agents` and `.codex` mount points inside every write root, so a single root the agent uid cannot create entries in fails *every* command of the cycle — `STACKS_STATE_DIR` is root-owned by design and the run could not write a file. `codexWritableRoots` (`orchestrator.ts`) therefore reshapes three entries of `sandboxSettings`' set and never adds one: the stack directories the agent owns stand in for the root-owned directory holding them (`agentWritableStackStateDirs`, `lstat` on a named volume, where a root stat is trustworthy — unlike a bind mount, which a VM layer may present as owned by whoever asks); `CLAUDE_CONFIG_DIR` is dropped, since it is in every set only because Claude Code writes the metered transcripts there, and handed to Codex it was write access to the operator's own `~/.claude`; and the temporary directory is dropped because Codex grants `/tmp` and `$TMPDIR` itself. It is read **whether or not the install has a managed sandbox**, unlike `sandboxWritableRoots`, because Codex is never unconfined under `workspace-write`: on a stock install a null left a Codex cycle without its build caches or, isolated, the repository `.git` it is told to commit into. **The vault is not on a Codex argv at all.** For Claude `--add-dir` is what makes the vault skill's path readable and write is its price; for Codex every sandbox mode already reads the whole filesystem and no skill reaches the cycle, so the flag granted write and nothing else. **`ensureSandboxMountPoints` is skipped for a Codex cycle** — its names are the paths Claude Code's sandbox overmounts, and run against a write set that is all `--add-dir` it planted a `.claude/` of twelve empty files in six trees, `~/.claude` and `/tmp` among them. And the last-message directory is handed to the agent uid on every cycle, through an `O_NOFOLLOW` descriptor because it sits in a home the agent owns and a root `chown` must not follow a link planted there. What is left: a SIGKILLed cycle leaves the three mount points behind, empty, in its roots and in `/tmp` (SIGTERM cleans them), and none of this has yet run inside a real `codex exec` — it is measured through `codex sandbox --sandbox-state-json` with the recorded profile.

**A Codex cycle's commands are offline unless the operator opened the network, and only `acceptEdits` can be opened.** Codex's `workspace-write` sandbox — `acceptEdits`' row in `CODEX_PERMISSIONS` — blocks the network for every command the agent runs, which a Claude cycle in the same mode does not: measured on 0.153.4, `curl https://example.com` failed in a cycle and answered 200 with `-c sandbox_workspace_write.network_access=true`. `settings.codexNetworkAccess` adds that override, read per cycle, on the `acceptEdits` row alone — `plan` and `default` are read-only and stay offline, `bypassPermissions` has no sandbox, and a Claude argv never carries the key. It is off by default because it is a widening, the one direction the table refuses to take on its own: an agent with the network can push, publish or send a file away. The run form says so beside a Codex run started without it, since a run that cannot install a package fails at a step that reads like the model's mistake. Codex's own connections — to OpenAI and to this app's taskboard — are not commands and work either way.

**A Codex cycle's reasoning effort is its own install-wide setting, on its own scale.** `settings.codexRunEffort` becomes `-c model_reasoning_effort` ahead of `resume`, on `runEffort`'s terms — no proposal, template, agent or node carries it, so the orchestrator chat cannot move it — but as a separate field, because Codex's scale runs to `ultra` ("automatic task delegation", so possibly sub-agents) and each CLI's level is a value the other does not take: `buildCodexArgs` reads only `codexEffort` and `buildArgs` only `effort`. Null leaves each model on its own default, which differs per model (`gpt-6-astra` low, `gpt-5.5` xhigh on the measured account), so setting one level is a per-model change of price. A level a model does not list is passed anyway: measured on 0.153.4, `ultra` on `gpt-5.6-luna`, which lists no `ultra`, completed and the session recorded `ultra`.
