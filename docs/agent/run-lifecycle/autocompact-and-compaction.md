# What replaced `--autocompact`, and compaction notices

[← run-lifecycle index](../run-lifecycle.md)

Read before editing where `src/lib/contextPruning.ts` stands in for `--autocompact`, the context flags `buildArgs` passes in `src/lib/cycleInvocation.ts`, or `readCompactions` in `src/lib/transcripts.ts` and `compactionNotice` in `src/lib/orchestrator.ts`.

**`--autocompact` is gone, and `contextPruning.ts` is what replaced it.** The flag was a ceiling rather than a guard — no `BudgetVerdict`, absent from `LIVE_ENFORCEABLE_CODES`, `RUN_ENFORCEABLE_CODES` and `evaluateBudget`'s check order — and it was the only reason any conversation here compacted at all. It no longer rides the argv. `buildArgs` emits nothing in its place and `orchestrator.test.ts` asserts the absence, because a reinstated flag fails nothing and looks like an ordinary cycle. It stays in `ARGV_ARITY` and `CARRIES_NO_CONTEXT`: those two say how to *read* an argv, and every cycle spawned before the change stored one carrying the flag, so dropping it there would make those rows report an unclassified flag and a stray `200000`.

**What the removal gave up is measured, and it is the strongest measurement in this repository.** The flag did not lower a threshold the CLI already had. This install's model resolves a window near 1M and the CLI **refuses** auto-compaction for such a model, so before it 604 container sessions — 246 of them past 167,000 tokens, one request reaching 752,172 — produced zero compactions. And it fired at `min(asked, window) − min(maxOutput, 20,000) − **13,000**`, so `--autocompact 200000` compacted at 167,000 rather than the 180,000 `effectiveWindow` alone suggests. Between the two arms of a natural experiment over 1,147 transcripts split at the commit that added it, turns past the cap cost **0.45× per turn and 0.50× per 1,000 output tokens**. That figure is now a cost of the swap rather than a reason for the flag, and `docs/verification.md` carries it under both headings so a later reading can tell a decision from a regression.

**The two mechanisms are not the same operation, which is the case for the swap.** Compaction replaced the conversation with a model-written summary: much smaller afterwards, and the detail is gone, so the agent re-derives what it had just worked out. A prune removes tool output and keeps the conversation, so it shrinks less and forgets less. It is also no longer true that nothing resets a prefix — a boundary prune does, at the one moment it is free.

**Never run both.** The CLI would summarise a conversation moments before this app ended the cycle to prune it: the prune would then be measuring what the summariser had already discarded, and the run pays for both.

**Every failure on this path is a log line and nothing else.** A missing tool, an unreadable transcript, a non-zero winnow — none of them is a reason to end a run that is otherwise fine. The one thing that must not happen quietly is nothing at all: this is what bounds a cycle now, so a prune that could not run says so in the pane the operator is watching.

**When a compaction happens the run says what it took, and it says it from the vendor's table rather than from anything measured here.** The loop reads the transcript for `compact_boundary` records after every cycle — `readCompactions`, bounded by session id **and** by the cycle's own clock, because a resumed session copies earlier records forward carrying their original timestamps and a reader bounded by id alone re-reports every earlier compaction at the end of every later cycle. It sits after `runIteration` has returned and after the row UPDATE: the child has exited so the transcript is flushed, an interrupted cycle still reports, and `interrupts` is read afterwards so an interrupt landing during the read is not lost. Its own failure is caught and logged rather than allowed to end a cycle that has already been paid for. What the notice says about *survival* is `injectionFates`, and it is derived from the cycle's own argv rather than from a list of what this app injects — a cycle spawned without plugins reports no skills, one spawned with three plugin directories reports three, and a flag this function has never been taught reports itself `unclassified` rather than dropping out, which `orchestrator.test.ts` pins by running the widest real `buildArgs` output through it and asserting zero such rows. So the next flag added to `buildArgs` fails a test instead of silently leaving the record short. The table itself is Anthropic's documentation self-pinned to CLI `2.1.198` and this install pins `2.1.226`, so `compactionNotice` compares the boundary record's own `version` against `SURVIVAL_TABLE_CLI_VERSION` and words every line as a hypothesis whenever they differ — which is today always. That is a mechanism rather than copy discipline, on purpose: a note that reads as measured behaviour of this install is the one way this feature can lie. **It observes and never acts.** No `--autocompact` change, no `DISABLE_AUTO_COMPACT`, no threshold and no `context_management` block: those are the options `proposals/ContextControl/17-recommendation.md` rejects by name, and none of them is in scope for a record of what already happened. Nor does anything here read, summarise or judge the conversation — the boundary record and the argv are the whole of its input.
