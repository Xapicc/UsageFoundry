# The live context ceiling

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `ceilingCut` or `planCut` in `src/lib/contextPruning.ts`, or `contextWatches`, `liveGuardTick`'s ceiling check and the `prune` interrupt in `src/lib/orchestrator.ts`.

**The ceiling asks the engine that would do the cutting, and asking the other one silenced the feature for two days.** `ceilingCut` resolves `contextPruningEngine` to a measurement: `winnow plan --tier CB` under the fork engine, a `treat -rx <strictness>` **dry run** under the in-place one. Before it, the ceiling asked `planCut` whichever engine was configured — and `plan` runs SPEC §4's rules at tier CB, which is the fork engine's classifier and not the in-place pruner's twenty inherited strategies. On the two transcripts this install declined on 2026-08-28, CB stripped 9 of 183 and 13 of 172 tool results (2.2% and 7.1% of the file) where `treat -rx aggressive` strips every one of them and frees 49% and 53%. So the gate refused every crossing on a figure five to twenty times smaller than the cut it was refusing, `prune_receipts` stood empty from 2026-08-26, and the pane repeated "a cut would remove 8.0k tokens" every few minutes. `planCut`'s own docblock names this failure about `break_even_turns`; reading its `netBytes` instead was the same error under a different field name, so the pairing is structural now — there is no way to reach a measurement except through the function that resolves the engine. The dry run is the inherited CLI's **default**, `--execute` being the opt-in, and that matters here because this runs against a session a live Claude process is holding: `orchestrator_safe.refusal_for` would not catch a mutating argv, since it looks for a Claude *above itself* in the process tree and in this container the walk stops at `next-server`.

**A `treat` dry run is read in bytes and converted as a share, never through `BYTES_PER_TOKEN`.** Two traps, both silent. Its token column does not move — orchestrator-safe mode excludes `metadata-strip`, so the `usage` frames survive and winnow's exact count re-anchors on the same turn, printing "Saved 0 tokens (0.0%)" for a cut that halves the file; a parser taking the first number on that line prices every legacy cut at nothing. And the byte column is *transcript* bytes: session `02584a86` was 3.83 MB against an API context of 258.3k tokens — 14.8 bytes a token, four times `BYTES_PER_TOKEN` — because the file holds JSON envelopes, thinking blocks with signatures, and tool results the intake filter already dropped on the wire. Read at 3.6 that dry run's 1.79 MB came to 521k tokens "removed" from a 258k-token conversation, so `apiContextNow − D` floored at zero and every cut priced at 0 turns: prune always. `treatRemovedTokens` takes the share instead — this fraction of the file, so assume this fraction of the prompt — which cancels the units and makes `D ≤ apiContextNow` hold by construction. `planCut`'s figure is **not** converted that way and that is not an inconsistency: CB selects recent large results still standing in the prompt (`keep_last: 6`, `min_bytes: 2048`, an intervening-read test), and its overlap with what the intake filter already dropped is bounded and measured at 4.06%. What is still wrong with the share is named rather than absorbed: it is taken against the whole prompt, ~55k of which is a system prompt and tool list no prune reaches, so it over-claims by about a quarter and leans **permissive** — on `docs/verification.md`'s not-verified list, and `resumeControl` is the machinery that would settle it.

**The ceiling has its own watch map, not `liveGuards`.** That map is registered only when `enforcement` is not `between-cycles`, which is an opt-in about *budgets*; the flag this replaced rode every cycle of every run. `contextWatches` is registered unconditionally beside the spawn, on its own `globalThis` key, and `liveGuardTick` checks it before the budget scan. The check reads the transcript and parses backwards from its end to the first `usage` frame. It used to `stat` the file first and skip anything smaller than the ceiling's worth of bytes, which was sound one-sided while the measure was `contextTokens` — message content is a subset of the file. It stopped being sound when the measure became `apiContextTokens`: the prompt carries ~55,000 tokens of system prompt, tool list and project instructions that are in no transcript, so a file under the gate can be a cycle over the ceiling, and what that hides is a run that is never ended and never pruned. The gate is gone; `CYCLE_CONTEXT_CEILING_TOKENS` is 200,000 since 2026-08-25 — raised to 300,000 and lowered again on that same day, because at 300,000 the extra prompt carried on every turn at the cache-read rate read as cost with no return — and the constant carries why it moved off the 167,000 the removed flag fired at.

**A `prune` interrupt is the one kind that does not end the run**, and the loop's post-cycle checkpoint tests for it before `applyInterrupt` — which has no status meaning "carry on" and would file the run as `stopped`. It is ordered ahead of the exit-code and refusal tests for the general interrupt check's reason: the child was killed, so it closed with a null code and reported no `result`. The cycle it ended is **refunded**, because a compaction never cost a work cycle and a crossing that consumed one would quietly change what `maxIterations` buys — bounded by `MAX_EARLY_ENDS_PER_RUN`, or a run whose every cycle crossed the ceiling would loop forever, always ending, always refunded, never finishing. Past the cap the crossing still prunes and simply counts.
