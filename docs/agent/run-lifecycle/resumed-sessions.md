# Resumed sessions

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `adoptSession` or `looksLikeResumeFailure` in `src/lib/orchestrator.ts`, `cycleDidNoWork` or `startsFresh` in `src/lib/cycleInvocation.ts`, or `resolveSessionTranscript` or `sessionTranscriptPresence` in `src/lib/transcripts.ts`. Split out of `reopen-and-resume.md` on 2026-10-25; reopening a finished run and the pick-up that follows it are there.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && cycleDidNoWork(res)`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind". `cycleDidNoWork` is no result and no text, **or an error `result` with `num_turns: 0`**, and the second is the shape the pinned CLI refuses a `--resume` in — measured — which `!sawResult` alone read as a cycle that worked and then failed, so no refusal ever reached the retry or the stop reason naming the CLI's hand-resume command (`exitStopReason`: `claude --resume <id>`, `codex resume <id>` for a Codex run). The fork settlement and `forkWouldNotResume` take the same function, because a settlement that called a refused fork resumed leaves the rollback nothing to roll back. A session a kill truncated mid-turn, which this branch was written for, is not refused at all: the pinned CLI pairs the dangling `tool_use` with a synthetic interrupted result and resumes (measured against a stub API). It deliberately does **not** also require `pause_count > 0` — a resume is refused or not whether a guard parked the run or a crash ended it, and a run picked up by hand after a crash may never have parked at all — a pick-up neither adds to `pause_count` nor clears it — so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for — and it is handed the message the refused attempt was, above.

**A session whose transcript is gone is restarted before the cycle, not discovered by failing one.** The pinned CLI deletes its own transcripts 30 days after they were last written (`cleanupPeriodDays`, measured on its default), and nothing here sets that or hears about it; `sweepTranscripts` clears `session_id` before it unlinks a file of its own, but a file the CLI removed first is never listed by it. A run picked up on such a session put `--resume` on the argv, and the CLI answered with a `result` event (`error_during_execution`, *No conversation found with session ID*) and exit 1 without calling the API — measured, and not the shape the paragraph above retried until `cycleDidNoWork` learned it, because a result arrived. So the cycle was charged and the run ended `failed` on a bare exit code that named neither the session nor the reason, on every pick-up, since nothing on the row changed. So `startRun` asks `sessionTranscriptPresence` before the first spawn of a segment, and on `absent` clears the session through `adoptSession(null)`, the move `startsFresh` already makes: the cycle opens with the task — under `priorWorkNotice` once the run has been charged for a cycle — carries no `--resume`, and spends no failing cycle and no retry. Only `absent` acts, and it is narrower than `resolveSessionTranscript`'s null: two files under one id are a conversation the CLI can still resume, an unreadable directory may hold the file, and a tree with no transcripts at all is a fresh install or a `CLAUDE_HOME` that is not where the CLI writes — each answers `unknown` and resumes as before. That is also why it masks neither a wrong working directory nor an expired credential: both leave the file where it was, so both still reach the resume and end as they did, a refusal now through the retry and the stop reason above — and the pinned CLI was measured finding a transcript from a working directory other than the one that wrote it. It skips a carried fork, whose failed resume returns to the conversation it was cut from, and every run whose sessions are not Claude Code transcripts under `PROJECTS_DIR` — Codex, and `local`, whose CLI writes under its own config directory. It sits above the pre-spawn interrupt re-check because it awaits a walk, and a Stop pressed during that walk must still win. **The follow-up a pick-up resolved is re-decided with it.** `reopenRun` resolves its message at the door against a session it cannot check without an `await` its one-turn checkout check may not take, so `runs.follow_up_is_note` records whether `follow_up` is the operator's own note. A note survives the restart and is appended to the task, as on any pick-up without a session; text this app wrote for the conversation — the DONE pushback, the restart and needs-review notices, a stack resume — is dropped from the loop and from the row, because it describes a conversation that is gone. Every writer of `follow_up` writes the flag beside it, and rows written before the column read as app text. The pick-up's own status line still says it continues the session, because it is written before anybody looks; the run's log says what happened instead. `resumeMissingTranscript.test.ts` pins it.
