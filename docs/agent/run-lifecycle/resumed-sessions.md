# Resumed sessions

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `adoptSession`, `looksLikeResumeFailure`, `exitStopReason` or the `type === "result"` branch of `handleStreamLine` in `src/lib/orchestrator.ts`, `cycleDidNoWork`, `startupFailureSentence`, `refusedWithoutApiCall` or `startsFresh` in `src/lib/cycleInvocation.ts`, or `resolveSessionTranscript` or `sessionTranscriptPresence` in `src/lib/transcripts.ts`. Split out of `reopen-and-resume.md` on 2026-10-25; reopening a finished run and the pick-up that follows it are there.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && cycleDidNoWork(res)`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind" — and, since 2026-11-08, not a cycle the CLI refused to *start*, which is asked first (below). `cycleDidNoWork` is no result and no text, **or an error `result` with `num_turns: 0`**, and the second is the shape the pinned CLI refuses a `--resume` in — measured — which `!sawResult` alone read as a cycle that worked and then failed, so no refusal ever reached the retry or the stop reason naming the CLI's hand-resume command (`exitStopReason`: `claude --resume <id>`, `codex resume <id>` for a Codex run), which since 2026-11-09 is followed by the CLI's own sentence off the result's `errors` (the `errorText` paragraph below). The fork settlement and `forkWouldNotResume` take the same function, because a settlement that called a refused fork resumed leaves the rollback nothing to roll back. A session a kill truncated mid-turn, which this branch was written for, is not refused at all: the pinned CLI pairs the dangling `tool_use` with a synthetic interrupted result and resumes (measured against a stub API). It deliberately does **not** also require `pause_count > 0` — a resume is refused or not whether a guard parked the run or a crash ended it, and a run picked up by hand after a crash may never have parked at all — a pick-up neither adds to `pause_count` nor clears it — so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for — and it is handed the message the refused attempt was, above.

**A session whose transcript is gone is restarted before the cycle, not discovered by failing one.** The pinned CLI deletes its own transcripts 30 days after they were last written (`cleanupPeriodDays`, measured on its default), and nothing here sets that or hears about it; `sweepTranscripts` clears `session_id` before it unlinks a file of its own, but a file the CLI removed first is never listed by it. A run picked up on such a session put `--resume` on the argv, and the CLI answered with a `result` event (`error_during_execution`, *No conversation found with session ID*) and exit 1 without calling the API — measured, and not the shape the paragraph above retried until `cycleDidNoWork` learned it, because a result arrived. So the cycle was charged and the run ended `failed` on a bare exit code that named neither the session nor the reason, on every pick-up, since nothing on the row changed. So `startRun` asks `sessionTranscriptPresence` before the first spawn of a segment, and on `absent` clears the session through `adoptSession(null)`, the move `startsFresh` already makes: the cycle opens with the task — under `priorWorkNotice` once the run has been charged for a cycle — carries no `--resume`, and spends no failing cycle and no retry. Only `absent` acts, and it is narrower than `resolveSessionTranscript`'s null: two files under one id are a conversation the CLI can still resume, an unreadable directory may hold the file, and a tree with no transcripts at all is a fresh install or a `CLAUDE_HOME` that is not where the CLI writes — each answers `unknown` and resumes as before. That is also why it masks neither a wrong working directory nor an expired credential: both leave the file where it was, so both still reach the resume and end as they did, a refusal now through the retry and the stop reason above — and the pinned CLI was measured finding a transcript from a working directory other than the one that wrote it. A file that is there can still be refused: an empty, non-JSON or unreadable transcript (*No conversation found*) and one the model ended (*Claude ended this conversation*) each take the retry and end `resume_failed` above, and since 2026-11-09 the retry's refusal is not charged either (`budgets-and-guards/silence-refunds-and-background-waits.md`). It skips a carried fork, whose failed resume returns to the conversation it was cut from, and every run whose sessions are not Claude Code transcripts under `PROJECTS_DIR` — Codex, and `local`, whose CLI writes under its own config directory. It sits above the pre-spawn interrupt re-check because it awaits a walk, and a Stop pressed during that walk must still win. **The follow-up a pick-up resolved is re-decided with it.** `reopenRun` resolves its message at the door against a session it cannot check without an `await` its one-turn checkout check may not take, so `runs.follow_up_is_note` records whether `follow_up` is the operator's own note. A note survives the restart and is appended to the task, as on any pick-up without a session; text this app wrote for the conversation — the DONE pushback, the restart and needs-review notices, a stack resume — is dropped from the loop and from the row, because it describes a conversation that is gone. Every writer of `follow_up` writes the flag beside it, and rows written before the column read as app text. The pick-up's own status line still says it continues the session, because it is written before anybody looks; the run's log says what happened instead. `resumeMissingTranscript.test.ts` pins it.

**A cycle the CLI refused to start is not a refused resume, and its stderr sentence is the stop reason.** On 2.1.319 a startup failure — a missing or invalid `--mcp-config`, a missing `--settings` — writes nothing to stdout, one sentence to stderr and exits 1 (`docs/verification/run-lifecycle-hooks-and-endings.md`, 2026-11-08). With no result and no text that is `cycleDidNoWork`'s first clause, so on a picked-up run's first cycle the loop retried once and then ended `resume_failed`, sending the operator to `claude --resume <id>` for a session that was fine: the argv failed, it fails identically on the retry, and the hand command does not carry it. `startupFailureSentence` is asked before `cycleDidNoWork` and holds only when all of these do: Claude Code (the shape is unmeasured for Codex, whose resume keeps its retry), a positive exit code (a signal-killed child exits `-1` and has said nothing), no `result`, **no line on stdout at all** (`IterationResult.stdoutLines`, counted before the parser sees a line — no field the parser fills can say "nothing arrived", because an event this build does not recognise leaves them all at their starting values), and something on stderr. The run then ends `exit_code` with `exitStopReason`'s plain form carrying the clipped, flattened sentence in quotes (`Claude Code exited with code 1 and said: “Error: Invalid MCP configuration: MCP config file not found: <path>”.`), is not retried, and does not name `claude --resume`; on any other cycle it was already `exit_code` and now carries the sentence too. **A child that dies with nothing on stderr keeps the retry and the hand command**, because with no sentence to quote a resume that went wrong is still the best account of it. The same condition is why a child that wrote its `init` and then died is not a startup failure whatever stderr says: stderr then holds the agent's own noise. A pick-up that meets the same bad argv ends the same way, once per press, and since 2026-11-09 none of them is a work cycle: nothing reached stdout, which is evidence of no API call because the CLI writes its `init` before its first request (`budgets-and-guards/silence-refunds-and-background-waits.md`). The CLI's own refusal of a resume (`error_during_execution`, zero turns, `errors`) is a `result`, so it never reaches this stderr-only test and keeps its retry and its hand command, and its `errors` sentence after it.

**A startup failure the CLI writes as a `result` is told by `startup_failure_reason`, and the session id on that result is not the run's.** `config_file_invalid`, `org_config_required_unavailable` and `org_config_refused` are written to every stream-json run as a zeroed `error_during_execution` (`num_turns: 0`, `errors` holding the failure, exit 1); only the first has been driven (a `.claude.json` that is not JSON, plan e8). That is the shape `cycleDidNoWork` reads as a refused `--resume`, and it fails every condition above — a result arrived and a line reached stdout — so the picked-up run retried once and ended `resume_failed` at `claude --resume` for a session that was fine, with the file the operator has to repair named only in the sentence after it. `handleStreamLine` reads the field into `IterationResult.startupFailureReason`, and `startupFailureSentence` holds on it alone, whatever the exit code, stdout count or `sawResult` say: the result's own sentence, then stderr's, then the reason's name, and never null, because null would return the cycle to the retry. The run ends `exit_code` and is not retried. **The same result's `session_id` is minted for it** — not the id `--resume` was given, with nothing written under it — so `handleStreamLine` does not announce it to `adoptSession`. Adopted, it replaced the run's real session on the row, and the pick-up after the repair found no transcript under it, cleared the session as a missing one and started the task over; left alone, the repair continues the conversation. It is asked of a Claude run only, as the stderr form is. `cycleEndingSentence.test.ts` pins both, with the captured bytes. This one is not a work cycle either, on the figures it reports (`duration_api_ms` 0, no tokens, no cost) and not otherwise: a result that reports an API call, or none, stays charged.

**A `result` that says `is_error: true` keeps its sentence in `IterationResult.errorText`, which is not `apiError`.** `handleStreamLine` read only the subtype, so a result with `subtype: "success"` and `is_error: true` was a clean result with a text. 2.1.319 refuses a `--resume` whose session holds a deferred tool call (a `PreToolUse` hook returned `defer`) with that shape, `terminal_reason: "tool_deferred_unavailable"` and the sentence *"mcp__… isn't available, so its deferred call didn't run. Reconnect the tool and resume, or resume with a prompt and CLAUDE_CODE_DROP_UNAVAILABLE_DEFERRED_TOOL=1 to drop the call and continue."*; the run ended on `exited with code 1.` with the sentence nowhere on the row. It now ends `exit_code` with that sentence quoted, which names the tool and both ways out. Three decisions in it, each made on purpose. **It does not feed `apiError`**, which `refusalKind` turns into a park, a rate-limit ladder or a refusal ending: a sentence the CLI wrote about itself would be matched against patterns written for the provider's wording, and a tool's output that reads like a rate limit would back the run off and respawn it. The provider's refusals still reach `apiError` through the `<synthetic>` message and a non-success subtype, and the API-key long-context 429 — the same `is_error` shape, `terminal_reason: "api_error"` — still ends `refusal`, measured on a replay of its capture. **It does not set `isError` either**: whether such a result fails the cycle stays the exit code's to say, which is 1 on both shapes measured, and an exit-0 `is_error` result is unmeasured. **It is not retried and not a resume failure**: the result has `num_turns` of the session so far (16 in the capture), so `cycleDidNoWork` is false, and the refusal is deterministic. **What is not done:** nothing stops a pick-up from resuming the same session into the same refusal. The app cannot see an MCP server come back, so any gate would be a guess; the pick-up is the operator's press, it costs one spawn, and the stop reason says what to change first. **It costs no work cycle** (since 2026-11-09): the refusal makes no API call, measured (`duration_api_ms: 0`, usage all zero, `total_cost_usd` equal to the session's total), and a cycle left charged ate the cap one press at a time until the door refused the next ("already used N work cycles"). `refusedWithoutApiCall` hands it back, and it is a spending-guard change, so it holds only when every way the cycle could have bought something is affirmatively absent: `terminal_reason` is exactly `tool_deferred_unavailable`, `duration_api_ms` is *reported* and 0 (an absent figure is not evidence), no tokens were counted, and the cycle's cost did not move. A refusal failing any of them stays charged. It does not touch `worked_refunds`, which counts refunds of cycles that spent, so `ranWorkCycle` still reads this one as a cycle in which nothing happened. Two further options were not taken: a per-pick-up opt-in that sets `CLAUDE_CODE_DROP_UNAVAILABLE_DEFERRED_TOOL=1` (unmeasured, and it would silently bypass a `defer` hook that exists to hold a call for a person's decision), and the refusal's reason on the `result` event so the door could warn (cheap, and changes nothing about cost). Nothing re-enters on its own — `restartClosedRuns` takes only restart-closed rows, and `reopenFleet` takes explicit ids. The deferring cycle itself (`stop_reason: "tool_deferred"`, exit 0, empty text) is also not noticed: the loop's continuation resumes into the session, which runs the call when the server is connected. `cycleEndingSentence.test.ts` pins both.

**A refused resume's sentence is in `errors`, not `result`, and is quoted after the hand command, never in place of it.** The measured refusal of a `--resume` of an unknown id (`error_during_execution`, zero turns, exit 1) has no `result` string, so `errorText` stayed null and the stop reason named the command and not why; the CLI's sentence was on the run's log under `stream: stderr` alone. `errors` is `z.array(z.string())` on the error variants of the 2.1.319 result schema (`error_during_execution`, `error_max_turns`, `error_max_budget_usd`, `error_max_structured_output_retries`), read out of the binary, and the success variant carries `result` instead. So `handleStreamLine` takes `errorText` from `result` when it is a string and from `resultErrorsSentence` (the string entries joined with a space) when it is not, on `is_error: true` only, clipped by `clipCliSentence` either way; `exitStopReason` used to drop any sentence on a failed resume, because the command answers a different question, and now appends it as a second sentence, `…pick it up by hand with: claude --resume <id>. Claude Code said: “No conversation found with session ID: <id>”.` The command stays first and whole, because it is what the operator can do. Unmeasured: an `errors` of more than one entry (joined, none lost) and whether the other `error_*` subtypes carry it in practice. `resumeMissingTranscript.test.ts` pins the whole reason; the verification is in `docs/verification/run-lifecycle-cli-output.md`.

**The frames a resumed deferred call writes around its `result` are dropped by name, and only the measured ones.** On a `--resume` of a deferred tool call 2.1.319 writes `command_lifecycle` frames (a `command_uuid`, a `state` of `started`, `completed` or `cancelled`, the session id; `queued`, `discarded` and `refused` are in its schema and were not seen) around each `result`, and in the cycle where the call finally runs it writes the hook's result a second time as a top-level `attachment` whose `attachment.type` is `hook_success`, right after the `system:hook_response` of the same hook. Both fell to `noteUnknownStreamEvent` and filed a vocabulary-moved warning on every such cycle. `handleStreamLine` now returns on `command_lifecycle` as it does on `rate_limit_event`: it carries no cost, no session change and no stop reason that the `result` beside it does not. The `attachment` is dropped only at that one subtype, and because it is a duplicate rather than because the type is noise: `clipHookEvent` bounds a hook event's own `output`, `stdout` and `stderr` and the attachment nests them where it does not look, so storing it would keep a second, unclipped copy of what a chatty hook prints, and reading it would put the app on a union the CLI's own schema calls internal with its "wire shape pending". Every other `attachment` subtype is unmeasured and carries content (an at-mentioned file, a hook that blocked), so it still reaches `noteUnknownStreamEvent`: a deny list wide enough to cover a future subtype loses it silently. The duplicate exists only with `--include-hook-events`, which `buildArgs` passes on every cycle; without it the same cycle wrote the attachment and no `hook_response`. `orchestrator.test.ts` pins both drops, the stored `hook_response`, and an unmeasured subtype still being filed.
