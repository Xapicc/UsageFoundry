# Reopening, pick-ups and resumed sessions

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `reopenRun`, `reopenPrompt`, `reopenFleet` or session adoption in `src/lib/orchestrator.ts`, or `nextPrompt` in `src/lib/cycleInvocation.ts`.

**Reopening a finished run is an operator decision, not a resume.** `reopenRun` (`failed`/`stopped`/`completed`/`needs-review` — `REOPENABLE`) puts a terminal row back in the queue keeping its folder, checkout, branch, session id and spend, so `startRun` continues the same conversation. A row that never started work (no `work_dir`, no session, no counted cycle) goes back to `waiting` instead, whatever it ended as: a run behind a dependency can end `stopped` while it waits or `failed` by its own release without ever being given a workspace, and queued it would work in `work_dir ?? folder`, the operator's own folder, with no checkout and no wait for its dependency. It takes a **budget**, because the usual reason a run needs picking up is that its own limits ended it, and re-queueing under the limits that stopped it just reproduces the stop; the three carried-forward guards (`iterations`, run spend, run tokens) are therefore checked at the door rather than left to the pre-cycle check, which would refuse seconds later with the row already flickering queued → stopped and nothing said about what to change. **A fourth check sits at that door and is not one of the three.** The terminus pair — no cycle cap *and* no time limit — is a fact about the budget rather than about this run, and it used to be refused only in `POST /api/runs/[id]/reopen`. That route is one of the two ways in; the other is `reopenFleet`, which calls this function directly with a budget composed by a sheet that has no time-limit field at all, so one press could queue twenty-five runs with no monotone terminus between them. The refusal now sits at the one door every caller passes and the route keeps its own copy, with the longer explanation a form can show. `evaluateBudget` does refuse the pair again as `no_terminus`, but only once the row has flickered queued → blocked with nothing said about what to change, which is exactly the seconds-later refusal the three above are here to avoid. `started_at` is **cleared**, and that is the one deliberate divergence from a pause: a parked run keeps its original start, and closes the park it is leaving into `runs.paused_ms` so the time already worked survives the wait, while a run picked up by hand days later would otherwise be refused by its own time limit before it spawned. `paused_ms` is cleared in the same statement and may never be separated from it — it is a correction to the span since `started_at`, so carried across a reset it would hand the picked-up run hours of credit against a cap it has not spent a minute of. `refusal_pauses` is zeroed in that statement too and `pause_count` deliberately is not — the first is the refusal allowance a run ended `pauses-spent` needs back, the second is what `ensureWorktree` reads as "has worked before"; `parking-and-refusals.md` has both reasons. `permissionMode` is not accepted from the wire — the stored value carries forward, so reopening adds no second route to `--permission-mode`. An isolated run whose slot an active run has since taken is refused by name, because `allocateSlotPath` only avoids slots held by *active* rows and a terminal row is not one. So is one whose branch a holder that is not a run has: a `running` conflict resolution or a merge-queue row at `landing` or `resolving` (`branchHolderRefusal`, read off the tables because `land.ts` imports this module). The cycle a pick-up starts is granted `git add` and `git commit` in the slot a resolution holds mid-merge, and executed against a row held at `landing` the run went `running` in it.

**A reopened run carries one message, resolved at the door and consumed at the spawn.** `reopenRun` writes the literal first-cycle prompt into `runs.follow_up` — led, when there is no operator note, by the stopped-tasks note if the last cycle left one (`background-work.md`); `nextPrompt` prefers it over the continuation, and the loop clears the column the moment it hands it to a spawn — not after the cycle returns, because a run that parks or is killed from there on has already had it delivered and replaying it would say the same thing twice. **That makes every refusal that can stop a cycle before its child exists belong above the clear**, and above the loop's `iterations += 1` beside it: the working directory's containment check, Codex's process-kill rules, and the local provider's sign-in and its config directory. They used to sit between the clear and the spawn, so a `local` run created while signed out failed with `iterations = 1` and nothing spawned, reopening it with `maxIterations: 1` as its own stop reason says was refused as having used that cycle, and a note it was reopened with was cleared although no child received it — one more cycle and one more note per pick-up. A cycle refused there now charges nothing and leaves `follow_up` and the validator's `pendingPushback` for the cycle that carries them; `parksAndRefunds.test.ts` pins both. Resolving to *text* rather than to a flag is what lets `completed` be reopenable at all: the substitution depends on the status the row is being picked up **from**, which a queued row no longer records. With no operator note, a run whose agent replied `DONE` gets `donePushbackPrompt` — the continuation prompt asks for `DONE` when the work is complete, so replying to a `DONE` with it is the same billed spin `continueAfterDone` already avoids — while `failed`/`stopped` get the continuation as before. **`completed` is not that reply**: it is also what a run that used up `maxIterations` is written as, and `maxIterations` defaults to 1, so keying the substitution on the status told the ordinary interrupted run that it had reported the task complete and then forbade it from starting new work. `runs.reported_done` records what the agent actually said, at the moment the cycle ends and the answer still exists — the stop reasons differ, but they are user-visible prose and not something to parse — and `reopenPrompt` is the one branch that reads it. Rows written before that column read as not-done, which is the cheaper error: a continuation into a finished session buys one billed cycle that says `DONE` again, where the pushback costs the work the run was reopened for. A note with no session to resume into is **appended** to the original task rather than sent alone: the run is starting over, and a reply-shaped note would read as the whole job. `nextPrompt` and `reopenPrompt` are pure and unit-tested for exactly these branches; every one of them is billed.

**A run that asked for a person is picked up by name, never in bulk, and is told what to check first.** `needs-review` joins `REOPENABLE`, or `reopenRun`'s gate answers *"this run is needs-review, so there is nothing here to pick up"*, which is the opposite of what the state is for. `reopenPrompt` then gets a branch of its own, and the reason it needs one is that doing nothing already *looks* right: the pushback tests `completed`, which this row is not, so the run would fall through to the plain continuation — *"Continue working on the task. If it is fully complete and verified, reply with exactly DONE"* — into a conversation whose last turn was the agent reporting a wall, which is the same defect `RESTART_KILLED_NOTICE` was added to fix on this same function. The ordinary reason an operator reopens one of these with no note is that they have cleared the wall, so `NEEDS_REVIEW_PICKUP_NOTICE` asks whether it is still there; it does not quote the reason back, because the branch requires a session and the agent's own words are already the last thing in that conversation. Its position — below `restartKilled`, above the pushback — is **inert today** and written that way on purpose: `restartKilled` holds only for a `failed` row or one whose child the shutdown found running, which the loop's post-cycle checkpoint ends `stopped` before any cycle ending is read, so the two can never both be true, unlike the pushback below it which reads a *column* that survives the ending it described. It is for the next change rather than for this code. Neither bulk pick-up offers one, and only one of them needed a decision: `restartClosedRuns` reads only `failed` and `stopped` rows, the two endings a restart writes — it had no status predicate until 2026-10-06, on the premise that `restart_closed` could never be set on any other row, which was measured false: the shutdown flagged every row it interrupted, including one whose loop went on to an ending of its own — while `reopenFleet` takes the explicit ids the page displayed — so the exclusion lives in the client's own `REOPENABLE` set on the runs page, and `needs-review` is deliberately kept out of it for the argument that keeps `completed` out. A control that acts on twenty-five runs at once must not answer the one ending whose entire content is *a person is being asked to look at this*: pressing it would put an agent that accepts edits back to work, unattended, on a wall nobody has read about, with nothing recording that the question was skipped. That the run's own page still offers Resume is the same split `set_aside_at` already makes — picking a run up by name, on its own page, is a decision; picking up twenty-five is a press.

**A cycle the container killed is told so, above the branch that reads a stale column.** `reconcileOnBoot` writes `failed` with `restart_closed` set, `reopenPrompt` had three branches, and a restart-killed run with no operator note fell to the empty one — so `nextPrompt` sent `continuationPrompt`, *"Continue working on the task. If it is fully complete and verified, reply with exactly DONE"*, into a conversation whose last event was a child dying mid-tool-call. Twenty-four runs took that path, and the trees those kills leave are not hypothetical: one was cut down immediately after `git checkout -- src/lib/chat.ts` with the only copy of its fix in `/tmp`, another mid-mutation-test with a deliberately wrong variant of a source file on disk, a third with a tracked file moved aside and `tsconfig.json` rewritten by a dev server. Every one of them reconstructed the tree in its next cycle *despite* being asked whether it was finished. `restartKilled` is `cycleCutByRestart(run)`, and it has two writers that record the same fact differently. `reconcileOnBoot` fails a row the previous process left `running`, with `restart_closed` set, and its queued and paused-too-long branches write `stopped`, so `failed` beside the flag is that branch alone. `shutdownRuns` interrupts every `running` row, and every one whose loop then ends on that interrupt is written `stopped` through `interruptOutcome` with `restart_closed` beside it, the run whose child it killed and the run it caught in its pre-cycle scan alike, so it records `restart_cut_cycle` from `procs.has(id)` before it signals. Not every interrupted row ends that way, which this paragraph used to say: a loop at a cycle boundary takes the ending its cycle earned, so a run whose agent replied DONE during the verdict wait ends `completed`, and that ending is not flagged — `shutdown-and-restart.md` has why. The predicate read `failed` alone until then, which missed every run a `docker compose up --build` cut off, and widening it to every `stopped` restart row would tell a run that never started a cycle that one was cut off. Both columns are read at the call site *before* the UPDATE that clears them in the same statement. `restart_cut_cycle` is cleared with `restart_closed` because only a shutdown rewrites it: left standing, a later boot that set `restart_closed` again from its queued or paused branch would re-read it for a run whose last cycle had finished cleanly. The price is a run picked up and then closed out of the queue before it ran, which loses the notice it was never sent. The branch sits **above** the pushback and that order is the decision: `reported_done` is whatever the previous cycle left on the row, and a cycle killed mid-tool-call never reached the code that changes it, so a run that said DONE two segments ago, was reopened, worked and was then killed would otherwise be told it had reported the task complete and forbidden from starting anything new. It requires a session for the same reason the pushback does.

**A restart on top of existing work says so in the prompt.** `nextPrompt` takes `priorCycles` (read *before* the loop's increment) and, when it has to open with the task text on a run that has already been charged for cycles, prepends a notice naming the branch for an isolated run and the folder otherwise. Nothing else in that prompt refers to the earlier attempt — the conversation that held it is gone by definition — and an agent handed a bare task does the first thing it says, which is the work it is standing on. This is the floor under a restart, not a replacement for resuming: `DEFAULT_CONTINUATION_PROMPT` still restates nothing, because on a conversation that really is intact a restatement is spend for no information.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && !sawResult && finalText === ""`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind". It deliberately does **not** also require `pause_count > 0` — a session truncated mid-turn is truncated whether a guard parked the run or a crash ended it, and a run picked up by hand after a crash may never have parked at all — a pick-up neither adds to `pause_count` nor clears it — so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for.

**A session whose transcript is gone is restarted before the cycle, not discovered by failing one.** The pinned CLI deletes its own transcripts 30 days after they were last written (`cleanupPeriodDays`, measured on its default), and nothing here sets that or hears about it; `sweepTranscripts` clears `session_id` before it unlinks a file of its own, but a file the CLI removed first is never listed by it. A run picked up on such a session put `--resume` on the argv, and the CLI answered with a `result` event (`error_during_execution`, *No conversation found with session ID*) and exit 1 without calling the API — measured, and not the shape the paragraph above retries, because a result arrived. So the cycle was charged and the run ended `failed` on a bare exit code that named neither the session nor the reason, on every pick-up, since nothing on the row changed. So `startRun` asks `sessionTranscriptPresence` before the first spawn of a segment, and on `absent` clears the session through `adoptSession(null)`, the move `startsFresh` already makes: the cycle opens with the task — under `priorWorkNotice` once the run has been charged for a cycle — carries no `--resume`, and spends no failing cycle and no retry. Only `absent` acts, and it is narrower than `resolveSessionTranscript`'s null: two files under one id are a conversation the CLI can still resume, an unreadable directory may hold the file, and a tree with no transcripts at all is a fresh install or a `CLAUDE_HOME` that is not where the CLI writes — each answers `unknown` and resumes as before. That is also why it masks neither a wrong working directory nor an expired credential: both leave the file where it was, so both still reach the resume and end as they did — and the pinned CLI was measured finding a transcript from a working directory other than the one that wrote it. It skips a carried fork, whose failed resume returns to the conversation it was cut from, and every run whose sessions are not Claude Code transcripts under `PROJECTS_DIR` — Codex, and `local`, whose CLI writes under its own config directory. It sits above the pre-spawn interrupt re-check because it awaits a walk, and a Stop pressed during that walk must still win. **The follow-up a pick-up resolved is re-decided with it.** `reopenRun` resolves its message at the door against a session it cannot check without an `await` its one-turn checkout check may not take, so `runs.follow_up_is_note` records whether `follow_up` is the operator's own note. A note survives the restart and is appended to the task, as on any pick-up without a session; text this app wrote for the conversation — the DONE pushback, the restart and needs-review notices, a stack resume — is dropped from the loop and from the row, because it describes a conversation that is gone. Every writer of `follow_up` writes the flag beside it, and rows written before the column read as app text. The pick-up's own status line still says it continues the session, because it is written before anybody looks; the run's log says what happened instead. `resumeMissingTranscript.test.ts` pins it.
