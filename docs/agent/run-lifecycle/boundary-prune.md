# The cycle-boundary prune

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `pruneAtBoundary` or `forkAndAdopt` in `src/lib/orchestrator.ts`, or the pruning, payback and receipt code in `src/lib/contextPruning.ts`.

**A prune happens at two moments and only one of them is free.** Editing a cached prefix invalidates everything after the cut, so with `D` removed and `S` the suffix as it stood before the cut, the edit pays `1.9·S − 2·D` once and earns `0.1·D` on every later turn — break-even after `19·(S/D) − 20` further turns. At the boundary between cycle N and cycle N+1 the `2·D` term is **refunded**, because `--resume` was going to rewrite that prefix regardless, so the boundary prune is the cheap one, and it sits at the very end of the loop body, after every `break`. Moved above one of them it would prune a transcript nothing resumes. **It is no longer unconditional.** The refund argues about the cost side only, while `S` grows every cycle against a `D` that is just the newest cycle's strippable results, so `S/D` and the payback horizon with it drift up until a boundary cut can need more turns than the run has left — measured with `winnow inspect` on this install's own transcripts, `T*` at tier CB runs 68 to 598 turns against runs that billed 113 to 520. `boundaryAction` (`contextPruning.ts`) is the gate, and it is deliberately one-sided: `predictedPayback` at or under `PAYBACK_HORIZON_TURNS` prunes, `null` — unmeasured — *also* prunes, because always-prune nets +$214.46 over this repo's 175-session corpus and every unknown here goes the permissive way. Only a reading strictly over the horizon declines, and because a decline writes no receipt it would re-read the same prediction for ever, so every `BOUNDARY_RECHECK_AFTER` (4) declines in a row prunes anyway to retake it. The early end *manufactures* a boundary, pays the invalidation in full, and is therefore gated: `ceilingPayback` against `CEILING_PAYBACK_HORIZON_TURNS`, over a dry run of **this** conversation. It used to be predicted from the run's own last receipt, and `null` — "this run has not cut yet" — resolved to act, so every run's first crossing was unconditional: a $1.80 cold rewrite decided by the absence of a reading.

**Two engines do the cutting, and which one is configured never labels a figure.** `contextPruningEngine` picks between `winnow treat` — "Edit in place" in the UI, which rewrites the transcript and keeps the session id, writing a `prune_receipts` row — and `winnow fork`, which writes a **new** transcript under a UUIDv5 and moves the run onto it, writing a `fork_attempts` row and never a receipt. Both `forkAndAdopt` call sites read `getSettings()` on the same turn they act, so the switch takes effect at the next boundary and no run carries a frozen copy; adoption, by contrast, is written to `runs.session_id` and is **not** undone by switching back, so a run's transcript lineage and the engine that would cut it next are independent facts. `pricedCuts` unions both tables deliberately and `PruneActivityDTO` deliberately does not carry `engine`: a figure covering only the engine currently configured would drop the other's work out of the total the moment the setting moved, so the engine reaches a screen only as a statement about *now*, never as a label beside money.

**A cut is priced at the model its resume billed at, and `runs.model` only stands in until one has.** That column is NULL for every run started on Claude Code's own default — the stock install, `defaultModel: null` and a blank form field — and for a run whose model came from its agent, so pricing at it left every prune and fork on such a run unpriced while the turns it is netted over named a model with a price, and the run page blamed the price table for it. `atResumeModel` takes the `model` of the first billed turn after the cut, the turn the invalidation is read off, in both `priceReceipts` and `priceForks`; the rate is still the one in force at the cut's own timestamp. The receipt's stored `model` is therefore a fallback and not a statement of what the cut ran on. The turns the saving is counted over pass the same test the resume does, `billedAnything`: the CLI's `<synthetic>` record at a restart or an API error carries an all-zero usage block, read nothing and avoided no re-read, and counted as a turn it credited `0.1·D` per frame.

**A prune answers two questions and one subtraction cannot answer both.** `pruneTranscript` reports *did anything leave the prompt* by differencing `contextTokens` across the child, and *was the file rewritten* by comparing `(ino, size, mtimeMs)` around it — the inode because `save_messages` writes a temp and `os.replace`s it, so a rewrite moves the file however few bytes changed. They come apart because `contextTokens` is deliberately narrow: it sums `JSON.stringify(message)` and nothing else, while winnow demonstrably edits records outside `message` — every record surviving a prune on this install lost its `version`, `gitBranch` and `userType` keys with `message` byte-identical, 461 of them on one session. A child that did only that earns nothing and still breaks the cached prefix, so the next `--resume` pays a full cache write and an `early-end` has additionally spent a work cycle manufacturing the boundary. That is the `rewritten` outcome, and it writes a `prune_receipts` row with `tokens_removed = 0` rather than no row at all, because `netReceipt` can only charge an invalidation against a row. Folded into `nothing` it dropped exactly the cuts that earned nothing and kept the ones that earned something, which is one-directional and flatters the net. It returns its outcome to `pruneAtBoundary` for the same reason: `outcome !== null` is what `settleBoundary` files a resume as **clean** on, and a resume reading a prefix that was replaced is not one.

**Tokens, never bytes, and the number is computed here rather than read from the tool.** Measured against a real 2.0 MB transcript on this install, winnow reported `Saved 0 tokens (0.0%)` for a prune that removed **28% of the API-visible context** — its token figure comes from the transcript's historical `usage` frames, which record what was billed and cannot change when content is edited. And it freed 970 KB of file while removing 290 KB of what is actually sent, a 3.4× overstatement, because its largest strategy removes `toolUseResult`, an envelope field the CLI writes and never transmits. `contextTokens` counts `message` alone, before and after, and that difference is the only figure anything reports. **That last sentence holds for `treat` and is false for `fork`, and the difference is which file the run goes on using.** `treat` edits the session the run keeps resuming and strips `toolUseResult` along with the content, so nothing can rebuild what it removed: its `message`-basis figure of 108,534 tokens on run `115c617d` sat against a measured API fall of 114,350. `fork` writes a **new** transcript, rewrites `message.content` into a pointer and leaves `toolUseResult` bit-identical — 0 bytes removed on every one of the five forks this install has written — and the CLI resuming that new session rebuilds the tool results from the field that was left. Measured on all five, the API window after the resume was 1,153 to 5,238 tokens *higher* than before the cut while `net_bytes` claimed 4,678 to 17,594 tokens had gone; the table is in `docs/verification.md`. So a fork's removal is read off the wire or not read at all: `fork_attempts.api_context_before` is taken from the source session at the cut, `api_context_after` is the first billed turn of the cycle that resumed it, and `forkCutFromRow` credits their difference and nothing else. `netReceipt` carries `removalKnown` so an unmeasured fork reads as unknown rather than as nothing — `PruneSavings.unmeasuredPrunes` counts it through the sum, every surface draws its removal and saving as not measured or as a floor, `netBound` labels the net `at least`, and the context chart's mark carries `tokensRemoved: null` — and `ceilingCut` takes the `D` it divides by from `measuredForkRemoval` rather than from the plan's bytes — a gate that spends ~$1.80 manufacturing a boundary may not divide by a quantity of file. What that difference still overcounts is winnow's **intake filter**, which rewrites the request and never the transcript: a result already replaced with a pointer on the wire is still here in full, so a prune removing it counts tokens the API never held. Measured 2026-08-24 across this install's ten largest transcripts, **4.06% of removed tokens corpus-weighted** (3.07% unweighted, range 0.00%–9.92%), and an upper bound because the reconstruction ignores `keep_newest`. It is **not corrected** and the reason is that the correction does not exist yet: telling those blocks apart needs a `tool_use_id` on each ledger line and winnow writes none, so the alternative is reimplementing its rule set here against a Python module in another repository — still an approximation, since `keep_newest` turns on per-request state no transcript records. The consequence is a rule on the dashboard rather than in the arithmetic: the prune figure and `intakeFilter.ts`'s are added under one title, in one place — `ContextControlAside` — where each span carries the filter's share of itself. The card **does not print the overstatement**: a footnote naming the 4.06% was removed by the operator in `6a78ef9`, restored by `78c87fa` on the strength of this sentence, and removed again with it, so the bound is documented here, in `contextTokens`' docblock and in `docs/verification.md` rather than on the page. Nowhere else adds them, and no meter ever does. `contextTokens`' own docblock carries the number, and so does `docs/verification.md`.

**Every boundary writes down how it ended, and that is what makes an empty section honest.** `prune_decisions` takes one row per terminus — `cut`, `nothing`, `declined`, `refused`, `unavailable`, `failed` — written beside the `log()` line at each branch rather than once at the end, so the durable row and the sentence in the operator's pane come from the same branch and cannot drift. It is **a count of events and never a cost source**: nothing in the netting reads it, an `outcome = 'cut'` row is not a receipt, and it is a table of its own precisely because a non-cut row landing in `prune_receipts` would silently corrupt `pricedCuts`, `contextOccupancy` and `countFor` alike. The six counts sum to `boundaries`, which is what lets `pruneStatement` build a checkable sentence; a clause dropped by a typo would otherwise render as a shorter sentence that still reads as complete. Before it, four of the five ways a boundary could end left no durable trace anywhere — `boundaryDeclines` is a `globalThis` map cleared when the run ends — so "declined at every boundary for forty cycles" and "pruning was never switched on" were the same blank a day later. **The ceiling's own declines were outside that claim for longer**, and that is the path almost every cut comes down: 55 of the 58 on this install, against 3 from the natural boundary. `checkContextCeilings` logged its refusal and `continue`d, so the same blank came back a day later on 95% of the traffic — and with it the denominator `PruneSavings.tsx` says the money is measured against, since a card that only sees the boundaries that cut cannot tell four-of-twelve from four-of-four. It records now, on the same branch as the line and paced by the same `CEILING_REMEASURE_GROWTH_TOKENS`, so the count follows the conversation rather than the ticker and a run climbing from 200k to 300k is written down the whole way up rather than latched by `earlyEndDeclined`, which tracks only whether the operator has been *told*. Three outcomes and not one, because the branch swallows three answers: a null from `ceilingCut` is `unavailable` — winnow absent or a subprocess that failed, which it collapses — a measurement that frees nothing is `nothing`, and only a figure past `CEILING_PAYBACK_HORIZON_TURNS` is `declined`, carrying that figure in `predicted_turns`. An install missing the engine must not read as one whose arithmetic refused. It is **never swept**, on `prune_receipts`' rule and for its reason: `/api/usage` reads it span-scoped and slices it into the dashboard's session and weekly windows, so it answers a weekly KPI and not a question about one run's page. It rode the `run_events` horizon until 2026-09-08 on `context_samples`' reasoning, which was the wrong reading of what it is for — an install with `eventRetentionDays` below 7, accepted since the settings route clamps only at 1, printed a weekly boundary count covering fewer days than the savings figure beside it. `retentionSweep.test.ts`'s deep-equal is what forces a newly-swept store to be named, and what would catch this table being put back into that sweep.

**`PAYBACK_HORIZON_TURNS` and `CEILING_PAYBACK_HORIZON_TURNS` are one policy in two arithmetics, and sharing a number got it wrong.** Both say *cutting half is clearly worth doing, and past that this app is betting on a run's remaining length it cannot price*. `paybackTurns` is `19·(S/D) − 20` over the suffix and half of it costs 18; `ceilingPayback` is `20·(C − D)/D` over the whole conversation and half of *it* costs 20. The ceiling read the 18, so an exactly-half cut priced at 20 was refused by two turns nobody decided on. Neither constant may be used at the other's call site, and what they keep in common is the *case*, not the number it comes out as.

**`paybackTurns` takes the suffix *before* the cut.** Passing `tokens_after` is off by exactly `D` — small when the cut is small and enormous when it is large — so it flatters precisely the marginal cuts the test exists to refuse. `predictedPayback` reads `tokens_before` and the docblock says why.

**`gentle` is not offered.** Winnow ships three prescriptions; measured here `gentle` freed 0 bytes on that same transcript, and structurally so — its one strategy that fires on an ordinary session is `metadata-strip`, which orchestrator-safe mode excludes **by name** because it deletes the `usage`, `costUSD` and `duration` fields every window, every budget guard and `runs.spent_usd` are computed from. Offering it would be a control that reads as on and provably does nothing.

**Pruning and `startsFresh` are independent switches, and the one place they touch is a correction.** `freshStartContextTokens` reads `lastContextTokens` — the last cycle's *billed* resident window, from `usage` frames recorded before the boundary prune ran. So with both on, a prune that took a 200k conversation to 124k would be followed straight away by a fresh start fired on the stale 200k, and the run would pay to re-derive a conversation something had just shrunk to fit under the very threshold being tested. That is `IterationResult.contextTokens`' own **"Last, not largest"** warning arriving from a direction that did not exist when it was written. `contextAfterPrune` subtracts what the cut removed from the billed figure — corrected rather than replaced, because the two are different measurements and substituting the estimate would put a different basis into a threshold the operator set against the first. The **amount** and not a ratio: most of the gap between the two measures is a fixed system prompt, tool list and set of project instructions, and a proportion shrinks those along with the turns. **The fork engine subtracts nothing here, and that is a measurement.** `forkAndAdopt` returns `tokensRemoved: 0` because a fork's transcript delta is not an API delta, and `lastContextTokens` is a wire-basis figure — handing it the file's delta told `startsFresh` that a 200k conversation had become a 180k one while the API went on carrying all 200k, an invented shrink on the one figure whose failure is to throw a conversation away. Neither feature requires the other and neither reads the other's setting.
