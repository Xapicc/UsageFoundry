# What a work cycle does with background tasks

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `src/lib/backgroundWork.ts`, the `backgroundWaitMs` argument of `runIteration`, `previousCycleStoppedTasksNotice` or the `backgroundNotice` argument of `nextPrompt` in `src/lib/cycleInvocation.ts`, or before setting `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` anywhere. What was measured and what was only read out of the binary is in `docs/verification/run-lifecycle-background-work.md` and `docs/verification/budgets-and-guards.md`.

**In `-p` mode the CLI keeps its process alive after the agent ends its turn for as long as a background sub-agent is running, and kills the lot when its own ceiling passes — so the ceiling is set per cycle, and it is a guard rather than a tuning knob.** The CLI's default is 600 seconds (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, milliseconds, `0` unbounded). Run `350ef202` started four `general-purpose` sub-agents and four background shells, ended its turn, and had all eight killed at ten minutes with 210k–250k tokens each spent and nothing written down; cycle 2 resumed into a conversation that still said they were working, waited on them, and the run ended on its cycle cap with nothing committed, at $24.45. Nothing the operator configured asked for the ten minutes — it was the CLI's own default acting as an accidental bound — so the bound has to come from what the operator *did* configure. The value is, in order: the server's own `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` if it set one (left alone, never overridden, and said once per pick-up on the run's log, `contextShapingEnv`'s ground: the configuration is the operator's to make; a **blank** one is read as unset because compose renders every optional variable as `${VAR:-}` and the CLI reads an empty one as its own 600 seconds); otherwise what is left of the run's `maxDurationMinutes` in milliseconds, measured on the same worked clock the guard reads (`workedMs` in `budget.ts`, which `evaluateBudget` now also calls, so the two cannot drift); otherwise `0`, because with no time limit there is no number to derive and the silence deadline already ends a cycle that has hung. **Never `0` while a limit is set**, however little is left — `0` is the CLI's spelling of no ceiling, so a spent limit would be handed the one value that outlives it; the floor is one second. **Always a bare integer**: the pinned parser reads `1.5` and `10s` as one millisecond and `abc`, an empty string and `-5` as its default, none of which is an error. It is set in `runIteration` through `childEnv`'s extras, for Claude Code cycles and for the `local` provider (which is the same CLI and whose env is built over `childEnv`'s), and not for Codex, whose CLI has no such wait; it is deliberately not in `childEnv` itself or in `chatEnv`, `reviewEnv` or `authEnv`, none of which starts a background sub-agent, and a chat turn has a pipe-lifetime problem of its own that a ceiling of `0` would make worse. Dreaming spawns no work cycle and is untouched.

**Which guards bind while the CLI sits idle waiting, under `between-cycles`, and which do not — measured where the table says so, otherwise read from code.** The default guard set and most templates are `between-cycles`, and `LIVE_ENFORCEABLE_CODES` only applies to the live modes.

| Guard | Binds during the wait? | Basis |
|---|---|---|
| `maxDurationMinutes` | **No** — read before a cycle starts, so a cycle can outlive it by as long as its sub-agents run. This is the guard the ceiling carries. | read from code (`evaluateBudget`, `liveGuards` registered only when `enforcement !== "between-cycles"`) |
| `--max-budget-usd` (the run's remaining `maxRunCostUSD`) | **Yes.** The CLI checks sub-agent spend while it waits; at the cap it prints `Budget limit reached ($1.00 of $0.5); stopping background agents.`, kills them and ends the cycle. | measured, stub server |
| cycle-silence deadline (`maxCycleSilenceMinutes`, default 120) | **Yes, for a wait in which nothing is printed.** The CLI printed nothing for 140 s of idle wait; a sub-agent that is making tool calls emits `task_progress` and assistant lines that reset it. It ends the cycle `failed` through `interruptRun`, which is the less graceful end: the CLI's own ceiling reports a cost and a `result`, the watchdog does not. | the CLI's silence measured; the watchdog's reaction read from code |
| 5-hour and weekly window guards, `maxRunTokens` | **No.** Between-cycles reads them before each cycle, which is that mode's documented overshoot of one cycle. A foreground `Task` call overshoots them identically; background waiting is not a new kind of exposure, only a longer one. | read from code |
| operator Stop, fleet stop, shutdown | **Yes** — `interruptRun` signals the child. | read from code |

So a duration limit shorter than the silence deadline is ended by the ceiling, gracefully, and one longer than it can be ended first by the watchdog as `failed`. That is left as it is: lowering the ceiling to the silence deadline would kill sub-agents that are visibly progressing at two hours, and the watchdog's reason names the cause. **Two overshoots remain and are stated rather than closed.** The ceiling is fixed at the spawn, from the remainder *then*, and the CLI's clock starts at the first idle moment after the main thread's last activity — so a cycle whose main turn ran for *M* can run to *M* plus the remainder, past the guard by up to *M*; and the clock restarts every time a finished sub-agent wakes the agent and it goes idle again (measured), so a cycle that keeps being woken is ordinary work and is bounded as a foreground cycle is. Both are inside the one-cycle overshoot `between-cycles` already documents.

**When a cycle ends with background tasks the CLI stopped, the next cycle's prompt says so, names them, and gives their output files.** `previousCycleStoppedTasksNotice` reads the previous cycle's `system:task_started`, `task_updated`, `task_notification` and `background_tasks_changed` rows out of `run_events` and hands them to `stoppedTasksNotice`, which reduces them with `runTasks` — the run page's own reducer, so the panel and the prompt cannot disagree about what ended — and keeps the tasks whose state is `killed` or `stopped`. Measured: a ceiling kill is `task_updated {status:"killed"}` then `task_notification {status:"stopped", output_file, summary}`, and so is a budget kill. **The note is read off the log rather than carried in the loop's frame**, which is how `pendingPushback` travels and is the wrong shape here: a verdict is produced at a boundary and consumed at the next spawn, so dropping it with the frame costs nothing, while this is a fact about work that is gone and a park, a refusal's wait or a restart between two cycles discards the frame while the agent's conversation survives believing otherwise. **The previous cycle is everything after the run's latest `iteration` event**, which is written when a prompt is built and before its spawn, so at the call that builds the next prompt it is still the cycle that just ended — and the next `iteration` event is also what delivers a note once. The query is `ORDER BY id DESC LIMIT 1` rather than `MAX(id)` because with a `kind` filter beside `run_id` SQLite reads every event the run has written for the latter. The note is a statement of fact **placed ahead of** whichever reply `nextPrompt` would have sent — the operator's continuation text, a template's, the DONE pushback or a validator's findings — and replaces none of them, because a note with no instruction leaves the agent without one and an instruction with no note leaves it waiting. On a fresh conversation (no session to resume) it follows the task, where the agent has no memory of the tasks and the output files are all that survives of them. **It is not appended to an operator's own follow-up, which `docs/runs.md` promises is sent verbatim**; the operator who typed one picked the run up from its log, which names the tasks. **A follow-up this app wrote is the opposite case and carries it.** A pick-up with no note (`reopenPrompt`'s needs-review and restart notices, and the DONE pushback) and a stack resume (`stackResumeNotice`) are sent alone just the same, nobody read the log for them — a stack resume is not a pick-up at all — and the `iteration` event their cycle writes moves the boundary, so the note was dropped there and never given again. `withStoppedTasksNotice` puts it ahead of that text at the door that writes it, `reopenRun` with no note and `releaseStackWaits`, which is `follow_up`'s own rule of resolving at the door; the boundary is the one the spawn would have read, because nothing writes an `iteration` event between a cycle's end and its pick-up. Not without a session, where `nextPrompt` already puts the note after the task and the follow-up, and not for Codex. A task still `running` when the log stops is not named, though a child that is gone cannot be running one: `runTasks` is explicit that a finished task simply leaves the snapshot, so "no ending seen" is also what finished work looks like, and a note that told an agent finished work was lost would send it to redo it. The cost is a cycle hard-killed mid-wait, which says nothing; that is the lesser error. A task the agent stopped itself on purpose is named too — the wording is true whoever stopped it and says so — because telling it nothing about a task the CLI killed at its ceiling is the failure this exists for, and telling the two apart would mean this app guessing which instant the main turn ended. Only a Claude Code cycle's log is read; a Codex stream has no such events. The note is capped at twelve tasks and each task's description at one bounded line, because a description is model-written text with no length of its own. The output path is given whole: it is the CLI's rather than the model's, it is the one thing that survives a stopped sub-agent, and clipped at the description's bound or with its whitespace folded it named a file that does not exist.

**What this does not do.** It does not make a background Bash shell outlive its cycle: the binary's wind-down gives a shell-only wait a five-second grace whatever the ceiling is (read, not measured — the CLI's Bash tool cannot start inside the sandbox this was investigated in), so the exposure `350ef202` shows is sub-agents; shells are named in the note when they are killed. It does not tell the agent *why* a task was stopped, only that it was. It does not carry a stopped sub-agent's findings forward — the output file is the CLI's, was 0 bytes after a kill in the stub measurement (whose sub-agent had made two tool calls), and whether a real sub-agent's partial work lands there before a kill is not measured, so the note says "whatever they wrote" and promises nothing. And it does nothing for a chat turn.
