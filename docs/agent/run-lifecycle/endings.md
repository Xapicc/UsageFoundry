# How a run ends: the terminus, cancellation, DONE, needs-review and verdicts

[← run-lifecycle index](../run-lifecycle.md)

Read before editing the end-of-cycle ladder and the `cancelled` checks in `src/lib/orchestrator.ts`, the `DONE` and `NEEDS_REVIEW` notices and `nextPrompt` in `src/lib/cycleInvocation.ts`, `normalizePolicy` in `src/lib/budget.ts`, or `validationAtBoundary` in `src/lib/validation.ts`.

**The UI says "work cycle", the code says "iteration".** User-facing copy names the unit a first-time user must reason about; `Settings`, `BudgetPolicy`, the API payloads, and the `runs` table keep `iteration`/`maxIterations`. Don't rename the internals to match the copy, and don't reintroduce "iteration" into the UI.

**Every budget rule can be switched off, but the loop must always have a monotone terminus.** `null` means "no limit" for cost, tokens, duration, and both fractions — `normalizePolicy` maps `null`/`""`/`0` to `null` rather than to a default, so a blank field disables a guard instead of quietly restoring one. `maxIterations` is nullable too, but only alongside `maxDurationMinutes`: those two are the only quantities that move one way and keep moving. This run's own spend stops accruing the moment a cycle is killed before it reports, and both window fractions can *fall*. The pair is enforced in `POST /api/runs` (which has an error channel) and refused again as `no_terminus` in `evaluateBudget`; `normalizePolicy` must stay total and idempotent, so it never rejects — and never coerces the illegal pair into a limit the user did not ask for. Only an explicit `null` asks for an uncapped loop; blank, zero, negative and missing all still mean one cycle.

**`cancelled` is checked twice per cycle, and both matter.** Once before committing to a cycle (the top-of-loop check is separated from the spawn by a transcript scan that takes seconds, and `stopRun` has already promised no further cycle will start), and once after the child returns, *before* the exit-code test — a SIGTERM'd child closes with a null code that reads as `-1`, so testing the code first files every deliberate stop as `failed`. Likewise `runIteration` resolves on `exit` with a grace period, not on `close` alone: `close` waits for inherited pipes, and an agent that leaves a grandchild behind would otherwise hold its folder until the next restart.

**The first cycle is told how the run ends, and it is told in generated text.** `reportedDone` matches `/^\s*DONE\s*$/m` against *every* cycle's final text, cycle 1 included, but the token was named only by `DEFAULT_CONTINUATION_PROMPT` — which `nextPrompt` returns on the `sessionId !== null` branch and nowhere else. So the terminus existed and the opening cycle had never been given it, which is not a subtle effect: measured over 251 runs, of those whose budget allowed a second cycle, the ones whose *task text* happened to carry the token ended in a single cycle 53% of the time and the ones without did so twice out of 120 — both a crash and an operator stop rather than a completion. `reported_done` was 69% in **both** groups, so the second cycle was not finding more work; it was the first turn permitted to say the job was over, and 92 of them cost $162 to say one word into a re-sent conversation. `COMPLETION_NOTICE` closes that, last in the `sessionId === null` join so it reads as a statement about the task above rather than a preamble to one the agent has not seen, and restating `continuationPrompt`'s bar almost verbatim on purpose — cycle 1 and cycle 2 disagreeing about what "finished" means is the whole defect. Its second sentence is load-bearing for `donePushbackPrompt`'s reason: an instruction an agent cannot satisfy produces churn rather than silence, so a run that is genuinely unfinished is told what to say instead. `endsOnDone` gates it on the two cases where the promise would be false — `maxIterations === 1`, where the cap ends the run either way and the only thing the sentence would change is `reported_done`, which is the sole input to `reopenPrompt`'s pushback branch; and `continueAfterDone`, where the run is set to carry on past a DONE and the pushback says so in as many words. **And it is generated here rather than added to `Settings`**, which is the half that makes it reach anything: see `saveSettings` in `conventions.md` — before that changed, one press of Save materialised every `DEFAULT_*` prompt into the stored blob and the constants were dead for that install forever. `continuedWorkNotice` already made this split for the same reason.

**There is a fourth ending, the agent asks for it, and it is the only rung of the ladder that is about the task rather than the machine.** `completed` was written both for a run that replied `DONE` and for one that merely used up `maxIterations`, which defaults to 1 — so on a stock install almost every finished run is the second kind, and a run that met a wall it could not pass had three futures and all three were wrong: spend the rest of its cycle cap restating the problem, because `COMPLETION_NOTICE` says stopping without `DONE` buys another cycle; reply `DONE` anyway and land in `completed`, which `STATUS_TONE` paints `ok`; or run out of cycles and land in `completed` too, indistinguishable on the list. `needs-review` is that missing ending. It is deliberately **not** `failed`, which is where the *machine* went wrong and which would file a judgement under `danger` beside dead containers and dropped sockets; not `stopped`, which is a person or a rule they configured deciding; and not `blocked`, which means refused before its first work cycle with nothing spent. `cycleEnding(finalText)` is the whole matcher, pure and tested, and what it pins is the **precedence**: a turn carrying both tokens is an agent contradicting itself and `needs-review` wins, because `completed` is green and never re-read while this one is warn-toned, reopenable and asks for somebody. The test sits below every refusal test *and* below the exit-code test — everything above it is a statement about the machine, and filing a 429 or a dropped socket as the agent's judgement would be a lie about who decided and would send an operator who came to read what the agent could not do to a rate limit. A cycle that names the sentinel and then exits non-zero is therefore `failed`, which is right rather than merely incidental: the exit code is the CLI's own verdict that the cycle did not complete. **The branch must assign `reportedDone = false` before it breaks**, and that is the trap: `reportedDone` is hydrated from the row rather than being a fresh local, so a branch that breaks out without touching it writes a stale `1` for a run picked up after an earlier `DONE` and then sends `donePushbackPrompt` into a run that never said it was finished. It writes `needs_review_reason` — the cycle's own final text, clipped at the write to `MAX_NEEDS_REVIEW_REASON` with a trailing `…`, because `RunDTO` is polled every three seconds and is the row shape the list ships for every row, and nothing is lost since the full text is in `run_events`. The column describes *the ending the row currently records*, `stop_reason`'s invariant, so `carried` initialises it null on every other ending and `reopenRun` clears it in the same UPDATE that clears `stop_reason`. And it puts a sentence in the log, `error_max_budget_usd`'s rule: a run that only changed status reads in the stream like a cycle that stopped for no stated reason.

**The sentinel is taught on every prompt but the operator's own, and it is not gated on `endsOnDone`.** `NEEDS_REVIEW_NOTICE` is generated beside `COMPLETION_NOTICE` for the same reason that one is — one press of Save materialises every `DEFAULT_*` prompt into the stored blob, so a sentence added to `Settings` would be dead on every install whose operator has ever pressed it — and it rides on the opening join, the continuation *and* the pushback, not on cycle 1 alone. `continuationPrompt` names `DONE` on every resumed turn, so an agent on cycle 5 re-told about one ending four times and about the other once, on a turn that has scrolled out of the conversation, has been told there is one ending. The one branch it is **not** appended to is `o.followUp`: `docs/runs.md` promises the operator's words are sent verbatim, a run whose operator wrote a note already has the person this ending exists to reach, and the contract returns on the very next cycle. Reusing `endsOnDone` is the obvious symmetry and is wrong: that flag withholds a promise that would be *false* — under `maxIterations === 1` the cap ends the run whatever the agent says, and under `continueAfterDone` a `DONE` is explicitly overridden — where reporting a wall always ends the run with the reason recorded. Since `maxIterations` defaults to 1, gating would withhold the new ending from precisely the one-cycle runs that are written green today. The cost is stated rather than absorbed: `continueAfterDone` is documented as "the run ends only when a limit is reached", and after this it can also end when the agent reports a wall — the better trade, since the alternative is one more billed cycle every time until the cap, but a change to a documented promise and `docs/runs.md` says so. The wording itself is the other half: an ending the agent controls is a cheap way out of a large task, so the sentence has to make reporting it *more* work than carrying on — it names what counts as a wall, refuses what does not, and asks for the three facts an operator needs. The collision hazard is real and bounded rather than closed: the matcher runs over generated text, so a run whose *task* is this feature can trip it. Three things reduce it — the sentinel is `NEEDS_REVIEW` where the stored value is `needs-review`, so a task quoting the *status* cannot fire it; it must be alone on its own line; and sub-agent text never becomes a cycle's `finalText` — and the remaining case is accepted, because the fix is a per-run nonce that would have to survive a `--resume` and would make nothing in this app's logs read the same twice. What it costs is one run ending early with its own text recorded, visible and reopenable in one click.

**`continueAfterDone` sends the agent back in after `DONE`, with a different prompt.** It must be `settings.donePushbackPrompt`, never `continuationPrompt` — that one says "if it is fully complete, reply with exactly DONE", so feeding it back after a DONE produces an immediate second DONE and a tight, billed spin loop. The flag is read as `=== true`, not `Boolean(...)`: it makes a run refuse to stop, so a string `"false"` off the wire must fail safe.

**A cycle boundary can now be held open by a verdict, and where that test sits in the ending ladder is the whole of its safety.** When `validateTaskCompletion` is on, the boundary awaits a validation this cycle started — `validationAtBoundary`, bounded by the assist's own ten minutes plus a margin — and reads what it decided before any ending is chosen. It waits rather than checking at the next boundary because the boundary *is* the decision: a run that called `complete_task` in its last few seconds would otherwise end with the verdict still in flight and no cycle left to act on it. What it holds while waiting is its own folder and its own slot, which it was holding anyway; nothing has been released, `releaseDependents` has not run, and no dependent is waiting on an opinion — which is the pitch's objection to a validator *inside* the ending path, and it does not reach a test between two cycles of one run. **The placement is below `needs-review` and above both `completed` endings.** Below, because `needs-review` is the agent saying it could not finish and that ending belongs to the agent: sending a run back into a cycle it has just said it cannot complete is the one shape this must never take. Above the other two, because those are exactly the endings a validator exists to question — the agent's own `DONE`, and a run that merely used up its cycle cap. `reported_done` is still written from the agent's reply and never from the verdict: that column means one thing, the agent replied `DONE`, it is the sole input to `reopenPrompt`'s pushback branch, and a machine's opinion about a claim is not the claim. Nothing else about the ending moves — no new status, no change to `TERMINAL_STATUSES`, `edgeSatisfied` or any edge condition, and a run whose task was held open still ends `completed` when its grants run out. **An operator's Stop that lands during the wait ends the run `stopped`, and a shutdown does not.** The wait returns as soon as anything is pending, and the loop went straight on to the two `completed` endings, so a Stop pressed there was answered as a stop and the run ended `completed` saying the agent had finished; the loop now reads the map for the operator's kind after writing `reported_done`, which still records the reply, and before either ending. A shutdown is left the ending the cycle earned, for the restart notice's reason in `concurrency-and-ownership/shutdown-and-restart.md`. A guard or a prune cannot be pending there, since both watch a cycle and their watches end with it.

**An operator's Stop also reaches the validation, and the task it leaves is claimed by the stopped run.** Until 2026-10-06 `stopRun` signalled only the work cycle's child, so the check went on reading on its own ten-minute clock, billed, and its settle then acted against the stopped run: a pass, an `unjudgeable` or no verdict closed the task `done` with the run as actor, and a `not-finished` left it claimed. Letting it finish answers neither half of what Stop means. It keeps spending, and the only thing its verdict can still do is make the run act — a run that has ended buys no cycle with a `not-finished`, and a pick-up does not read one, since `reopenRun` clears `verdicts_unread_since`. The close is the half that matters: `done` is green and never re-read, so a task the operator stopped a run *over* would be closed on the claim nobody checked, where a claim left standing is visible on the board beside a run whose status they can see. So `stopRun` signals the run's validation child ahead of every branch — a check outlives the verdict wait, and a parked run has one reading as often — through `validationProcs` in `orchestrator.ts`, its own `globalThis` key. It marks the entry `stopped` before the SIGINT, because a CLI may print its `result` on the way out, and `settleValidation` reads that mark before it reads any verdict: nothing is closed whatever came back, the row is written `failed` with an error naming the Stop (so its null verdict does not read as "closed unchecked"), and the run's log says the task stays claimed. **The task then ends claimed by the stopped run in every verdict case**, which is what `taskboard/tasks-and-transitions.md` already has a stopped run's claim become: the operator's to close or release, and still the run's if it is picked up, where it can call `complete_task` again and be checked afresh. Releasing it to `open` instead would be a release that fires when a run is stopped, which that file refuses by name. This is the one exception to "every way of not getting a verdict closes the task" (`taskboard/completion-validation.md`), and it is not a breach of that rule's reason: the rule exists so a shortage cannot turn into billed work, and a task held by a stopped run buys nothing. Three things are left as they were. A verdict that settled before the Stop has already acted. A guard's stop and a shutdown do not mark the check, so it settles as before — a guard watches the run's own spend, which the check's `--max-budget-usd` bounds separately, and a guard's pause must not kill a check whose verdict the boundary after the park reads. And a process killed hard in the eight seconds between the Stop and the child's settle leaves the row `running` for the boot, whose `closeStrandedValidations` closes the task on the run's word: the mark is in memory, and a graceful shutdown waits for the settle, so only a crash reaches that window.

**The cycle a verdict buys carries the evidence, not a scolding, and `nextPrompt` ranks it above both standing prompts and below the operator's own words.** `validation` is a fourth branch there and it outranks `continuation` and `donePushback` for a plain reason: both of those are settings somebody wrote once, and this is produced at the boundary immediately above about this run's own work — "carry on" and "you said DONE, carry on anyway" are both true and neither says what is missing. It ranks *below* `followUp`, which is still returned alone and verbatim: a person who typed a note into a run while a verdict was landing is the one deciding what that run does next, and nothing is lost that the agent cannot see, since the verdict is on the run's log and the task is still open in `list_my_tasks`. The text is `validationPushback`'s and it carries the validator's reason and evidence word for word, because that is what makes the cycle worth paying for — `Self-Correction and Reflection`'s measured result is that a loop fed a verifier's *evidence* improves and a loop asked to think again does not. It is held in the loop's frame and never on the row, unlike `follow_up`: an operator's note is written before a run is picked up and has to outlive a restart, where this is produced at a boundary and consumed at the very next spawn, and a restart in between should drop it rather than deliver a sentence about a cycle that never happened into a conversation that has moved on.
