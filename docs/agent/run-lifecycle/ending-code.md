# How a run ended, as a code: `runs.ending_code`

[← run lifecycle index](../run-lifecycle.md)

Read before adding a way for a run to end, before writing a status outside the run loop, and before counting runs by how they ended.

**`runs.ending_code` says how a run ended, and the branch that ended it writes it.** One closed union, `RunEndingCode` in `apiTypes.ts`, because `status` cannot say it — `completed` is both DONE and the cycle cap, `stopped` is a person, a guard and a restart — and `stop_reason`, which can, is prose that is never parsed (`db.ts`). Every terminal `break` in `startRun` sets `endingCode` beside `finalStatus`; the `catch` writes `error`; an interrupt's comes from `interruptOutcome`, with `Interrupt.ending` saying when an `operator` stop was a workflow rather than a person; and every terminal write outside the loop carries its own — `stopRun`'s four branches for a run with no child, `blockWaitingRun` and `stopWaitingRun` (whose `ending` is a required argument, so each caller decides rather than inheriting a default that labels a halt as a dependency), `passOverWaitingRun`, `admitWaiting`'s failure, the sweeper's `end` and `reconcileOnBoot`. A guard is `guard:<code>` through `guardEnding` in `budget.ts`, except `iterations`, which is `cycle_cap` because using what it was given is the ending a reading of runs most wants apart from a tripped limit; a workflow halt is `workflow_guard` or `operator_stop` through `haltEnding`, with the verdict left on the instance, once, as the halt already did with its prose.

**Null means not recorded, and that is the load-bearing part.** A park writes null — a parked run has not ended — and `reopenRun` and a revival of a blocked dependent clear it beside `stop_reason`, for `needs_review_reason`'s reason. The column is nullable with no default and is not backfilled, so a row older than it reads as an unknown ending and so does a row a later `break` forgot to label, which is the failure to watch for: an omitted key on a `Partial<RunRow>` typechecks. The one-line assertions in the loop tests that already reach each ending (`docs/agent/testing/work-cycle-prompts-and-endings.md`) are what catch it. The runs list and the run page draw it through `ENDING_LABEL`, in work-cycle copy, and draw a missing code as "unknown" rather than as anything the status suggests; the run DTO and MCP `list_runs` / `get_run` carry it as is.

**It is the field a count of finished runs reads, and `reported_done` was deliberately not repaired.** `proposals/ContinuousImprovement/` found twenty rows reading "Agent reported the task complete." with `reported_done = 0`, written before that column existed, and proposed setting it. That would change what a pick-up of one of them sends — today the continuation prompt and `NEEDS_REVIEW_NOTICE`, afterwards the DONE pushback, whenever its session survives — and turn the run page's Resume into "Ask for more"; and the repair's `WHERE` is a match on `stop_reason` prose, the parse `db.ts` forbids. So `reported_done` stays what a pick-up, the run page's headline and Resume, and `planLoopPass` read, its pre-column rows as they are, and `ending_code` is what a reading across runs counts by — which files those twenty rows as unknown rather than as either answer. Never let it answer one of `reported_done`'s questions: two fields describing one fact is how they drift.
