# Context samples and the tick's cadence

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `prunerState`, `pruningEnabled` or `sampleContext` in `src/lib/contextPruning.ts`, or `liveTickPlan` in `src/lib/orchestrator.ts`.

**`prunerState()` is shipped unconditionally, and `observePlan` is gated.** The readout that says whether the tool is there must not itself be gated on the tool being there — `winnowAvailable()` was consumed only by `orchestrator.ts`, so an image built with `WINNOW_REF=` empty rendered a byte-identical dashboard while every prune no-opped, reporting the failure once per cycle into a per-run log nothing aggregates. `pruningEnabled()` is now defined *over* `prunerState()` rather than beside it, so the guard that decides whether to spawn and the sentence that explains what happened cannot come apart. The probe is memoised behind a 60-second TTL on its own `globalThis` key, because it is now on two request paths rather than the run loop alone. And the feature check moved **above** the payback gate in `pruneAtBoundary`: below it, an install with pruning switched off still ran the gate, still incremented the decline counter and still wrote "the last prune here removed too little to pay for another one" into the pane every cycle — a considered decision the app had not made. `observePlan` carries its own copy of the same check, because `settleBoundary` reaches it on the off branch too, and read-only is not the same as permitted: the one thing an operator who turned the feature off has asked for is that winnow is not spawned against their conversation.

**The tick's reading is written down, and the one thing it is not gated on is pruning.** The ceiling's scan was the only answer this app had to *how full is this run's context*, and it was thrown away — `tokens < CYCLE_CONTEXT_CEILING_TOKENS` discards every reading below the ceiling, which is every reading a graph of occupancy is made of. `sampleContext` stores it on the way past, **before** that comparison; after it, the only runs on record would be the ones already over. The store is deliberately outside `pruningEnabled()`, which used to guard the whole of `checkContextCeilings`: the *watch* is registered unconditionally beside every spawn because the ceiling replaced a flag that rode every cycle of every run, so the reading belongs with the watch and only the acting-on-it belongs with the feature — sampling inside the gate leaves the indicator permanently blank on every install with pruning switched off, which is silent and install-dependent, and is what `contextSamples.test.ts` pins by name. It costs nothing extra where pruning is on, because one scan answers both. What lands in `context_samples` is `apiContextTokens` and the row says so: `basis` is `api`, or `transcript` when the reading fell back to the byte estimate for a conversation with no usable `usage` frame — those two are **different currencies** and a series that mixed them silently would draw a step where only the measure moved. The lag by one turn and the fallback are both left exactly as they are. Rows are deduplicated on the frame the number came from (`message.id`, or on `(basis, tokens)` where there is no frame to name), because the ticker is time-based and one tool call routinely outlasts several ticks — a row per tick makes the series mostly flat duplicates and understates the slope, which is the one thing a context meter is read for. `turn_index` counts distinct main-thread `message.id`s, so a turn the CLI wrote as several records is one turn, and `<synthetic>` and `isSidechain` frames are excluded exactly as the ceiling excludes them; `turns_exact` is 0 when the count is a **floor**, which the megabyte tail scan makes possible on a run's first sample, and a floor added to anything stays one. Bounded twice — `CONTEXT_SAMPLES_PER_RUN` on insert, oldest first, and `sweepRunEvents` on the event horizon, which is the right horizon because these are read only beside the log they explain. `contextOccupancy` puts the series on the run's existing three-second poll rather than an endpoint of its own, carrying `CYCLE_CONTEXT_CEILING_TOKENS` (a constant that has already moved twice) and **both** cut tables' rows as marks — `prune_receipts`, and the `written = 1` rows of `fork_attempts` converted through `forkCutFromRow` because a fork stores bytes and files no receipt, so a panel reading receipts alone drew an unmarked series and reported zero prunes beside a pruning section, out of the same response, that priced the cut; the arrays are the newest **tail** and the stored totals ride beside them, because a series thinned by a rule the reader cannot see misstates its own peaks.

**When the number last moved and when it was last looked at are two facts, and the panel needs both.** Deduplication is right and it is also what made the indicator unreadable: the series only gains a point when the run's **main thread** finishes another request, so a run whose agent spawned one sub-agent at 18:15:59 on this install gained no sample for **22 minutes** — every frame written in that stretch was `isSidechain`, which this measure excludes exactly as the ceiling does — while the tick read the transcript twenty-two times and got the right answer every time. The panel had only the newest row's timestamp and rendered "read 22m ago", which is what an operator reads as a poll that has died; the figure was current throughout, because a parent's context genuinely does not grow while a sub-agent works. So `sampleContext` writes down **every** read — before the two early returns, since those are the ordinary case rather than the exception — and `lastCheck` carries it on the DTO beside the series. The store is a `Map` on `globalThis` and not a row on purpose: it describes the process doing the reading, so a server restarted mid-run has read nothing however recently the run it inherited was read by the server before it, and a row would let it claim otherwise across exactly the restart somebody is most likely to be watching. `unreadable` reaches the wire as itself and is rendered in place of the age rather than beside it — a read that found nothing reported as a fresh reading is the one wording that leaves the panel worse than absent — and a hold is named only past `HOLD_NOTICE_MS`, which sits above the read's own ceiling so that a gap small enough to be one tick says nothing.

**The read's cadence came off the budget's.** Both halves rode `liveGuardIntervalSeconds`, which is a setting about *money* — its description on the settings page is about re-reading usage mid-cycle, it has no upper bound, and an operator on an install where nothing stops mid-cycle is entitled to put it at ten minutes. Doing so took the context indicator with it silently, and the panel is the only answer this app has to *how full is this run*. `liveTickPlan` splits the two: the ticker fires at `min(interval, CONTEXT_READ_MAX_INTERVAL_MS)` so the reading is never more than two minutes old, and `guardScanDue` holds the budget half — `buildSnapshot`, which is uncoalesced and is the expensive one — to the operator's own interval across the ticks it sits out. The slack in `guardScanDue` is half a tick and is load-bearing: `setInterval` drifts, and refusing a tick that lands a few milliseconds early pushes the budget scan a whole tick past the cadence that was set, compounding every time it happens. On the default 60 seconds the two collapse back into one tick and the split costs nothing. One consequence is deliberate rather than incidental: on an install with the interval set high, the **ceiling** is now also evaluated every two minutes rather than every ten, so a cycle over it is ended that much sooner. It was never right that how promptly a cycle got pruned rode a setting about re-reading spend; that was a coincidence of the two sharing a timer. Its own `globalThis` key rather than a field on `timers`, per the shape rule: `??=` does not re-initialise an object a dev hot reload is already holding.

**A Codex run's samples come off its session rollout, on the same basis, and are drawn against its window rather than a ceiling.** The tick reads no transcript for a Codex cycle: `checkContextCeilings` asks `codexCycleTracked` first and, for one, stores `sampleCodexContext` from the rollout's newest `token_count` — `last_token_usage.input_tokens`, the request's whole input as the provider reported it, which is the `api` basis a Claude sample is on — and goes no further, because no ceiling, prune or composition acts on a Codex cycle. A last sample is taken when the cycle ends, so a cycle shorter than the tick still draws a point. `context_samples.window_tokens` stores the `model_context_window` it was measured against, null on every Claude row, and `contextOccupancy` draws a Codex run against that window with `ceilingKind: "window"` — the component then labels the line "context window" — because labelling the model's whole window as the cycle ceiling would claim a cut-off that never comes. `IterationResult.contextTokens` is deliberately not set from this reading: it would switch fresh-start on for Codex runs, which is a separate decision. The composition section answers `provider` for a Codex run and says why in a sentence, rather than reading as a feature switched off.
