# Context samples and the tick's cadence

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `sampleContext`, `sampleCodexContext` or `contextOccupancy` in `src/lib/contextSamples.ts`, `sampleLiveContexts` or `liveTickPlan` in `src/lib/orchestrator.ts`.

**The tick's reading is written down, and nothing acts on it.** `sampleLiveContexts` is the only answer this app has to *how full is this run's context*, and since the winnow removal it is a measurement and nothing more: it raises no interrupt and cuts nothing, so a long cycle runs toward the model's whole window (see `autocompact-and-compaction.md`). The watch is registered beside every spawn and the store is not gated on any setting, because a reading that exists only when a feature is switched on leaves the indicator blank on every install without it, which is silent and install-dependent. What lands in `context_samples` is `apiContextTokens` and the row says so: `basis` is `api`, or `transcript` when the reading fell back to the byte estimate for a conversation with no usable `usage` frame — those two are **different currencies** and a series that mixed them silently would draw a step where only the measure moved. The lag by one turn and the fallback are both left exactly as they are. Rows are deduplicated on the frame the number came from (`message.id`, or on `(basis, tokens)` where there is no frame to name), because the ticker is time-based and one tool call routinely outlasts several ticks — a row per tick makes the series mostly flat duplicates and understates the slope, which is the one thing a context meter is read for. `turn_index` counts distinct main-thread `message.id`s, so a turn the CLI wrote as several records is one turn, and `<synthetic>` and `isSidechain` frames are excluded; `turns_exact` is 0 when the count is a **floor**, which the megabyte tail scan makes possible on a run's first sample, and a floor added to anything stays one. Bounded twice — `CONTEXT_SAMPLES_PER_RUN` on insert, oldest first, and `sweepRunEvents` on the event horizon, which is the right horizon because these are read only beside the log they explain. `contextOccupancy` puts the series on the run's existing three-second poll rather than an endpoint of its own; the array is the newest **tail** and the stored total rides beside it, because a series thinned by a rule the reader cannot see misstates its own peaks. A Claude run's DTO carries `windowTokens: null` and the chart draws no rule line and no meter: nothing in this app knows a Claude model's window, and a line drawn at a guess would be read as a limit.

**When the number last moved and when it was last looked at are two facts, and the panel needs both.** Deduplication is right and it is also what made the indicator unreadable: the series only gains a point when the run's **main thread** finishes another request, so a run whose agent spawned one sub-agent at 18:15:59 on this install gained no sample for **22 minutes** — every frame written in that stretch was `isSidechain`, which this measure excludes exactly as the ceiling does — while the tick read the transcript twenty-two times and got the right answer every time. The panel had only the newest row's timestamp and rendered "read 22m ago", which is what an operator reads as a poll that has died; the figure was current throughout, because a parent's context genuinely does not grow while a sub-agent works. So `sampleContext` writes down **every** read — before the two early returns, since those are the ordinary case rather than the exception — and `lastCheck` carries it on the DTO beside the series. The store is a `Map` on `globalThis` and not a row on purpose: it describes the process doing the reading, so a server restarted mid-run has read nothing however recently the run it inherited was read by the server before it, and a row would let it claim otherwise across exactly the restart somebody is most likely to be watching. `unreadable` reaches the wire as itself and is rendered in place of the age rather than beside it — a read that found nothing reported as a fresh reading is the one wording that leaves the panel worse than absent — and a hold is named only past `HOLD_NOTICE_MS`, which sits above the read's own ceiling so that a gap small enough to be one tick says nothing.

**The read's cadence came off the budget's.** Both halves rode `liveGuardIntervalSeconds`, which is a setting about *money* — its description on the settings page is about re-reading usage mid-cycle, it has no upper bound, and an operator on an install where nothing stops mid-cycle is entitled to put it at ten minutes. Doing so took the context indicator with it silently, and the panel is the only answer this app has to *how full is this run*. `liveTickPlan` splits the two: the ticker fires at `min(interval, CONTEXT_READ_MAX_INTERVAL_MS)` so the reading is never more than two minutes old, and `guardScanDue` holds the budget half — `buildSnapshot`, which is uncoalesced and is the expensive one — to the operator's own interval across the ticks it sits out. The slack in `guardScanDue` is half a tick and is load-bearing: `setInterval` drifts, and refusing a tick that lands a few milliseconds early pushes the budget scan a whole tick past the cadence that was set, compounding every time it happens. On the default 60 seconds the two collapse back into one tick and the split costs nothing. Its own `globalThis` key rather than a field on `timers`, per the shape rule: `??=` does not re-initialise an object a dev hot reload is already holding.

**A Codex run's samples come off its session rollout, on the same basis, and are drawn against its window.** The tick reads no transcript for a Codex cycle: `sampleLiveContexts` asks `codexCycleTracked` first and, for one, stores `sampleCodexContext` from the rollout's newest `token_count` — `last_token_usage.input_tokens`, the request's whole input as the provider reported it, which is the `api` basis a Claude sample is on — and goes no further. A last sample is taken when the cycle ends, so a cycle shorter than the tick still draws a point. `context_samples.window_tokens` stores the `model_context_window` it was measured against, null on every Claude row, and `contextOccupancy` returns it as `windowTokens`, which the component draws as the "context window" line. `IterationResult.contextTokens` is deliberately not set from this reading: it would switch fresh-start on for Codex runs, which is a separate decision.
