# Waiting for a stack

[← run-lifecycle index](../run-lifecycle.md)

Read before editing `request_stack` in `src/app/api/mcp/route.ts`, `src/lib/stackRequests.ts`, the `waiting-for-stack` status, `releaseStackWaits` in `src/lib/orchestrator.ts`, or the boot call to it in `src/instrumentation.ts`. What a run may and may not do through the tool is in [`security/stacks.md`](../security/stacks.md).

**A run has a third answer to a missing tool, and it is a question rather than an install.** Before this a run that needed `cargo` could fail inside a tool call or report it could not finish. `request_stack` lets it ask: it names a stack, the binaries it needs on `PATH`, a sentence of why and optionally a draft `stack.json`, and the run parks as `waiting-for-stack` at the end of that cycle. The operator reads the request on the run page or under Settings → Tools, writes the declaration under `./stacks/<name>/` on the host themselves and restarts, or presses Decline, and the run resumes in the same session either way, told which. Nothing in the app installs, writes a declaration or runs the applier, so `/etc/uf-stacks` stays a read-only bind and the applier stays boot-only — the decision that made this design and the one not to route around. A request answered by the receipts already — every binary linked by an `ok` stack, or an `ok` stack under the name — records nothing and says so.

**The park is read off the record at the cycle boundary, below the machine's rungs and above the task's.** `startRun` asks `stackWaitOf(id)` after the exit-code rung and before `cycleEnding`. Below every statement about the machine, so `failed`, `stopped`, a refusal's `paused` and a guard's keep their meaning whatever the agent asked for. Above every statement about the task, because whatever the cycle said about the task it said without the tool: a `NEEDS_REVIEW` is usually the wall the stack exists to clear, a `DONE` is premature and is not recorded (`reported_done` is cleared on this branch for the trap the `needs-review` branch names), and the cycle-cap check below would end on the default cap of one a run that is about to be given what it was missing. A claim for the validator is left in flight for the same reason. Asked of the record rather than of the reply, so a model that calls the tool and carries on working still parks, and one that only says it needs a tool does not. A cycle that ends on a machine rung with a request pending is parked or ended by that rung; a `paused` run resumed later meets this check at its next boundary.

**The cycle that asked is refunded, and the refund is bounded.** Without the refund a run on the default `maxIterations` of 1 that asked in its only cycle was ended on the cap by the pre-cycle guard the moment it resumed, having waited a restart for nothing. A refund nothing bounds stops `maxIterations` being a terminus, so `runs.stack_waits` counts every stack park and `MAX_STACK_WAITS_PER_RUN` (3) bounds it — `guard_refunds`' arrangement: on the row, never reset by `reopenRun`, and past it a park charges the cycle. `request_stack` refuses to file at the bound rather than file a wait the run cannot afford, so a charged park is reachable only for a run attached before it. Every wait needs a person's answer, which bounds it in practice too, but a terminus that rests on a person doing something is not one. `pause_count` advances with it, because the refund can put `iterations` back to zero on a run whose branch exists and `ensureWorktree` reads that column as "has worked before".

**It is a park in every column `paused` writes except `resume_at`.** `paused_at` opens on the way in and `startRun`'s claim closes it into `paused_ms`, so the wait is never worked minutes and `maxDurationMinutes` is untouched by it (`budgets-and-guards/termini-and-waiting.md`); `installSpend` bounds the run's spend on that `paused_at` as it does a paused row's. It is in `activeRuns()`, so its worktree slot is reserved and every land, delivery, commit, purge and branch delete refuses while it waits, and `walkQueue` ignores it, so its folder is yielded. `resume_at` stays null because it would be a promise about when somebody restarts a container. Every exit closes the park: `stopRun`'s branch spreads `pauseClosedAt`, the release leaves it for the claim, and no sweep or boot ends one.

**It survives every boot, and the boot is what releases it.** `reconcileOnBoot` keeps a `waiting-for-stack` row whatever its age — the one way it differs from `paused`, whose grace exists because a run waiting on a window that cleared hours ago is waiting on nothing, where this one is waiting on exactly the restart that has just happened. `src/instrumentation.ts` calls `releaseStackWaits()` after `reconcileBlocksOnBoot` and `reconcileHaltsOnBoot`, so a member of an instance the boot halted is stopped there rather than re-queued here, and `bootBlockPlan` spares an instance with such a member because `LIVE_STATUSES` holds the status. The decline route releases at once; `sweepPaused` calls the release first on every tick as a backstop, and keeps its timer while any run waits. Each call re-queues at most `MAX_RESUMES_PER_SWEEP`, because a restart that installs the stack twenty runs were waiting for is the fleet arriving in one event-loop turn, and on a sweep what it re-queued comes off the same tick's slots for `paused` runs, so the bound is one bound; the rest keep their row for the next tick. Always through `promoteQueued`, never `startRun`.

**The release is one pure decision, and it agrees with the tool about what is installed.** `decideStackWait(requests, receipts)` returns `resume`, `stay` or `declined`. Declined outranks everything, since it is a person's answer and the one that cannot change by waiting. A request is answered when `stackSatisfaction` says so, and that predicate is also what `request_stack` asks before filing — if the two disagreed, a run could file a request the next release treats as answered and park and resume in a loop with nothing installed, which is the case `stackRequests.test.ts` pins across every receipt shape. A `failed` or `conflicted` receipt under the requested name keeps the run waiting and is shown on the request with the applier's first line. A run attached to nothing resumes rather than waiting for ever.

**What the resumed run is told travels in `follow_up`, and the grant needs nothing.** `stackResumeNotice` is written into `runs.follow_up` by the flip to `queued`, the door `reopenPrompt`'s notices already use, so it is consumed at the spawn and is the resumed turn — behind the stopped-tasks note when the cycle that asked ended with background tasks stopped ([`background-work.md`](background-work.md)), since nobody read that cycle's log for it — saying the stacks and binaries now on `PATH`, what the stack did not provide, or that the operator declined and the agent should continue without it or reply `NEEDS_REVIEW`. The grant is `stackGrants()`, read per cycle from the receipts the new process found, and `buildArgs` puts it on a resumed cycle as on any other — pinned in `buildArgs`' suite composed with `stackGrants` over a receipts directory, and through the real loop in `stackWait.test.ts`, which checks the resumed cycle's `--resume` and `--allowedTools` against the first cycle's.

**An attachment means exactly "between asking and being answered".** `stack_request_runs.released_at` is set on every way out of a wait — the release, `stopRun`, any loop ending that is not a park, and `reopenRun`, which is the one door back from the boot's `failed` and the sweeper's `stopped`, neither of which passes the loop's `finally`. Left standing, a picked-up run parked at its first boundary on a request the operator may have stopped it to abandon. The request itself is untouched by any of these: other runs may still wait on it.

**It notifies, because only a person ends it.** `NOTIFY_PARKS` in `notify.ts` holds it, tested above the settled gate and consuming neither latch (`notifications.md`). Its stdout level is `info` like `paused`'s, since nothing went wrong.

**Two things are deliberately thin.** `request_stack` is a run tool, so it arrives with `taskboardForRuns` and is absent while that is off: on a stock install a run still has only its two old answers. And `/api/health`'s counts leave the status out — they exist for the stalled-sweeper test, and the sweeper is only this park's backstop.
