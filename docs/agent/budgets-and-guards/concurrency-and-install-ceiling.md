# Concurrency caps and the install's rolling limit

[← budgets-and-guards index](../budgets-and-guards.md)

Read before editing `maxConcurrentRuns`, `maxConcurrentAssists` or the cap in `promoteQueued` (`src/lib/orchestrator.ts`), or `src/lib/installBudget.ts` and every door that asks `installBudgetRefusal`. What the limit does to the three kinds of assist (counting their `run_reviews` rows, refusing them at `assistRefusal`, bounding the child) is in [Assists under the install's rolling limit](assists-under-the-install-limit.md).

Concurrency multiplies overshoot — `maxRunCostUSD` is per run, so N runs at $5 is a $25 worst case — and `maxConcurrentRuns` bounds N. The cap is enforced in `promoteQueued`, counting **running** rows only: it is a limit on work in flight, so a run over it waits rather than being refused, and queued *or paused* rows — which cost nothing — must never consume it.

**The concurrency cap is a bound on the host, so it ships as a number and it covers every kind of `claude` child.** It is the one figure in `DEFAULTS` that is not left null, and the reason the no-default-ceilings rule does not reach it is precise: a ceiling is null because we would be guessing at something Anthropic publishes nowhere, where how many Node processes a container can carry is a property of the machine. `null` used to be the state a fresh install was in, which meant the shipped configuration had no bound on the fleet at all; it stays available as an explicit opt-out and is no longer the default. `maxConcurrentRuns` is **4** and covers work cycles; `maxConcurrentAssists` is **2** and covers the other three kinds of child, which consulted nothing at all — a review, a merge-conflict resolution, a chat turn and a workflow orchestrator block's deciding turn, each a full Node process, none of which a cap on work cycles could see. Both numbers are chosen against the `mem_limit` `docker-compose.yml` now ships rather than measured, and the arithmetic is in README's *Sizing the container*: raising the fleet means raising the compose limits with it, because what those limits buy is a **local** failure — Docker OOM-kills the container, `restart: unless-stopped` recovers it and `reconcileOnBoot` closes out its runs, instead of the host degrading and the server process that is supposed to be guarding the runs being the first thing starved. The two are split rather than one number for the reason `run_templates` and `InstanceBudgetPolicy` are two budgets: a chat turn eating a run's slot is a queue that stalls for a reason nobody can see, and the ceiling on the container is the *sum*, which is what the settings copy and the README both state. The second cap is read at one door — `assistRefusal()` in `review.ts`, which all four of those callers already passed through — off `liveAssistChildren()`, a count over the three tables that already record each of those children for a boot reconciler to close out. Two things about that count are load-bearing and silent: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so it is excluded by `kind`, and the check is not a claim — the person-facing callers have an `await` between the answer and the row that fills the slot, so the overshoot is the number of requests in flight, which is accepted because this bounds memory rather than a folder. What happens over the budget differs by caller and that difference is the design: a review, a resolution and a chat turn are **refused** with a sentence, because a person is there and has an error channel, while a block's deciding turn is left `waiting` — gated at `advanceInstance`'s claim rather than inside `startBlockTurn`, which is why that function calls `windowRefusal` and not `assistRefusal` and would otherwise refuse itself whenever it was the turn that filled the budget. `blocked` there would end the branch of the graph behind it for a shortage of memory that clears in minutes, so whatever frees a slot advances again: `settleBlock` already did, and `review.ts`'s `finish` and `chat.ts`'s `finishTurn` now do too, through the dynamic import `releaseDependents` already uses.

**A local run needs a slot under two caps, and the second is about another machine.** `maxConcurrentLocalRuns` (**1**) bounds local-provider runs alone, in `walkQueue` beside the regular cap, and a local run takes a slot under both. Under both because the regular cap is the container's memory bound and a local cycle is still a `claude` child in the container, so the sum README sizes the container against does not move. The second bounds the machine the local server runs on: a server several cycles reach at once answers each of them later, and a cycle waiting on it is silent, which `LOCAL_IDLE_TIMEOUT_MS` in `localProvider.ts` stretches but does not remove. A local run this cap holds takes neither slot and gets `localCap` as its blocker, so a Claude run queued behind it still starts. It is asked after the folder, for the folder's reason, and before the regular cap, being the narrower of the two waits.

**And a cap on N still bounds nothing about the total, so there is one limit that is about the install rather than about a spender.** Every other guard here bounds one thing: `maxRunCostUSD` a run, `maxInstanceCostUSD` one press of Run, `chatTurnBudgetUSD` one turn. Nothing bounded the sum, and nothing bounds the *rate* at which new spenders appear — `promoteQueued` refills a slot the instant one frees, a schedule presses Run with nobody present, an orchestrator block starts up to `MAX_FAN_OUT` runs with no approval — so the fleet's spend was `waves × concurrency × per-run limit` with no term under an operator-set maximum. `settings.installDailyCostLimitUSD` is that term, `null` by default and normalized by `normalizeInstallBudget` under the `null`/`""`/`0`-means-off rule every budget field here follows. `evaluateInstallBudget` is the verdict, pure and unit-tested beside the other two and sharing their `BudgetVerdict` and their `BudgetStopCode` vocabulary (`install_cost`); `installBudget.ts` is the reading, and it is a **fourth** reading rather than a fourth cost source — `runs.spent_usd`/`spent_usd_est`, `workflow_instance_blocks.cost_usd`, `chat_turn_spend.cost_usd` — the same money `chat_sessions.cost_usd` totals, dated per turn so a day's window can be taken out of it — and, for cycles in flight, `telemetrySpendSince` through the one door with its one per-run per-cycle bound, each cycle capped at the `--max-budget-usd` it was spawned with (`inFlightCostForOthers`). The cap is there because a cycle can post its own telemetry and every other run's pre-cycle check reads this figure: uncapped, one forged `cost_usd: 1e9` ended each run that reached that check on `install_cost`. A Claude cycle is handed the tighter of what this limit and its workflow's `maxInstanceCostUSD` have left (`installBudgetReading`, `instanceHeadroom`, `cycleBudgetUSD`'s third input) wherever that is smaller than what its run's own `maxRunCostUSD` has left, read at the pre-cycle guard off the figures the two checks just passed, so it is positive. That is not the guessed ceiling that would blind these limits, because it is where they would end the run anyway; a cycle it cuts short ends on `guard:install_cost` or `workflow_guard`, not `cli_budget` ([cycle-argv-and-notices.md](../run-lifecycle/cycle-argv-and-notices.md)). It bounds a real cycle as well as a forged one, and **it does not stop a forger filling the limit**: capped at the headroom, a posted `cost_usd: 1e9` reads as a cycle that spent all of it, so the install figure reaches the limit and every door above refuses until that cycle ends. A cycle that really spent its headroom reads the same, where a forged one used to read $1,000,000,000 past the limit. Two closures were measured and neither holds on a stock install: the headers helper, and binding ingest to the CLI's pid, which a root server without `CAP_SYS_PTRACE` cannot check and which a repository's `.claude/settings.json` gets around ([telemetry-token](../../verification/security-and-sandboxing-telemetry-token.md)). Closing that needs the ingest token out of the agent's reach, and it is not done. Also open: the headroom is a cap and not a reservation, so concurrent unlimited runs are each handed the same figure and can carry the install past it by their sum, the overshoot above; and a workflow limited by window fractions alone, a Codex cycle and a local cycle are handed none ([run-spend-readings.md](../metering/run-spend-readings.md)). It never reaches `buildSnapshot()`, `runs.spent_usd` or any window meter, it carries the same display-versus-guard split everything else here does, and it must never be summed with the meters above it on the dashboard: those are our price table over every transcript on the machine measured against Anthropic's windows, and this is money this app itself recorded spending over a rolling 24 hours. The window is **rolling** rather than a calendar day for `buildPeriods`' own reason turned into a guard — the container runs in UTC and the operator does not — and because a calendar boundary is a cliff every run in the install would cross together. A run still going, or one that finished inside the window, contributes its whole spend: `runs.spent_usd` is one figure for a whole run and there is no per-hour breakdown of it, so this over-counts, which is the safe direction for a limit and is why it feeds a guard and its own card and never a rollup. **But the over-count has to stay bounded, so every row here names the instant that takes it out of the window and none is bounded on a column it may never write.** A run is bounded on `finished_at`, or on `paused_at` while the row is still `paused`: a parked run deliberately has no `finished_at` — it is not finished, it is waiting out the 5-hour window and keeping its folder and its session — so bounding on that column alone counted its spend for ever, and three runs parked at $40 read $120 against a $100 limit on every call, refusing every door in the app for as long as they stayed parked, under a refusal saying the spend would age out of the window when nothing would ever age it out. The status test beside it is load-bearing rather than decoration: `startRun` closes a park off into `paused_ms` and clears `paused_at` at its claim, but the flip out of `paused` is into `queued`, so a run the sweeper handed back and `maxConcurrentRuns` has held in the queue ever since still carries an instant a day old and starts the moment a slot frees — a bare `COALESCE(finished_at, paused_at)` would drop that spender out of the reading altogether. A block gets the same treatment on `started_at`, which bounds the one case that matters — a settled block put back to `waiting` with its `finished_at` cleared and its accumulated cost kept — and drops nothing live, because the only rows summed are orchestrator blocks and `settleBlock`, the one writer that adds to those, leaves `finished_at` set when it is done — its cost UPDATE is unlatched so a turn billed before a halt still counts, and the latched UPDATE that writes `finished_at` follows in the same transaction, or `haltBlocks` wrote it seconds earlier. It is not one statement, and a review row does not even keep that pairing (`bankReviewSpend` adds to a block still `thinking`), which is a second reason the sum is not taken over every kind. And a chat contributes **per turn**: `chat_sessions.cost_usd` is a running total over the life of a thread, so summing it bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in — a limit on the install's whole history wearing a 24-hour label, closing every door and stopping the runs already in flight at their next pre-cycle guard. `chat_turn_spend` is one dated row per settled turn, written inside `finishTurn`'s existing latch so a late settle that moved no total writes no row either, and the running total beside it is left exactly as it is, because the chat page displays it and a column that quietly began meaning something narrower would be the worse repair. A thread that predates the table is backfilled as a single turn at its `updated_at` — bit-for-bit what the old query counted — inside the same transaction as the CREATE, since reading an un-backfilled table as $0 would *widen* the limit on the boot that upgrades, which is the one direction a limit must never move by accident. Five doors read it and no more — `createRun` (refused rather than queued, and inside that function rather than in `POST /api/runs`, because the chat's approval batch, a workflow's pass and a block's emission all arrive there too), `startRun`'s pre-cycle guard, `startWorkflow`, `startBlockTurn` and `assistRefusal` (which a chat turn, a review, a conflict resolution and a validation all pass) — and the pre-cycle one sits ahead of the instance guard because it is the wider limit and halting a whole graph over a limit that is not about that graph would take down blocks that are not the problem. This is emphatically **not** `buildPeriods` feeding a guard: that measures history against a weekly ceiling pro-rated over a span nobody set an allowance for, where this is a number the operator typed meaning what it says.

**A limit handed to a child bounds a turn only while nothing buys the turn again under a fresh one.** A deciding block saved with `turnRetries` started a turn the CLI had stopped at `--max-budget-usd` over again, each attempt handed `chatTurnBudgetUSD` afresh, so the limit bounded the attempt rather than the turn and a block with two retries spent three times the figure the operator set. `blockTurnRetries` now settles an `error_max_budget_usd` ending as it is, which is the run loop's rule for a work cycle at that subtype ([enforcement-modes.md](enforcement-modes.md)): the limit holding is not the child failing, and stopping is the whole point. The subtype is the only place the CLI says the limit was why it stopped — by exit code and `is_error` it is any other failure — so anything that wraps a retry or a restart around a budgeted child owes the same check, and the block's is in [orchestrator-and-merge-blocks.md](../workflows-and-schedules/orchestrator-and-merge-blocks.md).
