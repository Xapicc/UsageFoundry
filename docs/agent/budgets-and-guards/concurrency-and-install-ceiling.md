# Concurrency caps and the install's rolling limit

[← budgets-and-guards index](../budgets-and-guards.md)

Read before editing `maxConcurrentRuns`, `maxConcurrentAssists` or the cap in `promoteQueued` (`src/lib/orchestrator.ts`), or `src/lib/installBudget.ts` and every door that asks `installBudgetRefusal`.

Concurrency multiplies overshoot — `maxRunCostUSD` is per run, so N runs at $5 is a $25 worst case — and `maxConcurrentRuns` bounds N. The cap is enforced in `promoteQueued`, counting **running** rows only: it is a limit on work in flight, so a run over it waits rather than being refused, and queued *or paused* rows — which cost nothing — must never consume it.

**The concurrency cap is a bound on the host, so it ships as a number and it covers every kind of `claude` child.** It is the one figure in `DEFAULTS` that is not left null, and the reason the no-default-ceilings rule does not reach it is precise: a ceiling is null because we would be guessing at something Anthropic publishes nowhere, where how many Node processes a container can carry is a property of the machine. `null` used to be the state a fresh install was in, which meant the shipped configuration had no bound on the fleet at all; it stays available as an explicit opt-out and is no longer the default. `maxConcurrentRuns` is **4** and covers work cycles; `maxConcurrentAssists` is **2** and covers the other three kinds of child, which consulted nothing at all — a review, a merge-conflict resolution, a chat turn and a workflow orchestrator block's deciding turn, each a full Node process, none of which a cap on work cycles could see. Both numbers are chosen against the `mem_limit` `docker-compose.yml` now ships rather than measured, and the arithmetic is in README's *Sizing the container*: raising the fleet means raising the compose limits with it, because what those limits buy is a **local** failure — Docker OOM-kills the container, `restart: unless-stopped` recovers it and `reconcileOnBoot` closes out its runs, instead of the host degrading and the server process that is supposed to be guarding the runs being the first thing starved. The two are split rather than one number for the reason `run_templates` and `InstanceBudgetPolicy` are two budgets: a chat turn eating a run's slot is a queue that stalls for a reason nobody can see, and the ceiling on the container is the *sum*, which is what the settings copy and the README both state. The second cap is read at one door — `assistRefusal()` in `review.ts`, which all four of those callers already passed through — off `liveAssistChildren()`, a count over the three tables that already record each of those children for a boot reconciler to close out. Two things about that count are load-bearing and silent: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so it is excluded by `kind`, and the check is not a claim — the person-facing callers have an `await` between the answer and the row that fills the slot, so the overshoot is the number of requests in flight, which is accepted because this bounds memory rather than a folder. What happens over the budget differs by caller and that difference is the design: a review, a resolution and a chat turn are **refused** with a sentence, because a person is there and has an error channel, while a block's deciding turn is left `waiting` — gated at `advanceInstance`'s claim rather than inside `startBlockTurn`, which is why that function calls `windowRefusal` and not `assistRefusal` and would otherwise refuse itself whenever it was the turn that filled the budget. `blocked` there would end the branch of the graph behind it for a shortage of memory that clears in minutes, so whatever frees a slot advances again: `settleBlock` already did, and `review.ts`'s `finish` and `chat.ts`'s `finishTurn` now do too, through the dynamic import `releaseDependents` already uses.

**A local run needs a slot under two caps, and the second is about another machine.** `maxConcurrentLocalRuns` (**1**) bounds local-provider runs alone, in `walkQueue` beside the regular cap, and a local run takes a slot under both. Under both because the regular cap is the container's memory bound and a local cycle is still a `claude` child in the container, so the sum README sizes the container against does not move. The second bounds the machine the local server runs on: a server several cycles reach at once answers each of them later, and a cycle waiting on it is silent, which `LOCAL_IDLE_TIMEOUT_MS` in `localProvider.ts` stretches but does not remove. A local run this cap holds takes neither slot and gets `localCap` as its blocker, so a Claude run queued behind it still starts. It is asked after the folder, for the folder's reason, and before the regular cap, being the narrower of the two waits.

**And a cap on N still bounds nothing about the total, so there is one limit that is about the install rather than about a spender.** Every other guard here bounds one thing: `maxRunCostUSD` a run, `maxInstanceCostUSD` one press of Run, `chatTurnBudgetUSD` one turn. Nothing bounded the sum, and nothing bounds the *rate* at which new spenders appear — `promoteQueued` refills a slot the instant one frees, a schedule presses Run with nobody present, an orchestrator block starts up to `MAX_FAN_OUT` runs with no approval — so the fleet's spend was `waves × concurrency × per-run limit` with no term under an operator-set maximum. `settings.installDailyCostLimitUSD` is that term, `null` by default and normalized by `normalizeInstallBudget` under the `null`/`""`/`0`-means-off rule every budget field here follows. `evaluateInstallBudget` is the verdict, pure and unit-tested beside the other two and sharing their `BudgetVerdict` and their `BudgetStopCode` vocabulary (`install_cost`); `installBudget.ts` is the reading, and it is a **fourth** reading rather than a fourth cost source — `runs.spent_usd`/`spent_usd_est`, `workflow_instance_blocks.cost_usd`, `chat_turn_spend.cost_usd` — the same money `chat_sessions.cost_usd` totals, dated per turn so a day's window can be taken out of it — and, for cycles in flight, `telemetrySpendSince` through the one door with its one per-run per-cycle bound. It never reaches `buildSnapshot()`, `runs.spent_usd` or any window meter, it carries the same display-versus-guard split everything else here does, and it must never be summed with the meters above it on the dashboard: those are our price table over every transcript on the machine measured against Anthropic's windows, and this is money this app itself recorded spending over a rolling 24 hours. The window is **rolling** rather than a calendar day for `buildPeriods`' own reason turned into a guard — the container runs in UTC and the operator does not — and because a calendar boundary is a cliff every run in the install would cross together. A run still going, or one that finished inside the window, contributes its whole spend: `runs.spent_usd` is one figure for a whole run and there is no per-hour breakdown of it, so this over-counts, which is the safe direction for a limit and is why it feeds a guard and its own card and never a rollup. **But the over-count has to stay bounded, so every row here names the instant that takes it out of the window and none is bounded on a column it may never write.** A run is bounded on `finished_at`, or on `paused_at` while the row is still `paused`: a parked run deliberately has no `finished_at` — it is not finished, it is waiting out the 5-hour window and keeping its folder and its session — so bounding on that column alone counted its spend for ever, and three runs parked at $40 read $120 against a $100 limit on every call, refusing every door in the app for as long as they stayed parked, under a refusal saying the spend would age out of the window when nothing would ever age it out. The status test beside it is load-bearing rather than decoration: `startRun` closes a park off into `paused_ms` and clears `paused_at` at its claim, but the flip out of `paused` is into `queued`, so a run the sweeper handed back and `maxConcurrentRuns` has held in the queue ever since still carries an instant a day old and starts the moment a slot frees — a bare `COALESCE(finished_at, paused_at)` would drop that spender out of the reading altogether. A block gets the same treatment on `started_at`, which bounds the one case that matters — a settled block put back to `waiting` with its `finished_at` cleared and its accumulated cost kept — and drops nothing live, since every UPDATE that adds to `workflow_instance_blocks.cost_usd` writes `finished_at` in the same statement. And a chat contributes **per turn**: `chat_sessions.cost_usd` is a running total over the life of a thread, so summing it bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in — a limit on the install's whole history wearing a 24-hour label, closing every door and stopping the runs already in flight at their next pre-cycle guard. `chat_turn_spend` is one dated row per settled turn, written inside `finishTurn`'s existing latch so a late settle that moved no total writes no row either, and the running total beside it is left exactly as it is, because the chat page displays it and a column that quietly began meaning something narrower would be the worse repair. A thread that predates the table is backfilled as a single turn at its `updated_at` — bit-for-bit what the old query counted — inside the same transaction as the CREATE, since reading an un-backfilled table as $0 would *widen* the limit on the boot that upgrades, which is the one direction a limit must never move by accident. Five doors read it and no more — `createRun` (refused rather than queued, and inside that function rather than in `POST /api/runs`, because the chat's approval batch, a workflow's pass and a block's emission all arrive there too), `startRun`'s pre-cycle guard, `startWorkflow`, `startBlockTurn` and `assistRefusal` (which a chat turn, a review, a conflict resolution and a validation all pass) — and the pre-cycle one sits ahead of the instance guard because it is the wider limit and halting a whole graph over a limit that is not about that graph would take down blocks that are not the problem. This is emphatically **not** `buildPeriods` feeding a guard: that measures history against a weekly ceiling pro-rated over a span nobody set an allowance for, where this is a number the operator typed meaning what it says.

**`installSpend` reads a fifth place, and the reason it did not before stopped being true.** `run_reviews.cost_usd` was outside the install's rolling limit for as long as every row in that table was a person pressing something — a review and a merge-conflict resolution, one press each, with somebody watching what it produced. A **validation** is not: it fires whenever a run asks to close a task, which on a fleet is once per finished piece of work with nobody present. Left out, a limit that says "this install may spend $N a day" would not have counted the one spender the operator never triggered, and on a 20-block workflow that is twenty validations no instance budget bounds either. All three kinds are counted rather than validations alone, because what this reading *is* is money this app recorded spending inside the window, and a reviewed run's money is no less spent for having been asked for. **That is also why the block sum is `kind = 'orchestrator'` and nothing else:** a review block and an auto-resolving merge block copy their `run_reviews` rows' cost onto their own `cost_usd` so `instanceSpend`, which reads no `run_reviews`, can see it, and a block sum over every kind counted each of those dollars a second time and tripped the limit at half the money. An orchestrator block's deciding turn is the one spend with no other row. Bounded on `COALESCE(finished_at, created_at)`, the shape a block already uses; there is no estimated half, unlike a run and unlike a chat turn, because a child killed before it reported leaves the row `failed` and this app prices nothing for it. The other half of the same problem is on the child rather than in the reading: `spawnAssist` now takes an optional `--max-budget-usd`, passed by the validator off `validationBudgetUSD` and, since the paragraph below, by every conflict resolution off `resolutionBudgetUSD`, because a door is read once and a spender admitted at 99% of a window would otherwise have no limit at all.

**Counting a spender and refusing it are two halves, and the install limit had only the first for assists.** From the paragraph above until 2026-09-27, `installSpend` counted `run_reviews.cost_usd` and no assist asked `installBudgetRefusal`, so once `installDailyCostLimitUSD` was reached a review, a validation and a conflict resolution still started — including the one nobody presses, the merge queue draining a batch queued with auto-resolve, which is what a workflow merge block's `mergeAutoResolve` queues. A limit that counts a spender and never refuses it is a report about that spender. So **assists are inside what the rolling 24 hours bounds**: `assistRefusal` asks it after the process count and before `windowRefusal`, cheapest first (a `COUNT`, a handful of `SUM`s, a transcript scan), and the chat turn, which asked it beside that door, now asks it through it. What each caller does with the sentence is its own, and the automatic one is the decision worth stating. A review and the Resolve button return the sentence to the person. **An automatic resolution is failed, not left waiting**: its queue row fails with the sentence and `refusesEveryLaterResolution` stops the drain asking again for the rest of that batch's conflicts, as it already did for a spent window; clean branches behind it still land, because landing spends nothing, and a merge block reports the conflicting ones as not landed. The `waiting` a block's deciding turn gets is the process budget's answer, for a shortage that clears in minutes and that a settling child wakes. A rolling day clears when spend ages out of it, which no event announces, so waiting would need a timer on the landing path, where `isolation-and-landing.md` says nothing may have a clock. Failing is also how this limit already treats every other spender with nobody present: `startBlockTurn` fails the block on it, the pre-cycle guard stops the run and `createRun` refuses a schedule's press. A **validation** closes the task unchecked with the sentence as its reason, the validator's fail-open rule, because a task held open would sit claimed behind a run that the same limit stops at its next pre-cycle guard.

The door is read once, so what an admitted child spends has to be bounded on the child, and **every conflict resolution now carries `resolutionBudgetUSD` as `--max-budget-usd`**: $20 by default, about five times the $4.04 mean of this install's 59 completed resolutions (the spread was not recorded; eight in throwaway checkouts priced at $0.36 to $3.18 at list rates), blank to remove it, read at the spawn. It covers the button as well as the queue. "A person is there" decides who gets a refusal sentence and not who is bounded, because no control a person has reaches an assist's child once it is spawned: there is no stop on a `run_reviews` row, and `cancelBatch` takes the rest of the queue but not the child already running. One that trips is rolled back like any failed resolution. **Three things stay unbounded, deliberately.** A resolution still has **no clock**, `assistTimeoutMs` returning 0 for it: a wall clock cannot tell a wedged child from a large merge and it was ending the large merges, which is the landing rule, and the limit now bounds the spend a clock would have stood in for. What neither bounds is a child that spends nothing and never exits, which held one of `maxConcurrentAssists` and its repository's merge worker until a restart; that one is now ended by a silence deadline, `RESOLVE_SILENCE_MS`, an hour with nothing printed, which is `maxCycleSilenceMinutes`' shape rather than a budget, and `isolation-and-landing.md` records the measurement behind it and the landing rule it narrowed. A **review** carries no money limit, being one press under `plan` that its ten-minute clock ends. And the install limit is still a bound on what may *start*: every child admitted under it spends up to its own limit, so concurrent assists can carry the install past it by the sum of theirs, the same overshoot a work cycle and a chat turn already leave.
