# The doors that ask `windowGuardRefusal`, and the ones that do not

[← budgets-and-guards index](../budgets-and-guards.md) · [← termini, waiting out a window and the duration cap](termini-and-waiting.md)

Read before editing `windowGuardRefusal`, `fractionGuardRefusal` or `guardWindowsOf` in `src/lib/budget.ts`, the readings a route fetches before it asks them (`fleetGuardWindows`, `restartClosedGuardWindows`, `approvalGuardWindows`, `workflowGuardWindows`), or any code that creates or puts back a run whose budget can carry a fraction. Continues [Termini, waiting out a window and the duration cap](termini-and-waiting.md), which holds the terminus rule and the `no_ceiling` verdict these doors refuse on; the six doors are the first paragraph here.

**Six doors ask `windowGuardRefusal`, and every other way a run is made or put back does not.** `POST /api/runs` and `POST /api/runs/[id]/reopen` ask it of the policy on the wire. `POST /api/fleet` `reopen` asks it **per run**, of the budget it is about to hand `reopenRun` — the sheet's fields laid over that run's stored blob — because the stored blob is how a fraction reaches that door at all: the page's sheet sends `moreIterations` and `maxRunCostUSD` and neither fraction, so a refusal of a fraction on the wire alone would have closed nothing. Measured 2026-11-08 before it asked, through a stubbed CLI on an install with no weekly ceiling: a stopped run whose blob carried `maxWeeklyFraction: 0.5`, picked up with only `{ moreIterations: 1 }`, answered 200, was queued and spawned its cycle, with `enforceable: false` on the `budget` event and `run.guard_unreadable` on stdout — the guard recorded and never read, which is `no_ceiling` doing what `RUN_ENFORCEABLE_CODES` says it does. The refusal needs an async reading and `reopenFleet` is synchronous on purpose (`concurrency-and-ownership.md`), so the route fetches the readings first — `fleetGuardWindows` names which of Claude's and Codex's the batch needs, and none for a batch with no fraction guard in it, so the common press pays for no transcript scan — and hands them in. The merge that decides what a run will be bound by is one function, `pickUpBudget`, read by both the refusal and `reopenRun`, so the thing checked is the thing written. A refused run lands in `report.refused` by its short id and stays `stopped`; the rest of the batch goes ahead, and a batch that refused everything is the route's existing 400. A Codex run is judged against `codexGuardSnapshot`, never against the Claude reading beside it. A caller that hands `reopenFleet` no readings gets every fraction-guarded run refused, which is the safe way to be wrong. **The restart notice's press (`POST /api/runs/restarted`, `reopenRestartClosed`) is the fourth, and asks the same way of the stored blob alone** — it takes no sheet, so the blob is the whole budget — through the same `fractionGuardRefusal` and `guardWindowsOf` (in `budget.ts`, below both callers, because `fleet.ts` sits above `orchestrator.ts`), with the route fetching the readings `restartClosedGuardWindows` names before the synchronous loop. It was decided that it should refuse because the press is a bulk one by a person who cannot see the blobs, and the run it refuses costs them nothing: it stays `restart_closed`, so it stays in the notice's count and is named in `refused`, and its own page's reopen takes a budget they can edit. Measured 2026-11-08 through a stubbed CLI on an install with no weekly reading, one `restart_closed` row whose blob was `{ maxIterations: 1, maxWeeklyFraction: 0.5 }`: before, 200 with `reopened: 1`, one spawn, a `budget` event with `code: "no_ceiling"` and `enforceable: false`, the run `completed`; after, 200 with `reopened: 0` and the weekly sentence in `refused`, no spawn, the run `stopped` with `restart_closed` still 1. **A chat approval (`POST /api/chat/[id]/proposals`, through `approveRunBatch` and `approveProposal`) is the fifth, and asks of the budget `planProposal` hands `createRun`** — the set the card froze, or the template's budget read live. A fraction reaches it either way, because `PUT /api/settings` accepts one on `chatDefaultGuards.budget` and a template can hold one; both ship `null`, so a stock install is asked nothing and pays for no scan. It refuses the **click**, not the proposal: a 400 in the window's sentence, led by the card's title, with nothing decided and every proposal still `pending`, because `failed` is terminal and this clears when the reading returns. Refusing one member inside the batch would have failed its dependents for good while it stayed pending itself. The route fetches the readings (`approvalGuardWindows` names which) **before** it reads what is pending: `markProposal` overwrites without checking, so an `await` after that read lets a second click on the same card pass it and then mark the proposal the first one approved `failed` (read from the code, not driven). A direct caller of `approveProposal` that passes no readings gets every fraction-guarded proposal refused. Measured 2026-11-09, `docs/verification/budgets-and-guards.md`.

**A workflow's press of Run (`POST /api/workflows/[id]/run`, and a schedule's fire, through `startWorkflow`) is the sixth, and asks of every block the graph can create.** `startWorkflow` plans each node that becomes a run in one pass — run blocks, orchestrator blocks (the runs they emit take that template's guards) and the members of a loop's body — and asks `fractionGuardRefusal` of each plan's budget, the template's or `chatDefaultGuards`'. A refusal is a 400 led by the block's name, and nothing exists: no instance row, no run. The instance's own fraction guard was already asked there; this is the per-run one a member carries, a different budget. A Codex block is judged against `codexGuardSnapshot`, which the route fetches only when `workflowGuardWindows` says a block needs it, and a caller that hands `startWorkflow` none has such a block refused as unchecked. A schedule's fire is refused and recorded `refused` in the same sentence; it hands no Codex reading because `scheduleRefusal` already refuses a graph holding a block that reports no cost, which a Codex block is. Measured 2026-11-09, `docs/verification/budgets-and-guards.md`.

**The later creators of workflow members do not ask, on purpose, and record instead.** `advanceInstanceRound` (a node behind a block that had to settle first), `stepPass` (a loop's passes), `emitBlockRuns` and the review block's fix round (which carries the run it continues' stored budget) hand `createRun` the same template's guards hours later with nobody present, and each could refuse only by `upsertBlock(..., "blocked", ...)`. That is terminal and cascades `blocked` down the chain behind it, for a reading that may only have lapsed — `INSTANCE_ENFORCEABLE_CODES`' argument, which is why the instance's own `no_ceiling` is asked at the press and never after. They are also synchronous with no reading in hand, and an `await` there would break `createRun`'s folder claim. What records it is the member's own pre-cycle check: a `budget` event with `enforceable: false` and `run.guard_unreadable` on stdout. The price is that a template edited after the press to carry a fraction, or a reading lost since, starts a later member with its guard unread, recorded on that run's feed and not on the instance's page. The dreaming pass cannot carry a fraction at all: `dreamingRun.ts` writes `maxWeeklyFraction: null` and `maxSessionFraction: null`. A new door that creates or puts back a run whose budget can carry a fraction has to ask, with the run's own provider's reading, or say here that it does not.
