# A cycle's silence deadline, the refund when a pause cuts it and the wait on background sub-agents

[← budgets-and-guards index](../budgets-and-guards.md) · [← the enforcement modes](enforcement-modes.md)

Read before editing `cycleSilenceMs` and `maxCycleSilenceMinutes`, the `guard_refunds` and `MAX_PAUSES_PER_RUN` accounting around the loop's increment, or the `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` value set per cycle. Split out of [Enforcement modes and what bounds one cycle](enforcement-modes.md), whose three modes the first paragraph here calls "those".

**All three of those modes bound what a cycle may *spend*, and none of them bounds a cycle that spends nothing — so a work cycle also has a deadline, and the deadline is silence rather than wall clock.** `runIteration` registers `exit` and `close` and settles on nothing else, so a `claude` wedged on a socket read, or an agent's own tool call blocked on a read with no timeout, leaves that promise pending for the life of the process: the row stays `running`, holding its folder against every other run in that subtree, its checkout slot, and one of `maxConcurrentRuns` — recoverable only by restarting the container, since the live ticker is registered for the two non-default modes only, the sweeper selects `paused` rows, and `reconcileOnBoot` is a restart by definition. Every other child here already had one (git 30 minutes, a chat turn ten, an orchestrator block ten); the one that runs unattended for hours, twenty-five at a time, did not. `settings.maxCycleSilenceMinutes` (default 120) is that deadline and `cycleSilenceMs` narrows it at the spawn, `chatGuards`' read-time rule, with a floor rather than an off switch — the absence of a deadline is the defect, so there must be no way to type one. **Silence, not duration**, and the two are different guarantees: the clock is the time since the last thing the child printed and every stdout line and stderr chunk resets it, because a cycle that is still reporting is working however long it takes, and ending one for its *duration* is what `enforcement: "live"` is for. Deriving it from `maxDurationMinutes` — the obvious reading, and the one this deliberately does not take — would make `between-cycles` a live mode without saying so, and that mode is the default and the only one whose accounting is exact. The default is deliberately generous for the same reason: the stream is silent for the whole of one model turn and the whole of one tool call, so a run whose test suite takes an hour is silent for an hour and perfectly healthy, and the error is asymmetric — a killed working cycle loses paid work, where a slot recovered in two hours instead of one is still recovered the same day. While a background sub-agent is running the deadline is the larger of this and the default, because a tool running inside an agent prints nothing (`run-lifecycle/background-work.md`). It goes through `interruptRun` rather than killing the child itself, so there is still exactly one kill path: the `SIGINT`-first ladder gives the cycle its chance to report its own cost, the loop's post-cycle checkpoint picks the interrupt up like any other, and `reconcileKilledCycle` recovers the spend into `spent_usd_est`. What it deliberately does *not* do is settle the promise on its own — the folder goes to whatever is queued behind it the moment `runIteration` returns, so resolving while a child might still be writing there would trade a held slot for two agents in one working tree. `Interrupt.kind` gains `deadline` as a third value rather than reusing `guard`, and `interruptOutcome` is where that becomes something an operator reads: it ends the run **`failed`**, because `stopped` is what this app writes when a person or a rule they configured decided and nobody decided this, and a hung agent filed as "stopped" is the sentence that stops anyone looking for the cause. It is not on `LIVE_ENFORCEABLE_CODES` and is not a `BudgetStopCode` at all: a deadline on a child is not a budget re-read, which is the thing that list excludes.

**A cycle cut short by a pause is refunded to the counter.** The loop increments before it spawns, so a live interrupt — and a provider refusal, which does no work at all — lands on a cycle that has already been charged. A refusal this app makes itself before any child exists — containment, Codex's rules, the local sign-in — is not one of these: it is taken above the increment and charges nothing (`run-lifecycle/reopen-and-resume.md`). Left charged, `live-resume` with `maxIterations: 1` can only park and then stop at `cycles` without ever finishing: the pre-cycle guard checks cycles before the session window. **Unbounded, it is the opposite failure, and it was unbounded until the counter below existed.** A run whose cycle is longer than its guard's share of a window is cut, refunded and parked every window, so `iterations` never reaches `maxIterations` and a run with no time limit and no spending limit parks for ever, spending its guard fraction each window on a cycle whose work is thrown away. So the guard-cut refund is counted on `runs.guard_refunds` and stops at `MAX_PAUSES_PER_RUN`: past it a cut cycle stays charged, so over a run's whole life guard cuts add at most three billed invocations to what `maxIterations` buys. **A charged cut that reaches the cap ends the run where it is cut, not at the next check.** The cut is a pause, and it used to park like every other: the run then held its folder and its checkout until `sweepPaused` next looked, up to a whole 5-hour window later, only to end it `stopped` on the cycle cap — and everything queued behind it waited that long for a run that was already over. So the post-cycle interrupt site tests the cap itself when it withholds the refund, against `maxIterations` plus the pass's own `grantedCycles` (`termini-and-waiting.md`), and ends the run `stopped` with `cycleCapReason`, the verdict the pre-cycle guard and the sweeper would both have reached. A charged cut that leaves the run cycles to spend, a granted one included, still parks. The count is on the row and written with `iterations` in the same ending, because every cut ends a segment and a local would restart at zero; nothing resets it, `reopenRun` included, because it corrects `iterations` and a pick-up carries `iterations`. The same constant bounds the refusal allowance on a column of its own (`refusal_pauses`, `run-lifecycle.md`), which is what refunds a refused cycle; neither count is `pause_count`. The refund is applied at the post-cycle interrupt site only — `applyInterrupt`'s two other call sites run *before* the increment and would discount a cycle that completed. It also means `iterations` can no longer be read as "has this run worked before": the prompt/`--resume` choice keys on `sessionId === null`, and `ensureWorktree`'s orphaned-branch guard keys on `pause_count`, which counts every park and is never reset. The pre-cycle guard's `blocked`-or-`stopped` choice and the handoff card's gate ask `ranWorkCycle` over the loop's own refund counters (`everWorked` in `startRun`), not `iterations`: a refunded cycle that spent, refused by the run's spending limit on the next pass, ends `stopped` with its card, where `iterations === 0` wrote `blocked` beside a row showing the spend.

**A cycle that is only waiting on its background sub-agents is bound by three of these guards and not by the rest, and the duration limit is the one the CLI's wait ceiling has to carry.** In `-p` mode the CLI stays alive after the agent ends its turn while a background sub-agent runs, and it used to kill them at its own ten minutes, which bounded the wait by accident. `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` is now set per cycle to what is left of `maxDurationMinutes` (or `0` with none), because `between-cycles` reads that limit only before a cycle starts. `--max-budget-usd` and the silence deadline still bind during the wait (measured and read respectively); the window fractions and `maxRunTokens` do not, which is this mode's one-cycle overshoot and not new. `run-lifecycle/background-work.md` has the table, the two overshoots that remain, and what the next cycle is told when the CLI kills a task anyway.
