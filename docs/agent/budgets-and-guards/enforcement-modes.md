# Enforcement modes and what bounds one cycle

[← budgets-and-guards index](../budgets-and-guards.md)

Read before editing `evaluateBudget` or `LIVE_ENFORCEABLE_CODES` in `src/lib/budget.ts`, `liveGuardTick`, `cycleSilenceMs` or `needsLiveSpendTelemetry` in `src/lib/orchestrator.ts`, or the `--max-budget-usd` flag `buildArgs` passes in `src/lib/cycleInvocation.ts`.

**How guards are enforced is the operator's choice, and none of the three modes is a hard cap.** `BudgetPolicy.enforcement` selects it per run.

- `between-cycles` (the default) reads the guards only before each iteration. Overshoot is bounded by one iteration **per run active at the time**, and this is the only mode whose accounting is exact — every cycle reports its own cost.

- `live` also reads them on a global ticker (`liveGuardTick`, `settings.liveGuardIntervalSeconds`, floor 15s) while a child is in flight, and interrupts it. That bounds overshoot to *one model turn plus one interval plus the kill* instead, and costs the in-flight cycle's work. Every input moves per tick, but from three different places: `duration` off the run's worked minutes, the two window fractions off a fresh `currentSnapshot()`, and the run's own spend off telemetry (see below — the locals cannot supply it). Neither usage source is instant, and the window half is the older of the two: its preferred reading is the provider's own percentage, which `planUsage.ts` refreshes at most every five minutes and keeps serving for up to an hour while requests are being refused, so `guardFraction` also takes the derived reading — recomputed from the transcripts on every check — and acts on whichever is worse. Telemetry is a batch exporter a second or so behind. A verdict reached on a reading older than `STALE_PLAN_READING_MS` names its age in the reason, and every `budget` event carries `sessionPlanAgeMs`/`weeklyPlanAgeMs` so the log can tell a fresh decision from a frozen one. Tighter, not exact — say so in every piece of copy.

- `live-resume` is `live`, except the 5-hour window parks the run instead of ending it.

`LIVE_ENFORCEABLE_CODES` is the whitelist. `iterations` is excluded because the loop increments before it spawns — a live check must be passed `iterations - 1` or it kills the cycle the pre-cycle guard just authorised. `no_ceiling`/`no_terminus` are excluded because re-reading configuration mid-flight means a Settings edit in another tab kills a running agent. The ticker deliberately emits **no** `run_events` row per tick; only an interrupt is recorded.

**All three of those modes bound what a cycle may *spend*, and none of them bounds a cycle that spends nothing — so a work cycle also has a deadline, and the deadline is silence rather than wall clock.** `runIteration` registers `exit` and `close` and settles on nothing else, so a `claude` wedged on a socket read, or an agent's own tool call blocked on a read with no timeout, leaves that promise pending for the life of the process: the row stays `running`, holding its folder against every other run in that subtree, its checkout slot, and one of `maxConcurrentRuns` — recoverable only by restarting the container, since the live ticker is registered for the two non-default modes only, the sweeper selects `paused` rows, and `reconcileOnBoot` is a restart by definition. Every other child here already had one (git 30 minutes, a chat turn ten, an orchestrator block ten); the one that runs unattended for hours, twenty-five at a time, did not. `settings.maxCycleSilenceMinutes` (default 120) is that deadline and `cycleSilenceMs` narrows it at the spawn, `chatGuards`' read-time rule, with a floor rather than an off switch — the absence of a deadline is the defect, so there must be no way to type one. **Silence, not duration**, and the two are different guarantees: the clock is the time since the last thing the child printed and every stdout line and stderr chunk resets it, because a cycle that is still reporting is working however long it takes, and ending one for its *duration* is what `enforcement: "live"` is for. Deriving it from `maxDurationMinutes` — the obvious reading, and the one this deliberately does not take — would make `between-cycles` a live mode without saying so, and that mode is the default and the only one whose accounting is exact. The default is deliberately generous for the same reason: the stream is silent for the whole of one model turn and the whole of one tool call, so a run whose test suite takes an hour is silent for an hour and perfectly healthy, and the error is asymmetric — a killed working cycle loses paid work, where a slot recovered in two hours instead of one is still recovered the same day. It goes through `interruptRun` rather than killing the child itself, so there is still exactly one kill path: the `SIGINT`-first ladder gives the cycle its chance to report its own cost, the loop's post-cycle checkpoint picks the interrupt up like any other, and `reconcileKilledCycle` recovers the spend into `spent_usd_est`. What it deliberately does *not* do is settle the promise on its own — the folder goes to whatever is queued behind it the moment `runIteration` returns, so resolving while a child might still be writing there would trade a held slot for two agents in one working tree. `Interrupt.kind` gains `deadline` as a third value rather than reusing `guard`, and `interruptOutcome` is where that becomes something an operator reads: it ends the run **`failed`**, because `stopped` is what this app writes when a person or a rule they configured decided and nobody decided this, and a hung agent filed as "stopped" is the sentence that stops anyone looking for the cause. It is not on `LIVE_ENFORCEABLE_CODES` and is not a `BudgetStopCode` at all: a deadline on a child is not a budget re-read, which is the thing that list excludes.

**Every one of those three bounds is a bound on a count of cycles, so the run's own spending limit is enforced somewhere else as well — inside the CLI.** Read the modes above literally and `maxRunCostUSD` bounds *how many* cycles may start past a threshold and not *how much* the one crossing it spends: a run at $34.99 of a $35 limit was authorised for a further cycle of arbitrary size, which is the same sentence twenty-five times over on a fleet whose settings page reads $875. So `buildArgs` carries `--max-budget-usd` with `max(0, maxRunCostUSD - spentGuardUSD)` — the fourth kind of child getting the flag the other two already had, and the one that spends most. `spentGuardUSD` rather than `runs.spent_usd` is the whole of the arithmetic's correctness: the measured floor excludes a killed cycle's reconciled estimate, so a limit derived from it hands the child more room than the guard believes the run has left, which is the display-versus-guard split inverted at the one door where it costs money. The arithmetic is inside `buildArgs` rather than at the call site because it is pure and tested there and because both ways of getting it wrong are silent, and the two inputs are **required** parameters so a caller cannot drop the limit by omission. `maxRunTokens` has no equivalent and is still bounded by a whole cycle — the CLI's limit is denominated in dollars. What comes back is `result.subtype`, kept on `IterationResult` for this one member, and the branch that reads it sits **after** the interrupt check and **before** the refusal test. Before, and this is the expensive ordering: the CLI latches its own summary of a non-success result into `apiError`, `isUsageLimit` matches "reached your … limit" loosely on purpose because the provider labels its walls per window and per model, and a ceiling this app handed over read as the subscription allowance running out would park a `live-resume` run for hours waiting on money that is never coming. It ends the run `stopped` — the word the pre-cycle `run_cost` verdict already uses — with the limit and what had been spent against it named, and the cycle stays charged to `iterations` because it happened. That the pinned CLI honours the flag on a `-p` work cycle and reports that subtype is reasoned from `chat.ts` using the same flag against the same binary, not measured; it is on the README's *Not yet verified* list by name.

**`run_cost`/`run_tokens` are live only because telemetry makes them live — this is the one place OTLP feeds a budget decision.** The ticker's `progress()` closes over `startRun`'s locals, and `spentUSD`/`spentTokens` only move when the CLI's `result` event is folded in *after* `runIteration` returns — by which point the `finally` has already removed the `liveGuards` entry. Those locals are therefore the *completed cycles'* total and nothing else, which made `maxRunCostUSD` overshoot by one full cycle under `live` exactly as under `between-cycles`: a between-cycles guard wearing a live label. `telemetrySpendSince(runId, cycleStartedAt)` supplies the missing half, bounded by the cycle start so the cycles that already reported through `result` are not counted twice, and added to `spentGuardUSD`/`spentGuardTokens` — **never** to `spentUSD`, so `runs.spent_usd` stays a floor of what Claude Code itself measured. Same display-vs-guard split as `costUSD`/`costGuardUSD`. **That bound holds only while the guard's cycle is still running, so the tick checks after its scan that it is.** `liveGuardTick` takes its list of guards and then awaits `currentSnapshot()`, a coalesced scan that can take seconds, and a cycle ending inside that await is ordinary. A guard evaluated anyway reads the loop's live `spentUSD`, which by then includes the finished cycle's `result`, and adds `telemetrySpendSince` from that same cycle's start: the cycle counted twice. $3 reported and $3 of telemetry read $6 against a $5 limit, and a run that had spent $3 was stopped. With no child left to signal, `interruptRun` still records the stop, which then lands on the run's next cycle — or, if the loop has already exited, survives in a map nothing else clears and ends the run's next pick-up at once. So after the await the tick skips any run whose registered guard is not the one it took (`liveGuards.get(id) !== guard`), the identity test `checkContextCeilings` already makes, because the entry is re-set per cycle. As a second line, `startRun` discards a guard-kind interrupt it finds at the claim and logs that it did. This loop has no cycle in flight yet, so such a verdict can only be about one that has finished. It does not discard an operator's stop, which is a request about the run whenever it landed. **That split now holds on the recovery path too, which is the one place collapsing it cost money rather than accuracy.** `reconcileKilledCycle` returns `costUSD` *and* `costGuardUSD`: the first is the displayed figure and is what `spent_usd_est` and the run's own log carry, the second charges an unpriced model the fallback rate and is what the next pre-cycle check, the live ticker and `--max-budget-usd`'s remainder are computed from. Accumulating only the first left the guard side of a run on an unpriced model at exactly $0 however much it burned, so `maxRunCostUSD` could never fire on a run whose cycles are always killed before they report — precisely the run that function exists for. The two differ only for an unpriced model. What deliberately does **not** exist is a column for the guard half: `spentGuardEstUSD` is a local of `startRun`'s frame, hydrated from `spent_usd_est`, which is the *displayed* estimate — so what survives a restart or a pick-up is a floor and only this segment's own killed cycles are charged at the guard rate. Understating a guard is the direction that admits a cycle it should have refused, which is why it is stated here rather than left to be inferred from a column name. The window fractions were never part of this: they move on every tick already, off a fresh snapshot, and a run's own turns land in that scan — but that is the whole machine's counter, not this run's, which is why it does not substitute.

**A guard whose input is optional is not a guard, so the input stops being optional.** `settings.telemetryForRuns` opts into *reporting* — the dashboard card and the run card. A run whose policy needs telemetry to be enforceable (`needsLiveSpendTelemetry`: live enforcement, plus a run cost or token limit) gets `telemetryEnv(runId, required)` regardless of that setting — and what that function hands the child is a capability scoped to writing that one run's records, never `UF_AUTH_TOKEN`, which is why `middleware.ts` exempts the ingest path and the route checks the capability itself — because a guard that silently stops guarding when an unrelated toggle is off is the failure `guardCostOf()` exists to prevent for unpriced models. Refusing such a run at the door would have been the consistent alternative and was rejected: it refuses a policy that works today. `/api/usage` still gates its card on the setting, so nothing about the dashboard changes. What is *not* covered is an export that is configured and does not arrive — so the loop compares the CLI's own figure for each finished cycle against what telemetry reported for it, and logs a `run_events` line naming the cost when a paid cycle reported nothing. The alternative is a guard reading zero, which refuses nothing and looks exactly like a guard that was never reached.

**A cycle cut short by a pause is refunded to the counter.** The loop increments before it spawns, so a live interrupt — and a provider refusal, which does no work at all — lands on a cycle that has already been charged. Left charged, `live-resume` with `maxIterations: 1` can only park and then stop at `cycles` without ever finishing: the pre-cycle guard checks cycles before the session window. **Unbounded, it is the opposite failure, and it was unbounded until the counter below existed.** A run whose cycle is longer than its guard's share of a window is cut, refunded and parked every window, so `iterations` never reaches `maxIterations` and a run with no time limit and no spending limit parks for ever, spending its guard fraction each window on a cycle whose work is thrown away. So the guard-cut refund is counted on `runs.guard_refunds` and stops at `MAX_PAUSES_PER_RUN`: past it a cut cycle stays charged, so over a run's whole life guard cuts add at most three billed invocations to what `maxIterations` buys. **A charged cut that reaches the cap ends the run where it is cut, not at the next check.** The cut is a pause, and it used to park like every other: the run then held its folder and its checkout until `sweepPaused` next looked, up to a whole 5-hour window later, only to end it `stopped` on the cycle cap — and everything queued behind it waited that long for a run that was already over. So the post-cycle interrupt site tests the cap itself when it withholds the refund, against `maxIterations` plus the pass's own `grantedCycles` (`termini-and-waiting.md`), and ends the run `stopped` with `cycleCapReason`, the verdict the pre-cycle guard and the sweeper would both have reached. A charged cut that leaves the run cycles to spend, a granted one included, still parks. The count is on the row and written with `iterations` in the same ending, because every cut ends a segment and a local would restart at zero; nothing resets it, `reopenRun` included, because it corrects `iterations` and a pick-up carries `iterations`. The same constant bounds the refusal allowance on a column of its own (`refusal_pauses`, `run-lifecycle.md`), which is what refunds a refused cycle; neither count is `pause_count`. The refund is applied at the post-cycle interrupt site only — `applyInterrupt`'s two other call sites run *before* the increment and would discount a cycle that completed. It also means `iterations` can no longer be read as "has this run worked before": the prompt/`--resume` choice keys on `sessionId === null`, and `ensureWorktree`'s orphaned-branch guard keys on `pause_count`, which counts every park and is never reset.

**A cycle that is only waiting on its background sub-agents is bound by three of these guards and not by the rest, and the duration limit is the one the CLI's wait ceiling has to carry.** In `-p` mode the CLI stays alive after the agent ends its turn while a background sub-agent runs, and it used to kill them at its own ten minutes, which bounded the wait by accident. `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` is now set per cycle to what is left of `maxDurationMinutes` (or `0` with none), because `between-cycles` reads that limit only before a cycle starts. `--max-budget-usd` and the silence deadline still bind during the wait (measured and read respectively); the window fractions and `maxRunTokens` do not, which is this mode's one-cycle overshoot and not new. `run-lifecycle/background-work.md` has the table, the two overshoots that remain, and what the next cycle is told when the CLI kills a task anyway.
