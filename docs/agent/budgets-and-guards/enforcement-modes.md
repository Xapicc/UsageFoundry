# Enforcement modes and what bounds one cycle

[← budgets-and-guards index](../budgets-and-guards.md)

Read before editing `evaluateBudget` or `LIVE_ENFORCEABLE_CODES` in `src/lib/budget.ts`, `liveGuardTick` or `needsLiveSpendTelemetry` in `src/lib/orchestrator.ts`, or the `--max-budget-usd` flag `buildArgs` passes in `src/lib/cycleInvocation.ts`. The cycle's silence deadline (`cycleSilenceMs`), the refund of a cycle a pause cut short and the wait on background sub-agents are in [A cycle's silence deadline, the refund when a pause cuts it and the wait on background sub-agents](silence-refunds-and-background-waits.md).

**How guards are enforced is the operator's choice, and none of the three modes is a hard cap.** `BudgetPolicy.enforcement` selects it per run.

- `between-cycles` (the default) reads the guards only before each iteration. Overshoot is bounded by one iteration **per run active at the time**, and this is the only mode whose accounting is exact — every cycle reports its own cost.

- `live` also reads them on a global ticker (`liveGuardTick`, `settings.liveGuardIntervalSeconds`, floor 15s) while a child is in flight, and interrupts it. That bounds overshoot to *one model turn plus one interval plus the kill* instead, and costs the in-flight cycle's work. Every input moves per tick, but from three different places: `duration` off the run's worked minutes, the two window fractions off a fresh `currentSnapshot()`, and the run's own spend off telemetry (see below — the locals cannot supply it). Neither usage source is instant, and the window half is the older of the two: its preferred reading is the provider's own percentage, which `planUsage.ts` refreshes at most every five minutes and keeps serving for up to an hour while requests are being refused, so `guardFraction` also takes the derived reading — recomputed from the transcripts on every check — and acts on whichever is worse. Telemetry is a batch exporter a second or so behind. A verdict reached on a reading older than `STALE_PLAN_READING_MS` names its age in the reason, and every `budget` event carries `sessionPlanAgeMs`/`weeklyPlanAgeMs` so the log can tell a fresh decision from a frozen one. Tighter, not exact — say so in every piece of copy.

- `live-resume` is `live`, except the 5-hour window parks the run instead of ending it.

`LIVE_ENFORCEABLE_CODES` is the whitelist. `iterations` is excluded because the loop increments before it spawns — a live check must be passed `iterations - 1` or it kills the cycle the pre-cycle guard just authorised. `no_ceiling`/`no_terminus` are excluded because re-reading configuration mid-flight means a Settings edit in another tab kills a running agent. The ticker deliberately emits **no** `run_events` row per tick; only an interrupt is recorded.

**Every one of those three bounds is a bound on a count of cycles, so the run's own spending limit is enforced somewhere else as well — inside the CLI.** Read the modes above literally and `maxRunCostUSD` bounds *how many* cycles may start past a threshold and not *how much* the one crossing it spends: a run at $34.99 of a $35 limit was authorised for a further cycle of arbitrary size, which is the same sentence twenty-five times over on a fleet whose settings page reads $875. So `buildArgs` carries `--max-budget-usd` with `max(0, maxRunCostUSD - spentGuardUSD)` (or the install's or workflow's headroom where that is smaller or the run has no limit: [cycle-argv-and-notices.md](../run-lifecycle/cycle-argv-and-notices.md)) — the fourth kind of child getting the flag the other two already had, and the one that spends most. `spentGuardUSD` rather than `runs.spent_usd` is the whole of the arithmetic's correctness: the measured floor excludes a killed cycle's reconciled estimate, so a limit derived from it hands the child more room than the guard believes the run has left, which is the display-versus-guard split inverted at the one door where it costs money. The arithmetic is inside `buildArgs` rather than at the call site because it is pure and tested there and because both ways of getting it wrong are silent, and the two inputs are **required** parameters so a caller cannot drop the limit by omission. `maxRunTokens` has no equivalent and is still bounded by a whole cycle — the CLI's limit is denominated in dollars. What comes back is `result.subtype`, kept on `IterationResult` for this one member, and the branch that reads it sits **after** the interrupt check and **before** the refusal test. Before, and this is the expensive ordering: the CLI latches its own summary of a non-success result into `apiError`, `isUsageLimit` matches "reached your … limit" loosely on purpose because the provider labels its walls per window and per model, and a ceiling this app handed over read as the subscription allowance running out would park a `live-resume` run for hours waiting on money that is never coming. It ends the run `stopped` — the word the pre-cycle `run_cost` verdict already uses — with the limit and what had been spent against it named, and the cycle stays charged to `iterations` because it happened. That the pinned CLI honours the flag on a `-p` work cycle and reports that subtype is reasoned from `chat.ts` using the same flag against the same binary, not measured; it is on the README's *Not yet verified* list by name.

**`run_cost`/`run_tokens` are live only because telemetry makes them live — this is the one place OTLP feeds a budget decision.** The ticker's `progress()` closes over `startRun`'s locals, and `spentUSD`/`spentTokens` only move when the CLI's `result` event is folded in *after* `runIteration` returns — by which point the `finally` has already removed the `liveGuards` entry. Those locals are therefore the *completed cycles'* total and nothing else, which made `maxRunCostUSD` overshoot by one full cycle under `live` exactly as under `between-cycles`: a between-cycles guard wearing a live label. `telemetrySpendSince(runId, cycleStartedAt)` supplies the missing half, bounded by the cycle start so the cycles that already reported through `result` are not counted twice, and added to `spentGuardUSD`/`spentGuardTokens` — **never** to `spentUSD`, so `runs.spent_usd` stays a floor of what Claude Code itself measured. Same display-vs-guard split as `costUSD`/`costGuardUSD`. **That bound holds only while the guard's cycle is still running, so the tick checks after its scan that it is.** `liveGuardTick` takes its list of guards and then awaits `currentSnapshot()`, a coalesced scan that can take seconds, and a cycle ending inside that await is ordinary. A guard evaluated anyway reads the loop's live `spentUSD`, which by then includes the finished cycle's `result`, and adds `telemetrySpendSince` from that same cycle's start: the cycle counted twice. $3 reported and $3 of telemetry read $6 against a $5 limit, and a run that had spent $3 was stopped. With no child left to signal, `interruptRun` still records the stop, which then lands on the run's next cycle — or, if the loop has already exited, survives in a map nothing else clears and ends the run's next pick-up at once. So after the await the tick skips any run whose registered guard is not the one it took (`liveGuards.get(id) !== guard`), because the entry is re-set per cycle. As a second line, `startRun` discards a guard-kind interrupt it finds at the claim and logs that it did. This loop has no cycle in flight yet, so such a verdict can only be about one that has finished. It does not discard an operator's stop, which is a request about the run whenever it landed. **That split now holds on the recovery path too, which is the one place collapsing it cost money rather than accuracy.** `reconcileKilledCycle` returns `costUSD` *and* `costGuardUSD`: the first is the displayed figure and is what `spent_usd_est` and the run's own log carry, the second charges an unpriced model the fallback rate and is what the next pre-cycle check, the live ticker and `--max-budget-usd`'s remainder are computed from. Accumulating only the first left the guard side of a run on an unpriced model at exactly $0 however much it burned, so `maxRunCostUSD` could never fire on a run whose cycles are always killed before they report — precisely the run that function exists for. The two differ only for an unpriced model. What deliberately does **not** exist is a column for the guard half: `spentGuardEstUSD` is a local of `startRun`'s frame, hydrated from `spent_usd_est`, which is the *displayed* estimate — so what survives a restart or a pick-up is a floor and only this segment's own killed cycles are charged at the guard rate. Understating a guard is the direction that admits a cycle it should have refused, which is why it is stated here rather than left to be inferred from a column name. The window fractions were never part of this: they move on every tick already, off a fresh snapshot, and a run's own turns land in that scan — but that is the whole machine's counter, not this run's, which is why it does not substitute.

**A guard whose input is optional is not a guard, so the input stops being optional.** `settings.telemetryForRuns` opts into *reporting* — the dashboard card and the run card. A run whose policy needs telemetry to be enforceable (`needsLiveSpendTelemetry`: live enforcement, plus a run cost or token limit) gets `telemetryEnv(runId, required)` regardless of that setting — and what that function hands the child is a capability scoped to writing that one run's records, never `UF_AUTH_TOKEN`, which is why `middleware.ts` exempts the ingest path and the route checks the capability itself — because a guard that silently stops guarding when an unrelated toggle is off is the failure `guardCostOf()` exists to prevent for unpriced models. Refusing such a run at the door would have been the consistent alternative and was rejected: it refuses a policy that works today. `/api/usage` still gates its card on the setting, so nothing about the dashboard changes. What is *not* covered is an export that is configured and does not arrive — so the loop compares the CLI's own figure for each finished cycle against what telemetry reported for it, and logs a `run_events` line naming the cost when a paid cycle reported nothing. The alternative is a guard reading zero, which refuses nothing and looks exactly like a guard that was never reached.

**A Codex run's `run_tokens` is live off its session rollout, and its `run_cost` is never live because there is no cost.** `codex exec` exports no telemetry this app can ingest, so `liveSpendTelemetry` is false for a Codex run whatever its policy asks — the telemetry variables would be set for nothing, and the post-cycle "a paid cycle reported nothing" check would misread every Codex cycle as a broken export. Nor is a Codex cycle handed the variables at all, `settings.telemetryForRuns` included: `cycleTelemetryEnv` withholds them, because the rollout below never reads `otlp_requests` and the ingest capability's only use in that child would be posting records of its own. What stands in for it is `codexRollout.ts`: `beginCodexCycle` notes where the cycle's part of the thread's rollout starts *before* the spawn, so a resumed thread's earlier cycles are behind that line, and `codexInFlightSpend` hands the guard's `progress()` the cycle's running `token_count` total as `tokens`, with `costUSD` zero. That total is exactly the figure `turn.completed` then reports for the cycle — measured equal on a one-cycle and a two-cycle run, 2026-10-07 — so nothing is counted twice when the cycle's `result` is folded in after the guard entry has gone. A cycle that ends without `turn.completed` — killed by this guard, among others — banks that same total into `spent_tokens_est` once it has returned, which `spentGuardTokens` and `reopenRun` count, so a run stopped at its limit is not reopened under it (`metering/codex-killed-cycles.md`). It is read on the live tick rather than per request, so a Codex run stops a little past its token limit rather than at it, and the run's log says so at its start when the policy has a live token limit. A file found only after a resumed cycle began is read from its end at that moment, which makes the reading a floor rather than a figure counting a past cycle again. `maxRunCostUSD` still cannot act on a Codex run — `spent_usd` is a zero that measures nothing — and the run form says so beside the field and offers `maxRunTokens` for that provider instead. A workflow's spending limit has the same blindness one level up, over its Codex members and a loop's Codex passes, and its answer is in `workflows-and-schedules/instance-budget.md`.
