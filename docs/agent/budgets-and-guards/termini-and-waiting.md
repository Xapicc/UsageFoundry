# Termini, waiting out a window and the duration cap

[← budgets-and-guards index](../budgets-and-guards.md)

Read before editing `no_terminus`, `providerTerminusRefusal` or `normalizePolicy` in `src/lib/budget.ts`, `runs.paused_ms`, or how `src/lib/validation.ts` extends `maxIterations`.

**A run's provider changes nothing about the terminus rule and everything about the sentence.** `maxIterations` and `maxDurationMinutes` are the only two monotone termini whatever CLI runs the cycle, so `no_terminus` — refused at `POST /api/runs` and again in `evaluateBudget` — already means "one of these two must be present" for every run. `providerTerminusRefusal` tests that same condition and is therefore *not* a new gate; it is checked immediately before the generic one so that its sentence is the one a person sees, and both stay reachable because it fires only for a provider this app cannot meter. What it adds is the reason, and the reason is different in kind rather than in degree: a Claude run refused for no terminus still had three limits doing real work — the two window fractions read this account's own utilisation, and `maxRunCostUSD` reaches the cycle as `--max-budget-usd` — where for a provider whose usage this app cannot read, the fractions measure a population that run is not in and no in-cycle ceiling is handed to anything. Telling that operator only "nothing would ever end it" leaves them believing the percentages they set were a safety net. Constraint C2 in `proposals/ProviderFallback/01-constraints.md`, and the whole point of choosing the provider at a form rather than at a wall is that this refusal lands where somebody is watching. It is deliberately not enforced in `normalizePolicy`, which has no error channel, for the reason `no_terminus` is not.

**Only the 5-hour window can be waited out.** It is the sole quantity that refills on its own, on a schedule, with no configuration. The weekly window does not qualify: with `weeklyAnchor` unset (the default) `weekly.endsAt === now`, so there is no reset instant at all — the trailing total merely decays over days. `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume` and for nothing else, as a discriminated union so `resumeAt` is unreachable without narrowing. The check order — terminus, cycles, duration, run spend, weekly, *then* session — is load-bearing: a run that is out of time **and** out of window must end, not park, or the clock stops being a terminus. It is the same order now that the clock measures worked minutes, and for a sharper reason: the sweeper re-runs this verdict on a parked row with the open park subtracted, so a run reaching `duration` there is one that was already out of time when it parked — and parking it again would be a decision to wait for a window that cannot change the answer. **And a window that cannot be read must not end that order early.** `no_ceiling` is the one verdict nothing acts on, so returning it where it is found disabled every guard below it: an install with a real 5-hour reading and no weekly one never reached the session check at all, and a `live-resume` run at 97% of a 50% 5-hour guard logged that the *weekly* guard could not be enforced and spawned the cycle anyway — with nothing catching it at the door either, since workflow members and chat approvals never pass `windowGuardRefusal`. The verdict is now **held** and returned only once every readable guard has passed, through a `??=` so the window checked first names the refusal, which is the precedence `windowGuardRefusal` already gives it. A park is decided about a guard that *was* read, so it has to have had its chance above before an unreadable one speaks. `evaluateInstanceBudget` has the same shape for the sharper version of the same reason: returning it where it is found switches the 5-hour guard off silently for every block of the instance.

**`maxDurationMinutes` caps the minutes a run *worked*, not the wall clock since it started — and it is still a terminus.** A run that parks on the 5-hour window used to go on burning its time cap while it sat doing nothing, so when the window refilled and the run resumed, the pre-cycle duration check ended it on the first cycle after the wait: the guard charged it for the hours it had just spent waiting for that guard's own sibling. `runs.paused_ms` is the correction. It accumulates parked milliseconds, `startRun` closes the open park into it at the claim that takes the run back to `running`, and `evaluateBudget` subtracts it from `now - startedAt`. The terminus argument survives intact because worked time still only ever goes up while a run is working and nothing a run does subtracts from it — the only way to add to `paused_ms` is to *stop* working — and `maxIterations` did not move at all. What did move, and must be said rather than inferred, is that the cap is no longer a bound on how long a run may **exist**: a run that parks four times can outlive a 60-minute cap by however long those windows kept it waiting. What bounds *that* is `maxIterations`, and only `maxIterations`, which is exactly what the wall clock used to cover — and it holds only because the refund of a guard-cut cycle is bounded too. `MAX_PAUSES_PER_RUN` caps two counts and never guard *parks*: the refusals one run may wait out (`refusal_pauses`), and the cycles a live guard may cut and have refunded (`guard_refunds`), past which a cut cycle is charged and `iterations` advances even for a run whose every cycle is cut. A park at the pre-cycle check spent no cycle, so nothing is refunded and nothing is counted. Say the shape out loud, because it is the price of the change and nothing in the code will say it for you: a `live-resume` run the sweeper hands back into a window that has closed again before its pre-cycle check parks again having worked no minutes, and a run with a time limit and no cycle cap can repeat that indefinitely. A wall-clock backstop beside the worked-minutes cap is the obvious answer and is deliberately not here, because it is the guard this replaced under another name; the answer for a run that may park is a cycle cap.

Three rules follow from the column rather than from the arithmetic, and each fails silently. **Every exit from `paused` must close the park**, not just the one that resumes: a run stopped, ended by the sweeper or closed out by a boot while parked leaves a final row whose `paused_ms` is short by the park it died in, and the run page then draws those hours as worked minutes on a figure nothing will ever correct — `pauseClosedAt` is the one patch all three of those writes spread. **`paused_ms` travels with `started_at`**: `reopenRun` nulls the clock, so it zeroes the correction in the same statement, or a picked-up run carries yesterday's parked hours as credit against a cap it has not spent a minute of. And **the one guard site with a park in flight is `sweepPaused`**, which adds `now - paused_at` to the closed total before it evaluates; without that the parked run's measured span grows while it waits and the sweeper ends on `duration` precisely the runs it exists to hand back. The browser needs the same arithmetic — `pausedMsAt` in `apiTypes.ts` is shared by the run page's time bar and by the orchestrator, so a parked run's bar is frozen at the figure the guard is about to read rather than creeping towards a limit that will not fire.

**One guard can now be extended, by a bounded count, and nothing else about the terminus rule moves.** `maxIterations` and `maxDurationMinutes` are the only two monotone termini and `no_terminus` refuses a run with neither; the external validator (`validation.ts`, routed from `docs/agent/taskboard.md`) is the one thing in the app that can add to the first. It does it the way the context ceiling's refund does and for the same reason `MAX_EARLY_ENDS_PER_RUN` exists: `runs.validation_cycles` only ever increases, it is written straight to the row so a restart cannot reset it, and `maxValidationCycles` is its ceiling — floored at zero, and **the one budget-shaped field in `Settings` that may never be null**, because a limit that can be removed is a run nothing ends. A grant is permission to *ask* for another cycle and never permission to have one: `evaluateBudget` at the top of that cycle reads duration, run spend, both window fractions and the install's own daily ceiling exactly as it did, in the same order, so a run that is out of time or out of money still ends there. Zero is a real setting rather than an off switch with a different name — the task is still held open and the operator is still told why, which is the notify-only design the pitch recommends, arrived at through a number.
