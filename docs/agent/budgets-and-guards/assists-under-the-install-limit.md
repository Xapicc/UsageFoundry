# Assists under the install's rolling limit: counting them, refusing them and bounding their children

[← budgets-and-guards index](../budgets-and-guards.md) · [← the install's rolling limit](concurrency-and-install-ceiling.md)

Read before editing `installSpend`'s reading of `run_reviews.cost_usd`, `assistRefusal`'s ask of `installBudgetRefusal`, `resolutionBudgetUSD` or the `--max-budget-usd` `spawnAssist` passes. Continues [Concurrency caps and the install's rolling limit](concurrency-and-install-ceiling.md), which holds the limit's four readings and the doors that ask it; the fifth reading is the first paragraph here.

**`installSpend` reads a fifth place, and the reason it did not before stopped being true.** `run_reviews.cost_usd` was outside the install's rolling limit for as long as every row in that table was a person pressing something — a review and a merge-conflict resolution, one press each, with somebody watching what it produced. A **validation** is not: it fires whenever a run asks to close a task, which on a fleet is once per finished piece of work with nobody present. Left out, a limit that says "this install may spend $N a day" would not have counted the one spender the operator never triggered, and on a 20-block workflow that is twenty validations no instance budget bounds either. All three kinds are counted rather than validations alone, because what this reading *is* is money this app recorded spending inside the window, and a reviewed run's money is no less spent for having been asked for. **That is also why the block sum is `kind = 'orchestrator'` and nothing else:** a review block and an auto-resolving merge block copy their `run_reviews` rows' cost onto their own `cost_usd` so `instanceSpend`, which reads no `run_reviews`, can see it, and a block sum over every kind counted each of those dollars a second time and tripped the limit at half the money. An orchestrator block's deciding turn is the one spend with no other row. Bounded on `COALESCE(finished_at, created_at)`, the shape a block already uses; there is no estimated half, unlike a run and unlike a chat turn, because a child killed before it reported leaves the row `failed` and this app prices nothing for it. The other half of the same problem is on the child rather than in the reading: `spawnAssist` now takes an optional `--max-budget-usd`, passed by the validator off `validationBudgetUSD` and, since the paragraph below, by every conflict resolution off `resolutionBudgetUSD`, because a door is read once and a spender admitted at 99% of a window would otherwise have no limit at all.

**Counting a spender and refusing it are two halves, and the install limit had only the first for assists.** From the paragraph above until 2026-09-27, `installSpend` counted `run_reviews.cost_usd` and no assist asked `installBudgetRefusal`, so once `installDailyCostLimitUSD` was reached a review, a validation and a conflict resolution still started — including the one nobody presses, the merge queue draining a batch queued with auto-resolve, which is what a workflow merge block's `mergeAutoResolve` queues. A limit that counts a spender and never refuses it is a report about that spender. So **assists are inside what the rolling 24 hours bounds**: `assistRefusal` asks it after the process count and before `windowRefusal`, cheapest first (a `COUNT`, a handful of `SUM`s, a transcript scan), and the chat turn, which asked it beside that door, now asks it through it. What each caller does with the sentence is its own, and the automatic one is the decision worth stating. A review and the Resolve button return the sentence to the person. **An automatic resolution is failed, not left waiting**: its queue row fails with the sentence and `refusesEveryLaterResolution` stops the drain asking again for the rest of that batch's conflicts, as it already did for a spent window; clean branches behind it still land, because landing spends nothing, and a merge block reports the conflicting ones as not landed. The `waiting` a block's deciding turn gets is the process budget's answer, for a shortage that clears in minutes and that a settling child wakes. A rolling day clears when spend ages out of it, which no event announces, so waiting would need a timer on the landing path, where `isolation-and-landing.md` says nothing may have a clock. Failing is also how this limit already treats every other spender with nobody present: `startBlockTurn` fails the block on it, the pre-cycle guard stops the run and `createRun` refuses a schedule's press. A **validation** closes the task unchecked with the sentence as its reason, the validator's fail-open rule, because a task held open would sit claimed behind a run that the same limit stops at its next pre-cycle guard.

The door is read once, so what an admitted child spends has to be bounded on the child, and **every conflict resolution now carries `resolutionBudgetUSD` as `--max-budget-usd`**: $20 by default, about five times the $4.04 mean of this install's 59 completed resolutions (the spread was not recorded; eight in throwaway checkouts priced at $0.36 to $3.18 at list rates), blank to remove it, read at the spawn. It covers the button as well as the queue. "A person is there" decides who gets a refusal sentence and not who is bounded, because no control a person has reaches an assist's child once it is spawned: there is no stop on a `run_reviews` row, and `cancelBatch` takes the rest of the queue but not the child already running. One that trips is rolled back like any failed resolution. **Three things stay unbounded, deliberately.** A resolution still has **no clock**, `assistTimeoutMs` returning 0 for it: a wall clock cannot tell a wedged child from a large merge and it was ending the large merges, which is the landing rule, and the limit now bounds the spend a clock would have stood in for. What neither bounds is a child that spends nothing and never exits, which held one of `maxConcurrentAssists` and its repository's merge worker until a restart; that one is now ended by a silence deadline, `RESOLVE_SILENCE_MS`, an hour with nothing printed, which is `maxCycleSilenceMinutes`' shape rather than a budget, and `isolation-and-landing.md` records the measurement behind it and the landing rule it narrowed. A **review** carries no money limit, being one press under `plan` that its ten-minute clock ends. And the install limit is still a bound on what may *start*: every child admitted under it spends up to its own limit, so concurrent assists can carry the install past it by the sum of theirs, the same overshoot a work cycle and a chat turn already leave.
