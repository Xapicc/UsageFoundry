# Retention: what is evidence and what is permanent

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/retention.ts.**

**Three stores, one retention decision, and the decision is what a run's row is for.** `run_events` in the named volume, `.uf-worktrees` on the workspace bind mount, `~/.claude/projects` in the operator's own home — three media, three growth rates, and for a long time not one `DELETE` between them. They were filed as three findings because each sweep found the store in front of it, and they are **one** design because they share one question: what is safe to discard, and what does this app promise about history it has already shown somebody. The answer is a single sentence. **A run's row is permanent; everything behind it is evidence, and evidence has a horizon.** Nothing in `retention.ts` deletes a `runs` row, a `run_reviews` row, a `workflow_instance_*` row or a settings key, so every figure this app has ever put on the dashboard, the runs list or a run's own state card keeps reading true for ever — the spend columns, the cycle count, the stop reason, the branch, the landing record. What each sweep removes is the *working material* those figures were derived from: the event log's payloads, the checkout on disk, the session transcript. Each is bounded by its own horizon in Settings (`eventRetentionDays` 30, `checkoutRetentionDays` 7, `transcriptRetentionDays` 30; `null` on any of them means keep for ever, the reading every switchable rule here takes), and each horizon is separate because the media are — a checkout is hundreds of megabytes and is rebuilt by `worktree add` in seconds, where a transcript is the only thing `--resume` can continue.

Four properties are shared by all three sweeps and none of them is optional. **Nothing in flight is touched**: a non-terminal run keeps its whole event log, a checkout an active run holds is skipped by name, and a transcript whose session id belongs to a live run or to any chat is never a candidate — which is why each sweep asks the *database* what is live rather than inferring it from a file's age. **The decision is pure and the syscall is not**: `reclaimableCheckouts` and `expiredTranscripts` are the two functions that decide what goes, and both are unit-tested against fixtures, for `releasableRuns`' reason — every way of being wrong here is silent, lands on somebody's disk, and throws nothing. **A removal is recorded where the operator would look for it**: a reclaimed checkout emits a `land` event on its own run, and every sweep's counts are stored under `retention.lastSweep` and shown on the Settings page beside the sizes. And **a sweep never destroys the only copy of anything**: it removes no branch and no commit (`worktree remove` without `--force`, so git gets a second veto), it never touches the operator's own checkout, and a transcript it removes is one whose spend is already recorded in `runs.spent_usd` and in the `run_events` row that reported it.

Two consequences are written down rather than absorbed. **A pruned transcript takes its session with it**, so the sweep clears `runs.session_id` on the terminal runs it belonged to: `--resume` against a file that is gone fails the first cycle of a pick-up outright, where a null session id is already the documented restart — `nextPrompt` writes the task with `priorWorkNotice` naming the branch. Clearing is what turns a silent failure into the path this app already has. **And it shortens the dashboard's own history**, which is the one place the promise above is genuinely at risk: `buildPeriods` offers twelve months and a 30-day horizon empties eleven of them. Making the horizon a year would defeat the retention, so the card says so instead — `PeriodSeries.completeFrom` carries the cutoff, `/api/usage` fills it from the same setting the sweep reads, and any bucket that starts before it is marked as covering transcripts that have since been pruned. `buildPeriods` already drops buckets that closed before the first entry, so the effect is a *shorter* history rather than a wrong one; the sentence exists for the one bucket the cutoff falls inside. Nothing here reaches `evaluateBudget`: a guard reads the 5-hour and weekly windows, both far inside every horizon.

**`runs.provider` is permanent, and the clause that matters is that no sweep may ever write to it.** It is one column on a row this module already promises to keep, so it needs no horizon and gets none; it is written down here because `null` on it is load-bearing in a way `runs.session_id` above is not. `session_id` is cleared *by* a sweep precisely so that a missing transcript reads as the restart path this app already has. `provider` is the opposite: `null` means the row predates the column and nobody ever recorded what it ran as, the run page renders exactly that and never "Claude", and a future sweep that cleared the column — or a migration that backfilled it — would be manufacturing an answer to a question that was never asked. Which agent CLI produced a diff is the one thing a reviewer reading a two-year-old landed run cannot recover from anywhere else, so it keeps for as long as the row does. Nothing derived from it may be summed into `runs.spent_usd` or any window meter; `architecture.md:10`'s rule about the three populations is what forbids it, and this column changes nothing about that.

**A fourth table rides the event sweep, and which sweep it rides is the decision.** `context_samples` is the occupancy series `run-lifecycle.md` describes — a row per moved `usage` frame per live run, written on the run loop's own path — so it is exactly the shape this module exists to bound. It goes with `run_events`: same horizon, same `settled` test, because it is the same kind of thing as the log it sits beside on the same page, and a series that outlived its own log would be a graph with nothing left to read it against. It deliberately does **not** get `prune_receipts`' treatment, which is permanent because a weekly KPI cannot lose the evidence behind its first days; nothing aggregates samples across runs, so nothing here is a figure that would silently stop covering a week. The other half of the bound is on insert — `CONTEXT_SAMPLES_PER_RUN`, oldest first — because a run with no cycle cap has nothing bounding how many turns it takes, and a horizon alone would leave one such run unbounded for as long as it lives. The two are not redundant: the cap bounds a run, the sweep bounds the install.

**A fifth table rides it on the fourth's ticket, and one clause is its own.** `context_compositions` is the other half of the same picture — `winnow context` at each paced reading, a row per provenance — so it takes `context_samples`' horizon, `settled` test and per-run cap without argument: it is drawn on the same card, on the same axis, and a composition outliving the occupancy it apportions is a stack of bands with no total left to read them against. Where it differs is what the cap counts. `CONTEXT_COMPOSITIONS_PER_RUN` bounds a run in **readings**, not rows, and the delete is keyed on `reading` rather than on `id`: one reading is six rows, and a cap counted in rows would truncate a reading down the middle, leaving a stack whose bands stop at different moments — a picture of a conversation that never happened, drawn without an error anywhere. The horizon sweep has no such trouble, since every row of a reading carries the same `ts`. `context_composition_children` — the newest reading's tree, the two levels below a band — rides the same clause one level further down, and needs no cap of its own on this side: `recordComposition` deletes the run's rows and rewrites them on every reading, so the store holds one tree per run and the horizon is only there to stop that tree outliving the run it describes. It carries the reading's own `ts`, written by the same statement, so one cutoff settles both and neither can be left behind by the other. Its rows are added into the sweep's `compositions` figure rather than reported separately, on the grounds that the number answers how much came out and not which of the two tables it came from.

**The taskboard rides no sweep at all, and the refusal is the decision rather than an omission.** `tasks` is the one table added since this file was written that no horizon reaches, and it is on the `runs` side of this module's one question rather than the evidence side. A task is not working material behind a figure somebody was shown — it *is* the thing somebody was shown, and it is the only copy: the brief in `tasks.body` is the text a future agent is handed with nothing else to go on, and there is no transcript, no event log and no checkout it can be recovered from. So **an open task never expires**, on the plainest reading of the sentence at the top of this file: it is the operator's backlog, losing it silently is the worst outcome this feature has, and a horizon that quietly emptied a backlog would be indistinguishable from an install where nobody had written anything down. **A closed one is kept until the operator deletes it**, and that is the same decision one step further rather than a second one — `done` and `dropped` are what this install got done and what it decided against, which is exactly the kind of answer `runs.spent_usd` is kept for ever to be able to give, and a board that could only answer for the last thirty days would be a board nobody could ask "did we ever do this". `deleteTask` is the only `DELETE` on the table, it is the operator's alone (`taskboard.md` says why), and a sweep that reached this table would be the second one — which is the shape of the failure `retention.ts` exists to avoid, not an extension of it. The argument that would put it on a horizon is the one `context_samples` won on — a table written on a machine's own path, unbounded by anything an operator does — and it does not carry here: three of the four origins are machine-written, but each row is a deliberate decision by a model that a human then reads on a board, which is `chat_proposals`' shape and `chat_proposals` is likewise swept by nothing. What bounds this table is that somebody has to want each row. If that ever stops being true the answer is a cap on what one run may file, on `CONTEXT_SAMPLES_PER_RUN`'s reasoning — bound the writer, not the store — and never a horizon over rows a person put there.

What the sweep deliberately does **not** do is `VACUUM`. SQLite reuses freed pages, so the retention bounds the database's growth to a steady state, and only a `VACUUM` returns the space to the filesystem — which rewrites the whole file and blocks the single writer for as long as that takes, on a process that is also carrying live guards. So the file size is *reported* rather than silently shrunk, and `README.md` gives the one-line command beside the backup procedure.

**The card's two store sizes are measured rather than counted, so they are cached — and which half of this module the cache sits on is a structural decision rather than a tuning one.** `GET /api/storage` took 5.3-7.4s warm to answer 585 bytes, and two operators opening the Settings page together each paid it in full: the two `COUNT(*)`s beside the walks are 0.05 ms and 0.01 ms against a walk of 5,981 ms. `storageReport` reads both walks through a five-minute TTL with the single-flight `status.ts` already uses for the same measurement, so a second reader joins the walk in progress rather than starting one — the measurement takes seconds, so concurrent readers are the ordinary case rather than a race — while the figures the database can answer stay fresh on every call, which is the half of the card an operator watches after changing a horizon. **The cache is on the report's reading and deliberately not on `treeSize`**, and that is the whole of what keeps a five-minute-old size out of a removal: `sweepCheckouts` decides from the database and from git, `sweepTranscripts` from its own walk of `~/.claude/projects`, and neither asks for a size at all — the only way a stale one could reach a delete path is a future sweep reaching for the cached reading instead. A figure this old is something an operator reads; it is not something to delete against. **The fourth store on the card is read fresh on every call and is not part of that cache**: `backupStore` is one `readdir` of a directory holding tens of files, and the reason to open this card after running a backup is to see the backup. It is also the one store here nothing in this app writes and the only one no horizon applies to — this module measures it and never sweeps it, which is the correct asymmetry for the store a recovery depends on. `treeSize` itself now issues its `lstat`s in bounded batches rather than awaiting each one (88,325 entries over 2.62 GB: 5,981 ms serially against 1,750 ms with 64 outstanding), and the tail — including the batch a spent budget abandons mid-directory — is drained before it returns, because a total that came back with stats still in flight would be silently *short*, and a store that reads 1.4 GB while holding 2.6 is the figure a horizon gets set against.

The transcript sweep is the one whose protection cannot come from a file's age, so it comes from the database: `expiredTranscripts` takes a horizon and a `keepSessions` set built from every non-terminal run and **every** chat thread — a chat has no terminal state to key on, since an operator may type into one at any moment, and a *parked* run's transcript is old precisely because it is the one about to be resumed. The session id is the file's own basename, which is how the pinned CLI names one; that is verified against the shipped layout rather than assumed, and if it ever stops holding the cost is the extra protection rather than the age test, which is on the README's *Not yet verified* list by name. The cache is told about exactly the files that went (`forgetTranscriptFiles`) rather than invalidated — invalidating the whole of it makes the next scan re-read every file from byte 0, which is the pass the byte-offset cache exists to avoid, and there is deliberately no function that does it: `337f355` deleted `invalidateTranscriptCache` "rather than left reading as an eviction path that exists", the eviction the cache actually has being `TRANSCRIPT_CACHE_MAX_ENTRIES`, which drops a file whole and coldest-first. A removed file's parsed entries would otherwise be held for the life of the process, leaving the dashboard showing spend from transcripts that are gone and disagreeing with the cutoff the period card had just been handed.

The checkout sweep is the one whose store is somebody else's directory, so what it may touch is narrower than the other two and is worth stating outright. It removes a *directory* and never a ref: `worktree remove` without `--force`, which leaves the branch and every commit on it exactly where they were and gives git a second veto over the cleanliness `planCheckoutReclaim` already checked. Six clauses have to hold, and each of them is a keep — `slotIsDirty`'s rule that an unreadable status counts as dirty is one of them, unchanged and not to be weakened, since `git status` cannot see the gitignored trees that are most of the bytes. It never removes a checkout an active run holds, one the newest run recorded in it has not finished with, one a run that has not started yet is set to carry the branch on from, or one whose branch carries commits its target does not have — where "does not have" is `landed_tip` unmoved for a squash and `rev-list --count target..branch` for everything else, because a squash rewrites the commits and git's own ancestry test can never call such a branch merged. What it costs when it does fire is the installed dependency tree the next run in that slot would have reused, which is the whole of why the horizon is a week: slot reuse is what makes isolation practical, and a horizon short enough to break it would trade disk for an install per run.
