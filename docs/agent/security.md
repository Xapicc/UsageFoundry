# Security-critical paths

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing anything touching auth, path containment, spawn argv, or a credential.**

## Security-critical paths

- **The server is root and every child it spawns is not, and that one difference is what makes three separate defences mean anything.** `docker-compose.yml` runs the container as `0:0` and the server drops each child to `UF_AGENT_UID`/`UF_AGENT_GID` — the operator's own `UF_UID`/`UF_GID`, so the processes that write the bind mounts are the uid they always were. `privsep.ts` is the one place that decides it, `childCredentials()` is spread into all seven spawn sites (the work cycle, the reviewer, both of `chat.ts`'s, both of `git.ts`'s — the git ones are not an afterthought, a root git leaves root-owned objects in a tree the operator has to keep using — and `claudeAuth.ts`'s, which is the one site where the drop is a *correctness* measure rather than a containment one: `claude auth login` writes the 0600 credential named below, so a login taken with the server's own authority would produce a file the page reports as a healthy sign-in and no agent can open), and what it buys is that a *file mode* now excludes somebody: `/proc/<server>/environ` is 0400 owned by the server, so `childEnv`'s strip of `UF_*`/`ANTHROPIC_ADMIN_KEY`/`DATA_DIR` is enforced rather than advised, where one `tr '\0' '\n' < /proc/<server pid>/environ` used to hand every one of them back; `/data` is root-owned 0700, so an agent cannot rewrite a budget, a status or `chatDefaultGuards.permissionMode` straight in the database, nor the lock `serverLock.ts` keeps beside it; and the MCP capability file stops being decorative — that last one taking a second cut, because 0600 owned by the agents' uid excluded nobody either: the chat and block child (`chatChildCredentials()`, the one spawn site that differs) keeps the agents' uid and takes `UF_CHAT_GID` instead, and the per-turn directory and file are handed to that group at 0710/0040, so a work-cycle agent that reads `--mcp-config <path>` off a sibling's world-readable `/proc/<pid>/cmdline` fails the owner check, fails the group check, and is left with the "other" bits. A gid rather than a second uid because the chat child must stay the uid that owns `~/.claude`, which is what it bills against; `resolveChatGid` refuses group 0 and refuses the agents' own gid, since either would hand the file to the half it is kept from. The direction is forced, not chosen: the child **must** be the mount owner, because an isolated run is ordered to commit and its commits land in the operator's own `<repo>/.git`, and the server **must** read `~/.claude/.credentials.json`, which the CLI keeps 0600 owned by that same uid — so the privileged half is the one process running code from this repository rather than the twenty-five unattended children whose prompts came out of repositories nobody here reviewed. Two consequences are written down rather than absorbed. The server's own writes into a bind mount land root-owned, so the three that exist go through `chownForChild`. Two of them — the `.uf-worktrees` store and `seedWorktree`'s copies — let it **throw**: a checkout the agent cannot write fails inside a tool call the run loop does not read, which is a run that simply does not do the work. The third, `ensureSandboxMountPoints`' empty files, catches it instead and keeps the file, and the asymmetry is the point: those exist only so bwrap finds a mount point it would otherwise create itself, bwrap binds over a file it does not own, and a run refused at spawn over a cosmetic chown would trade a recoverable tool call for an unrecoverable run. And the whole thing is inert when the server is not root — `npm run dev`, the tests, a compose override — which is a boundary that disappears with the page looking identical, so `describeSeparation()` states the arrangement in the boot log and an environment that *names* an agent uid the process cannot switch to throws instead of degrading. What it does **not** buy is in `docs/security.md`: a work cycle can still read the account's own OAuth credential — it has to, that credential is what it bills against — and every child still shares one uid, so the group above is the only thing separating them, and clearing `UF_CHAT_GID` removes it.
- `resolveInMount()` (`orchestrator.ts`) checks containment on the lexically resolved path **before** touching the filesystem, then **again** after `realpathSync` — a symlink inside the root can still point out of it. Both checks are load-bearing. `resolveWorkspaceFolder()` runs that pair against **one mount at a time**; multiple mounts widen which roots are legal, never what counts as contained. A run is confined to the mount it started in.
- Containment stays **per mount**, while collision detection is deliberately **cross-mount**: `conflictKey`/`overlaps` see two mounts onto one directory as one folder. Widening what counts as a collision never widens what a run is permitted to touch.
- Worktrees live at `<mountRoot>/.uf-worktrees/<repo>-<slot>` so the unmodified `resolveInMount` validates the agent's cwd. `ensureWorktree` `lstat`s that directory and refuses a symlink **before** git writes — validating afterwards would mean a full checkout had already landed wherever the link pointed.
- The agent is spawned with an argument array and `stdio: ["ignore", "pipe", "pipe"]`, **never a shell**, so prompt metacharacters are inert. `gitSync` does the same, and additionally clears **both** ways a repository gets git to run a command of its choosing — `core.fsmonitor=`, which `status` reads, and `core.hooksPath=/dev/null`, which is what `worktree add`'s `post-checkout`, `checkout`'s, and `merge`/`commit`'s four would otherwise fire, the last of them inside the operator's own checkout at a moment the operator triggered. An agent can write `.git/hooks/post-checkout` in any repository it works in and this app would then execute it on behalf of a run that did not, with no permission mode, no tool lists and nothing in `run_events`; `/dev/null` is not a directory, and the `-c` outranks a `core.hooksPath` the repository sets for itself (verified on 2.39). This is the git *this app* runs and it reaches no further: `buildArgs` passes no config, so a repository's `pre-commit` still runs for the agent that was asked to commit, which is part of the work. `gitEnv()` strips what `childEnv` and `reviewEnv` strip — `UF_*`, `ANTHROPIC_*`, `OTEL_*`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `CLAUDE_CODE_ENABLE_TELEMETRY`, `DATA_DIR` — rather than the shorter list it had, because the drivers reached through `.gitattributes` are repository-controlled too and this is the one child kind that runs code this app did not write.
- `gitArgs` also passes `safe.directory=*`, and the image sets it system-wide for the agent's own git. This is a deliberate waiver, not an oversight: a bind mount carries the *host* uid, and git's ownership refusal reaches `probeIsolation` as an unreadable repository — indistinguishable from "not a repository", so isolation would switch itself off and say the wrong thing about why. The check guards against repositories encountered by surprise on a shared host; every path that reaches `gitSync` has already been proved inside a configured mount by `resolveInMount`, which is the containment guarantee that actually matters here. Keep it paired with `UF_UID`/`UF_GID` in compose — the waiver makes git *work* against a foreign-uid mount, it does not make the mount *writable*.
- **`UF_GITHUB_TOKEN` is scoped by host and by child, and there are three kinds of child rather than one.** The credential helper `githubEnv()` installs is keyed to `https://github.com`, so a repository whose submodule or remote points at another host asks for credentials and gets none — with `GIT_TERMINAL_PROMPT=0` alongside it, that fails in a second rather than hanging until the run's duration limit. What it reaches is the part to read exactly, because "work cycles and nothing else" has been false since the orchestrator chat gained tools. A **work cycle** takes the credential its own repository is configured with, through `selectGithubToken` off `runs.repo_root`. `chatEnv()` hands the **install-wide** token to `runOrchestratorChild`, which is *two* callers: the orchestrator chat turn and a workflow's orchestrator-block child. That widening is the point of the feature — a turn asked to look at open issues cannot otherwise, and it fails inside a tool call the way `git push` used to — but the child it widens to is the one running `bypassPermissions` with no allowlist and `--add-dir` on every mount, so the token authenticates **writes** as well as reads and the system prompt is the only thing saying not to make them. It is install-wide deliberately and this is the one child where that is still right: an orchestrator turn's whole job is to look across every mount before it knows which repository it is proposing work in, so narrowing it to a cwd would withhold the credential from every question about a repository the turn had not yet been pointed at. The lever that withholds it is the same one as everywhere else and is worth stating rather than deducing: leave `UF_GITHUB_TOKEN` blank and configure only `UF_GITHUB_TOKENS`, and the per-repository credential still reaches work cycles while these two children get none. `UF_*` still leaves that child's environment by namespace, so nothing hands it this app's own credentials.
- `permissionMode` is narrowed against the four literals in `POST /api/runs` before it reaches `--permission-mode`.
- **The child environment is a denylist, and a denylist fails open — so a credential shape gets closed before this app has a use for it, not after.** Five functions hold byte-identical copies of it, deliberately rather than by omission, each citing the block above `CONTEXT_SHAPING_ENV` in `orchestrator.ts` for the reasoning: `childEnv` (the work cycle), `chatEnv` (`chat.ts`), `reviewEnv` (`review.ts`), `authEnv` (`claudeAuth.ts`, whose docblock says why it is a copy rather than an import) and `gitEnv` (`git.ts`, a superset). **A sixth spawn site adds a sixth copy; it does not add a shared module.** `OPENAI_API_KEY` and `CODEX_API_KEY` are on all five and reach none of them, which is the point: no child here is anything but `CLAUDE_BIN`, so an operator running a second provider's CLI on the same server was handing its credential to twenty-five unattended agents in sessions that have `Bash`, where `env` is read-only shell `acceptEdits` approves without asking. `ANTHROPIC_API_KEY` is the one credential deliberately *not* stripped — it is what a work cycle bills against, and the auth panel has to report the credential runs actually get. Only `childEnv` is pinned by a test (`docs/agent/testing.md`); the other four move by hand, which is what the shared docblock is for. `proposals/ProviderFallback/` is where this was found, and it recommends **against** the per-run provider that would have made these variables this app's business — the strip stands either way.
- **A named agent is not a capability surface, and the absence of two columns is what enforces that — more so now that the run *is* the agent.** `--agents` members accept a `tools` array; `normalizeAgentInput` refuses one by name and the `agents` table has no column for it, and none for a permission mode either — so the routes to `--permission-mode` stay the two they were, and no chat proposal, workflow block or emitted spec can reach one by naming an agent. The refusal got **stronger** with the singular flag rather than weaker, and the opposite reading is the one to close off: a `tools` list on a definition merely *offered* would have bounded one delegated subtask inside a run whose own mode and lists still stood over it, where a list on the definition the session **is** is a statement about what the whole run may do. Two things follow that are worth not re-deciding by accident. The deny list is the one that matters: `PROCESS_KILLERS` is `--disallowedTools`, deny is *verified* to beat `--permission-mode`, and whether it would also beat a member's own `tools: ["Bash"]` — as a delegate or as the session — is **not** verified, which is why the field is refused rather than stored and narrowed. And what a child may be started as is never taken off the wire: `resolveAgentForRun` accepts an **id** and looks the definition up, so an agent that nobody saved cannot be assembled in a request body — which under `--agent` is the difference between a run being a role somebody wrote down and a run being a system prompt that arrived in an HTTP body.
- **Reading an agent definition off disk is scoped, and only the scope that needs no path is on the wire.** `listAmbientAgents` walks `$CLAUDE_CONFIG_DIR/agents/**` and, for a caller that has already resolved a folder, that folder's `.claude/agents/**`. `GET /api/agents` and `/api/usage` pass no folder and report the user scope alone — not because the project scope is secret, but because taking a directory off a request would be a second path-resolution surface beside `resolveInMount`, for a payload that only feeds a sentence on a page. Nothing in that walk bounds what a child may do; the definitions it finds already reach every child, mounted from the operator's own `~/.claude`.
- **An agent cannot select processes by name to signal them.** `buildArgs` passes `--disallowedTools Bash(pkill:*) Bash(killall:*)` on every spawn — a deny rejects the whole Bash call, so a `pkill` buried in a `;`-chain takes the chain with it, which is the form the incident arrived in — and `--append-system-prompt` carries the reason *and the safe recipe*. The deny alone buys one turn, since `kill $(pgrep -f next-server)` is not `pkill` and is exactly as fatal; a bare prohibition buys the opposite failure, a dev server nobody can stop holding its port for the life of the container. So the notice spells out pid capture, the `pgrep -P` child form, and selecting on the port rather than the title. Next renames this server's process to `next-server (v…)`, which is *also* the title of any dev server an agent starts to check its work, so a name match cannot tell the two apart and reaches whichever was there first. One `pkill -f "next-server|next dev"` ended the container (`restart: unless-stopped` brought it back) and `reconcileOnBoot` marked fourteen runs failed 690ms later, including the run that issued it. There is no ownership boundary to enforce this with instead: compose runs a single uid. Plain `kill` stays permitted — a pid is a handle on a process the agent started, a pattern is a guess about the machine — and denial survives `bypassPermissions`, which is the only reason the argv is worth anything here. The **allow** list beside it now also appears on every spawn, and it is deliberately not a member of the guard set: `SEARCH_TOOLS` is `Grep` and `Glob`, two tools that read, named because the pinned CLI drops both from the tool list whenever `Bash` is present unless something names one. It grants no command, it moves no permission mode, and the test beside `buildArgs` asserts that a run in the operator's own checkout still gets no `Bash(...)` entry through it.
- **…and the notice must contain no literal an agent could match on, because the notice is itself on every sibling's command line.** `--append-system-prompt` puts `SELF_HOSTING_NOTICE` in the argv of every concurrently running `claude`, so any literal string in it is a pattern that selects the whole fleet. The worked example used to be `kill $(pgrep -f 3100)`, which made the one command this notice recommends by name match every agent on the box. Measured twice. At 2026-08-15 23:39:42 run `b81e7c70` escalated from a narrow `pgrep -f "next dev -p 3100"` through an explicit pid to a bare `pgrep -f 3100`, and `9b98ddec` — a Go run in a different repository, with no port-3100 process and no tool call of its own naming the number — died in the same second with "exited with code 143", taking five dependents into `blocked` behind it; it happened again on 2026-08-16 at 14:23:38, `02c3e132` ending `8d6b1ffc`. No work was lost, because all four resumed the same session, but three runs were truncated at their cycle cap and every dependent needed picking up by hand. The port is a shell variable now and the *mechanism* is stated rather than the conclusion — an agent told only "no bare numbers" reaches for a different literal, where one told why a literal is dangerous checks first — and `pgrep -af` is named because looking before killing is the habit that generalises to the next pattern nobody anticipated. `orchestrator.test.ts` asserts the notice carries no multi-digit run, beside the `PROCESS_KILLERS` assertion it belongs with, and asserts it against a spawn that carries a **rendered price list** — with the strict form scoped to whatever the flag holds *without* one, derived rather than listed, so a sixth notice inherits it without anybody naming it there. That scoping is the whole of it: asserted against a fixture with no price list on the flag, as it was, the strict form read as a claim about every notice while never once seeing the only one that carries digits at all. The flag now carries **five** notices under one value — `SELF_HOSTING_NOTICE`, `DELEGATION_NOTICE`, `RENDERING_NOTICE`, `COMMIT_IDENTITY_NOTICE` and the run's own frozen file price list — because a second `--append-system-prompt` is a replacement rather than an addition; anything added to any of them inherits this bullet's rule, since all five are equally on every sibling's command line. The price list is the case that makes the rule worth restating rather than merely surviving it: it is a list of **repo-relative paths**, which is exactly the kind of shared literal that made `pgrep -f 3100` fatal, since every run on that repository carries the same ones. What keeps it safe is not that the strings are different but that nothing near them offers a pattern — they sit in a price list, no verb beside them is `kill`, and it names no command at all. `fileCostNotice.test.ts`'s "offers no literal as a thing to run" pins that, and the argv test pins it a second time over the price-list half of the flag it splits — the duplication is deliberate, because the strict assertion's failure message is read *there*, and a rule that lives only in another file is one an editor at this one never meets. `SELF_HOSTING_NOTICE`'s own sentence about literals is scoped to the whole appended prompt, so it already covers this half. The notice still names no tool the image lacks: the Dockerfile installs `procps` and neither `psmisc` nor `iproute2`, so `fuser` and `ss` are absent, and warning about — or recommending — an absent command is how an agent learns to look for it.
- **An agent must not sign a commit with the address it was given to recognise the operator by.** The CLI puts the signed-in account's email in every child's own system prompt, worded as "use it only to identify the user, such as for authorship, attribution" — so the one credential-shaped string this app never handed a child is the one the child arrives holding, and an agent this app has just told to commit reads that wording as permission. Two commits on this repository's own `main` were authored `UsageFoundry Agent <the operator's address>` by an isolated run that reached for `git -c user.name=… -c user.email=… commit` unprompted; GitHub maps a commit to an account by author email, so both were attributed to the operator's other GitHub identity and it took a place in the public contributor list. Nothing failed on the way: `/etc/gitconfig` sets `agent@usagefoundry.local` and still does, the commits landed, the run completed, and the attribution was found by someone reading a panel weeks later — which is why the answer is a notice rather than a check, there being nothing here that inspects an author line. `ISOLATED_GIT_TOOLS` cannot be that answer twice over: its entries are prefix-matched, so `git -c …` sits outside them by construction, and the run that did this was on `bypassPermissions`, where an allowlist decides nothing. `COMMIT_IDENTITY_NOTICE` therefore rides `--append-system-prompt`, which is the only thing that reaches every run whatever its mode and whether or not it is isolated — the unisolated case being the one whose commits land in the operator's own checkout with no branch in front of them. It names all four spellings (`-c`, `git config`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL`) because an agent told only that one is forbidden reaches for the next, and it satisfies the bullet above the way the price list does: git configuration keys, no verb but "commit" beside them, nothing selecting a process, and no digits at all.

- **A monitor must not be handed the credential that starts agents.** `UF_AUTH_TOKEN` opens every route in the app, including the ones that spawn billed children, so polling any of them from a monitoring system means a scraper holds the master key. `UF_STATUS_TOKEN` is a second, read-only credential that reaches `/api/status` and nothing else, checked in that route rather than in the edge middleware for `/api/mcp`'s reason. The exemption is **conditional on the variable being set**, which is the one thing about it not to undo: with no read-only token configured there is nothing to check, so the route falls back behind the ordinary gate and an operator who never set one gets a 401 instead of an open endpoint. The payload's own rule is the second half — counts, bytes, fractions and timestamps, never a prompt, a folder path, a setting or a branch name — and it is stricter than it looks, because a monitoring system retains and forwards what it scrapes.
- `src/middleware.ts` runs in the **edge runtime**: it reads `process.env.UF_AUTH_TOKEN` directly and must not import `lib/config` (which pulls in `node:os`/`node:path`). It may import `lib/sessionToken`, which is Web Crypto and string handling and imports nothing at all — that constraint is what shapes the cookie, below. Comparison is constant-time; API paths get 401, page paths redirect to `/login`. Five paths are exempted, and two of them **authenticate themselves** for one reason: the credential each takes is a per-turn or per-run capability, and checking it needs SQLite and module state, neither of which exists in the edge runtime. `/api/mcp` is the chat's tool surface; `/api/otlp/v1/logs` is a run's telemetry export, exempted when the exporter stopped carrying `UF_AUTH_TOKEN`. Removing either check makes that surface public — the tool list in one case, an open write into `otlp_requests` in the other, where a pre-inserted `request_id` is silently dropped by the `INSERT OR IGNORE` and understates the figure a live spending guard reads. Keep each of those exemptions paired with its check. **And an exempted path's own refusal must not be written into a capped table**, which is the second thing `/api/mcp` owes its exemption: `auditMutation` wrapped the handler from outside, so a credential-free POST — a request that has passed nothing, since the middleware let it by — wrote a `request_log` row, and every insert evicts past the 20,000-row cap. That handed anyone who could reach the path a lever on the audit log itself: twenty thousand correctly-refused requests, and every line naming a run that was started, a setting that was changed or a sign-in that failed is gone. Only the handler that already holds a subject is wrapped now, `DELETE` (a 405 answered before any credential is read) is not audited at all, and the refusal goes to stdout, which nothing caps. `/api/logout` is the third, and it is the one that grants nothing — **on the branch that clause describes**. It revokes the id inside the cookie it is handed, so requiring a valid session there would make a stale cookie the one state an operator can never leave. The `all: true` branch is not that branch and was not covered by the sentence: it is handed no cookie, acts on sessions the caller was never given, and used to run for anyone who could reach the port — zeroing the `activeSessions` figure an operator reads to check whether anybody else is signed in. It now takes a credential of its own, a signature-valid cookie or the master bearer, and its 401 is answered **before** any audit wrapper for the reason `/api/mcp`'s is: an exempted path's own refusal must not spend the `request_log` cap. A revocation that actually happens writes an `ops_events` row instead. `/api/health` is the fourth, and it is exempt on a different ground again: it holds no credential of its own and answers with counts, so what keeps it safe is the *shape of its payload* rather than a check. That makes the exemption a constraint on the route — run counts, whether SQLite answers, whether this process owns `DATA_DIR`, two timings, and nothing else. A prompt, a folder path, a setting or a token added to that body turns this line into an unauthenticated data route, and the test beside it asserts the absence rather than trusting the comment. `/api/status` is the fifth and the only *conditional* one — see the read-only-credential note above.
- **The audit trail is two tables, and which one a line belongs in is decided by what evicts it.** `request_log` is the trail of *requests* — method, `pathname`, status, subject, credential class, first hop, duration — written by `auditMutation` at the export of every mutating route behind the gate, and it is a 20,000-row window trimmed on every insert. That is right for what it holds and wrong for a credential: the line saying the OAuth credential every billed child runs against was replaced is the one that has to survive twenty thousand ordinary presses, and it is the first thing an ordinary week deletes. So a mutation that *changed* something also writes `recordDurableMutation` into `ops_events`, which is written at boot frequency and at operator-press frequency and which ordinary traffic therefore cannot evict. **Both, not either**, and each half covers what the other cannot: the wrapper records the refusals, which is the line an audit most wants and which the durable half never sees, because the durable half fires only behind a success. Every credential route follows one rule — the row is written when the credential changed, never when the press was made, so a refused code, a cancel over no pending login and a CLI that would not run leave the request line alone. **Who** is the credential class and the first hop and nothing else: this install has one credential and no user model, so any name in a row here would be invented rather than recorded, and `detail` is named field by field for the reason `request_log` takes no body — a body posted to `/api/codex-auth/api-key` is an API key, and `recordOpsEvent` writes to SQLite *and* stdout in the same call. The one thing not to undo: `ops_events` keeps **500** rows against `request_log`'s 20,000, so a durable row written on an exempt path's refusal is a forty-times sharper version of the `/api/mcp` lever below — an anonymous caller empties the durable trail in five hundred requests. `/api/logout` is the only exempt path that writes here, it is unwrapped for that reason, and both of its branches record only after a revocation has happened; `revokeSession` returns whether *this* call was the one that ended the session precisely so a replayed cookie is worth one row rather than one per replay.
- **`/api/login` is the one unauthenticated write surface here, so it is the one route with a rate limit.** `middleware.ts` exempts it correctly — the page has to be reachable — and nothing else bounded it: no counter, no lockout, no record, and a 400 ms `await` on a timer that delays one request and serialises nothing, so two hundred concurrent connections guess at the rate of the event loop and compete with every running agent for the one Node process. `planLoginAttempt`/`recordFailure` in `loginLimiter.ts` are the decision, pure and unit-tested for the usual reason: a limiter that never fires is bit-for-bit the unbounded route, and one that never lets go locks the operator out of an app whose only other credential is an environment variable and a restart. **Two budgets, and the second exists because the first is evadable**: a source is `x-forwarded-for`'s first hop, which a client sets itself when no proxy is in front, so an attacker who rotates it gets a fresh per-source budget every request — the install-wide bucket is what still bounds them. The global lockout is deliberately **much shorter** than the per-source one (60s against 15min) because it refuses the operator too, so a sustained attack degrades sign-in rather than removing it. The check runs **before the body is read and long before the token is compared**, and answers the *same body* as a wrong token with a 429 and a `Retry-After` — a limiter that let a correct token through while locked would be an oracle telling the guesser when they had got it right. State is in `login_attempts` rather than a `Map`: a burst has to be visible afterwards, and a lockout held in memory is one an attacker clears by restarting the container, which `restart: unless-stopped` does for them. A successful sign-in clears **both** buckets, the global one included, because the person who just presented the token is the operator. The Settings page reports the count, the first and the last, and the row is absent at zero. The comparison is `node:crypto`'s `timingSafeEqual` behind a length guard rather than `!==`: the 400 ms floor masks the difference in practice, and the point is that `middleware.ts` goes to the trouble for the same secret and two paths comparing one token should not differ in how.
- **The session cookie is a handle, and the master token is what it is deliberately not.** `uf_session` used to be `UF_AUTH_TOKEN` byte for byte, `secure: false`, for thirty days — so a browser jar held a replayable copy of the credential that opens every route as a bearer header, and invalidating one meant editing `.env` and restarting the container, which kills every run in flight. It is now `v1.<32 random bytes>.<expiry>.<HMAC-SHA256 keyed by the token>`: not the token, not usable as a bearer (the bearer branch still compares raw equality against the token, which is what a script presents — `telemetryEnv`'s OTLP exporter no longer does, carrying a per-run capability the ingest route checks for itself), and carrying its own signed absolute expiry — `SESSION_TTL_MS`, 24h, with no sliding renewal, because a window an active holder can extend is a window a *captured* cookie never leaves. The id names an `auth_sessions` row, so `POST /api/logout` revokes one (or all) and the Settings page can say how many are outstanding — questions the old cookie could not answer at all. What that does **not** buy is written down rather than absorbed: the edge gate cannot read SQLite, so a revoked session's *captured* cookie stays signature-valid until its own expiry. Closing that means moving the gate off the edge runtime, which is a change to what `middleware.ts` is. **The Settings copy under "Sign out everywhere" says so in one line**, because the button used to be described as the remedy for a cookie that got out, which is the one case this shape cannot answer. And a *second* place had not absorbed it either: `/api/status` authenticated a browser by comparing `uf_session` against `UF_AUTH_TOKEN` — the shape the cookie had *before* this change — so the branch that exists to let the operator's own browser read that route could not be satisfied by any cookie the login route can issue. It verifies with `readSessionCookie` now; anything keyed on the cookie *being* the token is a leftover of the old shape and is a bug. `Secure` is decided by `cookieIsSecure` — `x-forwarded-proto`'s first hop, then the URL's protocol, with `UF_COOKIE_SECURE` overriding **both ways**: `"1"` for a terminator that sets no header, `"0"` because a false positive is an install where sign-in appears to work and no cookie ever comes back. `httpOnly` and `sameSite: "lax"` are unchanged and are what stands in for CSRF protection. `next.config.ts` sets HSTS, `nosniff`, `frame-ancestors 'none'`/`X-Frame-Options` and a referrer policy; there is deliberately no `script-src`, since one written without measuring Next's inline bootstrap and the pre-paint theme script is a blank page.
- The chat's capability token is compared constant-time against every live token in `subjectForCapability`, rather than looked up by key: a `Map.get` on a secret leaks its prefix through timing. The live set is the number of orchestrator turns in flight — one chat turn, plus whatever blocks of a workflow are deciding right now — so it is small rather than one, and the linear scan is affordable for that reason rather than for a bound. What it returns is a **subject** rather than a chat id, and `docs/agent/chat.md` carries why that is a discriminated union.
- `bypassPermissions` is offered in the new-run form with a warning; the default stays `acceptEdits`.
