# Environment gotchas

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing docker-compose.yml, .env, Dockerfile, src/lib/config.ts.**

## Environment gotchas

- The app reads `WORKSPACE_ROOTS` (multiple mounts, `Label=/path` entries joined by `|`) and falls back to the single `WORKSPACE_ROOT` when it is unset. `.env` / `.env.example` define `UF_WORKSPACE`, `UF_WORKSPACE_N` and `UF_WORKSPACE_N_NAME`, which are **only** consumed by `docker-compose.yml` — to pick the host mounts and to compose `WORKSPACE_ROOTS`. Running `npm run dev` without either set falls back to `~/workspace`, so `/api/folders` will look empty even though `.env` names a directory.
- An entry in `WORKSPACE_ROOTS` with an *explicitly empty* label (`=/workspace2`) is **skipped**, while a bare path (`/workspace2`) is labelled from its basename. That asymmetry is load-bearing: compose cannot omit a volume conditionally, so all four slots are always mounted and an unset `UF_WORKSPACE_N_NAME` is what switches a slot off. Switching one of the four on or off must stay an `.env` edit, not a compose edit — and the same sentence is why a *fifth* cannot be one: a slot is a hand-written volume line, so `.env` can reach four of them and no more. That ceiling used to be nowhere in the code and silent at the edge of it, which is the one thing it could not be: `UF_WORKSPACE_5_NAME` was interpolated by nothing, so the directory was never mounted and never reached the picker — indistinguishable from a mounted directory with nothing in it, which is what an operator would then go looking for. `MOUNTED_WORKSPACE_SLOTS` names it in `config.ts`, compose forwards the slots past it as `UF_UNMOUNTED_WORKSPACES` (names, never values — a host path is not needed to say which variable is wrong), and `unmountedWorkspaceRefusal` refuses the boot naming them, which is the treatment `${UF_WORKSPACE:?…}` already gets one line over. `parseMounts` itself stays uncapped, because a `docker-compose.override.yml` mounting a fifth slot is the supported route for one and clears that variable to say the mount was really made. `deployment.test.ts` pins the constant against the volume lines, since a fifth line added without bumping it would refuse a slot the deployment does mount — the same silence inverted.
- `CLAUDE_HOME` (default `~/.claude`) determines which transcripts are parsed; `DATA_DIR` (default `./.data`) holds the SQLite file.
- `UF_BACKUP_DIR` (default `./backups`) is bind-mounted at `/backups`, and being a bind mount rather than the named volume is the whole of it: a snapshot kept inside `usagefoundry-data` is destroyed by the `docker compose down -v` it exists to survive. Nothing writes there on its own — `scripts/backup-db.mjs` is run by hand or by the operator's own cron, which the README states in words rather than shipping a scheduler, because a timer that spends nothing still needs somewhere to put a file that grows without bound. The mechanism is `VACUUM INTO` through a **read-only** connection, never a file copy: the database is in WAL mode, so a copy of `usagefoundry.db` omits every transaction since the last checkpoint and says nothing about it, and read-only is what keeps the second process off the single-writer assumption `db.ts` opens with. The restore refuses while `server.lock` is still beating, for the reason the lock exists at all. **The server now *reads* that directory, and reads it at `/backups` rather than through `UF_BACKUP_DIR`** — `config.ts`'s `BACKUP_DIR`, surfaced as a Backups row on the Storage card and as a path-free reading on `/api/status`. The variable is the bind **source**, a path on the host, so reading it inside the container would point the reading at a directory that does not exist there; forwarding it into the container to make that work would break the mount's one honest meaning, and `deployment.test.ts` catches the attempt, since it is a `UF_` name the `environment:` block does not carry. The refusal above is about **writing** and is unchanged: nothing here schedules a backup. What it closes is that an install backed up nightly and one backed up once in August used to present identically on every page and in every alertable condition. Three states, never two — a directory this process cannot read (a missing bind mount, or one Docker created as root) is reported as unreadable and not as a count of zero, because those need opposite actions.
- `UF_AUTH_TOKEN` blank disables auth entirely, and the app now **refuses to boot** in that state unless `UF_ALLOW_NO_AUTH=1` says the operator meant it — `authBootSignal` in `authGuard.ts` is that decision, pure and unit-tested, called from `instrumentation.ts` before the reconcile guard. Acknowledged, it logs a block at boot and `layout.tsx` puts an undismissable banner on every page through `AppShell`'s `authDisabled` prop, read from a server component so no failed request can leave it off. `/api/login` answers **409** rather than a success when there is no token, because a sign-in that checked nothing looked exactly like one that did. The acknowledgement is compared as the exact string `"1"`, `continueAfterDone`'s rule: a value that makes the app stop protecting itself must fail towards refusing to start. `ANTHROPIC_ADMIN_KEY` blank leaves the API-account page in an explicit "not configured" state rather than showing zeros.
- `UF_GITHUB_TOKEN` blank means runs cannot use GitHub at all, and the Settings header says so — the failure otherwise arrives mid-run, inside a tool call nothing here reads. `UF_GITHUB_TOKENS` is the per-repository half beside it (`folder=token` entries, `|`-separated), and the header says which of the three states an install is in, because how *wide* the credential is was the one thing that page could not say. The `UF_` prefix is load-bearing rather than cosmetic: `gitEnv()` and `reviewEnv()` strip that namespace, so both tokens are withheld from every child except the ones `githubEnv()` hands one to — and a second credential shape needing no second exclusion is the whole point of withholding by namespace.
- All process-level config is centralised in `src/lib/config.ts` and fixed at boot. User-editable values belong in the settings table (`src/lib/settings.ts`), not here.
- **Rotating any of these is a container restart, and *which* of them a restart is the only answer for is the part worth knowing.** Nothing outside a process can write that process's environment and nothing in this app writes its own, so `process.env` is fixed for the life of this server — the same sentence `orchestrator.ts` already gives for reading the GitHub credential once per pick-up rather than once per cycle. **Where a value is read therefore decides nothing.** `middleware.ts:41` and `:114` read `UF_AUTH_TOKEN` and `UF_STATUS_TOKEN` out of `process.env` on every single request — measured rather than assumed, the built `.next/server/src/middleware.js` carries both as property accesses, Next inlining neither into the edge bundle because `docker build` has no token to inline — and they rotate exactly as poorly as `AUTH_TOKEN`'s module `const` two files over. So turning a `const` here into a function that reads at use buys nothing observable, and for the GitHub pair it would cost the guarantee `orchestrator.ts` names in words: that a run keeps one credential for the whole of its life, rather than pushing from one cycle and not the next with nothing saying why. **What differs between these values is who issued them**, which is the question an operator actually has at the moment one leaks.
  - **Issued here, so a restart is the only revocation there is.** `UF_AUTH_TOKEN` (`config.ts:328`, the two per-request reads above, `api/login/route.ts:39`, `api/logout/route.ts:102`, `api/status/route.ts:49`) and `UF_STATUS_TOKEN` (`middleware.ts:114` and nowhere else). Nothing outside this container knows either value, so there is no console to revoke them at and a leaked one stays live until the process holding it is replaced. These two are the whole of the rotation problem. The compensation is worth stating because it is the same lever: rotating `UF_AUTH_TOKEN` is also the *only* thing that invalidates a captured session cookie before its own TTL, since the cookie is HMAC'd with the token (`api/login/route.ts:118`) — which is precisely the hole "sign out everywhere" cannot close, the edge gate having no way to read `auth_sessions`.
  - **Issued elsewhere, so the leak closes without this container and the restart only re-arms the install.** `ANTHROPIC_ADMIN_KEY` (`config.ts:350` → `adminApi.ts:45`), `UF_GITHUB_TOKEN` (`:367`) and `UF_GITHUB_TOKENS` (`:407`, both through `githubTokenFor` into `githubEnv()`), `UF_WEBHOOK_URL` (`:509`) and `UF_WEBHOOK_SECRET` (`:517`, both into `notify.ts:389`), and `DISCORD_WEBHOOK_URL`, which this process never holds at all — the entrypoint launches the relay with it and `unset`s it before `exec`, so rotating it is the relay's restart rather than the server's. Revoke each where it was issued — GitHub, the Anthropic console, the webhook's own receiver — and the exposure is over in seconds with nothing restarted and no run ended. What the restart then buys is the *new* value, and in between the install is **degraded rather than exposed**: pushes fail inside a tool call, the API-account panel reports nothing, notifications stop. That is a different decision from the one above and should not be deferred like it.
  - **Not credentials, and on this footing only because they are read the same way.** `UF_PUBLIC_URL` (`:527`), `UF_INSTALL_LABEL` (`:530`), `UF_NOTIFY_ON_SUCCESS` (`:547`), `UF_ALLOW_NO_AUTH` (`:340`), `UF_COOKIE_SECURE` (`:347`), `UF_TRANSCRIPT_CACHE_MAX_ENTRIES` (`:93`), and `UF_UNMOUNTED_WORKSPACES` (`:258`), which is compose's output rather than an operator's input. Beside them sit three credentials this app reads **nowhere** and forwards anyway, so they rotate on this same restart and are easy to forget for exactly that reason: `ANTHROPIC_API_KEY`, deliberately not stripped by any of the five child environments because it is what a work cycle bills against, and `OPENAI_API_KEY`/`CODEX_API_KEY`, stripped from every child except `codexAuth.ts`'s. Every child is spawned from `{ ...process.env }`, so each of them is this process's copy.
  - **What would make one genuinely rotatable, and why none of it is here.** It takes a second source that can change while the process runs, and there are two. The settings table is refused outright at `config.ts:492-508` — `/api/settings` is reachable with the master key, so a repointable webhook target turns one credential into an exfiltration channel — and that refusal covers every value on this list, not just the notifier's. A file is the other, the `*_FILE` convention Docker and Kubernetes secrets use, and it would work for the third-party group; it does **not** work for the one value that most needs it, because `UF_AUTH_TOKEN` is checked in the edge runtime, which has no `node:fs` and must not import `lib/config`, so a file-backed master key means moving the gate off the edge — which `docs/agent/security.md` calls a change to what `middleware.ts` *is*. Neither is a smaller change than the restart it avoids. The restart's real cost is one module over rather than here: `reconcileOnBoot` closes out every live run, and `lastBootReconcile.closed` is the count `README.md` describes as needing picking up by hand.
  - `deployment.test.ts` pins this list against `config.ts` and `middleware.ts`, because the way it went wrong last time was by **growing**: five variables were added to the notification channel, read the same way for the same reason, and nothing anywhere said so.
- **The configuration is checked before the server serves, and exactly one check refuses.** `configCheck.ts` runs first in `instrumentation.ts`, before the data directory is claimed and before anything opens the database, because every way of pointing this app at the wrong place used to present identically: a container that starts, answers `/login` and shows an empty dashboard, which is also what a quiet week looks like. `DATA_DIR` **refuses** — a blank value, a path that is not a directory, or one a real write fails in — and the refusal is `process.exit(1)` rather than a thrown `register()`, because Next logs a rejected boot hook and then serves anyway, which for this variable means a container writing every row into the image's writable layer where the next `docker compose up --build` deletes it. Blank is the case worth naming: `env()` reads it as unset, so `DATA_DIR=` is not a request for the default, and the refusal names the path it *would* have used rather than a variable the operator will not find in their own configuration. Everything else **warns** — a mount that is not a directory, a `CLAUDE_HOME` with no `projects/`, any other variable set to the empty string — and the asymmetry is the decision: a workspace is optional by design (four slots mounted unconditionally, a bind source that may not be up yet), `~/.claude/projects` legitimately does not exist until the machine has run Claude Code once, and refusing there would take the dashboard, the run history and the merge queue away from an install that is degraded rather than broken. Warnings are logged and ride on `/api/usage`'s `meta.configProblems` to a banner above the meters — above rather than under, because unlike the notices there they do not explain a number, they say the numbers may describe the wrong machine. Writability is a real write: `mkdirSync(recursive: true)` reports success for a directory it cannot write to, which is why an ownership mismatch used to arrive later as an `EACCES` out of `writeLock`. The variables where blank *is* the answer go through `optionalEnv` and are never reported, and there are two kinds of them: an **off switch** (`UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY`, `UF_GITHUB_TOKEN`, `UF_GITHUB_TOKENS`, and the notifier's `UF_WEBHOOK_URL`/`UF_WEBHOOK_SECRET`, where blank on either one is a channel that sends nothing) and a **"take the default"** (`UF_ALLOW_NO_AUTH`, `UF_COOKIE_SECURE`, `UF_TRANSCRIPT_CACHE_MAX_ENTRIES`, and `UF_PUBLIC_URL`/`UF_INSTALL_LABEL`, whose default is an empty field on a body rather than a behaviour), plus `UF_UNMOUNTED_WORKSPACES`, which is not an operator value at all. `STRICT_ENV_VARS` is collected by `env()` as the module runs rather than listed, so a variable added to `config.ts` cannot be forgotten, and the two lists being disjoint is what `configCheck.test.ts` asserts. **What that disjointness cannot see is compose**, and that is the second pin rather than a detail: compose cannot omit an environment key conditionally, so every optional variable is rendered `${VAR:-}` and a correct install has all of them explicitly blank — which makes each one an edit away from a permanent warning on the dashboard of every stock deployment, naming a variable the operator never wrote. Three of them were exactly that, for as long as the block grew and `BLANK_MEANINGFUL_ENV_VARS` did not, and `UF_UNMOUNTED_WORKSPACES` is the one with no floor under the cost: compose *computes* it from the slots it could not mount, blank is its success case and any non-blank value refuses the boot, so there was no `.env` edit that could clear the warning it raised. Nothing else notices — it typechecks, it boots, every page works, and the only symptom is a banner that is always on, which is how a banner stops being read. So `deployment.test.ts` reads the `environment:` block, resolves it as an install that configures nothing gets it, and refuses a blank-by-default key that `config.ts` reads through `env()`; it pins the exported list against what `optionalEnv` actually reads in the same pass, since that list is what the warning's own sentence enumerates. It pins the other direction too, which is the mirror-image failure and just as quiet: there is no `env_file:`, so that block is the whole of what reaches the container, and a `UF_` name added to `config.ts` and not to compose is read as unset on every compose install no matter what the operator wrote in `.env`. For a credential that is a feature that refuses; for a notifier it is silence, which is what a healthy fleet also looks like.
- `UF_BIND_ADDRESS` (default `127.0.0.1`) is compose-only — the app never reads it, so it is outside everything `configCheck.ts` can say. It is one setting whose other two halves fail *silently* in opposite directions, which is why the comment beside it names both rather than pointing at a doc: an operator who publishes on `0.0.0.0` without setting `UF_AUTH_TOKEN` (or who leaves `UF_ALLOW_NO_AUTH=1` from a loopback install) exposes every route including the one that starts billed agents against mounted code, and the app cannot tell that state from the one it was told to accept; and `UF_COOKIE_SECURE=1` carried over from a loopback install becomes a sign-in that *succeeds* and issues a cookie the browser will never send back over plain HTTP, so every request after it is anonymous and the only symptom is a redirect to `/login`. Do not add a check for the first here: nothing in this process can see which interface Docker published on, and a guess would refuse correct installs behind a terminator.
- `UF_WORKSPACE` and `HOME` use compose's `${VAR:?message}` form, so a missing one aborts `docker compose up` instead of substituting. Both previously had defaults, and both failure modes were silent: Docker *creates* a bind source it is handed, so a wrong path yields an empty folder picker and a dashboard of zeros — indistinguishable from a quiet week. Do not restore a default to either. `UF_WORKSPACE_2..4` still fall back to `UF_WORKSPACE`, which is what keeps all four slots mountable.
- `mem_limit` / `memswap_limit` / `pids_limit` / `cpus` in compose exist because memory here is linear in `maxConcurrentRuns` and `maxConcurrentAssists`: every work cycle is a full Claude Code process — 309 MB before it holds a conversation — that then starts builds and test suites of its own inside the same container. Those two settings bound how many such processes exist; these bound what they may take. Without a limit the kernel's OOM killer picks its victim across the *whole host*, so the process that dies may be an unrelated one; with it the kill is confined, `restart: unless-stopped` brings the container back, and `reconcileOnBoot` closes out the runs with a reason on each. The defaults are sized for the shipped settings — four work cycles plus two other Claude processes — and the arithmetic is in the compose comment and README's *Sizing the container*; raise them **with** the settings, never after. `memswap_limit` matches `mem_limit` because Docker otherwise defaults the swap limit to *twice* it, so the stated ceiling would silently carry that much swap behind it. `cpus` ships as `0` (no quota) because Docker refuses a value larger than the host's CPU count, so any positive default would fail `docker compose up` on a smaller machine.
- `NODE_OPTIONS` states the server's heap ceiling so the term of that arithmetic belonging to this process is a number rather than a property of the host — V8 derives it from the machine's RAM otherwise. It is the one env var here **not** under the `UF_` namespace that every child environment strips (`childEnv`, `chatEnv`, `reviewEnv`, `gitEnv`): the CLI is a Node program too, so inherited it silently becomes each agent's heap ceiling as well, and a `heap out of memory` part-way through a billed cycle is filed by the loop as the agent crashing. Do not move it into the Dockerfile to save a line — an image-level `ENV` is inherited the same way, and the strip is what makes the compose comment true.
- `UF_AGENT_UID`/`UF_AGENT_GID` in compose exist because the container writes to both bind mounts, and they carry `${UF_UID:-1000}`/`${UF_GID:-1000}` — the same numbers `user:` used to carry for the whole container. macOS Docker Desktop remaps bind-mount ownership onto the container user, which is why uid 1000 was never questioned; Linux preserves the host uid and a mismatch breaks `/login`, transcript writes, and `.uf-worktrees` creation. `user:` is now `"0:0"` and the *server* is the only thing that runs as root — see the privilege-separation invariant below for why the split has to be that way round. The image still sets `HOME`, `DATA_DIR`, `CLAUDE_HOME` and `CLAUDE_CONFIG_DIR` explicitly — required, because a uid with no `/etc/passwd` entry makes `os.homedir()` unreliable. A documented command that has to run as that uid takes it from `docker compose exec -T usagefoundry printenv UF_AGENT_UID` and **never** from `-u "${UF_UID:-1000}"`: that expansion happens in the operator's own shell, and `.env` is compose's input, not an exported environment, so it is 1000 on every install that set `UF_UID` in the file and nothing else — which is every install this page's own instructions produce (#147). `docs/security.md` and `docs/verification.md` still carry the old shape.
- The image carries `gh` (`ARG GH_CLI_VERSION`, checksum-verified release tarball rather than an apt source) for the same reason it carries a compiler: an agent asked to open a pull request finds out `gh` is missing halfway through a cycle, inside a tool call, and works around it badly. It is credentialed only by `githubEnv()`, never by a config file in the image — nothing about the image knows a token.
- The image carries Go (`ARG GO_VERSION`, release tarball, digest fetched from `dl.google.com/go/…` — `go.dev/dl/` serves HTML for that path) on the same grounds as `gh` and the compiler, and it is the one toolchain here with a *second* half: `GOPATH=/home/node/go` and `GOCACHE=/home/node/go/build-cache` are stated in the image so that one named volume, `usagefoundry-gocache`, covers both. Without that volume the caches live in the container's writable layer, which `docker compose up --build` discards — so every agent on a Go repository re-downloads every dependency after each upgrade, inside a billed work cycle, and nothing reports it as anything but a slow run. The volume inverts `/data`'s requirement: the *children* are what write it, so the image ships the directory owned by `node` (uid 1000) rather than root 0700, and `docker-entrypoint.sh` chowns it to `UF_AGENT_UID:UF_AGENT_GID` when those are not 1000 — guarded on a `stat` of the volume root, because a populated module cache is tens of thousands of files and an unconditional recursive chown would sit in front of the healthcheck's start period on every restart. `GOTOOLCHAIN` is deliberately left at `auto`: a repository whose `go.mod` demands a newer Go fetches it into that same persisted cache instead of failing the cycle.
- The image pins `@anthropic-ai/claude-code` (`ARG CLAUDE_CLI_VERSION`) and sets a system-wide git identity. The pin protects a reverse-engineered contract: the `stream-json` parser and the OTLP shapes were captured from one build, and both degrade *quietly* when it moves — an unparsed line becomes a log entry, a missing `result` event understates spend. The identity is not cosmetic: a container hostname has no domain, so git rejects its own auto-detected address under the strict ident every commit uses, and an isolated run — whose preamble orders it to commit — ends with an empty branch.
- `UF_SANDBOX`, `UF_SANDBOX_ENFORCEMENT` and `UF_SANDBOX_ALLOWED_DOMAINS` are the CLI's own Linux sandbox, and all three are consumed **entirely by `docker-entrypoint.sh`** — nothing in `config.ts` reads them, which is what keeps them off the blank-by-default warning surface two bullets up, exactly as `UF_GH_EXTENSIONS` is. Blank is off and off writes **nothing**: no `/etc/claude-code`, no policy, no behaviour change, so a stock `docker compose up --build` is byte-for-byte the install it was before the switch existed. `UF_SANDBOX=1` generates `/etc/claude-code/managed-settings.json` root-owned 0644 — root because the agents are `UF_AGENT_UID` and that is the one policy surface they cannot rewrite, 0644 because the `claude` children that must *read* it are that same uid. **Generated at boot rather than baked into the image, and that is the decision.** The seccomp relaxation it needs lives in `docker-compose.yml`'s commented `security_opt` block — or in a `docker-compose.override.yml`, which is where one host's answer belongs — so an install whose Docker rejects or never applied that profile has no working sandbox, and `failIfUnavailable: true` compiled into an image would then mean every `claude` invocation exits non-zero, fleet-wide, with no off switch short of a rebuild (`proposals/Sandboxing/09-implementation-sketch.md:15`–`22`). `UF_SANDBOX_ENFORCEMENT` is that switch and it is an `.env` edit. **What it does not switch is the failure this install actually had**, and that is the sharpest thing on this page: `failIfUnavailable` is a *startup* gate over an availability check that only asks whether `bwrap` and `socat` exist and are executable — it never runs one. So an installed bubblewrap the kernel refuses passes the check, the gate never fires at either setting, and every command is wrapped in a program that exits 1 before the command does. Measured here the expensive way: 214 failed `Bash` calls across 10 runs over fifteen hours, on runs recording $407 between them, with `UF_SANDBOX_ENFORCEMENT=refuse` set and nothing refused. `sandbox.ts`'s `bwrap-failed` markers exist so the next one is a `sandbox` row on the run's own log instead. **Five further things are load-bearing and each fails silently.** The policy carries `enableWeakerNestedSandbox: true` unconditionally, and it is not a confinement: it switches the CLI from mounting a fresh procfs (`--proc /proc`, refused inside Docker's masked `/proc`, measured as `Can't mount proc on /newroot/proc` even as root under the profile) to binding the existing one. Without it the seccomp profile buys a namespace the sandbox still cannot use. It is deliberately **not** counted by `policyNamesSomething`, since a policy naming only it would confine nothing while reading as "on". The policy **can never resolve to nothing**: the CLI hands a command back *unwrapped* when the whole policy names no read deny, no write restriction, no network entry and no credential — and `failIfUnavailable` does not catch that, because a sandbox nothing was asked of is not one that failed — so the credential deny and the two `denyRead` paths are unconditional and are not operator-configurable. It writes `denyRead` and **never** `allowWrite`/`denyWrite`: a write config of any kind makes the CLI bind `/` read-only and rw-bind only the allow set, so a deny-write list with no allow list is a read-only filesystem and a fleet that fails inside its first tool call. Naming `sandbox.filesystem` at all is also what pins `sandbox.filesystem.disabled` to managed settings, which matters because a run that could set that key would drop the credential deny with it. And the file is written to a temp name, parsed, and only then moved into place — a policy the CLI cannot read has its whole `sandbox` block ignored, taking `failIfUnavailable` with it, and a write that fails must leave an operator's own `managed-settings.json` alone. Which is also why the removal on the way back down is gated on `/etc/claude-code/.usagefoundry-owned`: `docker restart` keeps the writable layer, so a policy written under an earlier setting would outlive it, and an off switch that leaves the sandbox on is worse than no switch. The app reads the **file** (`src/lib/sandbox.ts`), never the variable, so an install where the write failed reports no sandbox rather than repeating what `.env` claims — the two are joined by a `[usagefoundry]` line from the entrypoint and nothing else. **Some of it has now been executed, and badly**: an install ran with the policy on and bubblewrap unable to start for thirteen hours, which is where the paragraph above's figures come from and why the `bwrap:` markers exist. What has been measured is that the seccomp profile is what lets a namespace be created (exit 0 at both uids with it, "No permissions to create new namespace" without), that Docker's masked `/proc` refuses the CLI's default bubblewrap shape and accepts the weaker one, and that the availability check does not run what it checks. And, since the seccomp profile and that key went in together, that a `claude` runs a `Bash` command through a sandbox that started (`echo` into `/tmp`, returned, $0.298) and that the credential deny **denies** — a file uid 1000 owns and can `cat` from a plain `docker exec` comes back `Permission denied` through a sandboxed tool call, which is a policy enforced rather than a policy reported. What has **not** been measured is a work cycle doing real work under one: no per-run `--settings` overlay has ever reached a running sandbox, and the `denyRead` paths and the network allowlist are unexercised. `docs/verification.md` carries both the results and the steps still outstanding.
- `UF_LOCK_CLAUDE_HOME` is the other half of that sandbox and a **separate switch on purpose**, also read only by `docker-entrypoint.sh`. `$CLAUDE_CONFIG_DIR/settings.json` is an honored source for `sandbox.*` — the pinned binary resolves the policy from `[...managed, flagSettings, userSettings]` and `filesystem.allowWrite` is documented as *additional* paths — and it is owned by `UF_AGENT_UID`, so until this is on a run appends `{"sandbox":{"filesystem":{"allowWrite":["/"]}}}` and every later session, its own and every sibling's, starts confined to nothing (`proposals/Sandboxing/10-validation.md`, finding 1). Root-owning the *file* does not close it: unlinking is a write to the directory, which the agents own, so the **directory** becomes `0:$UF_AGENT_GID` 0750 and the file `0640` — group rather than world, because on the operator's host this is their own `~/.claude` at 0700, and readable at all because the agents must read their own hooks, permission rules and environment out of it. Nothing is chowned recursively except an entry found in the wrong hands, so **every entry not on the hand-back list keeps the owner it had**, which on a stock install is the agent's. The list is `projects sessions todos shell-snapshots history.jsonl .credentials.json .claude.json backups`; the last two were measured rather than taken from the sketch (CLI 2.1.226 against a throwaway `CLAUDE_CONFIG_DIR` creates `.claude.json`, `backups/`, `projects/` and `sessions/` before it authenticates, and `.claude.json` lands *inside* the directory precisely because `CLAUDE_CONFIG_DIR` is set). Four things are load-bearing and each fails silently. It is **all or nothing and hand-backs run first**: a failure leaves metering intact and the hole open, where the reverse order would trade a policy hole for a dashboard of zeros — `projects/` is `transcripts.ts`'s scan and therefore every window, every guard and every spend figure. A missing `projects/` **refuses the boot's whole block** rather than locking, because a root-owned directory is one the CLI cannot create it in; the other entries are named once, on the boot that takes the directory, and not repeated. The post-condition is asked **from the agent's own uid** (`setpriv`, `test -r`/`-w`), not from `stat`, because root's own `test -w` says yes to everything and a `fakeowner` bind mount can report a chown that the kernel does not enforce; a `projects/` that came back unwritable undoes the lock, where a `settings.json` that is still writable is reported and kept. And **off undoes it**, from the state rather than a stamp — a stamp in the writable layer would be discarded by `docker compose up --build` while the bind mount kept the ownership, so the boot that most needs to hand the directory back is the one that would have forgotten it did anything; the signature is root owning the directory while the agents own `projects/`, which leaves a `~/.claude` that is root's all the way down (compose under `sudo`) alone. Skipped with a line when `UF_AGENT_UID` is unset, the same condition the chown blocks above skip under, because root is not stopped by an owner. **`docker-compose.yml` forwards it**, and it has to: the `environment:` block names every variable it passes and there is no `env_file`, so until that line existed a `UF_LOCK_CLAUDE_HOME=1` in `.env` was read by compose for interpolation and never reached the container — a security control switched on in a file, never applied, and indistinguishable from one that is off (#125). Forwarding it is safe for the reason nothing else here is forwarded blank: no `config.ts` read means no `STRICT_ENV_VARS` entry, so `${UF_LOCK_CLAUDE_HOME:-}` on a stock install is not a permanent warning. What kept it missing was that `deployment.test.ts`'s forwarding assertion matched the `UF_SANDBOX` prefix, which no more covers this name than it would the next entrypoint-only variable; it now derives the list from every `UF_` the entrypoint reads outside a comment.  **Never executed**: no container has run this, and `docs/verification.md` carries the steps, the branch harness that stands in for them and what that harness does not prove.
- `UF_GH_EXTENSIONS` names the `gh` extensions an install wants, and `docker-entrypoint.sh` installs them at boot into `usagefoundry-gh`, the **third named volume** — mounted at `/home/node/.local/share/gh`, which is where gh resolves extensions from (`$XDG_DATA_HOME/gh`, `$HOME/.local/share/gh` when that is unset). Boot rather than the image, because which extensions are wanted is the operator's answer and baking one in versions it with the app while still not reaching the next one; and boot rather than a shell, for the reason the Go cache above is a volume at all — gh's default location is the writable layer, so an extension installed by hand survives `docker restart` and is discarded by the `docker compose up --build` this project is deployed with. The symptom of that is `unknown command` inside a tool call, which the run loop reads as the agent deciding not to use the tool. The image creates the directory so a fresh volume inherits `node` rather than root, and the entrypoint chowns it on the same `stat` guard as the Go cache when `UF_AGENT_UID` is not 1000. Every install runs **as that uid** (`setpriv`), never as root: an extension is an executable the children invoke, and root-owned files there leave them unable to upgrade or remove what they run. It is best-effort and never fatal — a refused extension is a degraded install, not a broken one — so each outcome is one `[usagefoundry]` line and nothing else, and the whole block is skipped with a warning naming the variable when `UF_GITHUB_TOKEN` is blank, because gh answers **no** API call unauthenticated, a public repository included, and `UF_GITHUB_TOKENS` cannot stand in for it (those are chosen by the folder a run works in, and this runs before any run exists). An entry already installed is skipped even when its `@tag` has moved, since a restart is the wrong moment to silently replace an executable that holds a token; the operator removes it and restarts. Nothing in `config.ts` reads this variable — it is consumed entirely by the entrypoint, which is what keeps it off the blank-by-default warning surface the bullet above describes. `deployment.test.ts` pins the three files against each other, because a path that moves in one of them leaves a container that boots, installs, reports success and loses everything on the next rebuild — the original defect wearing a variable that says it is fixed.
- `WINNOW_REF` and `WINNOW_REPO` are **build arguments, not environment variables**, and that is the whole difference between them and `UF_PY_TOOLS` beside them. The Dockerfile clones winnow at a pinned commit into `/opt/winnow`, builds it its own virtualenv there, and `contextPruning.ts` runs `/opt/winnow/venv/bin/python -m winnow` from the image layer. Boot-time installation was the obvious alternative and is wrong here for one reason: with `--autocompact` removed this tool is the **only** thing bounding a work cycle's context, so an install where it failed to arrive is an install whose long cycles run to the model's whole window. `UF_PY_TOOLS` installs best-effort and reports it in a line nobody reads; a `RUN` that fails fails the build. `/opt` rather than `/home/node/pytools` for a second reason that is not taste — that path is a named volume, and a volume takes its contents from the image exactly once, at creation, so a build-time install there is masked by whatever the existing volume already holds. Which is precisely the "installed by hand, lost on rebuild" failure the whole mechanism exists to end. Root-owned and 0755: every agent uid reads it and none writes it, because a tool the run loop shells out to on every cycle boundary, sitting where a sibling agent could rewrite it, is a way for one run to put its own code on every other run's transcript. Pinned to a commit on `CLAUDE_CLI_VERSION`'s argument — the run loop measures this tool's effect and prices it, so an unpinned rebuild moves that contract with no announcement. `WINNOW_REF=` empty builds without it, and `winnowAvailable()` then reports the feature unavailable rather than silently pruning nothing. **Nothing in `config.ts` reads either**, which keeps them off the blank-by-default warning surface, and neither is in `docker-compose.yml`'s `environment:` block at all — a build argument in there would be a variable the container carries and nothing consumes.

- `UF_PY_TOOLS` is that mechanism a second time, for Python, and the reason it exists is a *plugin* rather than an agent. `docker-entrypoint.sh` installs each entry at boot with `uv` into `usagefoundry-pytools`, the **fourth named volume** — mounted at `/home/node/pytools`, holding `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR` and `UV_PYTHON_INSTALL_DIR` under one root so one mount covers all three, with the bin directory on the image's `PATH` (which reaches a hook because `childEnv` copies the server's environment and strips only `UF_*`, `OTEL_*` and four named keys). **The failure it prevents is quieter than the gh one.** A plugin registered through `--plugin-dir` reaches the operator only through its hooks, and a hook body conventionally ends in `|| true`, so a command that is not installed produces no error at all: the hook exits 0 having done nothing and a plugin that announces itself on session start keeps announcing itself. Measured here — 213 sessions told a plugin was active against a command that was never present, which is also the run that settled that `--plugin-dir` **does** register hooks (`SessionStart:startup`/`:resume`/`:compact` all fired). The CLI emits a `hook_response` stream event only for `SessionStart` and `Setup` (`zRo`/`JKy` in the pinned bundle, everything else gated behind `CLAUDE_CODE_REMOTE`), so silence from the other events is not evidence they did not run. **`uv` rather than apt's `python3-venv` + `python3-pip`, and that is the decision.** It gives each tool its own environment, so two Python-backed plugins are not each other's resolution problem; and its bin directory holds launchers, where a shared venv's `bin` on `PATH` would shadow `python3` fleet-wide to install one plugin's dependency. `UV_PYTHON_PREFERENCE=system` so the ordinary case uses the 3.11 already in the image and downloads no interpreter; the install dir is on the volume anyway, for the tool that needs a newer one. **An absolute path is a checkout and takes a different branch**: installed `--editable` and exempt from the already-installed test, so it is re-run on every boot. Both halves are the point. Editable makes the container follow the mounted source rather than copy it — measured, `cozempic.__file__` resolves into `/workspace/…` and a host edit reads back changed — and the boot re-run is the only thing that picks up what editable fixes at install time, the dependencies and the console scripts. A tree too broken to build leaves the previous install in place rather than removing it (measured), so an unconditional reinstall cannot lose a working tool. `name@file:///path` is the pinned counterpart and needs no branch: it carries a name, so it copies once and skips thereafter. **The reach this opens is real and is not new**: an editable install runs code out of a mount the agents can write, on every session start, with no restart in between — which is what a `--plugin-dir` directory already is. The pinned form is the one that does not have it. **Split on spaces and `|` but never on commas** — the one place this deviates from its sibling, because a comma is meaningful inside a version specifier and accepting it would turn `pkg>=1,<2` into two unpinnable entries. The entry goes to `uv` verbatim as a PEP 508 requirement; only the *name* is parsed out, and only for the already-installed test, which is **exact** rather than the substring match the gh block uses (`rich` is a substring of `rich-cli`). Everything else is that block's arrangement unchanged: the image creates the directories so a fresh volume inherits `node` rather than root, the entrypoint chowns on the same `stat` guard when `UF_AGENT_UID` is not 1000, every install runs **as that uid** under `setpriv`, it is best-effort and never fatal, an entry already installed is skipped even when its version has moved, and nothing in `config.ts` reads the variable — which is what keeps it off the blank-by-default warning surface. `deployment.test.ts` pins the three files against each other for the same reason it does for gh. **Two things this does not solve and cannot, both the tool's own behaviour rather than the mechanism's.** A tool with an auto-updater re-installs itself past the pin on every session start, so that switch is the operator's (`COZEMPIC_NO_AUTO_UPDATE=1`). And a tool that installs itself into `~/.claude` on first run is writing the operator's **host** file — that path is a bind mount, which is the whole reason `plugins.ts` passes `--plugin-dir` instead of ever running `claude plugin install` — so it reaches every Claude Code session on the machine and not just this app's. Measured: one `cozempic --version` in a throwaway container wrote 7 hooks into `~/.claude/settings.json`. The plugin's own hook bodies already export both switches (`COZEMPIC_NO_AUTO_UPDATE`, `COZEMPIC_NO_GLOBAL_INIT`); what neither covers is an agent, or an operator, invoking the command directly. And the switches cannot go in `.env` — compose reads that for interpolation and this file has no `env_file`, the trap `UF_LOCK_CLAUDE_HOME` is forwarded against — so they belong in a `docker-compose.override.yml`, which is also the right home for one host's answer to a third-party tool this project does not ship.

- **Playwright and one Chromium are in the image, and nothing configures them.** There is no `UF_` variable here and that is the decision: rendering is not a per-install preference the way a gh extension or a Python tool is — an agent working on a web app either can look at the page it built or it cannot, and the failure of the second is silent. It reads its own JSX, curls its own HTML, and never learns that a dialog opened behind its backdrop. `playwright screenshot <url> shot.png` is one tool call and the PNG goes into the transcript as an image the model reads. **The reason it is a `RUN` rather than a boot install** is the one the Go and gh blocks make: a hand `npm install -g` survives `docker restart` and is discarded by `docker compose up --build`, and what an agent meets after that upgrade is `playwright: not found` inside a tool call the run loop reads as the agent deciding not to look. **What it costs is the largest line in the Dockerfile** — ~640 MB Chromium, ~340 MB headless shell, ~250 MB of X, mesa and font packages, against a 1.9 GB image, all measured (`docs/verification.md`). `--only-shell` would drop the first, but the shell is reachable only through `--channel=chromium-headless-shell`, so every screenshot command an agent writes from memory would fail — a saving paid for in failed tool calls. Firefox and WebKit are absent because a second engine answers a rendering-*difference* question and this answers "does it look right at all"; both are one `playwright install` away for a run that needs them. **`/opt/playwright/browsers` rather than the default `$HOME/.cache/ms-playwright`, and that is not cosmetic**: `/home/node` is chowned recursively in the Dockerfile, and a recursive chown over a gigabyte of browser writes a second copy of that gigabyte into the image. It is also the reason the browsers are not a **fifth named volume** — a volume takes its contents from the image exactly once, at creation, so a shipped browser written into one would be masked by whatever an existing volume already held, which is the trap the winnow block records. The directory belongs to `node` while its contents stay root-owned: the shipped build is one every agent reads and none can rewrite, and a repository pinning a different Playwright version can still put its own build alongside rather than meeting EACCES inside a tool call. `docker-entrypoint.sh` chowns that one directory — **not `-R`**, unlike the three cache volumes above, because a recursive chown of a read-only gigabyte would copy it into the writable layer on the first boot after every rebuild. **`.links` is the one exception and is chowned recursively**, because it holds one 67-byte file per installed package and `playwright install` rewrites its own even on a re-install that downloads nothing: root-owned, the command an agent runs to *check* that a browser is there dies with EACCES under the words "Failed to install browsers", which reads as "there is no Playwright here" and sends the run off to fetch a second Chromium somewhere it can write. **That fix reaches only the installs where the sandbox is off**, which is how the image ships. Under `UF_SANDBOX=1` bubblewrap binds everything outside the write allow-list read-only, so the same command answers `Read-only file system` whoever owns the file, and no chown can change it (measured, `docs/verification.md`). Adding the path to the policy's `allowWrite` does reopen it, and is deliberately **not** done: whether the CLI's `allowWrite` merges with or replaces the working-directory defaults it adds was not measured, and a replacement would leave every agent unable to write its own worktree. Running the browser is unaffected either way — only installing is refused. **Chromium's own sandbox does not work here** for the reason `bwrap` does not — `unshare` is EPERM under Docker's default seccomp profile — and does not need to: Playwright defaults `chromiumSandbox` to false, so the CLI and an ordinary `launch()` both work unchanged, and a script that asks for it explicitly is the one thing that will not.

- **The Codex CLI is in the image and this app never spawns it.** `npm install -g @openai/codex`, pinned by `CODEX_CLI_VERSION`, on the argument the `gh`, Go and Playwright blocks beside it all make: an install typed into a shell lands in the writable layer, survives `docker restart` and is discarded by the `docker compose up --build` this project is deployed with, so what the next upgrade hands an agent is `codex: command not found` inside a tool call — which no part of the run loop reads, and which ends the cycle looking like the agent decided not to run it. It is a tool on the agents' PATH and nothing more: `CLAUDE_BIN` is still the only child kind this app spawns, and `proposals/ProviderFallback/13-recommendation.md` argues out why a second *provider* would be a second `buildArgs`, a second stream parser, a second refusal classifier and a second cost story rather than a flag — none of that is here. **It arrives signed out, and that is deliberate rather than a gap to close**: `childEnv` and its four byte-identical siblings strip `OPENAI_API_KEY` and `CODEX_API_KEY` from every child this app spawns (`docs/agent/security.md`), and `codex login` writes under `$HOME/.codex`, which is an image layer rather than one of the five named volumes — so a signed-in codex lasts until the next rebuild either way, and making it persist is a mount plus a decision about who holds the key rather than a line in the Dockerfile. It is the **last** install block in that file so that moving the pin does not invalidate the Playwright layer above it, which is a 640 MB re-download. ~335 MB unpacked on amd64 and ~292 MB on arm64 from a 123 MB download, and the `rg`, `bwrap` and `zsh` it vendors stay under the package's own `vendor/` — the image's own ripgrep and bubblewrap are untouched.

**`DISCORD_WEBHOOK_URL` is the one variable in this file that is deliberately absent from the process it configures.** It is the switch that starts `scripts/discord-relay.mjs` from `docker-entrypoint.sh` — set, and the relay boots on loopback inside the container under a restart loop; blank, and nothing starts. The entrypoint then `unset`s it, and the ordering is the whole point: the relay is launched *before* the unset so it inherits the URL, and the unset happens *before* `exec "$@"` so the server never has it. `orchestrator.ts` builds every agent's environment as `{ ...process.env }`, which makes any variable the server holds readable by twenty-five unattended models, and this one posts to a channel on possession alone. A relay process started as root keeps it out of reach of the agent uid's `/proc/<pid>/environ`. `deployment.test.ts` pins all three of those positions, because an edit that reorders them still delivers every notification and is invisible in every other way.

The adjacent temptation, refused: the entrypoint does **not** fill in `UF_WEBHOOK_URL` when `DISCORD_WEBHOOK_URL` is set and it is blank. Blank means the notification channel is off, in `notify.ts`, in `webhookConfigured()` and on `/api/status`, and a boot that silently turned one operator variable into another would make "off" a state the operator could no longer express. It warns on the boot log instead — the same asymmetry as everything else here, where only `DATA_DIR` refuses.
