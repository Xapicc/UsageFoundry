# The folder claim, the slot walk and the server lock

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing createRun/promoteQueued in orchestrator.ts, serverLock.ts, db.ts, instrumentation.ts.**

**One writing run per folder subtree, unless the run is isolated.** A **paused** run holds two claims and yields one of them. Its **worktree slot** is absolute — it resumes onto the same branch carrying its own commits, so `activeRuns()` still selects `('queued','running','paused')` and `allocateSlotPath` still skips it. Its **folder** is not: `selectPromotable` reserves for `running` rows only, so a run submitted afterwards takes the folder and works while the parked one waits. Nothing is in the directory twice, because the parked run cannot come back until the folder is free — `sweepPaused` refuses to un-park it while a run is in there, and says so in its stop reason rather than leaving "waiting for the next 5-hour window" standing after that window cleared. It stays `paused` while it waits, deliberately: `paused` is what `reconcileOnBoot`'s grace exception keys on, and joining the queue instead would make a restart close it out. The cost is that a younger queued run can be promoted ahead of it in the ≤60s before the next sweep — accepted, because a parked run losing priority to work that is ready now is the point. `/api/folders` reports the two separately (`busyRunId` blocks, `parkedRunId` is a note), and a parked run has never consumed a concurrency slot. "Folder" means `(physical tree, path within it)` — `conflictKey()` — compared segment-wise and case-folded by `overlaps()`. Path equality is wrong three ways, all reachable from shipped config: the picker offers the mount root, which contains every folder under it; two mounts can be one host directory (compose defaults `UF_WORKSPACE_2..4` to `${UF_WORKSPACE}`); and macOS is case-insensitive. Mount identity is resolved once, at first use, because `/api/folders` annotates up to 400 folders per request and because a per-check `stat` that throws would fail **open**, permitting exactly the collision this prevents.

**The folder claim is a synchronous check-then-insert.** `createRun` runs from entry to INSERT with **no `await`**, so one event-loop turn covers deciding a folder is free and recording that it was taken. Adding a single `await` to that path silently reintroduces two agents in one directory; the `db().transaction()` wrapper does not save you, because better-sqlite3 is synchronous either way. Never key occupancy on `isRunning()` — `procs` is emptied at the end of every iteration, so it reads false while a running run sits in its pre-iteration scan.

**…so what that one turn is allowed to contain is bounded by a constant, not by a repository's history.** The same absence of an `await` that makes the claim atomic makes every subprocess inside it a hold on the loop that drains all the agents' stdout, feeds every SSE stream and beats the server lock's heartbeat — and the slot walk was bounded by nothing. Dirty checkouts are left behind deliberately (`allocateSlotPath`) and are never `taken`, so every admission re-ran `git status --porcelain` over every one of them, for ever: 64 of them at git's own 20-second ceiling in the limit, and hundreds of milliseconds each in the ordinary one, since this app clears `core.fsmonitor` on every call so there is no daemon to make that walk cheap. `MAX_SLOT_PROBES_PER_ADMISSION` is the bound and it is four checkouts — nine git subprocesses with the repository's own `--git-common-dir` asked once, on top of `probeIsolation`'s four — and the walk is ordered cheapest-question-first so the budget is only ever spent on a slot nothing else could settle: one an active run holds comes from SQLite, one an earlier admission found unusable comes from a `globalThis`-pinned memo, and one that is not on disk yet is settled by a `stat`, since a directory that does not exist cannot be dirty and cannot belong to another repository. The memo holds **negative verdicts only**, and that asymmetry is its whole safety argument: acting on a stale *dirty* reading costs a slot number, where acting on a stale *clean* one hands a run a checkout `ensureWorktree` then refuses by name — so a slot is only ever returned after this admission has seen it clean for itself. It expires after five minutes because an operator can clean a checkout up by hand, and the two buttons that do it from inside this app (`commitPending`, `purgeBranch`) say so directly through `forgetSlotVerdict` rather than leaving that window to be waited out. Past the budget the walk still returns a slot number nothing has ever used, which is free by construction, and gives up rather than returning one it has not seen clean — giving up being a **refusal**: `resolveIsolation` throws `slotExhaustionRefusal`, and it does not degrade to `mode: "none"`, because isolation being *used up* is the one downgrade that was never an answer (`docs/agent/isolation-and-landing.md` argues the split between unavailable and used up). The thrown sentence names "the ones this admission looked at" as their own cause, because claiming to have checked all 64 would be a sentence it cannot stand behind. That is reachable only on a store where all 64 slots exist *and* more than four of the low ones are unusable, and it clears itself: each admission's budget is spent learning about four slots the next one then skips for nothing, so a store with eight dirty slots refuses two runs and then settles. **A second thing now runs inside that same turn, and it is bounded on these grounds rather than on its own.** `createRun` generates the run's file price list before the INSERT — a `readdirSync` walk of the folder and one SQLite aggregate over `run_events` — synchronous like everything else on that path, with no `await` to offer and none introduced. The walk stops at `MAX_WALK_ENTRIES`, because a mount pointed at something enormous has to cost a truncated list rather than a stalled server, and the read-count query is memoised per folder for a minute on `globalThis`, since a ranking over thirty days of history is no worse for being sixty seconds old. Every failure inside it degrades to `""`: this is the one door every run in this app comes through, and a run refused because a cost hint could not be built would be that hint costing infinitely more than it saves.

**…and exactly one process may write, which is enforced rather than assumed.** The atomicity above is the event loop and not the database, so two processes against one `DATA_DIR` is the collision the claim exists to prevent, reached with nothing to report it. `serverLock.ts` decided that correctly and gated almost nothing on the answer: a second replica served traffic, admitted runs and spawned billed agents having *correctly* reported that it owned nothing, and the only signal was one `console.warn` at boot. Ownership is now read at the moment of the write, by every writer, through one of three doors on the same pure `ownershipRefusal`: `requireDataDir()` throws for `createRun` — the single admission door, so the API route, the chat's approval pass, a workflow's instantiation and an orchestrator block's emission are all covered once — `dataDirRefusal()` returns the sentence for the callers that answer in prose (`reopenRun`, `mergeQueue.enqueue`, `sendChatMessage`, `startReview`, `startWorkflow`), and `mayWriteDataDir()` is the boolean for the loops with nobody to answer (`promoteQueued`, which is the one route to `startRun` and therefore to a spawn, `sweepPaused`, `startWorker`, and `retention.ts`'s `tick`). That last one is the only loop on this list that **deletes**, and it was gated at boot alone until 2026-09-08: `instrumentation.ts` asked `ownsDataDir()` once, and a process that later lost the directory — `heartbeat` returning `lost`, or a `writeLock` that threw — kept its interval and six hours later ran the whole sweep against a database and mounts another process owned, beside that owner's own sweeper. It stops its own timer rather than skipping a tick, on `sweepPaused`'s rule. **`unclaimed` is not a refusal**, and that distinction is the whole of why `mayWriteDataDir` is not `ownsDataDir`: the claim is made once, at boot, so a process that has never asked has never been told no — every test and every script reaching this module without `instrumentation.ts` in front of it depends on that. A read-only second process is still allowed to boot, deliberately: that is the dev-server workflow `serverLock.ts` was written around, and it now reads without being able to close out the owner's runs. What it cannot be is silent — `GET /api/health` answers **503** with the refusal (keyed on the refusal rather than on ownership, so the seconds before the boot hook has finished asking are not reported as a server that is down), and `ReadOnlyNotice` puts the same sentence above every page. The claim is asked **once and never retried**: a second process that keeps asking is a second process waiting to take the directory the moment the owner stalls past `STALE_MS`, which is the incident this module exists to prevent, so it stays read-only until somebody starts it again.

**A shutdown accounts for the cycles it kills, and it is the only reason the process lingers.** The handler was `killAllAgents(sig)`, `releaseDataDir()`, `process.exit(0)` — synchronous end to end — so not one suspended `startRun` frame resumed and nothing after `await runIteration(...)` ran. `reconcileKilledCycle` exists for exactly this and was reachable from that one place, so a routine `docker compose up --build` discarded every in-flight cycle's measured spend: invisible afterwards to `RunProgress.spentGuardUSD`, to `maxRunCostUSD` and to the instance budget, so a run picked up later overshoots its own cost limit by a whole cycle with nothing saying why. `shutdownRuns` is the replacement and its order is the whole of it. **Nothing new starts** — a `globalThis` flag `promoteQueued` reads, because a run settling during the wait reaches its `finally` and calls it. **Every `running` row is interrupted rather than merely signalled**, through the same single kill path an operator's Stop uses: that is what buys the `SIGINT` first, which is the difference between the cycle's cost being measured and being estimated; it is what stops the loop spawning the *next* cycle now that the process lingers; and it gives the run an ending that names the shutdown instead of `Claude Code exited with code -1`. Every `running` row and not only the ones holding a child, because a run in its pre-cycle scan has nothing to signal and is about to spawn. **The loops are given a bounded grace** (`SHUTDOWN_GRACE_MS`, ten seconds — one step past `interruptRun`'s own 8s `SIGKILL`), waited on only for the runs that actually had a child, so a row left over from a crash cannot make every shutdown as slow as the worst one. **Then whatever they did not finish is mopped up**: `reconcileInterruptedCycles` reads `active_started_at` — the column that made the cycle's own bound answerable from outside `startRun`'s frame — and its UPDATE is *relative* and guarded on that same column, so whichever of it and the loop's own post-cycle write lands second is a no-op rather than a second charge. A cycle whose estimate cannot be recovered says so in the run's log, because an understated run and a run that spent nothing are otherwise identical on every page. `docker-compose.yml` sets `stop_grace_period: 30s`; Docker's default 10s would `SIGKILL` the server at the exact moment the last agent died. What this deliberately does **not** touch is `reconcileOnBoot`'s rule that a restart never resumes anything — that pass still clears `active_iteration`/`active_started_at` for the endings no handler reaches, and a run stopped here is still picked up by a person. What changes is that they can be picked up *together*: `runs.restart_closed` is a flag rather than a reading of `stop_reason`, which is prose and the one thing here that must never become a parse, and it covers both endings a restart now produces — a run the handler stopped and a run the boot failed. The orphaned `waiting` rows are deliberately left out of it, because `reopenRun` puts a `stopped` row back in the *queue* rather than back to `waiting`, and a run whose dependency the same boot closed out would start on work that never happened. **And all of it is the owner's to do**, which `shutdownRuns` asks for itself, before the install-wide `SELECT`, rather than leaving to the handler that calls it: the handler is registered outside `instrumentation.ts`'s ownership branch, so a second process's ordinary exit — a `next dev` restart on a file change, in the very worktree workflow this module exists for — ran the whole reconciliation against the owner's database, logging a shutdown against live rows and firing the webhook for each, setting `restart_closed`, and clearing `active_started_at` on cycles whose agents were still billing. That last one is the one that fails **open**: `installBudget` and a workflow instance's budget both bound `telemetrySpendSince` below by that column, so a stray dev server widened two ceilings at once. `killAllAgents` stays unconditional and is the only part that may be — those children are this process's whatever the lock says — and it goes outright there, because the caller exits the moment the guard returns and a gentler signal has no grace left in which to be noticed.

**The owner asks every beat whether the directory is still its own.** `beat()` wrote the lock unconditionally and compared nothing, though `releaseDataDir` had always compared `ownerId` before unlinking. So a stall longer than `STALE_MS` — and one `gitSync` can reach git's own 20-second ceiling on the admission path, which is why that constant is now derived from `GIT_SYNC_TIMEOUT_MS` rather than chosen — ended with a second process claiming the directory, running all six boot reconcilers over runs whose agents were alive and billing, and then the first process's next beat stamping its own claim back over the top. **Both held it from then on, permanently**, with the folder claim's one guarantee void. `heartbeatVerdict` is that decision, pure and unit-tested for `lockVerdict`'s reason, and a *missing* lock is `beat` rather than `lost` — the owner releases by unlinking, so absence is nobody holding it, which is `stillBeating`'s reading of the same file. On `lost` the timer stops, ownership goes, and every gate in the invariant above answers no from that moment, because they read it at the write. The margin itself is stated where the constant is: staleness is the *second* question `lockVerdict` asks — after only "is there a lock at all", and before both pid comparisons — so it decides two cases rather than one, and only one of them is what the window is for. A live pid that has stopped beating is exactly the stalled owner that must not be claimed, and a longer window only waits longer before claiming it. The other case is a lock whose beat is old and whose pid is *also* gone, which is what a server killed without releasing leaves behind: asking staleness first claims it outright rather than sending it to `OBSERVE_MS`, and that is a shortcut rather than a second answer, because a dead pid and a beat older than the window are two independent readings of the same corpse and the observation ends in a claim too — unless a third process writes the file inside those four seconds, which `heartbeatVerdict` settles within a beat either way. So a longer window costs four seconds on that case, and, on the one that is genuinely a cost, an owner whose dead pid a live process has since taken.

**A restart must close out its own runs, except a recent pause.** `reconcileOnBoot()` (via `src/instrumentation.ts`) marks stale `running` rows failed and `queued` rows stopped. Without it one crash blocks a folder permanently. It **never signals a pid**: the DB outlives the container, so a recorded pid names something else after a restart — plausibly this server. Queued rows are stopped rather than resumed, because auto-starting a days-old prompt as an unattended `acceptEdits` agent is the one thing a queue must not do by itself. A `paused` row within `settings.resumeGraceHours` (default 24) is the deliberate exception: it is not an unreviewed prompt but a run the operator started in a mode chosen precisely so it would carry on across windows, and the sweeper re-evaluates its budget from scratch before anything spawns. Past the grace period it is closed out like any other stale row — that boundary is what keeps the exception from becoming the rule it exempts. A `running` row stays `failed` even under `live-resume`: the child is gone with unknown state, and mapping that to `paused` would be guessing. A `waiting` row is closed out like a queued one, and the reasoning is in the dependency invariants below.

**What `migrate()` finds wrong with the file it opened is a row, not just a line.** Three findings had reached `console.error` and stopped there — a `downgrade` verdict (a rollback to an older image, the one case `schemaVerdict` exists for), a `*_old` table an interrupted migration left behind, and a `chat_proposals_old` whose columns this build does not know — plus the `console.warn` for the stranded proposals it *did* recover. In a container that stream is a scrollback buffer the next restart destroys, and a restart is exactly when somebody comes looking; `reconcileOnBoot` had already made this argument for itself one function over and `migrate` did not inherit it. Each finding now also goes to `ops_events` under the single event name `schema.fault`, with `detail.finding` naming which. **It cannot use `recordOpsEvent`**, and that is the trap to know: `db()` assigns `__ufDb` only once `open()` has *returned*, so a write from inside the migration it is reporting on re-enters `open()`, opens a second connection, migrates again and recurses until the stack goes — which is why the primitive is `appendOpsEvent(handle, …)` in `db.ts`, taking the connection the caller already holds, and why `recordOpsEvent` in `ops.ts` is now a wrapper that passes `db()` rather than the owner of the INSERT. It is also why the `ops_events` CREATE is the **first** statement in `migrate()`: the downgrade is found before this file has any other table at all. The recording is never fatal and must not become so — reporting rather than refusing is argued in `recoverStrandedProposals` and `reportOrphanTables` themselves, and a report that could abort a boot would quietly invert it — so `noteSchemaFault` swallows a failed INSERT for `recordOpsEvent`'s reason. `/api/status` carries the findings of **this process's** migration (`schemaFaultsThisBoot()`, a `globalThis`-pinned list `migrate()` clears each time it runs) rather than a query over the rows, for the reason `restartClosedOutstanding` exists beside `lastBootReconcile`: a monitor built on the archive goes red at the first fault and stays red, where a boot is the only event that can clear one of these.

**A repository's worktree registry is a third claim, and it is the one that waits.** The folder claim above is about a directory an agent writes in; `land.ts`'s `landing` set is about the operator's own checkout; `withRepoAdmin` (`repoLock.ts`) is about `$GIT_DIR/worktrees`, which every checkout in a repository shares. Four callers mutate it and none knew about the others: `ensureWorktree` prunes it at the start of every isolated run, `resolveCheckout` removes a slot and prunes before adding one, and `deleteBranch` and `purgeBranch` remove a slot and delete a ref. **`git worktree prune` is why it has to exist** — it is the one operation here that is repository-wide rather than scoped to a named entry, so it is the one git's own per-entry locking does not serialise for us. Three things about its shape are decisions rather than details. **It waits rather than refusing**, which is the opposite of `landing`, and it follows from who takes it: the run loop is one of the four, and a refusal there would fail a run start because somebody pressed Delete — where a land takes minutes and "another branch is being landed into this folder" is the honest answer. **The sections are short**: the registry read and the removals are inside, `worktree add` and the seeding copy after it are deliberately outside, because an add on a large repository is minutes and serialising it would make concurrent run starts in one repository sequential for no registry reason. **The read that decides is inside the claim that acts** — `worktreeHolding` is called within the bracket in both deletion doors, since a slot read outside it is a slot another caller may since have taken or freed, which is the folder claim's own check-then-act rule one level down. The queue chains on **both** settlements: a section that threw must not wedge the key, because a wedged key is every isolated run in that repository never starting again, which is worse than not having the claim at all. Never take it from inside a section that already holds it for the same repository — every call site is a leaf that runs git and nothing that re-enters. `commitPending` takes neither this nor `landing` and needs neither: it writes into the run's own checkout and touches no registry. **None of this is evidence of a collision** — `proposals/GapRegister/`'s B1 ranks that row on blast radius and records that none was ever reproduced; what this closes is the app-level interleaving, which is the half this repository owns.
