# The orchestrator chat

> load into a session. Each paragraph records a correctness or safety decision

> src/app/chat/page.tsx's question surface, src/app/api/mcp/.**

**The orchestrator chat picks what work to do; something a person wrote picks what an agent may do; a person decides whether it happens.** `chat.ts` is a conversation with a read-mostly tool surface, and the two tools that write anything add a `chat_proposals` row or a template's *prompt* — both inert, holding no folder claim and no concurrency slot. `planProposal` is where a proposal becomes a run, and the branch that matters is the one that is *not* in it: no value off a proposal sets a budget, a permission mode or an isolation choice. Those come from the named template, or from `settings.chatDefaultGuards` when it names none. **A proposal may name a `model` of its own, and it is not a fourth guard however much a new field on `ProposalInput` looks like one.** The precedence is stated once and applied once, in `planProposal`: the proposal's model, then the template's — inherited here with the prompt and the guards — then null, which `createRun` turns into `settings.defaultModel`. What licenses the field is `agents.ts`' ground, restated by `templates.ts` and again beside the column: a model moves cost rather than capability, it reaches `--model` and nothing else, and every cost guard already covers whatever it selects, since the run's spend lands on its own `result` event and in its telemetry whatever model produced it. So `propose_run` and `save_template` each grew a field for it and neither grew one for a guard: the budget, the work-cycle limit, the permission mode and the isolation choice still come from the template or from `settings.chatDefaultGuards`, and there is still nothing on the wire that reaches one. Both tool descriptions say that outright, because a model told it may set the model reads the omission as an oversight. `settings.chatDefaultGuards` is a guard set and holds no model, so an untemplated proposal that named none has nothing to inherit and falls straight through — the second one exists because requiring a template made the chat useless on a stock install, and it is a *person's* configuration either way, which is the property that matters. The second is also *frozen onto the proposal* when it is written rather than re-read at the click, for the reason the paragraph below gives. A proposal that names a template that has since been deleted is refused by name rather than falling back to the defaults: the operator approved the card that said "Fix a bug", and a run under different rules than the card stated is what this gate exists to prevent. `--permission-mode` is not something a model should be able to reach for — the same reason `reopenRun` refuses to become a third route to that flag. The approval route takes an explicit list of ids the page displayed, so a proposal the chat added between render and click is not swept into an approval nobody saw, and it approves in one synchronous pass because `createRun`'s folder claim is only atomic inside an event-loop turn. An id that is not pending in *that* chat is dropped rather than approved — and `decisionNote` then has to say which of the two things it was, because "already decided" is a sentence about this thread's proposals and a selection carried over from another one is not. A batch where every id is dropped is a 400 for the same reason an empty list is: a 200 with nothing started is indistinguishable from a batch that worked, and the page clears the selection on `res.ok`. **A click refused by something that will have cleared by the time the operator looks again is a 400 too, and it is refused whole, before anything is decided.** `createRun` throws for five things and two of them are facts about the moment rather than about the proposal — the install ceiling, whose 24 hours are *rolling*, and another process holding the data-directory lock — so `approveRunBatch` asks both once, up front, and hands the route a sentence rather than a verdict per member. What that avoids is `markProposal(id, "failed")`, which is terminal: `planProposal` refuses anything not `pending`, the route only ever offers what is pending, and the approval loop has no early exit, so one tripped ceiling marked every member of a twenty-proposal click in turn and the only way back to any of them is a billed turn asking the chat to propose it again. The refusal an operator reads says nothing new will start *until spend ages out of the window*, which was true of the install and false of their proposals. Everything else `createRun` refuses for is a property of the proposal — a folder outside every mount, a folder that does not exist, a template or agent since deleted, a rival already continuing the branch — and stays terminal. This is deliberately not a fourth validation pass over what a proposal may be: three doors already re-check those conditions with their own reasons, and `admitDependencies` stays the sole owner of what an edge may be. **There is deliberately no setting that approves a proposal automatically, and the chat itself starts nothing — but auto-start does exist, in one place, and the approval it needs is a different one.** A workflow's orchestrator block starts its runs with nobody clicking anything, because a person saved a graph that had already named that block's folder, its guard set and the most runs it may ever start. The approval moved from the run to the graph; it did not disappear, and everything that made this paragraph's gate worth having survives the move unchanged — see the orchestrator-block invariant below.

**An untemplated proposal's guards are frozen when it is written; a templated one's are read at the click, and the asymmetry is the point.** `chat_proposals.guards_json` holds `chatGuards()` as it stood at the proposal, written server-side by `createProposal` and read back through `proposalGuards` by the only two things that ask — the card and `approveProposal`. The reason the two kinds differ is what each card *promises*. A templated card names a handle, so the operator can go and read the template and see whatever it says today, and reading it live is what lets them fix a bad guard set and have the fix take effect. An untemplated card has no handle and so spells the values out — `plan · own checkout · 3 cycles · $5.00` — and values on a card are a promise about the run that click starts. Both used to be re-derived from `chatGuards()`: the label on every poll, and the run again at the click. So an edit to `chatDefaultGuards` landing in between changed the card under the operator between two renders and started the run under a set no card had ever shown — measured at `plan · own checkout · 3 cycles · $5.00` against a `bypassPermissions` agent in the operator's own folder with no cap on cycles and none on money, and nothing anywhere recording that the two disagreed. That is the same sentence one gate along from the deleted-template refusal, which exists because "a run under different rules than the card stated is what this gate exists to prevent". Freezing removes the window rather than detecting it: there is no fingerprint on the request, no refusal on drift and nothing that tells the operator to reload, **because the card does not go stale**. What null means is a fallback and only ever a fallback — a templated proposal, a workflow one, every proposal already pending across the upgrade that added the column — and it falls back to the live set, which is what every reader did before. A blob that will not parse is null too; a *partial* one is not, and is narrowed by the same `narrowGuards` the settings blob goes through, so an older shape or a hand-edited row resolves to `plan`, a checkout of its own and one work cycle. Every way this can be wrong is narrower than what was asked for, because a guard set arriving from storage may never widen what a run may do. Nothing on the wire can reach the column: `ProposalInput` has no field for it and `propose_run` has no argument, which is `prompt_override`'s rule — prompt text is the half of a run a model may write, and this is exactly what guards are not. The `model` field that now sits two columns over is not a counter-example and carries a comment saying so: it decides what the run costs, which every guard in this blob already measures rather than being set by, and nothing about what the run may do. A **workflow** proposal is deliberately outside all of it: approving one saves a graph the operator then presses Run on, and that is a different gate with its own guard set on each block.

**A proposal may name the task on the board it is for, and it is the one field that is neither frozen nor a gate.** `chat_proposals.task_id` holds an id from `list_tasks` and is read **live** at the click — the title and the status on the card are whatever the board says now — which puts it on the opposite side of the paragraph above from the guards and on a different side again from the template and the agent. The guards are frozen because a card that spells values out is a promise about the run this click starts. The template and the agent are read live *and refuse the click*, because both decide something about the run and a card naming one that has gone would start a run under rules or an identity nobody approved. The task decides **nothing about the run**: not a guard, not the folder, not the prompt, not who it is. It is a record of what prompted the work, so what it needs is a handle the operator can go and read — which is what an id resolved at the render buys — and there is nothing about it a click could be wrong about. So a task deleted between the proposal and the press does not refuse the approval: the run still starts, the card and the run page both say *a task since deleted*, and neither links, because the board row they would open is not there. Approving is also not a claim and not a completion — see `docs/agent/taskboard.md`, which owns the rule that nothing derives a task's status from a run. Unknown at the *tool call* is a different moment and is refused there by name, through `taskRefusal`, on the same ground `propose_run` refuses a deleted template and a deleted agent: a proposal that cannot be believed is otherwise discovered by a person reading a card. `create_task` is the one write on this surface that is not a proposal or a template prompt, and it is on the **chat's** list rather than the shared one — a block's turn is unattended, and the taskboard doc holds the reasoning.

**Prompt text is the one half of a run a model may write, and it is written down as an exception rather than absorbed.** `chat_proposals.prompt_override` replaces the template's prompt for one run, and `save_template` writes a name, a prompt and a model back for reuse — taking `chatGuards()` for a new template and the row's existing guards for an update, so no argument on that tool can move one. The model is the third thing it writes rather than a hole in that: it is a price, and a template that costs more or less than it did is a change the tool says in the thread rather than only returning. The distinction is not cosmetic: guards decide what an agent *may* do and prompts decide what it is *asked* to do, and a chat that cannot adapt a prompt just restates its objections inside the task, which puts the same text in the run with nothing recording that it happened. `composeTask` keeps the two halves in order and separated by a heading, and emits the task alone when there is nothing standing above it — a section marker for a section that is not there is worse than no marker. Every proposal card says which guard set applies, spelling out the untemplated one, and marks a rewritten prompt.

**Who does the work is the third half a model may write, and it is the same act as writing the task.** `chat_proposals.agent_id` and a proposed graph's `agentId` name the saved agent a proposed run would be started as, and neither is an exception to the paragraph above: an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so `planProposal` and `planNode` gain no branch that reads a guard off either. It is an **id** rather than the frozen copy `runs.agent` holds, which is `run_templates`' rule and for its reason — a proposal is form input a person decides on, so it should name the agent as it stands at the click rather than as it stood when the model wrote the card, and the copy is taken where it always is, by `createRun`. A deleted or decayed one is refused **by name** through the same `agentRefusal` at both moments the template is checked at: when the tool records the proposal, where a model can act on the sentence, and again at approval, where the operator can. `list_agents` is what a turn reads first, and it is on the **shared** tool list rather than the chat's: a block names one too, and the alternative is a deciding turn guessing at names out of its system prompt. It grants neither subject anything — the same reason naming one is allowed at all — and it declares the ambient definitions beside the registry, because those reach every run whatever is named and cannot be named at all. The card carries the agent in the line that already carries the folder and the guard set, and *outside* the guard mark: a phrase under the shield would claim it bounds something, which is the one thing about it that is not true however large a fact it is otherwise. `summarizeProposedGraph` says it per block for the same reason it says the fan-out cap.

**The chat's own turn is not started as one, and the asymmetry with an orchestrator block is the whole reason.** `runOrchestratorChild` takes one `agent` and a block hands it the one its node names; `runTurn` deliberately hands it none. **The old reason for that is gone, measured, and is replaced rather than kept** — this is exactly the paragraph the singular flag was expected to overturn and did not. It used to rest on a doubt: a `--agents` member carries a system prompt of its own, and whether `--append-system-prompt` also reached the turn it was delegated was not verified against the pin, so this child — the only one in the app whose boundary is *prose* — could not absorb the question the way the others could. That is now measured, and it went the other way: an agent asked to answer with a secret word stated only in the appended text answered with it, so the appended prompt reaches a `--agent` session alongside the agent's own. What stands in its place is the stronger half of the same argument, and it is not a doubt. This child is bounded by `bypassPermissions`, no allowlist, and `systemPrompt()`'s look-do-not-build paragraph carried by `--append-system-prompt`. Selecting an agent here would make some saved prompt the orchestrator's own role — reachable from a registry a chat proposal can name — which is precisely the thing that paragraph exists to fix, and no measurement can make that safe. The second half is unchanged: there is no work here for one to do, since a chat turn looks and proposes, so what an agent would change is how the orchestrator *thinks*. The `@`-mention in the composer is what an operator actually wants from this — it names the agent the proposed *run* will be started as. Nothing in this app parses it back out of the message: it is text, read by a model that has `list_agents`, which is why a name with a space in it is inserted as it stands rather than quoted into a syntax nothing else here speaks. The popover takes **Tab**, the arrows and Esc and never Enter or ⌘↩, because this composer sends on Enter and a list that accepted a completion with it would swallow the send exactly when the operator had finished typing a name.

**Order is the other half of the work a model may write, and it is a label until a person approves it.** `chat_proposals.spec_id` is the chat's own name for a proposal and `depends_on` is what it says that proposal starts after — labels rather than ids, because the model writes several proposals in one turn and has to point one at another before either has an id. They resolve to *run* ids at approval and nowhere else: `planApprovalBatch` is that decision, pure and unit-tested for `planProposal`'s reason with `releasableRuns`' failure modes. A label naming a sibling in the same click resolves to the run this pass is about to create; one naming a proposal of this chat that already became a run resolves to it; anything else **fails that one proposal by name**, and everything behind it fails too with its own sentence naming the one in front of it. Dropping the edge instead is the failure this exists to have none of — a run told to wait and started immediately is bit-for-bit a run that was never told, and the two agents then work in the same checkout in whatever order the queue felt like. The batch is created in `topologicalOrder`, which moved to `orchestrator.ts` beside `dependencyCycle` for that function's reason: three callers now create runs in one synchronous pass and "every one after what it waits for" has to mean one thing. Without it the order is whatever the page displayed, and a proposal is refused as naming a missing run — an artefact of a render, reported as a fact about the work. Everything `admitDependencies` already decides is deliberately *not* re-decided here — one branch handed over, both ends isolated, no rival continuation, no loop against the live graph — because those need rows and a second copy would be a second set of rules to keep in step; what `propose_run` does check at the door is the subset it can, for the reason it validates everything else there.

**The chat can write a workflow, and approving one saves it rather than starting it.** That asymmetry with `propose_run` is the whole design. An orchestrator block's runs start with nobody looking *because a person fixed its folder, its guard set and its fan-out cap when they saved the graph* — and a graph a model wrote has no such person in it. Saving rather than starting puts one back: the operator reads a card that spells out every guard-shaped fact a canvas would show (`summarizeProposedGraph` — which template supplies each block's guards or the untemplated set written out, where each block runs, how many runs a deciding block may start, whether a merge block may pay to reconcile), then opens the graph, then presses Run. Two separate human decisions stand behind every number in it before an agent exists. `planWorkflowProposal` re-normalizes through the *same* `normalizeWorkflowInput` and the same `folderRefusal` the save route and the validate route call, with the same `currentKnowledge()`, so a template deleted between the proposal and the click is refused by name exactly as `planProposal` refuses one — a second set of rules about what a workflow may be would be confidently wrong about what Approve does the day one of them changed. The **instance budget is not carried**, and there is nothing on the wire that could carry it: no field on the tool, no column on the row, no argument on the plan. That is `startWorkflow`'s "there is nothing to raise it *with*" applied one level up, and its cost is stated rather than absorbed — a proposed workflow runs by hand and `scheduleRefusal` will not let it be scheduled until the operator sets one, which the card says in words. `propose_workflow` requires a `folder` on every non-merge block even though `normalizeWorkflowInput` accepts `""`: the empty string is a real answer from the editor's picker and an *omitted* field is not that answer, and reading one as the other would silently put a block on the mount root — the one selection that blocks every other run in the tree.

**The chat's tools run in this process, and that is a correctness requirement rather than a convenience.** `/api/mcp` speaks MCP over HTTP by hand — `initialize`, `tools/list`, `tools/call` — and the handlers call `createRun`, `listTemplates` and `scanWorkspace` directly. A stdio MCP server would be a second process doing check-then-insert against the same SQLite file, which silently permits the two-agents-in-one-directory collision the folder claim exists to prevent. `workspace.ts` exists for the same reason in miniature: the picker and the chat must not be able to disagree about which folders exist or which are busy.

**The chat's child authenticates with a capability, never with `UF_AUTH_TOKEN`.** `middleware.ts` exempts `/api/mcp` because the edge runtime cannot reach SQLite to check a per-turn credential, so the route checks it itself — the exemption and the check must stay together, or the tool surface is public. That check also has to stand **outside** `auditMutation`, and for a reason about the audit log rather than about this route: it *is* the authentication for the whole tool surface, so a request that fails it has passed nothing at all, and auditing that refusal made `request_log`'s 20,000-row cap a lever anyone who could reach the path could pull — twenty thousand refusals and every line naming a run that was started or a sign-in that failed is evicted. Only the handler that already holds a subject is wrapped, which keeps the line the table exists for (a real capability whose tool call was refused, which is the burst somebody comes looking for afterwards); `DELETE` is not audited at all, being a 405 answered before any credential is read; and the refusal goes to stdout, which nothing caps. The capability is minted per turn, written to a 0600 file rather than into argv (where `ps` would show it), and revoked when the child exits. That file is in a per-turn directory of its own under a base the *server* owns, never in `os.tmpdir()`: `/tmp` is 1777, so `ls /tmp/uf-mcp-*.json` found a live capability without guessing its random name and any of the concurrent agents could run it — the name was never the protection, the directory was the leak. Both are removed on every settle path, including the partial-write one inside `writeMcpConfig`, since a directory left behind is a leak in a path nothing else sweeps. The directory closed enumeration and nothing else, and what closes the rest is a **group**: `--mcp-config <path>` is an argv element and `/proc/<pid>/cmdline` is world-readable, so a work-cycle agent read the path off a sibling's command line and opened a file its own uid owned. Under `UF_CHAT_GID` the per-turn directory and file are handed to a group the chat and block child is in and no work cycle is — 0710 and 0040, so a thief fails the owner check, fails the group check, and is left with the "other" bits, which are zero. A gid rather than a second uid because the chat child must stay the uid that owns the mounted `~/.claude`: that credential is what it authenticates and bills with, and a second uid would need a second Claude account. `chatChildCredentials()` is the one place that differs from `childCredentials()`, and `mcpConfigOwnership()` returning null — no `UF_CHAT_GID`, or no privilege separation at all — falls back to the previous arrangement whole rather than half-applying it, because a config the child cannot read is a turn with no tools, which reads as a model that chose not to call any. It names a **subject** rather than a chat id, and that is a discriminated union rather than two optional ids on purpose: the subject is what decides which tool list the caller is offered, and a shape where both ids can be absent is a shape where the route can forget to check which it has. The subject also *scopes* one tool: `get_run_diff` answers for the runs a chat proposed (`chatOwnsRun`) or the runs of a block's own instance (`instanceOwnsRun`), and refuses the rest with a sentence naming what to use instead. That is the one place blast radius is bounded rather than the theft prevented — a token is its holder's identity, so a stolen one is indistinguishable from the turn that minted it, and patch text was the one thing on this surface a work cycle could not otherwise reach from the folder it was started in. `list_runs` and `get_run` stay install-wide deliberately: "what is already in flight" is the question the orchestrator exists to answer, and a file list is not a patch. `telemetryEnv` used to hand a child `UF_AUTH_TOKEN`, and that precedent was deliberately not followed: that token opens every route for as long as it is set, where this one opens a read-mostly tool surface — the two things it can write are a proposal and a template's prompt, neither of which does anything until a person acts on it — and dies with the turn. That reasoning was an argument for fixing the exception rather than for keeping it, and the exception is gone: the exporter now carries a capability of the same shape, minted per run by `ingestTokenFor`, opening one thing (writes to that run's own telemetry) and revoked when the run's loop ends.

**The chat runs with no tool allowlist that bounds anything, so the system prompt is the boundary.** It runs `--permission-mode bypassPermissions` with no `--disallowedTools` and one `--allowedTools` that grants nothing — `SEARCH_TOOLS`, which is `Grep` and `Glob`, named because the pinned CLI otherwise does not offer them at all and an orchestrator with `Read` and no way to find what to read proposes badly for exactly the reason below. Under `bypassPermissions` there is no prompt for a named tool to skip, so it moves no boundary; what it moves is the tool list. An orchestrator's whole job is to find out enough to propose good work, and the allowlist this replaced — this app's tools, `Read`/`Glob`/`Grep`, read-only `gh`, `git log`/`status`/`branch`, `cd` — refused every question it had not anticipated (a build log, `gh api`, `git -C <path> log`, anything compound), which is a bad proposal an operator then approves believing it was researched. Not `plan`, which refuses MCP tool calls outright (measured: `Cannot call mcp__uf__list_templates while in plan mode`) and would leave the chat able to read GitHub and not this app; not `acceptEdits`, which holds mutating shell for an approval a `-p` child has nobody to give — the same failure `ISOLATED_GIT_TOOLS` exists to fix — so it would reproduce the refusals less predictably. What replaces the allowlist is `systemPrompt()`, which states the role rather than a list of forbidden tools: look, do not build; do not edit, commit, push, or act on GitHub; a task small enough to just fix is a proposal that says it is small. Everything that bounds this child is elsewhere and unchanged — nothing it can call starts a run, `--strict-mcp-config` keeps the mounted `~/.claude`'s MCP servers out, the capability token dies with the turn, `chatTurnBudgetUSD` caps the spend, and `--add-dir` still names only the mounts. The costs are real and are written down rather than absorbed: the chat can write into a checkout the operator also works in, and `githubEnv()`'s token now authenticates writes as well as reads. `permission_denials` is still read and shown in the thread — now because it should be *empty*, so an entry is the CLI declining something on its own.

**A chat turn is spend with no `evaluateBudget` behind it.** It passes the same gate a review does — `assistRefusal()`, the operator's own configured ceiling already spent — and nothing else, because there is no per-chat fraction and inventing one would be a threshold nobody set. `settings.chatTurnBudgetUSD` (default $2, null disables) is therefore the only other bound besides the ten-minute timeout, and it is enforced *inside* the CLI via `--max-budget-usd` rather than between cycles. `chat_sessions.cost_usd` is displayed on the chat page only: never added to `runs.spent_usd`, never to the meters. The same money also lands as **one dated row per settled turn** in `chat_turn_spend`, and the two are both needed because neither is derivable from the other: the running total answers *what has this thread cost*, which is what the page shows, and the rows answer *what did this install spend on chat inside the window*, which is what the install-wide ceiling reads. Summing the running total bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in, closing every door in the app and stopping the runs already in flight. The row is written inside `finishTurn`'s existing latch and after it, so a late settle that moved no total adds none. `githubEnv()` reaching this child is a real widening of "GitHub credentials reach a work cycle and nothing else" — a chat asked to read issues cannot without it — and is written down rather than absorbed quietly.

**A settle belongs to one turn, and `finishTurn` refuses to settle any other.** `endTurn` writes `failed`, appends the sentence and returns while the child it signalled is still working through an eight-second SIGINT/SIGTERM/SIGKILL ladder — deliberately, because the turns that need ending are the ones whose `close` is not coming, so the row has to be usable before the child is gone. But `failed` is also exactly what invites the retry, so the row is routinely `thinking` again *under a different turn* by the time the old child exits. `chat_sessions.turn_seq` is bumped by the claim in the same statement that writes `status` and `turn_started_at`, never reset, and carried by the child claimed under it; `finishTurn` matches on it as well as on the status, and a settle that matches neither changes nothing. Latched on status alone, a stopped turn's child settled the turn that replaced it: its text appended as the answer to a question it never read, its cost and session id adopted, the live turn left unwatched by a sweeper that reads only `thinking` rows, that turn's own answer later discarded in silence against an `idle` row, and a third billed message admitted by a guard that reads the row rather than the process. A counter rather than `turn_started_at`, which is otherwise written and cleared in all the right places: it is `Date.now()`, two turns claimed inside one millisecond would share it, and the entire value of the latch is that it can never mistake one turn for another. The timeout path is the same sequence with a different first sentence, because `sweepStuckChats` calls the same `endTurn`. What a refused settle costs is a superseded child's own figures, and that is the trade rather than a free win — the CLI reports cost and session id only in the final JSON object a signalled child is not expected to print, but one that does has them dropped rather than charged to a turn the operator is still watching.

**Every way a turn can end writes the ending into the thread, and the row is not a record of it.** There are four — a cancel and a timeout through `endTurn`, a failure through `finishTurn`, and a restart through `reconcileChatsOnBoot` — and each appends a `system` message saying what happened, in the words the row was given. The reason is `claimTurn`: it writes `error=NULL` in the same statement that takes the next turn, and that is right, because `chat_sessions.error` describes the turn the row is on and not the one before it. So the row's copy lasts exactly until the operator retries, which is the *first* thing they do, and a thread whose only record was there reads afterwards as one question followed by another with no reply and no note between them — an answer that never came rather than a turn something killed, which is a different thing to do next. The restart path is the one where this is easiest to leave out and where it is worth the most: it is the only ending nobody is present for, so the sentence is the whole of what the operator finds when they come back. It reads the `thinking` ids *before* the UPDATE, because `status` is the only mark a stranded turn carries and the UPDATE is what removes it. Nothing is resumed on any of the four — a chat turn is a question somebody asked minutes ago, and re-asking it unattended is spend nobody is present to want — so saying so is the entire remedy.

**The chat can ask the operator a question, and asking is how the turn ends rather than something it waits through.** `CHAT_TIMEOUT_MS` is ten minutes, an overrunning turn is killed and its answer is discarded, so a tool call that blocked on a click would spend the whole window and lose the turn that asked — `ask_operator` therefore records `chat_questions` rows and returns immediately, and the second sentence of what it returns is that no answer is coming back through it. That sentence is load-bearing rather than decorative, and so is the description above it: the tool-calling half of the orchestrator's instructions lives in `/api/mcp`'s descriptions and is deliberately not repeated in `systemPrompt()`, because a description cannot drift from the schema and a prompt can — and a model reading this one as "returns the operator's answer" calls it, gets a receipt, and calls it again until `chatTurnBudgetUSD` stops it. That fact is the single exception the prompt makes to the split: the asking paragraph names `ask_operator`, says it records the questions and ends the turn, and points at the description for the judgement about what is worth asking, which stays where it cannot drift. The pointer is there because a deferred description is only fetched when something names it, and 3 of 98 surveyed conversations fetched this one. The answer arrives on the **next** turn, which is the same conversation to the model (`--resume` against `chat_sessions.session_id`) and a different process to everything else, which is why the answer message quotes each question above the answer to it instead of sending the bare string the operator typed: a fresh child has the thread but not the tool call, and "pnpm" on its own is a referent it has to guess at silently. `chat_questions` holds even less than `chat_proposals` does, and what it holds is nothing — no guard, no permission mode, no budget, no model, no folder claim, no concurrency slot, and nothing derived from `activeRuns()` can see it. A question is a sentence and an answer is a sentence; the only thing answering one starts is another chat turn, and it starts it *through* `sendChatMessage` rather than around it, so every gate a message passes — `dataDirRefusal`, `assistRefusal`, the install ceiling, the claim, the sweeper — an answer passes unchanged. The bounds on asking are the same shape as `MAX_PENDING_PROPOSALS`' and exist for its reason: at most five questions open on a thread and at most eight choices on one, because past that it is a form rather than a question and a form gets skimmed — and a skimmed answer is worse than none, since the model proposes on it either way and only one of the two is something the operator will remember agreeing to. Three shapes are refused by name rather than repaired, and the reason is the same each time — which of two things the model meant is not something the route can know, and a question repaired into a different question is one the operator answers correctly and the model reads wrongly. A single choice is a decision already taken rather than a choice. A list longer than the cap is counted **after** normalizing, so "twenty options" and "twenty copies of one option" are told apart and the number in the refusal is the number that would have been rendered. And no choices with no typed answer is a card with nothing on it to press — reachable without the model meaning any of it, since `choices` sent as a bare string normalizes to none, which is exactly the arrival shape `normalizeChoices` exists to survive.

**A pending question is derived from `chat_questions` and is never a fourth `chat_sessions.status`.** Three reasons, each sufficient on its own, and all three are about paths that already exist. `finishTurn` settles under `WHERE status='thinking' AND turn_seq=?`, which is the settle-once latch every stranded-turn path depends on, so a status meaning "asked and waiting" would have to be written by that same statement — and a turn cancelled or timed out after it had asked would then settle as `failed` and lose the question, or as `asking` and lose the failure. `reconcileChatsOnBoot` fails out `thinking` rows because the child is gone with the process that started it, where a question is a row in a database and survives a restart intact, so a status that meant both would need excluding there by hand — a silent way for a restart to eat every open question. And `sendChatMessage` refuses to send into a `thinking` chat, so a status meaning "waiting for the operator" would sit directly beside the guard that must not refuse the answer it exists to collect. What deriving costs is one query on the poll the proposals already pay for; what it buys is that **nothing about the turn lifecycle changes at all** — a turn that asked ends `idle` like any other, a chat with a question open has no child and an operator who may type anything into the composer, and a question outlives every way a turn can die.

**A question is drawn in the conversation and never in the panel beside it, and *where* it lands is a decision rather than an ordering.** The panel is work waiting to be approved and costs nothing until somebody clicks; a question is a sentence, answering one starts a chat turn and never a run, and it belongs in the half of the page the other sentences are in. It is drawn as an object because it has controls on it, and it is deliberately not a `Card`: `emphasis` carries padding as well as elevation, so a box that changed emphasis inside the scrolled transcript would re-pad the transcript under a reader's hands on a surface that polls — which is the same trap `PROPOSALS_EMPHASIS` records for the conversation card itself. `threadItems` is the placement, pure and unit-tested on the grounds the three functions above it are: every way of getting it wrong produces a *page* rather than an error, and the worst of them is the quietest thing this whole mechanism can do — a question the page never draws leaves the thread waiting on an answer to something the operator was never shown, with no error, no empty state and nothing in the console. The unconditional tail append is what makes that unreachable and is the first case in the file. A question is placed **before the operator's next message** rather than at its own `created_at`: `ask_operator` records the row *during* the turn, so by timestamp alone the card would sit above the reply explaining why it was being asked, and everything between a question and the operator's next message is the rest of the turn that asked it. That is what puts a pending one at the foot of the thread beside the composer and a settled one directly above the message that carried the answer. The comparison is **strict** — `sendChatMessage` appends the message and only then spawns the child that asks, so on `<=` a question would be drawn above the message that provoked it every time the two landed on one millisecond. Only a `user` message closes the placement, because an assistant reply and a `system` failure notice are both the same turn still finishing.

**A settled question keeps its place, and the message beside it is not a duplicate of it however much it reads like one.** A card that vanished when it was answered reads as a question nobody was ever asked, and `answerMessage`'s quoted `Q:`/`A:` block — appearing in the operator's own voice, in words they did not type — then reads as text that arrived from nowhere. Both are drawn, and they are two different facts: the card is the question as it was *asked*, and the message is the text the model was *sent*. Suppressing the message was considered and refused, and the reason is a coupling rather than a preference — the only way for the page to know which message is the generated one is that an `answered` row can only have been settled by `answerChatQuestions`, so a later change letting an ordinary message settle a question as answered would silently eat the operator's real words. `superseded` is drawn as neither an answer nor a failure: saying something else *is* an answer, and danger red would report a redirection as a fault.

**A choice sends on one press only when it is the last question open, and the card says which of the two shapes it is in.** Sending on the press is the entire point of offering buttons, and with nothing else open there is nothing the send can take with it. With siblings still open it cannot: the answer message settles the set and supersedes everything it did not name, so one hasty press would close two questions the operator was still reading — and `answerMessage` would carry them to the model as `(not answered)`, which is the model's cue to stop asking about them. So above one question the choices fill in, `aria-pressed` marks the chosen one, and the row's own button sends them together under a line saying that anything left blank is sent as not answered. The typed answer is an `Input` from the kit and not a hand-written control: below the shell's breakpoint iOS Safari zooms the page in on any text field under 16px and never zooms back out, `CONTROL_BASE` is where that floor lives, and the composer is this app's one hand-written exception rather than a precedent for a second. Enter inside a question's field answers, which is the composer's own chord in the one other field on the page that sends. Every control on the card is out while the chat is `thinking`, with the reason said in words: `ask_operator` returns immediately, so a question can be open while the very turn that asked it is still running, and `sendChatMessage` refuses a second billed child on one conversation.

**The composer beside an open question is neither disabled nor pre-filled, and it says what sending does.** The chat is `idle`, there is no child, and the operator may type anything they like — which is the paragraph above about a pending question not being a status, made visible. What the page owes them is the consequence: an ordinary message is the operator declining and redirecting, and the same statement that records it closes every open question as overtaken. Unsaid, a question answered in prose reads as still waiting and its card stays pressable a week later to start a billed turn about a conversation nothing in the thread is about any more. Pre-filling would be worse than disabling: the words would go out through `/message`, which supersedes rather than answers, so the model would be told nobody answered while the operator watched their own answer being sent.

**A chat waiting on an answer is drawn as waiting, and it stays on the *idle* poll.** The fast cadence exists to catch a turn landing; nothing on the server can produce an answer, so three-second polling would be three times the requests for a row that cannot move until a person clicks. It equally does not stand down, which is the half worth writing down: the answer can arrive from another tab, and the thread list beside it moves for reasons that have nothing to do with this conversation. In the list a waiting thread says `asked you` in the row's own voice rather than in a second accent chip beside `N waiting` — `pendingCount` and `pendingQuestionCount` are kept apart because one is approving work and the other is answering a sentence, and two badges that looked alike would send the reader to the wrong half of the page, which is the confusion not summing them exists to avoid. `thinking` is already drawn that way one span over and the two can legitimately be true at once.

**An ordinary message supersedes every open question, and an answer supersedes the ones it did not name.** Saying something else *is* an answer — it is the operator declining and redirecting — and leaving the question open instead leaves a card that can be clicked a week later to start a billed turn about a conversation nothing in the thread is about any more. The row is marked `superseded` rather than deleted, for `chat_proposals`' reason: the thread has to read as what happened, and a question that vanished reads as one nobody was ever asked. `answered_at` stays null on it, because it is the instant an answer was given and a superseded question was never answered. Both halves are one `UPDATE ... WHERE chat_id=? AND status='pending'` inside `sendChatMessage`'s no-`await` window, so a request that loses the claim settles nothing exactly as it appends nothing, and the pass is idempotent — an id that stopped being open is a no-op rather than a resurrection. The refusal a person can act on is `settleQuestions`, decided before any of it is paid for, and it fails the **whole** call when any id is not open. That is deliberately not the approval route's rule, and the difference is what the ids are: there they are independent, so a stale one is dropped and reported in a sentence; here they compose one message, so a dropped id is the operator's typed answer silently absent from the text the model reads — and the model then answers as though the questions that survived were all it asked. An unanswered question is named in that message rather than left out for the same reason: omitted, it is indistinguishable from one that was never asked, and the next move is to ask it again.

**`GET /api/chat` answers two different questions, and which one is decided by whether it was given a parameter at all.** Bare, it is what the page polls: the newest 30 threads *and* the thread to open on, which is `latestChat()` — and that **creates** a thread when the install has none. With `q`, `offset` or `limit` it answers with the list alone, because a search must not do that: an operator looking for a conversation from March would otherwise leave an empty thread behind every time they typed. The 30 stays, and is not the gap — it is the live sidebar list, re-read on every poll while a turn runs, and streaming every thread through that payload would grow it with the install. What was missing was any *other* way to reach a thread, so an approved proposal's reasoning became unreachable the moment thirty conversations had happened since. `findChats` is that way: `LIMIT`/`OFFSET` beside a `COUNT(*)` over the same predicate, and the text matched against the title **or** any message in the thread — a title is written by the model from the opening line, so searching titles alone finds only the conversations somebody already remembers. `EXISTS` rather than a join, so a thread with forty matching messages is one row. The operator's text is a bound parameter and its `%` and `_` are escaped, because unescaped a `%` anywhere in a query matches every thread in the install and a search that returns everything reads exactly like a search that found everything. On the page the results are held apart from the polled list and not for tidiness: that list is overwritten every few seconds, so a result set kept in it would be wiped mid-read.

**The poll asks for the messages it does not have, and that is the only half of the thread a cursor may be right about.** `GET /api/chat/[id]` takes `?after=`, the highest `chat_messages.seq` the page holds, and `chatDTO` answers with the messages past it — the mechanism `/api/runs/[id]/stream` has always used for the run log, arriving here because the chat page re-asked for the whole conversation every three seconds for as long as it was open, so the cost of leaving a chat on screen rose with the chat and never came back down. Measured on a 500-message thread, one poll went from 246,362 bytes of JSON to 1,136, and on a 2,000-message thread from 1,004,522 to 1,137 — the point being the two figures after, not the ratio. **Only the messages ride it.** They are the one store on this page that is written by appending and never touched again; proposals and questions are both updated in place after they are written, so a cursored read of either would leave a decided proposal drawn with its buttons and an answered question still asking. Those two are re-read whole on every poll on purpose, and so is the thirty-thread sidebar above. **The bound is the index, not the parameter.** On `idx_chat_messages_chat (chat_id, ts)` SQLite answers `seq > ?` by visiting every row of the thread and sorting the survivors in a temp B-tree, so the cursor would shrink the *response* and leave the work where it was; `idx_chat_messages_seq (chat_id, seq)`, created in `migrate()` after the column it names, is what turns it into a range scan. The page appends what comes back rather than replacing what it holds — `mergeMessages`, which drops anything at or below the highest `seq` on screen, because the interval fires whether or not the last request has answered and two polls on one cursor are ordinary. `messagesFrom` on the payload is what says which kind of answer it is: a send, a cancel, an answer, a decision, the first load and a `?after=` the page could not have sent all come back as the whole thread, at zero, and replace.

**A chat turn is durable while it is happening, and it was not.** The child runs `--output-format stream-json --verbose` — the run loop's format, for `emit()`'s reason — and every event folds into `chatStream.ts`'s accumulator, which `chat.ts` writes to the row every half-second. Under `--output-format json` the CLI printed **one object when it exited**, so the whole turn existed in one process's memory until it was done: a restart, an OOM or a deploy in the middle lost the assistant's text, the `chat_turn_spend` row and the thread's running total *together*, while the money stayed spent. Four columns carry it — `partial_text`, `turn_tokens`, `turn_cost_est`, and `partial_at` — and all four are **per turn**, cleared by `claimTurn` and by `finishTurn` in the same statement that takes or settles the turn, for `error`'s reason: a value that survived into the next turn is the previous turn's text and the previous turn's money attributed to this one. `partial_text` is a **live view and never the stored message**: a settled turn still appends the CLI's own `result` string, so what a finished thread looks like is unchanged, and the DTO nulls the partial the moment the status does so the answer is never drawn twice. **The two figures are different kinds of number and nothing may merge them.** `turn_tokens` is what the CLI reported and is measured, so a turn that was cut off folds it straight into the thread's count. `turn_cost_est` is this app's own price for those tokens through `guardCostOf`, so it is a **guard** figure: it lands in `cost_usd_est` beside `cost_usd` and never inside it, and the `chat_turn_spend` row it produces carries `estimated = 1` so `installSpend` can put it in `spentGuardUSD` and keep it out of `spentUSD`. That is `runs.spent_usd_est`'s rule one table over, and the page states the split rather than adding the two. **Four endings reach `keepPartialTurn` and none of them gets a `result` event** — a cancel, a timeout, the install ceiling closing on a live turn, and a restart through `reconcileChatsOnBoot`. The half-answer becomes an ordinary assistant message *before* the sentence about how the turn ended, because the note is a footnote to the text above it and the other order reads as an answer that arrived after the failure.

**The install's ceiling is asked again while the turn runs, and that is what `chatTurnBudgetUSD` never covered.** It used to be read once, at admission (`sendChatMessage`), so a turn admitted at 99% of a rolling 24-hour window could run for ten minutes past it, and a turn admitted before three runs finished ran against a figure that had already moved. `--max-budget-usd` bounds *this* turn inside the CLI and always did; what nothing bounded was the install while this turn was going. `recordProgress` re-asks every ten seconds, and only on an event that moved the spend — the ceiling is a scan of three tables and the answer changes slowly, so the overshoot it accepts is ten seconds of one turn. The estimate it has just written is what `installSpend` reads for it, so the check includes the turn asking it. A turn stopped this way ends through `endTurn` like any other, keeping its text and naming the ceiling rather than the symptom.
