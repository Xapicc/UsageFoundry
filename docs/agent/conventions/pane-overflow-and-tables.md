# Pane overflow, tables and character art

[← conventions index](../conventions.md)

Read before editing `src/components/ui/Table.tsx`, `ListView.tsx` or `AsciiArt.tsx`, or anything inside the pane sized in viewport units or unable to wrap.

  - **A control that cannot wrap is a control that pushes the pane sideways.** `SegmentedControl` is an `inline-flex`, and a five-option group is about 330px of segments against the ~358px a 390px phone has once the pane's gutter is off — so it carries `max-md:flex-wrap`, in the component rather than at the two call sites that are near the line, because the next five-option group will not know it is near it. Nothing above the breakpoint comes close to the width, so the rule changes nothing there.

  - **Character art is sized by the widest glyph in it, which is not the monospace advance, and getting that wrong widens a card rather than overflowing it.** This app downloads no font on purpose (`globals.css` says why beside `--family-sans`), so every stack it ships **falls back** for the block and box-drawing ranges, and the face that answers draws one glyph per em: measured in Chromium on the app's own `--family-mono` at `font-size: 14px`, `M` is 7.00px and every one of `█ ░ ▒ ─ ╳` is 14.00px. Two consequences, both silent. A run of blocks is **one unbreakable word**, so it sets its container's min-content width, and a card is a grid item whose automatic minimum size is exactly that — an over-wide bar therefore does not overflow, it widens the column, and `AppShell` clips the result rather than scrolling it, so `smoke-pages`' sideways-scroll assertion stays green while the card's right edge is off screen. And a mark mixed in from ASCII draws at *half* the width of the blocks around it, so a `?` track is half the length of a `█` one: `AsciiBar` uses U+2573 for "no ceiling" for that reason and not for a typographic one. **And which face answers is the reader's, not this app's**: the same `█` measured 0.602em — the mono advance, the range covered by the mono face itself — in the browser a VisualEdit handoff came from on 2026-09-11, which is a `default` meter 141px wide where the budget said 221. So a *count* is fitted rather than budgeted: `AsciiBar` divides its own drawn run by the cells in it, subtracts that from the bar to get the brackets, and fits the remainder to the track (`fittedCells`, and `contain: inline-size` on `.uf-meter` is what stops the bar it then draws from moving the box it measured). Budget a count only where nothing has been measured yet — the server's render, and the default skin, where the bar is `display: none` and measures zero — and budget that one against **one em a cell**, the widest a cell can draw, with `.uf-meter`'s containment as the backstop, so a bar that is still too wide hangs over its card visibly instead of quietly drawing a fuller reading. Measure a new glyph before using it rather than assuming the file it came from is monospaced. **A box-drawing glyph's stroke runs down the *middle* of its em box**, which is the same measurement one level up and the one that decides where a character frame goes: laid flush inside a surface it draws its line half a character in from the border it replaces — measured on `/agents` in dark, the card surface began at x=16 and the stroke stood at x=23, a 7px band of card outside its own edge on all four sides. `AsciiFrame` and `AsciiEdge` are therefore inset by `-0.5em`, not `0`, and the half that hangs outside is the glyph's empty side. **Half is the whole correction only where the host carries no border of its own**, because an absolutely positioned frame is placed against its host's *padding* box and `uf-unboxed` paints a border out rather than removing it: measured on `/` at 1920x963, DPR 2, light, a `Card` whose border box ended at x=1900.00 inked its `│` on device columns 3797–3798 — centre css 1898.73 — while the identical frame on `ListGroup`'s border-less wrapper, ending at x=1883.00, inked at 3765–3766, centre css 1882.73. One component, one em, a pixel apart relative to the box each was framing, and device column 3799 still card fill: the last pixel of the halo the `-0.5em` was introduced to remove. `globals.css`'s `.uf-unboxed > .uf-ascii-frame` backs that pixel out of the inset and the two agree (1899.75 against 1882.73, same reading at 1280). **`AsciiEdge` needed the same pixel and could not take the same rule**, because `inset` is a shorthand: the right edge carries `inset-y-0` and the bottom one `inset-x-0`, and a shorthand would take those with it and leave one character where an edge was — so `AsciiEdge` emits `uf-ascii-edge-right`/`uf-ascii-edge-bottom` and `globals.css` moves each on its own axis, which is also the only axis its host has a border on (`Sidebar` `border-r`, `Toolbar` `border-b`; correcting the other would push the stroke a pixel *out* of true). Measured on `/` at 1280x900, DPR 2, ascii, light: the sidebar's `│` went from device columns 445-446, centre css 222.99 against a border box ending at 224.00, to columns 447-448, centre 223.99 — the card's own reading on that page, 1260.00 against 1260.00 — and device column 447, which was still `bg-inset` (245) against the pane's 240, is now the stroke. The toolbar's `─` takes the same one pixel, 51.36 to 52.36 against a box bottom of 52.00; it reads as 0.36 outside where the card's `─` reads 0.03 inside, and that gap is the device grid and not the rule — a 13px `─` inks two rows weighted 0.22 of a device row below its em centre, and the toolbar's centre lands on a whole css pixel where the card's lands on 412.39. Below that, the stroke rasterises ~0.27px left of its column's geometric centre at `--text-sm` = 13px, unchanged by the correction and not worth chasing with one. **And a full block is a 0.94 square in that box, on both axes**: `█`'s ink is 94.00 tall at a 100px font size and `████` is 394.00 of ink across 400.00 of advance, so character *art* — a stack of blocks meant to read as one shape — needs `line-height` and `letter-spacing` pulled in, while `│` fills its box exactly (1.0000) and a frame is right to keep `leading-none`. Do not carry a blank character into block art either: a space is half an em here and `▀` measured 0.709em, so the block range is answered by more than one face and the only safe gap is an ink glyph drawn transparent (`ui/AsciiArt.tsx`).

- **A box inside the pane is never sized in viewport units, because the pane is not the viewport.** It is the window less the toolbar less the pane's own `pt-5`/`pb-12` less whatever heading the page puts above the box — so `62vh`, `68vh` and `calc(100dvh - var(--toolbar-h))` all named a box taller than the space it had, and every one of them hung past the bottom edge and gave the pane a scrollbar whose whole travel was empty: a screen-deep band under a 62vh log that the inspector beside it had already stretched the row past, a composer under the fold behind a thread that was scrolling itself. What replaces the figure is a mechanism rather than a better figure — `main`'s wrapper is a **flex column of `min-h-full`**, so `flex-1` means "fill what is left" and `min-h-full` rather than `h-full` keeps a page longer than the pane growing exactly as before. A box that fills that way must not also report its *content* as its intrinsic height, or the row is sized by the transcript instead of by the pane: the run log fills by being taken out of flow (`lg:absolute lg:inset-0` in a `relative` parent that has the height), which contributes nothing to the measurement. The fill is `lg:`-only on both split pages — stacked at one column there is a second column of content below the fold and the page is *meant* to scroll, so the box stays bounded there. `--pane-h` (`100dvh` less `--toolbar-actual`, which is the `max()` the toolbar and the sidebar's brand strip already compute inline) is for the one case a flex parent cannot reach: a `sticky` inspector's own cap. And a `sticky bottom-0` bar is never pushed *past* where it sits in flow, so the pane's `pb-12` stayed underneath it as a band of nothing — the three pane footers pair `-mb-12` with it exactly as they already pair `-mx-4` with `px-4`.

- **A table must not be the reason the pane scrolls sideways.** A truncating line is `white-space: nowrap`, so its min-content width is the whole sentence — a `max-w-[56ch]` cap on it is therefore a *floor* under the column, and the runs list stayed 916px wide however narrow the window got, scrolling sideways into empty canvas beside cards that had stopped at the pane's own edge. `w-full max-w-0` on the cell is what makes it the column that gives: zero as its max content contribution, 100% as its preference, so the fixed columns keep their widths and this one takes what is left, which is what the ellipsis was for. The `56ch` stays as an upper bound on a wide window. The list view is deliberately not wrapped in `overflow-x-auto` — that would pin its sticky header to a box that never scrolls — so the column that gives is the whole of what keeps that decision affordable. Below the mobile breakpoint the same cell **releases** the cap with a `max-md:max-w-none`, and it has to: there is no column left to give to there, so a zero max-width is a zero-width block with the task hanging out of it.

- **`Table`'s `stack` is the narrow-window answer, and the label on each `Td` is the other half of it.** `TableWrap`'s sideways scroll is right where a row is a set of readings a reader compares; it is not a presentation of a *record*. At 390px a run's status and its spend are never on screen together, and the row tint `Tr` exists for — the thing that holds a label and a figure on one line as the eye crosses — does not exist on touch at all. So `stack` makes the whole grid one block per row below `md`, `THead` takes the column heads off the screen, the hairline moves from the cells to the row, and each `Td` carries the `label` that names its own field. **The two are one decision and neither works alone**: with the heads gone, a table switched on without labels is a column of unnamed figures, which is worse than the scroll it replaced — which is exactly why this is opt-in per table rather than a change to what `Table` does everywhere. Twenty-nine of the app's thirty-five carry it — count them with `grep -rn '<Table[ >]' src --include='*.tsx'`, which finds the kit's own six beside them and nothing else. The six that do not are still a list rather than a backlog, and only one of them is a table it was forgotten on: the settings page's **calibration suggestion table** (`Ceiling` / `Set now` / `Observed peak`, under *Where a ceiling can come from*), which was out of the scope this landed under. `RunAgentCost` was the other and now carries it — an agent's name is an operator's own string with a badge beside it, so the cell that names the record is the one that grows, and in that card's scrolling box it put a name on screen with its cost off it. The remaining four are two shapes that are **not** waiting for anybody. `/account`'s daily cost, `ContextControl`'s filter rows and `PruneSavings`'s pruning rows have **no `<thead>` at all**, so there is no column name for `THead` to take away and a label beside a figure is already two short columns that fit — stacking one would spend two lines naming what the left-hand column is already saying, and the label a `Td` would carry is the cell beside it word for word. `ContextOccupancy`'s two are inside `sr-only` divs and are never painted at any width, so there is no narrow layout for `stack` to fix and switching it on would only churn the roles the flat table already has. That first shape is what to check for before reaching for `stack`. A cell left deliberately without a label is the headline the record is identified by (a status, a task, a branch), never a figure; `labelPlacement="above"` is for a value that is prose or a list, which in the right half of a 390px row is a four-word column. **The explicit ARIA roles are not decoration.** `display: block` strips a table element's implicit role in every engine, and the row and column relationships go with the layout — so `Table`/`THead`/`TBody`/`Tr`/`Td` state theirs whenever `stack` is on, and above the breakpoint each is exactly the role the element already had. The value is wrapped in a `block md:contents` span so the flex row has one item to place: several cells hold two children, and `contents` is what makes that wrapper generate no box at all in the flat table. Only `display` may be switched on it — an inherited property stated there would reach the children *through* `contents` and change the desktop.

- **A capped scroll region is released below the breakpoint, not kept.** `ListView`'s `capped` box pairs `max-h-80` with `overflow-auto` so the sticky head has a box to stick inside. Below `md` there is no head — `THead` hid it — and the rows are blocks, so what is left is a 320px nested scroller inside a scrolling pane with nothing pinned to the top of it: a trap on touch, where the only way past a list is through it. `max-md:max-h-none max-md:overflow-visible`, and it lives in `ListView` because it was written out by hand five times: three copies carried it, one box is uncapped and one is not a scroll container at all. Only the last of those is a difference anybody recorded a reason for — the missing cap, and the one sticky head drawn without its hairline, are open questions the typed `box` preserves rather than answers, which is the difference between a variant and a copy that drifted.
