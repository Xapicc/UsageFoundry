# Polling, list DTOs, filters and Settings saves

[← conventions index](../conventions.md)

Read before editing a page's poll, a list route and its DTO in `src/lib/apiTypes.ts`, a control that filters what a page shows (such as `src/lib/logLine.ts`'s log filter), or `saveSettings` in `src/lib/settings.ts` and `src/app/settings/page.tsx`.

- **Pages are client components** that poll their API route (dashboard 120s, run detail 3s for the row while SSE carries the log). There is no server-side data fetching or React Server Component data layer. **A poll stands down when its subject can no longer move, and re-arming it is the half that has to be designed.** A terminal run cannot change on its own, so the run page's 3s interval is gated on the row being live — with three edges, of which two are relied on rather than hoped for: the first load sits *above* the gate, so opening a finished run still reads it; a run that finishes while the page is open flips the gate only *because* a poll said so, and the effect re-runs on that flip and loads once more before declining to re-arm, which is what catches a `finished_at`, a stop reason or a spend figure written between the two; and a run picked up from another tab arrives over SSE, which stays subscribed whatever the row says, so the first event after the poll has stood down re-runs the effect and the load it does sees the row running again. The runs list makes the same distinction between two clocks: a 1Hz tick runs only while something is actually counting down, and everything measuring an *age* — the restart notice's relative phrase — reads the instant the list was fetched, because those answers cannot change without the rows changing and were being recomputed for every row sixty times a minute. **The 24-hour bucket boundary is a third clock and the one to be careful with.** The poll buckets its rows against it and the older-runs fold asks the route for the settled runs from *before* it, so it must be one value read by both and never two readings of `Date.now()`: a few seconds between them leaves a run sitting on the boundary in neither list — which on that page is a run that has simply vanished — or in both, which is the duplication the bucket pass exists to prevent. It is advanced by the poll and **quantised to the minute** by `bucketBoundary`, and the fold's request is keyed on it, so the fold reloads when it steps rather than on every poll. Both halves of that are load-bearing: pinning it instead would drift, until a tab left open overnight files yesterday's runs under the last 24 hours, and leaving it at millisecond resolution makes every poll a second request for an answer that cannot have changed. The fold is otherwise **not** polled — a run that settled more than a day ago does not move on its own, and an operator picking one up comes back through the page's own reload.
- **A poll keeps one request of its own out at a time, so it re-arms on the answer rather than on a clock.** `startPoll` (`src/lib/poll.ts`) calls the load and sets the next timeout only once that load has settled, where `setInterval` over an async load fires whether or not the last answer arrived. `/runs/live` is the case: `/api/runs/live` prices pruning through a transcript scan, and the first scan in a process measured 14-18 s cold and 5.7-6.5 s warm against a 5 s poll (`docs/verification/context-control-pruning.md`), so the page sent further polls behind the first, their answers landed in whichever order the server finished them, and `setFigures` drew whichever came last — an older reading over a newer one, with nothing on the page to say so. The period becomes interval plus latency, which on a slow route is the point. Stopping holds across a load that is in flight, because the re-arm after it settles is skipped — the shape that clears only the pending timer keeps an unmounted page polling for the life of the tab, which `poll.test.ts` pins — and discarding that load's *answer* stays the page's own `alive`/`mounted` flag. Every poll in `src/app` and `src/components` goes through it, and a new one does too; the `setInterval`s left there (`grep -rn "setInterval(" src/app src/components`) are the one-second clocks that redraw an age or a countdown and the SSE routes' heartbeats, none of which waits on an answer. `startPoll` loads at once, which settles two shapes. A poll whose period moves with what it reads — the dashboard's working and idle, a chat thinking or not, `/branches`' merge queue active or not — re-runs its effect on the change, so the first read after the edge goes out then rather than a period later. And an unconditional poll is the page's first read: a mount effect loading beside it puts two requests out together, which is why chat and `/branches`' queue have none, while a poll that only runs in some state (the land card while resolving, a review in flight, a pending Codex sign-in) keeps its mount read and repeats it on the edge, one request. A read outside the poll — the re-read after a press — can still overlap the poll's own, and ordering those is the page's job: `/runs`, `/tasks`, chat, a workflow's page, `/branches`' queue and inventory and the land and review cards let only their newest request write — a ticket taken before the request and compared after the await — and a new one does too. Chat's poll reads the thread last opened rather than the one on screen, or a tick before the opened one lands would be the newest request and undo the click.
- **A page holds one `EventSource` whatever it shows, and a page that follows several runs follows them through one multiplexed stream.** This server speaks HTTP/1.1 — `next start` and the standalone `server.js` are both `http.createServer` — and a browser allows about six connections per origin over it, each SSE connection holding one for as long as the page is open. A page that opened `/api/runs/[id]/stream` per run would hold all six at six running runs and queue everything after, its own polls and every other request the tab makes included, so it reads as a hung page rather than a failing one. `/runs/live` is the case: `/api/runs/live/stream` carries every running run's events off the bus's `"*"` topic (`subscribeAll`) tagged with the run id, and announces runs joining and leaving, while the figures stay on a poll — the run page's split, readings on a poll and the log on SSE. Its frames carry no `id:`, the opposite of the per-run route: one `Last-Event-ID` cannot describe a stream whose mid-stream joins replay history out of id order, so a reconnect replays each run's last `LIVE_TAIL_EVENTS` and the page replaces its tails. A second surface that follows several runs reuses that route rather than opening streams of its own. HTTP/2 behind a TLS terminator would lift the ceiling, but nothing the image ships provides one, so nothing may assume it.

- **A list route ships the list's own DTO, and both readers of a list move together.** `GET /api/runs` shipped every row's whole prompt (75% of a 696 KB payload) for a column clipped to 56 characters, plus the normalised budget and the run's frozen agent, neither of which anything on that page draws — 37 KB over a hundred rows, measured. It now answers `RunListItemDTO` with the prompt clipped at `MAX_LIST_PROMPT`; the run's own page asks the route that has the rest, which is one row rather than a hundred. `GET /api/workflows` did the same with every node's full graph — 29,106 bytes of a 30,290-byte answer for two workflows, the node bodies being task prompts — so a list could print `nodes.length`, and now sends `WorkflowListItemDTO` with a block count, computing to 471 bytes. A **second shape beside the full DTO rather than a weakened one**: the detail route, the editor and the duplicate route all need the graph, and it exists in one place so five routes cannot disagree. And quick open reads both of those lists, so a field dropped from one has to be dropped from its reader in the same change — `jsonRequest` is an unchecked cast, so removing it silently typechecks and throws on the first press of the shortcut. **A list that pages carries the page's own figures beside the rows**, which is why `/api/runs` answers a `RunListDTO` rather than a bare array: `total` is counted over every matching row rather than over what was sent, so a page can say what it is a slice of, and `offset`/`limit` are the *applied* ones after the clamp rather than the asked-for ones. A count that is itself truncated cannot say a run has fallen out of reach, which is exactly how a hundred-row ceiling stayed invisible for the first ninety-nine runs. **And a list route reads `offset`, `limit` and its own filters off `searchParams` rather than answering with its newest page and letting the reader narrow that** — `/api/runs` read none at all and answered with the hundred newest runs, so the page's status segments filtered *those*, and "show me the failed runs" got the failed runs among the hundred newest: the same shape of answer as the question, and wrong, and indistinguishable from right. It now reads `offset`, `limit`, `status` — one status or a comma-separated set — `q`, `settledBefore`, `settledAfter` and `order` (`src/app/api/runs/route.ts:88-124`), which is the principle `/api/branches:19-23` already stated. The page's own two top bands broke the same rule after the fold had stopped breaking it: "In flight" and "Finished in the last 24 hours" were cut in the browser out of the unfiltered hundred newest rows, so behind a queue of more than a hundred the run actually spending — the *oldest* active row — was in neither band, Stop button and all, while the Fleet card still counted it. Each band is its own query now: `running,paused`, then `queued,waiting`, split where the bound changes because over all four statuses a capped page is the newest *queued* rows; and `settledAfter` the same boundary the fold sends as `settledBefore`, `>=` against `<` over one instant, so a run on it is in exactly one list. Each asks at the route's 200-row ceiling. What happens past the ceiling was decided band by band, because each of the three answers — an order, a pager, or declaring 200 the limit — fits one band and fails another. **The queue asks `order=queue`**, which is `queueCompare` in SQL (priority, then age, then `id`). Newest first, a queue past the cap showed the runs that start *last* and dropped the ones that start next, and a pager would only have moved those to the last page. In queue order the cap drops the tail, which moves into the band as the runs ahead of it start, so "In flight" keeps `Showing n of total.` under itself. **The recent band pages instead**, with Previous/Next beside it as the fold has, because no order fits 210 runs into 200 rows and each of them is equally an answer. Its offset rides the four-second poll, and an answer requested before the offset moved is dropped. **200 was not declared the limit**, because a workflow fleet settles past it in a day, and the rows past it are on no other part of the page: the fold's `settledBefore` excludes them by the same boundary that defines the band. Measured against `idx_runs_settled_at` at 50,000 runs, the queue page takes 0.50ms in queue order against 0.54ms newest first with 250 queued, and 1.04ms against 4.15ms with 5,000 queued. The recent band's second page takes 0.50ms. `listRunsPage`'s tests seed all three bands' cases. Three parts of that are load-bearing and each fails silently. The narrowing happens **in the query**, never in the client over an already-capped page. An **unknown filter value is refused rather than dropped**, and which way to fall depends on what the parameter decides: `/api/knowledge/notes` falls back on an unknown `sort` because a sort is presentation, while an unknown `status` is a 400 (`route.ts:91-103`), and so is a set with one unknown member, because it decides *which rows exist*, and quietly answering "every run" to "show me the failed ones" is the miss that reads as an absence. An unknown `order` is a 400 as well (`:105-114`), although an order looks like a `sort`: over a capped page it decides which rows are on it, and reading a typo as `newest` answers "what starts next" with the runs that start last. And every value arriving off a query string can be missing, blank, a word or negative, so the reading is **pure and tested** — `normalizeRunListQuery` and `clampRunOffset` (`src/lib/orchestrator.ts:1158, :1201`) for the reason `selectBranchCandidates` is: a limit read as zero is a one-row page, an unescaped `%` or `_` in a task prompt matches rows that hold neither, an epoch of 0 taken as a real boundary hides every settled run, and each wrong answer is a list that looks like an answer. An offset past the end is **clamped, not refused** — that is what pressing Next on a list which shrank under you produces.

- **A payload may carry a position into its own answer, and it is turned back into an id at the fetch boundary.** `GET /api/knowledge/graph` answered 9,864,990 bytes of which the edges were 9.39 MB, and eight of their ten fields were read by nothing — every use is `e.from` or `e.to`, and the canvas holds no edge reference at all. Links now travel as a pair of indices into the same answer's `nodes` (738,217 bytes, 92.5% off) and `expandGraph` resolves them to ids at the boundary the fetch lands on. **Ids past that point and never indices**, because every filter stage drops nodes and a stale index neither throws nor draws nothing: it draws a line between two notes that are not linked. The note view keeps the whole edge DTO, being a different route with different readers.

- **A control that narrows what is on screen narrows the *data*, never the way the data is drawn — and it says what it left out.** Three of these shipped together and they share one failure mode: a filter that hides a line is indistinguishable from a run that never wrote one. (1) **The log's filter takes the event's kind beside the rendered line** (`matchesLogFilter`, `src/lib/logLine.ts:690`), because `describeEvent` renders `tool_error` and `sandbox` as *system* rows — the tool voice is a chip and a muted line, which is what a call that **worked** looks like. Grouped on the rendered voice, "show me the tool calls" answers with every call except the ones that failed, and an operator reads that as nothing having failed: a filter's artefact presented as a fact about the run. `EVENT_GROUP` (`:654-673`) is a `Record` over the whole `RunEventDTO` kind union rather than a switch with a default, so a new kind is a compile error instead of an event that belongs to no group and vanishes from every narrowed view; `problem` is the one group keyed on the rendered **tone**, because a refusal, a tripped guard, a failed call and a parked status are four kinds and one question. (2) **The settings field search's corpus is the rendered page**, a walk over `[data-setting-name]` marks (`findFields`, `src/app/settings/page.tsx:195-222`), rebuilt on every keystroke *and* every edit because several descriptions interpolate the value beside them and some rows exist only while the switch above them is on. Not a declared index: that would duplicate sixty labels and their help text with nothing keeping the two in step, and a search naming a field the page no longer has is worse than no search — it sends the reader after a control that is not there and looks exactly like a search that works. (3) **Each of the three says what it narrowed and what it could not reach.** The header count becomes `n of m`, a capped result list states the count it dropped (`MAX_FIELD_HITS`, `:186`), and a filter over a *truncated* replay carries a warning hint naming the dropped-event count (`src/app/runs/[id]/page.tsx:1555-1560`, fed by the number the stream route now sends beside its sentence at `src/app/api/runs/[id]/stream/route.ts:141`) — because a filter that finds nothing in a knowingly incomplete log otherwise reads as proof of absence. And because a list is replaced **without anything moving focus**, each carries an `sr-only` `aria-live="polite"` count (`src/app/runs/page.tsx:1011-1015`, `src/app/runs/[id]/page.tsx:1597-1601`, `src/app/settings/page.tsx:2050-2054`); the runs history's says "searching" while a request is out, because a count that has not caught up yet reads as the answer.

- **A Save stores only what differs from `DEFAULTS`, and that is a correctness decision rather than a size one.** `getSettings()` is `{...DEFAULTS, ...stored}` and the settings page PUTs the whole *effective* object, so writing it verbatim materialised all thirty-three keys into the blob the first time anybody pressed the button — and from that moment every `DEFAULT_*` in `settings.ts` was dead for that install. There is no versioning, no migration, and nothing surfaces the divergence: a shipped default and a running install disagree silently and permanently. Measured, not reasoned. `8651bcd` raised `maxConcurrentRuns` from `null` to 4 at 20:28 on 2026-08-14 to bound exactly the failure that happened two minutes later — sixteen concurrent runs meeting the provider's 5-hour wall inside a 44-second span, every one of them with its first cycle amputated — and the stored row carried an explicit `"maxConcurrentRuns": null` that put itself back over the 4 on every read, so the fix was never in force on the install it was written for. The four prompt strings are the same trap one door over, which is why `COMPLETION_NOTICE`, `SHARED_CHECKOUT_NOTICE` and `RESTART_KILLED_NOTICE` are generated in `orchestrator.ts` instead of living in `Settings`. **The trade is real and it is the one being chosen:** a value an operator set *to today's default* is now indistinguishable from one they never set, so a later change to that default moves it — which is precisely what lets a shipped number reach an existing install, and the effective object is identical either way until that day comes. If pinning ever needs to be sayable, the answer is a stored marker, never a return to writing the whole blob. The comparison is structural rather than `!==` because five keys hold an object or an array and every one of them arrives off the wire as a fresh instance, and it is not `JSON.stringify` because that is key-order sensitive and a reordered `chatDefaultGuards` would read as an edit and be stored forever — the original failure arriving through its own fix. `src/lib/settings.test.ts` asserts on the stored blob rather than the round trip, because a test that only checks `getSettings()` after `saveSettings()` passes either way, which is why this survived as long as it did. Since model discovery, "the defaults" is `settingsDefaults()` — `DEFAULTS` with the catalogue replaced by the seed plus what discovery added — and the page sends `modelCatalogue` only when it was edited there, both for reasons `docs/agent/agents-and-templates/templates-and-model-catalogue.md` gives. **The `beforeunload` guard over that page is registered only while `dirty` and torn down the moment it is not** (`src/app/settings/page.tsx:1703-1711`): a listener that outlives the dirty state prompts on a page with nothing on it, which teaches the operator to dismiss the dialog without reading it — and the next one they dismiss is the real one. `preventDefault()` **and** `returnValue`, because either alone is a silent no-op in a browser somebody uses, and neither can choose the wording. It does not fire on a **client-side** navigation and nothing here can without the shell holding this page's state; the per-field rails and the bar's own unsaved count are what stand in for that, and the gap is stated in the code rather than left to be rediscovered.
