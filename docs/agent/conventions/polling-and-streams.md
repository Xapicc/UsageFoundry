# Polling and the page's event stream

[← conventions index](../conventions.md)

Read before editing a page's poll (`startPoll` in `src/lib/poll.ts`) or the `EventSource` a page holds. List routes and their DTOs, the controls that filter a page and Settings saves are in [polling-dtos-and-settings-save.md](polling-dtos-and-settings-save.md).

- **Pages are client components** that poll their API route (dashboard 120s, 60s while a run is working, with `WaitingOnYou` polling its own `/api/waiting` at that same cadence rather than riding the transcript scan; run detail 3s for the row while SSE carries the log; the shell's two polls — `ReadOnlyNotice` 60s and `UsageRemaining` 120s — run on every page and so each reads a route made for the purpose, never a page's own heartbeat). There is no server-side data fetching or React Server Component data layer. **A poll stands down when its subject can no longer move, and re-arming it is the half that has to be designed.** A terminal run cannot change on its own, so the run page's 3s interval is gated on the row being live — with three edges, of which two are relied on rather than hoped for: the first load sits *above* the gate, so opening a finished run still reads it; a run that finishes while the page is open flips the gate only *because* a poll said so, and the effect re-runs on that flip and loads once more before declining to re-arm, which is what catches a `finished_at`, a stop reason or a spend figure written between the two; and a run picked up from another tab arrives over SSE, which stays subscribed whatever the row says, so the first event after the poll has stood down re-runs the effect and the load it does sees the row running again. The runs list makes the same distinction between two clocks: a 1Hz tick runs only while something is actually counting down, and everything measuring an *age* — the restart notice's relative phrase — reads the instant the list was fetched, because those answers cannot change without the rows changing and were being recomputed for every row sixty times a minute. **The 24-hour bucket boundary is a third clock and the one to be careful with.** The poll buckets its rows against it and the older-runs fold asks the route for the settled runs from *before* it, so it must be one value read by both and never two readings of `Date.now()`: a few seconds between them leaves a run sitting on the boundary in neither list — which on that page is a run that has simply vanished — or in both, which is the duplication the bucket pass exists to prevent. It is advanced by the poll and **quantised to the minute** by `bucketBoundary`, and the fold's request is keyed on it, so the fold reloads when it steps rather than on every poll. Both halves of that are load-bearing: pinning it instead would drift, until a tab left open overnight files yesterday's runs under the last 24 hours, and leaving it at millisecond resolution makes every poll a second request for an answer that cannot have changed. The fold is otherwise **not** polled — a run that settled more than a day ago does not move on its own, and an operator picking one up comes back through the page's own reload.
- **A poll keeps one request of its own out at a time, so it re-arms on the answer rather than on a clock.** `startPoll` (`src/lib/poll.ts`) calls the load and sets the next timeout only once that load has settled, where `setInterval` over an async load fires whether or not the last answer arrived. `/runs/live` is the case: `/api/runs/live` used to price pruning through a transcript scan, and the first scan in a process measured 14-18 s cold and 5.7-6.5 s warm against a 5 s poll (`docs/verification/context-control-pruning.md`, a historical measurement; the scan went with the winnow removal, and any slow route reproduces the shape), so the page sent further polls behind the first, their answers landed in whichever order the server finished them, and `setFigures` drew whichever came last — an older reading over a newer one, with nothing on the page to say so. The period becomes interval plus latency, which on a slow route is the point. Stopping holds across a load that is in flight, because the re-arm after it settles is skipped — the shape that clears only the pending timer keeps an unmounted page polling for the life of the tab, which `poll.test.ts` pins — and discarding that load's *answer* stays the page's own `alive`/`mounted` flag. Every poll in `src/app` and `src/components` goes through it, and a new one does too; the `setInterval`s left there (`grep -rn "setInterval(" src/app src/components`) are the one-second clocks that redraw an age or a countdown and the SSE routes' heartbeats, none of which waits on an answer. `startPoll` loads at once, which settles two shapes. A poll whose period moves with what it reads — the dashboard's working and idle, a chat thinking or not, `/branches`' merge queue active or not — re-runs its effect on the change, so the first read after the edge goes out then rather than a period later. And an unconditional poll is the page's first read: a mount effect loading beside it puts two requests out together, which is why chat and `/branches`' queue have none, while a poll that only runs in some state (the land card while resolving, a review in flight, a pending Codex sign-in) keeps its mount read and repeats it on the edge, one request. A read outside the poll — the re-read after a press — can still overlap the poll's own, and ordering those is the page's job: `/runs`, `/tasks`, chat, a workflow's page, `/branches`' queue and inventory and the land and review cards let only their newest request write — a ticket taken before the request and compared after the await — and a new one does too. An action that draws its own answer moves the ticket as it draws it, or a read sent before the press lands after and puts back the state from before it; chat's `drawAnswer` is the one there is, and an action whose thread was left meanwhile drops all of its answer (`hasLeftThread`). Chat's poll reads the thread last opened rather than the one on screen, or a tick before the opened one lands would be the newest request and undo the click.
- **A page holds one `EventSource` whatever it shows, and a page that follows several runs follows them through one multiplexed stream.** This server speaks HTTP/1.1 — `next start` and the standalone `server.js` are both `http.createServer` — and a browser allows about six connections per origin over it, each SSE connection holding one for as long as the page is open. A page that opened `/api/runs/[id]/stream` per run would hold all six at six running runs and queue everything after, its own polls and every other request the tab makes included, so it reads as a hung page rather than a failing one. `/runs/live` is the case: `/api/runs/live/stream` carries every running run's events off the bus's `"*"` topic (`subscribeAll`) tagged with the run id, and announces runs joining and leaving, while the figures stay on a poll — the run page's split, readings on a poll and the log on SSE. Its frames carry no `id:`, the opposite of the per-run route: one `Last-Event-ID` cannot describe a stream whose mid-stream joins replay history out of id order, so a reconnect replays each run's last `LIVE_TAIL_EVENTS` and the page replaces its tails. A second surface that follows several runs reuses that route rather than opening streams of its own. HTTP/2 behind a TLS terminator would lift the ceiling, but nothing the image ships provides one, so nothing may assume it.
