# Route handlers, server modules and the schema

[← conventions index](../conventions.md)

Read before editing a route handler under `src/app/api/`, `src/lib/http.ts`, `src/lib/apiTypes.ts`, a `globalThis` singleton, `migrate()` in `src/lib/db.ts`, or `next.config.ts`.

- **Server-only vs client.** `src/lib/apiTypes.ts` holds the DTO mirror of the server types so client components never transitively import `node:fs`. `src/lib/format.ts` is likewise client-safe. Don't import `windows.ts`/`transcripts.ts` types into a `"use client"` file — add to `apiTypes.ts` instead.

- **Route handlers** that touch SQLite or the filesystem need `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`. Every existing data route has both.

- **A body a handler reads fields off goes through `readJsonObject` (`src/lib/http.ts`), not `(await req.json().catch(() => ({}))) as Record<string, unknown>`.** The `.catch` covers a body that does not parse and not one that parses to something other than an object: the literal body `null` resolves to `null`, the next property read throws, and the route answers — and `auditMutation` records — a 500 for the caller's mistake. The helper answers both with a 400 and a sentence naming what arrived. A body that does not parse is refused rather than read as `{}`, because `{}` is a real request on some routes: on `PATCH /api/tasks/[id]` it means "change nothing", and a garbled edit read as `{}` answered 200 as though it had landed. Every route that reads fields off its body uses it, with three kinds of exception. `POST /api/tasks`, `POST /api/tasks/[id]/comments`, `POST /api/agents`, `PUT /api/agents/[id]`, `POST /api/templates`, `PUT /api/templates/[id]`, `POST /api/workflows`, `PUT /api/workflows/[id]` and `PUT /api/workflows/[id]/schedule` keep the old line because the normaliser behind each reads `raw ?? {}` and refuses every non-object with a 400, so switching would only have changed the sentence. `/api/logout` keeps a tolerant read on purpose: no body is the ordinary sign-out, and its own test sends none, so any body that is not an object is read as asking for no options rather than refused, because `readJsonObject` would refuse the empty one too. `/api/login` answers a non-object with the 401 a wrong token gets, counted and delayed like one: the door is reachable without a credential and gives every caller without the token one answer, and a 400 there would be a second answer for a guesser to learn from. On the switched routes a body that does not parse is now refused too, which matters most where `{}` did something: `POST /api/runs/[id]/land` read it as `action: "land"`, and `POST /api/runs/[id]/reopen` as a reopen under a one-cycle default budget. `/api/mcp` answers the JSON-RPC way instead, off `isJsonObject`: a body that is no message — `null`, `5`, `[]` — is `-32600 Invalid Request` with a 400, where `null` used to throw and the rest read as notifications and got an empty 202, and a batch member that is not an object is answered in its own slot. **It checks the top level only**, so a field read off that body that has to be an object or a string goes through `optionalObjectField` or `optionalStringField` beside it rather than `(body.x ?? {}) as Record<…>` or `String(body.x ?? "")`. The first let `budget: 5` through to `normalizePolicy`, whose `in` test threw — a 500 one level down — on `POST /api/runs`, its reopen, `PUT /api/settings` and the template doors; the second admitted a billed run whose task was "[object Object]". Both answer a wrong type with a 400 naming the field, and absent or `null` as not given. `normalizePolicy` itself reads a non-object as `{}`, because it must stay total, which is why the refusal has to be at the door: a total normaliser alone would silently turn `"oops"` into the default policy.

- **Twenty-four routes answer through `jsonMaybeGzipped` (`grep -rl 'jsonMaybeGzipped(' src/app/api`), and the streaming ones are excluded by name** — buffering a live log to compress it is a stall, and `/api/runs/[id]/stream` and `/api/runs/live/stream` each say so in their own comment rather than being merely absent. The count is of routes, one file each, and every one answers a GET; `chat` and `stacks/[name]` each answer from two branches, which is why `grep -rn` over the same pattern finds two more lines than that. No `/api` response was compressed while HTML and JS from the same server were, and the cause is not obvious enough to rediscover: Next's `sendResponse` copies a route handler's headers through `appendHeader`, which stores every value as an array, so the raw response holds `content-type: ['application/json']` and `compression`'s filter asks `compressible()`, which returns false for anything that is not a string — every app-router handler in this version filtered out by a one-element array, reproduced against Next 15.5.23's own `sendResponse` and its own bundled `compression`. Four properties of the helper are decisions rather than defaults. The floor is 1400 bytes, one Ethernet segment: below it gzip buys no round trip while costing a threadpool hop and a `Vary` that splits a cache entry, and under ~250 bytes the answer comes back *larger* (measured: 169 → 178). It is async zlib and never `gzipSync`, because this process runs the fleet's guards on the same loop — `gzipSync` on the 8.8 MB graph body blocks it for 30.6 ms and fires zero timer callbacks while it does. `Vary` goes on **both** branches, since announcing it only when compressing is the version of the bug that survives testing. And the `Accept-Encoding` grammar is honoured rather than sniffed: `q=0` is a refusal, an explicit `gzip` outranks a `*`, and an absent header means the client never said and gets bytes it can certainly read. Measured on the running container: `/api/knowledge/graph` 8.8 MB → 488 KB, `/api/runs` 699 KB → 174 KB, `/api/branches` 255 KB → 76 KB, `/api/usage` 52 KB → 10 KB. A route that answers through it and needs a cache directive has to write one at the call site, because the helper knows nothing about caching and `jsonNoStore` is no longer in front of it.

- **Module state survives dev hot reload** via `globalThis` singletons: `__ufDb`, `__ufBus`, `__ufProcs`, `__ufInterrupts`, `__ufTranscriptCacheV2`. Those are examples rather than the roster — there are seventy-odd such keys and `grep -rn "globalThis as" src/` finds every one. New long-lived state must follow the same pattern or it silently resets on every request in dev. Take a **new** key whenever the shape at an old one changes rather than reusing it, which is what `__ufInterrupts` did to the former `__ufCancelled` (the comment on `orchestrator.ts`'s `interrupts` declaration) and what `__ufTranscriptCacheV2` did to `__ufTranscriptCache` when each cache entry gained a second array: `??=` only initialises when the key is absent, so a pre-upgrade value survives the reload and every call on it throws.

- **Schema changes** go in `migrate()` in `db.ts` as idempotent `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements, or as an `addColumn` that reads the live schema — there is no migration framework, and `PRAGMA user_version` is a record rather than one: nothing keys a step on it. **A destructive change is the exception and it is one transaction.** `db.exec` maps to `sqlite3_exec`, which runs each statement in autocommit, so `relaxProposalTemplate`'s four statements used to commit independently — and a kill after the first left every proposal in `chat_proposals_old`, which no query here reads. The next boot then recreated `chat_proposals` empty from the same `CREATE TABLE IF NOT EXISTS` and the rebuild's own guard (`template_id` is already nullable, return) made the loss permanent: the guard that makes a migration idempotent is what stops it noticing a half-applied one. So the rebuild runs inside `db.transaction`, `recoverStrandedProposals` completes a leftover from a build that predates that (`INSERT OR IGNORE`, so a boot interrupted between the INSERT and the DROP is a no-op rather than a primary-key failure, and the index is recreated because the rename took it and the drop took it away), and any other `*_old` table is named on stdout and left alone — a table this build cannot read is not one it may drop, and refusing to boot over it would strand the whole install rather than one table. `SCHEMA_VERSION` records what a live-schema read cannot: that a *rebuild* completed, and that the file was last written by a newer build, which is what a rollback after a failed deploy produces. It is stamped after `migrate()` returns, so it means finished rather than started. Keying the ~50 `addColumn` calls on it would be fifty numbers or an ordering nobody can change, which is why those still read the schema. **And `migrate()` is gated on the data-directory claim**: `open()` runs on the first `db()` call in *any* process, which is how a second server — an agent's `next dev` pointed at the live database by an inherited `DATA_DIR` — was entitled to rebuild a table under the server that owns it. `heldByAnotherProcess()` is the synchronous half of `serverLock.ts` that answers it, and it reads an undecided lock as free. The exception is a file with no `settings` table: a process that owns nothing and finds no schema has nothing to destroy, and refusing there would leave it with no tables and every query throwing.

- `better-sqlite3` is a native addon — it must stay in `serverExternalPackages` in `next.config.ts`, and the Dockerfile's `deps` stage carries the build toolchain for it.

- Comments in this codebase explain *why* a decision was made (usually a correctness or safety trade-off), not what the code does. Match that when editing.
