# The component kit, its spacing and interface defects

[← conventions index](../conventions.md)

Read before editing a component in `src/components/ui/` (`Field`, `Sheet`, `SegmentedControl`, `Icon`, `ListGroup`/`ListRow`), a caller's class on one, or when you fix an interface defect.

  - **`SegmentedControl` is how a short, fixed set of choices is offered, and `Icon` is the app's only glyph set.** The control is a radiogroup with a roving tabindex — one tab stop for the whole thing, arrows moving *and* selecting, focus following selection back so the next arrow press announces the right option. Both states carry a border and the same font weight, because a chip that gained either on selection would shift every segment beside it. `Icon` draws every glyph in a 16×16 box and sets the stroke attributes on the `<svg>`, so nothing can arrive a half-weight heavier than its neighbour; a glyph that is genuinely a filled shape cancels the stroke locally. Icons are decorative by default and only take a `title` where the glyph is the whole message — an icon announced beside the label it duplicates is noise. The set covers the eleven panes — the count the same closed vocabulary states in `docs/agent/conventions/design-language-and-grouping.md` — plus disclosure, status and appearance, and the shell's own two (`sidebar`, `search`); a new destination needs a glyph here before it needs a row in `panes.ts`.
  - **`Sheet` is a native `<dialog>`, and that is a correctness decision.** `showModal()` gives the top layer, the inert background, the focus trap and Esc-to-dismiss from the browser; a hand-rolled overlay would be a hand-rolled focus trap, which is the part that silently stops working the day someone adds a control to the footer. Three rules follow from using the element rather than imitating it: it is always rendered and never conditionally mounted, because mounting in the same commit that calls `showModal()` is a race; nothing sets `display` on it, because a `display` utility outranks the UA's `dialog:not([open]) { display: none }` and leaves a closed sheet lying across the page; and `cancel` is prevented so Esc goes through `onDismiss` and React's `open` stays the single source of truth. It takes **one** default action and Cancel, and a `danger` sheet opens with Cancel focused — `showModal` would otherwise land on the first focusable thing, and one Return on a destructive confirmation is not a confirmation.
  - **What a new component owes.** Five interaction states — rest, hover, active, focus-visible, disabled — with **no layout shift between them**, and a hit target of at least `--control-h`. Where two class strings could set the same property under the same variant, both go in the same `Record<Union, string>` entry: split across a shared string and a per-variant one, the winner is Tailwind's internal sort order rather than anything written down (this is why `Button`'s focus outline colour is per variant). Those states are guarded with `not-disabled:` rather than `enabled:`, and that is what lets `ButtonLink` — a button that is a destination, so ⌘-click and middle click still work — share `Button`'s one `VARIANT` map: `:enabled` matches form controls and nothing else, so on an `<a>` every hover and press state would emit and never match, which is a filled control that does not answer the pointer. Verify a variant spelling in the emitted CSS rather than assuming it; Tailwind emits nothing for one it does not know, silently. And the four states that are not interactions — empty, loading, error, stale — are designed, not left to a spinner: `Empty`, `Skeleton`/`SkeletonText`, `Notice`, `Field`'s `error`.
  - **`Field` is finished; do not fork it.** Label, `hint`, `error`, `unit`, `prefix`, `disabled` and the mode-picker-plus-value row (`LimitField`) are all props. A context carries `aria-describedby`, `aria-invalid` and `disabled` down to `Input`/`Select`/`Textarea`/`Switch`, so a hint written as a prop actually reaches the control — children are never cloned, because several Fields hold a fragment. That context is **exported**, and `ListRow` provides it rather than carrying a copy, which is what makes a control behave identically in a grouped row and in a Field. Everything the context supplies is a default the control's own prop overrides. Width is the one thing no control states: two width utilities on one element resolve by stylesheet order, not class order — so a caller that needs a narrow input puts the width on a wrapper, never on the control. **A call site that ignored that is worth naming, because it read as compliance:** `RunLand` passed `className="w-auto"` to a `Select` under a comment claiming `Select` never states a width, and `CONTROL` is literally `w-full`. Confirmed in the emitted stylesheet — `.w-auto` at byte 15178 against `.w-full` at 15197, same specificity — so the caller lost, the select filled the flex line and `flex-wrap` put *Land into …*, the most consequential button in the app, on a row of its own beneath a full-width dropdown. The width is on a wrapper now, with a `shrink-0` beside it so a line too narrow for both wraps the button rather than squeezing the choice it is pressed with. **That rule is not about width, and the density pass measured the general case**: Tailwind emits a numeric utility's values *ascending*, so on any element that concatenates a component's own class string with a caller's, the larger value wins whatever the caller wrote. `Field`'s root is `mb-3.5` and `CardTitle`'s is `mb-3`, and `.mb-0{` is at byte 10980 of the emitted sheet against `.mb-3{` at 11231 — so a `className="mb-0"` on either is a **no-op**: three `CardTitle` call sites relied on one and rendered 12px of margin while reading as though they did not, and each now cancels on a wrapper instead (`RepoSpendCard.tsx:98`, `UsagePeriods.tsx:148`, `app/page.tsx:973`, all three carrying a comment saying why). That is the move a caller who has to cancel a component's own spacing makes — a wrapper (`-mb-3`, `-mb-3.5` against a `Field`), the same one the width rule already asks for — verified in the emitted CSS rather than assumed.
  - **`Slider` and `ColorSwatch` are `Field`'s two newest members, and a slider always shows its figure.** Both take the same context every other control does, so `hint`, `error` and `disabled` reach them unchanged, and both carry the 44px floor below `md` (`max-md:min-h-11` on the range, `max-md:h-11 max-md:w-11` on the swatch). A range has no styling surface but its vendor pseudo-elements, so the track and thumb are reached through `[&::-webkit-slider-runnable-track]` and `[&::-moz-range-track]` — and **both spellings are always written out**, because an engine drops an entire rule block naming a selector it does not recognise, which is a slider that silently renders as the platform default in one browser and correctly in the other. The numeric readout beside the track is not optional and not a caller's choice: a control whose effect is immediate still leaves nobody able to say what they set, compare two settings, or get back to one. `ColorSwatch` is a native `<input type="color">` with the picker chrome stripped, because the alternative is an in-app colour picker, and this app has one colour decision in it.
  - **`ListGroup`/`ListRow` is the grouped inset list, and `Switch` is the control that usually sits in one.** Label left, control right, hairlines between rows, a rounded box, a footnote under it. The box deliberately does **not** clip its overflow: rows carry no background of their own, so a hairline never reaches a corner and nothing needs `overflow-hidden` — which matters, because a caller with a marker in the gutter (the settings page draws an edited rail there) would have it clipped away. A row is inert and has no hover tint: every interaction state belongs to the control inside it, and a row that lit up under the pointer would be claiming to be clickable across a width where only the 38px switch is. `Switch` *is* its track, so the focus halo hugs the pill rather than a padded box around it, and the hit target comes from an `::after` overlay stretched to `--control-h` — a target the pointer hits and the layout never sees. `Toggle` is the same switch with its label on the left, for a stack of Fields with no right edge to align against.

- **When you fix an interface defect, record its class.** One short paragraph on the list in `docs/interface-defects.md` — what was wrong, where, how it was found, and which of `proposals/UIChecks/01-what-only-a-rendered-page-decides.md`'s five classes it belongs to: **A** source text, **B** static markup, **C** a state machine (DOM and events, no layout), **D** layout (needs a real engine), **E** needs a person. The class is the cheapest instrument that could have *caught* it, not the one that happened to find it. This is a measurement rather than bookkeeping: `proposals/UIChecks/` recommends buying a browser-level harness, and its entire case is one class-D defect (`RunLand.tsx:623-636`) — so if the next three are class C, jsdom is the right answer instead and this list is what says so. It also records the hole: **class C is checked by nothing here**, deliberately, and a green `npm test` does not cover it.
