The twelve modules at the end of that list are the ones whose grounds are not obvious from the function's name, and each states them in its own file's docblock.
`budgetFromForm` is where every limit's off state is decided: `null` is the wire form of "off", so a number left in a box the operator switched off is a perfectly valid `BudgetPolicy` and starts an unattended agent under a cap nobody set, and the window pair reads 0–100 on the form against 0–1 on the wire, which makes a slip of a hundred a guard that never fires.
`modelFromForm`, in the same file, is where an *absent* key is the answer: `createRun` resolves a run's model as `input.model ?? settings.defaultModel`, so the form has to send nothing at all for the blank field to mean "whatever Settings says", and a form that posts the default it is only meant to be showing freezes that model onto `runs.model` where it stops following the setting it came from — a run that costs what last month's default cost, with the page, the types and the log all agreeing it was chosen deliberately. The trim is the second half: an argv entry of spaces is `--model "  "`, which is a spawn the CLI refuses, where a blank field is a run that starts.
A template's `model` is covered twice over, in `templates.test.ts` for the normalizer and the row read and in `chat.test.ts`/`workflows.test.ts` for the two functions that inherit it, and the two halves earn it differently. The normalizer's is the *absence* of a narrowing: every other value on a template is refused against a list, and this one must not be, because the list this build knows would refuse whatever ships next week — a template refused for naming a real model is a wrong answer nothing else on the page would explain. `rowToTemplate`'s is the same fact one build later: a row can outlive the build that wrote it, and degrading an unrecognised model the way an unrecognised permission mode is degraded would silently start every run from that template on something other than what the operator picked. `planProposal` and `planNode` are where the failure costs money rather than a refusal: a template that saved a model, named by a chat proposal or a workflow block, quietly running on `settings.defaultModel` instead is the right task at a different price, and nothing — not the run page, not the event log, not the cost rollups, which are correct about what was actually spent — would say the model was not the one asked for. Each of the three is asserted beside the guards that arrive by the same route, so a passing model assertion cannot be one read off the wrong record. `planProposal` then earned three more when the chat gained a model of its own, because the precedence is the thing that can be wrong: the proposal's model over the template's, the same over no template at all, and a blank one — `undefined` on a row written before the column, `""` or whitespace off a trimmed argument — reading as "named none" rather than as `--model ""`, which is a spawn the CLI refuses and a rung the fallback would never reach. Each was run against the implementation it exists to refuse: the first two fail on the template-only read they replaced, the third on a plain `??` chain.

`runFormProblems` is the same page's other half and the same silence: it is every reason the new-run form refuses to start, and a refusal that stops firing does not throw, does not fail a typecheck and leaves a page that looks right — it just starts the unattended agent the refusal held back. Two of them are load-bearing beyond their own sentence. The deleted-agent and the unusable-agent refusals both name the `agent` control and the page shows one problem per control via `.find`, so their push order decides which the operator reads; and `immediate` is what separates a range error, true the moment it is typed, from an emptiness error that has to wait for a blur, which is the difference between a form that argues under the caret and one that never says anything at all.
`authBootSignal` is whether anything at all is said about an install that serves every route to whoever can reach the port.
`config.ts`'s three each fail *as an ordinary state* rather than as an error — a fifth workspace slot compose never mounted looks exactly like a mounted directory with nothing in it, and the wrong GitHub token **works**, leaving a commit in somebody else's history as the only evidence.
`configCheck`'s two decide which configurations boot and which are refused, which is the one decision made before anything else can report.
`git.ts`'s are what every git call this app makes carries: a missing `-c` is a repository-controlled hook run by this server's own git child, with no permission mode and no line in `run_events`, and a variable that survives the scrub is that hook handed `DATA_DIR`.
`jsonNoStore` serves the one page with nothing but a poll to learn from, so a cached body is the last thing it ever sees — frozen at `thinking`, with the composer disabled; the same file reads source text for the wiring half, which only `otlp.test.ts` does beside it, because a header on the wire has no pure function behind it.
`readCappedBody` is the ceiling on the one *write* path `middleware.ts` exempts, and its two directions cost different things. A cap that stops firing is bit-for-bit the unbounded read it replaced, on a path reachable without passing the edge gate and buffered in the single process that holds every run — `loginLimiter`'s first half, with a restart at the end of it. A cap that fires *early* is quieter and is why the number is derived rather than picked: a batch exporter meets a refusal no retry can shrink past, that run's telemetry stops arriving, and the figure that reads zero is the mid-cycle half of a live spending guard which has no second source and cannot tell "spent nothing" from "heard nothing". The size cases run against a *streamed* body rather than a string, because a counter that reset per chunk passes every one-chunk test and fails on the wire.
`loginLimiter`'s two fail in opposite directions, one that never fires being bit-for-bit the unbounded route and one that never lets go locking the operator out of an app whose only other credential is an environment variable and a restart.
`plugins.ts`'s two decide what code every agent loads, and a bare `--plugin-dir` with no value takes the *next* argv entry as its path — which in `buildArgs` is a permission mode nobody chose.
`retention.ts`'s pure half decides what lands on disk and what is discarded from it, `releasableRuns`' grounds exactly.
`sessionToken`'s four are the whole of what keeps a captured cookie from being the master credential.
Three of them are not pure functions, and each earns the exception on its own terms.
`settleOnExit` spawns a real child, which is what the fault requires: an inherited pipe held open past the exit is the entire mechanism, and a stubbed emitter would only pin the wiring back to whatever it was written against.
`sendChatMessage`'s claim on a chat is the second, driven against a temporary database with `spawn` replaced by a counter — what it decides is not a value but whether a second billed child joins a conversation that already has one, and the only assertion that says so is the number of children.
`jsonRequest` is the third, and it is the one that makes the request: what it pins is that it *returns*, whatever happens, because an unguarded `fetch` rejecting out of a handler reports nothing at all — the chat page's flag disabling the composer, Approve, Reject and Select-all stayed set with no way back but a reload; the branches page's Land, Purge and Delete re-enabled their button and left the table exactly as it was, which is what a press that did nothing also looks like; and the land card's poll went on rendering a conflict resolution as in flight long after it had finished.
The status it carries is the other half — `null` is nobody answered and a number is somebody refused, which is the split between `pollFailureMessage` on a poll and `actionFailureMessage` beside a press that may or may not have landed.
`chatRequest` is a caller of it and keeps its own test, because the chat page reads a thread off the answer and that shape is its own.
Eleven are renderings rather than functions — every `*.test.tsx` in the tree, which is the whole of that class and is countable as `find src -name '*.test.tsx' | wc -l`.

`canvasView.test.ts` is the view above that layout, and it exists because the arithmetic became assertable: the transform, the hit test and the framing were private inside `KnowledgeGraphCanvas` until `canvasView.ts` was extracted, and a component's internals are not something this suite can reach.

`repoLock.test.ts` is a mutual exclusion tested for the failure that it excludes nothing, which is what every wrong promise-chained lock does: chain onto the wrong promise and two bodies run side by side, and the only symptom is two callers overlapping on a live install months later. `taskTransitionRefusal` is the taskboard's whole authority model, and it is asserted as a **matrix** rather than as a sample: four statuses against four statuses against four actor kinds is 64 cases, which is the entire behaviour of the function, so an edit that quietly *adds* an edge fails here rather than shipping. Sampling would have been the wrong shape for the same reason a spot-check of a permission table is — the case nobody wrote down is exactly the one that gets admitted. The two directions are not symmetrical and both are covered: an edge admitted that should not be is a task marked done by something that did not do it, and an edge refused that should not be is a backlog nobody can clear. Four cases beyond the matrix are the ones a matrix cannot state, because they are about identity rather than about the pair: a run completing a task **another** run holds, which is the failure the whole rule exists for — a work cycle that read the board, picked the wrong id out of a list and closed work nobody did, silently and with the board agreeing; a `claimed` row whose `claimed_by_run_id` is null completing for *nobody*, since two nulls comparing equal would let any run close any orphaned claim; a run that must claim before it may complete; and a claim that names no run at all, which is refused because nothing on this path expires a claim and one naming nobody could never be released. Each refusal is additionally asserted to be a *sentence* rather than a code, on `runFormProblems`' grounds — three doors will eventually show it, and a refusal nobody can act on is the same as no refusal.

The taskboard's **move effects** are the writes no pure function reaches, and they earn their database fixture where the parked sweeper's three writes earned theirs: each is silent in exactly the same way. The operator's own completion must record **no** run id, because a person is not a run and inventing one puts a run id on work no run did; a re-open must clear both run columns and `closed_at`, because a task that is open while naming the run that completed it is a row contradicting its own status on every surface that draws the board; a refused move must write **nothing**, including the title the same patch carried, since a partial write is the one outcome nothing anywhere would report; and deleting a parent must keep its children and clear only the link, which is `ON DELETE SET NULL` doing what the schema says — a test that would fail loudly if the `foreign_keys` pragma were ever turned off, which is a global setting no reader of `tasks.ts` would think to check. The folder validation is asserted through the **real** resolver against a real mount, and both of `security.md`'s containment checks are exercised by name: a lexical escape (`../outside`, and an absolute path outside the root) and a **symlink inside the mount pointing out of it**, which is the case the second check exists for and the one a lexical check alone admits.
