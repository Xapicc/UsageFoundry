# A run's life: origin, parking, refusals, prompts, endings

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/orchestrator.ts, fleet.ts, requestLog.ts,
> notify.ts.**

**A run records the gate it came through, and a pick-up is not that gate.** `runs.origin` is one of five — `form`, `chat`, `workflow`, `orchestrator-block`, `schedule` — written by `createRun` from a **required** field on `CreateRunInput`, and `origin_ref` is the record that authorised it (the proposal, the instance, the schedule, the block's node). Required rather than defaulted, and stated at the call site rather than carried on a plan object, because the whole point is that it is *recorded* rather than deduced: a default would be a deduction with a compiler behind it, and the two paths that share `planNode` — a press of Run and a schedule firing — differ in exactly this field. Provenance was previously a join across `chat_proposals`, `workflow_instance_runs` and `emitted_by` whose absence was ambiguous between the run form and a run picked up by hand, and which did not survive deleting the chat or workflow it came from; both columns are plain, `emitted_by`'s rule, so they keep reading true after that row has gone. Three of the five start an agent with nobody at the keyboard, which is what the column is for. **`reopenRun` deliberately does not write one of these values.** It creates nothing, so recording it in `origin` would lose the fact the column exists for while `created_at` went on pointing at the original creation, and a query grouped by origin over a time range would then be a lie about an audit column; it stamps `reopened_at` instead, with the request that asked for it on `request_log`. An orchestrator block's emitted runs are `orchestrator-block` even inside a *scheduled* instance, because what authorised each of those is a model's decision taken moments ago; a deferred plain node created hours later reads the instance's own copy, so a scheduled graph's late nodes stay the schedule's.

**Every mutating request leaves a line, and the line is a shape rather than a dump.** `auditMutation` wraps each mutating handler at its export — not inside the handler, because a handler has several return paths and the one that would be missed is a refusal, which is the line an audit most wants. It records the method, the URL's `pathname`, the status, the id the route named (from its own params, or from the `x-uf-subject` header a *creating* handler sets and the wrapper strips), which **credential class** was used, the first hop of `x-forwarded-for`, and the duration. What it must never carry is named rather than assumed: no request body (`POST /api/runs` carries every prompt and `POST /api/login` carries the master token), no query string (where a credential ends up when somebody puts one there by mistake), no cookie or `authorization` value — `actor` says *how* a caller authenticated and never with what. Two mutating routes are deliberately outside it and say so in their own comments: the OTLP ingest, whose callers are this app's own children delivering every few seconds per run, and `/api/workflows/validate`, a POST that writes nothing and is polled while somebody draws. A third exemption is narrower than a route and is about the *table* rather than about the caller. `/api/mcp` authenticates itself — `middleware.ts` exempts the path — so a credential-free POST reaches the handler having passed nothing, and while `auditMutation` wrapped that handler from outside, every such request wrote a row and every insert evicts past the 20,000-row cap: twenty thousand correctly-refused requests, and every line naming a run that was started, a setting that was changed or a sign-in that failed is gone. Only the handler that already holds a subject is wrapped now, so the case the table exists for — a real capability whose tool call was refused — still leaves a line; `DELETE` is not audited at all, being a 405 answered before any credential is read and mutating nothing; and the refusal leaves its trace on stdout instead, where nothing is capped, so somebody hammering the path is visible without being able to push anything out of it.

**There is one install-wide stop, one install-wide hold, and neither is a new way for a run to end.** Every stop was per run or per workflow instance, so halting twenty-five unattended runs was twenty-five requests through twenty-five pages and the only real alternative was stopping the container — which discards every in-flight cycle's spend accounting. `src/lib/fleet.ts` is the three missing controls and it *composes* them: `stopFleet` walks every `started` instance through `stopInstance` — the one door, which closes its orchestrator blocks before it signals anything, so a block left `thinking` cannot emit into a fleet being taken down — and then every run outside one through `stopRun` and `blockWaitingRun`, choosing between them with the very same `haltSteps` a workflow halt uses. `memberSteps` became that generic exported function for exactly this reason: a second copy of "which rows does this take down" is a second chance to rewrite a `completed` row as stopped, or to miss a member that then goes on spending. Waiting rows are blocked **before** any live run is signalled, `walkMembers`' ordering for `walkMembers`' reason, and the whole walk is synchronous. The cause is a third `HaltCause` kind rather than `operator` with different words, because once the sentence has scrolled off the stored cause is the only thing distinguishing a workflow somebody stopped from one that went down with everything else.

**The hold is a settings row of its own, and four separate call sites read it.** `settings.newWorkPaused` suppresses `promoteQueued` (through `selectPromotable`), `releaseDependents` (through `releasableRuns`, the release half only — a chain that can never start is still ended, because `blocked` costs nothing and holding it back would leave a dead chain nobody can end), `tickSchedules` (through `decideSchedule`'s own `paused`, so the cursor stays put and the windows that pass are recorded as missed rather than made up) and `emitBlockRuns` (at its door, beside the two refusals that are already facts about the machine rather than about the specs). It suppresses *starting*, never recording: a press of Run on a workflow still writes its graph out, the rows simply never leave the queue. Persisted rather than a process variable because the usual reason it gets set is the restart it has to survive, and deliberately **not** a key of `Settings` — the settings page sends the whole object on Save, so a field in that blob is one an unrelated edit from a stale tab would silently clear, which for a preference is a nuisance and for the fleet's kill switch is the failure it exists to prevent. Clearing it calls `releaseDependents` then `promoteQueued`, in that order and for `sweepPaused`'s reason; without that pair the queue would sit still until the next terminal transition, which on a fleet that has just been stopped is never. It is stated on the dashboard in words, because a held fleet and a quiet one are otherwise identical there. The bulk pick-up takes an **explicit list of the ids the page displayed**, `POST /api/chat/[id]/approve`'s rule and its reason, with one budget for all of them — **laid over each run's own stored blob rather than substituted for it**, because `reopenRun` writes `budget=?` wholesale, so handing it the sheet's two fields would rewrite every ceiling a run was started with to the two the sheet happens to expose and silently drop the rest: a time limit, a token limit, an enforcement mode chosen per run, gone on a press aimed at the cycle cap. Spreading the wire over the stored blob keeps an explicit answer explicit — a blank cycle cap arrives as `null` and means "no cycle limit" here exactly as it does anywhere else — while a field the sheet never asked about keeps the value that run was started with, and `permissionMode` is untouched by the merge because it rides on the stored blob, `normalizePolicy` drops it and `reopenRun` reads it back off the row. It is deliberately narrower than `reopenRun` accepts: `completed` is what a run that used up its cycle cap is written as *and* what a run that reported DONE is written as, so a fleet control that swept it in would restart everything that worked, and that decision keeps its own button on its own page.

**A control that acts on a set needs a per-run way to say no, and `runs.set_aside_at` is it.** There are two bulk pick-ups — the restart notice, over every `restart_closed` row, and the fleet's own, over every terminal run the page is displaying — and neither had anything an operator could say about one run in the set. So a run somebody had deliberately stopped was started again by a press aimed at the twenty-four beside it: an agent that accepts edits, back at work in a folder that was finished with, under limits nobody re-read, and nothing anywhere recording that it had been held back. The alternative was to stop pressing the button, which at twenty-five runs is worse than the one-page-at-a-time state the button replaced. `setRunAside` writes **only** that column — status, `stop_reason` and `restart_closed` are left exactly as the ending wrote them, which is what makes putting the run back an undo rather than a fifth way for a run to end, and it is why the two readers *filter* on the column instead of clearing anything. The three doors are deliberately not the same mechanism. `restartClosedRuns` filters the query, so the notice's count and the press that reads that list are the same answer and cannot disagree. `reopenFleet` checks the column **against the row**, at the moment of the write, because the ids it is given are a list the page rendered earlier and a run set aside since is exactly the stale case the check exists for — refused by name, never silently skipped. And `reopenRun` does not read it at all: it **clears** it, because picking one run up by name on its own page is the decision being taken back, and a mark that survived would go on excluding a run that had since been picked up and worked again. Setting aside a *live* run marks it **before** `stopRun` signals anything, `stopFleet`'s ordering for `stopFleet`'s reason: stopping first leaves the row terminal and unmarked for as long as the loop takes to notice, which is precisely the set a bulk pick-up sweeps, so the press meant to hold a run back could hand it to one instead. The route composes the two rather than `setRunAside` doing its own stopping, so a stop is still a stop with its own audit line.

**A run parks on two triggers, and only one of them needs configuring.** Our own guard is the first: `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume`, which needs both a per-run fraction *and* a numeric 5-hour ceiling — and ceilings default to `null` by design, so on a stock install that trigger never fires. The provider's own refusal is the second, and it needs neither — **including the enforcement mode**, which it used to need and must not again. That gate read `limited && policy.enforcement === "live-resume"`, and the default is `between-cycles` in all three places one is set, so the ordinary run met the shared account's wall and was written `failed`: terminal, with the only way back an HTTP request a person makes, and at twenty-five runs sharing one allowance that is the steady state rather than the exception. The two facts were never related — `enforcement` is the operator's answer to *when guards are read*, where a 5-hour window refilling on its own is a fact about the provider and the one quantity this app already reasons about as waitable — and nothing on that control said it was also deciding whether a wall is survivable. `refusalDisposition` is that decision now, pure and unit-tested, and it takes no enforcement argument at all: there is nothing left to gate on. What still bounds it is exactly what did before — `MAX_PAUSES_PER_RUN`, and the run's own wall clock, which `evaluateBudget` checks ahead of the window at the pre-cycle guard and `sweepPaused` checks again, ending a parked run on a verdict that can never clear rather than leaving it holding a folder. The run failed at that cap says it ran out of *waits* rather than out of allowance, because by then the allowance may well have refilled and the operator's next move differs. Claude Code reports API-level refusals as an assistant turn whose `message.model` is the literal `<synthetic>` (the marker `transcripts.ts` already keys on to keep an all-zero record out of the unpriced warning); `isUsageLimit()` decides whether that refusal is an exhausted allowance. Nothing parses a reset instant out of the message: the CLI renders a *formatted local time*, and the `usage limit reached|<epoch>` form every community wrapper keys on appears nowhere in the shipped binary. The refusal test sits **before** the exit-code test *and* before the `DONE` test — a refusal exits non-zero, so the exit code would file the provider's decision as the agent crashing, and a refusal that exits 0 would otherwise match nothing and re-spawn straight back into the wall.

**A refused run backs off; it does not trust the window boundary.** `refusalResumeAt` reads the end of the last block with real spend in it — not `session.endsAt`, because the refusal's own zero-token `<synthetic>` record opens a block of its own that reads as a window five hours out. Even that boundary is approximate in both directions: it runs late by the opening turn's latency, and early whenever the window was really opened by work this app cannot see — claude.ai, Desktop and Cowork spend the same allowance and write no local transcript. A boundary still in the future is waited for; one already passed falls through to a 20/40/60-minute backoff, floored so nothing re-spawns immediately and capped at six hours. `MAX_PAUSES_PER_RUN` bounds the whole thing, because unlike the guard path — where wall clock is checked ahead of the window and terminates the run — a refusal is someone else's claim about someone else's counter, and a misread one must not park forever.

**…and every run's answer is spread, because every input to it is shared.** All of the above is a statement about *one* run. The ladder is a module constant and the boundary comes from a `currentSnapshot()` whose file scan is coalesced across concurrent callers, so twenty-five runs refused inside the same minute read one block boundary and, with nothing randomised anywhere, computed **one** `resume_at` between them — measured, not reasoned. They woke in one sweep, spawned in one turn, met the same approximate boundary and re-parked together, three times, at which point the cap ended the fleet inside two hours with no operator input. `jitterMs` is the one design for that, shared with the transient ladder below: uniform over `[0, width]` where `width` is half the wait, floored and capped, and **never negative** — jitter may only delay, because both callers have a floor underneath them (`MIN_REFUSAL_WAIT_MS`, and the ladder's own rung) that a shortening spread would quietly undo. It is applied *after* `refusalResumeAt`'s floor and cap and clamped again, so neither moves; the band collapses only at `MAX_REFUSAL_WAIT_MS`, which a real 5-hour boundary cannot reach. The randomness is a **parameter** rather than a `Math.random` inside, which is what keeps the ladder, the floor and the cap pinned at the numbers they had — those cases pass `() => 0` and read exactly as before. The floor is `3 × SWEEP_MS` and it is the sweeper's property rather than the jitter's: a parked run wakes at the first sweep *after* its `resume_at`, so a band narrower than a tick is invisible. `MAX_RESUMES_PER_SWEEP` is the other half, and it is the half no spread can reach — a fleet parked before this existed, or bunched against the floor, or carrying a null `resume_at`, is due in one tick, and the sweep used to flip every one of them and hand the lot to a single `promoteQueued()`, which starts everything startable in one synchronous turn. Four per tick, and a run over the cap simply keeps its `paused` row and its already-past `resume_at`: nothing is written, so nothing is rewritten every 60 seconds, which is `FOLDER_TAKEN_REASON`'s rule one branch over. The cap belongs here and not in `promoteQueued`, which must stay the one owner of FIFO order, the folder claim and the concurrency cap — the last of which is `settings.maxConcurrentRuns`, **4** in `DEFAULTS` since `8651bcd` and nullable only as an explicit opt-out, so a stock install is bounded twice over and an install that has taken that opt-out is bounded here and nowhere else.

**A `<synthetic>` turn is not by itself a refusal — the cycle's own outcome decides.** When a stream drops after some blocks have been yielded, Claude Code finalises the partial response with an ordinary `end_turn` and carries the cycle on (`tengu_streaming_partial_finalized`, and the watchdog/stale-connection retries beside it). The `API Error: Connection closed mid-response` turn it leaves behind is then a warning *about a completed cycle*, followed by a clean `result` and exit 0 — but `apiError` latches on first sight, so the marker alone was ending runs whose work cycle had finished. `recovered` requires the CLI's own verdict (a `result` event, a success subtype, a zero exit) — never anything inferred from the text — and excludes an allowance refusal by name, because a wall that exits 0 must still stop the run rather than re-spawn into itself, which is the reason this whole test sits ahead of the exit-code test.

**A refusal has three answers, not two, and the third one is not a park.** A cycle can also die because the connection dropped mid-response or the upstream was briefly overloaded — `isTransientApiError`, matched on the five stream-truncation sentences read out of the shipped binary, on the statuses and `error.type` names the provider documents as retryable, and on the socket errors that never reach a status. That is neither the wall nor the agent failing, so the loop retries it in place: 5/20/60 seconds of backoff and another spawn into the same session. Retried rather than parked because `resume_at` exists to wait out a five-hour window and a run that parks yields its folder — for a fault measured in seconds, on a run whose session is intact. `MAX_TRANSIENT_RETRIES` is **consecutive**, reset by any cycle that gets through and held in `startRun`'s frame rather than on the row (a restart hours later is not "in a row"), so a long run meeting one blip an hour is never terminated by the total while a dead upstream ends the run in ~85s and names the attempt count. The retried cycle is refunded to `iterations` *and* to `cyclesThisSegment` — the first for the reason a parked cycle is, the second because that counter means "no cycle in this segment has completed yet", which is what lets `looksLikeResumeFailure` still recognise a retry that cannot resume the truncated session. The order of the tests is load-bearing: `isUsageLimit` first, because a wall can arrive as a 429 and no backoff refills an allowance. `refusalInStderr` deliberately does **not** consult this — an agent's own build output says "connection error" constantly, and a run must not re-spawn because its test suite could not reach a registry.

**…and a rate limit is a transient failure that is not the same transient failure, so it has its own ladder and its own ending.** `isRateLimited` is a **strict subset** of `isTransientApiError` — both patterns already match there — so it widens nothing about what is retried; all it decides is which ladder and which sentence, and `refusalKind` asks it after the wall and before the general blip, because the wider predicate matches every 429 too. The distinction is what the two faults *are*. A dropped socket clears in seconds whatever this app does, and 5/20/60 is generous for it. A 429 at twenty-five concurrent runs against one account is the provider describing this app's own steady-state request rate: it lasts as long as the fleet keeps asking, so the three fast retries became three twenty-five-wide waves into the condition that caused them and the fleet was `failed` inside ninety seconds, every dependent chain `blocked` behind it, with an 85-second tolerance against a limit the concurrency itself produced. `RATE_LIMIT_BACKOFF_MS` is minutes rather than seconds for that reason — 30 seconds, 2 minutes, 5 and 10, so four retries and five attempts in a row, about 17 minutes of tolerance at the floor of the jitter band and about 26 at its ceiling — and the wait is the back-pressure: a run that is sleeping is a run that is not asking. What that costs is paid in occupancy rather than in spend, and it is a deliberate trade rather than an oversight: the cycle is retried **in place**, so the run holds its folder, its worktree slot and one of `maxConcurrentRuns` for the whole ladder. Parking instead would yield the folder — which is the right answer for a five-hour window and the wrong one here, because the run queued behind it meets the same 429 and the session this run would have to resume is intact. It is bounded on the other side by the run's own wall clock, since a retry re-enters the loop at the top and `evaluateBudget` reads `maxDurationMinutes` before every re-spawn. It bounds the tolerance and does not promise the fleet survives, which is why the ending says so: `rate-limited` is a separate `RefusalCause` from `retries-spent`, because "the upstream is down" and "we were rate limited and gave up" call for opposite responses, and the sentence names `maxConcurrentRuns` — the N this whole failure is proportional to — rather than telling the operator to wait. `transientBackoffMs` is the schedule, pure and taking the attempt index and a randomness source, where it was `TRANSIENT_BACKOFF_MS[transientRetries]`: a constant lookup on a per-run counter that starts at 0 for every run, so twenty-five runs meeting one failure retried at exactly the same instants. It shares `jitterMs` with the refusal path above, additive and half a rung wide — half being what keeps the ladder *strictly* climbing, each rung's floor above the one below it at the top of its band — and passes no floor, because this wait is slept in-process rather than served by the 60-second sweeper, so any spread at all is real.

**A paused run is reconsidered, not trusted.** `resume_at` decides *when to look*; `evaluateBudget` decides *whether to run*. `sweepPaused` (60s, lazily started and stopped) re-evaluates from a fresh snapshot and re-queues through `promoteQueued` rather than calling `startRun` directly — that is what keeps FIFO order, folder reservation and the concurrency cap in one place. A verdict that can never clear ends the run instead of leaving it holding a folder — except the one verdict that is not about this run at all: `no_ceiling` reads as clear, through the same `RUN_ENFORCEABLE_CODES` the pre-cycle guard reads, because ending every parked run 60 seconds after the pre-cycle guard ended every running one is the same wrong answer twice. `pauseVerdictClears` is that one rule and it has two readers: the decision, and the occupancy read that feeds it — a verdict that clears without asking who is in the folder is the two-agents-in-one-working-tree collision arriving through the one door allowed to un-park a run. A cleared verdict is still not enough on its own: a run whose folder was taken while it waited stays `paused` and re-checks next tick, because the alternative is a `queued` row that a restart would close out.

**Reopening a finished run is an operator decision, not a resume.** `reopenRun` (`failed`/`stopped`/`completed`/`needs-review` — `REOPENABLE`) puts a terminal row back in the queue keeping its folder, checkout, branch, session id and spend, so `startRun` continues the same conversation. It takes a **budget**, because the usual reason a run needs picking up is that its own limits ended it, and re-queueing under the limits that stopped it just reproduces the stop; the three carried-forward guards (`iterations`, run spend, run tokens) are therefore checked at the door rather than left to the pre-cycle check, which would refuse seconds later with the row already flickering queued → stopped and nothing said about what to change. **A fourth check sits at that door and is not one of the three.** The terminus pair — no cycle cap *and* no time limit — is a fact about the budget rather than about this run, and it used to be refused only in `POST /api/runs/[id]/reopen`. That route is one of the two ways in; the other is `reopenFleet`, which calls this function directly with a budget composed by a sheet that has no time-limit field at all, so one press could queue twenty-five runs with no monotone terminus between them. The refusal now sits at the one door every caller passes and the route keeps its own copy, with the longer explanation a form can show. `evaluateBudget` does refuse the pair again as `no_terminus`, but only once the row has flickered queued → blocked with nothing said about what to change, which is exactly the seconds-later refusal the three above are here to avoid. `started_at` is **cleared**, and that is the one deliberate divergence from a pause: a parked run keeps its original start so wall clock stays a terminus it cannot wait out, while a run picked up by hand days later would otherwise be refused by its own time limit before it spawned. `permissionMode` is not accepted from the wire — the stored value carries forward, so reopening adds no second route to `--permission-mode`. An isolated run whose slot an active run has since taken is refused by name, because `allocateSlotPath` only avoids slots held by *active* rows and a terminal row is not one.

**A reopened run carries one message, resolved at the door and consumed at the spawn.** `reopenRun` writes the literal first-cycle prompt into `runs.follow_up`; `nextPrompt` prefers it over the continuation, and the loop clears the column the moment it hands it to a spawn — not after the cycle returns, because a run that parks or is killed from there on has already had it delivered and replaying it would say the same thing twice. Resolving to *text* rather than to a flag is what lets `completed` be reopenable at all: the substitution depends on the status the row is being picked up **from**, which a queued row no longer records. With no operator note, a run whose agent replied `DONE` gets `donePushbackPrompt` — the continuation prompt asks for `DONE` when the work is complete, so replying to a `DONE` with it is the same billed spin `continueAfterDone` already avoids — while `failed`/`stopped` get the continuation as before. **`completed` is not that reply**: it is also what a run that used up `maxIterations` is written as, and `maxIterations` defaults to 1, so keying the substitution on the status told the ordinary interrupted run that it had reported the task complete and then forbade it from starting new work. `runs.reported_done` records what the agent actually said, at the moment the cycle ends and the answer still exists — the stop reasons differ, but they are user-visible prose and not something to parse — and `reopenPrompt` is the one branch that reads it. Rows written before that column read as not-done, which is the cheaper error: a continuation into a finished session buys one billed cycle that says `DONE` again, where the pushback costs the work the run was reopened for. A note with no session to resume into is **appended** to the original task rather than sent alone: the run is starting over, and a reply-shaped note would read as the whole job. `nextPrompt` and `reopenPrompt` are pure and unit-tested for exactly these branches; every one of them is billed.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && !sawResult && finalText === ""`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind". It deliberately does **not** also require `pause_count > 0` — a session truncated mid-turn is truncated whether a guard parked the run or a crash ended it, and a run picked up by hand has `pause_count === 0`, so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for.

**The first cycle is told how the run ends, and it is told in generated text.** `reportedDone` matches `/^\s*DONE\s*$/m` against *every* cycle's final text, cycle 1 included, but the token was named only by `DEFAULT_CONTINUATION_PROMPT` — which `nextPrompt` returns on the `sessionId !== null` branch and nowhere else. So the terminus existed and the opening cycle had never been given it, which is not a subtle effect: measured over 251 runs, of those whose budget allowed a second cycle, the ones whose *task text* happened to carry the token ended in a single cycle 53% of the time and the ones without did so twice out of 120 — both a crash and an operator stop rather than a completion. `reported_done` was 69% in **both** groups, so the second cycle was not finding more work; it was the first turn permitted to say the job was over, and 92 of them cost $162 to say one word into a re-sent conversation. `COMPLETION_NOTICE` closes that, last in the `sessionId === null` join so it reads as a statement about the task above rather than a preamble to one the agent has not seen, and restating `continuationPrompt`'s bar almost verbatim on purpose — cycle 1 and cycle 2 disagreeing about what "finished" means is the whole defect. Its second sentence is load-bearing for `donePushbackPrompt`'s reason: an instruction an agent cannot satisfy produces churn rather than silence, so a run that is genuinely unfinished is told what to say instead. `endsOnDone` gates it on the two cases where the promise would be false — `maxIterations === 1`, where the cap ends the run either way and the only thing the sentence would change is `reported_done`, which is the sole input to `reopenPrompt`'s pushback branch; and `continueAfterDone`, where the run is set to carry on past a DONE and the pushback says so in as many words. **And it is generated here rather than added to `Settings`**, which is the half that makes it reach anything: see `saveSettings` in `conventions.md` — before that changed, one press of Save materialised every `DEFAULT_*` prompt into the stored blob and the constants were dead for that install forever. `continuedWorkNotice` already made this split for the same reason.

**There is a fourth ending, the agent asks for it, and it is the only rung of the ladder that is about the task rather than the machine.** `completed` was written both for a run that replied `DONE` and for one that merely used up `maxIterations`, which defaults to 1 — so on a stock install almost every finished run is the second kind, and a run that met a wall it could not pass had three futures and all three were wrong: spend the rest of its cycle cap restating the problem, because `COMPLETION_NOTICE` says stopping without `DONE` buys another cycle; reply `DONE` anyway and land in `completed`, which `STATUS_TONE` paints `ok`; or run out of cycles and land in `completed` too, indistinguishable on the list. `needs-review` is that missing ending. It is deliberately **not** `failed`, which is where the *machine* went wrong and which would file a judgement under `danger` beside dead containers and dropped sockets; not `stopped`, which is a person or a rule they configured deciding; and not `blocked`, which means refused before its first work cycle with nothing spent. `cycleEnding(finalText)` is the whole matcher, pure and tested, and what it pins is the **precedence**: a turn carrying both tokens is an agent contradicting itself and `needs-review` wins, because `completed` is green and never re-read while this one is warn-toned, reopenable and asks for somebody. The test sits below every refusal test *and* below the exit-code test — everything above it is a statement about the machine, and filing a 429 or a dropped socket as the agent's judgement would be a lie about who decided and would send an operator who came to read what the agent could not do to a rate limit. A cycle that names the sentinel and then exits non-zero is therefore `failed`, which is right rather than merely incidental: the exit code is the CLI's own verdict that the cycle did not complete. **The branch must assign `reportedDone = false` before it breaks**, and that is the trap: `reportedDone` is hydrated from the row rather than being a fresh local, so a branch that breaks out without touching it writes a stale `1` for a run picked up after an earlier `DONE` and then sends `donePushbackPrompt` into a run that never said it was finished. It writes `needs_review_reason` — the cycle's own final text, clipped at the write to `MAX_NEEDS_REVIEW_REASON` with a trailing `…`, because `RunDTO` is polled every three seconds and is the row shape the list ships for every row, and nothing is lost since the full text is in `run_events`. The column describes *the ending the row currently records*, `stop_reason`'s invariant, so `carried` initialises it null on every other ending and `reopenRun` clears it in the same UPDATE that clears `stop_reason`. And it puts a sentence in the log, `error_max_budget_usd`'s rule: a run that only changed status reads in the stream like a cycle that stopped for no stated reason.

**The sentinel is taught on every prompt but the operator's own, and it is not gated on `endsOnDone`.** `NEEDS_REVIEW_NOTICE` is generated beside `COMPLETION_NOTICE` for the same reason that one is — one press of Save materialises every `DEFAULT_*` prompt into the stored blob, so a sentence added to `Settings` would be dead on every install whose operator has ever pressed it — and it rides on the opening join, the continuation *and* the pushback, not on cycle 1 alone. `continuationPrompt` names `DONE` on every resumed turn, so an agent on cycle 5 re-told about one ending four times and about the other once, on a turn that has scrolled out of the conversation, has been told there is one ending. The one branch it is **not** appended to is `o.followUp`: `docs/runs.md` promises the operator's words are sent verbatim, a run whose operator wrote a note already has the person this ending exists to reach, and the contract returns on the very next cycle. Reusing `endsOnDone` is the obvious symmetry and is wrong: that flag withholds a promise that would be *false* — under `maxIterations === 1` the cap ends the run whatever the agent says, and under `continueAfterDone` a `DONE` is explicitly overridden — where reporting a wall always ends the run with the reason recorded. Since `maxIterations` defaults to 1, gating would withhold the new ending from precisely the one-cycle runs that are written green today. The cost is stated rather than absorbed: `continueAfterDone` is documented as "the run ends only when a limit is reached", and after this it can also end when the agent reports a wall — the better trade, since the alternative is one more billed cycle every time until the cap, but a change to a documented promise and `docs/runs.md` says so. The wording itself is the other half: an ending the agent controls is a cheap way out of a large task, so the sentence has to make reporting it *more* work than carrying on — it names what counts as a wall, refuses what does not, and asks for the three facts an operator needs. The collision hazard is real and bounded rather than closed: the matcher runs over generated text, so a run whose *task* is this feature can trip it. Three things reduce it — the sentinel is `NEEDS_REVIEW` where the stored value is `needs-review`, so a task quoting the *status* cannot fire it; it must be alone on its own line; and sub-agent text never becomes a cycle's `finalText` — and the remaining case is accepted, because the fix is a per-run nonce that would have to survive a `--resume` and would make nothing in this app's logs read the same twice. What it costs is one run ending early with its own text recorded, visible and reopenable in one click.

**A run that asked for a person is picked up by name, never in bulk, and is told what to check first.** `needs-review` joins `REOPENABLE`, or `reopenRun`'s gate answers *"this run is needs-review, so there is nothing here to pick up"*, which is the opposite of what the state is for. `reopenPrompt` then gets a branch of its own, and the reason it needs one is that doing nothing already *looks* right: the pushback tests `completed`, which this row is not, so the run would fall through to the plain continuation — *"Continue working on the task. If it is fully complete and verified, reply with exactly DONE"* — into a conversation whose last turn was the agent reporting a wall, which is the same defect `RESTART_KILLED_NOTICE` was added to fix on this same function. The ordinary reason an operator reopens one of these with no note is that they have cleared the wall, so `NEEDS_REVIEW_PICKUP_NOTICE` asks whether it is still there; it does not quote the reason back, because the branch requires a session and the agent's own words are already the last thing in that conversation. Its position — below `restartKilled`, above the pushback — is **inert today** and written that way on purpose: `restartKilled` is `failed && restart_closed`, so the two can never both be true, unlike the pushback below it which reads a *column* that survives the ending it described. It is for the next change rather than for this code. Neither bulk pick-up offers one, and only one of them needed a decision: `restartClosedRuns` has no status predicate at all and `restart_closed` can never be set on such a row, while `reopenFleet` takes the explicit ids the page displayed — so the exclusion lives in the client's own `REOPENABLE` set on the runs page, and `needs-review` is deliberately kept out of it for the argument that keeps `completed` out. A control that acts on twenty-five runs at once must not answer the one ending whose entire content is *a person is being asked to look at this*: pressing it would put an agent that accepts edits back to work, unattended, on a wall nobody has read about, with nothing recording that the question was skipped. That the run's own page still offers Resume is the same split `set_aside_at` already makes — picking a run up by name, on its own page, is a decision; picking up twenty-five is a press.

**A cycle the container killed is told so, above the branch that reads a stale column.** `reconcileOnBoot` writes `failed` with `restart_closed` set, `reopenPrompt` had three branches, and a restart-killed run with no operator note fell to the empty one — so `nextPrompt` sent `continuationPrompt`, *"Continue working on the task. If it is fully complete and verified, reply with exactly DONE"*, into a conversation whose last event was a child dying mid-tool-call. Twenty-four runs took that path, and the trees those kills leave are not hypothetical: one was cut down immediately after `git checkout -- src/lib/chat.ts` with the only copy of its fix in `/tmp`, another mid-mutation-test with a deliberately wrong variant of a source file on disk, a third with a tracked file moved aside and `tsconfig.json` rewritten by a dev server. Every one of them reconstructed the tree in its next cycle *despite* being asked whether it was finished. `restartKilled` is `status === "failed" && restart_closed !== 0`, which names exactly `reconcileOnBoot`'s in-progress branch and `shutdownRuns`' marked rows — the queued and paused-too-long branches both write `stopped`, and `markRestartClosed` only touches rows that were `running` — and it is read at the call site *before* the UPDATE that clears the column in the same statement. The branch sits **above** the pushback and that order is the decision: `reported_done` is whatever the previous cycle left on the row, and a cycle killed mid-tool-call never reached the code that changes it, so a run that said DONE two segments ago, was reopened, worked and was then killed would otherwise be told it had reported the task complete and forbidden from starting anything new. It requires a session for the same reason the pushback does.

**An isolated run is told what its worktree does not isolate.** `refs/stash` is a **common** ref rather than a per-worktree one, so every isolated run on a repository pops from one shared stack — reproduced on git 2.50.1: worktree A stashes, worktree B stashes, and A's `git stash pop` applies B's entry and drops it. Across 251 runs there are 123 `git stash pop` calls and **not one** names a `stash@{n}`; eight runs left assistant text saying they had popped a sibling's work. `isolationPreamble` actively invites the belief — it says the checkout is the agent's own — so `SHARED_CHECKOUT_NOTICE` travels beside it, generated for `COMPLETION_NOTICE`'s reason, and names the clean-tree case explicitly because that is the one that surprises: `git stash -u` with nothing to stash creates no entry, so the `pop` paired with it in the agent's plan takes whatever a sibling pushed. `/tmp` gets one clause and no mechanism — it is shared by every concurrent agent and 117 paths in that corpus were used by more than one run, but not one confirmed clobber was found, and a per-run `TMPDIR` is a change to every child's environment to close a path nothing has yet taken.

**A restart on top of existing work says so in the prompt.** `nextPrompt` takes `priorCycles` (read *before* the loop's increment) and, when it has to open with the task text on a run that has already been charged for cycles, prepends a notice naming the branch for an isolated run and the folder otherwise. Nothing else in that prompt refers to the earlier attempt — the conversation that held it is gone by definition — and an agent handed a bare task does the first thing it says, which is the work it is standing on. This is the floor under a restart, not a replacement for resuming: `DEFAULT_CONTINUATION_PROMPT` still restates nothing, because on a conversation that really is intact a restatement is spend for no information.

**`cancelled` is checked twice per cycle, and both matter.** Once before committing to a cycle (the top-of-loop check is separated from the spawn by a transcript scan that takes seconds, and `stopRun` has already promised no further cycle will start), and once after the child returns, *before* the exit-code test — a SIGTERM'd child closes with a null code that reads as `-1`, so testing the code first files every deliberate stop as `failed`. Likewise `runIteration` resolves on `exit` with a grace period, not on `close` alone: `close` waits for inherited pipes, and an agent that leaves a grandchild behind would otherwise hold its folder until the next restart.

**The UI says "work cycle", the code says "iteration".** User-facing copy names the unit a first-time user must reason about; `Settings`, `BudgetPolicy`, the API payloads, and the `runs` table keep `iteration`/`maxIterations`. Don't rename the internals to match the copy, and don't reintroduce "iteration" into the UI.

**Every budget rule can be switched off, but the loop must always have a monotone terminus.** `null` means "no limit" for cost, tokens, duration, and both fractions — `normalizePolicy` maps `null`/`""`/`0` to `null` rather than to a default, so a blank field disables a guard instead of quietly restoring one. `maxIterations` is nullable too, but only alongside `maxDurationMinutes`: those two are the only quantities that move one way and keep moving. This run's own spend stops accruing the moment a cycle is killed before it reports, and both window fractions can *fall*. The pair is enforced in `POST /api/runs` (which has an error channel) and refused again as `no_terminus` in `evaluateBudget`; `normalizePolicy` must stay total and idempotent, so it never rejects — and never coerces the illegal pair into a limit the user did not ask for. Only an explicit `null` asks for an uncapped loop; blank, zero, negative and missing all still mean one cycle.

**`continueAfterDone` sends the agent back in after `DONE`, with a different prompt.** It must be `settings.donePushbackPrompt`, never `continuationPrompt` — that one says "if it is fully complete, reply with exactly DONE", so feeding it back after a DONE produces an immediate second DONE and a tight, billed spin loop. The flag is read as `=== true`, not `Boolean(...)`: it makes a run refuse to stop, so a string `"false"` off the wire must fail safe.

**Two flags ride *every* cycle's argv, not the opening one, and `--resume` restores none of them.** `--plugin-dir` is the case `architecture.md` records, and it now carries two *generated* directories beside the plugins found in the mounts: the vault skill, and the read guard `readGuard.ts` writes when the operator has switched it on. There were three; `--autocompact` was the third and is gone, replaced by `contextPruning.ts` — see below. The **three-part** `--append-system-prompt` is the other — one flag carrying `SELF_HOSTING_NOTICE`, `DELEGATION_NOTICE` and the run's own frozen file price list, joined by filtering rather than by interpolation, because a second `--append-system-prompt` is a replacement and because an absent price list has to leave that string byte-identical to what it was before the column existed, trailing blank lines included, or every run created before it pays a cold prefix on its next cycle for a notice it never got. Each fails the same way — nothing throws, no run fails, and a later cycle simply behaves like one that was never given the thing. `buildArgs` rebuilds the argv per cycle, so the correct shape is the unconditional one, and `orchestrator.test.ts` asserts each survives a `resumeSessionId`.

**`--autocompact` is gone, and `contextPruning.ts` is what replaced it.** The flag was a ceiling rather than a guard — no `BudgetVerdict`, absent from `LIVE_ENFORCEABLE_CODES`, `RUN_ENFORCEABLE_CODES` and `evaluateBudget`'s check order — and it was the only reason any conversation here compacted at all. It no longer rides the argv. `buildArgs` emits nothing in its place and `orchestrator.test.ts` asserts the absence, because a reinstated flag fails nothing and looks like an ordinary cycle. It stays in `ARGV_ARITY` and `NON_CONTEXT_FLAGS`: those two say how to *read* an argv, and every cycle spawned before the change stored one carrying the flag, so dropping it there would make those rows report an unclassified flag and a stray `200000`.

**What the removal gave up is measured, and it is the strongest measurement in this repository.** The flag did not lower a threshold the CLI already had. This install's model resolves a window near 1M and the CLI **refuses** auto-compaction for such a model, so before it 604 container sessions — 246 of them past 167,000 tokens, one request reaching 752,172 — produced zero compactions. And it fired at `min(asked, window) − min(maxOutput, 20,000) − **13,000**`, so `--autocompact 200000` compacted at 167,000 rather than the 180,000 `effectiveWindow` alone suggests. Between the two arms of a natural experiment over 1,147 transcripts split at the commit that added it, turns past the cap cost **0.45× per turn and 0.50× per 1,000 output tokens**. That figure is now a cost of the swap rather than a reason for the flag, and `docs/verification.md` carries it under both headings so a later reading can tell a decision from a regression.

**The two mechanisms are not the same operation, which is the case for the swap.** Compaction replaced the conversation with a model-written summary: much smaller afterwards, and the detail is gone, so the agent re-derives what it had just worked out. A prune removes tool output and keeps the conversation, so it shrinks less and forgets less. It is also no longer true that nothing resets a prefix — a boundary prune does, at the one moment it is free.

**Never run both.** The CLI would summarise a conversation moments before this app ended the cycle to prune it: the prune would then be measuring what the summariser had already discarded, and the run pays for both.

**A prune happens at two moments and only one of them is free.** Editing a cached prefix invalidates everything after the cut, so with `D` removed and `S` the suffix as it stood before the cut, the edit pays `1.9·S − 2·D` once and earns `0.1·D` on every later turn — break-even after `19·(S/D) − 20` further turns. At the boundary between cycle N and cycle N+1 the `2·D` term is **refunded**, because `--resume` was going to rewrite that prefix regardless, so the boundary prune runs unconditionally whenever the feature is on and sits at the very end of the loop body, after every `break`. Moved above one of them it would prune a transcript nothing resumes. The early end *manufactures* a boundary, pays the invalidation in full, and is therefore gated: `ceilingPayback` against `CEILING_PAYBACK_HORIZON_TURNS`, over a dry run of **this** conversation. It used to be predicted from the run's own last receipt, and `null` — "this run has not cut yet" — resolved to act, so every run's first crossing was unconditional: a $1.80 cold rewrite decided by the absence of a reading.


**Two engines do the cutting, and which one is configured never labels a figure.** `contextPruningEngine` picks between `winnow treat` — "Edit in place" in the UI, which rewrites the transcript and keeps the session id, writing a `prune_receipts` row — and `winnow fork`, which writes a **new** transcript under a UUIDv5 and moves the run onto it, writing a `fork_attempts` row and never a receipt. Both `forkAndAdopt` call sites read `getSettings()` on the same turn they act, so the switch takes effect at the next boundary and no run carries a frozen copy; adoption, by contrast, is written to `runs.session_id` and is **not** undone by switching back, so a run's transcript lineage and the engine that would cut it next are independent facts. `pricedCuts` unions both tables deliberately and `PruneActivityDTO` deliberately does not carry `engine`: a figure covering only the engine currently configured would drop the other's work out of the total the moment the setting moved, so the engine reaches a screen only as a statement about *now*, never as a label beside money.

**Every boundary writes down how it ended, and that is what makes an empty section honest.** `prune_decisions` takes one row per terminus — `cut`, `nothing`, `declined`, `refused`, `unavailable`, `failed` — written beside the `log()` line at each branch rather than once at the end, so the durable row and the sentence in the operator's pane come from the same branch and cannot drift. It is **a count of events and never a cost source**: nothing in the netting reads it, an `outcome = 'cut'` row is not a receipt, and it is a table of its own precisely because a non-cut row landing in `prune_receipts` would silently corrupt `pricedCuts`, `contextOccupancy` and `countFor` alike. The six counts sum to `boundaries`, which is what lets `pruneStatement` build a checkable sentence; a clause dropped by a typo would otherwise render as a shorter sentence that still reads as complete. Before it, four of the five ways a boundary could end left no durable trace anywhere — `boundaryDeclines` is a `globalThis` map cleared when the run ends — so "declined at every boundary for forty cycles" and "pruning was never switched on" were the same blank a day later. **The ceiling's own declines were outside that claim for longer**, and that is the path almost every cut comes down: 55 of the 58 on this install, against 3 from the natural boundary. `checkContextCeilings` logged its refusal and `continue`d, so the same blank came back a day later on 95% of the traffic — and with it the denominator `PruneSavings.tsx` says the money is measured against, since a card that only sees the boundaries that cut cannot tell four-of-twelve from four-of-four. It records now, on the same branch as the line and paced by the same `CEILING_REMEASURE_GROWTH_TOKENS`, so the count follows the conversation rather than the ticker and a run climbing from 200k to 300k is written down the whole way up rather than latched by `earlyEndDeclined`, which tracks only whether the operator has been *told*. Three outcomes and not one, because the branch swallows three answers: a null from `ceilingCut` is `unavailable` — winnow absent or a subprocess that failed, which it collapses — a measurement that frees nothing is `nothing`, and only a figure past `CEILING_PAYBACK_HORIZON_TURNS` is `declined`, carrying that figure in `predicted_turns`. An install missing the engine must not read as one whose arithmetic refused. It rides the `run_events` horizon on `context_samples`' reasoning, and `retentionSweep.test.ts`'s deep-equal is what forces a newly-swept store to be named.

**`prunerState()` is shipped unconditionally, and `observePlan` is gated.** The readout that says whether the tool is there must not itself be gated on the tool being there — `winnowAvailable()` was consumed only by `orchestrator.ts`, so an image built with `WINNOW_REF=` empty rendered a byte-identical dashboard while every prune no-opped, reporting the failure once per cycle into a per-run log nothing aggregates. `pruningEnabled()` is now defined *over* `prunerState()` rather than beside it, so the guard that decides whether to spawn and the sentence that explains what happened cannot come apart. The probe is memoised behind a 60-second TTL on its own `globalThis` key, because it is now on two request paths rather than the run loop alone. And the feature check moved **above** the payback gate in `pruneAtBoundary`: below it, an install with pruning switched off still ran the gate, still incremented the decline counter and still wrote "the last prune here removed too little to pay for another one" into the pane every cycle — a considered decision the app had not made. `observePlan` carries its own copy of the same check, because `settleBoundary` reaches it on the off branch too, and read-only is not the same as permitted: the one thing an operator who turned the feature off has asked for is that winnow is not spawned against their conversation.
**The ceiling asks the engine that would do the cutting, and asking the other one silenced the feature for two days.** `ceilingCut` resolves `contextPruningEngine` to a measurement: `winnow plan --tier CB` under the fork engine, a `treat -rx <strictness>` **dry run** under the in-place one. Before it, the ceiling asked `planCut` whichever engine was configured — and `plan` runs SPEC §4's rules at tier CB, which is the fork engine's classifier and not the in-place pruner's twenty inherited strategies. On the two transcripts this install declined on 2026-08-28, CB stripped 9 of 183 and 13 of 172 tool results (2.2% and 7.1% of the file) where `treat -rx aggressive` strips every one of them and frees 49% and 53%. So the gate refused every crossing on a figure five to twenty times smaller than the cut it was refusing, `prune_receipts` stood empty from 2026-08-26, and the pane repeated "a cut would remove 8.0k tokens" every few minutes. `planCut`'s own docblock names this failure about `break_even_turns`; reading its `netBytes` instead was the same error under a different field name, so the pairing is structural now — there is no way to reach a measurement except through the function that resolves the engine. The dry run is the inherited CLI's **default**, `--execute` being the opt-in, and that matters here because this runs against a session a live Claude process is holding: `orchestrator_safe.refusal_for` would not catch a mutating argv, since it looks for a Claude *above itself* in the process tree and in this container the walk stops at `next-server`.

**A `treat` dry run is read in bytes and converted as a share, never through `BYTES_PER_TOKEN`.** Two traps, both silent. Its token column does not move — orchestrator-safe mode excludes `metadata-strip`, so the `usage` frames survive and winnow's exact count re-anchors on the same turn, printing "Saved 0 tokens (0.0%)" for a cut that halves the file; a parser taking the first number on that line prices every legacy cut at nothing. And the byte column is *transcript* bytes: session `02584a86` was 3.83 MB against an API context of 258.3k tokens — 14.8 bytes a token, four times `BYTES_PER_TOKEN` — because the file holds JSON envelopes, thinking blocks with signatures, and tool results the intake filter already dropped on the wire. Read at 3.6 that dry run's 1.79 MB came to 521k tokens "removed" from a 258k-token conversation, so `apiContextNow − D` floored at zero and every cut priced at 0 turns: prune always. `treatRemovedTokens` takes the share instead — this fraction of the file, so assume this fraction of the prompt — which cancels the units and makes `D ≤ apiContextNow` hold by construction. `planCut`'s figure is **not** converted that way and that is not an inconsistency: CB selects recent large results still standing in the prompt (`keep_last: 6`, `min_bytes: 2048`, an intervening-read test), and its overlap with what the intake filter already dropped is bounded and measured at 4.06%. What is still wrong with the share is named rather than absorbed: it is taken against the whole prompt, ~55k of which is a system prompt and tool list no prune reaches, so it over-claims by about a quarter and leans **permissive** — on `docs/verification.md`'s not-verified list, and `resumeControl` is the machinery that would settle it.

**`PAYBACK_HORIZON_TURNS` and `CEILING_PAYBACK_HORIZON_TURNS` are one policy in two arithmetics, and sharing a number got it wrong.** Both say *cutting half is clearly worth doing, and past that this app is betting on a run's remaining length it cannot price*. `paybackTurns` is `19·(S/D) − 20` over the suffix and half of it costs 18; `ceilingPayback` is `20·(C − D)/D` over the whole conversation and half of *it* costs 20. The ceiling read the 18, so an exactly-half cut priced at 20 was refused by two turns nobody decided on. Neither constant may be used at the other's call site, and what they keep in common is the *case*, not the number it comes out as.

**`paybackTurns` takes the suffix *before* the cut.** Passing `tokens_after` is off by exactly `D` — small when the cut is small and enormous when it is large — so it flatters precisely the marginal cuts the test exists to refuse. `predictedPayback` reads `tokens_before` and the docblock says why.

**The ceiling has its own watch map, not `liveGuards`.** That map is registered only when `enforcement` is not `between-cycles`, which is an opt-in about *budgets*; the flag this replaced rode every cycle of every run. `contextWatches` is registered unconditionally beside the spawn, on its own `globalThis` key, and `liveGuardTick` checks it before the budget scan. The check reads the transcript and parses backwards from its end to the first `usage` frame. It used to `stat` the file first and skip anything smaller than the ceiling's worth of bytes, which was sound one-sided while the measure was `contextTokens` — message content is a subset of the file. It stopped being sound when the measure became `apiContextTokens`: the prompt carries ~55,000 tokens of system prompt, tool list and project instructions that are in no transcript, so a file under the gate can be a cycle over the ceiling, and what that hides is a run that is never ended and never pruned. The gate is gone; `CYCLE_CONTEXT_CEILING_TOKENS` is 200,000 since 2026-08-25 — raised to 300,000 and lowered again on that same day, because at 300,000 the extra prompt carried on every turn at the cache-read rate read as cost with no return — and the constant carries why it moved off the 167,000 the removed flag fired at.

**A `prune` interrupt is the one kind that does not end the run**, and the loop's post-cycle checkpoint tests for it before `applyInterrupt` — which has no status meaning "carry on" and would file the run as `stopped`. It is ordered ahead of the exit-code and refusal tests for the general interrupt check's reason: the child was killed, so it closed with a null code and reported no `result`. The cycle it ended is **refunded**, because a compaction never cost a work cycle and a crossing that consumed one would quietly change what `maxIterations` buys — bounded by `MAX_EARLY_ENDS_PER_RUN`, or a run whose every cycle crossed the ceiling would loop forever, always ending, always refunded, never finishing. Past the cap the crossing still prunes and simply counts.

**The tick's reading is written down, and the one thing it is not gated on is pruning.** The ceiling's scan was the only answer this app had to *how full is this run's context*, and it was thrown away — `tokens < CYCLE_CONTEXT_CEILING_TOKENS` discards every reading below the ceiling, which is every reading a graph of occupancy is made of. `sampleContext` stores it on the way past, **before** that comparison; after it, the only runs on record would be the ones already over. The store is deliberately outside `pruningEnabled()`, which used to guard the whole of `checkContextCeilings`: the *watch* is registered unconditionally beside every spawn because the ceiling replaced a flag that rode every cycle of every run, so the reading belongs with the watch and only the acting-on-it belongs with the feature — sampling inside the gate leaves the indicator permanently blank on every install with pruning switched off, which is silent and install-dependent, and is what `contextSamples.test.ts` pins by name. It costs nothing extra where pruning is on, because one scan answers both. What lands in `context_samples` is `apiContextTokens` and the row says so: `basis` is `api`, or `transcript` when the reading fell back to the byte estimate for a conversation with no usable `usage` frame — those two are **different currencies** and a series that mixed them silently would draw a step where only the measure moved. The lag by one turn and the fallback are both left exactly as they are. Rows are deduplicated on the frame the number came from (`message.id`, or on `(basis, tokens)` where there is no frame to name), because the ticker is time-based and one tool call routinely outlasts several ticks — a row per tick makes the series mostly flat duplicates and understates the slope, which is the one thing a context meter is read for. `turn_index` counts distinct main-thread `message.id`s, so a turn the CLI wrote as several records is one turn, and `<synthetic>` and `isSidechain` frames are excluded exactly as the ceiling excludes them; `turns_exact` is 0 when the count is a **floor**, which the megabyte tail scan makes possible on a run's first sample, and a floor added to anything stays one. Bounded twice — `CONTEXT_SAMPLES_PER_RUN` on insert, oldest first, and `sweepRunEvents` on the event horizon, which is the right horizon because these are read only beside the log they explain. `contextOccupancy` puts the series on the run's existing three-second poll rather than an endpoint of its own, carrying `CYCLE_CONTEXT_CEILING_TOKENS` (a constant that has already moved twice) and **both** cut tables' rows as marks — `prune_receipts`, and the `written = 1` rows of `fork_attempts` converted through `forkCutFromRow` because a fork stores bytes and files no receipt, so a panel reading receipts alone drew an unmarked series and reported zero prunes beside a pruning section, out of the same response, that priced the cut; the arrays are the newest **tail** and the stored totals ride beside them, because a series thinned by a rule the reader cannot see misstates its own peaks.

**When the number last moved and when it was last looked at are two facts, and the panel needs both.** Deduplication is right and it is also what made the indicator unreadable: the series only gains a point when the run's **main thread** finishes another request, so a run whose agent spawned one sub-agent at 18:15:59 on this install gained no sample for **22 minutes** — every frame written in that stretch was `isSidechain`, which this measure excludes exactly as the ceiling does — while the tick read the transcript twenty-two times and got the right answer every time. The panel had only the newest row's timestamp and rendered "read 22m ago", which is what an operator reads as a poll that has died; the figure was current throughout, because a parent's context genuinely does not grow while a sub-agent works. So `sampleContext` writes down **every** read — before the two early returns, since those are the ordinary case rather than the exception — and `lastCheck` carries it on the DTO beside the series. The store is a `Map` on `globalThis` and not a row on purpose: it describes the process doing the reading, so a server restarted mid-run has read nothing however recently the run it inherited was read by the server before it, and a row would let it claim otherwise across exactly the restart somebody is most likely to be watching. `unreadable` reaches the wire as itself and is rendered in place of the age rather than beside it — a read that found nothing reported as a fresh reading is the one wording that leaves the panel worse than absent — and a hold is named only past `HOLD_NOTICE_MS`, which sits above the read's own ceiling so that a gap small enough to be one tick says nothing.

**The read's cadence came off the budget's.** Both halves rode `liveGuardIntervalSeconds`, which is a setting about *money* — its description on the settings page is about re-reading usage mid-cycle, it has no upper bound, and an operator on an install where nothing stops mid-cycle is entitled to put it at ten minutes. Doing so took the context indicator with it silently, and the panel is the only answer this app has to *how full is this run*. `liveTickPlan` splits the two: the ticker fires at `min(interval, CONTEXT_READ_MAX_INTERVAL_MS)` so the reading is never more than two minutes old, and `guardScanDue` holds the budget half — `buildSnapshot`, which is uncoalesced and is the expensive one — to the operator's own interval across the ticks it sits out. The slack in `guardScanDue` is half a tick and is load-bearing: `setInterval` drifts, and refusing a tick that lands a few milliseconds early pushes the budget scan a whole tick past the cadence that was set, compounding every time it happens. On the default 60 seconds the two collapse back into one tick and the split costs nothing. One consequence is deliberate rather than incidental: on an install with the interval set high, the **ceiling** is now also evaluated every two minutes rather than every ten, so a cycle over it is ended that much sooner. It was never right that how promptly a cycle got pruned rode a setting about re-reading spend; that was a coincidence of the two sharing a timer. Its own `globalThis` key rather than a field on `timers`, per the shape rule: `??=` does not re-initialise an object a dev hot reload is already holding.

**Tokens, never bytes, and the number is computed here rather than read from the tool.** Measured against a real 2.0 MB transcript on this install, winnow reported `Saved 0 tokens (0.0%)` for a prune that removed **28% of the API-visible context** — its token figure comes from the transcript's historical `usage` frames, which record what was billed and cannot change when content is edited. And it freed 970 KB of file while removing 290 KB of what is actually sent, a 3.4× overstatement, because its largest strategy removes `toolUseResult`, an envelope field the CLI writes and never transmits. `contextTokens` counts `message` alone, before and after, and that difference is the only figure anything reports. What that difference still overcounts is winnow's **intake filter**, which rewrites the request and never the transcript: a result already replaced with a pointer on the wire is still here in full, so a prune removing it counts tokens the API never held. Measured 2026-08-24 across this install's ten largest transcripts, **4.06% of removed tokens corpus-weighted** (3.07% unweighted, range 0.00%–9.92%), and an upper bound because the reconstruction ignores `keep_newest`. It is **not corrected** and the reason is that the correction does not exist yet: telling those blocks apart needs a `tool_use_id` on each ledger line and winnow writes none, so the alternative is reimplementing its rule set here against a Python module in another repository — still an approximation, since `keep_newest` turns on per-request state no transcript records. The consequence is a rule on the dashboard rather than in the arithmetic: the prune figure and `intakeFilter.ts`'s are added under one title and the card **prints the overstatement** — one place, `ContextControlAside`, where the 4.06% is named beside the sum and each span carries the filter's share of itself. Nowhere else adds them, and no meter ever does. `contextTokens`' own docblock carries the number, and so does `docs/verification.md`.

**`gentle` is not offered.** Winnow ships three prescriptions; measured here `gentle` freed 0 bytes on that same transcript, and structurally so — its one strategy that fires on an ordinary session is `metadata-strip`, which orchestrator-safe mode excludes **by name** because it deletes the `usage`, `costUSD` and `duration` fields every window, every budget guard and `runs.spent_usd` are computed from. Offering it would be a control that reads as on and provably does nothing.

**Pruning and `startsFresh` are independent switches, and the one place they touch is a correction.** `freshStartContextTokens` reads `lastContextTokens` — the last cycle's *billed* resident window, from `usage` frames recorded before the boundary prune ran. So with both on, a prune that took a 200k conversation to 124k would be followed straight away by a fresh start fired on the stale 200k, and the run would pay to re-derive a conversation something had just shrunk to fit under the very threshold being tested. That is `IterationResult.contextTokens`' own **"Last, not largest"** warning arriving from a direction that did not exist when it was written. `contextAfterPrune` applies the prune's own ratio to the billed figure — scaled rather than replaced, because the two are different measurements and substituting an estimate would put a different basis into a threshold the operator set against the first, where the ratio is basis-independent. Neither feature requires the other and neither reads the other's setting.

**The tick reads what the window is *made of* as well as how full it is, and the two are not one measurement.** `contextComposition` spawns `winnow context --depth 3 --json` beside `sampleContext` on the same tick, and stores one row per provenance in `context_compositions` — tool traffic, prefix, retained reasoning, standing configuration, conversation, and the residual winnow calls `unattributed`. It exists because every other figure on this path is a *size*: how full the window is, how much a cut would take out, what the cut would cost. None of them says what the window is growing **on**, so an operator watching a run climb to the ceiling could see the climb and had no way to tell whether it was tool output a prune would take, a prefix a prune cannot touch, or retained reasoning that is neither — three cases with three different remedies behind one line. Five things about it are decisions rather than tuning. It is **gated on `pruningEnabled()`**, on `observePlan`'s rule and for its reason rather than by analogy: read-only is not the same as permitted, and an operator who switched the feature off has asked that winnow is not spawned against their conversation — where `sampleContext` beside it stays ungated because it spawns nothing. It is read **above** the ceiling comparison rather than below it, because "what is this growing on" is worth answering at 60,000 tokens and not only at the 200,000 where the app starts acting; below the `continue` it would exist only for conversations already past the point where anything cheap can be done. Its pacing is its own constant, `COMPOSITION_REMEASURE_GROWTH_TOKENS` at 40,000 against the ceiling's 25,000, on its own map — `ceilingMeasuredAt` paces a *decision* where being late costs money on every turn between, this paces a *picture* where being late costs a point on a graph, and one mark for both would tie the picture's cadence to a policy constant that moves for reasons of its own. And that distance is **absolute** where the ceiling's is one-sided: a prune drops the conversation by tens of thousands of tokens, so a one-sided test would leave the whole post-cut shape unread until the run had grown back — the one moment the composition is worth having. The mark is set *before* the await, not after, because the subprocess is bounded at `PRUNE_TIMEOUT_MS` and two minutes of ticks would each find an unmarked run and spawn their own winnow at the same transcript. And the **depth is 3 while the chart is still depth 1**, which is the fifth: the stacked area draws one band per top-level provenance and nothing under it, from exactly the rows it drew from when the reading itself stopped at depth 1, but the two levels below — the tool or attachment class, then the artefact, a file path with its repeat count, a Bash command head, an MCP tool, one sub-agent's return — are read and stored for a detail view. They are stored on **different terms**, and the difference is the whole bound. The series stays one row per provenance per reading, because `CONTEXT_COMPOSITIONS_PER_RUN` counts *readings* and that argument only holds while a reading is a handful of rows. The tree goes to `context_composition_children`, for the **newest reading of a run only, replaced whole on each reading**, in the same transaction that writes the bands. That is what bounds the store by runs instead of by readings × paths: nothing on this path caps how many distinct files a run may touch, so a tree per reading is unbounded in the one dimension with no ceiling anywhere. The trade is stated rather than hidden — the tree answers "what is in this window **now**", which the newest reading is, and cannot answer what was in the third of forty. Within a reading, `COMPOSITION_CHILDREN_PER_NODE` caps a node's children at 64, largest first, and the tail is **dropped rather than pooled**: a subtree short of its parent is visible, where an "other" bin is a node indistinguishable from `unattributed`, whose whole job is to say what nothing accounted for. `parseComposition` lifts winnow's `×N` off an artefact label into its own field, because `decorate()` welds the two together and a view keyed on the composed string treats one file read three times and the same file read four as two different files; null there is "winnow attached no count", never "once". Measured 2026-09-04 against the pinned ref, a depth-3 `--json` body on this install's four largest transcripts — 7.2 MB to 12.9 MB of JSONL — came back at 18 KB to 29 KB with 72 to 110 sub-nodes and at most 29 under any one parent, so the 4 MB stdout bound `contextComposition` was written with keeps two orders of headroom and the per-node cap does not fire on anything here.

**Winnow's window and this app's are the same measure from different anchors, and nothing may subtract one from the other.** Both are `input + cache_creation + cache_read` on a priced request. `apiContextSample` anchors on the last **main-thread** `usage` frame, sidechains excluded exactly as the ceiling excludes them, because a sub-agent's turns are not this conversation's context; winnow anchors on the last priced request in the file whatever wrote it, and a sub-agent's frames are written to that same file. So the two agree on an idle conversation and come apart for exactly as long as a sub-agent runs — 22 minutes at a stretch on this install, the same stretch `noteContextCheck` exists for. `recordComposition` therefore stores **winnow's own** window on the row and the stack is drawn against it. Scaling the slices onto the sample's figure would make the two agree by construction and would be a lie in the one case it mattered: the bands would then apportion a total they were never measured against. The component no longer says which reading is which: that sentence was removed from the page at the operator's request, so the separation is stated here and in `CompositionStack`'s own header comment and nowhere the operator will read it. Nothing on the page now warns against the subtraction. A reading is written whole or not at all — one transaction, a row per band — because a half-written one is the stacked area's single unrecoverable state: the bands sum to less than the window and the gap reads as unattributed context rather than as a missing row. The cap is counted in **readings** and not rows for the same reason, and `parseComposition` drops a node it cannot read rather than zeroing it, since zero is a measurement and a short sum is visible where a false band is not.

**Every failure on this path is a log line and nothing else.** A missing tool, an unreadable transcript, a non-zero winnow — none of them is a reason to end a run that is otherwise fine. The one thing that must not happen quietly is nothing at all: this is what bounds a cycle now, so a prune that could not run says so in the pane the operator is watching.

**When a compaction happens the run says what it took, and it says it from the vendor's table rather than from anything measured here.** The loop reads the transcript for `compact_boundary` records after every cycle — `readCompactions`, bounded by session id **and** by the cycle's own clock, because a resumed session copies earlier records forward carrying their original timestamps and a reader bounded by id alone re-reports every earlier compaction at the end of every later cycle. It sits after `runIteration` has returned and after the row UPDATE: the child has exited so the transcript is flushed, an interrupted cycle still reports, and `interrupts` is read afterwards so an interrupt landing during the read is not lost. Its own failure is caught and logged rather than allowed to end a cycle that has already been paid for. What the notice says about *survival* is `injectionFates`, and it is derived from the cycle's own argv rather than from a list of what this app injects — a cycle spawned without plugins reports no skills, one spawned with three plugin directories reports three, and a flag this function has never been taught reports itself `unclassified` rather than dropping out, which `orchestrator.test.ts` pins by running the widest real `buildArgs` output through it and asserting zero such rows. So the next flag added to `buildArgs` fails a test instead of silently leaving the record short. The table itself is Anthropic's documentation self-pinned to CLI `2.1.198` and this install pins `2.1.226`, so `compactionNotice` compares the boundary record's own `version` against `SURVIVAL_TABLE_CLI_VERSION` and words every line as a hypothesis whenever they differ — which is today always. That is a mechanism rather than copy discipline, on purpose: a note that reads as measured behaviour of this install is the one way this feature can lie. **It observes and never acts.** No `--autocompact` change, no `DISABLE_AUTO_COMPACT`, no threshold and no `context_management` block: those are the options `proposals/ContextControl/17-recommendation.md` rejects by name, and none of them is in scope for a record of what already happened. Nor does anything here read, summarise or judge the conversation — the boundary record and the argv are the whole of its input.

**A run is told to delegate, and the instruction has a floor in it.** `DELEGATION_NOTICE` travels with `SELF_HOSTING_NOTICE`, `RENDERING_NOTICE` and the file price list under one `--append-system-prompt`, because a second one is a replacement rather than an addition — the same trap `--allowedTools` carries — and with four notices on that flag the one that would go missing is whichever the last edit did not think about, one of them being the process-safety one. It is worth its own tokens on figures that are **re-measured** rather than carried forward: over 1,194 transcripts and 49,038 deduped assistant turns across 12.3 days, priced through `pricing.ts` and split on the transcripts' own `isSidechain`, a tool call inside a sub-agent costs **5.0 cents against 13.6** on a run's own main thread, most of the gap being cache re-read at 3.0 against 8.2, and the same call costs 8.4 cents over turns 11-25, 15.7 over 101-200 and 20.4 past turn 200. The previous reading over 1,011 transcripts was 6.5 against 13.9 with 2.7 against 8.3 — the same claim, with the sub-agent side if anything cheaper. **One weakness in it is stated rather than absorbed:** sub-agents are handed the self-contained errands precisely because those are the ones worth delegating, so an unknown share of the 5.0-against-13.6 gap is the task rather than the context. What is not confounded is the within-thread gradient — 8.4 to 20.4 across turn position on the same threads doing the same kind of work — and that gradient alone is the reason to delegate. The floor is in the text rather than left to the agent: a sub-agent's opening turn averages 10.6 cents of its own, and grouped by `agentId` the invocations under five turns measured *worse* per tool call than every longer band, 6.7 cents against 4.1 at 11-25, so a run that delegated every errand would spend more than one that delegated none. That floor moved down — it was ten turns and is now about five — which is why the notice's own words still read "more than a handful of steps" **unchanged**: the string is what keeps every run in flight off a cold prefix across the deploy that re-measured it.

**A run is told a browser is already here, because the command it reaches for from memory is the one thing that does not work.** The image ships Playwright and a Chromium (`docs/agent/environment.md`) and nothing told the agents, so they ran `playwright install` — which fails, and whose failure text is "Failed to install browsers". That reads as *there is no Playwright here* and sends a run off to fetch a second Chromium into a path it can write, or to stop looking at the page it just changed. Both error strings are measured and are in `docs/verification.md`: EACCES on the root-owned link file with the sandbox off, `Read-only file system` under `UF_SANDBOX=1`, where bubblewrap binds everything outside the write allow-list read-only and no ownership can change it. So `RENDERING_NOTICE` says how to take a screenshot **and** that a refusal from `playwright install` is not evidence about whether rendering works. It names a command, which the file price list deliberately does not, and what makes that safe is the same property: the only verb near `playwright` is "run", the command is synchronous and leaves no process to clean up, and nothing near it suggests selecting a process by name. It carries **no viewport size** for the other half of that rule — `--viewport-size=1280,800` is the natural thing to write in a worked example, and the digits test refuses it, because `1280` reads as a port and the recipe further up the same prompt says to select a process by the port it chose.

**A run ending can leave the machine, and where that sink attaches is the whole of its data-minimisation argument.** `notifyLifecycle` is a third sink inside `emit()`, on the line after `logLifecycle(published)` and reading the same `PersistedRunEvent`, which is the position rather than a convenience: `logLifecycle` already decided, and had reviewed, what a lifecycle event may say about a run out loud, and it *projects* rather than serialises — an `iteration` payload carries the whole prompt and a creation `status` payload carries the folder. A notifier hung off a route handler or wrapped around `setStatus` starts that decision over with nothing behind it. The body is a **closed list of six fields** — `install`, `event`, `run_id`, `status`, `at`, `url` — and the exclusions are the point: no task text, no folder or mount path, no branch, no repository, no model, no cost, no diff, and **no `runs.title`**, which is forbidden beside the interface *by name* because a title is model-writable text (`chat.ts` lets a proposal name its own run) and a field whose contents an agent chooses is a field an agent can put anything in. `status.ts`'s rule is the standard here and it is stricter than this: counts, timestamps and fractions only. `url` is `UF_PUBLIC_URL` plus `/runs/<id>` and is the empty string when that variable is unset, because a link to `localhost` in somebody's chat client is worse than no link. **Nothing on this path is awaited**, and that is the one way this feature breaks the run loop silently: `emit()` is synchronous from `run_events` through the publish, `createRun`'s folder claim depends on stretches with no `await` in them, and an `await` here would put a run's ending behind a receiver's DNS lookup. The `fetch` carries `AbortSignal.timeout(DELIVERY_TIMEOUT_MS)` and a `.catch` that records and returns; the whole call sits inside a `try`/`catch` that logs `webhook.sink_failed`, because a throw out of a sink would take the emit with it. All four variables — `UF_WEBHOOK_URL`, `UF_WEBHOOK_SECRET`, `UF_PUBLIC_URL`, `UF_INSTALL_LABEL` — are read through `config.ts`'s `optionalEnv` door and are **deliberately not settings keys**: `/api/settings` is reachable with `UF_AUTH_TOKEN`, so a receiver held there is repointable by anything holding the master key, and `saveSettings` stores only what differs from `DEFAULTS` and is a product-defaults mechanism rather than a secret store. In the environment, aiming this app's POSTs somewhere else takes a container restart, which is a decision a person makes at a shell. Delivery requires **both** the URL and the secret: a Home Assistant webhook id is an unauthenticated URL, an unsigned body is one the receiver cannot tell from anybody else's, and a configured-but-secretless install logs `webhook.unsigned` at error level per notification rather than sending one.

**What is worth a notification is its own named constant and its own four-part filter, and every part of it is a decision about noise.** `NOTIFY_STATUSES` is `needs-review`, `blocked`, `failed` — explicitly **not** `TERMINAL_STATUSES`, which has five readers and carries `completed`, so reusing it would page somebody every time a run worked. `UF_NOTIFY_ON_SUCCESS=1` is how an operator asks for exactly that anyway, and it is a **branch in `notifiableEvent`, not a member of the constant** — a set named "the statuses that always notify" whose contents depend on the environment lies to every other reader, and the point of the constant is that the next edit reaching for it finds the fleet-scale default rather than this install's. The branch sits below the always-notify test for the same reason the guard-caused `stopped` does: widening it can add to what notifies and can never subtract. A `stopped` is notified only when a guard caused it, and that is decided by a latch rather than by reading `stop_reason`: a `budget` event with `allowed === false`, `disposition === "stop"` and `enforceable !== false` arms a per-run mark that the next *settled* status consumes. An absent `enforceable` counts as enforceable, because two of the three stop emits omit the field while `no_ceiling` sets it false and the run carries on; the mark is consumed only on a settled status, so a `running` between the verdict and the stop cannot eat it; and an operator's own cancel emits no `budget` event at all, which is what makes a cancel silent without anything parsing prose. A 429's in-place ladder changes no status, so it notifies on the **first rung only** — a second latch, cleared when the run settles, so a reopened run can announce a new wall — and a park's up-to-three `paused` rungs need no state at all, because `paused` is not one of the three endings and the terminal `failed` is. Both latches are bounded at `MAX_TRACKED_RUNS` with insertion-order eviction, since a run that never settles in this process (a container restarted mid-cycle) leaves an entry nothing removes. **One deviation from the brief that specified this, stated rather than absorbed:** it asked for an `error` payload carrying `retrying && usageLimit`, and that conjunction is unreachable in this tree — the emit sets `usageLimit: kind === "allowance"` and `refusalDisposition` answers an allowance refusal with `park` or `fail`, never `retry`, so `retrying` is true exactly when `usageLimit` is false. The reading acted on is `retrying === true`, which is the same reading the loop makes and the one that actually identifies a wait; adding `refusalKind` to that payload would have been the alternative and was left alone, being a change to a producer outside the attach point. Every attempt lands on `webhook_deliveries`, bounded on insert on `request_log`'s pattern, and `/api/status` reports the count since the last success — **derived from the rows rather than from a counter in memory**, because "this channel has been dead since Tuesday" is exactly the answer that has to survive the restart, and a fire-and-forget sink that has been answering 404 for a week is otherwise indistinguishable from a fleet with nothing wrong. No error string reaches that payload: a fetch failure's message names the receiver's host and `/api/status` is scraped and retained somewhere else.


**What the queue is allowed to consider besides age.** `runs.priority` is an
integer, higher first, and `created_at` breaks every tie — so an install that
never sets one queues exactly as it did before the column existed, which is the
property that makes it safe to have. `queueOrder` is the single definition of
that ordering and `selectPromotable` is its only caller, so "what runs next" has
one answer rather than one per query. Priority is clamped to ±100 by
`setRunPriority`: an unbounded integer invites `MAX_SAFE_INTEGER` as a way of
saying "definitely first", and the row after it is then unreachable by any value
a person would type. Setting one never starts, stops or skips a run — on a
running row it means nothing until that row is queued again, which is why it
refuses nothing based on status.
