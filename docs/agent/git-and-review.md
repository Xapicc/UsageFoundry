# Reviews, GitHub credentials and diffs

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision

> **Read before editing src/lib/review.ts, git.ts, diff.ts, patch.ts.**

**Reviewing a diff is not a work cycle and is never automatic.** `startReview` exists only behind a POST; nothing in the run loop reaches it. It refuses when the operator's *own* configured ceiling is already spent (`guardFraction >= 1` on either window) rather than going through `evaluateBudget` — there is no per-run fraction for a review and inventing a threshold would be a limit nobody set. The reviewer is given the diff, the run's task and how the run ended, but **not** the event log: the log is the process rather than the outcome, and a reviewer that reads how the agent got there reviews the journey. A large diff is cut at a file boundary and the omitted files are *named* in the prompt, because a reviewer handed a third of a change with no marker writes a confident review of a change that did not happen.

**A conflict resolution may check its own merge only where a toolchain can exist, and only where an operator named the command.** `resolveConflicts` pins `acceptEdits`, which auto-approves file edits and read-only shell and holds everything else for a human — and a `-p` child has nobody to ask. So the resolver could edit the conflicted files and could not run one command against the result: 19 of 58 completed resolutions, $109.94 of $233.85, say in their own report text that they could not compile or test what they had merged, across the whole recorded window. `AssistRequest.allowedTools` is the same door `ISOLATED_GIT_TOOLS` opens for a work cycle and the same flag — additive, so everything not named still follows the mode. **The reviewer passes no command and must keep passing none**: it is `--permission-mode plan` precisely so that nothing it does can write, and a command granted through that field would be the one hole in that. What the flag now always carries underneath the operator's list is `SEARCH_TOOLS` — `Grep` and `Glob`, which is why the emptiness guard is gone, since the list can no longer be empty. That is a bound by capability rather than by count, and the difference is the whole of what makes it not a hole: the pinned CLI drops both tools from the tool list whenever `Bash` is present unless something names one of them, so naming them buys their existence and not a permission. Measured on this install — zero of 469 recorded `system:init` events ever carried `Grep`, and every one of the five `Grep`/`Glob` calls an agent attempted came back "No such tool available" — and measured the other way on the pin, where adding the two to `--allowedTools` puts them back and changes nothing else in the list. `settings.resolveAllowedTools` is **empty by default and that is not timidity** — this app runs against whatever repository is mounted, so there is no command it could ship that is right for one, and `npm run typecheck` means nothing in a Go or Python tree. It is granted only on `resolveCheckout`'s **reuse** branch, where the run's own worktree was clean and standing on the branch and therefore has a dependency tree; the other branch cuts a fresh `git worktree add` with none, where a check fails for a reason that is not the merge and an agent reading a missing-module error as its own bad resolution will "fix" code that was right. `resolvePrompt` takes the granted list rather than assuming one, so the prompt cannot ask for a command the argv did not allow — an agent told to verify and then refused reports the refusal as a finding about the merge, which is how nineteen reports came to carry a limitation instead of a result. **It is not a gate and its name no longer says it is.** It was `resolveVerifyTools`, one line from `landVerifyCommand` in the same interface, which made it read as the install-wide answer to "what must pass before code lands" — and it is read in exactly one place, `resolveConflicts`, where it becomes the assist's `allowedTools` and decides no land at all. The cost of the old name was an operator setting this one believing they had set the gate, which leaves the gate off and looks identical to having set it. Stored settings are the non-default keys only and carry no version, so `getSettings` reads the old key when the new one is absent: without that the rename is somebody's grant silently becoming `[]`, and `saveSettings` drops the dead key the next time anything saves because it rebuilds the blob from `SETTINGS_KEYS`.

**GitHub credentials reach a work cycle and nothing else.** The container has no other way to authenticate — the `~/.claude` mount carries Claude's login and neither `~/.gitconfig`, `~/.ssh` nor `~/.config/gh` — so `git push`, `gh pr create` and `gh issue view` all fail, and they fail *inside a tool call the run loop never inspects*: the cycle simply ends without the pull request. `githubEnv()` is where the token is turned into an environment, mirroring `telemetryEnv()`, and it sets three things because the failure arrives three ways: `GH_TOKEN`/`GITHUB_TOKEN` for the CLI, a credential helper for `https://github.com` for plain git, and `url.…insteadOf` rewriting `git@github.com:` to HTTPS because no key and no agent reach this container — that last one is the likeliest reason this fails on *some* repositories and not others. It travels as `GIT_CONFIG_*` rather than a config file, so it applies to every git the agent runs and dies with the process instead of outliving the run in a mounted tree; the helper list is **reset** first, because a repository cloned on the host can name `osxkeychain` in its own config and git consults helpers in order. The helper reads `$GH_TOKEN` at call time rather than embedding the token, so `git config --list` does not print it. `GIT_CONFIG_COUNT` must equal the number of key/value pairs — git discards the entire block otherwise, silently, which looks exactly like the unauthenticated container this exists to fix. Withholding is by namespace, not by remembering: `gitEnv()` and `reviewEnv()` strip `UF_*`, so the reviewer (which cannot write) and this app's own git (whose children run repository-controlled hooks, and which never touches the network) are excluded by construction — and `UF_GITHUB_TOKENS` is covered by that same rule with no second exclusion. **There is now a second contributor to that block and there may only ever be one block.** `core.excludesFile` rides in it too — `sandboxMountPoints.ts` carries why, and it is that the sandbox's own bind mounts are character devices at the root of the checkout while a tool call is live, which `git add -A` refuses to stage. Since git numbers the pairs from zero and reads exactly `GIT_CONFIG_COUNT` of them, two contributors spread into one environment do not merge: the second overwrites the count and the low indices and strands the first's remaining pairs past the count, which loses the credential in exactly the silent way the count rule above describes. So both contributors hand over *pairs* and `agentGitEnv` is the only place that numbers them; `githubEnv` is that function with nothing else in the block, which is what its callers want. A third contributor goes through the same door. What the block costs the child is written beside it rather than left to be found: it outranks the repository's `.git/config`, the operator's `~/.gitconfig` and the image's `--system` settings, so a child that runs `git config --global core.excludesFile …` writes a file nothing then reads, and a child that exports its own `GIT_CONFIG_COUNT` for one command replaces the whole block and wins, which is the escape hatch. The operator's own excludes are deliberately not carried forward, because re-deriving git's precedence at every spawn holds a snapshot that goes stale mid-run and fails silently, where overriding fails loudly as a globally-ignored file turning up in the diff they review — and in the container there is nothing to override, which is the same absence `githubEnv` exists for.

**…and *which* credential a work cycle gets is the repository's, not the install's.** One token for the whole install is one token for the whole fleet: `.env.example`'s own advice — a token limited to the repositories you run agents against — yields a one-repository token at one repository and a fifteen-repository token at fifteen, at which point an unattended agent asked to fix a test in one of them holds a credential that can force-push to the other fourteen. `selectGithubToken` is that choice, pure and unit-tested for `githubEnv`'s reason one function over: nothing downstream can see it go wrong, because the wrong token *works* — the push succeeds and the only evidence is a commit in somebody else's history. It is keyed by folder through the same `matchFolderKey` `copyGlobsFor` uses, longest key winning, absolute or relative to any mount; a folder no entry names still takes `UF_GITHUB_TOKEN`, which is what keeps an existing install's behaviour exactly what it was, so narrowing a whole install is leaving that blank and naming the repositories that should have one. An entry with an **empty** token is an answer rather than a typo — this repository gets none — because the narrowest thing an operator can write must not be the widest thing it does. The run resolves it once from `runs.repo_root ?? runs.folder` and hands it to `runIteration` as a **required** parameter, `buildArgs`' rule for the run-cost ceiling: a credential an unattended agent holds is not something a call site should widen by omission, and `cwd` cannot supply it, since an isolated run's cwd is its checkout under `.uf-worktrees` rather than the repository the token is about. What this does *not* do is narrow the helper, which still answers for `github.com` as a whole — how far the token reaches on GitHub's side is still GitHub's answer, and this only decides which token is handed over. The chat is the one child that keeps the install-wide one, and the asymmetry is the argument: an orchestrator turn looks across every mount *before* it knows which repository it is proposing work in, so narrowing it to a cwd would withhold the credential from every question about a repository it had not been pointed at yet — which is the failure `chatEnv` was widened to remove.

**Diffing runs repository-controlled code unless it is told not to.** Every `git diff` that reads a file's *contents* carries `--no-ext-diff --no-textconv`, through the one `DIFF_FLAGS` array in `diff.ts` (`--no-color` and `-M` with them): `diff.external` and a `diff.<driver>.textconv` reached through `.gitattributes` are both *commands git runs*, configured by the repository being rendered. Same class as the `core.fsmonitor` clearing that already applies to every call. The one call site outside that array is `land.ts`'s `conflictedFiles`, `["diff", "--name-only", "--diff-filter=U"]`, and its exemption is written here rather than left to be re-derived: `--name-only` emits paths and never opens a blob, so neither driver is invoked. That is an argument about *that* call's arguments and not a relaxation of the rule — a `--name-only` that grows a content flag, or any new `diff` call, takes `DIFF_FLAGS`. The same site passes `NO_CLOCK`, so a driver invocation there would also run unbounded, which is the second reason not to let one become reachable. Paths that come back from git and go out again as pathspecs are pinned with `:(top,literal)`, or a filename containing `*` would be read as a glob.

**A diff that was shortened says so.** The file *list* is always complete; patch bodies are budgeted (`selectForPatch`), and what the budget leaves out is counted and rendered as "N files listed without contents" rather than dropped. `splitPatches` matches chunks to files **by position**, never by parsing the header path — git re-quotes odd filenames there — and a count mismatch yields no patches at all rather than hunks filed under the wrong name.

**What a run *touched* is a different fact from what it changed, and the three ways of having none of it are three different sentences.** The Files tab draws both halves: `diff.ts` says what came out of the branch, and `runTouchScan.ts` says what the run's `kind: "tool"` events named, so an operator can read the set difference — a file changed by something that names no file (a `Bash` running `sed -i`, a formatter, a codegen step), a file read and never written, a file touched outside the checkout at all. **Two modules, and the split is load-bearing rather than tidy:** `runTouches.ts` holds the reconciliation and reaches nothing — no database, no `node:fs`, no `git` — because `RunTouches.tsx` is a `"use client"` file and imports it, which is `apiTypes.ts`'s own reason one module over; `runTouchScan.ts` holds the query. Reconciling on the server instead would mean a second `runDiff` — several more git processes for the file list the tab has already fetched — which is the whole reason the changed set arrives as a prop rather than as a fetch. **The scan is `readCountsFor`'s `CASE` and must stay it**: keying on `repo_root` rather than `COALESCE(work_dir, folder)` then `folder` returns an empty result for every worktree-isolated run and looks exactly like a working query. Two differences from that one, both deliberate — it is not filtered to `$.name = 'Read'`, and it **keeps** the rows that query drops at its `ELSE NULL`, which are the touches outside the checkout and are a group of their own. The path fields come from `TOOL_FILE_FIELDS` in `logLine.ts`, a subset of `HEADLINE_FIELDS` typed as one, so a field renamed there fails to compile instead of leaving this reading `NULL` for every row; `path` is deliberately not among them, because on `Glob` and `Grep` it is the directory a search ran in. **There is a second reader over the same rows and it is a second function rather than a flag on the first.** `scanTouchSequence` answers the map's replay — one row per *call*, uncollapsed, `ORDER BY e.id` — where `scanTouches` answers the Files tab, one row per file. Neither derives from the other: a count has no positions in it, and a list of positions is the wrong payload for a table drawing one row per file. A flag would have joined them anyway at the caller that does not want the other's shape, which is why the ordering rides on `/api/runs/[id]/touched/sequence` and not on `touched`: that route is fetched by every run page's Files tab and folding the sequence in would multiply its payload by however many times the busiest file was read. What the two *do* share is the relativising `CASE`, which is now the `TOUCH_ROWS` subquery both read — one copy, because a second would be a second thing to get right and the one that drifted would be the one nobody read. **Ordered by `e.id` and never by `ts`**: `id` is `AUTOINCREMENT` and so ascending in emit order, where `ts` is a millisecond clock several calls routinely share, and a tie broken by the planner is a replay drawing a plausible order that did not happen. The derivation over those rows is `touchReplay.ts`, beside `runTouches.ts` and under the same rule for the same reason — the page that scrubs is a `"use client"` file — and it is **never** derived in the browser from the run page's event array, which is the newest 2,000 events inside 4 MB and would describe the tail of a long run as the whole of it. **No row may carry a success or failure mark**, and that binds the sequence harder than the table: a mark advancing file to file reads as progress. A tool call is recorded when it is made and a result only when it *failed* (`orchestrator.ts:7343-7344`), and the failure row carries no `tool_use` id joining it back — only a whitespace-flattened 160-character command string, which is wrong exactly inside a retry loop. So the header says once that a touch is an *attempt*, and that is where the hedge stays. **An absent diff is an *unknown* changed set, not an empty one.** With the diff route's `kind: "none"` — a branch deleted after the run finished, a run that never had one — the card still renders, because its two figures and its three empty states are facts about the events rather than about the branch, and an old run whose branch was deleted is exactly the one whose events are most likely to have been swept. What it drops is the two groups whose *labels* make a claim about the diff: "changed, never named" and "named, and not changed" over a file nobody can say was not changed is the reconciliation asserting the thing it exists to check. **Nothing may render as an empty list.** `run_events` is swept at `eventRetentionDays` while a checkout is kept on its own clock, so a run old enough has a diff and no touches: `touchesFor` answers `swept`, `empty` and `none` as three `kind`s and the component gives each its own sentence, because all three otherwise read as a run that touched no file. The horizon is checked **after** the scan and not instead of it — a run past the horizon whose sweep has not run yet still has its rows, and announcing the policy over data that is sitting there would be a readout describing the schedule instead of the database. And the header prints the **distinct touched-file count** and the **work-cycle count**: they are the measurement that decides whether a file-by-cycle grid has an axis short enough to draw, which `proposals/SessionFlow/` deferred for want of them.

**The map at `/runs/[id]/touched` draws the same rows and is allowed to claim less than the table, never more.** The operator read the landed card on a real run — 39 distinct files across one work cycle — and asked for the picture `proposals/SessionFlow/` had turned down; that call is made and is not to be relitigated, but the survey's *findings* are facts about the stored data and every one of them still binds. Four rules, and each fails silently by drawing something plausible. **The node set is files and the arrangement is the path hierarchy** (`touchedMap.ts`): tool → file is a bipartite star at every size — a dozen hubs with nearly everything hanging off `Read`, which the mockup's own fake run put at degree 321 — and it draws one fact the header already states. Tool identity is therefore an *attribute*, `TouchedFile.tools` on the node and the union of them on a directory, and a line on the canvas means **is in** and never *was called by*. A tool node here would have to earn its place against that, and none has. **Nothing on it says a touch succeeded**: the fill says read, written or both, which is what the call asked for, and the sentence saying a recorded call is an *attempt* is shared with the table through `RunTouchNotes.tsx` rather than written a second time. **No file is ever dropped**, and the rule lives in `pathMap.ts` — the arrangement, over any per-file payload — rather than beside the touches, because the next map laid out this way inherits it instead of pasting it. Over budget, the tree folds at a **depth** — deepest directories first, so the top level of the repository survives — and each folded node carries the count behind it and the surface says the total out loud; opening a directory opens its ancestors, or the next plan closes one over the top of the click. `capGraph` is deliberately not reused: it prunes by degree largest-first, which over this graph keeps the directories and discards the files. And **`changedKnown` withholds the changed ring**, on the same grounds as the two groups the card drops: a mark meaning "the branch changed this" over a file nobody can speak for is the reconciliation asserting the thing it exists to check. The one place the map says *more* than the table is a run whose events are `empty` and whose diff is not: it wrote through `Bash` alone, and those files have paths and therefore positions, which is exactly the group the survey recorded a tool → file graph as structurally unable to show.

**`AssistKind` has a third member and it is the one that is not a person's press.** A review and a merge-conflict resolution are each started by somebody pressing something; a **validation** is started by a run asking to close a task, and `docs/agent/taskboard.md` carries what it decides and why. What belongs here is what it does to this module. It is on the same table, the same lifecycle and the same boot reconciler, which is the reason a third `kind` was chosen over a fourth table. It takes the review's clock rather than the resolution's absence of one, and more sharply than the review needs it: a run is waiting at its cycle boundary for the answer, holding its folder and one of `maxConcurrentRuns`, so a verdict that never arrives is a slot that never comes back — where a resolution is unbounded precisely because there is no length of time after which reconciling somebody's work becomes the wrong thing to do. It is the only kind that passes `maxBudgetUSD`, and `AssistRequest` carries that as an optional field rather than a constant here so the two a person starts keep the behaviour they had. `after` is the hook it settles through, exactly as a resolution commits its merge through it, and the verdict reaches `run_reviews.verdict` as a `Partial<AssistResult>` — this module never parses one and must not learn to, because what a verdict *means* is the other file's subject. Three new columns ride along: the task the claim was about, and the base and head it read, written at the **start** rather than at the settle, because what they record is what the child was shown and a branch that moved while the validation ran would otherwise be recorded as the thing that was judged.

**An assist streams, and every tool call it makes is on the run's log wearing its own name.** The three kinds spawned here ran `--output-format json` until 2026-09-09, which prints one object when the child exits: a validation therefore showed as the `complete_task` that claimed the task, then a minute of nothing while a billed child read the branch, then a verdict — and the half an operator needs in order to decide whether to believe that verdict, which files it opened before deciding the work was there, existed nowhere at all. `stream-json` plus `--verbose` is the pair the CLI gates streaming on, `chat.ts` carries the same two for the same durability reason one file over, and the shape was measured against the pin before the change rather than assumed (`docs/verification.md`, 2026-09-09). Two things follow and neither is optional. **Only `tool_use` blocks are taken**: the assistant's own text belongs in `run_reviews.text`, where the page draws it as a verdict or a review, and the same words on the run's log would read as the run's report about itself. **And every one of those rows carries `assist`**, which is what `describeEvent` turns into the `check ›` / `review ›` / `resolve ›` prefix — attribution is load-bearing here in a way it is not even for a sub-agent, because a check reads the branch while the run that asked for it is still mid-cycle, so its calls land *interleaved* with the run's own rather than after them, and an unlabelled `Grep` between two of the run's lines reads as the run's.

**That field is also a filter, and two readers had to grow it in the same change.** A `tool` row is not only a log line: `runTouchScan.ts` reduces them into "what did this run touch", which the Files tab draws and the touched-versus-changed reconciliation reads, and `fileCostNotice.ts` counts the `Read`s in a folder to tell the next agent what is expensive to keep re-reading. Both would have silently absorbed the assist's reads — files nobody edited appearing as the run's work, and a reviewer's single pass over a file being reported back as a habit — so both now require `json_extract(payload, '$.assist') IS NULL`. That is the whole reason the marker is a field on the row rather than a prefix baked into `name`: a string that only the renderer understands cannot be filtered on in SQL, and these two readers are SQL.

**`parseReviewOutput` reads the `result` event and refuses anything else, including the last line that happens to parse.** A stream's final complete line is an ordinary `assistant` event whenever the child was killed, and read as the result it reports a turn that never finished as one that finished with no text having cost nothing — with the stderr that says what actually happened dropped. So the scan is for `type === "result"` and the fall-through to a whole-string parse is taken only when no such event arrived *and* the one object printed does not name itself as some other kind of event, which is what keeps the older one-object shape readable.
