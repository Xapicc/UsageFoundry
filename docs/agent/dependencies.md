# Run dependencies

> load into a session. Each paragraph records a correctness or safety decision

> **Read before editing releasableRuns/admitDependencies/releaseDependents in orchestrator.ts.**

**A run can be told to start after other runs, and while it waits it holds nothing.** `run_deps` is a join table rather than a `depends_on` column because fan-in is the case that matters — "after both of these" is a list with identity — and because the condition belongs on the edge rather than on the run: one dependent can reasonably want "only if that one worked" from one dependency and "once that one is out of the way" from another. `waiting` is a status rather than a flag on `queued` precisely for what it must *not* hold. `activeRuns()` cannot see it, so it reserves no folder, takes no checkout slot, spends no concurrency slot and has no place in line. That absence is the whole design: a `queued` run reserves its folder against everything younger — deliberately, or a run on the workspace root is overtaken for ever — so a four-run chain admitted up front as `queued` would stall every unrelated run on that repository for the length of the chain. Isolation is planned at *release* rather than at admission for the same reason: choosing a checkout slot is claiming it, and a run that may not start for days must not hold one. `isolate: false` is the one thing recorded at admission, because that is the operator's own answer and the release must not overrule it — everything else (`work_dir`, `repo_root`, the branch, the base commit) is null until `admitWaiting` fills it in, which is also why a waiting row is invisible to `landState` rather than a branch with nothing on it. `continues_run` is the second, and it is not an exception to any of that: it names a run rather than claiming one, and the isolation invariants below say why the landing rules need it before there is a branch to see.

**A dependency succeeds by reaching `completed`, and a run that never ran a work cycle satisfies nothing.** The first half is the choice `reopenPrompt` already forced once: `completed` is written both for a `DONE` reply and for a run that used up its cycle cap, and `maxIterations` defaults to 1, so keying success on `reported_done` would mean a dependent almost never starts and the chain would terminate saying "it did not report done" about a run that did exactly what it was asked. Success here is the *absence of a fault* — no crash, no guard, no operator stop — which is the question a person chaining two runs is asking; `reported_done` is on the DTO for anyone who wants the stronger reading and decides nothing here. The second half is what makes a chain terminate rather than sit there: a guard refusing a run at the door, a run whose own dependency failed, a run stopped before it started and a run closed out by a restart are all terminal with `iterations === 0`, and reading `on-finish` as "any terminal status" would start the next run on the strength of a run that never opened a file — and would leave a `blocked` run satisfying its dependents, so nothing would ever end the chain behind it. Both conditions are named explicitly on the wire and neither is defaulted, because a silent default is wrong half the time in both directions: `on-success` terminates a chain the operator meant to run regardless, `on-finish` starts a run on top of a dependency that crashed.

**`needs-review` is terminal and is not a success, and both halves are carried by one constant.** A run whose agent reported it could not finish has settled — it holds no folder, no checkout slot and no concurrency slot, and nothing will restart it but a person — so `TERMINAL_STATUSES` gains it, and that single entry is what makes `releasableRuns` reach its fixed point, `retention.ts` begin ageing its evidence out, and a workflow's loop and edge verdicts settle. Forgetting it produces a run that is terminal everywhere a person looks and unsettled everywhere the machine looks: chains that never start, loops that wait for ever, evidence that never expires, and not one line anywhere saying so. `edgeSatisfied` then answers both edges without a second rule, and the answers are the ones wanted: `on-success` is `=== "completed"` and nothing else, so a dependent stays `blocked` with a sentence naming the run that asked for review — a run that reported it could not get past something did not do the work the next run was chained behind — while `on-finish` starts, which is what that edge has always meant about a `failed` predecessor. The `iterations < 1` rule still comes first, so a `needs-review` run that never completed a cycle satisfies neither. One consequence is stated rather than absorbed: `branchVerdict` has no run-status test, so a **merge block** behind an `on-finish` edge will land the branch of a run that asked for review with nobody looking. That is not new — it already does so for a `failed` predecessor — and the operator's control is the same one they already have, which is to choose `on-success`.

**A dependent that can never start is terminated with a sentence naming what stopped it, and so is everything behind it.** The status is `blocked` — the one this app already writes for a run refused before its first work cycle, and the true thing to say: nothing ran, nothing was spent. `releasableRuns` is the whole decision and it is pure and unit-tested for exactly this, because both failure modes are silent: a run released too early starts on top of work that has not happened, and a run neither released nor terminated sits `waiting` for ever holding a prompt the operator believes is queued. The cascade is a fixed point rather than a graph walk — a run blocked in one pass is a settled dependency that ran no cycle in the next — so every run in a chain gets its own reason naming the run *in front of it* rather than one shared verdict about a run at the head it never heard of.

**A loop is refused at admission, because nothing downstream of it would ever be woken or ended.** `releasableRuns` reaches a fixed point and leaves a cyclic set alone, which is precisely the row nothing wakes; admission is the only moment an edge is created, so it is the only place this can be caught. `dependencyCycle` names the loop, and a self-reference is reported as the one-run loop it is. `createRun` cannot construct a cycle today — it mints the run's id *after* reading the edges, so nothing can already point at it — and the check is what keeps acyclicity a property of the data rather than of who happens to write it.

**Every terminal transition wakes the dependents, and a boot deliberately does not.** `releaseDependents` is called from `startRun`'s `finally`, from both of `stopRun`'s pre-spawn branches and its new waiting branch, and from the sweeper's never-clearing verdict when its ending lands (a miss means an operator's stop or resume took the row first: a stop releases for itself, and a resume settles nothing) — missing one leaves a dependent asleep with nothing that will ever wake it. Released runs join the queue rather than starting there, so folder reservation, FIFO order and the concurrency cap stay in `promoteQueued`, the same reason `sweepPaused` re-queues instead of calling `startRun`. `reconcileOnBoot` is the exception, and it decides its waiting rows only after the active ones, against what it did to each one's dependency. A row behind a run that same boot has just failed or stopped is `blocked` with a sentence naming that run, on either edge, because releasing it would promote a days-old prompt into an unattended agent that accepts edits (the queued rule arrived at from the other side), and an `on-finish` edge would do exactly that for a run that did a cycle and then died with the container. It is not flagged `restart_closed`: its dependency is, and picking that up revives it through `reviveBlockedDependents` — unless it has been set aside, which that revive never undoes. Every other waiting row goes through the ordinary pass with its release half held, so what can never start still ends naming the run in front of it, while a row behind a pause the boot kept, or held behind a completed run, stays `waiting`. Stopping those too, as the boot once did, recorded a restart that had closed nothing they waited for. It is the pass and not `releaseDependents`, whose workflow advance `reconcileBlocksOnBoot` has to run ahead of. A loop whose ending is the shutdown's, the ending flagged `restart_closed`, blocks what waits on it the same way, in `blockBehindRestartClosed` with the boot's sentence, before its own release pass: that is the ending the boot gives a run a crash left `running`, and released instead an `on-finish` dependent was queued mid-shutdown, flagged by the boot as a queued row, and reopened by the restart notice's one press beside the run it was set to follow.

**An isolated run is granted the two git commands it is ordered to use.** `acceptEdits` — the default the run form and `chatDefaultGuards` both start from — auto-approves file edits and read-only shell, and holds mutating git for a human: `git add` and `git commit` each come back `This command requires approval`, and a `-p` child has nobody to give it. So the isolation preamble told the agent to commit as it went and the permission mode made that impossible. Measured, not reasoned: four runs finished `completed`, on their own branches, each having tried to commit and been refused, with the whole change left uncommitted in a worktree that `landState` then read as a branch with nothing on it. `buildArgs` therefore passes `--allowedTools Bash(git add:*) Bash(git commit:*)` for `isolation === "worktree"` only — additive, so everything else still follows the mode, and verified against the real CLI along with the fact that `--allowedTools` does not restrict what it does not name. Not `bypassPermissions`, which would also hand the run the network and `rm`; and not for a run in the operator's own checkout, which is told nothing about committing.

**A refused tool call is reported, because the alternative is a run that looks like it chose not to.** The `result` event carries `permission_denials` (confirmed on the wire for `stream-json`, not only for the `--output-format json` that `chat.ts` reads), and `permissionDenials()` groups it by tool *and command* — every entry's `tool_name` is the bare `Bash`, so "Bash ×7" would say nothing. This is the line that turns the failure above from a transcript-archaeology exercise into a log entry.
