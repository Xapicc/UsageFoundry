# Run dependencies

> **Read before editing releasableRuns/admitDependencies/releaseDependents in orchestrator.ts.**

**A run can be told to start after other runs, and while it waits it holds nothing.** `run_deps` is a join table rather than a `depends_on` column because fan-in is the case that matters — "after both of these" is a list with identity — and because the condition belongs on the edge rather than on the run: one dependent can reasonably want "only if that one worked" from one dependency and "once that one is out of the way" from another. `waiting` is a status rather than a flag on `queued` precisely for what it must *not* hold. `activeRuns()` cannot see it, so it reserves no folder, takes no checkout slot, spends no concurrency slot and has no place in line. That absence is the whole design: a `queued` run reserves its folder against everything younger — deliberately, or a run on the workspace root is overtaken for ever — so a four-run chain admitted up front as `queued` would stall every unrelated run on that repository for the length of the chain. Isolation is planned at *release* rather than at admission for the same reason: choosing a checkout slot is claiming it, and a run that may not start for days must not hold one. `isolate: false` is the one thing recorded at admission, because that is the operator's own answer and the release must not overrule it — everything else (`work_dir`, `repo_root`, the branch, the base commit) is null until `admitWaiting` fills it in, which is also why a waiting row is invisible to `landState` rather than a branch with nothing on it. `continues_run` is the second, and it is not an exception to any of that: it names a run rather than claiming one, and the isolation invariants below say why the landing rules need it before there is a branch to see.

**A dependency succeeds by reaching `completed`, and a run that never ran a work cycle satisfies nothing.** The first half is the choice `reopenPrompt` already forced once: `completed` is written both for a `DONE` reply and for a run that used up its cycle cap, and `maxIterations` defaults to 1, so keying success on `reported_done` would mean a dependent almost never starts and the chain would terminate saying "it did not report done" about a run that did exactly what it was asked. Success here is the *absence of a fault* — no crash, no guard, no operator stop — which is the question a person chaining two runs is asking; `reported_done` is on the DTO for anyone who wants the stronger reading and decides nothing here. The second half is what makes a chain terminate rather than sit there: a guard refusing a run at the door, a run whose own dependency failed, a run stopped before it started and a run closed out by a restart are all terminal having run nothing, and reading `on-finish` as "any terminal status" would start the next run on the strength of a run that never opened a file — and would leave a `blocked` run satisfying its dependents, so nothing would ever end the chain behind it. Both conditions are named explicitly on the wire and neither is defaulted, because a silent default is wrong half the time in both directions: `on-success` terminates a chain the operator meant to run regardless, `on-finish` starts a run on top of a dependency that crashed.

**"Ran a work cycle" is `ranWorkCycle`, which is `iterations > 0` or a refunded cycle, because the refunds put `iterations` back to zero on a run that worked and paid.** A stack park, a live-guard cut and a context-ceiling end each hand the cycle they ended back to the counter, so a run that spent a whole cycle and was then stopped while parked ends `stopped` with `iterations === 0`. Read as "never ran", it blocked its `on-finish` dependent with "ended stopped without running a work cycle", a sentence that was false; "Try again" on the dependent re-blocked it at once, and the only way out restarted the dependency's agent. `DependencyState.refundedCycles` carries `guard_refunds + stack_waits + early_ends` (`refundedCyclesSql` for a query, `refundedCyclesOf` for a row in hand), and it is a required field so that a state built without it is a compile error and not a run read as idle. Those three and not `pause_count`, which `ensureWorktree` reads for a different question ("might a branch exist"): `pause_count` also counts a provider refusal, whose cycle was turned away before any work and refunded too, so a run refused at the wall and then stopped would have satisfied `on-finish` having done nothing, which is the failure the rule exists to prevent. A transient retry is left out for the same reason. `on-success` is unchanged by all of this: a refunded run that was stopped is not `completed`, so its dependent still blocks, now with the sentence about how it ended. Not changed: `reviveBlockedDependents` filters the *dependents* it wakes (`iterations = 0` on a row that never reached a workspace, which is true of them whatever their dependency did), and `reopenRun`'s `neverStarted` is a question about whether a row holds a session or a workspace, which a parked run always does. The branch-ownership reads follow the same rule through the same helpers, because a link that committed and was then parked or cut is the same run read the same wrong way: `branchOwner` (`ChainMember.refundedCycles`, required for the reason above, and the branches page's collapse, which builds its members itself), `chainRuns`' ordering, and `admitDependencies`' refusal of a second run continuing one branch. Asking `iterations > 0` alone named the link before it as the owner, and admitted a second continuer onto a branch carrying the first one's commits.

**`needs-review` is terminal and is not a success, and both halves are carried by one constant.** A run whose agent reported it could not finish has settled — it holds no folder, no checkout slot and no concurrency slot, and nothing will restart it but a person — so `TERMINAL_STATUSES` gains it, and that single entry is what makes `releasableRuns` reach its fixed point, `retention.ts` begin ageing its evidence out, and a workflow's loop and edge verdicts settle. Forgetting it produces a run that is terminal everywhere a person looks and unsettled everywhere the machine looks: chains that never start, loops that wait for ever, evidence that never expires, and not one line anywhere saying so. `edgeSatisfied` then answers both edges without a second rule, and the answers are the ones wanted: `on-success` is `=== "completed"` and nothing else, so a dependent stays `blocked` with a sentence naming the run that asked for review — a run that reported it could not get past something did not do the work the next run was chained behind — while `on-finish` starts, which is what that edge has always meant about a `failed` predecessor. The never-ran rule (`ranWorkCycle`) still comes first, so a `needs-review` run that never completed a cycle satisfies neither. One consequence is stated rather than absorbed: `branchVerdict` has no run-status test, so a **merge block** behind an `on-finish` edge will land the branch of a run that asked for review with nobody looking. That is not new — it already does so for a `failed` predecessor — and the operator's control is the same one they already have, which is to choose `on-success`.

**A dependent that can never start is terminated with a sentence naming what stopped it, and so is everything behind it.** The status is `blocked` — the one this app already writes for a run refused before its first work cycle, and the true thing to say: nothing ran, nothing was spent. `releasableRuns` is the whole decision and it is pure and unit-tested for exactly this, because both failure modes are silent: a run released too early starts on top of work that has not happened, and a run neither released nor terminated sits `waiting` for ever holding a prompt the operator believes is queued. The cascade is a fixed point rather than a graph walk — a run blocked in one pass is a settled dependency that ran no cycle in the next — so every run in a chain gets its own reason naming the run *in front of it* rather than one shared verdict about a run at the head it never heard of.

**A loop is refused at admission, because nothing downstream of it would ever be woken or ended.** `releasableRuns` reaches a fixed point and leaves a cyclic set alone, which is precisely the row nothing wakes; admission is the only moment an edge is created, so it is the only place this can be caught. `dependencyCycle` names the loop, and a self-reference is reported as the one-run loop it is. `createRun` cannot construct a cycle today — it mints the run's id *after* reading the edges, so nothing can already point at it — and the check is what keeps acyclicity a property of the data rather than of who happens to write it.

**Every terminal transition wakes the dependents, and a boot deliberately does not.** `releaseDependents` is called from `startRun`'s `finally`, from both of `stopRun`'s pre-spawn branches and its new waiting branch, and from the sweeper's never-clearing verdict when its ending lands (a miss means an operator's stop or resume took the row first: a stop releases for itself, and a resume settles nothing) — missing one leaves a dependent asleep with nothing that will ever wake it. Released runs join the queue rather than starting there, so folder reservation, FIFO order and the concurrency cap stay in `promoteQueued`, the same reason `sweepPaused` re-queues instead of calling `startRun`. `reconcileOnBoot` is the exception, and it decides its waiting rows only after the active ones, against what it did to each one's dependency. A row behind a run that same boot has just failed or stopped is `blocked` with a sentence naming that run, on either edge, because releasing it would promote a days-old prompt into an unattended agent that accepts edits (the queued rule arrived at from the other side), and an `on-finish` edge would do exactly that for a run that did a cycle and then died with the container. It is not flagged `restart_closed`: its dependency is, and picking that up revives it through `reviveBlockedDependents` — unless it has been set aside, which that revive never undoes. Every other waiting row goes through the ordinary pass with its release half held, so what can never start still ends naming the run in front of it, while a row behind a pause the boot kept, or held behind a completed run, stays `waiting`. Stopping those too, as the boot once did, recorded a restart that had closed nothing they waited for. It is the pass and not `releaseDependents`, whose workflow advance `reconcileBlocksOnBoot` has to run ahead of. A loop whose ending is the shutdown's, the ending flagged `restart_closed`, blocks what waits on it the same way, in `blockBehindRestartClosed` with the boot's sentence, before its own release pass: that is the ending the boot gives a run a crash left `running`, and released instead an `on-finish` dependent was queued mid-shutdown, flagged by the boot as a queued row, and reopened by the restart notice's one press beside the run it was set to follow.

**A run a restart closed out satisfies no edge until it is picked up, and nothing new is chained onto it meanwhile.** `releasableRuns` blocks a waiting run behind any dependency that is `restart_closed` and `failed` or `stopped` — `ReleaseState.restartClosed`, `restartClosedSql`, the restart notice's own condition without `set_aside_at` — on either edge, ahead of the edge test, with the boot's sentence. The boot and the loop already blocked what waited on a run they had just closed out, but only then: any later pass read the same ending as an ordinary one, and an `on-finish` edge is satisfied by a restart's `stopped` once a cycle has been counted. A fan-in reached it. B after A and C, both closed out; picking up C alone by name revives B through `reviveBlockedDependents`, which follows edges out of the run picked up and asks nothing about B's other dependencies; C's next ending ran the pass, which released B on the strength of A's restart ending, and picking A up afterwards ran the two side by side — inferred from the code, then reproduced in `shutdown.test.ts` against `17704ac`, B `queued`. Blocked rather than left pending, because nothing obliges anybody to pick the run up, and a row waiting for a pick-up that never comes is the asleep-for-ever row; blocked is what the pick-up revives, so the sentence stays true. Narrowing the revive instead was rejected: it fixed only the path that was found, left B blocked with a sentence naming the run just picked up, and every other way a row reaches `waiting` behind a closed-out run — a never-started row picked up by name, a row woken earlier — would still have been released. A run set aside still counts: setting it aside holds it back from the notice's press, and it has not finished any more for that. `dependenciesOf` reads the flag the same way, so the page never calls a dependency satisfied that the pass blocks on. **A new run** told to start after such a run is refused at `createRun` with a sentence of its own — pick that run up first, or start this one without waiting for it. It used to be created `queued` on an `on-finish` edge, beside a run the notice's one press would then start, and refused on `on-success` with "it ended stopped", which sent the operator nowhere. Not created `blocked` either: a row born terminal is a run the operator is told they made and cannot reopen, since `blocked` is not `REOPENABLE`. The explicit `blockBehindRestartClosed` calls in the boot and the loop still run ahead of their passes; the pass now agrees with them rather than being where the rule lapsed. A workflow's own edge verdicts do not read the flag: what they hand to `createRun` meets the refusal, and the node is written `blocked` and revived by the pick-up, while an orchestrator, merge or review block behind such a run still goes ahead on it — read from the code and not yet driven, and filed as its own task.

**An isolated run is granted the two git commands it is ordered to use.** `acceptEdits` — the default the run form and `chatDefaultGuards` both start from — auto-approves file edits and read-only shell, and holds mutating git for a human: `git add` and `git commit` each come back `This command requires approval`, and a `-p` child has nobody to give it. So the isolation preamble told the agent to commit as it went and the permission mode made that impossible. Measured, not reasoned: four runs finished `completed`, on their own branches, each having tried to commit and been refused, with the whole change left uncommitted in a worktree that `landState` then read as a branch with nothing on it. `buildArgs` therefore passes `--allowedTools Bash(git add:*) Bash(git commit:*)` for `isolation === "worktree"` only — additive, so everything else still follows the mode, and verified against the real CLI along with the fact that `--allowedTools` does not restrict what it does not name. Not `bypassPermissions`, which would also hand the run the network and `rm`; and not for a run in the operator's own checkout, which is told nothing about committing.

**A refused tool call is reported, because the alternative is a run that looks like it chose not to.** The `result` event carries `permission_denials` (confirmed on the wire for `stream-json`, not only for the `--output-format json` that `chat.ts` reads), and `permissionDenials()` groups it by tool *and command* — every entry's `tool_name` is the bare `Bash`, so "Bash ×7" would say nothing. This is the line that turns the failure above from a transcript-archaeology exercise into a log entry.
