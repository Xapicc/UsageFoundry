# Gate blocks

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing what a gate block may hold (`GATE_IS_TOLD_NOTHING` in `src/lib/workflowGraph.ts`), `holdGate` or `continueGate`. Split out of [nodes-and-instantiation.md](nodes-and-instantiation.md), whose rules about what a node holds and how a graph is instantiated it builds on.

**A gate is a block that waits for a person, and it is a ledger row that never has a turn.** `gate` is the seventh `WorkflowNodeKind` and the only one whose job is to *not* proceed: when the instance reaches it, nothing is spawned, billed or created, and everything behind it waits until the operator presses Continue on the instance page. Approval used to happen once, at save, and after that the only lever was Stop — 7 of the 26 settled loops measured on this install ended in an operator stop, each before its merge landed anything — so a gate is the place a person is asked *again*, at a point the graph names. It holds **no agent, template, workspace, folder, task or prompt**, and `normalizeNode` refuses each of those **by name** (`GATE_IS_TOLD_NOTHING`, `LOOP_IS_TOLD_NOTHING`'s treatment and for its reason: a template chosen for a block that starts nothing is a choice no process will act on, and this is the door built to say so out loud). It is `startsNoRun`, skipped by `planNode`, `folderRefusal` and `startWorkflow`'s plan loop with the other four. A gate with no link out is refused: it would stop the instance for a press that releases nothing.

**It is `waiting` the whole time, and `held_at` is the only thing that says it was reached.** A new status would be five more places that must name it — the docblock over `BlockStatus` says why `looping` was the last exception — and "costs nothing, as a `waiting` row does" is already true of a row that is `waiting`. `planInstanceStep` lists a gate whose every incoming edge is satisfied in `InstanceStep.hold`, on every plan until it is let through; `holdGate` writes `held_at` with an UPDATE guarded on `held_at IS NULL`, and that guard is the *once*: the notification goes out when it changes a row and not before or after. Continue (`continueGate`, `POST …/instances/[instanceId]/continue`) writes `emitted`, guarded on `waiting` and on `held_at IS NOT NULL`, so a press on a gate not yet reached changes nothing and one that raced a halt keeps the halt's answer. `edgeVerdict` reads a gate as it reads a merge or deliver block — `waiting` pending, `emitted` satisfied, `blocked` a sentence naming it — and pushes nothing onto `dependsOn`. Everything behind a gate is therefore deferred (`deferredNodes` is "behind any non-run") and is created by the advance Continue triggers, not before. Stop is not a second door: it is `POST …/stop`, `stopInstance`, which writes the gate `blocked` with every other waiting block, and `reviveBlockedBlocks` clears `held_at` when a pick-up puts one back, so a revived gate is held, and announced, afresh.

**A gate hands on no runs, and that is the cost the diagram pays.** It is the fourth block, after merge, deliver and loop, that resolves to no run, so a merge block whose only predecessor is a gate has nothing to land: `run → gate → merge` is refused at save, and the refusal says to link the run to the merge as well as to the gate (`gateHint`). The diamond — `run → gate`, `run → merge`, `gate → merge` — is the shape that holds a merge, because the merge then waits for the gate and still lands the run. Making the gate transparent (resolving to the runs behind it) was considered and left: it would change what `edgeVerdict` pushes for every successor kind, apply the outgoing link's condition to runs it was never drawn against, and add a look-through to every rule that asks what is "directly in front of" a merge, deliver or review block — a rewrite of rules whose silent failures are the point of this file, for a convenience the diamond already gives. A `continueBranch` link into or out of a gate is refused by name, as it is for every other block that cuts none.

**Whether a chat may propose one: yes.** A gate holds nothing dangerous — it starts and spends nothing and only ever makes a run *wait* — so `propose_workflow` takes it, unlike `deliver`, which publishes. The approval card says "no agent" for it, and the Guards cell on `/workflows/[id]` says the same in the same words. What a model cannot do is the other half: no tool a model holds continues a gate. `continueGate` is reached from the one route above and from nothing else.
