# Editing loops on the canvas: frames, gestures, inspector and Run page

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing the frame gestures (`resolveRepeat`, `linksWithoutMember`, `resolveLinkRelease`, `linkRefusal` in `src/lib/canvasGraph.ts`), a loop's inspector in `src/components/WorkflowEditor.tsx`, or its row on `src/app/workflows/[id]/page.tsx`.

**A loop is made by framing blocks and unmade by deleting the frame, which is why it is in no palette and in no kind picker.** A loop with nothing inside it is refused at Save, so a palette entry would be a control whose only outcome is that refusal — and the kind picker is worse: switching an existing loop away leaves an orphaned `repeats` link, which is now drawn as no arrow at all, so the refusal it earns at Save has nothing on the canvas to explain it. `resolveRepeat` is the gesture: it takes the marked ids and answers which block the frame would **start** at, in `bodyOrder`'s order, and the editor mints the loop and one `repeats` link to it. The membership that appears is whatever the graph already links after that block, which is what makes marking the head of a chain and marking the whole chain the same gesture — and is the route below the breakpoint, where there is no modifier to hold. Its two refusals are about the *gesture* and are refused on the server too, by name: a loop inside a loop, and a block already framed. Everything else is left to `graphRefusal`, which is already under the canvas.

**Taking a block out of a frame splices rather than cuts, and that is the whole of `linksWithoutMember`.** Membership is the forward walk from the entry, so cutting a middle member's links would take everything after it out of the frame as well — the operator asked for one block and loses four, in an app with no undo. So each predecessor inside the section is linked to each successor inside it; the entry is the same rule with the loop standing in, its single `repeats` link re-pointed at the first successor in pass order and the rest linked after that one so they stay in. `linksWithMember` is the other direction and reads the frame it is applied to: an empty frame takes the block as its entry, a frame that already lands takes it **beside** the section so the exit lands it too, and anything else links it after the last member. Both write `sectionLink`, which answers the two questions a member link may not be asked — the condition is always *only if it completes*, because a pass has to land what it produced — and which must test the **kind** at both ends before carrying a branch: only a run block has one, and a link handing a branch to an orchestrator or a merge is refused at Save by name, over a control the operator was never shown. It asks at **both** ends, because a run holds one ref: a block already handing its branch on hands it to no second link, and a block already carrying one is handed no second — the fan-in half is what a splice where two branches met, and a fan-in drawn with the Link tool, used to get wrong, into a graph refused as “set to carry on two branches”. A kind picked afterwards is answered the way the mint is: `linksWithKind` takes the branch off every section link of a block that stops being a run, and leaves a link outside a section alone, where the panel shows the switch that set it and the refusal names the block. The panel for a link inside a section has no controls, so what it says is what the operator acts on, and `sectionLinkStatement` says what the link was **drawn** with rather than what `sectionLink` would mint: the server honours an *either way* link inside a section, and the panel that called one refused and said to draw it again swapped the operator's choice for *only if it completes* in silence. Only a link with no condition is called refused, and redrawing that one overwrites nothing.

**A loop's inspector holds what a loop has and nothing else, because a control for a refused field is a trap.** `normalizeNode` refuses the task, the workspace, the folder, the template, the agent and the prompt override **by name**, so a control offering one is a field the operator can fill in and then be refused for, over a value nothing was ever going to read — the editor drops all six for a loop exactly as it already drops them for a merge block. What is left is the pass cap, the spend cap across passes, the board condition, and a **statement** of what it repeats in pass order, which is a read-only list because the canvas is where membership is said. The kind picker does not offer `loop` and does not offer to switch one away; the row states the kind instead. `BlockStatement` is the whole sentence: how many blocks and in what order, at most how many passes, the **worst case in runs with an orchestrator member's fan-out spent again on every pass**, that each pass lands its own work through the exit merge block **named**, and the four endings. Where there is no exit it says so in the danger tone rather than naming a block — a promise about where the operator's work ends up may not be made on a graph that has nowhere to land it. Where the frame is empty it says that too, rather than rendering blank: that is the ordinary state of one whose last member was just deleted, and a panel that looked finished over a graph that cannot be saved is worse than one that says what is missing.

**A loop's six fields are hidden rather than disabled, on the inspector, the canvas card and `/workflows/[id]` alike, and nothing has to come back.** Disabling keeps a control in view for when it applies again, and that is what makes it the usual answer; here it never applies again. Every one of the six is refused by name in `LOOP_IS_TOLD_NOTHING`, so a disabled field would be showing a value the model forbids, and a loop cannot become a run: the kind picker neither offers `loop` nor switches one away, and deleting the frame removes the block rather than turning it back. So the risk that made hiding look expensive, a field that vanishes and has to return with what was typed, has no path to it. A value a loop's `BlockDraft` still carries, from a graph saved before the refusal existed, goes nowhere either: `draftToGraph` drops all six for a loop.

**Put in is the link tool's own two gestures over a second relation, down to `resolveLinkRelease` deciding both releases.** A handle that arms itself at the press, a drag that reaches another block, a click-in-place that arms or disarms, and `handledByPointer` keeping the trailing `click` of a captured sequence from firing the action a second time — copying that shape rather than writing a second one is what keeps the bug `resolveLinkRelease` was written for from being reachable again through a different handle. Two differences are its own. Reaching a block that is **already** in the frame takes it back out, because a member has no control of its own to press Delete on the way a link has its chip, so the gesture that put it in is the gesture that removes it and the handle says which before it is pressed. And a connect leaves the frame **armed**, because a section is several blocks and disarming after each one turns a body of four into four round trips to a control at the top of the frame. Only one tool may be armed at a time: both are "press a handle, then a block", and two armed at once makes the next press on a card ambiguous. `removeBlock` drops a deleted block from every section for the reason it already drops the links to it — a section naming a block that has gone is refused by name at Save.

**The Repeat gesture is a mark and a press, and marking is canvas state rather than the editor's selection.** `selection` names exactly one thing because the inspector shows exactly one thing; `marked` is what lets an operator **see** what Repeat is about to enclose before pressing it, which is the only reason to mark at all — membership is derived, so marking the head alone frames the same section. Every route lands on one handler — `pressBlock`, which marks and then selects — because the press arrives four ways and a gesture written out beside each is a gesture whose copies will stop agreeing: the card's body through `endDrag`, the card's name and the frame's own name through their `click`, and the row below the breakpoint through its tap. It was written twice once, and for as long as it was, the only place a Shift-click marked anything was the 200px name button, while the card around it — nearly all of what an operator aims at — selected and marked nothing. The modifier is read off the event in one place, `extendsMark`, and ⌘ and ctrl count beside Shift; a `PointerEvent` and the `click` Shift+Enter dispatches carry the three alike, so the keyboard reaches the gesture through the control the pointer reaches it through rather than through a key nobody would guess. A press that moved is a drag and marks nothing. An armed Link or Put in still has first claim on a press on a block — `claimArmed` before any of this — and the tap below the breakpoint never extends, because that footer offers no chord and that list draws no mark. A loop is pressed like any other block and so can be marked, which is what makes `resolveRepeat`'s refusal reachable rather than dead: the frame then wears the card's own mark, and pressing Repeat says why a loop cannot go inside one. A press on the bare surface empties it, beside the two armed tools it already put down — a half-made Repeat is the same kind of state, and the alternative is a Repeat still aimed at a section the operator stopped pointing at. A marked block that is then deleted is dropped from the list, or Repeat stays enabled over a selection with nothing in it and `resolveRepeat` frames whatever is left rather than refusing.

**The one refusal this surface states in its own words is the link drawn into a frame, and it is stated at the release.** `linkRefusal` answers it and names the **frame** to link to instead, which is the thing the operator actually meant — a link into the frame runs before the whole loop. `graphRefusal` answers the same thing about the graph, and by the time it does the operator has drawn an arrow, watched it appear, and has to work out which of its two ends the sentence is about. Nothing else is answered here: whether the section lands anything, whether the graph has a cycle and whether a member may be a loop are all the server's, and a second copy would be a second set to keep in step with nothing to notice them drifting. `draftSignature` is what makes the gestures survive leaving the page — it reads `draftToGraph`'s output, so a frame built, a member put in and a member taken out all move `bodyNodeIds` and the links under it, and a frame built and not saved raises the dialog.

**`/workflows/[id]` is the page Run is pressed from, so its loop row must state the same number the editor's statement does.** Three of its sentences were true only while a pass was one run. Its *up to N pass(es), one run each* understated what a press of Run agrees to by the size of the section; passes × members then understated it again by an orchestrator member's fan-out, which is spent **per pass** — a section of one deciding block at 5 over 4 passes is twenty runs, and "4 blocks" says four. Both surfaces read `worstCaseRuns`, which answers **null** rather than guessing where a figure is not stated, since a blank read as zero is an unbounded press of Run approved on the operator's behalf. Its *Starts after* said "nothing — starts immediately" off an empty `waitsFor`, where instantiation deliberately creates none of them: a block the graph never starts, reading as the one that starts first, is the worst way round that can be wrong; it now names the loop that repeats it. And it printed a loop's workspace and task, which the model refuses by name — an empty path under a block that never had one — and a guards badge naming a template the loop never reaches, where every run of a pass is under its **member's** guards.
