# Review blocks and a block's provider

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing a review block (`startReviewBlock`, `driveReviewItem`, `setAside`, `reviewVerdict`, `approvedRunsOf` in `src/lib/workflows.ts`; `src/lib/reviewBlock.ts`), a node's `provider`, `fixRounds` or `verdictSource` (`normalizeNode` in `workflowGraph.ts`, `statusVerdict`, `settleReviewByStatus`, `commandVerdict`, `settleReviewByCommand`, `commandVerdictRefusal`, `planNode`, `planEmittedRun`, `localReady`), or the `workflow_review_items` table. Experimental, on the `local-provider` branch.

**A run block and an orchestrator block may name the provider their runs use, and only a person saving the graph can.** `WorkflowNode.provider` is on the node — refused by name on a merge, loop or review block, which start no run — and `emit_runs` has no field for it, for the fan-out cap's reason: an orchestrator block's runs start with nobody looking, so what they run as is fixed where the graph is saved. The deciding turn itself stays Claude Code whatever the node says; the field is about the runs, not the planner. The run form's rules are applied where each run is created rather than at save, because a template's guards are live: `planNode` refuses a Codex or local block whose guards carry neither a work-cycle nor a time limit (`providerTerminusRefusal`) and drops the template's Claude model for both; `readyToCreate` reads the local sign-in at every creation site — `startWorkflow`, `advanceInstance`, `stepPass`, `createEmitted` — and freezes its model onto the run, blocking the block by name when nobody is signed in; it asks the operator's model list first (`modelOnList`, see `agents-and-templates/templates-and-model-catalogue.md`), which only a Claude run is held to. `startBlockTurn` asks both questions before an orchestrator block's turn is paid for, since a turn that decided on runs that could then never start is a billed decision nothing acts on. A Codex run block naming a saved agent is refused at save, and a Codex block's emission naming one is refused whole — the agent's prompt reaches Claude Code's `--agent` only, so either would be a run that is not the agent it names.

**A review block hands on the branches a frontier model approved, and nothing it set aside.** It takes the runs its incoming links resolve to — the merge block's `InstanceMerge` shape, so an orchestrator's fan-out is covered — and drives each branch through `reviewBlock.ts`: the review assist in `--permission-mode plan`, always asked for a verdict (`startReview`'s `requireVerdict`), read with `parseCertificationVerdict`'s strict rule; an approval passes the branch on, a rejection starts a fix run that carries the same branch on under the continued run's own provider, model, agent and guards — never wider — briefed with the review, up to `fixRounds` (0–3, required, capped at save); a branch still not approved is set aside. What `reviewVerdict` hands on is read from `workflow_review_items`' approved rows, **not** from the runs the block started, because after a fix round the approved run is the fix run and on round zero it is a run some other block started — so `instanceState` and `loopPasses` both override a review block's `emitted` with `approvedRunsOf`. `edgeSatisfied` is not asked of an approved run: the review is the verdict, and a branch whose last run asked for review is still one a frontier model approved. A block that set everything aside is **satisfied with no runs**, not blocked, so the merge behind it settles with "There was no branch to land" and a loop carries on — the operator's decision that set-aside work is ignored rather than fatal. A loop's DONE rung learns this from the member's `workSetAside` rather than from its empty `emitted`, which cannot tell a branch turned down from one that was never there; a branch set aside because its run committed nothing is written `committed_nothing` and does not keep a loop going (`loop-termination.md`). A review block that *failed* — a restart mid-review, the machinery rather than a verdict — blocks what is behind it on either condition, because nothing it was given has been judged. **"Frontier" is a claim the block makes about the reviewer, so the block makes sure of it.** `driveReviewItem` passes `startReview`'s `requireFrontier`: a review of a Claude run on a Haiku (or an id `pricing.ts` cannot place) runs on the Settings default, and when that default is itself not a frontier model nothing is spawned and the branch is set aside "it could not be reviewed: …" — never marked needs-frontier, because no frontier model judged it. Until 2026-10-08 a Haiku run was reviewed on Haiku and the rejection was worded and marked as a frontier model's; the rule and its reasons are in `docs/agent/git-and-review/reviews-and-assists.md`.

**A set-aside branch marks its tasks needs-frontier, and only when a frontier model turned it down.** `setAside` sets `tasks.needs_frontier` on every task linked to the run the branch began with, and comments on each saying why. A review that could not run, a run that committed nothing, a fix the operator stopped — none of those are a judgement on the model, so none of them mark anything (`nextReviewStep`, `afterFixRun`). The mark is what keeps the next loop pass's local block off the task: `readTaskLinks` refuses it in `taskIds` for a local run, which `planEmission` and `propose_run` both reach, and `blockSystemPrompt` tells a local block's turn not to try. The task is then **reopened** — a claim nobody is working, or a tick nobody earned — through `reopenRejectedTask`, the one move off the transition table no actor asks for, and deliberately narrow: only when the run holding it or the run that closed it is one of the rejected runs (the branch's first and last). A task another run holds or closed, one the operator holds, and one the operator dropped, are someone's decision about other work and are left, with the comment saying which. The mark is set before the reopen, so the task is never open and unmarked for a local pass to take. This is the frontier's mark; the one other model that sets the flag is a local run releasing a task with `release_task`, on its own word rather than a review's. `docs/agent/taskboard/operator-only-and-release.md` holds the flag's authority rule and that second door.

**A review block may take its verdict from each run's status instead of a model, and then it bills nothing and marks nothing.** `WorkflowNode.verdictSource` is `{ kind: "model" }`, `{ kind: "status" }` or `{ kind: "command", command }` — an object keyed on `kind`, so a source with settings of its own, as `command`'s line is, is one more member of the union rather than a second field every reader has to pair with this one — and absent or null is `model`, so every graph saved before it keeps the frontier review it was saved to pay for; a reader asks `?.kind === "status"` and never the reverse. It is read on a review block only (`normalizeVerdictSource`), refused when it is not an object or names a kind this app does not have, and dropped unread on every other kind. Under `status`, `startReviewBlock` hands the branches to `settleReviewByStatus` before the instance-budget boundary and settles them in one synchronous pass — no assist starts and nothing is spent, so it is the merge block's free case, and there is no `await` for a halt to land in — and `statusVerdict` approves a `completed` run and sets aside every other ending with a sentence naming it. Two save-time refusals keep that the whole of it. `fixRounds` must be 0, refused rather than coerced because rounds the operator set are billed runs they expect, and there is no review for one to answer; the canvas hides the picker under `status` and `draftToGraph` sends 0, so a hidden control cannot make the block unsavable and the editor's run statement never counts those rounds. And every incoming link must be `on-finish`: behind `on-success`, `edgeSatisfied` blocks the block on the first run that does not complete, which is the stop this verdict exists to remove. The never-ran rule still applies on the link, so a run that never completed a work cycle blocks it either way. A status set-aside is **never needs-frontier and never reopens a task**: no model judged the work, a run that asked for review may have been stopped by anything, and `reopenRejectedTask` is kept for a frontier rejection — a claim a run still holds when it ends is the operator's to release, the board's standing rule (`docs/agent/taskboard/tasks-and-transitions.md`). Nor does it comment on the task; the block's note names the status. It is written with `committed_nothing` 0, since no diff is read, so it counts in `workSetAside` (`loop-termination.md`). What it removes is a pass stopped by an orchestrator's emitted run that ended `needs-review` — the merge's `on-success` link blocked on it, and `memberCompleted` does not read emitted runs — where a *run member* that ends that way still stops a loop on the not-completed rung, whatever is behind it.

**A review block may take its verdict from a verify command saved on it, and then exit 0 is the whole of an approval.** Under `{ kind: "command", command }` the block runs that line once per branch and nothing else: `settleReviewByCommand`, one branch at a time, each through `verifyBranchForReview` — Land's own `verifyTreeVerdict` and `verifyInSlot`, so in the run's own slot, clean and on its branch, held from a later run, as the child uid, bounded by `VERIFY_TIMEOUT_MS` (`isolation-and-landing/land-verify-and-deliver.md`). `commandVerdict` approves a pass and sets aside everything else, and *everything* is the point: a non-zero exit, a signal, a timeout and a command that never ran — no slot, a slot a later run took, uncommitted edits, a branch that moved under it — are all set aside, because "could not check" read as a pass hands the merge a branch nothing looked at — and `commandVerdict` asks `ran` beside `passed`, since `landVerdict`'s pass for a blank command never ran. Its one structural cost is Land's: a slot `allocateSlotPath` has since handed to a later run is refused, so an orchestrator fanning out past `maxConcurrentRuns` in one repository leaves its early branches set aside unchecked. No fresh worktree is cut, for `verifyTreeVerdict`'s reason (no dependency tree to test with); board task 5e2c7ffa holds the decision. A command that ran writes how it ended on the note's first line and the tail of its output on the lines after, which the instance page shows under the branch's row; `reviewBlockSummary` names each set-aside branch by its note's first line, so the block's note stays one line a branch rather than carrying up to `VERIFY_TAIL_BYTES` of each. The rest is the status source's, for its reasons: no model, no spend and so no budget boundary; never needs-frontier, never a reopen and no task comment, since a red suite is no verdict on the model; `committed_nothing` 0, so each set-aside holds a loop's DONE off; and `fixRounds` must be 0 — refused rather than coerced — because nothing briefs a fix run with the failure yet, which is a later decision. Unlike `status` it takes either link: behind `on-success` it judges completed runs only, behind `on-finish` every run that ran a cycle, and both are things an operator may mean. It awaits, so it asks `reviewStillOpen` after every await; a halt does not signal a command already running — it is bounded by the timeout and what it says is discarded — and the shutdown's sweep of `runningVerifyChildren` ends one at exit. The line is validated at save by `parseVerifyCommand` and is a person's to write and never a model's; `security/path-containment-and-spawn-argv.md` holds that rule and where it is enforced.

**Its fix runs are the instance's runs and its reviews' cost is the block's.** A fix run is recorded under the review block with the `#`-suffixed id an orchestrator's emitted runs use, so a halt stops it, the instance budget guard covers it at its cycle boundary, and a loop pass's id prefix finds it. The reviews are assists — `run_reviews` rows, queued behind `maxConcurrentAssists` by waiting while `assistBudgetFull()` rather than failing, and by waiting again when `startReview` comes back `busy` — and what each costs lands on the block's `cost_usd` **as it ends** (`bankReviewSpend`), not when the block does, because the block row is all the instance total and its guard read: counted at the end, a block's reviews were invisible to the guard for as long as it worked and lost outright when a halt ended it first. A failed review that reported nothing is counted in `cost_unreported`, a deciding turn's rule. The block's start is an instance-budget boundary, `enforceInstanceBudgetForBlock` — always, where a merge block's is conditional, since every branch it is handed is a billed review. `worstCaseRuns` counts a review member's worst case as `fixRounds` fix runs for every branch the pass can cut, so the editor, the saved page and the `MAX_LOOP_RUNS` refusal state one figure, and the refusal names the rounds beside an orchestrator's fan-out.

**A full assist queue is waited out at both doors a review passes, because the first is a check and not a claim.** Every branch of a block passes `assistBudgetFull()` in the same tick, before any of them has written the row that fills a slot, and a chat turn or another block can take one while `runDiff` reads the diff — so `startReview`'s own door finds the queue full. Until 2026-10-06 that refusal was written `set-aside` as "it could not be reviewed", and four approvable branches at the default cap of two came out two approved, two set aside, the merge behind landing half the work over a queue. `startReview` now marks a refusal by the process budget `busy`, decided by `assistDoor` at the moment it refused rather than inferred by asking `assistBudgetFull()` again afterwards, which reads a later moment — a slot taken during the window scan would turn a spent window into a wait. Only the budget is `busy`: a spent window or install limit is an answer no wait would change and still sets the branch aside, and the shutdown refusal outranks the budget and is never `busy`. A halt or a shutdown ends either wait at the top of `driveReviewItem`'s loop, because `reviewStillOpen` answers false to both, leaving the block for the halt or `reconcileBlocksOnBoot` to settle. Serialising a block's review starts was the alternative and was not taken: it removes only the siblings from the race, and a chat turn or another block would still need this wait. The install-wide hold is waited out at the first door the same way, and holds the block at its claim before that; `run-lifecycle/fleet-stop-hold-and-set-aside.md` says why.

**It is one async function per block, the merge block's shape.** Claimed `thinking` by `claimBlock`, polling what it waits on at `MERGE_POLL_MS`, and giving up the moment the block is no longer `thinking` — which is how a halt reaches it, and why `driveReviewItem` asks that after **every** `await` rather than at the top of each poll: asked only there, a rejection read after the halt started a fix run into the stopped workflow, a member no stop and no guard then reached. `startReview`'s `stillWanted` carries the question past its own awaits to the moment before the child is spawned. The one wait a halt does not cut short is a review's own, because the halt signals that reviewer and what it reports on the way out is still the instance's money. Settled through `finishMergeBlock`'s latch with a `reviewBlockSummary` note. A restart kills the loop driving it, so `reconcileBlocksOnBoot` fails a `thinking` review block with its own sentence — and counts a review it killed in `cost_unreported` — and nothing it had not yet approved is handed on.
