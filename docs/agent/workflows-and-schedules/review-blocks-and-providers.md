# Review blocks and a block's provider

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing a review block (`startReviewBlock`, `driveReviewItem`, `setAside`, `reviewVerdict`, `approvedRunsOf` in `src/lib/workflows.ts`; `src/lib/reviewBlock.ts`), a node's `provider` or `fixRounds` (`normalizeNode` in `workflowGraph.ts`, `planNode`, `planEmittedRun`, `localReady`), or the `workflow_review_items` table. Experimental, on the `local-provider` branch.

**A run block and an orchestrator block may name the provider their runs use, and only a person saving the graph can.** `WorkflowNode.provider` is on the node — refused by name on a merge, loop or review block, which start no run — and `emit_runs` has no field for it, for the fan-out cap's reason: an orchestrator block's runs start with nobody looking, so what they run as is fixed where the graph is saved. The deciding turn itself stays Claude Code whatever the node says; the field is about the runs, not the planner. The run form's rules are applied where each run is created rather than at save, because a template's guards are live: `planNode` refuses a Codex or local block whose guards carry neither a work-cycle nor a time limit (`providerTerminusRefusal`) and drops the template's Claude model for both; `localReady` reads the local sign-in at every creation site — `startWorkflow`, `advanceInstance`, `stepPass`, `createEmitted` — and freezes its model onto the run, blocking the block by name when nobody is signed in. `startBlockTurn` asks both questions before an orchestrator block's turn is paid for, since a turn that decided on runs that could then never start is a billed decision nothing acts on. A Codex run block naming a saved agent is refused at save, and a Codex block's emission naming one is refused whole — the agent's prompt reaches Claude Code's `--agent` only, so either would be a run that is not the agent it names.

**A review block hands on the branches a frontier model approved, and nothing it set aside.** It takes the runs its incoming links resolve to — the merge block's `InstanceMerge` shape, so an orchestrator's fan-out is covered — and drives each branch through `reviewBlock.ts`: the review assist in `--permission-mode plan`, always asked for a verdict (`startReview`'s `requireVerdict`), read with `parseCertificationVerdict`'s strict rule; an approval passes the branch on, a rejection starts a fix run that carries the same branch on under the continued run's own provider, model, agent and guards — never wider — briefed with the review, up to `fixRounds` (0–3, required, capped at save); a branch still not approved is set aside. What `reviewVerdict` hands on is read from `workflow_review_items`' approved rows, **not** from the runs the block started, because after a fix round the approved run is the fix run and on round zero it is a run some other block started — so `instanceState` and `loopPasses` both override a review block's `emitted` with `approvedRunsOf`. `edgeSatisfied` is not asked of an approved run: the review is the verdict, and a branch whose last run asked for review is still one a frontier model approved. A block that set everything aside is **satisfied with no runs**, not blocked, so the merge behind it settles with "There was no branch to land" and a loop carries on — the operator's decision that set-aside work is ignored rather than fatal. A loop's DONE rung learns this from the member's `workSetAside` rather than from its empty `emitted`, which cannot tell a branch turned down from one that was never there; a branch set aside because its run committed nothing is written `committed_nothing` and does not keep a loop going (`loop-termination.md`). A review block that *failed* — a restart mid-review, the machinery rather than a verdict — blocks what is behind it on either condition, because nothing it was given has been judged.

**A set-aside branch marks its tasks needs-frontier, and only when a frontier model turned it down.** `setAside` sets `tasks.needs_frontier` on every task linked to the run the branch began with, and comments on each saying why. A review that could not run, a run that committed nothing, a fix the operator stopped — none of those are a judgement on the model, so none of them mark anything (`nextReviewStep`, `afterFixRun`). The mark is what keeps the next loop pass's local block off the task: `readTaskLinks` refuses it in `taskIds` for a local run, which `planEmission` and `propose_run` both reach, and `blockSystemPrompt` tells a local block's turn not to try. The task is then **reopened** — a claim nobody is working, or a tick nobody earned — through `reopenRejectedTask`, the one move off the transition table no actor asks for, and deliberately narrow: only when the run holding it or the run that closed it is one of the rejected runs (the branch's first and last). A task another run holds or closed, one the operator holds, and one the operator dropped, are someone's decision about other work and are left, with the comment saying which. The mark is set before the reopen, so the task is never open and unmarked for a local pass to take. `docs/agent/taskboard/operator-only-and-release.md` holds the flag's authority rule.

**Its fix runs are the instance's runs and its reviews' cost is the block's.** A fix run is recorded under the review block with the `#`-suffixed id an orchestrator's emitted runs use, so a halt stops it, the instance budget guard covers it at its cycle boundary, and a loop pass's id prefix finds it. The reviews are assists — `run_reviews` rows, queued behind `maxConcurrentAssists` by waiting while `assistBudgetFull()` rather than failing — and what they cost lands on the block's `cost_usd`, which the instance total reads. `worstCaseRuns` counts a review member's worst case as `fixRounds` fix runs for every branch the pass can cut, so the editor, the saved page and the `MAX_LOOP_RUNS` refusal state one figure.

**It is one async function per block, the merge block's shape.** Claimed `thinking` by `claimBlock`, polling what it waits on at `MERGE_POLL_MS`, and giving up the moment the block is no longer `thinking` — which is how a halt reaches it — and settled through `finishMergeBlock`'s latch with a `reviewBlockSummary` note. A restart kills the loop driving it, so `reconcileBlocksOnBoot` fails a `thinking` review block with its own sentence, and nothing it had not yet approved is handed on.
