# Picking up a stuck workflow run

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `pickUpsOf`, the pick-up doors that call it, or `startRefusals` and `liveInstancesOf` in `src/lib/workflows.ts`. How an instance is halted, read as a status and ended is in [instance-lifecycle.md](instance-lifecycle.md).

**A stuck workflow run is picked up one named obstacle at a time, and never through a halt.** `pickUpsOf` lists what is holding an open instance up — a run whose ending wrote something off behind it (inside a loop, only in the pass that stopped it), a merge or deliver block that failed, an orchestrator block whose deciding turn failed having decided nothing, and a stopped loop whose latest pass a dry run of `planInstanceStep` says would now go through, or that failed on reading its board with nothing blocked, its pass settled whole or never opened — and each has its own door: `leaveRunBehind`, `retryMergeBlock` (and `retryDeliverBlock`, its sibling), `retryOrchestratorBlock`, `resumeLoop`. The last two share a pass's rule with the merge: inside a loop only the pass that stopped it is offered, and a pass's failed block is the obstacle to name, so the loop's own pick-up waits until it is gone. What the deciding turn's retry keeps, clears and refuses is in [orchestrator-and-merge-blocks.md](orchestrator-and-merge-blocks.md). Resuming a run is deliberately none of them: it is `reopenRun` on the run's own page, and `reviveBlockedBlocks` now carries a root inside a pass to that pass and its loop, because a pass member's id names no node of the graph and the graph walk alone left a resumed pass stopped for ever — measured on the Sep 25 Dockrac run, whose resumed run completed under a loop that never moved. **Leaving a run behind is a column on the membership row, never a status**: `left_behind_at` leaves the run's own ending exactly as it was, and every reader of the graph's state honours it the same way — `instanceState` and `passState` drop it from an orchestrator block's `emitted`, `edgeVerdict` answers a run block's edge as satisfied resolving to no run, and `planLoopPass` counts it neither as unfinished nor as DONE — so a merge behind it does **not** land its branch. A reader that missed it is a pick-up that does nothing visibly or one that lands the branch the operator chose not to. It is refused for a run another *run* waits on through `run_deps`, because `releasableRuns` knows nothing of workflows and a waiver half the scheduler honoured would still block. Reopening a pass is refused by `loopPassRefusal` — the loop must be `failed` rather than having ended on its own terms, the pass must be its latest, nothing behind the loop may have left `waiting`, its graph must carry a pass cap and its board must be countable, because a pick-up is for letting the loop carry on and one whose board cannot be counted cannot: `advanceLoop` would carry the reopened pass to its landing and then fail the loop again on the same sentence, so the operator is told what to fix before a pass is billed rather than after. A halted instance is refused whole, `reviveBlockedDependents`' rule. Every pick-up only reopens the question: the next advance re-plans the pass and reads every rung of `planLoopPass`, so the caps end a loop where they always would have.

**A pick-up is refused while another press of the same workflow works in a folder it shares — an authorisation rule, the one `startWorkflow` holds at a press, held at every door that brings a press back.** A pick-up turns a `finished` or `blocked` instance into a `started` one as surely as Run starts one, and a newer press into its folder is exactly what [nodes-and-instantiation.md](nodes-and-instantiation.md)'s gate admits while the older one is idle: measured 2026-10-16 on 02f3b764, a deciding turn's retry on press 1 answered `{"ok":true}` with press 2 live in the same folder, two presses' deciding turns on one repository. So `openInstanceFor`, the shared gate of `resumeLoop`, `leaveRunBehind`, `retryMergeBlock`/`retryDeliverBlock` and `retryOrchestratorBlock`, asks `pickUpSharedFolderRefusal` after the halt, and `reopenRun` asks the same question of a member through `memberPickUpRefusal`, right after `haltedWorkflowOf`. It is `sharedFolderRefusal` over the *other* live presses (this one being live is no conflict with itself) and this instance's own graph copy, whose chosen folder was applied when it was pressed; it is asked of an instance already live too, because two live presses sharing a folder is the state the rule exists to have none of. The sentence is that function's, in its `"pick-up"` wording: the press being picked up may be the older one and cannot choose another folder, so "an earlier press" and "choose a folder" would both be untrue. `pickUpsOf` puts the same sentence on every entry, ahead of each door's own refusal and in the door's order, so the page names it rather than offering a button the route refuses. `reopenRun` reaches `workflows.ts` with a `require` at the call: a static import is a cycle, since `workflows.ts` imports `orchestrator.ts`, and the `import()` the release paths use would answer after the run had been queued. The run page offers Try again as before and renders the refusal when pressed; `RunDTO` does not carry it.

**The page that presses Run states the refusal to press it again before it is pressed, per folder, and the instance it links is found in both halves of the graph.** `/workflows/[id]` disables Run while `startRefusals` holds an entry for the folder the picker would send (null on a workflow that saves none), shows that entry's sentence — `startWorkflow`'s own, from `sharedFolderRefusal` — and links its `instanceId`; picking a folder no live press works in turns Run back on. `startWorkflow` still refuses on its own account: the page reads the same fact one poll earlier, so a press that races the poll earns the 400 it always did. `liveInstancesOf` asks the run rows *and* the block ledger, through the two status lists the counts read, because a press is not always going through a live run — a block still deciding, or a loop between two passes, keeps it going with no run in flight anywhere, and a lookup over runs alone would let a second press into its folder and leave the notice nothing to open. It lists the newest first, and the newest press sharing a folder is the one named. `liveRunCount` still totals every press, for the list's "N in flight"; it no longer decides Run.
