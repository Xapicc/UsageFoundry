# Halting, status and pick-ups of a workflow instance

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `stopInstance`, `haltPlan`, `reconcileHaltsOnBoot`, `instanceStatus`, `pickUpsOf` or `setLoopStopAfter` in `src/lib/workflows.ts`.

**A workflow instance is halted through one door, and the door is closed before anything is signalled.** `stopInstance` is that door: an operator's control and a tripped instance guard both call it and differ *only* in the recorded cause, because a second implementation of "which members does this take down" is a second chance to miss one, and a missed member goes on spending under a page that says the workflow is stopped. The instance is marked `stopping` by an UPDATE guarded on `status='started'` — the closed door and the idempotence in one statement, a second stop changing no rows rather than running a second kill ladder over children that are already dying — and from there to the last member there is **no `await`**, the property `createRun`'s folder claim already documents for the same reason. Every kind of member is covered at once and each keeps the machinery it already had: `running`, `queued` and `paused` go through `stopRun` and its existing branches, so there is still exactly one way to signal a child and the `SIGINT`-first ladder still buys a cycle the chance to report its own cost; a `waiting` member is written `blocked` — what this app already writes for a run refused before its first work cycle, and the true thing to say, which also keeps it out of `REOPENABLE`, since picking one link of a halted chain back up would start it on work that never happened; a member already terminal is **left alone**, because a `completed` row rewritten as stopped destroys the record of work that landed and nothing on the page afterwards says it happened; and a node whose `createRun` never ran is not a member at all, so it is never created. `haltPlan` is that whole decision, pure and unit-tested, for the reason `releasableRuns` and `landRefusal` are. **Waiting members are blocked before any other member is touched**, because stopping a run releases its dependents and a dependent released a moment before the halt reached it would be admitted, promoted and spawned — a member starting *because* the workflow was stopped. Stopping a queued member can still promote another queued member inside the same turn; that is harmless and deliberately not designed around, since `stopRun` re-reads the row and `startRun`'s pre-spawn checkpoint sees the interrupt before any child is spawned, costing a transcript scan rather than a billed cycle. The halt never removes a checkout, never touches a branch and never commits: uncommitted work stays in its slot with its own branch checked out, where `slotIsDirty` keeps the next run out and `commitRefusal` — which already settled whose work is in a slot — still decides whether it may be committed. Queued `merge_queue` rows for those runs are cancelled and one in flight is left to finish, exactly as `cancelBatch` has it. The instance records that it was stopped, by what and when, and the member's own reason distinguishes the three endings on sight: halted with its workflow, halted by that workflow's budget guard, or stopped on its own run page (`stopRun`'s unchanged default). `stopped` is **derived** rather than stored — `stopping` plus no live member — because a signalled child takes seconds to die and nothing would run a second pass after a restart; `reconcileHaltsOnBoot` exists only for the crash *inside* the walk, where `reconcileOnBoot`'s deliberate exception for a recently `paused` row would otherwise leave the sweeper to re-queue a member of a stopped workflow. A halt is terminal: there is no pause and resume for an instance — **and no way back in through a member either**. `reopenRun` refuses a run whose instance is `stopping`, naming the workflow, and `reviveBlockedDependents` leaves those runs out of its candidate set; `haltedWorkflowOf` is the one condition both read, so a run refused on its own page cannot be woken from the page in front of it, and it tests `stopping` alone because that is the only stored value — `stopped` is the same row read later. `reviveBlockedBlocks` is the third reader and the one that does **not** share it, deliberately: it walks the ledger rather than the runs, and it asks the positive question — is this instance still `started` — because the row it would rewrite is also what `startWorkflow`'s own rollback writes onto a `failed` instance, and reviving one of those would restart half a graph that was deliberately never built. Stricter than "not halted", which is the direction that costs nothing. Neither the status nor `REOPENABLE` is the gate any more: a halted `waiting` member is `blocked` with no `work_dir`, which is exactly the shape `reopenRun`'s `waitingAgain` branch accepts and exactly the row the revive selects, so without the membership condition **Try again** — or reopening the stopped run in front of it — put agents back to work under an instance the page reads as "Stopped", with the instance guard unable to stop them because it acts only on a `started` one. `RunDTO.haltedWorkflow` carries the same answer to the run page, which declines to offer the button rather than let the operator find out by pressing it. **Orchestrator blocks go first, before any member is touched**, and that is the waiting-member rule sharpened: a block does not merely get *released* by a stop, it creates runs, so one left `thinking` while the walk ran could emit into a workflow being taken down and every run it started would be a member the halt had already walked past. A `waiting` block becomes `blocked` and a `thinking` one `failed` — that turn was billed, and saying it never ran would hide the spend already on its row — both written before the child is signalled, so the guarded UPDATEs in `emitBlockRuns` and `settleBlock` refuse whatever the dying turn still tries to *do* — its status, its reply, its emission — and **never its bill**. The settle that carries a halted turn's cost always arrives after that latch has closed, so `settleBlock` and `finishMergeBlock` add the cost columns in a statement of their own, unlatched; inside the latch, every halted turn read as a measured `$0.00` and the instance total dropped it. A review block's reviewers are billed children too and are not in `blockTurns`: `haltBlocks` signals each running one through `assistChild`, on the same ladder, `memberTally` counts it live until its row settles — so the instance reads `stopping` rather than `stopped` while one is dying, by the definition above — and `driveReviewItem` waits it out to bank what it reported.

**Four of an instance's six readings are derived, and `started` is not a word for a press of Run that is over.** `workflow_instances.status` records what has been *done to* an instance — rolled back at creation, or a halt closing its door — and never what its members have got to, which is a fact about the runs and the ledger. Nothing would write that second fact: no pass runs when the last member settles, and after a restart nothing would run one at all, which is the reason `stopped` was derived before this and the same reason `finished` and `blocked` are now. So `instanceStatus` is the whole decision, pure and unit-tested for `haltPlan`'s reason, over one tally taken across **both** halves of the graph — `stopping`/`stopped` are one halted row either side of its last live member, and `started`/`finished`/`blocked` are one unhalted row: still working, reached its end, or had part of it written off because something in front of it satisfied nothing. A halt outranks the members, because what ended a press of Run is the headline and a member says the rest on its own row; and `finished` is a claim about the *graph* rather than the work, since how a member ended is on the member's own row and a word here that said otherwise would report a failed run as work that landed. None of it is stored, so every query that reads the column is untouched — `advanceInstances`' own SQL, `fleet.ts`'s `startedInstances`, `guardInstance`, `bootBlockPlan`'s input, `haltedWorkflowOf`. What is **not** untouched is every site that acts on the object: each tested `status === "started"` when that was the only word for an unhalted row, and each would silently close a door that is open the moment two more words exist — so they ask `instanceIsOpen` instead, named once rather than repeated. `settleBlock` is the sharp one and the reason this is a rule rather than a tidy-up: the UPDATE that settles a block runs immediately before it, so if that block was the last live member the instance reads `finished` on the very next line, and a test for `started` there would drop the runs the turn had just decided on — a fan-out billed for and never started, with the block's own row saying it emitted them. A stop is the one place the new words are genuinely *reachable*, and `haltPlan` already had the answer: an instance with nothing live falls through to "every block has already finished", which is the true thing to say and the thing a status-shaped test would have replaced with "already stopping". **The reading is shown and the page acts on one thing only: whether to keep asking.** The instance page wears the list's badge and clause (`INSTANCE_OUTCOME_LABEL`, `instanceOutcomeDetail` in `format.ts`, the same ones `/workflows/[id]` draws), and `instanceCanMove` stands its poll down for `stopped` and `failed` alone — a halt is the door nothing re-opens and a rollback never had a member — while `finished` and `blocked` keep polling, because a pick-up on one member turns either back into `started`. Re-arming a page that stood down is a reload; the Stop and pick-up presses write their own answer into the page.

**A stuck workflow run is picked up one named obstacle at a time, and never through a halt.** `pickUpsOf` lists what is holding an open instance up — a run whose ending wrote something off behind it (inside a loop, only in the pass that stopped it), a merge or deliver block that failed, an orchestrator block whose deciding turn failed having decided nothing, and a stopped loop whose latest pass a dry run of `planInstanceStep` says would now go through — and each has its own door: `leaveRunBehind`, `retryMergeBlock` (and `retryDeliverBlock`, its sibling), `retryOrchestratorBlock`, `resumeLoop`. The last two share a pass's rule with the merge: inside a loop only the pass that stopped it is offered, and a pass's failed block is the obstacle to name, so the loop's own pick-up waits until it is gone. What the deciding turn's retry keeps, clears and refuses is in [orchestrator-and-merge-blocks.md](orchestrator-and-merge-blocks.md). Resuming a run is deliberately none of them: it is `reopenRun` on the run's own page, and `reviveBlockedBlocks` now carries a root inside a pass to that pass and its loop, because a pass member's id names no node of the graph and the graph walk alone left a resumed pass stopped for ever — measured on the Sep 25 Dockrac run, whose resumed run completed under a loop that never moved. **Leaving a run behind is a column on the membership row, never a status**: `left_behind_at` leaves the run's own ending exactly as it was, and every reader of the graph's state honours it the same way — `instanceState` and `passState` drop it from an orchestrator block's `emitted`, `edgeVerdict` answers a run block's edge as satisfied resolving to no run, and `planLoopPass` counts it neither as unfinished nor as DONE — so a merge behind it does **not** land its branch. A reader that missed it is a pick-up that does nothing visibly or one that lands the branch the operator chose not to. It is refused for a run another *run* waits on through `run_deps`, because `releasableRuns` knows nothing of workflows and a waiver half the scheduler honoured would still block. Reopening a pass is refused by `loopPassRefusal` — the loop must be `failed` rather than having ended on its own terms, the pass must be its latest, nothing behind the loop may have left `waiting`, and its board must be countable, because a pick-up is for letting the loop carry on and one whose board cannot be counted cannot: `advanceLoop` would carry the reopened pass to its landing and then fail the loop again on the same sentence, so the operator is told what to fix before a pass is billed rather than after. A halted instance is refused whole, `reviveBlockedDependents`' rule. Every pick-up only reopens the question: the next advance re-plans the pass and reads every rung of `planLoopPass`, so the caps end a loop where they always would have.

**The page that presses Run states the refusal to press it again before it is pressed, per folder, and the instance it links is found in both halves of the graph.** `/workflows/[id]` disables Run while `startRefusals` holds an entry for the folder the picker would send (null on a workflow that saves none), shows that entry's sentence — `startWorkflow`'s own, from `sharedFolderRefusal` — and links its `instanceId`; picking a folder no live press works in turns Run back on. `startWorkflow` still refuses on its own account: the page reads the same fact one poll earlier, so a press that races the poll earns the 400 it always did. `liveInstancesOf` asks the run rows *and* the block ledger, through the two status lists the counts read, because a press is not always going through a live run — a block still deciding, or a loop between two passes, keeps it going with no run in flight anywhere, and a lookup over runs alone would let a second press into its folder and leave the notice nothing to open. It lists the newest first, and the newest press sharing a folder is the one named. `liveRunCount` still totals every press, for the list's "N in flight"; it no longer decides Run.

**Ending a loop after its pass is not a second halt, and it never reaches `stopInstance`.** An instance is halted through one door, closed before anything is signalled; "Stop after this pass" signals nothing, writes no member `blocked` or `failed`, and closes no door — it records a number on the loop's ledger row (`stop_after_pass`) and the pass in flight finishes and lands. Routing it through `stopInstance` would have been the opposite of what it is for, since a halt leaves the in-flight pass's branches unlanded: 7 of the 26 settled loops measured on this install ended in an operator stop, and in each the merge block was stopped before it landed anything. Stop wins when both are pressed. A halt writes the loop `failed` and the instance `stopping`, and `loopStopAfterRefusal` refuses a press on either — so a *Keep going* pressed after Stop cannot read as having revived a loop the operator took down, and `settleLoop`'s latch on `looping` keeps a request that raced the halt from rewriting the halt's wording. The page's poll needs nothing new: the instance stays `started` while the pass runs, so it keeps asking, and the press writes its own answer into the page as Stop and the pick-ups do. The instance guard is unchanged and still halts through `stopInstance` during the last pass.

**A held gate leaves the instance `started`, and it is the operator's to end — Continue lets it through, Stop halts through the same door as every other halt.** Reading a gate as a seventh word beside the six was considered and not done, for the reason the six are what they are: `instanceStatus` is a function of one tally, and a held gate is a live `waiting` row, so it already reads `started` — "something is still live" — and every site that asks `instanceIsOpen` (the second press of Run, `liveInstancesOf`, the budget guard, the poll, a schedule's overlap rule, `bootBlockPlan`) already treats the instance as open for exactly the reason it should. A new word would be a new entry in `INSTANCE_OUTCOME_LABEL`, `INSTANCE_OUTCOME_TONE` and `INSTANCE_CAN_MOVE` (all three `Record`s, so the compiler would find them) and a decision at every `=== "started"`, to say less than the block row already says. What changes is the page: the block's DTO carries `heldAt`, `isHeldGate` is the one reader of it, and a reached gate wears "waiting for you" in the warn tone, has a card of its own above the pick-ups ("Waiting for you", with **Continue** and **Stop all**), and puts "· N waiting for you" after the heading clause. **That card is not a pick-up and `pickUpsOf` does not list it.** A pick-up is something that went wrong and can be stepped past; a held gate has gone right, and listing it there would put the decision it was drawn for among the obstacles. **Stop is not a second door.** The button opens the page's existing sheet and posts to `…/stop`; `haltPlan` counts a `waiting` gate in `liveBlocks`, so a run waiting only at a gate is live and a stop acts, and `haltBlocks` writes every gate — held or not yet reached — `blocked` with a sentence saying nobody let it through, which keeps it out of `reviveBlockedBlocks` like every other halted waiting block. **Continue is refused, with its reason, on every state it cannot be honoured in** (`gateContinueRefusal`, pure): a gate the run has not reached, one already let through, one a halt wrote off, and any run that is not open, because a bare 409 reads as a button that does not work. **Nothing ends a held gate but a person**: there is no timeout and no budget or hold that releases or closes one, because a timer that closed it would be the unattended decision the block exists to prevent. The price is that an instance can sit `started` for as long as nobody looks — a second press of Run into a folder it shares is refused meanwhile, and a schedule's later windows are skipped when its press would share one (see [schedules.md](schedules.md)) — and it is stated on the schedule card rather than absorbed. The heading's "N block(s) working" counts a gate and the waiting blocks behind it as live, as it did for any waiting block; the clause beside it is what says which of them is a person.
