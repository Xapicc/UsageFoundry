# What planInstanceStep decides for an edge

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `planInstanceStep` or `edgeVerdict` in `src/lib/workflows.ts`, or the `restartClosed` reading they ask: what a block that emits nothing, an `on-failure` link and a run a restart closed out hold back. What a node may hold and how a workflow is instantiated is in [nodes-and-instantiation.md](nodes-and-instantiation.md).

**A block that emits nothing blocks what is behind it, and that is a decision rather than a fallout.** `planInstanceStep` is `releasableRuns` for the half of a graph that is not runs yet, pure and unit-tested for the same two silent failures, and it reads `edgeSatisfied`'s rule one level up: a dependency that did no work satisfies nothing. A block behind a fan-out exists to review it, land it or follow it up; started with nothing in front of it, it spends a billed cycle finding that out, where `blocked` costs nothing and names the block that decided there was nothing to do. A block that decided on runs none of which could be created blocks what is behind it just the same, but `edgeVerdict` says so rather than blaming the decision — `InstanceNodeState.block` carries the decided count and the block's notes for that sentence, from `instanceState` and `loopPasses` alike, since both feed the one reader. Nodes behind an orchestrator block are **not created** at `startWorkflow` — their edges would name runs a model has not decided on yet — so each holds a `waiting` row in `workflow_instance_blocks` instead, which costs nothing for the reason `waiting` costs nothing one level down: no folder, no checkout, no place in the queue. A node is created only once every edge into it is *satisfied* rather than merely resolvable, so its edges are recorded on a run `admitDependencies` then re-checks, and a node that becomes a run gives up its ledger row so it is never in both tables. The cascade is the same fixed point `releasableRuns` uses, so every link gets its own sentence naming the one in front of it. `advanceInstances` is called from `releaseDependents` — one place rather than the five call sites that would have to be kept in step — and it is synchronous end to end for `createRun`'s reason, with a guarded UPDATE claiming each turn so two overlapping passes cannot both spawn one. A restart closes out **every** unsettled block of an instance it left nothing alive in, not only the ones behind a turn in flight: `on-finish` is satisfied by a run that did a cycle and then died with the container, so a block left `waiting` would be released into an unattended agent hours after anyone asked for it — which is `reconcileOnBoot`'s rule for a queued run. **Unless a member survived that same boot**, and that is `reconcileOnBoot`'s own exception rather than a second one: a `paused` run inside `settings.resumeGraceHours` is kept, because it is a run the operator started in a mode chosen precisely so it would carry on across a restart. Every premise above fails for the blocks behind it — nothing they are waiting for was closed out, the sweeper *will* wake it, and the agent the next advance starts is the one already being paid for and waited on. Closing them out anyway wrote off the tail of a live graph, under a sentence claiming the run in front of them had been closed out by the restart while it was parked and about to resume. So the question is asked per instance: `bootBlockPlan` is that decision, pure and unit-tested for `haltPlan`'s reason, and it reads `LIVE_STATUSES` rather than testing for `paused`, so what survives is decided in one place. It tests `started` **positively** rather than merely excluding a halt: a `stopping` instance's blocks still come down whatever its members are doing, and a `failed` one is `startWorkflow`'s own rollback, which wrote every other block off in the same pass — reviving half of either is a graph nobody finished building, started again. Ordering is what makes the survivors readable rather than guessed at — `src/instrumentation.ts` runs `reconcileOnBoot` first — and a spared block is decided later by `planInstanceStep`, off what is true when the member settles.

**An `on-failure` link is drawn only out of a run block and only outside a loop, and a node on the branch it did not take is `not-needed` in the ledger as it is in `runs`.** `planInstanceStep` has a third verdict beside `block` for it, `notNeeded`, and `edgeVerdict` reads a run block's run through `edgeSatisfied` and `notNeededReason` — the same two functions `releasableRuns` asks — so a node deferred in the ledger and a node created up front as a `waiting` run are passed over alike, and a run that was `stopped` blocks the node with a sentence saying a stop is not a failure. Every kind of predecessor whose own row is `not-needed` hands that on along every edge (`passedOverBehind`), and a blocked verdict on another edge outranks it, `releasableRuns`' order. `BlockStatus` gains `not-needed` for the ledger's half: settled, never started, counted by `memberTally` as neither live nor blocked, so an instance whose only unrun members were passed over reads `finished` rather than `blocked`; `reviveGraphDependents` wakes one as it wakes a blocked one, and `startedBehind` reads it as not started. `normalizeWorkflowInput` refuses the link out of an orchestrator, merge, deliver, review or loop block by name: each settles in words of its own — a merge that did not land everything, a turn that decided nothing, a review that set work aside, a loop that stopped on a pass — and which of those a fixer should start on is a decision nobody has made. It refuses one with either end inside a section, because a pass would have a member that is neither unfinished nor DONE and `planLoopPass` has no reading for it; `stepPass` still writes a `notNeeded` verdict rather than leaving the member `waiting` for ever. An orchestrator block's own `emit_runs` keeps the two older conditions (`EMITTED_EDGES`): the block behind it waits for every run it emitted, and has no way to wait for one that was not needed. The canvas offers the condition on a link out of a run block and keeps it on a link that already carries it, so Save can say why.

**A run a restart closed out blocks every edge out of it until it is picked up, and what it holds back is revived rather than failed.** `edgeVerdict` asks `restartClosed` ahead of the edge test, on either condition, for a run node's run and for every run an orchestrator block emitted — `releasableRuns`' rule, read through the same `restartClosedSql`. `InstanceNodeState.run` and `emitted` are `ReleaseState` for it, required for `refundedCycles`' reason, built by `instanceState`, `loopPasses` and `approvedRunsOf` alike. The boot's closing-out was not enough on its own. A block written off at the boot is revived through `reviveBlockedBlocks` by picking up *any* member it can be reached from, and the next advance then read the restart's `stopped`, with a cycle counted, as `on-finish` satisfied for the members nobody had picked up. Each kind of block behind it met that differently. A deferred run node hit `createRun`'s refusal and went `blocked`, which is right by accident. A loop's first pass member hit the same refusal, which by reading the code leaves the loop `failed`, where the revive does not reach. Orchestrator, merge and review blocks create no run, so they went ahead. In `shutdown.test.ts` a merge block behind two closed-out runs was claimed and handed both branches by the release pass the shutdown's own ending ran, before anybody picked anything up. Blocked, never pending and never failed: nothing obliges anybody to pick the run up, and `blocked` is the one ending the pick-up revives, so the sentence names the run and says that. A run the operator left behind is waived ahead of the check, since carrying on without it is a decision already taken. A review block's approved runs are not asked, `reviewVerdict`'s rule: the review is the verdict on them.
