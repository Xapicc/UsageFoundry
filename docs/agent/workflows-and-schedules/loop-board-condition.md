# A loop's board condition: when it is read, and what it counts

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `loopBoardCount`, `advanceLoop`'s board read or `planLoopPass`'s `boardCounts` in `src/lib/workflows.ts`, `boardThresholds` in `src/lib/apiTypes.ts`, or `normalizeBoardCondition`, `resolveBoardFolder` and `folderRefusal`'s loop branch in `src/lib/workflowGraph.ts`. The other ways a loop ends — what the agents said, the two caps, a requested stop — are in [loop-termination.md](loop-termination.md).

**A loop's board condition is a third terminus and the only one that is not a fact about a pass, which is why it alone is read before the first pass and never while one is still working.** `stopWhenTasks` sits beside `maxPasses` and `maxLoopCostUSD` and is the same kind of number both of those are — it can only ever end the loop earlier, it reaches no guard, `evaluateInstanceBudget` does not read it, and nothing a model emits can widen it. What it is not is a fact about a settled pass: the others are read off the pass that just ended, where this one is read off the board at the moment it is asked, so `planInstanceStep` routes a loop's **first** pass through `advanceLoop` rather than straight to a first pass. That indirection is the whole feature — a loop pointed at a project that is already clear must start no run at all, and the two caps can only refuse a second one. Its place in `planLoopPass`'s order is load-bearing in both directions: **below `reportedDone`**, because an agent that said the work is finished outranks a board that has not caught up with it and reporting the board would send somebody to look at a backlog that is about to be clear; and **above the two caps**, because a clear board is the loop *finishing* and the stop reason is what an operator reads to decide whether to raise a cap. The function stays pure: the counts arrive as `boardCounts`, null together with the condition, exactly as `spentGuardUSD` arrives beside `maxCostUSD`. `loopBoardCount` is the reader, and it is the one place here that can fail **silently** — `tasks.folder` holds the absolute path `resolveTaskFolder` proved at filing and `listTasks` matches the column exactly, where a node holds a path within its mount, so a folder passed through unresolved counts zero for ever and stops every loop before its first pass with nothing anywhere saying why; it therefore goes through the board's own resolver, and `loopBoardCount.test.ts` files a task through the ordinary door and counts it back. **The same resolver is asked before anything exists**: `folderRefusal` resolves each loop's condition through `resolveBoardFolder`, the function `countBoardCondition` counts through, at every save door and in `startWorkflow` after `withChosenFolder` and before the instance row, and refuses by the loop's name — otherwise a board folder that does not resolve (a project renamed or deleted since the save, or one a chat or the API typed) saves, starts, runs and bills every block in front of the loop, and only then fails it at its first check. Past those doors, what the run-time check meets is a folder that went while the instance was working: one that will not resolve **fails** the loop rather than reading as zero, which is the one answer that would end it — but only once the latest pass has settled. `advanceLoop` steps an unsettled pass before it reads the board at all, asking `planLoopPass`'s own first rung ahead of the read, because `advanceInstances` runs after every terminal run anywhere in the app and a folder an agent in the pass renamed, or a mount that blipped, would otherwise fail the loop **mid-pass**: the block behind it is decided on a loop whose runs are still in its folders — released on `on-finish` — and the pass's unreleased members stay `waiting` with nothing ever to step them, so its merge never lands and the instance stays open until it is stopped. The check for an instance blob whose loop carries no `maxPasses` sits behind the same rung for the same reason. **And it fails the loop only when nothing else would end it**: a board that cannot be read is left out of the decision rather than ahead of it, so `advanceLoop` asks `planLoopPass` with no condition and fails the loop only if the answer is another pass. DONE and *Stop after this pass* rank above the board and a cap reached ends the loop whichever way the board reads, so failing any of those protected nothing — and it turned an ending that releases the `on-success` block behind the loop into one that writes it off, in a pass with nothing blocked for `pickUpsOf` to offer, so the instance sat `blocked` with nothing on its page to press. What the rule still fails is offered, though: `passWouldProceed` answers yes for a pass with nothing blocked when it settled whole and every member completed — the pass was not what failed the loop, the read between two passes was — and `loopPassRefusal` says whether that read can succeed yet, so the page shows the board's own sentence while the folder is gone and a plain *carry on* once it is back, and the press reopens the loop and the written-off block behind it, re-reads the board before pass 2 and ends on its rung, releasing that block, if it is clear by then. A loop that failed before pass 1, on the board read in front of it or on a graph with no cap, is offered the same way as pass 0, because with no pass to press the instance sat `blocked` with nothing to press. It goes back to `waiting` and **not** `looping`: the scheduler's release is what hands pass 1's entry the runs the loop was released behind and whether their branch continues, `advanceLoop` is given those by the release alone, and a loop put straight to `looping` starts its entry after nothing, on a fresh branch, with nothing on the page to say so. The press advances once: `advanceInstance` plans again when a loop settles at its release ([loop-passes.md](loop-passes.md)), so the block behind a loop that is clear or fails at once is decided by that same advance. `loopPassRefusal` refuses a graph with no `maxPasses` by `advanceLoop`'s own sentence, ahead of the board as `advanceLoop` reads them, and a loop that repeats no section is not offered at all, since it would fail the same way again — nor is the press accepted, because `resumeLoop` asks `passWouldProceed` as `pickUpsOf` does, and a press answered ok for a loop the page offers nothing for would release it and fail it again on the same sentence. `done` and `dropped` are refused at save **by name** on the same reasoning inverted — those counts only ever grow, so "at most N" against one holds at the first check — and `claimed` is offered but is not the default, because a claim here is a record and not a lease, so one task left claimed by a dead run holds the loop open for every pass it is allowed. Absent is off, and that reading is what keeps every graph saved before the field existed behaving exactly as it did.

**The condition's numbers are an `or`, its project is one folder unless told otherwise, and a condition saved as one number is read in exactly one place.** Three claims, each with a failure behind it. `thresholds` holds up to five `{ priority, atMost }` pairs and `planLoopPass` stops on **any** of them, never all: an all-of reading keeps a loop going on a board nobody thought was full, and a loop is billing a whole run per pass, so the condition that ends it earlier is the one to prefer when the two readings disagree. Each threshold may name a priority or `any`, no priority twice — a duplicate is refused at save rather than merged, because two numbers for one priority is an `or` in which the larger silently decides and the smaller is a line the operator wrote that can never fire. The stop reason names the threshold that was met, its priority and both figures, because five lines in "the board is clear enough" cannot be read back to a decision. `loopBoardCount` counts **every** priority and not the ones the thresholds happen to name: a reading that could be missing a figure the decision needs is a decision that can only skip the threshold it has no number for, and a skipped threshold is a loop that runs past its own ending. `includeSubfolders` defaults to **false**, which is how the board itself groups a project — `…/terraServe` and `…/terraServe/docs` are two projects on that page and must stay two here — and when it is on the match is `folder = ?` OR a `LIKE` on the canonical path **with the separator appended** and `%`/`_` escaped the way `likeNeedle` does in `orchestrator.ts`; without that separator `…/UsageFoundryWeb` is counted for `…/UsageFoundry`, silently and in the direction that keeps a loop running, since a project counted too full never reaches the number it was told to stop at. A condition carrying `atMost` and no `thresholds` reads as one `any` threshold with that number, and `boardThresholds` in `apiTypes.ts` is the **only** place that reading lives: nothing re-normalises a stored graph — `rowToWorkflow` and `rowToInstance` both hand the blob's nodes back as they were written — so a loop saved or started before thresholds existed reaches `planLoopPass`, `loopBoardCount`, `normalizeBoardCondition` and the editor still carrying the old shape, and four opinions about it would be four chances to refuse a workflow nobody changed. Its `?.` on a field the type says is always there is load-bearing for the same reason `advanceLoop` asks `typeof node.maxPasses !== "number"`. The editor's project picker offers the mount-and-folder pairs as single choices with `fmtTaskPlace`'s own labels, so the loop and the board name a project identically, and the figure beside it is the **server's** reading through `loopBoardCount` — answered by `/api/workflows/validate` beside the verdict rather than behind it, because a graph being drawn is refused for most of the time it is being drawn, and because anything this surface counted for itself would be comparing a path within a mount against a canonical absolute one, which is the defect that reader exists to prevent.
