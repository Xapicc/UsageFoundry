# The instance budget and the instance total

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `evaluateInstanceBudget` or `normalizeInstanceBudget` in `src/lib/budget.ts`, or `enforceInstanceBudget`, `instanceSpend` and `blockSpendReading` in `src/lib/workflows.ts`.

**A workflow instance carries its own budget, and it is checked between blocks rather than during one.** `run_templates` bounds one block; ten blocks under a $5 block limit is a $50 workflow, and `InstanceBudgetPolicy` — `maxInstanceCostUSD` plus the two window fractions, all nullable, `null`/`""`/`0` all meaning off — is what bounds the graph. It goes through `evaluateInstanceBudget`, which is the *same* `BudgetVerdict`, the same `BudgetStopCode` vocabulary and the same `readWindowGuard` reading as `evaluateBudget`, because an instance limit with its own words for "no ceiling configured" would be a second set of budget rules to keep in step. `readWindowGuard` is that shared half and it exists to make one thing unmissable: `fraction` answers "is there a reading at all" and `guardFraction` answers "is it past the threshold". Those are **different fields for different reasons** — `fraction` is what `windows.ts` fills from the provider's own percentage when `planUsage.ts` answered, so a window can carry a perfectly good reading with nothing typed into Settings and refusing it as `no_ceiling` would disable the guard on a stock install, while `guardFraction` is what charges an unpriced model the fallback rate so the guard does not quietly stop existing the week a new model ships — and, on a window the provider answered for, what takes the worst of that percentage and the derived reading, so a cached figure cannot authorise every cycle started inside one refresh interval. Both are null together, by construction in `buildWindow` and again in `makeWindow`. What it does **not** share with `evaluateBudget` is that function's body, for two reasons that are the whole design: an instance needs **no monotone terminus** — the run loop requires one because the loop manufactures its own next unit of work, where an instance is a finite graph created in one pass whose members each already carry a terminus, so all three limits are legally null together and the `no_terminus` refusal has no analogue — and an instance **never parks**, because parking is a decision about a run that yields its folder and keeps its checkout for the same conversation, and an instance holds neither. Enforcement is **between nodes**, and at two kinds of boundary rather than one. `enforceInstanceBudget` is called from `startRun`'s pre-cycle guard off the snapshot that check has just read; `enforceInstanceBudgetAfterMember` is called from `startRun`'s `finally`, once the status write has put that member's spend on its row. The second is what makes the limit reachable at all: every other call site in this app is "before something spends", and a block with `maxIterations: 1` — `normalizePolicy`'s answer when a template says nothing — reaches the pre-cycle guard exactly once, before its only cycle, while the pass that would have seen that cycle's cost is refused on `iterations` and `break`s out *ahead* of the instance check. So a graph of single-cycle blocks released together compared its limit with zero once per member and never again. It is fired-and-forgotten rather than awaited, because `releaseDependents` and `promoteQueued` are synchronous by requirement and a transcript scan in front of them would break the folder claim's one-event-loop-turn atomicity; nothing escapes by going first, since a member promoted in the meantime meets the pre-cycle check before any child is spawned. An orchestrator block is the third boundary — `enforceInstanceBudgetForBlock`, same door, same verdict vocabulary, called from `startBlockTurn` before the child is spawned, and from `startReviewBlock` before a review is, and from an auto-resolving merge block's start. Without it a graph of nothing but deciding blocks would carry a workflow-wide limit that never fires, since nothing in it ever reaches a *cycle* boundary. There is deliberately **no live mode**, and the copy on the editor and the instance page says so in words: `liveGuardTick` reads one run's policy against that run's own progress and every code on `LIVE_ENFORCEABLE_CODES` is a fact about a run, so extending it would kill every member mid-cycle and turn each one's measured `result` cost into a reconciled estimate, for a bound that is already one cycle in the ordinary case. The cost of not doing it is stated rather than absorbed — a block already working carries on until it or another block reaches a boundary, so the total can overshoot by up to one work cycle per block running at the time, and concurrency multiplies it. What used to be the limiting case, a graph whose blocks all start at once with one cycle each, is what the post-member boundary exists for: it had no boundary between its blocks at all and the guard never fired, where now the first block to finish is one. Both the editor and the README say so. `settings.maxConcurrentRuns` is what bounds that multiplier, and what that lever is and is not has to be read exactly: it bounds a **count of cycles in flight**, so it bounds `N × one cycle` and nothing more, and it was only ever a bound on *money* because `buildArgs` carries `--max-budget-usd` and bounds the one cycle inside the CLI — before that, a cap on N bounded N × unbounded, which is unbounded. The two are one guard read together, and the same sentence holds one level down for `maxConcurrentAssists`: it bounds how many turns exist, where `settings.chatTurnBudgetUSD` inside the CLI is what bounds each. A tripped verdict calls `stopInstance` with `{ kind: "guard" }` rather than re-deciding which members to take down, and `startRun`'s pre-spawn checkpoint picks up the resulting interrupt like any other. `INSTANCE_ENFORCEABLE_CODES` is the whitelist, and it is `LIVE_ENFORCEABLE_CODES`'s reasoning applied to the one code that is about configuration rather than spending: `no_ceiling` is refused **at the door** by `startWorkflow`, which has an error channel, and is deliberately not acted on afterwards. On a stock install the reading behind `fraction` is the provider's own percentage, discarded after an hour without a fresh answer, so halting on its absence would turn an unreachable Anthropic host into every fraction-guarded workflow stopped and every one of their blocks killed mid-cycle. It is not ignored either — the run whose check found it logs that the guard had nothing to read, the same answer this app already gives a live spending limit whose telemetry never arrived. **And because nothing acts on it, `evaluateInstanceBudget` holds it rather than returning it where it is found**: returning on the first unreadable window ended the check order early, so an instance with a real 5-hour reading and no weekly one had its 5-hour guard switched off silently for every block. The verdict is returned only once every readable guard has passed, `??=` keeping the weekly wording in front — `evaluateBudget`'s shape one level down, and the same argument.

**The instance total is a fourth reading, and the door telemetry reaches it through is the same one, widened by one caller.** `instanceSpend` returns two figures and never one. `spentUSD` is the sum of the members' `runs.spent_usd` — a floor, since a cycle in flight has emitted no `result` and contributes zero for its whole duration — and is what the instance page draws as the meter's solid fill. **A member whose provider reports no cost is skipped rather than added, and counted.** `codex exec` returns token counts and no money, so the run loop withholds its `+=` and leaves `runs.spent_usd` at 0: a null in disguise, which the runs list, the run page and the MCP tools all already answer as `—` or `null`. `sumMemberSpend` reads `providerReportsSpend` for that, and adding the zero anyway would be arithmetically identical and still wrong — `$0.00` across a graph of Codex members is a measurement claim nobody made. `memberSpendReading` is the same reading for that member's own Spent cell. `spentGuardUSD` adds each member's `spent_usd_est` and, for `running` members only, `telemetrySpendSince(runId, active_started_at)`; it is what `evaluateInstanceBudget` compares, and it is drawn as the hatched band past the fill, the same rendering an unpriced model's gap already gets. It never reaches `runs.spent_usd`, `buildSnapshot()` or any dashboard meter, and it is not a fifth cost source. The telemetry door was "one run, its own current cycle, its own live guard"; it is now also "each member, its own current cycle, the instance guard" — same function, same per-run and per-cycle bound, same `*Guard*` destination, and that widening is written down here rather than absorbed. `runs.active_started_at` is what made it readable from outside `startRun`'s frame: the other half of the fact `active_iteration` already carries, stamped and cleared in exactly the three places that column is, and read only for a `running` row for the reason `fmtCycleInFlight` refuses it on any other status. Both figures also carry what this instance's **blocks** paid a model for — a deciding turn, a merge's resolutions, a review block's reviews, each banked as it ends — out of `workflow_instance_blocks.cost_usd`, and `review` is a paying kind beside `orchestrator` and `merge`. That is not a fifth source and not a widening of the telemetry door: it is the CLI's own `total_cost_usd` for a turn that ended, the same authority `runs.spent_usd` has, so it is measured rather than estimated and belongs in the display figure as well as the guard's. **A turn that never reported has the same three-column shape a run does, for the same reason.** `turnResultOf` returns a failure with no `costUSD` at all when the child produced no readable `result` event — killed, crashed or timed out — and the tokens it burned first were still billed; `blockTurnSpend` splits that verdict so `cost_usd` only ever takes a figure a CLI reported, `cost_usd_est` takes our own price for the usage the stream did show, and `cost_unreported` counts the turn — including one a halt killed, since those columns are written outside `settleBlock`'s status latch, and one a restart killed, which `reconcileBlocksOnBoot` counts. A turn refused before anything was spawned settles with `costUSD: 0`, a known zero rather than a gap. `addBlockSpend` then puts `cost_usd_est` in `spentGuardUSD` and nowhere else, beside `spent_usd_est` and the telemetry reading, so the estimate reaches `evaluateInstanceBudget` without ever widening the figure the page calls measured. `cost_unreported` is a column rather than a test for a zero because both readings can legitimately be 0 — a turn killed before its first assistant event leaves no usage to price either — and it is what `instanceSpend` returns as `unmeasured`, alongside `subjects` — the members and paying blocks it is counted out of, so the page can state coverage rather than a bare number. Non-zero `unmeasured` means the total is what the *rest* of the graph reported, from either cause: a block turn that died before saying, or a member on a provider that never says. The page then drops the word "measured", says how many of how many the money covers, and `blockSpendReading` gives that block's Spent cell `null` rather than `$0.00`, which is the runs list's rule about a measurement nobody made applied one page over. It never touches `runs.spent_usd`, `buildSnapshot()` or a dashboard meter — the split that matters is display-versus-guard, and this is neither side of it, it is simply money the press of Run spent that no member run's row records. Where a figure has no denominator — no `maxInstanceCostUSD` — the meter is the hatched indeterminate bar, never an empty one: an instance whose share of a limit is unknown and one that has spent nothing must not look alike.

**A person sets an instance budget, and there is nothing on the wire that could.** It lives on the saved workflow, is normalized by `normalizeInstanceBudget` (total and idempotent, `normalizePolicy`'s rules), and is **copied onto the instance** at `startWorkflow` — the treatment the graph blob already gets, so editing the workflow cannot move the guard under a graph already running. `POST /api/workflows/[id]/run` still reads no body, there is no override argument on `startWorkflow`, and no route writes `workflow_instances.instance_budget`, which is the strongest form of "an orchestrator block must not raise its own instance's budget": there is nothing to raise it with. The route's one new job is to `await currentSnapshot()` and hand it over, because `startWorkflow` must stay synchronous from its first `createRun` to its last and the door check needs a real reading — a fraction guard with no ceiling behind it, or a window already past the guard, is a 400 with a sentence rather than a graph that halts before its first block does anything. `normalizeWorkflowInput` deliberately does **not** refuse the missing ceiling at *save*, the one place it departs from its own "refuse at save what instantiation refuses" rule: a ceiling is a Settings value that can be typed at any moment, so such a graph is not unstartable, only unstartable today. The editor warns beside the field.
