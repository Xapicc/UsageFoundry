# The two kinds of section

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `handsOnBranch`, `sectionLands` or `sectionTail` in `workflowGraph.ts`, the member and exit rules in `loopBodyRefusal`, the merge rule in `graphRefusal`, the `needBranch` probe in `startWorkflow`, or the isolation reading in `canvasGraph.ts`. The landing kind's own rules are in [loop-sections.md](loop-sections.md).

**A section is a landing section or an in-folder section, decided by its members, and the two are mixed in one place only: a landing section's tail.** It **lands** when some member hands on a branch: a run whose guards isolate, an orchestrator whose template isolates (its emitted runs take its guards), or any review (it reviews only isolated work). It is **in-folder** when none does. `handsOnBranch(kind, isolates)` is the one table of kinds and `sectionLands(members, isolates)` the one question; `isolates` is the caller's answer because `loopBodyRefusal` reads the template table while `startWorkflow` reads the guards it has already planned. A landing section is held to every rule in `loop-sections.md`, and may end in the in-folder tail below. An in-folder section is held to the shape alone — one way in, one way out, and any member kind a section allows as the single sink except a gate (below) — because each pass's commits are already in the folder the next pass reads, which is the whole of what the merge block gave the other kind. Nothing is carried between passes in either.

**Mixed is refused rather than half supported, and that is the line and not an omission.** A merge landing a branch into a checkout the same pass is also editing in place is two writers on one tree with nothing recording which pass put what there, and nothing was designed for it — not the landing rules, not the pass-ownership hold. The refusal is where a run or orchestrator member is asked about isolation, and it names the member that makes the section a landing one (`brancher`, the first member in section order that hands on a branch; a review is never first, because the isolated sources it needs come before it) **and where its checkout comes from** (`isolationBecause`: its template by name, or the default guards in Settings), because the operator who flips a block's "Work in the folder chosen at Run" switch has changed *which* folder, not whether it gets a checkout of its own, and the sentence has to point at the template. The ways out are the operator's to choose: give this block guards that isolate, make every block work in the folder, **or** move it after the section's last merge block — the last offered only where there is a merge and the block is not already behind it. **An orchestrator is asked as a run is** (board task `496e54fb`): its deciding turn writes nothing, but its emitted runs take its guards and edit the folder in place while the merge lands, so the exemption it had by name was the hole in this line. A merge has no guards and is the one kind not asked. What stays refused is every in-folder member that is not in the tail: before a merge, beside a member that hands on a branch (a fork), or followed by one.

**A landing section may end in an in-folder tail.** The tail is `sectionTail`: the members that come after **every** merge block of the section (strict descendants of each), when none of them hands on a branch. When a section has one, its exit may be the tail's single last block instead of a merge; every other landing rule stays — each branch cut before the tail is handed on to a merge, each run member before it isolates, one exit. A merge in front of a tail "lands the branches" and the tail's exit "ends the pass"; the sentence for a second sink says "where the pass ends" and not "a branch nothing lands" when every sink is in the tail. `worstCaseRuns` is untouched: it reads kinds and never guards (the operator's shape is 10 + 1 + 1 a pass).

**Why the tail is safe, and what that rests on.** The tail starts only after the merges in front of it have settled, and the next pass is created only once the whole pass has. Both are measured in the tree and neither is stated where the code is. `startMergeBlock` is fire and forget and the queue polls every two seconds, but the merge block's ledger row is `thinking` from the claim until `awaitBatch` has seen every queue row of its batch terminal, and only then does `finishMergeBlock` write `emitted` or `failed`; `edgeVerdict` reads `waiting` and `thinking` as pending, so nothing behind a merge is released while it is landing. `memberSettled` reads the same statuses, and a tail run is a member, so `passSettled` is false until it is terminal. `loopMergeOwnership.test.ts` ("a block behind a pass's merge block") drives it against the real queue and the operator's checkout: the run behind the merge does not exist while the row is `thinking`, and exists only after the branch is in `main`. **Both conditions are needed**: a block behind one merge and not the other is released while the other may be landing, which is why the tail is behind *every* merge.

**The tail must leave the folder clean, and the loop refuses a pass over what it left rather than committing for it.** The paragraph above is the tail being safe while it edits; this is the other direction. Nothing in the app commits an in-folder run's work — the doors that commit are the operator's, `commitPending` (a press) and a landing's own merge — so an edit, or a file git has not seen, that the tail's agent did not commit is still in the operator's tree when the next pass would open. That costs twice: the pass's isolated runs cut their branches from the last commit and never see it, and its merge block is refused over it at `planItem` in `mergeQueue.ts` ("The checkout has uncommitted changes"), after the runs were created and billed, which fails the loop on "did not land everything it produced". `advanceLoop` therefore asks `tailLeftDirt` before it opens any pass after the first, ahead of `openPass`, so nothing is created or billed. It reads the section's tail with `sectionTail(…, () => false)` — which blocks come after every merge does not depend on any guard — takes the folder each tail run recorded (`runs.folder`, where it actually worked; for an orchestrator member, those of its `emitted` runs, since it has no run of its own and its emitted runs are what edit the folder), and runs `git status --porcelain` there by the merge queue's own rule: non-empty or unreadable is dirty, an untracked file counts, an ignored one does not. A dirty folder fails the loop with a sentence that names the tail and the first paths and says to commit or discard. It is a synchronous `gitSync`, asked only where something is decided — once per pass boundary and once per press of *Carry on* (`resumeLoop`, through `loopPassDirt`) — and only for a section that has a tail; nothing that polls asks it, and the page offers *Carry on* for such a loop without having read the folder. When that is read, and why the press and not the page, is [loop-termination.md](loop-termination.md)'s "Whether a failed loop can carry on is read twice, and only the press reads the folder". **Committing for the tail was the other way and was not taken**: a commit on the operator's own branch that nobody pressed is a departure no other door makes (`commitToLeave` in `land.ts` commits nothing — it reads where a branch points), and the message, the files staged and whose identity signs it would all become this loop's to decide. Refusing leaves the tail's own prompt responsible for what it leaves. A tail that leaves the tree clean is not asked anything, and a section with no tail is not asked at all: the operator's own edit in front of a pass there is still refused at the merge, as before. `loopMergeOwnership.test.ts` drives two passes through the real queue with a tail that edits a tracked file, one that leaves an untracked file, and one that leaves nothing.

**A link out of a merge may not be `on-finish` on any path to the tail, and the sentence says why.** A merge that failed still *finished*, so `on-finish` releases the block behind it; `on-success` does not, and the pass stops on "did not land everything it produced". What a failed land leaves in the folder is `unwind`'s answer in `land.ts`: usually `restored`, and the dirty-checkout case — the operator's own edit, which the queue refuses to merge over — leaves the tree exactly as it was (pinned in the same test file, with the tail blocked behind it). But `unwind` can also report `mid-merge` (a MERGE_HEAD it could not abort) or `changed` (the branch's work written and not taken back), and a tail run released over either would edit on top of it. **That second pair is read from the code and was not reproduced**, so the refusal stands on the code's own admission that it can happen. A link between two tail blocks may say either condition: it is the merge's failure that can leave the folder unfit.

**Any path, not only a direct merge-to-tail link.** The rule is asked of the link *out of the merge* (`unsafeLink` in `loopBodyRefusal`): it refuses an `on-finish` link from a merge whose target is the tail or reaches it. A gate in between does not make it safe, because a gate is held and not skipped: with the merge failed and the link `on-finish`, `planInstanceStep` holds the gate, a person presses Continue, and `gateContinueRefusal` asks nothing about the gate's predecessors, so the tail is released over what the failure left. Another merge in between is the same, `m1 → m2 → tail` with the first link `on-finish`: `m2` lands onto a folder `m1` may have left mid-merge. That one is mostly covered at runtime, since a merge halts on a dirty or mid-merge checkout, but Save does not lean on it. Once the link out of the merge is `on-success`, nothing behind it starts over a failed merge, so a later link on the path — gate to tail, say — may say either condition. The sentence is the same one with the block it names changed: the link's own target, and, where that target is not itself in the tail, "the blocks it leads to at the end of the section". `workflows.test.ts` pins the direct link, the gate, the second merge, and the `on-success` forms of the last two that must still save.

**A merge block drawn at the end of an in-folder section is answered by `graphRefusal`'s merge rule, and a second refusal for it in `loopBodyRefusal` would be wrong.** The merge rule runs before the section rules and asks every producer in front of a merge to isolate, so the operator reads "leaves no branch for “M” to land" — and, when the merge is a section member (`owners.get`), both ways out in the same sentence: remove the merge, or give the block guards that isolate. The section rules are never reached, so the two cannot contradict each other; add one and the operator reads two sentences about one block. The "ends in N places" sentence is kind-aware for the same reason: it names a branch nothing lands only for a landing section.

**A gate is never a section's exit, and the general rule is what says so.** `graphRefusal`'s "gate with nothing after it" rule runs ahead of the section rules and asks every gate for a link out, inside a section or not, so `l → a → g` and `o → m → tail → g` are refused by that sentence and `loopBodyRefusal` has no sentence of its own for it — the arrangement the merge at the end of an in-folder section has, above. The exemption was weighed and not made, though the runtime would carry it: a gate at the exit is a `waiting` row, `memberSettled` reads it as unsettled, and so `planLoopPass` waits on its first rung. That is what is wrong with it. The pass does not settle until a person presses Continue, so a pass that reported DONE, or was the last the cap allows, still waits on the press before the loop may end, while a gate at the entry (`repeats → gate → work`, [loop-sections.md](loop-sections.md)) is a row of a pass the loop has already decided to open, and holds every pass that will run and none that will not. `workflows.test.ts` pins the refusal for an in-folder section and for a tail, and the entry form beside it.

**Nothing in a pass assumes the exit is a merge block, and the loop holds no claim on a folder.** Read through `planLoopPass`, `memberSettled`, `memberCompleted`, `openPass` and `stepPass`: a member settles on its run's status or its ledger row, a pass completes on `completed`/`emitted`, and the one merge-specific arm is the sentence for a failed pass (`broken.kind === "merge"`), which a section with no merge never reaches. `loopStillRepeating` in `land.ts` is keyed on the **run** of a pass's member and guards the doors that move or destroy a *branch*; an in-folder run has none, so it holds nothing and never refuses to start one. The loop takes no claim of its own — `workflows.ts` never calls `claimCheckout`, which is a writer claim on a run's checkout — so what serialises in-folder runs on one folder is occupancy by the runs themselves. A `waiting` member holds no folder, pass N+1's entry is created only once every member of pass N is terminal, and members of one pass that share a folder queue behind each other like any two runs. `loopSection.test.ts` drives two passes of an in-folder section to the cap and to DONE with no merge row written.

**`startWorkflow` probes the run members of landing sections that cut a branch, and nothing else.** A landing member needs a worktree, which only the disk can answer: a subdirectory of a repository, submodules and a repository with no commits are refused by name. An in-folder member — a whole in-folder section's, or a landing section's tail — cuts no branch, so the probe would refuse a press with nothing wrong; `folderRefusal`, asked just before, has already established that the folder resolves, which is all it needs. The probe reads the plans' `isolate` rather than the template table or a list of tail members, so what is asked is what the member will run under. `loopSection.test.ts` holds it with a landing head and a flat tail in a plain directory.

**The editor reads isolation off what its page already holds, and keeps its own copy of the kind table.** `canvasGraph.ts` may not import `workflowGraph.ts`, so `blockIsolates`, `sectionLands`, `sectionTail`, `sectionExit` and `sectionShape` (the one reading the frame and the inspector both take, so they cannot disagree) copy the server's; they must agree with it, and `canvasGraph.test.ts` checks the graphs the editor mints against `normalizeWorkflowInput`. The knowledge is the templates list and `chatDefaultGuards.isolate` from the settings read the editor already makes — no fetch of its own — and **absent means isolating** in every pure function, so a caller that passes nothing, and the editor before settings answer, read a section as landing, which is what every surface said before in-folder sections existed. It decides more than the "ends the pass" label. `sectionLink` mints the first link out of a block carrying its branch, and the server refuses a hand-over at a block with no checkout, over a section panel that has no switch to take it off; so in-folder blocks get links that carry none, `linksWithTemplate` clears the branch when a template change makes a block flat (as `linksWithKind` does for a kind change), and the link panel says no branch is handed over.

**The inspector says which of the two a block is, from what the editor already holds.** Beside the guards picker one line reads "Works in a checkout of its own" or "Works directly in the folder" (the runs it starts, for an orchestrator), from `blockIsolates` over the templates list and `chatDefaultGuards.isolate`. It exists because the "Work in the folder chosen at Run" switch beside it reads as the answer and is not. A link the editor mints from a merge into a tail block carries no branch, and `canvasGraph.test.ts` checks the shape and four near-misses (the default guards at the end, a flat run before the merge, a flat run followed by an isolating run, a block behind one merge and not the other) against `normalizeWorkflowInput`. The link panel does not refuse an `on-finish` link out of a merge toward the tail itself; the graph check under the canvas does.
