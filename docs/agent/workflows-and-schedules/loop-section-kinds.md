# The two kinds of section

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `handsOnBranch` or `sectionLands` in `workflowGraph.ts`, the member and exit rules in `loopBodyRefusal`, the merge rule in `graphRefusal`, the `needBranch` probe in `startWorkflow`, or the isolation reading in `canvasGraph.ts`. The landing kind's own rules are in [loop-sections.md](loop-sections.md).

**A section is a landing section or an in-folder section, decided by its members, and the two are never mixed.** It **lands** when some member hands on a branch: a run whose guards isolate, an orchestrator whose template isolates (its emitted runs take its guards), or any review (it reviews only isolated work). It is **in-folder** when none does. `handsOnBranch(kind, isolates)` is the one table of kinds and `sectionLands(members, isolates)` the one question; `isolates` is the caller's answer because `loopBodyRefusal` reads the template table while `startWorkflow` reads the guards it has already planned. A landing section is held to every rule in `loop-sections.md`. An in-folder section is held to the shape alone — one way in, one way out, any member kind a section allows as the single sink — because each pass's commits are already in the folder the next pass reads, which is the whole of what the merge block gave the other kind. Nothing is carried between passes in either.

**Mixed is refused rather than half supported, and that is the line and not an omission.** A merge landing a branch into a checkout the same pass is also editing in place is two writers on one tree with nothing recording which pass put what there, and nothing was designed for it — not the landing rules, not the pass-ownership hold. The refusal is where a run member is asked about isolation, and it names the member that makes the section a landing one (`brancher`, the first member in section order that hands on a branch; a review is never first, because the isolated sources it needs come before it) because both ways out — give this block guards that isolate, or make every block work in the folder — are the operator's to choose. **One mixed shape still saves:** an orchestrator on a template that works in the folder inside a landing section, because it spends nothing on disk itself and `workflows.test.ts` holds it as exempt by name. Its emitted runs edit the folder in place while the merge lands, so it is the hole in this line; close it deliberately, not in passing.

**A merge block drawn at the end of an in-folder section is answered by `graphRefusal`'s merge rule, and a second refusal for it in `loopBodyRefusal` would be wrong.** The merge rule runs before the section rules and asks every producer in front of a merge to isolate, so the operator reads "leaves no branch for “M” to land" — and, when the merge is a section member (`owners.get`), both ways out in the same sentence: remove the merge, or give the block guards that isolate. The section rules are never reached, so the two cannot contradict each other; add one and the operator reads two sentences about one block. The "ends in N places" sentence is kind-aware for the same reason: it names a branch nothing lands only for a landing section.

**Nothing in a pass assumes the exit is a merge block, and the loop holds no claim on a folder.** Read through `planLoopPass`, `memberSettled`, `memberCompleted`, `openPass` and `stepPass`: a member settles on its run's status or its ledger row, a pass completes on `completed`/`emitted`, and the one merge-specific arm is the sentence for a failed pass (`broken.kind === "merge"`), which a section with no merge never reaches. `loopStillRepeating` in `land.ts` is keyed on the **run** of a pass's member and guards the doors that move or destroy a *branch*; an in-folder run has none, so it holds nothing and never refuses to start one. The loop takes no claim of its own — `workflows.ts` never calls `claimCheckout`, which is a writer claim on a run's checkout — so what serialises in-folder runs on one folder is occupancy by the runs themselves. A `waiting` member holds no folder, pass N+1's entry is created only once every member of pass N is terminal, and members of one pass that share a folder queue behind each other like any two runs. `loopSection.test.ts` drives two passes of an in-folder section to the cap and to DONE with no merge row written.

**`startWorkflow` probes the run members of landing sections only.** A landing member needs a worktree, which only the disk can answer: a subdirectory of a repository, submodules and a repository with no commits are refused by name. An in-folder member cuts no branch, so the probe would refuse a press with nothing wrong; `folderRefusal`, asked just before, has already established that the folder resolves, which is all it needs. The probe reads the plans' `isolate` rather than the template table, so what is asked is what the member will run under.

**The editor reads isolation off what its page already holds, and keeps its own copy of the kind table.** `canvasGraph.ts` may not import `workflowGraph.ts`, so `blockIsolates`, `sectionLands` and `sectionExit` copy the server's; they must agree with it, and `canvasGraph.test.ts` checks the graphs the editor mints against `normalizeWorkflowInput`. The knowledge is the templates list and `chatDefaultGuards.isolate` from the settings read the editor already makes — no fetch of its own — and **absent means isolating** in every pure function, so a caller that passes nothing, and the editor before settings answer, read a section as landing, which is what every surface said before in-folder sections existed. It decides more than the "ends the pass" label. `sectionLink` mints the first link out of a block carrying its branch, and the server refuses a hand-over at a block with no checkout, over a section panel that has no switch to take it off; so in-folder blocks get links that carry none, `linksWithTemplate` clears the branch when a template change makes a block flat (as `linksWithKind` does for a kind change), and the link panel says no branch is handed over.
