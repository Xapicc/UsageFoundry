# When a loop stops: exit conditions, caps and the board condition

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `planLoopPass`, `advanceLoop` or `loopBoardCount` in `src/lib/workflows.ts`, or `normalizeBoardCondition` in `src/lib/workflowGraph.ts`.

**A loop's exit conditions are four, and the first of them is what the agents said rather than what a row says.** `planLoopPass` is the whole decision, pure and unit-tested for `releasableRuns`' reason sharpened by what a pass costs — not a work cycle but a whole section, with its own runs and its own spend. In order, and the order is load-bearing: an unsettled pass **waits**, because nothing can be read off a pass still working and starting the next one on top of it would put two passes into the same folders at once — and a member is settled only once the runs it *emitted* are, since an orchestrator member's own row says `emitted` the moment its turn ends; a pass that produced **nothing at all** stops it, because the next would be created the same way and fail the same way, which is a hot loop rather than a retry; a member that did **not complete** stops it, over members of all three kinds, because a loop is not a retry mechanism and `MAX_TRANSIENT_RETRIES` and the refusal backoff already sit inside one run. **A pass whose merge did not land everything is the case that needs its own sentence**, and it is why the reading is per member rather than per run: a merge block that failed still *finished*, so such a pass looks complete from every other angle — and because the next pass's runs cut fresh branches from the folder, what was left behind is invisible to them and they would do the same work again, billed and in silence. The stop names what did not land. Then **DONE, which is every run member of the pass reporting it**, not one of them: with a section that may run blocks side by side, one member finishing is not the section finishing and there is no last-run-of-a-chain left to read. The alternative was marking one member as the one whose DONE counts, and it was rejected as a second control over a fact the members already carry — it has to be kept in step with the graph as the section is edited, and every way of setting it wrong ends the loop early and silently. A pass with **no** run members never reports done: an orchestrator and a merge alone say nothing about whether the work is finished, and reading "all of none" as done would stop such a loop after its first pass. Nor does a pass whose **review** member set aside a branch with work on it, whichever member's branch it was: that work was turned down and will not land, so "complete" would be false, and the loop carries on as `reviewVerdict` promises, giving the next pass another go at it. `emitted` cannot say so — it holds only what the review approved — so `loopPasses` hands each review member its `workSetAside` count, and the rung reads it per pass rather than tracing a branch to the member it came from: after a fix round a branch's last link is the fix run, and a review may be handed an orchestrator's runs or another review's, while DONE needs every run member anyway, so discounting one is the same answer wherever a trace exists. A branch set aside because its run **committed nothing** is the exception, recorded as `workflow_review_items.committed_nothing`: it lost no work, and a run finding nothing left to do is the ordinary way such a loop ends, so counting it would run every loop with a review in it to its pass cap. `runs.reported_done` is what each of them is read on, not the status, for the reason `reopenPrompt` reads it — `completed` is written both for the `DONE` reply *and* for a run that used up its cycle cap, and `maxIterations` defaults to 1, so a loop keyed on the status would stop after its first pass every time, which is a loop that does not loop. Then the two caps. A shell predicate as an exit test is deliberately **out of scope**: running one would be a fifth kind of child process, which `architecture.md` treats as a decision rather than a detail.

**A pass that reported it could not finish ends the loop, and the rung above it is why that works at all.** `needs-review` is in `TERMINAL_STATUSES`, so the first rung stops reading such a pass as still working — without that entry the block `wait`s for ever, holding everything behind it with nothing on any page to say why, which is the single most expensive way to get this change wrong. With it the third rung matches and the loop stops with *"…ended needs-review, so the loop stopped rather than repeating on top of it"*, which is exactly right: a loop is not a retry mechanism, and handing the next pass the same wall costs a whole run rather than a work cycle. Two notes on that stop, and both are deliberate. The `code` stays `"failed"` — `LoopStopCode` is branched on by callers, `advanceLoop` maps every `stop` to `settleLoop(…, "emitted", …)` whatever the code is, and the operator-facing sentence already names the status verbatim; it is the vocabulary rather than the behaviour, and a fifth code would go here if loops ever gain per-code copy. And the `reportedDone` rung below is now unreachable for such a pass, so a loop whose last pass did the work *and* asked for review reports the stop rather than the completion — the same precedence as the cycle-outcome ladder, for the same reason. **A `needs-review` member is settled, not written off**, so `memberTally` counts it as neither live nor blocked and the instance reads `finished`: `finished` is a claim about the **graph** rather than about the work, and `blocked` means part of the graph was written off because something in front satisfied nothing, which is not what happened here. `haltSteps` leaves such a row exactly as it is, through the same fall-through that spares a `completed` one — a record of a question that was asked is destroyed by a rewrite as surely as a record of work that landed.

**A loop's two caps are termini, not guards, and that is why they are allowed on a node at all.** A node holds no permission mode, no isolation choice, no model and no budget blob, and a loop does not change that: every pass takes its guards from the block's template or from `settings.chatDefaultGuards`, through the same `planNode` a run block uses. `maxPasses` and `maxLoopCostUSD` are the same kind of number `fanOut` already is — a bound on how many times a block *repeats*, which can only ever end the loop earlier. Neither can raise a run's budget, neither is reachable from anything a model emits, and neither widens the workflow-wide limit: `evaluateInstanceBudget` does not read them, and that guard still halts the whole instance at every member's cycle boundary whatever they say. The pass cap is **not nullable**, refused at save, for the reason `maxIterations` may only be null alongside `maxDurationMinutes` — a loop manufactures its own next unit of work, and nothing else here moves one way and keeps moving. The spend cap is nullable because the pass cap already terminates it, and `loopSpend` reads the **guard** figure rather than the floor, or a loop would take another pass on money it had already spent.

**A loop's board condition is a third terminus and the only one that is not a fact about a pass, which is why it alone is read before the first pass and never while one is still working.** `stopWhenTasks` sits beside `maxPasses` and `maxLoopCostUSD` and is the same kind of number both of those are — it can only ever end the loop earlier, it reaches no guard, `evaluateInstanceBudget` does not read it, and nothing a model emits can widen it. What it is not is a fact about a settled pass: the other four conditions are read off the pass that just ended, where this one is read off the board at the moment it is asked, so `planInstanceStep` routes a loop's **first** pass through `advanceLoop` rather than straight to a first pass. That indirection is the whole feature — a loop pointed at a project that is already clear must start no run at all, and the two caps can only refuse a second one. Its place in `planLoopPass`'s order is load-bearing in both directions: **below `reportedDone`**, because an agent that said the work is finished outranks a board that has not caught up with it and reporting the board would send somebody to look at a backlog that is about to be clear; and **above the two caps**, because a clear board is the loop *finishing* and the stop reason is what an operator reads to decide whether to raise a cap. The function stays pure: the counts arrive as `boardCounts`, null together with the condition, exactly as `spentGuardUSD` arrives beside `maxCostUSD`. `loopBoardCount` is the reader, and it is the one place here that can fail **silently** — `tasks.folder` holds the absolute path `resolveTaskFolder` proved at filing and `listTasks` matches the column exactly, where a node holds a path within its mount, so a folder passed through unresolved counts zero for ever and stops every loop before its first pass with nothing anywhere saying why; it therefore goes through the board's own resolver, and `loopBoardCount.test.ts` files a task through the ordinary door and counts it back. A folder that will not resolve **fails** the loop rather than reading as zero, which is the one answer that would end it — but only once the latest pass has settled. `advanceLoop` steps an unsettled pass before it reads the board at all, asking `planLoopPass`'s own first rung ahead of the read, because `advanceInstances` runs after every terminal run anywhere in the app and a folder an agent in the pass renamed, or a mount that blipped, would otherwise fail the loop **mid-pass**: the block behind it is decided on a loop whose runs are still in its folders — released on `on-finish` — and the pass's unreleased members stay `waiting` with nothing ever to step them, so its merge never lands and the instance stays open until it is stopped. The check for an instance blob whose loop carries no `maxPasses` sits behind the same rung for the same reason. `done` and `dropped` are refused at save **by name** on the same reasoning inverted — those counts only ever grow, so "at most N" against one holds at the first check — and `claimed` is offered but is not the default, because a claim here is a record and not a lease, so one task left claimed by a dead run holds the loop open for every pass it is allowed. Absent is off, and that reading is what keeps every graph saved before the field existed behaving exactly as it did.

**The condition's numbers are an `or`, its project is one folder unless told otherwise, and a condition saved as one number is read in exactly one place.** Three claims, each with a failure behind it. `thresholds` holds up to five `{ priority, atMost }` pairs and `planLoopPass` stops on **any** of them, never all: an all-of reading keeps a loop going on a board nobody thought was full, and a loop is billing a whole run per pass, so the condition that ends it earlier is the one to prefer when the two readings disagree. Each threshold may name a priority or `any`, no priority twice — a duplicate is refused at save rather than merged, because two numbers for one priority is an `or` in which the larger silently decides and the smaller is a line the operator wrote that can never fire. The stop reason names the threshold that was met, its priority and both figures, because five lines in "the board is clear enough" cannot be read back to a decision. `loopBoardCount` counts **every** priority and not the ones the thresholds happen to name: a reading that could be missing a figure the decision needs is a decision that can only skip the threshold it has no number for, and a skipped threshold is a loop that runs past its own ending. `includeSubfolders` defaults to **false**, which is how the board itself groups a project — `…/terraServe` and `…/terraServe/docs` are two projects on that page and must stay two here — and when it is on the match is `folder = ?` OR a `LIKE` on the canonical path **with the separator appended** and `%`/`_` escaped the way `likeNeedle` does in `orchestrator.ts`; without that separator `…/UsageFoundryWeb` is counted for `…/UsageFoundry`, silently and in the direction that keeps a loop running, since a project counted too full never reaches the number it was told to stop at. A condition carrying `atMost` and no `thresholds` reads as one `any` threshold with that number, and `boardThresholds` in `apiTypes.ts` is the **only** place that reading lives: nothing re-normalises a stored graph — `rowToWorkflow` and `rowToInstance` both hand the blob's nodes back as they were written — so a loop saved or started before thresholds existed reaches `planLoopPass`, `loopBoardCount`, `normalizeBoardCondition` and the editor still carrying the old shape, and four opinions about it would be four chances to refuse a workflow nobody changed. Its `?.` on a field the type says is always there is load-bearing for the same reason `advanceLoop` asks `typeof node.maxPasses !== "number"`. The editor's project picker offers the mount-and-folder pairs as single choices with `fmtTaskPlace`'s own labels, so the loop and the board name a project identically, and the figure beside it is the **server's** reading through `loopBoardCount` — answered by `/api/workflows/validate` beside the verdict rather than behind it, because a graph being drawn is refused for most of the time it is being drawn, and because anything this surface counted for itself would be comparing a path within a mount against a canonical absolute one, which is the defect that reader exists to prevent.
