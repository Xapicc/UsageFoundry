# When a loop stops: exit conditions, caps and a requested stop

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `planLoopPass`, `advanceLoop`, `setLoopStopAfter` or `loopStopAfterRefusal` in `src/lib/workflows.ts`, or `stop-after-pass/route.ts`. A loop's board condition, which `planLoopPass` also reads, is in [loop-board-condition.md](loop-board-condition.md).

**A loop's exit conditions are five, and the first of them is what the agents said rather than what a row says.** `planLoopPass` is the whole decision, pure and unit-tested for `releasableRuns`' reason sharpened by what a pass costs — not a work cycle but a whole section, with its own runs and its own spend. In order, and the order is load-bearing: an unsettled pass **waits**, because nothing can be read off a pass still working and starting the next one on top of it would put two passes into the same folders at once — and a member is settled only once the runs it *emitted* are, since an orchestrator member's own row says `emitted` the moment its turn ends; a pass that produced **nothing at all** stops it, because the next would be created the same way and fail the same way, which is a hot loop rather than a retry; a member that did **not complete** stops it, over members of all three kinds, because a loop is not a retry mechanism and `MAX_TRANSIENT_RETRIES` and the refusal backoff already sit inside one run. **A pass whose merge did not land everything is the case that needs its own sentence**, and it is why the reading is per member rather than per run: a merge block that failed still *finished*, so such a pass looks complete from every other angle — and because the next pass's runs cut fresh branches from the folder, what was left behind is invisible to them and they would do the same work again, billed and in silence. The stop names what did not land. Then **DONE, which is every run member of the pass reporting it**, not one of them: with a section that may run blocks side by side, one member finishing is not the section finishing and there is no last-run-of-a-chain left to read. The alternative was marking one member as the one whose DONE counts, and it was rejected as a second control over a fact the members already carry — it has to be kept in step with the graph as the section is edited, and every way of setting it wrong ends the loop early and silently. A pass with **no** run members never reports done: an orchestrator and a merge alone say nothing about whether the work is finished, and reading "all of none" as done would stop such a loop after its first pass. Nor does a pass whose **review** member set aside a branch with work on it, whichever member's branch it was: that work was turned down and will not land, so "complete" would be false, and the loop carries on as `reviewVerdict` promises, giving the next pass another go at it. `emitted` cannot say so — it holds only what the review approved — so `loopPasses` hands each review member its `workSetAside` count, and the rung reads it per pass rather than tracing a branch to the member it came from: after a fix round a branch's last link is the fix run, and a review may be handed an orchestrator's runs or another review's, while DONE needs every run member anyway, so discounting one is the same answer wherever a trace exists. A branch set aside because its run **committed nothing** is the exception, recorded as `workflow_review_items.committed_nothing`: it lost no work, and a run finding nothing left to do is the ordinary way such a loop ends, so counting it would run every loop with a review in it to its pass cap. A review member whose verdict is the run's status reads no diff, so it writes every set-aside with `committed_nothing` 0 and each one holds DONE off: what it set aside is a run that did not complete, which is work not done whatever it committed. A verify-command verdict reads no diff either and writes the same 0: a branch its command failed is work that will not land. `runs.reported_done` is what each of them is read on, not the status, for the reason `reopenPrompt` reads it — `completed` is written both for the `DONE` reply *and* for a run that used up its cycle cap, and `maxIterations` defaults to 1, so a loop keyed on the status would stop after its first pass every time, which is a loop that does not loop. Then the operator's request to end after the pass in flight, which is the fifth and the only one a person writes while the loop runs — the paragraph headed “Stop after this pass” below. Then the two caps. A shell predicate as an exit test is deliberately **out of scope**: running one would be a fifth kind of child process, which `architecture.md` treats as a decision rather than a detail.

**A pass that reported it could not finish ends the loop, and the rung above it is why that works at all.** `needs-review` is in `TERMINAL_STATUSES`, so the first rung stops reading such a pass as still working — without that entry the block `wait`s for ever, holding everything behind it with nothing on any page to say why, which is the single most expensive way to get this change wrong. With it the third rung matches and the loop stops with *"…ended needs-review, so the loop stopped rather than repeating on top of it"*, which is exactly right: a loop is not a retry mechanism, and handing the next pass the same wall costs a whole run rather than a work cycle. Two notes on that stop, and both are deliberate. The `code` stays `"failed"` — `LoopStopCode` is branched on by callers, `advanceLoop` maps every `stop` to `settleLoop(…, "emitted", …)` whatever the code is, and the operator-facing sentence already names the status verbatim; it is the vocabulary rather than the behaviour, and a fifth code would go here if loops ever gain per-code copy. And the `reportedDone` rung below is now unreachable for such a pass, so a loop whose last pass did the work *and* asked for review reports the stop rather than the completion — the same precedence as the cycle-outcome ladder, for the same reason. **A `needs-review` member is settled, not written off**, so `memberTally` counts it as neither live nor blocked and the instance reads `finished`: `finished` is a claim about the **graph** rather than about the work, and `blocked` means part of the graph was written off because something in front satisfied nothing, which is not what happened here. `haltSteps` leaves such a row exactly as it is, through the same fall-through that spares a `completed` one — a record of a question that was asked is destroyed by a rewrite as surely as a record of work that landed.

**A loop's two caps are termini, not guards, and that is why they are allowed on a node at all.** A node holds no permission mode, no isolation choice, no model and no budget blob, and a loop does not change that: every pass takes its guards from the block's template or from `settings.chatDefaultGuards`, through the same `planNode` a run block uses. `maxPasses` and `maxLoopCostUSD` are the same kind of number `fanOut` already is — a bound on how many times a block *repeats*, which can only ever end the loop earlier. Neither can raise a run's budget, neither is reachable from anything a model emits, and neither widens the workflow-wide limit: `evaluateInstanceBudget` does not read them, and that guard still halts the whole instance at every member's cycle boundary whatever they say. The pass cap is **not nullable**, refused at save, for the reason `maxIterations` may only be null alongside `maxDurationMinutes` — a loop manufactures its own next unit of work, and nothing else here moves one way and keeps moving. The spend cap is nullable because the pass cap already terminates it, and `loopSpend` reads the **guard** figure rather than the floor, or a loop would take another pass on money it had already spent. It is refused over a section holding a block whose runs report no cost, which it could never count ([instance-budget.md](instance-budget.md)). The third terminus beside them, the board condition, is read before a pass rather than off one and has its own file: [loop-board-condition.md](loop-board-condition.md).

**The guards are read again for every pass, and a pass whose guards no longer match the section it was accepted as is blocked, not carried on.** A section's kind is fixed at Save and again at Run, from the guards as they stood, but `stepPass` plans each member from the guards as they stand when the pass opens. A template's isolate switch or the default guards in Settings can change in between, and nothing else asks whether what a pass now plans is still what the section was accepted as: an in-folder section's pass 2 would cut branches no merge block lands and the loop would carry on repeating work no pass reads, and a landing section's head would edit the folder in place while its merge lands into it. `sectionKindRefusal` is the question, asked of every run member in `stepPass` and of an orchestrator's turn in `startBlockTurn` before it is paid for (its emitted runs take its guards). The kind is read off the instance's own graph — a section with a merge block lands, so a member in front of its last merge isolates and one behind it works in the folder, and in a section without one none does — so nothing is recorded at Run, pass 1 is held to it as pass 2 is, and both directions of the flip are caught. **Blocked, not frozen.** Pinning each member's isolation at Run would keep a loop going on guards the operator has since changed, and would run a block against the template that now says otherwise; a block that names the switch and the way back leaves the choice with them, and the loop stops because the pass did not complete, as it does for any block `planNode` refuses. The pick-up's dry run, `passWouldProceed`, plans no guards — it does not for a deleted template either — so *carry on* is offered before the switch is put back and blocks the member again on the same sentence.

**"Stop after this pass" is a terminus read when the pass settles, never a halt, and it sits between what the pass did and what a limit says.** `workflow_instance_blocks.stop_after_pass` holds the number of the pass the loop was on when the operator pressed it; `advanceLoop` hands it to `planLoopPass` as `stopAfterPass` and the decision stops with the code `requested` once the latest pass has settled and is **at or past** that number — `>=`, so a pick-up that reopens a later pass cannot step over a request recorded for an earlier one. The pass in flight is not touched: the unsettled-pass rung still comes first, so its members run and its merge lands exactly as they would have, which is the whole point of the control and the reason it cannot go through `stopInstance`, whose door closes before anything is signalled and takes every member down. Its place is **below the failures and `done`** because those say how the pass went and this says only that nobody wants another: a pass that did not land, reported as a stop the operator asked for, would be written `emitted` rather than `failed` by `loopStopStatus` and would start an `on-success` successor on work that never arrived — `planLoopPass`'s cases pin each of the three. It is **above the board and the caps** because it is the more specific sentence: the operator pressed it, and a loop that was also at its cap would tell them it ran out. **What is behind the loop is decided as for a pass cap**: `requested` is `emitted`, so a block behind it proceeds per its edges. The alternative was halting the whole instance once the pass settles, and it was not taken because the control is on one loop's card and says "this loop"; in all four workflows on this install nothing sits behind a loop, so the two readings are identical there and the choice is for the first workflow that has a block behind one. It is a column and not a field of the graph, because the instance's graph is the frozen record of what was saved, and not process memory, because a restart reconciles a `looping` block and a request held only in the process would be lost across it while the loop took passes the operator had refused. `setLoopStopAfter` records it and takes it back (`Keep going`) through one route, `stop-after-pass`, for as long as the loop is `looping`; `loopStopAfterRefusal` is the pure answer for everything else, and it reads the instance first so that Stop wins — a halted instance is refused whole, and `settleLoop`'s latch on `looping` keeps a request that raced the halt from rewriting the halt's wording. The request survives a pick-up that reopens a failed loop, deliberately: the card shows it (*Ends after pass N*) beside a *Keep going* button, so it is visible and reversible, where clearing it inside `reopenLoopPass` would be a silent change to the pick-up's code for a case the card already covers. The instance budget is untouched and still enforced through the last pass: `evaluateInstanceBudget` does not read the request, so a pass allowed to finish is still bounded at every member's cycle boundary.

**Whether a failed loop can carry on is read twice, and only the press reads the folder.** `loopPassRefusal` answers from the rows — the pass cap, the board, whether a block behind the loop has started — and `pickUpsOf` asks it on every poll of an instance page, so it spawns nothing. What an in-folder tail left uncommitted (`tailLeftDirt`, see [loop-section-kinds.md](loop-section-kinds.md)) is a synchronous `git status` and is asked only where something is decided: `advanceLoop` at the boundary and `resumeLoop` at the press, through `loopPassDirt`. So the page offers *Carry on* for a loop that failed on a dirty folder, and the press answers 409 with the sentence the loop failed on until the folder is committed. The read in `loopPassRefusal` showed that sentence on the page first, and cost one `git status` plus its filter-probe spawns (each up to 20 s on the event loop) per open tab per 10 s for as long as the loop stayed failed; nothing failed, the server's other runs stalled. `loopSection.test.ts` pins it by counting spawns across `pickUpsOf`. The tail's folders are those of its run members' runs **and of an orchestrator member's `emitted` runs**: an orchestrator has no run of its own, and read through `member.run` alone its tail looks like one that touched nothing and the next pass opens over what it left.
