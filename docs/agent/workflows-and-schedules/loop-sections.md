# Loop blocks and their sections

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing what a loop block may hold or how its section is resolved: `normalizeNode`, `resolveSections` and `graphRefusal` in `src/lib/workflowGraph.ts`, or `sectionOf` and `linksOfGraph` in `src/lib/canvasGraph.ts`.

**A section repeats by unrolling — the back edge is the thing that must not exist.** A loop block holds a **pass cap**, an optional total spend cap and the section it frames, and the obvious implementation is an edge in `run_deps` pointing from a pass back to its own block. That edge is refused at admission, and the reason is the whole design: `releasableRuns` reaches a fixed point and leaves a cyclic set alone, so a loop in the run graph is precisely the row nothing ever wakes, which is why `dependencyCycle` exists. So the loop lives in the workflow layer and `run_deps` never learns about it — pass N+1 is a **fresh instantiation of the section**, depending on nothing that pass N left, the run graph stays a DAG, and every rule written against one holds unchanged. It needs no schema of its own: the graph is a JSON blob and `emitted_by` already existed for an orchestrator block's runs, so the whole feature adds not one column. The next reader will reach for the back edge first; the comment on `planLoopPass` says so.

**A loop is told nothing, and the next reader will try to give it work.** It is a **region** — a frame round the blocks it repeats — so it names no task, no template, no mount, no folder, no agent and no prompt override. `normalizeNode` refuses each of those **by name** when one arrives, which is the treatment `agentId` on a merge block already gets and is the same judgement: a choice the operator made that no process would ever act on is exactly what a door exists to answer out loud, and coercing it away in silence is how a graph comes to run something nobody asked for. `LOOP_IS_TOLD_NOTHING` is that list, as a table rather than six branches, so somebody checking it is complete can read it as a list; its keys are the **wire's**, because this is what arrived and none of it has been coerced yet. What a loop does hold is `maxPasses`, `maxLoopCostUSD`, `stopWhenTasks` and the derived `bodyNodeIds`, every one of which bounds the *repetition* rather than describing a run. Past that point a loop and a merge block are the same block — nothing to run and nowhere to run it — which is why `startsNoRun` is one flag and not two conditions, why `guardsFor` is never asked about a loop's template, and why `folderRefusal` and `planNode` skip one. There is no loop that carries work of its own to fall back on: that mode existed, it was the loop that repeated its own task, and it ended when the `repeats` link became required.

**Membership is derived from a marked link, and the link is the *only* thing that states a section.** A link out of a loop block may carry a third condition, `repeats`, and that link is the whole statement an operator makes: its target is the section's first block, and the section is that target plus everything reachable from it along ordinary links. `resolveSections` walks it and writes the result to `bodyNodeIds` before `graphRefusal` runs, so every rule below, every runtime reader and every saved graph stays written against one field. A second list beside the links is what this replaced, and it was two mechanisms for one fact: the ticks said who was in, the links said the order, a link from the loop to a member was accepted and meant nothing, and the operator found out which was which by being refused. The derivation is duplicated in `sectionOf` for the canvas — `canvasGraph.ts` is reached from a `"use client"` file and may not import `workflowGraph.ts` — and the two must agree exactly, because one is what the graph *says* and the other is what the operator *approves*. **A loop with no `repeats` link is refused**, and so is a list that arrives without one; the list is a **cross-check** on the links and never a second way of saying it. A graph carrying both and disagreeing is refused **by name** rather than resolved in favour of one, because a caller who sent both meant something by each. The editor cannot produce that disagreement: `draftToGraph` derives the list from the links it sends it beside, and `linksOfGraph` materialises the link on the way *in*, which is now what keeps a workflow openable rather than a compatibility path.

**A `repeats` link is never a run dependency.** It is written only by the two frame gestures, a loop has at most one — two is refused naming both targets — and it may not carry a branch. Nothing ever waits for the block it names, because that block is created once per pass by the loop itself: read as a dependency it is the back edge this whole design exists to avoid, and `releasableRuns` would hold the loop `waiting` for a run only the loop can start, leaving the instance unfinishable with nothing on the page saying why. `WorkflowEdge.edge` is therefore a union `DependencyEdge` is *not* widened to, `isDependencyEdge` is a type guard rather than a predicate so the compiler stops any reader turning one into a `run_deps` row, `planInstanceStep` drops it by its own condition rather than relying on the membership test beside it, and a unit test holds that drop in place. It is also excluded from `dependencyCycle` and from both `topologicalOrder` calls: it is not a wait, and left in, a member linked back to its loop would be reported as "these blocks wait for each other" instead of by the boundary rule that names the link to draw. **It is also drawn as no arrow at all.** The frame is how containment is said on the canvas, and an arrow from a loop to its entry reads as "the section runs after the loop", which is exactly what a loop is not; `LinkTone` is three tones rather than four and one filter decides what is drawn, because a containment arrow surviving in any one of the three places that walk the links — the curves, the chips, the narrow list's incoming chips — is the picture contradicting the frame beside it. Nothing offers to convert an ordinary link into one either: `LinkPanel` cannot be reached by a `repeats` link and its condition picker drops the option, since a link converted to it would be a link that vanished with no way to get it back.

**A loop's `bodyNodeIds` is derived from its `repeats` link and is never empty.** A loop with no such link is **refused** — that is what ended the body-less loop, the mode where a loop repeated its own task, and it is a refusal rather than a reading because a region frames work and does not do any. A list sent without a link is refused too, with its own sentence, because a caller that sent one meant something by it and is owed the half that is missing. Where a list arrives *beside* a link it is a **cross-check**: `resolveSections` compares the two and refuses a disagreement by naming both sections rather than resolving it in favour of either. The derivation took three older refusals with it — a derived section cannot name a block that is not in the graph, cannot contain its own loop (`sectionFrom` seeds its walk with the loop's id) and cannot name one twice (the walk is a visited set) — and the one claim question it leaves open is two loops whose `repeats` links reach the same block, which is still refused by naming both. The field is stored **on the loop** rather than as a parent pointer on each member, because every refusal that makes a section safe is a whole-graph fact and `normalizeNode` can answer none of them; they live in `graphRefusal`, read **last**, so the exit test may assume the section is acyclic. Every one of them names the link to **draw** and not only the one that is wrong. It is still true that no read outside `normalizeNode` may index `bodyNodeIds` directly: an instance carries a *copy* of its graph taken when it was created, so a loop repeating since an older build is read back from a blob with **no such key** — `undefined`, which a `for…of` throws on and `.length` crashes an advance on, mid-instance, with nobody to show it to. Every read goes through `bodyOf`. That is the trap `advanceLoop` already records for `maxPasses` one field over, and it fails identically because the type says the field is there and the build that wrote the row agreed.

**A section is one way in and one way out, and the way out has to land.** The chain rule is gone, and so is the rule that every link inside a section says *only if it completes* and carries the branch — that was the chain rule stated a second way, and both fell with "one branch, all the passes". What is left is the two ends: the entry is the `repeats` link's target, and the exit is the section's single **sink**, which must be a merge block. In between the shape is free, any acyclic subgraph, and a section that forks may meet again at the merge that lands both halves. A second sink and a member with no path to the exit are **one fact and get one sentence**, because they are the same defect seen from two sides: the member whose work nothing lands *is* where the section ends a second time. Say both halves — what is wrong and what it costs — since "the section ends in two places" on its own is a shape complaint and the reason it matters is a branch nobody lands. The three kinds of member are `run`, `orchestrator` and `merge`; a **nested loop** is the one kind left out and is refused by name, because one pass cap multiplying another is a number nobody can work out from the two they typed. Guards that isolate are asked of **run** members only, and the other two are exempt **by name** rather than by passing a test written about a checkout — an orchestrator spends nothing on disk and a merge has no guards at all, so "its guards work directly in the folder" would be a sentence about a folder neither works in. `startWorkflow` draws the same line: it probes a section's run members and not the loop, which names no folder to probe.

**A path to the exit is not a branch to it, so every run member has to hand its branch to something that takes it.** A merge block lands the runs **directly** in front of it — `planInstanceStep` queues it with the runs its own incoming links resolved — and a run whose way on carries no branch leaves its commits where they are, because its successor starts fresh. So in a fan-in, `a` and `b` meeting at `j` with `j` linked to the exit `m`, `j` can carry on one of the two branches (a run holds one ref), `m` lands `j`, and `b`'s work lands nowhere while `b` has a perfectly good path to `m`. The exit rule above checks paths and cannot see it. The rule, in `loopBodyRefusal` after the exit test: a **run** member needs a link out of it that either carries its branch — the run it hands the branch to is asked the same question in turn — or leads straight to a merge or review block. A review block counts, because what it sets aside it sets aside on purpose. The sentence names the member and the link that lands it: the member to the section's exit. The same sentence answers a run whose only way on is an orchestrator member, and any run whose every link out starts its successor fresh, including a fork where neither link carries the branch. All of these used to save and all of them stranded a branch. Five fixtures in `workflows.test.ts` had been saving one or another of them as legal. A graph saved before this rule is refused at Run with the same sentence, because `startWorkflow` normalizes the saved graph again. **It is a refusal rather than something the editor draws**, for three reasons. The editor is one of three doors: `POST /api/workflows` and the chat's `propose_workflow` save a graph no canvas ever saw. The exit is often not drawn yet when `sectionLink` mints the fan-in link, so there is nothing to link it to. And the link to the exit is not the only fix: the operator may rather have `j` carry on `b`'s branch and land `a`'s. Drawing one of those in silence would be the editor making a choice the operator was never shown.

**An orchestrator or review member is asked the same question about the branches it hands on**, and only a link straight to a merge or review block answers it: both resolve to their successors with `continueBranch: false` whatever the link says, and neither may sit on a `continueBranch` edge at all. So `e → o → j → m` lands `j` and strands every run `o` started, and `e → v → j → m` strands every branch `v` approved. An orchestrator's runs take its guards, so it is asked only when `isolatedTemplate(o.templateId, known)` says they cut a branch. One naming a template that works in the folder leaves nothing to land, and requiring `o → m` of it would trip the merge rule's "leaves no branch to land" on a section that works. A review member is always asked, because the review rule already requires every source to isolate. The sentence names what goes unlanded, the runs the orchestrator starts or the branches the review approves, and the same link to draw: the member to the section's exit. A graph saved before this is refused at Run with the same sentence, as the run members' is. One fixture had been saving the stranding shape: `canvasGraph.test.ts`'s kind switch, whose `b` becomes an isolating orchestrator in front of a run, and it now draws `b → m`.

**A loop's own task and an intra-section link's condition were each answered a different way before the frame, and both of those answers are still findable in the tree.** The task refusal was *deferred*: `normalizeNode` cannot see the `repeats` link a section is derived from, and a loop with a section starts no run of its own — every run of a pass is a member's, and `planRunInput` is never handed the loop's node — so requiring the text there made the one block whose words reach no agent the one block that could not be saved without writing some, and the way past the refusal was text nothing would read. `emptyLoopTaskRefusal` is that move, in `graphRefusal` and therefore after `resolveSections`, asking *no section, no task* once the derived section is on the node. The frame carried both halves further and left it **belt and braces**: a task that arrives is refused by name with the other five fields in `LOOP_IS_TOLD_NOTHING`, and a loop that frames nothing is refused by `resolveSections` before `graphRefusal` is reached, so nothing can fire it today and a leftover task is no longer kept-and-labelled because the field is no longer accepted at all. The link rule went the other way. `planPass` used to create every member `on-success` and carrying the branch whatever the operator had drawn — one pass, one branch, the last member's tip continued by the next pass — which made both controls on an intra-section link decoration, and the answer at the time was to refuse anything else and have the panel state the rule. That rested on the chain, and the chain went: each pass now lands its own work through the section's exit, so a member may wait `on-finish` and may cut its own branch, `edgeVerdict` resolves exactly what was drawn, and the editor's `sectionLink` mints a conforming link without the model insisting on one. What survives from both is the rule each was an answer to: a choice the operator was shown may not be silently rewritten — refuse it by name or honour it as drawn, never overwrite it.

**A body member is the one node here that is neither a run nor a ledger row.** It is skipped by the instantiation and skipped again by `planInstanceStep`, and both skips are load-bearing in opposite directions. Created as an ordinary node it would be an extra run on the body's folder that nothing repeats and nothing counts against the pass cap — a member with no edges is a source node, so this is the default outcome rather than a corner. Given a `waiting` ledger row instead, that row is counted live by `liveBlocksOf` and settled by nothing, which leaves the instance unfinishable and every later press of Run refused by the second-press rule. So the loop's own row is the member's record, and the member's work is `workflow_instance_runs` rows under the loop's `emitted_by` — the column an orchestrator block's runs already use, which is what makes `loopSpend`, `stopInstance`, the instance budget guard and the instance page cover a pass of six with no new code. The **only** edge that may cross a body boundary is the loop's own `repeats` link, which states containment and is inert at runtime for the reason above. An *ordinary* edge from a loop to a block of its own section used to be allowed and inert, which is the defect the third condition replaced — an arrow the operator could see, told nothing, while the section came from a control somewhere else. It is now refused by name, as is a member linked back to its loop, as is a link drawn *into* the section from outside it; each of the three has its own sentence, because only one of them is "you linked the wrong block". There is deliberately no fourth for a link drawn *out* of a section, and looking for one is the mistake: membership is the forward closure of the entry, so a block linked after the section's exit **joins** the section. What answers is the exit rule — the section now ends somewhere that lands nothing — and that is the sentence the operator can act on.
