# Orchestrator blocks and merge blocks

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing an orchestrator block's turn or emission (`startBlockTurn`, `planEmission`, `blockSystemPrompt`, `settleBlock` in `src/lib/workflows.ts`), the `block` capability in `src/app/api/mcp/route.ts`, a merge block (`mergeBlockOutcome`), or a deliver block (`deliverBlockOutcome`, `startDeliverBlock`).

**A block can decide what runs next, and those runs start with no approval — because the approval moved to the graph rather than disappearing.** An orchestrator block is a node whose `kind` is `orchestrator`, holding a brief, a folder, an optional template and a **fan-out cap**; when the workflow reaches it the server spawns one headless turn through `runOrchestratorChild`, and the specs it emits become runs that enter the queue. No `chat_proposals` row, no card, nothing between the decision and the spawn. What makes that defensible is not the block, it is the four things a person fixed when they saved the graph, and every one of them is unreachable from anything the model emits. **Guards** come from the block's named template or from `settings.chatDefaultGuards` — `planProposal`'s rule reused a third time, through the shared `guardsFor`, and `planEmittedRun` has no branch that reads a budget, a permission mode or an isolation choice off a spec, for the reason `reopenRun` refuses to become a third route to `--permission-mode`. **The folder** goes through `resolveWorkspaceFolder` against the block's *own* mount and no other, so containment is `resolveInMount`'s two checks unchanged. **The cap** is not nullable: `normalizeWorkflowInput` refuses an orchestrator block without one at *save*, which is the `no_terminus` rule applied where it bites hardest — this is the one block whose runs start with nobody looking, so a missing limit is an unbounded number of billed agents from one press of Run. And **`emit_runs` is a spec and nothing more** — a title, a task, a folder, an optional agent, and edges among the runs being emitted — with `/api/mcp` publishing it only to a `block` capability and `propose_run`/`save_template` only to a `chat` one, checked again in `callTool` because a tool absent from a list is not a tool absent from the wire. **The agent is the exception that is not one**: an emitted spec may name a saved agent for the run to be started as, and that is the same class of act as writing the task text beside it — an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so it decides *who* the run is and never what the run may do. It is named by **name**, because a name is what `blockSystemPrompt` showed the turn and an id is a thing only this app's own forms hold; `planEmission` refuses one this install does not have, beside the cap and the loop, before anything is created, and stores the registry's own spelling so what reaches `--agent` is what the operator saved — and a name is also literally what that flag takes, so a misspelling this refusal let through would be a run that fails at the spawn rather than one that quietly starts as nobody. The block's *own* deciding turn is started as the agent the node names, refused by name before it spawns rather than dropped. The block's own spend lands in `workflow_instance_blocks.cost_usd`, never in `runs.spent_usd` and never in a meter, bounded by `settings.chatTurnBudgetUSD` inside the CLI exactly as a chat turn's is; it *is* added to the instance's own total — in both figures when the turn reported and in the guard's alone when it did not, see [instance-budget.md](instance-budget.md) — because it is money this press of Run spent and a graph with several deciding blocks would otherwise understate itself against the one limit meant to bound the whole thing.

**The model is the one thing on an emitted run nobody saved and nobody reads, and that is now allowed.** Where the block's template and the spec's agent name no model, the model decider may pick one for each emitted run in the `emit_runs` handler, and the run starts on it with no approval — the operator overruled `RunSpec`'s "a model choosing what it costs to run is a choice with nobody in the loop" on 2026-10-05 for the decider alone. The turn itself still has no field for a model, the template's model still wins when it is created, and every pick, abstention and failure is a line in the block's notes. See [model-decider.md](../agents-and-templates/model-decider.md).

**And what the turn said is kept, in three fields that are three voices.** A block that starts nothing blocks every node behind it, so it ends the graph — and the row that says so used to carry a status, a count of zero and nothing else, which is one appearance for three different endings: it decided there was nothing worth doing, this app refused what it asked for, or it never reached a decision. `reply` is the model's own account, which its system prompt asks for in as many words and which was read off stdout and dropped; `notes` is *this app's* — an `emit_runs` refused by `planEmission`, a tool call the CLI declined, the instance guard `startBlockTurn` could not read, a decided spec `createEmitted` could not then create — appended as each happens, because they arrive from four places across a turn and an operator reading them for a cause needs all of them rather than the last; `error` stays the turn failing and nothing else — a spec that could not be created is not the turn failing, and written into `error` it read as the model's fault while the block behind it was told the model had decided on nothing. The one failure that is a note rather than an `error` is a turn that **emitted and then ended with no `result` event** — killed, timed out, or a stream the reader could not use, which `turnResultOf` returns as a failure with no `costUSD`: the block is `emitted` and its runs go ahead, so what the turn ended on is how it finished and not a verdict on what it decided, and `blockSettlement` writes it into `notes` and leaves `error` empty, while `blockTurnSpend` already counts the turn's cost as unreported. A `result` that did arrive and said the turn failed carries a cost and stays `error`, and a turn that failed having emitted nothing is `failed` with the error as before. None of the three has anything to record unless the stream was read: `reply`, the session id and the cost all come off the accumulator `runOrchestratorChild` folds each stdout line into, and that fold runs whether or not the caller passes `onProgress`. A block passes none, and the fold used to be an argument of the optional call, so every block turn measured between 2026-09-21 and 2026-10-07 (53 that emitted runs) settled `The chat produced no readable output (exit 0).` with no reply and its cost unreported, over a valid `result` — `blockTurnReading.test.ts`. `blockSettlement` is that decision, pure and unit-tested for `mergeBlockOutcome`'s reason one level over: every way of being wrong here typechecks and looks identical on the page. It is also why `settleBlock` reads the row before it writes — the flat `error=?` it used to run wiped the guard note on every turn that did not itself fail. `decided` is `emitted_specs IS NOT NULL` and is on the DTO for the one distinction the count cannot make: `[]` is a turn that called the tool and named nothing, null is a turn that never called it. Every emitted run is a `workflow_instance_runs` row, so the instance budget guard, `stopInstance` and the second-press refusal all cover it with no new code.

**A deciding turn that failed is run again by itself, and only when it had decided nothing.** `retryOrchestratorBlock` is `retryMergeBlock`'s shape for the other block that spends: the row goes `failed` to `waiting`, `reviveGraphDependents` (or `reopenLoopPass`, inside a pass) brings back what its failure wrote off, and the next advance claims it and starts the turn through `startBlockTurn` — so the fan-out cap, the instance budget, the hold and the process budget are asked of the retried turn by the same code that asked them of the first, with no second copy of any of them. It is refused once a block behind it has started, `startedBehind`'s reason, and through a halt, `openInstanceFor`'s. **A block that had decided is not retried**, and `orchestratorRetryRefusal` is that rule, pure and unit-tested: `blockSettlement` records `failed` only for a turn that failed *and* emitted nothing, so a failed block normally has no decision on it — the exception is a restart, because `reconcileBlocksOnBoot` writes a `thinking` block `failed` without settling it, with the specs the turn had already accepted still stored and nothing created from them. A new turn would decide from nothing and replace that decision rather than carry it out, and where any run did exist it would start the same work again, so `emitted` and `started` are both asked and the way through is a new press of Run; the refusal says how many runs it had decided on. A turn that called `emit_runs` with `[]` had decided nothing and *is* retried, which is why the pick-up writes `emitted_specs=NULL`: `emitBlockRuns` refuses a second call on any block whose column is set, `[]` included, and without the clear the retried turn is billed to be refused at everything it decides. **The cost columns are not touched and the error is cleared.** The failed turn was billed, so `cost_usd`, `cost_usd_est`, `cost_unreported` and `tokens` keep their figures and the retry's `settleBlock` adds to them — the block's Spent and the instance total are what the block has cost in all, which is what the instance guard compares its limit against; `error` and `finished_at` clear for the merge retry's reason and `claimBlock` clears the reply and notes, which belonged to a turn that is over. The failed turn's own error is therefore not kept once the retry starts; a retry that fails again writes its own.

**A deciding turn that failed is also started again inside the press of Run, up to a limit a person saved on the block — and by a different mechanism, which is why the two are not one.** `turnRetries` is an integer from 0 to `MAX_TURN_RETRIES` (2) on an orchestrator node, absent is 0, and `normalizeNode` refuses anything else by name: above the cap, negative, fractional, and any non-number (`true`, `"1"`, `[]`), since `Number()` reads each of those as a count and this authorises billed turns. It is on the node for `fanOut`'s reason and nothing a model emits can raise it; a chat-proposed graph carries it on a card that states it (`ProposedBlockSummary.turnRetries`). `startBlockTurn`'s `onSettle` goes through `settleBlockTurn`, which asks `blockTurnRetries` — pure and unit-tested, `blockSettlement`'s own test for `failed` (the turn failed *and* emitted nothing, so the two cannot disagree) plus `used < allowed` and no emission refused by this app — and, because it has the database, whether the block is still `thinking`, its instance open and the process not exiting. A halt writes the block `failed` and closes the instance *before* it signals the child, so an operator's stop and the instance guard's stop both arrive as a dying turn on a row already written off: they fall through to `settleBlock`, which still banks that turn's cost, and the block's notes do not say it was about to be tried again. **A refusal by this app is not the turn failing.** `emitBlockRuns` writes every refusal through `noteRefusedEmission`, which puts one shared prefix on the note, and a turn whose notes carry it settles as it did: another billed turn would be asked to decide the same thing under the same rules. It is read off the notes rather than off module state because `emitBlockRuns` runs in the MCP route's bundle and the settle in the server's, and in dev those do not share a module; the prefix is added by the helper and never typed at a call site, so rewording a refusal cannot make it stop counting. The retry is not `retryOrchestratorBlock`'s mechanism, because the block never leaves `thinking`: no successor is revived, no pass is reopened and the claim does not repeat. It banks the failed attempt through `bankBlockSpend` (the three cost columns and tokens `settleBlock` writes, so the instance total holds the attempt before the next question is asked), sets `emitted_specs` back to NULL for the manual pick-up's reason, appends `Attempt n of m failed: <error>` to the notes — the block's `error` is the last attempt's alone, so the earlier ones would otherwise be lost — and enters `startBlockTurn` with `retriesUsed + 1`, which asks the hold, the process budget, the provider, the agent and the instance budget ([instance-budget.md](instance-budget.md)) of the attempt as it did of the first. A refusal there settles the block `failed` with that refusal as its error. Under the install-wide hold it settles `failed` rather than handing the block back to `waiting`, because the next claim starts at attempt 0 and the block would get its retries over again; for the same reason `retriesUsed` is an argument and not a column, and the manual pick-up gives a person a fresh allowance. A retried turn is spend but not a run, so it is outside `MAX_LOOP_RUNS` ([loop-passes.md](loop-passes.md)). `orchestratorTurnRetry.test.ts` counts the stub CLI's invocations, which is the only evidence a second child was or was not started.

**`taskIds` on an emitted spec is not a sixth field on the list `emit_runs` refuses to grow, and it is not on the node at all.** A spec may carry the board ids of the tasks the run is for; they set no guard, pick no folder, do not change the brief and do not name who the run is, so they are nowhere near the line the five fields above are drawn against — and the emission moves nothing on the board: the run claims them when it starts and nothing closes one when it ends. `docs/agent/taskboard.md` holds that rule, and the one beside it that matters most on this unattended door: a spec whose text names an open task it does not list — in `taskIds` to work it, `relatedTaskIds` to mention it — refuses the whole emission, because a run that does a task it was not linked to cannot close it. It is on the **spec** rather than on the node for the reason the task text and the folder are: a saved graph is a shape a person agreed to, and which backlog item a particular pass is working is a decision the turn makes when it gets there, not a value frozen into the graph months earlier. An id that is not on the board refuses the **whole** emission by name, on `planEmission`'s all-or-nothing rule and `agentRefusal`'s wording — through `readTaskLinks`, so a block and a chat turn word it the same. `EmissionLimits` takes the board as a function rather than as data, unlike `agents` beside it, because the registry is curated where the backlog is not; the taskboard doc has the sizing argument.

**Acyclicity stops being a property of who wrote the graph, so it is checked as a property of the data.** `createRun` mints a run's id after reading its edges, which is why nothing could point at it and why a cycle was impossible by construction. That still holds for each individual insert — but the graph being inserted is now one a **model** wrote, and a cyclic set of specs has no creation order at all, so the first one would be refused for naming a run that does not exist rather than for the loop it is part of. `planEmission` therefore runs `dependencyCycle` over the specs and names the loop before anything is created, `admitDependencies` re-runs it over the whole live graph at every one of those inserts, and a spec may only depend on its siblings in the same emission — an edge onto a run the block did not create is an edge into a graph it cannot see. A spec's `dependsOn` that is present and not a list is refused by name rather than read as no edge, for the reason `chat/what-a-model-may-write.md` gives beside `propose_run`'s: here nobody reads the emission before the runs start.

**A block can land what the blocks in front of it built, and every protection that made `land.ts` safe stays where it is.** A merge block is a node whose `kind` is `merge`: no agent, no task, no template, no mount and no folder — it holds a strategy and one switch. When the instance reaches it, the runs its satisfied edges resolved to (the same `dependsOn` a run block would have been created with, so an orchestrator block's fan-out is covered with no second reading of what it emitted) go through `mergeQueue.enqueue` and nothing else. The block mints the batch id itself and writes `merge_batch_id` **before** that call rather than after it, which is a correctness requirement and not bookkeeping: that column is how the doors in `land.ts` tell this block from a person reaching in behind it — a pass's merge block is the only caller allowed to land a branch its own live pass owns — and `enqueue` starts the worker, so a row drained before the tie was written is refused by the guard the tie exists to lift, and the pass lands nothing for want of a statement a microtask away. A refused `enqueue` clears it again, so the column never names a batch that has no rows. That is the whole design: one merge in flight per repository, every item re-previewed against git at *its* turn, a conflict reconciled on the run's own branch in a throwaway checkout, and `landRefusal`'s requirement that the operator's checkout be clean *and* on the recorded target **not weakened** — a dirty tree halts that repository and the block says so, because landing onto the wrong branch is the one mistake here with no undo. The target is never named on the node, for `worktree_base_branch`'s reason: a run records where it branched from, and that is where it goes back to. `mergeAutoResolve` is the one thing it can spend, and it is on the saved graph rather than in settings for `merge_queue.auto_resolve`'s reason — configuration that can change under a graph already running is not authorisation — so `enforceInstanceBudgetForBlock` is consulted **only when it is on**, since halting a graph at a free step would leave work already paid for unlanded for a limit that block cannot move. Under the install-wide hold the queue refuses that resolution and still lands what needs none (`run-lifecycle/fleet-stop-hold-and-set-aside.md`). `mergeBlockOutcome` is the verdict, pure and unit-tested for `landRefusal`'s reason one level up: it decides whether the blocks *behind* the merge start, and both readings are silent — a chain that landed cleanly stopping with nothing to do, or a follow-up run starting on a target that never received the work. Its load-bearing distinction is skipped-versus-failed: a branch with no commits and one already merged both leave the operator with what they asked for, where a predecessor that *should* have had a branch and has none is isolation having degraded at run time, which is the case where silence would leave someone believing work landed. A branch can also reach its target after `branchVerdict` queued it and before its turn, and the queue then records it `already-landed`; `queuedBranchOutcome` is the one reading of a returned row, and it takes that as the same skip while the queue's own `skipped` — a repository the checkout halted — stays a failure. `blocksOf` counts an `already-landed` row as neither landed nor failed, as it counts a branch skipped before the queue. A merge block reuses `BlockStatus` verbatim rather than adding `merging`/`landed` — `thinking` and `emitted` are what every liveness query, every halt and both boot reconcilers key on, and two more words would be five more places to remember, one of them a merge running under an instance the page says is stopped; the page says "merging" and "landed", the column says what the machinery reads. An edge *out* of one carries no run at all (it created none), so its condition is the whole of what it says: `on-success` waits for every branch to land, `on-finish` is satisfied by the block finishing either way, and `blocked` — it never ran — satisfies neither, which is `edgeSatisfied`'s rule for a run that did no cycle. Two things are refused at *save*, where there is a person: a merge block on either end of a `continueBranch` edge (it has no checkout, so it has no branch to hand over or carry on) and one with no predecessor that runs something whose guards isolate — the second being the `fanOut` rule applied where it bites, since the alternative is a block that reaches the front of the graph and can only report that it was pointless.

**A block can publish what the blocks in front of it built, and it removes the person, so two doors stay shut.** A deliver block is a node whose `kind` is `deliver`: the merge block's sibling for the other exit, holding no strategy, switch, agent, template, mount, folder or task — `normalizeNode` drops every field that describes a run unread and refuses a named agent by name, as it does for a merge block. When the instance reaches it, the runs its satisfied edges resolved to (`InstanceStep.deliver`, the merge block's shape and its dedupe) go to `startDeliverBlock`, which calls `deliverRun` once for each and nothing else. **One at a time**, and that is not caution: `deliverRun` takes the `landing` claim on the operator's checkout and refuses a second delivery to that folder while it is held, so two in flight would fail the second for a reason that has nothing to do with its branch. Everything that decides whether a branch may leave stays in `deliverRun` and is not restated — the verify gate, the seeded-file refusal, the certification gate, the per-repository token, the claim and the shutdown gate — which is why the block can reach no remote the Land card's button could not. **It does not need the operator's checkout clean**, which is the question the block was written to answer: `deliverRun` reads `remote get-url` in the checkout and runs `push --set-upstream` there, which writes `.git/config` and nothing in the working tree, and it never reads `landState`'s `blocked`, which is where the dirty-checkout and wrong-branch refusals live. `deliverBlockRun.test.ts` pushes with a dirty tracked file and an untracked one in the checkout. What it does refuse is a run working *in that folder* and a second delivery holding the claim, and each arrives as one failed branch with its sentence. So the two failures that sent this here — "the checkout has uncommitted changes" and "git refused the merge" — do not recur; nothing else of the merge block's trouble is claimed away, and a pull request can still conflict on GitHub where nothing here looks.

`deliverBlockOutcome` is the verdict, pure and unit-tested for `mergeBlockOutcome`'s reason, and it draws the same line between skipped and failed: a branch with no commits, one already on its target and one that already carries a pull request (`deliveredPullRequest`, the Land card's own rule, since a second push would be refused by GitHub's "already exists") are skips; a predecessor that should have had a branch and has none, and any refusal `deliverRun` gives, are failures. A failed branch does not stop the ones after it. The note is never null when something was delivered, unlike the merge block's, because the pull request's address is the whole product and the instance page has nowhere else to read it. Its outgoing edges read as a merge block's — `on-success` when none failed, `on-finish` either way, neither when it never ran — through the same `edgeVerdict` arm, and it settles through `finishMergeBlock` on the same `BlockStatus`. The two SQL sweeps that pick a sentence by block kind, `haltBlocks` and `reconcileBlocksOnBoot`, carry a `deliver` arm by parameter position, and `bootBlocks.test.ts` pins both. **A failed deliver block is retried from the instance page, through the merge block's door.** `pickUpsOf` offers it as `kind: "deliver"` — the merge pick-up's member widened by `kind` rather than a block-retry kind, so the sheet's wording ("push the branches it missed", not "land") and the route's `retry-deliver` action stay per exit — and `retryDeliverBlock` and `retryMergeBlock` are both `retryExitBlock`, so the two guards (nothing behind it has started, `startedBehind`; and `loopPassRefusal` inside a pass, unreachable while a section may not hold a deliver block) cannot drift between them. What makes a repeat safe is delivery's own: `deliverBranch` asks `deliveredPullRequest` before any git read, so a branch the first try opened a pull request for is skipped and never pushed again, and the retry's note, which replaces the first's, still carries that address in the skip. `deliverBlockRun.test.ts` fails one of two branches on a verify command, retries with it satisfied, and pins that each branch is pushed once.

**A branch refused because a land or a run holds its checkout is failed, not waited for, and that was decided.** The merge queue waits on `checkoutHeld` with no clock (`isolation-and-landing/merge-queue.md`), because a drain that recorded the hold against a row failed a repository's whole queue within fifty milliseconds. A deliver block meets the same hold one branch at a time and fails each in turn with the same sentence, and it was not given the wait for three reasons. The retry above is the way through, costs one press and cannot repeat work. Waiting needs `deliverRun`, which the Land card's press shares, to mark the refusal as a hold the way `landRun` marks `heldCheckout`, and a poll loop in `deliverBranch` with its own reads of the halt latch and the shutdown. And the wait has no bound and nowhere to say what it waits on: a run working in that folder holds it for as long as it works, and a block `thinking` behind it would read as stuck, where the merge queue's panel at least names what holds a row. Revisit if a graph that delivers beside a merge block proves common.

Each of the merge block's save-time refusals was decided for delivery rather than copied. `continueBranch` at either end is **kept**, on the merge block's ground: it cuts no branch and extends none. A predecessor whose guards isolate is **kept**, since `deliverRun` answers a branchless run with "no branch to deliver" an hour in. At least one predecessor that runs something is **kept with a different set**: a merge block, a loop and another deliver block hand on no runs, so none counts as something to push — a deliver block behind a merge block would be asked to open a pull request from a branch already on its target — and a merge block does not count a deliver block as something to land, for the same reason. And **a loop section may not hold one**, which the merge block has no counterpart to: each pass would push and open pull requests with nobody pressing anything, up to the pass cap, and a pass already lands its own work through its merge block. The two doors it shuts are the ones that take the person out of the press. A schedule keeps the press and removes the person, so `scheduleRefusal` refuses a workflow holding a deliver block — at the door and at every fire, however well its budget bounds the spend, because spend is not what leaves the machine. And a chat cannot draft one: `propose_workflow` refuses the kind by name, though `normalizeWorkflowInput` accepts it from the editor, because the approval card describes a block as "no agent" beside blocks that only write to disk. Either is one line to lift when the operator decides otherwise, and neither is the way round. Which process holds the credential is in `security/child-uid-and-credentials.md`.
