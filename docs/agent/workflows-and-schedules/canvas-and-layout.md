# The workflow canvas and block layout

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `src/components/WorkflowCanvas.tsx` or `src/components/WorkflowEditor.tsx`, or `resolveLayout`, `autoLayout`, `draftToGraph` and `bodyOrder` in `src/lib/canvasGraph.ts`.

**A workflow is drawn on a canvas, and where a block sits is not part of it.** The obvious home for a coordinate is `WorkflowNode`, and it is wrong twice over: `normalizeWorkflowInput` rebuilds each node from a fixed list of fields, so an `x`/`y` would be dropped in passing and the drag would silently not persist; and let through, it would make moving a block two inches a rewrite of the object `topologicalOrder` reads, bumping `updated_at` and landing in the blob an instance copies. So the graph is untouched and a position is a *view* of it — held per browser under `uf.workflow-layout.<id>`, and reconciled by `resolveLayout` against an arrangement `autoLayout` derives from the edges. That derivation is what makes "a graph saved before the canvas opens readable" true with **no migration at all**, which is the only way to be sure a layout change cannot lose an edge; the cost, stated rather than absorbed, is that a hand-made arrangement does not follow the operator to another browser. `autoLayout` is bounded rather than run to a fixed point because it has to be able to draw a **cycle**: refusing a loop is `normalizeWorkflowInput`'s decision and it can only answer about a graph it has been sent, so one is on screen between the second click and the answer, and an unbounded relaxation there is a frozen tab that typechecks. It reserves the height of a frame's strip above its first row wherever the graph holds a loop block, and the condition is the **kind** rather than actual membership: a layout that gained the reservation the instant somebody pressed Repeat would move every card away from the hand that was reaching for one. **Nothing in the browser decides what a workflow may be.** `POST /api/workflows/validate` calls the same `normalizeWorkflowInput` and the same `folderRefusal` the save route calls, with the same `currentKnowledge()`, and the editor renders the sentence it gets back — a second copy of those rules in the client would be a second set to keep in step, confidently wrong about what Save would do the day one of them changed. That route answers **200 for a refusal**, because a 400 is indistinguishable from the route being unreachable and the editor says different things in those two cases; Save stays enabled behind it for the same reason, since a disabled Save behind a failed advisory check strands the operator with no way to reach the authority at all. A drawn link carries `edge: ""` all the way onto the wire and is refused by name: `on-success` terminates a chain the operator meant to run regardless and `on-finish` starts a run on top of a dependency that crashed, so the picker offers the unanswered state as a real option rather than pre-selecting one. The picker's third option, `repeats`, is offered **only** where the source is a loop block and is drawn distinctly — the **frame** and no arrow at all, because drawing containment as an arrow is what made the picture ambiguous — an arrow from a loop to its entry reads as "the section runs after the loop"; the Repeat gesture and the frame's Put in handle are what write that link, both with their keyboard route, and `handledByPointer` covers the second for the reason it covers Link. Adding a block, linking two and removing a link each have a keyboard route as well as a pointer one, and `handledByPointer` is what keeps them from both firing — a captured pointer sequence still dispatches a trailing `click`, which would otherwise add a second block or disarm a link that had just been drawn; the `click` handler stays because it is also what a screen reader dispatches, with no pointer events in front of it. There is no canvas library: the drag is `setPointerCapture` and the edges are cubics in an SVG overlay, about 4 kB over the form this replaced. **The surface is a framed pane and the selection is a halo, never a border.** The frame is a toolbar strip (the palette, and the block and link counts), a recessed scroll region standing on a faint `dot-grid`, and a footer naming the gestures — the grid is the only cue that an arrangement is somebody's rather than the app's. Replacing a card's border on selection is what this had before and it cost the one thing that border is for: an orchestrator block wears the warn edge permanently *because* it starts runs with no approval, and painting it accent at the moment somebody selected it withdrew that statement exactly when it was being read. A ring is outside the box and sets a different property, so both facts are on screen and neither class string can outrank the other. **Delete removes the selection, and there is no undo.** The surface handles it for whatever the inspector is showing; a block's name and a link's condition chip handle it for their own identity and stop it there, so the *focused* thing wins over the *selected* one on the rare occasion Tab has moved them apart. `preventDefault` on that key is load-bearing rather than tidy — Backspace outside a text field is the browser's own Back on more than one engine, and losing the whole draft to it is worse than anything this key is for. A ⌘Z was considered and rejected: this app has no undo model, and one that put a block back without its links, or without the position it was dragged to, is worse than the absence because the operator stops checking. What stands in for it is that nothing on the canvas is saved until Save. **And because nothing is saved until Save, no exit may take the graph without asking.** `draftSignature` in `canvasGraph.ts` is what decides there is anything to lose: the body a save would send, against the signature taken when the page mounted rather than against a re-derivation of the saved workflow, so a graph opened for editing and not touched is never dirty. It reads `draftToGraph`'s output rather than the drafts behind it, so a fan-out typed into a block that is not an orchestrator raises nothing — a dialog over a page with nothing to lose is how an operator learns to dismiss the next one unread. The layout is deliberately outside it, for this file's neighbour's reason: `writeLayout` has already persisted the arrangement per browser, so a dragged box survives the tab that a typed task does not. `beforeunload` covers exactly one exit — the closed tab, the reload, the typed URL — and the other four are client-side navigations it never fires on. `exitHref` in `unsavedWork.ts` decides which clicks are one of those, and the editor stops them in the **capture** phase with `stopPropagation` as well as `preventDefault`, because `next/link` navigates from a React handler at the root container that reads neither the default nor who prevented it. ⌘ 1…⌘ 9 and quick open are `router.push` calls in the shell with no event to stop, so they ask `leaving()` instead, against the single guard `registerLeaveGuard` holds — and its disposer clears only its own registration, because a route change runs the leaving page's cleanup after the arriving page's setup. Browser Back is the one exit left uncovered, and it is stated rather than absorbed: intercepting `popstate` means pushing a sentinel entry nobody made and re-pushing it against the router's own restore, which corrupts the history stack in exchange for a dialog, and the graph is one Forward away. **The inspector is a sticky column beside the canvas, not a form under it**, and every block states in one sentence what a press of Run is approved against — which template supplies its guards or that it takes the untemplated set from Settings, where it runs, which saved agent its child is started as, how many runs a deciding block may start with nobody looking, and whether a merge block may pay to reconcile a conflict. `BlockStatement` is that sentence and it is prose on purpose: those five facts were five separate pickers to read off, and the card the operator approves against has to say them rather than imply them. The agent is stated *outside* the guard clause and its picker sits outside the guards group, because an agent bounds nothing — a phrase inside "under …" would claim it does — and the picker declares the ambient set beside itself for the reason the run form's does: the registry is a part of the set and not the whole of it.

**Containment is never derived from where a block sits, and the frame is where an operator sees it.** A loop is drawn as a **frame** round its section and has no card at all — what a loop *is* is a boundary, and a card beside its members would draw it as a seventh block in a graph of six. What an operator approves is what they can see, so the frame's strip carries everything the card used to: the name, how many blocks are in a pass, the pass cap, the endings, a Link handle for what runs before and after the whole loop, and the handle that puts a block in or takes one out. But the *arrow* is what makes the section and the frame is a reading of it, never the other way round. A box dragged inside the frame joins nothing, and a member dragged out of it leaves nothing: `sectionOf` walks links, and `positions` is a view held per browser under `uf.workflow-layout.<id>` that `normalizeWorkflowInput` never sees. Reading membership off geometry would fail in the direction that costs money and says nothing — a block nudged over a boundary would quietly start running once per pass, on a layout that does not even travel to another browser. **The frame itself may never gain a coordinate**, which is the canvas's own rule read one shape along: `normalizeWorkflowInput` builds a node from a fixed list of fields, so an `x`/`y` on a frame would be dropped on the way through and the drag that set it would silently not persist. `bodyRegions` therefore bounds the frame by where the members already sit — `positions`, which `resolveLayout` has reconciled — and clamps it to the surface rather than pushing anybody's block aside to make room. Three consequences are deliberate and are the price of that. A frame with **nothing in it** is still drawn, round the loop's own coordinate and sized like a block: the frame is the only thing on the canvas that can select or delete a loop, so one that vanished when its last member was deleted would leave the loop in the graph with no way to reach it but abandoning the draft. `autoLayout` reserves the strip's height above the first row wherever the graph holds a loop — condition on the **kind** rather than on actual membership, so the layout does not jump the moment somebody presses Repeat and move every card away from the hand — and where a member has been dragged against the top edge anyway the frame is clamped and the **strip** is what goes under the card, not the block. And a bounding box over members laid out either side of the loop's own coordinate **encloses it**; that is the arrangement saying the section is scattered, not a defect to special-case, and the operator's answer is to drag, or to link the scattered block on towards the merge the section ends at — which is what the server is refusing at the same moment.

**The client orders a body by the body's own edges, and it has to be the same order the server will run it in.** `bodyOrder`, reached through `sectionOf`, is `loopBody`'s reading on the canvas: the frame marks its members by it, the inspector reads it back, and `BlockStatement` is the sentence a press of Run is approved against — so an order taken off anything else would look exactly like a section that ran, and run it in a different order. They agree because both use the body's **own** edges and nothing else, ignoring every edge that crosses the boundary. A body that is not yet one way in and one way out is the ordinary state of one being assembled, and `bodyOrder` answers deterministically for it — rank first, walk order second — rather than refusing: the refusal is the server's, it is already under the canvas, and a second opinion in the browser would be a second set of rules with nothing to notice them drifting. `sectionExit` is the same judgement about the other end and answers **null** where there is not exactly one sink and it is not a merge block, rather than naming one of them: a graph this surface has not had judged yet may not promise where an operator's work lands. The relaxation both `bodyOrder` and `autoLayout` use is `longestPathRank`, **bounded by the number of ids rather than run to a fixed point**, because a section being assembled is disjoint, forked or cyclic for as long as it takes to assemble and an unbounded loop there is a frozen tab that throws nothing and typechecks.
