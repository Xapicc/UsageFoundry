# Workflow nodes and instantiation

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing what a workflow node may hold (`planNode` in `src/lib/workflows.ts`, `normalizeWorkflowInput` in `src/lib/workflowGraph.ts`), instantiation in `startWorkflow`, or `planInstanceStep` and `advanceInstances`. What `planInstanceStep` decides for a block that emits nothing, an `on-failure` link and a run a restart closed out is in [instance-step-verdicts.md](instance-step-verdicts.md).

**A workflow is the third thing here that is form input, and it is not the fourth route to `--permission-mode`.** `workflows` holds a name, a graph and one budget for the whole instance (see [instance-budget.md](instance-budget.md)); a node in it holds the *work* — mount, folder, task, an optional prompt override — and names a **template** for every guard and for the model, or names none and takes `settings.chatDefaultGuards`, which is a guard set and holds no model, so a node under it names none. That is `planProposal`'s rule reused rather than restated, and `planNode` is deliberately shaped like it, down to refusing a node whose template has been deleted **by name** instead of falling back to the untemplated set: the operator saved a graph that said "under these guards". There is no `permission_mode` column, no budget blob and no model on a **node**, so the three narrowings stay three and the two routes to that flag stay two — and "no model on a node" now reads as one more thing a node names its template for, rather than as an absence with nowhere to come from — the instance budget is on the workflow rather than on a node precisely because it bounds the graph and not a block, and it holds none of those three. Prompt text is the one exception and the same one a proposal makes — `promptOverride` replaces the template's standing instructions for one node, joined to the task by the *same* `composeTask`, so how the two halves are ordered and marked has one definition. The mount and folder are on the node rather than inherited from its template, which is where this *diverges* from a proposal: a proposal is approved minutes after it is written, where a workflow is saved once and run for months, and a template edited in between would silently move a node's run to another repository with nothing in the graph changing. **The agent is on the node for that same reason and is deliberately not inherited either**, which is the one place a workflow block and the run form read a template differently: the form applies one as a seed for every field, where a node reads one for exactly three things — its guards, through `guardsFor`; the standing instructions `promptOverride` replaces; and, since `run_templates` grew one, the model. `run_templates.agent_id` therefore decides nothing about a block, and `guardsFor` still returns three fields, which is the absence this whole design rests on — the model is passed beside its return rather than added to it, precisely so that a guard helper stays a guard helper. The model joins the inherited list on the ground that keeps the agent off it: it moves cost and never capability, and a node has no model of its own for it to override, where a node names its own agent. It is an **id** rather than a copy, `run_templates`' rule and the opposite of `runs.agent`'s: a graph is applied again and again, so an operator who fixes their reviewer's prompt expects the next press of Run to use the fixed one, and the copy is taken where it always is, by `createRun`, so an agent deleted between two blocks of one instance cannot reach a run already started. It carries no capability — an agent holds no tool list and no permission mode — so this is not a fifth route to `--permission-mode`; and it is refused **by name** at save, at `/api/workflows/validate` and at instantiation, through the same `agentRefusal` the run door and the template door use, never falling back to none. Which child it names differs by kind and the field does not: a run block's own run, an orchestrator block's *deciding turn* (the runs that block emits name their own, per spec — the opposite way round from `promptOverride`, which it holds on behalf of those runs, because standing instructions are what a run is asked and the deciding turn is asked by `blockSystemPrompt`), and a merge block **none**, where one is refused rather than dropped: that block spawns no child at all, so there is nothing for the named agent to *be* — accepting it would be this app quietly discarding a choice the operator made, at the one door built to end exactly that. Everything else follows `run_templates` — no folder claim, no concurrency slot, invisible to `activeRuns()`, and deleting one cannot reach a run that has already started. A node's `kind` is the one thing that changes what it *becomes* rather than what it says: `run` is a fixed run and the default, because every graph saved before this existed says nothing there and the other reading would turn one of them into a graph that starts agents nobody wrote. `orchestrator` is the other, and it adds exactly two fields a node may hold — `fanOut`, which is not nullable, and `turnRetries`, which is optional and absent is 0 — and no route to a guard; see the orchestrator-block invariant in [orchestrator-and-merge-blocks.md](orchestrator-and-merge-blocks.md).

**A workflow is instantiated in topological order, in one synchronous pass, all or nothing.** `topologicalOrder` — in `orchestrator.ts`, beside `dependencyCycle`, because a saved graph, an orchestrator block's emitted specs and a batch of approved chat proposals all create runs in one pass and all need one answer to "every one after what it waits for" — is pure and unit-tested because both ways of being wrong are silent: a node released before its dependencies exist is a `createRun` whose `dependsOn` names rows that are not there, and an unplaceable node is a row that sits `waiting` for ever — `releasableRuns` reaches a fixed point and leaves it alone, which is the one outcome the dependency design has none of. Ties break on the node's declaration order, so two presses of Run on one graph produce the same queue; runs are admitted oldest-first and a queued run reserves its folder against everything younger, so an unstable order would silently reorder work on one repository. The pass itself has no `await` between the `createRun` calls, for the reason the chat's approval route batches: the folder claim is only atomic inside one event-loop turn. Everything checkable is checked *before* anything is created — the graph against the templates and mounts that exist now, `resolveWorkspaceFolder` for every node, and every node's guards — so a mid-pass failure should be unreachable; if one happens the created runs are **stopped** (never deleted: one may already hold a checkout and a child, and the row is what the kill path and `reconcileOnBoot` need) and the instance is recorded `failed` with the reason. Half a graph is not a smaller workflow. Re-running into a folder a previous instance is still working in is refused with a sentence rather than left to chance — per folder rather than per workflow since the folder list, by the rule in the last paragraph here. `normalizeWorkflowInput` refuses the same things at *save* that instantiation does — the `normalizeTemplateInput` rule, because a graph that can be saved and never started fails weeks away from the form that caused it — and it takes the templates, mounts and default isolation as an argument rather than reading them, which is what makes it pure and what makes "saved, then no longer startable" a sentence instead of a surprise. `folderRefusal` is the one check that is *not* in it, because it is a syscall; it runs beside it at both moments.

**One saved graph may run against more than one folder, and every folder it may work in is one a person saved on it.** `workflows.folders` is a list of `{mountId, folder}` saved with the graph, and a run or orchestrator block that carries `followsChosenFolder` works in the one a press of Run chose; every other block keeps its own, so a block with a folder of its own never changes meaning, and a graph saved before the list existed has no flag and no list and starts exactly as it did. The rule above — the folder is on the node, so a saved graph cannot silently move repositories — holds one level up: the list is saved by a person in the editor, `normalizeWorkflowInput` refuses an unmounted or duplicated entry and `listedFolderRefusal` one that does not resolve, both at every save door, and Run *chooses among* the list rather than reading a path. `chooseFolder` is that choice, pure and unit-tested because both ways of being wrong are silent: an entry is accepted only if it is **exactly** a saved one, a choice sent to a workflow with no list is refused rather than dropped, several saved and none chosen is refused rather than guessed, and a schedule — with nobody to ask, and no field on `workflow_schedules` that could name another — takes the **first**, so reordering the list is a saved edit that moves the schedule, the same as editing a block's folder. A flagged block still *stores* a concrete folder, the first saved one, written by the normalizer and never typed: every reader of a saved graph other than instantiation then reads a folder a person saved, where the absence the flag replaces would have been `""`, which is the mount root. `withChosenFolder` applies the choice once, at `startWorkflow`, to the graph the instance copies, before the plans, `folderRefusal` and the isolation probe, so the chosen folder is checked as a block's own is; every later reader — a deferred block, each loop pass, an orchestrator block's bounds and the folder its emitted runs are held to — reads it off that copy and never off the workflow, and `workflow_instances.chosen_folder` records it, a copy with no route that writes it, the instance budget's rule. An orchestrator block learns which project its shared brief is about from its bounds, which already name its folder, plus one sentence `blockSystemPrompt` adds only for a block that follows the choice; a block with its own folder is asked exactly what it was. One thing is deliberately left out: a chat cannot propose a list. `propose_workflow` passes none, so a block flagged by a model is refused by the same normalizer, and the approval card has no list to show. Two presses against two folders at once is the next paragraph's rule. A loop's `stopWhenTasks` follows the choice only when its own `followsChosenFolder` is set, and it is the condition that carries the flag, not the loop, which names no folder: `normalizeBoardCondition` stores the first saved folder in it as a block does and reads its typed `mountId`/`folder` unread, and `withChosenFolder` rewrites that pair on the instance's copy, so `advanceLoop` and `loopBoardCount` read the chosen project off the instance and never the workflow, and `folderRefusal` resolves it there before the instance exists. A condition without the flag keeps its own project exactly — a loop that does not follow counts the board it names whichever folder Run chose — and a following condition counts as something the list is followed by, so a list only a loop's condition follows is accepted.

**Two presses of one workflow run at the same time only when they share no folder — an authorisation rule, since it decides where unattended agents work side by side.** `startWorkflow` refuses a press only when a live instance works in a folder it would. `sharedFolderRefusal` decides, pure and unit-tested beside `chooseFolder`, because a press let in wrongly is the same block twice in one repository and one refused wrongly is the list not doing what it was saved for. Compared are every run and orchestrator block's folder (`workingFolders`; an orchestrator's covers the runs it emits), off the live instance's own graph copy and off the chosen graph, by the folder claim's `overlaps` over `conflictKey` — never path equality. So a block **with its own folder** is shared by every press and keeps the refusal standing whichever folder is chosen, and a graph saved before the list, being all such blocks, runs one press at a time as before; a folder that cannot be placed, or a stored graph that cannot be read, shares everything, the old rule's direction; a loop's board condition works in nothing and is not counted. The check runs after `withChosenFolder` and `folderRefusal`, in the creating pass's `await`-free turn. `liveInstancesOf` reads both halves for the reason [instance-pick-ups.md](instance-pick-ups.md) gives the page, and deleting the workflow is still refused while any instance is live. The page and a schedule ([schedules.md](schedules.md)) read the same function. Every pick-up door asks it too, of the other live presses ([instance-pick-ups.md](instance-pick-ups.md)).
