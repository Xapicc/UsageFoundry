# Workflow nodes and instantiation

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing what a workflow node may hold (`planNode` in `src/lib/workflows.ts`, `normalizeWorkflowInput` in `src/lib/workflowGraph.ts`), instantiation in `startWorkflow`, or `planInstanceStep` and `advanceInstances`.

**A workflow is the third thing here that is form input, and it is not the fourth route to `--permission-mode`.** `workflows` holds a name, a graph and one budget for the whole instance (see [instance-budget.md](instance-budget.md)); a node in it holds the *work* — mount, folder, task, an optional prompt override — and names a **template** for every guard and for the model, or names none and takes `settings.chatDefaultGuards`, which is a guard set and holds no model, so a node under it names none. That is `planProposal`'s rule reused rather than restated, and `planNode` is deliberately shaped like it, down to refusing a node whose template has been deleted **by name** instead of falling back to the untemplated set: the operator saved a graph that said "under these guards". There is no `permission_mode` column, no budget blob and no model on a **node**, so the three narrowings stay three and the two routes to that flag stay two — and "no model on a node" now reads as one more thing a node names its template for, rather than as an absence with nowhere to come from — the instance budget is on the workflow rather than on a node precisely because it bounds the graph and not a block, and it holds none of those three. Prompt text is the one exception and the same one a proposal makes — `promptOverride` replaces the template's standing instructions for one node, joined to the task by the *same* `composeTask`, so how the two halves are ordered and marked has one definition. The mount and folder are on the node rather than inherited from its template, which is where this *diverges* from a proposal: a proposal is approved minutes after it is written, where a workflow is saved once and run for months, and a template edited in between would silently move a node's run to another repository with nothing in the graph changing. **The agent is on the node for that same reason and is deliberately not inherited either**, which is the one place a workflow block and the run form read a template differently: the form applies one as a seed for every field, where a node reads one for exactly three things — its guards, through `guardsFor`; the standing instructions `promptOverride` replaces; and, since `run_templates` grew one, the model. `run_templates.agent_id` therefore decides nothing about a block, and `guardsFor` still returns three fields, which is the absence this whole design rests on — the model is passed beside its return rather than added to it, precisely so that a guard helper stays a guard helper. The model joins the inherited list on the ground that keeps the agent off it: it moves cost and never capability, and a node has no model of its own for it to override, where a node names its own agent. It is an **id** rather than a copy, `run_templates`' rule and the opposite of `runs.agent`'s: a graph is applied again and again, so an operator who fixes their reviewer's prompt expects the next press of Run to use the fixed one, and the copy is taken where it always is, by `createRun`, so an agent deleted between two blocks of one instance cannot reach a run already started. It carries no capability — an agent holds no tool list and no permission mode — so this is not a fifth route to `--permission-mode`; and it is refused **by name** at save, at `/api/workflows/validate` and at instantiation, through the same `agentRefusal` the run door and the template door use, never falling back to none. Which child it names differs by kind and the field does not: a run block's own run, an orchestrator block's *deciding turn* (the runs that block emits name their own, per spec — the opposite way round from `promptOverride`, which it holds on behalf of those runs, because standing instructions are what a run is asked and the deciding turn is asked by `blockSystemPrompt`), and a merge block **none**, where one is refused rather than dropped: that block spawns no child at all, so there is nothing for the named agent to *be* — accepting it would be this app quietly discarding a choice the operator made, at the one door built to end exactly that. Everything else follows `run_templates` — no folder claim, no concurrency slot, invisible to `activeRuns()`, and deleting one cannot reach a run that has already started. A node's `kind` is the one thing that changes what it *becomes* rather than what it says: `run` is a fixed run and the default, because every graph saved before this existed says nothing there and the other reading would turn one of them into a graph that starts agents nobody wrote. `orchestrator` is the other, and it adds exactly two fields a node may hold — `fanOut`, which is not nullable, and `turnRetries`, which is optional and absent is 0 — and no route to a guard; see the orchestrator-block invariant in [orchestrator-and-merge-blocks.md](orchestrator-and-merge-blocks.md).

**A workflow is instantiated in topological order, in one synchronous pass, all or nothing.** `topologicalOrder` — in `orchestrator.ts`, beside `dependencyCycle`, because a saved graph, an orchestrator block's emitted specs and a batch of approved chat proposals all create runs in one pass and all need one answer to "every one after what it waits for" — is pure and unit-tested because both ways of being wrong are silent: a node released before its dependencies exist is a `createRun` whose `dependsOn` names rows that are not there, and an unplaceable node is a row that sits `waiting` for ever — `releasableRuns` reaches a fixed point and leaves it alone, which is the one outcome the dependency design has none of. Ties break on the node's declaration order, so two presses of Run on one graph produce the same queue; runs are admitted oldest-first and a queued run reserves its folder against everything younger, so an unstable order would silently reorder work on one repository. The pass itself has no `await` between the `createRun` calls, for the reason the chat's approval route batches: the folder claim is only atomic inside one event-loop turn. Everything checkable is checked *before* anything is created — the graph against the templates and mounts that exist now, `resolveWorkspaceFolder` for every node, and every node's guards — so a mid-pass failure should be unreachable; if one happens the created runs are **stopped** (never deleted: one may already hold a checkout and a child, and the row is what the kill path and `reconcileOnBoot` need) and the instance is recorded `failed` with the reason. Half a graph is not a smaller workflow. Re-running while a previous instance still has live runs is refused with a count rather than left to chance: the second instance points the same nodes at the same folders, and a node continuing a branch would be refused mid-pass because the first instance's run already continues it. `normalizeWorkflowInput` refuses the same things at *save* that instantiation does — the `normalizeTemplateInput` rule, because a graph that can be saved and never started fails weeks away from the form that caused it — and it takes the templates, mounts and default isolation as an argument rather than reading them, which is what makes it pure and what makes "saved, then no longer startable" a sentence instead of a surprise. `folderRefusal` is the one check that is *not* in it, because it is a syscall; it runs beside it at both moments.

**A block that emits nothing blocks what is behind it, and that is a decision rather than a fallout.** `planInstanceStep` is `releasableRuns` for the half of a graph that is not runs yet, pure and unit-tested for the same two silent failures, and it reads `edgeSatisfied`'s rule one level up: a dependency that did no work satisfies nothing. A block behind a fan-out exists to review it, land it or follow it up; started with nothing in front of it, it spends a billed cycle finding that out, where `blocked` costs nothing and names the block that decided there was nothing to do. A block that decided on runs none of which could be created blocks what is behind it just the same, but `edgeVerdict` says so rather than blaming the decision — `InstanceNodeState.block` carries the decided count and the block's notes for that sentence, from `instanceState` and `loopPasses` alike, since both feed the one reader. Nodes behind an orchestrator block are **not created** at `startWorkflow` — their edges would name runs a model has not decided on yet — so each holds a `waiting` row in `workflow_instance_blocks` instead, which costs nothing for the reason `waiting` costs nothing one level down: no folder, no checkout, no place in the queue. A node is created only once every edge into it is *satisfied* rather than merely resolvable, so its edges are recorded on a run `admitDependencies` then re-checks, and a node that becomes a run gives up its ledger row so it is never in both tables. The cascade is the same fixed point `releasableRuns` uses, so every link gets its own sentence naming the one in front of it. `advanceInstances` is called from `releaseDependents` — one place rather than the five call sites that would have to be kept in step — and it is synchronous end to end for `createRun`'s reason, with a guarded UPDATE claiming each turn so two overlapping passes cannot both spawn one. A restart closes out **every** unsettled block of an instance it left nothing alive in, not only the ones behind a turn in flight: `on-finish` is satisfied by a run that did a cycle and then died with the container, so a block left `waiting` would be released into an unattended agent hours after anyone asked for it — which is `reconcileOnBoot`'s rule for a queued run. **Unless a member survived that same boot**, and that is `reconcileOnBoot`'s own exception rather than a second one: a `paused` run inside `settings.resumeGraceHours` is kept, because it is a run the operator started in a mode chosen precisely so it would carry on across a restart. Every premise above fails for the blocks behind it — nothing they are waiting for was closed out, the sweeper *will* wake it, and the agent the next advance starts is the one already being paid for and waited on. Closing them out anyway wrote off the tail of a live graph, under a sentence claiming the run in front of them had been closed out by the restart while it was parked and about to resume. So the question is asked per instance: `bootBlockPlan` is that decision, pure and unit-tested for `haltPlan`'s reason, and it reads `LIVE_STATUSES` rather than testing for `paused`, so what survives is decided in one place. It tests `started` **positively** rather than merely excluding a halt: a `stopping` instance's blocks still come down whatever its members are doing, and a `failed` one is `startWorkflow`'s own rollback, which wrote every other block off in the same pass — reviving half of either is a graph nobody finished building, started again. Ordering is what makes the survivors readable rather than guessed at — `src/instrumentation.ts` runs `reconcileOnBoot` first — and a spared block is decided later by `planInstanceStep`, off what is true when the member settles.

**An `on-failure` link is drawn only out of a run block and only outside a loop, and a node on the branch it did not take is `not-needed` in the ledger as it is in `runs`.** `planInstanceStep` has a third verdict beside `block` for it, `notNeeded`, and `edgeVerdict` reads a run block's run through `edgeSatisfied` and `notNeededReason` — the same two functions `releasableRuns` asks — so a node deferred in the ledger and a node created up front as a `waiting` run are passed over alike, and a run that was `stopped` blocks the node with a sentence saying a stop is not a failure. Every kind of predecessor whose own row is `not-needed` hands that on along every edge (`passedOverBehind`), and a blocked verdict on another edge outranks it, `releasableRuns`' order. `BlockStatus` gains `not-needed` for the ledger's half: settled, never started, counted by `memberTally` as neither live nor blocked, so an instance whose only unrun members were passed over reads `finished` rather than `blocked`; `reviveGraphDependents` wakes one as it wakes a blocked one, and `startedBehind` reads it as not started. `normalizeWorkflowInput` refuses the link out of an orchestrator, merge, deliver, review or loop block by name: each settles in words of its own — a merge that did not land everything, a turn that decided nothing, a review that set work aside, a loop that stopped on a pass — and which of those a fixer should start on is a decision nobody has made. It refuses one with either end inside a section, because a pass would have a member that is neither unfinished nor DONE and `planLoopPass` has no reading for it; `stepPass` still writes a `notNeeded` verdict rather than leaving the member `waiting` for ever. An orchestrator block's own `emit_runs` keeps the two older conditions (`EMITTED_EDGES`): the block behind it waits for every run it emitted, and has no way to wait for one that was not needed. The canvas offers the condition on a link out of a run block and keeps it on a link that already carries it, so Save can say why.

**A run a restart closed out blocks every edge out of it until it is picked up, and what it holds back is revived rather than failed.** `edgeVerdict` asks `restartClosed` ahead of the edge test, on either condition, for a run node's run and for every run an orchestrator block emitted — `releasableRuns`' rule, read through the same `restartClosedSql`. `InstanceNodeState.run` and `emitted` are `ReleaseState` for it, required for `refundedCycles`' reason, built by `instanceState`, `loopPasses` and `approvedRunsOf` alike. The boot's closing-out was not enough on its own. A block written off at the boot is revived through `reviveBlockedBlocks` by picking up *any* member it can be reached from, and the next advance then read the restart's `stopped`, with a cycle counted, as `on-finish` satisfied for the members nobody had picked up. Each kind of block behind it met that differently. A deferred run node hit `createRun`'s refusal and went `blocked`, which is right by accident. A loop's first pass member hit the same refusal, which by reading the code leaves the loop `failed`, where the revive does not reach. Orchestrator, merge and review blocks create no run, so they went ahead. In `shutdown.test.ts` a merge block behind two closed-out runs was claimed and handed both branches by the release pass the shutdown's own ending ran, before anybody picked anything up. Blocked, never pending and never failed: nothing obliges anybody to pick the run up, and `blocked` is the one ending the pick-up revives, so the sentence names the run and says that. A run the operator left behind is waived ahead of the check, since carrying on without it is a decision already taken. A review block's approved runs are not asked, `reviewVerdict`'s rule: the review is the verdict on them.

**A gate is a block that waits for a person, and it is a ledger row that never has a turn.** `gate` is the seventh `WorkflowNodeKind` and the only one whose job is to *not* proceed: when the instance reaches it, nothing is spawned, billed or created, and everything behind it waits until the operator presses Continue on the instance page. Approval used to happen once, at save, and after that the only lever was Stop — 7 of the 26 settled loops measured on this install ended in an operator stop, each before its merge landed anything — so a gate is the place a person is asked *again*, at a point the graph names. It holds **no agent, template, workspace, folder, task or prompt**, and `normalizeNode` refuses each of those **by name** (`GATE_IS_TOLD_NOTHING`, `LOOP_IS_TOLD_NOTHING`'s treatment and for its reason: a template chosen for a block that starts nothing is a choice no process will act on, and this is the door built to say so out loud). It is `startsNoRun`, skipped by `planNode`, `folderRefusal` and `startWorkflow`'s plan loop with the other four. A gate with no link out is refused: it would stop the instance for a press that releases nothing.

**It is `waiting` the whole time, and `held_at` is the only thing that says it was reached.** A new status would be five more places that must name it — the docblock over `BlockStatus` says why `looping` was the last exception — and "costs nothing, as a `waiting` row does" is already true of a row that is `waiting`. `planInstanceStep` lists a gate whose every incoming edge is satisfied in `InstanceStep.hold`, on every plan until it is let through; `holdGate` writes `held_at` with an UPDATE guarded on `held_at IS NULL`, and that guard is the *once*: the notification goes out when it changes a row and not before or after. Continue (`continueGate`, `POST …/instances/[instanceId]/continue`) writes `emitted`, guarded on `waiting` and on `held_at IS NOT NULL`, so a press on a gate not yet reached changes nothing and one that raced a halt keeps the halt's answer. `edgeVerdict` reads a gate as it reads a merge or deliver block — `waiting` pending, `emitted` satisfied, `blocked` a sentence naming it — and pushes nothing onto `dependsOn`. Everything behind a gate is therefore deferred (`deferredNodes` is "behind any non-run") and is created by the advance Continue triggers, not before. Stop is not a second door: it is `POST …/stop`, `stopInstance`, which writes the gate `blocked` with every other waiting block, and `reviveBlockedBlocks` clears `held_at` when a pick-up puts one back, so a revived gate is held, and announced, afresh.

**A gate hands on no runs, and that is the cost the diagram pays.** It is the fourth block, after merge, deliver and loop, that resolves to no run, so a merge block whose only predecessor is a gate has nothing to land: `run → gate → merge` is refused at save, and the refusal says to link the run to the merge as well as to the gate (`gateHint`). The diamond — `run → gate`, `run → merge`, `gate → merge` — is the shape that holds a merge, because the merge then waits for the gate and still lands the run. Making the gate transparent (resolving to the runs behind it) was considered and left: it would change what `edgeVerdict` pushes for every successor kind, apply the outgoing link's condition to runs it was never drawn against, and add a look-through to every rule that asks what is "directly in front of" a merge, deliver or review block — a rewrite of rules whose silent failures are the point of this file, for a convenience the diamond already gives. A `continueBranch` link into or out of a gate is refused by name, as it is for every other block that cuts none.

**Whether a chat may propose one: yes.** A gate holds nothing dangerous — it starts and spends nothing and only ever makes a run *wait* — so `propose_workflow` takes it, unlike `deliver`, which publishes. The approval card says "no agent" for it, and the Guards cell on `/workflows/[id]` says the same in the same words. What a model cannot do is the other half: no tool a model holds continues a gate. `continueGate` is reached from the one route above and from nothing else.
