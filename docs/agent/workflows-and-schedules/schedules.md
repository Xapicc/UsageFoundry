# Schedules

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `src/lib/schedules.ts`: `decideSchedule`, `putSchedule`, `nextOccurrence`, `scheduleRefusal` or its timer.

**A schedule is the first thing here that starts an agent with no person present at all, and every property that makes that defensible is somewhere else.** The run form, the chat's approval route and a workflow's Run button all have somebody pressing something at the instant the spend begins. A schedule keeps the press and removes the person, so what bounds it has to be true *before* it fires — and none of it is new machinery, which is the point. **Guards** come from the block's template or from `settings.chatDefaultGuards`, because a schedule calls `startWorkflow` and nothing else: there is no field on the wire, no argument on `putSchedule` and no column on `workflow_schedules` that could reach `--permission-mode`, a budget or an isolation choice, which is the same "there is nothing to raise it *with*" that already keeps an orchestrator block out of its own instance's budget. **The instance budget guard and the instance stop** cover a scheduled instance exactly as they cover a clicked one, for the same reason — it is the same `startWorkflow`, the same copy of the guard taken at instantiation, the same `stopInstance`. And **a workflow whose instance budget sets nothing cannot be scheduled**: `scheduleRefusal` is checked at the door, where there is a person and an error channel, and again at every fire, because clearing that budget afterwards is one edit away and nothing about that edit knows a schedule exists. Refusing rather than warning is `normalizeWorkflowInput`'s rule for an orchestrator block's fan-out cap, reused one level up and for the identical reason: a banner is read once, when the schedule is created, and the spend it is about happens every hour for the next month. Any one of the three limits is enough, and it asks `instanceBudgetIsOff` rather than naming a cost limit, because the two window fractions are the ones that bound *repetition* — an instance that would start into an already-spent window is refused at `startWorkflow`'s own door. **There are two doors to `putSchedule`, and the second adds no rule.** The chat's `propose_schedule` reaches it only through a person's approval, via `approveScheduleProposal`, and asks `scheduleRefusal` at the tool call and again at the click; `docs/agent/chat.md` holds what is frozen on that card and what is read live. **The switch back on takes a boolean and nothing else.** `PATCH /api/workflows/[id]/schedule` answers 400 for a `paused` that is not `true` or `false` and for a body that is not a JSON object, and leaves the row as it was. Resume is `false`, so a reading like `=== true` turns every malformed value into a resume, and a reading the other way would answer a garbled resume with a 200.

**A missed window is not made up, an overlap is skipped rather than queued, and both are on the page.** `decideSchedule` is that whole decision — fire, skip, missed, idle, paused — pure and unit-tested, because both ways of being wrong are silent and each is expensive in the opposite direction: a window fired twice bills twice with nobody watching, and a schedule that never fires is bit-for-bit what a working one looks like between occurrences. `cursor_at` is the last occurrence *decided about* rather than the last one started, and `reconcileSchedulesOnBoot` moves it to the instant of the boot without firing anything — the queued-run rule and the queued-merge rule arrived at from a third direction, that a server coming back up must not start unattended agents because of something that should have happened hours ago. `FIRE_GRACE_MS` is therefore only ever a late *tick*: two minutes, far shorter than the shortest recurrence this app accepts, so it can never honour a window a later one has superseded. An overlap is decided here rather than left to `startWorkflow`'s existing refusal — which still stands behind it — and it is a **skip**, never a retry, because a queued press of Run is a press nobody is present for by the time it happens; the cursor moves past it and the next occurrence is the next chance. Consecutive identical outcomes collapse into `streak`/`streak_since`, keyed on `last_code` and never on `last_reason`, since the sentence carries a count that moves and a streak breaking on that would be the fifty identical rows again with a counter stuck at one.

**The zone is stored with the schedule, and an unknown one is refused rather than replaced.** The container runs in UTC and the operator does not, so a wall-clock recurrence read in the server's zone fires an hour out for half the year — the failure this app already solved once for calendar buckets, where `/api/usage?tz=` carries the browser's zone. `isTimeZone` is split out of `resolveTimeZone` precisely because the two callers want opposite things from an unknown name: a bucket falls back to the server's zone, since a day cut an hour out is a display error in front of the operator, where a schedule refuses, since an hour out is an hour out for months with nobody looking. `nextOccurrence` solves a local time with the two-pass offset solve `zonedMidnight` uses, and on a spring-forward day whose nominal time does not exist it lands an hour to one side — which is the answer a schedule wants: the day still gets exactly one occurrence, within an hour of the time asked for, strictly between its neighbours. Returning nothing would silently skip one day a year, which is again indistinguishable from working. `everyHours` is deliberately an *interval* off an anchor rather than a wall-clock time, so it is DST-immune by construction and the zone only affects how it is displayed. The surface is three plain choices and no cron expression: `0 0 * * 1` and `0 0 1 * *` differ by one character and by a factor of four in what they spend, and a raw expression would first have to earn `describeSchedule`'s ability to render itself back in words. The page states the next fire time as an **absolute instant** beside those words, because a schedule the operator cannot verify at a glance is a schedule they will not trust with an unattended agent.

**One timer per process, `globalThis`-pinned, lazily started and stopped.** `sweepPaused`'s shape, for `sweepPaused`'s reason: module state that is not pinned silently resets on every request in dev, and an install with no schedules must hold no interval at all. It is started from the boot hook, from `putSchedule` and from a resume, and it stops itself the moment no active schedule is left. `currentSnapshot()` — the expensive half — is read only on a tick that actually fires. The boot start is inside `claimDataDir`'s `owned` branch with every other reconciler, and that is not tidiness: two servers firing one schedule is one window pressed twice, and the row they both read says nothing about whose it is. The cursor advances *before* the snapshot is awaited, so a tick that overruns cannot decide one window twice; the cost is that a process dying between the two loses that window with nothing recorded, which is the safe direction and the same one the boot takes. The row a tick holds is also older than every earlier schedule's snapshot and start in the same tick, and than its own snapshot. So a Pause, Remove or Change pressed in either gap wins. The window is claimed only by an `UPDATE` conditional on `paused=0` and an unchanged `updated_at`, which Pause, Resume and Change all write, Remove takes with the row, and none of the tick's own writes touches. The row is read again once the snapshot is in, and `recordOutcome` carries the same condition. A fire the operator overtook starts nothing and records nothing, losing the window rather than retrying it: the card already says paused, gone or the new recurrence, and nobody is present to see an agent start behind it.
