# Schedules

[← workflows-and-schedules index](../workflows-and-schedules.md)

Read before editing `src/lib/schedules.ts`: `decideSchedule`, `putSchedule`, `nextOccurrence`, `scheduleRefusal` or its timer.

**A schedule is the first thing here that starts an agent with no person present at all, and every property that makes that defensible is somewhere else.** The run form, the chat's approval route and a workflow's Run button all have somebody pressing something at the instant the spend begins. A schedule keeps the press and removes the person, so what bounds it has to be true *before* it fires — and none of it is new machinery, which is the point. **Guards** come from the block's template or from `settings.chatDefaultGuards`, because a schedule calls `startWorkflow` and nothing else: there is no field on the wire, no argument on `putSchedule` and no column on `workflow_schedules` that could reach `--permission-mode`, a budget or an isolation choice, which is the same "there is nothing to raise it *with*" that already keeps an orchestrator block out of its own instance's budget. **The instance budget guard and the instance stop** cover a scheduled instance exactly as they cover a clicked one, for the same reason — it is the same `startWorkflow`, the same copy of the guard taken at instantiation, the same `stopInstance`. And **a workflow whose instance budget sets nothing cannot be scheduled**: `scheduleRefusal` is checked at the door, where there is a person and an error channel, and again at every fire, because clearing that budget afterwards is one edit away and nothing about that edit knows a schedule exists. Refusing rather than warning is `normalizeWorkflowInput`'s rule for an orchestrator block's fan-out cap, reused one level up and for the identical reason: a banner is read once, when the schedule is created, and the spend it is about happens every hour for the next month. Any one of the three limits is enough, and it asks `instanceBudgetIsOff` rather than naming a cost limit, because the two window fractions are the ones that bound *repetition* — an instance that would start into an already-spent window is refused at `startWorkflow`'s own door. **There are two doors to `putSchedule`, and the second adds no rule.** The chat's `propose_schedule` reaches it only through a person's approval, via `approveScheduleProposal`, and asks `scheduleRefusal` at the tool call and again at the click; `docs/agent/chat.md` holds what is frozen on that card and what is read live. **The switch back on takes a boolean and nothing else.** `PATCH /api/workflows/[id]/schedule` answers 400 for a `paused` that is not `true` or `false` and for a body that is not a JSON object, and leaves the row as it was. Resume is `false`, so a reading like `=== true` turns every malformed value into a resume, and a reading the other way would answer a garbled resume with a 200.

**No instance limit is the bound of a press whose blocks report no cost.** `scheduleRefusal` refuses a workflow holding any block in `blocksReportingNoCost` — a run block on Codex or the local model, or an orchestrator block whose runs go to one — whichever of the three limits is set, and names the block. Each limit is blind to it for its own reason. `sumMemberSpend` leaves those runs out of the figure `maxInstanceCostUSD` compares, so that limit reads $0 for them for ever. The two fractions are read by `evaluateInstanceBudget` off the snapshot `currentSnapshot` builds, which is the Claude account's windows: a Codex member adds nothing to them (its own windows are `codexAccount.ts`'s, which the run guard hands a Codex run and the instance guard does not), and a local member is in neither, so a fraction bounds the schedule's repetition only through whatever else spends Claude usage, while the clock fires every window regardless. Any such block, not only an all-Codex graph: the blocks that report can stay under a limit while that one spends. The run form only warns about a spending limit on a Codex run because a person is there to read the warning; here nobody is, which is the paragraph above. **A window guard used to satisfy the rule, and that was the bug**: it admitted exactly the case the refusal sentence declines to recommend it for, and a guard is not a bound over spending it cannot see. The sentence offers running the block on Claude or pressing Run by hand, and it is worded for the limits actually set (dollars, windows, or both). **Decided (board task bf494de3), not left open:** a window guard stops counting for such a graph. The other two answers were weighed and not taken. Having the instance guard read the Codex snapshot for Codex members' share, as the run guard does, makes one instance's guard read two accounts' windows inside `evaluateInstanceBudget` — a mixed graph needs both and a rule for combining them, and a local member is still in neither — which is a larger change than this evidence supports. An instance-level Codex token limit (`maxRunTokens` one level up) is a new setting nobody has asked for. **What it costs:** any graph with a Codex or local block is unschedulable under any instance limit, **including an all-local graph that spends nothing billable**; the rule does not exempt it, because `blocksReportingNoCost` is the one list the loop cap and the schedule both read and a local run's cost is its machine's time, which no limit here reads. **A schedule saved under the old rule is neither migrated nor stopped silently**, and needs no code of its own for that: `scheduleRefusal` is asked at every fire (twice, on either side of the snapshot), so the next fire records `unbudgeted`, "not started", with the sentence; a resume and a change are refused with it; and the card shows it, with an Edit workflow button, as soon as the workflow loads. That is all the dollar-only refusal did for schedules saved under it, and the gap is the same for both: nothing tells the operator when the workflow is edited or the build is deployed, so the first notice is the card or the first fire that did not start, and an instance already started keeps running. **Open:** the way to make such a workflow schedulable again is an instance-level limit that reads those members' own usage — the third answer above — and nobody has asked for it yet.

**A missed window is not made up, an overlap is skipped rather than queued, and both are on the page.** `decideSchedule` is that whole decision — fire, skip, missed, idle, paused — pure and unit-tested, because both ways of being wrong are silent and each is expensive in the opposite direction: a window fired twice bills twice with nobody watching, and a schedule that never fires is bit-for-bit what a working one looks like between occurrences. `cursor_at` is the last occurrence *decided about* rather than the last one started, and `reconcileSchedulesOnBoot` moves it to the instant of the boot without firing anything — the queued-run rule and the queued-merge rule arrived at from a third direction, that a server coming back up must not start unattended agents because of something that should have happened hours ago. `FIRE_GRACE_MS` is therefore only ever a late *tick*: two minutes, far shorter than the shortest recurrence this app accepts, so it can never honour a window a later one has superseded. An overlap is decided here rather than left to `startWorkflow`'s existing refusal — which still stands behind it — and it is a **skip**, never a retry, because a queued press of Run is a press nobody is present for by the time it happens; the cursor moves past it and the next occurrence is the next chance. What counts as an overlap is that refusal's rule, per folder: `overlapCount` asks `sharedFolderOf` of the press the fire would make — the first saved folder, through `chooseFolder` — so a press a person started against another saved folder does not cost the schedule its window, while its own previous fire, or anything sharing a block with its own folder, still does. Consecutive identical outcomes collapse into `streak`/`streak_since`, keyed on `last_code` and never on `last_reason`, since the sentence carries a count that moves and a streak breaking on that would be the fifty identical rows again with a counter stuck at one. **The install-wide hold is stated on the card before the window it will cost passes.** `GET /api/workflows/[id]` carries `newWorkPaused`, and the card of a schedule that is switched on says its next start will be recorded as missed; a paused schedule's card does not, since it would not have started either way. The behaviour is `fireIfDue`'s and unchanged — the card only says in advance that it does nothing under the hold, so that a held install is not read as a schedule that stopped working.

**A window that passes under the install-wide hold is recorded as missed on the tick that sees it, and the cursor moves past it — it is never left behind for the grace.** Decided 2026-10-17 on board task 869a2c4e, after a bug hunt measured the opposite on 02f3b764: the paused branch of `decideSchedule` returned `cursorAt: ctx.lastFireAt` and `missed: []`, on the reasoning that lifting the hold would then record the windows as missed. It did not, whenever the hold was lifted within `FIRE_GRACE_MS` of the occurrence: the next tick enumerated that window from the old cursor, found it inside the grace, took it for a tick that ran late and started an unattended instance, recording `started` with `last_fire_at` at the occurrence — the card promised "recorded as missed and not made up afterwards" and the outcome was the made-up window under a card saying it started on time, which the timer paragraph below names as the very defect. So the paused branch now enumerates what passed (`windowsThrough`, shared with the live branch and bounded by `MAX_CATCHUP` the same way), returns all of it as `missed`, the newest included, and moves `cursorAt` to the newest; `fireIfDue` claims, records and returns, since the action is `paused`. The same applies to the other door: a hold pressed in the snapshot gap records the window the fire had claimed as missed (the cursor is already on it) where `releaseWindow` used to put the cursor back behind it, and `releaseWindow` is gone. `ScheduleContext.paused` therefore means the install-wide hold and nothing else — a schedule's own pause is filtered in SQL by `activeSchedules`, and `pauseSchedule` moves the cursor on resume — and the old unit case that said "nothing is missed by a schedule somebody switched off" was describing a call no caller makes. What this does not cover, and cannot without recording the hold's own intervals: a hold set and lifted entirely between two ticks (30 s apart) that straddles an occurrence is indistinguishable from a tick that ran late, so that window starts. The hold is read once per tick, at the top of `fireIfDue`.

**The zone is stored with the schedule, and an unknown one is refused rather than replaced.** The container runs in UTC and the operator does not, so a wall-clock recurrence read in the server's zone fires an hour out for half the year — the failure this app already solved once for calendar buckets, where `/api/usage?tz=` carries the browser's zone. `isTimeZone` is split out of `resolveTimeZone` precisely because the two callers want opposite things from an unknown name: a bucket falls back to the server's zone, since a day cut an hour out is a display error in front of the operator, where a schedule refuses, since an hour out is an hour out for months with nobody looking. `nextOccurrence` solves a local time with the two-pass offset solve `zonedMidnight` uses, and on a spring-forward day whose nominal time does not exist it lands an hour to one side — which is the answer a schedule wants: the day still gets exactly one occurrence, within an hour of the time asked for, strictly between its neighbours. Returning nothing would silently skip one day a year, which is again indistinguishable from working. `everyHours` is deliberately an *interval* off an anchor rather than a wall-clock time, so it is DST-immune by construction and the zone only affects how it is displayed. The surface is three plain choices and no cron expression: `0 0 * * 1` and `0 0 1 * *` differ by one character and by a factor of four in what they spend, and a raw expression would first have to earn `describeSchedule`'s ability to render itself back in words. The page states the next fire time as an **absolute instant** beside those words, because a schedule the operator cannot verify at a glance is a schedule they will not trust with an unattended agent. That instant is read **in the schedule's zone and names it** (`fmtInstantWithZone`): beside "Every day at 09:00 (Europe/Berlin)", an instant on the browser's clock verifies the words only for a reader who happens to sit in that zone, and is an hour out for everyone else. A zone the browser's ICU does not know — the server accepted it against its own — is read in the browser's and labelled with *that*, since a throw in render takes the page down and a label naming a clock the digits are not on is the defect. The zone field offers `Intl.supportedValuesOf("timeZone")` in a `<datalist>`, which only suggests: `isTimeZone` at the door still refuses an unknown name. The recurrence's own numbers are refused the same way rather than coerced: `normalizeScheduleInput` requires the time, the weekday and the interval to arrive as numbers, and the latter two as whole ones, because `Number(null)` is a legal midnight or Sunday and `Math.trunc(1.5)` is a legal "every hour" — each a rule nobody chose, run with nobody present. The form blocks Save on a missing time or a fractional interval as well, but the server's refusal is the one that holds, because `propose_schedule` reaches it with no form in between.

**One timer per process, `globalThis`-pinned, lazily started and stopped.** `sweepPaused`'s shape, for `sweepPaused`'s reason: module state that is not pinned silently resets on every request in dev, and an install with no schedules must hold no interval at all. It is started from the boot hook, from `putSchedule` and from a resume, and it stops itself the moment no active schedule is left. `currentSnapshot()` — the expensive half — is read only on a tick that actually fires. The boot start is inside `claimDataDir`'s `owned` branch with every other reconciler, and that is not tidiness: two servers firing one schedule is one window pressed twice, and the row they both read says nothing about whose it is. The cursor advances *before* the snapshot is awaited, so a tick that overruns cannot decide one window twice; the cost is that a process dying between the two loses that window with nothing recorded, which is the safe direction and the same one the boot takes. The row a tick holds is also older than every earlier schedule's snapshot and start in the same tick, and than its own snapshot. So a Pause, Remove or Change pressed in either gap wins. The window is claimed only by an `UPDATE` conditional on `paused=0` and an unchanged `updated_at`, which Pause, Resume and Change all write, Remove takes with the row, and none of the tick's own writes touches. The row is read again once the snapshot is in, and `recordOutcome` carries the same condition. So is the workflow, and `scheduleRefusal` is asked again on that read with nothing awaited before the start: clearing the instance budget writes the workflow's row and not the schedule's, so the schedule's re-read cannot see it, and `startWorkflow` never asks. A fire the operator overtook starts nothing and records nothing, losing the window rather than retrying it: the card already says paused, gone or the new recurrence, and nobody is present to see an agent start behind it. **The install-wide hold is pressed in the same gap and wins the same way**, asked again beside those re-reads because `decideSchedule` took it before the snapshot and `startWorkflow` writes an instance's rows under a hold by design — the run would sit queued and be promoted the moment the hold is lifted, a window made up afterwards under a card saying it started on time. It differs from a Pause in one respect: the hold promises the window is recorded as missed, so that fire records it (`missedSentence`, held wording) and the cursor `claimWindow` moved stays on it — see the paragraph on the hold below.

**A schedule can now start an instance that stops at a gate with nobody present, and nothing on the schedule card bounds that.** Every limit this file lists bounds spend, and a gate spends nothing, so `scheduleRefusal` does not refuse a workflow for holding one — the opposite of a deliver block, which publishes and is refused. What a gate does to a schedule is arithmetic on the overlap rule: an instance held at a gate is live, so `decideSchedule` records the next windows as skipped whenever the fire would share a folder with it (an overlap is a skip, never a retry) until somebody presses Continue or Stop, and a missed window is not made up. Nothing is lost that was not already lost to a long run, but it is silent in the same way: a schedule that never fires and a schedule held up behind a gate that nobody has seen look alike from `/workflows`. So the card states it before the schedule exists and while it does (`hasGate`, a notice that a scheduled run stops at the gate waiting for you and the schedule skips later windows meanwhile), `notifyGateHeld` tells the operator's receiver when the gate is reached if one is configured, and the instance page's gate card says a schedule started the run. The notice is derived from the saved graph on every render rather than stored with the schedule, so adding a gate to a workflow that is already scheduled changes the card without anyone touching the schedule.
