# Stacks

[← security index](../security.md)

Read before editing `scripts/apply-stacks.mjs`, a `stack.json`, the stacks steps in `Dockerfile` and `docker-entrypoint.sh`, or `request_stack` and `src/lib/stackRequests.ts`.

- **A stack is software the operator chose to install, and what this mechanism buys is that the choice is reviewable and revocable rather than safe.** `scripts/apply-stacks.mjs` reads each `stack.json` under `/etc/uf-stacks` — one a third party may have written — downloads what it names and links the result into `/var/lib/uf-stacks/bin`, which the image puts first on the server's `PATH` and so on every agent's. The honest sentence is `proposals/CustomStacks/01b-stack-format.md` §6's and belongs here rather than in a proposal: *consuming a third party's stack is the same act as taking their `RUN` line into your Dockerfile.* What is bought is that the act is one small file an operator can read in thirty seconds — every URL, digest and denied command visible — and that `rm -r` of its directory and a restart undoes it: the next boot removes the package, its state, the links its receipt records and the receipt. Editing the file into one the parser refuses is not the same act, because that records a `failed` receipt and removes nothing installed before it. None of this makes the act safe, and nothing that installs software can. What is **not** bought is any check on where a URL points — the parser requires `https://` and nothing more, there is no host allowlist and **there is no signature verification** — because this repository holds no key material and inventing a trust root is a larger decision than this mechanism. **The three verbs differ in what they trust.** `archive` executes nothing it downloads, ever, and verifies it before unpacking with `sha256sum --ignore-missing --check`, the pattern of the `gh` download at `Dockerfile:199-203`, so a stack using it is worth exactly its URL — which is why it shipped first and alone. The trust boundary is the stack and not the digest: an author who writes the digest is the author who wrote the URL, so `checksums` — the publisher's own manifest — is the documented form and a literal `sha256` exists only for a publisher who ships none; the parser takes exactly one of the two and treats them alike. `uv-tool` and `npm-global` verify nothing and run the package's install hooks at boot, as `UF_AGENT_UID` when that is set and as root when it is not, so a stack using either is worth the package it names — the trade `docker-entrypoint.sh`'s `UF_PY_TOOLS` loop already makes through `uv_install_tool`, stated rather than glossed. Three more things enforce the rest, and each is load-bearing. **Never a shell**: the applier interpolates into argv arrays and `spawnSync` without `shell`, so a URL or a filename out of somebody's file is inert the same way a prompt's metacharacters are at the spawn sites above — the format's four expansion tokens, `{arch}`, `{arch_uname}`, `{state}` and `{pkg}`, exist precisely so an author never reaches for `$( )`. **The uid split inverts here on purpose**: download, verify, unpack and the `chmod` of what was unpacked drop to `UF_AGENT_UID`, and the `chown -R root:root`, the `chmod -R go-w` after it and the links into `bin/` are root's — the opposite of the gh and Python loops, because `bin/` is on the *server's* `PATH` and a directory there that a sibling agent can rewrite is a way for one run to put its own code on every other run's transcript. `/home/node/pytools/bin` is already one of those; there is not a second. The split is safe only because the applier runs before `exec "$@"`, in the one window with no agent process alive. And **what a stack may never do is decided at parse, before a byte is downloaded**, in `parseStack`. A stack's `env` is a denylist that fails closed: `refuseEnv` refuses every `UF_*` key (which `childEnv` would delete after the stack set it, silently) and the `GIT_`, `CLAUDE_`, `ANTHROPIC_`, `OPENAI_` and `CODEX_` prefixes, the names that decide where things are (`PATH`, `HOME`, `NODE_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DATA_DIR`), any value carrying a shell metacharacter, and any absolute value that normalises under `/home/node/.claude` — which is the *host's* `~/.claude` for every session on the machine. No `bin.from` may escape `{pkg}`. A `deny` entry is refused unless its first word is a name the stack itself links, and that rule is doing the opposite job from the one it looks like: it stops a stack **denying** what it does not own, since deny beats `ISOLATED_GIT_TOOLS` the same way it beats the mode, and a stack that could write `git commit` there would silently break every isolated run on the install. **And the names root runs are reserved**: `parseStack` refuses a `bin.as` in `RESERVED_BIN_NAMES` — `git`, `node`, the applier's own tools, and what `docker-entrypoint.sh` and winnow run as root while the uid split is on — with a refusal that names the word. Before it, `bin/` being first on root's `PATH` meant a stack's `git`, `chown` or `node` was root's on the next boot whatever its verb, which made an `archive` stack worth far more than its URL; and a stack that linked `git` owned it in the deny rule's sense too. The list stops at what root runs rather than at everything the image ships, the fail-closed form, which was declined: shadowing the image is what `bin/` is first on `PATH` for, and the operator's `python` stack links `python`, `pip` and `pip3` over an image whose `python3` it leaves alone. A list of names is only as good as its last read of the entrypoint, so the processes this repository spawns as root no longer look their tools up at all: the applier spawns through `TOOLS`, the image's absolute paths, and throws on a name it does not hold; `GIT_BIN` defaults to `/usr/bin/git`, an operator's setting still winning; and the `HEALTHCHECK` runs `/usr/bin/curl`. What still resolves by name as root is the entrypoint's own commands, `node` among them, which is the list's to cover — and the list does nothing about `/home/node/pytools/bin`, which no stack writes, an agent owns, and root's `PATH` searches before `/usr/bin` (board task `aff25da4`). Nothing downstream re-checks any of it, deliberately: a second gate is a second thing that can disagree with the first about what a stack may grant, and the receipts it would be re-checking are root-owned files in `/var/lib/uf-stacks/receipts`, which no agent can write.

- **A run may ask for a stack, and asking is all it can do: `request_stack` records text a person reads and never anything the app applies.** The tool (`src/app/api/mcp/route.ts`, the record in `src/lib/stackRequests.ts`, the lifecycle in [`run-lifecycle/waiting-for-stack.md`](../run-lifecycle/waiting-for-stack.md)) takes a name, the binaries a run needs, a sentence of why and an optional draft `stack.json`, writes a request row and parks the run that asked. It cannot install anything, write a declaration, reach `/etc/uf-stacks` — still a read-only bind of the host's `./stacks` — or run the applier, which still runs only at boot, as root, before `exec`, with no agent alive. That is the whole of the argument and it is this file's first paragraph applied to a new author: a stack is software the operator *chose*, and what the mechanism buys is that the choice is reviewable, so the one thing a run must never be able to do is make it. A run's request is untrusted text from an agent nobody is watching, and a draft from it is the third party's `RUN` line with the third party being a model — so it reaches the operator as text, on the run page and under Settings → Tools, and goes nowhere else: never written to disk, never rendered as HTML or markdown, and shown in a preformatted block beside the boot parser's verdict on it (`checkStackDraft` loads `scripts/apply-stacks.mjs` from the image at runtime, so the verdict is the parser the boot will run, and a layout without the file answers `unchecked` rather than guessing). The operator who decides to install it copies it to the host, reads every URL and digest in it, and restarts — the same thirty-second review as any other stack, which is the act the mechanism protects. Three rules hold the text in its place. **The name is stricter than the applier's**: the applier takes any directory entry, because a directory under `./stacks` is one the operator made, while this name is printed inside the path the operator is told to create and so is a line somebody pastes into a shell — it takes the `bin.as` rule, a plain command name, which admits no separator, whitespace or metacharacter, and every name it admits the applier admits too. **What is installed is never recorded**: a request is `pending` or `declined` and has no state for an install, which is always read from the receipts, so the table cannot become a second, disagreeing record of what is installed — the reason `stacks.ts` has no `stacks` table. **The run token is what names the run**, and no argument does, so a misdirected or stolen call parks the token's own run until the operator answers and puts a request on Settings a person reads before anything happens, and reaches no other run. The tool rides the run tool list, so it exists only where `taskboardForRuns` is on, the operator's opt-in to an unattended agent writing into this app's database. A request does not change what a stack may do once installed, and needs no rule of its own for the names root runs: a draft that links a `git` of its own meets the same `parseStack` the boot runs, so the verdict beside it names `git` as reserved before the operator has read a line.
