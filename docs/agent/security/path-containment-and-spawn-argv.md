# Path containment, spawn argv and permission modes

[← security index](../security.md)

Read before editing `resolveInMount`, `conflictKey` or `ensureWorktree` in `src/lib/orchestrator.ts`, `buildArgs` or `promptArgs` in `src/lib/cycleInvocation.ts`, `gitArgs` or `gitSync` in `src/lib/git.ts`, `src/lib/agents.ts`, or how `POST /api/runs` takes `permissionMode`.

- `resolveInMount()` (`orchestrator.ts`) checks containment on the lexically resolved path **before** touching the filesystem, then **again** after `realpathSync` — a symlink inside the root can still point out of it. Both checks are load-bearing. `resolveWorkspaceFolder()` runs that pair against **one mount at a time**; multiple mounts widen which roots are legal, never what counts as contained. A run is confined to the mount it started in.

- Containment stays **per mount**, while collision detection is deliberately **cross-mount**: `conflictKey`/`overlaps` see two mounts onto one directory as one folder. Widening what counts as a collision never widens what a run is permitted to touch.

- Worktrees live at `<mountRoot>/.uf-worktrees/<repo>-<slot>` so the unmodified `resolveInMount` validates the agent's cwd. `ensureWorktree` `lstat`s that directory and refuses a symlink **before** git writes — validating afterwards would mean a full checkout had already landed wherever the link pointed.

- **A repository at the mount root is isolated only while its own ignore rules keep the store out, and this app's git never climbs out of a slot.** For that repository `<mountRoot>/.uf-worktrees` is inside the working tree it serves, so `probeIsolation` asks `storeIgnoredBy` (`git -c core.excludesFile= check-ignore -q -- .uf-worktrees/`) and otherwise refuses with a reason naming the `.gitignore` line that would allow it; untracked, every slot is a full copy of the repository in the operator's `git status` and a gitlink to a plain `git add -A`. The user-level excludes file is switched off for the question because it is this container's and the operator's host git reads its own; the `-c` also outranks a `GIT_CONFIG_COUNT` block in the environment (both measured on 2.39, 2026-10-24). A rule that re-includes one slot under `.uf-worktrees/*` still passes, since the question is about the directory. What a run may write does not change: an isolated run there gets its slot and `<repo>/.git`, as every isolated run does, and nothing on the repository root; a run on that root with isolation off has the whole mount, store included, as a mount-root run always had, and the folder claim serialises it against running slot runs (not parked ones) exactly as before. Two things did change because the store is inside a repository. `gitEnv()` sets `GIT_CEILING_DIRECTORIES` to every mount's store, because a slot directory that has lost its `.git` file would otherwise resolve to the operator's checkout and every slot read in `land.ts` and `allocateSlotPath` would answer for the operator's branch; with it git says "not a git repository" there, which those callers already refuse (the store directory itself is not covered and nothing runs git in it; the agent's own git is not covered, its sandbox is what bounds it). And `runWorkingIn` (`land.ts`) skips a run working in its own checkout, or every isolated run in the mount would hold Land, Deliver and Push of that repository. `planSeedCopies` never opens the store at a repository's root, and `repoRelative` and `runTouchScan` count a path into the store as outside the run's tree. `mountRootIsolation.test.ts` covers each.
- **A repository nested below a mount root that is itself a repository is isolated only while the outer repository's own ignore rules keep the store out.** For that run the store `<mountRoot>/.uf-worktrees` is outside the repository it serves and inside the outer one, so unignored it has the same three effects on the outer repository: every slot is `?? .uf-worktrees/` in its `git status`, Land of a run on it is refused as dirty, and a plain `git add -A` records each slot as a gitlink. `probeIsolation` therefore asks `storeIgnoredBy` of the mount root too, once the repository's own gates pass, and otherwise refuses with a reason naming `<mountRoot>/.gitignore` and the line to add. Decided 2026-10-25 (board task `bb6af2dd`) to refuse rather than isolate into the outer tree: isolating dirties the outer repository and refuses its Land, and the only cure after the fact is emptying the store, where the refusal is cleared by one line. On this install it refuses nothing that isolates today: `/workspace` is not a repository and `/workspace2` ignores the store and holds no nested repository (measured 2026-10-25); an install with a nested repository under a non-ignoring mount-root repository meets the refusal at its next admission. Whether the mount root is a repository is a `stat` of its `.git`, not a git call, for three reasons. The common layout, a mount root that is not a repository, then costs no subprocess inside `createRun`'s no-`await` window (`slotProbes.test.ts` still pins four). Git asked from such a mount root climbs to whatever repository is above it, the ceilings in `gitEnv()` covering only the stores, and refusing over *that* repository's rules would be refusing over a store that is not inside it. And git's answer is accepted only when `rev-parse --show-toplevel` names the mount root, because an empty `.git` directory is skipped by git's discovery and answers with the repository above. A `.git` git cannot use, such as a host checkout's absolute gitdir that is not under the mount, counts as no repository: the refusal's remedy is a `.gitignore` line, and no edit makes that repository readable here, so it would be a refusal nothing clears. `mountRootIsolation.test.ts` has a case each for the refusal, the ignored store, the repository above the mount root and the unusable `.git`; the last two fail when `isRepositoryRoot` answers `true` unconditionally.

- The agent is spawned with an argument array and `stdio: ["ignore", "pipe", "pipe"]`, **never a shell**, so prompt metacharacters are inert. Inert to a shell is not inert to the CLI, whose own parser still reads every token: `-p` is a boolean and the prompt the root command's positional, so a prompt beginning with `-` — a pasted bullet list — was an unknown option that ended the child before it read a word. Every site that hands `claude` a prompt (`buildArgs`, the chat child, `spawnAssist`) therefore ends its argv with `promptArgs`, a `--` and then the prompt, and nothing may be pushed after it: the CLI would take a flag there as an ignored operand. A prompt that is exactly a subcommand's name — `update`, `install`, `doctor`, `mcp` — is a prompt too, and the separator is not why: commander's `_parseCommand` dispatches whenever `_findCommand(operands[0])` matches, operands after `--` included. What closes it is the CLI's start-up order, read off the pinned 2.1.280 bundle and not run (board task `f36fa8cc`): when `-p` or `--print` appears ahead of the first `--` and no `cc://` token does, `pl` calls `parseAsync` before it registers a single subcommand, so the root has none to dispatch to. All three argvs open with `-p`, and every value they carry ahead of the `--` belongs to a flag the CLI's own scan steps over, so no value can flip that test. The two argv reads ahead of commander do not reach the prompt either: `--handle-uri` wants a token after it, and the `import` rewrite declines once a `--` precedes the word. A pin bump re-reads that gate; `promptArgv.test.ts` transcribes it. `gitSync` does the same, and additionally clears **both** ways a repository gets git to run a command of its choosing — `core.fsmonitor=`, which `status` reads, and `core.hooksPath=/dev/null`, which is what `worktree add`'s `post-checkout`, `checkout`'s, and `merge`/`commit`'s four would otherwise fire, the last of them inside the operator's own checkout at a moment the operator triggered. An agent can write `.git/hooks/post-checkout` in any repository it works in and this app would then execute it on behalf of a run that did not, with no permission mode, no tool lists and nothing in `run_events`; `/dev/null` is not a directory, and the `-c` outranks a `core.hooksPath` the repository sets for itself (verified on 2.39). This is the git *this app* runs and it reaches no further: `buildArgs` passes no config, so a repository's `pre-commit` still runs for the agent that was asked to commit, which is part of the work. `gitEnv()` strips what `childEnv` and `reviewEnv` strip — `UF_*`, `ANTHROPIC_*`, `OTEL_*`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `CLAUDE_CODE_ENABLE_TELEMETRY`, `DATA_DIR` — rather than the shorter list it had, because the drivers reached through `.gitattributes` are repository-controlled too and this is the one child kind that runs code this app did not write.

- **A review block's verify command is argv and never a shell, and only a person saves one.** A review block whose `verdictSource` is `{ kind: "command", command }` makes this app spawn a program in every branch's checkout with nobody looking: the approval is the save. So the command is held to `parseVerifyCommand` at the save (`normalizeVerdictSource`) and again by `runVerify` before it spawns — split on whitespace, every shell metacharacter refused rather than escaped, `landVerifyCommand`'s rule — and it runs as `runVerify` runs Land's: the child uid, `verifyEnv`'s strip, its own process group, `VERIFY_TIMEOUT_MS`. What it runs is not the operator's even though the line is — `npm test` executes a script from the `package.json` an agent just wrote — which is why the uid and the strip are not optional here either. A model may never set it: `propose_workflow` refuses a graph carrying one **by name** (`commandVerdictRefusal`), asked of the normalized graph so no spelling the normalizer reads as a command slips past, and `planWorkflowProposal` asks again at the click, because the approval card shows a review block as "no agent" and the person approving would never be shown the command. `emit_runs` emits runs and has no field a block could take. Only the workflow editor and the save route — both behind the operator's own authentication — write one. Being able to type the command is not the same as having reviewed what it runs, and nothing here pretends otherwise: the guarantee is that the line is the operator's and is executed as argv, not that the tree it runs in is safe.
- **`gitArgs` pins the signing programs and neutralises the repository's filter drivers, for the same reason it clears `core.hooksPath`.** A work cycle writes its repository's real common `.git`, so `commit.gpgSign=true` with `gpg.program=<path>` makes `git commit` run that path, and a `filter.<x>.clean`/`smudge`/`process` paired with a `* filter=x` line in `.git/info/attributes` makes `add`, `commit`, `checkout`, `merge` and `worktree add` run it — as this server's git child, outside the permission model, with no line in `run_events`, on the next run's `worktree add` with nobody pressing anything (board task `9f3f9226`). So `gitArgs` forces `commit.gpgSign=false` and pins `gpg.program`/`gpg.x509.program`/`gpg.ssh.program` to git's own defaults on every call, exactly the signing pins `CHAT_GIT_CONFIG` carries, all on the command line where they outrank `.git/config`. `credential.helper` and `core.sshCommand` are **not** pinned here: an empty `-c credential.helper=` resets the whole helper list at top precedence and would take `githubEnv`'s scoped `credential.https://github.com` helper with it (measured for the chat, `chat-child-config-files.md`), so those belong to Deliver's own fetch/push env. git 2.39 has no flag that turns filtering off wholesale, so `git()`/`gitSync()` read the repository's `filter.*` driver names (`git config --includes --get-regexp '^(filter|merge)\.'`) and blank each one's clean, smudge and process. Each blank goes as `--config-env=<key>=USAGEFOUNDRY_BLANK` with that variable set empty, never as `-c <key>=`: git splits a `-c` at its first `=` and a driver name may hold one, so `-c filter.a=b.clean=` set `filter.a` and the planted `filter.a=b.clean` ran (board task `a9fde194`), while `--config-env` splits at its last `=` (measured, 2.39.5). The blanks go **only on the subcommands that convert content between the working tree and the object store** (`CONTENT_SUBCOMMANDS`), never on the object-store reads (`rev-parse`, `log`, `cat-file`, `ls-tree`, `show`) that are the bulk of this app's git and never invoke a filter, because the enumeration costs one extra `git config` child. `status`, `update-index` and `diff` are on the list because a stat-dirty file is re-hashed through its clean filter: `conflictedFiles`' `diff --name-only` ran one mid-merge (measured). `diff` is gated whole, ranges included, because telling a range from a working-tree diff means parsing git's grammar and the probe is small beside a diff. **Merge drivers are blanked the same way, and `merge-tree` is gated with the rest:** a `merge.<x>.driver` paired with `* merge=x` runs on every three-way content merge, and Land runs two with nobody watching, the `merge-tree` preview and the real `merge` (board task `a38856ec`). The blank is an empty driver, so git runs nothing and fails the merge with `cannot run :`; `false` would read as a markerless conflict and `true` as a clean merge that dropped theirs (measured, 2.39.5). A repository relying on a merge driver has this app's merges of such a file fail, as with a required filter. **The probe fails closed:** only exit 1 with an empty stdout is "no filters" and only exit 0 is a list to blank; a probe killed by its clock or a signal, never started, refused by git (any other status) or exiting 1 with output makes the real call fail with `ok: false`, `code: null` and a `stderr` that says the filter probe failed and how, before the call is spawned, because a status that went unread let a planted `filter.<x>.clean` run on exactly those endings (board task `c032f10c`). It is not retried (a probe the clock killed on a slow checkout would likely be killed again) and it takes the clock the caller gave the call, so landing's no-clock call has none on its probe. `readFilterProbe` is the one reader for `git()` and `gitSync()`. A `filter.<x>.required=true` driver then fails the operation rather than running the planted program — the right failure, since nothing of the repository's choosing runs either way; the cost is that a repository relying on a *required* filter (git-lfs) has this app's `add`/`worktree add` fail loudly rather than silently transform content. `gitDirWatch.ts` still records these keys at a run's end, but it detects and does not prevent; this is the prevention for the app's own git.
- **`core.hooksPath=/dev/null` does not switch off a hook defined in config on git 2.54 or later, and git has no switch that does.** git 2.54 added hooks named in config (`hook.<name>.command` plus `hook.<name>.event`), and git reads them from every config scope without consulting `core.hooksPath`, which only moves the hooks directory. So on a git of 2.54 or later, a `hook.x.*` pair a work cycle writes into `.git/config` runs on this app's own `commit`, `merge`, `checkout`, `worktree add`, and even `branch` and `update-ref` (`reference-transaction`), as this server's git child, despite `gitArgs`. Measured on git built from `v2.54.0` and `v2.56.0`; the evidence and the source lines are in `docs/verification/security-and-sandboxing-server-git.md`. It is not live while the image ships 2.39.5, which has no hooks in config, but upgrading the image's git or pointing `GIT_BIN` at a newer one makes it live with no change here. The only off switches are per hook name (`hook.<name>.enabled=false`, which outranks the repository from the command line) and, from 2.55, per event (`hook.<event>.enabled=false`), and the per-event one is not a defence: a repository that also sets `hook.<event>.command` turns it into a per-name switch for a hook that never fires (measured, 2.56.0). Whether to disable each name the repository lists, as `driverNeutralizers` does for filter drivers, or to refuse git 2.54 and later, is the operator's decision on board task `6b4dccf3`; until it is made, do not describe `gitArgs` as turning every hook off.

- `gitArgs` also passes `safe.directory=*`, and the image sets it system-wide for the agent's own git. This is a deliberate waiver, not an oversight: a bind mount carries the *host* uid, and git's ownership refusal reaches `probeIsolation` as an unreadable repository — indistinguishable from "not a repository", so isolation would switch itself off and say the wrong thing about why. The check guards against repositories encountered by surprise on a shared host; every path that reaches `gitSync` has already been proved inside a configured mount by `resolveInMount`, which is the containment guarantee that actually matters here. Keep it paired with `UF_UID`/`UF_GID` in compose — the waiver makes git *work* against a foreign-uid mount, it does not make the mount *writable*.

- `permissionMode` is narrowed against the four literals in `POST /api/runs` before it reaches `--permission-mode`.

- `bypassPermissions` is offered in the new-run form with a warning; the default stays `acceptEdits`.

- **A named agent is not a capability surface, and the absence of two columns is what enforces that — more so now that the run *is* the agent.** `--agents` members accept a `tools` array; `normalizeAgentInput` refuses one by name and the `agents` table has no column for it, and none for a permission mode either — so the routes to `--permission-mode` stay the two they were, and no chat proposal, workflow block or emitted spec can reach one by naming an agent. The refusal got **stronger** with the singular flag rather than weaker, and the opposite reading is the one to close off: a `tools` list on a definition merely *offered* would have bounded one delegated subtask inside a run whose own mode and lists still stood over it, where a list on the definition the session **is** is a statement about what the whole run may do. Two things follow that are worth not re-deciding by accident. The deny list is the one that matters: `PROCESS_KILLERS` is `--disallowedTools`, deny is *verified* to beat `--permission-mode`, and whether it would also beat a member's own `tools: ["Bash"]` — as a delegate or as the session — is **not** verified, which is why the field is refused rather than stored and narrowed. And what a child may be started as is never taken off the wire: `resolveAgentForRun` accepts an **id** and looks the definition up, so an agent that nobody saved cannot be assembled in a request body — which under `--agent` is the difference between a run being a role somebody wrote down and a run being a system prompt that arrived in an HTTP body.

- **Reading an agent definition off disk is scoped, and only the scope that needs no path is on the wire.** `listAmbientAgents` walks `$CLAUDE_CONFIG_DIR/agents/**` and, for a caller that has already resolved a folder, that folder's `.claude/agents/**`. `GET /api/agents` and `/api/usage` pass no folder and report the user scope alone — not because the project scope is secret, but because taking a directory off a request would be a second path-resolution surface beside `resolveInMount`, for a payload that only feeds a sentence on a page. Nothing in that walk bounds what a child may do; the definitions it finds already reach every child, mounted from the operator's own `~/.claude`.
