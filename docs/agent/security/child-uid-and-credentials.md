# Child uid, child environment and credentials

[← security index](../security.md)

Read before editing `src/lib/privsep.ts`, `childEnv` or `githubEnv` in `src/lib/orchestrator.ts`, `chatEnv` or the capability tokens in `src/lib/chat.ts`, or any other function that builds a child's environment.

- **The server is root and every child it spawns is not, and that one difference is what makes three separate defences mean anything.** `docker-compose.yml` runs the container as `0:0` and the server drops each child to `UF_AGENT_UID`/`UF_AGENT_GID` — the operator's own `UF_UID`/`UF_GID`, so the processes that write the bind mounts are the uid they always were. `privsep.ts` is the one place that decides it, `childCredentials()` is spread into all seven spawn sites (the work cycle, the reviewer, both of `chat.ts`'s, both of `git.ts`'s — the git ones are not an afterthought, a root git leaves root-owned objects in a tree the operator has to keep using — and `claudeAuth.ts`'s, which is the one site where the drop is a *correctness* measure rather than a containment one: `claude auth login` writes the 0600 credential named below, so a login taken with the server's own authority would produce a file the page reports as a healthy sign-in and no agent can open), and what it buys is that a *file mode* now excludes somebody: `/proc/<server>/environ` is 0400 owned by the server, so `childEnv`'s strip of `UF_*`/`ANTHROPIC_ADMIN_KEY`/`DATA_DIR` is enforced rather than advised, where one `tr '\0' '\n' < /proc/<server pid>/environ` used to hand every one of them back; `/data` is root-owned 0700, so an agent cannot rewrite a budget, a status or `chatDefaultGuards.permissionMode` straight in the database, nor the lock `serverLock.ts` keeps beside it; and the MCP capability file stops being decorative — that last one taking a second cut, because 0600 owned by the agents' uid excluded nobody either: the chat and block child (`chatChildCredentials()`, the one spawn site that differs) keeps the agents' uid and takes `UF_CHAT_GID` instead, and the per-turn directory and file are handed to that group at 0710/0040, so a work-cycle agent that reads `--mcp-config <path>` off a sibling's world-readable `/proc/<pid>/cmdline` fails the owner check, fails the group check, and is left with the "other" bits. A gid rather than a second uid because the chat child must stay the uid that owns `~/.claude`, which is what it bills against; `resolveChatGid` refuses group 0 and refuses the agents' own gid, since either would hand the file to the half it is kept from. The direction is forced, not chosen: the child **must** be the mount owner, because an isolated run is ordered to commit and its commits land in the operator's own `<repo>/.git`, and the server **must** read `~/.claude/.credentials.json`, which the CLI keeps 0600 owned by that same uid — so the privileged half is the one process running code from this repository rather than the twenty-five unattended children whose prompts came out of repositories nobody here reviewed. Two consequences are written down rather than absorbed. The server's own writes into a bind mount land root-owned, so the three that exist go through `chownForChild`. Two of them — the `.uf-worktrees` store and `seedWorktree`'s copies — let it **throw**: a checkout the agent cannot write fails inside a tool call the run loop does not read, which is a run that simply does not do the work. The third, `ensureSandboxMountPoints`' empty files, catches it instead and keeps the file, and the asymmetry is the point: those exist only so bwrap finds a mount point it would otherwise create itself, bwrap binds over a file it does not own, and a run refused at spawn over a cosmetic chown would trade a recoverable tool call for an unrecoverable run. **That third one also writes into `$CLAUDE_CONFIG_DIR` itself**, which is a bind mount of the operator's real `~/.claude` and holds the credential this install bills against, so what bounds it is worth stating: the names are a closed list read out of the CLI's own sandbox construction and pinned there by a test, never a path from a request and never a path from a repository. It creates only the ten the sandbox binds as *files* and none of the twenty-two it binds as directories, so `projects`, `plugins`, `rules` and `skills` can never become an empty file; and of the files it refuses `CLAUDE.md`, `policy-limits.json` and `remote-settings.json`, which are memory a person wrote and policy a managed install is governed by — this app inventing an empty one of those would be authoring the document the CLI then decides against. `.credentials.json` is on neither list: the CLI denies it from `/dev/null` itself, and nothing here creates, reads or names it. And the whole thing is inert when the server is not root — `npm run dev`, the tests, a compose override — which is a boundary that disappears with the page looking identical, so `describeSeparation()` states the arrangement in the boot log and an environment that *names* an agent uid the process cannot switch to throws instead of degrading. What it does **not** buy is in `docs/security.md`: a work cycle can still read the account's own OAuth credential — it has to, that credential is what it bills against — and every child still shares one uid, so the group above is the only thing separating them, and clearing `UF_CHAT_GID` removes it.

- **The child environment is a denylist, and a denylist fails open — so a credential shape gets closed before this app has a use for it, not after.** Six functions hold byte-identical copies of it, deliberately rather than by omission, each citing the block above `CONTEXT_SHAPING_ENV` in `orchestrator.ts` for the reasoning: `childEnv` (the work cycle), `chatEnv` (`chat.ts`), `reviewEnv` (`review.ts`), `verifyEnv` (`landGate.ts`, the check in front of Land — which for a long time passed no `env` at all and so handed the whole list to a command whose script body lives in the tree an agent just wrote), `authEnv` (`claudeAuth.ts`, whose docblock says why it is a copy rather than an import) and `gitEnv` (`git.ts`, a superset). A seventh, `codexAuthEnv` (`codexAuth.ts`, behind the four Codex sign-in commands), is a copy of `authEnv` that is deliberately *not* byte-identical: it differs over the Codex credential variables named below, and its docblock says which and why. **An eighth spawn site adds an eighth copy; it does not add a shared module.** `OPENAI_API_KEY`, `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN` are on all six and reach none of them, which is the point: they are the Codex CLI's three credential variables (`proposals/ProviderFallback/14-validation.md` §1f), a `CLAUDE_BIN` child has no use for any of them, and the one child of those six spawned as `CODEX_BIN`, a Codex work cycle going through this same `childEnv`, authenticates from `$CODEX_HOME/auth.json` rather than from the environment. Before the strip an operator running a second provider's CLI on the same server was handing its credential to twenty-five unattended agents in sessions that have `Bash`, where `env` is read-only shell `acceptEdits` approves without asking. `ANTHROPIC_API_KEY` is the one credential deliberately *not* stripped — it is what a work cycle bills against, and the auth panel has to report the credential runs actually get. `childEnv`, `chatEnv`, `reviewEnv` and `verifyEnv` are pinned by a test (`docs/agent/testing.md`) — the four that feed an agent child, and the four the `PATH` claim in `proposals/CustomStacks/01c-reach-and-permission.md` §2 rests on; `authEnv` and `gitEnv` move by hand, which is what the shared docblock is for. `proposals/ProviderFallback/` is where this was found, and it recommends **against** the per-run provider that would have made these variables this app's business — the strip stands either way.

- **No Claude Code child this app spawns may list or message another session, and one variable is what enforces it.** The pinned CLI turns on cross-session messaging by default, and its scope is the container. Every session writes `<CLAUDE_CONFIG_DIR>/sessions/<pid>.json`, listens at `${XDG_RUNTIME_DIR || tmpdir}/cc-socks/<pid>.sock`, and gets `ListAgents` to find the others, so any run, chat turn or reviewer can reach every other session on this uid. `proposals/CrossSessionCommunication/` measured runs listing siblings on the same repository, runs on other repositories, and a session in the operator's vault folder. Read from the binary, a message that arrives mid-cycle makes the cycle take another turn, `plan` and `acceptEdits` sessions share an acceptance class (so a reviewer could ask a writing run to write), and nothing about the message reaches the receiver's `stream-json`. Every env that spawns `claude` therefore sets `CLAUDE_CODE_HARBOR_KITE=0`: `childEnv` after its extras, so no caller can turn it back on, and `chatEnv`, `reviewEnv` and `authEnv` as the last key. The `localCycleEnv` overlay leaves it alone. With it, `ListAgents` is gone, `SendMessage` stays for the run's own sub-agents and refuses peer addresses, and the inbox never opens. `docs/verification/` has the measurement and what is still open. `--disallowedTools SendMessage ListAgents` is the wrong lever: it removes sub-agent messaging and leaves the inbox open. `pruneEnv` does not set the variable because winnow's `safe run` never spawns `claude`, and its docblock names the winnow paths that would. The variable is the CLI's internal name, so a pin bump re-runs `proposals/CrossSessionCommunication/scripts/native-tools.sh` with `EXTRA_ENV=CLAUDE_CODE_HARBOR_KITE=0` and refuses the bump if `ListAgents` is in `init.tools`. `orchestrator.test.ts` pins the key on all four builders.

- **`UF_GITHUB_TOKEN` is scoped by host and by child, and there are three kinds of child rather than one.** The credential helper `githubEnv()` installs is keyed to `https://github.com`, so a repository whose submodule or remote points at another host asks for credentials and gets none — with `GIT_TERMINAL_PROMPT=0` alongside it, that fails in a second rather than hanging until the run's duration limit. What it reaches is the part to read exactly, because "work cycles and nothing else" has been false since the orchestrator chat gained tools. A **work cycle** takes the credential its own repository is configured with, through `selectGithubToken` off `runs.repo_root`. `chatEnv()` hands the **install-wide** token to `runOrchestratorChild`, which is *two* callers: the orchestrator chat turn and a workflow's orchestrator-block child. That widening is the point of the feature — a turn asked to look at open issues cannot otherwise, and it fails inside a tool call the way `git push` used to — but the child it widens to is the one running `bypassPermissions` with no allowlist and `--add-dir` on every mount, so the token authenticates **writes** as well as reads and the system prompt is the only thing saying not to make them. It is install-wide deliberately and this is the one child where that is still right: an orchestrator turn's whole job is to look across every mount before it knows which repository it is proposing work in, so narrowing it to a cwd would withhold the credential from every question about a repository the turn had not yet been pointed at. The lever that withholds it is the same one as everywhere else and is worth stating rather than deducing: leave `UF_GITHUB_TOKEN` blank and configure only `UF_GITHUB_TOKENS`, and the per-repository credential still reaches work cycles while these two children get none. `UF_*` still leaves that child's environment by namespace, so nothing hands it this app's own credentials.

- **A work cycle can now write to this app's database, and what bounds that is the tool list rather than a file mode.** The capability's third subject is `{ kind: "run"; runId }`, minted per run by `mintRunCapability`, named in an `--mcp-config` written for each cycle and revoked by `revokeRunCapabilities` in `startRun`'s `finally` on every path the loop can leave by — outright, with none of the batching grace the OTLP exporter's credential gets, because a tool call is synchronous with a child that no longer exists and a grace would be a window in which a recovered token still closes tasks. The containment that protects the *chat's* config does not exist here and is not merely absent: the chat and block child takes `UF_CHAT_GID` and its config is handed to that group at 0710/0040, which is what excludes a work cycle reading a sibling's `--mcp-config` path off a world-readable `/proc/<pid>/cmdline`. A run's config must be readable by the agents' own uid, which every work cycle shares, so **there is no file mode that separates two work cycles from each other** and a second gid would not help because all of them would be in it. What answers for that is the size of what a stolen token buys: the eight tools of `RUN_TOOLS` — `list_my_tasks`, `get_my_task`, `complete_task`, `release_task`, `create_task`, `comment_on_task`, `add_task_dependency` and `request_stack` — none of which starts a run, approves anything, installs anything, reads another run's diff, log or transcript, or moves a task the token's own run does not hold. Two read, and what they return is bounded by the token's run rather than by the thief: `list_my_tasks` and `get_my_task` answer with the tasks that run holds and the tasks open in its folder, with every note on them — which includes notes other runs wrote, so a thief reads what any run in that folder could. Six write. `complete_task` and `release_task` move only a task the token's run holds. `create_task`, `comment_on_task` and `add_task_dependency` write onto the board beyond it — a new open task, a note signed by the token's run on a task that run holds or one open in its folder (`get_my_task`'s scope, so a thief writes only where it could read), an ordering edge that gates nothing — each visible as what it is and none able to close or claim work. `request_stack` files a request the operator reads and parks the token's own run at its next cycle boundary until the operator answers, so a thief can stall the run whose token it took and no other, and installs nothing (`security/stacks.md`). `docs/agent/taskboard.md` carries the enforcement — the run id is the token's and no tool takes one as an argument — and the reason a `runId` parameter would turn a bounded capability into an unbounded one. The whole path is behind `taskboardForRuns`, off by default, because a write into this app's database from an agent nobody is watching is an operator's decision rather than a guard's.

- The chat's capability token is compared constant-time against every live token in `subjectForCapability`, rather than looked up by key: a `Map.get` on a secret leaks its prefix through timing. The live set is the number of orchestrator turns in flight — one chat turn, plus whatever blocks of a workflow are deciding right now, plus **one per live run** now that a work cycle carries one too — so it is small rather than one, and the linear scan is affordable for that reason rather than for a bound. What it returns is a **subject** rather than a chat id, and `docs/agent/chat.md` carries why that is a discriminated union.
