# What the chat child loads from files a work cycle writes

[← security index](../security.md)

Read before editing `chatEnv`, `chatHome`, `chatHomeEnv`, `CHAT_GIT_CONFIG`, `chatSettingsArgs` or `chatCwd` in `src/lib/chat.ts`, `scratchDirMode` in `src/lib/privsep.ts`, or `agentGitEnv`'s `extra` and `sandboxOverlay` in `src/lib/orchestrator.ts`.

The chat and block child holds `UF_CHAT_GID`, the one thing keeping a work cycle out of the chat's capability file (`child-uid-and-credentials.md`, first bullet), and that capability approves proposals and starts runs. It runs as the agents' uid, so any file a work cycle can write that this child **executes or loads as configuration** is a work cycle running code with that capability. `child-path-lookups.md` closed the names it runs on `PATH`. This file is the rest, from board task `7dd5f973`. Every "measured" below was measured on 2026-10-06 against scratch files, with Claude Code 2.1.280, git 2.39.5 and Python 3.11.2. Each entry is in `docs/verification/security-and-sandboxing-chat-config.md`.

- **The chat child's `HOME` is its own, because the agents' is every work cycle's to write.** `HOME` was the image's `/home/node`. Three things in it ran in the chat child, all measured. The CLI's `Bash` tool snapshots the shell with `bash -c -l` over the `~/.bashrc` it resolves from `HOME`, so a planted `~/.bashrc` and `~/.profile` both ran. That was read out of the binary and then run against a stub API. The snapshot ran while the sandbox around the tool call failed to start, so turning the sandbox on does not obviously confine it. git read a planted `~/.gitconfig`, whose `core.fsmonitor` ran on `git status`. And `python3` ran a planted `usercustomize.py` from the user site under `~/.local`. Under a chat group, `chatEnv` now hands the child `/run/uf-chat-home`, made by `chatHome()`. It is root's and the chat group's at `scratchDirMode`, `0770`: the child writes there, because the CLI creates `~/.config/anthropic` during a turn (measured), and a work cycle has no bit at all. A directory rather than a list of overrides (`GIT_CONFIG_GLOBAL`, `PYTHONNOUSERSITE`, …), because every tool that keeps configuration under `HOME` — `gh`, `npm`, `ssh`, `curl` — is the same channel, and a list is a denylist. It costs the chat everything the agents keep there, the `gh` extensions `UF_GH_EXTENSIONS` installs included. `chatHome()` **throws** rather than falling back, because the fallback is the agents' `HOME`, the channel reopened with nothing reporting it; `runOrchestratorChild` turns the throw into a failed turn. With no chat group it returns null and `HOME` is left alone, as `mcpConfigOwnership()` leaves the capability file: the child then holds nothing a work cycle does not. `cliPath.test.ts` plants a `diff.external` in `~/.gitconfig`, a `~/.bashrc`, a `~/.profile` and a `usercustomize.py` in the agents' `HOME`, and asserts that each ran under `chatEnv(null)` and that none ran under `chatEnv(<scratch home>)`.

- **Every variable naming a path in the agents' `HOME` leaves with it, except the Claude config directory.** The image states such paths outright: `GOPATH`, `GOCACHE`, `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR`, `UV_PYTHON_INSTALL_DIR`. Each is a place a work cycle writes and a tool loads from, so moving `HOME` alone would leave them pointing back. `chatHomeEnv` removes them rather than rewriting them, because each tool's default is under `HOME`, which is now the chat's. A list variable goes whole if any entry is inside. `PATH` is exempt because it is `chatPath()`'s. `CLAUDE_CONFIG_DIR` and `CLAUDE_HOME` are exempt because they are the operator's Claude home, which the chat bills against and is metered from. `CLAUDE_CONFIG_DIR` is filled in from the old `HOME` when unset; otherwise the CLI would look under the new `HOME` and find no credential. A `HOME` of `/` names nothing, so nothing is removed. Pure, and unit-tested for all of these.

- **A repository's `.git` may not run a command in the chat's git, as far as git lets that be said.** The chat runs `git status`, `log` and `diff` in the operator's checkouts. A work cycle there commits into that `.git`, and no review ever shows it. Measured: a `core.fsmonitor` in `.git/config` ran on `status`, `diff` and `blame`. `.git/hooks/post-checkout` and `reference-transaction` ran on `checkout -b`. `CHAT_GIT_CONFIG` puts `core.fsmonitor=` and `core.hooksPath=/dev/null` into the child's one `GIT_CONFIG_*` block, after the GitHub pairs, through `agentGitEnv`'s `extra`. With them, neither ran, and the env `core.hooksPath` outranked one the repository set itself. These are the two `gitArgs` already clears for this app's own git. `GIT_CONFIG_*` rather than `-c` because it reaches every git the child starts, submodules included. The block is still the child's to override for one command: a `GIT_CONFIG_COUNT` of its own replaces it, which is the chat's own doing rather than a work cycle's. **Still open, measured:** a `diff.external` in `.git/config` ran on `git diff`, and `diff.external=` does not clear it — git dies with "cannot run". A `filter.<name>.clean` or `diff.<name>.textconv`, named from `.git/info/attributes`, ran on `diff`, `log -p`, `show` and `blame`. Those keys are named by the repository, so no fixed override reaches them. No pager ran, because the tool call has no TTY. **Still open, not measured:** the settings git reads only on a network operation — `core.sshCommand`, a `credential.helper` for a host other than github.com, a local remote's `uploadpack` — and `gpg.program` with `log.showSignature`. `cliPath.test.ts` plants `core.fsmonitor` and both hooks and asserts that they run with the block switched off (`GIT_CONFIG_COUNT=0`) and do not run under `chatEnv()`.

- **The chat reads the user's settings and nobody's cwd, and runs no hooks.** Measured against a stub API with the chat's flags: a planted `SessionStart` and `PreToolUse` hook ran from each of `$CLAUDE_CONFIG_DIR/settings.json`, the cwd's `.claude/settings.json`, the cwd's `.claude/settings.local.json`, and a plugin's `hooks/hooks.json`. A work cycle writes the cwd files in any checkout it works in, and the second is never in a diff. The default cwd `/run/uf-chat` was `chownForChild`'s, which is the agents'. The enabled plugins live in `$CLAUDE_CONFIG_DIR/plugins/`, which `UF_LOCK_CLAUDE_HOME` leaves agent-owned; this install's `orient@orient` carries a `hooks.json` there. `chatSettingsArgs` passes `--setting-sources user`, which drops both cwd scopes: measured for their hooks, and by the flag's definition for their `env` and `apiKeyHelper` too. It also passes `disableAllHooks` in `--settings`, which stops the user's and every plugin's hooks. Both were measured to do so, and `--agent` still selects a saved agent under the first. `chatCwd()` now makes `/run/uf-chat` root's and the chat group's at `0770`, the same as the home, wherever there is a chat group. The cost is that no hook the operator wrote runs in a chat turn. That is the trade `chatPath` made for the same child. **One `--settings`**, carrying the sandbox overlay from `sandboxOverlayFor` too, because the CLI keeps only the last `--settings` it is given. Measured: a `disableAllHooks` followed by a sandbox overlay ran every hook. A second flag would silently drop either the hook switch or the sandbox write set. That is pinned by a unit test over `chatSettingsArgs`. `promptArgv.test.ts`'s parsing stub knows the flag, so the chat's real spawn still parses.

- **What is still open, and what would settle it.** First, `$CLAUDE_CONFIG_DIR/settings.json` itself. Its `env`, `apiKeyHelper` and permission rules still reach the chat, since the user scope is kept on purpose, so a work cycle that can write that file can still reach the chat. `UF_LOCK_CLAUDE_HOME=1` is what closes it (`../environment/sandbox-and-claude-home.md`), and no container has run that lock. Second, `CLAUDE.md`, `rules/`, `skills/`, `agents/` and `commands/` under the same directory stay agent-owned under the lock. They are text the model reads rather than code anything runs, so they were not in scope here. Third, the repository git settings listed as open above. Fourth, whatever the chat chooses to run in a checkout: a `Makefile`, a `package.json` script, a `conftest.py`, or `python3` with the cwd first on `sys.path`. The chat reads trees work cycles write by design, its prompt tells it to look and not build, and no environment variable changes that. And nothing above has run in a booted image as root. The two directories' ownership, a turn completing with `HOME=/run/uf-chat-home`, and a work cycle refused at both paths are unmeasured; the verification file carries the commands.
