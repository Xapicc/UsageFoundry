# What a reviewer or validator may read

[← security index](../security.md)

Read before editing `assistSettingsArgs` or its call in `spawnAssist` (`src/lib/review.ts`), the `permissionMode` any caller of `startAssist` passes, or the `assist` case of `sandboxSettings` in `src/lib/orchestrator.ts`. What an assist loads from the main checkout is [project-config-discovery.md](project-config-discovery.md)'s, and what a work cycle may write is [file-tool-write-boundary.md](file-tool-write-boundary.md)'s.

- **A reviewer or validator refuses a file-tool read outside its checkout, through `permissions.blockReadsOutsideWorkingDirectories` in the assist's one `--settings`, because `plan` refuses no read.** Decided 2026-11-09 under board task `a73d9d8a`. On 2.1.319 against a stub API, a validator through `startAssist` and a reviewer through `startReview`, both `--permission-mode plan` in a run's linked worktree, read a file in each of two directories beside the mount and one in another repository on it. `Read`, `Grep`, `Glob` and a `Read` spelled `../../other/…` all returned the contents, and no rule anywhere granted any of it. That held under this container's managed sandbox, where the app puts a write set on the argv, and with `/etc/claude-code` hidden, as on a stock install, where it puts none. It matters because both prompts carry text the run wrote, its diff and its task, and the answer is stored in `run_reviews` and shown on the run's page. An instruction planted in either could have the judge quote another repository, another run's worktree or the transcripts under `CLAUDE_CONFIG_DIR` into its verdict. With the setting, every one of those reads was refused with an `is_error` result naming the path, the checkout and the setting, on both installs. Reads in the checkout, the files the diff names among them, still worked, and so did a `git log` through `Bash`. The CLI also refused a `Bash` `cat` of the outside file, naming the setting. It is emitted on a stock install too, because it rides `assistSettingsArgs`' flag rather than the sandbox overlay, which is withheld there. The "keeps a plan-mode assist's file-tool reads in its checkout" case in `review.test.ts` pins it. `docs/verification/security-and-sandboxing-assist-reads.md` has the measurements.

- **A sandbox `denyRead` would not have done it, and neither would a deny rule.** A `sandbox.filesystem.denyRead` naming the three directories, on the same `--settings`, refused none of the five reads. It confines `Bash` and nothing else, which is also why the managed policy's `denyRead` of `/data` and `/backups` says nothing about what the file tools may open. A `permissions.deny` cannot say "outside the cwd": a rule names what it denies, and a deny outranks every allow, so a deny on everything takes the checkout with it. That last point is the CLI's documented rule order and was not measured.

- **What it costs is a judge's reads of anything but its own checkout, and on this install that is almost nothing.** Across this container's transcripts from 2026-10-13 to 2026-11-09, 569 validator sessions made 56 file-tool calls and none was outside the session's cwd. The one reviewer session made 10 `Read`s of `/tmp` files it had written through `Bash`, and those are now refused, as a `cat` of them would be. A validator for a run whose folder is a subdirectory of a repository is refused the repository's other files, though the diff it is shown can name them: in that cwd the repository root's `README.md` was refused. The CLI exempts its own spilled tool output, so a large `Bash` result stays readable. The setting has a sandbox half: with a managed sandbox it hands bwrap a `--tmpfs` over `/home`, `/media`, `/mnt`, `/root`, `/srv` and `$HOME`. A `git log` in the worktree still ran under it, and the image's `safe.directory` and `user.*` are `--system` git config, outside every one of those.

- **The resolver is left without it.** `acceptEdits` already asks before its `Read` leaves the checkout, and a `-p` child has nobody to answer, so it was refused the three reads and the relative one with the setting or without it. Its `Grep` and `Glob` were not refused, because `--allowedTools` names both on every assist, and an allow rule with no path covers every path. That reach is filed as its own task. The sandbox half above would hide `$HOME` from a build command `resolveAllowedTools` grants it, and what that breaks was not measured.

- **What it does not cover.** The CLI's schema says the setting does not limit shell commands, and only a command that names an outside path was driven. A `Bash` command whose path the CLI cannot read is left to the permission mode. In this rig such a `cat` without the setting was refused as "Auto mode is unavailable", because the stub runs no safety check. What a real API decides there was not measured. Under a managed sandbox, `Bash` itself can still read the mounts, and `plan` does not stop a sandboxed command. This install's one reviewer session, `permissionMode: plan` in its transcript, ran `tsc` and `node --test` and wrote their output to `/tmp` through `Bash` without an error. That is filed as its own task. MCP tools were not driven. The server running as root and dropping the child to the agent uid was not run, and no assist started by a running server has been seen carrying the setting. The rig was the compiled modules in a scratch process.
