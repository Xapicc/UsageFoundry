# What a dropped child runs by name

[← security index](../security.md)

Read before editing `SERVER_PATH`, `CLAUDE_BIN`, `CODEX_BIN` or `spawnCommand` in `src/lib/config.ts`, `chatPath` in `src/lib/stacks.ts` or the `PATH` `chatEnv` sets, or a `setpriv` line in `docker-entrypoint.sh`.

- **What a dropped child is spawned as is decided on root's `PATH`, never on its own.** `CLAUDE_BIN` and `CODEX_BIN` used to reach `spawn` as the bare names they default to, and Node looks a bare command up on the `PATH` of the `env` it is handed. Every builder for a dropped child (`security/child-uid-and-credentials.md`) sets that to `agentPath()`, whose second entry is the agent-owned `/home/node/pytools/bin` on a persistent volume, so a `claude` a work cycle left there was what every later spawn ran: the next work cycle, every reviewer, `claude auth`, and the chat and block child, which holds `UF_CHAT_GID`. One write moved a work cycle into the chat's capability, where it can approve proposals and start runs, and it survived restarts (board task `af2a031b`). It was no route to root, because each of those spawns drops the uid before the lookup, but it reached the one gid the first paragraph of `security/child-uid-and-credentials.md` builds on. `config.ts` now resolves both once, at boot, against `SERVER_PATH`. That is the server's own `PATH`, root's in the image, and it names nothing an agent or a stack can write. An operator's absolute value is kept as written, and a relative one is resolved against the server's cwd rather than each child's worktree. Every spawn of either goes through `spawnCommand`: the work cycle (`runIteration`, either adapter), the reviewer, the chat and block child, and `claudeAuth.ts`'s and `codexAuth.ts`'s. It does two things the bare spawn did not. **It refuses a name that did not resolve**, with a sentence naming the variable and the `PATH` it searched, rather than handing it to the child to find. The boot does not refuse, because Codex is optional and the tests and `smoke-pages.mjs` point `CLAUDE_BIN` at stubs, so `instrumentation.ts` logs the same sentence instead. Each caller already handled a synchronous spawn failure, so the refusal lands as that caller's failure: a failed run, assist or turn, or an error on the auth panel. **And it resolves a `#!/usr/bin/env <name>` interpreter on the same `PATH`**, spawning it with the script as its first argument, because otherwise `env` repeats the lookup this closes one step later. The image's `codex` is `codex.js` behind exactly that line, so a `node` planted in the pytools directory used to run every Codex cycle and sign-in. The image's `claude` is a native binary and is spawned as it is. `cliPath.test.ts` plants all three names first on the agents' `PATH` and asserts that none ran.

- **The boot's own dropped helpers keep the same rule.** `uv_as_agent` in `docker-entrypoint.sh` ran `env PATH=<the agents'> uv`, which looked `uv` up on that `PATH`, so a `uv` a work cycle left in the pytools directory ran at every boot with `UF_PY_TOOLS` set; and because that was `env` rather than `env -i`, it ran holding the entrypoint's whole environment, `UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY` and the GitHub tokens included, which nothing an agent is spawned with carries (board task `7e2073d5`). It and `gh_as_agent` now name `/usr/local/bin/uv` and `/usr/local/bin/gh` and hand the dropped process `env -i` with an allowlist, as `winnow_filter_as_agent` already did: `HOME`, a `PATH` for what the tool itself spawns, and the image's four `UV_*` or `GH_TOKEN`. `deployment.test.ts` asserts that every `setpriv … env` in the entrypoint is `env -i`, names no `UF_*` or `ANTHROPIC_ADMIN_KEY`, and runs a program by a path the `Dockerfile` installs.

- **What the chat and block child runs by name once started is decided on root's `PATH` too.** `spawnCommand` reaches only the executable, and that child's own `Bash` calls run `git`, `ls` and `python3` by name and a hook is often an `env node` script, so a `git` a work cycle left in the pytools directory ran the next time a chat turn ran `git`, under `UF_CHAT_GID` (board task `6f85c72a`). `chatEnv` sets `PATH` to `chatPath()` (`stacks.ts`): the agents' `PATH` less every directory that is neither on `SERVER_PATH` nor the stacks' toolbox, which the applier leaves root-owned and `go-w`. A filter rather than a list, so a directory added to `UF_AGENT_PATH` later reaches the chat only if root's `PATH` already has it. Installing pytools as root instead was weighed and refused: it would close the one directory and change what `UF_PY_TOOLS` is for every agent, where this closes the class for the one child that holds a gid the others do not. What it costs is that a `UF_PY_TOOLS` launcher does not resolve in a chat turn, a hook in the operator's own `~/.claude` settings that calls one included; the chat gets no `--plugin-dir`, so no plugin this app registers is affected, and the same package as a `uv-tool` stack does resolve. Work cycles, reviewers and the auth children keep the agents' whole `PATH`, because they hold nothing a work cycle does not. `cliPath.test.ts` plants a `git` and a `node` first on the agents' `PATH` and asserts that neither ran from `chatEnv()`. This closes lookups on `PATH` and nothing else the chat child reads from a place an agent writes, such as its `HOME`.
