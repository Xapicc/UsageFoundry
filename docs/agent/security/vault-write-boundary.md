# The knowledge vault's write boundary

[← security index](../security.md)

Read before editing the `vaultSkill` option, its `permissions.additionalDirectories` entry, the `--disallowedTools` list or the `--settings` overlay in `buildArgs` (`src/lib/cycleInvocation.ts`), `vaultWritableBy`, `VAULT_GLOB_CHARS` or the search command in `renderVaultSkill` (`src/lib/vaultSkill.ts`), the `vaultSkill` argument at the run loop's `buildArgs` call in `src/lib/orchestrator.ts`, or `searchVault` in `src/lib/vaultPointer.ts`.

- **The vault is read-only to every run whose workspace is not the vault, and the harness enforces that, not the skill.** A run with the vault skill on gets the vault as a working directory, a `permissions.additionalDirectories` entry in its one `--settings` overlay, so that it can read what the skill names. That entry also puts the vault in the run's sandbox write set, and makes it a working directory the file tools edit without asking, exactly as the `--add-dir` it replaced did (below). Until 2026-10-31 only the skill's "Never write to the vault" stood in the way, and a run that writes where it should not is the poisoning risk in the operator's own research (`3 Resources/AI Security/Memory and Knowledge Base Poisoning.md`). The fix was measured, not assumed. On 2.1.310 against a stub API, a run with `--add-dir` alone created a note with `Write`, rewrote a notebook with `NotebookEdit` and created a file with Bash `touch`, and bwrap was given the vault as `--bind`. With the two denies below, under `acceptEdits` and `bypassPermissions` alike, the same run still read a note and ran the search. Every write failed: `Write`, `Edit` and `NotebookEdit` by the permission rule, and Bash `touch`, `>`, `sed -i` and a Python `open()` with `Read-only file system` inside a sandbox that had started. Writes into the run's own workspace landed. `scripts/sandbox-probe/vault-readonly-probe.mjs` is the measurement, and `docs/verification/knowledge-and-plugins.md` has its caveats.

- **Each deny closes only one half, so both are emitted, and dropping either one silently reopens that half.** `Edit(//<vault>/**)` on `--disallowedTools` refused `Write`, `Edit` and `NotebookEdit` (the CLI's `Edit` rule covers all three, measured), but bwrap still got the vault as `--bind`. `denyWrite: [<vault>]` beside `allowWrite` in the `--settings` overlay made the CLI hand bwrap a `--ro-bind` of the vault after the `--bind`, but `Write` and `Edit` still wrote: the sandbox config binds Bash and nothing else. Both ride flags that already exist, and that is the property to keep. A second `--disallowedTools` or a second `--settings` replaces the first: the first case drops the process-kill denial, the second drops the endpoint pins or the write set. Every cycle's `blockWritesOutsideWorkingDirectories` ([file-tool-write-boundary.md](file-tool-write-boundary.md)) does not stand in for the `Edit` deny. The vault's entry makes it a working directory, and with the setting on a vault writer's `Write` into the vault still landed (2.1.319, through `--add-dir` and through the entry alike).

- **The vault is a working directory through the overlay's `permissions.additionalDirectories`, never `--add-dir`, because that flag loads the vault's `.claude/` into every reader.** Decided 2026-11-08 under board task `7a30963a`. On 2.1.319 against a stub API, a skill and an agent planted in the vault's `.claude/skills/` and `.claude/agents/` were in a reader's requests when the vault was an `--add-dir`, under `acceptEdits` and `bypassPermissions`, and in no reader's request when it was the overlay's entry. Vault writers can create and commit those files, so through the flag one write into the vault became a skill or agent in every reader's context, and a skill's `allowed-tools` is applied even in an untrusted `-p` folder. The entry keeps everything the flag was there for, each measured on the same pin: a reader's `Read` of a note under `acceptEdits`, which with neither spelling was refused as ungranted; the skill's search; and the write set the reader's `denyWrite` takes back, since bwrap still got the vault as `--bind` and then `--ro-bind`. Every write into the vault the probe tries was still refused. A writer still wrote into its worktree and into the vault outside it. The vault rides the same list as the scratch directory, after it, for readers and writers alike, so an argv without the skill keeps its bytes; the "never hands the vault over as --add-dir" case in `orchestrator.test.ts` pins it and failed with the flag put back. On a vault with no `.claude/`, the first request was the same under both spellings apart from the CLI's temporary settings-file name, which hashes the overlay. `vault-readonly-probe.mjs` and `write-boundary-probe.mjs` (turn 4v is the `--add-dir` control) are the measurement, and `docs/verification/security-and-sandboxing-file-tool-writes.md` has its caveats. The run loop's sandbox mount points no longer reach the vault, because `addDirsIn` reads `--add-dir` off the argv; on 2.1.319 bwrap was handed nothing inside the vault's `.claude/` under either spelling, so nothing it asks for was lost.

- **`denyWrite` rides on the write set and is withheld wherever the write set is.** A write config of any kind binds `/` read-only and rw-binds only what is allowed, so a deny with no allow beside it is a policy nobody has measured. That is `sandboxOverlay`'s reason for `denyRead`. So on an install with no managed sandbox (`UF_SANDBOX` blank, the stock install), and on a sandboxed install whose run paths `sandboxWritableRoots` could not spell, a reader gets the `Edit` rule alone. **There, Bash can still write the vault.** Nothing on the argv confines Bash on such an install, and the vault has to stay writable at the agents' uid for the runs below.

- **A run may write the vault only when its checkout or its repository is at or below the vault — `vaultWritableBy`.** That covers the operator's own runs on the vault, an isolated one in a worktree under the vault's `.uf-worktrees/`, and Dreaming's writer, which is a run whose folder is the vault (`dreamingRun.ts`). The repository counts as well as the checkout because a vault below a mount root keeps its worktrees in the mount's `.uf-worktrees/`, outside the vault, while its runs still commit into the vault's own `.git`. A run whose folder only *contains* the vault is a reader: it can see the vault but was not asked to change it. The comparison is lexical, on paths the run loop already resolved, and a name that merely starts with the vault's is not inside it. The writable argv is the reader's without either deny: the same `additionalDirectories` entry, which hands bwrap the vault as `--bind` (measured, 2.1.319). `writable` absent is read-only, so a call site that forgets to decide gets the safe argv. These runs write the whole vault, not only their worktree: `denyWrite` outranks `allowWrite`, so the vault cannot be denied with a hole left for one worktree.

- **The search writes nothing into the vault, so a read-only vault does not break it.** `vault_search.py` builds its BM25 index in memory on every call and keeps no index file. Its one write is the bytecode of `vaultlib.py`, which it imports, into `_Meta/__pycache__/`. Measured on a read-only copy: exit 0 with byte-identical output and no bytecode written, because CPython skips a bytecode write it cannot make. Measured in the probe: run without `-B` inside the sandbox, the search answered and left no `__pycache__`. Both the skill's command and the pointer's own search (`searchVault`) are `python3 -B` anyway. The pointer's search is a child at the agents' uid outside any sandbox, so without `-B` it was writing into the vault on every reader's behalf.

- **A vault whose path reads as a glob pattern gets no skill rather than a writable one.** The CLI drops a `sandbox.filesystem` entry with `*?[]{}!` in it on Linux, with only a debug line, and an `Edit(...)` rule with one in it matches some other set of files. `prepareVaultSkill` answers `unavailable` for such a vault, and that is a line on every cycle's log. A vault run loses its skill along with every reader, which costs it nothing it uses.

- **What is still open.**
  - **No managed sandbox.** On the stock install and the `unconfined` reading above, a reader's Bash can write the vault. Closing that would need the vault non-writable at the agents' uid, which would break its own runs and Dreaming. Short of that, the skill's sentence is still the only thing in a reader's way there.
  - **Not yet run in the container.** The probe ran nested inside an agent's own sandbox, where bwrap starts only on some pids, and against a scratch vault under `$TMPDIR` rather than the bind-mounted vault. No work cycle spawned by the app has yet been seen refused. `docs/verification/knowledge-and-plugins.md` has the command that settles it.
  - **`allowNestedUserNamespaces` must stay off in the managed policy.** The CLI's own schema says a command allowed nested user namespaces "can then take the read-only binds that enforce denyWrite … out of its own view". The entrypoint does not set it, and nothing else may.
  - **`~/.claude/settings.json` is an honoured source for `sandbox.filesystem`** (`sandboxSettings`' note). A run that writes `allowWrite: ["/"]` there cannot undo a `denyWrite`, which outranks it. A key that switches filesystem policy off is pinned to managed settings once the managed policy names `sandbox.filesystem`, which this install's does (`docs/agent/environment/sandbox-and-claude-home.md`).
  - **A reader whose folder contains the vault is shown the vault's `CLAUDE.md`.** Measured on 2.1.319: after such a run read a vault note, the vault's root `CLAUDE.md` was in its next request; the vault's skill and agent were not. The overlay entry does not reach this, since the vault is inside the run's own folder. Board task `b2fd06d0`.
  - **A vault writer in a worktree is shown the vault's own untracked `.claude/`.** The CLI reads a linked worktree's main checkout for skills (measured, board task `687b0d2f`), so a writer under the vault's `.uf-worktrees/` sees what any other writer left in the vault uncommitted. That is the writer's own repository, and the reader-side door above is what this boundary is for.
  - **Codex.** A Codex cycle is never given the vault (`buildCodexArgs`), and under `workspace-write` it cannot write there (measured 2026-10-07). Under `bypassPermissions` Codex runs with no sandbox at all, so it can.
