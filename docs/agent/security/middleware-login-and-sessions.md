# Middleware, login, sessions and the audit trail

[← security index](../security.md)

Read before editing `src/middleware.ts`, `/api/login`, `/api/logout`, `/api/status`, `src/lib/sessionToken.ts`, `src/lib/loginLimiter.ts`, `src/lib/requestLog.ts` or `src/lib/ops.ts`.

- **A monitor must not be handed the credential that starts agents.** `UF_AUTH_TOKEN` opens every route in the app, including the ones that spawn billed children, so polling any of them from a monitoring system means a scraper holds the master key. `UF_STATUS_TOKEN` is a second, read-only credential that reaches `/api/status` and nothing else, checked in that route rather than in the edge middleware for `/api/mcp`'s reason. The exemption is **conditional on the variable being set**, which is the one thing about it not to undo: with no read-only token configured there is nothing to check, so the route falls back behind the ordinary gate and an operator who never set one gets a 401 instead of an open endpoint. The payload's own rule is the second half — counts, bytes, fractions and timestamps, never a prompt, a folder path, a setting or a branch name — and it is stricter than it looks, because a monitoring system retains and forwards what it scrapes.

- `src/middleware.ts` runs in the **edge runtime**: it reads `process.env.UF_AUTH_TOKEN` directly and must not import `lib/config` (which pulls in `node:os`/`node:path`). It may import `lib/sessionToken`, which is Web Crypto and string handling and imports nothing at all — that constraint is what shapes the cookie, below. Comparison is constant-time; API paths get 401, page paths redirect to `/login`. Five paths are exempted, and two of them **authenticate themselves** for one reason: the credential each takes is a per-turn or per-run capability, and checking it needs SQLite and module state, neither of which exists in the edge runtime. `/api/mcp` is the chat's tool surface; `/api/otlp/v1/logs` is a run's telemetry export, exempted when the exporter stopped carrying `UF_AUTH_TOKEN`. Removing either check makes that surface public — the tool list in one case, an open write into `otlp_requests` in the other, where a pre-inserted `request_id` is silently dropped by the `INSERT OR IGNORE` and understates the figure a live spending guard reads. Keep each of those exemptions paired with its check. **And an exempted path's own refusal must not be written into a capped table**, which is the second thing `/api/mcp` owes its exemption: `auditMutation` wrapped the handler from outside, so a credential-free POST — a request that has passed nothing, since the middleware let it by — wrote a `request_log` row, and every insert evicts past the 20,000-row cap. That handed anyone who could reach the path a lever on the audit log itself: twenty thousand correctly-refused requests, and every line naming a run that was started, a setting that was changed or a sign-in that failed is gone. Only the handler that already holds a subject is wrapped now, `DELETE` (a 405 answered before any credential is read) is not audited at all, and the refusal goes to stdout, which nothing caps. `/api/logout` is the third, and it is the one that grants nothing — **on the branch that clause describes**. It revokes the id inside the cookie it is handed, so requiring a valid session there would make a stale cookie the one state an operator can never leave. The `all: true` branch is not that branch and was not covered by the sentence: it is handed no cookie, acts on sessions the caller was never given, and used to run for anyone who could reach the port — zeroing the `activeSessions` figure an operator reads to check whether anybody else is signed in. It now takes a credential of its own, a signature-valid cookie or the master bearer, and its 401 is answered **before** any audit wrapper for the reason `/api/mcp`'s is: an exempted path's own refusal must not spend the `request_log` cap. A revocation that actually happens writes an `ops_events` row instead. `/api/health` is the fourth, and it is exempt on a different ground again: it holds no credential of its own and answers with counts, so what keeps it safe is the *shape of its payload* rather than a check. That makes the exemption a constraint on the route — run counts, whether SQLite answers, whether this process owns `DATA_DIR`, two timings, and nothing else. A prompt, a folder path, a setting or a token added to that body turns this line into an unauthenticated data route, and the test beside it asserts the absence rather than trusting the comment. `/api/status` is the fifth and the only *conditional* one — see the read-only-credential note above.

- **The audit trail is two tables, and which one a line belongs in is decided by what evicts it.** `request_log` is the trail of *requests* — method, `pathname`, status, subject, credential class, first hop, duration — written by `auditMutation` at the export of every mutating route behind the gate, and it is a 20,000-row window trimmed on every insert. That is right for what it holds and wrong for a credential: the line saying the OAuth credential every billed child runs against was replaced is the one that has to survive twenty thousand ordinary presses, and it is the first thing an ordinary week deletes. So a mutation that *changed* something also writes `recordDurableMutation` into `ops_events`, which is written at boot frequency and at operator-press frequency and which ordinary traffic therefore cannot evict. **Both, not either**, and each half covers what the other cannot: the wrapper records the refusals, which is the line an audit most wants and which the durable half never sees, because the durable half fires only behind a success. Every credential route follows one rule — the row is written when the credential changed, never when the press was made, so a refused code, a cancel over no pending login and a CLI that would not run leave the request line alone. **Who** is the credential class and the first hop and nothing else: this install has one credential and no user model, so any name in a row here would be invented rather than recorded, and `detail` is named field by field for the reason `request_log` takes no body — a body posted to `/api/codex-auth/api-key` is an API key, and `recordOpsEvent` writes to SQLite *and* stdout in the same call. The one thing not to undo: `ops_events` keeps **500** rows against `request_log`'s 20,000, so a durable row written on an exempt path's refusal is a forty-times sharper version of the `/api/mcp` lever below — an anonymous caller empties the durable trail in five hundred requests. `/api/logout` is the only exempt path that writes here, it is unwrapped for that reason, and both of its branches record only after a revocation has happened; `revokeSession` returns whether *this* call was the one that ended the session precisely so a replayed cookie is worth one row rather than one per replay.

- **`/api/login` is the one unauthenticated write surface here, so it is the one route with a rate limit.** `middleware.ts` exempts it correctly — the page has to be reachable — and nothing else bounded it: no counter, no lockout, no record, and a 400 ms `await` on a timer that delays one request and serialises nothing, so two hundred concurrent connections guess at the rate of the event loop and compete with every running agent for the one Node process. `planLoginAttempt`/`recordFailure` in `loginLimiter.ts` are the decision, pure and unit-tested for the usual reason: a limiter that never fires is bit-for-bit the unbounded route, and one that never lets go locks the operator out of an app whose only other credential is an environment variable and a restart. **Two budgets, and the second exists because the first is evadable**: a source is `x-forwarded-for`'s first hop, which a client sets itself when no proxy is in front, so an attacker who rotates it gets a fresh per-source budget every request — the install-wide bucket is what still bounds them. The global lockout is deliberately **much shorter** than the per-source one (60s against 15min) because it refuses the operator too, so a sustained attack degrades sign-in rather than removing it. **A request with neither `x-forwarded-for` nor `x-real-ip` has no source**, and is held to the global budget alone. It used to be the source `"unknown"`, one bucket for every such client — which behind compose's own port binding, with nothing in front, is every browser including the operator's — so ten guesses from anybody put the operator under the fifteen-minute lock, and ten more a quarter hour kept them there: the premise that the long lock falls on the guesser fails exactly when the guesser cannot be told from the operator. Nothing is given away, since that guesser could always have written a fresh header for a fresh bucket. What this does **not** close is a proxy that *appends* to a client-written `x-forwarded-for` (`$proxy_add_x_forwarded_for`): the first hop is then whatever the client wrote, so somebody who knows the operator's address can still fill that address's bucket. Closing it takes a configured count of trusted hops read from the right, which is a new variable; it is board task f21c1a57. The check runs **before the body is read and long before the token is compared**, and answers the *same body* as a wrong token with a 429 and a `Retry-After` — a limiter that let a correct token through while locked would be an oracle telling the guesser when they had got it right. **The check and the charge are one synchronous step**, `reserveLoginAttempt`, a single transaction with nothing awaited inside it: every attempt is charged as a failure the moment it is allowed, and the success refunds it by clearing. They used to sit either side of the body's `await`, so every request in a concurrent burst passed the check before any had recorded a failure — three hundred wrong tokens at once were three hundred comparisons, and both lockouts fired after the last of them. Do not move the charge back behind the comparison: the route has to await its body, and any `await` between the two reopens exactly that. The cost is that the lockout line on stdout counts *attempts*, since the one that reaches the threshold has not been compared yet and may still be the operator. State is in `login_attempts` rather than a `Map`: a burst has to be visible afterwards, and a lockout held in memory is one an attacker clears by restarting the container, which `restart: unless-stopped` does for them. A successful sign-in clears **both** buckets, the global one included, because the person who just presented the token is the operator. The Settings page reports the count, the first and the last, and the row is absent at zero. The comparison is `node:crypto`'s `timingSafeEqual` behind a length guard rather than `!==`: the 400 ms floor masks the difference in practice, and the point is that `middleware.ts` goes to the trouble for the same secret and two paths comparing one token should not differ in how. A body that is not a JSON object carrying a token (`null`, an array, one that does not parse) is a wrong guess, counted and delayed like one, and never a 400 through `readJsonObject`: this door gives every caller without the token one answer, and a second refusal would be a second answer to learn from; `null` used to throw here, answering anyone who could reach the port with a 500 and a stack trace in the log.

- **The session cookie is a handle, and the master token is what it is deliberately not.** `uf_session` used to be `UF_AUTH_TOKEN` byte for byte, `secure: false`, for thirty days — so a browser jar held a replayable copy of the credential that opens every route as a bearer header, and invalidating one meant editing `.env` and restarting the container, which kills every run in flight. It is now `v1.<32 random bytes>.<expiry>.<HMAC-SHA256 keyed by the token>`: not the token, not usable as a bearer (the bearer branch still compares raw equality against the token, which is what a script presents — `telemetryEnv`'s OTLP exporter no longer does, carrying a per-run capability the ingest route checks for itself), and carrying its own signed absolute expiry — `SESSION_TTL_MS`, 24h, with no sliding renewal, because a window an active holder can extend is a window a *captured* cookie never leaves. The id names an `auth_sessions` row, so `POST /api/logout` revokes one (or all) and the Settings page can say how many are outstanding — questions the old cookie could not answer at all. What that does **not** buy is written down rather than absorbed: the edge gate cannot read SQLite, so a revoked session's *captured* cookie stays signature-valid until its own expiry. Closing that means moving the gate off the edge runtime, which is a change to what `middleware.ts` is. **The Settings copy under "Sign out everywhere" says so in one line**, because the button used to be described as the remedy for a cookie that got out, which is the one case this shape cannot answer. And a *second* place had not absorbed it either: `/api/status` authenticated a browser by comparing `uf_session` against `UF_AUTH_TOKEN` — the shape the cookie had *before* this change — so the branch that exists to let the operator's own browser read that route could not be satisfied by any cookie the login route can issue. It verifies with `readSessionCookie` now; anything keyed on the cookie *being* the token is a leftover of the old shape and is a bug. `Secure` is decided by `cookieIsSecure` — `x-forwarded-proto`'s first hop, then the URL's protocol, with `UF_COOKIE_SECURE` overriding **both ways**: `"1"` for a terminator that sets no header, `"0"` because a false positive is an install where sign-in appears to work and no cookie ever comes back. `httpOnly` and `sameSite: "lax"` are unchanged and are what stands in for CSRF protection. `next.config.ts` sets HSTS, `nosniff`, `frame-ancestors 'none'`/`X-Frame-Options` and a referrer policy; there is deliberately no `script-src`, since one written without measuring Next's inline bootstrap and the pre-paint theme script is a blank page.
