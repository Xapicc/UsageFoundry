# The file tools' write boundary

[← security index](../security.md)

Read before editing the `permissions` key of the `--settings` overlay or the `scratchDir` option in `buildArgs` (`src/lib/cycleInvocation.ts`), the `scratchDir` argument at the run loop's `buildArgs` call in `src/lib/orchestrator.ts`, or anything that adds an `--add-dir` to a work cycle.

- **Every Claude work cycle refuses a file-tool write outside its working directories, and the CLI enforces that, not the sandbox.** `permissions.blockWritesOutsideWorkingDirectories: true` rides the cycle's one `--settings` overlay on every install, sandbox or none. The sandbox write set confines `Bash` and nothing else ([vault-write-boundary.md](vault-write-boundary.md) measured `Write` and `Edit` writing where bwrap refused). So until 2026-11-08 an isolated run's `Write`, `Edit` and `NotebookEdit` could reach the main checkout it was isolated from, its repository's `.git`, any other repository in the mount, and `~/.claude`, under every template's `bypassPermissions`. The setting was measured on 2.1.319 against a stub API, under `bypassPermissions` and `acceptEdits` alike. Each of those writes was refused, including one spelled through `..` and one through a symlink inside the checkout. The model got an `is_error` tool result naming the path, the working directories and the setting. Writes inside the checkout, `package.json` included, still landed. `true` from the overlay held against a `false` in the checkout's own `.claude/settings.json`, and the CLI's schema says `true` in any source wins. `scripts/sandbox-probe/write-boundary-probe.mjs` is the measurement, and `docs/verification/security-and-sandboxing-file-tool-writes.md` has its caveats.

- **The working directories are the cwd, each `--add-dir` and each `permissions.additionalDirectories` entry, and the sandbox write set is not among them.** With the setting on, a write to `$TMPDIR`, the CLI's per-uid temp root, a literal `/tmp` path, the repository's `.git` or `CLAUDE_CONFIG_DIR` was refused, though bwrap would have let `Bash` write every one. The CLI exempts what it keeps for itself: a write to this project's auto-memory landed, under the worktree's project key and the main checkout's. A plan file whose name the CLI had not chosen was refused, and a `-p` session is offered no scratchpad.

- **The temporary directory is made a working directory through `permissions.additionalDirectories`, never `--add-dir`, because `--add-dir` loads what is in it.** Without the temporary directory, the setting breaks a path runs use. Over this container's transcripts from 2026-10-10 to 2026-11-08, 283 of 3,576 file-tool writes went to `/tmp`, in 164 of the 561 sessions that wrote at all, and 282 of those 283 went under the `$TMPDIR` a sandboxed `Bash` command is given. Measured on 2.1.319, an `--add-dir` of a directory put the skill and the agent planted in its `.claude/` into the request the model was sent. The temporary directory is shared by every run on the install, so as an `--add-dir` it would let one run plant a skill into every other run. Through `additionalDirectories` the same planted files reached no request, and the scratch writes landed. The run loop passes `os.tmpdir()`, the directory `writeSet` already names. What that grants the file tools, all of it including other runs' scratch, is what `Bash` already had under the write set.

- **A settings file is refused even inside the checkout.** The CLI refuses a file-tool write to a Claude Code settings file while the setting is on, because such a file could lift it, and the checkout's `.claude/settings.json` was refused. No session in the transcripts above wrote a settings file with the file tools. A run asked to change one can still do it through `Bash`, which is also why the overlay's `true` outranking every file is what holds and the refusal is not.

- **What it does not cover.**
  - **`Bash`.** The CLI's schema says the setting does not limit shell commands, MCP tools, the programs hooks run, or the memory tools. `Bash` is confined by the sandbox write set alone, and only where a managed sandbox is on. On the stock install a cycle's `Bash` still writes anywhere the agent uid can, the main checkout included.
  - **The vault.** Its `permissions.additionalDirectories` entry makes the vault a working directory, so the setting lets the file tools write it: a vault writer's `Write` into the vault landed with the setting on. A reader keeps both of its denies, `Edit(//<vault>/**)` and `denyWrite`, for [vault-write-boundary.md](vault-write-boundary.md)'s reasons.
  - **Codex cycles, the chat child, the reviewer and the conflict resolver.** None of them is built by `buildArgs`'s overlay. Codex has its own sandbox. The chat is given every mount as an `--add-dir`, so the setting would refuse it little. The assists' argv is `assistSettingsArgs` in `review.ts`.
  - **`EnterWorktree` and `ExitWorktree`.** The schema says the setting takes both off the tools on offer. Neither was on offer to a `-p` session with the setting off either, so a run loses nothing it had.

- **What is still open.** No work cycle spawned by the app has yet been seen refused: the probe drove the real CLI with this argv's shape, not `runIteration`. `Bash` under the setting was not observed, because nested in an agent's sandbox the probe's `Bash` calls hung. The working directories ride the first user message of every request, the temporary directory now among them (measured), so a run whose session spans this change most likely re-reads its context once at full price on its next cycle. That cost is inferred, not measured. `docs/verification/security-and-sandboxing-file-tool-writes.md` has the commands that would settle each.
