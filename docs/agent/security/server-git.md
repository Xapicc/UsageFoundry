# What this app's own git runs from a repository a work cycle wrote

[← security index](../security.md)

Read before editing `gitArgs`, `git`, `gitSync`, `addWorktree` or the filter probe that `prepareContentCall` drives in `src/lib/git.ts`, or `UNPROBED_SUBCOMMANDS`. The `core.fsmonitor` and `core.hooksPath` pins every call carries, and why git is never run through a shell, are in [path-containment-and-spawn-argv.md](path-containment-and-spawn-argv.md).

- **`gitArgs` pins the signing programs and neutralises the repository's filter drivers, for the same reason it clears `core.hooksPath`.** A work cycle writes its repository's real common `.git`, so `commit.gpgSign=true` with `gpg.program=<path>` makes `git commit` run that path, and a `filter.<x>.clean`/`smudge`/`process` paired with a `* filter=x` line in `.git/info/attributes` makes `add`, `commit`, `checkout`, `merge` and `worktree add` run it — as this server's git child, outside the permission model, with no line in `run_events`, on the next run's `worktree add` with nobody pressing anything (board task `9f3f9226`). So `gitArgs` forces `commit.gpgSign=false` and pins `gpg.program`/`gpg.x509.program`/`gpg.ssh.program` to git's own defaults on every call, exactly the signing pins `CHAT_GIT_CONFIG` carries, all on the command line where they outrank `.git/config`. `credential.helper` and `core.sshCommand` are **not** pinned here: an empty `-c credential.helper=` resets the whole helper list at top precedence and would take `githubEnv`'s scoped `credential.https://github.com` helper with it (measured for the chat, `chat-child-config-files.md`), so those belong to Deliver's own fetch/push env. git 2.39 has no flag that turns filtering off wholesale, so `git()`/`gitSync()` read the repository's `filter.*` driver names (`git config --show-origin --includes --get-regexp '^(filter|merge|hook|include|includeif)\.'`; the hook keys are the last bullet's, the include keys feed the fingerprint below) and blank each one's clean, smudge and process. Each blank goes as `--config-env=<key>=USAGEFOUNDRY_BLANK` with that variable set empty, never as `-c <key>=`: git splits a `-c` at its first `=` and a driver name may hold one, so `-c filter.a=b.clean=` set `filter.a` and the planted `filter.a=b.clean` ran (board task `a9fde194`), while `--config-env` splits at its last `=` (measured, 2.39.5). The blanks go on **every subcommand but the object-store reads on `UNPROBED_SUBCOMMANDS`** (`rev-parse`, `log`, `cat-file`, `ls-tree`, `show` and the like), the bulk of this app's git, which invoke no filter and fire no hook, because preparing one costs three git children per repository it reaches; a subcommand nobody has measured is probed rather than trusted. `status`, `update-index` and `diff` are on the list because a stat-dirty file is re-hashed through its clean filter: `conflictedFiles`' `diff --name-only` ran one mid-merge (measured). `diff` is gated whole, ranges included, because telling a range from a working-tree diff means parsing git's grammar and the probe is small beside a diff. **Merge drivers are blanked the same way, and `merge-tree` is gated with the rest:** a `merge.<x>.driver` paired with `* merge=x` runs on every three-way content merge, and Land runs two with nobody watching, the `merge-tree` preview and the real `merge` (board task `a38856ec`). The blank is an empty driver, so git runs nothing and fails the merge with `cannot run :`; `false` would read as a markerless conflict and `true` as a clean merge that dropped theirs (measured, 2.39.5). A repository relying on a merge driver has this app's merges of such a file fail, as with a required filter, and the failure says so: the blanked drivers and that this app runs none are appended to git's own `cannot run :` line, the one `parseMergeTree` (line 0) and `gitFailureLine` (first `error:`) keep (board task `adb9e828`). **The probe fails closed:** only exit 1 with an empty stdout is "no filters" and only exit 0 is a list to blank; a probe killed by its clock or a signal, never started, refused by git (any other status) or exiting 1 with output makes the real call fail with `ok: false`, `code: null` and a `stderr` that says the filter probe failed and how, before the call is spawned, because a status that went unread let a planted `filter.<x>.clean` run on exactly those endings (board task `c032f10c`). It is not retried (a probe the clock killed on a slow checkout would likely be killed again) and it takes the clock the caller gave the call, so landing's no-clock call has none on its probe. `readFilterProbe` is the one reader for `git()` and `gitSync()`. A `filter.<x>.required=true` driver then fails the operation rather than running the planted program — the right failure, since nothing of the repository's choosing runs either way; the cost is that a repository relying on a *required* filter (git-lfs) has this app's `add`/`worktree add` fail loudly rather than silently transform content. `gitDirWatch.ts` still records these keys at a run's end, but it detects and does not prevent; this is the prevention for the app's own git.
- **A conditional include is probed where the child git reads it.** `worktree add` checks out in a child inside the new tree and `worktree remove` without `--force` runs `status` inside the tree it removes; each reads config with that tree's HEAD, git directory and `config.worktree`, so a filter behind `includeIf "onbranch:…"` or `"gitdir:…/.git/worktrees/"` escaped the probe and ran (board task `d8cae532`). So `git()` refuses an add that is not `--no-checkout`, `addWorktree` checks the new tree out through `git()` inside it (locked `initializing` until then, as git's own add is), and a remove is probed in its tree as well. This app never evaluates a condition, and an in-process `checkout` reads config before HEAD moves, as the probe did (measured).
- **A submodule is probed where its own child git reads it, and none the probe has not read is recursed into.** A content subcommand starts a child git in each populated submodule (`status`, work-tree `diff`, `add -A`, a reporting `checkout`), which reads `.git/modules/<name>/` or the submodule's `.git`, so a filter planted there ran on this app's `status` (board task `a559b561`). `--ignore-submodules` is no fix: `add` has none and ignores every ignore setting, and `diff.ignoreSubmodules` loses to the repository's `submodule.<name>.ignore` (measured). So each populated gitlink a probed index lists is probed too, nested ones in turn, up to 64; the blanks reach the child in `GIT_CONFIG_PARAMETERS`. One no index lists yet is kept out by `submodule.recurse=false`, `diff.submodule=short` and `--quiet` on `checkout`/`switch` (why each: `SUBMODULE_PINS`, `QUIETED`).
- **The probe and the call still read configuration separately; a fingerprint narrows the window between them and does not close it.** git 2.39 cannot be handed what the probe read (board task `7d41bb25`). Each site's `config`, `config.worktree` and the include targets the probe names are fingerprinted (inode, ctime, size; `utimes` forges mtime), and a change before the call is spawned refuses it. Chosen over blanking every name the attributes give (every reachable `.gitattributes`, untracked ones too) and over re-probing after the call (detects only, and flags calls that write config themselves). Measured, 2.39.5, a writer renaming `.git/config` back and forth: nonstop, 1 of 600 calls ran the driver against 143; 10–50 ms apart, 54 of 3000 against 56, no gain. Open: a rewrite after the last fingerprint and before git's own read, an include target rewritten while the probe reads it, a swapped `.git` file or `commondir`, configuration outside the repository.
- **A hook defined in config is switched off by name on every call that can fire one, because `core.hooksPath=/dev/null` does not reach it and git has no switch that does.** git 2.54 added hooks named in config (`hook.<name>.command` plus `.event`), read from every scope without consulting `core.hooksPath`, which only moves the hooks directory; a pair a work cycle wrote into `.git/config` ran on this app's own `commit`, `merge`, `checkout`, `worktree add`, `branch -D`, `update-ref` and `push` (board task `6b4dccf3`). The only off switches are per name, `hook.<name>.enabled=false`, which outranks the repository from the command line, and from 2.55 per event, which a repository undoes by also defining a hook named after the event. So the probe lists `hook.*` and `neutralizers` passes `--config-env=hook.<name>.enabled=USAGEFOUNDRY_FALSE` per name, `--config-env` for the `=` reason the driver blanks have. Because `branch`, `update-ref`, `fetch` and `push` fire `reference-transaction` without moving content, the gate is `UNPROBED_SUBCOMMANDS`, reads measured to fire nothing, and not a list of what to probe. A git this one starts (a `commit`'s auto-gc, a submodule push) gets the switches in `GIT_CONFIG_PARAMETERS`; a probed `push` also carries `submodule.recurse=false`, which outranks a repository's `push.recurseSubmodules` and stops that push outright. On the image's 2.39.5 the switches are inert. Evidence: `docs/verification/security-and-sandboxing-server-git.md`.
