# What this app's own git runs from a repository a work cycle wrote

[← security index](../security.md)

Read before editing `gitArgs`, `git`, `gitSync`, `addWorktree` or the filter probe that `prepareContentCall` drives in `src/lib/git.ts`, or `UNPROBED_SUBCOMMANDS`. The `core.fsmonitor` and `core.hooksPath` pins every call carries, and why git is never run through a shell, are in [path-containment-and-spawn-argv.md](path-containment-and-spawn-argv.md).

- **`gitArgs` pins the signing programs and neutralises the repository's filter drivers, for the same reason it clears `core.hooksPath`.** A work cycle writes its repository's real common `.git`, so `commit.gpgSign=true` with `gpg.program=<path>` makes `git commit` run that path, and a `filter.<x>.clean`/`smudge`/`process` paired with a `* filter=x` line in `.git/info/attributes` makes `add`, `commit`, `checkout`, `merge` and `worktree add` run it — as this server's git child, outside the permission model, with no line in `run_events`, on the next run's `worktree add` with nobody pressing anything (board task `9f3f9226`). So `gitArgs` forces `commit.gpgSign=false` and pins `gpg.program`/`gpg.x509.program`/`gpg.ssh.program` to git's own defaults on every call, exactly the signing pins `CHAT_GIT_CONFIG` carries, all on the command line where they outrank `.git/config`. `credential.helper` and `core.sshCommand` are **not** pinned here: an empty `-c credential.helper=` resets the whole helper list at top precedence and would take `githubEnv`'s scoped `credential.https://github.com` helper with it (measured for the chat, `chat-child-config-files.md`), so those belong to Deliver's own fetch/push env. git 2.39 has no flag that turns filtering off wholesale, so `git()`/`gitSync()` read the repository's `filter.*` driver names (`git config --show-scope --show-origin --includes --get-regexp '^(filter|merge|hook|include|includeif|usagefoundry)\.'`; the hook keys are the last bullet's, the include keys feed the fingerprint below, and the `usagefoundry` key is the site marker described there) and blank each one's clean, smudge and process. Each blank goes as `--config-env=<key>=USAGEFOUNDRY_BLANK` with that variable set empty, never as `-c <key>=`: git splits a `-c` at its first `=` and a driver name may hold one, so `-c filter.a=b.clean=` set `filter.a` and the planted `filter.a=b.clean` ran (board task `a9fde194`), while `--config-env` splits at its last `=` (measured, 2.39.5). The blanks go on **every subcommand but the object-store reads on `UNPROBED_SUBCOMMANDS`** (`rev-parse`, `log`, `cat-file`, `ls-tree`, `show` and the like), the bulk of this app's git, which invoke no filter and fire no hook, because preparing one costs three git children per repository it reaches; a subcommand nobody has measured is probed rather than trusted. The subcommand is read past leading `-c` pairs and a `--git-dir=<path>`, which `readGitDir`'s `config` listing carries, so that listing asks nothing; a probed subcommand behind `--git-dir=` has the flag on each probe step in `cwd`, because probed without it the drivers of the repository `cwd` was in were blanked and the named one's ran (board task `507d7792`). Any other option ahead of a probed subcommand refuses the call before a git child runs, with a reason naming it, rather than being taught to the probe: `-C A add -A` and a two-word `--git-dir A/.git --work-tree A add -A` from `B` each ran `A`'s driver, probed in `B` (board task `c011fcd1`), and `-C` composes with `--git-dir` and relative paths in ways each step would have to replay exactly; since the subcommand is read past `-c` and `--git-dir=` only, this refuses a read behind such an option as well. `status`, `update-index` and `diff` are on the list because a stat-dirty file is re-hashed through its clean filter: `conflictedFiles`' `diff --name-only` ran one mid-merge (measured). `diff` is gated whole, ranges included, because telling a range from a working-tree diff means parsing git's grammar and the probe is small beside a diff. **Merge drivers are blanked the same way, and `merge-tree` is gated with the rest:** a `merge.<x>.driver` paired with `* merge=x` runs on every three-way content merge, and Land runs two with nobody watching, the `merge-tree` preview and the real `merge` (board task `a38856ec`). The blank is an empty driver, so git runs nothing and fails the merge with `cannot run :`; `false` would read as a markerless conflict and `true` as a clean merge that dropped theirs (measured, 2.39.5). A repository relying on a merge driver has this app's merges of such a file fail, as with a required filter, and the failure says so: the blanked drivers and that this app runs none are appended to git's own `cannot run :` line, the one `parseMergeTree` (line 0) and `gitFailureLine` (first `error:`) keep (board task `adb9e828`). **The probe fails closed:** only exit 1 with an empty stdout is "no filters" and only exit 0 is a list to blank; a probe killed by its clock or a signal, never started, refused by git (any other status) or exiting 1 with output makes the real call fail with `ok: false`, `code: null` and a `stderr` that says the filter probe failed and how, before the call is spawned, because a status that went unread let a planted `filter.<x>.clean` run on exactly those endings (board task `c032f10c`). It is not retried (a probe the clock killed on a slow checkout would likely be killed again) and it takes the clock the caller gave the call, so landing's no-clock call has none on its probe. `readFilterProbe` is the one reader for `git()` and `gitSync()`. A `filter.<x>.required=true` driver then fails the operation rather than running the planted program — the right failure, since nothing of the repository's choosing runs either way; the cost is that a repository relying on a *required* filter (git-lfs) has this app's `add`/`worktree add` fail loudly rather than silently transform content. `gitDirWatch.ts` still records these keys at a run's end, but it detects and does not prevent; this is the prevention for the app's own git.
- **A conditional include is probed where the child git reads it.** `worktree add` checks out in a child inside the new tree and `worktree remove` without `--force` runs `status` inside the tree it removes; each reads config with that tree's HEAD, git directory and `config.worktree`, so a filter behind `includeIf "onbranch:…"` or `"gitdir:…/.git/worktrees/"` escaped the probe and ran (board task `d8cae532`). So `git()` refuses an add that is not `--no-checkout`, `addWorktree` checks the new tree out through `git()` inside it (locked `initializing` until then, as git's own add is), and a remove is probed in its tree as well. This app never evaluates a condition, and an in-process `checkout` reads config before HEAD moves, as the probe did (measured).
- **A submodule is probed where its own child git reads it, and none the probe has not read is recursed into.** A content subcommand starts a child git in each populated submodule (`status`, work-tree `diff`, `add -A`, a reporting `checkout`), which reads `.git/modules/<name>/` or the submodule's `.git`, so a filter planted there ran on this app's `status` (board task `a559b561`). `--ignore-submodules` is no fix: `add` has none and ignores every ignore setting, and `diff.ignoreSubmodules` loses to the repository's `submodule.<name>.ignore` (measured). So each populated gitlink a probed index lists is probed too, nested ones in turn, up to 64; the blanks reach the child in `GIT_CONFIG_PARAMETERS`. One no index lists yet is kept out by `submodule.recurse=false`, `diff.submodule=short` and `--quiet` on `checkout`/`switch` (why each: `SUBMODULE_PINS`, `QUIETED`).
- **The probe and the call still read configuration separately; a fingerprint narrows the window between them and does not close it.** git 2.39 cannot be handed what the probe read (board task `7d41bb25`). Each site's `config`, `config.worktree`, the `commondir` in its git directory, which says where `config` and the branches are (board task `2290ab7a`; watched as absent in a main checkout), and the include targets the probe names are fingerprinted (inode, ctime, size; `utimes` forges mtime), each target where git reads it: a relative origin against the top of the work tree, which is how git prints it from a subdirectory, and `~user/` placed by git itself through the user database (board task `10264b6b`), as is `%(prefix)/`, which git expands to its own install prefix (board task `12d0e24c`); every target is joined as git joins it, by string with `..` left in, because the kernel follows a symlink before it applies the `..` after it and a target folded first was watched beside the link instead of beside its target (board task `bbbe1aff`). So is what an `includeIf` condition reads, which is not configuration (board task `9d44342d`): for `onbranch:`, HEAD, and each ref behind it only by whether it is a symbolic ref and to what, since every commit rewrites a branch's file; for `gitdir:`, every `.git` git's discovery passes on its way up from the site and the git directory it found, a directory by realpath and inode, since git's lock files move its ctime. So, below the top of the work tree only, is what would make a directory git passes on its way up a git directory, since git stops at the first one and reads its `config` (board task `fbd6d8dd`): at each level `<at>/.git` and `<at>` itself, each one's `HEAD` and `commondir` as configuration and the `objects/` and `refs/` of what the `commondir` names, or of it, by whether they are there, because an empty `.git` given a `HEAD` moves no inode the `gitdir:` watch reads, and a `HEAD` committed first needs only `objects/` made beside it. So, at every site, is what keeps the git directory it was found in one, the common directory's `objects/` and `refs/`, by realpath and inode, since every commit writes inside both and `git stash` writes `refs/stash` in `refs/` itself: with either moved away git's discovery climbed past that directory to an enclosing repository and ran a filter only that one defined (board task `9ef321d6`). **The probe shows which git directory it read**, because either moved away only while the probe ran, and back before it exited, read the same at both ends and sent the probe alone to the enclosing repository, so the site's own driver ran (board task `f3122092`): the probe carries `--config-env=includeIf.gitdir:<the git directory SITE_PATHS found, glob-escaped>.path=` a marker file, and a call whose probe lists no `usagefoundry.probed` record in the `command` scope is refused, which also refuses one where only `SITE_PATHS` saw the other repository. The scope is what is read, since a repository that includes the marker file itself lists it in its own. Chosen over pinning the probe with `--git-dir=`, which failed open (`git config` takes a named directory without `objects/` or `refs/` for no repository, reads only the global files and exits 1 with nothing, measured, 2.39.5), and over watching the two directories across the probe, which a rename back before the probe exits leaves unseen. `worktreeDiff`'s `status` runs from a non-isolated run's folder, which may be a subdirectory, so refusing calls from below the top was not the fix. A change before the call is spawned refuses it, so a call that overlaps a checkout, a rebase or a commit on a detached HEAD in its tree fails rather than runs. Chosen over blanking every name the attributes give (every reachable `.gitattributes`, untracked ones too) and over re-probing after the call (detects only, and flags calls that write config themselves). Measured, 2.39.5, a writer renaming `.git/config` back and forth: nonstop, 1 of 600 calls ran the driver against 143; 10–50 ms apart, 54 of 3000 against 56, no gain. A writer flipping HEAD under an `onbranch:` include the same way: nonstop, 0 of 600 against 131; 20 ms apart, 8 of 400 against 14. Open: a rewrite after the last fingerprint and before git's own read; an include target rewritten or a branch made a symbolic ref only while the probe reads it; a site's `objects/` or `refs/` moved away only while its index is listed, which skips its submodules (board task `8e9fe2ed`); refs in a reftable; configuration outside the repository.
- **A hook defined in config is switched off by name on every call that can fire one, because `core.hooksPath=/dev/null` does not reach it and git has no switch that does.** git 2.54 added hooks named in config (`hook.<name>.command` plus `.event`), read from every scope without consulting `core.hooksPath`, which only moves the hooks directory; a pair a work cycle wrote into `.git/config` ran on this app's own `commit`, `merge`, `checkout`, `worktree add`, `branch -D`, `update-ref` and `push` (board task `6b4dccf3`). The only off switches are per name, `hook.<name>.enabled=false`, which outranks the repository from the command line, and from 2.55 per event, which a repository undoes by also defining a hook named after the event. So the probe lists `hook.*` and `neutralizers` passes `--config-env=hook.<name>.enabled=USAGEFOUNDRY_FALSE` per name, `--config-env` for the `=` reason the driver blanks have. Because `branch`, `update-ref`, `fetch` and `push` fire `reference-transaction` without moving content, the gate is `UNPROBED_SUBCOMMANDS`, reads measured to fire nothing, and not a list of what to probe. A git this one starts (a `commit`'s auto-gc, a submodule push) gets the switches in `GIT_CONFIG_PARAMETERS`; a probed `push` also carries `submodule.recurse=false`, which outranks a repository's `push.recurseSubmodules` and stops that push outright. On the image's 2.39.5 the switches are inert. Evidence: `docs/verification/security-and-sandboxing-server-git-hooks.md` and, for the pushes, `docs/verification/security-and-sandboxing-server-git-push.md`.
- **Land's merge preview reads the blanked-driver sentence, not the exit status.** A merge driver `git()` blanked fails the merge with exit 128 on git 2.39.5 and with exit 1 and a conflict listing for the file on 2.56.0, so `parseMergeTree` (`land.ts`) returns `unknown` with the line carrying `BLANKED_MERGE_DRIVER_NOTE` (exported from `git.ts`, the sentence `explainBlankedMergeDrivers` appends) before it reads the status, and the operator sees that this app refused to run the driver rather than a file list. This replaces the "line 0" wording above: the line is found by the sentence, not by position. The real `git merge` exits 1 on 2.56.0 as well, for `merge` and `merge --squash` alike, with the file listed unmerged, so its readers ask the sentence before the files git left: `mergeRefusal` (`land.ts`) gives git's line carrying it as Land's reason whatever `conflictedFiles` returns, keeping the warnings for a checkout `unwind` could not restore, `refusedMerge` (the shape `landRun` returns) gives `conflicts: []` for it while `unwind` and `passing` still read the raw list, so the 400 body of `POST /api/runs/[id]/land` names no file either (board task `31d91115`), and `unresolvableMerge` stops a resolution's merge before a resolver is started on that file (board task `716f904b`; `docs/verification/security-and-sandboxing-server-git-drivers.md`).
- **In a reftable repository the fingerprint watches the stacks, and a ref update refuses the call it overlaps.** `$GIT_DIR/HEAD` is the stub `ref: refs/heads/.invalid` there and HEAD, with every branch an `onbranch:` condition follows from it, is in `reftable/` (a linked worktree's own HEAD in `worktrees/<id>/reftable/`), so `refsBehindHead` watched nothing a `symbolic-ref` moved and the driver ran (measured, git 2.56.0, board task `4c645539`). `reftableFiles` (`git.ts`) adds each stack's `tables.list` and the tables it names to `watched`, by `configFingerprint`'s stat, and this closes the "refs in a reftable" item left open above. The cost is the one `symrefFingerprint` avoids for loose refs: `tables.list` is rewritten by every ref update, so a call that overlaps a commit, a branch move or an auto-compaction in any worktree of the repository is refused, about one call per update when calls are back to back, and the reason says a ref update did it. Chosen over refusing every content call in a reftable repository, which has the same effect on every call and not only on those, and over reading HEAD with `git symbolic-ref HEAD`, which follows the chain as the condition does but returns the same value after a flip and a flip back, and a writer in a loop does exactly that across the probe; the stat changes on every write. A files repository reads the same `absent` at both ends, costing two failed stats and one `existsSync` a site. Measured costs and the sibling-commit rates are in `docs/verification/security-and-sandboxing-server-git-fingerprints.md`. If a reftable repository with several runs committing makes the refusals frequent, the choice to revisit is the first of those two, not the stat.
