# What a run left in its repository's git directory

[← security index](../security.md)

Read before editing `src/lib/gitDirWatch.ts`, `src/lib/gitDirRead.ts`, `src/components/RunGitDirNotice.tsx`, the `runs.git_dir_baseline` and `runs.git_dir_report` columns, the `recordGitDirBaseline` call in `startRun`, or `setStatus`'s call to `settleGitDirInBackground` in `src/lib/orchestrator.ts`.

A work cycle writes the operator's real `<repo>/.git` as the bind mount's owner, and every worktree of a repository shares it. It can plant a `core.fsmonitor`, a `core.hooksPath`, an executable in `.git/hooks`, or a driver named from `.git/info/attributes`, and the operator's own `git status` on the host then runs it as them. Board task `9d74a9ef` answered that with a paragraph in `docs/security.md` ("Your own git"); board task `3fafd392` is the warning described here. It detects; it prevents nothing — except that this app's *own* git child no longer runs a planted `gpg.program` or filter driver, because `gitArgs` pins the one and blanks the other (`path-containment-and-spawn-argv.md`, board task `9f3f9226`). The watch is still what the operator reads, since the plant remains on the host for the operator's own `git`, and still fires for every key the app's git does not neutralise.

- **A run's end says what changed in its repository's git directory, because nothing else does.** None of these files is in a branch, a diff or anything Land shows. The start reads the repository's **common** git directory (`git rev-parse --git-common-dir` of the run's checkout): `config` and every file it includes, `config.worktree`, every entry of `hooks/` not ending `.sample` with its content hash and exec bit, the same of the directory a `core.hooksPath` the repository sets names, and `info/attributes`; and all of that again for each submodule git directory under `modules/`. It reads them once per run, in `startRun` after `ensureWorktree` and before the first cycle, and only while `git_dir_baseline` is null. A resumed, picked-up or reopened run is therefore compared against the state before it first worked, and a change made before a park is still in the comparison at the end. Every terminal `setStatus` reads the directory again and stores the report. That covers the loop's own ending, a Stop or sweep ending a parked run, and the boot closing one out. The endings that bypass `setStatus` are raw UPDATEs of `waiting` rows, which never started and have no baseline. Both columns are on the `runs` row rather than in a file or in memory, because a parked run outlives restarts and its baseline must still be the pre-first-cycle one when it ends. On the row they also go when retention deletes the run, with nothing of their own to expire. Neither read is inside `createRun`, so the folder claim's no-`await` window is untouched. The run page draws the report in the inspector's state block, and the land card draws it as its own element, `RunGitDirNotice`, because landing is when the operator goes back to that checkout.

- **The check compares a list of keys that run commands, never the whole file.** This app's own git writes `.git/config` on every isolated run (`branch.<name>.*`, remotes, worktree bookkeeping, `extensions.worktreeConfig`), so a whole-file diff would warn on every run, and a warning that always fires is one nobody reads. `commandClassOf` is the list, one class per way the operator's git gets made to run a key:
  - `fsmonitor` and `hooks-path`;
  - `config-hook`: every variable of a `hook.<name>` section, which git 2.54 and later reads as a hook defined in configuration, whatever `core.hooksPath` says. Not run here, where git is 2.39.5; added from git's 2.54 release notes and `hook.c`;
  - `attribute-driver`: `filter.<x>.clean`, `smudge` and `process`, `diff.<x>.textconv` and `command`, `merge.<x>.driver`;
  - `external-diff`;
  - `remote`: the credential helpers, `core.askPass`, `core.sshCommand`, `core.gitProxy`, `core.alternateRefsCommand`, a remote's `uploadpack`, `receivepack` and `vcs`, `protocol.*allow`, an `ext::` URL or `insteadOf` base, a `!` submodule update, and `git svn`'s `svn.authorsProg`. The URL may be a remote's, a submodule's, or a branch's `remote` or `pushRemote` or `remote.pushDefault` standing in for a remote's name;
  - `signing`: `gpg.*program` and `gpg.ssh.defaultKeyCommand`;
  - `interactive`: pager, editor, `sequence.editor`, `interactive.diffFilter`, the `difftool`, `mergetool`, `browser` and `man` tools' `cmd` and `path` (for a tool git knows, the path is the command), `trailer.<x>.cmd` and `command`, `send-email`'s `toCmd`, `ccCmd`, `headerCmd`, `sendmailCmd` and an absolute `smtpServer`, `guitool.<name>.cmd`, `imap.tunnel`, `tar.<format>.command`, and `instaweb.httpd`, `gitwebDir` and `modulePath` (instaweb looks for the server in `gitwebDir`, which git-config(1) leaves out, and runs its `gitweb.cgi`; Apache loads its modules from `modulePath`). git 2.39.5 was measured running a planted `difftool.<tool>.path` on `git difftool`, `trailer.<x>.command` on any `git commit --trailer`, and `trailer.<x>.cmd` on a `--trailer` of its own key; send-email, git gui, git svn and Apache are not in the image, so their keys are reasoned from the documentation and source, not run. `diff.tool` and `merge.tool` are not watched: choosing a tool runs that tool's `cmd` or `path`, watched here, or a program the operator installed;
  - `gc`: `gc.recentObjectsHook`, which git 2.42 and later runs in a shell when gc writes a cruft pack or loosens unreachable objects; commit, merge and fetch start gc on their own. Not run here (2.39.5);
  - `alias`;
  - `include`: `include.path` and `includeIf.*.path`.

  It starts from `CHAT_GIT_CONFIG` in `chat.ts`, which is what was measured running from a planted `.git/config`, and adds what runs at the operator's terminal rather than in a chat turn. Some keys are watched only for some values (an `ext::` URL, an `ext::` `insteadOf` base, a `!` update, an absolute `sendemail.smtpServer`), so the class is decided from the full value at read time and stored on the entry. Values are compared per key, in git's order, because for a single-valued key the last one wins. `gitDirWatch.test.ts` has one failing-first case per class, plus one case of everything this app writes legitimately coming out unchanged. `info/attributes` is compared whole, because nothing this app runs writes it.

  Board task `0543690d` swept git-config(1) and the command pages at git 2.39.5 and 2.56.0 for the rest. What it found that runs is above, measured where the image allows (`docs/verification/git-and-review-command-keys.md`). Left out: `uploadpack.packObjectsHook`, which git honours only in protected configuration; a key that chooses a tool by name (`web.browser`, `help.browser`, `instaweb.browser`, `man.viewer`, `diff.guiTool`, `merge.guiTool`), for the reason `diff.tool` is not watched; and a URL naming another transport, which runs `git-remote-<transport>` from the operator's own `PATH`.

- **Reading runs nothing the repository chose, and reads nothing outside a mount.** Configuration is read with `git config --list --show-scope --show-origin -z --includes`, which was measured running no fsmonitor, hook or filter (`docs/verification/git-and-review.md`). It goes through `git()`, so `gitArgs`' cleared `core.fsmonitor` and `core.hooksPath` ride on it anyway. It runs with `--git-dir=<common>` from inside that directory. That makes the reading the main checkout's view (its `config.worktree`, not the run's linked slot's), and it needs neither checkout to exist at the end. Only the `local` and `worktree` scopes are kept: system and global are not the repository's, and `command` is this app's own `-c` pairs. `hooks/` and `info/attributes` are read as files this server opens as root. Each is opened `O_NOFOLLOW|O_NONBLOCK`, so a symlink is never opened through and a FIFO is recorded and never waited on. A file over 1 MiB is identified by size and mtime. git's own hook names (`GIT_HOOK_NAMES`) are always read, and past 256 other entries in one hooks directory the rest are counted: a `…` entry that is never compared, and a `notRead` sentence. A name only one end listed in a directory cut at that end is not reported added or removed, since past the cut nothing is known. Before this, padding `hooks/` with names sorting ahead of `pre-commit` read a rewritten `pre-commit` as "removed", or, with the padding there at the start, as "unchanged" (board task `c3d33fa6`). The common directory's real path must sit inside a configured mount, because in an in-place run the checkout's `.git` is the work cycle's to point anywhere, this app's data directory included. The end does not ask the checkout again: it re-reads the real path the start resolved, and reports the run unreadable if that path now resolves elsewhere. `gitDirRead.test.ts` plants a fsmonitor, a clean filter, a textconv, an included `diff.external`, two hooks, a FIFO and a symlink, reads twice, and asserts no marker was written. Its control is a plain `git status` that writes them. A folder with no `.git` at or above it spawns no git at all (`insideAnyRepository`), so a run in a plain folder reaches its first cycle exactly as before. `shutdown.test.ts`'s fake `spawn` is what showed that this matters: there, a `rev-parse` before the first cycle hung the loop.

- **A symlinked hook, `hooks/`, `info/` or `info/attributes` is resolved, and read by its real path only inside a mount.** git follows each of these links, so comparing the link's text alone, as this app first did, read a rewrite of the target as "unchanged": `ln -s ../.githooks .git/hooks`, a symlinked `info/`, or `.git/hooks/pre-commit -> ../../scripts/pre-commit` (board task `39aaa5b2`, measured on git 2.39.5 with `git hook run` and `git check-attr` as controls). That decision's reason was never reading as root wherever a link points, and it still holds: `place` resolves the target exactly as `readHooksPath` resolves a `core.hooksPath`, with `locate` and `insideAMount`. Inside a mount, the target is read by its real path under the same rules (a hook file's identity becomes the link's text, `THROUGH_LINK`, then the target's; a directory's entries are listed under the names git runs them by, beside its `"."` entry). Outside every mount, or through a link the container does not have, it is a `notRead` sentence naming the link, because the alternative is the same "nothing changed" about something never read that the `core.hooksPath` bullet below rejects. A target missing inside a mount is missing on the host too, so it reads as nothing there, and a symlinked hook's exec bit is still its target's, read with a `stat`. A real path that turns into a symlink mid-read is not followed again, and says so. A baseline from before this has no `unread` field and only the link's text, so the end's link is compared by its text and the report says the start did not read through it.

- **A `core.hooksPath` the repository already had is followed to the directory git runs hooks from.** Watching the key alone said nothing when the key never changes. husky v9 sets `.husky/_`, a gitignored directory in the main checkout, so a rewrite of `.husky/_/pre-commit`, or of the `h` stub every hook there sources, is in no branch and no diff, and the operator's next `git commit` runs it (board task `602e9c65`). `hooksPathOf` takes the last `local` or `worktree` value from the listing already made; `command` is this app's own `/dev/null`. A relative value is resolved as git does for the main checkout: against its work tree, which for a non-bare repository is the common directory's parent. git 2.39.5 was measured resolving it against the work tree's root whatever directory git ran from, and a linked worktree against its own root (`docs/verification/git-and-review.md`); `gitDirRead.test.ts`'s control commits from a subdirectory and has git run exactly the file compared. The directory's entries are read by the same `readHookDir` as `hooks/`, with every name under `HOOKS_PATH_PREFIX` and the directory's real path, so a repointed `core.hooksPath` reads as one directory's hooks going and another's arriving, beside the key's own finding. `hooks/` is still read as well, because a run that unsets the key makes it live again.
  - Its real path must sit inside a configured mount, for the same reason the common directory's must. A directory that does not exist yet is placed by its nearest ancestor that does. Inside a mount, nothing there is the host's state too, so it reads as empty, and a hook created there later is `added`. Outside every mount, or through a symlink the container cannot follow, a missing directory says nothing about the host's, so it is not read. The walk drops components rather than normalising the path, because the kernel resolves a `..` after a symlink from the link's target.
  - Not read, rather than guessed at: a value starting `~` or `%(prefix)/`, which git expands against the host's home or install; an empty value; and a relative value when the common directory is not named `.git` (a bare repository, or a separate git directory), because this app cannot tell what it is relative to. `/dev/null` is read as no hooks, because it is the usual way to switch them off and is no directory on either side.
  - A baseline taken before this read existed has no `hooksPathUnread` field and none of the directory's entries. The end's entries are left out of that comparison and the report says the directory was not compared at the start, instead of listing every one of them as added.

- **Each submodule's own git directory is read as the repository's is, because the superproject's `git status` runs from it.** git keeps an absorbed submodule's git directory at `<common>/modules/<name>`, inside the run's own common directory, so a work cycle can write it. A plain `git status` in the superproject recurses into the submodule and ran a `core.fsmonitor` planted in `modules/<name>/config`, measured on git 2.39.5 (`gitDirRead.test.ts`'s control); the submodule's hooks run on the operator's commits inside it (board task `eb1ab9fd`). `readModules` reads each with the same `readGitDir` as the top level: its own `git config --list`, `hooks/`, its `core.hooksPath` directory and `info/attributes`, under the same `O_NOFOLLOW` and size rules. Its findings carry `module`, the directory relative to the common one, and the page names it first, because that is where the operator has to look.
  - A directory under `modules/` is a submodule's when it holds a `HEAD`. One that does not is part of a name with a slash in it, which git stores as nested directories, and is looked inside. A submodule's own `modules/` is followed three deep. The walk uses `lstat` and follows no symlink: a symlinked `modules/` or entry there is a `notRead` sentence instead.
  - The bounds each say what they cut, never "unchanged": past 256 entries looked at under `modules/`, no submodule is compared at all, because which were missed could differ between the two ends; past 32 submodules, the rest are listed with no reading and one sentence; a submodule `git config` cannot list is one sentence. A submodule either end did not read is left out of the comparison rather than reported as removed or added. One present at only one end is compared against nothing, so what it would run reads as added or removed; a fresh `git submodule add` sets no watched key and no hook, so it reads as nothing.
  - A relative `core.hooksPath` inside a submodule is not read, and says so: the submodule's git directory is not named `.git`, so `readHooksPath` cannot tell what it is relative to.
  - A baseline from before submodules were read has no `modules` field. Its submodules are not compared, and when the end has any, the report says the start did not read them.

- **A change is attributed only as far as this app's record goes.** Worktrees share the git directory, so a change seen at run A's end may be run B's. `concurrentRuns` names every other run whose baseline names the same directory and whose time there overlaps this one's, from its baseline's `takenAt` to its `finished_at`, and a run not finished counts as still there. The window opens at the baseline rather than `started_at` because a reopen clears `started_at`, and the baseline is never retaken. The report keeps these ids beside the findings, and the page links them as "may be theirs". The record can never name the operator, the chat, or another program. The copy says so in every case, including when no other run overlapped: the run made the change unless one of those did.

- **A start or end that was not read is a warning, never "unchanged".** A failed start is stored as `{ ok: false, reason }` and compared as `unreadable`. So is a failed end, or a directory that moved. A settled run with a baseline and no report says "not compared". That covers a comparison that threw, which also writes a log line, and the one race left: `settleGitDirInBackground` is not awaited, because `setStatus`'s callers are synchronous by requirement, so a process that exits inside the few milliseconds of the read leaves no report. "Nothing changed" is drawn only on the run page, as a muted line; the land card stays as it was for a clean run. A `core.hooksPath` directory that either end did not read goes on the report as `notRead`, one sentence per end, and so does every other part of the directory a reading skipped (the snapshot's `unread`). A report carrying `notRead` is never drawn as "nothing changed": it is a warning in both places, findings or none. That fires on every run in a repository configured that way. It is kept anyway, because such a configuration is unusual and the alternative is a "nothing changed" about a directory this app never read. A reopened run keeps its last report on the page, dated by its own `checkedAt`, until its next end replaces it. `RunGitDirNotice.test.tsx` pins which states reach which placement.

- **No credential is kept or shown.** A `credential.*` value is stored as a digest only, and drawn as "not shown because one may carry a token". Every other value is cut at 200 characters. The baseline never leaves the server: `GET /api/runs/[id]` strips both raw columns and sends `gitDir`, which holds the report and when and where the start read. The runs list strips both and sends neither. Only watched keys are stored at all, so a remote URL carrying a token is never copied into the database.

- **What it does not cover.**
  - A hook written into another checkout's copy of a relative `core.hooksPath`. git resolves it against the work tree it runs in, so every linked worktree, the run's own slot included, has its own `.husky/_`, and only the main checkout's is read.
  - A `core.worktree` that moves the main work tree away from the common directory's parent. A relative `core.hooksPath` is still resolved against the parent.
  - What is in a `core.hooksPath` directory, or behind a symlink, that this app reports as not read: outside every mount, or under the host's home.
  - The run's own slot's `config.worktree` under `.git/worktrees/<slot>/`, which only git run inside that slot reads.
  - The contents of a conditionally included file whose condition is false in the container (the host's paths differ). Its `includeIf` key is watched, so adding one is reported; a later edit to an existing include's file that git did not include here is not.
  - A `.git` a run creates with `git init` in a folder that had none.
  - A submodule's linked worktrees' own `config.worktree`, and a submodule whose git directory is not under `modules/` (one never absorbed, with a `.git` directory in its own checkout).
  - Any repository other than the run's own.

  Nothing here has run on a host, or in a booted image as root with the uid split on; `docs/verification/git-and-review.md` carries both.
