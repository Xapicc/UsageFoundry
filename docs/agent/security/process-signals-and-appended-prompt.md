# Process signals, the appended system prompt and commit identity

[← security index](../security.md)

Read before editing `buildArgs`'s `--disallowedTools` or `--append-system-prompt`, or any notice in `src/lib/cycleInvocation.ts` that rides on it (`SELF_HOSTING_NOTICE`, `COMMIT_IDENTITY_NOTICE` and the rest).

- **An agent cannot select processes by name to signal them.** `buildArgs` passes `--disallowedTools Bash(pkill:*) Bash(killall:*)` on every spawn — a deny rejects the whole Bash call, so a `pkill` buried in a `;`-chain takes the chain with it, which is the form the incident arrived in — and `--append-system-prompt` carries the reason *and the safe recipe*. The deny alone buys one turn, since `kill $(pgrep -f next-server)` is not `pkill` and is exactly as fatal; a bare prohibition buys the opposite failure, a dev server nobody can stop holding its port for the life of the container. So the notice spells out pid capture, the `pgrep -P` child form, and selecting on the port rather than the title. Next renames this server's process to `next-server (v…)`, which is *also* the title of any dev server an agent starts to check its work, so a name match cannot tell the two apart and reaches whichever was there first. One `pkill -f "next-server|next dev"` ended the container (`restart: unless-stopped` brought it back) and `reconcileOnBoot` marked fourteen runs failed 690ms later, including the run that issued it. There is no ownership boundary to enforce this with instead: compose runs a single uid. Plain `kill` stays permitted — a pid is a handle on a process the agent started, a pattern is a guess about the machine — and denial survives `bypassPermissions`, which is the only reason the argv is worth anything here. The **allow** list beside it now also appears on every spawn, and it is deliberately not a member of the guard set: `SEARCH_TOOLS` is `Grep` and `Glob`, two tools that read, named because the pinned CLI drops both from the tool list whenever `Bash` is present unless something names one. It grants no command, it moves no permission mode, and the test beside `buildArgs` asserts that a run in the operator's own checkout still gets no `Bash(...)` entry through it.

- **…and the notice must contain no literal an agent could match on, because the notice is itself on every sibling's command line.** `--append-system-prompt` puts `SELF_HOSTING_NOTICE` in the argv of every concurrently running `claude`, so any literal string in it is a pattern that selects the whole fleet. The worked example used to be `kill $(pgrep -f 3100)`, which made the one command this notice recommends by name match every agent on the box. Measured twice. At 2026-08-15 23:39:42 run `b81e7c70` escalated from a narrow `pgrep -f "next dev -p 3100"` through an explicit pid to a bare `pgrep -f 3100`, and `9b98ddec` — a Go run in a different repository, with no port-3100 process and no tool call of its own naming the number — died in the same second with "exited with code 143", taking five dependents into `blocked` behind it; it happened again on 2026-08-16 at 14:23:38, `02c3e132` ending `8d6b1ffc`. No work was lost, because all four resumed the same session, but three runs were truncated at their cycle cap and every dependent needed picking up by hand. The port is a shell variable now and the *mechanism* is stated rather than the conclusion — an agent told only "no bare numbers" reaches for a different literal, where one told why a literal is dangerous checks first — and `pgrep -af` is named because looking before killing is the habit that generalises to the next pattern nobody anticipated. `orchestrator.test.ts` asserts the notice carries no multi-digit run, beside the `PROCESS_KILLERS` assertion it belongs with, and asserts it against a spawn that carries a **rendered price list** — with the strict form scoped to whatever the flag holds *without* one, derived rather than listed, so a sixth notice inherits it without anybody naming it there. That scoping is the whole of it: asserted against a fixture with no price list on the flag, as it was, the strict form read as a claim about every notice while never once seeing the only one that carries digits at all. The flag now carries **five** notices under one value — `SELF_HOSTING_NOTICE`, `DELEGATION_NOTICE`, `RENDERING_NOTICE`, `COMMIT_IDENTITY_NOTICE` and the run's own frozen file price list — because a second `--append-system-prompt` is a replacement rather than an addition; anything added to any of them inherits this bullet's rule, since all five are equally on every sibling's command line. The price list is the case that makes the rule worth restating rather than merely surviving it: it is a list of **repo-relative paths**, which is exactly the kind of shared literal that made `pgrep -f 3100` fatal, since every run on that repository carries the same ones. What keeps it safe is not that the strings are different but that nothing near them offers a pattern — they sit in a price list, no verb beside them is `kill`, and it names no command at all. `fileCostNotice.test.ts`'s "offers no literal as a thing to run" pins that, and the argv test pins it a second time over the price-list half of the flag it splits — the duplication is deliberate, because the strict assertion's failure message is read *there*, and a rule that lives only in another file is one an editor at this one never meets. `SELF_HOSTING_NOTICE`'s own sentence about literals is scoped to the whole appended prompt, so it already covers this half. The notice still names no tool the image lacks: the Dockerfile installs `procps` and neither `psmisc` nor `iproute2`, so `fuser` and `ss` are absent, and warning about — or recommending — an absent command is how an agent learns to look for it.

- **An agent must not sign a commit with the address it was given to recognise the operator by.** The CLI puts the signed-in account's email in every child's own system prompt, worded as "use it only to identify the user, such as for authorship, attribution" — so the one credential-shaped string this app never handed a child is the one the child arrives holding, and an agent this app has just told to commit reads that wording as permission. Two commits on this repository's own `main` were authored `UsageFoundry Agent <the operator's address>` by an isolated run that reached for `git -c user.name=… -c user.email=… commit` unprompted; GitHub maps a commit to an account by author email, so both were attributed to the operator's other GitHub identity and it took a place in the public contributor list. Nothing failed on the way: `/etc/gitconfig` sets `agent@usagefoundry.local` and still does, the commits landed, the run completed, and the attribution was found by someone reading a panel weeks later — which is why the answer is a notice rather than a check, there being nothing here that inspects an author line. `ISOLATED_GIT_TOOLS` cannot be that answer twice over: its entries are prefix-matched, so `git -c …` sits outside them by construction, and the run that did this was on `bypassPermissions`, where an allowlist decides nothing. `COMMIT_IDENTITY_NOTICE` therefore rides `--append-system-prompt`, which is the only thing that reaches every run whatever its mode and whether or not it is isolated — the unisolated case being the one whose commits land in the operator's own checkout with no branch in front of them. It names all four spellings (`-c`, `git config`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL`) because an agent told only that one is forbidden reaches for the next, and it satisfies the bullet above the way the price list does: git configuration keys, no verb but "commit" beside them, nothing selecting a process, and no digits at all.

- **Nothing on a run's appended system prompt may carry a literal an agent could `pgrep -f`**, and the taskboard notice is the case that most looks like a violation and is not. It names three tool names shared across every board-enabled run on the box — exactly the kind of shared literal that made a port number fatal — and what keeps it safe is that nothing near them offers a pattern: no verb selects a process, no command is named, and the notice carries no digits at all. The names are spelled out rather than alluded to because a model told "there is a board" without them writes prose about filing a task instead of filing one. The rule for anything added beside it is unchanged: the test is not whether a string is unique, it is whether the text around it teaches an agent to match on it. A worker-count advisory — one line telling the agent how many CPUs the container exposes, so it caps its own test runner — was proposed and **refused** on 2026-09-16 for two independent reasons. A worker count is a number, and `orchestrator.test.ts` asserts this half of the prompt carries no multi-digit run at all; and the standing half is frozen at run creation inside the cached prefix, so it could not carry a figure that depends on what else is running anyway. The lever that does the same job without putting a digit on every sibling's command line is a compose `environment:` entry the tool itself reads, which is what `VITEST_MAX_WORKERS` already is; `docker-compose.yml`'s `cpus` comment records what that was measured to reach and what it does not.
