# What a work cycle loads from directories that are not its own

[← security index](../security.md)

Read before editing the `workDir` or `isolated` option in `buildArgs` (`src/lib/cycleInvocation.ts`), its `--project-config-root`, the `workDir` and `isolated` arguments at the run loop's `buildArgs` call in `src/lib/orchestrator.ts`, `ensureWorktree`, `assistConfigRootArgs` and its call in `spawnAssist` (`src/lib/review.ts`), the `cwd` any caller of `startAssist` passes, or anything else that starts Claude Code in a linked worktree. What a cycle loads from inside the vault is [vault-write-boundary.md](vault-write-boundary.md)'s, and what an `--add-dir` loads is [file-tool-write-boundary.md](file-tool-write-boundary.md)'s.

- **An isolated run reads its project config from its own worktree, through `--project-config-root <workDir>`, because without the flag the CLI reads part of it from the main checkout.** Decided 2026-11-09 under board task `687b0d2f`. On 2.1.319 against a stub API, a run in a linked worktree with nothing committed under `.claude/` was offered the main checkout's untracked skill, agent and command. A worktree that had committed its own `.claude/skills/` was not offered the main checkout's skill, but was still offered its agent and its command. The CLI falls back to the main checkout one directory name at a time, wherever the worktree has none of its own. The main checkout's untracked `.claude/settings.local.json` applied as well. Its `language` reached the request, it outranked the worktree's own `settings.local.json`, and its `SessionStart` hook ran and its output reached the request. An absent or empty main-checkout file left the worktree's own in force. The main checkout's untracked `settings.json`, `CLAUDE.md` and `CLAUDE.local.md` reached no run, and neither did anything in `.uf-worktrees/` or the mount above it. With the flag, nothing from the main checkout reached the run, under `$TMPDIR` and on this container's virtiofs mount alike. The worktree's committed skills, agents and commands still loaded, and so did its committed `settings.json`, whose `language` applied and whose hook ran, and its own `settings.local.json`. This matters because anything that writes the main checkout's working tree reached every later isolated run of that repository, with nothing committed, reviewed or landed. A non-isolated run on the main checkout created `.claude/skills/x/SKILL.md`, `.claude/agents/x.md`, `.claude/commands/x.md` and `CLAUDE.md` there with `Write` under `bypassPermissions`. Under `acceptEdits` its three `.claude/` writes were refused as ungranted. A hook runs outside bwrap. The main checkout's `permissions` widened the run as well: under `acceptEdits`, an `allow` for `Read` of a directory outside the working directories let the worktree run read it, which the control without the rule and the run with the flag were refused as ungranted. `scripts/sandbox-probe/write-boundary-probe.mjs` checks the flag in every worktree turn, turn 10c is its control, and `docs/verification/security-and-sandboxing-project-config-discovery.md` has the rest.

- **The flag changed nothing else that was measured, and it costs the operator's uncommitted config in the main checkout.** The tool list was the same. The auto-memory key was still the main checkout's project key, and the transcript directory was still the worktree's. A session started without the flag resumed with it and kept its messages, and so did one started with it. The first request differed only in the sandbox section's deny list: the main checkout's `settings.local.json` and `.cc-writes` left it, and the worktree's `settings.local.json` joined it. A run that spans the change therefore pays one cold prefix. The CLI's own text says a session with the flag refuses `--routine` and cannot make durable scheduled tasks or project-scope MCP changes. None of those is on a work cycle's argv, and none was exercised. A skill nested in a subdirectory's `.claude/skills/` was not discovered on a `Read` or `Write` there, with the flag or without it, so no loss was seen and none is ruled out. The cost by design is what the CLI's fallback is for: the operator's own uncommitted settings, permissions, hooks and skills in the main checkout no longer reach isolated runs. The place for them is the repository's committed `.claude/` or the user scope. TokenEconomizer seeds the slot's own `settings.local.json` (`seedTokenEconomizerSlot`), and with the flag that file is the one in force. Without it, a main checkout with a non-empty `settings.local.json` outranked the seed. Only isolated runs get the flag. A run on the main checkout has no main checkout to fall back to. For a plain folder the flag changed nothing (below). No `workDir` means no flag, because the CLI refuses a relative or missing path at the spawn. The "reads an isolated run's project config from its own worktree" case in `orchestrator.test.ts` pins it, on a resumed cycle too, since `--resume` restores no flag.

- **A run on a plain folder is still offered its ancestors' `.claude/`, and that is accepted.** On the same pin, a run whose cwd is in no git repository was offered the skills, agents and commands in its parent's `.claude/` and in the mount's, and the mount's `CLAUDE.md`. The walk stops at a git root, and by the binary's reading at `$HOME`, which was not measured. A worktree run was offered nothing from `.uf-worktrees/` or the mount, and neither was a run in a checkout's root (board task `687b0d2f`'s measurement). `--project-config-root` did not stop it, because the CLI walks up from the root it is given. Nothing else found in the binary or the settings schema stops it and keeps the run's own skills. `--setting-sources` without `project`, and `--bare`, drop those too. `strictPluginOnlyCustomization` is managed-only and blocks every project skill. `skillOverrides` needs the names in advance. It is accepted because of what can write an ancestor's `.claude/`: the operator, a run whose folder is that ancestor, and, on an install with no managed sandbox, any run's `Bash`. A sandboxed cycle's file tools refuse writes outside its working directories ([file-tool-write-boundary.md](file-tool-write-boundary.md)), and its `Bash` write set holds no ancestor of its folder. An operator who wants the walk stopped makes the folder a git repository, or keeps nothing under the mount root's `.claude/`.

- **A reviewer, resolver or validator in a linked worktree reads its project config from that worktree's top level, through `--project-config-root`, because without it the main checkout's untracked config reached the assists that judge a run.** Decided 2026-11-09 under board task `097ca029`. On 2.1.319 against a stub API, through `startAssist`, a validator and a resolver in a run's worktree with nothing committed under `.claude/` were shown the main checkout's untracked skill, agent and command and its `settings.local.json` `language`. That file's `permissions.allow` for `Read` of a directory outside the checkout let the resolver, under `acceptEdits`, read a file there, which it was refused as ungranted with nothing planted. Their hooks and `apiKeyHelper` were already off ([cycle-settings-env.md](cycle-settings-env.md)). With the flag none of the four reached either, and the worktree's own committed skills, agents and commands, its `settings.json` `language` and its `permissions.deny` still applied. It matters more here than for a cycle: a validator closes a task on its word, a reviewer's verdict marks tasks, and the main checkout's untracked files are in no diff either of them is shown. The root is the nearest directory at or above the assist's `cwd` whose `.git` is a file, not the `cwd` itself. Pointed at a subdirectory, the flag left the checkout root's settings files unapplied, so a worktree's committed `settings.json` stopped applying. Where `.git` is a directory or absent there is no flag, so an assist in the operator's own checkout, a subdirectory of one, or a plain folder keeps its argv, and it was shown what it was shown before. The cost is the cycle's: the operator's uncommitted config in the main checkout no longer reaches an assist in a worktree. Unlike the cycle's flag this one is read off the filesystem rather than off `run.isolation`, so it covers the resolver's throwaway checkout too. It also covers a run with isolation off whose folder the operator made a linked worktree, whose own cycles carry no flag: there the assist sees less of the main checkout than the run did, which is the safer side for a judge. The two "assistConfigRootArgs" cases in `review.test.ts` pin it over a real `git worktree add`.

- **What it does not cover.** Board task `097ca029`'s question has a measured answer: the main checkout's skill, agent, command and `settings.local.json` reached a validator and a resolver in a run's worktree, and with the flag above they no longer do. The reviewer was not run, though it shares their spawn and so their flag. A validator under `plan` read files outside its checkout with no grant in every case, the control with nothing planted included, while the resolver was refused them. That reach is not this flag's, and [assist-read-boundary.md](assist-read-boundary.md) records how it was closed. A Codex cycle reads none of these files. No cycle or assist spawned by a running server has yet been seen carrying the flag; the assists were measured through `startAssist` in a scratch process.
