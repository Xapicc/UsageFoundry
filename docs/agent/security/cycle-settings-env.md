# Where a work cycle's settings may send its credential

[← security index](../security.md)

Read before editing `PINNED_CYCLE_ENV`, `cycleEnvPins` or the `--settings` overlay in `buildArgs` (`src/lib/cycleInvocation.ts`), `cycleEnv` or the `envPins` argument at the run loop's `buildArgs` call in `src/lib/orchestrator.ts`, `assistSettingsArgs` or the `env` `spawnAssist` builds in `src/lib/review.ts`, `chatSettingsArgs` or the `env` `launchOrchestratorChild` builds in `src/lib/chat.ts`, `authArgv` or the spawn sites of `src/lib/claudeAuth.ts`, or before adding `--setting-sources` to a work cycle. Every measurement here is in `docs/verification/security-and-sandboxing-telemetry-token.md`, taken on 2.1.310 on 2026-10-25 under board task `a0c412bf` and, for the assist and the chat, on 2026-10-26 under `dcd92557`, and the assist's hooks under `9ec70b90`, and its `apiKeyHelper` on 2026-11-08 under `d704ceae`, the work cycle's and the chat's the same day under `9d7770b6` and `59fd8643`; the `claude auth` children's are in `security-and-sandboxing-sign-in-and-bearer.md`, 2026-11-08 under `27323691`.

- **A work cycle loads its checkout's settings, and their `env` decides where its API requests go.** `runIteration` passes no `--setting-sources`, so the CLI applies the `env` of the cwd's `.claude/settings.json`, its `settings.local.json` and `$CLAUDE_CONFIG_DIR/settings.json` over the environment this app spawned it with. The checkout is repository content: a clone can ship the file, and with `UF_SANDBOX` off an agent's `Bash` writes it for the next cycle. Measured, the file moved the credential to a host it named in five ways, all listed on `PINNED_CYCLE_ENV`. The host it names also answers with the usage the CLI then reports, so the same file fills `installSpend` and every meter that reads the cycle's telemetry. No ingest token or process binding can tell that figure from a true one.

- **The cycle's own `--settings` outranks every one of those files, so the endpoint variables are pinned there and project settings stay loaded.** `cycleEnvPins` reads each variable off `cycleEnv({}, local)`, which is the same function `runIteration` spawns with. A local cycle's pin is therefore its own server, and a stack's exported proxy is pinned like the server's. A variable the environment does not set is pinned to `""`, because leaving it out would let the project's value stand. `""` was measured to read as unset to the CLI and to the node, python, curl and git a `Bash` call starts. With no `ANTHROPIC_BASE_URL` configured, the pin is `""` and requests go to `api.anthropic.com`. Pinning was chosen over `--setting-sources user` because that flag also drops a repository's permissions, hooks and agents and changes agent discovery (`agents.ts`, `../agents-and-templates/agent-references-and-ambient-agents.md`), which is the operator's decision rather than this fix's. The pins share one `--settings` with the sandbox write set, because the CLI keeps only the last one it is given. That means every Claude cycle's argv now carries `--settings`, a stock install's included. `cycleEnvPins`' cases in `orchestrator.test.ts` pin this. **The reviewer, resolver and validator carry the same pins** (`assistSettingsArgs`, from `spawnAssist`), because they run in a run's checkout or a merge of one with no `--setting-sources`. Before, their only `--settings` was the sandbox overlay, withheld on a stock install, and a checkout's file sent the reviewer's key to the host it named and recorded the spend that host reported (measured). The flag is now on every assist's argv. The pins are read off the one `reviewEnv()` the spawn is handed, never a second call, because `agentEnvironment`'s cached stack exports can refresh between two. The chat's pins are `chat-child-config-files.md`'s.

- **The pins also outrank the operator's own user-scope `env`, and a variable the server does not set is pinned to `""`, so a gateway, proxy or provider switch kept only in `~/.claude/settings.json` is lost.** Decided under board task `554c08b9`, option (1): keep the pins as they are. `--settings` outranks every scope, so `$CLAUDE_CONFIG_DIR/settings.json` (the mounted `~/.claude/settings.json`) is overridden for all 19 keys of `PINNED_CYCLE_ENV`, not only the project files named above, in every work cycle, reviewer, resolver and validator, and in the chat, whose `--setting-sources user` keeps that scope for everything the pins do not name. With `env.HTTPS_PROXY`, `env.ANTHROPIC_BASE_URL` or `env.CLAUDE_CODE_USE_BEDROCK` set there and not in the server's environment, the pin is `""`, which reads as unset: requests go direct to `api.anthropic.com`, or fail where direct egress is closed, and the spend lands there rather than at the gateway. Measured by the 2026-10-26 hunt on 2.1.310 with a loopback proxy: a user-scope `HTTPS_PROXY` took 7 proxy hits from a bare `-p` call and 0 once `--settings` pinned it to `""`. **Set such a variable where the server reads it, `.env` or `docker-compose.yml`'s `environment:`.** Every pinned child inherits it from there and is pinned *to* it, so it applies uniformly and no file a cycle can write can change it. The operator-facing pointer is in `README.md`, under "The configuration is checked before the server serves". The `--setting-sources ""` children go further and read no user-scope key at all: the vault pointer's gate and `auth login` and `auth logout` (above). Not built, on purpose: reading the user file's `env` back into the pins (option (2)). That file is the one a work cycle can write unless `UF_LOCK_CLAUDE_HOME` is on, so honouring it would give the pins to whatever a cycle planted there, which is the hole the `auth` children's flag closes; and doing it only under the lock was not measured. A proxy URL with a password in it now also sits on the argv of a cycle, readable through `/proc/<pid>/cmdline`. Inside the container it was already in the environment every agent can print; on a host `npm run dev` install, where a process's environment is readable by its own user and its argv by every user, that is a widening (inferred from how `/proc` works, not measured).

- **No credential is pinned, and none may be.** The overlay is on the argv, and `/proc/<pid>/cmdline` is readable by every process in the container. A project `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` replaces or adds the project's own key, sent to the pinned host. That takes nothing of the operator's. The values that are pinned (URLs, proxy URLs, TLS switches) are already in every cycle's environment, where `env` prints them.

- **An assist runs no hooks, because its checkout's hooks speak to its model.** Measured on 2.1.310 through `startAssist` (board task `9ec70b90`): a `UserPromptSubmit` and a `SessionStart` hook in the checkout's `settings.local.json`, which is never in the diff, and a `SessionStart` in its `settings.json` all ran in a validator, and all three texts reached its request. A run could write its own validator's brief. `assistSettingsArgs` therefore puts `disableAllHooks: true` in the assist's one `--settings`, which stopped all three, a project file's `"disableAllHooks": false` included. It was chosen over `--setting-sources user` for the reason the pins were: that flag also drops the repository's permissions and agents. The cost is the chat's: the operator's own user-scope and plugin hooks no longer run in a reviewer, resolver or validator either. A work cycle still runs its checkout's hooks, since there the run acts only on itself.

- **The `claude auth` children lead their argv with a settings flag, because a planted `$CLAUDE_CONFIG_DIR/settings.json` steers the sign-in itself.** That file is writable by every work cycle unless `UF_LOCK_CLAUDE_HOME` is on, and an `env.HTTPS_PROXY` in it took `auth login`'s token exchange (the authorization code and PKCE verifier go to `platform.claude.com`), `auth logout`'s three connections and `auth status`'s one. Both `--settings` and `--setting-sources` beat it for all three subcommands, and only when they come **before** `auth`: behind the subcommand the CLI exits 1 with `unknown option`. `authArgv` (`claudeAuth.ts`) is the one place the argv is built. Login and logout get `--setting-sources ""`, which closes them by construction. Pins would have left a planted `CLAUDE_CODE_CUSTOM_OAUTH_URL` free to break the sign-in (the CLI refuses it as not an approved endpoint, before it prints a link), and `PINNED_CYCLE_ENV` names no OAuth variable. Status gets the pins instead, from the `authEnv()` it is spawned with, because it answers for the credential a work cycle gets and a cycle loads the user scope: with a user-scope `ANTHROPIC_API_KEY`, `--setting-sources ""` reported the claude.ai login and `--settings` reported `api_key`. `claudeAuth.test.ts` reads the argv each child is started with. Both choices cost an operator a proxy or gateway configured only in the user settings file, as the cycle's pins do.

- **An assist runs no `apiKeyHelper` either, because hooks off did not stop a checkout's.** Measured on 2.1.310 through `startAssist` (board task `d704ceae`): with `disableAllHooks` set, a helper in the checkout's `settings.local.json` still ran in the validator's environment, which holds the reviewer's credential. Beside an API key, its key went on the request too. On an OAuth login, from the environment or a stored `.credentials.json`, it replaced the operator's credential outright. `assistSettingsArgs` therefore puts `apiKeyHelper: ""` in the one `--settings`. That stopped a helper in either checkout file and in the user file, and left the environment's key, OAuth token or stored login as the only credential sent. `null` did not stop it, and a command such as `true` sent an empty `Bearer` beside the key, so the value is the empty string and nothing else. Chosen over `--setting-sources user` for the hooks' reason. The cost is an operator's own user-scope helper, which no longer runs in a reviewer, resolver or validator.

- **A work cycle runs no `apiKeyHelper` either, and neither does the chat.** Measured on 2.1.310 through `runIteration` (board task `9d7770b6`), with the argv the run loop builds, pins included: a helper in the checkout's `settings.local.json` or `settings.json`, or in the user file, ran in a cycle. Beside an API key its key went on the request too. On an OAuth login, the environment's token or a stored `.credentials.json`, it was sent in both headers and the operator's in neither. A clone can ship `.claude/settings.json`, and with `UF_SANDBOX` off an agent's `Bash` writes the other two. `buildArgs` therefore puts `apiKeyHelper: ""` in the cycle's one `--settings`, which stopped all three files in every credential mode. It is emitted whether or not `envPins` is passed, so a caller that omits them is not the one that leaves it open. The chat's `--settings` carries it too (board task `59fd8643`, `chat-child-config-files.md`), where `--setting-sources user` keeps the user file. Chosen over `--setting-sources user` for the pins' reason. **The cost** is an operator's own helper, which no longer runs in a work cycle, an assist or a chat turn. No supported install authenticates through one: the README names the Settings sign-in and `ANTHROPIC_API_KEY`, and `docs/agent/environment/` names no helper. So it falls on an install that put one in `~/.claude/settings.json` by hand, whose children then use the sign-in or the key. `cycleEnvPins`' cases in `orchestrator.test.ts` pin it, and failed on the code before. Three assertions there encoded the old overlay, no `--settings` at all or the pins alone, and were rewritten to say what it carries now. **`claude auth status` carries it too** (board task `ed6a7179`), in the one `--settings` beside its pins: without it a user-file helper was reported as the login, `api_key_helper`, over an API key, an OAuth token or a stored sign-in, and with no credential at all; a credential cycles no longer use.

- **What is still open.** An install whose server environment turns a third-party provider on keeps that provider's own endpoint variables (`ANTHROPIC_VERTEX_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `AWS_ENDPOINT_URL*` and the like) open to a project file. Only the switches are pinned, since `""` for those other keys was not measured and could break such an install. The same holds for an assist's project file and for the chat's user file. Nothing above ran in a booted container as root. The status read carries the pins and an empty `apiKeyHelper`, so of the gaps above it inherits only the provider endpoint keys, and the 2026-10-26 hunt saw it exit before sending a credential. Nothing about the `auth` children ran with a real sign-in, in a booted container as root, or with `UF_LOCK_CLAUDE_HOME` off end to end; the command that would settle it is the last item in `security-and-sandboxing-sign-in-and-bearer.md`'s "Not yet verified by hand". The Codex children read `$CODEX_HOME/config.toml`, which a cycle can create, and only `codexAccount.ts`'s `app-server` was measured to follow one: a planted `chatgpt_base_url`, `openai_base_url`, `model_provider` or `[otel]` exporter took its ChatGPT bearer or its telemetry, so it starts with `-c` pins on those keys, `--ignore-user-config` being refused by every subcommand this app runs; any other key in that file is still open to it, and the `codexAuth.ts` children carry no pin because none of those keys moved a connection of theirs (`security-and-sandboxing-sign-in-and-bearer.md`, 2026-11-08).
