# Where a work cycle's settings may send its credential

[← security index](../security.md)

Read before editing `PINNED_CYCLE_ENV`, `cycleEnvPins` or the `--settings` overlay in `buildArgs` (`src/lib/cycleInvocation.ts`), `cycleEnv` or the `envPins` argument at the run loop's `buildArgs` call in `src/lib/orchestrator.ts`, `assistSettingsArgs` or the `env` `spawnAssist` builds in `src/lib/review.ts`, `chatSettingsArgs` or the `env` `launchOrchestratorChild` builds in `src/lib/chat.ts`, or before adding `--setting-sources` to a work cycle. Every measurement here is in `docs/verification/security-and-sandboxing-telemetry-token.md`, taken on 2.1.310 on 2026-10-25 under board task `a0c412bf` and, for the assist and the chat, on 2026-10-26 under `dcd92557`, and the assist's hooks under `9ec70b90`.

- **A work cycle loads its checkout's settings, and their `env` decides where its API requests go.** `runIteration` passes no `--setting-sources`, so the CLI applies the `env` of the cwd's `.claude/settings.json`, its `settings.local.json` and `$CLAUDE_CONFIG_DIR/settings.json` over the environment this app spawned it with. The checkout is repository content: a clone can ship the file, and with `UF_SANDBOX` off an agent's `Bash` writes it for the next cycle. Measured, the file moved the credential to a host it named in five ways, all listed on `PINNED_CYCLE_ENV`. The host it names also answers with the usage the CLI then reports, so the same file fills `installSpend` and every meter that reads the cycle's telemetry. No ingest token or process binding can tell that figure from a true one.

- **The cycle's own `--settings` outranks every one of those files, so the endpoint variables are pinned there and project settings stay loaded.** `cycleEnvPins` reads each variable off `cycleEnv({}, local)`, which is the same function `runIteration` spawns with. A local cycle's pin is therefore its own server, and a stack's exported proxy is pinned like the server's. A variable the environment does not set is pinned to `""`, because leaving it out would let the project's value stand. `""` was measured to read as unset to the CLI and to the node, python, curl and git a `Bash` call starts. With no `ANTHROPIC_BASE_URL` configured, the pin is `""` and requests go to `api.anthropic.com`. Pinning was chosen over `--setting-sources user` because that flag also drops a repository's permissions, hooks and agents and changes agent discovery (`agents.ts`, `../agents-and-templates/agent-references-and-ambient-agents.md`), which is the operator's decision rather than this fix's. The pins share one `--settings` with the sandbox write set, because the CLI keeps only the last one it is given. That means every Claude cycle's argv now carries `--settings`, a stock install's included. `cycleEnvPins`' cases in `orchestrator.test.ts` pin this. **The reviewer, resolver and validator carry the same pins** (`assistSettingsArgs`, from `spawnAssist`), because they run in a run's checkout or a merge of one with no `--setting-sources`. Before, their only `--settings` was the sandbox overlay, withheld on a stock install, and a checkout's file sent the reviewer's key to the host it named and recorded the spend that host reported (measured). The flag is now on every assist's argv. The pins are read off the one `reviewEnv()` the spawn is handed, never a second call, because `agentEnvironment`'s cached stack exports can refresh between two. The chat's pins are `chat-child-config-files.md`'s.

- **No credential is pinned, and none may be.** The overlay is on the argv, and `/proc/<pid>/cmdline` is readable by every process in the container. A project `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` replaces or adds the project's own key, sent to the pinned host. That takes nothing of the operator's. The values that are pinned (URLs, proxy URLs, TLS switches) are already in every cycle's environment, where `env` prints them.

- **An assist runs no hooks, because its checkout's hooks speak to its model.** Measured on 2.1.310 through `startAssist` (board task `9ec70b90`): a `UserPromptSubmit` and a `SessionStart` hook in the checkout's `settings.local.json`, which is never in the diff, and a `SessionStart` in its `settings.json` all ran in a validator, and all three texts reached its request. A run could write its own validator's brief. `assistSettingsArgs` therefore puts `disableAllHooks: true` in the assist's one `--settings`, which stopped all three, a project file's `"disableAllHooks": false` included. It was chosen over `--setting-sources user` for the reason the pins were: that flag also drops the repository's permissions and agents. The cost is the chat's: the operator's own user-scope and plugin hooks no longer run in a reviewer, resolver or validator either. A work cycle still runs its checkout's hooks, since there the run acts only on itself.

- **What is still open.** An install whose server environment turns a third-party provider on keeps that provider's own endpoint variables (`ANTHROPIC_VERTEX_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `AWS_ENDPOINT_URL*` and the like) open to a project file. Only the switches are pinned, since `""` for those other keys was not measured and could break such an install. The same holds for an assist's project file and for the chat's user file. A project file's `apiKeyHelper` still runs in a cycle and in an assist, `disableAllHooks` notwithstanding. Measured in a validator, it ran in the validator's environment and the key it printed went to the pinned host in `authorization`, beside the environment's `x-api-key`. Closing it in an assist would take `--setting-sources` without `project,local`, or an `apiKeyHelper` pinned in the `--settings`, and whether `""` there turns a project helper off was not measured. Nothing above ran in a booted container as root with winnow on.
