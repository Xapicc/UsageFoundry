# The audit trail

[← security index](../security.md)

Read before editing `src/lib/requestLog.ts`, `recordDurableMutation`, or any route that takes, replaces or destroys a credential — `/api/claude-auth/*`, `/api/codex-auth/*`, `/api/local-provider` — or the `readAuthStatus` pair in `src/lib/claudeAuth.ts` and `src/lib/codexAuth.ts`.

- **The audit trail is two tables, and which one a line belongs in is decided by what evicts it.** `request_log` is the trail of *requests* — method, `pathname`, status, subject, credential class, source address, duration — written by `auditMutation` at the export of every mutating route behind the gate, and it is a 20,000-row window trimmed on every insert. That is right for what it holds and wrong for a credential: the line saying the OAuth credential every billed child runs against was replaced is the one that has to survive twenty thousand ordinary presses, and it is the first thing an ordinary week deletes. So a mutation that *changed* something also writes `recordDurableMutation` into `ops_events`, which is written at boot frequency and at operator-press frequency and which ordinary traffic therefore cannot evict. **Both, not either**, and each half covers what the other cannot: the wrapper records the refusals, which is the line an audit most wants and which the durable half never sees, because the durable half fires only behind a success. Every credential route follows one rule — the row is written when the credential changed, never when the press was made, so a refused code, a cancel over no pending login and a CLI that would not run leave the request line alone. Codex's device start is the one place it reads *may have changed*: the pinned CLI deletes `auth.json` before it asks OpenAI for a code (measured), so a start cancelled while it waits for its link, or failing after its CLI ran, writes a `warn` row carrying `may_have_cleared_credential` — one per press, none when nothing was spawned. **Who** is the credential class and the source address and nothing else: this install has one credential and no user model, so any name in a row here would be invented rather than recorded, and `detail` is named field by field for the reason `request_log` takes no body — a body posted to `/api/codex-auth/api-key` is an API key, and `recordOpsEvent` writes to SQLite *and* stdout in the same call. The one thing not to undo: `ops_events` keeps **500** rows against `request_log`'s 20,000, so a durable row written on an exempt path's refusal is a forty-times sharper version of the `/api/mcp` lever in [middleware-login-and-sessions.md](middleware-login-and-sessions.md) — an anonymous caller empties the durable trail in five hundred requests. `/api/logout` is the only exempt path that writes here, it is unwrapped for that reason, and both of its branches record only after a revocation has happened; `revokeSession` returns whether *this* call was the one that ended the session precisely so a replayed cookie is worth one row rather than one per replay.

- **"Changed" is the mutation's own exit, never the status read after it.** A provider credential changed when `auth logout` or `logout`, the code exchange or the key store exited 0, and that is what writes the row. All four used to end by returning `readAuthStatus()`, with the row written only when that read was ok, and it was wrong both ways it could be (measured with stub CLIs, 2026-10-16). A read already in flight — a second tab, a script, the Settings block's own reload — was *joined*, and answered for the credential as it was: a stored Codex key answered 400 with no row, a Claude sign-in was audited as `method: "none"`, and both sign-outs answered "still signed in". A status child that failed after `auth logout` had deleted the file answered 502 and wrote no `auth.provider_signed_out`, the row the logout route exists to keep. So the confirming read is `readFreshAuthStatus`, a spawn that joins nothing and takes the shared slot, so a later reader joins it rather than the stale one. A read that **fails** leaves the change standing: the row carries `unconfirmed: true` (a sign-in's at `warn`, `method: null`), and the route answers 200 with `auth: null` and an `error` saying it could not confirm — never the non-2xx that means nothing changed. Only a read that **answers and contradicts** a sign-in refuses it, 400 and no row: Codex not on `apikey`, since `--with-api-key` exits 0 having stored nothing, and Claude still signed out. A sign-out is never refused on what the read says, because with `ANTHROPIC_API_KEY` set Claude reports `loggedIn` after a sign-out that did delete the OAuth credential.
