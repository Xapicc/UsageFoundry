# What a reviewer or validator may run

[← security index](../security.md)

Read before editing `assistSettingsArgs` or its call in `spawnAssist` (`src/lib/review.ts`), the `permissionMode` any caller of `startAssist` passes, or the `assist` case of `sandboxSettings` in `src/lib/orchestrator.ts`. What the same two may read is [assist-read-boundary.md](assist-read-boundary.md)'s, and the resolver, which runs `acceptEdits` and the build commands it is granted, is neither file's.

- **A reviewer or validator runs no `Bash` command the CLI does not read as read-only, through `useAutoModeDuringPlan: false` in the assist's one `--settings`, because `plan` refuses none.** Decided 2026-11-09 under board task `3c44bd13`. On 2.1.319 against a stub API, a validator through `startAssist` and a reviewer through `startReview`, both `--permission-mode plan` in a run's linked worktree, asked for a write into the checkout, a `touch` and a `cp` into `/tmp`, and a `curl` of the loopback stub and of `registry.npmjs.org`. None was refused by `plan`. Each was handed to auto mode's safety check, and came back "Auto mode is unavailable: its safety check does not run for this session", under this container's managed sandbox and with `/etc/claude-code` hidden alike. That refusal is the stub's doing. A real API runs the check, and what it approves then runs. This install's one reviewer session, on 2.1.280, ran `tsc` and `node --test` and unpacked a `git archive` into `/tmp` without an error. The setting is read from flag settings, and with it each of those commands was refused as needing approval, on both installs. `git log`, `git diff` and a `cd` into the checkout ahead of both still ran. It matters for the reason the read boundary does: both prompts carry text the run wrote, and an instruction planted there could have the judge run what the check approves. The "leaves a plan-mode assist's Bash nothing to run but what the CLI reads as read-only" case in `review.test.ts` pins it. `docs/verification/security-and-sandboxing-assist-reads.md` has the measurements.

- **`autoAllowBashIfSandboxed: false` rides beside the write set, and on the pin it changed nothing that was measured.** The CLI documents the auto-allow as on by default, approving a command because the sandbox would contain it. Under `plan` on 2.1.319 it approved none of the commands above, with the setting or without it: `touch` and `cp` into `/tmp`, both inside the write set, went to the auto-mode check either way. It is set so that a later pin which does apply the auto-allow under `plan` cannot hand a judge every write its sandbox allows. It is added only where a write set is, because a stock install's argv carries no `sandbox` key and must keep carrying none.

- **What it leaves, under the managed sandbox, is a read-only command's output redirected into the write set outside the checkout, and that reach is accepted.** With both settings, `echo PWNED >` a literal path in `/tmp` and a new file in `CLAUDE_CONFIG_DIR` both wrote. Every redirect let through had its target outside the working directories and inside the sandbox's write set, which is how the CLI appears to decide. It refused the same redirect onto that directory's `settings.json`, `CLAUDE.md` and a file under `projects/`, and the checkout itself is not in a judge's write set. Stock, with no sandbox to contain a redirect, both were refused. The reasons it is accepted rather than closed: both directories are in the write set because the sandbox runtime and the metering path need them (`writeSet` in `orchestrator.ts`). And every work cycle's write set holds them too, so a run that plants an instruction for its judge could make the same write itself, without a judge. Closing it means a narrower write set for the two plan-mode kinds, and what the CLI's own sandboxed shell then fails on was not measured. A redirect whose target is a variable, such as `"$TMPDIR/x"`, is refused already: the read block's parser cannot check it.

- **What it costs is a judge that checks by running things.** The 2.1.280 reviewer's `tsc`, `node --test` and scratch trees in `/tmp` would each be refused now. Validators on this install made 149 `Bash` calls across 587 sessions between 2026-10-13 and 2026-11-09, and every one was a read. Most were `git log`, `git diff` and `git show`, often after a `cd` into the checkout, and the rest were `sed -n`, `grep`, `awk`, `wc` and `head`, plus one `python3` script. Only the `git` forms were driven under the setting. The `python3` script would be refused, since nothing grants it.

- **What it does not cover.** The stub runs no auto-mode check, so the rig shows which path decides a command and not what a real API's check would have said. That the setting keeps a real API's check from being asked is the CLI's code read through its refusal text, not a measured verdict. The 2.1.280 reviewer's commands were not replayed on 2.1.319. MCP tools were not driven. The server running as root and dropping the child to the agent uid was not run. The rig was the compiled modules in a scratch process. The resolver's own `Bash`, which the managed sandbox auto-allows, is filed as its own task.
