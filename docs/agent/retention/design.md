# One decision over three stores, and what every sweep promises

[← retention index](../retention.md)

Read before editing `src/lib/retention.ts` as a whole, the `eventRetentionDays`, `checkoutRetentionDays` or `transcriptRetentionDays` settings, or `transcriptCutoff` and what `/api/usage` and `PeriodSeries.completeFrom` do with it.

**Three stores, one retention decision, and the decision is what a run's row is for.** `run_events` in the named volume, `.uf-worktrees` on the workspace bind mount, `~/.claude/projects` in the operator's own home — three media, three growth rates, and for a long time not one `DELETE` between them. They were filed as three findings because each sweep found the store in front of it, and they are **one** design because they share one question: what is safe to discard, and what does this app promise about history it has already shown somebody. The answer is a single sentence. **A run's row is permanent; everything behind it is evidence, and evidence has a horizon.** Nothing in `retention.ts` deletes a `runs` row, a `run_reviews` row, a `workflow_instance_*` row or a settings key, so every figure this app has ever put on the dashboard, the runs list or a run's own state card keeps reading true for ever — the spend columns, the cycle count, the stop reason, the branch, the landing record. What each sweep removes is the *working material* those figures were derived from: the event log's payloads, the checkout on disk, the session transcript. Each is bounded by its own horizon in Settings (`eventRetentionDays` 30, `checkoutRetentionDays` 7, `transcriptRetentionDays` 30; `null` on any of them means keep for ever, the reading every switchable rule here takes), and each horizon is separate because the media are — a checkout is hundreds of megabytes and is rebuilt by `worktree add` in seconds, where a transcript is the only thing `--resume` can continue.

Four properties are shared by all three sweeps and none of them is optional. **Nothing in flight is touched**: a non-terminal run keeps its whole event log, a checkout an active run holds is skipped by name, and a transcript whose session id belongs to a live run or to any chat is never a candidate — which is why each sweep asks the *database* what is live rather than inferring it from a file's age. **The decision is pure and the syscall is not**: `reclaimableCheckouts` and `expiredTranscripts` are the two functions that decide what goes, and both are unit-tested against fixtures, for `releasableRuns`' reason — every way of being wrong here is silent, lands on somebody's disk, and throws nothing. **A removal is recorded where the operator would look for it**: a reclaimed checkout emits a `land` event on its own run, and every sweep's counts are stored under `retention.lastSweep` and shown on the Settings page beside the sizes. And **a sweep never destroys the only copy of anything**: it removes no branch and no commit (`worktree remove` without `--force`, so git gets a second veto), it never touches the operator's own checkout, and a transcript it removes is one whose spend is already recorded in `runs.spent_usd` and in the `run_events` row that reported it.

Two consequences are written down rather than absorbed. **A pruned transcript takes its session with it**, so the sweep clears `runs.session_id` on every run it belonged to — *before* its first `await`, in the same synchronous section that read the keep set, because `reopenRun` can land anywhere inside the unlink loop and a clear after it, filtered to terminal rows, left that run holding the id of a file the sweep then deleted for good (a file that will not unlink puts its ids back; one already gone does not): `--resume` against a file that is gone fails the first cycle of a pick-up outright, where a null session id is already the documented restart — `nextPrompt` writes the task with `priorWorkNotice` naming the branch. Clearing is what turns a silent failure into the path this app already has. **And it shortens the dashboard's own history**, which is the one place the promise above is genuinely at risk: `buildPeriods` offers twelve months and a 30-day horizon empties eleven of them. Making the horizon a year would defeat the retention, so the card says so instead — `PeriodSeries.completeFrom` carries the cutoff, `/api/usage` fills it through the same `transcriptCutoff` the sweep decides by, and any bucket that starts before it is marked as covering transcripts that have since been pruned. `buildPeriods` already drops buckets that closed before the first entry, so the effect is a *shorter* history rather than a wrong one; the sentence exists for the one bucket the cutoff falls inside. Nothing here reaches `evaluateBudget`, and since the settings route accepts a horizon of 1 that is a floor rather than a coincidence: with no provider reading the weekly guard is summed from these files, so `transcriptCutoff` never reaches back past seven days ago — inside which every week `windows.ts` can open, anchored or provider-reset, starts.
