# Which tables the event sweep reaches, and the column no sweep writes

[← retention index](../retention.md)

Read before editing `sweepRunEvents` in `src/lib/retention.ts`, `CONTEXT_SAMPLES_PER_RUN` in `src/lib/contextSamples.ts`, or anything that writes `runs.provider`, `context_samples` or reads the orphaned winnow tables (`prune_receipts`, `prune_decisions`, `fork_attempts`, `resume_probes`, `plan_observations`, `context_compositions`).

**`runs.provider` is permanent, and the clause that matters is that no sweep may ever write to it.** It is one column on a row this module already promises to keep, so it needs no horizon and gets none; it is written down here because `null` on it is load-bearing in a way `runs.session_id` is not (`design.md`'s *"A pruned transcript takes its session with it"*). `session_id` is cleared *by* a sweep precisely so that a missing transcript reads as the restart path this app already has. `provider` is the opposite: `null` means the row predates the column and nobody ever recorded what it ran as, the run page renders exactly that and never "Claude", and a future sweep that cleared the column — or a migration that backfilled it — would be manufacturing an answer to a question that was never asked. Which agent CLI produced a diff is the one thing a reviewer reading a two-year-old landed run cannot recover from anywhere else, so it keeps for as long as the row does. Nothing derived from it may be summed into `runs.spent_usd` or any window meter; `docs/agent/architecture/data-sources.md`'s *"three data sources"* paragraph's rule about the three populations is what forbids it, and this column changes nothing about that.

**Seven tables outlive the code that wrote them, and only one of them is still swept.** `prune_receipts`, `prune_decisions`, `fork_attempts`, `resume_probes`, `plan_observations`, `context_compositions` and `context_composition_children` were winnow's. The winnow removal made no destructive migration, so they stay in the schema with their historical rows and nothing writes or reads them any more — dropping a table with a year of savings history in it is a decision for an operator, not a side effect of deleting a module. `prune_receipts` and `prune_decisions` were never swept (a weekly KPI cannot lose the evidence behind its first days) and still are not; they are now simply static. **The one exception is the composition pair**, which `sweepRunEvents` still deletes on the run-events horizon so that old rows age out rather than sitting forever behind a reader that no longer exists; its `compositions` figure stays on the sweep's report. The per-run composition cap went with the writer. Anything that reads one of these tables again must read it as history: a row says what an earlier version of this app did, not what the install does now.

**A fourth table rides the event sweep, and which sweep it rides is the decision.** `context_samples` is the occupancy series `run-lifecycle/context-samples.md` describes — a row per moved `usage` frame per live run, written on the run loop's own path — so it is exactly the shape this module exists to bound. It goes with `run_events`: same horizon, same `settled` test, because it is the same kind of thing as the log it sits beside on the same page, and a series that outlived its own log would be a graph with nothing left to read it against. Nothing aggregates samples across runs, so nothing here is a figure that would silently stop covering a week, which is the argument for sparing a table from a horizon and does not apply. The other half of the bound is on insert — `CONTEXT_SAMPLES_PER_RUN`, oldest first — because a run with no cycle cap has nothing bounding how many turns it takes, and a horizon alone would leave one such run unbounded for as long as it lives. The two are not redundant: the cap bounds a run, the sweep bounds the install.

**The holdouts' evidence is copied out ahead of this sweep, into tables it never reaches, and a run it could not copy keeps its events.** `holdout_runs`, `holdout_cycles`, `holdout_tool_events` and `prior_read_snapshots` are not the samples' kind of table: what a prompt named and what the run then opened lives only in the thirty-day log, and an analysis that needs the experiment's first month at its end cannot be run from a log that has lost it. `exportHoldoutEvidence` runs as the first statement of `runRetentionSweep`, so the evidence is out before the sweep that would take it and the first pass after an upgrade reaches back to the oldest events that survive; it is deliberately not a separate nightly job, because a job with its own clock can fall behind a sweep that has none. A run that throws is named in the export's summary and `sweepRunEvents(now, keepEventsOf)` leaves exactly that run's `run_events` alone — they are the only copy, and the next tick six hours on has the same horizon to spare — so one malformed row cannot stop the log being bounded for every other run. If the export fails outright (the table is gone, the query will not run), the event sweep is skipped for the tick. The checkout and transcript sweeps, which are about other stores, run either way. The export is monotone: evidence rows are `INSERT OR IGNORE` on the event's own id, a count only grows, and a derived field is never rewritten from less than it had, so a pass made on a half-swept run cannot make its row worse. A settled run is finalised and not visited again until it is picked up. The tables carry no foreign key to `runs`, and are the one place a run's evidence outlives `eventRetentionDays` on purpose; ending the experiment is when they can be dropped.
