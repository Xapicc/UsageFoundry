# No VACUUM, and the storage card's cache

[← retention index](../retention.md)

Read before editing `storageReport`, `treeSize` or `backupStore` in `src/lib/retention.ts`, `GET /api/storage`, or anything that would shrink the database file.

What the sweep deliberately does **not** do is `VACUUM`. SQLite reuses freed pages, so the retention bounds the database's growth to a steady state, and only a `VACUUM` returns the space to the filesystem — which rewrites the whole file and blocks the single writer for as long as that takes, on a process that is also carrying live guards. So the file size is *reported* rather than silently shrunk, and `README.md` gives the one-line command beside the backup procedure.

**The card's two store sizes are measured rather than counted, so they are cached — and which half of this module the cache sits on is a structural decision rather than a tuning one.** `GET /api/storage` took 5.3-7.4s warm to answer 585 bytes, and two operators opening the Settings page together each paid it in full: the two `COUNT(*)`s beside the walks are 0.05 ms and 0.01 ms against a walk of 5,981 ms. `storageReport` reads both walks through a five-minute TTL with the single-flight `status.ts` already uses for the same measurement, so a second reader joins the walk in progress rather than starting one — the measurement takes seconds, so concurrent readers are the ordinary case rather than a race — while the figures the database can answer stay fresh on every call, which is the half of the card an operator watches after changing a horizon. **The cache is on the report's reading and deliberately not on `treeSize`**, and that is the whole of what keeps a five-minute-old size out of a removal: `sweepCheckouts` decides from the database and from git, `sweepTranscripts` from its own walk of `~/.claude/projects`, and neither asks for a size at all — the only way a stale one could reach a delete path is a future sweep reaching for the cached reading instead. A figure this old is something an operator reads; it is not something to delete against. **The backup store on the card is read fresh on every call and is not part of that cache**: `backupStore` is one `readdir` of a directory holding tens of files, and the reason to open this card after running a backup is to see the backup. It is also the one store here nothing in this app writes and the only one no horizon applies to — this module measures it and never sweeps it, which is the correct asymmetry for the store a recovery depends on. `treeSize` itself now issues its `lstat`s in bounded batches rather than awaiting each one (88,325 entries over 2.62 GB: 5,981 ms serially against 1,750 ms with 64 outstanding), and the tail — including the batch a spent budget abandons mid-directory — is drained before it returns, because a total that came back with stats still in flight would be silently *short*, and a store that reads 1.4 GB while holding 2.6 is the figure a horizon gets set against.
