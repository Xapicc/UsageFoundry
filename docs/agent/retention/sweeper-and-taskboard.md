# Who may sweep, and the taskboard no sweep reaches

[← retention index](../retention.md)

Read before editing `startRetentionSweeper` or its `tick` in `src/lib/retention.ts`, or before putting any table — `tasks` above all — on a horizon.

**Every tick re-asks who owns the data directory, and this is the only sweep in the app for which that is a deletion question.** `startRetentionSweeper` arms a six-hour interval and `tick` calls `mayWriteDataDir()` before anything else, stopping its own timer rather than skipping the tick — `sweepPaused`'s rule, and for its reason: nothing here will ever be a stood-down process's to decide again. The gate in `instrumentation.ts` is still there and is still not sufficient, because it is asked once at boot and the answer moves: `heartbeat` returns `lost` when the directory changes hands, and a `writeLock` that throws — a full disk, a read-only remount — stands the process down too. Until 2026-09-08 the interval survived both, so six hours after losing the claim a process ran the whole sweep against a database and mounts another process owned, beside that owner's own sweeper: the `DELETE`s above, `git worktree remove` on its checkouts, `unlink` on its transcripts, `UPDATE runs SET session_id = NULL`, and `LAST_SWEEP_KEY` written over. `timer.running` is a per-process module variable and was never a cross-process lock; it cannot see the other server at all.

**The taskboard rides no sweep at all, and the refusal is the decision rather than an omission.** `tasks` is the one table added since `design.md`'s decision was written that no horizon reaches, and it is on the `runs` side of this module's one question rather than the evidence side. A task is not working material behind a figure somebody was shown — it *is* the thing somebody was shown, and it is the only copy: the brief in `tasks.body` is the text a future agent is handed with nothing else to go on, and there is no transcript, no event log and no checkout it can be recovered from. So **an open task never expires**, on the plainest reading of the sentence at the top of `design.md`: it is the operator's backlog, losing it silently is the worst outcome this feature has, and a horizon that quietly emptied a backlog would be indistinguishable from an install where nobody had written anything down. **A closed one is kept until the operator deletes it**, and that is the same decision one step further rather than a second one — `done` and `dropped` are what this install got done and what it decided against, which is exactly the kind of answer `runs.spent_usd` is kept for ever to be able to give, and a board that could only answer for the last thirty days would be a board nobody could ask "did we ever do this". `deleteTask` is the only `DELETE` on the table, it is the operator's alone (`taskboard.md` says why), and a sweep that reached this table would be the second one — which is the shape of the failure `retention.ts` exists to avoid, not an extension of it. The argument that would put it on a horizon is the one `context_samples` won on — a table written on a machine's own path, unbounded by anything an operator does — and it does not carry here: three of the four origins are machine-written, but each row is a deliberate decision by a model that a human then reads on a board, which is `chat_proposals`' shape and `chat_proposals` is likewise swept by nothing. What bounds this table is that somebody has to want each row. If that ever stops being true the answer is a cap on what one run may file, on `CONTEXT_SAMPLES_PER_RUN`'s reasoning — bound the writer, not the store — and never a horizon over rows a person put there.
