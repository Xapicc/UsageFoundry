# The transcript sweep and the checkout sweep

[← retention index](../retention.md)

Read before editing `expiredTranscripts`, `sweepTranscripts`, `reclaimableCheckouts`, `planCheckoutReclaim` or `sweepCheckouts` in `src/lib/retention.ts`, `forgetTranscriptFiles` in `src/lib/transcripts.ts`, or `slotIsDirty` in `src/lib/orchestrator.ts`.

The transcript sweep is the one whose protection cannot come from a file's age, so it comes from the database: `expiredTranscripts` takes a horizon and a `keepSessions` set built from every non-terminal run and **every** chat thread — a chat has no terminal state to key on, since an operator may type into one at any moment, and a *parked* run's transcript is old precisely because it is the one about to be resumed. The session id is the file's own basename, which is how the pinned CLI names one; that is verified against the shipped layout rather than assumed, and if it ever stops holding the cost is the extra protection rather than the age test, which is on the README's *Not yet verified* list by name. The cache is told about exactly the files that went (`forgetTranscriptFiles`) rather than invalidated — invalidating the whole of it makes the next scan re-read every file from byte 0, which is the pass the byte-offset cache exists to avoid, and there is deliberately no function that does it: `337f355` deleted `invalidateTranscriptCache` "rather than left reading as an eviction path that exists", the eviction the cache actually has being `TRANSCRIPT_CACHE_MAX_ENTRIES`, which drops a file whole and coldest-first. A removed file's parsed entries would otherwise be held for the life of the process, leaving the dashboard showing spend from transcripts that are gone and disagreeing with the cutoff the period card had just been handed.

The checkout sweep is the one whose store is somebody else's directory, so what it may touch is narrower than the other two and is worth stating outright. It removes a *directory* and never a ref: `worktree remove` without `--force`, which leaves the branch and every commit on it exactly where they were and gives git a second veto over the cleanliness `planCheckoutReclaim` already checked. Six clauses have to hold, and each of them is a keep — `slotIsDirty`'s rule that an unreadable status counts as dirty is one of them, unchanged and not to be weakened, since `git status` cannot see the gitignored trees that are most of the bytes. It never removes a checkout an active run holds, one the newest run recorded in it has not finished with, one a run that has not started yet is set to carry the branch on from, or one whose branch carries commits its target does not have — where "does not have" is a squash `landed_tip` on **any run of the branch's `continueBranch` chain** equal to the branch's tip, whose `landed_commit` the target still has, and `rev-list --count target..branch` for everything else, because a squash rewrites the commits and git's own ancestry test can never call such a branch merged. The squash commit is asked of the target because a land the operator undid with `reset --hard` leaves the tip where it was (`docs/agent/isolation-and-landing/branch-inventory-and-deletion.md`). The tip is read across the chain, with `land.ts`'s own `isLandedTip(repoRoot, target, chainRuns(run), tip)`, and not off the one row the slot reports: `landRun` writes it on the run that landed, and a link that continues that run afterwards inherits its slot and its branch while carrying no tip of its own — and being the newest run recorded in the slot, that link is the row asked about. Read per row, a squashed branch looked never landed and its checkout was kept for as long as it existed; the miss was conservative, which is the only reason nothing noticed. What it costs when it does fire is the installed dependency tree the next run in that slot would have reused, which is the whole of why the horizon is a week: slot reuse is what makes isolation practical, and a horizon short enough to break it would trade disk for an install per run.
