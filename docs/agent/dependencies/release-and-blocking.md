# Releasing, blocking and waking a dependent

[← dependencies index](../dependencies.md)

Read before editing `releasableRuns`, `releaseDependents`, `reviveBlockedDependents`, `blockBehindRestartClosed` or the waiting-row half of `reconcileOnBoot` in `src/lib/orchestrator.ts`.

**A dependent that can never start is terminated with a sentence naming what stopped it, and so is everything behind it.** The status is `blocked` — the one this app already writes for a run refused before its first work cycle, and the true thing to say: nothing ran, nothing was spent. `startRun`'s own pre-cycle refusal chooses it on `ranWorkCycle` too (`everWorked`), so a run whose refunded cycle spent and was then refused by a guard ends `stopped`. `releasableRuns` is the whole decision and it is pure and unit-tested for exactly this, because both failure modes are silent: a run released too early starts on top of work that has not happened, and a run neither released nor terminated sits `waiting` for ever holding a prompt the operator believes is queued. The cascade is a fixed point rather than a graph walk — a run blocked in one pass is a settled dependency that ran no cycle in the next — so every run in a chain gets its own reason naming the run *in front of it* rather than one shared verdict about a run at the head it never heard of.

**Every terminal transition wakes the dependents, and a boot deliberately does not.** `releaseDependents` is called from `startRun`'s `finally`, from both of `stopRun`'s pre-spawn branches and its new waiting branch, and from the sweeper's never-clearing verdict when its ending lands (a miss means an operator's stop or resume took the row first: a stop releases for itself, and a resume settles nothing) — missing one leaves a dependent asleep with nothing that will ever wake it. Released runs join the queue rather than starting there, so folder reservation, FIFO order and the concurrency cap stay in `promoteQueued`, the same reason `sweepPaused` re-queues instead of calling `startRun`. `reconcileOnBoot` is the exception, and it decides its waiting rows only after the active ones, against what it did to each one's dependency. A row behind a run that same boot has just failed or stopped is `blocked` with a sentence naming that run, on either edge, because releasing it would promote a days-old prompt into an unattended agent that accepts edits (the queued rule arrived at from the other side), and an `on-finish` edge would do exactly that for a run that did a cycle and then died with the container. It is not flagged `restart_closed`: its dependency is, and picking that up revives it through `reviveBlockedDependents` — unless it has been set aside, which that revive never undoes. Every other waiting row goes through the ordinary pass with its release half held, so what can never start still ends naming the run in front of it, while a row behind a pause the boot kept, or held behind a completed run, stays `waiting`. Stopping those too, as the boot once did, recorded a restart that had closed nothing they waited for. It is the pass and not `releaseDependents`, whose workflow advance `reconcileBlocksOnBoot` has to run ahead of. A loop whose ending is the shutdown's, the ending flagged `restart_closed`, blocks what waits on it the same way, in `blockBehindRestartClosed` with the boot's sentence, before its own release pass: that is the ending the boot gives a run a crash left `running`, and released instead an `on-finish` dependent was queued mid-shutdown, flagged by the boot as a queued row, and reopened by the restart notice's one press beside the run it was set to follow.

**A run a restart closed out satisfies no edge until it is picked up, and nothing new is chained onto it meanwhile.** `releasableRuns` blocks a waiting run behind any dependency that is `restart_closed` and `failed` or `stopped` — `ReleaseState.restartClosed`, `restartClosedSql`, the restart notice's own condition without `set_aside_at` — on either edge, ahead of the edge test, with the boot's sentence. The boot and the loop already blocked what waited on a run they had just closed out, but only then: any later pass read the same ending as an ordinary one, and an `on-finish` edge is satisfied by a restart's `stopped` once a cycle has been counted. A fan-in reached it. B after A and C, both closed out; picking up C alone by name revives B through `reviveBlockedDependents`, which follows edges out of the run picked up and asks nothing about B's other dependencies; C's next ending ran the pass, which released B on the strength of A's restart ending, and picking A up afterwards ran the two side by side — inferred from the code, then reproduced in `shutdown.test.ts` against `17704ac`, B `queued`. Blocked rather than left pending, because nothing obliges anybody to pick the run up, and a row waiting for a pick-up that never comes is the asleep-for-ever row; blocked is what the pick-up revives, so the sentence stays true. Narrowing the revive instead was rejected: it fixed only the path that was found, left B blocked with a sentence naming the run just picked up, and every other way a row reaches `waiting` behind a closed-out run — a never-started row picked up by name, a row woken earlier — would still have been released. A run set aside still counts: setting it aside holds it back from the notice's press, and it has not finished any more for that. `dependenciesOf` reads the flag the same way, so the page never calls a dependency satisfied that the pass blocks on. **A new run** told to start after such a run is refused at `createRun` with a sentence of its own — pick that run up first, or start this one without waiting for it. It used to be created `queued` on an `on-finish` edge, beside a run the notice's one press would then start, and refused on `on-success` with "it ended stopped", which sent the operator nowhere. Not created `blocked` either: a row born terminal is a run the operator is told they made and cannot reopen, since `blocked` is not `REOPENABLE`. The explicit `blockBehindRestartClosed` calls in the boot and the loop still run ahead of their passes; the pass now agrees with them rather than being where the rule lapsed. A workflow's own edge verdicts read the flag the same way, ahead of the edge, for a run node's run and for every run an orchestrator block emitted: until they did, a merge block behind a fan-in landed the branch of a run the restart had cut off — driven in `shutdown.test.ts` — and the rule is in `workflows-and-schedules/nodes-and-instantiation.md`.

**A run that was released and ran nothing is asked every one of its conditions again when it is picked up.** `reopenRun` sends a row that never started back to `waiting`, where the release pass asks it everything, but a row that holds a workspace and ran no work cycle — released, then stopped, guard-refused or failed before its first cycle — is queued directly, and nothing on that path asked a dependency again. A plain `on-success` run whose predecessor completed, was released and was stopped at zero cycles went back in the queue after the predecessor had been picked up and failed: an `on-success` run started behind a failed dependency, which is the failure `releasableRuns` exists to prevent, with no branch shared and so nothing for `branchRivalOf` to notice. Found by reading the code, then driven in `stackWait.test.ts` against the tree before the change: the plain dependent and the fan-in's continuer were queued (`ok: true`), and a predecessor picked up and still queued was refused only by the checkout check, because the two shared a slot, with a sentence about the checkout and not about the dependency. `unworkedPickupRefusal` builds a `ReleaseState` for **every** `run_deps` row of the run and calls `releasableRuns`, so the answer is the release pass's own and cannot drift from it: a `block` or `notNeeded` verdict is the refusal's sentence, and neither verdict means the pass left it `waiting`, which is a dependency a pick-up put back in the queue and is said as *is queued again, wait for it*. Every edge and not the `continues_run` one, because a fan-in's other dependencies are conditions the run started on just the same; the first version of this check, for branch continuers only, re-asked one edge and let a continuer through behind a failure on another. `branchRivalOf` stays a continuer's question alone, since nothing else shares a ref. A run that ran a cycle is not asked, because starting spent its condition, and a row going back to `waiting` is not asked here, because the release pass asks it. One consequence follows from `reopenFleet`'s dependency order and was not driven: a press that picks up a predecessor and the unworked run behind it queues the first and refuses the second by name, because the second would otherwise start beside the run it was ordered behind, and nothing wakes it when the first ends — it is `stopped`, not `waiting`, so the operator picks it up afterwards.
