# What a waiting run holds, and what admission refuses

[← dependencies index](../dependencies.md)

Read before editing `run_deps`, `waiting`, `admitWaiting`, `admitDependencies` or `dependencyCycle` in `src/lib/orchestrator.ts`, or anything that lists what a block waits for.

**A run can be told to start after other runs, and while it waits it holds nothing.** `run_deps` is a join table rather than a `depends_on` column because fan-in is the case that matters — "after both of these" is a list with identity — and because the condition belongs on the edge rather than on the run: one dependent can reasonably want "only if that one worked" from one dependency and "once that one is out of the way" from another. `waiting` is a status rather than a flag on `queued` precisely for what it must *not* hold. `activeRuns()` cannot see it, so it reserves no folder, takes no checkout slot, spends no concurrency slot and has no place in line. That absence is the whole design: a `queued` run reserves its folder against everything younger — deliberately, or a run on the workspace root is overtaken for ever — so a four-run chain admitted up front as `queued` would stall every unrelated run on that repository for the length of the chain. Isolation is planned at *release* rather than at admission for the same reason: choosing a checkout slot is claiming it, and a run that may not start for days must not hold one. `isolate: false` is the one thing recorded at admission, because that is the operator's own answer and the release must not overrule it — everything else (`work_dir`, `repo_root`, the branch, the base commit) is null until `admitWaiting` fills it in, which is also why a waiting row is invisible to `landState` rather than a branch with nothing on it. `continues_run` is the second, and it is not an exception to any of that: it names a run rather than claiming one, and the isolation invariants below say why the landing rules need it before there is a branch to see. The condition is explicit on every surface that lists what a block waits for: `instanceDTO`'s `waitsFor` carries `{ nodeId, edge }` per wait (`instanceWaiter`), in the chip's own words on the instance page, and `edge` is null where no edge was saved — an orchestrator-emitted run, a pass's entry — rather than a guessed condition. That labels the edge and nothing else: whether it is *met* stays `edgeSatisfied`'s, and the page must not re-derive it.

**A loop is refused at admission, because nothing downstream of it would ever be woken or ended.** `releasableRuns` reaches a fixed point and leaves a cyclic set alone, which is precisely the row nothing wakes; admission is the only moment an edge is created, so it is the only place this can be caught. `dependencyCycle` names the loop, and a self-reference is reported as the one-run loop it is. `createRun` cannot construct a cycle today — it mints the run's id *after* reading the edges, so nothing can already point at it — and the check is what keeps acyclicity a property of the data rather than of who happens to write it.
