# What satisfies an edge: `edgeSatisfied` and its three conditions

[← dependencies index](../dependencies.md)

Read before editing `edgeSatisfied`, `ranWorkCycle`, `refundedCyclesSql`, `TERMINAL_STATUSES` or `notNeededReason` in `src/lib/orchestrator.ts`, `edgesExclude` in `src/lib/branchRival.ts`, or anything that reads a dependency's ending.

**A dependency succeeds by reaching `completed`, and a run that never ran a work cycle satisfies nothing.** The first half is the choice `reopenPrompt` already forced once: `completed` is written both for a `DONE` reply and for a run that used up its cycle cap, and `maxIterations` defaults to 1, so keying success on `reported_done` would mean a dependent almost never starts and the chain would terminate saying "it did not report done" about a run that did exactly what it was asked. Success here is the *absence of a fault* — no crash, no guard, no operator stop — which is the question a person chaining two runs is asking; `reported_done` is on the DTO for anyone who wants the stronger reading and decides nothing here. The second half is what makes a chain terminate rather than sit there: a guard refusing a run at the door, a run whose own dependency failed, a run stopped before it started and a run closed out by a restart are all terminal having run nothing, and reading `on-finish` as "any terminal status" would start the next run on the strength of a run that never opened a file — and would leave a `blocked` run satisfying its dependents, so nothing would ever end the chain behind it. Both conditions are named explicitly on the wire and neither is defaulted, because a silent default is wrong half the time in both directions: `on-success` terminates a chain the operator meant to run regardless, `on-finish` starts a run on top of a dependency that crashed.

**"Ran a work cycle" is `ranWorkCycle`, which is `iterations > 0` or a refunded cycle, because the refunds put `iterations` back to zero on a run that worked and paid.** A stack park, a live-guard cut, a context-ceiling end and a provider refusal the run survives each hand the cycle they ended back to the counter, so a run that spent a whole cycle and was then stopped while parked ends `stopped` with `iterations === 0`. Read as "never ran", it blocked its `on-finish` dependent with "ended stopped without running a work cycle", a sentence that was false; "Try again" on the dependent re-blocked it at once, and the only way out restarted the dependency's agent. `DependencyState.refundedCycles` carries `guard_refunds + stack_waits + early_ends + worked_refunds` (`refundedCyclesSql` for a query, `refundedCyclesOf` for a row in hand), and it is a required field so that a state built without it is a compile error and not a run read as idle. Not `pause_count`, which `ensureWorktree` reads for a different question ("might a branch exist"): it counts every refusal park, and a refusal on a cycle's first turn refunds a cycle in which nothing happened, so a run refused there and then stopped would have satisfied `on-finish` having done nothing, which is the failure the rule exists to prevent. A refusal is no evidence either way — a wall is met by whichever turn crosses the allowance, a 529 by any turn — so the wall's park and a transient retry add to `worked_refunds` only when the refused cycle had spent, in dollars or tokens. Spend and not `num_turns`, which the pinned CLI reports as 1 for an API error on a first turn that did nothing. `on-success` is unchanged by all of this: a refunded run that was stopped is not `completed`, so its dependent still blocks, now with the sentence about how it ended. Not changed: `reviveBlockedDependents` filters the *dependents* it wakes (`iterations = 0` on a row that never reached a workspace, which is true of them whatever their dependency did), and `reopenRun`'s `neverStarted` is a question about whether a row holds a session or a workspace, which a parked run always does. The branch-ownership reads follow the same rule through the same helpers, because a link that committed and was then parked or cut is the same run read the same wrong way: `branchOwner` (`ChainMember.refundedCycles`, required for the reason above, and the branches page's collapse, which builds its members itself), `chainRuns`' ordering, and `admitDependencies`' refusal of a second run continuing one branch. Asking `iterations > 0` alone named the link before it as the owner, and admitted a second continuer onto a branch carrying the first one's commits.

**`needs-review` is terminal and is not a success, and both halves are carried by one constant.** A run whose agent reported it could not finish has settled — it holds no folder, no checkout slot and no concurrency slot, and nothing will restart it but a person — so `TERMINAL_STATUSES` gains it, and that single entry is what makes `releasableRuns` reach its fixed point, `retention.ts` begin ageing its evidence out, and a workflow's loop and edge verdicts settle. Forgetting it produces a run that is terminal everywhere a person looks and unsettled everywhere the machine looks: chains that never start, loops that wait for ever, evidence that never expires, and not one line anywhere saying so. `edgeSatisfied` then answers both edges without a second rule, and the answers are the ones wanted: `on-success` is `=== "completed"` and nothing else, so a dependent stays `blocked` with a sentence naming the run that asked for review — a run that reported it could not get past something did not do the work the next run was chained behind — while `on-finish` starts, which is what that edge has always meant about a `failed` predecessor. The never-ran rule (`ranWorkCycle`) still comes first, so a `needs-review` run that never completed a cycle satisfies neither. One consequence is stated rather than absorbed: `branchVerdict` has no run-status test, so a **merge block** behind an `on-finish` edge will land the branch of a run that asked for review with nobody looking. That is not new — it already does so for a `failed` predecessor — and the operator's control is the same one they already have, which is to choose `on-success`. The other control is a review block whose verdict is the run's status (`workflows-and-schedules/review-blocks-and-providers.md`): put between the work and the merge, it is handed a run that asked for review and sets that branch aside by name while the completed ones land — and it refuses an `on-success` link into it at save, because this paragraph's rule would block it on the first such run instead. Its set-aside reads `needs-review` as not a success and as nothing more: no model judged the work, so it marks no task needs-frontier and reopens none.

**`on-failure` starts a run only behind a failure that did work, and a run on the branch it did not take is `not-needed` — never `blocked`.** It is the third condition, for a fixer, a fallback or a failure-only follow-up, and it is explicit on the wire like the other two. `edgeSatisfied` keeps the never-ran rule first, so a dependency that ran no cycle starts nothing on any edge; after it, `failed` and `needs-review` satisfy `on-failure` — a run that reported it could not get past something is exactly what a fixer is for — and `stopped` satisfies neither it nor its opposite. A stop, the operator's, a guard's or the fleet's, is a decision to stop spending, and a fixer started on it would undo that decision with a fresh agent; nobody judged the work, so the dependent is `blocked` naming the run, and picking the stopped run up revives it. A dependency that worked and `completed` makes the dependent `not-needed` (`notNeededReason`): a terminal status that holds nothing and spent nothing, in `TERMINAL_STATUSES` so the pass reaches its fixed point and retention ages it, out of `NOTIFY_STATUSES` because paging on a branch not taken is paging on success, neutral rather than `blocked`'s amber, and counted by an instance's tally as neither live nor blocked, so a workflow whose first run simply worked reads `finished`. **It cascades on every edge**: what sits behind a branch not taken is part of that branch, and the never-ran rule would block it with a sentence that is true and reads as a fault nobody made. Within one pass a dependency that blocks outranks one that passes over, because a fault is what the operator has to be shown, and either is decided as soon as it is known. `reviveBlockedDependents` wakes a `not-needed` row exactly as it wakes a `blocked` one, since a completed run picked up and then failed is when its fixer is needed after all; a run that would be `not-needed` the moment it exists is refused at `createRun`, as an `on-success` run behind a failed one is. Accepted by `POST /api/runs`, `propose_run` and a saved graph's link **out of a run block**; refused at save out of any other kind and inside a loop's section, and in an orchestrator block's `emit_runs` (`EMITTED_EDGES`) — the rules are in `workflows-and-schedules/nodes-and-instantiation.md`. One consequence is stated rather than absorbed: a fan-in of both branches never runs — it waits on the one not taken — so a fallback draws a merge block per branch. **A success run and a fixer may both carry on one run's branch, and no wider pair may.** `edgesExclude` is the whole exception, `on-success` with `on-failure` on the same dependency: `edgeSatisfied` meets them by `completed` and by `failed`/`needs-review`, and no ending meets both (`stopped` meets neither, so it is *at most one* committing). `on-finish` meets every ending, so it overlaps both, and a third continuer is refused whatever it waits on. Save asks it pairwise over the links out of one block (`graphRefusal`); admission reads the rival's own edge off `run_deps` and lets it through only while it is `waiting` having run nothing, a released one being on the branch whatever it waited for (`continuationRival`, `branchRivalOf`); `propose_run`'s check (`rivalContinuation`) agrees. `branchOwner` and `chainRuns` need nothing new: the one not taken is `not-needed`, a terminal run with no work cycle, which is not a link.
