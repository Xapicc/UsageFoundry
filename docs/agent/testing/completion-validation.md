# The completion validator

[← testing index](../testing.md)

Read before adding or editing tests of `validation.ts`, or of anything that stops, settles or waits for a validation.

`validation.test.ts` covers the five pure decisions the external validator is made of, and it is the one feature here where a model's opinion can spend money with nobody pressing anything — so the five are covered together and each fails silently in a *different* direction. `parseVerdict` decides whether there is a verdict at all, and no verdict closes the task: too strict and the feature switches itself off on exactly the runs whose replies are longest, too loose and a verdict is read out of whatever a diff persuaded the model to write, which is why the last object that *is* a verdict is taken — fenced or bare, in text order, so neither a JSON block the reasoning quoted out of the diff nor a quoted one after the answer is read as it, and a quoted fence no longer hides an answer whose own fence was dropped — and why an unknown value is null rather than coerced. `grantsAnotherCycle` is the whole of the terminus — wrong one way and the agent's word is the last word again, wrong the other and `maxIterations` no longer ends a run — so the cases pin the limit, the overshoot past it, and zero as an off switch rather than as "unlimited", which is the reading that would turn the operator's most cautious setting into the least. `verdictsToActOn` is what reaches that limit at all: a run may hold several tasks, and the boundary once read only the run's newest validation, so a second task's check hid the first one's `not-finished` and the run ended `completed` with that task claimed and nothing saying so — its first case is exactly that pair, and the others pin that each task is read at its own newest row, so a superseded reading sends nobody back, and that a check asked for before the last pick-up is left alone however late its verdict lands while one asked for after it, or carried across a park, is not. Two more cases hold the request time against the spawn: a row whose child spawned after the pick-up but whose `asked_at` is before it is left alone, and a row with no `asked_at` is read by `created_at` rather than as zero, which would drop every pre-column row from the wait and from the verdicts. `validationSkipReason` has to fail **open** in every branch, because a branch that refused instead of closing would turn a shortage of assist slots into a task nobody can close. And `buildValidationPrompt` carries the one prohibition no type can hold: the judge is never told the run claims to be finished — `LLM-as-a-Judge`'s agreement bias is directional, the trigger for the whole path *is* a claim of completion, and the way this regresses is somebody adding it back as helpful context, so five phrasings of it are asserted against by name.

`validationSettle.test.ts` is those decisions' writes, against a real database, and it is its own file because what it pins is a task left claimed by a run that has finished with it — a row, not a value, and one nothing anywhere reports. Its boundary cases are the two-task run end to end: a task judged unfinished and then hidden by a second task's newer check must still get its pushback, and two unfinished tasks get one pushback and one grant between them, with the line that says the grants are spent naming both. Its other three are the checks that never reached their settle, each of which closed nothing before: a restart mid-check must close the task as the run, with the row's verdict still null; the same restart must leave alone a task the operator released meanwhile; and a spawn that throws before any child exists — a prompt carrying a NUL byte is the one it uses — must still reach `after`, since that is the only thing that closes a validation's task or aborts a resolution's merge.

`validationStop.test.ts` is what an operator's Stop does to a check still reading, and it is the one file in this group that spawns a child, because both halves of the defect it pins live on a real one: `stopRun` signalled only the work cycle's, so the check went on reading, billed, and its settle closed the task `done` in the name of a run the operator had stopped — a green row nobody re-reads. So it drives the real path, a real repository and branch and `completeTaskWithValidation` as `complete_task` calls it, against a stand-in `claude` that reads until it is signalled and then answers `finished` on its way out, as a CLI that handles SIGINT may; that answer is what the settle has to refuse rather than merely not see. Its first case is Stop during the verdict wait, with `validationAtBoundary` running under the loop's own interrupt test, and its second a parked run, which `stopRun` settles in a branch of its own before any interrupt is written — the reason the reach sits ahead of every branch. Each asserts the child got the SIGINT, the task is still `claimed` by the run and not completed, and the row is `failed` with a null verdict and an error naming the Stop. Against `stopRun` as it was, both timed out waiting for the child to settle. Two more press Stop while `completeTaskWithValidation` is still awaiting its diff read — on a live run, where the interrupt is what records it, and on a parked one, where the row is — and assert no validation row, no `started` file from the stub and the task still claimed; before `runStoppedBeforeCheck` each found a check started for the stopped run.

`validationQueue.test.ts` is a run closing a second task while its first is still being checked, which used to close the second unchecked — and the briefs that worked around that by closing one task per turn spent a work cycle on each close, so runs holding more tasks than cycles ended with the rest claimed. It drives the real path with a stand-in `claude`, as `validationStop.test.ts` does, because what it pins is an order of children and a row nobody reports. Its first case calls `complete_task` for two tasks together, as a model's parallel tool calls arrive, and asserts the second is queued behind the first rather than closed, that only one child runs at a time, and that `validationAtBoundary` returns only once both have settled with a `finished` verdict on each row — a null there would be a close nobody checked. Against the old door it failed on both counts: the two calls each found nothing running and started a check apiece. Its second is the operator's Stop with a claim queued, which must start no child for it and close neither task; its third is a restart that left a claim queued, which `closeQueuedValidations` must close as the run, since nothing else would ever start it. Its last two are a restart *after* the drain has taken a claim and before its check row exists — the diff read and the window scan in between — which the boot must still close as the run: the drain used to delete the queue row first, so the boot found neither row and the task stayed claimed for good, and both failed against that drain with the task `claimed`. One is a `running` run, caught by polling `startingChecks` on `setImmediate` for the tens of milliseconds the read lasts; the other is a `paused` run, the one that resumes believing the check has its task, with `runDiff` swapped for one held open on a promise so the boot lands inside the read every time. Each lets the old process's check settle before it asserts, so a child it started late cannot be counted in the next case.

Its case for checks switched off while claims wait queues two behind a check, switches `validateTaskCompletion` off and lets the first settle: both must end `done`, with no child started for either. `startQueuedCheck`'s close for a switched-off setting returned without scheduling the next drain, which no other exit does, so the first queued claim closed and the second stayed claimed by the run until a boot — a row nothing reports, and one only a second waiting claim exposes, which is why the case queues two behind the check. It failed against that code with the third task never closing.

The pick-up floor on the boundary's wait is pinned twice, because the three things the wait counts do not share a row. `stackWait.test.ts`' `and by a needs-review ending, then picked up` holds the case that matters: a check the first segment started and that is still `running` when the pick-up's first cycle ends, which must let the run reach `completed` without waiting for it — it drives the real loop because what it asserts is the run's ending and how long it took, and it fails against the old wait by never leaving `running`, since a check that does not answer is waited for eleven minutes. It then asserts the row is still `running`, so it cannot pass because the check happened to settle. `validationQueue.test.ts`' last describe is the other two parts, which a row that is still reading does not reach: a queue row with an `asked_at`, and a check whose diff is still being read, each counted by a floor at or before its request and left out by one after it. Both halves are asserted because a floor wrong the loose way is the eleven-minute hold and a floor wrong the strict way is a run ending with its own segment's verdict still to come, dropped without a word. That describe's third case is the one the first two could not reach, and it runs the real path: two claims, the second queued behind the first, the pick-up floor written to `runs.reopened_at`, then the first check settling and the drain starting the second after it. The stand-in answers `not-finished` for both (a `verdict` control file beside `answer`, absent for every other case), so a check the floor lets through is a pushback and a bought cycle rather than a quiet null, and `runDiff` is held open for the second claim so the stand-in can be told to keep reading before its child exists. It asserts the premise first, that the row's `created_at` is after the pick-up and its `asked_at` before it, then that `validationInFlight` given the floor does not count the running row, then that `validationAtBoundary` returns null inside 1.5s where a wait for that row would hold it for the eleven-minute deadline, then that a second boundary after both settled still returns null. With the wait's floor read by `created_at` again it failed on `validationInFlight` counting the row, and with only `verdictsToActOn` reverted it failed on the second boundary returning a pushback for the second task (both measured by editing the compiled files in place). Its last case is the null `asked_at` row, which a `COALESCE(asked_at, 0)` fails, as that mutation does the pure case beside `verdictsToActOn`.

`validationQueue.test.ts`' describe `a claim repeated after the run's last pick-up` is the same floor reached by a repeat, and it earned its place because `INSERT OR IGNORE` and a running row's `asked_at` both keep the first claim's time, which no case above repeats a claim to see. Three cases each repeat a claim after `runs.reopened_at` is written — one queued behind another check, one whose check is reading, one whose diff is still being read — and assert the request time moved to the pick-up or later, that `validationInFlight` given the floor now counts it, and, for the first two, that `validationAtBoundary` returns a pushback naming that task and not the one asked for before the pick-up; all three fail with the repeat left alone. The fourth keeps the move honest: a repeat in the same segment as its first claim must leave the queue row's `asked_at` and its `ahead` as they were, and it fails if the `asked_at < floor` guard is dropped, which was measured by editing the compiled file in place (the other three still pass then, so they could not catch it).
