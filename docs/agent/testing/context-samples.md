# Context samples and the live tick

[← testing index](../testing.md)

Read before adding or editing tests of the context sample series, `apiContextTokens`/`contextTokens`, `liveTickPlan`/`guardScanDue` and `ContextOccupancy`.

`contextSamples.test.ts` is the series built on top of `apiContextTokens`' reading, and it is its own file for `bootBlocks.test.ts`'s mechanical reason — it opens the database — and its own group for a different one: every failure here is a graph that draws, looks entirely plausible, and is wrong, which is a worse outcome than a blank panel. Four of its cases are the four decisions. **A small reading is recorded**, because the tick already computed the number and a store that kept only readings past some threshold would produce a series that is never empty and never wrong-looking. **An unchanged frame writes nothing**: the ticker is time-based and one tool call outlasts several ticks, so a row per tick fills the series with flat duplicates, which does not read as a bug but as a run whose context was not growing — the opposite of what the meter is for. **A sidechain and a `<synthetic>` frame do not advance the turn count**, since inflating the turn axis lands hardest on the tool-heavy runs whose growth rate is the reason to look; a fifth case pins that a turn the CLI wrote as several records sharing one `message.id` is one turn, which is the same number wrong the same invisible way. And **the byte-estimate fallback says so on the row**, because `api` and `transcript` are different currencies and a series that mixed them silently would draw a step where only the measure moved. `nextTurnIndex` gets its own four on `paybackTurns`' former grounds — arithmetic whose every wrong answer is an ordinary-looking number — and the case that carries them is the whole-file one, because a `--resume` into a fresh transcript is indistinguishable from an advance unless the scan reaching the start of a file is treated as an absolute rather than added to what came before.

A fifth decision joined those four later and is the same one read from the other end: **a tick that writes no row still records that it looked.** Deduplication is right and it is also what made the panel unreadable, because the only timestamp on the wire was the newest row's — so the case reads the same frame twice, asserts the series did not grow and asserts the read is no older than the row it declined to write. Two beside it separate `unreadable` from unchanged, which are opposite statements reaching the same field, and keep one run's reads out of another's. `contextOccupancy` gains the matching pair: the read reaches the DTO beside a series that did not move, and a run whose rows this process inherited across a restart reports no read at all rather than the previous process's. That last one is the only guard on the decision to hold this in memory instead of in a row.

`contextReading.test.ts` holds the two pure readings the series is built from, recovered from the deleted `contextPruning.test.ts` when its other cases went with the code they tested. `apiContextTokens` is what the chart draws and is silent in every direction it can be wrong: the first frame instead of the last, a sub-agent's or `<synthetic>` frame counted, or message content the API never received counted, each draws a plausible line that is not this conversation. `contextTokens` is the fallback, and counting the file rather than the messages inside it is a different quantity, not an approximation. The tail-scan cases pin the cost promise (a large transcript is not read whole to find its last turn; a tail with no turn pays for the file) and the "never throws" promise, because every caller is on the run loop's path.

`liveTickPlan` and `guardScanDue` in `orchestrator.test.ts` are pure and both directions of each are silent. A `tickMs` that ignored `CONTEXT_READ_MAX_INTERVAL_MS` puts the context panel as far behind as an operator's budget setting, showing a plausible number with a stale age and nothing naming the setting that moved it; a `guardMs` that collapsed onto the floored tick runs `buildSnapshot` — uncoalesced, the expensive half — five times as often as was asked, and costs rather than lies. The slack case is the one worth having: `setInterval` drifts, and refusing a tick a hair early pushes the budget scan a whole tick past the cadence set, compounding, so a scan at 599,900 ms of a 600,000 ms interval is due and one at 539,999 is not. Its control is the default install, where the two cadences are one and an early tick must not be skipped into a two-minute one.

`ContextOccupancy.test.tsx` is the component half and is on the file's existing argument: a chart that renders and is wrong. Its cases pin that the percentage is against the window the DTO reports and moves with it, that a run with **no window gets no meter and no rule line but keeps its figure** (a Claude run: nothing here knows its model's window, and a line at a guess reads as a limit), that a window of zero is refused rather than divided by, and that a run with no readings says so instead of drawing a zero. A second group is the age, which is the `lastCheck` decision read from the page: the age shown is the tick's, not the newest point's; a gap inside one read interval is not named; a read that found nothing is not a fresh reading; a finished run is given no age at all. A third is the caption — a fallback reading is not presented as the same measurement, an all-api series claims nothing about a fallback, a series holding the end of a longer one says which end — and the last is that the series is not sighted-only. Writing the original found a defect nothing else would have: a `<title>` whose children are an *array* renders **empty** in React, with a console warning and no other symptom.

Two more cases are folded into `format.test.ts`' existing `fmtTokens` and `fmtBytes` boundary tests, on the same grounds: a display-only figure that is well formed and slightly wrong, which nothing else would notice. A deficit under half a token printed `−0`, because the negative branch wrote the minus and recursed before the magnitude had rounded to `0`; the case pins `-0.4` and `-0.001` as `0` and the control beside them, `-0.5`, as `−1`, since a fix that dropped the sign below one token would pass the first two. `fmtBytes` chose between `9.9 KB` and `10 KB` on the unrounded value, so 10,199 bytes (9.96 KB) printed `10.0 KB` while 10,240 printed `10 KB`; the case pins 9.96 and 10 as `10 KB` and 9.94 as `9.9 KB`, the last being the control that the decimal is still kept below the rounding line, and repeats it one unit up. Both were checked failing before the change (2026-11-08).

Two more in `format.test.ts`, for `fmtUSD` and `fmtPct`, on the same ground as the `fmtTokens` pair above and found by sweeping the file for it. `fmtUSD` of a negative called `toFixed` on the signed value, which put a hyphen after the dollar sign (`$-0.50`); no caller can pass one today — every call site is a spend, a limit or a rate, and `HoldoutReadbackCard`'s difference takes `Math.abs` first — so the case is on the formatter and not on a page: it pins U+2212 before the `$`, and `-0.0001` as `−$0.0001` beside `-0.00004` as `$0.0000`, the control that a fix dropping the sign under a cent would fail. The positive figures (`$0.01`, `$0.0099`, `$1234.57`, zero) are pinned because the negative branch was rewritten around them. `fmtPct` had the same shape and the same absence of a caller: every argument at all 28 call sites outside `format.ts` is a share, a window fraction or a configured limit, and `Meter` clamps the bar it draws but prints its `fraction` through `fmtPct` unclamped, so the formatter is the one place a ratio below zero would be written. `(f * 100).toFixed(1)` on the signed value printed `-0.0%` for `-0.0004` and a hyphen for `-0.25`; the case pins `−25.0%` and `−123.4%`, `-0.0001` and `-0.0004` as `0.0%`, and `-0.0006` as `−0.1%`, the control that a fix dropping the sign under one percent would fail, plus the positives, `null` and the non-finite inputs, which the rewrite went around. The assertions that print the old behaviour were checked failing before each change (2026-11-08, the `fmtPct` ones by running the compiled `fmtPct` on the pre-change source: `-0.0%`, `-0.0%`, `-25.0%`); the positive ones, `fmtUSD(-0)` and `fmtPct(-0)` pass on both sides and are there as controls. A third, `signedUSD`, was tested here and then deleted with its test: its last caller went with the winnow panels (83ef545b) and nothing has used it since. `fmtTokens`'s negative branch and its tests stay, and say in a comment that the branch is defensive: all 38 call sites pass a count, a limit or a sum of them.
