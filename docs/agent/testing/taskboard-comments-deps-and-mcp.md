# Task comments, dependencies, the validator and the board's MCP surface

[← testing index](../testing.md)

Read before adding or editing tests of `taskComments.ts`, `taskDeps.ts`, the task dependency graph, `validation.ts`, `mintRunCapability` and `/api/mcp`.

`taskComments.test.ts` is the second table's half and earns its place on the same two grounds `tasks.test.ts` does. The author rule is the load-bearing one: `commentAuthor` is a four-line pure function and both ways of getting it wrong end as a sentence somebody acts on — a run's note recorded as the operator's is an agent's guess read as an instruction, and an operator's note carrying a run id is a thread asserting a run said something it did not, and neither throws, fails a typecheck or renders as anything but an ordinary note. It is asserted over all four actor kinds in both halves (the word, and whether an id rides beside it) and then again through the door, because a body that could name its own `author` would put the rule behind a field rather than behind the token. The body rule is the smaller half and is boundary arithmetic on a trimmed string: the cap is measured **after** the trim, so the test pins a note of exactly `MAX_TASK_COMMENT` with trailing whitespace as legal and one character over as refused, and pins that the refusal says what the cap is — a limit a caller cannot read back is one they retry against.

The three at the end reach the database, on the grounds the status effects earned one file over: none of them is in a pure function and no pure function can reach them. **A comment must not bump `tasks.updated_at`** — the board sorts on that column, so a note that touched it would reorder the board and read as a move; the row's `updated_at` is rolled back to a literal before the write rather than compared against a clock, because milliseconds are coarse enough that a same-millisecond write would pass whatever the code did. **A capped thread must lose its oldest end** — the reply reads oldest first and the cap is applied to a descending query, so a reversal dropped anywhere in that pair silently hides the note somebody wrote a minute ago, which is the only one a run acting on the thread needs; the fixture writes its own `created_at` values for the same reason, since five inserts inside one millisecond would tie and test the tiebreak instead. **A deleted task must take its thread with it** — `ON DELETE CASCADE` is inert unless `PRAGMA foreign_keys` is on, which is a connection-level setting no type checks, and a second task's surviving thread is what tells a working cascade apart from a delete that hit nothing. A fourth joined them when the run page grew a copy of the thread: **`newestCommentsForTasks` must take the newest few of each task's notes and never another task's.** It is one windowed statement standing in for a query per task, and every way it can be wrong draws a picture that reads correctly — an ascending partition hands back the oldest three, which is a plausible thread that hides the note somebody wrote a minute ago; a window without a `PARTITION BY` hands one brief the notes written against another, attributed to it and readable as an instruction about it; and an outer order taken from the window's would draw the thread backwards. The fixture writes its own `created_at` values across two interleaved tasks for the cap test's reason, and pins the two ways of asking for nothing — an empty list and a cap of zero — because neither may reach SQL at all, one building `IN ()` and the other a `LIMIT` nothing satisfies.

`taskDeps.test.ts` is the third table's half and is two pure rules plus the four the pure functions cannot reach. **The loop refusal** is the load-bearing one and is the reason a second walker was not written: a self-edge stores happily and reads back as a task waiting for itself, and a longer loop is worse and quieter — every task in it shows as blocked for ever, each pointing at the next, with no surface anywhere in a position to notice that the set as a whole can never clear. It is asserted over a self-edge, a two-node loop, a three-node loop closed through edges the new one never names, and a **diamond**, which is the half that would otherwise be missed: a walker calling any re-visit a cycle would refuse “two things, then the thing after both”, which is the most common ordering an operator draws. A repeated edge is pinned as *not* a loop for the same reason in the other direction — the primary key is what answers a repeat, and a refusal that answered it would tell a caller restating one true edge that they had made a loop out of it — and the refusal is pinned to name the loop through the caller's `describe`, because a path drawn out of four UUIDs is a sentence nobody can act on. **The blocked reading** is the feature's one derived number and is counted over every edge *before* the lists are capped: the fixture is twelve dependencies with the first ten done against a cap of ten, which is exactly the shape that reports a task ready while two things it waits on are open if the count is taken over the capped list. Beside it, `dropped` is pinned as still blocking — reading it as satisfied would mark a dependent ready on the strength of work nobody did — and the cap's direction is pinned too, since a clipped list of finished dependencies beside a non-zero count names nothing a reader can act on.

The four at the end reach the database, on the grounds `tasks.test.ts` and `taskComments.test.ts` earned. **A repeated write must be idempotent and must say it was already there** — the primary key makes the insert harmless, but a caller told nothing cannot tell “I drew this” from “this was already drawn”, which is the distinction a model retrying a tool call is acting on. **An edge must not move either task** — `updated_at`'s rule again, rolled back to a literal before the write for the same reason, and asserted on both ends because the write touches two rows and only one of them is the obvious one. **A deleted task must take its edges both ways** — the two columns are two separate foreign keys, so a table declared with one of them would leave half the edges standing as orderings pointing at nothing, and a bystander's surviving edge is what tells a working cascade from a delete that hit nothing. **A remove that found nothing must be `missing`** — the asymmetry with a repeated add, and the one a surface acts on: a board told “done” would redraw itself as though the press had landed on a row that had already changed underneath it.

`taskDepGraph.test.ts` is what the dependency graph on a task's page is a picture of, and it is this suite's bar in its purest form: every failure here draws a plausible picture rather than an obviously wrong one. An arrow the wrong way round is a readable graph of the opposite ordering; a second level expanded the wrong way pulls in every task that happens to share a dependency and reads as a neighbourhood; an edge kept to a node nobody drew is an arrow into empty space, and one dropped between two nodes that *are* drawn says they are unrelated — none of it throws, none of it fails a typecheck, and the operator is looking at an ordering they believe somebody wrote down. Nothing here reaches the database or an environment, since the builder is a total function of one task and the neighbourhoods its caller already read, which is why it lives in `src/lib` rather than beside the component.

`validation.test.ts` covers the four pure decisions the external validator is made of, and it is the one feature here where a model's opinion can spend money with nobody pressing anything — so the four are covered together and each fails silently in a *different* direction. `parseVerdict` decides whether there is a verdict at all, and no verdict closes the task: too strict and the feature switches itself off on exactly the runs whose replies are longest, too loose and a verdict is read out of whatever a diff persuaded the model to write, which is why the last fenced block is taken rather than the first and why an unknown value is null rather than coerced. `grantsAnotherCycle` is the whole of the terminus — wrong one way and the agent's word is the last word again, wrong the other and `maxIterations` no longer ends a run — so the cases pin the ceiling, the overshoot past it, and zero as an off switch rather than as "unlimited", which is the reading that would turn the operator's most cautious setting into the least. `validationSkipReason` has to fail **open** in every branch, because a branch that refused instead of closing would turn a shortage of assist slots into a task nobody can close. And `buildValidationPrompt` carries the one prohibition no type can hold: the judge is never told the run claims to be finished — `LLM-as-a-Judge`'s agreement bias is directional, the trigger for the whole path *is* a claim of completion, and the way this regresses is somebody adding it back as helpful context, so five phrasings of it are asserted against by name.

`mintRunCapability` in `chat.test.ts` pins the life of the credential a work cycle carries, asserted through `subjectForCapability` because that is what the route asks. A token that is not revoked is a live write path into this app's database sitting in a map after the run has finished, and nothing reports it — the tools go on working, which is the problem. A token that is not stable across cycles fails the other way and looks like nothing at all: the set the constant-time scan walks would grow with the *length* of a run rather than with the number of live agents, and nothing but a run ending sweeps it. Two runs are asserted separately in both directions, since one credential shared would be a work cycle able to complete the task another run holds and a sweep keyed on the wrong field would disarm both.

`src/app/api/mcp/route.test.ts` pins what a work cycle may read of the board through `get_my_task`, on the wire rather than beside `taskVisibleToRun`, because the run id the scope is keyed on is the capability token's and a test of the predicate alone could not see a handler that took it off the call. Every way of widening that scope is silent — a run handed another project's brief, or the brief another run is working from, reads it as the truth about its own work — so the cases are its edges: a held brief longer than the list's clip comes back whole while `list_my_tasks` still reports `bodyClipped`; an open task in the run's own folder reads; another folder's task, another run's claimed and done ones and an id on no row are refused in **one** sentence once the id is taken out, since a refusal that told "not yours" from "not there" is a probe of the board; a token whose run row has gone reads only what it holds; and the tool lists of all three subjects are pinned, because the gate in `callTool` is a membership test against the same `toolsFor`, so a tool on the wrong list is reachable and not merely visible. Loading the route took its `@/lib/` imports becoming relative, `health/route.ts`' move. All six cases were checked failing against the tree before the tool existed.
