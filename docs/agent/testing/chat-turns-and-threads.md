# Chat turns, threads and the request helpers

[← testing index](../testing.md)

Read before adding or editing tests of `chat.ts`' turn claim, `settleOnExit`, `chatStream.ts`, `chatThread.ts`, `/api/chat/[id]`, and `jsonRequest.ts`/`chatRequest`.

Three of the entries on the list of what `npm test` covers are not pure functions, and each earns the exception on its own terms.

`settleOnExit` spawns a real child, which is what the fault requires: an inherited pipe held open past the exit is the entire mechanism, and a stubbed emitter would only pin the wiring back to whatever it was written against.

`sendChatMessage`'s claim on a chat is the second, driven against a temporary database with `spawn` replaced by a counter — what it decides is not a value but whether a second billed child joins a conversation that already has one, and the only assertion that says so is the number of children.

`jsonRequest` is the third, and it is the one that makes the request: what it pins is that it *returns*, whatever happens, because an unguarded `fetch` rejecting out of a handler reports nothing at all — the chat page's flag disabling the composer, Approve, Reject and Select-all stayed set with no way back but a reload; the branches page's Land, Purge and Delete re-enabled their button and left the table exactly as it was, which is what a press that did nothing also looks like; and the land card's poll went on rendering a conflict resolution as in flight long after it had finished.

The status it carries is the other half — `null` is nobody answered and a number is somebody refused, which is the split between `pollFailureMessage` on a poll and `actionFailureMessage` beside a press that may or may not have landed.

`chatRequest` is a caller of it and keeps its own test, because the chat page reads a thread off the answer and that shape is its own.

The first of the twenty that open the database, `src/app/api/chat/[id]/route.test.ts`, names a throwaway `DATA_DIR` and calls the handler, because what it pins is a *payload key*: the chat page polls that one route, so a list left out of its answer is frozen on screen until a reload, which is exactly what it did for as long as a comment claimed otherwise.

The second, `chatOrder.test.ts`, is in the SQL itself: a thread ordered by a random UUID puts a denial note above the reply it is a footnote to, which reverses what the operator is being told.

The third, `chatTurn.test.ts`, drives `sendChatMessage` through a failed pre-spawn setup, because what it pins is a *state transition* rather than a return value (a chat thread stranded at `thinking` for ever by one failed `writeFileSync`, unusable until the server restarts).

Its other two cases are one gate along and pin the transition that must *not* happen: an approval clicked while the install ceiling is up refuses the click and decides nothing, because `failed` on a proposal is terminal and the condition that caused it clears on its own — so the obvious behaviour, marking the proposal and telling the operator exactly why, is the one that destroys the work, and it does it a batch at a time.

Its control is half of that and is the direction the repair breaks in: a folder nobody mounted must still burn the proposal, since "a refusal must not decide a proposal" applied to every refusal leaves work that can never start pending for ever, offered again at every reload.

Its fourth case is the first one's shape at the other end of a turn, and is the first of the two in the file that replace `spawn` — with two children it closes by hand, because *which* child exits and when relative to the other one is the whole fault: `endTurn` returns while the child it signalled has eight seconds of ladder left, `failed` is what invites the retry, and a `finishTurn` latched on status alone let the stopped turn's child settle the turn that replaced it, adopt its cost and session id, and open the one-billed-child guard on a live child nothing was watching any more — every step a successful write, on a page that looks right. Its control is the direction *that* repair breaks in and is asserted in the same case: the live turn must still settle, since a latch matching nothing strands every turn at `thinking`. The replacement is installed and restored around that one `describe` rather than in `before`, because a fake `claude` standing in for the missing one would make the approval cases above pass for a reason they are not testing.

Its fifth case is the same file's third ending, and what it pins is an *absence* nothing else can see: `reconcileChatsOnBoot` wrote `failed` and an explanation onto a column `claimTurn` clears in the same statement that takes the next turn, so the operator's retry — the first thing they do — erased the only record that a turn had died, and the thread read afterwards as their question followed by their next one with no reply and no note between them. Both halves are asserted because either alone passes on the broken code's successor: the system line after the boot, and the same line still there once the retry has cleared the row. Its control is what the boot may not touch — a thread with nothing in flight gets no message — and it is the second case here to replace `spawn`, because a real `spawn` of the missing `claude` emits `error` on a `process.nextTick` that is drained ahead of the `await`, which would settle the row before the assertion on what the claim wrote could read it.

Its sixth case is one gate earlier and pins a *promise* rather than an ending: an untemplated card spells its guards out, so the values on it and the values the run starts under have to be one value, and both used to be re-derived from `chatGuards()` — the label on every poll, the run again at the click — which let an edit to `chatDefaultGuards` in between start a run under a set no card had ever shown, silently and in every field at once. It is end to end rather than a case beside `proposalGuards` in the pure suite because what it pins is that a *column* reaches both readers: the label the route serves, asserted twice so that a card re-derived after the edit fails here rather than at the click, and the budget blob on the row the approval wrote. Its control is a proposal whose snapshot is nulled by hand — every one already pending when the column arrived — which must still start under today's defaults, because refusing those is worse than the drift: the work is gone and getting it back is a billed turn. What it deliberately does not assert is the run's `isolation`, which degrades to `none` for this fixture's folder whichever way the flag was set; the isolation choice is asserted in the words on the card instead.

Its seventh case is what a resumed turn is charged, and its pure half is `turnCostOf` in `chat.test.ts`. The pinned CLI's `total_cost_usd` is the session's running total, so three $0.25 turns on one resumed session report 0.25, 0.5 and 0.75, and banking each as printed put $1.50 into `chat_turn_spend` — the table the install's ceiling sums — for $0.75 of work, with nothing throwing and the thread merely looking expensive. The case drives three turns through fake children and asserts the premise (turns two and three carry `--resume`), the three rows, the thread's total, and `installSpend`'s two figures as a difference, since the window is install-wide. `turnCostOf`'s own cases pin the three fallbacks to the whole figure — no earlier report, a changed session id, a total that went down — because each is where a subtraction would charge a real turn nothing.

`chatStream.test.ts` covers a reader whose every failure is silent in one direction: a turn that produced *less* than it did. Text folded from the wrong field is an empty half-answer, usage read from the wrong key is a ceiling that never sees the money, and an event type with no branch is a CLI rename that makes every turn look thinner rather than making one fail — which is the case with a precedent in this repository, since `orchestrator.ts`'s Claude parser has four branches and no fifth. Three of the ten are about the *kind* of number: usage is summed across requests rather than last-write-wins, because each API request bills its own input and its own cache reads; an unplaced model is priced at the fallback rate rather than at nothing, which is `guardCostOf`'s whole reason; and a 1h cache write is told from a 5m one whenever the breakdown is there, since reading the flat field under-charges the guard by a third. A delegated turn is kept out of the transcript for the run loop's reason, and a line that is not JSON at all is counted and then survived, because one bad line must not cost the rest of the turn. Three more cover the `<synthetic>` latch, which fails silently in the same direction the rest of the file does — a refusal not recognised leaves a dead turn reporting "produced no readable output (exit 1)" with the cause sitting unread in the stream. The first refusal is kept rather than the last, because the CLI retries and the retry that gives up prints something shorter than the one that said what went wrong; it stays in the turn's text as well, since the operator watching a stall is owed the sentence while it is still going; and an ordinary model quoting an error out of a log is not one, which is the direction that would fail a working turn. One of the ten is about a type this parser deliberately claims and deliberately does not read. `tool_progress` used to land on `unknownTypes`, which put a `chat.stream_unread` on every turn whose tool ran longer than the roughly 30 seconds between frames — the same failure `rate_limit_event` had, on slow turns instead of on every turn. The assertion that pinned that divergence is kept and turned round rather than deleted, so a future chat tool strip has to come back through this file: it now asserts both that the type is claimed and that the event moves *nothing* in the accumulator, since `handleStreamLine` folds the same event into the run page's live tool strip and a reader added here without a strip to draw it would be inventing a live-only field with no reader.

The durability half is driven against the database instead, in `chat.test.ts`, because what it pins is what a *boot* finds. A stranded turn's half-answer has to come back as an assistant message with the restart note **after** it, its measured tokens have to join the thread's count, its estimated cost has to land in `cost_usd_est` and not in `cost_usd`, and it has to leave a `chat_turn_spend` row marked `estimated` — the row being the only thing that tells the install's rolling ceiling the money went, and the mark being what keeps a derived figure out of the measured half of that reading. The second case is the opposite direction and matters as much: a turn killed before its first event must write **no** row and append **no** message, because a zero-cost row is a spend record for money nobody spent and an empty assistant message is an answer that was never given.

`installSpend.test.ts` gained the two readings that follow from it: an estimated row counts against `spentGuardUSD` and never `spentUSD`, and a turn that is spending *right now* is visible at all — the ceiling used to be read once, at admission, so a turn admitted at 99% ran for ten minutes past it. The second case also asserts the settle, because counting a row and its own live estimate together would charge the turn twice for as long as it stayed in the window.

`chatThread.test.ts` gained five over `mergeMessages`, on the grounds the two functions beside it earned: the chat page's poll now asks for the messages past the highest `seq` it holds, so what comes back is a tail and the page has to put the conversation back together — and every way of getting that wrong renders a transcript rather than an error. A dropped tail is a paragraph missing from the middle of a conversation with nothing on the page to say so; a kept duplicate is the model appearing to have answered twice. The cases pin the append, the replace a `messagesFrom` of zero has to mean, the overlap two polls on one cursor produce (the interval fires whether or not the last request has answered), the reference-identical array a poll that added nothing has to hand back, and the row itself: the same single message arriving onto a thread of ten and a thread of a thousand is the same merge.

`src/app/api/chat/[id]/route.test.ts` gained the server half of that, three tests that fail with the cursor removed and one that pins the boundary. The claim is stated as work rather than as time on purpose — a timing would measure the machine — so the poll after a cursor is asserted to carry exactly the message that arrived, at twenty messages and at two hundred, and the `EXPLAIN QUERY PLAN` for the cursored read is asserted to name `idx_chat_messages_seq` and to build no temp B-tree. That last one is the only test in this suite that reads a query plan, and it is here because the index is what makes the cursor a bound rather than a filter: without it SQLite answers `seq > ?` by visiting every row of the thread, the response is small, the work is not, and every other assertion in the file stays green. The fourth pins that a `?after=` the page could not have sent — empty, negative, fractional, not a number — is read as no cursor and answers with the thread, because the poll is what keeps "Thinking…" from standing for ever and a 400 there would freeze the page rather than report anything.
