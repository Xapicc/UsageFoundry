# Projects: Push, fetch and the inventory

[← testing index](../testing.md)

Read before adding or editing tests of `projects.ts`, its push and fetch routes and the chat's `list_projects` and `get_usage`: `planPush`, `pushProject`, `fetchProject` and `projectInventory`. Split out of [Deliver, and Push of the operator's branch](delivery.md), which holds the other door that sends with a token.

`projects.test.ts` is `planPush`, the decision in front of the git call that sends the operator's own branch to a remote, and it earns its place because every wrong answer is silent: a push that should have been refused succeeds, or fails at the remote over something else, and the button and the endpoint disagree with nothing saying so. Each refusal is pinned against a pushable baseline, and so is the order between refusals that can hold at once — moved before everything about a state the operator was not shown, an operation before the detached HEAD it leaves, the standing refusals before busy, behind before nothing-to-push — because each sentence assumes the ones above it did not fire. A repository whose `UF_GITHUB_TOKENS` entry gives it none must refuse naming the entry rather than take the install's token; a `pushurl` elsewhere must refuse Push while Fetch still goes, since the push URL is where the credential travels; and every URL form that reaches GitHub by a transport running a program the repository can name — scp and `ssh://` before the rewrite, a slash-spelled local path, `http://`, a host before an `@` — must refuse both, as must a second push URL. The remote's own answer is pinned apart (gone, moved past what was fetched, already there) and only after every refusal that needs no remote, and a run's branch is refused before its upstream is looked at. A refused URL's sentence must not carry the credentials written into it, and that includes a password with an unencoded `@`: `redactUrl` takes the userinfo to the last `@` of the authority, as git and curl do. Measured on 2026-10-25, before the fix, `https://user:p@ss@gitlab.example/o/r.git` came out as `https://ss@gitlab.example/o/r.git`; an `@` after the first `/`, `?` or `#` must stay. `planFetch` is pinned not to refuse on what only a push writes past. `delivery.test.ts` pins the four URL shapes `parseRemote` once read as GitHub and git takes elsewhere. `parseBranchStatus` is there for `parseStatusZ`'s reason — a rename's source path left in the stream counts twice — and `selectBranchReads` and `selectProjectPage` for `selectProbeTargets`' and `selectBranchCandidates`': a selection that starves a project or reaches past the cap is a wrong number with nothing red.

`projectPush.test.ts` drives `pushProject`, `fetchProject` and `projectInventory` against real repositories, because what it pins is what reaches a remote. Every remote is a genuine `https://github.com/acme/<name>.git`, and git's https transport is replaced for the process: `GIT_EXEC_PATH` names a copy of git's exec directory whose `git-remote-https` answers the remote-helper protocol with `connect` and hands the connection to a local bare repository, so nothing reaches GitHub, no credential is asked for, and the URL the decision reads is the real shape. Every other way of pointing a GitHub-looking URL at a local path is one the push check refuses, which is why it is done this way; each scene asserts the URL and that its first push reached the bare repository. The process's own `GIT_*`, `GH_*` and `GITHUB_*` variables are deleted before the first import and global config is `/dev/null`, because an agent's shell carries a real token and URL rewrites. A fast-forward must land the sha shown and nothing else — not an untracked file, not an annotated tag under `push.followTags` — with `.git/config` byte-identical and the tracking ref moved. Behind after a fetch, HEAD moved, another branch at the same sha, mid-merge, a held `landing` claim and a `pushurl` elsewhere must each refuse with the remote's `main` unmoved, and the claimed checkout must push once the claim is let go. So must a branch deleted on the remote (not created again), a remote that moved with nothing fetched, a second `remote.origin.url` (neither remote written), and a checked-out `uf/` branch with an upstream; a hidden folder holding a `.git` is a 404 to both presses. A malformed body is a 400 through the route with nothing pushed. The inventory must list a folder whose `.git` names a missing directory with git's error, split a run's branch from a hand-made one, leave out a squash-landed run branch until the squash is reset away, read the upstream of a branch with no commits and let it fetch, and never put the credentials a URL was written with on the wire; a branch with no upstream is refused by both presses with none written. Removing `--no-follow-tags`, the squash exclusion, the reset of the press's own claim, the `--push` URL read, the remote's answer, the `--all`, the `uf/` rule, the listed-folder test or the redaction from the compiled module each failed a case on 2026-10-16.

`src/app/api/mcp/route.test.ts` has one case for `list_projects`, the chat's read of the same inventory, and it is on the wire beside the other read tools rather than here beside `projectInventory` because the defect it closes is the handler: the chat and `/projects` are worked side by side, and a handler that read git its own way, paged differently or dropped the paging arguments would still return something plausible, which is two answers to "what is unmerged" and "what would a push send" with nothing saying which is wrong. It builds one repository with a branch not merged into `main` inside that file's workspace mount, and asserts the tool's answer equals `projectInventory()`'s — whole, then for one `offset`/`limit` pair — that the row names the mount id `propose_run` takes and lists the unmerged branch, that the description still says ahead and behind are as of the last fetch, and that neither a block nor a run is offered the tool or let through the gate. Mutation-checked 2026-10-16 on the compiled route: a handler passing `limit: 0` fails the paged equality (`limit: 60` against `1`).

`src/app/api/mcp/route.test.ts` has one case for `get_usage`, the chat's read of the usage windows, and it is on the wire for the same reason as `list_projects`' because the claim is about what the tool *returns*: the reply is built by `usageReport()`'s local `window()` mapping, which is not exported, and it was the one place that read only `snapshot.projectedExhaustionAt` and so offered an instant with no owner. The case writes two $15 Sonnet turns into a scratch `CLAUDE_HOME` (three hours and twenty minutes old, so $15/h of burn), gives only the week a $100 ceiling with `planUsageFromApi` off, and asserts that `weekly.projectedExhaustionAt` is 4h40m out, that `session.projectedExhaustionAt` is null, that the top-level field equals the week's, and that the tool description says the top-level one is "the earlier of the two". It asserts the spend (`$30.00`, `$15.00`/h) first, because a snapshot over no transcripts would make every null true for the wrong reason. Fail-first: with the new per-window property deleted from the compiled route the case fails with "got undefined". The arithmetic itself is `windows.test.ts`'s ("projected exhaustion"), not this case's.
