# Chat proposals: what the doors refuse

[← testing index](../testing.md)

Read before adding or editing tests of what a chat door refuses before it writes anything: a prompt, name, model or other field that is not the type `String()` used to coerce it to, a `propose_workflow` block, name or `loop` the click would refuse, a question's answer, a `continueBranch` and the fraction guard an approval cannot read. Split out of [chat-proposals.md](chat-proposals.md) on 2026-11-09, when that file reached 21,061 bytes; every paragraph from the first of the `String()` sweep on moved unchanged, so "the sweep" and "the ones above" in them still point at paragraphs in this file.

A prompt that is not text is refused at every door that read it through `String()`, and one case each pins that nothing was written. In `route.test.ts`, `save_template` with an object, array or number `prompt` saves no `run_templates` row and `propose_run` with a non-string `promptOverride` writes no `chat_proposals` row, both naming the field (`"prompt" has to be a string when it is given`) where the row used to read `[object Object]`, and a string still saves and proposes. `normalizeAgentInput` refuses a non-string `prompt` by name and still reads `null` and a missing one as the empty prompt it always refused; `parseRunAgent`, which is total, reads a stored non-string prompt as no agent. `normalizeWorkflowInput` refuses a run or orchestrator block's non-string `promptOverride` naming the block, and a merge block, which drops the field unread, is not refused for it. All were checked failing with the source changes reverted.

The same refusal stands in front of every other chat-proposal argument that `String()` used to read through, and the cases sit beside the ones above in `route.test.ts` and `workflows.test.ts`. `propose_workflow` refuses a non-string `summary` (the card's task text), `supersedes` (a list-wrapped label decided the card it named as replaced) and, per block, `id`, `kind` and `name`, and per `dependsOn` entry `id` and `edge`, each naming the field and, for a nested one, the block and entry; `propose_schedule` refuses `workflowId`, `kind` and `supersedes`, and `time` and `weekday` only for the kinds that read them; `propose_run` refuses a `dependsOn` entry's `id` and `edge`; and `planEmission` refuses the same two on an emitted run's `dependsOn`. Each case asserts that no `chat_proposals` row was written and that the card a wrapped `supersedes` named is still pending, and a string and a `null` still propose. Each of the three tests was checked failing with the source changes reverted. `normalizeWorkflowInput` carries it to every block field `normalizeNode` still read through `String()`, in four cases beside the one for a block's `id` and `kind`: a run or orchestrator block's `mountId`, `folder`, `templateId`, `agentId` and `provider`; a merge block's `mergeStrategy`, and its `agentId` and `provider`, which it reads to refuse by name; each `bodyNodeIds` entry; and a board condition's `mountId`, `folder`, each status and each threshold's `priority`. `["work"]` was the workspace `work`, and `mountId`, `folder` and `agentId` decide where a billed run starts and as whom. Each refusal names the block and the field, a nested one by its path (`stopWhenTasks.statuses[0]`); absent and `null` keep their meaning — no folder is the mount root, no template the guards in Settings — and a merge block is not refused for the workspace, folder or template it drops unread. All four were checked failing with the source change reverted. The numbers read through `Number()` get the same refusal in three more cases beside them: an orchestrator block's `fanOut`, a review block's `fixRounds`, a loop's `maxPasses` and `maxLoopCostUSD`, and a threshold's `atMost` each refuse a list, an object or a boolean as `“Name”: "<field>" has to be a number when it is given; got …` (`stopWhenTasks.thresholds[0].atMost` for the nested one). `Number(["3"])` is 3 and `Number(true)` is 1, so `fixRounds: true` saved as one billed fix round per rejected branch, and `[]` and `false`, which are 0, passed as a legal fix-round count, a spending cap that is off, and the strictest threshold there is. A numeric string is still read as the number, because the refusal is about the type and a form field holds a string; the second case pins that, and that absent, `null` and blank keep their meaning (no fix rounds is 0, no spending cap is off, a blank threshold is still refused by name). The third pins that a block is asked only for what it reads: a merge block drops `fanOut` unread, only a loop reads `maxPasses`, and a value that would be refused where it is read is saved as `null` where it is dropped. Only the first of the three fails without the change, and was checked doing so; the other two pass either side by design, as pins on the readings the change must not move.

The same refusal stands one layer down, in the normalizers other doors share, because the chat's check in front of them is not in front of the workflow save and validate routes. `workflows.test.ts` has one case each: `planEmission` refuses an emitted run's `id`, `title`, `task`, `folder` and `agent` as `Run N: "<field>" has to be a string…` (an object `task` was a billed run briefed with `[object Object]`, and `agent: ["reviewer"]` was the agent inside the list); `normalizeWorkflowInput` refuses a block's `id` (`Block N: …`) and `kind`, a loop's six not-told fields (`“Name”: …` — an empty list had read as blank, so as told nothing, and an object was refused in the sentence for a loop that had been given a task), and a link's `from`, `to` and `edge` (`Link N: …`). Each asserts that `null` and absent keep their meaning: a missing kind is still `run`, a folder of `""` is still the mount root, and a missing id or condition is refused for being missing. All four were checked failing with the source changes reverted (4 of 349 in the file, the rest passing).

`route.test.ts` has one case for `propose_workflow` refusing a block of kind `deliver`: the kind is the one `normalizeWorkflowInput` accepts from the editor and the tool must not, so nothing downstream would catch it, and a card for it would read "no agent" over a step that pushes branches and opens pull requests. The case asserts the refusal names the block and the editor, and that no card was written. A second case refuses a review block whose `verdictSource` is a verify command, which only a person may save because it is a program this app runs in every branch's checkout with nobody looking: it asserts the refusal names the block and the editor, that a `" command "` spelling the normalizer reads as a command is refused as one, that no card was written either time, and that the same block judging by run status is a card — so the refusal is about the command and nothing else. `workflows.test.ts` has the same refusal at `planWorkflowProposal`, the click that saves what a model wrote. Both were checked failing against the tree before the command verdict existed.

`route.test.ts` refuses a `propose_workflow` name the click would refuse, because the click's refusal is terminal: a card `createWorkflow` fails on `idx_workflows_name` is `failed` for good. The case pins a saved workflow's name sent in upper case and a waiting card's sent in lower case, each refused naming the holder's id and writing no card; a `supersedes` replacement keeping its own name still proposes; and `été`/`ÉtÉ` both propose, because `COLLATE NOCASE` folds ASCII capitals only and a wider fold refuses a name the index saves — a `toLowerCase()` fold was checked failing there. The case was checked failing on the tree before the refusal.

A third `propose_workflow` case refuses a `loop` block, a `repeats` link out of an ordinary block, and a kind outside the tool's enum, each by name and none writing a card, with the same graph minus the loop still a card. Nothing downstream would catch any of them: `normalizeWorkflowInput` saves a loop from the editor, and the card sums `fanOut`, so a 10-pass loop round a fan-out of 4 was approved as "up to 4 runs" over a worst case of 50. The case was checked failing on the tree before the refusal.

`settleQuestions` refuses an answer to a question asked without `allow_text` that is not exactly one of `questionChoices(row)`, and `chat.test.ts` pins it twice. The pure case earns its place on the questions' shared ground — it fails as a *question* rather than as an error: free text settled against a pick-one is a reply the model never offered, quoted back to it as the operator's answer, and nothing on the page could tell. It also pins the two directions beside the refusal: a listed choice still settles, and an unreadable list is no choices, so that question is unanswerable rather than open to anything. The database case drives `answerChatQuestions` with `spawn` counted, because what the refusal saves is a billed turn: the typed answer must start no child, write no message and leave the row pending, and the offered choice, sent padded, must then settle it in one turn. Both failed on the old function with `ok: true`.

The sweep's last text field is `model`, pinned at every door that read it through `String()`. `route.test.ts` has `propose_run` and `save_template` refuse a list-wrapped or object `model` by name and write no card and no template — `["<id>"]` was the enabled model inside it and `{…}` the model `[object Object]`, which on a Codex card, whose list is empty by default and so refuses nothing, was a card that spawns `codex exec -m "[object Object]"` — and a string still proposes. `templates.test.ts` refuses the same two shapes at `normalizeTemplateInput` for `mountId`, `folder`, `agentId` and `model` (a template saved with `folder: {path: …}` stored the folder `[object Object]`, and `["a1"]` was the agent inside it), and `agents.test.ts` at `normalizeAgentInput` for `model`, which reaches `--agents`. The same route case carries the board's `create_task` folder and `release_task` reason, recorded in `taskboard-comments-deps-and-mcp.md`. All three were checked failing before the change, and the route case's `save_template` door again with only its own source change reverted.

`route.test.ts` pins that `propose_run`'s `continueBranch` check reads an untemplated predecessor's isolation off the set its card froze, as `approveProposal` does, and not off today's `chatDefaultGuards`. Card A is written while the default isolates and card C while it does not, the default is switched before each successor, and B carrying A's branch on is accepted while D carrying C's is refused naming `"pc"`. Read live, both answers were wrong and neither threw: a chain the click would start was refused with a sentence telling the model to ask the operator to change a default, and a card was let through that `admitDependencies` refuses at the click, failing it for good, so the model has to re-propose it in a billed turn. It was checked failing before the change in both directions — B refused, and, with B's assertion skipped, D accepted.

`src/app/api/chat/[id]/proposals/route.test.ts` pins that an approval refuses a fraction guard with nothing to read, and it is route-level because the gap was between the route, which fetches the readings, and `approveRunBatch`, which judges with them: a unit test of either half passes with the other missing. Before it, a card whose frozen guards or template held `maxWeeklyFraction` became a run whose guard was recorded and never read (measured 2026-11-09, `docs/verification/budgets-and-guards.md`). Its cases: a frozen weekly, a frozen session and a templated budget, each a 400 with the proposal still `pending` and no run row; the same card starting on the next click once a reading exists, which is what refusing without `failed` buys; a mixed click refused whole; a Codex card beside a Claude reading; and a plain approval and a reject, to stop the refusal being widened. Six of eight failed on the old door, and forcing `guardWindowsOf` to `claude` fails the Codex case alone. The fleet is paused so a regression is held in `waiting` rather than spawned.
