# The git this app runs

[← testing index](../testing.md)

Read before adding or editing tests of `git.ts` or `runTrailers.ts`; `gitFilterProbe.test.ts`'s are in [The filter probe in front of this app's git](git-filter-probe.md).

`git.ts`'s are what every git call this app makes carries: a missing `-c` is a repository-controlled hook run by this server's own git child, with no permission mode and no line in `run_events`, and a variable that survives the scrub is that hook handed `DATA_DIR`.

`git.test.ts`'s `GIT_OPTIONAL_LOCKS` cases are a land refused for no reason of its own. `git status` refreshes the index and takes `index.lock` to write it back, and this app runs `status` in the operator's checkout from the poll behind every Land card, so a merge starting at that moment was refused by git with `Unable to create '…/index.lock': File exists`, and the lock was gone by the time anyone looked. One case asserts `gitEnv()` carries the variable and `agentEnvironment()` does not, since set there it would reach every agent. The other is a real repository with a stat-dirty file, a `status` through `git()` and the index's bytes compared, because a git that ignored the variable would pass the first; its control is a plain `status` rewriting the same index, without which a fixture that was not dirty would measure nothing. Before the change both failed. On 2.39 `git diff` against the working tree rewrites the index whatever the variable says, measured, which is why `gitEnv`'s comment requires every diff here to be between commits.

`git.test.ts`'s inode case is the cost of that same variable. A `status` that writes nothing back re-hashes every stat-dirty entry on every read, and after the Docker VM reboots OrbStack's virtiofs hands every checkout new inode numbers, so every entry of every idle slot's index was stat-dirty: one Branches page load hashed ~7 GB and took 17–22 s (measured 2026-11-08). `gitArgs` now carries `core.checkStat=minimal`. The case replaces a committed file with a copy, so the inode changes and the times and size don't, and asserts `diff-files` through `git()` lists nothing. `diff-files` is used because it decides by stat alone, where `status` would hash the file and find it clean either way. The file's times are set to 2001 before the commit so the entry is not racily clean, and the repository sets `core.trustctime=false` because the replacement moves the ctime, which virtiofs did not. Its control is a plain `diff-files` listing the file. Before the change it failed with `actual: 'f.txt'`.

`git.test.ts`'s planted-`.git` cases are the privilege-separation half: a work cycle writes the repository's real common `.git`, so `commit.gpgSign=true` with a `gpg.program`, or a `filter.<x>.clean`/`smudge` named from `.git/info/attributes`, makes this server's own git child run a program the run chose — on the next run's `worktree add`, on commitPending's `add`/`commit`, on the Land press — outside the permission model and with no line in `run_events` (board task `9f3f9226`). One case per plant drives `git()` through `commit`, `add -A`, `worktree add` and a stat-dirty working-tree `diff --name-only` (`conflictedFiles`' shape) and asserts the marker the planted program would write never appears, with a dotted-driver-name case because git preserves a filter subsection's case and the override must match it. The control plants the same clean filter and runs it under plain git, so a `-c` that stopped carrying its pin fails the suite rather than passing silently; before the fix every plant ran and the control still passed. `before` strips `GIT_*` from the process so only `gitArgs`/`gitEnv` and the repository's `.git/config` decide, which is why an inherited `GIT_CONFIG_*` cannot outrank the plant and quietly stop the control firing.

`git.test.ts`'s config-hook cases are the same plant for git 2.54's hooks defined in config, which `core.hooksPath=/dev/null` does not reach (board task `6b4dccf3`, `security/server-git.md`). Each writes `hook.<name>.command` and `.event` and drives `git()` through a call that fires the event: `commit` through `git()` and `gitSync()`, `update-ref` and `branch -D` with `reference-transaction`, `push` with `pre-push`, and names `a.b`, `MiXed`, `sp ace` and `a=b` because git keeps a subsection verbatim and splits a `-c` at its first `=`. Two more plant the hook in a second git that this app's git starts: a `commit` whose automatic maintenance runs `gc --auto` (`maintenance.strategy=gc` and two packs against `gc.autoPackLimit=1`), and a `push` that `push.recurseSubmodules=on-demand` sends into a submodule whose own config defines `pre-push`. The second also asserts the submodule's remote got nothing, since that push goes to a remote no door checks. All six failed with the marker present before the change, on Apple git 2.54.0. A git that reads no `hook.*` key cannot run a plant at all, so the cases skip there rather than pass having measured nothing; the control that decides it is a plain-git commit in `before`, and the last case asserts each plant fires under plain git. On the image's 2.39.5 they skip, so the gate is pinned separately in `gitFilterProbe.test.ts`, where a probe that fails is how being asked shows on any git: `branch -D`, `update-ref`, `fetch`, `push`, `remote rename` and an unmeasured `tag` must fail closed, which the first four did not when the gate listed only content subcommands, and `commit-tree` and `check-ignore` behind a leading `-c` pair, bare `remote` and `remote get-url` must not ask, since a gate reading `args[0]` takes `-c` for the subcommand. Nor must the `--git-dir=<dir> config --list` listing `readGitDir` makes, which paid the whole probe and failed with it; `add -A` behind a `--git-dir=` naming another repository than `cwd`'s must be probed in the named one, whose plant ran while the probe read `cwd`'s, and must still fail closed (board task `507d7792`).

`git.test.ts`'s `GIT_BIN` case plants a `git` first on `PATH` and asserts `gitSync` did not run it. The default was the bare name, and this server's `PATH` then started with the stacks' `bin/` and the agent-owned `/home/node/pytools/bin`, so whatever `git` was first there answered every diff, worktree and landing — as root wherever the uid split is off. Root's `PATH` no longer carries either (board task `aff25da4`); the case stays because the path is what keeps git from depending on that. Nothing about that is visible: a planted `git` that forwards to the real one passes every other test in the suite. Skipped when `GIT_BIN` is set, because the default is then not what runs.

`runTrailers.test.ts` and `runTrailersCycle.test.ts` are the commit trailers (`isolation-and-landing/commit-trailers.md`), and every way they fail is silent: a run that completes and a branch that lands with commits as anonymous as before, a model id that forges a second trailer, an author moved by a rewrite, or a commit the target already has re-made. The first file runs `stampBranchCommits` against real repositories and asserts what must not change as hard as what must: tree, author, committer and dates identical, the operator's branch where it was, a second pass moving nothing, a merge of the target into the branch keeping the target's own commit as its second parent, a tip an earlier run landed and everything under it left as it was, another run's stamped commit left alone with the ones above it stamped, and a commit with an `encoding` header stopping the whole stamp with the branch unmoved. With the target left out of the `rev-list` five of its twenty cases fail. The second drives a real run through `createRun` with a stub agent that commits in its working directory (`cutOffCheckout.test.ts`'s harness), because the stamp is one call in the run loop and a test of the module cannot see it missing: removing the call fails the isolated-run case, and the second case holds that a run in the operator's own checkout is not rewritten. The commits the app makes itself are asserted where their land is, not here: `landAfterVerify.test.ts`' last describe (squash, merge, the Commit button, a Dreaming night), `landAfterSquash.test.ts` (a merge landed past a squash and a resolution's merge past one) and `resolutionMarkerless.test.ts`' control (a conflicted resolution's message is exactly the subject and one trailer block, with no `# Conflicts:` comment). Those last two compare the whole message, because a duplicated block passes a `match`.

`land.test.ts`' `parseMergeTree` pair for a blanked merge driver exists because the real-git case cannot fail on the image: `gitFilterProbe.test.ts`' "Land's preview of a merge the blank failed names the driver and says why" gets exit 128 from 2.39.5 and passed before the change, and it is exit 1 with a full conflict listing on 2.54 and later (`security/server-git.md`, board task `9dddc18a`). The first feeds `parseMergeTree` the 2.56.0 output captured through `git()` under both statuses and asserts `unknown` with the driver's name and the sentence in the reason; with the check removed it fails on the exit-1 pass. The second keeps an exit 1 with an empty `stderr` a conflict, so the check cannot widen into reading every exit 1 as unknown. Its blanked-driver describe is the same reading for the real merge (board task `716f904b`): `mergeRefusal` and `unresolvableMerge` are fed the `stderr` that `merge` and `merge --squash` gave through `git()` on a built 2.56.0, with the `["f.txt"]` `conflictedFiles` returned there, and the 2.39.5 one with none. Each must give the driver's sentence and no conflict listing, the unrestored-checkout warnings must survive it, and a real conflict without the sentence must still read as one and still go to a resolver. Against the unfixed `mergeRefusal`, exported for the purpose, both blanked cases failed with "The merge conflicted … Conflicting: f.txt". `refusedMerge` is the same describe's third reading, of what `landRun` hands the 400 body of `POST /api/runs/[id]/land` (board task `31d91115`): `mergeRefusal` was right and `conflicts` beside it still listed `f.txt`, so the page named as conflicting a file that merges cleanly. Its blanked case fails against a `refusedMerge` that returns the raw list, on the 2.56.0 shape only, since 2.39.5 lists nothing; its `passing` case feeds the blanked line beside a held-lock line, because `passing` must read the raw list (unmerged paths mean the checkout is not as it was) and with a shaped one only that pairing would read as a refusal to retry. The end-to-end on 2.56.0 was measured once and is not a test, since it needs a second git.
