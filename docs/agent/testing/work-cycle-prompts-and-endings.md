# Work-cycle prompts, endings and deadlines

[← testing index](../testing.md)

Read before adding or editing tests of `nextPrompt`/`reopenPrompt`, `cycleEnding` and the `DONE`/`NEEDS_REVIEW` contracts, `edgeSatisfied`, the cycle silence deadline, the background-wait ceiling and note (`backgroundWork.ts`), `resumeControl` and `logLifecycle` in `orchestrator.ts`.

`nextPrompt` and `reopenPrompt` each gained the branch that decides what an unattended agent is told about *ending*: that the opening cycle carries the DONE contract and carries it after the task, that it is withheld where `endsOnDone` is false because the promise would be untrue, that an isolated opening turn names the shared stash stack, and that a restart-killed run is told its cycle was cut off — above the pushback branch, since `reported_done` is stale after a kill and below it a run would be told it had reported the task complete.

The fourth ending added six sets of cases and refused two more, and what each earned is the same bar read against what it costs.

`cycleEnding` is the one that had to be *extracted* to be testable, and the obvious answer — "test the sentinel matcher" — is the wrong one: a bare regex pins the language rather than a decision, and the `DONE` matcher beside it has gone untested since it was written.

What earns it is the **precedence**, that `NEEDS_REVIEW` outranks `DONE` in one turn's text and that neither fires unless it is alone on its line, because a wrong precedence files a run that said it was stuck as green `completed` — the exact defect the ending exists to remove — and throws nothing.

Its negative cases carry the same weight and will be exercised first: the matcher runs over generated text, so a run whose *task* is this feature carries the literal token in prose, and the two guards that bound that (a sentinel spelled unlike the stored status, and a line of its own) are pinned rather than commented.

`edgeSatisfied` earns its first direct cases here for `dependencies.md`'s two failures — a chain that never starts, or one started on top of work that did not happen — with the `releasableRuns` pair beside them saying the dependent is *named* rather than merely blocked. The refund case is the third failure: a run that paid for a cycle and was parked for a stack ends `stopped` at `iterations === 0`, and a dependent behind it was blocked as if nothing had run. The pure case pins both edges on `refundedCycles`; `stackWait.test.ts` drives the real chain (stack park, `Stop`, an `on-finish` dependent held `waiting` under the install-wide hold, an `on-success` one blocked on "it ended stopped"), plus the control that decides the counters: a run the provider refused at the wall parks and refunds too but did nothing, and its dependent must still block "without running a work cycle". A rule written as `pause_count > 0` passes the first two and fails that one. The refusals the run survives are the other side of that control: a cycle that edited, paid and then met the wall, parked and stopped, and one that met a 529 and was stopped in the retry's backoff, must each leave the `on-finish` dependent `waiting`; both failed before `worked_refunds`, blocked with that sentence. Their control is a 529 on a one-turn cycle that spent nothing, which must still block — a rule written on `num_turns` fails it.

`stackWait.test.ts`'s rival pair is the same failure at admission, on that harness because the refusal is a query: a second run continuing a branch whose first continuer worked, was refunded to zero by each of the four counters in turn and was stopped must be refused naming it, and its control — a continuer refused at the wall, `pause_count` 1 — must not. A nested describe there is the same query read for the exempt pair: an `on-success` and an `on-failure` continuer of one predecessor both admitted `waiting`, a third refused whatever it waits on, only the fixer released when the predecessor fails (and only the success run when it completes), with `chainRuns` and `branchOwnerOf` following the released one past the older, blocked sibling, and the fixer failed at release naming the success run when that run has already worked. The last was checked failing with the release-time check removed; nothing else drives `admitWaiting` for it.

`orchestrator.test.ts`' three `on-failure` cases are the same two failures for the third condition, plus one of its own: a dependent released behind a `completed` or `stopped` run starts a fixer on work that went fine or undoes a stop, one never decided sits `waiting` for ever, and one passed over as `blocked` rather than `not-needed` reads as a fault nobody made. They pin both releasing endings, the stop that blocks, the cascade naming the run in front, and a blocking dependency outranking one passed over. The same condition is pinned one level up, here rather than beside the instance tests because it is one rule read in three places: `workflows.test.ts`' `planInstanceStep — an on-failure link` cases (a node created only behind a failure that did work, passed over with everything behind it on a success, blocked on a stop, the older conditions unchanged) and its `normalizeWorkflowInput — an on-failure link` cases, the two save refusals whose absence would save a graph the scheduler has no reading for; and `instanceReading.test.ts`' case, which drives the real `releaseDependents` over a completed run and asserts the run and ledger row behind it `not-needed` and the instance `finished` with nothing blocked — counted as blocked, a workflow whose first run simply worked reads as missing its tail.

The restart-closed case is the fourth: a run a restart closed out after a cycle is `stopped` with one cycle counted, which `edgeSatisfied` reads as `on-finish` satisfied, and it is still outstanding. The pure case pins that `releasableRuns` blocks behind one on either edge with the sentence naming it, ahead of a fan-in's other, satisfied half, and releases as ever once the flag is gone; `shutdown.test.ts`'s fourteenth drives the fan-in that reached it, one half picked up by name. `ReleaseState.restartClosed` is required for `refundedCycles`' reason, so a state built without it is a compile error rather than a closed-out run read as finished.

`reopenPrompt` was already on this list for the branch that decides what an unattended agent is told about ending, and the new branch is the one whose absence looks correct: the pushback tests `completed`, which a `needs-review` row is not, so doing nothing sends the plain continuation into a conversation whose last turn was the agent reporting a wall.

`cycleCutByRestart` is the input the restart branch is only as good as, and it earns four cases because both of its mistakes are silent and point opposite ways. It read `failed` alone, which is what `reconcileOnBoot` writes, so a graceful shutdown — ending every run it interrupts `stopped` — sent the plain continuation or the DONE pushback to every run a deploy cut off; the case pinning a `stopped` row with `restart_cut_cycle` set failed against that predicate. Widening it to every `stopped` restart row is the other mistake, and the pre-cycle-scan row is its control. The boot's `failed` row stays true with the new flag at 0, because that writer does not set it and neither does any row older than the column.

`nextPrompt`'s new assertion is the **ungating** — that the notice rides on a prompt where `endsOnDone` is false — because `maxIterations` defaults to 1, so folding it under that flag would withhold the ending from the majority of runs on a stock install and nothing else would report the loss; its existing equalities compose against the notice rather than dropping to substring matches, since only an equality catches a second sentence appended by accident.

`cycleDeadline.test.ts` opens the database and is `settleOnExit`'s argument in its strongest form: what it pins is that `runIteration` *returns at all* against a child that prints nothing and does not exit, so the subject has to be a real process — a stubbed emitter would pin the wiring rather than the fault, and the fault is the child. Its third case stops a child that opened a background sub-agent (a Stop, since the deadline no longer ends one) and asserts the `/runs/live` roster is empty after `runIteration` returns: a killed cycle sends no `task_notification`, so the sweep in `finish()` is the only thing that ends the row, and its grounds are in [`stream-parsers-and-webhook.md`](stream-parsers-and-webhook.md) beside the fold's. The last two cases pin that `onSilence` *reads* that roster: a child that printed the CLI's `Agent` and `task_started` (backgrounded) lines and then nothing outlives a 1 s deadline for 3.5 s, and the same child stated foreground is still killed at it. The fault is a healthy cycle ended as hung — measured end to end, a 20 s deadline killed a cycle whose sub-agent was blocked in one `Read` — and only a real child shows the wiring, an argument dropped between the roster and the timer leaving the pure cases in `orchestrator.test.ts` (`quietDeadlineMs`: unchanged with none running, raised to the default with one, never lowered below an operator's longer value, finite so a hung one ends) green. Both were confirmed to fail with the read replaced by `0` and with the foreground counted.

It is the one file in the suite that points `CLAUDE_BIN` at a binary that exists (`process.execPath`, running an inline script, so it can reach nothing and spend nothing), which is exactly why it cannot be a case in `orchestrator.test.ts`, whose own harness pins that variable at a path that does not exist so a regression reaching a spawn is a failed test rather than a billed one.

Its control is half of it and is what says the clock is *silence*: a child printing every 100ms must survive a one-second deadline, which a wall-clock deadline would fail while passing every assertion in the case beside it.

The bound is the test's own `timeout`, because without one the only failure available is a test that never returns, and that is not a failure anything reports.

`resumeControl.test.ts` pins the control group's reading of which turn a clean resume actually was. `resumeControl` used to answer each probe by walking every main-thread turn on the machine and skipping the ones belonging to another session; grouping the turns by session once is meant to be the same loop over the only entries that could ever have answered it, and the failure mode of getting that wrong is silent: `warmShare` feeds `netReceipt`, so a control that quietly picked another session's turn would move every priced receipt's `netUSD` — the figure that decides whether pruning looks worth keeping — with nothing throwing and nothing failing to typecheck. The behaviour was untested before the change, so each case pins one thing the old whole-corpus walk did that the grouped read has to keep doing.

`resumeMissingTranscript.test.ts` pins the restart a pick-up takes when its session's transcript is gone, and drives real segments through `startRun` and `reopenRun` against a stubbed child because the decision is wiring rather than a function: `buildArgs` cannot see which session the loop chose and `nextPrompt` cannot see which follow-up survived. Both mistakes are billed and silent. Resuming a session that is gone charged a cycle the CLI refused on every pick-up and ended the run `failed` on a bare exit code; restarting one that is there throws away a conversation on disk and repeats the task on top of the work it already did. So it reads the second spawn's argv and prompt in five cases: gone, with no `--resume`, the prior-work notice and one cycle charged; gone with the operator's note, which must follow the task; gone after a DONE, where the pushback is dropped from the prompt and the row; and two controls with the transcript present, which still resume and still push back. The three gone cases failed before the change, each on the `--resume` it still carried, and the two follow-up cases were each confirmed to fail by dropping one half of `follow_up_is_note` from the compiled module. A sixth is the CLI's own refusal of a resume that check let through, fed the measured zero-turn `result` line: it must be retried once on the same session and end `failed` naming `claude --resume <id>`, and before `cycleDidNoWork` counted that line it ended on the bare exit code with no retry. Four more follow a refusal the retry gets past, because the message cleared at the spawn must reach the cycle that replaces one which did no work: the operator's note, the DONE pushback, the note on a refused fork's rollback, and the stopped-tasks note read off the log. Each failed before `handBack`, on the plain continuation the retry was sent, and only those four fail with its two calls removed from the compiled module. Its write of `follow_up` back to the row is not driven: it matters only when a park lands before the retry spawns. `transcriptPresence` earns seven cases beside them on the same grounds, since it is the one thing between a conversation on disk and a restart on top of it: two files under one id, a failed walk and an empty tree must each not read as `absent`.

`logLifecycle` in `orchestrator.test.ts` earns the not-pure exception on `settleOnExit`'s terms: what it decides is a *line* on container stdout, and both halves of that line fail silently. The level is a **routing** decision — the field a shipper filters on to decide whether a person is woken — so one `info` for all nine statuses made the ending whose entire content is *a person should look at this* arrive indistinguishable from an ordinary completion, and the only evidence of getting it wrong is an alert that never fires, which reads exactly like a fleet with nothing wrong. All nine statuses are therefore one case in both directions, `stopped` pinned at `info` beside the three at `warn`, since an operator's own cancel arrives as that one and a guard trip already has `run.guard_tripped`. The field set is the other half and fails the other way: the function **projects** rather than serialising, because a `status` payload at creation carries the folder and an `iteration` payload carries the whole prompt, so two cases assert a line's exact key set rather than the presence of a field — which is the only mechanical guard there is on a spread being added later, and the leak it would be is onto a stream with a different audience and a different lifetime from `run_events`. The 429 ladder's two booleans are pinned in all three of their readings, because `retrying: false` is a refusal that will park and an *absent* `retrying` is a spawn failure that was never a refusal at all, and collapsing the second into the first files every dead container as a rate limit the ladder had given up on. It is exported for that test and for nothing else, `tickSchedules`' precedent.

`backgroundWork.test.ts` pins two decisions that are billed and fail silently in opposite directions. The note a cycle opens with after its background tasks were stopped has to exist for a sub-agent the CLI killed at its ceiling — an agent that is not told resumes into a conversation saying its sub-agents are working, waits on them and spends a cycle on nothing, which is run `350ef202` at $24.45 — and has to be absent for a task that completed, for a cycle with no background task, and for a task whose ending never reached the log, because "no ending seen" is also what finished work looks like (`runTasks.ts`: a finished task leaves the snapshot). A note about finished work sends the agent to redo it, which is the same bill from the other side. A sub-agent the CLI filed as a *foreground* task and a Stop killed gets none either: 2.1.280 sends the same `killed` and `stopped` endings for it, and the agent saw that call interrupted in its own conversation. The note's output path is pinned whole past the description's 200-character bound and with a doubled space in it, because both were clipped or folded by the description's flattening and sent the agent to a file that does not exist. The ceiling's cases are the guard it exists to carry: it is what is left of `maxDurationMinutes` on the **worked** clock the guard reads, so a parked run is not given a shorter wait than the guard would allow, it ends at the instant the guard would, it is never `0` while a limit is set (the CLI's spelling of "no ceiling", so a spent limit would otherwise be handed the one value that outlives it), and it is a bare integer, because the pinned parser reads `1.5` and `10s` as one millisecond. The four prompt cases in `orchestrator.test.ts` pin that the note goes *ahead of* the continuation, the pushback or the validator's text and replaces none of them, rides a fresh conversation after the task, and leaves the operator's own note verbatim. The five boundary cases beside them drive the CLI's own stream lines through `handleStreamLine` into a real database and read the note back, because what only a database can get wrong is which rows are "the previous cycle": too wide and every later cycle is told again about tasks from three cycles ago, too narrow and the one cycle that needed it is not told — the second was confirmed to fail by dropping the `iteration` boundary from the query. Five more beside them write a pick-up through the real door — `reopenRun` with no note from `needs-review`, from a restart-cut `failed` and from a DONE `completed`, and `releaseStackWaits` — and build the next prompt from the row and the log as the loop does. Each must name the stopped task exactly once, because a follow-up is sent alone and the cycle it opens moves the boundary, so a note it does not carry is never given; and a note the operator typed must still be the whole turn. The four failed before the note was resolved at the door, each sending its notice alone. `cycleDeadline.test.ts` gained the ceiling's last hop for the reason that file exists: a spawned process, not a function, is the claim, and a parameter dropped between `runIteration`'s signature and its `spawn` leaves every case beside `childEnv` green and every cycle on the CLI's own ten minutes. `childEnv`'s cases are in [`spawn-argv-and-child-env.md`](spawn-argv-and-child-env.md).

`runs.ending_code` is pinned where the endings already are, rather than in a file of its own, because its one silent failure is a branch that settles a status and forgets the code — which no pure function can catch, since an omitted key on a `Partial<RunRow>` typechecks. `interruptOutcome` gained the code beside the status, and its cases say who: a person, a restart, the workflow `stopRun` was called for, the cycle cap a guard verdict names, and null — unknown, not a guess — for a guard with no code and for a prune; `planPausedRun`'s `end` arm carries the sweeper's code, and `haltEnding` in `workflows.test.ts` is the one that tells a workflow's guard from a person. The rest are one assertion each in a loop test that already reaches that ending, so a `break` added later without a code fails a case someone already reads: `done` and `cycle_cap` in `validationGrant.test.ts`, the cut at the cap in `parksAndRefunds.test.ts`, a Stop during the verdict wait, a shutdown and a boot close-out in `shutdown.test.ts`, a park writing null and the cascade's `dependency`, `not_needed` and `error` in `stackWait.test.ts`, a checkout refusal in `cutOffCheckout.test.ts`, a refused resume in `resumeMissingTranscript.test.ts`, and the fleet's stop in `fleet.test.ts`. `ENDING_LABEL` and `endingLabel` earn none: a wrong phrase or an unknown drawn as a code is on the page that draws it.

`priorReads.test.ts` pins the prior-read pointer's three pure parts, each of which fails silently in the direction that is hardest to notice. `repoRelative` must make a checkout's path and the repository's path one file, refuse another checkout's copy, a `..` that climbs out by spelling, a relative path and a path with a newline in it, and normalise inside the base. Wrong, the block names absolute paths or another run's tree, which look plausible in a prompt and match nothing. `priorReadRanking` must weight the newest run's reads above an older run's (the case is built so that raw frequency, distinct runs and the decay each give a different order), order runs by `created_at` whatever order the rows come in, drop every path outside its row's base, fill its limit past candidates `keep` refuses and stop asking once full, and break ties by path. `inHoldout` must return four pinned ids' arms, be the same answer twenty times for one id, hold out between 47% and 53% of 4,000 random ids, and agree with a bare-id split only at chance. A non-deterministic or re-dealt split leaves the whole holdout unanalysable after the fact. A mutation check of the compiled module, made when it landed, reversed the decay, dropped the experiment name from the preimage and removed the base check; each failed. `orchestrator.test.ts`'s "names what earlier runs read directly ahead of the task" pins the block's slot in `nextPrompt` — after `priorWorkNotice`, before the task, absent on a resumed session — and its wording as a record with each path's run count.
