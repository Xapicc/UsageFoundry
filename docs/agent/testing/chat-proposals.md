# Chat proposals, questions and search

[← testing index](../testing.md)

Read before adding or editing tests of `chat.ts`' proposals, guards and questions, `proposalContinuation.ts`, `findChats`, `planScheduleProposal`, `selectRemoteReads` and `spellGuards` in the chat DTOs.

`proposalGuards` earns its place on the direction its wrong answers run in — it resolves what an untemplated proposal's run may do out of a blob in a column, and the three ways of getting that wrong are a snapshot ignored (a run under rules no card stated, which is what freezing the set was for), a snapshot half-applied (a run under rules nobody wrote), and a row carrying none refused rather than run under today's set (every proposal pending across the upgrade destroyed, and getting one back is a billed turn); its fourth case is the control, that a templated proposal still resolves from the live template however much its row is carrying. `normalizeChoices`, `answerMessage` and `settleQuestions`, the three about questions to the operator, earn their place together, because each of them fails as a *question* rather than as an error: a choices list that arrived holding a null is a button reading "null" that somebody can click, an answer sent without the question above it is a bare string a fresh child has to guess the referent of, and an id dropped rather than refused is the operator's typed answer silently missing from the text the model reads. `answerMessage` carries one more case, about the constants rather than the function: every open question at `MAX_QUESTION_CHARS`, each answered by a choice at `MAX_CHOICE_CHARS`, in three-byte characters, must leave half of `MAX_CHAT_MESSAGE_BYTES` for typed answers, because the four live apart and raising any of the three question bounds alone brings back an Answer refused over text the operator did not write. What settles the rows is a query rather than any of them, so the supersede rule is pinned against the database on `chatOrder.test.ts`'s grounds — an ordinary message overtaking an open question, an answer closing the ones it names and overtaking the rest, and a stale card starting no turn at all — and the round trip of `chat_questions.choices` beside it on `proposalDeps`', where an unreadable list is a card with no buttons on a question the model asked as a pick-one. `threadItems` in `chatThread.ts` is the fourth of that group and is on the list for the quietest failure of the four: it decides where a question is *drawn* in the transcript, and one the page never draws leaves the thread waiting on an answer to something the operator was never shown — no error, no empty state, nothing in the console, and a page indistinguishable from an idle chat — so the first case pins the unconditional tail append and the rest pin the pairing the panel is built on, a question placed before the operator's *next* message rather than at its own timestamp, which is what puts an answered one directly above the message that carried the answer and a pending one at the foot of the thread beside the composer, and the strict comparison that keeps a question off the top of the message that provoked it. `rivalContinuation` in `proposalContinuation.ts`, pinned in `proposalContinuation.test.ts`, is lifted out of `/api/mcp`'s `propose_run` for the reason `threadItems` is lifted out of the page — nothing here tests a route, and the rule is where the failure is: two proposals set to carry on one label's branch are otherwise refused by `admitDependencies` at the click, in run ids that were on no card, and the second card is terminally `failed` by the time anybody reads it. Both directions of getting it wrong are silent — a rival missed is that refusal, a rival invented is a chain the model is told it cannot have — and the case that earns the file is an **approved** proposal deliberately not counting, since its run may have been refused at the door with no work cycle behind it, which is exactly what leaves the branch free.

`findChats` earns its four cases on the two ways a search fails silently in opposite directions. The operator's text goes into a `LIKE`, and unescaped a `%` anywhere in it matches every thread in the install — a search that returns everything reads exactly like a search that found everything, and the operator concludes their conversation is one of two hundred rather than that their query was ignored; `_` is the likelier accident, being in half the identifiers anybody would paste in. The other is that the page and the total come from two statements: a `LIMIT`/`OFFSET` beside a separate `COUNT(*)` computed from a different predicate shows "30 of 214" over a list with nothing more to give, which is a More button that does nothing. The case for matching message text rather than only titles is pinned as well, because it is the whole point of the feature — a title is written by the model from the opening line, so searching titles alone finds only the conversations somebody already remembers.

`planScheduleProposal` earns its cases on `planWorkflowProposal`'s ground sharpened by what it authorises: it is where a cadence a model wrote becomes a workflow that starts itself with nobody present. A workflow that lost its limits since the card was written, a deleted workflow, and an every-N-hours interval anchored at the proposal instead of the approval all produce a schedule that looks right on the page, and a weekday that did not survive the stored row fires on the wrong day under words naming the right one. `findPastProposals` earns its three on `findChats`' grounds — an unescaped `%`, a folder prefix matching a sibling (`acme/web` against `acme/webby`), and a replaced card or the asking thread listed as a second proposal of the same job all return a well-formed answer that is wrong.

`remoteReads.test.ts` is `selectRemoteReads` — which repositories a chat's `list_folders` pays a git child to identify — and it earns its place on `selectBranchCandidates`' grounds plus one that selection does not have: here the truncation and the answer are the *same rendering*. A repository the lookup did not read comes back with no `owner/name`, which is byte-for-byte how a folder that is not on GitHub comes back, so the chat says it cannot identify that repository and an operator with twenty-six of them reads a working one as broken. `MAX_REMOTES_READ` used to be `slice(0, 25)` over the folders in scan order, which made that permanent as well as silent — the same twenty-five won every call, and no parameter anywhere asked for the twenty-sixth — so the cases are built at that boundary and nowhere else: twenty-six repositories, a first page reading exactly the cap, a second reading exactly the one it left, and the union of the two asserted to be every repository, which is the property a cap is allowed to cost nothing. `notRead` is pinned as everything off the page rather than everything after it, because it is read beside `offset` and `matching` and a count that meant only one of the two directions would be right on the first page and wrong on every later one. The `folders` filter is asserted to read in scan order rather than in the order it was asked, since the caller renders the answer against the folder list; `gitRepos` is counted over the unfiltered scan for the reason `selectBranchCandidates` counts its own that way; and a key naming nothing must come back in `unmatched`, because it is the one input where reading nothing is a typo rather than an answer — dropped, it renders as exactly the "not a repository" this whole page exists to stop reporting.

`dto.test.ts` covers `spellGuards`, the sentence every proposal card is approved against, and its failure is the kind this suite is reserved for: a card asserting a limit the run does not have throws nothing, fails no typecheck, renders as an ordinary card, and the money is spent under a number nobody was shown. Both callers — the operator's own defaults and a template's — are pinned against one expected string rather than two, since a second spelling for the templated case would pass a test written against either alone and diverge the day a limit is added; the `null` cases sit beside them because `null` is this app's wire form of "no limit at all", and a cap invented for one or a real one dropped are the two directions the same clause fails in.

`approveRunBatch`'s two cases in `chat.test.ts` pin the sentence a run card gets when the label it waits on belongs to a workflow card — reachable with the tools alone, since a workflow that replaces a run card inherits its label. The refusal was always right; both sentences were false and pointed at each other. Approved alone, the run card was told to approve them together; approved together, it was told the workflow card was in neither the click nor the chat (or, through the real supersede path, that the card it replaced "was superseded"), because the outside map skipped the whole click rather than only the run cards `planApprovalBatch` was given. The cases are driven against the database because that map is built from rows, and they go through `createProposalReplacing` rather than writing the label directly, so the superseded run card still spelling it is part of the fixture. `planApprovalBatch`'s schedule case is the pure half: kind is asked before status, and a pending schedule card must not earn "approve them together". All three failed before the change.

A prompt that is not text is refused at every door that read it through `String()`, and one case each pins that nothing was written. In `route.test.ts`, `save_template` with an object, array or number `prompt` saves no `run_templates` row and `propose_run` with a non-string `promptOverride` writes no `chat_proposals` row, both naming the field (`"prompt" has to be a string when it is given`) where the row used to read `[object Object]`, and a string still saves and proposes. `normalizeAgentInput` refuses a non-string `prompt` by name and still reads `null` and a missing one as the empty prompt it always refused; `parseRunAgent`, which is total, reads a stored non-string prompt as no agent. `normalizeWorkflowInput` refuses a run or orchestrator block's non-string `promptOverride` naming the block, and a merge block, which drops the field unread, is not refused for it. All were checked failing with the source changes reverted.

The same refusal stands in front of every other chat-proposal argument that `String()` used to read through, and the cases sit beside the ones above in `route.test.ts` and `workflows.test.ts`. `propose_workflow` refuses a non-string `summary` (the card's task text), `supersedes` (a list-wrapped label decided the card it named as replaced) and, per block, `id`, `kind` and `name`, and per `dependsOn` entry `id` and `edge`, each naming the field and, for a nested one, the block and entry; `propose_schedule` refuses `workflowId`, `kind` and `supersedes`, and `time` and `weekday` only for the kinds that read them; `propose_run` refuses a `dependsOn` entry's `id` and `edge`; and `planEmission` refuses the same two on an emitted run's `dependsOn`. Each case asserts that no `chat_proposals` row was written and that the card a wrapped `supersedes` named is still pending, and a string and a `null` still propose. Each of the three tests was checked failing with the source changes reverted.
