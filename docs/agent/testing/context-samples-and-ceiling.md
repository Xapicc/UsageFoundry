# Context samples, the live tick and the context ceiling

[← testing index](../testing.md)

Read before adding or editing tests of the context sample series, `liveTickPlan`/`guardScanDue`, `checkContextCeilings`, `parseComposition`, the treat estimate and `ContextOccupancy`'s composition cases.

`contextSamples.test.ts` is the series built on top of `contextTokens`' reading, and it is its own file for `bootBlocks.test.ts`'s mechanical reason — it opens the database — and its own group for a different one: every failure here is a graph that draws, looks entirely plausible, and is wrong, which is a worse outcome than a blank panel. Four of its cases are the four decisions. **A sample below the ceiling is recorded**, because the tick already computed that number and `tokens < CYCLE_CONTEXT_CEILING_TOKENS` threw it away — a store put back after that comparison instead of before it would record only runs already over the ceiling, and the resulting series is never empty and never wrong-looking. **An unchanged frame writes nothing**: the ticker is time-based and one tool call outlasts several ticks, so a row per tick fills the series with flat duplicates, which does not read as a bug but as a run whose context was not growing — the opposite of what the meter is for. **A sidechain and a `<synthetic>` frame do not advance the turn count**, the ceiling's own two exclusions, since inflating the turn axis lands hardest on the tool-heavy runs whose growth rate is the reason to look; a fifth case pins that a turn the CLI wrote as several records sharing one `message.id` is one turn, which is the same number wrong the same invisible way. And **pruning being switched off does not switch the series off**, which is the trap the change was written against: sampling inside `checkContextCeilings`' old `pruningEnabled()` early return leaves the indicator permanently blank on every install with the feature off, install-dependent and with nothing saying why. That case asserts `pruningEnabled() === false` first, so it pins the decision rather than happening to pass. `nextTurnIndex` gets its own four on `paybackTurns`' grounds — arithmetic whose every wrong answer is an ordinary-looking number — and the case that carries them is the whole-file one, because a `--resume` into a fresh transcript is indistinguishable from an advance unless the scan reaching the start of a file is treated as an absolute rather than added to what came before.

A fifth decision joined those four later and is the same one read from the other end: **a tick that writes no row still records that it looked.** Deduplication is right and it is also what made the panel unreadable, because the only timestamp on the wire was the newest row's — so the case reads the same frame twice, asserts the series did not grow and asserts the read is no older than the row it declined to write. Two beside it separate `unreadable` from unchanged, which are opposite statements reaching the same field, and keep one run's reads out of another's. `contextOccupancy` gains the matching pair: the read reaches the DTO beside a series that did not move, and a run whose rows this process inherited across a restart reports no read at all rather than the previous process's. That last one is the only guard on the decision to hold this in memory instead of in a row.

`liveTickPlan` and `guardScanDue` in `orchestrator.test.ts` are pure and both directions of each are silent. A `tickMs` that ignored `CONTEXT_READ_MAX_INTERVAL_MS` puts the context panel as far behind as an operator's budget setting, showing a plausible number with a stale age and nothing naming the setting that moved it; a `guardMs` that collapsed onto the floored tick runs `buildSnapshot` — uncoalesced, the expensive half — five times as often as was asked, and costs rather than lies. The slack case is the one worth having: `setInterval` drifts, and refusing a tick a hair early pushes the budget scan a whole tick past the cadence set, compounding, so a scan at 599,900 ms of a 600,000 ms interval is due and one at 539,999 is not. Its control is the default install, where the two cadences are one and an early tick must not be skipped into a two-minute one.

`contextCeilingRace.test.ts` is the *acting* half of that same tick, and it is its own file because what it drives is `checkContextCeilings` rather than a pure function underneath it — with `planCut` replaced on the module `orchestrator.ts` reaches it through, `shutdown.test.ts`'s device and not one to leave standing in a file other cases share. What it pins is an **absence**. The loop reads `interrupts` once and then awaits twice, the second of them a winnow subprocess bounded at two minutes, so a cycle ending inside that window is the ordinary case rather than a race anyone has to arrange; and writing the interrupt anyway is silent in all three of its forms, which one depending only on where `startRun` had got to — a completed cycle refunded and its `DONE`, refusal and exit-code tests skipped, a healthy run filed `stopped` by an `interruptOutcome` that deliberately has no `prune` case, or an entry left in a process-lifetime map that only two lines ever delete, which settles that run's next Resume `stopped` having spawned nothing. Its control is half of it, for `dataDirClaim.test.ts`'s reason: a case that never reached the interrupt site at all would satisfy the first assertion for the wrong reason and go on satisfying it, so the second drives the same fixture with the watch left in place and asserts the prune is still written. Three more in that file pin the same tick's *other* silence, and they are absences of the opposite kind — a row that must be written where the first two pin an interrupt that must not be. The ceiling is the gate that takes 55 of 58 cuts here, and its decline branch logged and `continue`d without recording anything, so a run held above the ceiling for forty minutes and an install with pruning switched off read identically once the run had settled; nine runs on this install crossed 200,000 and left no row in any of the six pruning tables, one of them at 486,654 across 28 consecutive samples. The refusal case asserts the figure by recomputing `ceilingPayback` rather than writing a literal, because a literal goes on passing after a change that makes the row disagree with the decision above it. The second is the distinction the table exists for: a null from `ceilingCut` — winnow absent, or a subprocess that failed — must land as `unavailable` and not be folded into `declined`, or an operator goes looking for a horizon to move on an install that never measured anything. The third is the cadence, and it needs the conversation to actually grow, since `CEILING_REMEASURE_GROWTH_TOKENS` skips an unchanged transcript before either await: one row per admitted measurement and none for the tick in between, which is what pins that `earlyEndDeclined` latches the operator-facing line and not the record.

`parseComposition` is in that file too and earns its place on `parsePlanUsage`' grounds: it reads another program's output over a format nothing here can ask about, and its fixture is verbatim `winnow context --depth 3 --json` from the pinned ref with only the session id, its path and the checkout it names replaced. Kept whole rather than reduced to the two objects the parser touches, because a fixture trimmed to what today's parser happens to look at cannot fail when the shape *around* it moves. Four properties are pinned and each fails silently: the bands must sum to the window, since the residual is one of them and a dropped node still draws a plausible stack that quietly stops short of its own total; `kind` must survive, because it is the one thing about a band no fill can carry and `prefix` being a subtraction of two exact readings while `tool traffic` is characters over a constant are different claims about how far to trust a figure; an unrecognised label must render as itself, since winnow owns that vocabulary and has already changed it once, and a label folded into an "other" bin is indistinguishable from the residual, the one node whose whole job is to say what nothing accounted for; and a null window — no anchoring request, so nothing exact to apportion — must not collapse with a band measured at zero, which is an answer. Four more arrived with the depth-3 reading and each is silent in the same way — the chart is unchanged and looks right whichever way they go. Both levels below a band must survive, because a parse stopping at the class leaves a detail view saying `Read results` and nothing about which file, and one flattening the two puts tool names and file paths in a single list where no reader can tell which is which; a band with no subtree at all is winnow's answer for `prefix` and `unattributed` rather than a parse that gave up. Winnow's `×N` must come off the label into its own field, since `decorate()` welds them and a view keyed on the composed string reads one file touched three times and the same file touched four as two different files — with null there meaning "winnow attached no count" and never "once", which is why a label that merely ends in something count-shaped keeps it whole. A child that cannot be read must be dropped rather than drawn at zero, the top level's rule one level down and for its reason. And the per-node cap must keep the **largest** children: the case shuffles them rather than feeding them in winnow's own descending order, because a cap that took the tail would head a detail view with eleven-token artefacts and leave out the file actually filling the window, and the guarantee must not rest on another program's sort. The cap drops its tail and pools nothing, on the same argument as the label case above. A ninth pins the residual's sign and its denominator, and it came from a run rather than an argument: winnow prints the residual as the window less its nodes *plus the shed* and prints it negative wherever the estimates over-explain the window, and the parse floored it at zero — so every reading of a run with tool traffic summed past its window, and the stack, promised a sum equal to the window, drew three of its bands at no height. The case feeds a positive residual with a shed behind it and asserts the stored one is negative and that the bands sum to the window; its control is a negative provenance, which must stay floored, because winnow floors those itself and the stack treats every band but the residual as a height. `fmtTokens` gained one line in the same change and one case in `format.test.ts` on the same grounds: the legend prints the residual in a column of positive figures, and the unsigned formatter fell through every threshold on a negative and printed the raw integer beside them.

`parseTreatEstimate` and `treatRemovedTokens` are in the same file and earn their place on a two-day outage rather than on a hypothesis. The parse is a text parse — the inherited `treat` subcommand has no `--json`, only `plan` and `fork` do — over a fixture that is verbatim output from the deployed image, so a winnow release that renames those lines fails here rather than reading as "nothing worth removing" on every install at once. Two of its cases pin the specific ways a plausible parser is wrong: taking the first number on the `Saved` line gets winnow's token column, which does not move at all under orchestrator-safe mode (`metadata-strip` is excluded, the `usage` frames survive, and the exact count re-anchors on the same turn — "Saved 0 tokens (0.0%)" for a cut that halves the file), and reading KB and MB as decimal is 2.4% low against `fmt_bytes`' binary divisors, small and in the declining direction and therefore invisible. A zero saving is an answer and `null` is a fault, and the two must not collapse. `treatRemovedTokens` is pinned against the reading it replaces: session `02584a86`'s 1.79 MB read through `BYTES_PER_TOKEN` is 521k tokens removed from a 258k-token conversation, so `ceilingPayback` floors the remainder and prices the cut at 0 turns — prune always — and the test asserts that overshoot before asserting the share, because a case that no longer reproduces the bug is a case that proves nothing. The two real declined crossings sit either side of the horizon at 21 and 18 turns, which is the property worth pinning: the in-place pruner frees about half these transcripts, so `T*` lands beside the limit rather than three orders away from it.

`CEILING_PAYBACK_HORIZON_TURNS` gets a case for the same reason a constant rarely does: it is a *derivation*, not a preference. `ceilingPayback` prices an exactly-half cut at 20, the constant is 20 so that half is admitted, and the test also asserts it is **not** equal to `PAYBACK_HORIZON_TURNS` — the two price different formulas over different quantities, and sharing 18 across both refused the exact case the number was chosen to allow. A `ceilingDeclineMessage` case pins that the ceiling's line carries the ceiling's limit and never the boundary's, and another pins that the line names the engine that measured, which is the whole of what went wrong: a day of "a cut would remove 8.0k tokens" on an install whose pruner would have removed half the conversation, with nothing on screen saying whose figure it was.

`ContextOccupancy`'s composition cases are the component half of the same feature and are on the file's existing argument. Two are about the stack being a picture of the data rather than of the array it arrived in: winnow sorts its nodes largest-first *per reading*, so a provenance that overtakes another mid-run arrives in a different slot and, stacked in arrival order, the two bands cross — one provenance visibly turning into another, drawn from entirely correct data — and the residual sorted by size alone lands between two real provenances and reads as a third. A third pins that a lone reading is a column and not a full-width area, which would assert this composition held for a span it was never measured over and is indistinguishable from a flat run. The fourth is the currency case again in this half's terms: both charts are in tokens, both are the same measure, and they are anchored differently, so the stack is pinned to winnow's *own* window — scaled onto the sample's figure the two would agree by construction and the bands would apportion a total they were never measured against. It used to pin the sentence that said so on the page as well; that sentence was removed at the operator's request and only the arithmetic is pinned now. The fifth separates the two blanks — pruning switched off, which is winnow deliberately never spawned, from a run that has not grown enough to be read yet — which look identical on the page and have opposite fixes. Writing them found a real defect that nothing else would have: a `<title>` whose children are an *array* renders **empty** in React, with a console warning and no other symptom, so every band's tooltip was blank while the markup was well-formed.

The detail region under that stack added six more, and five of them break this file's own rule that a component is tested through its markup: the region is drawn only for the band an operator has *picked*, and picking is client state, which `renderToStaticMarkup` never enters — so `compositionRows` and `accountedShare` are exported and asserted directly, and that export exists for the test. Four of the five are the arithmetic, all silent: rows arrive from SQLite in `ORDER BY id`, which is `recordComposition`'s insertion order and not winnow's, so an unsorted list reads as winnow having found the small things first; a share taken against the band, or against the window, rather than against the node's own parent renders a percentage that looks entirely ordinary — 9,000 tokens is 90% of its parent, 9% of the band and 4.5% of a 200,000 window; a parent measured at zero must give no share rather than the `Infinity` or `NaN` a division would round into a figure; and a key built from the label alone collides where two tools carry the same path, which React answers by drawing one row and silently dropping the other. The fifth is the shortfall, and it is the tail rule in this half's terms: the store drops a tail past `COMPOSITION_CHILDREN_PER_NODE` and the parse drops a node it could not read, so the children are allowed not to reach their parent, the figure saying so is asserted in both directions — under *and* over 100%, since a subtree larger than its parent is a fault to be seen rather than clamped away — and an "other" row is what must never appear. The sixth is not arithmetic and is the one the markup can still reach: six legend `<button>`s with `aria-pressed`, and no `aria-controls` while nothing is open. An SVG `<path>` is not a control — the `<svg>` is `role="img"`, so a handler on a band is unreachable to assistive technology — and a row that regressed to a plain `<li>` renders identically to a sighted reader while leaving the panel mouse-only, which no other case here would notice.
