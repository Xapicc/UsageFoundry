# Spawn argv, the child environment and appended notices

[← testing index](../testing.md)

Read before adding or editing tests of `plugins.ts`' switch, the `--plugin-dir`, taskboard, skill-directory and prompt-separator cases among `buildArgs`' in `orchestrator.test.ts`, `cycleEnvPins`, the extras `childEnv` is handed per cycle, the self-hosting notice, `fileCostNotice` and `tmpdirNotice`. The earlier half of this page's grounds — `childEnv`, `githubEnv` and `telemetryEnv`'s strips, `privsep.ts`, `agents.ts`/`agentRegistry.ts` and `/api/agents`, and the agent and stack cases of `buildArgs` — is in [function-list-queue-to-proposals.md](function-list-queue-to-proposals.md), the first paragraph of which lists them. `spawnCommand`, `CLAUDE_BIN`/`CODEX_BIN` and what the chat child runs and loads are [`chat-child-lookups-and-config.md`](chat-child-lookups-and-config.md).

`plugins.ts`'s two (`plugins.test.ts`) decide what code every agent loads, and a bare `--plugin-dir` with no value takes the *next* argv entry as its path — which in `buildArgs` is a permission mode nobody chose.

`plugins.test.ts` also drives the switch against a scratch mount and database, on the same grounds one step earlier: an enabled plugin whose folder went or whose manifest broke could not be switched off, because switching off ran the enable proofs, and it stayed stored — a broken one still reaching every cycle's `--plugin-dir`, a vanished one waiting for whatever was next written to its path. Nothing about either looks different from a plugin left on deliberately. The cases pin that off succeeds in both states and leaves nothing stored, that a broken manifest is withheld from spawns, that every enabled entry the list has no row for is a problem carrying its switch-off, that a mount root whose own manifest is broken gets exactly one line (a plain one when off, only the switch-off one when on), and that switching on still refuses both containment escapes and a broken manifest.

`buildArgs`'s two argv cases in `orchestrator.test.ts` join the `--plugin-dir` one on the same grounds and against the same silence. The first is now the **inverse** of what it used to assert: `--autocompact` must *not* be emitted. Whether to restore it is an open operator decision (`run-lifecycle/autocompact-and-compaction.md`), and until it is made on purpose a flag reintroduced as a side effect of an unrelated change is exactly the kind that fails nothing. A reinstated flag fails nothing and looks like an ordinary cycle, which is the same silence the old direction was pinned against. The second is unchanged: a second `--append-system-prompt` is a replacement rather than an addition, so the delegation notice and the process-safety notice have to travel under one flag or one of them silently does not arrive, and the half that goes missing decides either what a run costs or whether it has been told why `pkill` is denied.

`buildArgs` gained three argv cases beside its `--plugin-dir` ones, on the same grounds and against the same silence: that the skill directory and the vault itself reach the child, that both survive `--resume` — which restores neither — and that neither appears when the switch is off.

The taskboard's argv earns three more, and its failure is the same silence one notch quieter: an MCP config the CLI was not handed is a child with **no tools**, which reads from a transcript exactly like a model that chose not to call any, so nothing anywhere reports it and the run finishes looking ordinary having closed nothing. The first asserts `--mcp-config` rides a **resumed** cycle as well as the opening one — the version that passes it once gives every run a board that works on cycle one and vanishes on cycle two. The second asserts `--strict-mcp-config` is never there, and it is pinned rather than commented because the two argv builders read alike and this is the line between them: strict on a run strips the operator's own MCP servers out of every cycle, which is invisible from inside this app and which they would read as their servers having broken. The third pins the notice to the flag in **both** directions — a run with the board is told the three tool names, and a run without it gets an appended prompt byte-identical to the one this app sent before the feature — because a run told to call tools it does not have and a run holding tools nobody told it about are the two failures that pairing exists to make impossible, and both look like a normal run from the outside. `--mcp-config` is also on the widest argv `injectionFates` classifies, so a row for it is a test rather than a note.

The self-hosting notice gained one assertion beside the `PROCESS_KILLERS` one it belongs with: that it contains no multi-digit literal, because `--append-system-prompt` puts the notice on every sibling's command line and the worked example it used to carry — `pgrep -f 3100` — matched them all, twice, in production.

That flag is five notices now and the assertion is two, because the last of them is a price list whose every line ends in a figure: the spawn under test carries one, rendered by the real generator rather than spelled out, the strict form is scoped to whatever the flag holds *without* it — derived, so a sixth notice inherits it unnamed — and the price list is held to the other half of the same rule, that nothing beside a figure reads as a command.

The split earns its place rather than the fixture merely growing a field: asserted against a spawn with no price list, as it was, the strict form was a test that passed on every input except the one it could not be given.

`fileCostNotice.test.ts` pins the two ways that feature is worse than not shipping it, and neither shows up in a typecheck, a smoke test or a run's log. **Drift is the expensive one**: the text joins the cached prefix, so a generator carrying an order-dependence or a clock would cold-start every token behind it on the next cycle of the same run — the run still works, it just costs several dollars a cycle more, for a notice worth a few cents — and freezing the column is only worth anything if what it freezes is deterministic. **Bloat is the quiet one**, since every character is re-read on every turn of every cycle, so a repository with very long paths has to cost a shorter list rather than a bigger prompt and a notice over its budget looks exactly like one under it. The rest is the degradations, because the alternative to a price list is not a broken run but last week's run: every failure has to land on `""` rather than on a half-built list or a throw at the one door every run comes through.

`tmpdirNotice.test.ts` earns its place on `fileCostNotice.test.ts`'s grounds, and against the same silence. A `$TMPDIR` sentence that names a path the child does not have is the misspelled prefix it exists to remove, now stated by the supervisor and so more trusted, and nothing reports it: the run reads the path, gets `File does not exist`, and looks like every other run that did. So the cases pin the value derived from the uid rather than a constant (a second uid must change it), the CLI's root order (`CLAUDE_CODE_TMPDIR`, then `TMPDIR`, `TMP`, `TEMP`, an empty string counting as unset) and its 44-byte bound at exactly 44 and 45; that **every** reading that cannot know the value — no managed sandbox, `empty` and `unknown` included, a Codex run, no uid, a relative root — yields `""` rather than a guess; that no command-shaped text sits beside the figure; and, on `buildArgs`, that the stored text is the same bytes on an opening, a resumed and a non-isolated cycle, rides after the price list without moving it, and leaves the prompt byte-identical when absent — the drift case, which costs a full-price re-read of the context and shows nowhere. What it does not pin is that `createRun` stores the text and the spawn reads the row's copy rather than recomputing: that is a call-site property with no DB harness here, held by the comments at both sites.

`childEnv`'s three cases for `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` pin what fails silently about a variable set per cycle by one caller: that the extra survives `childEnv`'s strip and a local cycle's env alike (either dropping it puts every cycle back on the CLI's ten minutes), that `childEnv` itself, `chatEnv`, `reviewEnv` and `authEnv` do **not** set it — a ceiling of `0` in a chat turn's environment would make the one child with a pipe-lifetime problem of its own wait for ever — and that the server's own value passes through when the cycle names none. The reasoning is in `run-lifecycle/background-work.md`.

`promptArgv.test.ts`, and the separator case among `buildArgs`' in `orchestrator.test.ts`, pin where the prompt sits, against a failure that is loud in the child and invisible everywhere else. `-p` is the CLI's boolean `--print` and the prompt its root command's positional, so a prompt beginning with `-` — a pasted bullet list — reached the CLI as an unknown option and the cycle, chat turn or review ended before reading it, while every assertion that read the prompt off `args[1]` passed. The `buildArgs` case asserts the widest argv ends in `--` and the prompt. `promptArgv.test.ts` drives the three spawn sites for real — a work cycle opened and then resumed on a follow-up, a chat's first message, an assist — with `CLAUDE_BIN` at a stub whose parser and option table are transcribed from the pinned bundle, and asserts each child got `- one\n- two` as its one operand. Run against the argv as it was, all three failed on `unknown option '- one\n- two'`. The stub also dispatches an operand naming a root subcommand unless `-p` preceded the `--`, the pinned CLI's start-up order (`security/path-containment-and-spawn-argv.md`), and the same sites must deliver `update` and `doctor` as prompts — which held before any change, since the pin cannot reach that hazard, and fails with the gate cut from the stub. It opens the database, for `resumedCycleSpend.test.ts`' reason, and starts real children because two of the three argvs are built inline at the spawn.

`cycleEnvPins`' six cases in `orchestrator.test.ts` earn their place because each failure hands the operator's credential to a host a repository names, and nothing about the cycle looks different. Measured on 2.1.310, a project `.claude/settings.json` moved the key or the OAuth bearer in five ways (`security/cycle-settings-env.md`). The cases assert four things. Every listed variable is pinned, and an unset one is pinned to `""` rather than left out, because left out the project's value wins. No credential reaches the argv. The pins and the write set share one `--settings` placed before `--`, because a second one drops the first. And the pins are read off `cycleEnv`, so a local cycle's are its own server. The census in "the cycle adapter" now lists `--settings` too. Mutated in the compiled copy, dropping the `env` half failed two cases and dropping the `""` fallback failed two. `assistSettingsArgs`' six cases in `review.test.ts` hold the reviewer's flag to the same things, a stock install's `null` overlay included, because before board task `dcd92557` that install sent an assist no `--settings` at all. The fifth pins `disableAllHooks` with and without a write set: before board task `9ec70b90` a checkout's hooks reached its own validator's request (measured), and it failed on that code. The sixth pins `apiKeyHelper: ""`: before board task `d704ceae` a checkout's helper ran in its validator (measured), and it failed on that code. `cycleEnvPins`' own seventh does the same for the cycle (board task `9d7770b6`): `apiKeyHelper: ""` in its one `--settings` with pins and a write set, with pins alone, and with neither, because the helper pin is not tied to `envPins`. Run on the unpinned source it failed, as did the two older cases whose assertions, now rewritten, had said a cycle with nothing else set carried no `--settings`, or the pins alone.
