# Provider sign-in: the Claude and Codex auth modules

[← testing index](../testing.md)

Read before adding or editing tests of `claudeAuth.ts` or `codexAuth.ts`. What the credential routes write to the audit trail is pinned in `credential-audit.test.ts`, in [auth-config-and-status-routes.md](auth-config-and-status-routes.md).

`extractLoginUrl` / `parseAuthStatus` / `normalizeCode` in `claudeAuth.ts` (`claudeAuth.test.ts`) earn theirs on the `parsePlanUsage` grounds — three parsers reading another program's console output, captured from the pinned CLI rather than read from a spec — with the added point that two of the three fail in the *wrong direction*: a status shape the parser no longer recognises reads as **signed out** unless it insists on the field it keys off, which is a Sign in button in front of somebody already signed in and a Sign out button they can no longer reach, and a URL not found is a Sign in button that silently opens nothing.

`extractDeviceLogin` / `parseCodexStatus` / `normalizeApiKey` / `redactSecrets` in `codexAuth.ts`, pinned in `codexAuth.test.ts`, are the same four questions for the other provider, on fixtures captured from `codex-cli 0.153.4` rather than from any spec, and two of them are sharper than their twins because that CLI is less helpful. `parseCodexStatus` has to read *text* rather than an exit code, since `Not logged in` and `Error checking login status` both exit 1 — and the reason the split matters is worse here than next door: a device sign-in **deletes the stored credential the moment it starts**, so an unreadable `auth.json` collapsed into "signed out" puts a button in front of the operator whose first act is to destroy what is there. `extractDeviceLogin` must find a link *and* a code or neither, because the two arrive in separate writes and a link accepted alone opens a sheet the operator cannot finish; its host check is `extractLoginUrl`'s, and the case that is not next door's is that the code is taken from **after** the link, so a code-shaped token in a future version's banner cannot be handed over as the thing to type into OpenAI.

`redactSecrets` is the fourth and has no twin at all. It is the last thing between CLI output and an HTTP body, and it fails in both directions with nothing on the page looking wrong: too loose and the CLI's own `sk-proj-***67890` mask — the only thing telling two API-key installs apart — is blanked out of the row; too tight and a CLI version that echoes a key writes it into a response. Both signs are pinned for that reason. `normalizeApiKey` is `normalizeCode`'s shape with one case added on the same argument: no refusal may quote the value, an error message being the part of a failed request that gets kept.

The host check on the URL is tested rather than commented because that string is rendered as the link an operator is asked to enter Anthropic credentials on.

`normalizeCode`'s refusal of interior whitespace is the third: the code is the one value a person types that reaches a child process, it reaches it on stdin, and the CLI reads one line — so a value carrying a newline answers this prompt with its first half and whatever is asked next with its second.

What is deliberately *not* unit-tested there is the spawn half, for `spawnAssist`'s reason — it needs a real `claude` — and the three outcomes that matter were measured by hand against the pinned CLI instead: a code the CLI rejects locally leaves the child on its prompt and the link reusable, a well-formed but spent code exits non-zero and ends it, and neither touches the credential on disk.

The exception is `beginLogin, started twice at once` in both files, which spawns a stub CLI on `settleOnExit`'s terms: the fault was a sign-in child nothing could reach — two overlapping starts both spawned, the second stored over the first without killing it, and the orphan's timer later cancelled the live login — and only a process shows one left running. A mocked clock pins that a timer expires only its own login. `the sign-in child's exit` in `claudeAuth.test.ts` is the same kind: that module acted on its child's exit only inside a submit, so a child that left on its own stayed pending behind a dead link for ten minutes, and a submit ended by a kill left its 100 ms rejection poll firing for the life of the process. `a code pasted from a superseded sign-in link` is the third: after two starts, a code naming the replaced login must reach no child — the stub logs every line it reads against its pid — and the newer login must stay pending and still redeem its own, because written to the newer child the stale code spent its one exchange and ended both sign-ins.
