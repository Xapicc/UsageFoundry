# The merge queue

[← testing index](../testing.md)

Read before adding or editing tests of `mergeQueue.ts` and its drain, and of what a restart does to a row caught mid-merge. The tests of the resolution a queue row buys are in [conflict-resolution.md](conflict-resolution.md).

`mergeQueueOrder.test.ts`, which opens the database, is in the SQL as well, `chatOrder.test.ts`'s grounds one table over: `nextQueuedIn`'s ORDER BY is the whole of what decides which branch is merged next, and reading the per-batch `position` first sorted a batch queued while the worker was still draining an earlier one into the middle of it.

It also pins the repository term beside it — that a branch in one repository stays eligible while another repository's is in flight, and that within one repository nothing does — because those are one question and the way to get the first is to drop the second.

Nothing crashes — every item is still re-previewed against git at its own turn — so all that is lost is the operator's sequence, in merge commits in a directory they own, with nothing afterwards to say that was not the order they chose.

It drives the selector the way the worker does, settling each row and asking again, because a comparator beside the query would be a second copy of the rule and the copy is the one that would stay right.

`mergeQueueView.test.ts`, which opens the database too, is that same table once more, and its decision is in the SQL too: `selectQueueBatches` is the rule and is tested pure, but the query that fed it never consulted a rule at all — it took the newest `batch_id` — so what `mergeQueueView.test.ts` pins is that the answer the page is handed covers every batch the worker can still act on, and that Cancel reaches one that is not the newest.

`mergeQueueDrain.test.ts` is the drain's own three writes, named beside `planItem` / `selectQueueBatches` in the list of what `npm test` covers: it is the only thing in the process that can move a row off `landing` or `resolving`, and no pure function reaches it.

Its fourth case is a branch already on its target by its turn: the batch's first row carries the second's commit, so the second finds itself in `main`. It must end `already-landed` and read back through `queuedBranchOutcome` as no failed landing; before the fix it ended `failed`, which failed the workflow merge block over it and stopped the loop around that block. `queuedBranchOutcome`'s own cases in `workflows.test.ts` pin the other half — the queue's `skipped`, a repository the checkout halted, still reads as failed.

Its fifth to eighth are one case in four variants: two links of one `continueBranch` chain queued in one batch, in both orders and under both `merge` and `squash`, which is what a workflow merge block wired to both ends of the link queues. No row may end `failed`, the owner alone may land, and both links' files must be on `main`. Three of the four failed before `enqueue` queued only the owner — the first link was failed with the owner refusal whenever it came first, and under a squash when it came second too, because `landed_tip` is written on the owner alone — and the one that passed, owner first under `merge`, is the control that shows the harness can tell them apart.

Its ninth and tenth are that pair a batch apart, which `enqueue`'s same-batch drop cannot see. In the ninth the owner squash-lands in one batch and the first link is queued alone in the next: it must end `already-landed` with the squash sentence and read back as no failed landing. In the tenth the first link squash-lands alone and a second link continues the branch with no commit of its own, which makes it the owner: its `landState` must read `landedUnchanged` and refuse Land with the squash sentence, its `branchInventory` row must read `landedUnchanged`, and queued alone it must end `already-landed`. Both failed before `landedUnchanged` was read across the chain — the ninth `failed` with the owner refusal, the tenth with nothing blocking a second squash — and the tenth's inventory assertion fails on its own with `branchInventory`'s per-run read put back.

Its eleventh is a first link queued alone with auto-resolve while its completed owner is not selected, conflicting with `main`. It must end `failed` with the owner refusal, `resolve_cost` 0, no `resolve` row on either link and nothing spawned. Before `planItem` asked the run's half of the refusal first, the queue spawned a resolution for the link, which the stand-in left unresolved, and failed the row with its rollback sentence and its cost. That case needs a `claude` that can spawn, so the file's `CLAUDE_BIN` is a stand-in that appends its working directory to a file and reports $0.37 without touching anything, where it used to be a missing path: it bills nothing either way, and every case can now see a spawn it did not expect. `CLAUDE_CONFIG_DIR` is set beside it because a regression of this case reaches `assistRefusal`'s window read. Its pure twin is in `mergeQueue.test.ts`: `planItem` over the owner refusal with a `conflict` preview returns `fail` with that refusal, where it returned `resolve`.

Its twelfth is the eleventh's shape from the certification side: a completed run with `provider = 'local'` queued alone with auto-resolve, conflicting with `main`. It must end `failed` with the conflict and `resolutionCertificationRefusal`'s sentence, `resolve_cost` 0, no `resolve` row and nothing spawned. Before `planItem` asked `certification`, it measured (2026-10-06, on `164001e`) one spawn, `resolve_cost` 0.37 and the stand-in's rollback sentence; a resolver that succeeded would have met the gate at `landRun` instead, which is read from the code. Its pure twin in `mergeQueue.test.ts` gives the branch an approval of its current tip, the case `certificationRefusal` alone would wave through. Both fail with the check taken out of `planItem`. A third pure case gives the conflicting state a seeded `.env` (`seededRefusal`): it must fail with the conflict and that sentence rather than resolve, and resolved before `planItem` asked `seeded`.

Its last case is that drain at a shutdown, last in the file because `shutdownRuns` sets a flag nothing clears. A `GIT_BIN` stub holds two workers part-way through a land until the case writes a release file, one inside its `git merge` and one inside `landState` with its row already `landing`, and a third branch is queued behind the first. The shutdown must not return while either row is unanswered; the first must end `landed`, the second `failed` with `landRun`'s shutdown refusal and its checkout's `HEAD` unmoved, and the third still `queued`. Taking out the wait on `trackLand`'s set, the drain's own registration of the row, `landRun`'s two reads of the flag, or the drain's read before each row each failed it at its own assertion. Release files rather than sleeps, because a case timed with sleeps passes whenever the machine is slow enough for the merge to finish before the shutdown begins.

The four before it are a checkout somebody else holds. A manual Land held inside its `git merge` and a Deliver held at its first `git remote` (the stub holds `remote` for this) each take `landing`'s claim while a batch of two clean branches is queued into the same checkout, and a third case puts a `running` run in the checkout instead. The rows must stay `queued`, the head one saying what holds it, and land once the hold is gone. All three failed before `landRun` marked those refusals `heldCheckout`, with both rows `failed` on its sentence — the working run's case too, which the task that found this had only inferred. The fourth cancels a batch waiting behind a held land and must find its row `cancelled` and its branch not on `main`; it fails with `requeue` changed to leave the row `landing`, which is the choice it pins. Each case clears its hold files, or the shutdown case's `holdAt` is answered by a stale `.started`.

The one before those is the boot after a resolution was cut off in the run's own slot, stranded by hand as a restart leaves it: a queue row `resolving` over a checkout with `MERGE_HEAD` and a `UU` file. Before `reconcileMergeQueueOnBoot` aborted that merge, Commit followed by Land put its markers on `main` as a fast-forward, so the case boots and then presses both, and asserts the slot is closed first, since `commitRefusal` alone would also pass the rest. Its companions each fail before the fix they pin: `commitRefusal` and `purgeRefusal` refusing a live resolution and `commitRefusal` refusing every unmerged status code or an open `MERGE_HEAD` (`land.test.ts`), with no mid-merge case for `purgeRefusal` because Purge is the door that discards those leftovers; `resolveCheckout` refusing such a slot without saying to commit it; `after` no longer calling a branch unchanged when its open merge was committed underneath it (`resolutionSilence.test.ts`, the one fixture with a live child); and `reopenRun` refusing while a resolve row or a queue row at `landing`/`resolving` holds the branch (`orchestrator.test.ts`).
