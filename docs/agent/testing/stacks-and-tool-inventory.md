# Stacks, the tool inventory and the end of the function list

[← testing index](../testing.md)

Read before adding or editing tests of `stacks.ts`, `stackRequests.ts`, `scripts/apply-stacks.mjs` and `toolInventory.ts`, or of the functions at the end of the list of what `npm test` covers (`workspace.ts`, `cycles.ts`, `format.ts`, `jsonRequest.ts`, `canvasGraph.ts`, `unsavedWork.ts`, `logLine.ts` and the rest named there).

`toolInventory.ts`'s four (`toolInventory.test.ts`) are one page's claim about what an operator's agents can run, and every one of them is wrong quietly. `parseToolList` splits two variables whose separator rules deliberately differ — a comma separates `UF_GH_EXTENSIONS` and belongs to the value in `UF_PY_TOOLS` — so getting it backwards draws two rows for one pinned entry, neither of which the container ever tried to install. `resolveOnPath` decides whether a tool is *there*, and an empty `PATH` element means the current directory, so mishandling the one a trailing colon writes by accident moves every row on the page at once. `composeState` is the six-branch composition, and its expensive direction is one-way: `installed` drawn over a resolution that failed is a page telling an operator that the thing costing them money is fine. `commandPositionNames` is the only one whose grounds are a measurement rather than an argument — the leading-prefix test it replaces was measured at 10.5% recall against this install's own history — 105 commands beginning `gh ` against 1,000 that invoke it at a command position, over the 53,833 `Bash` rows in the 30-day window — and at that rate no tool ever leaves `unverified` and the reading stops carrying anything at all.

The stacks applier's five (`applyStacks.test.ts`) are the same page one mechanism over, and the shift is that a stack is an artifact **somebody else wrote**, so a refusal that does not fire fails on a machine its author never had. `parseStack` is the whole refusal list and two of its branches exist only because a second worked example found them: one `sha256` against a URL carrying `{arch}` names two files and can be true of at most one, which installs on the author's architecture and fails the digest on the other, blaming the consumer's hardware in a message nobody wrote. `refuseEnv` is `01b-` §2.2's table, and its first row is the purest instance of a silent failure in this repository — a `UF_`-prefixed key is set by the applier and then deleted by `childEnv` on the way into every agent, so the variable is configured, present on the server, and absent everywhere it was meant to matter. `expandTokens` is two spellings of one switch, `dpkg --print-architecture` saying `arm64` where `uname -m` says `aarch64`, and the assertion that earns its place is that `{arch}` must not eat the first half of `{arch_uname}`. `reconcile` is the only one here whose wrong answer is **unrecoverable**: it decides which paths a boot deletes, and the rule is that it removes only paths its own receipts record — verified against a real volume on 2026-09-12, where a file dropped into the toolbox by hand survived the boot that removed the stack beside it. Its other two rules are quiet rather than destructive: a reinstall that took `state/` would throw away a provider cache and cost a slow work cycle nobody could see, and a failed stack skipped rather than retried would make the receipt set a record of the boot that first failed rather than of this one, which is the latch `/api/status` exists not to have. Two more cases in that file, added with `RESERVED_BIN_NAMES` and `TOOLS` (board task `1bc44141`), are about root rather than about an author. The reserved-name refusal is asserted for both shapes a `bin` entry is written in, and beside it every stack in the operator's `./stacks` on 2026-10-04 is parsed from a copy in the file — copied because `stacks/*` is git-ignored, and a case reading the directory would pass on every clean checkout having parsed nothing. That case passes before and after by construction: it is the bound on the list, since a reserved name the `python` stack links would refuse a stack nobody changed, at boot, on the operator's machine. The other spawns the applier, the file's one spawn, under a `PATH` that starts with a planted copy of every tool it runs, and asserts none of them ran; without `TOOLS` it ran the planted `dpkg` and `curl`, which as root on a real boot is a stack's code. Three more, with board tasks `aff25da4` and `76b451aa`, are about what reaches root rather than what a stack may declare. `refuseEnv`'s reach case in `applyStacks.test.ts` asserts the loader, interpreter, shell-startup, proxy and trust-store variables are refused — every one of them passed before — and, in the same breath, that `PIP_REQUIRE_VIRTUALENV` and an `npm_config_` key still are not, because a denylist that grew into the tool's own configuration would refuse the operator's `python` stack at boot. `agentEnvironment` (`stacks.test.ts`) is the merge every builder for a dropped child starts from, and its two precedences are each silent when reversed: a stack's value over an operator's — blank included — is a stack quietly redirecting something configured by hand, and the server's `PATH` over the agents' is every stack tool `command not found`. `pruneEnv` (`contextPruning.test.ts`) is the one builder that must **not** start from it, since winnow is root, and the case plants both a stack's `PYTHONPATH` and a distinct `UF_AGENT_PATH`, asserts the agents' environment received them — without which the case passes having planted nothing — and asserts winnow's received neither. It sets the server's own `PATH` rather than reading it, because a suite run inside an older image inherits one that already starts with the toolbox, which is how its first draft failed here. That case cannot fail against the tree before the change, which had no `agentEnvironment` to compare with; the defect was a merge in `instrumentation.ts`, which no pure function reaches, so it is a guard against the merge coming back through `pruneEnv` rather than a reproduction of it. `parseReceipt` (`stacks.test.ts`) is the reading end of the same boundary, and the branch that earns it is the truncated receipt a container killed mid-write leaves behind: a partial `ok` is the read-back reporting an install that did not happen, which is the failure the whole page exists to end, reintroduced by the thing that reports it. The install floor on `invocationCounts` is the one reading here that is a query rather than a pure function, and it is on the list because it is the only branch of that query whose wrong answer is a count that is too **high** — a command name outlives an install of it, and 20 `shellcheck` calls in the retained window against a binary four minutes old composed to `installed` before the floor existed.

A run's request for a stack (`stackRequests.test.ts`, `stackWait.test.ts`) is the same boundary crossed the other way: text from an agent nobody is watching, headed for a person who may act on it. `normalizeStackRequest` earns its cases on the name, because the name is printed inside the path the operator is told to create and a name the applier would take as a directory — a space, a `;`, a `$( )`, a leading `.` — is a shell line dressed as one; the cases pin each of those refused and a plain one accepted with its repeated binary folded. `decideStackWait` is the release, and both of its wrong answers are silent: resume too early and the next cycle meets the same missing binary under a notice saying it is there, never resume and the run waits for ever on a stack that is installed. A decline outranks a request still pending, a failed receipt keeps the run waiting and names the failure, and a run attached to nothing resumes. The case that earns `stackSatisfaction` its place is an agreement rather than an answer: `request_stack` asks it before filing and the release asks it before resuming, and over every receipt shape the test builds, whatever the tool would file the release must keep waiting on — the two disagreeing is a run that parks and resumes in a loop with nothing installed. The dedup cases open the database because one pending request per name is what makes the operator answer once for every run that asked: the second run attaches rather than filing, the request's binaries are the union, the first draft is kept rather than replaced under an operator who may be reading it, a run the operator declined cannot re-file, and a request the receipts already answer writes nothing. `checkStackDraft` is asked of the real `scripts/apply-stacks.mjs`, so its accepted and refused cases are the boot parser's own words, and a missing file must read `unchecked` and never `accepted`. `stackWait.test.ts` drives the real run loop against `parksAndRefunds.test.ts`'s stubbed child, because the park is decided in `startRun`'s ladder and nothing pure says where: a run on the default cap of one that asks and replies `DONE` in the same cycle must park rather than complete, with the cycle refunded, `paused_at` open and `reported_done` cleared; after the receipts gain the stack and `stackGrants()`' cache is re-primed — what a restart does — the release must resume it into the same session with `Bash(cargo:*)` on the resumed cycle's `--allowedTools` and the notice as its prompt. Its other cases are a failed receipt that must not release, a Stop that closes the park and leaves the request pending for others, a decline whose notice names `NEEDS_REVIEW`, and `reconcileOnBoot` keeping a week-old wait that a `paused` row of that age would have lost.
