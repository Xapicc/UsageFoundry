# Loop blocks and their passes

[← testing index](../testing.md)

Read before adding or editing tests of loop blocks: `planLoopPass`, `passMemberId`, `loopSection`, loop merge ownership, `loopBoardCount` and `normalizeWorkflowInput`'s loop refusals in `workflows.ts`.

`planLoopPass` earns its two because it is correct today by the *shape* of `r.status !== "completed"` rather than by intent, at a cost of one whole run per pass if a rewrite into an explicit list of failure statuses restores the defect — and the half that matters is `assert.notEqual(d.kind, "wait")`, which is what a missing `TERMINAL_STATUSES` entry produces: a loop block that waits for ever, holding everything behind it, with nothing on any page saying why. Its ordering cases are earned separately and by the same standard: the rung a stop is reported on is what the operator reads to decide whether to raise a cap, so a board condition that outranks `reportedDone` tells somebody to go and look at a backlog the agent has already finished, and one that ranks below the caps reports a loop that emptied its project as a loop that ran out of money. Both are one word in one sentence, both typecheck, and the tests are the only place the order is written down as behaviour rather than as a comment. `passMemberId` and the pass grouping are held to that same bar one function along, and earn it for the two ways a repeated *section* goes silently wrong. The member id is a format written in one place and parsed in three — `loopPasses` groups on it, `land.ts` names the pass holding a branch from it, and the instance DTO takes a row's pass and its block off it — so a format and a parser that drifted apart is a loop reporting one pass of six where there were three passes of two. Its prefix case is the one that is easy to lose: every row a loop causes has to sit under it, including a run an orchestrator member decided on, because that is what `loopSpend` sums and a run outside it is money a pass spent that its cap cannot see. The grouping earns its own on the arithmetic — three passes of two read as six passes of one trips a cap four passes early and reports it as the loop running out, six read as one never trips it at all — and the cases that matter most there are the two shapes real data produces and a fresh graph cannot: a member whose `runs` row has gone, which must be an empty slot rather than a missing pass, and a pass all of whose members have gone, which is the only way `planLoopPass`'s "started nothing" stop is reachable outside a creation that threw. The section refusals in `workflows.test.ts` are there because each stands in front of a failure that is either silent or arrives an hour into an instance, and the two ends of a section are the clearest of them. A section that ends anywhere but at a merge block is the worst of the set and is the one to keep if any go: nothing throws, nothing is refused at run time, and the next pass simply starts from a branch that cannot see the last pass's work — an agent redoing finished work, one billed pass at a time until the cap catches it. Its sibling, a section that ends in two places, earns its own because it is the same fact from the other side and the test is what pins the decision to answer both halves in one sentence. The run-count arithmetic earns three: the ceiling case, the exact-60 boundary, and an orchestrator inside — that last one because the fan-out term is the whole cost of letting one into a section and it is arithmetic nobody does, so a reading that charged a fan-out cap once for the loop instead of once per pass would be off by a factor of the pass cap and would still look like a working refusal. The refusals for a loop's own fields are a table-driven case rather than six, and they earn it together: each is a value the operator typed and no process would act on, and the failure a test catches is not the refusal going missing but the field being *coerced* away — which typechecks, saves, and runs a graph the operator did not write. The one thing no test here can reach any more is the loop that repeated its own task: `resolveSections` refuses a loop with no `repeats` link, so the shape survives only as an instance blob an older build wrote, and `bootBlocks.test.ts` is where one is inserted.

`loopSection.test.ts` is the one loop file that opens a database, and it earns that for the half `planLoopPass` cannot reach: a pass is the section run as a graph, and what `createRun` was actually given — the member ids, the `emitted_by`, the dependency rows and which branch each one carries — is decided in the wiring rather than in the decision. Four of its cases are the ones to keep if any go. **Nothing may carry a branch between passes**: every dependency row of every member is checked for `continue_branch`, because a pass that continued the one before it would be building on a ref that pass had already landed and may have deleted, and nothing on any page would say so. **Pass 2's entry is created after pass 1's merge block finished landing**, which is the other half of the same rule and the one that cannot be read off a status: a pass that started early would redo finished work, billed, in silence. **A pass whose merge lost a branch stops the loop**, because a merge block that failed still *finished* and such a pass looks complete from every other angle. And **DONE is every run member**, which is checked from both sides — a pass where all of them say it stops the loop, and a pass where only the section's entry says it takes another — because with a section that forks there is no last-run-of-a-chain, and a loop that read one member's DONE would stop while the rest was still finding work.

Its fixture shape is the note worth keeping. The instance rows are inserted rather than instantiated because `startWorkflow` probes the disk for a real worktree on every block of a section, and this file is about what happens after a loop is released; a **real git repository** is still needed, because a merge block resolves every branch in front of it against the disk and a plain directory gets none — after which the pass's merge fails by name, which is the right refusal about the wrong thing. **A concurrency cap of 1** is what keeps every member at `queued`, and it is the lever rather than folder occupancy: a member that isolates takes a checkout of its own and is released past a busy folder, after which it spawns against a `CLAUDE_BIN` that does not exist, fails *asynchronously*, and rewrites the status the test has just set. `settleQueuedRuns` writes the branch columns a release would have written, and gives each run its **own** branch, because that is what the section's links say here and what a pass's runs do. The merges land nothing — every branch sits at its own base, so `branchVerdict` skips it — which is deliberate: what is under test is the loop's reading of a merge, and git's own answer for one branch is `mergeQueue.ts`'s subject. The orchestrator member is driven through `emitBlockRuns` and `settleBlock`, the door a real turn's child comes back through, called in the same event-loop turn that claimed the block so that the spawn already fired against the missing binary settles nothing.

`loopMergeOwnership.test.ts` earns a database, a real repository and a real merge queue for the one question neither of its neighbours can ask: **who** may land a branch a live pass owns. It exists because the two files that should have caught the defect both passed. `land.test.ts` and `mergeQueue.test.ts` assert the decision each door makes, and each was right for the asker it was written for — a person. `loopSection.test.ts` drives a pass end to end, but its branches sit at their own base, so `branchVerdict` skips every one and no pass in it has ever reached the merge queue. **A commit on the branch** is the whole of what makes the defect reachable, and it is the fixture note to keep: `commitOnBranch` stages its own file rather than `-A`, so the dirty-checkout case can plant an untracked file in the tree without having it swept into the branch, and the parked concurrency-holding run sits *outside* the repository, because `landRun` refuses to merge into a folder an active run is working in and that refusal is the fixture's scaffolding rather than the rule under test. The case to keep if any go is the first: one pass, one member, a branch with a commit, driven through `advanceInstances` into the queue and into the operator's own `main`. Before the fix it produced the sentence a real install produced on ten branches — a merge block refused by the hold its own pass owns, the pass landing nothing, and the loop stopping correctly on a refusal that was wrong — and the status alone could not have caught it, because `failed` is a real outcome with a dozen causes; the assertion is on the sentence *not* appearing. The four door cases pin the half that did not change, one per door and each on its own wording, and the exemption cases pin its edge: a later pass of the same loop, another instance's merge block, and a batch nothing queued are each refused exactly as a person is, because an exemption that widened by one pass would hand a live pass's branches to the pass behind it. The resolution door gets its own pair on a branch that does not conflict — the owning pass reaches the honest "nothing to resolve" answer one check past the hold and a person does not — which is how that door is asserted without building a checkout or spending anything, and it is the door that would have spent.

`loopBoardCount` earns a file of its own, with a database and a directory tree in it, because the defect is a comparison between two spellings of one folder and nothing in a type tells them apart. A loop's board condition holds a path **within its mount**, as the folder the block runs in does; `tasks.folder` holds the absolute path `resolveTaskFolder` proved when the task was filed, and `listTasks` matches that column exactly because `normalizeTaskListQuery` deliberately does not re-resolve. Compared as saved, `backlog` never equals `/workspace/board-mount/backlog`: the count is zero for every project for ever, every loop with a condition stops before its first pass, and the wrong answer is a legitimate one — a clear board is precisely what the condition is asked to detect — so there is no symptom to notice on the run it was bought to save. It files through `normalizeTaskInput` *and* `createTask`, the pair every real door is, because the resolution happens in the first of them and a fixture that skipped it would store the relative spelling the defect compares against and pass on the broken reader. The sibling-folder case is what makes that load-bearing, since a reader resolving neither side also returns zero there; the unresolvable folder earns its line because zero is the one answer that ends a loop, so a project this app cannot find must not produce one.

The thresholds put four more cases in that file and they are the same bargain one field along. Two folders whose names share a prefix is now a pair that exists on disk — `backlog` and `backlogWeb` — because the widened match is a `LIKE` and a prefix written without the separator counts the second project's tasks as the first's: silent, and in the direction that keeps a loop running, since a project counted too full never reaches the number it was told to stop at. The per-priority case asserts all four figures move independently of the total, which is what says the reading cannot be missing one the decision needs. The default-off case is a claim about the *board's* grouping rather than about this reader — `backlog/docs` is a different project — and the old-shape case drives a node spelled the way a graph saved before thresholds existed spells one, through the real reader, because nothing re-normalises a stored blob and the compatibility reading is therefore load-bearing at a door no normaliser stands in.

One more case in that file leaves operator-only tasks out of the count, in the total and by priority, and back in once the operator clears the flag. It is silent in the same direction as the prefix trap: no pass can bring an operator-only task down, so a count that included them keeps a loop running to its pass cap with every pass looking as though it did its work.

`planLoopPass`'s board cases gained the any-of rule, which is the one behaviour here that is a *choice* rather than a mechanism: two thresholds, one met and one not, must stop the loop, and the case asserts the sentence names the one that was met — the reason exists to be read a day later against five lines the operator wrote, and "the board is clear enough" is not that. Its old-shape case is the same claim as the reader's, asked of the decision instead, and both are cheap because the single-number shape is a literal.

`normalizeWorkflowInput`'s refusals earn their lines on the existing grounds — each is a condition that is already met the first time it is asked, which is a loop that never starts a run and says nothing about why — with one addition that is quieter than the rest: a priority named twice leaves a working condition in which the larger number silently decides, so the smaller is a line somebody wrote that can never fire, and nothing about it looks wrong.

The three cases around a loop's own task earn their lines on where the question is answered rather than on the answer: the refusal used to live in `normalizeNode`, which cannot see the `repeats` link a section is derived from, so the one block whose task is never sent to an agent was the one block that could not be saved without one and the way past it was text nothing would read. A section loop saving with an empty task, a section-less one still refused by the sentence it has always had, and a leftover task kept rather than cleared are the three halves of that move, and each fails silently in its own direction — a refusal nobody can satisfy honestly, a billed run per pass with nothing to do, and the operator's own words disappearing on save.

Deliberately **not** tested: `STATUS_TONE`, `GLYPH` and `describeRun`, where the compiler is the test and a rendering earns one only when it pins something a reader would act on that is wrong in a way that typechecks; and the two SQL denylists, whose failures are a criterion to check by hand (`admitDependencies`, which has a visible symptom) and a read of the diff (`branchChain`, which has none at all).

`planInstanceStep` and `planLoopPass` each earn cases for a run left behind, and `loopSection.test.ts` earns four more against its database and repository. The waiver is silent in both directions: a scheduler that ignores it leaves the pick-up doing nothing, and one that honours it by resolving *through* the run lands the branch the operator chose not to — which is why the database case asserts the merge was handed the other run's branch and not that one. The other three are the ways through a stopped pass that nothing else reaches: a member resumed through `reviveBlockedBlocks`, whose pass id names no node of the graph; a failed merge retried once its branch exists; and the refusals — a completed run, and a loop that ended on its own terms — writing nothing. The left-behind case was checked failing with `passState`'s filter removed.

`loopSection.test.ts` earns two more for a loop that cannot decide while its pass is still working — a board condition whose folder is removed mid-pass, and an instance graph whose loop carries no `maxPasses`. Each asserts that the loop stays `looping`, the pass's merge stays `waiting` and the block behind the loop is not created while the pass works, then that the merge landed before the loop failed. The failure is silent and permanent: a loop failed mid-pass releases an `on-finish` block into folders its pass is still working in, and the pass's unreleased members sit at `waiting` for good, so the instance never finishes and `pickUpsOf` offers nothing. Both were checked failing before `advanceLoop` stepped an unsettled pass ahead of those two reads.
