# Container, compose and backups

[← testing index](../testing.md)

Read before adding or editing tests of `Dockerfile`, `docker-compose.yml`, `docker-entrypoint.sh` and the backup and restore scripts.

`deployment.test.ts` pins `Dockerfile` and `docker-compose.yml` against each other, that the directory compose sets `DATA_DIR` to is `chmod`ed 0700 in the image and reclaimed by the entrypoint on every boot, because `/data` is a *named volume*: Docker copies that directory's mode onto a fresh volume's root and never revisits it, so the mode is the whole of what keeps the database, the settings every guard reads and the server lock away from the children — and an *existing* volume, which is what every deployment with data in it has, keeps the old `node:node 0777` through any number of image pulls.

That file asserted the opposite until the uid split landed and it was deliberately inverted: the old rule was sound on its own premise, that one uid ran the server and the agents and a fresh volume had to be writable by whatever `${UF_UID}` was.

And, since the two files now express a uid boundary rather than one uid, that compose runs the server as root while handing the operator's own uid to the children through `UF_AGENT_UID`/`UF_AGENT_GID`, and that no `USER` line in the runner stage takes back the privilege the drop needs.

It also pins the *group* the chat and block child runs in against the group the image creates — `UF_CHAT_GID`'s compose default and the `groupadd` in the Dockerfile are only a boundary together, and the drift is invisible because the kernel checks numbers rather than `/etc/group` — and that the default is not the agents' own gid, which `privsep.ts` refuses at boot but which nobody would ever *see* refused if it shipped that way.

Dropping either half is silent in its own direction: no root and the server cannot switch uids at all, no agent uid and every child runs as root, which is worse than the shared arrangement the split replaced.

It clears the bar for the same reason — nothing else here notices.

It typechecks, it builds, and it passes on macOS, where Docker Desktop's bind-mount remapping makes 1000 right whatever the host uid is.

It pins a second agreement of the same kind, the `HEALTHCHECK` against the route it probes: a directive pointed at a path that has gone reports every container unhealthy for ever, and one pointed at `/` reports a server that cannot open its database as *healthy*, because under `UF_AUTH_TOKEN` that path is a 307 to `/login` and `curl -f` accepts a redirect.

It carries a third group of the same kind, about the one thing in this deployment with no second copy: that the image ships `scripts/backup-db.mjs` and `scripts/restore-db.mjs`, that `sqlite3` is in the runtime apt list — tokenised rather than matched as a substring, because `better-sqlite3` in the comments beside it satisfies any looser test — and that the backup destination compose mounts is *not* inside `DATA_DIR`, since a snapshot kept in the named volume dies with the one command it exists to survive.

It carries a fourth of the same kind, this one wholly inside compose: that `NODE_OPTIONS`' heap ceiling leaves room inside `mem_limit` for the children the container exists to supervise, and that `memswap_limit` matches `mem_limit` so the stated ceiling is the ceiling — Docker defaults the swap limit to *twice* the memory one, and a server permitted to fill the cgroup by itself never throws V8's own heap error, it gets the container OOM-killed and restarted with every run in flight failed.

It carries a fifth, the three-file agreement behind `UF_PY_TOOLS` — the directory the entrypoint installs into, the named volume compose mounts over it, and the `mkdir` that makes the image own it — on the grounds the `UF_GH_EXTENSIONS` group beside it already states, and one more that group does not have. A `gh` extension lost to a rebuild is at least an `unknown command`; these are invoked by a *plugin's hooks*, and a hook body ends in `|| true`, so a tool that is gone makes the hook exit 0 having done nothing and the plugin goes on announcing itself — 213 sessions of exactly that were what prompted the mechanism. So it pins a fourth file the gh group needs no equivalent of: that `UV_TOOL_BIN_DIR` is on the image's `PATH`. `gh` resolves its own extensions, where `uv` writes launchers into a directory and stops, and off `PATH` every tool here is present, correct, owned by the right uid, and never found. The three `UV_*` variables are pinned to point inside that volume for the same reason the volume exists: uv's defaults are under `$XDG_DATA_HOME`, which is the writable layer the rebuild discards. What is deliberately *not* pinned is the editable branch — that an absolute path is installed `--editable` and exempt from the already-installed test. It is shell logic with no cross-file half, a regex over it would break on any rewording, and its failure is visible rather than silent: the boot log says `(editable)` or it does not.

It carries the same agreement once more for `.claude-local`, the config directory local-model cycles resume their sessions from, and with a fourth party: the entrypoint's `CLAUDE_LOCAL_VOLUME`, the named volume compose mounts there, the `mkdir` in the image — and that the path is the sibling `.claude-local` of compose's `CLAUDE_CONFIG_DIR`, because `config.ts` derives it from that variable rather than naming it, so the volume could sit at a path nothing reads. The failure is the one the volume was added for: after an `up --build` every local run's session is gone and picking one up dies within a second on "No conversation found with session ID".

It carries a sixth, the one whose two halves are a *timer* rather than a name or a path: that `stop_grace_period` in compose is longer than `SHUTDOWN_GRACE_MS` in `orchestrator.ts` by enough for the reconciliation that follows the wait, and that the kill ladder's own SIGKILL step lands inside that wait rather than after it. What the pin buys is that neither number can move alone, and the one that moves is `SHUTDOWN_GRACE_MS` — it is what somebody raises when a slow agent is not dying cleanly, and past the container's grace Docker kills the process part-way through `reconcileInterruptedCycles`. That is the failure `shutdownRuns` was written to end, and half of it fails *open*: `active_started_at` left set on cycles whose agents are gone is a floor `installBudget` and a workflow instance's budget both bound their spend below by, so an unfinished shutdown widens two ceilings at once. Nothing anywhere says so — both literals are valid, both files parse, and `docker compose stop` returns 0 whether or not the server finished. The *timing* is what this cannot reach: Docker is not available here, so the headroom is a floor chosen to fail on the edit and not a measured shutdown, and `docs/verification.md`'s "Not yet verified by hand" carries the command that would time one.

It carries a seventh, and it is the only one of the group with a *single* file's value on one side of it: that `docker-compose.yml` declares a `logging:` block at all, that the block pins `json-file` — `max-size` and `max-file` are that driver's own options, and handed to a daemon defaulting to journald they refuse the container outright — and that `max-size` x `max-file` is wide enough to hold a full day of the worst case that writes to stdout. The grounds are the asymmetry the operations survey found rather than a Docker fact: `run_events`, the checkouts and the transcripts each have a retention horizon, a figure on `/api/status` and a suggested alert, and container stdout, which this app writes ten structured event kinds to on purpose, had none of the three while Docker's default keeps every line for ever. Nothing notices an absent block — compose parses, the container starts, every page works, and the evidence is a full disk on a host nobody was watching months later. The floor is derived from `run.sandbox_refusal` rather than from ordinary traffic, because that is the line that sized the cap: it is on stdout so a policy refusing every tool call is visible without opening twenty-five run pages, and at ~11,000 tool events an hour a cap such a storm empties inside a shift hides exactly what it was widened for. Its third assertion is the cross-file half after all — README's "Logs" has to state the same two numbers and has to keep saying that a cap discards the *oldest* lines, since an operator told 100 MiB who has 20 sizes a shipper and a disk against a window that is not there, and one who does not know which end is thrown away reads a truncated history as a complete one. What this cannot reach is any of it in force: Docker is not available here, so `docs/verification.md`'s "Not yet verified by hand" carries the `docker inspect` that would confirm the daemon applied it.

It carries an eighth, which pins a **doc** against `config.ts` and `middleware.ts` and is the one case in this file asserting no behaviour at all, deliberately: `process.env` is fixed for the life of the process, so every credential this deployment carries needs a container restart to change and there is no changed value a test could observe taking effect. What can go wrong is the *record* of what that restart costs, and it already had — the notification channel arrived as five more variables read exactly the way the credentials are, nothing said so, and the only place the fact lived was a survey somebody happened to re-derive against a moved tree. A restart ends every run in flight, so an operator weighing a leak against that needs the enumeration to be complete, and one short by five is worth the same as none. So the rotation bullet in `docs/agent/environment.md` has to name every variable `config.ts` reads through `optionalEnv`, every `UF_` name compared in the edge gate — the group with no way out, since the edge runtime has no `node:fs` and must not import `lib/config` — the three credentials this app forwards to children and never reads itself, and `DISCORD_WEBHOOK_URL`, pinned off the entrypoint because the server not holding it is the point rather than evidence it is out of scope. Derived from the sources for `namesRead`'s reason: the next omission arrives as a credential added to the code, never as an edit to the doc.

It carries a ninth, which is the sixth's precondition: that `NEXT_MANUAL_SIG_HANDLE` is set in the image's runtime stage and by both npm scripts, that compose does not name it, and that `npm run dev`'s `NEXT_EXIT_TIMEOUT_MS` sits above `SHUTDOWN_GRACE_MS` by the sixth's headroom. Without the variable Next's own handler exits about 0.1s into the signal, so neither grace the sixth pins is ever reached; measured on the standalone bundle, the in-flight cycle was left unreconciled with `active_started_at` still set, the same half that fails open. A blank value is the same as none, which is why compose may not name it: its `${VAR:-}` rendering would blank the image's `ENV`. The server still exits 0, so nothing else notices.

`backupRestore.test.ts` is the twenty-second of the thirty-eight that are neither a function nor a rendering, and it is the behaviour that pinning cannot reach: it drives those two scripts as an operator does, against a real migrated database with a second connection holding a write transaction open, and compares the restored file against the quiesced source object for object and row for row.

Its grounds are that every other check passes on a bad backup — a `cp` of a WAL database opens cleanly, reports `integrity_check ok`, and is silently missing every transaction since the last checkpoint (measured: 25 runs against the snapshot's 386, both files `ok`), and nobody looks at a backup until the volume is already gone.

The refusals beside it are the ones that turn a restore into a second incident: restoring under a live server (which corrupts rather than replaces, and is decided on the *age* of `server.lock`'s heartbeat, because a restore runs in another container where a pid means nothing), deleting the database being replaced or leaving its `-wal` behind for SQLite to replay into the new file, restoring some other SQLite file, and a prune that reaches a file this script did not write.

That first refusal is two cases rather than one, and the second is the one the script was failing: it watched the lock for a *beat* and read a lock that did not move as a corpse, though the beat is a `setInterval` on the server's own event loop and one `gitSync` holds that loop for up to git's 20s ceiling — so a live server inside one had its database renamed out from under its open descriptors, went on committing into an inode nothing would ever open again, and was told the restore succeeded.

The two are therefore the same lock with one thing changed, a heartbeat that keeps moving and a heartbeat stamped once and left alone, and both refuse.

Their control is half of it and a different half from the usual, since a refusal keyed on the lock being *present* passes both: a lock older than `STALE_MS` must still be restored over, which is the boundary `lockVerdict` itself answers `claim` at, and refusing there would refuse every restore after the killed container that is the state an operator reaches for this script in.

The number behind that boundary is the fourth case and is a *copy* — the image ships `scripts/` without `src/`, so the script cannot import `STALE_MS` — read back out of its source text and pinned to the original on `deployment.test.ts`'s grounds, one pair of files over: the drift is silent in both directions, a restore refused against a directory nothing holds or one performed under a server this app still calls the owner.

The fifth refusal is the same word one step earlier — *when* the database being replaced is moved aside — and it is the one refusal here whose failure is not an error at all: with the copy unguarded, a restore that died part-way (`ENOSPC` on the volume, or the container killed) left a data directory holding nothing but a `.superseded-` file whose name the disclosure below the copy never reached, and the next boot created a database at that path, migrated it, and came up green with no runs and no settings.

So the copy is staged under a temporary name and inspected before anything is moved, and what the case pins is that the database is still at its own path with its own rows in it — driven under a `ulimit -f`, which is the only way to make `copyFileSync` fail half-way from a test and is why `runScript` can put a shell between the fork and the exec.
