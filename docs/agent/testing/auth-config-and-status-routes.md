# Auth, credentials, config and the request log

[← testing index](../testing.md)

Read before adding or editing tests of `authGuard.ts`, `sessionToken.ts`, `/api/login` and `/api/logout`, the credential routes, `requestLog.ts` and `config.ts`/`configCheck.ts`. The OTLP ingest's body cap, `http.ts`, `saveSettings`, the settings and stream routes and the run doors' refusals are in [request-bodies-settings-and-run-streams.md](request-bodies-settings-and-run-streams.md), split out of this file on 2026-11-09 when it reached 22 KB. The health and status routes are in [health-and-status-routes.md](health-and-status-routes.md). What bounds guessing at the master token — the limiter, its budgets and its sources — is in [sign-in-limits.md](sign-in-limits.md). The parsers and sign-in children of `claudeAuth.ts` and `codexAuth.ts` are in [provider-sign-in.md](provider-sign-in.md).

`authBootSignal` (`authGuard.test.ts`) is whether anything at all is said about an install that serves every route to whoever can reach the port, and about one whose token is short enough to guess at the rate the limiters allow — pinned both ways, since a warning on the token the docs say to generate is one the operator learns to skip, and on the message never echoing the token.

`config.ts`'s three (`config.test.ts`) each fail *as an ordinary state* rather than as an error — a fifth workspace slot compose never mounted looks exactly like a mounted directory with nothing in it, and the wrong GitHub token **works**, leaving a commit in somebody else's history as the only evidence.

`configCheck`'s two (`configCheck.test.ts`) decide which configurations boot and which are refused, which is the one decision made before anything else can report. A third case and `ignoredGithubVars`' own pin the warning for a `GH_TOKEN` or `GITHUB_TOKEN` in the server's environment, which every child strip drops: it is silent in both directions — an operator who exported one loses a working `gh` with no message anywhere but a refused tool call, and a warning that fired on a blank or unset name would sit on the dashboard of every stock install — and the case feeds a fake token through the same path the boot uses to hold that the sentence never carries the value.

`sessionToken`'s four (`sessionToken.test.ts`) are the whole of what keeps a captured cookie from being the master credential.

`src/app/api/login/route.test.ts` pins what `POST /api/login` puts in the browser's jar and what it does with a wrong guess, from the *response* rather than from a pure half, because a `Set-Cookie` value and a status code are the whole of what a browser and an attacker respectively see.

`src/middleware.test.ts` pins which state-changing requests the edge gate lets a signed-in browser make, and the failure is silent in the worst direction: `SameSite=Lax` ignores the port, so a page on another localhost port — code an agent wrote — had its `no-cors` POST passed on the cookie alone, and nothing anywhere said so. It drives `middleware()` with `NextRequest`s, no database: the cross-port POST refused and the app's own passed, a bearer with no origin passed, the `Origin` fallback judged against the `Host` header rather than the bind address `nextUrl` carries in production, `UF_PUBLIC_URL` for a proxy that rewrites `Host`, and the two credential-free doors refusing only what the browser marks as from elsewhere.

`credential-audit.test.ts` is the file for the routes that take, replace or destroy a *provider* credential — six, plus `/api/local-provider`, whose token this app keeps itself and so could also echo back in its own answer, which is the third place that case looks — and what it exists to pin is a split rather than a value: the request line in `request_log` is written for every outcome including the refusals, and the durable line in `ops_events` is written only when something actually changed. Either half alone is a trail with a hole in it — a route recording only the durable line loses its refusals, and one recording only the request line loses the rotation to the 20,000-row window as soon as an ordinary week of traffic goes through. The negative is the case it is really for: the API key posted to `/api/codex-auth/api-key` and the authorize code posted to `/api/claude-auth/login/code` must appear in no row of either table, nor must the CLI's own mask of a stored key, which is a prefix and a suffix of the secret. It drives the two CLIs through stubs on `CLAUDE_BIN`/`CODEX_BIN` rather than mocking the modules that spawn them, because the credential's whole journey is *stdin* and a mock of the spawn site would assert nothing about that; it also means the Codex sign-in row is written behind the status read that stops a sign-in being reported over an unchanged install, rather than behind an exit code the CLI returns 0 from having read nothing. It also pins the status of a sign-in start taken over while it waited for its link: two overlapping POSTs to either login route answer 409 to the older and 200 to the newer, never the 502 a CLI failure gets, because the request line keeps the status and never the body, and a 502 there sends an operator after a broken CLI over a double press — and the superseded press still writes its request line and no durable row. And it pins the two Codex starts that end without a link after the stub has deleted `auth.json`, which the pinned CLI does before it asks for a code: a cancel landing during the wait and a CLI that exits each write a `warn` row carrying `may_have_cleared_credential`, and a start that spawned nothing writes none. Those rows are the only record of that sign-out, and a missing one fails silently. And it pins that the row follows the mutation's exit rather than the status read after it ([audit-trail.md](../security/audit-trail.md)): the stubs keep their credential in a file and read it at spawn, so a status read held in flight from before a sign-in, key store or sign-out must not be what any of the four answers with, and with the status child failing each one that changed still writes its row, marked `unconfirmed`, and answers "could not confirm" rather than an error.

`login/route.test.ts` gained the other side of the same rule, on the one mutating route that is deliberately not wrapped. `/api/logout` is exempt from the edge gate, so an anonymous request reaches the handler: three of them, alternating branches, must leave **both** tables empty. A row on that refusal would hand anyone who can reach the port a lever on the audit trail, and the durable table keeps 500 rows against `request_log`'s 20,000, so it is the sharper of the two levers rather than the safer one. The revocation that *does* happen is asserted to name the session id and to be written exactly once for a cookie replayed twice — `revokeSession` returning whether it was the call that ended it is what bounds a captured cookie to a single row. The `all` branch is held to the same bound by a cookie replayed five times: one `auth.sessions_revoked` row, for the press whose `closed` was not zero. That branch's 401 checks the cookie's signature and not its `revoked_at`, so the cookie whose own session the first press ended passes it every time after, and it wrote a `closed: 0` warning on each replay.

`requestLog.test.ts` opens the database, and its second case is the one it exists for: the wrapper is handed a body holding a token, a query string holding the same token and a session cookie, and the row must contain none of them — adding a field is the dangerous direction here, and a leak would typecheck, pass everything else and be found by whoever reads the logs.
