# Auth, credentials, config and the status routes

[← testing index](../testing.md)

Read before adding or editing tests of `authGuard.ts`, `sessionToken.ts`, `loginLimiter.ts`, `/api/login` and `/api/logout`, the credential routes, `requestLog.ts`, `claudeAuth.ts`/`codexAuth.ts`, `config.ts`/`configCheck.ts`, `otlp.ts`' body cap, `http.ts`, `saveSettings` and the settings, stream, health and status routes.

`authBootSignal` (`authGuard.test.ts`) is whether anything at all is said about an install that serves every route to whoever can reach the port.

`config.ts`'s three (`config.test.ts`) each fail *as an ordinary state* rather than as an error — a fifth workspace slot compose never mounted looks exactly like a mounted directory with nothing in it, and the wrong GitHub token **works**, leaving a commit in somebody else's history as the only evidence.

`configCheck`'s two (`configCheck.test.ts`) decide which configurations boot and which are refused, which is the one decision made before anything else can report.

`sessionToken`'s four (`sessionToken.test.ts`) are the whole of what keeps a captured cookie from being the master credential.

`loginLimiter`'s two (`loginLimiter.test.ts`) fail in opposite directions, one that never fires being bit-for-bit the unbounded route and one that never lets go locking the operator out of an app whose only other credential is an environment variable and a restart.

`src/app/api/login/route.test.ts` pins what `POST /api/login` puts in the browser's jar and what it does with a wrong guess, from the *response* rather than from a pure half, because a `Set-Cookie` value and a status code are the whole of what a browser and an attacker respectively see.

`src/middleware.test.ts` pins which state-changing requests the edge gate lets a signed-in browser make, and the failure is silent in the worst direction: `SameSite=Lax` ignores the port, so a page on another localhost port — code an agent wrote — had its `no-cors` POST passed on the cookie alone, and nothing anywhere said so. It drives `middleware()` with `NextRequest`s, no database: the cross-port POST refused and the app's own passed, a bearer with no origin passed, the `Origin` fallback judged against the `Host` header rather than the bind address `nextUrl` carries in production, `UF_PUBLIC_URL` for a proxy that rewrites `Host`, and the two credential-free doors refusing only what the browser marks as from elsewhere.

`credential-audit.test.ts` is the file for the routes that take, replace or destroy a *provider* credential — six, plus `/api/local-provider`, whose token this app keeps itself and so could also echo back in its own answer, which is the third place that case looks — and what it exists to pin is a split rather than a value: the request line in `request_log` is written for every outcome including the refusals, and the durable line in `ops_events` is written only when something actually changed. Either half alone is a trail with a hole in it — a route recording only the durable line loses its refusals, and one recording only the request line loses the rotation to the 20,000-row window as soon as an ordinary week of traffic goes through. The negative is the case it is really for: the API key posted to `/api/codex-auth/api-key` and the authorize code posted to `/api/claude-auth/login/code` must appear in no row of either table, nor must the CLI's own mask of a stored key, which is a prefix and a suffix of the secret. It drives the two CLIs through stubs on `CLAUDE_BIN`/`CODEX_BIN` rather than mocking the modules that spawn them, because the credential's whole journey is *stdin* and a mock of the spawn site would assert nothing about that; it also means the Codex sign-in row is written behind the status read that stops a sign-in being reported over an unchanged install, rather than behind an exit code the CLI returns 0 from having read nothing.

`login/route.test.ts` gained the other side of the same rule, on the one mutating route that is deliberately not wrapped. `/api/logout` is exempt from the edge gate, so an anonymous request reaches the handler: three of them, alternating branches, must leave **both** tables empty. A row on that refusal would hand anyone who can reach the port a lever on the audit trail, and the durable table keeps 500 rows against `request_log`'s 20,000, so it is the sharper of the two levers rather than the safer one. The revocation that *does* happen is asserted to name the session id and to be written exactly once for a cookie replayed twice — `revokeSession` returning whether it was the call that ended it is what bounds a captured cookie to a single row.

`requestLog.test.ts` opens the database, and its second case is the one it exists for: the wrapper is handed a body holding a token, a query string holding the same token and a session cookie, and the row must contain none of them — adding a field is the dangerous direction here, and a leak would typecheck, pass everything else and be found by whoever reads the logs.

`readCappedBody` is the ceiling on the one *write* path `middleware.ts` exempts, and its two directions cost different things. A cap that stops firing is bit-for-bit the unbounded read it replaced, on a path reachable without passing the edge gate and buffered in the single process that holds every run — `loginLimiter`'s first half, with a restart at the end of it. A cap that fires *early* is quieter and is why the number is derived rather than picked: a batch exporter meets a refusal no retry can shrink past, that run's telemetry stops arriving, and the figure that reads zero is the mid-cycle half of a live spending guard which has no second source and cannot tell "spent nothing" from "heard nothing". The size cases run against a *streamed* body rather than a string, because a counter that reset per chunk passes every one-chunk test and fails on the wire.

`src/app/api/otlp/v1/logs/route.test.ts` pins the status the ingest route answers a batch it read but could not write: 503, logged, with a malformed body still 200 and a retry after the failure recorded once. `otlp_requests` is the live spend guard's only input and the exporter reads a 200 as delivered, so the old catch-all 200 dropped spend from the guard with nothing thrown and nothing logged; a trigger refusing inserts makes only the write fail, so the read half runs for real.

`jsonNoStore` serves the one page with nothing but a poll to learn from, so a cached body is the last thing it ever sees — frozen at `thinking`, with the composer disabled; the same file reads source text for the wiring half, which only `otlp.test.ts` does beside it, because a header on the wire has no pure function behind it.

`readJsonObject` in the same file, and `src/app/api/jsonObjectBody.test.ts` beside it, pin that a body parsing to something other than a JSON object is a 400 with a sentence rather than a `TypeError` answered and audited as a 500. The unit half earns its place on the direction nobody would notice: a body that does not parse must be refused and not read as `{}`, because `{}` is "change nothing" on a task PATCH and a garbled edit then answers 200 as though it had landed. The route half opens the database and posts `null` to each door that used to read its body through `.catch(() => ({}))` and now goes through the helper — the chat, task, run, landing, queue, fleet, settings, plugin, skill, validate and provider sign-in writes — because a route that kept its own copy of the old line looks identical to one that did not until somebody sends it `null`; the rows are real so that a refusal cannot be a 404 that happened to arrive first. The two credential-free doors answer `null` their own way and `src/app/api/login/route.test.ts` pins each: `/api/login` as a wrong guess that is counted, `/api/logout` as the ordinary sign-out. `src/app/api/mcp/route.test.ts` carries the JSON-RPC half on the wire, where `5`, `"x"` and `[]` got an empty 202 — the answer that tells a caller its request was accepted. The same file carries the run doors' second half, because the helper checks the top level only: a `budget` that was not an object reached `normalizePolicy`'s `in` test and threw the same 500 one level down, and a `prompt` that was not a string went through `String()` and was admitted, with a 200, as a billed run whose task was "[object Object]". So each wrongly typed field `POST /api/runs` and `POST /api/runs/[id]/reopen` read — `budget`, `prompt`, `folder`, `mountId`, `model`, `followUp` — is posted inside a body that otherwise starts a run, against a real mount and with the fleet paused, and must come back a 400 naming the field with no run row written and the reopened run left stopped; the one start that passes is posted first, so a refusal cannot be a bad fixture. `PUT /api/settings`'s chat guard set carries the same budget case in `src/app/api/settings/route.test.ts`, and the template door's in `templates.test.ts`.

`extractLoginUrl` / `parseAuthStatus` / `normalizeCode` in `claudeAuth.ts` (`claudeAuth.test.ts`) earn theirs on the `parsePlanUsage` grounds — three parsers reading another program's console output, captured from the pinned CLI rather than read from a spec — with the added point that two of the three fail in the *wrong direction*: a status shape the parser no longer recognises reads as **signed out** unless it insists on the field it keys off, which is a Sign in button in front of somebody already signed in and a Sign out button they can no longer reach, and a URL not found is a Sign in button that silently opens nothing.

`extractDeviceLogin` / `parseCodexStatus` / `normalizeApiKey` / `redactSecrets` in `codexAuth.ts`, pinned in `codexAuth.test.ts`, are the same four questions for the other provider, on fixtures captured from `codex-cli 0.153.4` rather than from any spec, and two of them are sharper than their twins because that CLI is less helpful. `parseCodexStatus` has to read *text* rather than an exit code, since `Not logged in` and `Error checking login status` both exit 1 — and the reason the split matters is worse here than next door: a device sign-in **deletes the stored credential the moment it starts**, so an unreadable `auth.json` collapsed into "signed out" puts a button in front of the operator whose first act is to destroy what is there. `extractDeviceLogin` must find a link *and* a code or neither, because the two arrive in separate writes and a link accepted alone opens a sheet the operator cannot finish; its host check is `extractLoginUrl`'s, and the case that is not next door's is that the code is taken from **after** the link, so a code-shaped token in a future version's banner cannot be handed over as the thing to type into OpenAI.

`redactSecrets` is the fourth and has no twin at all. It is the last thing between CLI output and an HTTP body, and it fails in both directions with nothing on the page looking wrong: too loose and the CLI's own `sk-proj-***67890` mask — the only thing telling two API-key installs apart — is blanked out of the row; too tight and a CLI version that echoes a key writes it into a response. Both signs are pinned for that reason. `normalizeApiKey` is `normalizeCode`'s shape with one case added on the same argument: no refusal may quote the value, an error message being the part of a failed request that gets kept.

The host check on the URL is tested rather than commented because that string is rendered as the link an operator is asked to enter Anthropic credentials on.

`normalizeCode`'s refusal of interior whitespace is the third: the code is the one value a person types that reaches a child process, it reaches it on stdin, and the CLI reads one line — so a value carrying a newline answers this prompt with its first half and whatever is asked next with its second.

What is deliberately *not* unit-tested there is the spawn half, for `spawnAssist`'s reason — it needs a real `claude` — and the three outcomes that matter were measured by hand against the pinned CLI instead: a code the CLI rejects locally leaves the child on its prompt and the link reusable, a well-formed but spent code exits non-zero and ends it, and neither touches the credential on disk.

What `saveSettings` *writes* is now pinned in `src/lib/settings.test.ts`, and the assertions are deliberately about the stored blob rather than about a round trip: the effective object is `{...DEFAULTS, ...stored}`, so a test that only checked `getSettings()` after `saveSettings()` passes whether the blob holds one key or thirty-three, which is exactly why writing the whole object survived long enough to strand `maxConcurrentRuns`.

The cases are the ones whose failure is silent for weeks: an unedited Save storing nothing at all, a key dropped again when it is set back to the shipped value, an object value compared structurally rather than by reference, the same value with its keys reordered off the wire still reading as unchanged, and an explicit `null` that shadows a shipped number still being kept.

`src/app/api/settings/route.test.ts` pins that every key of `Settings` survives the route's per-key `if ("<key>" in body)` branches, off a probe table typed against `keyof Settings` so a new field is a compile error here until it is probed: a missing branch answers 200 with the value it already had, the page writes that back over the form, and the setting can never be changed at all.

The same file pins the one side effect a Save has beyond storage: `PUT /api/settings` drops `planUsage`'s cache only when `planUsageFromApi` actually changes. The page re-sends every field but an unedited model list on every Save, so dropping it whenever the key was present threw away the kept reading and the 429 back-off on a prompt edit, and a Save pressed during a refusal spell left `maxSessionFraction` and `maxWeeklyFraction` with nothing to read — recorded, never acted on, and nothing on screen to say so. `fetch` is stubbed to answer 200 once and 429 after, against a throwaway `CLAUDE_CONFIG_DIR` credential; the unchanged-source case fails with the drop restored, and the flip-off case is its control.

`src/app/api/runs/[id]/stream/route.test.ts` pins the run log's position on the wire — a live frame with no `id:` line leaves `Last-Event-ID` on the final replayed event, so the next reconnect replays the whole live portion on top of itself and a duplicated block reads exactly like an agent that did the same thing twice — and, on the same grounds, that a connection dying by a failed `enqueue` still unsubscribes and clears its heartbeat, which nothing would report, since the bus has `setMaxListeners(0)`.

`src/app/api/runs/live/stream/route.test.ts` opens the database and drives `/runs/live`'s one connection against the real bus, for the three things that are only true end to end and that nothing would report: a run that starts while the page is open arrives as a `join` carrying its tail — its `status` event reaches the route before anything follows that run, so a route forwarding only the runs it already knew would never draw it — and with the announcing event in that tail exactly once; a run that stops arrives as a `leave`, without which its tile stays up reading as an agent gone quiet; and a closed connection takes its `"*"` listener with it, which `setMaxListeners(0)` would otherwise let leak silently, each leaked one re-reading the runs table on every status change in the install. It also pins that no frame carries an `id:` line, the opposite of the per-run route's rule and for the reason the route's docblock gives.

`src/app/api/health/route.test.ts` opens the database and drives that route in both directions against a throwaway database: the unhealthy one is the case worth having, because a probe that always answers 200 is indistinguishable from a working one right up to the day the database goes read-only — which is exactly when Docker is reporting the container as fine.

It also asserts what the payload does *not* carry, because the middleware exemption above is justified by that and by nothing else.

`src/app/api/status/route.test.ts` opens the database and pins the same thing one route over, for a reader that is not a person: that the counts match the rows it seeded (a monitor thresholding a queue depth that never moves is bit-for-bit a queue that never backs up), that a prompt, a folder path and both tokens are absent from a payload something else will retain and forward, and that the read-only credential is checked here — since `middleware.ts` exempts that path only while `UF_STATUS_TOKEN` is set, the two have to be asserted together exactly as `/api/mcp`'s are.

It names `WORKSPACE_ROOTS` as well as the other three, because the report walks the checkout store for a byte count and any container this ships in has that variable set.

`backupStore` is tested for a three-state reading rendered as two. An unreadable directory reported as a count of zero tells an operator "no backups have been taken" when the truth is "this process could not look" — a missing bind mount, or a directory Docker created as root under a server running as somebody else — and those need opposite actions while rendering identically. The second case is what counts as a snapshot: `--dest` takes any path ending in `.db`, so matching only the script's own generated name reports zero for an operator who names their own, and the cron in `docs/backup-and-restore.md` writes its log in the same directory, which is not one.

The logout branch is covered inside `src/app/api/login/route.test.ts`, where the harness already exists, and its first case is the one it was written for: `POST /api/logout {"all":true}` from a caller holding no credential must answer 401 **and revoke nothing** — the second half being the assertion, since a route that refused and revoked anyway would pass on the status alone. That path is exempt from the edge gate, so the request reaches the handler having proved nothing, and the failure is silent in the direction that matters most: it zeroes the one figure an operator reads to check whether anybody else is signed in, while changing nothing about who actually is. The two credentials that *do* open it are pinned in both directions, a wrong bearer included, because a header checked for presence rather than for value is a flag rather than a credential.

`src/app/api/status/route.test.ts` gained two of this shape. `restartClosedOutstanding` is driven 2 → 1 → 0 across a pick-up and a set-aside, because the field exists precisely to de-latch and the one it replaces on the runbook never did — a monitor that goes red once and stays red is the fastest way to teach an operator to ignore the condition whose whole content is *somebody must act*. And the backup reading is asserted to carry **no path**, on the same ground as the prompt and the tokens beside it: this payload is retained and forwarded by whatever scrapes it.

`readOnlyBanner.test.ts` pins the client half of the health route — the sentence a 503 may put above every page — in one direction, because the inline decision it replaced, `res.ok ? null : res.error`, failed in both directions at once. In one it trained the eye: `jsonRequest` folds a fetch that never reached the server into `error` as `status: null`, and the notice rendered the transport's own words — "Failed to fetch" in Chrome, "Load failed" in Safari — so a single restart or a proxy blip put a warning banner above every page until the next poll; a banner that appears and disappears with the network is exactly what teaches an operator to skip the one that means something. In the other it was silent: the server that cannot write its own database answers 503 with the failure in `checks.databaseError` and no top-level `error` at all — the field every route uses to explain a refusal — so the notice read null and the page that most needed the banner showed nothing, looking exactly like the one that can write. The function is pure and its failure is silent both ways, which is the grounds the rest of this list shares.
