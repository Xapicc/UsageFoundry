# Conflict resolution

[← testing index](../testing.md)

Read before adding or editing tests of conflict resolution's checkout, a run's checkout stopped mid-rebase or mid-bisect, budget, silence deadline and refusal of marker-less conflicts, and `conflictedPaths`. The merge queue's own tests are in [merge-queue.md](merge-queue.md). That `resolveCheckout` refuses a slot a verify command holds or has switched is pinned in `landAfterVerify.test.ts` and its grounds are in [land-verify-gate.md](land-verify-gate.md).

`resolveCheckout.test.ts` pins *which directory* a conflict resolution is handed, against a real repository inside a real store because a path is only shared once two `git worktree add`s have said so: the aux checkout was one constant `<slug>-resolve` per repository and creating it force-removes whatever stands there, so two resolutions in one repository destroyed each other's working tree with a billed `claude` child editing files in each, and the guards on the way in had nothing to say — `assistRunning` is keyed on one run and `maxConcurrentAssists` is two, so both callers are positively permitted. It also pins *who else may write to that checkout* while a resolution is being set up, on the same fixture and for the same reason, since the fault is an interleaving of git calls: a Commit pressed as a resolution started, and a `reopenRun` in the git calls before its `run_reviews` row. Each holds one git call of the first caller through `mock.method` on `git.ts`'s export — Commit's `add -A`, the resolution's `merge` — until the second has run, so the race is run rather than hoped for. Both failed against the claim that `commitPending` read once and `reopenRun` could not read: the first with the conflict markers on the branch tip as a two-parent commit, the second with the pick-up answering `ok`. A third runs the same shape from Purge's end: Resolve is pressed inside Purge's `rev-list --count`, after `purgeRefusal` has passed and before the checkout is removed, and must be refused naming the purge, with no `run_reviews` row written and the checkout and branch both gone afterwards. Before Purge held the claim the resolution answered `ok`, having opened its merge in the checkout Purge then removed.

Its control is the half that says the deletion happened rather than merely that the names differ: the first checkout must still exist and still be standing on the first run's branch, which is what the second call took from it and what the first run's `after` handler would otherwise have staged and committed as its own.

Its last four cases are those doors asked from the other link of a two-link `continueBranch` chain sharing one slot and one branch, in both directions, because the queue resolves on whichever link it was handed and a card on its own run. While one link's `resolve` row is `running` with its merge open, the other link's Commit, Pick up and Purge must each refuse naming the resolution, and the slot, its `MERGE_HEAD` and the branch must all still be there; `resolutionHolds`, which the land route answers as `branchResolving`, must be true. And while one link's Commit is held at `add -A`, the other's Pick up and Resolve must refuse naming the commit. All four failed against the claim and rows keyed on the run id: Commit with the cut-off sentence telling the operator to `git merge --abort` a live resolution, Pick up answering `ok` and queueing the run, and, with those two taken out to reach it, Purge answering `ok` and removing the slot.

`resolveCheckout.test.ts` also pins *what it names when it refuses the run's own slot*, which was `trackedDirt`'s pure test until board task 7a9b4402 and is now one against a real slot, because the fault was in how the status was read and not in the parser: `git()` trims stdout, so an unstaged first record lost the leading space that is part of it and the sentence the operator acts on named `hared.txt`. The slot holds an unstaged `shared.txt` that sorts first, a staged `staged.txt` as the control and an untracked `scratch.txt` that must not be named, and the refusal must read `shared.txt, staged.txt`; it failed against the trimmed read with `hared.txt`. A second case, which passed before and is there to keep it so, reuses a slot whose only pending work is an untracked `.zshrc`, the state that once made a resolution impossible for any run that got some.

`midOperationSlot.test.ts` is a run's own checkout stopped part-way through a rebase or a bisect of its branch, on `resolveCheckout.test.ts`' harness and for its reason: the state is whatever git writes into the checkout's own git directory when it stops, and whether `worktree remove --force` ends the operation and `branch -D` then lets go is git's answer, which a fixture stating it would be assuming. Both operations detach HEAD, so every door that asked `worktree list` or `rev-parse --abbrev-ref HEAD` who held the branch heard nobody. With the slot stopped on the conflict `git rebase main` meets, Purge must remove the slot and the branch; Commit must refuse naming the rebase and `git rebase --abort`, never calling the checkout gone; Resolve must refuse the same way, with no `resolve-<id8>` checkout cut beside it; and a bisect, whose `BISECT_START` spells the branch short, must be named by Commit and purged as well. All four failed before the fix: Purge refused by `branch -D` as checked out at that very slot, Commit with "The checkout this run worked in is gone", Resolve with git's "already checked out". The control passed before and after: a worktree the operator made and stopped mid-rebase of the same branch is still left to git's refusal, the checkout and its rebase intact. It also pins what is said before any door is pressed, over the same repository: `landState`'s `pending` carries `operation` for a stopped rebase and for a bisect over a clean tree, and is never `merging`; the branches row carries it and reads `heldByCheckout`; a plain detached HEAD is neither. Both read the slot as holding no branch before, so the card drew nothing and the row never probed it.

`resolutionBudget.test.ts` pins *what limit* a conflict resolution's child is handed, end to end — a real repository with a real conflict, `resolveConflicts` asked as the Resolve button asks it, and a stub `CLAUDE_BIN` that writes down its argv — because the defect was an argument missing at one call site, which a pure helper beside it would have got right all along. A resolution has no clock on its duration and only an hour of silence stops its child once spawned, so `--max-budget-usd` off `resolutionBudgetUSD` is the only bound on what a working one spends, and the merge queue's auto-resolve spends it with nobody present; without the flag nothing fails and the row looks the same. Its sibling cases are in files already here: `assistBudget.test.ts` pins that `assistRefusal` refuses at the install's daily limit, which it counted and never asked, and `mergeQueue.test.ts` pins `refusesEveryLaterResolution` against the sentence `evaluateInstallBudget` actually words, and against `SHUTDOWN_REFUSAL` itself, so a rewording fails there rather than costing every later branch a fresh refusal.

`resolutionSilence.test.ts` pins the one deadline a resolution's child has, end to end on the same fixture as `resolutionBudget.test.ts`: a stand-in `claude` that prints nothing is stopped once an hour of faked time has passed, and its merge is rolled back through the resolution's own `after` with the branch tip, the operator's checkout, its file and the worktree list exactly as they were; one that printed half an hour in is still running at the hour and ends with its own verdict. Both failures are quiet. A deadline that output does not re-arm ends large merges that were working, the defect the landing path's no-clock rule was written against, and it reads as one more failed resolution; a stopped one that never reaches `after` leaves a merge half-done in a checkout nothing cleans up. It is the one file in the suite on `mock.timers`, faking `setTimeout` and `Date` only between the spawn and the tick, because `RESOLVE_SILENCE_MS` is a constant on purpose and a test-only way to shorten it would be a second deadline to keep honest; the child, git and the settle run in real time, and Node's `ExperimentalWarning` for that API is expected in the output. Both cases were checked to fail: with the deadline removed the silent one never settles, and with output no longer re-arming it the printing one is recorded as stuck.

`resolutionMarkerless.test.ts` pins *what a resolution may commit on the strength of no marker being left*, end to end on `resolutionBudget.test.ts`'s fixture and its ground, since what was wrong is what git leaves in a real checkout and what `after` concluded from it. A stand-in `claude` that reports success having settled nothing but `a.txt`'s markers is handed a binary clash, a modify/delete and a rename/delete, and each must end with no `completed` row, no child spawned, the branch tip where it was and a refusal naming the path — then Land is pressed and must leave `main`'s `logo.png`, or its deletion, as it was. All three failed before `markerlessRefusal` on the first of those, the row recorded `completed`, and with that half bypassed Land went ahead over each conflict, which is the target's change undone; nothing threw and the land message was the ordinary one. A content clash whose markers the stub does remove is the control and must still commit as before, so it passed before the fix and has to go on passing. Each refused case also asks `refusesEveryLaterResolution` of its refusal, because the queue's choice to fail that row and still try the next branch rests on its not matching. `unsettleableByEditing`, the pure classifier under the refusal, has three cases of its own for what the fixtures do not reach: the branch deleting what the target changed, an unreadable file, and a surviving version with marker-shaped lines, refused because its sides are asked before its markers.

`landAfterSquash.test.ts`'s fourth describe is a resolution of a branch past a squash, on that file's harness and its ground (`landing-and-delivery.md`): link A squash-landed, `main` editing `f1.txt` (A's lines) and `f2.txt`, link B editing `f2.txt`, and B's card listing `f2.txt` alone. `startAssist` is stood in for, which is the stop before the spawn and the one seam that hands a test the checkout with its merge open: it must find exactly `f2.txt` unmerged, be handed `f2.txt` alone and find `main`'s `f1.txt` already merged in, and the rollback it then triggers must leave the branch tip and the slot as they were. The second case keeps the branch's side of everything it is handed, then lands, and `main`'s `f1.txt` must survive. Before the fix the merge also conflicted in `f1.txt`, and the land put link A's `f1.txt` back on `main` under a success message.

`conflictedPaths.test.ts` is the conflicted-file list read against a real repository, and it earns a git child on `slotProbes.test.ts`' grounds turned around: what was wrong was not what this app computed but what it *asked git for*, so a fixture stating git's output would be stating the very thing in question, and a parser test over a pasted string passes with the `-z` left off the argv. Without it, `git diff --name-only --diff-filter=U` C-quotes any path holding a non-ASCII byte, so `café.txt` reached every consumer as `"caf\303\251.txt"` — a string that names nothing on disk — and every one of them uses what `conflictedFiles` returns as a path: the resolution prompt names it to the agent, `run_reviews.resolved_paths` keeps it for `resolutionChange`'s pathspec, the `after` handler joins it onto the checkout and reads it, and `git add` stages it. Nothing throws and nothing looks wrong. The read comes back null, an unreadable file counts as unresolved for the reason `unresolvedFiles` states, and a resolution the operator has already paid for is rolled back whole — including the files the agent got right — with "conflict markers are still in" naming a file that was never there, which is a branch that can never be auto-resolved. So the second case resolves the files that exist in the checkout rather than the ones this app named, which is what an agent working from the tree it can see would do, and then walks the `after` handler's own two steps: the read that decides whether markers are left, and the `:(top,literal)` add checked against `ls-files -u`. Dropping the empty record after the final NUL is asserted in the same breath and is not tidiness — `:(top,literal)` with an empty path matches the entire tree, so a split that kept it would stage every unrelated change in the checkout into the merge commit.
