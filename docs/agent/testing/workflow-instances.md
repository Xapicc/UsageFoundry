# Workflow instances, blocks and schedules

[← testing index](../testing.md)

Read before adding or editing tests of `workflows.ts`' instances and blocks (halt, boot reconcile, `instanceStatus`), `schedules.ts`' `putSchedule`, `/api/workflows/[id]` and the name `duplicateWorkflow` picks. The `canvasGraph.ts` section cases and the `format.ts` pass and schedule-drawing cases are in [workflow-canvas-and-formatting.md](workflow-canvas-and-formatting.md).

`haltedMembers.test.ts`, which opens the database, halts a real instance through `stopInstance` and then asks `reopenRun` and `reviveBlockedDependents` about its members, and drives the same pick-up against a graph's deferred nodes to pin `reviveBlockedBlocks` — the two halves of one question, because what it pins is a *join*: a halted member is an ordinary `blocked` row with a null `work_dir`, indistinguishable from the one the revive exists to rescue except by `workflow_instance_runs`, so every way of getting this wrong typechecks, throws nothing and reads identically on the page — the only evidence is a billed agent working under a workflow the page says is stopped.

Its three control cases are half the test, and the half more easily broken: a chain outside any workflow, and one inside an instance still `started`, must still wake exactly as before.

`bootBlocks.test.ts`, which opens the database, drives a whole boot — `reconcileOnBoot` then `reconcileBlocksOnBoot`, in `src/instrumentation.ts`'s order — because what it pins is neither a value nor a row but an *ordering between two reconcilers*: `bootBlockPlan` beside it decides which instances are spared, and this is what says the survivors it is handed are the ones the run reconciler had already decided to keep. Its cut-off describe drives a merge or deliver block the boot found `thinking`, with a gate hung off it `on-finish`, through a boot and the advance after it in the `spared` and `held` arms: the join is the boot sweep's `restart_closed` write read back by the very next `planInstanceStep`, which no pure case holds, and its failure is a run or a billed turn started after a restart off a landing that died with the container. Both failed at 9e878484, the gate reached rather than blocked.

Its own controls are again half of it, and one of them is the halt bound: a stale pause, a run the boot failed, and an instance already `stopping` must all still lose their blocks.

Its review describe boots with `reconcileReviewsOnBoot` between the two, as `src/instrumentation.ts` does, over one branch whose review the old process had not banked. A killed reviewer under a `thinking` block is the control; under a halted block's `failed` row it read as a measured $0.00, and so did a $0.05 review that reported before its poll came round. Two boots must bank that one once.

It asks the same question of a `looping` block, whose survivor is the loop's own current pass, because that sweep read no instance at all: the row went `failed`, `advanceLoops` only ever selects `looping`, and `loopVerdict` then wrote every successor off while the pass was still committing to their branch — so what the two positive cases pin is a row left *unchanged*, which is the one outcome no page and no status ever shows.

It asks it once more of a run `waiting` on another run, which the boot used to stop unconditionally under a sentence saying its dependency had been closed out by the same restart. Three cases: behind a pause the boot kept it stays `waiting`; behind a run the boot failed, on an `on-finish` edge that the ordinary release would read as satisfied, it and the run behind it end `blocked`, each naming the run in front; and behind a completed run while new work is held it stays `waiting` with nothing planned.

`shutdown.test.ts` carries one workflow case, beside its fan-in run case, because the ending it needs is the one only a real `shutdownRuns` writes: a merge block behind run nodes A and C, both closed out, then C picked up by name and stopped after a cycle. The block must be `blocked` after the boot, `waiting` again on C's pick-up, `blocked` after C's ending with no `started_at` and a sentence naming A, and `waiting` on A's pick-up. It is a merge block because a merge's claim asks nothing about the shutdown the file has already begun; an orchestrator block would be held by `isShuttingDown()` and pass for that reason instead. It failed before the change with the block `failed`, claimed by the release pass the shutdown's own ending ran and handed both branches. Three pure `planInstanceStep` cases in `workflows.test.ts` pin the verdict itself: the same fan-in blocked on both conditions, the control without the flag, and an orchestrator block one of whose emitted runs was closed out. The first and third failed with the two checks taken out.

`reviewBlockRun.test.ts`' second and third suites drive a real review block, stub reviewer and all, into a halt and into its instance's limit, because what each pins happens between a poll and a press, or between one review and the block's end, where no pure function can see it. A halt landing just after a rejection, or while `startReview` was still preparing, started a fix run or a reviewer into the stopped workflow; a halt mid-review left the reviewer billing under a page reading `stopped`, and dropped every review's cost from the total; a review that had finished was invisible to the guard until the block ended; and a block started over its limit reviewed anyway. Its last limit case hands one block four approvable branches at one assist slot under a $0.03 limit, each review reporting $0.02: exactly two reviews may start and the instance must be halted on `guard`. Before `driveReviewItem` asked the guard per review, all four started, $0.08 was spent and the instance stayed `started`. The Stop is pressed from inside a replaced `currentSnapshot` for the second case, the one `await` both the block's door and `startReview` make. The held-work describe presses the hold there instead: a reviewer was spawned under it, and the case also asserts the branch is still `reviewing` under the hold and `approved` after the lift with one review, because the cheap fix — refusing without `held` — would set it aside. That four-branch case also failed now and then under load, three reviews and $0.06, because a sibling woke inside the up-to-2 s before the review that freed the slot was banked; it now also asserts the total equals what the reviews billed, which a review banked by both its sibling's guard read and its own poll would double. The case after it seeds that gap directly — a `completed` $0.05 review on an item nobody has banked — and asks the guard, which passed it at $0 before `guardInstance` banked first.

`reviewBlockRun.test.ts`' suite on assist slots hands one block four approvable branches at the default `maxConcurrentAssists` of 2, because the race it pins is between siblings of one block, which no pure function has: every branch passes `assistBudgetFull()` before any has filled a slot, and `startReview`'s door then refuses the rest. All four must end `approved` with one review each; against the tree before `startReview` reported `busy`, two were set aside on the budget sentence. Its second case is the other half of that rule — a spent install limit must still set the branch aside with its own sentence — and it fails by its deadline, not by an assertion, against a door that reports every refusal `busy`, which is the wait that never ends. It spends past the limit with a run of its own rather than leaning on the cases before it, so it holds when run alone.

`instanceReading.test.ts` opens the database, and it is the half of one word that no pure function can be asked about.

`instanceStatus` decides which of the six readings a stored row is and is tested beside `haltPlan`; what it decides *from* is a count over two tables, because a graph is half runs and half a ledger of blocks that are not runs yet — and both halves can be live, and both can be written off.

Counting only the runs is the quiet failure: a node deferred behind an orchestrator block holds a `waiting` row in `workflow_instance_blocks` and nothing else, so an instance whose runs have all settled reads as *finished* while a block is still to wake, and when it wakes it starts a billed agent under a page that already told the operator this press of Run was over.

The mirror of it is the same shape one status along — a node written off because the block in front of it satisfied nothing is what separates a graph that reached its end from one missing its tail, and reported as `finished` a workflow that did half its work reads exactly like one that did all of it.

Its last suite asks `liveInstancesOf` the same question from the gate's side: which presses of Run are still going, newest first. A lookup over runs alone misses a block still deciding and a loop between two passes, so a second press would be let into that folder and the page would have nothing to open; against a runs-only lookup four of its cases fail. The last case holds the per-press counts to the totals the list shows, so the two cannot disagree about what is going.

Its newest suite asks `lastInstanceOf`, which the workflows list reads, for the same word: the list shows the badge and links the press, and a lookup that took the stored column raw would call every finished press "working" for ever, because nothing writes that second fact. Its first case seeds a graph whose members have all settled under a `started` row and holds the answer to `getInstance`'s, which is the page the badge links to; the others pin the newest press when an older one is still going, `null` for a workflow never pressed, and the timestamp `lastRunAt` returned before it.

Its last case is the bound the halt needs, `haltedMembers.test.ts`'s reason turned around: `stopping` and `stopped` must stay above both counts, however many members the halt itself wrote off, because what ended a press of Run is the headline and a member says the rest on its own row.

`src/app/api/workflows/dto.test.ts` pins what an instance member is told it waits for: `instanceWaiter` keeps the edge's condition beside the node id, because a wait that kept only the name reads "after Build" for a link that starts the next run only if Build completes. The cases are the three places a wait comes from — a saved edge, a section's edge inside a pass (the predecessor's condition, not the loop's), and a creator with no edge (null, never a guessed condition) — and the `repeats` link, which is containment and no wait. Two of five fail with the condition dropped; `format.test.ts`' `fmtInstanceWait` cases hold the wording to the canvas chip's, and its `instanceCanMove` case names all six readings, because the page's poll stood down for none of them and a seventh must not default to either side.

`runWorkflowOrigin.test.ts` opens the database for the join the run page's origin link is drawn from: `origin_ref` holds an instance id, a schedule id or a node id, so only `workflow_instance_runs` says which press of Run a run belongs to. Its cases are the ones a right join and a plausible one disagree on — a run that is no member (null, not the newest instance), a run an orchestrator block emitted, two presses of one workflow, and a workflow deleted since (null, because the instance went with it). Four of five fail with the lookup stubbed to null; the fifth is the control.

`schedulePut.test.ts` is `retentionSweep.test.ts`' shape one table over: `putSchedule`'s UPDATE carried a literal `paused=0`, so pressing Change on a paused schedule switched the one thing in this app that starts a billed agent with nobody present back on, as a side effect of a form that never asked.

`scheduleFire.test.ts` is that row again from the timer's side. `tickSchedules` read every active schedule once and acted on it after awaiting a snapshot, so a Pause or Remove pressed during that await still started an unattended instance, and a Change had its fresh cursor and cleared outcome overwritten by the recurrence it replaced. Each case presses the button from inside a replaced `currentSnapshot`, once for the schedule that is firing and once for a later one read in the same tick, and asserts that no `workflow_instances` row exists and that the cursor and `last_code` are what the press left. One case clears the workflow's instance budget there instead, an edit to the workflow's row that the schedule's re-read cannot see, and asserts no instance and `last_code` `unbudgeted`; before the workflow was read again after the snapshot, it started. Its first case is a control that fires with nothing pressed, because without it every other case passes on a fixture that never fires. A second suite presses the install-wide hold from inside the snapshot through `setFleetPaused`: before the hold was asked again after it, the fire created the instance, recorded `started` and advanced the cursor, and the run was promoted the moment the hold was lifted. It asserts no instance and no run, and that the cursor is where the tick found it with `last_code` unset, beside a control that sets the hold before the tick. A third case starts one occurrence behind, so the fire records that older window as missed first, and asserts the cursor comes back only to it, since a cursor put back past it has the next decision record the same window twice. It is apart from `schedulePut.test.ts` because `tickSchedules` acts on every active schedule in the database.

`workflows.test.ts`' `pickDuplicateName` cases are the one test here whose failure is not silent — it is a refusal on the Duplicate button — and they earn it on a narrower ground: the shape that shipped, testing `"<name> copy"` against the taken names and cutting the winner to `MAX_WORKFLOW_NAME` afterwards, typechecks and is right for every name short enough that the cut never happens, so an 80-character workflow could never be copied and a 77-character one exactly once, each refused under its own original's name. The cases are the lengths either side of the suffix, three copies deep, and the two ways the fix itself is wrong only on the *second* copy: a comparison that is not the index's (`COLLATE NOCASE` folds the 26 ASCII capitals and nothing else, so a locale fold can pass a name the index refuses), and a cut through a surrogate pair, which SQLite stores as replacement characters, so the stored name no longer equals the one tested and the next copy passes the test and collides. All four of the length, fold, surrogate and space cases fail against the cut-after-test implementation; only the short-name case passes it.

`src/app/api/workflows/[id]/route.test.ts` pins that a workflow's history is a *page* rather than a ceiling, and it is on the wire rather than beside `findInstances` because the defect it closes was the route: it read no `searchParams` at all and answered with the newest twenty presses of Run, so a `findInstances` that pages perfectly under a caller that passes it nothing is the same unreachable history and typechecks. Its cases are the four ways that is silent — a second page that neither repeats nor skips a press, a short last page rather than an empty one for an offset past the end (which reads as *this workflow has not been run*), an unusable `limit` answered with the ordinary page rather than the smallest legal one, and a `total` that counts this graph's presses rather than the install's, since a count that lost its `WHERE` is a plausible number on a pager whose last page is empty.

Its second suite pins the two facts the page is told so that it can state a refusal before the press — `workflow.startRefusals`, naming a press found through a block still deciding because no run exists to find it by, and `newWorkPaused`, on and off. Neither fails loudly when the route stops sending it: the page reads an absent field as `false`, so Run stays enabled and a schedule card keeps naming a start a held install will record as missed, which is bit-for-bit the page before. Without `newWorkPaused` on the route the hold case fails, and it is the only assertion that does.

`src/app/api/workflows/[id]/schedule/route.test.ts` is on the wire for the same reason: the defect was the route's own reading of `paused`. It read `body.paused === true` off a body whose parse failure became `{}`, so `"true"`, `1`, `null`, `{}`, a missing field and a body that is not JSON each resumed a paused schedule and answered 200, because `false` there is resume. Each case sends one of those to a paused schedule on a budgeted workflow, since an unbudgeted one refuses every resume anyway and the case would pass whatever `paused` said. It asserts a 400 and a schedule still paused. The last case is the control, a real pause and resume, without which the others pass against a route that refuses everything.

A dollar limit over blocks whose runs report no cost earns cases in four places, each silent in the direction that spends, because `sumMemberSpend`'s skip is right for both figures and left every guard reading $0 for those blocks. `budget.test.ts` pins that `evaluateInstanceBudget` returns `unmetered` for a spending limit over an unmetered member, keeps it off `INSTANCE_ENFORCEABLE_CODES`, still returns `instance_cost` or a tripped window ahead of it, and asks nothing of a workflow with no spending limit. `workflows.test.ts` pins that the count survives `addBlockSpend` into that verdict — the shape `instanceSpend` hands `guardInstance` — and that a killed block turn, whose estimate the guard does see, does not join it; and, under `normalizeWorkflowInput — loop blocks`, a loop's spending cap refused at save over a Codex, local or Codex-emitting orchestrator member while the same section saves without the cap. `schedules.test.ts` pins `scheduleRefusal` refusing a dollar-only bound over any such block, admitting it over Claude blocks, and still admitting a window guard beside it — the last pinned as the current answer to an open question (board task bf494de3). Each new case was seen to fail before the fix: a $0.01 limit admitted an all-Codex instance, a $20 limit made an all-Codex workflow schedulable, and a Codex section saved its cap.
