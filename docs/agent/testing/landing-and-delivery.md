# Landing, delivery and the land gate

[← testing index](../testing.md)

Read before adding or editing tests of `land.ts` and `repoLock`; the verify command's are in [The verify gate in front of Land](land-verify-gate.md), Deliver's are in [Deliver](delivery.md), `deleteBranch`'s, a squash-landed chain's second land's and a reused slot's `uncommittedIn` are in [Deleting a landed branch](branch-deletion-and-slot-reuse.md), and `git.ts`'s are in [The git this app runs](git-children.md).

`landRefusal`'s two are the cheap in-bar extension of an existing fixture rather than a new file, and they exist because that behaviour looks like an omission and is not — a run that asked for review is landable exactly like a `failed` one, and it owns its chain's branch once it has committed.

`landRefusal`'s refund case and `selectBranchCandidates`' beside it are `dependencies.md`'s refund failure on a branch chain: a link that committed and was then parked or cut reads `iterations === 0`, and `branchOwner` read that as empty and named the link before it. The second is there because the branches page builds its chain members itself rather than through `chainMember`, so a count only one of them carried would keep the row whose Land then refuses.

`unsettledBranchRefusal`'s five in `land.test.ts` are `landRefusal`'s run half asked for Deliver, which asked none of it. Four state what Deliver refuses and allows; the fifth keeps the split honest: `landRefusal` still answers each held case with exactly the sentence `unsettledBranchRefusal` gives for Land, so a second copy of the rule growing back in either door fails here.

`landUnwind.test.ts` is what a failed land's undo does to the operator's own checkout, against a real repository for `conflictedPaths.test.ts`' reason: the fault was in what git does to a working tree, so a fixture stating it would be stating the very thing in question. `unwind` followed a failed `--squash` with `reset --hard HEAD`, and git refuses a squash *because* the checkout holds changes it would overwrite, so the undo destroyed every uncommitted edit in the tree and the card said "rolled back". Its first case plants three edits — one the squash would overwrite, one unrelated, one staged — and asserts all three survive; the staged one is what makes "no undo at all" the answer rather than a gentler `reset --merge`, which resets a staged edit too. The second asserts a conflicted squash is rolled back while an unstaged edit it did not touch is kept, the third that a squash whose commit was refused is rolled back whole, and the fourth that an edit tangled with what the squash staged is refused rather than overwritten, with `unwind` saying so. Before the fix the first, second and fourth failed with the operator's edits back at the base commit. Its last describe is a fast-forward git wrote and then could not record because `main`'s ref lock was held: `unwind` must take it back out with the lock still held, and must keep an edit tangled with what it wrote and say the checkout was changed; before `undoFastForward` both read as restored over the branch's staged tree.

`landAfterVerify.test.ts` drives `landRun` end to end — a database, a repository, the run's own checkout and a verify command that does to the operator's checkout what a person would do while it runs — because what it pins is *when* `landRun` proves the checkout, and no test of `landRecheck` beside it can see that. It is `loopMergeOwnership.test.ts`' harness, `DATA_DIR` named before the first import. A control lands through an ordinary check, so that the refusals are not the harness; then a check that edits the checkout under a squash, one that `git switch`es it, and one held open while a run is written into the folder are each refused in `landRefusal`'s sentence, with the edits intact and nothing merged anywhere. Before the fix the first of those three reported "git refused the merge and it was rolled back" over a checkout reset to the base commit, and the other two landed. Its second describe is the run's own checkout during the check: uncommitted work there refuses the land before the command runs, which the `mark` probe's absence proves; with no command configured the same land goes through, which is the gate being off; and a run created in the same repository while the check is held open is given a different slot. Before that fix the first landed and the third was handed the slot the check was running in. Its last case holds the check open and commits to the branch in the run's slot, as a continuation adopting the slot or the card's Commit button would, and the land must be refused with `main` still at its base; before `verifyInSlot` compared the branch's tip after the check with the `HEAD` it ran against, that commit was merged. After it come two that commit nothing: a run continuing this one's branch, `queued` in one and `running` in the other and handed the slot as `inheritedSlot` hands it, is written while the check is held open, and the land must be refused with the owner refusal naming it and `main` still at its base. The tip has not moved, so `verifyInSlot` passes both; before `landRun` asked `unsettledBranchRefusal` again after the check, both landed. Its next describe: an ignored `local.settings.json` the branch tracks must refuse a merge and a squash by name, content and `main` unchanged, and lands with no such file there; before `--no-overwrite-ignore` both landed over it. It was `.env` until 2026-10-06, when a branch carrying a path the seeding list names began to be refused before the merge (`deliverRun.test.ts` pins that), so the file is one nothing seeds. Its last holds `.git/index.lock` in the operator's checkout, another git process as far as git can tell: a fast-forward merge and squash must be refused in `lockRefusal`'s sentence, naming the lock, with `main` at its base and no `MERGE_HEAD`, then land once it is removed; a merge that is not a fast-forward writes `MERGE_HEAD` before it finds the lock, and its abort needs the same lock, so it must say the checkout may be mid-merge. Before the change all three got the plain refusal, the last saying the checkout was as it was over a `MERGE_HEAD` the operator's next commit would have concluded. Its last two hold `.git/refs/heads/main.lock` instead: the fast-forward must be refused in the same sentence naming that lock, with `main` at its base and an empty status, then land once it is removed; before, it said the checkout was as it was over the branch's whole change staged. The squash stages without meeting the lock and is refused at its commit, and must get the same sentence over an empty status, then land once the lock is removed; before `resetDespiteRef`, `reset --merge` exiting 1 on that lock made it say the squash was still staged, then it gave git's line.

`landMovedBranch.test.ts` drives `landRun` for real behind a `GIT_BIN` stub that moves the branch inside the window between `landRun`'s read of the tip and its merge, because the fault is in what git is handed and when, and no fixture can state that. `GIT_BIN` is read when `config.ts` loads, so it is its own file, `mergeQueueDrain.test.ts`' stub in kind. The stub changes when things happen and nothing about what git does, and it does one of two things. It holds the operator checkout's `git status` once the verify command has passed, until the case has pressed `commitPending` with an `unverified.txt` and a `.env` in the slot (the realistic path, through the card's Commit button, which takes a claim `landRun` never reads); or it commits a forced `.env` and an `f3.txt` into the slot at the instant the first `git merge` that is not an `--abort` is spawned, strictly after every check. Five cases: the pressed Commit; a plain merge and a plain squash with the late commit armed; a merge past a squash (link A squash-landed, link B on the same branch, the operator's own ignored `.env` in the checkout); and a plain file committed at the first git step after the verify command passes, where main must receive the SHA the command ran on (with the ref re-read it took the file, 2026-10-20). Each asserts that main holds only what was checked, that the late commit is not an ancestor of main, that `landed_tip` is the SHA main received (the merge's second parent, or the tip itself on a fast-forward), that the late commit is still on the branch and reads unlanded, and, past a squash, that history and tree agree and the operator's `.env` is intact. Run against the merge-by-name `landRun` all four failed (2026-10-17): main tracked `.env` and `unverified.txt`, or `f3.txt`; and past a squash, `merge-base --is-ancestor` said the late commit was merged while `f3.txt` was absent from the tree. The stub's hold is the `landRecheck` read and not an arbitrary one: it is the last await before the spawn, and it is hundreds of milliseconds on a large checkout, so the case holds a window that exists unheld.

`repoLock.test.ts` is a mutual exclusion tested for the failure that it excludes nothing, which is what every wrong promise-chained lock does: chain onto the wrong promise and two bodies run side by side, and the only symptom is two callers overlapping on a live install months later. The case that carries the file asserts an *ordering* — the second body has not started while the first is still open — driven with explicit deferreds rather than timers, because a test that establishes an ordering by sleeping asserts the sleep. Two of the others are the opposite direction and matter as much: two repositories must still work at once, or a lock keyed on the process would serialise every install-wide run start behind one repository's registry work; and a body that threw must not wedge its key, because one of the four callers is the run loop and a wedged key is every isolated run in that repository never starting again — which is worse than not having the lock at all. The last two are about the map: it must forget a repository once the queue drains, and must **not** forget one while somebody is still queued behind the holder, since a third caller then chains onto nothing and runs beside the second. The second of those needed both bodies held open to be observable at all; the first version of it passed for the wrong reason, because the queued body returned inside the same tick.

`aheadRangeFor`, `parseCount` and `purgedMessage` in `land.test.ts`, and `landView.test.ts` beside them, are the count Purge reads out as what it is about to destroy. Every way of not having one became 0 — no recorded target, a target renamed away, a `rev-list` that failed and so read as `Number("") || 0` — and the one irreversible press in this app then said "Purge 0 commits" over a branch with work on it. What is pinned is that unknown and none stay two answers all the way to the sentence: the range falls back to the base commit, a count git would not give is null, and each sentence that states a count — the sheet, the armed button, `purgeBranch`'s answer, the run log's purge row in `logLine.test.ts` — names none it did not measure.

`landCardLine` in `landView.test.ts` is the Land card's one state line. `landed_at` is written once and never cleared, and a landed run can be reopened and commit again; the card said "Merged into main" whenever it was set, so a branch with new commits had Land withheld with no sentence saying why and Purge offered under a notice that the work was merged. What is pinned is that "merged" is drawn only while `merged || landedUnchanged` (or the branch is gone, which is the ordinary end of a landed run), and that otherwise the refusal is what shows.

`midOperationSlot.test.ts`'s last describe is its slot on a plain detached HEAD, on that file's harness and ground (`conflict-resolution.md`): Commit must name the detached HEAD rather than call the checkout gone, and a fast-forward land with a verify command set must be refused naming it rather than as taken over by a later run, `main` unmoved. Before `slotState` reported `detached`, both said those things about a directory standing there.

`midOperationSlot.test.ts`'s describe before that one is what the Land card says of the same two states once a verify command is set, on the same harness: a fast-forward land over a slot on a plain detached HEAD, and over one stopped mid-rebase after `main` was moved back under it, must each read `landState`'s `blocked` as the gate's sentence naming the state, and a press must answer that exact sentence with `main` unmoved and the rebase undisturbed; with no command, `blocked` must be null, which is the gate asking nothing. Both failed before `landState` asked the gate, `blocked` null with the command set, so the card drew Land.

`landAfterVerify.test.ts`' describe "a checkout a later run reused, with a verify command set" is the Land half of `review-verify-command.md`'s decision, on the same harness and for its reason: whether the slot is back on the later run's branch when the land returns, and whether the card and the press give one answer, are facts about git's state that a fixture stating them would assume. The later run is a row recording the same slot with its own branch cut in it, as `allocateSlotPath` leaves one. The command records the branch and the `shared.txt` it ran against, so the first case proves it saw the run's tree and not the later run's, that the slot is clean and back on the later branch, and that the later run then lands from its own card; the second holds the check open and reads the later run's card and press mid-switch, which must give one sentence ("because another verify command is running in it") with the slot borrowed; a slot holding the later run's uncommitted file, and one with that run `running`, must each be withheld on the card in the sentence the press gives, with the command never run and the file untouched; two runs whose slots hold each other's branch must both be refused naming the worktree that holds it, with neither slot moved; and a continuation created while the switched check runs must be refused in the owner's sentence with the slot already back. The first, second and last fail with the card still calling a switchable slot blocked, and again with `switchBack` removed; the swapped pair fails without `switchBlocker`'s `worktree list` read, git's own line being the refusal then (each by editing the compiled `.test-build/lib/land.js`, not by a revert of the source). `mergeQueue.test.ts` pins that `planItem` lands a row carrying `verifySwitch` and fails an unswitchable one in its sentence.
