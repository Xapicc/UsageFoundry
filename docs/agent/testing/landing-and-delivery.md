# Landing, delivery and the land gate

[← testing index](../testing.md)

Read before adding or editing tests of `land.ts`, `landGate` and `repoLock`; Deliver's are in [Deliver](delivery.md), and `git.ts`'s are in [The git this app runs](git-children.md).

`landRefusal`'s two are the cheap in-bar extension of an existing fixture rather than a new file, and they exist because that behaviour looks like an omission and is not — a run that asked for review is landable exactly like a `failed` one, and it owns its chain's branch once it has committed.

`unsettledBranchRefusal`'s five in `land.test.ts` are `landRefusal`'s run half asked for Deliver, which asked none of it. Four state what Deliver refuses and allows; the fifth keeps the split honest: `landRefusal` still answers each held case with exactly the sentence `unsettledBranchRefusal` gives for Land, so a second copy of the rule growing back in either door fails here.

`landUnwind.test.ts` is what a failed land's undo does to the operator's own checkout, against a real repository for `conflictedPaths.test.ts`' reason: the fault was in what git does to a working tree, so a fixture stating it would be stating the very thing in question. `unwind` followed a failed `--squash` with `reset --hard HEAD`, and git refuses a squash *because* the checkout holds changes it would overwrite, so the undo destroyed every uncommitted edit in the tree and the card said "rolled back". Its first case plants three edits — one the squash would overwrite, one unrelated, one staged — and asserts all three survive; the staged one is what makes "no undo at all" the answer rather than a gentler `reset --merge`, which resets a staged edit too. The second asserts a conflicted squash is rolled back while an unstaged edit it did not touch is kept, the third that a squash whose commit was refused is rolled back whole, and the fourth that an edit tangled with what the squash staged is refused rather than overwritten, with `unwind` saying so. Before the fix the first, second and fourth failed with the operator's edits back at the base commit. Its last describe is a fast-forward git wrote and then could not record because `main`'s ref lock was held: `unwind` must take it back out with the lock still held, and must keep an edit tangled with what it wrote and say the checkout was changed; before `undoFastForward` both read as restored over the branch's staged tree.

`landAfterVerify.test.ts` drives `landRun` end to end — a database, a repository, the run's own checkout and a verify command that does to the operator's checkout what a person would do while it runs — because what it pins is *when* `landRun` proves the checkout, and no test of `landRecheck` beside it can see that. It is `loopMergeOwnership.test.ts`' harness, `DATA_DIR` named before the first import. A control lands through an ordinary check, so that the refusals are not the harness; then a check that edits the checkout under a squash, one that `git switch`es it, and one held open while a run is written into the folder are each refused in `landRefusal`'s sentence, with the edits intact and nothing merged anywhere. Before the fix the first of those three reported "git refused the merge and it was rolled back" over a checkout reset to the base commit, and the other two landed. Its second describe is the run's own checkout during the check: uncommitted work there refuses the land before the command runs, which the `mark` probe's absence proves; with no command configured the same land goes through, which is the gate being off; and a run created in the same repository while the check is held open is given a different slot. Before that fix the first landed and the third was handed the slot the check was running in. Its last case holds the check open and commits to the branch in the run's slot, as a continuation adopting the slot or the card's Commit button would, and the land must be refused with `main` still at its base; before `verifyInSlot` compared the branch's tip after the check with the `HEAD` it ran against, that commit was merged. After it come two that commit nothing: a run continuing this one's branch, `queued` in one and `running` in the other and handed the slot as `inheritedSlot` hands it, is written while the check is held open, and the land must be refused with the owner refusal naming it and `main` still at its base. The tip has not moved, so `verifyInSlot` passes both; before `landRun` asked `unsettledBranchRefusal` again after the check, both landed. Its next describe: an ignored `local.settings.json` the branch tracks must refuse a merge and a squash by name, content and `main` unchanged, and lands with no such file there; before `--no-overwrite-ignore` both landed over it. It was `.env` until 2026-10-06, when a branch carrying a path the seeding list names began to be refused before the merge (`deliverRun.test.ts` pins that), so the file is one nothing seeds. Its last holds `.git/index.lock` in the operator's checkout, another git process as far as git can tell: a fast-forward merge and squash must be refused in `lockRefusal`'s sentence, naming the lock, with `main` at its base and no `MERGE_HEAD`, then land once it is removed; a merge that is not a fast-forward writes `MERGE_HEAD` before it finds the lock, and its abort needs the same lock, so it must say the checkout may be mid-merge. Before the change all three got the plain refusal, the last saying the checkout was as it was over a `MERGE_HEAD` the operator's next commit would have concluded. Its final case holds `.git/refs/heads/main.lock` instead: the fast-forward must be refused in the same sentence naming that lock, with `main` at its base and an empty status, then land once it is removed; before, it said the checkout was as it was over the branch's whole change staged.

`deleteBranch.test.ts` drives `deleteBranch` on `landAfterVerify.test.ts`' harness, a database and a real repository, for `conflictedPaths.test.ts`' reason: the fault was in what git answers to the question this app put to it, so a fixture stating git's answer would be stating the very thing in question. `git branch -d` tests a branch against HEAD of the operator's checkout rather than against the run's target, so with that checkout on any branch lacking the run's work every merged branch was refused as "not fully merged" — after its slot had been removed. Its first case is that scene and failed before the fix with exactly that sentence; a squash-landed branch with its tip unmoved is deleted through the same compare-and-delete, from the run that landed it and from the link before it, whose own `landed_tip` is empty — that case failed with the check before the claim reading one run ("has 2 commit(s) that are not in main"), and again with only the compare inside the claim reading one run ("one of the two changed while this was being checked") — and the tracking section Deliver's `--set-upstream` writes goes with it, as it did under `branch -d`. The two refusals are the half that says the door is still careful: a branch that gained a commit after it was merged keeps both its tip and its slot, and one the operator's own checkout stands on is refused and kept — which `update-ref` would not have refused by itself. So is one a linked checkout is stopped on at an `edit` step of `git rebase -i`, or bisecting from: both detach HEAD, so `worktree list` does not name the holder, and before `worktreeMidOperation` both were deleted — the rebase case with its `rebase --continue` left to fail on the missing ref. The bisect case is there because `BISECT_START` spells the branch without `refs/heads/`, which a comparison written for `head-name` alone would miss. Its second describe is a land the operator undid on the target, through the real `landRun`: a merge reset with `reset --hard ORIG_HEAD` and a squash reset with `reset --hard HEAD~1` must each leave `landState().landedUnchanged` false with Land offered, the branches row not "squashed in", and Delete refused with the branch and its checkout intact. Before the fix both failed at the first of those, the card reading "Already squashed into main" and Delete then removing the only ref the run's commits were in, because `isLandedTip` compared the recorded tip and never asked the target; the third case, the same squash not undone, is the control that Delete still takes it. The hand-written squash fixtures above record `landed_commit` as `landRun` now does — without it a squash reads as not landed by design.

`landAfterSquash.test.ts` drives landing a `continueBranch` chain a second time, after its first link was squash-landed through the real `landRun`, on `deleteBranch.test.ts`' harness and for its reason: the fault was in what git does from the base it was handed. With the squash reverted on `main` and link B touching only `f2.txt`, B's card must count 1 and preview clean, and the land must leave `f1.txt` reverted with a commit touching `f2.txt` alone — as a squash, and as a merge whose second parent is the branch; with `main` having edited the squashed lines since, B must be landable and counted 1 on its card and on the branches page; and a squash-landed branch with nothing new must not preview a conflict, and `resolveConflicts` must refuse with no `run_reviews` row. Before the fix all four failed: `f1.txt` came back as link A wrote it under a clean preview, B was refused for a conflict in `f1.txt`, the count was 2, and a resolution was started. The case that passed before and after is the control that the base moved rather than the check going away — a conflict in the file B did touch still refuses, with `main` unmoved. Its third describe is that ignored-file case past a squash, which `read-tree -u` overwrote, on `local.settings.json` for the same reason; its fourth, a resolution past the squash, is in `merge-queue-and-resolution.md`.

`diffSlotReuse.test.ts` is `deleteBranch.test.ts`' harness again, a database and a real repository, for the same reason: the fault was in what git says about a directory that has changed hands. Slots are reused, and `uncommittedIn` read `git status` in whatever the slot held, so once the next run had checked out its own branch there and edited a tracked file, the finished run's card listed that edit under "Uncommitted in the checkout" with the warning that landing would not bring it over, the review and validation prompts named it, and the Files tab moved a file the run only read from "named, and not changed" to "named, and left uncommitted" — while `landState` on the same run, which already proved the slot, said nothing was pending. Three of its four cases failed before the fix (the slot on another branch, the same with a branch that committed nothing, the reconciliation) and the fourth is the control that must keep passing: the run's own slot, still on its branch, with a file left in it, still lists it. The reconciliation case runs `changedSetOf` and `reconcileTouches` over the real diff rather than asserting on the diff alone, because that is the reader the operator's Files tab is.

`landGate.test.ts` is the gate in front of Land, and its two halves fail quietly in the same way: a parser that dropped a metacharacter runs a different command from the one the operator read back in Settings, and a verdict that treats "could not run" as "passed" hands back an open door to an operator who asked for a gate — neither throws, neither fails to typecheck, and the button looks the same either way. So both halves are asserted in both directions, the shapes that must be refused and the shapes that must be allowed, because a refusal that admits everything measures nothing and one that refuses everything is not a feature. A third half was added later and is the one with a security consequence: the spawn passed **no `env` at all**, so a command whose script body lives in the tree an agent just wrote inherited `UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY` and `DATA_DIR` — pinned on `childEnv`'s grounds, that no page, no log and nothing else in the app would report it if one came back. It is asserted twice on purpose. `verifyEnv` is a pure function, so a builder-only test still passes with the `env:` option deleted from the spawn, which is exactly the defect that was there; so the second describe runs the gate for real against a `node` probe that exits non-zero naming whichever variable it can see, and checks `PATH` in the same breath, because a strip that took `PATH` would refuse every land with "could not start" and read as the operator's command being wrong. A fourth half is whether the check ever ends, since `landRun` and `deliverRun` await it holding the folder's `landing` claim: under a one-second timeout a `sleep 8` script and a `sleep 6 &` one that exits 0 must both settle within the timeout plus the drain, and a process either leaves behind must not live to write its marker file. All three failed against a spawn that settled on `close` and killed only the direct child — at 8003ms, at 6004ms, and with the marker written — and they are real subprocesses on `settleOnExit`'s grounds, because the defect is a process tree. The verdict's last three cases are the uncommitted half of *which tree*: a slot holding uncommitted paths is refused and the paths named, five of them and a count of the rest, and a status that could not be read is refused rather than taken as clean — because the command runs against the files on disk and the land carries only the commits, and a check that passes on a fix nobody committed is the gate saying yes to work it never saw.

The `PATH` assertion in that file is one of four, and the other three are in `orchestrator.test.ts`, `chat.test.ts` and `review.test.ts` — one per environment builder that feeds an agent child. They exist because `PATH` is deliberately **absent** from a strip list held as six hand-copies (`docs/agent/security.md`), and `proposals/CustomStacks/01c-reach-and-permission.md` §2 rests its whole argument on that absence: a toolbox the `Dockerfile` puts on the agents' `PATH` reaches every agent child. Since board task `aff25da4` that is `UF_AGENT_PATH`, which each builder takes through `agentEnvironment`, and not this server's own `PATH`, which is root's and carries no toolbox — so each test sets the two to different values and asserts the child got the agents', which every one of them failed before the change. `chatEnv`'s is the exception since board task `6f85c72a`: its `PATH` is `chatPath()`, so `chat.test.ts` asserts that and that the toolbox still arrives first, and `cliPath.test.ts` asserts what it drops. An edit that added `PATH` to one copy has to be made in six places and nothing fails if it is made in five — the child simply stops finding a tool, inside a tool call nobody reads, with no page and no log in this app mentioning it. Each assertion is over a *planted* directory rather than over equality alone, because what §2 claims is that a directory on the agents' `PATH` arrives in the position it was put at, and each is over the composition the spawn site actually builds rather than over the bare strip: extras land after it and win every key they name. `chatEnv` is the one where that needed arranging — its extras are `githubEnv()`, whose token is a module constant fixed at load — so `chat.test.ts` sets `UF_GITHUB_TOKEN` at the top of the file and asserts the block is non-empty, since with it blank the composition is `{}` and the `PATH` line would pass having measured nothing. `chatEnv` and `reviewEnv` are exported for these tests and for nothing else, on `childEnv`'s footing rather than as an exception to the rule against it. `authEnv` and `gitEnv` are the two copies still unpinned; `gitEnv` has a `PATH`-adjacent assertion of its own at `git.test.ts:99`.

`repoLock.test.ts` is a mutual exclusion tested for the failure that it excludes nothing, which is what every wrong promise-chained lock does: chain onto the wrong promise and two bodies run side by side, and the only symptom is two callers overlapping on a live install months later. The case that carries the file asserts an *ordering* — the second body has not started while the first is still open — driven with explicit deferreds rather than timers, because a test that establishes an ordering by sleeping asserts the sleep. Two of the others are the opposite direction and matter as much: two repositories must still work at once, or a lock keyed on the process would serialise every install-wide run start behind one repository's registry work; and a body that threw must not wedge its key, because one of the four callers is the run loop and a wedged key is every isolated run in that repository never starting again — which is worse than not having the lock at all. The last two are about the map: it must forget a repository once the queue drains, and must **not** forget one while somebody is still queued behind the holder, since a third caller then chains onto nothing and runs beside the second. The second of those needed both bodies held open to be observable at all; the first version of it passed for the wrong reason, because the queued body returned inside the same tick.

`aheadRangeFor`, `parseCount` and `purgedMessage` in `land.test.ts`, and `landView.test.ts` beside them, are the count Purge reads out as what it is about to destroy. Every way of not having one became 0 — no recorded target, a target renamed away, a `rev-list` that failed and so read as `Number("") || 0` — and the one irreversible press in this app then said "Purge 0 commits" over a branch with work on it. What is pinned is that unknown and none stay two answers all the way to the sentence: the range falls back to the base commit, a count git would not give is null, and each sentence that states a count — the sheet, the armed button, `purgeBranch`'s answer, the run log's purge row in `logLine.test.ts` — names none it did not measure.

`landCardLine` in `landView.test.ts` is the Land card's one state line. `landed_at` is written once and never cleared, and a landed run can be reopened and commit again; the card said "Merged into main" whenever it was set, so a branch with new commits had Land withheld with no sentence saying why and Purge offered under a notice that the work was merged. What is pinned is that "merged" is drawn only while `merged || landedUnchanged` (or the branch is gone, which is the ordinary end of a landed run), and that otherwise the refusal is what shows.
