# Stream parsers, assist output and the outbound webhook

[← testing index](../testing.md)

Read before adding or editing tests of `buildCodexArgs`/`handleCodexStreamLine`, `toolProgressReading`, `review.ts`' assist stream parsing, `toolComposition`, `mcpStatus.ts` and `notify.ts`.

`buildCodexArgs` and `handleCodexStreamLine`, both in `orchestrator.test.ts`, are the second provider's argv and the second provider's stdout, and they earn tests on `buildArgs`' grounds plus one that half does not have: nothing in this repository has ever executed `codex exec`, so every flag in them was read off `--help` and off a rollout file rather than off a run that worked. Most of the ways of being wrong there are loud — a flag this CLI does not take fails the spawn — and the two that are not are what the cases are built around. `CODEX_PERMISSIONS` is pinned as four whole arrays rather than probed for a flag, because a row answering `--dangerously-bypass-approvals-and-sandbox` where the run asked for `acceptEdits` spawns cleanly, does the work, and hands an unattended agent the machine; its control is the assertion that exactly one mode reaches that flag and that no mode reaches `--approve-for-me` or `--ignore-rules`, the second of which would unload the `pkill` denial. And every flag must precede the `resume` subcommand: put after it they are rejected outright, which is loud, but a `resume` moved earlier confines cycle 1 and silently stops confining every cycle after it. The parser's three carrying cases are that a transport retry notice must not become the failure the run is filed under, that the token sum must take `input_tokens` and `output_tokens` and none of the three breakdowns reported beside them, and that an unrecognised event type is logged once per cycle — the last because that silence is what makes a moved CLI pin look like an idle agent. Its counterpart under `handleStreamLine` asserts the same two things of the Claude parser, which used to be the site that went silently; both now run through one `noteUnknownStreamEvent`, so a fix to one of them can no longer be half a fix. One case is there for the seam rather than for either function: the two adapters' `parseLine`s must never be each other, since reading one CLI's stdout with the other's parser reports nothing and every page renders that as a cycle that had nothing to say.

`toolProgressReading` in `orchestrator.test.ts` is the newest member of that parser's list and it earns a test for arithmetic whose every wrong answer reads as a healthy run. It turns one `tool_progress` frame — Claude Code's word that a tool call has not come back, restated every 30 seconds — into the entry the run page's live strip counts up from, and it is the only pure part of a path that is otherwise all plumbing. Three of its cases carry the weight. The start is dated from the CLI's own `elapsed_time_seconds`, so a page opened eight minutes into a build says eight minutes rather than zero, and a page that got that wrong would look exactly like a cycle that had just begun. The **first** reading of that figure wins against every later one, because whole seconds measured on another process's clock and crossed over a pipe would otherwise walk the operator's duration backwards and forwards every half minute for as long as the tool runs. And the entry is keyed on `parent_tool_use_id`, the running call's own id, never on the heartbeat's `<id>-heartbeat-<n>`, which is minted afresh each time — keyed on the second, a twenty-minute build is forty rows on a strip with room for two. The rest pin the directions the readings fall in: the name comes from the call the log already recorded rather than from the frame, since the CLI calls the `Task` tool `Agent` and one page must not have two names for one call; an unreadable elapsed figure dates the call from now rather than from the epoch, while a figure that merely arrives as a string is still honoured; and a frame with no call to key on returns null rather than an entry under an empty id. The shapes are the measured ones — 2.1.266 produced heartbeats at 30, 60 and 90 seconds for a 95-second foreground `Bash` — and the `subagent_retry` variant is pinned beside them because it is the one kind of this frame that does not mean *still working*.

`rateLimitEvent.test.ts` is gone, with the module it covered: the provider's own utilisation off the `stream-json` stream fed one dashboard card and nothing else, and card and parser were removed together on 2026-09-12 as a figure that reached no meter, no graph and no guard. One case survives, in `orchestrator.test.ts`, and it holds the deleted file's wiring grounds turned around once more: `rate_limit_event` arrives on most turns and is now deliberately ignored, so the branch that names it must go on keeping it away from `noteUnknownStreamEvent`. The case feeds a verbatim live event and asserts `acc.unknownEventTypes` stays empty. Remove that branch and nothing fails to compile, no page renders differently, and every run quietly files a routine event as a vocabulary this app has lost.

`assistToolUses` and the result-event half of `parseReviewOutput`, both in `review.test.ts`, are what an assist's stdout means now that it streams, and they earn cases in the two directions that stay quiet. A shape `assistToolUses` stops recognising is a check that appears on the run's log to have decided a task was finished without opening a single file — the exact doubt the lines were added to answer, arriving as an absence rather than an error — so the cases pin that every `tool_use` block on one `assistant` event is taken, that a `result`, a `tool_result` and a line that is not JSON at all yield nothing, and that a block carrying no `name` is still reported under a placeholder rather than dropped. The other direction is money: `parseReviewOutput` now reads a `result` event out of many lines, and the case that carries the weight is the one that gives it a stream which stopped *before* its result. A killed child's last complete line is an ordinary `assistant` event, and read as the result it files a turn that never finished as one that finished with no text having cost nothing, with the stderr that says what happened dropped — which is `settleOnExit`'s fault class reached by a different road. Both were also run over a real captured stream from the pinned CLI rather than only over fixtures; `docs/verification.md` carries that measurement and what it cost. The rendering half is two cases in `logLine.test.ts`, beside that file's plugin-attribution ones and about the same judgement: an assist's rows must wear the word the log already calls that child — `check ›`, `review ›`, `resolve ›` — while the run's own stay bare and a sub-agent's keep its name. Unattributed, those rows do not read as a missing label; they read as the run having opened a file it never touched.

`toolComposition.test.ts` is the parser on `toolResultFailures`' grounds — a shape captured from one CLI build, every field read defensively, so a rename costs the card its rows silently while the page still renders and the totals above it are unaffected — with its fixtures copied verbatim from this install's own transcripts. The rollup earns its own on `byAgent`'s bucket argument with one word changed: it *cannot* reconcile to a window total, so what it has to reconcile to is itself — every call in exactly one row, the shares adding to 1, and an unanswered call in the call total and in no share. A reading that silently dropped a bucket is a page of plausible percentages that add to 94%.

`mcpStatus.test.ts` is a cycle's `system:init` read for its MCP servers, on `toolComposition.test.ts`' grounds — a shape cut down from real init events on CLI 2.1.280, every field read defensively — and every way of getting it wrong renders as a plausible status rather than an error. The event names each server and its status but gives it no tool count, so the count is the tools whose name starts with `mcpToolPrefix(name)`, spelled the way the CLI spells it with every character it does not keep turned into an underscore. A prefix that matches nothing reads as a server that offered no tools, which is exactly what the local reader looks like with its model unloaded, so the one reading that means something would become the one every server shows; the fixture carries `uf` beside `uf_local` because a prefix loose by the trailing `__` counts one server's tools as the other's. `describeMcpServers` is the "MCP servers" line on a cycle's log, pinned whole: connected servers with their tools, failures by name, sign-ins as a count, and a status it has no wording for kept rather than dropped. `pluginMcpSightings` is what `/api/plugins` reports per plugin, and its three cases are the three ways a plugin gets somebody else's story: it takes the newest cycle that loaded *that* plugin rather than the newest cycle, so a failure is not written over by a later cycle the plugin was never in; a plugin no cycle loaded is left out rather than reported as failing; and `plugin:local-reader-probe:local` is not taken for `plugin:local-reader:local` because the two names share a start.

`notify.test.ts` covers the two halves of the outbound webhook that decide anything, and it is the filter that earns it. Getting that wrong is silent in both directions and there is no page in this app where a missed notification is visible: too wide and the channel is a POST per tool call, which is how an operator stops reading it, and too narrow is a channel that looks configured and never fires — indistinguishable from a fleet with nothing wrong. So all nine statuses are pinned in both directions, `completed` explicitly among the silent ones because the constant that carries it (`TERMINAL_STATUSES`, five readers) is the one a later edit would reach for — and pinned a second time *notified* under `UF_NOTIFY_ON_SUCCESS`, with the four statuses a run passes through and an operator's own cancel pinned still silent beside it, because the only way that opt-in can fail is by widening past the one status it names; a guard-caused `stopped` is pinned against an operator's own cancel, which is the same distinction `logLifecycle`'s level pins one file over and is made here by a latch rather than by parsing `stop_reason`; an absent `enforceable` is pinned as *enforceable* and a `no_ceiling` verdict as not, because two of the three stop emits omit the field entirely; and the 429 ladder's first rung is pinned notified with its next three silent. The eviction cap is asserted too, on `selectProbeTargets`' grounds — it bounds a set that would otherwise grow for the life of the process, and an eviction loop that never terminates is easy to write. The signature is the other half and it fails once for everybody: a receiver verifying the HMAC rejects every POST while this app records each one as attempted. Its vectors are therefore **frozen hex**, computed once and pasted rather than recomputed from `node:crypto` here, since a test that recomputes the answer with the same call the code makes passes whatever that call does — and one of them is deliberately non-ASCII, because `UF_INSTALL_LABEL` is text an operator typed and a signature over latin1 bytes is a channel that is 400 for ever.
