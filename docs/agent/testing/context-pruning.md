# Context pruning, winnow's intake filter and pruned transcripts

[← testing index](../testing.md)

Read before adding or editing tests of `contextPruning.ts`'s payback and statements, `intakeFilter.ts` and its ledger, `injectionFates`/`contextShapingEnv`, `pruneTranscript`, and transcript ownership after a prune. The `fork_attempts` row, what a cut is priced at and over, and what a forked conversation is reported as are in [forked conversations and prune money](forked-conversations-and-prune-money.md).

`contextPruning.test.ts` is its own group and earns it twice over. `paybackTurns` decides whether a cycle is ended early: wrong one way it ends a run's cycles for ever chasing a saving that never arrives, each ending paying a full-price rewrite, and wrong the other it never fires — indistinguishable from the feature being off, because all either produces is a cycle that carries on. Its two arithmetic cases are winnow's own worked examples (half the suffix pays back in 18 turns, a tenth needs 170), and they exist because the parameter is the suffix **before** the cut and passing the after figure is off by exactly the amount removed — an error that flatters the marginal cuts and typechecks perfectly. It was caught by this test during the change that introduced it. `contextTokens` is the whole of what the feature reports, and counting the file rather than the messages in it is not an approximation but a different quantity: measured here, 970 KB of file against 290 KB actually sent. `netReceipt`'s cases pin the one line that decides whether the feature looks like it earns anything — a boundary prune pays no invalidation, because `--resume` was rewriting that prefix regardless, and charging it would charge twice for one write at the 2× class against a saving at 0.1×, so every boundary prune would report a loss on the very page built to show whether it pays. Its unpriced case is `metering.md`'s rule reached from a new direction: a prune on a model with no price saved *something*, and $0.00 asserts it saved nothing.

`intakeFilter.test.ts` is the same argument one mechanism over, and it earns its place on a factor of nineteen. Winnow's intake filter is stateless: it re-drops the same tool result on every later request that still carries it, so a ledger line is a *request* and not a removal, and summing the file charges one removal once per surviving request — measured on this install's own ledger at 125 lines, 372 occurrences over 15 distinct results, a 24.8× overstatement of the only figure on that card, which nothing else in this app can be checked against, and a factor that is not a constant but roughly how many requests a result survives. So the de-dupe has a fixture of one result carried by thirty requests, written to fail if the de-dupe is removed rather than merely to describe it, with three cases around it for the ways the *key* goes wrong in each direction: byte-identical output of one tool in two sessions pooled into one saving, a `tool_use_id` ignored in favour of the fallback so that two results become one on exactly the lines winnow is being changed to write, and the ordinary life of a result — deferred for a turn under `keep_newest`, then dropped — counted twice. `netFilterSavings` is `2.0·D − 1.0·D + 0.1·D·T`, and the middle term is the one that fails invisibly: it is a **cost**, the result still being sent once uncached, so a sign flip roughly triples the headline while leaving every row above it on the card correct. The no-break-even case is asserted directly rather than left to follow from the formula, because it is the one property separating this from a prune — nothing is edited, so no prefix is invalidated and a result nothing followed still nets. Its unpriced case is `contextPruning.test.ts`'s, for the same reason. `parseLedger`'s two are `transcriptCompaction.test.ts`'s: the file is appended to by another process so its last line is routinely half-written, and a byte count that is not there must be dropped rather than read as a real figure — a zero would take a slot in the fallback key that every other unreadable line would then pool into. Its two `readFilterSavings` cases are on different grounds from everything else in the file: not arithmetic but a cache whose only failure mode is load. The route derives the horizon from `now`, so every ten-second poll asked for a span a few milliseconds later than the last one, the minute-long TTL never hit once, and the ledger read plus the join over every transcript entry ran six times a minute while returning correct figures throughout. One case pins that two polls inside a grain are one reading, and the other that a grain rollover is not — because an alignment that grew to swallow the window starts as well would serve one span's figures under another, which is the thing the cache key exists to refuse. `readLedgerAppended`'s four are on `transcriptCache.test.ts`' grounds rather than on this file's. The read went incremental because a `readFileSync` of the whole ledger cost ~214 MB of `heapUsed` on every poll that crossed that TTL at 101,929,100 bytes, and keeping a byte offset while quietly dropping rows would look exactly like that fix and understate every figure on the card, so the first case appends to a file it has already read and asserts both that the offset moved by exactly the bytes appended, anything less meaning the second pass re-read the first pass's, and that the rows are row for row what reading the file whole gives. The other three are the ways an offset goes wrong with nothing thrown: a file shortened underneath it, where holding the rows parsed before it would report requests that are no longer on disk for as long as the process lived; a half-written last line, which must neither be parsed nor be stepped over, since the process appending is not this one and stepping over it loses the row for good; and one line spanning chunk boundaries, where a carry held as a string rather than as bytes decodes half a UTF-8 sequence into a replacement character no later concatenation can undo: three megabytes of a three-byte character inside that line, so at least two of the boundaries must land mid-sequence whichever byte the run starts on.

`compactLedger`'s five cases in `intakeFilter.test.ts` are the ledger's horizon, and they are on `retentionSweep.test.ts`' grounds with one store's worth of difference: another process is appending to this file while the bound runs. Nothing bounded it — winnow has no rotation to switch on and `retention.ts`' other three sweeps reach a database, a mount and `~/.claude` — so it reached 141,916,052 bytes here, and since the reader went incremental it is the server's only per-request growth term at roughly the file's own size in heap. The inode is the case that matters most and the one a byte count would never catch: `docker-entrypoint.sh` creates this file and gives it to the agent uid as `0620`, winnow opens it by path in append mode once per line, and a compaction that renamed or recreated it would lose that race about as often as it won, leaving a root-owned `0644` file the filter can never write again — no error, no line on the card, every later request unrecorded. So the inode and the mode are asserted across a compaction, not just the contents. Beside it: a file under the ceiling comes back byte-identical and `null`, because a figure that says a sweep ran is not the same claim as one that says it found nothing; the kept region starts on a line boundary and every line in it parses, a cut inside one leaving a fragment `parseLedger` skips silently and for good; the file is still appendable and still readable end to end afterwards, which is the only way the downward-copy ordering can be asserted at all, winnow taking no lock this process could take too; and a ledger whose newest record is larger than the whole horizon is left over its ceiling rather than emptied — the case that was written first and failed, because the only line boundary in that file is its own end and truncating there took 20,070 bytes to 0.

`pruneStatement.test.ts` is `paybackTurns`' grounds transposed from arithmetic to copy, and it earns them because **every way of getting these two resolvers wrong renders a confident, well-formed sentence**. Six distinct facts — pruning switched off, winnow missing from the image, nothing worth removing, every boundary declined by the payback gate, a span no work cycle has ended in, and a span where every one of them cut — shared one blank before it, and a blank reads as "the feature did nothing" on the one card built to say whether context control earns its keep. A wrong branch here does not throw, does not fail to typecheck and does not look broken; it tells an operator something untrue in complete English. The **split** between the two is what most of the file pins: `prunerLine` answers "what is switched on", which no figure carries and which may therefore never be null — the case that forced it is real, an install with fourteen prunes on the card and no way to tell which engine made them, where a resolver allowed to fall silent went on saying nothing on exactly the install that had complained. `pruneStatement` answers "what happened in this span" and *is* allowed to be null, in the two cases where the money beside it already says everything. Its load-bearing case is the sum: the clause list is built by filtering zeroes out, so a clause lost to a typo produces a *shorter* sentence that is still grammatical and still adds up to a plausible story, which is why `boundaries` is printed as the denominator the six counts have to meet. One more pins a decision rather than behaviour — that the `unavailable` sentence carries the **server's** reason verbatim rather than one re-authored in a component. `sumPruneActivity` rides the same file for `sumPruneSavings`' reason: the counting is the half that must be testable without a database behind it. So does `netBound`, on this file's own grounds: an unsettled cost makes a net a ceiling and an unmeasured removal makes it a floor, and every wrong branch prints a well-formed label pointing the wrong way, so each of its four answers is pinned. The runs list's Pruning column rides it too — `prunedNetFields`, the route's mapping, and `prunedNetCell`, the cell — because `/api/runs` sent `netUSD` alone: a run whose only prunes were unpriced printed `+$0.00`, pruning that broke exactly even, and a ceiling printed bare, on the list an operator scans to compare runs. The final net's case asserts that nothing is sent beside it, since that list is polled every four seconds.

`injectionFates` and `contextShapingEnv` in `orchestrator.test.ts` earn theirs for the drift rather than for the arithmetic. `injectionFates` classifies the cycle's own argv against the vendor's survival table, and the failure it is built against is a flag added to `buildArgs` later that quietly has no row — a compaction notice short by one line, with nothing anywhere saying so. Its anti-drift case therefore runs the *widest real* `buildArgs` output, sandbox write set included, through the function and asserts zero `unclassified` rows, so the next flag fails a test instead of shortening a record; two more pin the two ways `ARGV_ARITY` goes wrong, an unknown flag and a known flag whose recorded arity is short, because both turn a value into a token in its own right and one of them used to be able to swallow `-p` and drop the prompt. A third pins that a token after the `--` ahead of the prompt is reported rather than read, because a flag pushed there reaches the CLI as an ignored operand. `contextShapingEnv`'s own case is the blank one, and it is the only reason it has a test: compose renders every optional variable as `${VAR:-}`, so an empty string treated as set would put `DISABLE_AUTO_COMPACT=` on the log of every stock install, which reads as a regime nobody chose.

`pruneTranscript.test.ts` is the file for what a prune does to the operator's own disk and to the receipt, around the one child it spawns, and it is the only test here that injects the child. That is `restoreTranscriptOwnership`'s exception rather than a new one: what is pinned is a difference between two directory listings taken around the spawn, and on a machine with no winnow installed — CI, and every developer checkout — `pruneTranscript` answers `unavailable` before either listing is taken, so the only test that would run at all is the one that proves nothing. Its first three are the backup sweep, whose failure is a full copy of the pre-prune transcript left inside the `~/.claude` bind mount with nothing in the tree that will ever come back for it (`grep -rn '\.bak' src/` returns one deletion in the whole codebase, and eleven such copies survived here, 18.8 MB). The mtime filter they replace could not match: winnow takes the backup with `shutil.copy2`, which carries the *source's* mtime, so the fixture's transcript is last written 999 ms into a second two seconds before the prune — the shape every leaked copy on this install had. The other two directions are asserted beside it, a backup that was already in the directory surviving, since deleting too much reaches the copy an operator kept precisely because they were about to let a tool rewrite their transcript, and a child that copied and then exited non-zero leaving nothing. The last two are the receipt: a child that rewrites the transcript outside `message` — dropping `version` and `gitBranch`, which is what every record surviving a prune here demonstrably lost — takes no prompt tokens out and still breaks the cached prefix, so it must produce a `prune_receipts` row with `tokens_removed = 0` that `netReceipt` can show a loss against, where folding it into `nothing` dropped exactly the cuts that earned nothing and kept the ones that earned something. Its control is the child that touched the file at all: a quiet boundary must not start writing receipts for invalidations that never happened.

`transcriptOwnership.test.ts` is who owns a transcript after the pruner has been over it. The pruner runs as the server, which is root, so every winnow verb that writes leaves the transcript `root:root 0600`; the next work cycle runs as the agent uid, cannot read it, and `claude --resume` answers `No conversation found with session ID: …`, which the orchestrator surfaces as `error_during_execution` at 0 ms and turns into a failed run. Measured before this existed: the same task with `contextPruning` on failed at cycle 2 for $0.14, with it off it completed for $0.41, and `chown` alone on the failing session turned the refusal into a successful resume — the failure is the expensive silent kind, since the failing cycle bills $0 and the cycle before it reports success, with nothing in the app saying what happened. The cases pin the three outcomes rather than describe them, because the whole point is that the wrong one is invisible: a `chown` that quietly did nothing looks exactly like a `chown` that worked.
