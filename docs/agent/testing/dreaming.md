# Dreaming

[← testing index](../testing.md)

Read before adding or editing tests of `dreaming.ts`, `dreamingLedger.ts`, the dreaming scan and its clock.

`dreaming.test.ts` and `dreamingLedger.test.ts` earn theirs on the same rule as `cycleCostAfterResult`, and the two files split on whether a database is needed. `signatureOf` is the whole deduplication mechanism: two spellings of one failure that fail to collapse write a second note beside a note that is already there, which is the failure mode the destination vault's own conventions exist to prevent, and nothing anywhere reports it — both notes are well-formed and only their existence together is wrong. It is asserted against the same normalisation `git show a74a1bb:"proposals/implemented - Dreaming/scripts/recurrence.mjs"` uses, because that script is where every figure behind the feature was measured and a drift would leave the proposal describing a different feature. `selectWritable` decides how many notes reach somebody's vault at all — off by one is 1,177 notes rather than 77, 93.5% of them about something that never recurred, and the symptom is a vault rather than an error. `dayKey` is tested on a zone boundary because a day is the unit the feature is denominated in and UTC is the wrong one: 22:30 UTC is already tomorrow in Berlin, so two sightings one local evening apart would read as a recurrence and qualify. `buildDreamingPrompt` is asserted on five sentences rather than on its shape, because that string *is* the enforcement — the vault's licence turns on the run reading `CLAUDE.md` first and nothing in this app checks that it does, so a prompt that quietly stopped saying it would still run, still write, and still look right in the log.

`dreamingScan.test.ts`'s first five cover the one thing in that module a pure test cannot reach, and the bug they pin was found by the feature's own first output rather than by anybody reading the code: a resumed session rewrites its earlier records into the new transcript, so the same failure is counted twice and a per-file pass cannot see it. The day assertion beside the instance assertion is the load-bearing half — deduplicating on the *signature* instead of on the record would collapse a genuine two-day recurrence into one sighting and stop the write policy firing at all, silently, which is a strictly worse bug than the one being fixed.

Its other three were added when `readOne` stopped reading a transcript whole. The scan reads at `READ_CONCURRENCY` 12 and memoises every parse, so `readFile(file, "utf8")` plus `split("\n")` held two copies of each file in flight and took `next-server`'s peak RSS to 1.5 GB on the cold scan the pane's mount fires; what replaced it changes *how a line is found*, and every way of getting that wrong leaves a readout indistinguishable from a correct one. A lone `\r` is a line break to `node:readline` and not to `split("\n")`, so the splitter is hand-rolled and the case pins it: these counts feed a write-on-second-sighting policy, and a reader that turned one unparseable line into two good records would change what reaches somebody's vault with nothing to say it had. A multi-byte character cut at a chunk edge decodes to two U+FFFD, which is still valid JSON — the record parses, carries a mangled prefix into `signatureOf`, and one recurring failure silently becomes two that each look like they happened once — so that case lays a four-byte character across the boundary `fs.createReadStream` actually reports rather than across a hard-coded 64 KiB, which would quietly stop testing anything the day Node changed its default. The third is the error path: a file really does vanish under the retention sweep between the scan's `stat` and its open, that window cannot be hit on demand, and a file that cannot be opened drives the same catch — the scan must answer for it rather than reject, and must not memoise the empty parse, which would hide the file until somebody wrote to it again. None of the three fails against the whole-file read it was written to protect, because nothing observable was meant to move; each fails against the plausible wrong version of the reader that replaced it, and each was run against one to prove it.

The ninth pins what the memo holds across a change of `dreamingTimeZone`. The memo is stamped on size and mtime, and neither moves when the zone does, so while it held each observation's day a scan after the change read every file it already had on the old boundary. Two sightings at 23:30Z and 18:00Z the next day are one Berlin day and two UTC days: scanned in UTC and then in Berlin with the memo warm, they came back spanning two days and qualified for a note, from one local evening. The case asserts one day and nothing writable, and that the Berlin scan re-read no file, because keying the day at scan time rather than stamping the zone is what keeps a zone change from costing a cold walk. It fails against the memo that held days.

The ledger's four are regression tests for two bugs a smoke test against the real corpus found after the code typechecked and passed everything else. `recordNight` upserted, so a press at noon that started a run and a 03:04 tick that then found nothing left read back as `quiet` — the one surface that shows this feature reporting a night that wrote into somebody's vault as a night that did nothing. And `reconcileDreamingNotes` indexed a night's claimed rows as one list, so a second pass in the same calendar night had its report's `NOTE 1` mapped onto the first pass's first signature: a real file path attached to a row about a different failure, with both rows existing, both paths real, and only the pairing wrong. Both are keyed on the run now, and both cases fail against the previous code. `noteStillPresent` is three-valued and tested for it, because a mount that has gone must not report every note this app ever wrote as deleted.

`reconcileDreamingNotes`'s two cases in `dreamingLedger.test.ts` are the first in any test file to call it (`git log -S reconcileDreamingNotes` over `*.test.ts` finds none before them), so the paragraph above describes a fix to the night-keyed index that no case pins. The first replays a retraction: claim three signatures for one run, report items 1 and 3, `forgetNote` the first, reconcile again. The rows used to be matched by position among the run's remaining rows, so item 1's path landed on the second row, a real file on a row about a different failure, which the pane's retraction list would send a person to delete. The case asserts that the second row stays without a path and the third keeps its own, and it fails against the positional reconciler. The second pins the fallback for rows claimed before `prompt_item` existed: they carry no number and must still reconcile in claim order rather than stop attaching altogether.

`dreamingClock.test.ts` is the file that should have existed before the feature shipped, and its nine cases exist because everything verified by hand went through the press. The clock is the half a press can never exercise, and it carried two faults that stop the feature dead while every surface still reads correctly. The cursor was a `YYYY-MM-DD` day key and the boot reconciler set it to today, so the tick's `cursor === today` test returned for the rest of the calendar day: on a machine restarted most days — this one, on every `docker compose up --build` — the nightly pass would have fired approximately never, and the only symptom is an empty Nights tab, which is also what a correctly configured install looks like on its first day. And `startDreaming` ran at boot alone, so switching Dreaming on in Settings produced a switch reading as on with no timer behind it. Neither is reachable from a typecheck, a build, or any number of manual presses. The cases pin the pair that pull against each other — a boot at 01:00 must leave that morning's 03:04 open, a boot at 10:00 must not replay it — plus the zone the window is read in, that a window fires once, and that a cursor which has never been set arms rather than fires, because a restored backup must not start an unattended agent over a window it has no record of deciding. `liveDreamingRun` in `dreamingLedger.test.ts` earns its four separately: it is one SQL predicate, and a status list that drifted from `TERMINAL_STATUSES` would put two of this app's own agents into the operator's live vault at once, which is the hazard `knowledge.ts:39` refuses a background writer over.
