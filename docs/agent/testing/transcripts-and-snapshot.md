# Transcript scanning and the usage snapshot

[← testing index](../testing.md)

Read before adding or editing tests of `transcripts.ts` (the scan, its cache, dedupe, walk and memo), `transcriptCompaction` and `buildSnapshot`'s coalescing.

The eleventh of the twenty that open the database is a count as well, one function over from `createRun`: `snapshotCoalesce.test.ts` wraps `buildSnapshot` module-wide and asks how many times it runs for 25 callers that arrive together.

It is a count and never a wall clock because the defect is invisible from any value the app produces — all 25 of those aggregations return the same answer — so a timing assertion would be the only other way to see it, and a timing assertion in CI is a flake.

Its own file for one reason: the question is what a *cold* process does with N simultaneous callers, and any case in the same process that reached `currentSnapshot()` first would already have answered it.

Its two other cases are the halves a cache would put at risk — a caller arriving after the aggregation settled must read the transcripts again rather than be served the reading already given out, and a failed aggregation must not stay in the slot, since a latched rejection would refuse every budget evaluation for the life of the process off one transient failure.

`transcriptCache.test.ts` pins that the parsed-transcript cache stops growing *and* that stopping it costs no accuracy, comparing two scans' totals through `buildSnapshot`, because keeping each file's byte offset and dropping its records would look like a fix and silently understate every window — the direction a budget guard fails open in.

`intern`'s two cases in `transcripts.test.ts` are on that file's grounds one level down, and both of its failures are silent. The table sits under `model`, `project`, `sessionId` and the six optional fields of every cached record, so one that handed back a string other than the one it was asked about would rewrite a session id in the cache and nowhere else — the transcript on disk still says what it said, so the re-read after an eviction would disagree with a figure the dashboard had already drawn, and nothing throws on the way; the values go in through `JSON.parse` rather than as literals, because a source-level duplicate is already one object in V8 and would make the case pass against a table that did nothing. The second is the growth the table would otherwise be: `project` and `sessionId` have a distinct value per checkout and per session rather than a fixed vocabulary, so a swept transcript's session id would stay interned after the records naming it had been evicted, and on a server that stays up the table, not the records, becomes the term that grows — 40,000 distinct strings go in and the table has to still be at or under `INTERN_MAX_ENTRIES`.

`transcriptScan.test.ts` pins that one scan holds a bounded number of transcripts open and reports a file it could not read rather than answering short, counting descriptors by replacing `fs.open` module-wide (`chat.test.ts`'s device for children) because sampling RSS measures the garbage collector as much as the code.

`transcriptDedupe.test.ts` pins *which* of the records sharing a dedupe key a scan keeps, which the two files above both leave open because their fixtures write one line per turn. The dedupe was written for a resumed session's identical copies, where first-seen is as good as any rule; Claude Code also writes one line per content block within a turn and puts a streaming placeholder in the output field of every line but the last, so first-seen charged `output_tokens: 4` for a turn that emitted 40,199 — 16% of corpus output on CLI 2.1.226 and 75% on 2.1.238, at 5× the price of input, in the direction a budget guard fails open in. Both halves of the rule are cases, because a scan that summed the copies instead would double every resumed session, which is the failure the dedupe existed to prevent.

`transcriptCompaction.test.ts` pins `parseCompactionBoundary` and `readCompactions` on `expiredTranscripts`' grounds — a pure parser over a format this app does not own, where every way of being wrong is silent — and the reason is `parseLine`'s own defensive style. Every field defaults to zero or the empty string so that a half-flushed record cannot throw inside a scan, and the price of that is a **renamed field reading as a real figure**: a CLI that moved `preTokens` puts "180,694 tokens summarised down to 0", or "0 down to 0", on a run log an operator has nothing to check it against. So the fixture is one of the 23 records this machine has actually written, copied verbatim and stored as a JSON *string* rather than an object, which is what stops a rename being "fixed" in the parser and the test at once; `docs/verification.md` records that those names are pinned to CLI `2.1.226` and to nothing else. The other silent half is the bound, and it has its own case: a resumed session copies earlier records forward carrying their original timestamps, so a reader bounded by session id alone re-reports every earlier compaction at the end of every later cycle — eleven cycles, one real compaction, a run log claiming eleven. One case exists only to keep the substring pre-filter from becoming the test, because a turn whose tool text merely *mentions* `compact_boundary` is the shape that actually occurs in this repository's own transcripts and taking one for a boundary reports a compaction that never happened.

`transcriptWalk.test.ts` is the directory walk, and it is `transcriptScan.test.ts`'s grounds applied to an ordering. The walk feeds a dedupe that keeps the record with the most output and a `sort` that is stable, so **file order decides which copy of a turn survives and where two turns sharing a millisecond land** — and the obvious reading of "run each level concurrently" emits every root-level transcript before any nested one, which is a different list inside the same order-insensitive-looking wrapper with every dollar figure still plausible. So the walk is compared against a depth-first reference rather than a written-down list. Its second half is the fan-out, asserted in both directions because a limit is not the same thing as reading one directory at a time and serialising would satisfy the bound while being the thing the change exists to remove; `fsPromises.readdir` is replaced module-wide to count the overlap and to refuse one directory, which is that file's device for counting descriptors.

`transcriptScanMemo.test.ts` is that the memoised scan result must be indistinguishable from rebuilding it. `runScan` skips its cross-file dedupe and its sort when every transcript's byte size and the walk's file list are what they were last time, which is 55% of the self time of a warm scan on a real corpus, and the failure mode of getting that wrong is the silent kind this suite exists for: the dashboard and every budget guard would go on reporting a figure that stopped moving, with nothing throwing and nothing failing to typecheck. Each case changes the tree in one specific way and asserts the scan saw it; the eviction bound is left at its default here, since `transcriptCache.test.ts` is where that interaction is already pinned.
