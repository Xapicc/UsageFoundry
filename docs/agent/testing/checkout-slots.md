# Checkout slots: the walk, the store and the git that readies one

[← testing index](../testing.md)

Read before adding or editing tests of how `createRun` chooses a checkout slot and how the run loop readies one: `allocateSlotPath`'s walk and what it costs in subprocesses, a checkout store inside the repository it serves, a symbolic link at a slot's path, the checkout a restart cut short and the clock on the git calls that make a reused one ready. Split out of [run-queue-and-admission.md](run-queue-and-admission.md) on 2026-11-09, when that file stood at 19,958 bytes and the ground for `slotLeafLink.test.ts` would have taken it past the ~20 KB ceiling; every paragraph but `slotLeafLink.test.ts`' moved from there unchanged, bar the first sentence of `slotProbes.test.ts`', whose "as well" pointed at a paragraph that stayed.

`slotProbes.test.ts` opens the database and is a count, though not of rows in tables or of children but of *subprocesses*: it wraps `spawnSync` module-wide and asks what one `createRun` spends on choosing a checkout slot, against two real repositories that differ only in how many of their slots were left dirty.

`createRun` runs from entry to INSERT with no `await`, which is what makes its folder claim atomic and also what makes every subprocess it spawns a hold on the one event loop that drains every agent's stdout, feeds every SSE stream and beats the server lock's heartbeat — and nothing bounded that walk: dirty slots are left behind deliberately, they are never `taken`, so every admission re-ran `git status --porcelain` over every one of them, for ever.

Nothing about that is visible from a value, a status or a page; the app stays correct and stops answering, for longer the older the repository is, so the only assertion that says so is the number of subprocesses.

Its own file for three reasons at once — it needs a real git repository inside the mount, where `orchestrator.test.ts`'s mounts are fixed at a layout that file's collision cases depend on; a wrapped `spawnSync`, which would otherwise count every other case beside it; and a cold slot memo, since the whole question is what a *first* admission on a repository costs.

Its two controls are half of it: the run must still come back isolated, because a walk that bounded itself by giving up would pass the count and quietly serialise every run on the repository, and a store whose settled slots have all been seen once must cost no git at all.

`mountRootIsolation.test.ts` opens the database and admits through the real `createRun` against mounts that are themselves repositories, because what it pins is how the checkout store being *inside* the repository it serves changes six readers that each assumed it was beside it, and every one of them fails silently. A repository at the mount root is isolated when its `.gitignore` ignores `.uf-worktrees/` and refused, with the line to add named, when it does not or when only this container's own excludes file does; a slot directory without `.git` resolves to nothing rather than to the operator's checkout, and admission skips it rather than handing it out; a run in a slot does not hold Land on the checkout its store is inside, and a run on that root with isolation off still does; a touch in another run's slot counts as outside the run's tree; and the folder listing marks the root as a repository and lists no slot. A repository nested below such a root is refused when the root does not ignore the store and isolated when it does, with two controls that a refusal alone would not catch going wrong: a repository *above* a mount root that is not one, and a mount root whose `.git` git cannot use, are not refused over. Each case failed with its fix reverted in the compiled build (2026-10-24; the nested ones 2026-10-25). The seeding and prior-read halves are pure and sit with their neighbours, in `orchestrator.test.ts`'s `planSeedCopies` and `priorReads.test.ts`'s `repoRelative`.

`slotLeafLink.test.ts` is a symbolic link standing at a checkout slot's path, admitted through the real `createRun` and, for its last case, set up through the real loop, against a real repository in a real mount with `spawn` and `spawnSync` wrapped to record where every git child ran, because the fault is in what `existsSync` and git do with a link and a fixture stating that would assume it. Nothing in this app makes a link there and anything that can write the store can plant one. `allocateSlotPath` asked `existsSync`, which follows one: a dangling link at `<slug>-1` was handed out as free and the run failed on git's "already exists", and a link to an empty directory inside the repository's own checkout read clean and ours, was handed out, and `worktree add` wrote a full checkout into the operator's tree through it before the first cycle's containment check failed the run. The first two cases assert each is skipped to `<slug>-2` and, for the second, that no git ran in the link or its target. The third plants the link after admission, while the run is queued, and asserts `ensureWorktree` refuses it by name with nothing written into the target, no git through it and nothing registered. All three failed against `aeca455d`'s source; with `ensureWorktree`'s check removed from the compiled `.test-build/lib/orchestrator.js` the third fails alone, on the checkout written through the link. The census clause the refusal gives a link is pinned in `orchestrator.test.ts` beside the other exhaustion sentences.

`cutOffCheckout.test.ts` is the checkout a picked-up run is handed when a restart cut its `git worktree add` short, driven through the real loop on `stackWait.test.ts`'s harness, because the adoption is decided in `ensureWorktree` against a real repository and a real `git status`, and its failure is a cycle that ends `completed`. The state is constructed rather than raced: the checkout removed and re-added with `--no-checkout` and git's `initializing` lock written back. The stub reports the directory, how many of the fixture's files are on disk and `git status`' line count. A run that has worked must be refused by the slot's name with the tree left as it was; one closed out by `reconcileOnBoot` before its first cycle must be spawned in a full checkout with a clean status and the lock gone; an unlocked never-worked checkout with every file deleted, and a hand-over onto the predecessor's half-made slot, must both be refused before any spawn. The four failed before the fix, each spawning the agent where 50 files read deleted. The control passed before and after: a run resumed into its own finished checkout keeps its uncommitted edit and its new file. Its own file for `stackWait.test.ts`'s reasons, `reconcileOnBoot` acting on every row among them.

`checkoutGitClock.test.ts` is the clock on the git calls that make a reused checkout ready for a run, driven through the real loop on `cutOffCheckout.test.ts`' harness with a `GIT_BIN` stub that hangs one call in the slot, and `mock.timers` to move 20 seconds and then thirty minutes without waiting. The fault was a `SIGKILL` that reads as `ok: false` and an empty `stderr`: the run failed at setup with `Could not start branch …: ` and, for `status`, with "still has uncommitted work" about a tree nobody had read, and neither throws or shows on a page that is not the run's own. Its stub changes when git answers and nothing about what it says; the child and the kill are real. Its own file because `GIT_BIN` is read when `config.ts` loads. The first run is waited out past its `handoff` event, because its `emitHandoff` runs a `status` in the same slot after the run reads `completed` and would take the hang meant for the second. The `index.lock` case is a guard rather than a fail-first: it asserts that git's own refusal reaches the run's reason unaltered, which was already true and is what a message built from the timeout would break.
