# The live page: its stream, tiles and sub-agent roster

[← testing index](../testing.md)

Read before adding or editing tests of the bounds on `/api/runs/live/stream`, of the `/runs/live` page's fold over that stream, or of the sub-agent roster its tiles carry. Split out of [Stream parsers, assist output and the outbound webhook](stream-parsers-and-webhook.md).

`liveStream.test.ts` pins the bounds on `/api/runs/live/stream`, on the per-run route's grounds multiplied by the number of running runs: a replay bounded by rows and not bytes is a response of megabytes held in the stream's queue once per open dashboard, so `boundTail` keeps the newest event even when it alone is over and counts what it dropped, and `replayShare` splits the budget evenly so one run's large events cannot empty another's tile. `clipForTile` earns the most cases, because the failure there is two pages disagreeing about what an agent did: a tile's `tool` line must be the run page's line character for character while carrying 160 characters rather than a `Write`'s body, so every input shape `toolArgs` distinguishes is checked through `describeEvent` both ways. `liveCounts` and `sameCounts` have cases for `waiting-for-stack`, which `activeRuns()` returns and the strip once counted nowhere, so it read "0 running · 0 queued · 0 paused" over a run waiting on a person; a `sameCounts` that skipped the field would leave the stream silent when that count alone moved.

`liveTiles.test.ts` is `/runs/live` as a fold over that stream, and every way of getting it wrong renders a page that looks right: a reconnect replays each tail, so a `join` that appended rather than replaced would double every tile's log once per dropped connection — a repeated block reads as an agent that did the same thing twice — and a tile that survives the `ready` naming the runs still running is a run that ended while the connection was down, on screen as one gone quiet. Its one case about the sub-agent roster is the mid-run page: a `join` that did not carry it would leave a tile opened after a delegation began saying nothing about it until the roster next moved.

`liveSubagents.test.ts` is the fold behind that roster, and it earns its cases on `runTasks.test.ts`'s grounds — a claim derived from an event stream, where every wrong answer renders as a tile that is working: a sub-agent missing reads as a run that delegated nothing, one never removed as a delegation still at it, and a heartbeat counted as one as a run busier than it is. Its lines are 2.1.280's own, captured on 2026-10-16 against a loopback stub of the Messages API and cut to the keys the fold reads. A foreground call is on the roster from its `tool_use` — the strip's first word is the 30-second heartbeat — its heartbeats move nothing and return the same state, so nothing is published, and it ends once whether the task's end or the `tool_result` says so first, and at the `tool_result` alone for a CLI that files no task. A background one survives the `tool_result` that acknowledges its launch and ends on `task_notification` alone, and an emptied `background_tasks_changed` does not end it, because leaving the snapshot is how a finish looks too. The case that carries the most weight is the measured surprise: a call with no `run_in_background` was backgrounded anyway, so the kind comes from `task_started`'s `is_backgrounded` — read off the input instead, the commonest sub-agent ends at its own launch, which was confirmed by mutating the compiled fold. A heartbeat from a tool inside a sub-agent opens nothing in either shape a later pin could send (2.1.280 sent none for a sub-agent's blocking `Read`); one that is the first word of a delegation is dated from its own elapsed figure and is left undated without one, `runTasks.ts`'s `startedAt` rule. The sweep at the cycle's end is a line in `runIteration` rather than in the fold, so it is pinned in `cycleDeadline.test.ts` against a real child a Stop kills mid-delegation, and confirmed to fail with the line removed. The count the silence deadline reads, `backgroundSubagents`, has four cases on the same fixtures: a foreground delegation is never counted at any prefix of its life, a background one is from its launch to its `task_notification`, a call that left the flag out is counted only once `task_started` says it is backgrounded, and a foreground call patched into the background is counted — each is a hung cycle kept alive or a healthy one killed, and the first was confirmed to fail with the foreground counted.
