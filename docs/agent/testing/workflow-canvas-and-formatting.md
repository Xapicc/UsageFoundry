# Workflow canvas ordering and page formatting

[← testing index](../testing.md)

Read before adding or editing tests of `canvasGraph.ts`' section ordering and `format.ts`' pass and schedule drawing. The tests of a workflow instance's status, halt, boot reconcile, schedules and routes are in [workflow-instances.md](workflow-instances.md).

`canvasGraph.test.ts`'s section cases are the two things the *browser* decides about a body, and both are silent. The order is one: `bodyOrder` is what the frame marks its members by and what `BlockStatement` reads out, and that sentence is what a press of Run is approved against — an order taken off anything but the body's own edges renders a plausible section and runs it in a different order, and nothing throws. So the cases pin that the edges decide it, that edges arriving from outside the section do not, and that a body which is not one way in and one way out yet still *terminates and answers the same twice* — which is the bounded relaxation, and a body is disjoint, forked or cyclic for as long as it takes to assemble one. The frame is the other: it has no stored coordinate by design, so a wrong derivation has nothing to fall back on, and the cases pin that it encloses every member and not the loop, that a member at the origin does not push it off the sheet, and that it fits inside what `layoutBounds` sizes the surface to — the last one because `CANVAS_PAD` is the whole of the margin a frame has to live in and a pad wider than it clips silently. A frame with **nothing** in it is a case of its own now that a loop has no card: the frame is the only thing on the canvas that can select or delete one, so a derivation that answered nothing there would leave the loop in the graph with no way to reach it but abandoning the draft. The frame gestures earn five more, and each stands in front of something an operator cannot undo in an app with no undo. `markedAfterPress` is the half in front of the gesture — what a press on a block leaves marked, which is what Repeat is then pointed at — and it is a function at all because the press arrives by four routes and used to be written out beside two of them: the card's body selected and marked nothing, so Repeat could not be aimed at a section an operator had clicked across, and the footer and every card's label said otherwise. Its cases pin that a plain press replaces however much was marked, that a held modifier appends rather than replaces, that a second press with one held takes the block back out — an id marked twice would draw one outline and count as two blocks — and that it never writes in place, because a list mutated under `setMarked` is a re-render that never comes. The gesture that reaches it cannot be asserted here at all: marking is client state and this suite has no DOM, so what a Shift-click does is on `docs/verification.md`'s by-hand list, where it was measured. `resolveRepeat` picks the block a frame *starts* at out of a marked set: picking the wrong one frames a different section, and the picture agrees with itself either way, because membership is derived from whatever it picked. `linksWithoutMember` splices rather than cuts, which is the one with the worst failure — membership is the forward walk from the entry, so a cut takes everything after the removed block out with it, and the operator asked for one and lost four. `worstCaseRuns` is the number a press of Run is approved against and the one nobody computes in their head, because an orchestrator member's fan-out is spent again on every pass; its null cases matter as much as its arithmetic, since a blank cap read as zero approves an unbounded press of Run, and one case holds it to `normalizeWorkflowInput` at every pass cap, because the figure an operator is shown and the figure Save refuses at are one promise and two copies of the arithmetic once disagreed by the deciding turn; another feeds it `worstCaseMembers`, the editor's own reading of its drafts, over a section with a review member, because that reading once dropped `fixRounds` and stated 20 runs where Save refused 80. And a link that reaches a member which holds no branch must not carry one — only a run block has one at either end — or the Put in gesture writes a graph the server refuses, over a control the operator was never shown. Three more routes reached the same refusal and are asserted through `normalizeWorkflowInput` rather than through the flag on one link, since the defect is the refusal: a fan-in drawn with the Link tool, a splice where two branches met, and a member switched away from a run block. The last has a partner pinning that `linksWithKind` leaves a branch outside a section as it was, where the operator set it with a switch they can still see. `sectionLinkStatement` is the in-section link panel's sentence, which is the whole of what that panel offers and what the operator acts on: it once called an *either way* link refused and said to redraw it, and a redrawn link is minted *only if it completes*, so the case pins the drawn condition, no refusal, and the server accepting that link. It is a function rather than a rendering because `WorkflowEditor.tsx` imports through `@/`, which the test build does not resolve at runtime. The `draftSignature` cases are the standing bar one field along: a frame built and not saved has to leave with a dialog, a member put in and taken out again must land back on the signature it started from, and a section on a block that is not a loop must not raise one, because a save refuses that by name. `duplicateBlock` and `spotBeside` earn their cases on a copy that saves without complaint and is wrong: a copy that kept a link is a second block fed by the same branch, a billed run nobody drew; one that kept a `repeats` link is a block in two bodies; one placed on another card is a block nobody can see and the server will still start. So the cases pin that the copy is wired to nothing once it is on a graph, that it is outside every frame, that it saves through `normalizeWorkflowInput`, that a loop and the 26th block are refused, and that its spot is clear of the cards already drawn.

`format.test.ts`'s `passesOf` cases guard what a pass is drawn as, and every one of them fails with the whole page still looking right. The load-bearing one is the member run that names its loop in `emittedBy`: read as "something decided on this" it is folded under the loop and drops off the page entirely, which is an agent that spent money with nothing on screen saying it ran. The fan-out case is the spend half of the same fact — a run an orchestrator *member* decided on belongs in the pass whose cap paid for it, and read anywhere else the figure beside that pass understates what one press of Run is spending. The ordering case earns its own because position is two sequences here, one for runs and one for ledger rows, so an interleave on it draws the merge member ahead of the runs it landed; and a member outside the section's declared order must sort last rather than vanish, since an instance written before that field existed reads every member that way. The landing case is the one claim on the page about somebody else's checkout: stated before the merge member has run it says the next pass starts from nothing, so "landed 0 of 0" on a pass still working is the failure the test pins shut. The two `loopSpendShown` cases pin the loop card's figure against `loopSpend`'s: a sum of runs alone typechecks and reads well under a cost limit the loop just stopped on, so one case asserts the orchestrator's and the merge's turns are in it and an unmeasured turn is not added as free, and the other that a loop with nothing measured reads as a dash rather than `$0.00`.

`format.test.ts`'s `fmtInstantWithZone` cases guard the schedule card's "Next start", which printed on the browser's clock beside words naming the schedule's zone: right for a reader in that zone and an hour out, well formed, for anyone else. They pin the schedule's wall clock on either side of a clock change and under two reader zones, and that a zone the browser does not know is read in the reader's own *and labelled with it*.
