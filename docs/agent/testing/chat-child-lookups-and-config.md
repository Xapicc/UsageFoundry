# Names a dropped child runs, and what the chat child loads

[← testing index](../testing.md)

Read before adding or editing tests of `spawnCommand` and what `CLAUDE_BIN`/`CODEX_BIN` resolve to, `chatPath`, or `chatEnv`'s `HOME`, `PATH` and git block, `chatHomeEnv` and `chatSettingsArgs`. Split out of [`spawn-argv-and-child-env.md`](spawn-argv-and-child-env.md) when that file passed 20 KB; the rest of the child environment's tests are still there.

`cliPath.test.ts` is `git.test.ts`'s `GIT_BIN` case moved one boundary down, to the children dropped to the agent uid. It plants a `claude`, a `node` and the configured `CODEX_BIN` name first on `UF_AGENT_PATH`, drives `claude auth status` and `codex login status` through their real spawn sites, and asserts that none of the three ran. `CLAUDE_BIN` and `CODEX_BIN` used to reach `spawn` as bare names, and Node looks a bare name up on the child's `PATH`. That `PATH` starts with the agent-owned `/home/node/pytools/bin`, so a `claude` a work cycle left there was what every later spawn ran, including the chat child with `UF_CHAT_GID` (board task `af2a031b`). The `node` covers the image's `codex`, whose `#!/usr/bin/env node` repeats the same lookup inside `env`. The rest of the file pins the resolver's branches, because each one fails the same silent way: an absolute value kept as written; a relative one resolved against the server's cwd rather than a child's worktree; a bare name taken from the first executable file on the server's `PATH`, with empty and relative entries skipped; an `env` interpreter resolved there and handed the script; and a name found nowhere refusing the spawn rather than the import, with one boot-log line naming the `PATH` it searched. Nothing about the failure is visible: a planted copy that forwards to the real CLI passes every other test in the suite. Its last block moves the same plant one step later, to what the chat and block child runs by name once started (board task `6f85c72a`): `/bin/sh -c git` and an `env node` hook script, each spawned with `chatEnv()`, must run the copies on the server's `PATH` and not the ones planted first on `UF_AGENT_PATH`, and `chatPath` must keep the stacks' toolbox and the server's directories in the agents' order while dropping an empty or relative entry. Run against `chatEnv` as it was, with no `PATH` line of its own, the two spawn cases failed because the planted `git` and `node` ran. That child holds `UF_CHAT_GID`, so a planted `git` there was a work cycle running code with the chat's capability. A second block does the same for what that child loads from a file (board task `7dd5f973`, `security/chat-child-config-files.md`): a `~/.gitconfig`, `~/.bashrc`, `~/.profile` and `usercustomize.py` in the agents' `HOME`, and a repository's `core.fsmonitor` and hooks, each asserted to run with the channel open and not under `chatEnv(<scratch home>)`. Against the old composition all four failed. A block nested in it does the same for what `fetch`, `push` and `log` run from a repository's `.git/config` (board task `5219cea7`): a credential helper and askpass, `core.sshCommand`, a local remote's `uploadpack` and `receivepack`, an `ext::` URL, `core.gitProxy`, and the three signature programs. With the old two pairs, all ten ran under `chatEnv`. A second case asserts that `chatEnv(…, <token>)` still answers github.com from the token. That case failed with `agentGitEnv` appending the chat's pairs after the GitHub ones, because the empty `credential.helper` among them empties the helper list. Its runner drops `GIT_SSH_COMMAND`, which an agent's own sandbox sets and which outranks `core.sshCommand`. Beside them are pure cases for `chatHomeEnv` and for `chatSettingsArgs` keeping one `--settings`, two for the capability directory's `denyRead` (board task `f3cb882a`) — that `chatCapabilityDenyRead` names `MCP_CONFIG_BASE` under a chat group and nothing without one, that it reaches the one `--settings` without `sandbox.enabled`, and that a stock install's `none` arrangement withholds the whole overlay and the deny with it — and `privsep.test.ts` pins that `scratchDirMode` gives a work cycle no bit and the chat child all three.

`blockStartupGit.test.ts` is the same plant moved to the one git this child runs before the model decides anything (board task `7764bc65`, `../security/chat-child-config-files.md`). In a repository cwd the pinned CLI runs `git status` at startup, outside any `Bash` sandbox, and a clean filter named from `.git/info/attributes` runs on it; no git setting turns a filter off. A workflow block was spawned standing in its folder, so a block run where a work cycle had worked ran that cycle's filter with the chat group. The file plants that filter in a repository under its mount. It first asserts that the measured `git status` under `chatEnv()` runs the filter in the repository, so the second case cannot pass on a plant that never fires. It then drives the real `runOrchestratorChild` with `folder` set to the repository and `CLAUDE_BIN` at a stub that runs the same `git status` in its own cwd. The filter must not run, the cwd must be outside the folder, the folder must be among the `--add-dir`s, and the appended system prompt must name it. With the compiled launch patched to stand in the folder again, the spawn case failed because the filter ran. It opens the database for `promptArgv.test.ts`'s reason, and starts a real child because the cwd is decided inline at the spawn.
