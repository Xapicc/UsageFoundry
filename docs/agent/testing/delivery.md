`delivery.test.ts` is the exit, and the three ways it could be wrong quietly. `parseRemote` decides *where* something is published, and getting it wrong does not throw — it opens a pull request on somebody else's repository, or refuses a perfectly good remote for having been cloned over SSH rather than HTTPS. `planDelivery` decides *whether*, and its dangerous failure is the permissive one: a plan that said yes with no token produces a push that fails half-way, and a plan that did not notice `head === base` opens a pull request with no commits in it. `readDeliveryFields` decides whether a press may start at all: the route used to cast its body, so a `title` that was not a string threw at `.trim()` after `git push` had published the branch, and its cases refuse each non-string shape by field and by what arrived while reading `{}` and an empty title as the ordinary press.

`deliverBlockRun.test.ts` drives a workflow's deliver block against a real repository, on `deliverRun.test.ts`' harness: a database, the run's own checkout, a local bare repository standing in for the remote through `pushInsteadOf`, and a `fetch` stub for the pull request, so nothing reaches GitHub. It is its own file for that harness's reason, and it earns a place because the block's whole reason to exist is a claim no pure function can state — that `deliverRun`, unlike a merge block, does not need the operator's checkout clean. The first case pushes with a tracked file modified and an untracked one in the checkout and asserts the working tree is exactly as it was afterwards; a refactor that made delivery ask `landState` whether the checkout is `blocked` would put the failure that sent this block here back, and nothing else would fail. The other three pin what silently differs from a merge block: a branch with nothing on it is the block's skip and pushes nothing, a branch that already has a pull request is not pushed again, and a refused verify gate fails the block and pushes nothing. The pure half — `deliverBlockOutcome`, the `deliver` arm of `edgeVerdict`, and the save-time refusals — is `workflows.test.ts`, beside the merge block's cases. `bootBlocks.test.ts` carries two cases for the sentence a restart and a halt write on a deliver block, which the SQL picks by parameter position, so an arm left out reads as "deciding what to start". `schedules.test.ts` pins that a budgeted workflow holding a deliver block is still refused a schedule, at the door and when a card is approved.

`deliverBlockRun.test.ts` has a second describe for the retry, `retryDeliverBlock`, on two branches behind one block with a verify command that refuses whichever branch a file names: the check runs in the run's own tree, so the command reads the commit's file, which names its branch. The first case fails one branch and delivers the other, asserts `pickUpsOf` offers the block as `kind: "deliver"` and nothing else, clears the refusal, retries, and asserts the pull requests opened are the first branch's and then the missed one's with the first branch's remote tip unchanged, its address still in the replaced note, and the list empty afterwards. It was confirmed to fail with the `deliveredPullRequest` skip removed from the compiled `deliverBranch`, which is the claim the whole retry rests on and is otherwise invisible: GitHub's refusal of a second pull request would surface only on a real remote. The second case retries with the refusal still in place and asserts the branch is asked again, refused again and offered again, so a retry never reads as a settlement. The third asserts the door and the list agree on a started successor, in the door's sentence and the list's, with nothing written; the fourth, that a block which is not failed is refused in its own sentence and that the merge door does not open a deliver block, so a stale button on the page cannot cross the two.
