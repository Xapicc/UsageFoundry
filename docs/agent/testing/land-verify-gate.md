# The verify gate in front of Land

[← testing index](../testing.md)

Read before adding or editing tests of `landGate.ts`, `verifyCommand.ts`, `verifyEnv` or `verifyTreeVerdict`. Split out of [Landing, delivery and the land gate](landing-and-delivery.md) on 2026-10-07, when that file reached the size cap; what the Land card says of the gate before a press is there, under `midOperationSlot.test.ts`.

`landGate.test.ts` is the gate in front of Land, and its two halves fail quietly in the same way: a parser that dropped a metacharacter runs a different command from the one the operator read back in Settings, and a verdict that treats "could not run" as "passed" hands back an open door to an operator who asked for a gate — neither throws, neither fails to typecheck, and the button looks the same either way. So both halves are asserted in both directions, the shapes that must be refused and the shapes that must be allowed, because a refusal that admits everything measures nothing and one that refuses everything is not a feature. A third half was added later and is the one with a security consequence: the spawn passed **no `env` at all**, so a command whose script body lives in the tree an agent just wrote inherited `UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY` and `DATA_DIR` — pinned on `childEnv`'s grounds, that no page, no log and nothing else in the app would report it if one came back. It is asserted twice on purpose. `verifyEnv` is a pure function, so a builder-only test still passes with the `env:` option deleted from the spawn, which is exactly the defect that was there; so the second describe runs the gate for real against a `node` probe that exits non-zero naming whichever variable it can see, and checks `PATH` in the same breath, because a strip that took `PATH` would refuse every land with "could not start" and read as the operator's command being wrong. A fourth half is whether the check ever ends, since `landRun` and `deliverRun` await it holding the folder's `landing` claim: under a one-second timeout a `sleep 8` script and a `sleep 6 &` one that exits 0 must both settle within the timeout plus the drain, and a process either leaves behind must not live to write its marker file. All three failed against a spawn that settled on `close` and killed only the direct child — at 8003ms, at 6004ms, and with the marker written — and they are real subprocesses on `settleOnExit`'s grounds, because the defect is a process tree. The verdict's last three cases are the uncommitted half of *which tree*: a slot holding uncommitted paths is refused and the paths named, five of them and a count of the rest, and a status that could not be read is refused rather than taken as clean — because the command runs against the files on disk and the land carries only the commits, and a check that passes on a fix nobody committed is the gate saying yes to work it never saw.

The `PATH` assertion in that file is one of four, and the other three are in `orchestrator.test.ts`, `chat.test.ts` and `review.test.ts` — one per environment builder that feeds an agent child. They exist because `PATH` is deliberately **absent** from a strip list held as six hand-copies (`docs/agent/security.md`), and `proposals/CustomStacks/01c-reach-and-permission.md` §2 rests its whole argument on that absence: a toolbox the `Dockerfile` puts on the agents' `PATH` reaches every agent child. Since board task `aff25da4` that is `UF_AGENT_PATH`, which each builder takes through `agentEnvironment`, and not this server's own `PATH`, which is root's and carries no toolbox — so each test sets the two to different values and asserts the child got the agents', which every one of them failed before the change. `chatEnv`'s is the exception since board task `6f85c72a`: its `PATH` is `chatPath()`, so `chat.test.ts` asserts that and that the toolbox still arrives first, and `cliPath.test.ts` asserts what it drops. An edit that added `PATH` to one copy has to be made in six places and nothing fails if it is made in five — the child simply stops finding a tool, inside a tool call nobody reads, with no page and no log in this app mentioning it. Each assertion is over a *planted* directory rather than over equality alone, because what §2 claims is that a directory on the agents' `PATH` arrives in the position it was put at, and each is over the composition the spawn site actually builds rather than over the bare strip: extras land after it and win every key they name. `chatEnv` is the one where that needed arranging — its extras are `githubEnv()`, whose token is a module constant fixed at load — so `chat.test.ts` sets `UF_GITHUB_TOKEN` at the top of the file and asserts the block is non-empty, since with it blank the composition is `{}` and the `PATH` line would pass having measured nothing. `chatEnv` and `reviewEnv` are exported for these tests and for nothing else, on `childEnv`'s footing rather than as an exception to the rule against it. `authEnv` and `gitEnv` are the two copies still unpinned; `gitEnv` has a `PATH`-adjacent assertion of its own at `git.test.ts:99`.

`midOperationSlot.test.ts`'s last describe is a run's detached checkout once a later run was handed the slot, on that file's harness (`conflict-resolution.md`) and for `worktrees-and-branch-chains.md`'s rule that a detached HEAD is the run's only while something ties it to the run. `slotState` read any detached HEAD at the recorded path as the run's, so with a later run running a rebase of its own branch there the Land card and Commit told the operator to switch that live checkout onto the earlier run's branch. What is pinned is that the card and the press give the taken-over sentence for a later run's plain detached HEAD, its rebase, and a finished one's, without switching anything; that Commit neither says "switch it back" nor calls the slot gone; and the two controls, a later run on its own branch and the run's own continuation recorded at the path, which must keep their answers. Four of the six failed before `laterRunHolds`; the controls passed.

`landAfterVerify.test.ts`' describe "whose own ignored file the run's branch tracks" is the switch of a reused slot meeting a file git ignores, on that file's harness and for `review-verify-command.md`'s reason: `git status` does not list it, so the slot reads clean, and `git checkout` replaced it going in and deleted it coming back. It asserts the later run's file content, which no refusal sentence can stand in for, for Land and for a review block's `verifyBranchForReview`, plus the control of a slot holding no file there, which must still switch and land. The first two failed before `--no-overwrite-ignore`.
