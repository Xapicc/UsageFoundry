# Run write order

[← testing index](../testing.md)

Read before adding or editing a test of the order runs are listed, queued, positioned or named in when several are written in one millisecond. The cases live in one test file, listed under [run-queue-and-admission.md](run-queue-and-admission.md) with the tests beside it, and are here because that file is past the size this directory keeps to.

`runWriteOrder.test.ts` opens the database and drives `createRun` with `Date.now` held, because a fan-out, a workflow press and an orchestrator block's emission each create their runs in one synchronous pass, `created_at` is a millisecond clock and `id` is a random UUID. Each wrong answer is a list that looks right. Five cases each write a batch and assert write order: the runs page lists it newest-written first (`listRunsPage`'s `rowid DESC`); the queue band lists queued and waiting runs in write order, and `walkQueue` promotes the queued ones in that order (a band with no tiebreak puts every waiting run last, because `idx_runs_status` hands the statuses back one at a time); `queuePosition` puts only earlier-written runs ahead in a shared folder (every one of eight read 7); a hand-over chain's Push refusal names its newest link (`runsOn` in `projects.ts`); and `branchInventory` lists a fan-out's branches newest-written first (`branchBearingRuns` in `land.ts`). The clock is held because in this container 200 `createRun`s in a loop took 409 ms and none shared a stamp. Each case was checked failing with its own change reverted in the compiled build, and with nothing else reverted (2026-11-08).

A further case, in its own `describe`, reopens a batch rather than listing one: eight runs written in one millisecond, finished having worked a cycle, are handed to `reopenFleet` newest first, the order the page sends them in. Its grounds are that the pick-up order is observable, because `reopenRun` ends in `promoteQueued` and so the first run picked up is the one that starts when a slot is free, and `queueCompare` can only re-order what is already queued. `dependenciesFirst` sorted its nodes on `created_at, id`, which gave UUID order inside a shared millisecond; the case asserts the picks came oldest-written first. The order is read off `reopened_at`, with `Date.now` moving one tick per read after the batch is written, so each run's stamp records its own pick. It failed with the query on `id` (the eight came back in sorted-UUID order) and passed on `rowid` (2026-11-09, compiled build).
