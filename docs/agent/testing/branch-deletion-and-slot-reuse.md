# Deleting a landed branch, a squashed chain's second land and a reused slot

[← testing index](../testing.md)

Read before adding or editing tests of `deleteBranch`, of landing a `continueBranch` chain after its first link was squash-landed, or of `uncommittedIn` on a slot a later run has reused. Split out of [Landing, delivery and the land gate](landing-and-delivery.md); the harness these drive is described there, under `landAfterVerify.test.ts`.

`deleteBranch.test.ts` drives `deleteBranch` on `landAfterVerify.test.ts`' harness, a database and a real repository, for `conflictedPaths.test.ts`' reason: the fault was in what git answers to the question this app put to it, so a fixture stating git's answer would be stating the very thing in question. `git branch -d` tests a branch against HEAD of the operator's checkout rather than against the run's target, so with that checkout on any branch lacking the run's work every merged branch was refused as "not fully merged" — after its slot had been removed. Its first case is that scene and failed before the fix with exactly that sentence; a squash-landed branch with its tip unmoved is deleted through the same compare-and-delete, from the run that landed it and from the link before it, whose own `landed_tip` is empty — that case failed with the check before the claim reading one run ("has 2 commit(s) that are not in main"), and again with only the compare inside the claim reading one run ("one of the two changed while this was being checked") — and the tracking section Deliver's `--set-upstream` writes goes with it, as it did under `branch -d`. The two refusals are the half that says the door is still careful: a branch that gained a commit after it was merged keeps both its tip and its slot, and one the operator's own checkout stands on is refused and kept — which `update-ref` would not have refused by itself. So is one a linked checkout is stopped on at an `edit` step of `git rebase -i`, or bisecting from: both detach HEAD, so `worktree list` does not name the holder, and before `worktreeMidOperation` both were deleted — the rebase case with its `rebase --continue` left to fail on the missing ref. The bisect case is there because `BISECT_START` spells the branch without `refs/heads/`, which a comparison written for `head-name` alone would miss. Its second describe is a land the operator undid on the target, through the real `landRun`: a merge reset with `reset --hard ORIG_HEAD` and a squash reset with `reset --hard HEAD~1` must each leave `landState().landedUnchanged` false with Land offered, the branches row not "squashed in", and Delete refused with the branch and its checkout intact. Before the fix both failed at the first of those, the card reading "Already squashed into main" and Delete then removing the only ref the run's commits were in, because `isLandedTip` compared the recorded tip and never asked the target; the third case, the same squash not undone, is the control that Delete still takes it. The hand-written squash fixtures above record `landed_commit` as `landRun` now does — without it a squash reads as not landed by design.

`landAfterSquash.test.ts` drives landing a `continueBranch` chain a second time, after its first link was squash-landed through the real `landRun`, on `deleteBranch.test.ts`' harness and for its reason: the fault was in what git does from the base it was handed. With the squash reverted on `main` and link B touching only `f2.txt`, B's card must count 1 and preview clean, and the land must leave `f1.txt` reverted with a commit touching `f2.txt` alone — as a squash, and as a merge whose second parent is the branch; with `main` having edited the squashed lines since, B must be landable and counted 1 on its card and on the branches page; and a squash-landed branch with nothing new must not preview a conflict, and `resolveConflicts` must refuse with no `run_reviews` row. Before the fix all four failed: `f1.txt` came back as link A wrote it under a clean preview, B was refused for a conflict in `f1.txt`, the count was 2, and a resolution was started. The case that passed before and after is the control that the base moved rather than the check going away — a conflict in the file B did touch still refuses, with `main` unmoved. Its third describe is that ignored-file case past a squash, which `read-tree -u` overwrote, on `local.settings.json` for the same reason; its fourth, a resolution past the squash, is in `conflict-resolution.md`. "A run squash-landed twice" lands one run twice, `main` reverting or editing the first squash in between, and resets the second away: the card must count 1 and preview clean, and the land must leave the revert in place; before `run_squashes` it counted 2, previewed a conflict in `f1.txt` or put the reverted change back. "Undoing a land past a squash" asserts `reset --hard ORIG_HEAD` returns `main` to just before that land; before, it went back past the first squash. Its last holds `main`'s ref lock while link B lands past the squash: a merge and a squash, both refused at their commit, must get `lockRefusal`'s sentence over an empty status with no `MERGE_HEAD`; before `resetDespiteRef` both said the land was still staged.

`diffSlotReuse.test.ts` is `deleteBranch.test.ts`' harness again, a database and a real repository, for the same reason: the fault was in what git says about a directory that has changed hands. Slots are reused, and `uncommittedIn` read `git status` in whatever the slot held, so once the next run had checked out its own branch there and edited a tracked file, the finished run's card listed that edit under "Uncommitted in the checkout" with the warning that landing would not bring it over, the review and validation prompts named it, and the Files tab moved a file the run only read from "named, and not changed" to "named, and left uncommitted" — while `landState` on the same run, which already proved the slot, said nothing was pending. Three of its four cases failed before the fix (the slot on another branch, the same with a branch that committed nothing, the reconciliation) and the fourth is the control that must keep passing: the run's own slot, still on its branch, with a file left in it, still lists it. The reconciliation case runs `changedSetOf` and `reconcileTouches` over the real diff rather than asserting on the diff alone, because that is the reader the operator's Files tab is.
