# Landing, conflict resolution and the merge queue

[← testing index](../testing.md)

Read before adding or editing tests of `git.ts`, `land.ts`, `mergeQueue.ts` and its drain, conflict resolution's checkout, budget and silence deadline, `landGate`, `delivery`, `repoLock` and `conflictedPaths`.

`git.ts`'s are what every git call this app makes carries: a missing `-c` is a repository-controlled hook run by this server's own git child, with no permission mode and no line in `run_events`, and a variable that survives the scrub is that hook handed `DATA_DIR`.

`landRefusal`'s two are the cheap in-bar extension of an existing fixture rather than a new file, and they exist because that behaviour looks like an omission and is not — a run that asked for review is landable exactly like a `failed` one, and it owns its chain's branch once it has committed.

The fifth of the twenty that open the database, `mergeQueueOrder.test.ts`, is in the SQL as well, `chatOrder.test.ts`'s grounds one table over: `nextQueuedIn`'s ORDER BY is the whole of what decides which branch is merged next, and reading the per-batch `position` first sorted a batch queued while the worker was still draining an earlier one into the middle of it.

It also pins the repository term beside it — that a branch in one repository stays eligible while another repository's is in flight, and that within one repository nothing does — because those are one question and the way to get the first is to drop the second.

Nothing crashes — every item is still re-previewed against git at its own turn — so all that is lost is the operator's sequence, in merge commits in a directory they own, with nothing afterwards to say that was not the order they chose.

It drives the selector the way the worker does, settling each row and asking again, because a comparator beside the query would be a second copy of the rule and the copy is the one that would stay right.

The sixth, `mergeQueueView.test.ts`, is that same table once more, and its decision is in the SQL too: `selectQueueBatches` is the rule and is tested pure, but the query that fed it never consulted a rule at all — it took the newest `batch_id` — so what `mergeQueueView.test.ts` pins is that the answer the page is handed covers every batch the worker can still act on, and that Cancel reaches one that is not the newest.

`mergeQueueDrain.test.ts` is the drain's own three writes, named beside `planItem` / `selectQueueBatches` in the list of what `npm test` covers: it is the only thing in the process that can move a row off `landing` or `resolving`, and no pure function reaches it.

Its fourth case is that drain at a shutdown, last in the file because `shutdownRuns` sets a flag nothing clears. A `GIT_BIN` stub holds two workers part-way through a land until the case writes a release file, one inside its `git merge` and one inside `landState` with its row already `landing`, and a third branch is queued behind the first. The shutdown must not return while either row is unanswered; the first must end `landed`, the second `failed` with `landRun`'s shutdown refusal and its checkout's `HEAD` unmoved, and the third still `queued`. Taking out the wait on `trackLand`'s set, the drain's own registration of the row, `landRun`'s two reads of the flag, or the drain's read before each row each failed it at its own assertion. Release files rather than sleeps, because a case timed with sleeps passes whenever the machine is slow enough for the merge to finish before the shutdown begins.

`resolveCheckout.test.ts` pins *which directory* a conflict resolution is handed, against a real repository inside a real store because a path is only shared once two `git worktree add`s have said so: the aux checkout was one constant `<slug>-resolve` per repository and creating it force-removes whatever stands there, so two resolutions in one repository destroyed each other's working tree with a billed `claude` child editing files in each, and the guards on the way in had nothing to say — `assistRunning` is keyed on one run and `maxConcurrentAssists` is two, so both callers are positively permitted.

Its control is the half that says the deletion happened rather than merely that the names differ: the first checkout must still exist and still be standing on the first run's branch, which is what the second call took from it and what the first run's `after` handler would otherwise have staged and committed as its own.

`resolutionBudget.test.ts` pins *what ceiling* a conflict resolution's child is handed, end to end — a real repository with a real conflict, `resolveConflicts` asked as the Resolve button asks it, and a stub `CLAUDE_BIN` that writes down its argv — because the defect was an argument missing at one call site, which a pure helper beside it would have got right all along. A resolution has no clock on its duration and only an hour of silence stops its child once spawned, so `--max-budget-usd` off `resolutionBudgetUSD` is the only bound on what a working one spends, and the merge queue's auto-resolve spends it with nobody present; without the flag nothing fails and the row looks the same. Its sibling cases are in files already here: `assistBudget.test.ts` pins that `assistRefusal` refuses at the install's daily ceiling, which it counted and never asked, and `mergeQueue.test.ts` pins `refusesEveryLaterResolution` against the sentence `evaluateInstallBudget` actually words, and against `SHUTDOWN_REFUSAL` itself, so a rewording fails there rather than costing every later branch a fresh refusal.

`resolutionSilence.test.ts` pins the one deadline a resolution's child has, end to end on the same fixture as `resolutionBudget.test.ts`: a stand-in `claude` that prints nothing is stopped once an hour of faked time has passed, and its merge is rolled back through the resolution's own `after` with the branch tip, the operator's checkout, its file and the worktree list exactly as they were; one that printed half an hour in is still running at the hour and ends with its own verdict. Both failures are quiet. A deadline that output does not re-arm ends large merges that were working, the defect the landing path's no-clock rule was written against, and it reads as one more failed resolution; a stopped one that never reaches `after` leaves a merge half-done in a checkout nothing cleans up. It is the one file in the suite on `mock.timers`, faking `setTimeout` and `Date` only between the spawn and the tick, because `RESOLVE_SILENCE_MS` is a constant on purpose and a test-only way to shorten it would be a second deadline to keep honest; the child, git and the settle run in real time, and Node's `ExperimentalWarning` for that API is expected in the output. Both cases were checked to fail: with the deadline removed the silent one never settles, and with output no longer re-arming it the printing one is recorded as stuck.

`conflictedPaths.test.ts` is the conflicted-file list read against a real repository, and it earns a git child on `slotProbes.test.ts`' grounds turned around: what was wrong was not what this app computed but what it *asked git for*, so a fixture stating git's output would be stating the very thing in question, and a parser test over a pasted string passes with the `-z` left off the argv. Without it, `git diff --name-only --diff-filter=U` C-quotes any path holding a non-ASCII byte, so `café.txt` reached every consumer as `"caf\303\251.txt"` — a string that names nothing on disk — and every one of them uses what `conflictedFiles` returns as a path: the resolution prompt names it to the agent, `run_reviews.resolved_paths` keeps it for `resolutionChange`'s pathspec, the `after` handler joins it onto the checkout and reads it, and `git add` stages it. Nothing throws and nothing looks wrong. The read comes back null, an unreadable file counts as unresolved for the reason `unresolvedFiles` states, and a resolution the operator has already paid for is rolled back whole — including the files the agent got right — with "conflict markers are still in" naming a file that was never there, which is a branch that can never be auto-resolved. So the second case resolves the files that exist in the checkout rather than the ones this app named, which is what an agent working from the tree it can see would do, and then walks the `after` handler's own two steps: the read that decides whether markers are left, and the `:(top,literal)` add checked against `ls-files -u`. Dropping the empty record after the final NUL is asserted in the same breath and is not tidiness — `:(top,literal)` with an empty path matches the entire tree, so a split that kept it would stage every unrelated change in the checkout into the merge commit.

`landGate.test.ts` is the gate in front of Land, and its two halves fail quietly in the same way: a parser that dropped a metacharacter runs a different command from the one the operator read back in Settings, and a verdict that treats "could not run" as "passed" hands back an open door to an operator who asked for a gate — neither throws, neither fails to typecheck, and the button looks the same either way. So both halves are asserted in both directions, the shapes that must be refused and the shapes that must be allowed, because a refusal that admits everything measures nothing and one that refuses everything is not a feature. A third half was added later and is the one with a security consequence: the spawn passed **no `env` at all**, so a command whose script body lives in the tree an agent just wrote inherited `UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY` and `DATA_DIR` — pinned on `childEnv`'s grounds, that no page, no log and nothing else in the app would report it if one came back. It is asserted twice on purpose. `verifyEnv` is a pure function, so a builder-only test still passes with the `env:` option deleted from the spawn, which is exactly the defect that was there; so the second describe runs the gate for real against a `node` probe that exits non-zero naming whichever variable it can see, and checks `PATH` in the same breath, because a strip that took `PATH` would refuse every land with "could not start" and read as the operator's command being wrong.

The `PATH` assertion in that file is one of four, and the other three are in `orchestrator.test.ts`, `chat.test.ts` and `review.test.ts` — one per environment builder that feeds an agent child. They exist because `PATH` is deliberately **absent** from a strip list held as six hand-copies (`docs/agent/security.md`), and `proposals/CustomStacks/01c-reach-and-permission.md` §2 rests its whole argument on that absence: a toolbox the `Dockerfile` puts on this server's `PATH` reaches every agent child for free. An edit that added `PATH` to one copy has to be made in six places and nothing fails if it is made in five — the child simply stops finding a tool, inside a tool call nobody reads, with no page and no log in this app mentioning it. Each assertion is over a *planted* directory rather than over equality alone, because what §2 claims is that a directory **added** to this server's `PATH` arrives in the position it was added at, and each is over the composition the spawn site actually builds rather than over the bare strip: extras land after it and win every key they name. `chatEnv` is the one where that needed arranging — its extras are `githubEnv()`, whose token is a module constant fixed at load — so `chat.test.ts` sets `UF_GITHUB_TOKEN` at the top of the file and asserts the block is non-empty, since with it blank the composition is `{}` and the `PATH` line would pass having measured nothing. `chatEnv` and `reviewEnv` are exported for these tests and for nothing else, on `childEnv`'s footing rather than as an exception to the rule against it. `authEnv` and `gitEnv` are the two copies still unpinned; `gitEnv` has a `PATH`-adjacent assertion of its own at `git.test.ts:97`.

`delivery.test.ts` is the exit, and the three ways it could be wrong quietly. `parseRemote` decides *where* something is published, and getting it wrong does not throw — it opens a pull request on somebody else's repository, or refuses a perfectly good remote for having been cloned over SSH rather than HTTPS. `planDelivery` decides *whether*, and its dangerous failure is the permissive one: a plan that said yes with no token produces a push that fails half-way, and a plan that did not notice `head === base` opens a pull request with no commits in it.

`repoLock.test.ts` is a mutual exclusion tested for the failure that it excludes nothing, which is what every wrong promise-chained lock does: chain onto the wrong promise and two bodies run side by side, and the only symptom is two callers overlapping on a live install months later. The case that carries the file asserts an *ordering* — the second body has not started while the first is still open — driven with explicit deferreds rather than timers, because a test that establishes an ordering by sleeping asserts the sleep. Two of the others are the opposite direction and matter as much: two repositories must still work at once, or a lock keyed on the process would serialise every install-wide run start behind one repository's registry work; and a body that threw must not wedge its key, because one of the four callers is the run loop and a wedged key is every isolated run in that repository never starting again — which is worse than not having the lock at all. The last two are about the map: it must forget a repository once the queue drains, and must **not** forget one while somebody is still queued behind the holder, since a third caller then chains onto nothing and runs beside the second. The second of those needed both bodies held open to be observable at all; the first version of it passed for the wrong reason, because the queued body returned inside the same tick.
