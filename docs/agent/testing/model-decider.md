# The model decider

[← testing index](../testing.md)

Read before adding or editing tests of `modelDecider.ts`, or of `planEmittedRun`'s reading of `RunSpec.decidedModel`.

`modelDecider.test.ts` pins the two decisions between the decider's answer and `--model`, and both fail silently and in money. `deciderApplies` answering yes for a Codex or local run hands a Claude id to a CLI that does not serve it, which fails at the provider rather than at this app's door; answering yes over a template's or an agent's model replaces a price the operator chose with one a 4B classifier chose, and the run page shows it as chosen either way. Its cases are the provider split, each of the three rungs that stand it aside, and a blank model read as none named — the rule every door keeps. `readDeciderReply` is the one place an answer meets the operator's list before it can become a run's model: an id switched off, or one the list never had, starts a run on it if let through, priced at `UNKNOWN_MODEL_PRICE` when the table has never heard of it, and an abstention, an error status or a body it cannot parse read as a pick does the same with no id at all. The last case bounds and flattens the decider's own text, because it is another process's output and lands on a card and in a block's notes. `decideRunModel` itself is not tested: it is the fetch and the settings read around that pure function, and was measured against the live service instead — see `docs/verification/agents-templates-and-models.md`.

`workflows.test.ts` asserts `planEmittedRun`'s precedence on the same ground: a decider pick that outranked the block's template would replace the price the operator saved with one nobody chose, and a pick that reached a Codex or local block would hand a Claude id to a CLI that does not serve it. The template is read when the run is created, so the case that matters most is the template's model winning over a pick already stored on the spec.
