# The model decider

[← testing index](../testing.md)

Read before adding or editing tests of `modelDecider.ts`, or of `planEmittedRun`'s reading of `RunSpec.decidedModel`.

`modelDecider.test.ts` pins the two decisions between the decider's answer and `--model`, and both fail silently and in money. `deciderApplies` answering yes for a local run hands an id to a server that serves none of them, which fails at the provider rather than at this app's door; answering yes over a template's or an agent's model on a Claude run replaces a price the operator chose with one a 4B classifier chose, and the run page shows it as chosen either way — while on a Codex run those two are Claude ids that never reach `codex exec`, and reading them as answers would leave every Codex run from a modelled template off the decider for good. Its cases are the provider split, each of the three rungs that stand a Claude run aside and the one that stands a Codex run aside, and a blank model read as none named — the rule every door keeps. `readDeciderReply` is the one place an answer meets the operator's list before it can become a run's model: an id switched off, or one the list never had, starts a run on it if let through, priced at `UNKNOWN_MODEL_PRICE` when the table has never heard of it, and an abstention, an error status or a body it cannot parse read as a pick does the same with no id at all. A Codex run's pick is held to the Codex list, and a Claude id the decider answered with is refused there with the Codex list's sentence. `planEmittedRun`'s cases in `workflows.test.ts` pin the other half: a Codex block's run takes the pick and never its template's model, which is a Claude id, and a local block's takes neither. The last case bounds and flattens the decider's own text, because it is another process's output and lands on a card and in a block's notes. `decideRunModel` has one pair of cases, against a loopback server standing in for the decider because the thing they pin only exists across the fetch: the request takes up to 30 s, and the answer is held to the list as it is when it arrives, not the one the question was built from. The first case has the server switch the model off in Settings and then answer with it, and expects `model: null` with a note naming it; without it a run starts on a model the operator had just refused to pay for, under a note saying the decider picked it, and nothing downstream re-checks (a chat approval goes straight to `createRun`, and `modelOnList` holds only the Claude list, so an emitted Codex run has no later door). The second answers with a model that stays enabled, so the first cannot pass by refusing everything. The file therefore loads the module in `before`, after a throwaway `DATA_DIR` and the loopback address are in the environment, because `config.ts` reads both once at import. The service itself was measured live instead — see `docs/verification/agents-templates-and-models.md`.

`workflows.test.ts` asserts `planEmittedRun`'s precedence on the same ground: a decider pick that outranked the block's template would replace the price the operator saved with one nobody chose, and a pick that reached a Codex or local block would hand a Claude id to a CLI that does not serve it. The template is read when the run is created, so the case that matters most is the template's model winning over a pick already stored on the spec.
