# Taskboard authority, moves and a run's board

[← testing index](../testing.md)

Read before adding or editing tests of `tasks.ts`' transition, operator-only and release rules, its move effects, `tasksForRun`, `readTaskLinks`/`tasksMentionedIn`, and `format.ts`' `runPageNotes` and `storedFolderState`.

`taskTransitionRefusal` is the taskboard's whole authority model, and it is asserted as a **matrix** rather than as a sample: four statuses against four statuses against four actor kinds is 64 cases, which is the entire behaviour of the function, so an edit that quietly *adds* an edge fails here rather than shipping. Sampling would have been the wrong shape for the same reason a spot-check of a permission table is — the case nobody wrote down is exactly the one that gets admitted. The two directions are not symmetrical and both are covered: an edge admitted that should not be is a task marked done by something that did not do it, and an edge refused that should not be is a backlog nobody can clear. Four cases beyond the matrix are the ones a matrix cannot state, because they are about identity rather than about the pair: a run completing a task **another** run holds, which is the failure the whole rule exists for — a work cycle that read the board, picked the wrong id out of a list and closed work nobody did, silently and with the board agreeing; a `claimed` row whose `claimed_by_run_id` is null completing for *nobody*, since two nulls comparing equal would let any run close any orphaned claim; a run that must claim before it may complete; and a claim that names no run at all, which is refused because nothing on this path expires a claim and one naming nobody could never be released. Each refusal is additionally asserted to be a *sentence* rather than a code, on `runFormProblems`' grounds — three doors will eventually show it, and a refusal nobody can act on is the same as no refusal.

`operatorOnlyRefusal` in `tasks.test.ts` is the operator-only flag's authority, and it is a matrix for the transition rule's reason: five actors — the operator, a run holding the task, a run that does not, a chat, a block — against filing marked, filing unmarked, marking in the write that releases the claim, marking outside one, clearing in and outside a release, and restating the flag, which is every case the function has. Both directions are silent. A model allowed to clear the flag starts a run on work the operator was told needs a Mac, and the run spends its budget finding that out again; a run refused the mark while releasing cannot say the blocker is the environment, so the next run is started on the same wall. The non-holder's refusal is asserted **equal** to `taskTransitionRefusal`'s own sentence, because a second copy of the holder check is the thing that drifts. Beside it: `open → claimed` refused for every actor while the flag is set, with every other edge untouched; the flag refused at both doors when it is not a boolean, because `"false"` coerced is truthy and would mark a task the caller said not to; `createTask` and `updateTask` asking the rule, including the one ordering that matters — the claim reads the flag as the same write leaves it; `listTasks` narrowing on it and saying nothing when it is not asked; and `readTaskLinks` refusing an operator-only id in `taskIds` while taking it in `relatedTaskIds` and still refusing a brief that names it in neither.

`releaseTask` earns four more in `tasks.test.ts`, and the one worth knowing is the transaction: a release whose note cannot be written must not open the task, because a release that loses its reason sends the next run to try the same thing again with nothing saying it was tried. The failure is forced at the store with a `BEFORE INSERT` trigger that raises, rather than through a seam made for the test, so what is pinned is the real function's `db.transaction`. The others are the holder's release (open, unclaimed, one note signed by the run, and the run can no longer complete it), the release that marks the task and the claim then refused, and the refusals that must write nothing — a stranger, an empty or over-long reason, and a task that is already `open`, the last because `open → open` is not a move and the transition rule allows it for anybody. `claimTasksForRun` is exported for one case beside them: a run started for an operator-only task logs the refused claim, claims the rest and is still `queued` afterwards, asserted against a seeded run row and its `run_events` rather than by driving a run. The migration case is last in the file because it reopens the database: `operator_only` dropped, a row written the old way, the connection reopened, and every old row reads as agent work.

The taskboard's **move effects** are the writes no pure function reaches, and they earn their database fixture where the parked sweeper's three writes earned theirs: each is silent in exactly the same way. The operator's own completion must record **no** run id, because a person is not a run and inventing one puts a run id on work no run did; a re-open must clear both run columns and `closed_at`, because a task that is open while naming the run that completed it is a row contradicting its own status on every surface that draws the board; a refused move must write **nothing**, including the title the same patch carried, since a partial write is the one outcome nothing anywhere would report; and deleting a parent must keep its children and clear only the link, which is `ON DELETE SET NULL` doing what the schema says — a test that would fail loudly if the `foreign_keys` pragma were ever turned off, which is a global setting no reader of `tasks.ts` would think to check. The folder validation is asserted through the **real** resolver against a real mount, and both of `security.md`'s containment checks are exercised by name: a lexical escape (`../outside`, and an absolute path outside the root) and a **symlink inside the mount pointing out of it**, which is the case the second check exists for and the one a lexical check alone admits.

`tasksForRun` in `tasks.test.ts` is the board narrowed to one run, and each of the three ways it goes wrong is silent and different. Widening `held` past `claimed_by_run_id` hands a run ids it cannot complete but will try to; widening `openInFolder` past the folder turns a tool scoped to one project into a read of the operator's whole backlog — one `WHERE` clause away, which is why the null-folder case is its own test rather than a branch of the first; and losing the count turns a clipped list into a silent one, which is how a run files the duplicate it read the list to avoid. A fourth assertion rides the first: `held` carries **every** status, because a run that has completed its task must still see it or a second `complete_task` reads as a board that lost the write.

`readTaskLinks` and `tasksMentionedIn` in `tasks.test.ts` are the check that a run's brief names no board task its run is not linked to, and they earn it on the most expensive silence this board has produced: a chat batched three tasks into one run, linked one, and the run did all three and could close one — ten tasks stayed open in one batch with nothing saying why. Both directions are pinned because both are silent. Missing a mention is that failure again, so the id, its eight-character prefix and a title quoted in curly quotes, another case and a stray backtick must all be found. Over-matching teaches a model to reword briefs instead of linking work, so a prefix inside a longer hex run (a commit sha), a closed task and a title under `MIN_MENTIONED_TITLE` must not be. The field rules ride beside them — `taskId` refused by name, a task in both lists, the cap at `MAX_RUN_TASKS` — and `planEmission` carries one case of its own asserting the refusal names *which* spec, since a whole-emission refusal that does not is one a model fixes on the wrong run.

`format.test.ts`'s `runPageNotes` cases guard the one line the run page's *On the board* block draws in place of the notes its own run wrote, and every way that line can be wrong is a confident, well-formed sentence over a page that otherwise looks right. A thread holding only this run's note must yield a line rather than nothing, since the component's fallback for no rows is "Nothing said yet" over a task the run has just reported on. Past `MAX_RUN_TASK_NOTES` the reply no longer says who wrote the older notes, so the line must count this run's notes *of the newest* rather than claim a total the route never sent, and "Newest 3 of 7" must not stand above one row without saying where the other two went. A note by **another** run is the control in every fixture: `authorRunId` is the whole test for "this run's", and a filter reaching for `author === "run"` instead would hide the one run id on the block that is information.

`format.test.ts`'s `storedFolderState` cases guard the task editor's warning that a task's folder has left the workspace scan, on `guardBadge`'s grounds one page over: an unread scan and a scan without the folder are different facts, and collapsed into one every task with a project opened under that warning until `/api/folders` answered, and kept it for good when the read failed — a confident sentence that the project had gone, with nothing saying the list was never read. `null` is asserted as `unread` against `[]` as `absent`, the mount is asserted to be part of the match (the same relative path under another mount is another directory), and a draft with no folder is asserted to have nothing to warn of however the scan stands. `absent` has to stay reachable, because a folder deleted under a task is refused at the next save and the warning is where the operator sees that first.
