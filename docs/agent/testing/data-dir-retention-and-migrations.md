# Data directory ownership, retention and migrations

[← testing index](../testing.md)

Read before adding or editing tests of `serverLock.ts`'s data-directory claim, `retention.ts` and its sweep, and `migrate()` in `db.ts`.

`dataDirClaim.test.ts` opens the database in order to be *refused* by it twice, in the two ways ownership ends: with the lock held by a live pid that is not ours, `createRun` has to throw, leave no row and spawn no child.

What it pins is the wiring rather than a value — `lockVerdict` was always right and nothing asked it, so a second replica served traffic, admitted runs and spawned billed agents having correctly reported that it owned nothing, and the collision that follows is silent in every table.

Its control is half of it, for `haltedMembers.test.ts`'s reason: the same call, with the lock removed and the directory claimed, must still come back with a run, or a refusal that fired for every caller would pass this test and break the app.

Its second case is the other ending — the directory taken while this server is up — and it drives the real `heartbeat`, because the fault is that the beat *wrote* rather than that it decided wrongly: the assertions are that the stranger's `ownerId` is still in the file afterwards and that the writer gates have flipped, neither of which any pure function can be asked about.

Its third case is what that ending then means for the loops rather than for one call, and it is deliberately not a test of the six boot reconcilers: they run once, at boot, behind `ownsDataDir()` in `src/instrumentation.ts` and carry no check of their own, so a test that rebuilt that `if` would pin its own copy of the gate, and the flipped `ownsDataDir()` in the case above is already the whole of the expression they sit behind.

What outlives a boot is the promoter and the parked sweeper, which go on deciding about rows that now belong to somebody else and carry exactly the exposure the reconcilers did: one is the only route to `startRun` and so to a billed child in a checkout this server no longer owns, the other the only door that may un-park a run.

So a `queued` row and a parked one are seeded and both loops are driven: nothing is promoted, nothing is un-parked and nothing is spawned, where the same two calls with the directory claimed again do all three.

Its control carries the same weight for the same reason, and the failure without it is silent in the way this whole file is about: a loop that quietly decides nothing reads exactly like a quiet minute.

`retention.ts`'s pure half decides what lands on disk and what is discarded from it, `releasableRuns`' grounds exactly.

`retentionSweep.test.ts` drives the sweep's SQL on `mergeQueueOrder.test.ts`'s grounds — the decision *is* the query — and both ways of getting it wrong are silent in opposite directions: delete too little and the store is still unbounded, delete too much and a run's own spend record goes with it.

`retentionSweep.test.ts` gained two groups. The first is that `prune_decisions` is **not** on the run-log horizon — a week of boundaries seeded under `eventRetentionDays: 1`, which the settings route accepts, asserting the weekly count `/api/usage` slices still covers seven days; the failure is a *smaller number* beside a savings figure over the full week, which reads as pruning having stopped happening, and its second case is a deep-equal over the sweep's own keys on the blank-horizon case's reasoning, so putting the table back on this sweep is a failure rather than a silent regression. The second group is the sweeper's ownership, and it is the only sweep in this app that deletes: a process stood down after boot kept its interval and six hours later ran the whole sweep — the `DELETE`s, `git worktree remove`, `unlink` on transcripts, `LAST_SWEEP_KEY` — against a database and mounts another process owned. It is refused for real rather than through a stubbed `mayWriteDataDir`, on `shutdown.test.ts`'s grounds, and its third case is the control that an owner's sweep is unchanged.

`schemaMigration.test.ts` pins what an *interrupted* migration leaves behind, with the throw injected inside `db.transaction` rather than a real kill: both end at a ROLLBACK, which is what makes "interrupted after statement k" a case rather than a race. It also pins that the completed rebuild ends with the columns added *after* it, because that path recreates `chat_proposals` from a frozen base list and everything since arrives from the `addColumn` calls below it — an install that rebuilt and lost `guards_json` is one where the chat cannot record a proposal at all, and only a boot that had a rebuild to make would ever find out. Its third block pins that each of those findings reaches `ops_events` rather than only `console.error`, and it is on the file for the ordering rather than for the INSERT: the reporting call sits inside the `open()` that has not returned, where `db()` would recurse without end and where a `CREATE TABLE` one line lower than it is now means the downgrade — the first finding, and the only one that cannot be produced by running this build forwards — is written to a table that does not exist yet. Both mistakes are silent in the same way the gap was, a boot that reports nothing looking exactly like a boot that found nothing. The de-latching case is here for `restartClosedOutstanding`'s reason and asserts the pair: the row survives a restart that clears the fault, and `schemaFaultsThisBoot()` does not. And it pins the one *destructive* statement in `migrate`: an install that predates the drop loses `plan_observations` on its next boot, `resume_probes` beside it does not, and a second boot with nothing to drop still starts — the failure it guards is the quiet one, since a build where only the `CREATE TABLE` was deleted keeps growing a store no page renders, no query reads and no sweep bounds, and looks in every respect like a healthy install.
