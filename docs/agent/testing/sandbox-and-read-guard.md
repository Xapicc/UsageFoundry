# The sandbox, Codex's rules file and the read guard

[← testing index](../testing.md)

Read before adding or editing tests of `sandbox.ts`' mount points, `codexRules`, and the generated read-guard plugin.

`sandboxMountPoints.test.ts` is the one test here that reads something outside the repository, and the transcription it covers is why. Three exported lists are a copy of another program's private decision — the paths Claude Code's sandbox binds `/dev/null` over at a checkout's root, inside its `.claude`, and in `$CLAUDE_CONFIG_DIR` — and both ways of holding a stale copy are silent in the way that costs most. A name the CLI **adds** is a mount point nobody creates, which reaches an operator as a `Bash` call that died naming a settings file the command never touched, attributed to anything but a CLI upgrade: 423 of those between 2026-09-04 and 2026-09-13 on this install alone. A name the CLI **drops** is this app writing an empty file into somebody's repository or config directory for ever, for nothing. Neither is a failure any other test in this file could see, because every other one asks whether the module does what it says and this one asks whether what it says is still true. So it extracts the sandbox construction out of the shipped single-file binary and asserts that the tree-root list is exactly what it binds at a cwd, and that `SANDBOX_CONFIG_DIR_NAMES` and `SANDBOX_CONFIG_DIR_REFUSED` together are exactly what it binds in the config directory — the second being an accounting assertion rather than a behavioural one, since a name in neither list is a mount point nobody has decided about. The file/directory split is taken from the CLI's own flag rather than guessed from the name, which is what keeps this app from creating an empty file where `projects` or `plugins` belongs. It anchors on string literals and not on minified identifiers wherever a literal will do, and every identifier it cannot avoid is discovered from the statement that binds the config directory's main list rather than written down. Two used to be written down, which is why 2.1.280, renaming all of them, first failed it at the extraction rather than at the one name that version added. When the shape changes past recognising it throws and says so, which is the right answer, because somebody has to go and read it again. It is skipped, with a reason, where no CLI is installed — a checkout outside the image rather than a defect. One real defect it caught while being written: anchoring the tree-root list on `.ripgreprc` alone matches a second, 38-name array of project configuration files the sandbox never binds, and every name in it would have become a placeholder in the operator's checkouts.

`sandboxMountPoints.test.ts` covers which trees get placeholders and nothing else in that module, and it earns its place because both ways of being wrong are silent and point in opposite directions. Too few directories and the `bwrap` failures this exists to remove carry on with the fix reporting success — the case that matters is the *ancestor*, since the single most frequent failing path on this install was `/workspace/.claude/settings.local.json` for a run whose working directory sat two levels below it. Too many and this app writes empty files into trees nobody pointed it at, which is why the ancestor half is guarded on `.claude` already being there while the working directory is the only one allowed to have one made.

`codexRules.test.ts` is the same `pkill`/`killall` denial as the flag on every Claude argv, written as an execpolicy file because Codex has no flag that can express it, and it is on this page for the shape of its failure rather than for its complexity. A rules file written in a dialect the installed Codex does not know **loads as zero rules**: nothing throws, nothing warns, `prepareCodexRules` answers `ready`, the cycle spawns, and the only difference from a working install is that an agent can now kill the server supervising it. So the text is pinned whole against the one dialect measured to work — `prefix_rule` with a one-word pattern, where `rule` and `define_program` read like plausible spellings and do not exist in this version at all — and a test asserting only that the word `pkill` appears somewhere would pass against every one of those. Its delivery half earns the exception on `settleOnExit`'s terms: it is the only thing in the process that decides whether a Codex cycle may start at all, so `unavailable` must name its path rather than answering `ready` for a file that is not there, and the directory it writes into is one Codex globs, which is why a temp file left behind is a case. Its uid-split cases (board task `57d1c7d6`) pass the owner explicitly, since the suite is not root and the fixture's own uid stands in for the server's, and refuse `ready` for a `CODEX_HOME` the agents can write that is not sticky or is not the server's, and for a `rules/` that is a link, a dangling link, a file or writable by others — each with a reason that names the directory, which is what an operator has to fix. They earn it on the same terms: the old delivery followed a link at `rules` and answered `ready` with the denial written where the agent could edit it, and its refusals named an errno. The control beside them is the shape the entrypoint makes, 1770 around 0755, because a check that refused that would refuse every Codex cycle on every install. The name `CODEX_HOME` is reached by (board task `7662bc8a`) is decided by `codexHomeNameUnsafeBecause`, pure over two `lstat` results because the suite can neither mount a volume nor chown to root: a mount point under the agents' directory and a plain directory under a parent only the server can write answer null, while a plain directory under the agents' and a server-owned parent with any group or other write bit, sticky included, refuse with both fixes named. The mount-point case is the control there, being the stock install. One case drives the check through `prepareCodexRules` by opening the fixture's parent to 0777, and it answered `ready` before the check existed; every other uid-split case runs under the 0700 parent `mkdtemp` makes, which is why they still answer as they did. The one exception is the case passing `self + 1` as owner, whose parent fails the name check too; it now asserts `CODEX_HOME`'s own owner in the reason, and `CODEX_HOME` is checked before its name, because otherwise a deleted owner check went unnoticed behind the name's refusal (measured by mutation). The parity that makes both halves mean something is asserted one file over, in `orchestrator.test.ts`, where the Claude argv's `--disallowedTools` values and the rules file's patterns are compared directly: a third process-killer added to one list and not the other is otherwise invisible, because both providers keep working and only one of them is still refusing the command.

`readGuard.test.ts` is the one with no precedent here: it writes the generated plugin to disk exactly as a spawn would and **runs the hook as a child process** with real stdin, `spawnSync` for `mergeQueueDrain.test.ts`'s reason, because the thing under test is a program and the assertion is about what it prints. A paraphrase of the logic would pin the paraphrase, and every failure mode this guard has is silent twice over: a `hooks.json` in the wrong shape registers no hook at all — no error, no warning, a run that behaves exactly like one with the guard switched off, which is also what a *working* guard looks like from every page in this app — and a deny missing `hookSpecificOutput.hookEventName` fails the CLI's own discriminated union and is discarded the same way. The third failure is the expensive one and is asserted directly: a refusal must leave `offset`/`limit` open, because a guard that strands the agent burns work cycles arguing with it, which costs more than the reads it prevented. What is deliberately not asserted is the prose of a refusal — that it names the file and leaves a route open is checked, the sentences are copy.

`codexWritableRoots` and `agentCanCreateIn`, in `orchestrator.test.ts`, are the Codex half of the write set and earn their place on `sandboxSettings`' grounds with a measured failure behind them: Codex's bwrap makes `.git`, `.agents` and `.codex` mount points in every root it is handed, so one root the agent uid cannot create entries in fails *every* command of the cycle — the first real Codex run could not write a file because `STACKS_STATE_DIR` is root-owned by design. The cases pin the three reshaped entries (the stacks' own directories in place of the root-owned one, `CLAUDE_CONFIG_DIR` and the temporary directory dropped) and that everything else — the checkout, the repository's `.git`, the caches — survives in order, since that is the narrow direction and fails inside a tool call. `agentCanCreateIn` exists because the server is root and `fs.access` answers for root; its cases follow the kernel's first-matching-class rule, where an owner without the write bit is refused even if "other" has it. `boundaryPruneApplies` sits beside them for the opposite edge: skipping a Codex run's boundary is the fix, and answering false for a Claude run would stop every run's pruning in silence.
