# How a loop is picked up, fails and ends

[← testing index](../testing.md)

Read before adding or editing tests of how a loop is picked up again, fails or ends: `planInstanceStep`'s and `planLoopPass`'s left-behind cases, `advanceLoop`'s reads of an unsettled pass, `resumeLoop`, `pickUpsOf`, `tailLeftDirt` and the cases for a loop that settles inside its own release, all in `loopSection.test.ts` and `workflows.test.ts`. The rest of a loop's tests are [workflow-loops.md](workflow-loops.md), and a loop's board condition is [workflow-loop-board.md](workflow-loop-board.md).

`planInstanceStep` and `planLoopPass` each earn cases for a run left behind, and `loopSection.test.ts` earns four more against its database and repository. The waiver is silent in both directions: a scheduler that ignores it leaves the pick-up doing nothing, and one that honours it by resolving *through* the run lands the branch the operator chose not to — which is why the database case asserts the merge was handed the other run's branch and not that one. The other three are the ways through a stopped pass that nothing else reaches: a member resumed through `reviveBlockedBlocks`, whose pass id names no node of the graph; a failed merge retried once its branch exists; and the refusals — a completed run, and a loop that ended on its own terms — writing nothing. The left-behind case was checked failing with `passState`'s filter removed.

`loopSection.test.ts` earns two more for a loop that cannot decide while its pass is still working — a board condition whose folder is removed mid-pass, and an instance graph whose loop carries no `maxPasses`. Each asserts that the loop stays `looping`, the pass's merge stays `waiting` and the block behind the loop is not created while the pass works, then that the merge landed before the loop failed. The failure is silent and permanent: a loop failed mid-pass releases an `on-finish` block into folders its pass is still working in, and the pass's unreleased members sit at `waiting` for good, so the instance never finishes and `pickUpsOf` offers nothing. Both were checked failing before `advanceLoop` stepped an unsettled pass ahead of those two reads.

`loopSection.test.ts` earns three more for the other side of the same read: a board removed mid-pass, under a pass that then **ended the loop on its own** — every member reporting DONE, the operator's *Stop after this pass*, and `maxPasses: 1` — with an `on-success` block behind the loop. Each asserts the loop ended `emitted` on its own rung's sentence and the block behind it was created. The failure is silent in the direction that writes work off: the loop read `failed`, the successor `blocked`, and `pickUpsOf` offers nothing for a pass with no blocked member, so the instance stays `blocked` after the folder is back. `on-success` is what makes the case reach it — the mid-pass case's `on-finish` block is released by a failed loop too. All three failed on the untouched code with the loop `failed` on "Its tasks could not be counted", and the mid-pass case passed throughout, which is the half of the rule that still fails a loop nothing else ends.

`loopSection.test.ts` earns three more for the loop that *does* fail on a board it cannot count — pass 1 settled whole, the folder gone, an `on-success` block behind the loop written off and the instance `blocked`. The first asserts `pickUpsOf` offers the loop with the board's sentence as its refusal while the folder is gone, and with none once it is back; the other two press it and assert the board is read again, pass 2 taken while the board is not clear, and the loop ended on its own rung, releasing the block behind it, when it is. The failure is silent: `passWouldProceed` read a pass with no blocked member as not stuck, so the instance sat `blocked` after the folder returned with nothing to press, although `resumeLoop` would have taken the loop. Only the first failed on the untouched code; the other two pass there too, because the route never refused the loop, and they stay for the half of the claim — what the press does — that the offer rests on.

`loopSection.test.ts` earns four more for a landing section whose in-folder tail is an **orchestrator**, over the same real repository: the tail's emitted runs leave an edit in the folder and the loop must fail at the boundary with no pass-2 row; a clean folder must still take pass 2; and, once failed, `pickUpsOf` must make no `spawnSync`/`spawn` call and offer the loop with no refusal, while `resumeLoop` answers 409 with the sentence the loop failed on and carries on once the edit is committed. All silent: an orchestrator member has no run of its own, so `tailLeftDirt` read through `member.run` found no folder and pass 2 was created, billed and refused at the merge; and a `git status` inside `loopPassRefusal` ran on the event loop on every poll of the instance page. Each was checked by mutating the compiled `workflows.js` back — `member.run` alone, the read put back inside `loopPassRefusal`, the status read without its header — and each mutation failed the cases that rest on it. The porcelain sentence's leading space is pinned in the same cases and in `loopMergeOwnership.test.ts`.

`loopSection.test.ts` earns five more for a loop that failed before it had a pass, and for one whose graph has no cap. The first four share one fixture, a block in front of the loop and an `on-success` block behind it, with the board folder removed before anything advances: the loop fails at its release and `pickUpsOf` has no pass to read. The first asserts the loop is offered with the board's sentence while the folder is gone and with none once it is back, and that a refused press writes nothing. The second presses it and asserts pass 1's entry carries a dependency row on the block in front of the loop with `continue_branch` set, the one claim that cannot be read off a status: a loop reopened to `looping` instead of `waiting` starts its entry after nothing, on a fresh branch. The third presses it over a board that is clear by then and asserts, with no further advance, that no pass was billed and the block behind the loop was created, which is `advanceInstance`'s re-plan after a loop settles at its release. The fourth is a loop that repeats no section: it is not offered, because the press would fail the same way again, and it is the one of the five that passes on the untouched code. The fifth is a loop that failed on a graph with no `maxPasses` after its pass settled whole: it is offered with the missing cap as its refusal and the press writes nothing, where before it was offered with none and answered `{ ok: true }`. The other four failed on `26f8124c`, and the carry and the section guard were each also checked failing on their own mutation: `looping` for `waiting`, and the guard answering yes. The second advance that `resumeLoop` made for the third has since been replaced by that re-plan, and the case now passes on one.

`loopSection.test.ts` earns three for a loop that settles inside its own release, each over one `advanceInstances()` and no more, because a second advance is what hid the defect: a loop with nothing in front of it and an `on-success` block behind it, over a board that is already clear and over a board whose folder is gone. The first two assert that one advance creates the block behind the loop, or writes it off `blocked` with the instance `blocked`; the third is the converse, a loop that took a pass and is advanced twice, which leaves the block behind it `waiting` and creates pass 1's entry once, and it passes on the untouched code. The first two failed on `94ec70ff`, and with the re-plan's flag held false they fail again together with the three cases above that no longer advance a second time.
