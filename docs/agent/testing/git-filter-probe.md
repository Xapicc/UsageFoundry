# The filter probe in front of this app's git

[← testing index](../testing.md)

Read before adding or editing tests in `gitFilterProbe.test.ts`. Split out of [The git this app runs](git-children.md) on 2026-11-09, when the grounds for board tasks `cdf5ae4b`, `b934c65b` and `8e9fe2ed` would have taken that file past 20 KB; every paragraph above theirs was moved unchanged, and "those filter cases" in the first are `git.test.ts`'s planted-`.git` cases there.

`gitFilterProbe.test.ts` is the other half of those filter cases: the probe that names the drivers to blank had its status deliberately unread, because `git config --get-regexp` exits 1 when there are none, so a probe killed by its clock, killed by a signal or refused by git read as "no filters" and the real call ran *without* the blanks: the planted `filter.x.clean` ran in this server's git, with nothing thrown and no line in `run_events` (board task `c032f10c`). The probe is made to fail with a `GIT_BIN` stub that recognises it by `--get-regexp` and runs real git for everything else: exit 128 with a stderr, `kill -9` of itself (a null code with a signal, which needs no clock and so serves `gitSync` too, whose 20 s clock is `spawnSync`'s own and cannot be mocked), a real `sleep` killed by a 400 ms caller clock for `git()` only, and exit 1 *with* output. Each asserts first that the marker the planted program writes is absent and then that the call failed with a reason that names the probe and how it ended, and all six failed before the change with the marker present. Two cases passed before and are there to keep it so: a repository with no filters, where real git answers exit 1 with nothing and the call must still run, since a check that failed that too would fail every `add` this app makes; and a `rev-parse` with the probe broken, since the probe is only for the content subcommands. Its `a=b` cases are the neutraliser's own: git splits a `-c` at its first `=`, so a clean filter named `a=b` ran under `git()` and `gitSync()` with its blank in place, and both cases failed with the marker present until the blanks moved to `--config-env` (board task `a9fde194`); a plain-git control keeps a plant that stopped firing from passing them. Its empty-name cases are the same neutraliser's: git reports `[filter ""]` as `filter..clean`, which a name pattern wanting one character never matched, so a `* filter=` or `* merge=` line ran the program on `add`, `merge-tree` and `merge` through `git()` and `gitSync()` (board task `582bceef`). `[hook ""]` has the same key shape, and its case skips on a git that reads no `hook.*` key, as `git.test.ts`'s do; four cases failed with the marker present on 2.39.5 and five on a built 2.56.0. Its merge-driver cases plant `merge.evil.driver` with `* merge=evil` over two branches that change different lines of one file, so the merge is a three-way content merge: `git()`'s `merge-tree --write-tree` and `merge` both ran the driver before the probe listed `merge.*` and `merge-tree` was gated, and must now run nothing and fail rather than report a merge (board task `a38856ec`); an `a=b` driver name and a plain-git control ride along. Its conditional-include cases put filter `evil` in a file reached only through `includeIf "onbranch:uf/**"` or `"gitdir:<repo>/.git/worktrees/"`, which the probe in the operator's checkout cannot see and the child inside a worktree can: `git()`'s `worktree add` ran the smudge and its `worktree remove` of a stat-dirty tree ran the clean filter, in both forms, until a plain add was refused and a remove probed in its tree (board task `d8cae532`). `addWorktree` is asserted to leave a whole, unlocked checkout with nothing run, and, when its checkout fails, no tree and the branch kept, since a half-made tree left behind is refused at the next start as uncommitted work. `git.test.ts`'s smudge case goes through `addWorktree` for the same reason. Its own file because `GIT_BIN` is read when `config.ts` loads.

`gitFilterProbe.test.ts`'s submodule cases plant a filter in a submodule's own git directory, which the probe in the superproject never read, and the child git a content subcommand starts inside the submodule did: `status` of the superproject (from its top, from a subdirectory, and through `gitSync`), `add -A`, which no flag or setting stops recursing, and a submodule inside a submodule each ran it, until every populated gitlink became a probe site (board task `a559b561`). Three more reach a submodule the index before the call does not list, and each ran its plant until it was pinned off: `read-tree -u` onto a commit adding one under the repository's `submodule.recurse` (`submodule.recurse=false`), `checkout` onto a branch whose index alone lists one (`--quiet`), and a patch of a submodule move under `diff.submodule=diff`, which ran the submodule's textconv past `--no-textconv` (`diff.submodule=short`). One plain-git control fires every plant, `add -A` under every ignore setting. Its race cases make the probe-then-call race deterministic with a stub that answers the probe from the configuration as it was and then writes the driver (board task `7d41bb25`): a `.git/config` rewritten that way ran the driver under `git()` and `gitSync()` and must now refuse the call naming the file, and an included file written while the index is listed must refuse it too. The included case passed its marker check before the change only because no listing step existed for the stub to write in; its control writes the include by hand. Two more write the include where the watch did not look (board task `10264b6b`): from a subdirectory, where git names `.git/config` relative to the top and the watch resolved it against the subdirectory, and under `~<user>/`, which git places through the user database and the watch read as a path inside `.git`. Each ran the plant through `git()` and through `gitSync()` before the change. The `~<user>/` case writes below this user's home, skips where it cannot, and has a plain-git control. Five more put a symlink before a `..` in the include (`sub/../evil.inc`, one nested in a file reached that way, and under `~/`, `~<user>/` and `%(prefix)/`), where git reads the file beside the link's target and the watch folded `..` into `.git/evil.inc`: each ran the plant through `git()` and `gitSync()` before targets were joined unfolded (board task `bbbe1aff`), and a plain-git control fires the first. Its subdirectory cases make a tracked subdirectory a git directory while the index is listed, with a `config` naming the repository as its work tree and defining the filter (board task `fbd6d8dd`): the subdirectory given a `HEAD`, an empty `.git` in it given one, `objects/` made beside a `HEAD` already there, and `objects/` made in what a `commondir` already there names. Each ran the plant from the subdirectory through `git()` and `gitSync()` before what makes a directory below the top a git directory was fingerprinted; a call with nothing made must still run, since that is a non-isolated run's diff, and a plain-git control shows each fires only once its last piece is made. Its found-directory cases move away the `objects/` or the `refs/` of a separate repository nested in one whose configuration defines the filter, while the index is listed (board task `9ef321d6`): each ran the enclosing repository's plant through `git()` and `gitSync()` before the common directory's `objects/` and `refs/` were watched, and a ref written straight into `refs/` or a blob that makes a new fan-out directory in `objects/` must still run, since a ctime watch on either refused both. Its include-condition cases flip, while the index is listed, what a condition reads rather than a configuration file (board task `9d44342d`): HEAD moved by `symbolic-ref` onto a branch an `onbranch:` include matches, the branch HEAD names rewritten as a symbolic ref to one, and a linked worktree's `.git` file pointed at a sibling's git directory a `gitdir:` include matches. Each ran the plant through `git()` and `gitSync()` before HEAD, the refs behind it and the `.git` entries were fingerprinted, and a plain-git control fires each flip and shows nothing fires before it. Its two merge-driver wording cases pass `git()`'s failure through `parseMergeTree` and `gitFailureLine`, the two readers that keep one line, and assert the blanked driver is named there (board task `adb9e828`).

`gitFilterProbe.test.ts`'s which-repository cases each make a call read a repository the probe did not, with that repository's driver planted and a plain-git control that it runs: `-C <A>` or a two-word `--git-dir <A>/.git` ahead of `add -A` from `B` must be refused with no git child spawned (stub mode `log-calls`, board task `c011fcd1`), and `objects/` or `refs/` moved away only while the probe reads (stub mode `move-away-while-probing`) must be refused, as must the same move when the enclosing repository includes the probe's marker file itself, the case that keeps the marker's scope test (board task `f3122092`); a marker file that cannot be made must fail the call, not reject `git()`. Each failed with the driver run before its change, through `git()` and `gitSync()` alike.

`gitFilterProbe.test.ts`' reftable describe has six cases and every one skips on a git that cannot `init --ref-format=reftable` (the image's 2.39.5, so CI never runs them; they ran on a built 2.56.0). The control proves the plant before anything is claimed about the fix: under plain git the stub `HEAD` is `ref: refs/heads/.invalid` and a `symbolic-ref` flip runs the driver, which is what makes "the call ran nothing" mean something. Three flips are refused, each with the fingerprint removed failing it: HEAD in the main worktree, HEAD in a linked worktree (a stack of its own, so the common one does not move), and `main` made a symbolic ref to a matching branch, which needs the `run-git` stub mode because it is not a file's write. The commit case pins the cost, not a goal: a ref update refuses the overlapping call and says it was one, so that lifting it is done knowing what must still stop the flips. The last asserts a call that overlaps nothing runs, since a fingerprint that refused every reftable call would pass the other four.
