# The chat page's thread: the cursored poll and what the page reads off it

[← testing index](../testing.md)

Read before adding or editing tests of `chatThread.ts`' `mergeMessages`, `hasLeftThread`, `draftAfterSend` and `failedTurnEnding`, or of the cursored read in `/api/chat/[id]`. Split out of [Chat turns, threads and the request helpers](chat-turns-and-threads.md).

`chatThread.test.ts` gained five over `mergeMessages`, on the grounds the two functions beside it earned: the chat page's poll now asks for the messages past the highest `seq` it holds, so what comes back is a tail and the page has to put the conversation back together — and every way of getting that wrong renders a transcript rather than an error. A dropped tail is a paragraph missing from the middle of a conversation with nothing on the page to say so; a kept duplicate is the model appearing to have answered twice. The cases pin the append, the replace a `messagesFrom` of zero has to mean, the overlap two polls on one cursor produce (the interval fires whether or not the last request has answered), the reference-identical array a poll that added nothing has to hand back, and the row itself: the same single message arriving onto a thread of ten and a thread of a thousand is the same merge.

`hasLeftThread` joined them for its null. `opened` is null until the operator first opens or starts a thread, and read as left it withholds every action's answer on a freshly loaded page, a refusal's sentence among them, which reads as a press nothing answered. The four call sites are wiring rather than a function and were driven in Chromium instead (`docs/verification/orchestrator-chat.md`).

`draftAfterSend` joined them on the same ground, losing the operator's words with nothing on the page to say any were there. The composer is never disabled while a send is out, and that POST can take seconds behind `assistRefusal`, so `send` clearing the draft outright on success deleted a follow-up typed in the wait that had never been sent. Two cases: the draft that still holds the sent text, trimmed as the send read it, is cleared, because the composer is not per thread and sent text left in it is one press from going again; and a draft written to since survives. With the compiled helper put back to the old unconditional `""`, the second failed and the first passed. The call site is a functional `setDraft`, since `send` closes over the draft from before the wait, and it was not driven in a browser.

`failedTurnEnding` joined them for a page that says a failure twice. The red block at the foot and the red edge on the failure note both compared `chat.error` with the *last* message, so once a note followed the failure while the chat stayed `failed` — `finishTurn`'s refused-tool-calls note, or an approval's or rejection's tally — the note went grey and the red copy was drawn again under the unrelated note, reading as the decision having failed. Three cases: the two notes that follow a failure in practice, each of which must leave the failure note marked and no block drawn, and the belt — a failure only the row carries draws the block, an operator message with the same words is not the note, and a chat that is not `failed` draws neither. With the compiled helper put back to the two old predicates, all three failed: the first two drew both, and the operator-words case drew neither.

`src/app/api/chat/[id]/route.test.ts` gained the server half of that, three tests that fail with the cursor removed and one that pins the boundary. The claim is stated as work rather than as time on purpose — a timing would measure the machine — so the poll after a cursor is asserted to carry exactly the message that arrived, at twenty messages and at two hundred, and the `EXPLAIN QUERY PLAN` for the cursored read is asserted to name `idx_chat_messages_seq` and to build no temp B-tree. That last one is the only test in this suite that reads a query plan, and it is here because the index is what makes the cursor a bound rather than a filter: without it SQLite answers `seq > ?` by visiting every row of the thread, the response is small, the work is not, and every other assertion in the file stays green. The fourth pins that a `?after=` the page could not have sent — empty, negative, fractional, not a number — is read as no cursor and answers with the thread, because the poll is what keeps "Thinking…" from standing for ever and a 400 there would freeze the page rather than report anything.
