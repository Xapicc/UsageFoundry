Thirteen cases, and four of them are the bar the rest were written to: an unreadable `limit` becomes the ordinary page rather than the smallest legal one (a one-row page is a far worse answer to a typo); the `LIKE` needle escapes `%` and `_`, both of which are ordinary characters in a task prompt and in a folder name, so an unescaped search for `50%` would match every row there is; a `settledBefore` at or before the epoch — what `Number(null)`, `Number("")` and a blank parameter all come to — is no boundary rather than a real instant that hides every settled run; and an offset past the end lands on the last rows rather than on nothing, because that is what pressing Next on a list which shrank under you produces. `isRunStatus` is asserted against what a prototype would answer for as well, since `includes` rather than `in` is the whole of why `?status=constructor` is a 400. And `listRunsPage` itself earns seven against the database, for the runs page's bands: seeded with one old `running` run, one old run that failed an hour ago, one that settled exactly on the boundary and a hundred newer `queued` runs, the unfiltered newest page holds neither old run, `running,paused` finds the running one, all four active statuses at the default page lose it again and say so in `total` — which is why the page asks for the queue apart — `settledAfter` finds the failed one and none of the queued, and the boundary run is in `settledAfter` and not in `settledBefore`. Two more seed past the 200 rows a band asks for, in a folder of their own, with milliseconds shared on purpose: over 250 queued runs, one of them raised, the newest-first page leaves out the oldest while `order=queue` holds the raised run and then the oldest 199 in id order — inserted last to first, so a missing `priority`, a missing `id` tiebreak and a newest-first order each fail it — and over 210 runs settled since the boundary, two pages of `settledAfter` reach all 210 with none repeated. Every one of those misses is a band that looks complete.

`queueOrder.test.ts` is the order the queue is considered in, and its failure mode is the quiet one: a comparator that ignores `priority` behaves identically to a working one on every install where nobody has set one, which is every install today. The first case is the one that would catch that; the last is the opposite mistake, a priority sort that quietly stopped being stable and started reordering runs an operator never touched.

The tenth of the twenty that open the database is a count as well, and of a third thing again — not rows in tables and not children, but *subprocesses*: `slotProbes.test.ts` wraps `spawnSync` module-wide and asks what one `createRun` spends on choosing a checkout slot, against two real repositories that differ only in how many of their slots were left dirty.

`createRun` runs from entry to INSERT with no `await`, which is what makes its folder claim atomic and also what makes every subprocess it spawns a hold on the one event loop that drains every agent's stdout, feeds every SSE stream and beats the server lock's heartbeat — and nothing bounded that walk: dirty slots are left behind deliberately, they are never `taken`, so every admission re-ran `git status --porcelain` over every one of them, for ever.

Nothing about that is visible from a value, a status or a page; the app stays correct and stops answering, for longer the older the repository is, so the only assertion that says so is the number of subprocesses.

Its own file for three reasons at once — it needs a real git repository inside the mount, where `orchestrator.test.ts`'s mounts are fixed at a layout that file's collision cases depend on; a wrapped `spawnSync`, which would otherwise count every other case beside it; and a cold slot memo, since the whole question is what a *first* admission on a repository costs.

Its two controls are half of it: the run must still come back isolated, because a walk that bounded itself by giving up would pass the count and quietly serialise every run on the repository, and a store whose settled slots have all been seen once must cost no git at all.

`runOrigin.test.ts` is the sixteenth of the twenty that open the database and drives all five creation paths *through the gates* rather than asserting about them — a `createRun({origin: "chat"})` written in a test would pin the test's own argument and nothing about `approveProposal` — plus the pick-up that must not rewrite what it finds. Its second describe drives the two creations that happen *after* `startWorkflow` has returned in a scheduled instance — a node behind an orchestrator block and a loop pass's member — because both read the origin back off the stored instance rather than being handed it, so a read path that drops the column is invisible to every creating-pass case and stamps those runs as a press of Run; the loop case is why the file keeps a one-commit repository beside its plain folder. Its last describe is the orchestrator door failing rather than succeeding: an emitted spec whose folder is removed before the settle, driven through `emitBlockRuns` and `settleBlock` because both halves are what those write — the failure in the block's `notes` with `error` left null, and the block behind it told that none of the decided runs could be started rather than that the model decided on nothing — both of which shipped wrong and looked right on the page. The verdict alone is also a pure case in `workflows.test.ts`.

Every way of being wrong here typechecks, throws nothing and produces a run that works: the only symptom is a row claiming a person filled in a form when a model decided it, read months later by somebody scoping what a stolen token did.

`settleBlock` is exported for `sweepPaused`'s reason and no other, being the only door to `createEmitted` whose other end is a real child exiting.
