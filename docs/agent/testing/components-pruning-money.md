# Components: what pruning saved

[← testing index](../testing.md)

Read before adding or editing tests of `ContextControl`, `RunPruning`, `LiveRunPruning` or `PruneSavingsRows`. Split out of [components: usage, context and run cards](components-usage-and-run-cards.md), whose argument for a rendering these all share.

`ContextControl` and `RunPruning` print the same `PruneSavingsDTO.netUSD` that `PruneSavingsRows` prints in the band lower down, and that DTO carries two fields whose only job is to say what the figure is not: an unsettled prune is already in the saving and not yet in what buying it cost, so the net can only come down, and an unpriced one is in neither half, so the money covers fewer prunes than the count printed beside it. Both rendered neither, which is the one direction this app's own copy says it must not mislead in — an upper bound wearing a net's clothes, on the two surfaces an operator opens first. Each pins a fault *and* its control, because a card that hedges unconditionally says nothing and would satisfy the positive cases alone; and the two are pinned apart rather than together, since marking an unpriced prune "at most" claims a sign the reading does not carry. `RunPruning` keeps both halves. **`ContextControl` keeps only the ceiling half**, because the tile no longer prints a coverage line or a footnote about the overlap: both were removed by the operator, restored by an agent reading the invariant that then licensed them, and removed again along with it. What stands in their place is one test asserting that neither string renders. It pins a rendering rather than a behaviour, which everything else in this file calls a liability, and it is here for the one reason that outranks that: this copy has been re-added once already by a pass that found the page and the docs disagreeing, and a test is the only part of the disagreement a build run cannot read past. A third field pulls the other way: `unmeasuredPrunes` is a fork whose removal waits on the turn that resumes it, so the saving and the token count are floors and the net can only rise. Both components pin it as `at least` — `RunPruning` beside "removal not measured yet" where it printed `0 tokens removed`, `ContextControl` on its span caption — and both take the label from `netBound`, so one run's net is not a ceiling on one screen and a floor on the next.

The tile's own unpriced case is the same fault one card up, and it is a third half beside the ceiling and the floor: `combinedUSD` added `netUSD` whenever a prune existed, so a week of prunes nothing could price led the dashboard with `+$0.00`. Pruning now contributes to a span only where a prune was priced — `filterShareUSD`'s rule for the other half — so that span reads "—", or the filter's share alone beside it, and its caption carries no bound over a figure that is not there. It prints no coverage count, for the operator decision above.

`RunPruning` is the same fault on the run page: its headline printed `netUSD` whenever a savings DTO existed, so a run whose every prune was unpriced led `/runs/[id]` with `+$0.00` beside "money over 0 of N". With `pricedPrunes === 0` the headline is a dash and the bound label is dropped, since there is no figure for it to qualify and the token count already says "at least" for an unmeasured fork; the count and the coverage text stay. `RunPruning.test.tsx` pins the unpriced run, the unpriced run with an unmeasured fork (so the bound is not said twice), and a priced run's headline beside them as the control.

`LiveRunPruning.test.tsx` is what pruning has done for a running run, on the same tile and the same grounds as `RunPruning.test.tsx`, which holds them for the run page: every failure is silent and reads as a measurement. A run that never pruned drawn as `+$0.00` says pruning earned nothing where it never ran; an unsettled prune's cost drawn as `$0.00` says the edits were free; and a net over prunes only some of which were priced, printed bare, is a total omitting part of its own subject. The case with no priced prune at all is pinned here because a tile has no room for a reader to be sent from another surface for it; the run page draws it the same way, as a dash headline beside the same count. The label saying it is not spend is asserted in every state. An unmeasured fork is the fourth case: `0 tokens removed, Saved +$0.00` is what a fork measured to remove nothing looks like, so the tile draws the removal and the saving as not measured yet and the net as `at least`, and beside an unsettled cost as `not final`, because then it is bounded on neither side.

`PruneSavings.test.tsx` is the dashboard's pruning band, `PruneSavingsRows`, one span at a time, and it became renderable under the test build only when its imports went relative — the bug report that found its unpriced case could not render it. The case is the tile's from the band's side: a prune on a model with no price here — every Claude Haiku 5.5 run, since a tiered model is deliberately unpriced, and any model the table does not know yet — is in `prunes` and in neither half of the money, so every dollar field is 0 on the wire and `netBound` says exact, and the band printed "+$0.00 over 36 later turns", "nothing — measured" and "Net +$0.00": pruning measured to have earned nothing, beside a runs list printing `?` for the same run. With no prune priced the money rows are omitted and the span says its money is unknown, keeping the token count, which is a measurement; an unmeasured fork in such a span keeps its count line and loses "so the net above is a floor", because there is no net above. With some priced the money prints and "Money covers k of n prunes" follows it, on `FilterSavingsRows`' wording for the same gap. The control, every prune priced, prints no coverage line, because a band that always hedged would satisfy the positive cases alone.
