# Budgets, spend guards and the run form's limits

[← testing index](../testing.md)

Read before adding or editing tests of `budget.ts`, `installBudget.ts`, `installSpend`, the instance budget, `assistRefusal`'s process count, `costBaseline`, `costSplit`, `cycleCostAfterResult`, `cycleSpendOf`, `liveGuardTick`'s budget half, the cycle a task check grants, the new-run form's `budgetPayload.ts`/`formProblems.ts`/`formSeed.ts` and the calibrate route's `measureCeilings`.

`budgetFromForm` (`budgetPayload.test.ts`) is where every limit's off state is decided: `null` is the wire form of "off", so a number left in a box the operator switched off is a perfectly valid `BudgetPolicy` and starts an unattended agent under a cap nobody set, and the window pair reads 0–100 on the form against 0–1 on the wire, which makes a slip of a hundred a guard that never fires.

`runFormProblems` (`formProblems.test.ts`) is the same page's other half and the same silence: it is every reason the new-run form refuses to start, and a refusal that stops firing does not throw, does not fail a typecheck and leaves a page that looks right — it just starts the unattended agent the refusal held back. Two of them are load-bearing beyond their own sentence. The deleted-agent and the unusable-agent refusals both name the `agent` control and the page shows one problem per control via `.find`, so their push order decides which the operator reads; and `immediate` is what separates a range error, true the moment it is typed, from an emptiness error that has to wait for a blur, which is the difference between a form that argues under the caret and one that never says anything at all. The mount refusal has a sentence per kind of nowhere, and the case pins the third apart: a workspace list that could not be read is neither "No workspace is mounted", which sends the operator to `.env` over a failed request, nor "Choose", which points at a picker with nothing in it — and it refuses a mount a copied run already named, because the form cannot show where that run would go. `limitProblems` is its limit half, split out because the template Save reads it as well, and its case pins that the two give the same sentences: a Save that drifted from Start stores a limit switched on with its box blank as no limit, which the chat and the canvas then inherit. The server half of that refusal is in `templates.test.ts`, and it failed before `normalizeTemplateInput` refused `""`. `guardProblems` is its window-guard half, split out for the same Save reason with the sharper stake: a guard the Save lets through is not a missing cap, it is a wrong one — `normalizePolicy` divides anything over 1 by a hundred again, so the 150 Start refuses is stored as a 1.5% guard and parks every run the chat or the canvas inherits from the template almost at once — and its case pins that Save gives Start's own two sentences for 150 in each box and allows 1 and 100. Unlike the limits, its server half is missing: `normalizeTemplateInput` folds the same double division at the door rather than refusing it. `windowGuardUnreadable` beside them is the form's forecast of the door's `no_ceiling` refusal, and its case asserts agreement with `readWindowGuard` itself rather than a restatement of it, because agreement is what drifted: the form asked whether a ceiling was set, the door asks whether the window has a fraction, and on a stock install the provider's percentage makes those two answers differ.

`formSeed.test.ts` is the same page's third door, *Start another like this*, and it earns its place on one mapping: `seedFromRun` reading a run's null `isolation` as off. `createRun` writes null only for a run that asked for a worktree and was never planned, so the copy landed on "This folder" on a git repository with nothing on the form marking it — an agent in the operator's own checkout, the failure isolation exists to prevent. The case failed on the old `=== "worktree"` reading. `"none"` copied as none and the gone-mount folder are pinned beside it because they are the two neighbours a fix to the first could plausibly break.

`assistBudget.test.ts`, which opens the database, is a *count over three tables*, which is what `assistBudgetRefusal` beside it cannot be tested on: the rule is pure and the defect was never in the rule — it was that the cap read one kind of child and three others consulted nothing, so a `run_reviews` row, a `chat_sessions` row and a `workflow_instance_blocks` row are written and the count asked about each.

Its two negative cases carry the same weight as its positives and one of them is not obvious: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so counting it refuses an operator's chat turn to make room for a process that does not exist.

Both directions were seen to fail before this landed.

`installSpend.test.ts` pins what the install-wide ceiling is *measured from*, which the pure verdict beside it cannot — a SUM across three tables each bounded on a different column, with a fourth contribution through `telemetrySpendSince` — because a window bound on the wrong column is a ceiling quietly larger than the one the operator typed and a plausible dollar amount either way.

`instanceBudget.test.ts` pins *when* the workflow-wide budget is evaluated: every call site was "before something spends", so a graph of single-cycle blocks compared its limit with zero N times and `maxInstanceCostUSD` could not fire at all, which looks exactly like a workflow that came in under its limit.

`validationGrant.test.ts` drives whole run loops, because the defect it pins was a disagreement *between* guard sites that each read correctly alone: the post-cycle cap check honoured a task check's grant, the pre-cycle guard one pass later read the unwidened cap, and on the default `maxIterations: 1` every run the check sent back ended there — verdict paid for, grant spent on the row, task left claimed. The child is `shutdown.test.ts`'s fake `spawn`, for `CLAUDE_BIN` only, and the verdict is `validationAtBoundary` replaced on its module, `contextCeilingRace.test.ts`'s device; `recordValidationCycle` stays real because the row it writes is the guard's input. Its fourth case pins the live guard's copy of the same figure: `iterations` is checked first and is not live-enforceable, so a live closure without the grant would skip the granted cycle on every tick. The arithmetic itself is in `budget.test.ts`, and the sweeper's re-reading of a run parked at that cycle is a case in `orchestrator.test.ts`. All three failed before the change. Its fifth pins the reopen door's copy: a run capped at 1 that was granted 1 and used both is refused a limit of 1 with the sentence naming 1 as the figure to beat, then picked up at 2 and must spawn exactly one cycle and end at the widened cap with its grant still on the row. It drives the loop rather than asserting `reopenRun`'s answer alone because the claim is about what the limit buys, and it failed before the change, at the refusal of 2.

The live tick's budget half earns three cases in `orchestrator.test.ts` on `contextCeilingRace.test.ts`'s grounds, one half of the tick over: what they pin is an interrupt that must *not* be written. A tick that evaluated a guard whose cycle ended during its scan counted that cycle twice and left a stop for whatever the run did next. The scan is held open through the in-flight promise `currentSnapshot` hands every caller, and the helper asserts the tick really joined that promise before the cycle is ended — without that check, a slower `checkContextCeilings` ahead of it would let the first case pass for the wrong reason. The control is a guard still registered, which must still stop the run. The third case is the claim-time discard, and it asserts *which* reason the run ends on, because the stale verdict and the run's own cap both end it `stopped`. Each failed with its own fix removed and the control passed without either.

`costBaseline.test.ts` is the guard that knows what a task normally costs, and each case pins a decision that fails silently if it is wrong. A signature that changed under a reflowed prompt would reset an operator's baseline to nothing at the exact moment they were iterating on wording, and the guard would simply stop firing with nothing to say so; a mean in place of a median would be dragged upward by the very runs the guard exists to catch, so two expensive runs would buy a third; and a verdict fired on one sample would teach an operator to switch the guard off, which costs more than the guard ever saves.

`costSplit.test.ts` is where the bill went, and the one property that keeps it honest. The split exists because a loop can be 92% cache reads by volume and still spend half its money on writes — the multipliers are 0.1× and 2.0×, a twentyfold ratio no token chart shows, and measured on one install across 90 deduplicated frames writes were 48.1% of the bill from 7% of the tokens. What it pins above any single figure is that the split and the total are one arithmetic: a readout that could drift from `costOf` would be two statements of one policy, with the operator reading a number the guard itself does not believe.

`cycleCostAfterResult` in `orchestrator.test.ts` earns its four on a measured 75%, and it is the rare case where the evidence came before the test rather than after. `total_cost_usd` is the session's running total and `usage` on the same event is only that stretch's own, so one `+=` was right for one of them and wrong for the other, and the wrong one is the money: on run `075f7959` two `result` events arrived in the same millisecond — the agent's turn ended while a background `Explore` sub-agent was still running, and the same session was woken again when it answered — and $7.025419 plus $9.330155 was stored as $16.355574 against the $9.330155 telemetry recorded across all 110 of that session's requests. Nothing about that run looked wrong: exit 0, a clean report, a log whose rows each named a plausible figure. The first case is that pair verbatim, because a regression here is not a shape that stopped parsing but an arithmetic one that keeps working. The second is the risk the fix itself introduces and is the reason the fold takes the larger rather than the last: a `result` whose cost field is absent, unparseable or zero says nothing about the session and must leave a figure already reported standing, or a cycle overstated by 75% is traded for one silently reported at $0 — seven readings, since `undefined`, `""` and `NaN` all reach it through the same `Number()`. The third pins the monotone direction, understating spend being the one a budget guard cannot recover from. The fourth is not a property of the function at all but of its scope: each child folds from zero, so a child that opened a fresh session, whose running total starts again below the last one's, is not swallowed by a fold carried across the run. It used to pin a run-wide `+=` on the grounds that a restarted child's accumulator starts at zero. The 2.1.280 binary restores the ledger on `--resume`, so that case was rewritten on purpose rather than left asserting arithmetic the loop no longer does.

`cycleSpendOf` in `orchestrator.test.ts` earns eight cases, and `resumedCycleSpend.test.ts` earns three, on the same kind of silent money as the fold above, one level up. A resumed child's `total_cost_usd` is its session's running total, so the loop adding it whole charged cycle N for cycles 1..N. Nothing threw, and the run page showed a total roughly double the work and a run stopped at half its limit. The pure cases pin `turnCostOf`'s rules as the loop applies them: the increase on a resumed session, and the whole figure for no resume, a different session, no baseline or a total that fell. They also pin what a cycle that reported nothing leaves behind, because both errors there are silent too: a kept baseline under-counts after a new ledger, and a cleared one over-counts after the same ledger. The file drives real runs through `startRun` against a stub child that restores its ledger on `--resume`, which the pure cases cannot reach, because the defect was in the wiring: which session the cycle resumed, and what it is measured from. It pins the stored total, the pre-cycle guard admitting a third cycle on the true figure, the `--max-budget-usd` remainder handed to each child, and a fresh start opening a new baseline. Run against the pre-fix loop, all three fail: $21 stored for $10 of work, a $10-limit run stopped after two of three cycles, and $17 for $11 across a fresh start. The premise the stub encodes was read off the binary rather than run, and `docs/verification/metering-and-cost.md` lists it as unverified.

`parksAndRefunds.test.ts` pins which counter each park is charged to, which no pure function here can say: the counts are written in `startRun`'s own ending, and a guard park and a refusal park reach that write identically. It drives whole segments of a real run against `shutdown.test.ts`'s stubbed `spawn` — a scripted child per work cycle, with the live guard's pause written onto the interrupt map rather than reached through the ticker — and un-parks with `resumeRun`. The refusal allowance has two cases and each is half the test: three parks at the run's own guard followed by a refusal must park rather than fail `pauses-spent`, and `MAX_PAUSES_PER_RUN + 1` refusals must still fail, or a refusal branch that advanced nothing would pass the first for ever. The pick-up's reset is a case in `orchestrator.test.ts` beside the other `reopenRun` cases, on that file's insert harness, because `reopenRun` spawns nothing. The guard-cut refund has three cases. The first is the run its unbounded version could not end: `live-resume`, `maxIterations: 1`, every cycle cut, handed back after each park. It must end on the cycle cap's own sentence after exactly `MAX_PAUSES_PER_RUN + 1` spawns, and it is matched on the sentence rather than the status because the pre-cycle guard ends a capped run `stopped` — which is also how the stub ends a run whose script ran out. The second is the same run handed back only after the refunded parks: the charged cut past the bound must end it `stopped` on the cap by itself, with no `resume_at`, rather than park it for the sweeper to end a window later; it failed before the change, parked. The third is its control, with a grant written onto the row during the first park: the charged cut then leaves a cycle to spend and must still park, which fails a check that ends every cut past the bound or reads `maxIterations` without the grant. The context ceiling's early end has the same shape one refund over: every early end the bound allows, a park and an un-park, then one more crossing, which must be charged and end the run at its cap rather than be refunded as the first of a fresh three.

`calibration.test.ts` pins `measureCeilings`, the "Measured" ceiling Settings offers for `sessionCostLimit` and `weeklyCostLimit`. A wrong one is a plausible dollar figure the operator saves, and every meter and guard is measured against it whenever the provider's reading is off or unavailable. Both cases came from the route's own formula. A rolled-over reading must measure nothing: the route divided the new window's $2 by the closed window's 88% and suggested $2.27 after an $80 block, and summed two weeks over one weekly percentage. An aged reading must count only the spend it had seen: $200 at 50% with half of it after the fetch measured $400 where the reading's rate says $200. That is 2x high, the unsafe direction for a ceiling.
