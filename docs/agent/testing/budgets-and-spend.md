# Budgets, spend guards and the run form's limits

[← testing index](../testing.md)

Read before adding or editing tests of `budget.ts`, `installBudget.ts`, `installSpend`, the instance budget, `assistRefusal`'s process count, `costBaseline`, `costSplit`, `cycleCostAfterResult`, `liveGuardTick`'s budget half, the cycle a task check grants and the new-run form's `budgetPayload.ts`/`formProblems.ts`/`formSeed.ts`.

`budgetFromForm` is where every limit's off state is decided: `null` is the wire form of "off", so a number left in a box the operator switched off is a perfectly valid `BudgetPolicy` and starts an unattended agent under a cap nobody set, and the window pair reads 0–100 on the form against 0–1 on the wire, which makes a slip of a hundred a guard that never fires.

`runFormProblems` is the same page's other half and the same silence: it is every reason the new-run form refuses to start, and a refusal that stops firing does not throw, does not fail a typecheck and leaves a page that looks right — it just starts the unattended agent the refusal held back. Two of them are load-bearing beyond their own sentence. The deleted-agent and the unusable-agent refusals both name the `agent` control and the page shows one problem per control via `.find`, so their push order decides which the operator reads; and `immediate` is what separates a range error, true the moment it is typed, from an emptiness error that has to wait for a blur, which is the difference between a form that argues under the caret and one that never says anything at all. `limitProblems` is its limit half, split out because the template Save reads it as well, and its case pins that the two give the same sentences: a Save that drifted from Start stores a limit switched on with its box blank as no limit, which the chat and the canvas then inherit. The server half of that refusal is in `templates.test.ts`, and it failed before `normalizeTemplateInput` refused `""`. `windowGuardUnreadable` beside them is the form's forecast of the door's `no_ceiling` refusal, and its case asserts agreement with `readWindowGuard` itself rather than a restatement of it, because agreement is what drifted: the form asked whether a ceiling was set, the door asks whether the window has a fraction, and on a stock install the provider's percentage makes those two answers differ.

`formSeed.test.ts` is the same page's third door, *Start another like this*, and it earns its place on one mapping: `seedFromRun` reading a run's null `isolation` as off. `createRun` writes null only for a run that asked for a worktree and was never planned, so the copy landed on "This folder" on a git repository with nothing on the form marking it — an agent in the operator's own checkout, the failure isolation exists to prevent. The case failed on the old `=== "worktree"` reading. `"none"` copied as none and the gone-mount folder are pinned beside it because they are the two neighbours a fix to the first could plausibly break.

The eighth of the twenty that open the database, `assistBudget.test.ts`, is a *count over three tables*, which is what `assistBudgetRefusal` beside it cannot be tested on: the rule is pure and the defect was never in the rule — it was that the cap read one kind of child and three others consulted nothing, so a `run_reviews` row, a `chat_sessions` row and a `workflow_instance_blocks` row are written and the count asked about each.

Its two negative cases carry the same weight as its positives and one of them is not obvious: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so counting it refuses an operator's chat turn to make room for a process that does not exist.

Both directions were seen to fail before this landed.

`installSpend.test.ts` pins what the install-wide ceiling is *measured from*, which the pure verdict beside it cannot — a SUM across three tables each bounded on a different column, with a fourth contribution through `telemetrySpendSince` — because a window bound on the wrong column is a ceiling quietly larger than the one the operator typed and a plausible dollar amount either way.

`instanceBudget.test.ts` pins *when* the workflow-wide budget is evaluated: every call site was "before something spends", so a graph of single-cycle blocks compared its limit with zero N times and `maxInstanceCostUSD` could not fire at all, which looks exactly like a workflow that came in under its limit.

`validationGrant.test.ts` drives whole run loops, because the defect it pins was a disagreement *between* guard sites that each read correctly alone: the post-cycle cap check honoured a task check's grant, the pre-cycle guard one pass later read the unwidened cap, and on the default `maxIterations: 1` every run the check sent back ended there — verdict paid for, grant spent on the row, task left claimed. The child is `shutdown.test.ts`'s fake `spawn`, for `CLAUDE_BIN` only, and the verdict is `validationAtBoundary` replaced on its module, `contextCeilingRace.test.ts`'s device; `recordValidationCycle` stays real because the row it writes is the guard's input. Its fourth case pins the live guard's copy of the same figure: `iterations` is checked first and is not live-enforceable, so a live closure without the grant would skip the granted cycle on every tick. The arithmetic itself is in `budget.test.ts`, and the sweeper's re-reading of a run parked at that cycle is a case in `orchestrator.test.ts`. All three failed before the change.

The live tick's budget half earns three cases in `orchestrator.test.ts` on `contextCeilingRace.test.ts`'s grounds, one half of the tick over: what they pin is an interrupt that must *not* be written. A tick that evaluated a guard whose cycle ended during its scan counted that cycle twice and left a stop for whatever the run did next. The scan is held open through the in-flight promise `currentSnapshot` hands every caller, and the helper asserts the tick really joined that promise before the cycle is ended — without that check, a slower `checkContextCeilings` ahead of it would let the first case pass for the wrong reason. The control is a guard still registered, which must still stop the run. The third case is the claim-time discard, and it asserts *which* reason the run ends on, because the stale verdict and the run's own cap both end it `stopped`. Each failed with its own fix removed and the control passed without either.

`costBaseline.test.ts` is the guard that knows what a task normally costs, and each case pins a decision that fails silently if it is wrong. A signature that changed under a reflowed prompt would reset an operator's baseline to nothing at the exact moment they were iterating on wording, and the guard would simply stop firing with nothing to say so; a mean in place of a median would be dragged upward by the very runs the guard exists to catch, so two expensive runs would buy a third; and a verdict fired on one sample would teach an operator to switch the guard off, which costs more than the guard ever saves.

`costSplit.test.ts` is where the bill went, and the one property that keeps it honest. The split exists because a loop can be 92% cache reads by volume and still spend half its money on writes — the multipliers are 0.1× and 2.0×, a twentyfold ratio no token chart shows, and measured on one install across 90 deduplicated frames writes were 48.1% of the bill from 7% of the tokens. What it pins above any single figure is that the split and the total are one arithmetic: a readout that could drift from `costOf` would be two statements of one policy, with the operator reading a number the guard itself does not believe.

`cycleCostAfterResult` in `orchestrator.test.ts` earns its four on a measured 75%, and it is the rare case where the evidence came before the test rather than after. `total_cost_usd` is the session's running total and `usage` on the same event is only that stretch's own, so one `+=` was right for one of them and wrong for the other, and the wrong one is the money: on run `075f7959` two `result` events arrived in the same millisecond — the agent's turn ended while a background `Explore` sub-agent was still running, and the same session was woken again when it answered — and $7.025419 plus $9.330155 was stored as $16.355574 against the $9.330155 telemetry recorded across all 110 of that session's requests. Nothing about that run looked wrong: exit 0, a clean report, a log whose rows each named a plausible figure. The first case is that pair verbatim, because a regression here is not a shape that stopped parsing but an arithmetic one that keeps working. The second is the risk the fix itself introduces and is the reason the fold takes the larger rather than the last: a `result` whose cost field is absent, unparseable or zero says nothing about the session and must leave a figure already reported standing, or a cycle overstated by 75% is traded for one silently reported at $0 — seven readings, since `undefined`, `""` and `NaN` all reach it through the same `Number()`. The third pins the monotone direction, understating spend being the one a budget guard cannot recover from. The fourth is not a property of the function at all but of its scope, and it is there because the obvious over-correction is to move the fix up to the run: a cycle that died at `error_during_execution` and resumed gets a second child whose CLI accumulator starts at zero, those runs reconciled to the cent before this change, and the `+=` across children has to survive it.

`parksAndRefunds.test.ts` pins which counter each park is charged to, which no pure function here can say: the counts are written in `startRun`'s own ending, and a guard park and a refusal park reach that write identically. It drives whole segments of a real run against `shutdown.test.ts`'s stubbed `spawn` — a scripted child per work cycle, with the live guard's pause written onto the interrupt map rather than reached through the ticker — and un-parks with `resumeRun`. The refusal allowance has two cases and each is half the test: three parks at the run's own guard followed by a refusal must park rather than fail `pauses-spent`, and `MAX_PAUSES_PER_RUN + 1` refusals must still fail, or a refusal branch that advanced nothing would pass the first for ever. The pick-up's reset is a case in `orchestrator.test.ts` beside the other `reopenRun` cases, on that file's insert harness, because `reopenRun` spawns nothing. The guard-cut refund has one case, the run its unbounded version could not end: `live-resume`, `maxIterations: 1`, every cycle cut, handed back after each park. It must end on the cycle cap's own sentence after exactly `MAX_PAUSES_PER_RUN + 1` spawns, and it is matched on the sentence rather than the status because the pre-cycle guard ends a capped run `stopped` — which is also how the stub ends a run whose script ran out. The context ceiling's early end has the same shape one refund over: every early end the bound allows, a park and an un-park, then one more crossing, which must be charged and end the run at its cap rather than be refunded as the first of a fresh three.
