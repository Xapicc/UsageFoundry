# Forked conversations and prune money

[← testing index](../testing.md)

Read before adding or editing tests of the `fork_attempts` row, of what a cut is priced at and over which turns (`priceReceipts`, `priceForks`, `pruneSavingsByRun`), of a failed pruning bookkeeping write, or of what a forked conversation is reported as. Split out of [context pruning](context-pruning.md), whose `contextPruning.test.ts` holds the pure arithmetic these price with.

`forkAttempts.test.ts` is the `fork_attempts` row written and read back against a real database, and it exists because of a defect the arithmetic cases could not see. The INSERT listed twelve columns and bound thirteen values; better-sqlite3 refuses that at bind time, `recordForkAttempt` catches it and returns null, and the feature went quiet whole — no fork ever recorded, `forkSavings` summing an empty table, `resumed` never written, and a savings panel at $0, which reads as a fork engine that did nothing. `parseFork` and `forkCutFromRow` were both tested and the defect sat between them, in the one step that needs a driver and a schema: a prepared statement's arity is checked by neither the type system nor a mock, and the fixture's numbers are all distinct from one another because an all-zeros row passes with two columns transposed. The other cases are the row's readers, each quiet when it is wrong: the dashboard reaching a fork through `pricedCuts`, the seam the run's page uses, where it once read the legacy table alone and a fork showed on one screen and not the other; a refusal recorded, because at winnow's default cold age every boundary refuses and forty cold-age rows are what tell an operator the engine is on at all; a resume's verdict carried in both directions, and `pendingForkFor` finding the fork a parked run came back holding and only that one; a recorded fork turned into a saving; and `measuredForkRemoval`'s per-row floor, which keeps a fork that removed nothing — all five measured here did — from paying for another conversation's saving and reopening `ceilingCut`'s ~$1.80 gate on arithmetic nobody intended. The last two are the claim itself. A fork with no API-side reading earns nothing from `forkSavings`, because `winnow fork` leaves `toolUseResult` for the resumed CLI to rebuild from, and all five forks written before those columns existed resumed into a larger API window than they were cut from while `net_bytes` claimed 4,678–17,594 tokens removed. And a boundary prune is priced the same on the runs list, its page and the dashboard, which disagreed over where a batch's control group started — one cut charged on one screen and free on the other two, measured here as a session net of −$0.95 beside two runs that both read positive. And a page of runs is priced in one pass per engine, whatever number of them forked: `pruneSavingsByRun` asked `forkSavings` once per run, each awaited call that found a fork started a scan of its own, and the live tiles ask it every five seconds, so a poll's cost grew with the runs that had forked while every figure stayed right. The case counts `scanUsage` calls across a mixed page and also pins that each run's figure is its own page's. And a cut on a run whose `runs.model` is NULL — every stock install's — is priced at the model its turns billed at, on both engines, deep-equal to its twin with the model named: priced at the column, the money read unknown on every run and the page blamed the price table for a model that has a price. A receipt no turn has followed yet sits beside it to pin the fallback to the column, because a prune made a moment ago must not read as unpriced. Beside that, a cut followed by two billed turns and the CLI's `<synthetic>` all-zero frame between them counts two turns on both engines: the frame read nothing, so counting it credited one more re-read avoided per restart, always in the flattering direction and invisible on any screen. Last, a fork nobody has measured and one measured to remove nothing must not sum to the same `PruneSavings`: both credit $0 saved, and without `unmeasuredPrunes` they were the same object byte for byte, so every surface printed the first as the second.

`contextPruningReporting.test.ts` covers one thing: a bookkeeping write that fails says so. `fork_attempts` shipped without the `suffix_bytes` column its own INSERT names, the write threw at every fork, `recordForkAttempt` caught it and returned null, and the table stayed empty — exactly what a fork engine that had never run looks like, so a day of runs produced no evidence about the thing being tested and nothing anywhere said why. The catch is still right, because a receipt must not fail the run it describes; what is pinned is that the failure now reaches `ops_events`, once however many boundaries hit it — twenty attempts, one row, since `ops_events` keeps 500 for the whole server and a fault that recurs at every boundary would evict everything an operator needs beside it — with a message naming the missing column, which is what makes the row actionable rather than an alarm. Its control writes the row once every column `db.ts` adds is there, and that list falling behind the INSERT is itself the fault under test. It is its own file on `schemaMigration.test.ts`' first reason: `DATA_DIR` has to be set before `config.ts` is imported, and a file that imported it first would run against the repository's real database.

`transcriptForkDedupe.test.ts` is which copy of a tool call counts when the same conversation is on disk twice. `winnow fork` writes a second transcript whose tool results are deliberately replaced by short pointers and never deletes the first, so both carry the same `tool_use` ids and the composition reading has to pick one. The rule it used, most characters wins, always picked the original's full result, and the fork was reported as having removed nothing, permanently, on the one screen an operator would read to decide whether forking was worth it — measured on a real fork at 92,498 characters against the fork's own 69,773. The rule is now recency, since the transcript still being appended to is the conversation the run is carrying, and both directions are pinned — the fork's pointer once the fork is the one being written to, the original once a rollback puts the run back in it — because the number is plausible whichever copy wins and nothing throws; a tie keeps the complete record. It is its own file because `config.ts` reads `CLAUDE_HOME` at module load, and a test that imported `transcripts` before setting it would scan the operator's real transcripts.
