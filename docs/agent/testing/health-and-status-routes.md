# The health and status routes

[← testing index](../testing.md)

Read before adding or editing tests of the health and status routes, the read-only banner the health route drives, and `backupStore`'s reading on the status payload. Split out of [auth-config-and-status-routes.md](auth-config-and-status-routes.md) when that file reached 20 KB; the credential checks on both routes are there and in [sign-in-limits.md](sign-in-limits.md).

`src/app/api/health/route.test.ts` opens the database and drives that route in both directions against a throwaway database: the unhealthy one is the case worth having, because a probe that always answers 200 is indistinguishable from a working one right up to the day the database goes read-only — which is exactly when Docker is reporting the container as fine.

It also asserts what the payload does *not* carry, because `middleware.ts`'s exemption of the route is justified by that and by nothing else.

`src/app/api/status/route.test.ts` opens the database and pins the same thing one route over, for a reader that is not a person: that the counts match the rows it seeded (a monitor thresholding a queue depth that never moves is bit-for-bit a queue that never backs up), that a prompt, a folder path and both tokens are absent from a payload something else will retain and forward, and that the read-only credential is checked here — since `middleware.ts` exempts that path only while `UF_STATUS_TOKEN` is set, the two have to be asserted together exactly as `/api/mcp`'s are.

It names `WORKSPACE_ROOTS` as well as the other three, because the report walks the checkout store for a byte count and any container this ships in has that variable set.

`backupStore` is tested for a three-state reading rendered as two. An unreadable directory reported as a count of zero tells an operator "no backups have been taken" when the truth is "this process could not look" — a missing bind mount, or a directory Docker created as root under a server running as somebody else — and those need opposite actions while rendering identically. The second case is what counts as a snapshot: `--dest` takes any path ending in `.db`, so matching only the script's own generated name reports zero for an operator who names their own, and the cron in `docs/backup-and-restore.md` writes its log in the same directory, which is not one.

`src/app/api/status/route.test.ts` gained two more. `restartClosedOutstanding` is driven 2 → 1 → 0 across a pick-up and a set-aside, because the field exists precisely to de-latch and the one it replaces on the runbook never did — a monitor that goes red once and stays red is the fastest way to teach an operator to ignore the condition whose whole content is *somebody must act*. And the backup reading is asserted to carry **no path**, on the same ground as the prompt and the tokens beside it: this payload is retained and forwarded by whatever scrapes it.

And a third, for a gauge measured from the wrong clock: a run created three days ago that worked two cycles, parked, and was resumed into a full fleet must report `queue.oldestQueuedAgeSeconds` under a minute, not 259,200. `README.md` tells an operator to alert on that field as a run queued and never started, and every way back into `queued` — a sweeper resume, `resumeRun`, a dependency release, the end of a stack wait, a pick-up — leaves `created_at` alone on purpose so `promoteQueued` keeps FIFO order, so aged from `created_at` the alert fired on runs that had already worked and nothing looked wrong. It drives the real `resumeRun` rather than seeding a row, because what is pinned is that the transition stamps `queued_at`; a seeded row would pass with every stamp deleted.

`readOnlyBanner.test.ts` pins the client half of the health route — the sentence a 503 may put above every page — in one direction, because the inline decision it replaced, `res.ok ? null : res.error`, failed in both directions at once. In one it trained the eye: `jsonRequest` folds a fetch that never reached the server into `error` as `status: null`, and the notice rendered the transport's own words — "Failed to fetch" in Chrome, "Load failed" in Safari — so a single restart or a proxy blip put a warning banner above every page until the next poll; a banner that appears and disappears with the network is exactly what teaches an operator to skip the one that means something. In the other it was silent: the server that cannot write its own database answers 503 with the failure in `checks.databaseError` and no top-level `error` at all — the field every route uses to explain a refusal — so the notice read null and the page that most needed the banner showed nothing, looking exactly like the one that can write. The function is pure and its failure is silent both ways, which is the grounds the rest of this list shares.
