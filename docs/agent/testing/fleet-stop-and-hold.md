# Fleet stop and hold

[← testing index](../testing.md)

Read before adding or editing tests of `fleet.ts` (`stopFleet`, the hold, the bulk pick-ups) and of any reader of `settings.newWorkPaused`. The tests of `shutdownRuns` and the shutdown ladder are in [shutdown.md](shutdown.md).

`fleet.test.ts` opens the database, and it is two subjects that are one file because both are about *whether anything is running*.

The stop half pins an ordering, `bootBlocks.test.ts`'s kind of fact: a dependent still `waiting` when the run it waits on is stopped is released, promoted and spawned — a run starting *because* the fleet was stopped — so the waiting rows are closed out first, and the only evidence otherwise is a billed agent under a page saying everything stopped. A further case pins that those rows are written `stopped` rather than `blocked`: the run in front is picked up by name and the one behind must stay as the stop left it, which failed on main at `50d60d8` with it back to `waiting`, revived by `reviveBlockedDependents`. It also checks the fleet's pick-up can still put that run back, since `stopped` is what makes it offerable at all.

It pins the third halt cause beside it, since `fleet` versus `operator` on the instance row is the only thing that afterwards tells a workflow somebody stopped from one that went down with everything else.

The hold half is a case per call site, and that shape is the point: nine separate places start work and a fix that misses one is silent, so each case drives the real entry point — `promoteQueued`, `releaseDependents`, `emitBlockRuns`, `tickSchedules`, an orchestrator block's deciding turn, and the sweeper's `sweepPaused` and `releaseStackWaits` below — and proves the *difference* by running the same call with the hold clear, or beside a row the same restart keeps.

Two of them need that second run to be legible rather than merely different: the emission is refused for a malformed payload once the hold is gone, and the schedule tick is refused by `scheduleRefusal` instead, which is what separates a tick that never looked from one that did.

`tickSchedules` is exported for that case and for nothing else.

The deciding turn is its own describe, because its failure was a bill rather than a start: under the hold the turn spawned and was then refused at `emitBlockRuns`. Each case asserts on the claim, since `thinking` is the row every spawn follows. One advances a ready head block under the hold and asserts it stays `waiting` with no `started_at`, then clears the hold and asserts the same call claims it. One lifts the hold through `setFleetPaused(false)` alone, because on a held and stopped fleet the lift is the only event left. One presses the hold after the claim and before `startBlockTurn`'s awaits return, and asserts the claim is handed back to `waiting`. All three failed on `17704aca` before the change: the first two because the turn was claimed under the hold, the third with the block `failed` against the absent `claude`. Each case halts its instance in a `finally`, because `advanceInstances` walks the whole file. The describe also opts out of `maxConcurrentAssists`: a first run whose earliest case failed left a turn `thinking` and so filled the second slot, and the lift case then passed for the wrong reason — its block was left `waiting` for want of a slot, not because of the hold. The loop pass's own claim loop is pinned in `loopSection.test.ts` ("leaves its turn unclaimed while new work is held"), on that file's section fixture, and failed before the change with the member claimed. The restart half is in `bootBlocks.test.ts`'s held describe. A head block, a block behind a completed member, and a loop between passes each stay as they were across a boot under the hold. The same head block without the hold is closed out, and so is a block behind a queued member the boot closed out — the `restart_closed` exception. The first two failed before the change, and the loop case failed with only the `looping` sweep's clause put back to the spared list. Two new `bootBlockPlan` unit cases in `workflows.test.ts` pin the held list and that a `restart_closed` member overrides it, and its partition case now carries a held instance.

A review block's reviews are the describe after it, for the deciding turn's reason one block over: every branch the block is handed is a billed reviewer nobody is watching. Three cases, one per site `advanceInstance` reaches. A review block with nothing in front of it, advanced under the hold, must stay `waiting` with no `started_at`, and the same call must claim it once the hold is cleared; it failed with the block claimed. One claimed before the hold and pressed before `startReviewBlock`'s snapshot returns must be handed back to `waiting`; it failed with the block `emitted`. One already reviewing, whose review waits on a full assist queue when the hold is pressed, must not start that review when the slot frees, and must start it once the hold lifts; it failed with the branch set aside, the review having run. That case's cap is read off `liveAssistChildren()` rather than written as 1, because an earlier case's deciding turn holds a slot for good: with 1 the wait never ended, and the case failed for that reason instead. The pass's claim loop is a case in `loopSection.test.ts`, on that file's section fixture, and it failed with the review member claimed. The merge queue's two doors are cases in `mergeQueueDrain.test.ts`, on its conflict fixture and its spawn recorder. Under the hold, a conflicting branch in an auto-resolve batch must fail with the hold's sentence, with no `resolve` row and nothing spawned. A hold pressed from inside `assistRefusal`, the window scan `resolveConflicts` awaits before its spawn, must end the same way and leave the branch at its tip. Both failed before the change, with the stub resolver spawned.

The sweeper's two sites are their own describe, last in the file because it calls `reconcileOnBoot`, which closes out every row it finds. Their failure is the restart rather than a spawn: a park whose wait ended under the hold was re-queued, the hold kept it there, and the restart the operator held the fleet for closed the queue out, so the run was ended `stopped` and filed in the restart notice instead of resuming. One case parks two runs, one due and one not, sweeps under the hold and reboots, and the not-yet-due run is the control the same restart keeps; one is a `waiting-for-stack` row with no request attached, which `decideStackWait` releases, swept and rebooted the same way. Both failed on main at `50d60d8`, the first with the due run `queued` after the sweep, the second with `releaseStackWaits` reporting it released. The third lifts the hold through `setFleetPaused(false)` with `maxConcurrentRuns` at 0 and asserts both rows are queued without a timer tick; it failed with the hold checks in and the kick not yet added, the stack row still `waiting-for-stack` when the call returned.

A third describe covers the per-run exemption from the bulk pick-ups, and it is three cases because there are three doors and none of them shares a mechanism: `reopenFleet` reads `set_aside_at` off the row rather than trusting the ids it was handed, `restartClosedRuns` filters the query in both directions — the notice has to come back when the run is put back, or the operator has a switch with no off — and `reopenRun` clears the column instead of reading it, because a mark that survived a hand pick-up would go on excluding a run that had since worked again. Two more cover the side door, the revive: each bulk press picks up the run a set-aside row waits on and never names the row itself. The fleet's pick-up and the restart notice's each have a case, because each reaches `reopenRun` by its own path. A dependent nobody set aside sits beside it as the control, and it is woken, so the revive ran. A third run behind the set-aside one must stay blocked, so the walk did not go through it. Both failed on main at `50d60d8`, the set-aside row back to `waiting`.

`restartClosedView.test.ts` pins what the restart notice draws after that press, and it is pure because the defect was a render choice rather than a query: `RestartClosed` had three early returns, and both ways a press can end fell into the wrong one. Only a successful pick-up clears `restart_closed`, so after a press that refused runs the count is still above zero, and the answer was drawn only at zero — the notice and its button came back unchanged and the sentence naming each refused run and its reason was never on screen, while a permanent refusal (a stopped workflow's run, a run whose work cycles are used up) was met again by every further press with nothing said. A failed press returned the error *instead* of the notice, which took away the button, and the button was the only thing that cleared the error. The two cases the task was filed with are the count of 2 with a refusing answer and the count of 2 with a failed one, and both fail when the function is swapped back to the old returns; the rest pin the summary for a press that refused everything and that a failed press keeps the button. A later case pins that the offer is withheld while the list holds a run the last press just refused — its sentence said such runs "can resume where they left off" over a button that only asks again — including when a run that was not refused has joined the list, since the press would ask the refused ones again too, and that refusals of runs no longer in the list withhold nothing. It fails when the offer is drawn for any non-empty list, which is what the function did before; the function takes the list's ids rather than its count for it.

Every one of those failures ends the same way and none of them throws: an agent that accepts edits, back at work in a folder somebody had finished with.

A fourth covers a run picked up before it ever had a workspace, because both doors that reach `reopenRun` are here. A run created behind another one has no `work_dir` and no isolation until `admitWaiting` plans them, and it can end `stopped` while it waits or `failed` by that release; a pick-up that queued it worked in the operator's own folder, with no checkout and no wait for its dependency. Three cases, stopped then reopened by hand, failed by a release that found every checkout slot held, and stopped then reopened through `reopenFleet`, each asserting the row goes back to `waiting` and is admitted into a checkout of a real repository once its dependency completes. A fourth has `reopenFleet` pick up both ends of an `on-finish` edge with the dependent named first, as the page's newest-first list names it: taken in that order the dependent's release pass reads its dependency as it ended, a cycle run and terminal, and admits it before the dependency is queued beside it, so both work at once. It fails with the dependent `queued` when `reopenFleet` walks the ids as sent. `maxConcurrentRuns` is set to 0 rather than the hold, since the hold would suppress the release under test.
