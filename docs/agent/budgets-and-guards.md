# Budgets, guards and concurrency caps

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/budget.ts, installBudget.ts, and every guard site in orchestrator.ts.**

**How guards are enforced is the operator's choice, and none of the three modes is a hard cap.** `BudgetPolicy.enforcement` selects it per run.

- `between-cycles` (the default) reads the guards only before each iteration. Overshoot is bounded by one iteration **per run active at the time**, and this is the only mode whose accounting is exact — every cycle reports its own cost.
- `live` also reads them on a global ticker (`liveGuardTick`, `settings.liveGuardIntervalSeconds`, floor 15s) while a child is in flight, and interrupts it. That bounds overshoot to *one model turn plus one interval plus the kill* instead, and costs the in-flight cycle's work. Every input moves per tick, but from three different places: `duration` off the wall clock, the two window fractions off a fresh `currentSnapshot()`, and the run's own spend off telemetry (see below — the locals cannot supply it). Neither usage source is instant, and the window half is the older of the two: its preferred reading is the provider's own percentage, which `planUsage.ts` refreshes at most every five minutes and keeps serving for up to an hour while requests are being refused, so `guardFraction` also takes the derived reading — recomputed from the transcripts on every check — and acts on whichever is worse. Telemetry is a batch exporter a second or so behind. A verdict reached on a reading older than `STALE_PLAN_READING_MS` names its age in the reason, and every `budget` event carries `sessionPlanAgeMs`/`weeklyPlanAgeMs` so the log can tell a fresh decision from a frozen one. Tighter, not exact — say so in every piece of copy.
- `live-resume` is `live`, except the 5-hour window parks the run instead of ending it.

`LIVE_ENFORCEABLE_CODES` is the whitelist. `iterations` is excluded because the loop increments before it spawns — a live check must be passed `iterations - 1` or it kills the cycle the pre-cycle guard just authorised. `no_ceiling`/`no_terminus` are excluded because re-reading configuration mid-flight means a Settings edit in another tab kills a running agent. The ticker deliberately emits **no** `run_events` row per tick; only an interrupt is recorded.

**All three of those modes bound what a cycle may *spend*, and none of them bounds a cycle that spends nothing — so a work cycle also has a deadline, and the deadline is silence rather than wall clock.** `runIteration` registers `exit` and `close` and settles on nothing else, so a `claude` wedged on a socket read, or an agent's own tool call blocked on a read with no timeout, leaves that promise pending for the life of the process: the row stays `running`, holding its folder against every other run in that subtree, its checkout slot, and one of `maxConcurrentRuns` — recoverable only by restarting the container, since the live ticker is registered for the two non-default modes only, the sweeper selects `paused` rows, and `reconcileOnBoot` is a restart by definition. Every other child here already had one (git 30 minutes, a chat turn ten, an orchestrator block ten); the one that runs unattended for hours, twenty-five at a time, did not. `settings.maxCycleSilenceMinutes` (default 120) is that deadline and `cycleSilenceMs` narrows it at the spawn, `chatGuards`' read-time rule, with a floor rather than an off switch — the absence of a deadline is the defect, so there must be no way to type one. **Silence, not duration**, and the two are different guarantees: the clock is the time since the last thing the child printed and every stdout line and stderr chunk resets it, because a cycle that is still reporting is working however long it takes, and ending one for its *duration* is what `enforcement: "live"` is for. Deriving it from `maxDurationMinutes` — the obvious reading, and the one this deliberately does not take — would make `between-cycles` a live mode without saying so, and that mode is the default and the only one whose accounting is exact. The default is deliberately generous for the same reason: the stream is silent for the whole of one model turn and the whole of one tool call, so a run whose test suite takes an hour is silent for an hour and perfectly healthy, and the error is asymmetric — a killed working cycle loses paid work, where a slot recovered in two hours instead of one is still recovered the same day. It goes through `interruptRun` rather than killing the child itself, so there is still exactly one kill path: the `SIGINT`-first ladder gives the cycle its chance to report its own cost, the loop's post-cycle checkpoint picks the interrupt up like any other, and `reconcileKilledCycle` recovers the spend into `spent_usd_est`. What it deliberately does *not* do is settle the promise on its own — the folder goes to whatever is queued behind it the moment `runIteration` returns, so resolving while a child might still be writing there would trade a held slot for two agents in one working tree. `Interrupt.kind` gains `deadline` as a third value rather than reusing `guard`, and `interruptOutcome` is where that becomes something an operator reads: it ends the run **`failed`**, because `stopped` is what this app writes when a person or a rule they configured decided and nobody decided this, and a hung agent filed as "stopped" is the sentence that stops anyone looking for the cause. It is not on `LIVE_ENFORCEABLE_CODES` and is not a `BudgetStopCode` at all: a deadline on a child is not a budget re-read, which is the thing that list excludes.

**Every one of those three bounds is a bound on a count of cycles, so the run's own spending limit is enforced somewhere else as well — inside the CLI.** Read the modes above literally and `maxRunCostUSD` bounds *how many* cycles may start past a threshold and not *how much* the one crossing it spends: a run at $34.99 of a $35 limit was authorised for a further cycle of arbitrary size, which is the same sentence twenty-five times over on a fleet whose settings page reads $875. So `buildArgs` carries `--max-budget-usd` with `max(0, maxRunCostUSD - spentGuardUSD)` — the fourth kind of child getting the flag the other two already had, and the one that spends most. `spentGuardUSD` rather than `runs.spent_usd` is the whole of the arithmetic's correctness: the measured floor excludes a killed cycle's reconciled estimate, so a ceiling derived from it hands the child more room than the guard believes the run has left, which is the display-versus-guard split inverted at the one door where it costs money. The arithmetic is inside `buildArgs` rather than at the call site because it is pure and tested there and because both ways of getting it wrong are silent, and the two inputs are **required** parameters so a caller cannot drop the ceiling by omission. `maxRunTokens` has no equivalent and is still bounded by a whole cycle — the CLI's ceiling is denominated in dollars. What comes back is `result.subtype`, kept on `IterationResult` for this one member, and the branch that reads it sits **after** the interrupt check and **before** the refusal test. Before, and this is the expensive ordering: the CLI latches its own summary of a non-success result into `apiError`, `isUsageLimit` matches "reached your … limit" loosely on purpose because the provider labels its walls per window and per model, and a ceiling this app handed over read as the subscription allowance running out would park a `live-resume` run for hours waiting on money that is never coming. It ends the run `stopped` — the word the pre-cycle `run_cost` verdict already uses — with the limit and what had been spent against it named, and the cycle stays charged to `iterations` because it happened. That the pinned CLI honours the flag on a `-p` work cycle and reports that subtype is reasoned from `chat.ts` using the same flag against the same binary, not measured; it is on the README's *Not yet verified* list by name.

**`run_cost`/`run_tokens` are live only because telemetry makes them live — this is the one place OTLP feeds a budget decision.** The ticker's `progress()` closes over `startRun`'s locals, and `spentUSD`/`spentTokens` only move when the CLI's `result` event is folded in *after* `runIteration` returns — by which point the `finally` has already removed the `liveGuards` entry. Those locals are therefore the *completed cycles'* total and nothing else, which made `maxRunCostUSD` overshoot by one full cycle under `live` exactly as under `between-cycles`: a between-cycles guard wearing a live label. `telemetrySpendSince(runId, cycleStartedAt)` supplies the missing half, bounded by the cycle start so the cycles that already reported through `result` are not counted twice, and added to `spentGuardUSD`/`spentGuardTokens` — **never** to `spentUSD`, so `runs.spent_usd` stays a floor of what Claude Code itself measured. Same display-vs-guard split as `costUSD`/`costGuardUSD`. **That split now holds on the recovery path too, which is the one place collapsing it cost money rather than accuracy.** `reconcileKilledCycle` returns `costUSD` *and* `costGuardUSD`: the first is the displayed figure and is what `spent_usd_est` and the run's own log carry, the second charges an unpriced model the fallback rate and is what the next pre-cycle check, the live ticker and `--max-budget-usd`'s remainder are computed from. Accumulating only the first left the guard side of a run on an unpriced model at exactly $0 however much it burned, so `maxRunCostUSD` could never fire on a run whose cycles are always killed before they report — precisely the run that function exists for. The two differ only for an unpriced model. What deliberately does **not** exist is a column for the guard half: `spentGuardEstUSD` is a local of `startRun`'s frame, hydrated from `spent_usd_est`, which is the *displayed* estimate — so what survives a restart or a pick-up is a floor and only this segment's own killed cycles are charged at the guard rate. Understating a guard is the direction that admits a cycle it should have refused, which is why it is stated here rather than left to be inferred from a column name. The window fractions were never part of this: they move on every tick already, off a fresh snapshot, and a run's own turns land in that scan — but that is the whole machine's counter, not this run's, which is why it does not substitute.

**A guard whose input is optional is not a guard, so the input stops being optional.** `settings.telemetryForRuns` opts into *reporting* — the dashboard card and the run card. A run whose policy needs telemetry to be enforceable (`needsLiveSpendTelemetry`: live enforcement, plus a run cost or token limit) gets `telemetryEnv(runId, required)` regardless of that setting — and what that function hands the child is a capability scoped to writing that one run's records, never `UF_AUTH_TOKEN`, which is why `middleware.ts` exempts the ingest path and the route checks the capability itself — because a guard that silently stops guarding when an unrelated toggle is off is the failure `guardCostOf()` exists to prevent for unpriced models. Refusing such a run at the door would have been the consistent alternative and was rejected: it refuses a policy that works today. `/api/usage` still gates its card on the setting, so nothing about the dashboard changes. What is *not* covered is an export that is configured and does not arrive — so the loop compares the CLI's own figure for each finished cycle against what telemetry reported for it, and logs a `run_events` line naming the cost when a paid cycle reported nothing. The alternative is a guard reading zero, which refuses nothing and looks exactly like a guard that was never reached.

**A cycle cut short by a pause is refunded to the counter.** The loop increments before it spawns, so a live interrupt — and a provider refusal, which does no work at all — lands on a cycle that has already been charged. Left charged, `live-resume` with `maxIterations: 1` can only park and then stop at `cycles` without ever finishing: the pre-cycle guard checks cycles before the session window. `MAX_PAUSES_PER_RUN` bounds the refund, so one work cycle is at most four billed invocations. The refund is applied at the post-cycle interrupt site only — `applyInterrupt`'s two other call sites run *before* the increment and would discount a cycle that completed. It also means `iterations` can no longer be read as "has this run worked before": the prompt/`--resume` choice keys on `sessionId === null`, and `ensureWorktree`'s orphaned-branch guard keys on `pause_count`.

Concurrency multiplies overshoot — `maxRunCostUSD` is per run, so N runs at $5 is a $25 worst case — and `maxConcurrentRuns` bounds N. The cap is enforced in `promoteQueued`, counting **running** rows only: it is a limit on work in flight, so a run over it waits rather than being refused, and queued *or paused* rows — which cost nothing — must never consume it.

**The concurrency cap is a bound on the host, so it ships as a number and it covers every kind of `claude` child.** It is the one figure in `DEFAULTS` that is not left null, and the reason the no-default-ceilings rule does not reach it is precise: a ceiling is null because we would be guessing at something Anthropic publishes nowhere, where how many Node processes a container can carry is a property of the machine. `null` used to be the state a fresh install was in, which meant the shipped configuration had no bound on the fleet at all; it stays available as an explicit opt-out and is no longer the default. `maxConcurrentRuns` is **4** and covers work cycles; `maxConcurrentAssists` is **2** and covers the other three kinds of child, which consulted nothing at all — a review, a merge-conflict resolution, a chat turn and a workflow orchestrator block's deciding turn, each a full Node process, none of which a cap on work cycles could see. Both numbers are chosen against the `mem_limit` `docker-compose.yml` now ships rather than measured, and the arithmetic is in README's *Sizing the container*: raising the fleet means raising the compose limits with it, because what those limits buy is a **local** failure — Docker OOM-kills the container, `restart: unless-stopped` recovers it and `reconcileOnBoot` closes out its runs, instead of the host degrading and the server process that is supposed to be guarding the runs being the first thing starved. The two are split rather than one number for the reason `run_templates` and `InstanceBudgetPolicy` are two budgets: a chat turn eating a run's slot is a queue that stalls for a reason nobody can see, and the ceiling on the container is the *sum*, which is what the settings copy and the README both state. The second cap is read at one door — `assistRefusal()` in `review.ts`, which all four of those callers already passed through — off `liveAssistChildren()`, a count over the three tables that already record each of those children for a boot reconciler to close out. Two things about that count are load-bearing and silent: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so it is excluded by `kind`, and the check is not a claim — the person-facing callers have an `await` between the answer and the row that fills the slot, so the overshoot is the number of requests in flight, which is accepted because this bounds memory rather than a folder. What happens over the budget differs by caller and that difference is the design: a review, a resolution and a chat turn are **refused** with a sentence, because a person is there and has an error channel, while a block's deciding turn is left `waiting` — gated at `advanceInstance`'s claim rather than inside `startBlockTurn`, which is why that function calls `windowRefusal` and not `assistRefusal` and would otherwise refuse itself whenever it was the turn that filled the budget. `blocked` there would end the branch of the graph behind it for a shortage of memory that clears in minutes, so whatever frees a slot advances again: `settleBlock` already did, and `review.ts`'s `finish` and `chat.ts`'s `finishTurn` now do too, through the dynamic import `releaseDependents` already uses.

**And a cap on N still bounds nothing about the total, so there is one ceiling that is about the install rather than about a spender.** Every other guard here bounds one thing: `maxRunCostUSD` a run, `maxInstanceCostUSD` one press of Run, `chatTurnBudgetUSD` one turn. Nothing bounded the sum, and nothing bounds the *rate* at which new spenders appear — `promoteQueued` refills a slot the instant one frees, a schedule presses Run with nobody present, an orchestrator block starts up to `MAX_FAN_OUT` runs with no approval — so the fleet's spend was `waves × concurrency × per-run limit` with no term under an operator-set maximum. `settings.installDailyCostLimitUSD` is that term, `null` by default and normalized by `normalizeInstallBudget` under the `null`/`""`/`0`-means-off rule every budget field here follows. `evaluateInstallBudget` is the verdict, pure and unit-tested beside the other two and sharing their `BudgetVerdict` and their `BudgetStopCode` vocabulary (`install_cost`); `installBudget.ts` is the reading, and it is a **fourth** reading rather than a fourth cost source — `runs.spent_usd`/`spent_usd_est`, `workflow_instance_blocks.cost_usd`, `chat_turn_spend.cost_usd` — the same money `chat_sessions.cost_usd` totals, dated per turn so a day's window can be taken out of it — and, for cycles in flight, `telemetrySpendSince` through the one door with its one per-run per-cycle bound. It never reaches `buildSnapshot()`, `runs.spent_usd` or any window meter, it carries the same display-versus-guard split everything else here does, and it must never be summed with the meters above it on the dashboard: those are our price table over every transcript on the machine measured against Anthropic's windows, and this is money this app itself recorded spending over a rolling 24 hours. The window is **rolling** rather than a calendar day for `buildPeriods`' own reason turned into a guard — the container runs in UTC and the operator does not — and because a calendar boundary is a cliff every run in the install would cross together. A run still going, or one that finished inside the window, contributes its whole spend: `runs.spent_usd` is one figure for a whole run and there is no per-hour breakdown of it, so this over-counts, which is the safe direction for a ceiling and is why it feeds a guard and its own card and never a rollup. **But the over-count has to stay bounded, so every row here names the instant that takes it out of the window and none is bounded on a column it may never write.** A run is bounded on `finished_at`, or on `paused_at` while the row is still `paused`: a parked run deliberately has no `finished_at` — it is not finished, it is waiting out the 5-hour window and keeping its folder and its session — so bounding on that column alone counted its spend for ever, and three runs parked at $40 read $120 against a $100 ceiling on every call, refusing every door in the app for as long as they stayed parked, under a refusal saying the spend would age out of the window when nothing would ever age it out. The status test beside it is load-bearing rather than decoration, because nothing clears `paused_at` on the way out of a park: a bare `COALESCE(finished_at, paused_at)` would drop a run that parked yesterday and is spending right now out of the reading altogether. A block gets the same treatment on `started_at`, which bounds the one case that matters — a settled block put back to `waiting` with its `finished_at` cleared and its accumulated cost kept — and drops nothing live, since every UPDATE that adds to `workflow_instance_blocks.cost_usd` writes `finished_at` in the same statement. And a chat contributes **per turn**: `chat_sessions.cost_usd` is a running total over the life of a thread, so summing it bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in — a limit on the install's whole history wearing a 24-hour label, closing every door and stopping the runs already in flight at their next pre-cycle guard. `chat_turn_spend` is one dated row per settled turn, written inside `finishTurn`'s existing latch so a late settle that moved no total writes no row either, and the running total beside it is left exactly as it is, because the chat page displays it and a column that quietly began meaning something narrower would be the worse repair. A thread that predates the table is backfilled as a single turn at its `updated_at` — bit-for-bit what the old query counted — inside the same transaction as the CREATE, since reading an un-backfilled table as $0 would *widen* the ceiling on the boot that upgrades, which is the one direction a ceiling must never move by accident. Five doors read it and no more — `createRun` (refused rather than queued, and inside that function rather than in `POST /api/runs`, because the chat's approval batch, a workflow's pass and a block's emission all arrive there too), `startRun`'s pre-cycle guard, `startWorkflow`, `startBlockTurn` and `sendChatMessage` — and the pre-cycle one sits ahead of the instance guard because it is the wider ceiling and halting a whole graph over a limit that is not about that graph would take down blocks that are not the problem. This is emphatically **not** `buildPeriods` feeding a guard: that measures history against a weekly ceiling pro-rated over a span nobody set an allowance for, where this is a number the operator typed meaning what it says.

**A run's provider changes nothing about the terminus rule and everything about the sentence.** `maxIterations` and `maxDurationMinutes` are the only two monotone termini whatever CLI runs the cycle, so `no_terminus` — refused at `POST /api/runs` and again in `evaluateBudget` — already means "one of these two must be present" for every run. `providerTerminusRefusal` tests that same condition and is therefore *not* a new gate; it is checked immediately before the generic one so that its sentence is the one a person sees, and both stay reachable because it fires only for a provider this app cannot meter. What it adds is the reason, and the reason is different in kind rather than in degree: a Claude run refused for no terminus still had three limits doing real work — the two window fractions read this account's own utilisation, and `maxRunCostUSD` reaches the cycle as `--max-budget-usd` — where for a provider whose usage this app cannot read, the fractions measure a population that run is not in and no in-cycle ceiling is handed to anything. Telling that operator only "nothing would ever end it" leaves them believing the percentages they set were a safety net. Constraint C2 in `proposals/ProviderFallback/01-constraints.md`, and the whole point of choosing the provider at a form rather than at a wall is that this refusal lands where somebody is watching. It is deliberately not enforced in `normalizePolicy`, which has no error channel, for the reason `no_terminus` is not.

**Only the 5-hour window can be waited out.** It is the sole quantity that refills on its own, on a schedule, with no configuration. The weekly window does not qualify: with `weeklyAnchor` unset (the default) `weekly.endsAt === now`, so there is no reset instant at all — the trailing total merely decays over days. `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume` and for nothing else, as a discriminated union so `resumeAt` is unreachable without narrowing. The check order — terminus, cycles, duration, run spend, weekly, *then* session — is load-bearing: a run that is out of time **and** out of window must end, not park, or the clock stops being a terminus. **And a window that cannot be read must not end that order early.** `no_ceiling` is the one verdict nothing acts on, so returning it where it is found disabled every guard below it: an install with a real 5-hour reading and no weekly one never reached the session check at all, and a `live-resume` run at 97% of a 50% 5-hour guard logged that the *weekly* guard could not be enforced and spawned the cycle anyway — with nothing catching it at the door either, since workflow members and chat approvals never pass `windowGuardRefusal`. The verdict is now **held** and returned only once every readable guard has passed, through a `??=` so the window checked first names the refusal, which is the precedence `windowGuardRefusal` already gives it. A park is decided about a guard that *was* read, so it has to have had its chance above before an unreadable one speaks. `evaluateInstanceBudget` has the same shape for the sharper version of the same reason: returning it where it is found switches the 5-hour guard off silently for every block of the instance.

**One guard can now be extended, by a bounded count, and nothing else about the terminus rule moves.** `maxIterations` and `maxDurationMinutes` are the only two monotone termini and `no_terminus` refuses a run with neither; the external validator (`validation.ts`, routed from `docs/agent/taskboard.md`) is the one thing in the app that can add to the first. It does it the way the context ceiling's refund does and for the same reason `MAX_EARLY_ENDS_PER_RUN` exists: `runs.validation_cycles` only ever increases, it is written straight to the row so a restart cannot reset it, and `maxValidationCycles` is its ceiling — floored at zero, and **the one budget-shaped field in `Settings` that may never be null**, because a limit that can be removed is a run nothing ends. A grant is permission to *ask* for another cycle and never permission to have one: `evaluateBudget` at the top of that cycle reads duration, run spend, both window fractions and the install's own daily ceiling exactly as it did, in the same order, so a run that is out of time or out of money still ends there. Zero is a real setting rather than an off switch with a different name — the task is still held open and the operator is still told why, which is the notify-only design the pitch recommends, arrived at through a number.

**`installSpend` reads a fifth place, and the reason it did not before stopped being true.** `run_reviews.cost_usd` was outside the install's rolling ceiling for as long as every row in that table was a person pressing something — a review and a merge-conflict resolution, one press each, with somebody watching what it produced. A **validation** is not: it fires whenever a run asks to close a task, which on a fleet is once per finished piece of work with nobody present. Left out, a ceiling that says "this install may spend $N a day" would not have counted the one spender the operator never triggered, and on a 20-block workflow that is twenty validations no instance budget bounds either. All three kinds are counted rather than validations alone, because what this reading *is* is money this app recorded spending inside the window, and a reviewed run's money is no less spent for having been asked for. Bounded on `COALESCE(finished_at, created_at)`, the shape a block already uses; there is no estimated half, unlike a run and unlike a chat turn, because a child killed before it reported leaves the row `failed` and this app prices nothing for it. The other half of the same problem is on the child rather than in the reading: `spawnAssist` now takes an optional `--max-budget-usd`, passed by the validator alone off `validationBudgetUSD` and by neither of the two a person starts, because `windowRefusal` is read once at the door and an automatic spender admitted at 99% of a window would otherwise have no ceiling at all.
