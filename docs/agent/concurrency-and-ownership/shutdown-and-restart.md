# What a shutdown accounts for, and what a restart closes out

[← concurrency-and-ownership index](../concurrency-and-ownership.md)

Read before editing `shutdownRuns`, `killAllAgents`, `trackAssistChild`, `trackLand`, `reconcileInterruptedCycles` or `reconcileOnBoot` in `src/lib/orchestrator.ts`, the signal handler in `src/instrumentation.ts`, or `stop_grace_period` in `docker-compose.yml`. "This module" in the shutdown paragraph's last step is `serverLock.ts`, whose rules are in [server-lock.md](server-lock.md).

**A shutdown accounts for the cycles it kills, and it is the only reason the process lingers.** The handler was `killAllAgents(sig)`, `releaseDataDir()`, `process.exit(0)` — synchronous end to end — so not one suspended `startRun` frame resumed and nothing after `await runIteration(...)` ran. `reconcileKilledCycle` exists for exactly this and was reachable from that one place, so a routine `docker compose up --build` discarded every in-flight cycle's measured spend: invisible afterwards to `RunProgress.spentGuardUSD`, to `maxRunCostUSD` and to the instance budget, so a run picked up later overshoots its own cost limit by a whole cycle with nothing saying why. `shutdownRuns` is the replacement and its order is the whole of it. **Nothing new starts** — a `globalThis` flag `promoteQueued` reads, because a run settling during the wait reaches its `finally` and calls it, and which every door to a child that is not a work cycle reads too. `assistRefusal` refuses a review, a resolution, a validation and a chat turn with `SHUTDOWN_REFUSAL`, read after its transcript scan so no `await` separates the answer from a chat turn's or a validation's spawn. A review and a resolution still await after it, for the checkout and for a resolution its merge and conflict scan, so `spawnAssist` reads the flag again where nothing awaits before `spawn` and settles the row `failed` with the same sentence through `after`, which is where a resolution aborts its merge and discards its checkout; refusing from `startAssist` instead would hand a caller mid-merge a reason and nothing to roll back with. The merge queue stops taking rows: `drainRepo` reads the flag before each one and leaves the rest `queued` for the boot to cancel, and `startWorker` starts no drain; `refusesEveryLaterResolution` still matches the sentence, as the belt. `landRun` reads it twice, after `landState` so the operator's check is not started in a process that is exiting, and again where nothing awaits before the `git merge`, so no merge begins during the grace; both refuse with the operator's checkout untouched. A block's turn is left `waiting` at `advanceInstance`'s claim, as a full process budget leaves it, and `startBlockTurn` writes off as `blocked` one claimed before a shutdown that began during its scans. A door that skips the flag, or reads it with an `await` still to come before its spawn, still hands the final sweep its child, since `trackAssistChild` registers every one, but the ladder below reaches only the children alive at the signal: one spawned during the grace gets no `SIGINT`, is not waited on, and leaves its row open for the boot, billed for up to the whole grace for nothing. **Every `running` row is interrupted rather than merely signalled**, through the same single kill path an operator's Stop uses: that is what buys the `SIGINT` first, which is the difference between the cycle's cost being measured and being estimated; it is what stops the loop spawning the *next* cycle now that the process lingers; and it gives the run an ending that names the shutdown instead of `Claude Code exited with code -1`. Every `running` row and not only the ones holding a child, because a run in its pre-cycle scan has nothing to signal and is about to spawn. **Interrupting a row does not decide its ending, so the flag is the loop's to write.** A loop suspended at a cycle boundary does not end on the interrupt: the verdict wait returns early and the loop takes the ending its cycle earned, DONE or the cycle cap, and one in its pre-cycle scan can meet a guard's refusal before its next interrupt check. `shutdownRuns` used to set `restart_closed` on every row it interrupted, so each of those kept the flag beside an ending of its own — measured 2026-10-05 at `50d60d8`, a run whose agent replied DONE during the verdict wait ended `completed`, flagged, counted by the notice and re-queued by its press under the pushback prompt: a billed agent told to keep working on a task it had finished. So `shutdownRuns` records only `restart_cut_cycle` up front, `applyInterrupt` notes when the ending it applies is the shutdown's, and the loop's terminal write sets `restart_closed` then and only then; a row whose loop never gets that far is still `running` for the boot, which flags it. The same ending is what blocks the runs waiting on it, ahead of the release pass its `finally` makes, with the sentence and for the reasons the boot blocks them (`dependencies.md`): an `on-finish` edge is satisfied by the shutdown's own `stopped` once a cycle has been counted, and measured 2026-10-06 at `0effa73` the pass queued the dependent mid-shutdown, the boot flagged it as a queued row, and the notice's one press reopened it beside the run it was ordered behind. An operator's Stop or a guard's interrupt that landed first wins as it always did, and its ending is not flagged either, since the run was not closed out by the restart. `restartClosedRuns` and `restartClosedCount` also read only `failed` and `stopped`, the two endings a restart writes, because the rows flagged the old way are still on every install that ran it. **The children that are not work cycles get the same ladder**: a review, a resolution, a validation, a chat turn and a block's turn are spawned `detached` exactly as a cycle is and no run's Stop reaches them, so `spawnAssist` and `runOrchestratorChild` hold each one in `trackAssistChild`'s set (its own `globalThis` key, read by nothing but the shutdown) from spawn to settle. The ones alive at the signal are waited on inside the same grace, and every one is in the final sweep. Before that, a server stopped from its terminal left them running and billed, with their rows closed by the next boot as if the child had gone. **The loops are given a bounded grace** (`SHUTDOWN_GRACE_MS`, ten seconds, one step past `interruptRun`'s own 8s `SIGKILL`), and what it waits for is each interrupted loop's own word that it has written the run's ending, not a reading of the row. The post-cycle UPDATE clears `active_started_at` a transcript read before the status and the stop reason land, and a run caught in its pre-cycle scan never set the column at all, so a wait that ended on no child and no open cycle measured as `npm run dev` exiting with the row still `running` and no stop reason, for the next boot to fail. Each `startRun` loop holds an entry on its own `globalThis` key from the line before its `try` until its status write has landed or thrown, and only the loops this process is running are waited on, so a row left over from a crash cannot make every shutdown as slow as the worst one. **A land in flight at the signal is waited for in that same grace, and nothing signals it.** Its `git merge` is a plain `git()` child that no registry held, so the wait ended once the cycles had settled and a SIGTERM mid-merge exited under it: under Docker, PID 1's exit takes the merge down part-way and can leave `MERGE_HEAD` or `index.lock` in the operator's checkout, and the boot then failed the row as uncertain. `trackLand` (its own `globalThis` key, read by nothing but the shutdown) holds every `landRun` from its registration to its `finally`, and every merge-queue row from the moment `drainRepo` takes it to the status write that answers it. The row as well as the call, because a row is `landing` in `landState` before `landRun` is reached and `resolving` while its interrupted resolution settles and the drain's two-second poll catches up. So the row in flight ends in the ordinary way: a merge already running finishes and lands, a land that had not begun its merge is refused at `landRun`'s door, a resolution the ladder interrupts fails as it would for any other reason, and only a grace that runs out first leaves the row for `reconcileMergeQueueOnBoot`. **Sharing the grace is not a clock on the merge**, which `isolation-and-landing.md` forbids. That rule is against a timer on the landing path deciding a merge has gone on too long and killing or failing it, which reads as git refusing and rolls the operator's work back. The grace signals nothing and fails nothing: the process was exiting at the signal whatever the merge was doing, and the grace only makes that exit wait for the merge, up to the bound compose's `stop_grace_period` was already set against. An unbounded wait was rejected because it buys nothing under Docker, which `SIGKILL`s the container at `stop_grace_period` whatever this process is waiting for, and on a host it would hold a stop for as long as the operator's own check takes, the part of `landRun` before the merge, which can run for minutes. That check is the one child a land holds, and the final sweep ends it rather than leaving it behind: `runVerify` spawns it `detached`, as its own process group, and keeps it from spawn to exit in its own `globalThis` set, which `killAllAgents` reads beside the other two, so a check still running when the grace is spent is `SIGKILL`ed with everything it started; a delivery's check is in the same set, swept the same way, though nothing waits for a delivery. Before that set existed a host server stopped with `kill <pid>` left the check running with nothing bounding it, since its fifteen-minute timer had lived in the process that exited. It is not interrupted at the signal, which would end the shutdown sooner and merge nothing either way, since a check that passes meets `landRun`'s second read of the flag: one that finishes inside the grace leaves the land a true ending — its own failure, or that refusal naming the shutdown — where one killed at the signal would record a signal death as the reason. **Then whatever they did not finish is mopped up**: `reconcileInterruptedCycles` reads `active_started_at` — the column that made the cycle's own bound answerable from outside `startRun`'s frame — and its UPDATE is *relative* and guarded on that same column, so whichever of it and the loop's own post-cycle write lands second is a no-op rather than a second charge. The same statement charges the cycle to `iterations`, which the loop writes only once a cycle returns, so a cycle no loop came back for was billed and never counted against `maxIterations`; the loop's own write is absolute and its local already holds the cycle, so landing second it writes the same count. A cycle whose estimate cannot be recovered says so in the run's log, because an understated run and a run that spent nothing are otherwise identical on every page. **The handler's one line counts the cycles recovered by either path**: the loop's own `reconcileKilledCycle` inside the grace, which is the ordinary case and leaves the mop-up nothing to find, and the mop-up's. Counting the mop-up alone printed 0 beside a row carrying the recovered spend. The loops' counts are read before the mop-up starts, so no cycle is reported twice. `docker-compose.yml` sets `stop_grace_period: 30s`; Docker's default 10s would `SIGKILL` the server at the exact moment the last agent died. **None of it runs while Next's own handler is on**: `start-server.js`, which `server.js`, `next start` and `next dev`'s server all go through, calls `process.exit(0)` about 0.1s after the signal unless `NEXT_MANUAL_SIG_HANDLE` is set, which measured as a run left `running` with its cycle unreconciled and the lock behind. So the Dockerfile and both npm scripts set it; `next dev` also gets `NEXT_EXIT_TIMEOUT_MS`, because its parent `SIGKILL`s the server 100ms after forwarding the signal; `register()` deletes it from the environment every child copies; and the handler, now the only listener, ignores every signal after the first, where `once` had left the second to Node's default action and killed the shutdown with 143. What this deliberately does **not** touch is `reconcileOnBoot`'s rule that a restart never resumes anything — that pass still clears `active_iteration`/`active_started_at` for the endings no handler reaches, once it has run the same reconciliation over them (below), and a run stopped here is still picked up by a person. What changes is that they can be picked up *together*: `runs.restart_closed` is a flag rather than a reading of `stop_reason`, which is prose and the one thing here that must never become a parse, and it covers both endings a restart now produces — a run the handler stopped and a run the boot failed. The rows a restart leaves `waiting`, and the ones it writes `blocked` behind a run it closed out, are deliberately left out of it: the waiting ones were not closed out at all, so the flag, which means *closed out by a restart*, would be false for them, and the blocked ones would share the flagged run in front of them in the one-press pick-up, where an `on-finish` dependent reached first would run beside it rather than after it. Picking the run up is what brings the blocked ones back, through `reviveBlockedDependents`, except one that has been set aside. **And all of it is the owner's to do**, which `shutdownRuns` asks for itself, before the install-wide `SELECT`, rather than leaving to the handler that calls it: the handler is registered outside `instrumentation.ts`'s ownership branch, so a second process's ordinary exit — a `next dev` restart on a file change, in the very worktree workflow this module exists for — ran the whole reconciliation against the owner's database, logging a shutdown against live rows and firing the webhook for each, setting `restart_closed`, and clearing `active_started_at` on cycles whose agents were still billing. That last one is the one that fails **open**: `installBudget` and a workflow instance's budget both bound `telemetrySpendSince` below by that column, so a stray dev server widened two limits at once. `killAllAgents` stays unconditional and is the only part that may be — those children are this process's whatever the lock says — and it goes outright there, because the caller exits the moment the guard returns and a gentler signal has no grace left in which to be noticed.

**A restart must close out its own runs, except a recent pause.** `reconcileOnBoot()` (via `src/instrumentation.ts`) marks stale `running` rows failed and `queued` rows stopped. Without it one crash blocks a folder permanently. **Before it decides anything it reconciles the cycles a hard stop left open.** A `SIGKILL`, an OOM kill, a host that lost power, or a `stop_grace_period` that ran out before the mop-up leaves a `running` row with `active_started_at` set and the cycle's transcript on disk, and the boot used to null that pair first, which made the spend unrecoverable for good and left the cycle off the cap — measured 2026-10-05 at `50d60d8`: `iterations` 0 and `spent_usd_est` 0 on a row whose transcript the mop-up read as $0.18, and nothing on its log. So `reconcileOnBoot` is async for exactly one `await`, `reconcileInterruptedCycles("crash")`, ahead of everything else it does: the same estimate, the same `iterations` charge, and a log line saying the server stopped without shutting down cleanly. Nothing else needs the rows meanwhile — the same assumption every `await` already ahead of it in `register()` makes — and it puts nothing in the queue. It **never signals a pid**: the DB outlives the container, so a recorded pid names something else after a restart — plausibly this server. Queued rows are stopped rather than resumed, because auto-starting a days-old prompt as an unattended `acceptEdits` agent is the one thing a queue must not do by itself. A `paused` row within `settings.resumeGraceHours` (default 24) is the deliberate exception: it is not an unreviewed prompt but a run the operator started in a mode chosen precisely so it would carry on across windows, and the sweeper re-evaluates its budget from scratch before anything spawns. Past the grace period it is closed out like any other stale row — that boundary is what keeps the exception from becoming the rule it exempts. A `running` row stays `failed` even under `live-resume`: the child is gone with unknown state, and mapping that to `paused` would be guessing. A `waiting` row is decided after the rest, against what the boot did to the run it waits for, and the reasoning is in `dependencies.md`.
