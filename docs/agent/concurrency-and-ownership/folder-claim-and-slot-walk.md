# The folder claim, the slot walk and the worktree registry

[← concurrency-and-ownership index](../concurrency-and-ownership.md)

Read before editing `createRun`, `promoteQueued`, `selectPromotable`, `sweepPaused`, `allocateSlotPath`, `resolveIsolation`, `conflictKey` or `overlaps` in `src/lib/orchestrator.ts`, or `withRepoAdmin` in `src/lib/repoLock.ts`.

**One writing run per folder subtree, unless the run is isolated.** A **paused** run holds two claims and yields one of them. Its **worktree slot** is absolute — it resumes onto the same branch carrying its own commits, so `activeRuns()` still selects `('queued','running','paused')` and `allocateSlotPath` still skips it. Its **folder** is not: `selectPromotable` reserves for `running` rows only, so a run submitted afterwards takes the folder and works while the parked one waits. Nothing is in the directory twice, because the parked run cannot come back until the folder is free — `sweepPaused` refuses to un-park it while a run is in there, and says so in its stop reason rather than leaving "waiting for the next 5-hour window" standing after that window cleared. It stays `paused` while it waits, deliberately: `paused` is what `reconcileOnBoot`'s grace exception keys on, and joining the queue instead would make a restart close it out. The new-work hold keeps a due row `paused` on the same ground ([fleet-stop-hold-and-set-aside.md](../run-lifecycle/fleet-stop-hold-and-set-aside.md)). The cost is that a younger queued run can be promoted ahead of it in the ≤60s before the next sweep — accepted, because a parked run losing priority to work that is ready now is the point. `/api/folders` reports the two separately (`busyRunId` blocks, `parkedRunId` is a note), and a parked run has never consumed a concurrency slot. "Folder" means `(physical tree, path within it)` — `conflictKey()` — compared segment-wise and case-folded by `overlaps()`. Path equality is wrong three ways, all reachable from shipped config: the picker offers the mount root, which contains every folder under it; two mounts can be one host directory (compose defaults `UF_WORKSPACE_2..4` to `${UF_WORKSPACE}`); and macOS is case-insensitive. Mount identity is resolved once, at first use, because `/api/folders` annotates up to 400 folders per request and because a per-check `stat` that throws would fail **open**, permitting exactly the collision this prevents.

**The folder claim is a synchronous check-then-insert.** `createRun` runs from entry to INSERT with **no `await`**, so one event-loop turn covers deciding a folder is free and recording that it was taken. Adding a single `await` to that path silently reintroduces two agents in one directory; the `db().transaction()` wrapper does not save you, because better-sqlite3 is synchronous either way. Never key occupancy on `isRunning()` — `procs` is emptied at the end of every iteration, so it reads false while a running run sits in its pre-iteration scan.

**…so what that one turn is allowed to contain is bounded by a constant, not by a repository's history.** The same absence of an `await` that makes the claim atomic makes every subprocess inside it a hold on the loop that drains all the agents' stdout, feeds every SSE stream and beats the server lock's heartbeat — and the slot walk was bounded by nothing. Dirty checkouts are left behind deliberately (`allocateSlotPath`) and are never `taken`, so every admission re-ran `git status --porcelain` over every one of them, for ever: 64 of them at git's own 20-second ceiling in the limit, and hundreds of milliseconds each in the ordinary one, since this app clears `core.fsmonitor` on every call so there is no daemon to make that walk cheap. `MAX_SLOT_PROBES_PER_ADMISSION` is the bound and it is four checkouts — nine git subprocesses with the repository's own `--git-common-dir` asked once, on top of `probeIsolation`'s four, while a run with isolation off asks only `probeIsolation`'s first, `rev-parse --show-toplevel`, for repository spend's sake — and the walk is ordered cheapest-question-first so the budget is only ever spent on a slot nothing else could settle: one an active run holds comes from SQLite, one an earlier admission found unusable comes from a `globalThis`-pinned memo, and one that is not on disk yet is settled by a `stat`, since a directory that does not exist cannot be dirty and cannot belong to another repository. The memo holds **negative verdicts only**, and that asymmetry is its whole safety argument: acting on a stale *dirty* reading costs a slot number, where acting on a stale *clean* one hands a run a checkout `ensureWorktree` then refuses by name — so a slot is only ever returned after this admission has seen it clean for itself. It expires after five minutes because an operator can clean a checkout up by hand, and the two buttons that do it from inside this app (`commitPending`, `purgeBranch`) say so directly through `forgetSlotVerdict` rather than leaving that window to be waited out. Past the budget the walk still returns a slot number nothing has ever used, which is free by construction, and gives up rather than returning one it has not seen clean — giving up being a **refusal**: `resolveIsolation` throws `slotExhaustionRefusal`, and it does not degrade to `mode: "none"`, because isolation being *used up* is the one downgrade that was never an answer (`docs/agent/isolation-and-landing.md` argues the split between unavailable and used up). The thrown sentence names "the ones this admission looked at" as their own cause, because claiming to have checked all 64 would be a sentence it cannot stand behind. That is reachable only on a store where all 64 slots exist *and* more than four of the low ones are unusable, and it clears itself: each admission's budget is spent learning about four slots the next one then skips for nothing, so a store with eight dirty slots refuses two runs and then settles. **A second thing now runs inside that same turn, and it is bounded on these grounds rather than on its own.** `createRun` generates the run's file price list before the INSERT — a `readdirSync` walk of the folder and one SQLite aggregate over `run_events` — synchronous like everything else on that path, with no `await` to offer and none introduced. The walk stops at `MAX_WALK_ENTRIES`, because a mount pointed at something enormous has to cost a truncated list rather than a stalled server, and the read-count query is memoised per folder for a minute on `globalThis`, since a ranking over thirty days of history is no worse for being sixty seconds old. Every failure inside it degrades to `""`: this is the one door every run in this app comes through, and a run refused because a cost hint could not be built would be that hint costing infinitely more than it saves.

**A repository's worktree registry is a third claim, and it is the one that waits.** The folder claim above is about a directory an agent writes in; `land.ts`'s `landing` set is about the operator's own checkout; `withRepoAdmin` (`repoLock.ts`) is about `$GIT_DIR/worktrees`, which every checkout in a repository shares. Four callers mutate it and none knew about the others: `ensureWorktree` prunes it at the start of every isolated run, `resolveCheckout` removes a slot and prunes before adding one, and `deleteBranch` and `purgeBranch` remove a slot and delete a ref. **`git worktree prune` is why it has to exist** — it is the one operation here that is repository-wide rather than scoped to a named entry, so it is the one git's own per-entry locking does not serialise for us. Three things about its shape are decisions rather than details. **It waits rather than refusing**, which is the opposite of `landing`, and it follows from who takes it: the run loop is one of the four, and a refusal there would fail a run start because somebody pressed Delete — where a land takes minutes and "another branch is being landed into this folder" is the honest answer. **The sections are short**: the registry read and the removals are inside, `worktree add` and the seeding copy after it are deliberately outside, because an add on a large repository is minutes and serialising it would make concurrent run starts in one repository sequential for no registry reason. **The read that decides is inside the claim that acts** — `worktreeHolding` is called within the bracket in both deletion doors, since a slot read outside it is a slot another caller may since have taken or freed, which is the folder claim's own check-then-act rule one level down. The queue chains on **both** settlements: a section that threw must not wedge the key, because a wedged key is every isolated run in that repository never starting again, which is worse than not having the claim at all. Never take it from inside a section that already holds it for the same repository — every call site is a leaf that runs git and nothing that re-enters. `commitPending` takes neither this nor `landing` and needs neither: it writes into the run's own checkout and touches no registry. What it does take is the claim on that checkout in `checkoutClaim.ts`, shared with a conflict resolution being set up, and that one refuses rather than waits, as `landing` does: each holder is answered with a sentence naming the other, and `isolation-and-landing/conflicts-and-resolution.md` has why the two may not overlap. **None of this is evidence of a collision** — `proposals/GapRegister/`'s B1 ranks that row on blast radius and records that none was ever reproduced; what this closes is the app-level interleaving, which is the half this repository owns. A fourth, `holdSlot` in `orchestrator.ts`, keeps a terminal run's slot out of `allocateSlotPath` while a land's or a delivery's verify command runs in it; `isolation-and-landing/land-verify-and-deliver.md` has why.
