# Workflows, orchestrator blocks, merge blocks and schedules

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/workflows.ts, schedules.ts, canvasGraph.ts.**

**A workflow is the third thing here that is form input, and it is not the fourth route to `--permission-mode`.** `workflows` holds a name, a graph and one budget for the whole instance (below); a node in it holds the *work* — mount, folder, task, an optional prompt override — and names a **template** for every guard and for the model, or names none and takes `settings.chatDefaultGuards`, which is a guard set and holds no model, so a node under it names none. That is `planProposal`'s rule reused rather than restated, and `planNode` is deliberately shaped like it, down to refusing a node whose template has been deleted **by name** instead of falling back to the untemplated set: the operator saved a graph that said "under these guards". There is no `permission_mode` column, no budget blob and no model on a **node**, so the three narrowings stay three and the two routes to that flag stay two — and "no model on a node" now reads as one more thing a node names its template for, rather than as an absence with nowhere to come from — the instance budget is on the workflow rather than on a node precisely because it bounds the graph and not a block, and it holds none of those three. Prompt text is the one exception and the same one a proposal makes — `promptOverride` replaces the template's standing instructions for one node, joined to the task by the *same* `composeTask`, so how the two halves are ordered and marked has one definition. The mount and folder are on the node rather than inherited from its template, which is where this *diverges* from a proposal: a proposal is approved minutes after it is written, where a workflow is saved once and run for months, and a template edited in between would silently move a node's run to another repository with nothing in the graph changing. **The agent is on the node for that same reason and is deliberately not inherited either**, which is the one place a workflow block and the run form read a template differently: the form applies one as a seed for every field, where a node reads one for exactly three things — its guards, through `guardsFor`; the standing instructions `promptOverride` replaces; and, since `run_templates` grew one, the model. `run_templates.agent_id` therefore decides nothing about a block, and `guardsFor` still returns three fields, which is the absence this whole design rests on — the model is passed beside its return rather than added to it, precisely so that a guard helper stays a guard helper. The model joins the inherited list on the ground that keeps the agent off it: it moves cost and never capability, and a node has no model of its own for it to override, where a node names its own agent. It is an **id** rather than a copy, `run_templates`' rule and the opposite of `runs.agent`'s: a graph is applied again and again, so an operator who fixes their reviewer's prompt expects the next press of Run to use the fixed one, and the copy is taken where it always is, by `createRun`, so an agent deleted between two blocks of one instance cannot reach a run already started. It carries no capability — an agent holds no tool list and no permission mode — so this is not a fifth route to `--permission-mode`; and it is refused **by name** at save, at `/api/workflows/validate` and at instantiation, through the same `agentRefusal` the run door and the template door use, never falling back to none. Which child it names differs by kind and the field does not: a run block's own run, an orchestrator block's *deciding turn* (the runs that block emits name their own, per spec — the opposite way round from `promptOverride`, which it holds on behalf of those runs, because standing instructions are what a run is asked and the deciding turn is asked by `blockSystemPrompt`), and a merge block **none**, where one is refused rather than dropped: that block spawns no child at all, so there is nothing for the named agent to *be* — accepting it would be this app quietly discarding a choice the operator made, at the one door built to end exactly that. Everything else follows `run_templates` — no folder claim, no concurrency slot, invisible to `activeRuns()`, and deleting one cannot reach a run that has already started. A node's `kind` is the one thing that changes what it *becomes* rather than what it says: `run` is a fixed run and the default, because every graph saved before this existed says nothing there and the other reading would turn one of them into a graph that starts agents nobody wrote. `orchestrator` is the other, and it adds exactly one field a node may hold — `fanOut`, which is not nullable — and no route to a guard; see the orchestrator-block invariant below.

**A `taskId` on an emitted spec is not a sixth field on the list `emit_runs` refuses to grow, and it is not on the node at all.** A spec may carry the board id of the task the run is for; it sets no guard, picks no folder, does not change the brief and does not name who the run is, so it is nowhere near the line the five fields above are drawn against — and it moves nothing on the board either, since an emitted run neither claims its task nor closes it when it ends. `docs/agent/taskboard.md` holds that rule. It is on the **spec** rather than on the node for the reason the task text and the folder are: a saved graph is a shape a person agreed to, and which backlog item a particular pass is working is a decision the turn makes when it gets there, not a value frozen into the graph months earlier. An id that is not on the board refuses the **whole** emission by name, on `planEmission`'s all-or-nothing rule and `agentRefusal`'s wording — through `taskRefusal`, so a block and a chat turn word it the same. `EmissionLimits` takes the board as a function rather than as data, unlike `agents` beside it, because the registry is curated where the backlog is not; the taskboard doc has the sizing argument.

**A workflow is instantiated in topological order, in one synchronous pass, all or nothing.** `topologicalOrder` — in `orchestrator.ts`, beside `dependencyCycle`, because a saved graph, an orchestrator block's emitted specs and a batch of approved chat proposals all create runs in one pass and all need one answer to "every one after what it waits for" — is pure and unit-tested because both ways of being wrong are silent: a node released before its dependencies exist is a `createRun` whose `dependsOn` names rows that are not there, and an unplaceable node is a row that sits `waiting` for ever — `releasableRuns` reaches a fixed point and leaves it alone, which is the one outcome the dependency design has none of. Ties break on the node's declaration order, so two presses of Run on one graph produce the same queue; runs are admitted oldest-first and a queued run reserves its folder against everything younger, so an unstable order would silently reorder work on one repository. The pass itself has no `await` between the `createRun` calls, for the reason the chat's approval route batches: the folder claim is only atomic inside one event-loop turn. Everything checkable is checked *before* anything is created — the graph against the templates and mounts that exist now, `resolveWorkspaceFolder` for every node, and every node's guards — so a mid-pass failure should be unreachable; if one happens the created runs are **stopped** (never deleted: one may already hold a checkout and a child, and the row is what the kill path and `reconcileOnBoot` need) and the instance is recorded `failed` with the reason. Half a graph is not a smaller workflow. Re-running while a previous instance still has live runs is refused with a count rather than left to chance: the second instance points the same nodes at the same folders, and a node continuing a branch would be refused mid-pass because the first instance's run already continues it. `normalizeWorkflowInput` refuses the same things at *save* that instantiation does — the `normalizeTemplateInput` rule, because a graph that can be saved and never started fails weeks away from the form that caused it — and it takes the templates, mounts and default isolation as an argument rather than reading them, which is what makes it pure and what makes "saved, then no longer startable" a sentence instead of a surprise. `folderRefusal` is the one check that is *not* in it, because it is a syscall; it runs beside it at both moments.

**A workflow is drawn on a canvas, and where a block sits is not part of it.** The obvious home for a coordinate is `WorkflowNode`, and it is wrong twice over: `normalizeWorkflowInput` rebuilds each node from a fixed list of fields, so an `x`/`y` would be dropped in passing and the drag would silently not persist; and let through, it would make moving a block two inches a rewrite of the object `topologicalOrder` reads, bumping `updated_at` and landing in the blob an instance copies. So the graph is untouched and a position is a *view* of it — held per browser under `uf.workflow-layout.<id>`, and reconciled by `resolveLayout` against an arrangement `autoLayout` derives from the edges. That derivation is what makes "a graph saved before the canvas opens readable" true with **no migration at all**, which is the only way to be sure a layout change cannot lose an edge; the cost, stated rather than absorbed, is that a hand-made arrangement does not follow the operator to another browser. `autoLayout` is bounded rather than run to a fixed point because it has to be able to draw a **cycle**: refusing a loop is `normalizeWorkflowInput`'s decision and it can only answer about a graph it has been sent, so one is on screen between the second click and the answer, and an unbounded relaxation there is a frozen tab that typechecks. **Nothing in the browser decides what a workflow may be.** `POST /api/workflows/validate` calls the same `normalizeWorkflowInput` and the same `folderRefusal` the save route calls, with the same `currentKnowledge()`, and the editor renders the sentence it gets back — a second copy of those rules in the client would be a second set to keep in step, confidently wrong about what Save would do the day one of them changed. That route answers **200 for a refusal**, because a 400 is indistinguishable from the route being unreachable and the editor says different things in those two cases; Save stays enabled behind it for the same reason, since a disabled Save behind a failed advisory check strands the operator with no way to reach the authority at all. A drawn link carries `edge: ""` all the way onto the wire and is refused by name: `on-success` terminates a chain the operator meant to run regardless and `on-finish` starts a run on top of a dependency that crashed, so the picker offers the unanswered state as a real option rather than pre-selecting one. Adding a block, linking two and removing a link each have a keyboard route as well as a pointer one, and `handledByPointer` is what keeps them from both firing — a captured pointer sequence still dispatches a trailing `click`, which would otherwise add a second block or disarm a link that had just been drawn; the `click` handler stays because it is also what a screen reader dispatches, with no pointer events in front of it. There is no canvas library: the drag is `setPointerCapture` and the edges are cubics in an SVG overlay, about 4 kB over the form this replaced. **The surface is a framed pane and the selection is a halo, never a border.** The frame is a toolbar strip (the palette, and the block and link counts), a recessed scroll region standing on a faint `dot-grid`, and a footer naming the gestures — the grid is the only cue that an arrangement is somebody's rather than the app's. Replacing a card's border on selection is what this had before and it cost the one thing that border is for: an orchestrator block wears the warn edge permanently *because* it starts runs with no approval, and painting it accent at the moment somebody selected it withdrew that statement exactly when it was being read. A ring is outside the box and sets a different property, so both facts are on screen and neither class string can outrank the other. **Delete removes the selection, and there is no undo.** The surface handles it for whatever the inspector is showing; a block's name and a link's condition chip handle it for their own identity and stop it there, so the *focused* thing wins over the *selected* one on the rare occasion Tab has moved them apart. `preventDefault` on that key is load-bearing rather than tidy — Backspace outside a text field is the browser's own Back on more than one engine, and losing the whole draft to it is worse than anything this key is for. A ⌘Z was considered and rejected: this app has no undo model, and one that put a block back without its links, or without the position it was dragged to, is worse than the absence because the operator stops checking. What stands in for it is that nothing on the canvas is saved until Save. **And because nothing is saved until Save, no exit may take the graph without asking.** `draftSignature` in `canvasGraph.ts` is what decides there is anything to lose: the body a save would send, against the signature taken when the page mounted rather than against a re-derivation of the saved workflow, so a graph opened for editing and not touched is never dirty. It reads `draftToGraph`'s output rather than the drafts behind it, so a fan-out typed into a block that is not an orchestrator raises nothing — a dialog over a page with nothing to lose is how an operator learns to dismiss the next one unread. The layout is deliberately outside it, for this file's neighbour's reason: `writeLayout` has already persisted the arrangement per browser, so a dragged box survives the tab that a typed task does not. `beforeunload` covers exactly one exit — the closed tab, the reload, the typed URL — and the other four are client-side navigations it never fires on. `exitHref` in `unsavedWork.ts` decides which clicks are one of those, and the editor stops them in the **capture** phase with `stopPropagation` as well as `preventDefault`, because `next/link` navigates from a React handler at the root container that reads neither the default nor who prevented it. ⌘ 1…⌘ 9 and quick open are `router.push` calls in the shell with no event to stop, so they ask `leaving()` instead, against the single guard `registerLeaveGuard` holds — and its disposer clears only its own registration, because a route change runs the leaving page's cleanup after the arriving page's setup. Browser Back is the one exit left uncovered, and it is stated rather than absorbed: intercepting `popstate` means pushing a sentinel entry nobody made and re-pushing it against the router's own restore, which corrupts the history stack in exchange for a dialog, and the graph is one Forward away. **The inspector is a sticky column beside the canvas, not a form under it**, and every block states in one sentence what a press of Run is approved against — which template supplies its guards or that it takes the untemplated set from Settings, where it runs, which saved agent its child is started as, how many runs a deciding block may start with nobody looking, and whether a merge block may pay to reconcile a conflict. `BlockStatement` is that sentence and it is prose on purpose: those five facts were five separate pickers to read off, and the card the operator approves against has to say them rather than imply them. The agent is stated *outside* the guard clause and its picker sits outside the guards group, because an agent bounds nothing — a phrase inside "under …" would claim it does — and the picker declares the ambient set beside itself for the reason the run form's does: the registry is a part of the set and not the whole of it.

**A workflow instance is halted through one door, and the door is closed before anything is signalled.** `stopInstance` is that door: an operator's control and a tripped instance guard both call it and differ *only* in the recorded cause, because a second implementation of "which members does this take down" is a second chance to miss one, and a missed member goes on spending under a page that says the workflow is stopped. The instance is marked `stopping` by an UPDATE guarded on `status='started'` — the closed door and the idempotence in one statement, a second stop changing no rows rather than running a second kill ladder over children that are already dying — and from there to the last member there is **no `await`**, the property `createRun`'s folder claim already documents for the same reason. Every kind of member is covered at once and each keeps the machinery it already had: `running`, `queued` and `paused` go through `stopRun` and its existing branches, so there is still exactly one way to signal a child and the `SIGINT`-first ladder still buys a cycle the chance to report its own cost; a `waiting` member is written `blocked` — what this app already writes for a run refused before its first work cycle, and the true thing to say, which also keeps it out of `REOPENABLE`, since picking one link of a halted chain back up would start it on work that never happened; a member already terminal is **left alone**, because a `completed` row rewritten as stopped destroys the record of work that landed and nothing on the page afterwards says it happened; and a node whose `createRun` never ran is not a member at all, so it is never created. `haltPlan` is that whole decision, pure and unit-tested, for the reason `releasableRuns` and `landRefusal` are. **Waiting members are blocked before any other member is touched**, because stopping a run releases its dependents and a dependent released a moment before the halt reached it would be admitted, promoted and spawned — a member starting *because* the workflow was stopped. Stopping a queued member can still promote another queued member inside the same turn; that is harmless and deliberately not designed around, since `stopRun` re-reads the row and `startRun`'s pre-spawn checkpoint sees the interrupt before any child is spawned, costing a transcript scan rather than a billed cycle. The halt never removes a checkout, never touches a branch and never commits: uncommitted work stays in its slot with its own branch checked out, where `slotIsDirty` keeps the next run out and `commitRefusal` — which already settled whose work is in a slot — still decides whether it may be committed. Queued `merge_queue` rows for those runs are cancelled and one in flight is left to finish, exactly as `cancelBatch` has it. The instance records that it was stopped, by what and when, and the member's own reason distinguishes the three endings on sight: halted with its workflow, halted by that workflow's budget guard, or stopped on its own run page (`stopRun`'s unchanged default). `stopped` is **derived** rather than stored — `stopping` plus no live member — because a signalled child takes seconds to die and nothing would run a second pass after a restart; `reconcileHaltsOnBoot` exists only for the crash *inside* the walk, where `reconcileOnBoot`'s deliberate exception for a recently `paused` row would otherwise leave the sweeper to re-queue a member of a stopped workflow. A halt is terminal: there is no pause and resume for an instance — **and no way back in through a member either**. `reopenRun` refuses a run whose instance is `stopping`, naming the workflow, and `reviveBlockedDependents` leaves those runs out of its candidate set; `haltedWorkflowOf` is the one condition both read, so a run refused on its own page cannot be woken from the page in front of it, and it tests `stopping` alone because that is the only stored value — `stopped` is the same row read later. `reviveBlockedBlocks` is the third reader and the one that does **not** share it, deliberately: it walks the ledger rather than the runs, and it asks the positive question — is this instance still `started` — because the row it would rewrite is also what `startWorkflow`'s own rollback writes onto a `failed` instance, and reviving one of those would restart half a graph that was deliberately never built. Stricter than "not halted", which is the direction that costs nothing. Neither the status nor `REOPENABLE` is the gate any more: a halted `waiting` member is `blocked` with no `work_dir`, which is exactly the shape `reopenRun`'s `waitingAgain` branch accepts and exactly the row the revive selects, so without the membership condition **Try again** — or reopening the stopped run in front of it — put agents back to work under an instance the page reads as "Stopped", with the instance guard unable to stop them because it acts only on a `started` one. `RunDTO.haltedWorkflow` carries the same answer to the run page, which declines to offer the button rather than let the operator find out by pressing it. **Orchestrator blocks go first, before any member is touched**, and that is the waiting-member rule sharpened: a block does not merely get *released* by a stop, it creates runs, so one left `thinking` while the walk ran could emit into a workflow being taken down and every run it started would be a member the halt had already walked past. A `waiting` block becomes `blocked` and a `thinking` one `failed` — that turn was billed, and saying it never ran would hide the spend already on its row — both written before the child is signalled, so the guarded UPDATEs in `emitBlockRuns` and `settleBlock` refuse whatever the dying turn still tries to do.

**Four of an instance's six readings are derived, and `started` is not a word for a press of Run that is over.** `workflow_instances.status` records what has been *done to* an instance — rolled back at creation, or a halt closing its door — and never what its members have got to, which is a fact about the runs and the ledger. Nothing would write that second fact: no pass runs when the last member settles, and after a restart nothing would run one at all, which is the reason `stopped` was derived before this and the same reason `finished` and `blocked` are now. So `instanceStatus` is the whole decision, pure and unit-tested for `haltPlan`'s reason, over one tally taken across **both** halves of the graph — `stopping`/`stopped` are one halted row either side of its last live member, and `started`/`finished`/`blocked` are one unhalted row: still working, reached its end, or had part of it written off because something in front of it satisfied nothing. A halt outranks the members, because what ended a press of Run is the headline and a member says the rest on its own row; and `finished` is a claim about the *graph* rather than the work, since how a member ended is on the member's own row and a word here that said otherwise would report a failed run as work that landed. None of it is stored, so every query that reads the column is untouched — `advanceInstances`' own SQL, `fleet.ts`'s `startedInstances`, `guardInstance`, `bootBlockPlan`'s input, `haltedWorkflowOf`. What is **not** untouched is every site that acts on the object: each tested `status === "started"` when that was the only word for an unhalted row, and each would silently close a door that is open the moment two more words exist — so they ask `instanceIsOpen` instead, named once rather than repeated. `settleBlock` is the sharp one and the reason this is a rule rather than a tidy-up: the UPDATE that settles a block runs immediately before it, so if that block was the last live member the instance reads `finished` on the very next line, and a test for `started` there would drop the runs the turn had just decided on — a fan-out billed for and never started, with the block's own row saying it emitted them. A stop is the one place the new words are genuinely *reachable*, and `haltPlan` already had the answer: an instance with nothing live falls through to "every block has already finished", which is the true thing to say and the thing a status-shaped test would have replaced with "already stopping".

**A workflow instance carries its own budget, and it is checked between blocks rather than during one.** `run_templates` bounds one block; ten blocks under a $5 block limit is a $50 workflow, and `InstanceBudgetPolicy` — `maxInstanceCostUSD` plus the two window fractions, all nullable, `null`/`""`/`0` all meaning off — is what bounds the graph. It goes through `evaluateInstanceBudget`, which is the *same* `BudgetVerdict`, the same `BudgetStopCode` vocabulary and the same `readWindowGuard` reading as `evaluateBudget`, because an instance limit with its own words for "no ceiling configured" would be a second set of budget rules to keep in step. `readWindowGuard` is that shared half and it exists to make one thing unmissable: `fraction` answers "is there a reading at all" and `guardFraction` answers "is it past the threshold". Those are **different fields for different reasons** — `fraction` is what `windows.ts` fills from the provider's own percentage when `planUsage.ts` answered, so a window can carry a perfectly good reading with nothing typed into Settings and refusing it as `no_ceiling` would disable the guard on a stock install, while `guardFraction` is what charges an unpriced model the fallback rate so the guard does not quietly stop existing the week a new model ships — and, on a window the provider answered for, what takes the worst of that percentage and the derived reading, so a cached figure cannot authorise every cycle started inside one refresh interval. Both are null together, by construction in `buildWindow` and again in `makeWindow`. What it does **not** share with `evaluateBudget` is that function's body, for two reasons that are the whole design: an instance needs **no monotone terminus** — the run loop requires one because the loop manufactures its own next unit of work, where an instance is a finite graph created in one pass whose members each already carry a terminus, so all three limits are legally null together and the `no_terminus` refusal has no analogue — and an instance **never parks**, because parking is a decision about a run that yields its folder and keeps its checkout for the same conversation, and an instance holds neither. Enforcement is **between nodes**, and at two kinds of boundary rather than one. `enforceInstanceBudget` is called from `startRun`'s pre-cycle guard off the snapshot that check has just read; `enforceInstanceBudgetAfterMember` is called from `startRun`'s `finally`, once the status write has put that member's spend on its row. The second is what makes the limit reachable at all: every other call site in this app is "before something spends", and a block with `maxIterations: 1` — `normalizePolicy`'s answer when a template says nothing — reaches the pre-cycle guard exactly once, before its only cycle, while the pass that would have seen that cycle's cost is refused on `iterations` and `break`s out *ahead* of the instance check. So a graph of single-cycle blocks released together compared its limit with zero once per member and never again. It is fired-and-forgotten rather than awaited, because `releaseDependents` and `promoteQueued` are synchronous by requirement and a transcript scan in front of them would break the folder claim's one-event-loop-turn atomicity; nothing escapes by going first, since a member promoted in the meantime meets the pre-cycle check before any child is spawned. An orchestrator block is the third boundary — `enforceInstanceBudgetForBlock`, same door, same verdict vocabulary, called from `startBlockTurn` before the child is spawned. Without it a graph of nothing but deciding blocks would carry a workflow-wide limit that never fires, since nothing in it ever reaches a *cycle* boundary. There is deliberately **no live mode**, and the copy on the editor and the instance page says so in words: `liveGuardTick` reads one run's policy against that run's own progress and every code on `LIVE_ENFORCEABLE_CODES` is a fact about a run, so extending it would kill every member mid-cycle and turn each one's measured `result` cost into a reconciled estimate, for a bound that is already one cycle in the ordinary case. The cost of not doing it is stated rather than absorbed — a block already working carries on until it or another block reaches a boundary, so the total can overshoot by up to one work cycle per block running at the time, and concurrency multiplies it. What used to be the limiting case, a graph whose blocks all start at once with one cycle each, is what the post-member boundary exists for: it had no boundary between its blocks at all and the guard never fired, where now the first block to finish is one. Both the editor and the README say so. `settings.maxConcurrentRuns` is what bounds that multiplier, and what that lever is and is not has to be read exactly: it bounds a **count of cycles in flight**, so it bounds `N × one cycle` and nothing more, and it was only ever a bound on *money* because `buildArgs` carries `--max-budget-usd` and bounds the one cycle inside the CLI — before that, a cap on N bounded N × unbounded, which is unbounded. The two are one guard read together, and the same sentence holds one level down for `maxConcurrentAssists`: it bounds how many turns exist, where `settings.chatTurnBudgetUSD` inside the CLI is what bounds each. A tripped verdict calls `stopInstance` with `{ kind: "guard" }` rather than re-deciding which members to take down, and `startRun`'s pre-spawn checkpoint picks up the resulting interrupt like any other. `INSTANCE_ENFORCEABLE_CODES` is the whitelist, and it is `LIVE_ENFORCEABLE_CODES`'s reasoning applied to the one code that is about configuration rather than spending: `no_ceiling` is refused **at the door** by `startWorkflow`, which has an error channel, and is deliberately not acted on afterwards. On a stock install the reading behind `fraction` is the provider's own percentage, discarded after an hour without a fresh answer, so halting on its absence would turn an unreachable Anthropic host into every fraction-guarded workflow stopped and every one of their blocks killed mid-cycle. It is not ignored either — the run whose check found it logs that the guard had nothing to read, the same answer this app already gives a live spending limit whose telemetry never arrived. **And because nothing acts on it, `evaluateInstanceBudget` holds it rather than returning it where it is found**: returning on the first unreadable window ended the check order early, so an instance with a real 5-hour reading and no weekly one had its 5-hour guard switched off silently for every block. The verdict is returned only once every readable guard has passed, `??=` keeping the weekly wording in front — `evaluateBudget`'s shape one level down, and the same argument.
**The instance total is a fourth reading, and the door telemetry reaches it through is the same one, widened by one caller.** `instanceSpend` returns two figures and never one. `spentUSD` is the sum of the members' `runs.spent_usd` — a floor, since a cycle in flight has emitted no `result` and contributes zero for its whole duration — and is what the instance page draws as the meter's solid fill. `spentGuardUSD` adds each member's `spent_usd_est` and, for `running` members only, `telemetrySpendSince(runId, active_started_at)`; it is what `evaluateInstanceBudget` compares, and it is drawn as the hatched band past the fill, the same rendering an unpriced model's gap already gets. It never reaches `runs.spent_usd`, `buildSnapshot()` or any dashboard meter, and it is not a fifth cost source. The telemetry door was "one run, its own current cycle, its own live guard"; it is now also "each member, its own current cycle, the instance guard" — same function, same per-run and per-cycle bound, same `*Guard*` destination, and that widening is written down here rather than absorbed. `runs.active_started_at` is what made it readable from outside `startRun`'s frame: the other half of the fact `active_iteration` already carries, stamped and cleared in exactly the three places that column is, and read only for a `running` row for the reason `fmtCycleInFlight` refuses it on any other status. Both figures also carry what this instance's **orchestrator blocks** spent deciding, out of `workflow_instance_blocks.cost_usd`. That is not a fifth source and not a widening of the telemetry door: it is the CLI's own `total_cost_usd` for a turn that ended, the same authority `runs.spent_usd` has, so it is measured rather than estimated and belongs in the display figure as well as the guard's. It never touches `runs.spent_usd`, `buildSnapshot()` or a dashboard meter — the split that matters is display-versus-guard, and this is neither side of it, it is simply money the press of Run spent that no member run's row records. Where a figure has no denominator — no `maxInstanceCostUSD` — the meter is the hatched indeterminate bar, never an empty one: an instance whose share of a limit is unknown and one that has spent nothing must not look alike.

**A person sets an instance budget, and there is nothing on the wire that could.** It lives on the saved workflow, is normalized by `normalizeInstanceBudget` (total and idempotent, `normalizePolicy`'s rules), and is **copied onto the instance** at `startWorkflow` — the treatment the graph blob already gets, so editing the workflow cannot move the guard under a graph already running. `POST /api/workflows/[id]/run` still reads no body, there is no override argument on `startWorkflow`, and no route writes `workflow_instances.instance_budget`, which is the strongest form of "an orchestrator block must not raise its own instance's budget": there is nothing to raise it with. The route's one new job is to `await currentSnapshot()` and hand it over, because `startWorkflow` must stay synchronous from its first `createRun` to its last and the door check needs a real reading — a fraction guard with no ceiling behind it, or a window already past the guard, is a 400 with a sentence rather than a graph that halts before its first block does anything. `normalizeWorkflowInput` deliberately does **not** refuse the missing ceiling at *save*, the one place it departs from its own "refuse at save what instantiation refuses" rule: a ceiling is a Settings value that can be typed at any moment, so such a graph is not unstartable, only unstartable today. The editor warns beside the field.

**A block can decide what runs next, and those runs start with no approval — because the approval moved to the graph rather than disappearing.** An orchestrator block is a node whose `kind` is `orchestrator`, holding a brief, a folder, an optional template and a **fan-out cap**; when the workflow reaches it the server spawns one headless turn through `runOrchestratorChild`, and the specs it emits become runs that enter the queue. No `chat_proposals` row, no card, nothing between the decision and the spawn. What makes that defensible is not the block, it is the four things a person fixed when they saved the graph, and every one of them is unreachable from anything the model emits. **Guards** come from the block's named template or from `settings.chatDefaultGuards` — `planProposal`'s rule reused a third time, through the shared `guardsFor`, and `planEmittedRun` has no branch that reads a budget, a permission mode or an isolation choice off a spec, for the reason `reopenRun` refuses to become a third route to `--permission-mode`. **The folder** goes through `resolveWorkspaceFolder` against the block's *own* mount and no other, so containment is `resolveInMount`'s two checks unchanged. **The cap** is not nullable: `normalizeWorkflowInput` refuses an orchestrator block without one at *save*, which is the `no_terminus` rule applied where it bites hardest — this is the one block whose runs start with nobody looking, so a missing ceiling is an unbounded number of billed agents from one press of Run. And **`emit_runs` is a spec and nothing more** — a title, a task, a folder, an optional agent, and edges among the runs being emitted — with `/api/mcp` publishing it only to a `block` capability and `propose_run`/`save_template` only to a `chat` one, checked again in `callTool` because a tool absent from a list is not a tool absent from the wire. **The agent is the exception that is not one**: an emitted spec may name a saved agent for the run to be started as, and that is the same class of act as writing the task text beside it — an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so it decides *who* the run is and never what the run may do. It is named by **name**, because a name is what `blockSystemPrompt` showed the turn and an id is a thing only this app's own forms hold; `planEmission` refuses one this install does not have, beside the cap and the loop, before anything is created, and stores the registry's own spelling so what reaches `--agent` is what the operator saved — and a name is also literally what that flag takes, so a misspelling this refusal let through would be a run that fails at the spawn rather than one that quietly starts as nobody. The block's *own* deciding turn is started as the agent the node names, refused by name before it spawns rather than dropped. The block's own spend lands in `workflow_instance_blocks.cost_usd`, never in `runs.spent_usd` and never in a meter, bounded by `settings.chatTurnBudgetUSD` inside the CLI exactly as a chat turn's is; it *is* added to the instance's own total, in both figures, because it is measured money this press of Run spent and a graph with several deciding blocks would otherwise understate itself against the one limit meant to bound the whole thing.

**And what the turn said is kept, in three fields that are three voices.** A block that starts nothing blocks every node behind it, so it ends the graph — and the row that says so used to carry a status, a count of zero and nothing else, which is one appearance for three different endings: it decided there was nothing worth doing, this app refused what it asked for, or it never reached a decision. `reply` is the model's own account, which its system prompt asks for in as many words and which was read off stdout and dropped; `notes` is *this app's* — an `emit_runs` refused by `planEmission`, a tool call the CLI declined, the instance guard `startBlockTurn` could not read — appended as each happens, because they arrive from three places across a turn and an operator reading them for a cause needs all of them rather than the last; `error` stays the turn failing and nothing else. `blockSettlement` is that decision, pure and unit-tested for `mergeBlockOutcome`'s reason one level over: every way of being wrong here typechecks and looks identical on the page. It is also why `settleBlock` reads the row before it writes — the flat `error=?` it used to run wiped the guard note on every turn that did not itself fail. `decided` is `emitted_specs IS NOT NULL` and is on the DTO for the one distinction the count cannot make: `[]` is a turn that called the tool and named nothing, null is a turn that never called it. Every emitted run is a `workflow_instance_runs` row, so the instance budget guard, `stopInstance` and the second-press refusal all cover it with no new code.

**A block can land what the blocks in front of it built, and every protection that made `land.ts` safe stays where it is.** A merge block is a node whose `kind` is `merge`: no agent, no task, no template, no mount and no folder — it holds a strategy and one switch. When the instance reaches it, the runs its satisfied edges resolved to (the same `dependsOn` a run block would have been created with, so an orchestrator block's fan-out is covered with no second reading of what it emitted) go through `mergeQueue.enqueue` and nothing else. That is the whole design: one merge in flight per repository, every item re-previewed against git at *its* turn, a conflict reconciled on the run's own branch in a throwaway checkout, and `landRefusal`'s requirement that the operator's checkout be clean *and* on the recorded target **not weakened** — a dirty tree halts that repository and the block says so, because landing onto the wrong branch is the one mistake here with no undo. The target is never named on the node, for `worktree_base_branch`'s reason: a run records where it branched from, and that is where it goes back to. `mergeAutoResolve` is the one thing it can spend, and it is on the saved graph rather than in settings for `merge_queue.auto_resolve`'s reason — configuration that can change under a graph already running is not authorisation — so `enforceInstanceBudgetForBlock` is consulted **only when it is on**, since halting a graph at a free step would leave work already paid for unlanded for a limit that block cannot move. `mergeBlockOutcome` is the verdict, pure and unit-tested for `landRefusal`'s reason one level up: it decides whether the blocks *behind* the merge start, and both readings are silent — a chain that landed cleanly stopping with nothing to do, or a follow-up run starting on a target that never received the work. Its load-bearing distinction is skipped-versus-failed: a branch with no commits and one already merged both leave the operator with what they asked for, where a predecessor that *should* have had a branch and has none is isolation having degraded at run time, which is the case where silence would leave someone believing work landed. A merge block reuses `BlockStatus` verbatim rather than adding `merging`/`landed` — `thinking` and `emitted` are what every liveness query, every halt and both boot reconcilers key on, and two more words would be five more places to remember, one of them a merge running under an instance the page says is stopped; the page says "merging" and "landed", the column says what the machinery reads. An edge *out* of one carries no run at all (it created none), so its condition is the whole of what it says: `on-success` waits for every branch to land, `on-finish` is satisfied by the block finishing either way, and `blocked` — it never ran — satisfies neither, which is `edgeSatisfied`'s rule for a run that did no cycle. Two things are refused at *save*, where there is a person: a merge block on either end of a `continueBranch` edge (it has no checkout, so it has no branch to hand over or carry on) and one with no predecessor that runs something whose guards isolate — the second being the `fanOut` rule applied where it bites, since the alternative is a block that reaches the front of the graph and can only report that it was pointless.

**Acyclicity stops being a property of who wrote the graph, so it is checked as a property of the data.** `createRun` mints a run's id after reading its edges, which is why nothing could point at it and why a cycle was impossible by construction. That still holds for each individual insert — but the graph being inserted is now one a **model** wrote, and a cyclic set of specs has no creation order at all, so the first one would be refused for naming a run that does not exist rather than for the loop it is part of. `planEmission` therefore runs `dependencyCycle` over the specs and names the loop before anything is created, `admitDependencies` re-runs it over the whole live graph at every one of those inserts, and a spec may only depend on its siblings in the same emission — an edge onto a run the block did not create is an edge into a graph it cannot see.

**A block that emits nothing blocks what is behind it, and that is a decision rather than a fallout.** `planInstanceStep` is `releasableRuns` for the half of a graph that is not runs yet, pure and unit-tested for the same two silent failures, and it reads `edgeSatisfied`'s rule one level up: a dependency that did no work satisfies nothing. A block behind a fan-out exists to review it, land it or follow it up; started with nothing in front of it, it spends a billed cycle finding that out, where `blocked` costs nothing and names the block that decided there was nothing to do. Nodes behind an orchestrator block are **not created** at `startWorkflow` — their edges would name runs a model has not decided on yet — so each holds a `waiting` row in `workflow_instance_blocks` instead, which costs nothing for the reason `waiting` costs nothing one level down: no folder, no checkout, no place in the queue. A node is created only once every edge into it is *satisfied* rather than merely resolvable, so its edges are recorded on a run `admitDependencies` then re-checks, and a node that becomes a run gives up its ledger row so it is never in both tables. The cascade is the same fixed point `releasableRuns` uses, so every link gets its own sentence naming the one in front of it. `advanceInstances` is called from `releaseDependents` — one place rather than the five call sites that would have to be kept in step — and it is synchronous end to end for `createRun`'s reason, with a guarded UPDATE claiming each turn so two overlapping passes cannot both spawn one. A restart closes out **every** unsettled block of an instance it left nothing alive in, not only the ones behind a turn in flight: `on-finish` is satisfied by a run that did a cycle and then died with the container, so a block left `waiting` would be released into an unattended agent hours after anyone asked for it — which is `reconcileOnBoot`'s rule for a queued run. **Unless a member survived that same boot**, and that is `reconcileOnBoot`'s own exception rather than a second one: a `paused` run inside `settings.resumeGraceHours` is kept, because it is a run the operator started in a mode chosen precisely so it would carry on across a restart. Every premise above fails for the blocks behind it — nothing they are waiting for was closed out, the sweeper *will* wake it, and the agent the next advance starts is the one already being paid for and waited on. Closing them out anyway wrote off the tail of a live graph, under a sentence claiming the run in front of them had been closed out by the restart while it was parked and about to resume. So the question is asked per instance: `bootBlockPlan` is that decision, pure and unit-tested for `haltPlan`'s reason, and it reads `LIVE_STATUSES` rather than testing for `paused`, so what survives is decided in one place. It tests `started` **positively** rather than merely excluding a halt: a `stopping` instance's blocks still come down whatever its members are doing, and a `failed` one is `startWorkflow`'s own rollback, which wrote every other block off in the same pass — reviving half of either is a graph nobody finished building, started again. Ordering is what makes the survivors readable rather than guessed at — `src/instrumentation.ts` runs `reconcileOnBoot` first — and a spared block is decided later by `planInstanceStep`, off what is true when the member settles.

**A schedule is the first thing here that starts an agent with no person present at all, and every property that makes that defensible is somewhere else.** The run form, the chat's approval route and a workflow's Run button all have somebody pressing something at the instant the spend begins. A schedule keeps the press and removes the person, so what bounds it has to be true *before* it fires — and none of it is new machinery, which is the point. **Guards** come from the block's template or from `settings.chatDefaultGuards`, because a schedule calls `startWorkflow` and nothing else: there is no field on the wire, no argument on `putSchedule` and no column on `workflow_schedules` that could reach `--permission-mode`, a budget or an isolation choice, which is the same "there is nothing to raise it *with*" that already keeps an orchestrator block out of its own instance's budget. **The instance budget guard and the instance stop** cover a scheduled instance exactly as they cover a clicked one, for the same reason — it is the same `startWorkflow`, the same copy of the guard taken at instantiation, the same `stopInstance`. And **a workflow whose instance budget sets nothing cannot be scheduled**: `scheduleRefusal` is checked at the door, where there is a person and an error channel, and again at every fire, because clearing that budget afterwards is one edit away and nothing about that edit knows a schedule exists. Refusing rather than warning is `normalizeWorkflowInput`'s rule for an orchestrator block's fan-out cap, reused one level up and for the identical reason: a banner is read once, when the schedule is created, and the spend it is about happens every hour for the next month. Any one of the three limits is enough, and it asks `instanceBudgetIsOff` rather than naming a cost limit, because the two window fractions are the ones that bound *repetition* — an instance that would start into an already-spent window is refused at `startWorkflow`'s own door.

**A missed window is not made up, an overlap is skipped rather than queued, and both are on the page.** `decideSchedule` is that whole decision — fire, skip, missed, idle, paused — pure and unit-tested, because both ways of being wrong are silent and each is expensive in the opposite direction: a window fired twice bills twice with nobody watching, and a schedule that never fires is bit-for-bit what a working one looks like between occurrences. `cursor_at` is the last occurrence *decided about* rather than the last one started, and `reconcileSchedulesOnBoot` moves it to the instant of the boot without firing anything — the queued-run rule and the queued-merge rule arrived at from a third direction, that a server coming back up must not start unattended agents because of something that should have happened hours ago. `FIRE_GRACE_MS` is therefore only ever a late *tick*: two minutes, far shorter than the shortest recurrence this app accepts, so it can never honour a window a later one has superseded. An overlap is decided here rather than left to `startWorkflow`'s existing refusal — which still stands behind it — and it is a **skip**, never a retry, because a queued press of Run is a press nobody is present for by the time it happens; the cursor moves past it and the next occurrence is the next chance. Consecutive identical outcomes collapse into `streak`/`streak_since`, keyed on `last_code` and never on `last_reason`, since the sentence carries a count that moves and a streak breaking on that would be the fifty identical rows again with a counter stuck at one.

**The zone is stored with the schedule, and an unknown one is refused rather than replaced.** The container runs in UTC and the operator does not, so a wall-clock recurrence read in the server's zone fires an hour out for half the year — the failure this app already solved once for calendar buckets, where `/api/usage?tz=` carries the browser's zone. `isTimeZone` is split out of `resolveTimeZone` precisely because the two callers want opposite things from an unknown name: a bucket falls back to the server's zone, since a day cut an hour out is a display error in front of the operator, where a schedule refuses, since an hour out is an hour out for months with nobody looking. `nextOccurrence` solves a local time with the two-pass offset solve `zonedMidnight` uses, and on a spring-forward day whose nominal time does not exist it lands an hour to one side — which is the answer a schedule wants: the day still gets exactly one occurrence, within an hour of the time asked for, strictly between its neighbours. Returning nothing would silently skip one day a year, which is again indistinguishable from working. `everyHours` is deliberately an *interval* off an anchor rather than a wall-clock time, so it is DST-immune by construction and the zone only affects how it is displayed. The surface is three plain choices and no cron expression: `0 0 * * 1` and `0 0 1 * *` differ by one character and by a factor of four in what they spend, and a raw expression would first have to earn `describeSchedule`'s ability to render itself back in words. The page states the next fire time as an **absolute instant** beside those words, because a schedule the operator cannot verify at a glance is a schedule they will not trust with an unattended agent.

**One timer per process, `globalThis`-pinned, lazily started and stopped.** `sweepPaused`'s shape, for `sweepPaused`'s reason: module state that is not pinned silently resets on every request in dev, and an install with no schedules must hold no interval at all. It is started from the boot hook, from `putSchedule` and from a resume, and it stops itself the moment no active schedule is left. `currentSnapshot()` — the expensive half — is read only on a tick that actually fires. The boot start is inside `claimDataDir`'s `owned` branch with every other reconciler, and that is not tidiness: two servers firing one schedule is one window pressed twice, and the row they both read says nothing about whose it is. The cursor advances *before* the snapshot is awaited, so a tick that overruns cannot decide one window twice; the cost is that a process dying between the two loses that window with nothing recorded, which is the safe direction and the same one the boot takes.

**A block can repeat itself, and it repeats by unrolling — the back edge is the thing that must not exist.** A loop block holds one task, a **pass cap** and an optional total spend cap, and the obvious implementation is an edge in `run_deps` pointing from a pass back to its own block. That edge is refused at admission, and the reason is the whole design: `releasableRuns` reaches a fixed point and leaves a cyclic set alone, so a loop in the run graph is precisely the row nothing ever wakes, which is why `dependencyCycle` exists. So the loop lives in the workflow layer and `run_deps` never learns about it — pass N+1 is a **fresh run** depending on pass N's, the run graph stays a DAG, and every rule written against one holds unchanged. It needs no schema of its own: the graph is a JSON blob and `emitted_by` already existed for an orchestrator block's runs, so the whole feature adds not one column. The next reader will reach for the back edge first; the comment on `planLoopPass` says so.

**A loop's exit conditions are four, and the first of them is what the agent said rather than what the row says.** `planLoopPass` is the whole decision, pure and unit-tested for `releasableRuns`' reason sharpened by what a pass costs — not a work cycle but a whole run, with its own cycles and its own spend. In order, and the order is load-bearing: an unsettled pass **waits**, because nothing can be read off a pass still working and unrolling ahead of it would put two runs on one predecessor's branch, which admission refuses — so the symptom would be a throw rather than a decision; a pass that created **no run at all** stops it, because the next would be created the same way and fail the same way, which is a hot loop rather than a retry; a run in the body that did **not complete** stops it, because a loop is not a retry mechanism and `MAX_TRANSIENT_RETRIES` and the refusal backoff already sit inside one run; **`runs.reported_done`** stops it, read instead of the status for the reason `reopenPrompt` reads it — `completed` is written both for the `DONE` reply *and* for a run that used up its cycle cap, and `maxIterations` defaults to 1, so a loop keyed on the status would stop after its first pass every time, which is a loop that does not loop. Then the two caps. A shell predicate as an exit test is deliberately **out of scope**: running one would be a fifth kind of child process, which `architecture.md` treats as a decision rather than a detail.

**A pass that reported it could not finish ends the loop, and the rung above it is why that works at all.** `needs-review` is in `TERMINAL_STATUSES`, so the first rung stops reading such a pass as still working — without that entry the block `wait`s for ever, holding everything behind it with nothing on any page to say why, which is the single most expensive way to get this change wrong. With it the third rung matches and the loop stops with *"…ended needs-review, so the loop stopped rather than repeating on top of it"*, which is exactly right: a loop is not a retry mechanism, and handing the next pass the same wall costs a whole run rather than a work cycle. Two notes on that stop, and both are deliberate. The `code` stays `"failed"` — `LoopStopCode` is branched on by callers, `advanceLoop` maps every `stop` to `settleLoop(…, "emitted", …)` whatever the code is, and the operator-facing sentence already names the status verbatim; it is the vocabulary rather than the behaviour, and a fifth code would go here if loops ever gain per-code copy. And the `reportedDone` rung below is now unreachable for such a pass, so a loop whose last pass did the work *and* asked for review reports the stop rather than the completion — the same precedence as the cycle-outcome ladder, for the same reason. **A `needs-review` member is settled, not written off**, so `memberTally` counts it as neither live nor blocked and the instance reads `finished`: `finished` is a claim about the **graph** rather than about the work, and `blocked` means part of the graph was written off because something in front satisfied nothing, which is not what happened here. `haltSteps` leaves such a row exactly as it is, through the same fall-through that spares a `completed` one — a record of a question that was asked is destroyed by a rewrite as surely as a record of work that landed.

**A loop's two caps are termini, not guards, and that is why they are allowed on a node at all.** A node holds no permission mode, no isolation choice, no model and no budget blob, and a loop does not change that: every pass takes its guards from the block's template or from `settings.chatDefaultGuards`, through the same `planNode` a run block uses. `maxPasses` and `maxLoopCostUSD` are the same kind of number `fanOut` already is — a bound on how many times a block *repeats*, which can only ever end the loop earlier. Neither can raise a run's budget, neither is reachable from anything a model emits, and neither widens the workflow-wide limit: `evaluateInstanceBudget` does not read them, and that guard still halts the whole instance at every member's cycle boundary whatever they say. The pass cap is **not nullable**, refused at save, for the reason `maxIterations` may only be null alongside `maxDurationMinutes` — a loop manufactures its own next unit of work, and nothing else here moves one way and keeps moving. The spend cap is nullable because the pass cap already terminates it, and `loopSpend` reads the **guard** figure rather than the floor, or a loop would take another pass on money it had already spent.

**A loop accumulates on one branch, so it is a chain, and it is unrolled lazily for exactly that reason.** Each pass carries on the previous pass's branch through the existing `run_deps.continue_branch` / `runs.continues_run` mechanism, so `landRefusal` offers one Land button owned by the last pass, `branchInventory` collapses the chain to one row, and nothing here is a second definition of what continuing a branch means. Pass N+1 is created only once pass N has **settled** — eager unrolling would be two runs continuing one predecessor, which admission refuses by name, and it would also have to be withdrawn whenever the loop turned out to be over. The cost of lazy is a gap: between a pass reaching a terminal status and the next being created there is no unsettled member on the ref at all, so `chainBlocker` reads the chain as finished. `loopStillRepeating` closes it — a `looping` ledger row is read straight off the tables by `land.ts`, which cannot import `workflows.ts` without closing a cycle through `mergeQueue.ts`, and refuses landing, deleting, purging and a paid conflict resolution by naming the block. A block *behind* a loop resolves to the last pass and no other: the passes are a chain, so waiting for it is waiting for all of them, and it is the only run a successor can continue.

**`looping` is the one exception to "a block adds no status", and it is an exception rather than a precedent.** `BlockStatus` is a lifecycle and a merge block reuses `thinking`/`emitted` verbatim precisely so that liveness, halts and boot reconciliation keep reading two words — the argument on `BlockStatus` itself, and it is the right one. A loop cannot: between passes it has no child in flight and is still not settled, so `thinking` would be a lie for the gap and `emitted` would release the block behind it into a branch the loop is still writing to. So it counts as live everywhere `thinking` does, and **every** site that docblock warns about names it: `memberTally`'s live count, `haltBlocks`' sweep, `reconcileBlocksOnBoot`, `loopVerdict`, and `land.ts`'s `loopStillRepeating`. A halt writes it `failed` rather than `blocked` — the passes it took were billed — and a restart closes it out for the queued-run reason, since another pass would be an unattended agent started hours after anyone asked for it; **unless a member of its instance survived that same boot**, which is the per-instance question `bootBlockPlan` already answers for the `waiting` blocks beside it, because the pass such a loop is on is the run `reconcileOnBoot` deliberately kept — nothing under it was closed out, and the pass the next advance starts is the one already being paid for. Its own `cost_usd` stays 0: a loop spawns nothing, and every pass's spend is on that pass's run row.
