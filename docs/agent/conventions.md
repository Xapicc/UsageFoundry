# Conventions and design language

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing any component in src/components/, any route handler, any CSS.**

## Conventions

- **Server-only vs client.** `src/lib/apiTypes.ts` holds the DTO mirror of the server types so client components never transitively import `node:fs`. `src/lib/format.ts` is likewise client-safe. Don't import `windows.ts`/`transcripts.ts` types into a `"use client"` file — add to `apiTypes.ts` instead.
- **Route handlers** that touch SQLite or the filesystem need `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`. Every existing data route has both.
- **Module state survives dev hot reload** via `globalThis` singletons: `__ufDb`, `__ufBus`, `__ufProcs`, `__ufInterrupts`, `__ufTranscriptCacheV2`. Those are examples rather than the roster — there are sixty-odd such keys and `grep -rn "globalThis as" src/` finds every one. New long-lived state must follow the same pattern or it silently resets on every request in dev. Take a **new** key whenever the shape at an old one changes rather than reusing it, which is what `__ufInterrupts` did to the former `__ufCancelled` (`orchestrator.ts:373`) and what `__ufTranscriptCacheV2` did to `__ufTranscriptCache` when each cache entry gained a second array: `??=` only initialises when the key is absent, so a pre-upgrade value survives the reload and every call on it throws.
- **Schema changes** go in `migrate()` in `db.ts` as idempotent `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements, or as an `addColumn` that reads the live schema — there is no migration framework, and `PRAGMA user_version` is a record rather than one: nothing keys a step on it. **A destructive change is the exception and it is one transaction.** `db.exec` maps to `sqlite3_exec`, which runs each statement in autocommit, so `relaxProposalTemplate`'s four statements used to commit independently — and a kill after the first left every proposal in `chat_proposals_old`, which no query here reads. The next boot then recreated `chat_proposals` empty from the same `CREATE TABLE IF NOT EXISTS` and the rebuild's own guard (`template_id` is already nullable, return) made the loss permanent: the guard that makes a migration idempotent is what stops it noticing a half-applied one. So the rebuild runs inside `db.transaction`, `recoverStrandedProposals` completes a leftover from a build that predates that (`INSERT OR IGNORE`, so a boot interrupted between the INSERT and the DROP is a no-op rather than a primary-key failure, and the index is recreated because the rename took it and the drop took it away), and any other `*_old` table is named on stdout and left alone — a table this build cannot read is not one it may drop, and refusing to boot over it would strand the whole install rather than one table. `SCHEMA_VERSION` records what a live-schema read cannot: that a *rebuild* completed, and that the file was last written by a newer build, which is what a rollback after a failed deploy produces. It is stamped after `migrate()` returns, so it means finished rather than started. Keying the ~50 `addColumn` calls on it would be fifty numbers or an ordering nobody can change, which is why those still read the schema. **And `migrate()` is gated on the data-directory claim**: `open()` runs on the first `db()` call in *any* process, which is how a second server — an agent's `next dev` pointed at the live database by an inherited `DATA_DIR` — was entitled to rebuild a table under the server that owns it. `heldByAnotherProcess()` is the synchronous half of `serverLock.ts` that answers it, and it reads an undecided lock as free. The exception is a file with no `settings` table: a process that owns nothing and finds no schema has nothing to destroy, and refusing there would leave it with no tables and every query throwing.
- **A Save stores only what differs from `DEFAULTS`, and that is a correctness decision rather than a size one.** `getSettings()` is `{...DEFAULTS, ...stored}` and the settings page PUTs the whole *effective* object, so writing it verbatim materialised all thirty-three keys into the blob the first time anybody pressed the button — and from that moment every `DEFAULT_*` in `settings.ts` was dead for that install. There is no versioning, no migration, and nothing surfaces the divergence: a shipped default and a running install disagree silently and permanently. Measured, not reasoned. `8651bcd` raised `maxConcurrentRuns` from `null` to 4 at 20:28 on 2026-08-14 to bound exactly the failure that happened two minutes later — sixteen concurrent runs meeting the provider's 5-hour wall inside a 44-second span, every one of them with its first cycle amputated — and the stored row carried an explicit `"maxConcurrentRuns": null` that put itself back over the 4 on every read, so the fix was never in force on the install it was written for. The four prompt strings are the same trap one door over, which is why `COMPLETION_NOTICE`, `SHARED_CHECKOUT_NOTICE` and `RESTART_KILLED_NOTICE` are generated in `orchestrator.ts` instead of living in `Settings`. **The trade is real and it is the one being chosen:** a value an operator set *to today's default* is now indistinguishable from one they never set, so a later change to that default moves it — which is precisely what lets a shipped number reach an existing install, and the effective object is identical either way until that day comes. If pinning ever needs to be sayable, the answer is a stored marker, never a return to writing the whole blob. The comparison is structural rather than `!==` because five keys hold an object or an array and every one of them arrives off the wire as a fresh instance, and it is not `JSON.stringify` because that is key-order sensitive and a reordered `chatDefaultGuards` would read as an edit and be stored forever — the original failure arriving through its own fix. `src/lib/settings.test.ts` asserts on the stored blob rather than the round trip, because a test that only checks `getSettings()` after `saveSettings()` passes either way, which is why this survived as long as it did. **The `beforeunload` guard over that page is registered only while `dirty` and torn down the moment it is not** (`src/app/settings/page.tsx:1703-1711`): a listener that outlives the dirty state prompts on a page with nothing on it, which teaches the operator to dismiss the dialog without reading it — and the next one they dismiss is the real one. `preventDefault()` **and** `returnValue`, because either alone is a silent no-op in a browser somebody uses, and neither can choose the wording. It does not fire on a **client-side** navigation and nothing here can without the shell holding this page's state; the per-field rails and the bar's own unsaved count are what stand in for that, and the gap is stated in the code rather than left to be rediscovered.
- **Pages are client components** that poll their API route (dashboard 120s, run detail 3s for the row while SSE carries the log). There is no server-side data fetching or React Server Component data layer. **A poll stands down when its subject can no longer move, and re-arming it is the half that has to be designed.** A terminal run cannot change on its own, so the run page's 3s interval is gated on the row being live — with three edges, of which two are relied on rather than hoped for: the first load sits *above* the gate, so opening a finished run still reads it; a run that finishes while the page is open flips the gate only *because* a poll said so, and the effect re-runs on that flip and loads once more before declining to re-arm, which is what catches a `finished_at`, a stop reason or a spend figure written between the two; and a run picked up from another tab arrives over SSE, which stays subscribed whatever the row says, so the first event after the poll has stood down re-runs the effect and the load it does sees the row running again. The runs list makes the same distinction between two clocks: a 1Hz tick runs only while something is actually counting down, and everything measuring an *age* — the restart notice's relative phrase — reads the instant the list was fetched, because those answers cannot change without the rows changing and were being recomputed for every row sixty times a minute. **The 24-hour bucket boundary is a third clock and the one to be careful with.** The poll buckets its rows against it and the older-runs fold asks the route for the settled runs from *before* it, so it must be one value read by both and never two readings of `Date.now()`: a few seconds between them leaves a run sitting on the boundary in neither list — which on that page is a run that has simply vanished — or in both, which is the duplication the bucket pass exists to prevent. It is advanced by the poll and **quantised to the minute** by `bucketBoundary`, and the fold's request is keyed on it, so the fold reloads when it steps rather than on every poll. Both halves of that are load-bearing: pinning it instead would drift, until a tab left open overnight files yesterday's runs under the last 24 hours, and leaving it at millisecond resolution makes every poll a second request for an answer that cannot have changed. The fold is otherwise **not** polled — a run that settled more than a day ago does not move on its own, and an operator picking one up comes back through the page's own reload.
- **A list route ships the list's own DTO, and both readers of a list move together.** `GET /api/runs` shipped every row's whole prompt (75% of a 696 KB payload) for a column clipped to 56 characters, plus the normalised budget and the run's frozen agent, neither of which anything on that page draws — 37 KB over a hundred rows, measured. It now answers `RunListItemDTO` with the prompt clipped at `MAX_LIST_PROMPT`; the run's own page asks the route that has the rest, which is one row rather than a hundred. `GET /api/workflows` did the same with every node's full graph — 29,106 bytes of a 30,290-byte answer for two workflows, the node bodies being task prompts — so a list could print `nodes.length`, and now sends `WorkflowListItemDTO` with a block count, computing to 471 bytes. A **second shape beside the full DTO rather than a weakened one**: the detail route, the editor and the duplicate route all need the graph, and it exists in one place so five routes cannot disagree. And quick open reads both of those lists, so a field dropped from one has to be dropped from its reader in the same change — `jsonRequest` is an unchecked cast, so removing it silently typechecks and throws on the first press of the shortcut. **A list that pages carries the page's own figures beside the rows**, which is why `/api/runs` answers a `RunListDTO` rather than a bare array: `total` is counted over every matching row rather than over what was sent, so a page can say what it is a slice of, and `offset`/`limit` are the *applied* ones after the clamp rather than the asked-for ones. A count that is itself truncated cannot say a run has fallen out of reach, which is exactly how a hundred-row ceiling stayed invisible for the first ninety-nine runs. **And a list route reads `offset`, `limit` and its own filters off `searchParams` rather than answering with its newest page and letting the reader narrow that** — `/api/runs` read none at all and answered with the hundred newest runs, so the page's status segments filtered *those*, and "show me the failed runs" got the failed runs among the hundred newest: the same shape of answer as the question, and wrong, and indistinguishable from right. It now reads `offset`, `limit`, `status`, `q` and `settledBefore` (`src/app/api/runs/route.ts:73-93`), which is the principle `/api/branches:19-23` already stated. Three parts of that are load-bearing and each fails silently. The narrowing happens **in the query**, never in the client over an already-capped page. An **unknown filter value is refused rather than dropped**, and which way to fall depends on what the parameter decides: `/api/knowledge/notes` falls back on an unknown `sort` because a sort is presentation, while an unknown `status` is a 400 (`route.ts:80-85`) because it decides *which rows exist*, and quietly answering "every run" to "show me the failed ones" is the miss that reads as an absence. And every value arriving off a query string can be missing, blank, a word or negative, so the reading is **pure and tested** — `normalizeRunListQuery` and `clampRunOffset` (`src/lib/orchestrator.ts:889, :923`) for the reason `selectBranchCandidates` is: a limit read as zero is a one-row page, an unescaped `%` or `_` in a task prompt matches rows that hold neither, an epoch of 0 taken as a real boundary hides every settled run, and each wrong answer is a list that looks like an answer. An offset past the end is **clamped, not refused** — that is what pressing Next on a list which shrank under you produces.
- **A control that narrows what is on screen narrows the *data*, never the way the data is drawn — and it says what it left out.** Three of these shipped together and they share one failure mode: a filter that hides a line is indistinguishable from a run that never wrote one. (1) **The log's filter takes the event's kind beside the rendered line** (`matchesLogFilter`, `src/lib/logLine.ts:690`), because `describeEvent` renders `tool_error` and `sandbox` as *system* rows — the tool voice is a chip and a muted line, which is what a call that **worked** looks like. Grouped on the rendered voice, "show me the tool calls" answers with every call except the ones that failed, and an operator reads that as nothing having failed: a filter's artefact presented as a fact about the run. `EVENT_GROUP` (`:654-673`) is a `Record` over the whole `RunEventDTO` kind union rather than a switch with a default, so a new kind is a compile error instead of an event that belongs to no group and vanishes from every narrowed view; `problem` is the one group keyed on the rendered **tone**, because a refusal, a tripped guard, a failed call and a parked status are four kinds and one question. (2) **The settings field search's corpus is the rendered page**, a walk over `[data-setting-name]` marks (`findFields`, `src/app/settings/page.tsx:195-222`), rebuilt on every keystroke *and* every edit because several descriptions interpolate the value beside them and some rows exist only while the switch above them is on. Not a declared index: that would duplicate sixty labels and their help text with nothing keeping the two in step, and a search naming a field the page no longer has is worse than no search — it sends the reader after a control that is not there and looks exactly like a search that works. (3) **Each of the three says what it narrowed and what it could not reach.** The header count becomes `n of m`, a capped result list states the count it dropped (`MAX_FIELD_HITS`, `:186`), and a filter over a *truncated* replay carries a warning hint naming the dropped-event count (`src/app/runs/[id]/page.tsx:1555-1560`, fed by the number the stream route now sends beside its sentence at `src/app/api/runs/[id]/stream/route.ts:141`) — because a filter that finds nothing in a knowingly incomplete log otherwise reads as proof of absence. And because a list is replaced **without anything moving focus**, each carries an `sr-only` `aria-live="polite"` count (`src/app/runs/page.tsx:1011-1015`, `src/app/runs/[id]/page.tsx:1597-1601`, `src/app/settings/page.tsx:2050-2054`); the runs history's says "searching" while a request is out, because a count that has not caught up yet reads as the answer.
- **Eighteen route answers go through `jsonMaybeGzipped` (`grep -rn 'jsonMaybeGzipped(' src/app/api`), and the streaming ones are excluded by name** — buffering a live log to compress it is a stall, and `/api/runs/[id]/stream` says so in its own comment rather than being merely absent. No `/api` response was compressed while HTML and JS from the same server were, and the cause is not obvious enough to rediscover: Next's `sendResponse` copies a route handler's headers through `appendHeader`, which stores every value as an array, so the raw response holds `content-type: ['application/json']` and `compression`'s filter asks `compressible()`, which returns false for anything that is not a string — every app-router handler in this version filtered out by a one-element array, reproduced against Next 15.5.23's own `sendResponse` and its own bundled `compression`. Four properties of the helper are decisions rather than defaults. The floor is 1400 bytes, one Ethernet segment: below it gzip buys no round trip while costing a threadpool hop and a `Vary` that splits a cache entry, and under ~250 bytes the answer comes back *larger* (measured: 169 → 178). It is async zlib and never `gzipSync`, because this process runs the fleet's guards on the same loop — `gzipSync` on the 8.8 MB graph body blocks it for 30.6 ms and fires zero timer callbacks while it does. `Vary` goes on **both** branches, since announcing it only when compressing is the version of the bug that survives testing. And the `Accept-Encoding` grammar is honoured rather than sniffed: `q=0` is a refusal, an explicit `gzip` outranks a `*`, and an absent header means the client never said and gets bytes it can certainly read. Measured on the running container: `/api/knowledge/graph` 8.8 MB → 488 KB, `/api/runs` 699 KB → 174 KB, `/api/branches` 255 KB → 76 KB, `/api/usage` 52 KB → 10 KB. A route that answers through it and needs a cache directive has to write one at the call site, because the helper knows nothing about caching and `jsonNoStore` is no longer in front of it.
- **A payload may carry a position into its own answer, and it is turned back into an id at the fetch boundary.** `GET /api/knowledge/graph` answered 9,864,990 bytes of which the edges were 9.39 MB, and eight of their ten fields were read by nothing — every use is `e.from` or `e.to`, and the canvas holds no edge reference at all. Links now travel as a pair of indices into the same answer's `nodes` (738,217 bytes, 92.5% off) and `expandGraph` resolves them to ids at the boundary the fetch lands on. **Ids past that point and never indices**, because every filter stage drops nodes and a stale index neither throws nor draws nothing: it draws a line between two notes that are not linked. The note view keeps the whole edge DTO, being a different route with different readers.
- **A run's page is a split view, and the pane shows one thing at a time.** The inspector on the right holds what the run *is* — state and the one control that acts on it, spend, work cycles, guards, telemetry, its checkout, its task — and is `lg:sticky` with its own scroll region, so it stays put while the pane scrolls. Column and row are placed explicitly rather than left to source order, because on a narrow window there is one column and the state is what the reader came for. The pane holds what the run *produced*, behind a `SegmentedControl`: log, report, changes, review, land. Three rules on it. **The log leads and nothing switches tabs on its own** — a run that finishes while you are reading one pane must not move you to another, which is the same reasoning that freezes the old log's open/closed state at the first status seen. **A tab is offered only when there is something behind it**, which is why `cycleOutputs` runs on the page rather than inside `RunOutput`: the bar has to know whether the agent said anything before it offers a Report tab, and two walks of the same event stream per paint is what the alternative costs. **Only the active tab is mounted**, so Files (labelled Changes until the touched/changed reconciliation landed under it) re-reads the repository each time it is opened — the same cost as loading the page, against four polling cards alive behind the one being looked at. The guard block draws each configured limit as a `Meter`, and the spend one keeps the display-versus-guard split the windows already make: `runs.spent_usd` is the solid fill and the killed-cycle estimate is the hatched band past it, never one summed fill, so the bar shows the threshold that will actually stop the run without presenting the estimate as a correction to what the CLI measured. The time bar reads `finished_at` where there is one, since the clock only ticks while a run can still move. On the runs list, the cycle in flight is a **column of its own** on the in-flight list and nowhere else, and `fmtCycleInFlight` is the only thing that decides it, wording included — for the reason that function documents, and separated from the completed count for the reason the wording says "in flight". That list's box is deliberately not a scroll container: the sticky header then pins to the content pane as the page scrolls, where a wrapper of its own would pin it to a box that never moves.
- **The chat's transcript says who is speaking with structure, never with colour.** The answer is the pane: plain prose at a readable measure with nothing drawn round it, because it is what the reader came for. The operator's own words are a bezelled block pulled right — the raised chip every secondary control here wears — and were an accent-tinted bubble, which is the web-chat idiom and which spent the app's one accent saying "a human typed this", a fact the position and the speaker label already carry. A `system` turn is this app speaking and keeps its own treatment, because a sentence about what the app did, rendered as though the model said it, is one the operator will later attribute to the wrong party. Proposals are rows of one grouped box and selection is a `--selection` wash rather than a border, since a row that gained a border would shift the two beside it; the action row puts the one default action at the right edge, where every `Sheet` here already puts it, and Select-all at the other end because it is not a decision about the work. Everything that makes a proposal card approvable is unchanged and must stay: the guard set spelled out (including the untemplated one), a rewritten prompt marked, the dependency order named, what the click starts counted in words, and the **explicit list of the ids the page displayed** on the wire. The composer is pinned to the foot of the pane and takes **⌘↩** as well as Enter — ⌘↩ is the chord the run form already commits with and the one the shell's keyboard layer deliberately binds to nothing; the `isComposing` guard is tested *after* it, because an IME composition can only be ended by a bare Enter. The waiting state stays legible frozen (`@layer base` flattens the spinner to a still, and the word and the clock beside it never moved), and it claims no progress it does not have: elapsed time is the only real measure of a turn.
- **The shell is a window, not a page.** `src/components/shell/` holds all of it — `AppShell` (the frame, and the app's one keyboard listener), `Sidebar`, `Toolbar`, `QuickOpen`, `panes.ts`, `shortcuts.ts` — and `layout.tsx` does nothing but the theme script, the skip link and `<AppShell>`. There is no centred column: the source list is fixed-width and full height, and the content pane owns its own scroll region, which is what makes a `sticky bottom-0` bar inside a page stick to the pane rather than to the document. A `fixed` bar is still positioned against the viewport and has to step around the sidebar itself — the branches page's selection bar does, with `left-[var(--sidebar-w)]`. `panes.ts` is the single list of destinations because four things read it: the source list draws them, the toolbar titles from them, ⌘1…⌘9 navigates to them and quick open searches them, and a pane added to one and missed in the others is a row you can reach and cannot get back from. Its `activePane` matches on a path *segment*, not a prefix — `startsWith("/runs")` is what the top nav did, and it also matches a future `/runsheet`. The toolbar's title and action are derived from the **route** rather than published by the page: the pages still carry their own `<h1>`, so the strip renders a plain `<div>` and not a second heading, and the action is only ever a *destination* — Start, Run, Approve and Land all need page state, and a toolbar button wired to one would be the shell reaching into a body it does not own.
- **A box inside the pane is never sized in viewport units, because the pane is not the viewport.** It is the window less the toolbar less the pane's own `pt-5`/`pb-12` less whatever heading the page puts above the box — so `62vh`, `68vh` and `calc(100dvh - var(--toolbar-h))` all named a box taller than the space it had, and every one of them hung past the bottom edge and gave the pane a scrollbar whose whole travel was empty: a screen-deep band under a 62vh log that the inspector beside it had already stretched the row past, a composer under the fold behind a thread that was scrolling itself. What replaces the figure is a mechanism rather than a better figure — `main`'s wrapper is a **flex column of `min-h-full`**, so `flex-1` means "fill what is left" and `min-h-full` rather than `h-full` keeps a page longer than the pane growing exactly as before. A box that fills that way must not also report its *content* as its intrinsic height, or the row is sized by the transcript instead of by the pane: the run log fills by being taken out of flow (`lg:absolute lg:inset-0` in a `relative` parent that has the height), which contributes nothing to the measurement. The fill is `lg:`-only on both split pages — stacked at one column there is a second column of content below the fold and the page is *meant* to scroll, so the box stays bounded there. `--pane-h` (`100dvh` less `--toolbar-actual`, which is the `max()` the toolbar and the sidebar's brand strip already compute inline) is for the one case a flex parent cannot reach: a `sticky` inspector's own cap. And a `sticky bottom-0` bar is never pushed *past* where it sits in flow, so the pane's `pb-12` stayed underneath it as a band of nothing — the three pane footers pair `-mb-12` with it exactly as they already pair `-mx-4` with `px-4`.
- **A table must not be the reason the pane scrolls sideways.** A truncating line is `white-space: nowrap`, so its min-content width is the whole sentence — a `max-w-[56ch]` cap on it is therefore a *floor* under the column, and the runs list stayed 916px wide however narrow the window got, scrolling sideways into empty canvas beside cards that had stopped at the pane's own edge. `w-full max-w-0` on the cell is what makes it the column that gives: zero as its max content contribution, 100% as its preference, so the fixed columns keep their widths and this one takes what is left, which is what the ellipsis was for. The `56ch` stays as an upper bound on a wide window. The list view is deliberately not wrapped in `overflow-x-auto` — that would pin its sticky header to a box that never scrolls — so the column that gives is the whole of what keeps that decision affordable. Below the mobile breakpoint the same cell **releases** the cap with a `max-md:max-w-none`, and it has to: there is no column left to give to there, so a zero max-width is a zero-width block with the task hanging out of it.
- **`Table`'s `stack` is the narrow-window answer, and the label on each `Td` is the other half of it.** `TableWrap`'s sideways scroll is right where a row is a set of readings a reader compares; it is not a presentation of a *record*. At 390px a run's status and its spend are never on screen together, and the row tint `Tr` exists for — the thing that holds a label and a figure on one line as the eye crosses — does not exist on touch at all. So `stack` makes the whole grid one block per row below `md`, `THead` takes the column heads off the screen, the hairline moves from the cells to the row, and each `Td` carries the `label` that names its own field. **The two are one decision and neither works alone**: with the heads gone, a table switched on without labels is a column of unnamed figures, which is worse than the scroll it replaced — which is exactly why this is opt-in per table rather than a change to what `Table` does everywhere. Twenty-two of the app's twenty-five carry it — count them with `grep -rn '<Table[ >]' src --include='*.tsx'`, which finds the kit's own test beside them and nothing else. The three that do not are still a list rather than a backlog: the settings page's **calibration suggestion table** (`Ceiling` / `Set now` / `Observed peak`, under *Where a ceiling can come from*) and `RunAgentCost` were out of the scope this landed under — the storage report this sentence used to name is no longer a table at all, it is a `ListGroup` of `ListRow`s, which is why the count is right and the name was not — and `/account`'s daily cost has **no `<thead>` at all**, so there is no column name for `THead` to take away and a date beside a dollar figure is already two short columns that fit — stacking it would spend two lines naming what a date and a dollar sign say on their own. That last one is the shape to check for before reaching for `stack`, rather than a table it was forgotten on. A cell left deliberately without a label is the headline the record is identified by (a status, a task, a branch), never a figure; `labelPlacement="above"` is for a value that is prose or a list, which in the right half of a 390px row is a four-word column. **The explicit ARIA roles are not decoration.** `display: block` strips a table element's implicit role in every engine, and the row and column relationships go with the layout — so `Table`/`THead`/`TBody`/`Tr`/`Td` state theirs whenever `stack` is on, and above the breakpoint each is exactly the role the element already had. The value is wrapped in a `block md:contents` span so the flex row has one item to place: several cells hold two children, and `contents` is what makes that wrapper generate no box at all in the flat table. Only `display` may be switched on it — an inherited property stated there would reach the children *through* `contents` and change the desktop.
- **A capped scroll region is released below the breakpoint, not kept.** `ListView`'s `capped` box pairs `max-h-80` with `overflow-auto` so the sticky head has a box to stick inside. Below `md` there is no head — `THead` hid it — and the rows are blocks, so what is left is a 320px nested scroller inside a scrolling pane with nothing pinned to the top of it: a trap on touch, where the only way past a list is through it. `max-md:max-h-none max-md:overflow-visible`, and it lives in `ListView` because it was written out by hand five times: three copies carried it, one box is uncapped and one is not a scroll container at all. Only the last of those is a difference anybody recorded a reason for — the missing cap, and the one sticky head drawn without its hairline, are open questions the typed `box` preserves rather than answers, which is the difference between a variant and a copy that drifted.
- **The collapse is a document state, and it is settled before the first paint.** The rail is 168px narrower than the list, so a state read after hydration would shove the whole content pane sideways one frame into every page load — a louder version of the flash the theme script exists to prevent, which is why it rides in the same script. `[data-sidebar="collapsed"]` on `:root` swaps `--sidebar-w` and hides the row labels (kept in the accessibility tree, since the glyph is then the only thing naming the destination), and that is the whole of what it changes. The attribute is the source of truth; React mirrors it so the toggle can announce `aria-expanded`, and `writeCollapsed` writes the attribute and `localStorage` together. Storage failing costs the next page load, not this one.
- **The shell is installable, and the toolbar knows it.** `src/app/manifest.ts` declares `display: "standalone"` with `window-controls-overlay` first in `display_override`, which is what makes a browser hand the whole title bar to the page and publish `env(titlebar-area-x/y/width/height)`. The toolbar's height is a *floor* — `max(--toolbar-h, env(titlebar-area-height, 0px))` — and its left padding steps around the traffic lights by however much the sidebar has not already absorbed; every one of those env values is zero in an ordinary tab, so nothing anywhere branches on which case it is in. - **Styling** is Tailwind v4, CSS-first — no `tailwind.config.js`, no CSS modules, no third-party component library. Primitives live in `src/components/ui/`. Four things in `src/app/globals.css` are load-bearing and were each arrived at by measurement, not preference:
  - **The `@layer theme, base, legacy, components, utilities` statement.** Layer precedence is declared, never inferred: `next dev` and `next build` emit the blocks in *different* orders, so an inferred order means the legacy sheet beats utilities in the browser and loses to them in the shipped image.

Do not put `font-size` back on `html`; it redefines `rem` and silently shrinks every spacing and type utility by 12.5%.

They change geometry and `color-scheme` and nothing else, and no component reads either as a variant.

- **Design language.** What the kit already decided, so a page does not decide it again differently.
  - **One thing leads on every screen, and elevation says which.** `Card`'s `emphasis` is the whole mechanism: `primary` (extra padding, `shadow-e2`) for the one card a page exists to show, `default` (`shadow-e1`) for everything the reader came for, `quiet` (flat) for a card that is scaffolding — a form section, a picker, a footnote table. More than one `primary` per screen means none of them is. Hierarchy is said with size, weight, elevation and whitespace; a second border or a colour is not a substitute for any of them.
  - **Grouping has a closed vocabulary, and it is seven things.** `docs/agent/ui-density-audit.md` settles it and carries the reasoning; this is the short form, because every feature that landed before it picked its own answer and the answers did not compose. Allowed: a **pane** (a row in `panes.ts` — the list is closed at eleven, because ⌘1…⌘9 is nine digits against eleven rows, so the last two already carry none, and four things read that file); a **sub-route** for a group that is both a screen's worth and used weekly or less; a **card**, for contents that answer one question a reader could ask out loud, capped at seven *as peers at one level*, at nine controls before it needs an inner `ListGroup`, and at **at most** one `primary` (a page may legitimately have none); a **`ListGroup` with a `label`**, for rows sharing a subject the card's title does not name — three to nine, more than nine is two, and fewer than three only where the *label* states something neither row does; a `ListGroup` *without* a label is a box rather than a group; a **`Disclosure`**, for evidence (a log, a diff, an older list, a preflight report) or a setting whose default is right for nearly everyone; a **`SegmentedControl` tab strip**, for two to five mutually exclusive views of one subject, one strip per page, and never as a way of moving between *subjects* — that is the sidebar's job; and a **`Sheet`**, for a decision that must be answered first or an action that is destructive, irreversible or handles a credential. Never used, each because a build run will reach for it: a twelfth pane; an accordion, meaning a *coordinated* set where opening one panel closes another — independent sibling `Disclosure`s are not one; a nested disclosure; a tab strip inside a tab; a **page-level drawer** (the sidebar's is the app's only one, and a second `<dialog>` in the top layer is a second focus trap competing for the same Esc); a tooltip carrying anything the reader needs (no touch equivalent — `Field`'s `hint` and `ListRow`'s `description` are where it goes); and any hover-reveal, since `ListRow` is deliberately inert. The order of moves matters as much as the set: **delete redundancy, then group, then reorder, then hide** — hiding is the last move and not the first, because a reader who cannot find a control concludes it does not exist. And a fact a decision is approved against is **never** folded however rare it is: `BlockStatement`'s sentence, the chat proposal card's facts and the run form's guard summary are all that kind of fact. **A *region* is not an eighth affordance and is not a group**: it is a heading over cards or blocks that are already peers, naming *why* they sit together, and it may hold one of them. Three surfaces landed one — the run inspector's, the dashboard's three cost sources, the editor's block groups — and all three obey the same two rules. It is a `<div>` with an `<h2>` in it and **never** a `<section>`, because `section + section { margin-top: 24px }` is still in the legacy layer and would push every region but the first down 24px, which reads as a spacing decision somebody made; `Card` records being bitten by the same rule. And **no figure, meter, badge, total or comparison is drawn at region level** — on the dashboard that is the never-sum rule made structural, so a card lands in the band whose source it reads and a total across a boundary is visibly wrong rather than merely undocumented. Two cards sit *above* every band, and that zone is closed at those two: the window card, which is the subject the bands are readings of, and `ContextControlAside`, which reads no cost source at all — it is the value of an intervention against a counterfactual. A card that reads one of the three sources may never go there, because a figure above the bands is a figure with no band saying where it came from. What keeps the second one safe next to money that *is* spend is on the card itself: `default` against the window card's `primary`, and a title that names an intervention rather than a cost. It carried a footnote saying it is added to nothing beside it; that line was removed by the operator in `6a78ef9`, restored by an agent in `78c87fa` on the strength of this sentence, and removed again with it. **Two removals is a decision about copy, not a defect to fix** — a pass that finds the footnote missing has found what was intended. Its four-figure derivation stays in a band below, **one block per span the tile prints** — it leads with a total rather than a window, and a headline whose arithmetic is nowhere on the page is what that band exists to prevent. That second card carries **two** mechanisms and is therefore titled for neither: winnow's intake filter, which rewrites a request on its way out, and the pruner, which edits the transcript between work cycles. A label has to cover what the figure under it contains, so a card holding both is titled for the subject both belong to — and the two figures **are** summed there, which is the one place in the app they may be: they overlap by construction, the overstatement is measured at 4.06% and carried by `docs/verification.md` and `contextTokens` (`contextPruning.ts`) rather than by the tile, and each span still carries the filter's share of itself, because an operator deciding whether to leave *either* on needs the halves. The overlap is documented and the sum is deliberate; naming it on the card is the copy decision above, and it went the other way. The card leads with the **week**, the span an allowance is measured in, then the 5-hour window, then the all-time total. Adding a third mechanism to that tile means renaming it and measuring its overlap with the other two, not appending a row.
  - **`ceiling`, `guard` and `limit` are three different words for three different things, and the app says which.** A **ceiling** is a number set in Settings that a window percentage is measured against — Anthropic publishes none, so it is the operator's estimate, and it is never a cap on one run. A **guard** is a threshold on a window (5-hour or weekly) that steps a run aside or ends it; it is a percentage, never dollars and never minutes. A **limit** is a cap on one unit of work — this run, this chat turn, this workflow, this install: work cycles, spend, time. The three are already distinct in the code — `sessionCostLimit` is a ceiling, `maxSessionFraction` is a guard, `maxRunCostUSD` is a limit — and the copy has drifted across them exactly once per surface, which is how "no 5-hour ceiling is set, so this guard has nothing to measure against" reads correctly on one line and "each cycle carries what is left of it as a ceiling" reads wrongly on another. Keep the three apart in new copy; a sentence that needs two of them is usually saying something true about both.
  - **The palette and the type scale are AppKit's, not the web's.** Surfaces are four steps rather than three: `--bg` is the window, `--bg-raised` a card or a sheet, `--bg-inset` a *recess* into one (a field, a meter track, a log), and `--bg-grouped` a grouped list inside a card. The last one moves in opposite directions per scheme — AppKit lightens a grouped row against a dark window and darkens it against a light one — so one hex pair cannot express it and `light-dark()` is what carries the difference; it is also why a bezeled control is `--bezel` and never `--bg-inset`, which is the recess a text field sits in and reads as the same object at a glance. `--border` is a hairline at AppKit weight, far lighter than the box border it replaced, and `--shadow-e1` is now barely more than a seam, so a `default` card reads as a grouped box separated by its hairline rather than a card floating off the page. Body is 13px on the SF stack (`-apple-system` first, so macOS resolves SF rather than whatever `system-ui` has been remapped to), and `--text-sm` is 13px as well, deliberately: AppKit sets a control's own text at body size, and the two names stay apart so a call site still says which of the two it meant and the body step can move again without dragging every control with it. Nothing shouts — `CardTitle` and `Th` are sentence case at a weight step, never uppercase with tracking, and the legacy `th` rule matches them.
  - **There is one accent, and two different things are measured against it.** `--accent` is the *text* blue and clears 4.5:1 as text on `--bg` and `--bg-raised` in both schemes. `--tint`/`--tint-fg` is the fill-and-label pair a filled control wears, and in dark it is a different, deeper blue, because no single one does both jobs — `#4a9bff` carries white at 2.8:1. Where the browser exposes the operator's own accent, `--tint`/`--tint-fg` and everything mixed from `--accent-source` (the ring, the selection wash) switch to it; it is taken as a **pair**, because `AccentColorText` is specified as the colour of text placed on `AccentColor` and that is the only thing keeping a Graphite or Yellow accent legible under its own label. `--accent` is deliberately left alone — nothing guarantees an arbitrary accent reads as body text on a card. The `@supports` test names the whole `color-mix(in oklab, AccentColor …)` expression rather than the keyword alone: the two features shipped years apart, and a browser with one and not the other would leave `--ring` invalid at computed-value time, which is a focus ring in `currentColor` — visible, wrong and silent. `Highlight`/`HighlightText` was the other candidate and is rejected: engines return the selection *wash* there rather than the accent, and a white label on a pale wash is the failure this split exists to prevent.
  - **One focus treatment, stated in one place.** `@layer base` draws `outline: 2px solid var(--ring)` at 2px offset on everything focusable, and the legacy sheet no longer sets `outline: none` on `input:focus` — that suppression is what made a *second* treatment necessary, and it is why a button and the input beside it used to wear different rings. `--shadow-focus` is gone with it; a second way of saying this is how the two drifted apart. A component may override the ring's **colour** and nothing else, which is how `Button` keeps `--ring-danger` on the one control that cannot be undone, and why no component in the kit states an outline width or offset.
  - **Tokens.** Colour and type as above, plus: `--motion-fast|base|slow` (120/180/240ms — a control answering the pointer, something arriving or leaving, something travelling a distance) and `--ease-standard`/`--ease-entrance`; `--control-h` (32px, the floor for anything clickable) and `--control-h-lg` (36px, a button or a text input), stated as `min-h-[var(…)]` so a control keeps its box when its content changes; `--ring`/`--ring-danger` (the focus halo, at 45%) and `--shadow-press` (inset, so a pressed control recesses without moving); `--selection`, the accent wash behind selected text, at an alpha low enough that `--fg` keeps its own contrast whatever accent it turns out to be; `--ok-line`/`--warn-line`/`--danger-line`/`--accent-line`, each tone at 40%, for an *edge* that has to say which tone without outshouting the text it annotates — full strength stays for a conditional warning, the tint is for anything permanently on screen; `--fill-hover`/`--fill-active`, a neutral wash at 8% and 14% of `--fg`, translucent rather than a hex pair because it lands on three different surfaces and has to darken a light one and lighten a dark one — every opaque token in the palette is within 2% of `--bg-inset` in light mode and reads as no change at all. The shell adds three of its own: `--sidebar-w` (14rem, swapped for `--sidebar-w-rail` at 3.5rem by `[data-sidebar="collapsed"]`) and `--toolbar-h` (52px, a floor rather than a height — see the shell notes below). `--canvas-dot` is the workflow canvas's ground, and it is a token rather than the `color-mix` written into the utility that reads it: Lightning CSS emits a fallback declaration for a `color-mix` it cannot resolve, and that fallback is the *first operand at full strength* — a grid of solid `--fg` dots on any browser without it. Behind a `var()` it gets the `@supports` pair every other translucent token here gets. Nine named utilities (`grep -c '^@utility' src/app/globals.css`): `hatched`, `mono`, `ui-transition`, `skeleton`, `sheet-enter`, `drawer-enter`, `dot-grid`, and `app-drag`/`app-no-drag` for Window Controls Overlay — named rather than written as arbitrary values because the property is `-webkit-app-region`, which has no unprefixed spelling that ships anywhere.
  - **Motion is explanation.** `ui-transition` is the one transition an interactive surface wears; it deliberately omits `transform` and `width`, because a control must not move or resize between its states. Nothing loops except `Spinner` and `skeleton`, both of which stay legible frozen — `@layer base` flattens every duration under `prefers-reduced-motion`, and that blanket is not to be defeated with a `!important` or a JS-driven animation.
  - **`SegmentedControl` is how a short, fixed set of choices is offered, and `Icon` is the app's only glyph set.** The control is a radiogroup with a roving tabindex — one tab stop for the whole thing, arrows moving *and* selecting, focus following selection back so the next arrow press announces the right option. Both states carry a border and the same font weight, because a chip that gained either on selection would shift every segment beside it. `Icon` draws every glyph in a 16×16 box and sets the stroke attributes on the `<svg>`, so nothing can arrive a half-weight heavier than its neighbour; a glyph that is genuinely a filled shape cancels the stroke locally. Icons are decorative by default and only take a `title` where the glyph is the whole message — an icon announced beside the label it duplicates is noise. The set covers the eleven panes — the count the same closed vocabulary states above — plus disclosure, status and appearance, and the shell's own two (`sidebar`, `search`); a new destination needs a glyph here before it needs a row in `panes.ts`.
  - **`Sheet` is a native `<dialog>`, and that is a correctness decision.** `showModal()` gives the top layer, the inert background, the focus trap and Esc-to-dismiss from the browser; a hand-rolled overlay would be a hand-rolled focus trap, which is the part that silently stops working the day someone adds a control to the footer. Three rules follow from using the element rather than imitating it: it is always rendered and never conditionally mounted, because mounting in the same commit that calls `showModal()` is a race; nothing sets `display` on it, because a `display` utility outranks the UA's `dialog:not([open]) { display: none }` and leaves a closed sheet lying across the page; and `cancel` is prevented so Esc goes through `onDismiss` and React's `open` stays the single source of truth. It takes **one** default action and Cancel, and a `danger` sheet opens with Cancel focused — `showModal` would otherwise land on the first focusable thing, and one Return on a destructive confirmation is not a confirmation.
  - **What a new component owes.** Five interaction states — rest, hover, active, focus-visible, disabled — with **no layout shift between them**, and a hit target of at least `--control-h`. Where two class strings could set the same property under the same variant, both go in the same `Record<Union, string>` entry: split across a shared string and a per-variant one, the winner is Tailwind's internal sort order rather than anything written down (this is why `Button`'s focus outline colour is per variant). Those states are guarded with `not-disabled:` rather than `enabled:`, and that is what lets `ButtonLink` — a button that is a destination, so ⌘-click and middle click still work — share `Button`'s one `VARIANT` map: `:enabled` matches form controls and nothing else, so on an `<a>` every hover and press state would emit and never match, which is a filled control that does not answer the pointer. Verify a variant spelling in the emitted CSS rather than assuming it; Tailwind emits nothing for one it does not know, silently. And the four states that are not interactions — empty, loading, error, stale — are designed, not left to a spinner: `Empty`, `Skeleton`/`SkeletonText`, `Notice`, `Field`'s `error`.
  - **`Field` is finished; do not fork it.** Label, `hint`, `error`, `unit`, `prefix`, `disabled` and the mode-picker-plus-value row (`LimitField`) are all props. A context carries `aria-describedby`, `aria-invalid` and `disabled` down to `Input`/`Select`/`Textarea`/`Switch`, so a hint written as a prop actually reaches the control — children are never cloned, because several Fields hold a fragment. That context is **exported**, and `ListRow` provides it rather than carrying a copy, which is what makes a control behave identically in a grouped row and in a Field. Everything the context supplies is a default the control's own prop overrides. Width is the one thing no control states: two width utilities on one element resolve by stylesheet order, not class order — so a caller that needs a narrow input puts the width on a wrapper, never on the control. **A call site that ignored that is worth naming, because it read as compliance:** `RunLand` passed `className="w-auto"` to a `Select` under a comment claiming `Select` never states a width, and `CONTROL` is literally `w-full`. Confirmed in the emitted stylesheet — `.w-auto` at byte 15178 against `.w-full` at 15197, same specificity — so the caller lost, the select filled the flex line and `flex-wrap` put *Land into …*, the most consequential button in the app, on a row of its own beneath a full-width dropdown. The width is on a wrapper now, with a `shrink-0` beside it so a line too narrow for both wraps the button rather than squeezing the choice it is pressed with. **That rule is not about width, and the density pass measured the general case**: Tailwind emits a numeric utility's values *ascending*, so on any element that concatenates a component's own class string with a caller's, the larger value wins whatever the caller wrote. `Field`'s root is `mb-3.5` and `CardTitle`'s is `mb-3`, and `.mb-0{` is at byte 10980 of the emitted sheet against `.mb-3{` at 11231 — so a `className="mb-0"` on either is a **no-op**: three `CardTitle` call sites relied on one and rendered 12px of margin while reading as though they did not, and each now cancels on a wrapper instead (`RepoSpendCard.tsx:98`, `UsagePeriods.tsx:148`, `app/page.tsx:973`, all three carrying a comment saying why). That is the move a caller who has to cancel a component's own spacing makes — a wrapper (`-mb-3`, `-mb-3.5` against a `Field`), the same one the width rule already asks for — verified in the emitted CSS rather than assumed.
  - **`Slider` and `ColorSwatch` are `Field`'s two newest members, and a slider always shows its figure.** Both take the same context every other control does, so `hint`, `error` and `disabled` reach them unchanged, and both carry the 44px floor below `md` (`max-md:min-h-11` on the range, `max-md:h-11 max-md:w-11` on the swatch). A range has no styling surface but its vendor pseudo-elements, so the track and thumb are reached through `[&::-webkit-slider-runnable-track]` and `[&::-moz-range-track]` — and **both spellings are always written out**, because an engine drops an entire rule block naming a selector it does not recognise, which is a slider that silently renders as the platform default in one browser and correctly in the other. The numeric readout beside the track is not optional and not a caller's choice: a control whose effect is immediate still leaves nobody able to say what they set, compare two settings, or get back to one. `ColorSwatch` is a native `<input type="color">` with the picker chrome stripped, because the alternative is an in-app colour picker, and this app has one colour decision in it.
  - **`ListGroup`/`ListRow` is the grouped inset list, and `Switch` is the control that usually sits in one.** Label left, control right, hairlines between rows, a rounded box, a footnote under it. The box deliberately does **not** clip its overflow: rows carry no background of their own, so a hairline never reaches a corner and nothing needs `overflow-hidden` — which matters, because a caller with a marker in the gutter (the settings page draws an edited rail there) would have it clipped away. A row is inert and has no hover tint: every interaction state belongs to the control inside it, and a row that lit up under the pointer would be claiming to be clickable across a width where only the 38px switch is. `Switch` *is* its track, so the focus halo hugs the pill rather than a padded box around it, and the hit target comes from an `::after` overlay stretched to `--control-h` — a target the pointer hits and the layout never sees. `Toggle` is the same switch with its label on the left, for a stack of Fields with no right edge to align against.
  - **Numbers behave.** Every figure `tabular-nums` (`Stat`, `Th`/`Td` with `num`, `Meter`, `mono`) so it cannot jitter as the page polls, units attached, and an unknown reading says so — the hatched indeterminate meter, never a 0% bar. Reserve space for anything that streams in.
- **A `<canvas>` settles three things the DOM already answered, and every one of this app's canvases answers them the same way — by importing the answer from `src/lib/canvasView.ts` rather than deciding again.** `WorkflowCanvas` draws with absolutely-positioned elements; `KnowledgeGraphCanvas` was the first real 2D context here, and what it decided was moved out from under it so the second one could not quietly decide differently. `PathMapCanvas` is that second one and it is the test of the extraction: it imports the transform, the gestures, the hit test, the sizing and the probe, hand-rolls nothing, and the only thing it added to `canvasView.ts` was nothing at all. There is now a second split of the same kind stacked on it, for the same reason one layer up: `PathMapCanvas` knows what a *path hierarchy* is — the fold transition, the place-keyed carry and drag pin, the golden-angle seeding of newly-unfolded children, the fit-once rule, the label ramp — and never which fact about a file it is colouring, so a map's radius, its file fill and rings, its token list and its `aria-label` arrive as props. `RunTouchedMap` is only the touched run's answers to those. A third surface that finds itself writing a pan, a wheel or a nearest-within-reach has `canvasView.ts`'s split backwards, not a missing feature; one that finds itself writing a fold transition or a place key has `PathMapCanvas`'s. The line that module holds is **what a pixel is, never what is drawn on it**: it owns the world/screen transform, the cull rectangle, framing a bounding box, the nearest-within-reach hit test, `devicePixelRatio` sizing and its `ResizeObserver`, the wheel's `deltaMode` normalisation and the colour probe — and it knows nothing about nodes, edges, radii, labels or where any of it came from. A surface's own arithmetic reaches in as an *argument* — `reachOf` for what a radius means, a `marginPx` for what has to stay drawable past an edge, its own token list for which colours it picks — and a consumer that finds itself wanting to add a domain type to `canvasView.ts` has the split backwards. Its arithmetic is unit-tested in `canvasView.test.ts`, which is the point of it living in `src/lib`: a transform that is wrong draws a plausible picture, so an assertion is the only thing that catches it. **Colour cannot be read from a custom property.** Every token is a `light-dark()` or a `color-mix()` and nothing registers an `@property` for them, so `getComputedStyle(root).getPropertyValue("--fg")` hands back the literal source text — which a 2D context rejects, silently, leaving the last colour drawn. The only thing that resolves one is a real element: set `style.color = "var(--fg)"` on a throwaway span, read the computed `color` back as an `rgb(...)`, and re-probe on both a `data-theme` mutation and a `prefers-color-scheme` change, or the graph keeps the old theme's palette until something else forces a rebuild. **The backing store is device pixels and the element is CSS pixels**, and setting one without the other is the whole of why a canvas looks soft — `width`/`height` are multiplied by `devicePixelRatio` under a `ResizeObserver` and the transform is reset to it at the top of every frame. **And the loop ends.** A settled layout still asking for frames is a warm laptop on a page that looks finished, so the rAF is re-armed only while `step()` reports the alpha is still above `ALPHA_MIN`, and every gesture, slider and filter change reheats it explicitly. `prefers-reduced-motion` does not slow the animation down, it removes it: the layout is stepped in one synchronous burst — to settled, or to a 300-step cap, whichever comes first — and drawn once. **And the element is out of flow**, which is the one of the four that looks like tidying and is not: the observer writes the host's measured height straight back onto the canvas as an inline `style.height`, so an in-flow canvas is a child whose intrinsic height is whatever the host was last time — and `KnowledgeGraphCanvas`'s host is sized by a grid row that the panel beside it can shrink. Put it back in flow and the box ratchets: it grows with the panel and never comes back down, silently, because every individual measurement is correct. That box is a 4:3 *floor* rather than a ratio, held by a `self-start` sizer sharing its grid cell, because the panel is the taller column at every width the two sit side by side and a fixed ratio left the graph in the top two thirds of its own card.
- **A chart small enough to read at a glance is inline SVG, and it takes its colours as classes rather than as probed values.** `ContextOccupancy`'s sparkline is the precedent, and it is deliberately not the canvas above: at a few hundred points in a 21rem column there is no frame loop to end and no backing store to scale, and the whole reason a canvas has to probe `getComputedStyle` for a colour — a 2D context takes a string, not a custom property — does not exist for an SVG element, which takes `stroke-accent` and `fill-surface` as ordinary Tailwind utilities and resolves them per element like every other box on the page. `WorkflowCanvas`'s link layer already did this. Three things follow from being an SVG and are easy to get wrong: **`preserveAspectRatio` stays at its default**, because `none` stretches the box to the column and takes the stroke widths, dot radii and marker triangles with it, so the same picture is drawn differently in the inspector and on a phone; **the height comes from the viewBox** (`h-auto w-full`) rather than a Tailwind height, which would letterbox and would then have to be kept in step with the viewBox's own; and **coordinates are rounded**, since this markup is re-rendered on a three-second poll and full float precision puts fifteen digits into every point of a five-hundred-point path. There is no charting dependency in `package.json` and adding one for a picture this size is not the trade — the whole component is under 500 lines including its copy. Its accessibility is `role="img"` with an `aria-label` carrying the series' *shape* — span, endpoints, peak, and where the marks are — and a `sr-only` `<Table>` for the discrete events under it, which is the split a sparkline wants: a transcription of five hundred coordinates is not a text alternative, and a list of the cuts is.
- **A chart whose marks are *identities* takes the six band tokens, in a fixed order, and never a status colour.** `--band-1` through `--band-6` exist because the composition stack under `ContextOccupancy`'s sparkline needs six fills that are told apart by hue, and the palette had four — three of which are states. `--danger` is already the ceiling rule on the chart directly above it, so a band wearing it would read as *this part of your context is the problem*, which a composition must not assert and least of all about `prefix`, the one part of it nothing here can cut; `--accent` is that chart's own series line. The order is **assigned to an entity and read by a stable index**, never cycled over however many bands came back: a conversation that stops carrying attachments loses a band, and a palette indexed by rank repaints every band above it at that moment. Six is the ceiling as well as the count — a seventh provenance is dropped, so the bands visibly fail to sum, rather than given a generated hue or a repeated one, which is not visible. Both modes are **selected rather than flipped** and both were *computed rather than judged*: every adjacent pair clears the CVD floor (worst 14.8 ΔE deutan in light, 12.6 protan in dark), every step sits inside its mode's lightness band, and each clears 3:1 against `--bg-raised`, which is the card they are drawn on. Re-run that check before moving one; a hue nudged by eye is how a palette stops being colourblind-safe with nothing to say it has. Two things follow at this size and are not the full-size chart's answers: the separator between stacked segments is a surface-coloured **stroke** rather than a real gap, since a gap lets the ground through and gives each band its own apparent baseline, and it is 0.75 rather than the 2 a large chart takes, because the viewBox is about 1:1 with device pixels and the stroke is centred on the boundary — `conversation` runs about 1% of the window, four units tall, and at 1.5 the separator was most of the band. The hover layer is a `<title>` per band and not a crosshair; it must be **one interpolated string**, because React renders a `<title>` whose children are an array as empty, with a console warning and no other symptom. It stayed a `<title>` when the stack gained its one piece of client state — the picked band — and the argument moved rather than lapsed: a hover readout does not exist on touch and cannot be reached from the keyboard, so what a reader is owed is the detail region below, which is on the page. **The bands themselves are a pointer shortcut and never the only way in**: the `<svg>` is `role="img"`, so everything inside it is presentational and no assistive technology can reach a handler on a `<path>` whatever element it hangs on — the legend row is the real control, a `<button>` with `aria-pressed`, sized to `--control-h` (44px under `md`) because it is one. And **nothing marks the picked band on the chart**: a stroke would eat it, since the separator is centred on the boundary and `conversation` runs about four units tall, and dimming its neighbours would take the six fills below the 3:1 against `--bg-raised` they were computed to clear. The state is carried by the legend row's wash instead. One region below the chart whose subject changes is a *selection*, and deliberately not six `Disclosure`s — those would be the coordinated set this vocabulary forbids, each opening under its own row and closing the others.
