# Landing: a night on a branch, and when its signatures are claimed

[← dreaming index](../dreaming.md)

Read before editing `startDreamingWriter` or the refusals in `runDreamingNight` in `src/lib/dreamingRun.ts`, `src/lib/dreamingLanding.ts`, or the `dreaming_pending` table and its functions in `src/lib/dreamingLedger.ts`.

**A night is isolated whenever its vault can be, and where it cannot be nothing changes.** `startDreamingWriter` asks `probeIsolation` of the folder `createRun` will resolve, the same question the run path asks in the same turn, and passes `isolate` from the answer. The vault became a git repository on 2026-10-24 (the board task that asked for this). A run writing into its checkout leaves modified and untracked notes there, `checkoutRefusal` reads that as uncommitted changes, and every other land into the vault is refused until somebody commits them. Where the probe says no (not a repository, a knowledge-base subpath inside one, submodules, a mount-root repository that does not ignore `.uf-worktrees/`), the run is `isolate: false` and claims its signatures at the start, exactly as it did. Whether the night was isolated is read off the created run's `isolation`, not off the probe, because the run's row is what the land will read. A repository whose checkout slots have run out makes `createRun` throw, and the night is recorded `refused` with that sentence; it is not downgraded to working in the checkout, for `resolveIsolation`'s reason that this is the failure isolation exists to prevent.

**The signatures are claimed when the branch lands, never when the run starts.** `dreaming_notes` says a note was written, and for a night on a branch nothing is in the vault until the land. Claimed up front, a refused land leaves a signature suppressed for a note that does not exist, and the next night does not try it again; nothing reports it, because the Nights tab shows a `selected` night with a completed run. So the selection is held in `dreaming_pending` (the exact array the prompt numbered, because `prompt_item` is a place in it) and `claimPendingLanding` moves it across in one transaction when `settleDreamingLandings` sees `runs.landed_at`, a `landed` or `already-landed` queue row, or a branch already merged. The first of those counts a land by hand, which is why a stuck night has an exit. A run that ended having written nothing claims too, as every night always has: that is how a night that found every item already covered ends, and retrying it would pay for it again each night.

**One night's branch is in flight at a time, and the next night refuses while it is.** `runDreamingNight` settles first and then refuses if a pending row is left, naming the earlier night and why. A second branch would be cut from a vault that lacks the first one's notes, so the two would edit the same hub notes (`Agent Error Memory.md` and the like) and the later land would conflict, and it would select signatures the first has not yet claimed. The exits are the operator's: land the branch from the run page, which claims it, or purge it, which lets the night go and frees its signatures for a later one (`dropPendingLanding`). A run row that retention deleted also lets it go.

**The minute tick tries a branch once, and the next night tries again.** `attempted_at` is null until the first try. `tickDreaming` settles on every tick, not only a due one, because a branch lands when its run ends, which has nothing to do with the next window. With `revisit: false` it leaves a branch whose queue row ended refused alone: the usual cause is the operator's checkout, which a minute does not change, and retrying would put a refusal a minute into the queue's history. `runDreamingNight` passes `revisit: true`, one more try a day, and that is the pass that notices a purged branch. A tick settles only while Dreaming is on, since it is the timer's tick: a branch left by a night that was running when the switch went off waits for the operator or for the switch.

**A stopped night is not landed for the operator.** Before this, whatever a stopped run had written was already in the vault, so a stop vetoed nothing. An isolated run is the first kind that can honour one, so a `stopped` run with commits or leftovers is left waiting for a land by hand or a purge, and nights refuse behind it until one happens. A `completed`, `failed` or `needs-review` branch is queued, which is what the non-isolated run left in the vault whatever way it ended.

**What reaches the queue is `enqueue` with `autoResolve: false` and the operator's `landStrategy`.** A resolution is a paid agent and a night's spend is `dreamingMaxCostUSD` and nothing else, so a conflicting branch fails its row and waits. Work the agent left uncommitted is committed with `commitPending` first, as the run page's button does, because `landRefusal` reads an empty branch with a full checkout as "no commits of its own" and the night would be lost. `buildArgs` grants the agent `git commit`, so this is the fallback and not the path. It is read **before** `merged`: a branch with no commits is an ancestor of its target and reads `merged`, so asking that first claimed exactly the night this exists for, with its note still on disk in the slot.

**What this does not cover.** The operator's own edits in the vault's checkout (Obsidian's workspace files, an unsaved note) still make `checkoutRefusal` refuse every land, Dreaming's included; that is a separate decision and is on the board. The agent works in a checkout of the committed tree, so a note the operator has not committed is not there for it to grow, and a night can write a second note beside one that exists. And the Dreaming pane does not show a night waiting to land: the Nights tab reads `selected` plus the run's ending, so it sees only the refusal the next night writes.
