# Agent references, and the agents this app did not write

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `runs.agent`, `run_templates.agent_id`, `parseRunAgent` in `src/lib/agents.ts`, or `src/lib/agentRegistry.ts`.

**A run records the agent it was started as; a template records the one it names; and the difference between a copy and a reference is the whole of it.** `runs.agent` holds the entire definition as JSON, the treatment `runs.budget` already gives `permissionMode` and the reason deleting a template cannot reach a run started from one. An id there would be wrong twice, and the singular flag makes it wrong harder: a run spawns a child per work cycle, so an agent deleted between cycle 3 and cycle 4 would leave cycle 4 selecting a name nothing on its argv defines, which the CLI refuses at the spawn — a run that silently stopped being what it was started as, part-way through, and then stopped running at all — and a run picked up by hand days later would lose it the same way. `startRun` therefore reads `parseRunAgent(run.agent)` and never the registry. `run_templates.agent_id` is a reference for the opposite reason: a template is applied again and again, so an operator who fixes their reviewer's prompt expects the next run from it to use the fixed one. **What that reference reaches is the new-run form and nothing else** — it is a seed for a field, the treatment the template's mount and folder already get, and it is *not* inherited by the two paths that read a template on the server. `planProposal` takes the agent off the proposal and `planNode` takes it off the node, both deliberately (the workflow invariant below argues that one out), so a template supplies a proposal its prompt, its guards and its model and never its agent. Which is the honest reading of "carries onto the run exactly as the guards do": true where a person applied the template to a form, and false everywhere a model named the template instead. **`model` beside it is the deliberate asymmetry rather than an oversight**, and it is worth stating in the same breath because the two fields sit next to each other and behave oppositely: a proposal and a node each name their own agent, so inheriting the template's would override an answer that surface already gave, while a node names no model at all and a proposal's own model is *read first* rather than overridden — null on the proposal is what falls through to the template, which is inheritance working rather than an exception to it. `planEmittedRun` takes it on the same terms, which is what makes `RunSpec`'s "no model, because the block's own template already answered all of those" true of the model rather than an absence with nowhere to come from. **A deleted agent is refused by name at every door and never falls back to none**, which is `planProposal`'s rule for a deleted template and the same reasoning — the operator started the run that said "as the reviewer". `agentRefusal` is that one wording for every door handed an **id**, pure and unit-tested: `POST /api/runs` through `resolveAgentForRun` (which takes an id off the wire and never a definition, since a definition would be a route to an agent nobody saved), `normalizeTemplateInput` through the `TemplateKnowledge` it is handed — `normalizeWorkflowInput`'s argument-rather-than-read shape, for that function's reason, and the `no_terminus` rule applied to a second field so a template cannot be saveable and never startable — `PUT /api/settings` for the form default, `propose_run` and `approveProposal` for a chat proposal, `normalizeWorkflowInput` at save and at `/api/workflows/validate`, `planNode` at both moments a block becomes a run, and `startBlockTurn` for a deciding turn's own. The two doors that were shown a **name** rather than an id — `planEmission` for a spec and `createEmitted` when that spec becomes a run — refuse in their own words for that reason and no other; the answer is the same refusal, and the sentence has to name what the turn typed. An agent that exists but has decayed into something the CLI would drop is refused the same way and *named*, because `rowToAgent` reports rather than repairs. `reopenRun` carries the column forward by not touching it: there is no argument on the function and no field on the reopen route that could reach it, which is `permissionMode`'s rule one field over and also what lets a run whose agent has since been deleted still be picked up as the agent it ran as. **What the surfaces say is bounded by what the flag does, and that placement was re-decided under the singular flag rather than carried over.** The obvious reading is that a run which *is* its agent has had its agent promoted into the guard group, and it is wrong: `--agent` sets the session's system prompt and, where the run named no model, its model — the permission mode, `ISOLATED_GIT_TOOLS`, `PROCESS_KILLERS` and `--append-system-prompt` are argued at the spawn sites and are untouched by it, which `orchestrator.test.ts` asserts again with an agent selected. A row inside the guard group would claim it bounds something, and it bounds strictly nothing; it is a bigger fact than it was and still not that kind of fact. So the run page keeps it beside the guards and never among them, and the form's picker declares the ambient set beside itself, because the registry is a part of the set and not the whole of it.

**The agents this app did not write are left in play and declared, never silently mixed.** `docker-compose.yml` bind-mounts the operator's `~/.claude`, so `$CLAUDE_CONFIG_DIR/agents/**` already reaches every child this app spawns — runs, chat turns, orchestrator blocks and reviews — and an isolated run's worktree carries the repository's own `.claude/agents/` for the same reason. `--agents` **merges** with that set rather than replacing it, verified — and `--agent` resolves its name against the merged set, which the pin's own refusal line shows directly: the `Available agents` it printed beside a typo carried the built-ins, `typescript` off that machine's disk, and the member supplied on the argv, all together. So starting a run *as* a saved agent withdraws nothing; the ambient definitions are still in play inside it, and are still the thing a picker cannot name. Excluding them is what `--strict-mcp-config` does one door over, and it was rejected on the mechanism rather than the principle: agent discovery is governed by `--setting-sources`, where `user` keeps the user scope, `project` keeps the repository's, and only the empty value drops both — and that flag governs settings *whole*, so passing it to exclude agents would silently drop the operator's own `settings.json`, hooks, permissions and environment from every child. There is no agent-scoped exclusion in 2.1.226, and a change that large made in passing for a feature nobody has switched on yet is worse than the thing it fixes. The second reason is that these are not new: a repository's `.claude/agents/` is part of the repository the agent was pointed at, and withholding it would make a run behave differently from the same checkout opened in a terminal. So the registry is a *part* of the set and the app has to say so wherever an agent is chosen. `listAmbientAgents` is what that sentence is built from, `GET /api/agents` returns it as `ambient` beside `agents` so no two surfaces can say it differently, and `parseAgentFile` reads a definition the way the CLI does — the name off the frontmatter `name:` key and never off the filename, a file with no `name:` key not registered at all, subdirectories walked. Only the **user** scope is on that payload, being the half that holds whatever a child's cwd turns out to be; `listAmbientAgents` takes a directory for a caller that has already resolved one, and resolving an arbitrary one on the wire would be a containment surface this does not need. A saved agent whose name collides with an ambient one is *not* refused — the ambient set is per-cwd and a pure validator cannot see it — so which definition wins is unverified and a surface that lists both is what makes the collision visible.

**The mounted `settings.json` can name a session agent too, and that one is measured and *not* declared.** `--agent`'s own help says it overrides "the `agent` setting", and on the pin that setting exists: an `agent` key in `$CLAUDE_CONFIG_DIR/settings.json` starts the session as that agent with no flag at all, which is the same class of fact as the ambient definitions — the registry is not the whole set — arriving through the same bind mount and reaching every child this app spawns. Four probes against 2.1.226, a definition whose entire prompt was "reply with exactly BANANA": the key set answered `BANANA` where the key absent answered an ordinary greeting; `--agent` naming a second definition answered that second one, so the flag wins as documented; `--agents` **alone** answered `BANANA`, so the plural flag does not override it; and a key naming an agent that does not exist answered an ordinary greeting at exit 0, where the same name on `--agent` exits 1 before any API call — silently ignored where the flag is loud, which is the opposite direction from every refusal `agents.ts` makes. What follows bounds how much this matters: every door that names an agent emits `--agent` and therefore outranks the key, so a run, block or turn started *as* something is unaffected. What the key reaches is everything this app starts as **nobody** — an agentless run, every chat turn (`runTurn` withholds one deliberately, and this is the one door that can put a saved prompt under `systemPrompt()`'s boundary without asking), every orchestrator block whose node names none, and every review (`spawnAssist` is on the plural flag, which the third probe shows does not override it). It is **not declared**, and that is a decision with a stated cost rather than an oversight: `describeAmbientAgents` is one sentence four pickers share, so carrying this would be a new read of `settings.json`, a new field on `GET /api/agents`, a second argument threaded through that sentence and its four call sites — and the sentence would be *false* on the surface carrying it, since picking an agent there is precisely what overrides the key, while the two children where it bites hardest (a chat turn, a review) have no picker at all. Recorded in `docs/verification.md` and in the README rather than built.
