# Saved agents: a role, refused at the door

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `src/lib/agents.ts` (`normalizeAgentInput`, `sessionAgentArgs`) or `src/app/agents/page.tsx`.

**A saved agent is the fourth thing here that is form input, and it carries a role rather than a capability.** `agents` holds a name, a description — what a *person* reads on a picker when they choose it — a prompt, and optionally a model; it takes no folder claim, consumes no concurrency slot, nothing derived from `activeRuns()` can see it, and deleting one cannot reach a child that has already been spawned, because every spawn writes the whole definition onto its own argv rather than a reference to the row. **It reaches a child as two flags, and the pair is the whole feature.** `sessionAgentArgs` emits `--agents <json>` through `agentsFlagValue` *and* `--agent <name>` beside it, so the definition travels and the session is then started as it — the saved prompt is the run's own, not a role inside it. This app was built the other way round, on the plural flag alone, and that reading is recorded here rather than deleted because the next person to read this file will otherwise re-open the question. `--agents` on its own *offers* a definition to the session's main agent as a specialist it may hand a subtask to; the `description` was then what the delegating model read when it chose, and this paragraph said in as many words that the singular flag was a different feature answering a different question. It is — and the question this app is for turned out to be the singular one, which is why every place the plural reasoning was embedded was re-decided rather than patched around. The pair is not redundant, and that is measured rather than assumed: `--agent` resolves a name against the built-ins, whatever is on disk, and whatever this argv defined, so sending only the name would select an agent this app never wrote down anywhere the CLI can see. On the pin (`@anthropic-ai/claude-code@2.1.226`), `claude --agents '{"uf-probe-agent":{…}}' --agent uf-probe-typo -p hi` refused with `Available agents: claude, Explore, general-purpose, Plan, statusline-setup, typescript, uf-probe-agent` — the built-ins, an ambient definition on that machine, and the member supplied on the same argv, in one set. `spawnAssist` is the one caller left on the plural flag alone, for the reason the child-process paragraph above gives. **A `tools` field is refused at save, and the refusal is the decision.** `--agents` members accept one and this app will not store one, because capability in this app comes from a guard set a person wrote — the permission mode, `ISOLATED_GIT_TOOLS`, `PROCESS_KILLERS`, and not `SEARCH_TOOLS`, which is on every spawn precisely because naming two read-only tools grants nothing and only makes the CLI offer them — reached through exactly two routes and re-narrowed at every one; an agent record is a third kind of thing that would carry it, and the surfaces that pick one put it within reach of a model, where `planProposal`'s rule is that prompt text is the one half of a run a model may write and capability is the other. **The singular flag strengthens that refusal rather than weakening it**, and the opposite reading is available enough to be worth closing off: under `--agents` alone a `tools` list would have bounded one delegated subtask inside a run whose own mode and lists still stood over it, which is at least arguably contained. Selected with `--agent` the run *is* this agent, so a list on it would be a statement about what the whole session may do — precisely the third route to that decision the two-routes-to-`--permission-mode` rule exists to prevent, arriving through a record a chat proposal or a workflow block can name. There is no reading of the new semantics under which the field becomes safer to store. There is also a concrete hazard behind it: `PROCESS_KILLERS` is a `--disallowedTools` entry and deny is *verified* to beat `--permission-mode`, but whether it also beats a member's own `tools: ["Bash"]` — offered as a delegate or selected as the session — is **not** verified, and the incident behind that list is one `pkill` that restarted the container and failed fourteen runs. Refused by name rather than dropped, for `normalizeTemplateInput`'s reason: an operator who typed a tool list and got a saved agent that ignored it would believe their agent was narrowed when it was not. **A model is the field whose *meaning* the singular flag changed, and `run_templates` holds one too now — on this record's ground rather than in spite of it.** Under `--agents` alone it was the model a delegated sub-turn ran on, a thing nothing else here can express, and that was once the whole reason this file departed from `run_templates`' "the model is not a template's to hold" rule. That rule is gone: the run form offers a model, so a template refusing one drops what the form was set to, and the argument that licenses this field — cost, never capability — licenses that one identically. What keeps *this* one from overriding a choice somebody made is measured off the `system`/`init` event, before any request is made: an explicit `--model` outranks it, and `buildArgs` passes one whenever the run has one. `--agents '{"uf-m":{…,"model":"sonnet"}}'` alone reported `claude-opus-5[1m]`; adding `--agent uf-m` reported `claude-sonnet-5`; `--model opus … --agent uf-m` reported `claude-opus-5`. So the agent's model fills a gap the run left rather than overriding a choice the operator made — a run with no model of its own, started as an agent that names one, runs on the agent's — and it still moves cost and not capability, since the run's spend lands on its own `result` event and in its telemetry whatever model produced it. It is free-form *in the registry* for `settings.defaultModel`'s reason — a list this build knows would refuse whatever ships next week, and a row can outlive the build that wrote it, so `normalizeAgentInput` still refuses nothing but a length and a stored model is never degraded. `settings.modelCatalogue` answers that objection elsewhere rather than here: the list is the operator's own and it is read at the doors that start work, so the `/agents` page offers it as a picker (keeping a model already saved and since switched off as an option, `defaultAgentId`'s rule) while what it stores is still whatever it is given. **The registry is written from `/agents` and nowhere else.** `GET /api/agents` is read by five surfaces — the run form, Settings, the workflow canvas, the chat's mention popover and that page — and for as long as the page did not exist, `POST`/`PUT`/`DELETE` were reachable by hand and by nothing else, so every picker in this app was empty on every install and the run form's Agent row, gated on `agents.length > 0`, never appeared at all. What that page may hold is the same absence this paragraph is about: a name, a description, a prompt and a model, and no control for a tool list, a permission mode, a budget, a folder or an isolation choice — `agentPayload` is a named projection rather than a spread so that adding one is a decision somebody makes in front of the test that counts the keys, and the singular flag is what makes that absence load-bearing rather than tidy, since a field on this form is now a statement about what a whole run may do. It decides nothing else: `normalizeAgentInput` lives beside a database and a filesystem so a client cannot import it, and the refusals below are written to be *shown*, so the draft goes to the server and the page renders the sentence that comes back — `/api/workflows/validate`'s rule and its reason. The ambient collision the next paragraph leaves unresolved is annotated there rather than refused (`ambientClash`, case-folded as `idx_agents_name` is), and the same page lists the ambient set beside the registry, which is the "a surface that lists both" that sentence asks for.

**The CLI will not register a malformed agent, so this app refuses one at the door — and the singular flag changed how loudly that fails, not whether it does.** Measured against the pin (`@anthropic-ai/claude-code@2.1.226`), not read from the docs: a `--agents` member with no `description` is dropped, one with no `prompt` is dropped, one whose `model` is JSON `null` is dropped, an empty name registers as an empty entry, and a `--agents` value that is not JSON at all is ignored outright — exit 0 in every case, nothing on stderr, no line in the stream. That silence was the whole argument for validating here, and it is worth being exact about what "dropped" now means. It is dropped from the set `--agent` resolves against, which was invisible while the member was only being offered and is a hard start failure when it is being selected. Re-measured on the pin for the first three: `claude --agents '{"uf-nodesc":{"prompt":"p"}}' --agent uf-nodesc -p hi` answered `--agent 'uf-nodesc' not found. Available agents: claude, Explore, general-purpose, Plan, statusline-setup, typescript` and exited **1**, before any API call, and identically for a missing `prompt` and for `"model": null`. The other two — the empty name and the non-JSON payload — have **not** been re-measured under the singular flag and are still on the *Not yet verified* list by name. So the class of fault now has two shapes rather than one, and both are worth refusing where the person is: a run that was given a specialist and does not have it (the old one, still exactly what `spawnAssist`'s offered member would produce, and bit-for-bit a run that was never given one — nothing downstream can tell them apart, not the event log, not the cost, not the transcript's own `attributionAgent`, which simply never names it), and a run whose every work cycle dies at the spawn with a message only the CLI's stderr carries. Louder is better, and it is still not a substitute for refusing at the form. The five are answered in three places rather than one, because they are not one kind of fault. `normalizeAgentInput` refuses the three a person can type — a missing description, a missing prompt, an empty name — where they were typed; the description stays required on a *stronger* ground than the one it lost, since nothing chooses on it any more but the CLI will not register a member without one. `rowToAgent` reports a row that has *decayed* into one as `usable: false` rather than repairing it with a placeholder, and every door reads that flag. And the last two are the encoder's, because they are shapes rather than values: `agentsFlagValue` **omits** `model` instead of nulling it — the only spelling of "inherit" that survives — and it is the one thing that writes the JSON, so there is no second place for a payload to stop being JSON. It is that one encoder for every caller that can carry the flag (`buildArgs` and `runOrchestratorChild` through `sessionAgentArgs`, `spawnAssist` through `agentsArgs`) precisely because a second copy of a shape whose violations are unreported would drift with nothing reporting it. A name that collides with one the CLI already answers to (`claude`, `Explore`, `general-purpose`, `Plan`, `statusline-setup`) is refused too, and the reason **narrows** rather than disappearing: `claude --agents '{"Explore":{…}}' --agent uf-typo -p hi` still lists one `Explore` and not two, so `--agent Explore` selects *an* Explore with no way to tell from outside whether it is the operator's prompt or the built-in — which is now the difference between a run that is the agent the operator wrote and a run that is something else entirely, under a name they chose. That list can go stale when the pin moves, in the direction that costs a shadow rather than a crash; note also that `typescript` appears in the CLI's own "Available agents" line on the probe machine and is *not* on it, being an ambient definition — which is what that line looks like when a name comes off disk rather than out of the binary.
