# The model decider

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `src/lib/modelDecider.ts`, `emittedModelWork`/`recordEmittedModels`/`RunSpec.decidedModel` in `workflows.ts`, `proposalModelDecision` and the `emit_runs` case in `src/app/api/mcp/route.ts`, or `chat_proposals.model_note`.

**A model may now choose what a run costs with nobody in the loop, and the decider is the only one that may.** `RunSpec` used to keep the model off an emitted run because "a spec is written by a model, and a model choosing what it costs to run is a choice with nobody in the loop". The operator overruled that on 2026-10-05 for one author: the model decider, a separate local service (the LocalDecider project — a Tev1-4B classifier behind `llama-server`) that is handed a run's title and task plus this install's enabled catalogue and answers with one of those ids or abstains. The block's own turn still cannot name a model: `normalizeSpec` builds a spec field by field, so `decidedModel` is reachable only from `recordEmittedModels`. What made the overrule defensible is the ground `agents.model` already stood on — a model moves cost and never capability, every cost guard measures whatever it selects — plus one check of its own: `readDeciderReply` holds every answer to `modelRefusal` against the operator's list before it can become a run's model, so an id switched off between the request and the answer is refused there.

**Two doors ask, and each asks outside the event-loop turn it must not break.** The chat's `propose_run` asks in `proposalModelDecision`, *before* `proposeRun`, because `proposeRun`'s rival-continuation check and its write are one synchronous pass; an `await` between them would let two concurrent proposals both pass the check. An orchestrator block's `emit_runs` asks *after* `emitBlockRuns` has stored the emission, for the same reason one level down — its "has this block emitted?" read and its write are what keep a block to one emission — and before the tool answers, so the turn cannot end in between unless it is killed. `recordEmittedModels` latches on `status='thinking'` for that case: a block settled while the decider was answering has had its runs created on the template's model or the default, and the note says the pick came too late rather than implying it was used. `settleBlock` and `createEmitted` stay synchronous and never ask.

**The decider fills one gap and outranks nothing a person set.** `deciderApplies` answers a Claude run (null provider or `claude`) and, since the Codex catalogue, a Codex run — each from its own list, one provider's per request, so no id crosses between them — and never a local one, whose server lists nothing the decider could be handed. A Claude run is answered only where the chat named no model, the template names none, and the agent the run is started as names none, because an agent pinned to a model is the operator's answer for that role; a Codex run only where the run itself named none, because a template's or an agent's model is a Claude id that never reaches `codex exec` and so answers nothing there. The decider sorts what it is handed into its tiers by family, and LocalDecider's `tiers.json` pairs each Claude family with a Codex one (haiku/luna, sonnet/terra, opus/sol, fable/mythos/astra, after the Codex CLI's own descriptions); a family it does not know is `unrecognised` and never offered. `settings.defaultModel` and `settings.codexDefaultModel` are deliberately not on that list: they are the fallbacks the decider sits above. A Codex block's emitted run takes the pick and never its template's model (`planEmittedRun`), and a Codex proposal's pick fills the proposal's own rung, which `planProposal` keeps for a Codex run. On a proposal the pick is written to `chat_proposals.model`, the proposal's own rung, so `planProposal`'s precedence is unchanged. On an emitted run it is `spec.decidedModel`, which `planEmittedRun` reads *after* the template's model, and the template is read again when the run is created, so a template given a model after the emission was decided on still wins.

**Off, down, slow, unsure and wrong all end the same way: the run takes the rung below, and a sentence says which.** `decideRunModel` never rejects — both callers are inside a tool call a model is waiting on, and a decider problem is a note, never a failed tool call or a refused run. It returns null without asking when `UF_MODEL_DECIDER_URL` is blank, and a `{model: null, note}` otherwise for an abstention, an error status, an unreadable body, a refused id, a timeout (15 s, above the decider's own 10 s so its 503 arrives first) or an unreachable host. The note is always kept, because "the decider was down" and "the decider was unsure" are invisible on a run that took the default otherwise: on a proposal it is `chat_proposals.model_note`, drawn on the card as ", picked by the model decider" beside the model or "model decider: no pick", with the sentence in the tooltip; on a block it is one `noteBlock` line per emitted run.

**The target is environment-only, and the task text is why.** `UF_MODEL_DECIDER_URL` is read through `optionalEnv` and listed in `BLANK_MEANINGFUL_ENV_VARS`, blank meaning off. Every request carries a run's title and task, so a target held in `settings.json` would let anything holding the master token aim task text anywhere the container can reach — `WEBHOOK_URL`'s argument with more at stake, since the webhook carries no task text at all. The decider binds to the host's loopback by default and a container on Docker Desktop reaches it through `host.docker.internal` (the discord relay's measurement, 2026-08-24).
