# The Codex model catalogue

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `src/lib/codexModelDiscovery.ts`, the model half of `src/lib/codexAccount.ts`, `settings.codexModelCatalogue` or `settings.codexDefaultModel`. The rules it inherits are in [templates-and-model-catalogue.md](templates-and-model-catalogue.md).

**The Codex catalogue is the same list for the other CLI, and its one difference is that it has no seed.** `settings.codexModelCatalogue` and `settings.codexDefaultModel` are `modelCatalogue` and `defaultModel` for a Codex run, under every rule above — an id, a label and a switch; validation and never a guard; empty means no list and refuses nothing; a default refused at Save when it names no enabled entry — and the two lists never stand in for each other: `POST /api/runs`, `propose_run` and `PUT /api/settings` each judge a model against the list of the provider it is for (`modelRefusal(…, "codex")`, whose sentence names the Codex list), and the run form offers each provider its own picker and drops a model that is not on the new provider's list when the provider changes. What is different is where the list comes from. Nothing in this build knows which models a ChatGPT plan reaches, so the shipped default is empty and `settingsDefaults()` lays over it what `codexModelDiscovery.ts` read off the Codex CLI's own `model/list` (`codexAccount.ts`, through `codex app-server` as the agent uid, so the list is the one a Codex cycle can reach). That makes the first listing the one case "empty stays empty" does not cover: an install still following its default reads an empty list until then, and that empty means "nothing listed yet", not an operator's "no list" — so `mergeDiscoveredModels` takes `fillEmpty`, passed only when `isStoredSetting("codexModelCatalogue")` is false. A stored empty list keeps the rule. Everything else is `modelDiscovery.ts`' bookkeeping on its own `settings` row (`codexModelDiscovery`): offered once so a Remove stays removed, the record and a stored list written in one transaction, additions written into a stored list and only into the record for an install following its default, a check at boot and daily behind the ownership gate, and one more the first time `GET /api/codex-auth` sees a sign-in, so a picker is not free text for a day after one. The id rule is `isCodexModelId` — `DISCOVERED_ID` without the `claude-` prefix, since the measured slugs (`gpt-6-astra`, `gpt-5.6-sol`, `codex-auto-review`) share none — and hidden models are not listed, because the hidden one on the measured account was `codex-auto-review`, the CLI's own approval reviewer. While the list is empty a Codex run's model is free text, exactly as before it. A chat proposal may name a Codex model now, judged against this list, and a Codex run takes the proposal's model but never its template's, which came from the Claude list; a workflow node still names none, so its Codex runs take `codexDefaultModel`.
