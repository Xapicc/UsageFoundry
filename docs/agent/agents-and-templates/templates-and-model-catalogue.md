# Run templates and the model catalogue

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `src/lib/templates.ts`, `src/lib/modelCatalogue.ts`, or any field that names a model.

**A template is form input, and the two settings that decide what an agent may do are applied but announced.** `run_templates` holds a task, guards, and optionally a target; it takes no folder claim, consumes no concurrency slot, and nothing derived from `activeRuns()` can see it. `permissionMode` is narrowed three times — on save, on read, and again by `POST /api/runs` — because a template is the *second* route to `--permission-mode`, the flag `reopenRun` deliberately refuses to become a third route to. Only the last narrowing guards anything; the first puts the mistake where it was made, and the second (unknown → `plan`, the only mode that cannot write) is what stops a row from a build this one does not understand from ever *widening* what it permits. Never invert that fallback. `enforcement` is the other one: there is no `settings.defaultEnforcement` precisely so that no single edit turns every run into a cycle-killing run, and a template that quietly carried `live` would reintroduce exactly that — so a carried non-default mode, and a carried `bypassPermissions`, each raise a banner above the form with a one-click way back to the safe value, and the banner clears the moment the control is touched. `normalizeTemplateInput` also refuses the `no_terminus` pair at the door rather than leaving it to `POST /api/runs`: a template that can be saved but never instantiated fails weeks away from the form that caused it. It refuses a `maxRunCostUSD` or `maxDurationMinutes` that arrives as `""` for a sharper version of the same reason: `budgetFromForm` sends `""` for a limit switched on with its box blank and `null` for one switched off, `normalizePolicy` reads both as no limit, and the run form refuses the first at Start — so a template saved from that form state instantiates fine, with no cap, in the chat and on the canvas, which inherit its guards with no form in front of them. The refusal is the template door's alone; `normalizePolicy` keeps the `null`/`""`/`0`-means-off rule for every other caller, and a blank `maxIterations` is not on the list because it already fails closed, to one cycle. The page's Save runs `limitProblems` from `formProblems.ts` first, which is the limit half of `runFormProblems`, so the sentence lands beside the box in Start's own words. `folder` is nullable and `""` is *not* the null — the empty string is the mount root, the one selection that blocks every other run in the tree. **The template holds a `model`, and it used to refuse one — the paragraph that refused it is replaced rather than deleted, because the premise is what changed.** The refusal said `settings.defaultModel` already set the model globally and the run form did not offer one at all, so a saved model would be a second place to set one thing and the second place is the one nobody remembers to check. The form offers one now, which turns the argument around: a template that cannot save a model silently drops half of what the form was set to. What makes the second place tolerable is `agents.model`'s own ground — **a model moves cost and never capability**. It reaches `--model` and nothing else, every cost guard already covers whatever it selects because the run's spend lands on its own `result` event whatever model produced it, and the two routes to `--permission-mode` are still two. It is free-form for `settings.defaultModel`'s reason, and the triple narrowing `permissionMode` gets deliberately does not apply: that one exists because a permission mode decides what a spawned process may *do*, so a value this build does not recognise must never widen it; this one would only refuse whatever ships next week. **That premise held only for as long as the list would have been this build's, and `settings.modelCatalogue` is not.** It is the operator's own list — seeded from `pricing.ts`' price table so there is no second answer to which models exist, carrying the CLI-shaped `[1m]` ids, and edited in Settings, so a model released after this build is a settings edit rather than a release. **A model released *with* a build reaches an install that already stores a list, and `mergeSeededModels` is the whole of what makes that true.** The settings page has always promised it — a seeded row has no Remove button, and the comment on that button says an operator's own entry never comes back where "the seed comes back on the next release" — and until that function nothing kept the promise: `adoptModelsInUse` writes at most once per install, `saveSettings` pins `modelCatalogue` into the stored blob the moment it differs from `DEFAULTS`, and one model switched off is enough to do that, after which every future seed addition was dead for that install. Claude Opus 5.5 is what found it, priced and labelled and seeded on and on nobody's picker. The merge runs on **every** boot, which is the exact opposite of the rule one function above it, and the asymmetry is the argument rather than an inconsistency: adoption re-reads templates and agents, so running it twice would switch a model back on the morning after the operator switched it off, while this only ever adds an id the stored list does not carry — and a seeded id is one they have no way to remove, since the switch retires it *in place* and a retired entry is present-and-disabled rather than missing. So "absent from a stored list" can only mean "shipped since that list was written", never "taken off", and an install that stores no list is skipped entirely because it is still following `DEFAULTS` and writing would pin it. Order is the seed's, because declaration order is display order and a new model appended to the end would read as the oldest thing on the page; the operator's own entries keep their order and follow, where they already sat. `enabled` is never revisited — it is their answer — and the one field the merge does rewrite is a label still equal to its raw id, which is what both `addModel` and `adoptModelIds` write for a model the build had not heard of and which would otherwise leave `claude-opus-5-5` sitting on a picker underneath "Claude Opus 5". A label is cosmetic and gates nothing, which is what makes that safe. What reads it is the doors that *start work*: `POST /api/runs` (scoped to the Claude provider — a Codex run names something this list has never been told), `PUT /api/settings`, and the chat's `propose_run` and `save_template`. What deliberately does **not** read it is `normalizeTemplateInput` and `rowToTemplate`, and that is the same rule as ever: a template outlives the build that wrote it, so a stored model is neither degraded nor refused where the person who could fix it is not standing. It is validation and never a guard — it may not reach a budget, a work-cycle limit, a permission mode or an isolation choice, and it is not a fifth thing a template supplies. An empty list means no list and refuses nothing. Precedence is stated once and applied once — the run's own model wins, then the template's, then `settings.defaultModel` at `createRun`, and an agent's still only fills a gap where the run named none. **The `settings.defaultModel` rung is the Claude provider's alone, as is every id on this list, and no model id crosses to the other CLI in either direction.** A Codex run that named none freezes null (`frozenRunModel` in `orchestrator.ts`), which `buildCodexArgs` turns into no `-m`, so Codex runs its own default. It used to freeze the Claude default and spawn `codex exec -m claude-…`, with the form's placeholder showing that id as though it were meant; the placeholder and the run page now say "Codex's own default" instead. Blank is not refused for a Codex run, because it has a true meaning for that CLI and the door already declines to check a Codex id against a list it was never told. The other direction is the assist: review, validation and conflict resolution always spawn `CLAUDE_BIN`, so `assistModel` in `review.ts` gives an assist on a Codex run `settings.defaultModel` as read when the assist starts, or no `--model` at all where that is unset, and never the run's own id, which used to reach `claude --model <codex id>`. A Claude run's assist keeps the run's frozen model, as before. Each direction has a unit test that failed on the code it replaced, in `orchestrator.test.ts` and `review.test.ts`. Where it lands differs by surface and that difference is the point: the run form **seeds** the field from it (the treatment `mountId`/`folder` get, so the form's own value is what starts the run and one run can be moved off a template's model without editing the template), while `planProposal` and `planNode` **inherit** it with the prompt and the guards, because there is no form there and a saved model that reached only the form would be one the chat and the canvas silently dropped. `planProposal` reads it *second*, behind a model the chat named on the proposal itself — one more rung on the same precedence rather than a second answer to it — and `planNode` has nothing above it to read. It *also* holds an `agent_id`, which is not another place for a model and not a fourth route to `--permission-mode` — an agent carries a role and no capability, and the model on it is only ever reached where the run itself named none, an explicit `--model` outranking it on the pin. See *A run records the agent it was started as* in `docs/agent/agents-and-templates/agent-references-and-ambient-agents.md` for why that one is a reference where `runs.agent` is a copy.
