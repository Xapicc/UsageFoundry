# Run templates and the model catalogue

[← agents-and-templates index](../agents-and-templates.md)

Read before editing `src/lib/templates.ts`, `src/lib/modelCatalogue.ts`, `src/lib/modelDiscovery.ts`, or any field that names a model.

**A template is form input, and the two settings that decide what an agent may do are applied but announced.** `run_templates` holds a task, guards, and optionally a target; it takes no folder claim, consumes no concurrency slot, and nothing derived from `activeRuns()` can see it. `permissionMode` is narrowed three times — on save, on read, and again by `POST /api/runs` — because a template is the *second* route to `--permission-mode`, the flag `reopenRun` deliberately refuses to become a third route to. Only the last narrowing guards anything; the first puts the mistake where it was made, and the second (unknown → `plan`, the only mode that cannot write) is what stops a row from a build this one does not understand from ever *widening* what it permits. Never invert that fallback. `enforcement` is the other one: there is no `settings.defaultEnforcement` precisely so that no single edit turns every run into a cycle-killing run, and a template that quietly carried `live` would reintroduce exactly that — so a carried non-default mode, and a carried `bypassPermissions`, each raise a banner above the form with a one-click way back to the safe value, and the banner clears the moment the control is touched. `normalizeTemplateInput` also refuses the `no_terminus` pair at the door rather than leaving it to `POST /api/runs`: a template that can be saved but never instantiated fails weeks away from the form that caused it. It refuses a `maxRunCostUSD` or `maxDurationMinutes` that arrives as `""` for a sharper version of the same reason: `budgetFromForm` sends `""` for a limit switched on with its box blank and `null` for one switched off, `normalizePolicy` reads both as no limit, and the run form refuses the first at Start — so a template saved from that form state instantiates fine, with no cap, in the chat and on the canvas, which inherit its guards with no form in front of them. The refusal is the template door's alone; `normalizePolicy` keeps the `null`/`""`/`0`-means-off rule for every other caller, and a blank `maxIterations` is not on the list because it already fails closed, to one cycle. A window guard above 1 is refused on the same footing, and it is the worse of the two because the stored value is wrong rather than missing: the form sends a 0–1 fraction and `normalizePolicy` reads anything above 1 as a percentage and divides it again, so 1.5 from an old build of the form or a direct request would be stored as a 1.5% guard that parks every run the template hands out. `normalizePolicy`'s dual reading stays for every other caller, and `createRun`'s door, whose guard does not outlive the run, is a separate decision. The page's Save runs `limitProblems` from `formProblems.ts` first, which is the limit half of `runFormProblems`, so the sentence lands beside the box in Start's own words. `folder` is nullable and `""` is *not* the null — the empty string is the mount root, the one selection that blocks every other run in the tree. **The template holds a `model`, and it used to refuse one — the paragraph that refused it is replaced rather than deleted, because the premise is what changed.** The refusal said `settings.defaultModel` already set the model globally and the run form did not offer one at all, so a saved model would be a second place to set one thing and the second place is the one nobody remembers to check. The form offers one now, which turns the argument around: a template that cannot save a model silently drops half of what the form was set to. What makes the second place tolerable is `agents.model`'s own ground — **a model moves cost and never capability**. It reaches `--model` and nothing else, every cost guard already covers whatever it selects because the run's spend lands on its own `result` event whatever model produced it, and the two routes to `--permission-mode` are still two. It is free-form for `settings.defaultModel`'s reason, and the triple narrowing `permissionMode` gets deliberately does not apply: that one exists because a permission mode decides what a spawned process may *do*, so a value this build does not recognise must never widen it; this one would only refuse whatever ships next week. **That premise held only for as long as the list would have been this build's, and `settings.modelCatalogue` is not.** It is the operator's own list — seeded from `pricing.ts`' price table so there is no second answer to which models exist, carrying the CLI-shaped `[1m]` ids, and edited in Settings, so a model released after this build is a settings edit rather than a release. **A model released *with* a build reaches an install that already stores a list, and `mergeSeededModels` is the whole of what makes that true.** The settings page has always promised it — a seeded row has no Remove button, and the comment on that button says an operator's own entry never comes back where "the seed comes back on the next release" — and until that function nothing kept the promise: `adoptModelsInUse` writes at most once per install, `saveSettings` pins `modelCatalogue` into the stored blob the moment it differs from `DEFAULTS`, and one model switched off is enough to do that, after which every future seed addition was dead for that install. Claude Opus 5.5 is what found it, priced and labelled and seeded on and on nobody's picker. The merge runs on **every** boot, which is the exact opposite of the rule one function above it, and the asymmetry is the argument rather than an inconsistency: adoption re-reads templates and agents, so running it twice would switch a model back on the morning after the operator switched it off, while this only ever adds an id the stored list does not carry — and a seeded id is one they have no way to remove, since the switch retires it *in place* and a retired entry is present-and-disabled rather than missing. So "absent from a stored list" can only mean "shipped since that list was written", never "taken off", and an install that stores no list is skipped entirely because it is still following `DEFAULTS` and writing would pin it. Order is the seed's, because declaration order is display order and a new model appended to the end would read as the oldest thing on the page; the operator's own entries keep their order and follow, where they already sat. `enabled` is never revisited — it is their answer — and the one field the merge does rewrite is a label still equal to its raw id, which is what both `addModel` and `adoptModelIds` write for a model the build had not heard of and which would otherwise leave `claude-opus-5-5` sitting on a picker underneath "Claude Opus 5". A label is cosmetic and gates nothing, which is what makes that safe. What reads it is the doors that *start work*: `POST /api/runs` (scoped to the Claude provider — a Codex run names something this list has never been told), `PUT /api/settings`, and the chat's `propose_run` and `save_template`. What deliberately does **not** read it is `normalizeTemplateInput` and `rowToTemplate`, and that is the same rule as ever: a template outlives the build that wrote it, so a stored model is neither degraded nor refused where the person who could fix it is not standing. It is validation and never a guard — it may not reach a budget, a work-cycle limit, a permission mode or an isolation choice, and it is not a fifth thing a template supplies. An empty list means no list and refuses nothing. Precedence is stated once and applied once — the run's own model wins, then the template's, then `settings.defaultModel` at `createRun`, and an agent's still only fills a gap where the run named none. **The `settings.defaultModel` rung is the Claude provider's alone, as is every id on this list, and no model id crosses to the other CLI in either direction.** A Codex run that named none freezes null (`frozenRunModel` in `orchestrator.ts`), which `buildCodexArgs` turns into no `-m`, so Codex runs its own default. It used to freeze the Claude default and spawn `codex exec -m claude-…`, with the form's placeholder showing that id as though it were meant; the placeholder and the run page now say "Codex's own default" instead. Blank is not refused for a Codex run, because it has a true meaning for that CLI and the door already declines to check a Codex id against a list it was never told. The other direction is the assist: review, validation and conflict resolution always spawn `CLAUDE_BIN`, so `assistModel` in `review.ts` gives an assist on a Codex run `settings.defaultModel` as read when the assist starts, or no `--model` at all where that is unset, and never the run's own id, which used to reach `claude --model <codex id>`. A Claude run's assist keeps the run's frozen model, as before. Each direction has a unit test that failed on the code it replaced, in `orchestrator.test.ts` and `review.test.ts`. Where it lands differs by surface and that difference is the point: the run form **seeds** the field from it (the treatment `mountId`/`folder` get, so the form's own value is what starts the run and one run can be moved off a template's model without editing the template), while `planProposal` and `planNode` **inherit** it with the prompt and the guards, because there is no form there and a saved model that reached only the form would be one the chat and the canvas silently dropped. `planProposal` reads it *second*, behind a model the chat named on the proposal itself — one more rung on the same precedence rather than a second answer to it — and `planNode` has nothing above it to read. It *also* holds an `agent_id`, which is not another place for a model and not a fourth route to `--permission-mode` — an agent carries a role and no capability, and the model on it is only ever reached where the run itself named none, an explicit `--model` outranking it on the pin. See *A run records the agent it was started as* in `docs/agent/agents-and-templates/agent-references-and-ambient-agents.md` for why that one is a reference where `runs.agent` is a copy.

**Model discovery adds to the catalogue and never edits it, and what it adds moves the install's default rather than its setting.** The list being the operator's closed the build-time gap from one side, a model shipped next week being a settings edit somebody has to know to make; `modelDiscovery.ts` closes it from the other by asking `GET /v1/models` at boot (inside `instrumentation.ts`'s ownership gate, re-asked every tick as the retention sweeper does), every 24 hours after, and on Settings' *Check for models*. It walks every page — `limit=1000`, the documented maximum, then `after_id` set to the page's `last_id` while `has_more` — and merges nothing until the whole listing has parsed, because merging part of one would mark as offered exactly the ids on the pages that loaded. **The credential is the one runs bill against, so the list it fills is the list a run can reach:** `ANTHROPIC_API_KEY` as `x-api-key` when the server has one (`childEnv` passes it to every cycle and the CLI prefers it), otherwise Claude Code's OAuth token as `Authorization: Bearer` with `anthropic-beta: oauth-2025-04-20`, read through `planUsage.ts`'s own `readAccessToken` — only `CLAUDE_CONFIG_DIR`, never refreshed, expired counts as none — rather than a second reader whose terms could drift. There is deliberately no fallback from a refused key to the sign-in: that would list models no run can reach. The token is sent from the server process alone, never logged, returned or handed to a child, and `redact` takes it out of the provider's own error text before that text is stored or shown. **`mergeDiscoveredModels` is the whole of what an operator keeps, and each rule is a configuration that would otherwise change with nothing saying so.** Existing entries come back as the same objects in the same order, so no id, label, switch or position moves. Nothing is removed for being unlisted, because the `[1m]` ids are the CLI's construct and no listing will ever carry one, and a hand-added id may be a model this credential cannot see. Every well-formed id a listing names is recorded as **offered** once it has been put in front of a non-empty list, whether or not it was added — including an id the operator had already typed — and an offered id is never added again, which is the only thing that keeps a Remove removed; "add whatever is missing" would undo it the next morning, enabled. An empty list stays empty and records nothing as offered, because empty means no catalogue and filling it would turn the check back on behind the operator's back. A new id arrives enabled, as a typed one does, under the API's `display_name` with control characters and runs of whitespace removed and the length bounded. Matching is exact, so a dated snapshot such as `claude-sonnet-4-5-20250929` is its own entry beside the undated seed id it prices like; on an existing install the first check will therefore likely add the dated ids the seed spells undated — unmeasured, since no listing has been read here — each removable once and for good. **Every id is held to a strict shape before it may become an entry**, because it reaches `--model` and this is the first door one arrives through unattended: `claude-`, then lowercase letters and digits in runs joined by `-` or `.`, at most 100 characters. That refuses a leading dash, whitespace, brackets and upper case; what it refuses is listed on Settings rather than dropped in silence, and the operator can still type such an id in. **Storage is a record beside the catalogue, merged at read time for an install that never edited its list, and written back only into a list that is already stored.** The record is its own `settings` row, `modelDiscovery` — `offered`, `added`, and the last success and failure — rather than a `Settings` key, because the page PUTs every key it holds and `saveSettings` rebuilds the blob from `SETTINGS_KEYS`, so a record kept there is one any Save could overwrite with whatever the page loaded. `settingsDefaults()` is `DEFAULTS` with the catalogue replaced by the seed plus `added`, laid on through `mergeSeededModels` so a model discovery found first and a later release seeds lands where the seed declares it and keeps discovery's switch — exactly what the boot merge does to a stored list, so the two cannot disagree. Every comparison against "what shipped" reads it, and each one undoes the choice if it does not: `getSettings`, `saveSettings` (which would otherwise store the catalogue the first time anybody saved anything), the settings route's `nonDefaultKeys` (which would otherwise report a list nobody edited as moved), and `adoptModelsInUse` in `db.ts`, which adopts onto it rather than the bare seed — onto the seed, a template naming one discovered model would pin seed-plus-that-one at the next boot and lose every other discovered model for good, since none is offered twice. **Writing the merged list back was the other choice, and it is refused for what it does to the install that never touched the list:** that install would be pinned by a fetch, after which `mergeSeededModelsInto` would still bring it seed *additions* but never again a seeded model a later release switches off, relabels or drops, and the fold would call the list edited when nobody had. A list the operator has stored does get the additions written into it, in one transaction with the record so a Save cannot land between "offered" and "added", because a stored list is what that install follows. A stored list that comes to equal the moved default stops being stored, which is `saveSettings`' existing trade and changes nothing an operator can see. **The page no longer re-sends the catalogue unless it was edited there**, since a copy loaded before a check would otherwise be saved back without what the check added, and offered-once means those models would never return. What remains is an operator who edits the list on a page loaded before the day's check and saves after it: that Save overwrites the check's additions, and the line above the list still names them. *Check for models* stands down while the list has unsaved edits, for the same reason. **A discovered model is not priced by being discovered.** Nothing here touches `pricing.ts` or a guard: a model the table has never heard of shows *Unpriced* on its Settings row, banners as unpriced on a run like any other, and is charged `UNKNOWN_MODEL_PRICE` by every guard. **Scope is the Claude catalogue alone** — Codex and the local provider take no model from it, and discovery reads nothing about either. Which credential path has been measured is in `docs/verification/agents-templates-and-models.md`: neither has been read against a real listing from here, and the OAuth path's acceptance by `/v1/models` is the open question, which is why a refusal is a sentence on Settings naming the status, the endpoint and the credential.
