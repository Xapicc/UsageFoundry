# Isolation, branch chains, landing and the merge queue

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/land.ts, mergeQueue.ts, and resolveIsolation/ensureWorktree in orchestrator.ts.**

**A run can be told to carry on the branch its dependency was working on, and what it claims is the branch rather than the checkout.** `run_deps.continue_branch` is the operator's request and `runs.continues_run` is the resolved decision — the same split `isolate` and `isolation` already make, and the second one exists because `ensureWorktree`, `landState`, `nextPrompt` and the run page all need one greppable column rather than a join. It is on the *edge* because only an edge can say which dependency hands the branch over; a fan-in has several, and at most one may set it. Unlike every other isolation column it is written at **admission**, while the run is still `waiting` and still holds nothing: it is an id and a statement of intent, it costs nothing, and the landing rules have to be able to see a chain coming before its branch exists — a dependent's `worktree_branch` is null until it is released, so a chain read off the branch column reports one link right up until the second one starts, which is exactly the window in which the first looks landable and is not. Two runs continuing the same predecessor is refused at admission: it is two runs on one ref, which git will not check out twice and which leaves the landing rules with no last link to name. Picking a failed continuation up again is `reopenRun`'s job, and that keeps a chain a path.

**A continued branch takes the chain's base, never the predecessor's tip.** `resolveIsolation` is the whole decision — pure, unit-tested across the three modes, and separated from `planWorkspace`'s syscalls for the reason `selectPromotable` is separated from the spawn: both ways of being wrong land on disk and neither throws. `worktree_base` is what `diff.ts`, `review.ts`, `emitHandoff` and the merge itself all measure from, so anchoring on the predecessor's tip would show and land only the last link, with the earlier agents' commits invisible in the review and missing from the patch. `worktree_base_branch` is copied forward for the same reason: the chain lands where it started, not where the folder's HEAD has since got to. The one asymmetry that matters is the error channel, and what falls on each side of it is *why* isolation is not happening rather than which mode asked for it. Isolation being **unavailable** — not a git repository, a bare one, submodules, switched off for the run — degrades to `mode: "none"` with a reason and still does the work in the folder, serialised, which is the work the operator asked for. Isolation being **used up** does not: a continuation that cannot be honoured has always thrown, and an ordinary run on a repository with no checkout slot left now throws too. Degraded, the continuation would silently commit to the target branch with the predecessor's work nowhere in sight, and the ordinary run would put an agent in the operator's own checkout on whatever branch that checkout is standing on, under `acceptEdits` and without even the `git add`/`git commit` grant `buildArgs` gives an isolated run — the exact failure isolation exists to prevent, announced as a scheduling note ("…so this run works in the folder directly and waits its turn"). It also collapsed the parallelism it claimed to preserve, since every downgraded run shares one `conflictKey`. So both are a sentence naming what is missing: `slotExhaustionRefusal` names the repository, the store, the ceiling (`MAX_WORKTREE_SLOTS`, which is a ceiling on *checkouts* and so is `maxConcurrentRuns` plus every slot `slotIsDirty` has retired, not a second concurrency cap), and which of the three causes actually took the slots — the old sentence asserted uncommitted work whatever it had found, so a repository whose slots were merely all in use read as one needing cleaning up. It names a fourth number beside them, and that one is `MAX_SLOT_PROBES_PER_ADMISSION`'s: the walk stops asking git after four checkouts, so on a store where every slot already exists it can give up with some of them unexamined, and a census that folded those into the three would be this admission claiming to have looked at all 64 when it had not. The `SlotCensus` that carries those counts is `allocateSlotPath`'s, taken as it walks, and it is an argument rather than a read for `normalizeWorkflowInput`'s reason. Nothing reclaims a retired slot, so the pressure only ever goes one way: `checkoutStores` is what puts it on the branches page — free of the ceiling, held by live runs, and each retired checkout by name with its uncommitted path count — and it appears at the *first* retired checkout rather than at a threshold, because the point is to be readable long before the refusal arrives.

**The chain claims a branch, not a slot, and that is what makes an unrelated run taking the checkout harmless.** A fresh branch is named from its run's own id, so no other run can ever mint it and a continuation only ever adopts one it was pointed at. The predecessor's slot is preferred and is taken in the same event-loop turn that records it — the property `createRun` already documents — so nothing interleaves between reading `activeRuns()` and joining it, and `allocateSlotPath` skips it from then on. When an active run does hold it, a fresh slot is used and git attaches the existing branch to it: that run took a slot `allocateSlotPath` had already found *clean*, so no uncommitted chain work is ever stranded behind, and it moved the slot off this branch with `checkout -b`, so the branch is free. If it has not got that far, `worktree add` refuses by name rather than branching from somewhere else. `ensureWorktree` therefore takes the third path at each of its three forks — `checkout` rather than `checkout -b`, `worktree add <path> <branch>` rather than `-b`, and past the orphaned-branch guard rather than into it. That guard loses nothing by it: it exists because `-b` would create a *second* branch at the base and leave the run's commits on a ref nothing points at, and attaching to a branch that already exists cannot orphan anything. Its other half is kept as `requireBranch` — a branch `purgeBranch` has destroyed is refused by name, because a `worktree add` there would quietly create a fresh one and produce a run that looks like it is continuing work and is in fact starting over.

**A handed-over checkout keeps what the predecessor left uncommitted, and says how much.** `commitRefusal` already settled whose work is in a slot: it belongs to the run whose branch the slot has checked out, and for a continuation that is this chain. So it is inherited rather than refused — the alternative strands a chain on a directory state the operator has a button for and no reason to look at — and the count goes in the run log and into the agent's own preamble, because silently inheriting somebody else's half-finished edits is the part that would be surprising. A run resuming its *own* checkout is told the old sentence: `iterations`/`pause_count` are what tell a hand-over from a pause, since a continuing run that has worked is resuming its own tree whatever it started from.

**One branch, one Land button: the last run on it, and only once nothing behind it can still commit.** Three runs extending each other share a ref, so every one of them would offer to land it — the operator merges the first, the second still reads unmerged because the branch has moved, and the merge queue takes the same branch once per link. `landRefusal` is where that is decided, pure and unit-tested for exactly this, and both refusals **name a run**: a greyed-out button on a page whose whole purpose is getting work merged is a dead end. The owner is the last member that is not terminal-with-zero-cycles, which is `edgeSatisfied`'s rule reused — a dependent blocked because its dependency failed is recorded on the branch and put nothing on it, and letting it own the branch would leave the run that did the work unlandable for ever. `waiting` counts as unsettled here and nowhere else in this app: it holds no folder and no checkout, but it is a declared future commit on this exact ref. `deleteBranch`, `purgeRefusal` and `resolveConflicts` take the same test through `chainBlocker`, because all three were written when "this run's branch" picked out a branch and a chain is what stopped that being true — the first two would destroy the starting point of a run that has not begun, and the third would pay for a resolution against a branch another run is about to move. `branchInventory` collapses to the owner for the same reason and not merely to tidy the page: that table keys its rows on the branch, so a three-link chain was three rows with one React key, three Land checkboxes and identical counts, and picking two of them queued one branch twice. It is deliberately the only place here that *groups* a chain by `worktree_branch` rather than by `continues_run`, so a `waiting` link — which has no branch yet — is invisible to it and a row can read landable while a run is queued up behind it. That is `canLand`'s existing approximation, and `landRun` re-derives the whole verdict from git and the full chain before anything merges. Which member of that group owns it is still read off `continues_run`, and has to be: the runs arrive `created_at DESC`, a chain is created in a single synchronous pass, and two links sharing a millisecond then come back in whatever order the sort settled on — the same collision `nextQueuedIn` needed `batch_id` for, except that here no tiebreak would do, because the true order *is* the links. Taking the arrival order as the chain's put the wrong link on the page, and the row it kept then refused to land while naming an owner it had never listed, which leaves committed work with no route in the UI that reaches it at all.

**A continuing agent is told whose commits it is standing on.** A different case from `priorWorkNotice` and the difference decides what it does: there the work is the run's own and "carry on from where you stopped" is right, here it is a separate agent's, there was never a conversation to resume, and the branch is the only record. Handed a bare task it does the first thing the task says, which is work already committed under it. `continuedWorkNotice` names the branch, the predecessor and the two commands — `git log --oneline <base>..HEAD` and `git diff --stat <base>...HEAD`, the same range the run page's diff and any review are measured over, so the agent, the reviewer and the merge all look at one thing. **The stat, never the diff**: an opening turn is not read once but re-sent on every turn after it, so a `git diff` ordered here stays resident for the life of the run — five commits of this repo is 176KB of diff against 1.2KB of stat, and the stat names the same files. The facts are generated and only the guidance is `settings.continuedWorkPrompt`: a placeholder an operator can delete is a notice that can silently stop naming the branch. Both notices render when both apply, branch history first — read the other way the agent meets "carry on from where you stopped" before it has been told the work is not its own.

**An isolated run works on a branch, and a worktree contains committed work only.** `seedWorktree` copies the gitignored config files named in `settings.isolationCopyGlobs` and nothing else — dependencies are the agent's job, and slot reuse is what makes that cheap. **A pattern names a path, and one list is not fifteen repositories' answer.** The walk was one `readdirSync` of the repository root filtered by `isFile()`, so a monorepo's `apps/web/.env` could not be named by any pattern at all — the setting says globs and what it matched was a bare filename in one directory. `planSeedCopies` is the traversal and it is pure and unit-tested, taking the directory reader as an argument for `normalizeWorkflowInput`'s reason: it descends only where some pattern's own next segment says to, so the default list still costs exactly one `readdir` and no repository is ever walked whole, and `MAX_SEED_DIRS` bounds the one shape that is not bounded by the pattern itself — a wildcard *directory* segment, against a repository this app did not write. A bare filename still matches a top-level file and nothing else, segment counts having to agree, because reading `.env` as "any `.env` anywhere" would silently widen every existing install's list; `..` and a leading `/` are refused rather than resolved, this being a walk of the operator's own checkout that copies into an agent's. `settings.isolationCopyGlobsByRepo` is the per-repository half, keyed by folder — absolute or relative to any mount, longest key winning, so a key on a parent is a default for the tree under it — and it **replaces** the global list rather than adding to it, which is the only way to say that one repository copies nothing. `copyGlobsFor` is that choice and is pure and unit-tested; falling back to the global list is what keeps an existing install's behaviour exactly what it was. And **"nothing to seed" is not "nothing matched"**: those were one log line with the `(copied …)` clause absent, so a checkout that needed configuration and got none read exactly like one that needed none — which costs a billed cycle failing on a file the operator believes is there, or an agent under `acceptEdits` writing a placeholder config and committing it onto the branch. `seedReport` says which, off `git ls-files --others --ignored --directory` asked only when nothing was copied, and the distinction is `regionsRead: false`'s one file over. The handoff card withholds the `git merge` command entirely while the operator's own checkout is dirty rather than showing it with a caveat, because a copyable command gets copied.

**The tool does now merge, and every protection the old "never merges" rule bought is a check in `land.ts` rather than a caveat.** The operator's checkout must be clean (unreadable counts as dirty, same rule as `emitHandoff`) *and* standing on the recorded target branch — landing onto the wrong branch is the one mistake here with no undo, so it is refused by name rather than caveated. An active run's branch is never landable: `running`/`queued`/`paused` can commit again, and the base that merges cleanly now will not be the base in ten minutes. A failed merge is aborted immediately and the conflicting files reported, so a half-merged index never survives the request. `landRefusal` is pure and unit-tested for exactly these branches, because it is the decision that writes into a directory a person also works in.

**Every branch this app produced is reachable, and the cap is on the page rather than on the set.** `branchInventory` used to take the newest 400 *runs*, collapse them and keep 60 — two truncations that stack, and the second one silently. Branches 61…N were dropped and counted; branches belonging to older runs were dropped *before* the count, so the page could not say they existed because nothing had looked. At twenty-five concurrent runs that is about five hours before committed work stops being reachable from any page in this app. So the candidate set is now its own query over the branch-bearing runs (`isolation='worktree'` with a branch and a repo root, every one of them, newest first) and `selectBranchCandidates` is the pure decision on top of it: collapse to one row per branch *before* the slice, so a page holds sixty branches rather than sixty runs and a five-link chain does not eat five rows; `total` counted over the whole matching set so `notShown` is derived from what exists rather than from what was examined; `repos` counted over the *unfiltered* set, because a filter that hides the repositories you would use to change it is a filter you cannot get out of. What the two caps bound is unchanged and is the point: `MAX_INVENTORY` `rev-list` calls and `MAX_PENDING_PROBES` status probes per request, whatever `repo` and `offset` are set to — they move which sixty branches are paid for, never how many. **What did change is when the second cap is applied, and it had to.** Both per-branch git reads are now resolved after the collection loop under a bounded pool rather than one per turn of it: serially they *were* the request, a `git status` against a 15,082-entry checkout measuring 140 ms and eight of them making up 1.12 s of a 1.13 s `GET /api/branches`, with the cap of twenty putting the worst case at 2.8 s — and neither read decides anything the other or the loop needs. Once they overlap, a `probes < MAX_PENDING_PROBES` test spread across awaits caps nothing: every turn scheduled together reads the counter before any of them has incremented it, so the cap is exceeded by however many started at once and *which* rows got a probe becomes a function of how the event loop interleaved them — two identical requests answering `uncommitted` on different branches, with nothing anywhere saying so. `selectProbeTargets` is that decision, pure and made in one synchronous pass before the first probe is dispatched, and it keeps the answer the serial loop gave: the first `limit` rows, in page order, whose branch some checkout still holds, with rows no checkout holds skipped without spending cap since there is nothing to ask git about. A row nothing probed stays `null`, which the page reads as "not asked" — the same answer a failed probe gives, and never a claim of clean. Only the examined rows are read back in full, so listing sixty branches on a machine with fifty thousand runs does not load fifty thousand prompts. The route is still not polled, for the reason its own comment gives.

**Finding out whether a merge works must cost the operator nothing.** `merge-tree --write-tree` does the three-way merge in memory — no checkout, no index, only unreferenced objects in the object store — so the preview is honest *before* any decision. It needs git ≥ 2.38; an older git reports `unknown`, never "clean". `parseMergeTree` treats every exit code other than 0 and 1 as undetermined for that reason. Those unreferenced objects are also what makes the conflicting *content* free: the tree it writes holds each file as a real merge would leave it, so `withRegions` reads the `<<<<<<<` blocks straight out of it — capped at `MAX_CONTENT_FILES`, since this runs on every load of the land card. A file past that cap keeps `regionsRead: false` rather than an empty list, because "not looked at" and "nothing there" are different sentences and a modify/delete really does leave no markers.

**What conflicts comes from the stage records; why comes from the messages, and only the first is trusted.** `-z` is what makes the conflict type readable at all — the plain output states it only in prose, and finding the path in "CONFLICT (content): Merge conflict in f.txt" means parsing a filename out of a sentence, which is the mistake `splitPatches` exists to avoid. But the informational section's field layout was captured from git 2.50 and the container ships 2.39, so it is parsed defensively and contributes nothing but annotation: an unreadable one loses the type and the explanation and still lists every conflicting file. A message naming a path the stage records did not is **ignored**, never added — what counts as conflicting is what `landRefusal` counts, and that must not shift with a prose format.

**The map at `/runs/[id]/conflicts` draws the preview the land card already fetched, and is allowed to claim less than the list beside it, never more.** It adds no git call, widens nothing `land.ts` reads and puts a clock on nothing — `conflictMap.ts` is a pure reduction over `LandStateDTO` and the page reads the same `GET /api/runs/<id>/land` the card polls. Four rules, each failing silently by drawing something plausible. **The touch map's encoding is not reused and could not be**: that one sizes by `√calls` and a conflicted file has no calls, so every node would draw at the floor radius in one colour — a uniform dot dendrogram, which is a picture of nothing. Size is the clash count (`regions.length + regionsOmitted`) on the same damped curve and the same floor; fill is git's conflict *type*, with `content` and `modify/delete` in different colours because one leaves markers to read and the other leaves none. **`regionsRead: false` is the load-bearing field and it survives the reduction as `null`, never as a zero.** `withRegions` opens only the first `MAX_CONTENT_FILES`, so the path list is complete and the counts are not, and a `modify/delete` that *was* opened holds zero regions honestly — collapsing the two makes an ancestor state a total the preview never had, with nothing on a canvas to contradict it. A node whose count is unknown therefore draws the floor and nothing above it, hollow and dashed, and the card above the map says how many were never opened. It is the exact analogue of `changedKnown` on the touch map. **git's `-z` type field says `contents`, plural, where its message says `content`** — verified against `merge-tree --write-tree -z` on 2.39.5, the version the container ships — so `clashKindOf` takes both spellings, and a type git gave nothing for is its own case rather than the commonest one, because `parseMergeTree` declines to guess there on purpose. **And every way of having no conflict keeps its own sentence.** `already-merged`, `fast-forward` and `clean` are three different true statements; `unknown` is git declining to answer and may never render as a clean merge; a run with no branch, a branch that is gone, and a `conflict` naming no path are three more. `conflictMapView` is that decision, pure and unit-tested, and it tests `branchExists` **before** the outcome: `landState` returns before it previews anything when the branch has gone, so the preview it carries is still the `"Not checked."` placeholder and outcome-first reading buries the sentence saying where the work went. The page draws and never acts — no Land, no Resolve, no Delete — because the card is where every refusal is written and a second surface with the same button is a second place for the chain rules to be wrong. The list on the card is unchanged and stays the primary route; the map is the second one, for the case the list reads worst, and there is exactly one link between them.

**A resolution is shown as what it did, not only as what it said.** `run_reviews.resolved_commit` is read off the isolated checkout the moment the merge commits, because that checkout is removed seconds later and the commit is the only handle on the work afterwards; `resolved_paths` is recorded at the same time so the display is the resolution rather than everything the merge brought across. `resolutionChange` diffs that commit against its **first** parent — the branch as it stood — which is the one framing that never comes back empty: a `--cc` combined diff shows nothing at all for a clash settled by taking one side whole, and "the resolution changed nothing" is exactly the wrong thing to tell someone about to land it.

**Several branches are a queue, never a batch, and the queue re-decides at every turn.** `mergeQueue.ts` reverses the "one button per run" rule, and earns it by keeping what that rule protected: one merge in flight **per repository** (a single sequential worker, one of them per repository and never two), and `landRun` re-deriving the whole `LandState` for every item at *its* turn rather than trusting the answer the page had — each landing changes the base for the one behind it, so a preview taken when the queue was made is worthless by the second item. `position` is the operator's order **within one batch** and the only thing that decides what runs next inside it; it restarts at 0 for the next batch, so it says nothing across batches and `nextQueuedIn` reads `(created_at, batch_id, position)` — one batch at a time, oldest first. Ordering by `position` first is what interleaved a batch queued while the worker was still draining an earlier one (three rows at 0,1,2 and two at 0,1 came out A0, B0, A1, B1, A2), which puts a merge nobody sequenced into the operator's own checkout, and a merge has no undo. `batch_id` is the tiebreak because two batches can share a millisecond — a workflow instance releases its merge blocks in one synchronous pass — and which of those goes first cannot be anybody's order, but interleaving them is still the one outcome nobody chose.

**The repository is the unit of serialisation, not the process.** "Each landing changes the base for the next" is true of two branches in one repository and false of two branches in different ones, so one loop draining every repository was head-of-line blocking and nothing else: a twelve-minute conflict resolution in one of them held every clean branch in all the others, with nothing in their rows saying why and nothing on any page looking wrong. `workers.active` is a `Set` of repository keys pinned on `globalThis`, and **the set is the mutual exclusion** — a repository is claimed before any `await` and released in a `finally`, `createRun`'s folder-claim property, so two calls to `startWorker` cannot both take one. `landing` in `land.ts` is the other half and is unchanged, because it also has to hold against the manual land route, which never goes through this queue. The key is `repo_root ?? folder`, which is what `halted` was already keyed on — the module modelled the repository as the unit that shares state well before the worker did — and `halted` is now a single value per loop rather than a map, the same decision with the key moved into the loop's identity. `MAX_MERGE_WORKERS` bounds the fan-out, and the bound is about money rather than correctness: every worker can be holding a billed resolution child for as long as that child takes, which is *unbounded* — `assistTimeoutMs` gives a `resolve` no clock at all, per the landing-clock rule below, so it runs until it exits, until the batch is cancelled, or until the process ends — and what this change is for is a clean branch not waiting out somebody else's conflict, not parallel spend. Nothing is dropped — a repository over the cap waits for a slot, and the drain that frees one calls `startWorker` again. `resolutionsRefused` stays **process-wide** for the length of a drain rather than becoming per repository: what it records is that the operator's own usage window is spent, which is a fact about the account, and each rediscovery costs a full transcript scan. It is cleared when the last worker leaves, which is what it meant when there was one loop. The join in `nextQueuedIn` is a LEFT one so a row whose run is missing still reaches a worker that can fail it; an inner join would leave it `queued` for ever and make the worker's own "that run no longer exists" branch unreachable.

**Every outstanding batch is on the page, because the worker has never known what a batch is.** `nextQueuedIn` takes the next `queued` row in its repository wherever it sits, so "the queue" is the table rather than one press of Land — but the view was defined as the newest `batch_id` and nothing else. Queue a second repository's branches while the first repository's are still landing and the first went off the page while its merges carried on into a directory a person works in; and since `cancelBatch` is scoped by `batch_id`, a batch the page could not name was a batch nobody could stop. `queueView` answers with every batch holding a `queued`, `landing` or `resolving` row, oldest first, plus the most recently finished one, so a batch's report of what landed survives the next press of Land rather than being replaced by it. A batch is kept **whole** rather than trimmed to its unfinished rows: "1 landed · 2 waiting" is a sentence about a batch, and one cut down to what is left reads as a batch that never started. `selectQueueBatches` is that decision, pure and unit-tested for `planItem`'s reason, and the cap is on *finished* batches alone — bounding the outstanding ones would be this same defect with a larger number in it. **And the finished tail is one only because what it drops is now reachable.** It was three, chosen when a finished batch that left this answer left the app entirely; the tail was never the point, though, it only moved the cliff — a batch is as many rows as branches were selected, so three of them is routinely thirty rows of finished work standing permanently above the branch table (measured on a live install: 1 + 10 + 21), and the fourth batch back was still gone for good. `selectHistoryBatches` is the other end of the same decision and returns exactly what `selectQueueBatches` leaves out, newest first — the two **partition** the finished batches, which is what `mergeQueue.test.ts` asserts across four tail lengths, because a batch in neither is a press of Land with no record anywhere in the app and a batch in both is the same rows twice on one card. `queueHistory(withRows)` is the read: the count costs the one `GROUP BY` the route was already paying for and is what the closed disclosure is labelled with, where the rows are bounded by `MAX_HISTORY_BATCHES` and asked for through `?history=1` only while somebody is looking — the card polls every three seconds while the worker runs, so the closed case has to stay the cheap one. `total` counts every earlier batch rather than the ones read, or a history that stopped at its cap would read as an install that had only ever pressed Land twenty times. What must **not** move behind that disclosure is any batch the worker still owes an answer for: it drains the whole table, so one it is still merging has to be on screen without anybody opening anything, which is this paragraph's own rule with a `<details>` in front of it. `working` stays the worker's own flag and is honest by construction now that it does: the row it can be working on is `landing` or `resolving`, which this view covers by definition, so there is no longer a "busy on something you cannot see" to distinguish. Cancel is a button per group, which is what `batch_id` scoping always permitted and only the page could not express. What a row is waiting behind is counted **across** batches and **within** its own repository, and both halves were arrived at separately: counting within the batch told the second press of Land it was next while five merges stood in front of it, and counting across repositories says the opposite now that they drain in parallel — sixth in line for a branch about to land. `MergeQueueItemDTO.repo` is on the wire for that second half and nothing else.

**A queue tells a branch's problem apart from the checkout's.** `planItem` returns `fail` for the first — the branch behind it is unaffected — and `halt` for the second, which marks every remaining row *in that repository* skipped with one reason instead of scrolling ten identical refusals past. It therefore tests the checkout **before** the conflict, the one place it deliberately disagrees with `landRefusal`'s ordering: that function answers "why can this not be landed", where the conflict is the fact about this branch; this one answers "what should happen next", and paying a model to reconcile a branch into a checkout that will refuse the merge anyway is money spent on nothing.

**Auto-resolution is authorised per batch and recorded per row.** `review.ts` says nothing automatic may reach it, because spend nobody asked for is spend nobody authorised — queueing with the toggle on *is* that authorisation, which is why `auto_resolve` lands on every `merge_queue` row rather than in `settings`, where it could change under a queue already running. `POST` reads it as `=== true` for the same reason `continueAfterDone` does. A refusal that is about the operator's *window* rather than about the branch stops later resolutions being attempted at all: it will refuse every one of them identically, and each attempt costs a full transcript scan to find that out again.

**The worker answers the row it took, including when this app is the thing that broke.** `setStatus` is reachable from `drainRepo` and nowhere else — `cancelBatch` and `cancelQueuedFor` touch `queued` rows alone, and `reconcileMergeQueueOnBoot` needs a restart — so a throw escaping that loop was a row stuck on `landing` or `resolving` for the life of the container, and every row behind it stuck on `queued`. Nothing crashed: Next's own `unhandledRejection` handler logs and carries on, so the server went on serving a panel with a spinner on it. And because `queuedRunIds` counts a stranded row as still in the queue, `enqueue` refused that run **by name** for ever, which left the manual Land button as the only retry — it worked, and the queue row went on saying `landing`, which is the whole of the symptom. So each row's work is wrapped: the row is **failed**, never retried, and the message says the merge state is unknown, because the throw can land after `landRun` has merged into the operator's checkout and written `runs.landed_at` — the same sentence the boot reconciler gives a row it caught mid-merge, for the same reason. It **halts the repository** for `planItem`'s reason: a fault in this app will meet the branch behind this one identically, and each rediscovery is another merge attempted into a directory a person owns. `startWorker()` moved inside the `finally`, where a throw from `nextQueuedIn` itself cannot skip it — outside it, a bad drain stranded every repository the `MAX_MERGE_WORKERS` cap was holding back too.

**`git()` never rejects, and that is a contract rather than an observation.** Every caller in `land.ts` reads a `GitResult` and not one of them has a `catch`, so a rejection was the merge queue's stranded row above. `spawn` demotes exactly `EACCES`/`EAGAIN`/`EMFILE`/`ENFILE`/`ENOENT` to the `error` event this already handled and throws every other errno synchronously — `ENOTDIR` from a `cwd` that has become a file, `EPERM` from `childCredentials()`. `EMFILE` and `ENFILE` are worse than a throw: they *return*, having deliberately skipped the stdio wiring, so `child.stdout` is `undefined` and `setEncoding` is what throws — and file descriptors are the resource this app runs closest to spending, at four merge workers of a dozen git children each beside a fleet of agents. A child that could not be started is now the failed call it is, with the errno in `stderr`, where every caller already looks.

**The queue panel polls whatever it last said.** Gating the interval on "something in the last answer was active" made an idle queue an absorbing state: with no interval running nothing fetched a newer answer, so nothing could say the queue had started again, and the only thing that could restart it was a press of Land in *that* tab. A workflow's merge block queues branches directly and so does a second tab, and both advanced, failed and landed with the page frozen on whatever it happened to be showing — the same sentence as above from the other end. One failed read on load froze it identically, the mount effect running once. So the tick is unconditional, slow while idle and every three seconds while working; it is one `GROUP BY` and no git, where the inventory beside it costs a git process per row and is still read only on the edge. `/api/branches/queue` answers through `jsonNoStore` for that helper's own stated reason: `dynamic = "force-dynamic"` governs Next's cache and puts nothing on the wire, and `cache: "no-store"` on the page's `fetch` speaks only to the browser's.

**A queued merge is cancelled on boot, never resumed.** Same rule as a queued run, for a stronger reason: this one writes into the operator's own checkout, and a server coming back up and merging four branches into the tree someone is working in is the one thing a queue must not do by itself. A row caught mid-merge is failed without a guess about what happened — `landState` will say, from git, the next time anyone asks. Cancelling a batch leaves the row *in flight* alone: a merge is a multi-step write and a resolution is a child holding a checkout, and interrupting either part-way is worse than the second it takes to finish.

**Nothing on the landing path has a clock on it, and that is a rule rather than an omission.** There is no length of time after which merging somebody's work becomes the wrong thing to do, so no timer anywhere decides that a merge has taken too long — a branch that needs ten hours gets ten hours. Five separate ones used to, each a number nobody measured and each failing in the same silent direction: a `SIGKILL`'d `git merge` (two minutes) arrives at `landRun` as `ok: false`, which that function cannot tell from git refusing, so a large repository was told its work conflicted and had it rolled back; a killed `merge-tree` or `status` (twenty) reads as a conflict state that could not be determined or a checkout that could not be read, both of which refuse the land outright; a resolution child killed at ten minutes took the merge with it, since `after` aborts and discards the checkout, so the branch was rolled back with the agent most of the way through; the queue's own twelve-minute wait failed the item and recorded that the branch could not be merged when what had happened was that the loop stopped watching, while the child carried on spending; and a merge block's hour reported its branches as not landed while the queue was still landing them, so the graph carried on past a merge it said had failed. `git()` therefore takes `timeoutMs: 0` — zero is *no clock*, not *kill now* — and `land.ts` passes `NO_CLOCK` at every call that decides or performs a land, `assistTimeoutMs` gives a `resolve` none where a `review` keeps its ten minutes (a review is a card waiting on an answer; a resolution is a step in a merge), and neither `resolveWithClaude` nor `awaitBatch` holds a deadline any more. What the ceilings were protecting against — a wedged child holding the one sequential worker — keeps the escapes that are somebody's *decision*: the assist settles on the child's `exit`, `stopInstance` writes a block off and `awaitBatch` tests that on every pass, `cancelBatch` takes the rest of the queue, and a restart cancels queued rows and fails the one caught mid-merge. The cost is stated rather than absorbed: a `claude` that never exits at all now holds the queue until the container is restarted, which is an operator's call and not a timer's — a clock cannot tell that case from a large merge, and it was ending the large merges.

**The merge target is recorded, never assumed.** `worktree_base` is a *commit*: it says where a branch started, not where it belongs. `probeIsolation` now also records `worktree_base_branch`, and a detached HEAD stores null rather than the literal `HEAD`. Rows written before that column existed fall back to the branch currently checked out — but only after proving the run's base commit is an ancestor of it, which makes it a deduction, and `targetInferred` says so in the UI.

**A squash is landed work that git cannot see.** Squashing rewrites the commits, so the branch is never an ancestor of its target and `merged` is false for ever — which would both offer it for landing a second time and leave it undeletable. `landed_tip` records the branch tip at land time; `landedUnchanged` (tip unmoved) is what stands in for ancestry, and it stops being true the moment the branch gains a commit, which is exactly when deleting would lose something. Branch deletion uses `-d` wherever git can see the merge itself and `-D` only in this case.

**Work an agent left uncommitted goes onto its own branch, and nowhere else.** `commitPending` exists because that state is reachable and its symptoms point the wrong way: before `buildArgs` granted `git add`/`git commit` to an isolated run, every such run ended `completed` with a full checkout and an empty branch, which the land card reported as "this branch has no commits of its own" — a run that looks like it did nothing. It is also what frees the slot, since `ensureWorktree` refuses to reuse a checkout with work in it. The decision is `commitRefusal`, and the branch that earns the unit test is the slot one: a slot is reused, so what is uncommitted in it is only this run's while it still has this run's branch checked out — otherwise the commit lands one run's work on another run's branch, authored by nobody. `add -A` rather than the listed paths, because gitignored files stay ignored and a file written since the page loaded belongs to the same work. A failed commit is left **staged** rather than reset: this app's own git runs with hooks off, so the refusal is git's own and re-running is the likely next move, and the agent may have staged part of it itself. `git status --porcelain` is the one output in this app that must not be trimmed — `" M path"` opens with a space that means "unstaged", and `git()` takes `trim: false` for it alone.

**Getting rid of a branch is two doors, and only the careful one is called Delete.** `deleteBranch` still refuses anything git cannot see as merged — that refusal is all that stands between a stray click and work that exists nowhere else — and `purgeBranch` is the deliberate other one, for the attempt that went nowhere and the slot it is holding hostage. It destroys committed work by design, so the caller has to **name the branch back**: that echo is not authentication and never selects anything (the row still decides what is deleted), it is what stops a request aimed at one branch from landing on another, and what forces the interface to spell out what goes. It force-removes the checkout, which `deleteBranch` will not do, and counts the commits and the uncommitted paths *before* anything is removed so the sentence afterwards says what was lost. Neither door is offered for an active run, and the UI never shows both at once.

**A conflict is resolved on the run's branch, never in the operator's checkout.** `resolveConflicts` merges the *target into the branch* — the opposite direction from landing — inside the run's own checkout when it still holds that branch, and otherwise a throwaway `<slug>-resolve-<id8>` slot that is removed either way. That slot is named for the **run** and not for the repository, which is the half that was missing: the store is shared by every run in the repository, creating the slot begins by force-removing whatever stands at the path, and a resolution holds its checkout for as long as its agent runs — so one `<slug>-resolve` for the whole repository meant a second resolution deleting a live one's working tree with a billed child editing files inside it, and that one's `after` handler then aborting the merge it found in its place. The guard on the way in is per run for the same reason it always was, and `resolveConflicts` now holds a claim on the run from entry until `startAssist` has written the row `assistRunning` reads, since the two callers that reach it — the merge queue draining a repository and the operator's own button — can otherwise both pass a guard that is asking about a row neither has inserted yet. A resolution that goes badly therefore costs a branch nobody has landed yet. The agent resolves **text only**: it runs `acceptEdits` (not `bypassPermissions`) and is told not to run git, because the app stages and commits *after* checking that no marker survived. `unresolvedFiles` treats an unreadable file as unresolved, and any failure ends in `merge --abort` with the branch exactly as it was — an agent that reports success having left `<<<<<<<` in a file is the specific failure this ordering exists to catch. When it succeeds the branch contains the target, so landing becomes a fast-forward and still goes through every check above. `hasConflictMarkers` matches only the two labelled markers, never a bare `=======`, which is a markdown heading underline.


**The check in front of Land, and what an empty one means.** Every other
condition Land enforces is about the *checkout* — clean, on target, nobody
working in it. `landVerifyCommand` is the only one about the **work**: set it
and a non-zero exit refuses the land, leave it empty and Land behaves exactly
as it did before the field existed. An empty command is not a check that
passed, and neither is one that could not be parsed — `landGate.landVerdict`
returns `passed: false` for a malformed command precisely because the operator
asked for a gate, and handing them an open door because their string was wrong
is the failure the field exists to prevent. It is argv and never a shell line:
`parseVerifyCommand` refuses shell metacharacters rather than escaping them,
for the reason `security.md` gives about spawn argv generally. It runs on the
run's own tree, as the child uid, before anything merges — a failing check on
an already-merged branch is a report, and what was asked for was a refusal.

**The other exit.** `deliverRun` pushes a run's branch and opens a pull request
on the checkout's GitHub remote. It is reached from one endpoint on one press
and from nothing in the run loop: an outward-facing action taken by a loop is a
different product from one taken by a person. It never force-pushes, it runs
the same verify gate Land does — an operator who said "not unless this passes"
has said nothing about which exit the work leaves by — and with
`UF_GITHUB_TOKEN` unset it refuses, which is the honest default for a feature
that publishes. The run's timeline carries it as `deliver`, beside `land`:
`land` is work entering the operator's own checkout, `deliver` is it leaving
the machine.
