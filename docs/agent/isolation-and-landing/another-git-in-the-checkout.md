# Another git process in the operator's checkout

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `mergeIntoCheckout`, `passingRefusal`, `PASSING_ATTEMPTS`, `unwind`'s abort or `checkoutStateOf`'s `merging` in `src/lib/land.ts`, or `planItem`'s halt on a merging checkout in `src/lib/mergeQueue.ts`.

**A land that meets another git process's lock is asked again, from a fresh read, four times in all, and only over a checkout proved as it was.** The operator's checkout is a bind mount that the host's own tools read too: an editor's or a shell prompt's `git status` takes `index.lock` to write a refreshed index, and the files a land has just written are what set it off. `GIT_OPTIONAL_LOCKS=0` keeps this app's own reads off that lock (`git.ts`), but nothing here reaches the host's. Of the 72 failed merge-queue rows on the install by 2026-10-26, 35 were that lock — "Unable to write index.", "stash failed", the lock by name, and git's "You have not concluded your merge" on the row behind one — every one since 2026-09-12 and none of them about the branch, and a merge block over them counted failed landings and stopped its loop. `landRun` therefore calls `mergeIntoCheckout` again after one, two and four seconds while the refusal is `passingRefusal`'s kind, no conflict was listed and `unwind` said `restored`. Each attempt asks everything `landRun` re-proves before it writes — the checkout, a run working in the folder, the run's half of the verdict, the shutdown, the past-squash tree — so the rule `lockRefusal` used to cite against retrying, that nothing awaits between the last read of the checkout and the merge's spawn, holds for every attempt rather than being traded away. The verify command and the `commitToLeave` read are not repeated: neither is about the checkout, and the tip the merge takes is the one the check passed. A refusal that is not that kind, or a checkout that is not proved as it was, is never retried, because a second merge onto a tree nobody has looked at is the one thing a land must not do. The sentence a person reads after the last attempt is the first refusal's, with how many times it was tried.

**The abort that takes a refused land back is asked again on the same terms.** Under 2.39.5 a true merge writes MERGE_HEAD before it meets the index lock, and its `merge --abort` needs the same lock (measured, `docs/verification/isolation-and-landing-contention.md`). Asked once, it gave up, the row said the checkout might be mid-merge, and that was the cascade: 10 of the 35 rows left a MERGE_HEAD, and 13 more were the row behind one. `unwind` now asks the abort again on `passingRefusal`'s kind with the same waits. An abort that fails for any other reason — "There is no merge to abort", which is every refused fast-forward — is not asked again, so the common path pays nothing.

**A merge open in the checkout refuses the land and halts the queue, and nothing here aborts it.** `git status --porcelain` lists nothing for a MERGE_HEAD over a tree that matches HEAD, so `checkoutStateOf` read such a checkout as clean, the next land merged into it, met "You have not concluded your merge", and its own `unwind` aborted the leftover under a card saying the checkout was as it was. It happened to be the previous row's leftover; nothing proved that, and a merge the operator has open is theirs. `CheckoutState.merging` is read off `rev-parse -q --verify MERGE_HEAD`, with anything but git's "no such ref" counted as a merge, `dirty`'s rule for an unreadable status. `checkoutRefusal` asks it ahead of `dirty`, since stashing — what that sentence offers — is no way out of a merge, and `planItem` halts on it for the reason it halts on a dirty checkout: it refuses every branch in the repository identically. With the abort asked again this is rare, and when it happens it is one halted queue with one sentence instead of every other row failing.

**The waits are not a clock on the land.** `landing-timeouts.md` rules out any timer that decides a merge has taken too long. These decide nothing about a merge in progress: they are pauses between attempts that have each already ended, seven seconds at most, held under `landing` so nothing else merges into the checkout in between, and a shutdown during one refuses the next attempt at its `isShuttingDown()` read rather than waiting it out.
