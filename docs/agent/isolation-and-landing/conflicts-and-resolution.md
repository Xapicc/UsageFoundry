# Merge previews, the conflicts map and conflict resolution

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `parseMergeTree`, `resolveConflicts`, `openMergePastSquash`, `resolveCheckout`, `commitPending` or `resolutionChange` in `src/lib/land.ts`, `src/lib/checkoutClaim.ts`, `src/lib/conflictMap.ts`, or the `/runs/[id]/conflicts` page.

**Finding out whether a merge works must cost the operator nothing.** `merge-tree --write-tree` does the three-way merge in memory — no checkout, no index, only unreferenced objects in the object store — so the preview is honest *before* any decision. It needs git ≥ 2.38; an older git reports `unknown`, never "clean". `parseMergeTree` treats every exit code other than 0 and 1 as undetermined for that reason. Those unreferenced objects are also what makes the conflicting *content* free: the tree it writes holds each file as a real merge would leave it, so `withRegions` reads the `<<<<<<<` blocks straight out of it — capped at `MAX_CONTENT_FILES`, since this runs on every load of the land card. A file past that cap keeps `regionsRead: false` rather than an empty list, because "not looked at" and "nothing there" are different sentences and a modify/delete really does leave no markers. **A branch landed again after a squash is previewed from the squashed tip, not from git's merge-base** (`squashBase`, and the branch-inventory doc's squash paragraph for why). `merge-tree --merge-base` would say that directly, but it is git 2.40 and the image ships bookworm's 2.39, so `overBase` writes three unreferenced commits — the squashed tip's tree with no parent, and the target's and the branch's trees on top of it — and `merge-tree` finds that root as their merge-base. Same cost class as the trees `merge-tree` already writes, gc takes them, and the identity is passed with `-c` and signing turned off so a repository with no `user.email` or with `commit.gpgSign` does not fail or prompt a preview. A resolution opens its merge from the same base, below. A squash still in the target with nothing after it previews as `already-merged`, never as a merge: measured from anywhere, the target's later edits to the squashed lines read as conflicts in work that has nothing left to land, and `resolveConflicts` refuses with `alreadyOnTargetRefusal`'s sentence before it looks at the preview, as the card's `canResolve` does, so no resolution is bought for a branch that is already in.

**What conflicts comes from the stage records; why comes from the messages, and only the first is trusted.** `-z` is what makes the conflict type readable at all — the plain output states it only in prose, and finding the path in "CONFLICT (content): Merge conflict in f.txt" means parsing a filename out of a sentence, which is the mistake `splitPatches` exists to avoid. But the informational section's field layout was captured from git 2.50 and the container ships 2.39, so it is parsed defensively and contributes nothing but annotation: an unreadable one loses the type and the explanation and still lists every conflicting file. A message naming a path the stage records did not is **ignored**, never added — what counts as conflicting is what `landRefusal` counts, and that must not shift with a prose format.

**The map at `/runs/[id]/conflicts` draws the preview the land card already fetched, and is allowed to claim less than the list beside it, never more.** It adds no git call, widens nothing `land.ts` reads and puts a clock on nothing — `conflictMap.ts` is a pure reduction over `LandStateDTO` and the page reads the same `GET /api/runs/<id>/land` the card polls. Four rules, each failing silently by drawing something plausible. **The touch map's encoding is not reused and could not be**: that one sizes by `√calls` and a conflicted file has no calls, so every node would draw at the floor radius in one colour — a uniform dot dendrogram, which is a picture of nothing. Size is the clash count (`regions.length + regionsOmitted`) on the same damped curve and the same floor; fill is git's conflict *type*, with `content` and `modify/delete` in different colours because one leaves markers to read and the other leaves none. **`regionsRead: false` is the load-bearing field and it survives the reduction as `null`, never as a zero.** `withRegions` opens only the first `MAX_CONTENT_FILES`, so the path list is complete and the counts are not, and a `modify/delete` that *was* opened holds zero regions honestly — collapsing the two makes an ancestor state a total the preview never had, with nothing on a canvas to contradict it. A node whose count is unknown therefore draws the floor and nothing above it, hollow and dashed, and the card above the map says how many were never opened. It is the exact analogue of `changedKnown` on the touch map. **git's `-z` type field says `contents`, plural, where its message says `content`** — verified against `merge-tree --write-tree -z` on 2.39.5, the version the container ships — so `clashKindOf` takes both spellings, and a type git gave nothing for is its own case rather than the commonest one, because `parseMergeTree` declines to guess there on purpose. **And every way of having no conflict keeps its own sentence.** `already-merged`, `fast-forward` and `clean` are three different true statements; `unknown` is git declining to answer and may never render as a clean merge; a run with no branch, a branch that is gone, and a `conflict` naming no path are three more. `conflictMapView` is that decision, pure and unit-tested, and it tests `branchExists` **before** the outcome: `landState` returns before it previews anything when the branch has gone, so the preview it carries is still the `"Not checked."` placeholder and outcome-first reading buries the sentence saying where the work went. The page draws and never acts — no Land, no Resolve, no Delete — because the card is where every refusal is written and a second surface with the same button is a second place for the chain rules to be wrong. The list on the card is unchanged and stays the primary route; the map is the second one, for the case the list reads worst, and there is exactly one link between them.

**A conflict is resolved on the run's branch, never in the operator's checkout.** `resolveConflicts` merges the *target into the branch* — the opposite direction from landing — inside the run's own checkout when it still holds that branch, and otherwise a throwaway `<slug>-resolve-<id8>` slot that is removed either way. **When the slot holds the branch there is no "otherwise"**: git gives a branch to one worktree at a time, so a `worktree add` for it cannot succeed, and `resolveCheckout` therefore reuses or refuses rather than falling through to one that will fail. A slot stopped mid-rebase or mid-bisect of the branch holds it too while reading as detached, so it is refused naming the operation rather than fallen through (`branch-inventory-and-deletion.md`). What it refuses on is `trackedDirt`, never `status --porcelain` being non-empty: an untracked file cannot reach the merge commit — staging is pinned to the conflicted paths and `commit --no-edit` writes the index — and where a merge would clobber one git refuses by name and that refusal is already reported, while a tracked modification is the run's own uncommitted work and a staged one *would* be folded in. Slots collect untracked files from outside this app, so the blunter test made resolution permanently impossible for any run that got some, and said so as `Preparing worktree (checking out '<branch>')` — `worktree add` writes progress to stderr before it fails, so `gitFailureLine` takes the labelled line rather than the first. That slot is named for the **run** and not for the repository, which is the half that was missing: the store is shared by every run in the repository, creating the slot begins by force-removing whatever stands at the path, and a resolution holds its checkout for as long as its agent runs — so one `<slug>-resolve` for the whole repository meant a second resolution deleting a live one's working tree with a billed child editing files inside it, and that one's `after` handler then aborting the merge it found in its place. The guard on the way in asks every run on the branch, for the chain's reason two paragraphs down, and `resolveConflicts` now holds a claim on the branch's checkout (`checkoutClaim.ts`) from entry until `startAssist` has written the row `assistRunning` reads, since the two callers that reach it — the merge queue draining a repository and the operator's own button — can otherwise both pass a guard that is asking about a row neither has inserted yet. A resolution that goes badly therefore costs a branch nobody has landed yet. The agent resolves **text only**: it runs `acceptEdits` (not `bypassPermissions`) and is told not to run git, because the app stages and commits *after* checking that no marker survived. `unresolvedFiles` treats an unreadable file as unresolved, and any failure ends in `merge --abort` with the branch exactly as it was — an agent that reports success having left `<<<<<<<` in a file is the specific failure this ordering exists to catch. When it succeeds the branch contains the target, so landing becomes a fast-forward and still goes through every check above — and the run's diff is measured from the target commit the merge brought in, not from `worktree_base`, or everything the target gained would read as the run's work (`diffRange`, `docs/agent/git-and-review.md`). `hasConflictMarkers` matches only the two labelled markers, never a bare `=======`, which is a markdown heading underline.

**A resolution past a squash opens its merge from the squash, or it resolves conflicts the card never listed.** A plain `git merge` takes git's merge-base, which for a squash-landed chain is still the chain's base, so a target that had since edited the squashed lines conflicted there too, and a resolver keeping the branch's side made the target an ancestor of a branch undoing its edit — Land then fast-forwarded the undo under a success message. So when `squashBase` names a squash, `openMergePastSquash` records the merge with `merge -s ours --no-ff --no-commit` (the target stays the second parent, so landing is still a fast-forward), works the content out with `overBase` and `merge-tree` from the `HEAD` and `MERGE_HEAD` that record names, writes it with `read-tree -m -u`, and marks the conflicted paths unmerged by feeding `merge-tree`'s own stage records to `update-index -z --index-info` (the one call `git()`'s `input` exists for). Everything after it — `conflictedFiles`, `markerlessRefusal`, `after`, `merge --abort`, `resolved_paths` — then meets what a conflicted `git merge` leaves, holding the card's list. The markers carry `overBase`'s commit ids as labels, so `resolvePrompt` says which side is which. Refusing instead was cheaper, and was not taken: a squash-landed chain whose next link conflicts would have no way through but by hand, and the queue's auto-resolve would fail every one.

**No marker left is evidence only about a file git wrote markers into, so a conflict it left none in is refused before the spawn.** A binary clash leaves the branch's bytes whole and a modify/delete or rename/delete the surviving version whole, and the resolver can neither write the other side's bytes nor delete a file. The marker check passed on the untouched file all the same: the merge was committed and recorded `completed`, and Land fast-forwarded the target onto it, undoing the target's own edit or deletion on the target under an ordinary "Merged" message — and the merge queue's auto-resolve did it with nobody present. `markerlessRefusal` therefore reads each conflicted path's stages from `ls-files -u` straight after the merge and before anything is staged, since `git add` clears them and the `ls-files -u` read in `after` cannot see this case, and `unsettleableByEditing` lets through only a path holding both stage 2 (the branch) and stage 3 (the target) whose working file has markers in it. Sides are asked before markers, because a surviving version can hold marker-shaped lines of its own. Anything else aborts the merge, through `rollBackResolution`, and refuses the whole resolution, since the merge commits only once every path is settled: no child is spawned, so nothing is billed, and the sentence names each path, which side has no version, and git's own `CONFLICT`/`warning:` lines as annotation only. The preview's conflict type is not what decides, because it labels a binary clash `contents`. This refusal is also what keeps `resolvePrompt`'s "Each one contains conflict markers" true.

**While a resolution holds the run's checkout nothing else writes to it, and a restart does not hand it back open.** For as long as the agent works, the run's own slot is mid-merge: `MERGE_HEAD` present and the conflicted files `UU` with their markers in them. The run is terminal, so `activeRuns()` does not see the holder, and Commit, Purge and `reopenRun` each went ahead: `add -A` and a commit wrote the markers onto the branch as a two-parent merge, and Land then carried them to the target as a fast-forward, which was executed end to end. So `commitRefusal` and `purgeRefusal` take `resolutionRunning` (`resolutionHolds`: the checkout claim held by a resolution, then the `running` row), the card draws neither button while the resolution runs, and `reopenRun`'s `branchHolderRefusal` asks that claim, `run_reviews` and `merge_queue`, refusing a queue row at `landing` as well as `resolving`. **Reading the claim once is not holding it**, and that left two windows before the row exists. `commitPending` asked `resolutionHolds` once and then awaited `add -A` and `commit`: a resolution entering between them found a slot whose pending work was untracked only, which `resolveCheckout` lets through, opened its merge, and the `add -A` staged the conflicted files — the markers-on-the-branch commit above, from two presses a few hundred milliseconds apart. So Commit takes the claim itself, in the turn that asked, holds it until its commit is made, and a resolution arriving meanwhile is refused with a sentence about the commit. And `reopenRun` could not ask the claim at all while it lived in `land.ts`, which imports `orchestrator.ts`: an operator's resolution has no queue row, so a pick-up in the git calls before its `run_reviews` row was written queued a work cycle, granted `git add` and `git commit`, into the checkout the merge was being opened in. The claim is therefore in `checkoutClaim.ts`, which imports nothing, and it records who holds it — `resolution`, `commit` or `purge` — because each door answers the other with a different sentence. **Purge holds it too, for the same read-once reason.** `purgeBranch` asked `resolutionHolds` once and then awaited `countAhead` and `withRepoAdmin`, whose body force-removes the checkout and deletes the branch, so a resolution pressed in between opened its merge and spawned a billed child in a checkout that was about to go. Conflict markers could not reach a landed branch that way, since the branch goes too; what it cost was the spend, and a resolution whose `after` had nothing left to roll back. So Purge takes the claim in the turn its refusal was asked and holds it until the branch is deleted, and `resolveConflicts`, `commitPending` and `reopenRun`'s `branchHolderRefusal` each refuse in a sentence naming the purge. Its check and take are one call, the folder claim's rule, and `reopenRun` is synchronous from that read to its `UPDATE`, so a resolution entering after a pick-up has the run read as active at entry and refuses itself; that is why `startResolution` needs no second status read before its merge. The claim is on `globalThis` under a key of its own, `__ufCheckoutWriters`, because the `Set` it replaced (`__ufResolving`) had another shape. `resolveCheckout.test.ts` runs those interleavings against a real repository, holding one git call of the first caller until the second has run. The same checkout with nobody left to finish it (a restart while the child ran) is refused from git itself: `commitRefusal` refuses any unmerged status code or an open `MERGE_HEAD`, because `git add` marks a file resolved whatever is still in it, and `resolveCheckout` refuses it with a sentence of its own, since the dirty-slot one told the operator to commit. Both boot reconcilers hand what they caught resolving to `abortInterruptedResolutions`, which aborts only in the run's own slot, while that is a directory in the store still holding its branch, and in its `resolve-<id8>` checkout, never in the operator's; nothing is live at boot, so nothing is aborted under an agent. And `after`'s rollback is checked, not assumed: its `merge --abort` used to go unread, so a merge committed underneath it reported "rolled back; unchanged" about a branch whose target had just become its ancestor. `rollBackResolution` compares the branch tip with the one read before the merge and asks the checkout whether a merge is still open, and says the branch is unchanged only when both agree.

**The hold is the branch's, never the pressed run's, because a chain shares the checkout it protects.** A `continueBranch` link inherits its predecessor's slot (`planWorkspace`) and both rows name one `worktree_path` and one `worktree_branch`, but the claim was keyed on the run id and `resolutionHolds`, `branchHolderRefusal` and the land route read the pressed run's own rows. So while one link's resolution had its merge open in the shared slot with its agent editing there, the other link's card offered Purge, which force-removed the slot under the billed child and deleted the branch; its Pick up queued a cycle granted `git commit` into the open merge; and its Commit, refused only by the git-state check, called the live resolution cut off and told the operator to `git merge --abort` it. Two links' Commit and Resolve took two keys and raced as one run's did before the claim existed. Both directions are reachable: Resolve on a card records the resolution on that card's run, and the merge queue on whichever link it was handed, an earlier one included. So `checkoutClaim.ts` keys on `repo_root` plus `worktree_branch` (a run with no branch keeps its own id), and the `run_reviews` and `merge_queue` reads ask every id `runsOnBranch` returns, which selects on that same pair so that the claim and the rows agree on what the checkout is. The branch rather than the slot path, because git gives a branch to one worktree at a time, so it names the checkout a resolution opens its merge in whether that is the slot or a throwaway, and because a slot is reused by an unrelated run once its own is terminal. The land GET answers `branchResolving` beside the card's own `resolution`, and the card reads either as resolving: no Purge, no Commit, a disabled Resolve, and the poll that notices the resolution finish. `startResolution` deliberately does not refuse a link that is not the branch's owner. With the hold on the branch every link's doors see it, the merge it makes is the one the owner's would make, and refusing it would leave the card offering a button whose whole answer is a refusal, or the card deriving ownership a second time. The merge queue's own route into a non-owner resolution is closed in `planItem` instead (`merge-queue.md`). `resolveCheckout.test.ts` runs both directions.

**A resolution is shown as what it did, not only as what it said.** `run_reviews.resolved_commit` is read off the isolated checkout the moment the merge commits, because that checkout is removed seconds later and the commit is the only handle on the work afterwards; `resolved_paths` is recorded at the same time so the display is the resolution rather than everything the merge brought across. `resolutionChange` diffs that commit against its **first** parent — the branch as it stood — which is the one framing that never comes back empty: a `--cc` combined diff shows nothing at all for a clash settled by taking one side whole, and "the resolution changed nothing" is exactly the wrong thing to tell someone about to land it.
