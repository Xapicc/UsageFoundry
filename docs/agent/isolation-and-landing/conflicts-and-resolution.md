# Merge previews, the conflicts map and conflict resolution

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `parseMergeTree`, `resolveConflicts`, `resolveCheckout` or `resolutionChange` in `src/lib/land.ts`, `src/lib/conflictMap.ts`, or the `/runs/[id]/conflicts` page.

**Finding out whether a merge works must cost the operator nothing.** `merge-tree --write-tree` does the three-way merge in memory — no checkout, no index, only unreferenced objects in the object store — so the preview is honest *before* any decision. It needs git ≥ 2.38; an older git reports `unknown`, never "clean". `parseMergeTree` treats every exit code other than 0 and 1 as undetermined for that reason. Those unreferenced objects are also what makes the conflicting *content* free: the tree it writes holds each file as a real merge would leave it, so `withRegions` reads the `<<<<<<<` blocks straight out of it — capped at `MAX_CONTENT_FILES`, since this runs on every load of the land card. A file past that cap keeps `regionsRead: false` rather than an empty list, because "not looked at" and "nothing there" are different sentences and a modify/delete really does leave no markers.

**What conflicts comes from the stage records; why comes from the messages, and only the first is trusted.** `-z` is what makes the conflict type readable at all — the plain output states it only in prose, and finding the path in "CONFLICT (content): Merge conflict in f.txt" means parsing a filename out of a sentence, which is the mistake `splitPatches` exists to avoid. But the informational section's field layout was captured from git 2.50 and the container ships 2.39, so it is parsed defensively and contributes nothing but annotation: an unreadable one loses the type and the explanation and still lists every conflicting file. A message naming a path the stage records did not is **ignored**, never added — what counts as conflicting is what `landRefusal` counts, and that must not shift with a prose format.

**The map at `/runs/[id]/conflicts` draws the preview the land card already fetched, and is allowed to claim less than the list beside it, never more.** It adds no git call, widens nothing `land.ts` reads and puts a clock on nothing — `conflictMap.ts` is a pure reduction over `LandStateDTO` and the page reads the same `GET /api/runs/<id>/land` the card polls. Four rules, each failing silently by drawing something plausible. **The touch map's encoding is not reused and could not be**: that one sizes by `√calls` and a conflicted file has no calls, so every node would draw at the floor radius in one colour — a uniform dot dendrogram, which is a picture of nothing. Size is the clash count (`regions.length + regionsOmitted`) on the same damped curve and the same floor; fill is git's conflict *type*, with `content` and `modify/delete` in different colours because one leaves markers to read and the other leaves none. **`regionsRead: false` is the load-bearing field and it survives the reduction as `null`, never as a zero.** `withRegions` opens only the first `MAX_CONTENT_FILES`, so the path list is complete and the counts are not, and a `modify/delete` that *was* opened holds zero regions honestly — collapsing the two makes an ancestor state a total the preview never had, with nothing on a canvas to contradict it. A node whose count is unknown therefore draws the floor and nothing above it, hollow and dashed, and the card above the map says how many were never opened. It is the exact analogue of `changedKnown` on the touch map. **git's `-z` type field says `contents`, plural, where its message says `content`** — verified against `merge-tree --write-tree -z` on 2.39.5, the version the container ships — so `clashKindOf` takes both spellings, and a type git gave nothing for is its own case rather than the commonest one, because `parseMergeTree` declines to guess there on purpose. **And every way of having no conflict keeps its own sentence.** `already-merged`, `fast-forward` and `clean` are three different true statements; `unknown` is git declining to answer and may never render as a clean merge; a run with no branch, a branch that is gone, and a `conflict` naming no path are three more. `conflictMapView` is that decision, pure and unit-tested, and it tests `branchExists` **before** the outcome: `landState` returns before it previews anything when the branch has gone, so the preview it carries is still the `"Not checked."` placeholder and outcome-first reading buries the sentence saying where the work went. The page draws and never acts — no Land, no Resolve, no Delete — because the card is where every refusal is written and a second surface with the same button is a second place for the chain rules to be wrong. The list on the card is unchanged and stays the primary route; the map is the second one, for the case the list reads worst, and there is exactly one link between them.

**A conflict is resolved on the run's branch, never in the operator's checkout.** `resolveConflicts` merges the *target into the branch* — the opposite direction from landing — inside the run's own checkout when it still holds that branch, and otherwise a throwaway `<slug>-resolve-<id8>` slot that is removed either way. **When the slot holds the branch there is no "otherwise"**: git gives a branch to one worktree at a time, so a `worktree add` for it cannot succeed, and `resolveCheckout` therefore reuses or refuses rather than falling through to one that will fail. What it refuses on is `trackedDirt`, never `status --porcelain` being non-empty: an untracked file cannot reach the merge commit — staging is pinned to the conflicted paths and `commit --no-edit` writes the index — and where a merge would clobber one git refuses by name and that refusal is already reported, while a tracked modification is the run's own uncommitted work and a staged one *would* be folded in. Slots collect untracked files from outside this app, so the blunter test made resolution permanently impossible for any run that got some, and said so as `Preparing worktree (checking out '<branch>')` — `worktree add` writes progress to stderr before it fails, so `gitFailureLine` takes the labelled line rather than the first. That slot is named for the **run** and not for the repository, which is the half that was missing: the store is shared by every run in the repository, creating the slot begins by force-removing whatever stands at the path, and a resolution holds its checkout for as long as its agent runs — so one `<slug>-resolve` for the whole repository meant a second resolution deleting a live one's working tree with a billed child editing files inside it, and that one's `after` handler then aborting the merge it found in its place. The guard on the way in is per run for the same reason it always was, and `resolveConflicts` now holds a claim on the run from entry until `startAssist` has written the row `assistRunning` reads, since the two callers that reach it — the merge queue draining a repository and the operator's own button — can otherwise both pass a guard that is asking about a row neither has inserted yet. A resolution that goes badly therefore costs a branch nobody has landed yet. The agent resolves **text only**: it runs `acceptEdits` (not `bypassPermissions`) and is told not to run git, because the app stages and commits *after* checking that no marker survived. `unresolvedFiles` treats an unreadable file as unresolved, and any failure ends in `merge --abort` with the branch exactly as it was — an agent that reports success having left `<<<<<<<` in a file is the specific failure this ordering exists to catch. When it succeeds the branch contains the target, so landing becomes a fast-forward and still goes through every check above — and the run's diff is measured from the target commit the merge brought in, not from `worktree_base`, or everything the target gained would read as the run's work (`diffRange`, `docs/agent/git-and-review.md`). `hasConflictMarkers` matches only the two labelled markers, never a bare `=======`, which is a markdown heading underline.

**While a resolution holds the run's checkout nothing else writes to it, and a restart does not hand it back open.** For as long as the agent works, the run's own slot is mid-merge: `MERGE_HEAD` present and the conflicted files `UU` with their markers in them. The run is terminal, so `activeRuns()` does not see the holder, and Commit, Purge and `reopenRun` each went ahead: `add -A` and a commit wrote the markers onto the branch as a two-parent merge, and Land then carried them to the target as a fast-forward, which was executed end to end. So `commitRefusal` and `purgeRefusal` take `resolutionRunning` (`resolutionHolds`: the `resolving` claim, then the `running` row), the card draws neither button while the resolution runs, and `reopenRun` asks `run_reviews` and `merge_queue` directly, `land.ts` importing `orchestrator.ts`, refusing a queue row at `landing` as well as `resolving`. The same checkout with nobody left to finish it (a restart while the child ran) is refused from git itself: `commitRefusal` refuses any unmerged status code or an open `MERGE_HEAD`, because `git add` marks a file resolved whatever is still in it, and `resolveCheckout` refuses it with a sentence of its own, since the dirty-slot one told the operator to commit. Both boot reconcilers hand what they caught resolving to `abortInterruptedResolutions`, which aborts only in the run's own slot, while that is a directory in the store still holding its branch, and in its `resolve-<id8>` checkout, never in the operator's; nothing is live at boot, so nothing is aborted under an agent. And `after`'s rollback is checked, not assumed: its `merge --abort` used to go unread, so a merge committed underneath it reported "rolled back; unchanged" about a branch whose target had just become its ancestor. `rollBackResolution` compares the branch tip with the one read before the merge and asks the checkout whether a merge is still open, and says the branch is unchanged only when both agree.

**A resolution is shown as what it did, not only as what it said.** `run_reviews.resolved_commit` is read off the isolated checkout the moment the merge commits, because that checkout is removed seconds later and the commit is the only handle on the work afterwards; `resolved_paths` is recorded at the same time so the display is the resolution rather than everything the merge brought across. `resolutionChange` diffs that commit against its **first** parent — the branch as it stood — which is the one framing that never comes back empty: a `--cc` combined diff shows nothing at all for a clash settled by taking one side whole, and "the resolution changed nothing" is exactly the wrong thing to tell someone about to land it.
