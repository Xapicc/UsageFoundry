# Clocks on the checkout start path

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `CHECKOUT_GIT_TIMEOUT_MS`, `checkoutGit`, `ensureWorktree` or `finishCutOffCheckout` in `src/lib/orchestrator.ts`, or `gitFailureReason` and `timedOutAfterMs` in `src/lib/git.ts`, and before adding a git call to the path that gives a run its checkout.

**A git call that walks a whole tree while a run is given its checkout has thirty minutes, not `git()`'s twenty seconds.** The reuse path's `status --porcelain` and `checkout` / `checkout -b`, the handover's `status`, `finishCutOffCheckout`'s `status` and `reset --hard`, and both `worktree add`s go through `checkoutGit`. Twenty seconds is a `SIGKILL` in the middle of a call that is making progress, and on a checkout whose files are slow to read (an iCloud Drive vault with most of its notes evicted) it is reached with nothing stuck. Decided 2026-10-25, after the nightly Dreaming run `a8be776a` failed at setup with `Could not start branch …: ` and nothing after the colon. This is not the landing rule above it: landing has no clock because there is no length of time after which merging becomes wrong, whereas a hung `checkout` holds a run's slot and its repository's start path, so a bound is right and only has to be longer than slow. `rev-parse`, `worktree prune` / `list` / `unlock` and `requireBranch` read no working tree and stay on the default, where twenty seconds already means hung and a longer clock would only make a hung one slower to report.

**A call the clock ended says so, and the reason is never empty.** A kill arrives as `ok: false`, `code: null` and an empty `stderr` — the shape of a git that could not be started — so a message built from `stderr` alone ended at its own colon. `git()` returns `timedOutAfterMs`, null unless its clock killed the child, and `gitFailureReason` turns a failed result into one of three sentences: the clock's, naming the command, the checkout and the time; git's own `stderr`, unaltered; or a statement that git printed nothing. An unreadable `status` is refused as "could not tell whether … has uncommitted work", not "still has uncommitted work": it used to be the latter, which sent an operator to clean a tree that was never dirty.

**A leftover `index.lock` is git's to explain, and nothing here removes it.** A `checkout` killed by the clock leaves its lock in the slot's git directory, and the next run to reuse the slot fails with git's "Unable to create …/index.lock: File exists", which reaches the run's reason as git wrote it (`checkoutGitClock.test.ts`). Deleting a lock would be a guess that no other git holds it, so the slot stays refused until the operator clears it. Three calls on this path stay on the default clock and degrade rather than fail the run when it kills them: `slotIsDirty` (admission; unreadable counts as dirty, so the slot is skipped), `unseededIgnoredFiles` (reports nothing about seeding), and the filter probe in front of every content subcommand.
