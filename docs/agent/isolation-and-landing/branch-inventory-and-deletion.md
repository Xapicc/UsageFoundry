# Branch inventory, squashes and deleting a branch

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `branchInventory`, `deleteBranch` or `purgeBranch` in `src/lib/land.ts`, `withRepoAdmin` in `src/lib/repoLock.ts`, or `GET /api/branches`.

**Every branch this app produced is reachable, and the cap is on the page rather than on the set.** `branchInventory` used to take the newest 400 *runs*, collapse them and keep 60 — two truncations that stack, and the second one silently. Branches 61…N were dropped and counted; branches belonging to older runs were dropped *before* the count, so the page could not say they existed because nothing had looked. At twenty-five concurrent runs that is about five hours before committed work stops being reachable from any page in this app. So the candidate set is now its own query over the branch-bearing runs (`isolation='worktree'` with a branch and a repo root, every one of them, newest first) and `selectBranchCandidates` is the pure decision on top of it: collapse to one row per branch *before* the slice, so a page holds sixty branches rather than sixty runs and a five-link chain does not eat five rows; `total` counted over the whole matching set so `notShown` is derived from what exists rather than from what was examined; `repos` counted over the *unfiltered* set, because a filter that hides the repositories you would use to change it is a filter you cannot get out of. What the two caps bound is unchanged and is the point: `MAX_INVENTORY` `rev-list` calls and `MAX_PENDING_PROBES` status probes per request, whatever `repo` and `offset` are set to — they move which sixty branches are paid for, never how many. **What did change is when the second cap is applied, and it had to.** Both per-branch git reads are now resolved after the collection loop under a bounded pool rather than one per turn of it: serially they *were* the request, a `git status` against a 15,082-entry checkout measuring 140 ms and eight of them making up 1.12 s of a 1.13 s `GET /api/branches`, with the cap of twenty putting the worst case at 2.8 s — and neither read decides anything the other or the loop needs. Once they overlap, a `probes < MAX_PENDING_PROBES` test spread across awaits caps nothing: every turn scheduled together reads the counter before any of them has incremented it, so the cap is exceeded by however many started at once and *which* rows got a probe becomes a function of how the event loop interleaved them — two identical requests answering `uncommitted` on different branches, with nothing anywhere saying so. `selectProbeTargets` is that decision, pure and made in one synchronous pass before the first probe is dispatched, and it keeps the answer the serial loop gave: the first `limit` rows, in page order, whose branch some checkout still holds, with rows no checkout holds skipped without spending cap since there is nothing to ask git about. A row nothing probed stays `null`, which the page reads as "not asked" — the same answer a failed probe gives, and never a claim of clean. The same probe reads `MERGE_HEAD` beside the status, so a row says when its checkout is mid-merge — `MERGE_HEAD` or an unmerged code, either alone, as `commitRefusal` reads them — and `offersCommit` withholds Commit there and the row says so, rather than letting the press discover the refusal the Land card already states. `merging` false means "not seen", which is also what an unprobed row says, so it withholds nothing. **A run's own slot stopped mid-rebase or mid-bisect is the same kind of fact, and `worktree list` cannot give it:** both detach HEAD, so the slot is listed `detached` and has no `branch` line for the holder map to read. The one listing also returns the detached checkouts, and a row whose branch nothing holds but whose run's own slot is one of them has that slot as its probe candidate — the probe asks `slotMidOperation` first and the status only if it finds the slot part-way through an operation *on that branch*. Only then does the row read `heldByCheckout`, carry `operation`, and have `offersCommit` withhold Commit with the state named; a plain detached HEAD answers nothing and the row reads as it did. `selectProbeTargets` caps these exactly as it caps held rows, so an idle detached slot spends one probe and no more, and a stopped rebase's unmerged paths are the rebase's and never `merging`. Only the examined rows are read back in full, so listing sixty branches on a machine with fifty thousand runs does not load fifty thousand prompts. The route is still not polled, for the reason its own comment gives.

**A squash is landed work that git cannot see.** Squashing rewrites the commits, so the branch is never an ancestor of its target and `merged` is false for ever — which would both offer it for landing a second time and leave it undeletable. `landed_tip` records the branch tip at land time and `landed_commit` the commit the squash made on the target; `landedUnchanged` — tip unmoved, **and that commit still an ancestor of the target** — is what stands in for ancestry. It stops being true the moment the branch gains a commit or the target loses the squash, and those are exactly when deleting would lose something. The second half is not optional: the recorded tip says which commits were taken and nothing about whether the target still has them, so after an operator undid a land with `reset --hard ORIG_HEAD` — git's own undo, and the only one there is — the branch read "squashed in", Land was refused as already squashed, and Delete removed the only ref the run's commits were in. Only a squash is read at all (`landed_strategy = 'squash'`): a merge's commit makes the tip an ancestor of the target, so ancestry is the whole answer and goes false by itself when the merge is reset away. A squash landed before `landed_commit` existed has nothing to prove it by, and reads as not landed — kept, and refused by Delete, which leaves Purge for it — because the other reading is the one that loses work. `deleteBranch.test.ts` undoes a merge and a squash through `landRun` and asserts the Land card, the branches row and Delete all read the branch as unlanded. **And once a branch has gained commits past a squash, it is measured from the squash, not from git's merge-base.** A squash leaves no ancestry, so the merge-base between the target and the branch stays where the chain started, and counting, previewing or landing from there takes the squashed work a second time: a change the operator reverted on the target after the squash came back under a clean preview and a success message, a later edit on the target to the squashed lines refused the next link for a conflict in a file it never touched, and the count included the squashed commits. `squashBase` is the decision — the newest squash on the chain whose commit the target still has, whose tip the branch still contains, and whose tip the target does not (a later merge moves git's own merge-base past it) — and `landState` counts `rev-list <branch> ^<squashed tip> ^<target>`, previews over `overBase`, and the inventory counts the same way; a conflict resolution opens its merge from it too (`conflicts-and-resolution.md`). `landRun` works the merge out in the object store first, before the recheck, so a conflict refuses with the checkout untouched; then `read-tree -m -u <target as read> <merged tree>` stages it — a commit the operator made to the target meanwhile is carried forward, and one that overlaps is refused with nothing written — and a squash commits it as before, while a merge is recorded with `merge -s ours --no-commit` first, so the commit keeps the branch as its second parent and the branch is an ancestor of the target afterwards. `landAfterSquash.test.ts` drives all of it through `landRun`. **It is read across the chain** — any run on the branch whose `landed_tip` is the tip — because `landRun` writes it on the run that landed, which on a `continueBranch` chain is the owner at the time. Read per run, every other link saw a squashed branch as never landed: a link queued after its owner had squash-landed was failed with the owner refusal rather than recorded `already-landed`, a later link that added nothing owned the branch and was offered for landing again — replaying the squash — and Delete refused the branch from any link but the one that landed it. `landState`, `branchInventory`, `deleteBranch`'s compare inside its claim and retention's `branchIsSettled` all take `isLandedTip` over `chainRuns`, and it is the one place either half is decided. The Land card reads the same pair the same way: `landCardLine` (`landView.ts`) says "merged" only while `merged || landedUnchanged`, because `landed_at` is never cleared and a reopened run can commit again — after that the refusal is the line, and the earlier land sits beneath it as history. Deleting it goes through the same compare-and-delete a merged branch does, below.

**Delete deletes the exact tip it proved, and proves it against the target, never against whatever the operator has checked out.** It used to delete with `git branch -d`, kept as a second opinion on the ancestry test, and `-D` for a squash. But `-d` asks a different question — merged into the branch's upstream or, with none, into HEAD of the repository's main working tree, which is the operator's own checkout — so whenever that checkout stood on a branch without the run's work, every merged branch was refused as "not fully merged" (reproduced against git 2.39.5), and refused *after* its slot had been removed. So inside the `withRepoAdmin` claim `deleteBranch` reads the tip once, proves it again — an ancestor of `refs/heads/<target>`, or, for a squash, equal to a `landed_tip` some run on the chain recorded whose `landed_commit` that target still has — before anything is removed, and deletes with `git update-ref -d --no-deref refs/heads/<branch> <tip>`, which refuses if the ref no longer points there. That is the property `-d` was chosen for, never deleting a branch that moved since it was judged, and the squash case now has it too, so the `-d`/`-D` split is gone. Two things `git branch` did and `update-ref` does not are now `deleteBranch`'s. It does not refuse a ref a checkout is standing on, so **removing the holder first is load-bearing**: a clean slot is removed, and the operator's own checkout — which git will not `worktree remove` — refuses the Delete. A worktree stopped mid-rebase or mid-bisect on the branch lists as detached, so `worktreeHolding` does not see it, and `worktreeMidOperation` is the rest of git's refusal (`find_shared_symref`): it reads `rebase-merge/head-name`, `rebase-apply/head-name` and `BISECT_START` in the repository's git directory and each `worktrees/<id>`, inside the claim and before the holder is removed, and refuses the Delete naming that checkout. The commits are in the target either way, so what it protects is the operation's last step — the rebase's final ref write, `bisect reset`'s checkout — which would otherwise fail and leave the checkout detached. A git directory it cannot read is a refusal too, never an idle checkout. And it does not drop the `[branch "…"]` section Deliver's `push --set-upstream` writes, so `dropBranchConfig` does, and the success message says so when it could not. `purgeBranch` keeps `branch -D`: it deletes whatever the tip is by design, and git's own checked-out refusal is exactly the one it wants about every checkout but the run's own slot, which Purge removes first, mid-rebase included (below). `deleteBranch.test.ts` drives it against a real repository with the operator's checkout elsewhere.

**Getting rid of a branch is two doors, and only the careful one is called Delete.** `deleteBranch` still refuses anything git cannot see as merged — that refusal is all that stands between a stray click and work that exists nowhere else — and `purgeBranch` is the deliberate other one, for the attempt that went nowhere and the slot it is holding hostage. It destroys committed work by design, so the caller has to **name the branch back**: that echo is not authentication and never selects anything (the row still decides what is deleted), it is what stops a request aimed at one branch from landing on another, and what forces the interface to spell out what goes. It force-removes the checkout, which `deleteBranch` will not do — **and the run's own slot stopped mid-rebase or mid-bisect of the branch is that checkout too.** An agent that ran `git rebase main` and stopped on a conflict ended its run there, and `worktreeHolding` reads the detached slot as holding nothing, so Purge skipped the removal and `branch -D` was refused as checked out at that very slot on every press: the attempt that went nowhere and the slot it holds hostage, with the one door meant for both shut. So inside the claim, when nothing holds the branch, `purgeClaimedBranch` asks `worktreeMidOperation` and takes the checkout it names as the holder when that is the run's `worktree_path`; removing it ends the operation and `branch -D` lets go. Anybody else's — the operator's checkout, a worktree made by hand — is still left to git's refusal, and so is a git directory that could not be read, since git reads the same files before it deletes. The other doors read that slot through `slotMidOperation`, the same reading asked of one checkout: `slotState` reports it as `operation`, and Commit (`commitRefusal`), the verify gate (`verifyTreeVerdict`) and Resolve (`resolveCheckout`) each refuse naming the rebase or bisect and the command that ends it, where they called the checkout gone, taken over by a later run, and — through a second `worktree add` — already checked out. The Land card says it before any of them is pressed: `pendingWork` returns the slot with `operation` set even when nothing is uncommitted, because the state is what it exists to report, and the card's heading is the state beside the command from `OPERATION_ENDED_BY` (`landView.ts`, which a client bundle can reach and `land.ts` cannot) with no Commit row. It draws no Resolve or Delete there either, and a landed branches row no Delete, because `resolveCheckout` and `deleteBranch` refuse each in that state; Purge is keyed on what Delete would have been, so the destructive door never takes a withheld Delete's place. `slotState` reads the status of such a slot for the one reason the Purge sheet counts what it removes. It counts the commits and the uncommitted paths *before* anything is removed so the sentence afterwards says what was lost. A count git will not give is null and is said to be, on the sheet, the armed button and that sentence alike, never 0: the branch with no recorded target is counted from `worktree_base` (`aheadRangeFor`), and "Purge 0 commits" over one that could not be counted told the operator there was nothing to lose. Neither door is offered for an active run, and the UI never shows both at once.

**The other doors are claimed too, and by a *second* claim, because they are
not about that folder.** `landing` is the operator's checkout — a directory a
person also works in — and it **refuses**, which is the honest answer for
something that takes minutes. What `resolveCheckout`, `deleteBranch` and
`purgeBranch` share with the run loop is the repository's
`$GIT_DIR/worktrees` registry, and `withRepoAdmin` (`repoLock.ts`) is that one:
keyed on the repository root, and it **waits** rather than refusing, because the
run loop is one of the four callers and a refusal there would fail a run start
because somebody pressed Delete. `git worktree prune` is the operation that
makes it necessary — it is the only one here that is repository-wide rather than
scoped to a named entry, so it is the one git's own per-entry locking does not
serialise. Two rules for the sections it brackets. **They are short**: the
registry read and the removals are in, and `worktree add` and the seeding copy
after it are deliberately out, so concurrent run starts in one repository still
overlap where the cost is. And **the read that decides is inside the claim that
acts** — `worktreeHolding` moved in for both deletion doors, since a slot read
outside is a slot another caller may since have taken or freed. `commitPending`
takes neither and needs neither: it writes into the run's own checkout with
`add`/`commit`, touches no registry, and already tests for a live holder.
**None of this is evidence of a collision** — nothing has ever reproduced one,
which is why `proposals/GapRegister/` ranks that row on blast radius; it closes
the app-level interleaving, which is the half this repository owns.
