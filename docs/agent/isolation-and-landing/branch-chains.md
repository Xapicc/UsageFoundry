# Branch chains

Split out of `worktrees-and-branch-chains.md` on 2026-10-25; what a worktree contains, the merge target, and the slot and column rules a chain leans on are there.

**A run can be told to carry on the branch its dependency was working on, and what it claims is the branch rather than the checkout.** `run_deps.continue_branch` is the operator's request and `runs.continues_run` is the resolved decision — the same split `isolate` and `isolation` already make, and the second one exists because `ensureWorktree`, `landState`, `nextPrompt` and the run page all need one greppable column rather than a join. It is on the *edge* because only an edge can say which dependency hands the branch over; a fan-in has several, and at most one may set it. Unlike every other isolation column it is written at **admission**, while the run is still `waiting` and still holds nothing: it is an id and a statement of intent, it costs nothing, and the landing rules have to be able to see a chain coming before its branch exists — a dependent's `worktree_branch` is null until it is released, so a chain read off the branch column reports one link right up until the second one starts, which is exactly the window in which the first looks landable and is not. Two runs continuing the same predecessor is refused at admission: it is two runs on one ref, which git will not check out twice and which leaves the landing rules with no last link to name. The one pair let through is `dependencies.md`'s, an `on-success` and an `on-failure` continuer, and `admitWaiting` asks again at release because time defeats that pair: a completed predecessor picked up and ended failed meets the second condition after its sibling has committed, and the late run fails naming the sibling (`branchRivalOf`) rather than committing beside it. Picking a failed continuation up again is `reopenRun`'s job, and that keeps a chain a path — including for a continuer that ran no work cycle, which admission reads as holding nothing and a pick-up queues directly once it holds a workspace. `reopenRun` asks such a row the release pass's two questions again (`unworkedPickupRefusal`, which asks every edge of any such row, not only a continuer's: `dependencies/release-and-blocking.md`) and refuses it naming the run when another continuer has taken the branch since (`branchRivalOf`, on its own edge), and with `releasableRuns`' sentence when the predecessor, picked up meanwhile, no longer meets that edge: an `on-success` run is never queued behind a failure onto the branch its fixer took. A row going back to `waiting` is asked both by the release pass instead.

**A continued branch takes the chain's base, never the predecessor's tip.** `resolveIsolation` is the whole decision — pure, unit-tested across the three modes, and separated from `planWorkspace`'s syscalls for the reason `selectPromotable` is separated from the spawn: both ways of being wrong land on disk and neither throws. `worktree_base` is what `diff.ts`, `review.ts` and `emitHandoff` measure from, and git's merge-base for the merge itself is the same commit, so anchoring on the predecessor's tip would show and land only the last link, with the earlier agents' commits invisible in the review and missing from the patch. That reason holds for links that have not landed. Once a link is squash-landed its commits are in the target, and the next land, and any resolution of its conflicts, is measured from its squashed tip instead (`squashBase`, in `branch-inventory-and-deletion.md`), while the review and diff still run from the chain's base and so show the squashed work too — more than lands, never less. `worktree_base_branch` is copied forward for the same reason: the chain lands where it started, not where the folder's HEAD has since got to. The one asymmetry that matters is the error channel, and what falls on each side of it is *why* isolation is not happening rather than which mode asked for it. Isolation being **unavailable** — not a git repository, a bare one, submodules, switched off for the run — degrades to `mode: "none"` with a reason and still does the work in the folder, serialised, which is the work the operator asked for. Isolation being **used up** does not: a continuation that cannot be honoured has always thrown, and an ordinary run on a repository with no checkout slot left now throws too. Degraded, the continuation would silently commit to the target branch with the predecessor's work nowhere in sight, and the ordinary run would put an agent in the operator's own checkout on whatever branch that checkout is standing on, under `acceptEdits` and without even the `git add`/`git commit` grant `buildArgs` gives an isolated run — the exact failure isolation exists to prevent, announced as a scheduling note ("…so this run works in the folder directly and waits its turn"). It also collapsed the parallelism it claimed to preserve, since every downgraded run shares one `conflictKey`. So both are a sentence naming what is missing: `slotExhaustionRefusal` names the repository, the store, the ceiling (`MAX_WORKTREE_SLOTS`, which is a ceiling on *checkouts* and so is `maxConcurrentRuns` plus every slot `slotIsDirty` has retired, not a second concurrency cap), and which of the three causes actually took the slots — the old sentence asserted uncommitted work whatever it had found, so a repository whose slots were merely all in use read as one needing cleaning up. It names a fourth number beside them, and that one is `MAX_SLOT_PROBES_PER_ADMISSION`'s: the walk stops asking git after four checkouts, so on a store where every slot already exists it can give up with some of them unexamined, and a census that folded those into the three would be this admission claiming to have looked at all 64 when it had not. The `SlotCensus` that carries those counts is `allocateSlotPath`'s, taken as it walks, and it is an argument rather than a read for `normalizeWorkflowInput`'s reason. Nothing reclaims a retired slot, so the pressure only ever goes one way: `checkoutStores` is what puts it on the branches page — free of the ceiling, held by live runs, and each retired checkout by name with its uncommitted path count — and it appears at the *first* retired checkout rather than at a threshold, because the point is to be readable long before the refusal arrives.

**The chain claims a branch, not a slot, and that is what makes an unrelated run taking the checkout harmless.** A fresh branch is named from its run's own id, so no other run can ever mint it and a continuation only ever adopts one it was pointed at. The predecessor's slot is preferred and is taken in the same event-loop turn that records it — the property `createRun` already documents — so nothing interleaves between reading `activeRuns()` and joining it, and `allocateSlotPath` skips it from then on. When an active run does hold it, a fresh slot is used and git attaches the existing branch to it: that run took a slot `allocateSlotPath` had already found *clean*, so no uncommitted chain work is ever stranded behind, and it moved the slot off this branch with `checkout -b`, so the branch is free. If it has not got that far, `worktree add` refuses by name rather than branching from somewhere else. `ensureWorktree` therefore takes the third path at each of its three forks — `checkout` rather than `checkout -b`, `worktree add <path> <branch>` rather than `-b`, and past the orphaned-branch guard rather than into it. That guard loses nothing by it: it exists because `-b` would create a *second* branch at the base and leave the run's commits on a ref nothing points at, and attaching to a branch that already exists cannot orphan anything. Its other half is kept as `requireBranch` — a branch `purgeBranch` has destroyed is refused by name, because a `worktree add` there would quietly create a fresh one and produce a run that looks like it is continuing work and is in fact starting over.

**A handed-over checkout keeps what the predecessor left uncommitted, and says how much.** `commitRefusal` already settled whose work is in a slot: it belongs to the run whose branch the slot has checked out, and for a continuation that is this chain. So it is inherited rather than refused — the alternative strands a chain on a directory state the operator has a button for and no reason to look at — and the count goes in the run log and into the agent's own preamble, because silently inheriting somebody else's half-finished edits is the part that would be surprising. A run resuming its *own* checkout is told the old sentence: `iterations`/`pause_count` are what tell a hand-over from a pause, since a continuing run that has worked is resuming its own tree whatever it started from.

**A continuing agent is told whose commits it is standing on.** A different case from `priorWorkNotice` and the difference decides what it does: there the work is the run's own and "carry on from where you stopped" is right, here it is a separate agent's, there was never a conversation to resume, and the branch is the only record. Handed a bare task it does the first thing the task says, which is work already committed under it. `continuedWorkNotice` names the branch, the predecessor and the two commands — `git log --oneline <base>..HEAD` and `git diff --stat <base>...HEAD`, the same range the run page's diff and any review are measured over, so the agent, the reviewer and the merge all look at one thing. **The stat, never the diff**: an opening turn is not read once but re-sent on every turn after it, so a `git diff` ordered here stays resident for the life of the run — five commits of this repo is 176KB of diff against 1.2KB of stat, and the stat names the same files. The facts are generated and only the guidance is `settings.continuedWorkPrompt`: a placeholder an operator can delete is a notice that can silently stop naming the branch. Both notices render when both apply, branch history first — read the other way the agent meets "carry on from where you stopped" before it has been told the work is not its own.
