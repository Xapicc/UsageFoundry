# A verify command on a slot a later run reused

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `verifyRunBranch`, `verifyBranchForReview`, `verifyGateOf`, `verifyOnSwitchedSlot`, `switchRefusal`, `switchBlocker`, `switchBack`, `verifyInSlot` or `verifyHeldSlot` in `src/lib/land.ts`, or `borrowSlot`, `slotHolder`, `holdSlot`, `isSlotBorrowed`, `planWorkspace`'s `inheritedSlot` or `reopenRun`'s slot check in `src/lib/orchestrator.ts`. Split out of `land-verify-and-deliver.md` on 2026-10-08, which holds the gate this one shares with Land and Deliver; the block itself is in `workflows-and-schedules/review-blocks-and-providers.md`. Written for the review block, whose switch Land and Deliver took over the same day (the last section).

**A review block's verify command takes the same two steps, and nothing about the slot is read twice.** A review block whose verdict is a command runs its own saved line — never `landVerifyCommand` — through `verifyBranchForReview`, which is `verifyRunBranch` asked as `"review"`: `verifyTreeVerdict` then `verifyInSlot`: the run's own slot, clean and on its branch, held from `allocateSlotPath` until the command returns, and the branch proved not to have moved under it. A copy of either would be the failure `land-verify-and-deliver.md` describes, one tree checked and another handed on. One branch at a time, so two suites never share a repository's ports or caches at once. What differs is the asker, `VerifyAsker`: a refusal keeps its first sentence and drops Land's last — "Nothing was landed", "Clear the command in Settings" — which names a door and a setting a review block is not. `asker` is optional and absent is Land, so Land's and Deliver's sentences are unchanged byte for byte. `VerifyOutcome` carries `ending` and `tail` beside Land's `reason` for the same reason: the block words its own note from them, and its timeout note carries the output, which Land's sentence never did. A branch the block approved is checked again at Land when `landVerifyCommand` is set; the block's verdict is about the branch, not a pass through the gate. The block takes no `landing` claim, so Land pressed on a branch it is checking runs a second command in the same slot; `holdSlot` counts holders so neither release ends the other's hold.

**A slot a later run reused is switched back to the run's branch for the command, and put back after, because the block judges when every branch has finished and by then the early slots are somebody else's.** `allocateSlotPath` gives the lowest clean slot to the next isolated run in the repository, and a finished run whose work is committed leaves one. So an orchestrator fanning out more runs than `maxConcurrentRuns` lets run at once has runs 4..N take the slots of runs 1..3, and the block then met runs 1..3 in slots holding other branches and set every one aside unchecked, each time. The shape is wider than that fan-out: any isolated run started in the repository between a run finishing and the block judging it takes the slot the same way. `verifyBranchForReview` therefore answers a slot that is there, readable and standing on a different branch — not gone, not mid-rebase, not detached — with `verifyOnSwitchedSlot`: `borrowSlot` the slot, read it again under that hold, require an empty `status --porcelain -z`, no `MERGE_HEAD` and a branch that still exists, `git checkout <branch> --`, run the command through `verifyHeldSlot` (the body of `verifyInSlot` after its hold, so the tip comparison is the same code), and `switchBack`. It is `ensureWorktree`'s own move for a new run, and for its reason: reuse needs only a clean `git status`, which ignores gitignored files, so `node_modules` and build output are still there for `npm test`.

**Anything that stops the switch refuses with the original sentence and says why nothing was switched, and nothing unrun is approved.** A slot holding uncommitted paths (named, five at most), a merge open, a branch deleted or checked out in another worktree, a status git could not read, and a slot an active run is working in are each set aside, "it was not switched back to X for the check, because …". The active run is not waited for, since it may be hours; a verify command another holder already has running there is, because it ends within `VERIFY_TIMEOUT_MS` and says nothing about the branch: `busy` on `ReviewVerifyOutcome`, which `settleReviewByCommand` waits out at `MERGE_POLL_MS` and which a halt ends at the usual check. A branch set aside over a land's press would be judged by the schedule.

**The borrow is exclusive, and the writers it keeps out are the reason, not a convenience.** `verifyInSlot` compares the branch's ref after a pass, not the tree the command ran in, so a second writer that switched the checkout to *another* branch mid-command leaves the first branch's ref where it was and the check passes on a tree that was half one branch and half another. `borrowSlot` refuses while any `holdSlot` holder is in the slot; `holdSlot` refuses a borrowed slot in turn (Land's and Deliver's press gets its own sentence, "a review block is running its own check in …"); `planWorkspace` does not hand a borrowed slot to a continuation, which takes a slot of its own and has git attach the branch to it; and `reopenRun` refuses a run whose checkout is borrowed. `allocateSlotPath` already skipped a held slot. `reviewBlockRun.test.ts` pins the `holdSlot`, `planWorkspace`, `reopenRun` and wait-for-a-holder halves, trying the first three from inside the running command; Land's sentence for a borrowed slot is not pinned.

**The exclusion runs from the other side too, because `holdSlot` and `borrowSlot` only keep out what asks them (decided 2026-10-20, board tasks 92ffa0e0 and f6983243).** Three doors that write to or remove a checkout never asked, and were let into a slot a command was running in. Purge's `worktree remove --force` removed the *later run's* checkout while a switched check held this run's branch in it — the holder `worktreeHolding` names is the borrowed slot, and `activeRuns()` does not see a borrower — so the later run lost its ignored files and was then told a later run had taken its checkout over. Delete's plain `worktree remove` takes the ignored files with it as well. And Resolve's `resolveCheckout` opened its merge in the tree being checked, so the block recorded a pass for a tree with `MERGE_HEAD` and conflict markers in it. `checkHoldsSlot` (`slotHolder(slot) === "check"`, which a borrow also is) now refuses all three in the hold's own words, saying whether the slot is the run's own or a later run's switched checkout and "Nothing was deleted" or "Nothing was started"; it is asked in the turn that starts the removal and not before an `await`, `holdSlot`'s reason, and `resolveCheckout` has no second checkout to cut instead, since git gives a branch to one worktree. The retention checkout sweep keeps a held slot for the same reason: its second occupancy read is `slotHolder`, not `activeRuns()`, because a settled run past the horizon is the profile of a candidate whether or not a block is checking another branch in its directory.

**A pass is not recorded over a tree something wrote to.** After the tip comparison `writtenDuringCheck` refuses a pass when the slot has `MERGE_HEAD` or a modified tracked path, because neither moves the ref the comparison reads. It covers what the refusals above cannot: a resolution that claimed the checkout before the command took its hold and opened its merge after, and a continuation the hold cannot see. Untracked and ignored files are left alone, build output being what a command writes. **A command that itself rewrites a tracked file now fails its own gate** (a formatter, a regenerated lockfile): from the slot that is the same picture as a foreign writer, the refusal names the path, and the fix is for the output to go to an ignored path. Pinned in `landAfterVerify.test.ts`, "kept from Purge, Delete and Resolve", and in `retentionSweep.test.ts`.

**The switch back is best effort and never a verdict.** The branch has been judged by then, and a slot left on the run's branch is a clean checkout like any other that `allocateSlotPath` reuses. `switchBack` leaves it where it is, with a `console.warn`, when HEAD moved off the branch while the command ran, when the command left uncommitted paths — a switch would carry them onto the later run's branch, whose Commit button would then offer them as its work — and when git refuses, for instance because a continuation has since attached the later run's branch to a slot of its own. What a left slot costs is the later run's own view: its Land card reads the slot as taken over until something switches it back, which its own Land or Deliver now does. While the command runs the same is true of the later run, and its pending-work read is empty, by `slotState`'s rule that nothing under another branch is the run's; the slot was proved clean before the switch, so nothing is hidden.

**What the check still cannot tell from the work.** The ignored files are whatever the slot's last branch left, as for every run that reuses a slot, so a branch that changes its dependencies is checked against the previous branch's `node_modules`, and one that deletes a source file against a stale build directory. A command failing for that reason is set aside with its output, and nothing here can tell it from a failing branch. A fresh worktree would fail every `npm test` for a certain reason; this fails some for a possible one.

**Options not taken, and why, for whoever reopens it** (board task 5e2c7ffa). *A temporary worktree seeded with the slot's dependency tree* needs machinery this app does not have: `isolationCopyGlobs` copies the operator's own `.env` files from their checkout into a new slot, not a dependency tree from another slot; copying `node_modules` per branch is hundreds of megabytes (543 MB in this repository) and seconds each; a copied Python `.venv` carries absolute paths and does not run; and a symlinked `node_modules` resolves real paths from where it lives, the trap `CLAUDE.md` records for `.next`. *Keeping the slot from reuse while a later block will verify it* puts a graph question on the admission path, which `allocateSlotPath` keeps to a bounded number of synchronous probes; needs a reservation with a lifetime, which an abandoned instance leaks; takes a slot out of `MAX_WORKTREE_SLOTS` per branch of a fan-out; and does nothing for an unrelated run starting in the repository, which takes the slot just the same. *Leaving it and warning in the editor* cannot be written as a rule about the graph, since fan-out beyond `maxConcurrentRuns` is only one of the ways a slot is reused, and it leaves the early branches never landing.

**Land and Deliver switch a slot a later run took over, as the block does (decided 2026-10-08, board task 4b2c2080; a concurrency change).** `landRun` and `deliverRun` call `verifyRunBranch(run, command, "land" | "deliver")`, the function the block's `verifyBranchForReview` is the `"review"` asker of, so there is one switch and not a copy. What each part of the question was decided as:

- **The card says what the press will do.** `landState` asks `verifyGateOf` once `landRefusal` and `seededRefusal` have nothing to say. A taken-over slot that `switchRefusal` finds switchable is no longer in `blocked`; `LandState.verifySwitch` carries `{ path, holds }` and the card draws "The check switches X from Y to this branch and back". One that is not is blocked in the press's own sentence (`unswitchedReason`: the original, why nothing was switched, "Nothing was landed. Try again once that checkout is free, or clear the command in Settings"). The poll must not claim the slot to find out, so `switchRefusal` is `slotHolder` (a read of `borrowSlot`'s two refusals) then `switchBlocker`, the same reads the press makes under its hold. The extra reads are a `status`, a `MERGE_HEAD`, a `rev-parse` and a `worktree list`, only for a slot standing on another branch with a command set; not re-measured. The hint is hidden when something else refuses the land, so a Deliver pressed past a conflict is switched without being announced.
- **A press during another's switch is refused, not waited for.** The slot is borrowed, `slotHolder` says `check`, and both the card and the press give "because another verify command is running in it". Only the block waits (`busy`): it is a loop that asks again, and a press waiting up to `VERIFY_TIMEOUT_MS` would hold the `landing` claim, and a queue's worker, behind someone else's command.
- **The merge queue is unchanged.** `planItem` reads `blocked`, so a switchable row is `land` and `landRun` switches it; an unswitchable one fails in that sentence at its turn, a row whose slot a review block happens to be checking then included, and is queued again by hand.
- **The `landing` claim and the borrow compose without a cycle.** Land takes `landing` on the operator's folder, then borrows the run's slot; the block takes only the borrow. Neither waits for the other while holding: the exits refuse a borrow, and the block waits for a *check* holding no claim. Two Lands of runs that share a slot, in different folders, are serialised by the borrow.
- **The switch is undone before anything is merged.** `switchBack` is in `verifyOnSwitchedSlot`'s `finally` and awaited, so it is done before `verifyRunBranch` returns. `landRun` reads the tip, `landRecheck` of the *operator's* checkout (never the slot) and `unsettledBranchRefusal` from a fresh `getRun` and `branchChain` after that; Deliver's push likewise. A `switchBack` that cannot (HEAD moved, the command left paths) leaves the slot on the run's branch with a `console.warn`, which changes nothing about the merge and is undone by the later run's own Land.
- **Two runs whose slots hold each other's branches are refused, not worked around.** git lets a branch be checked out in one worktree, so `switchBlocker` now says "X is checked out in Y" where it used to pass on git's own line, for the block as well. The command is not run in Y, because the run's checkout is the one it recorded. Neither can be landed with a command set until one slot is moved by hand or the command cleared.
