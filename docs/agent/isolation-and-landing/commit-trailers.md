# Commit trailers: which run wrote this

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `src/lib/runTrailers.ts`, `stampCycleCommits` and its one call in the run loop in `src/lib/orchestrator.ts`, or any `git commit`, `git merge -m` or `commit-tree` this app runs in `src/lib/land.ts`. Board task `f0ee509b` (adopted by the operator, 2026-10-31); the reasoning there is the vault's `This Vault as an Agent Memory Store.md`, item 3.

**Every commit on a run's branch used to carry the one identity the container is configured with.** "Everything the run that wrote bad notes wrote" was recoverable only from a branch name in a merge subject, and a fast-forward land (the vault's usual one) leaves not even that: 87 of the vault's 88 commits on 2026-10-31 had the same author. A commit now names its run in its message: `UF-Run: <run id>`, one `UF-Task: <task id>` per board task the run was started for (`run_tasks`, since `runs.task_id` is no longer written), `UF-Night: <date>` on a Dreaming night's run (from `origin_ref`), and `Model: <model id>`. `git log --grep 'UF-Run: <id>'` lists a run's commits and `git log --format='%(trailers)'` shows the rest. **The author and committer are never touched.** This is a trailer and not an identity: `git shortlog`, blame and a forge's account mapping read the author, and changing it would break every attribution the operator already has.

**Two routes, split by who makes the commit.**

- **The app's own commits take their trailers where they are made.** `commitPending` (the Commit button, and Dreaming's landing commit, which is that call) and the squash commit pass `--trailer`; the merge commit of a land is handed a second `-m` paragraph (`git merge -m a -m b` writes `a`, a blank line, `b`: measured on 2.39.5); a resolution's merge, and a land past a squash, restate their message with `commit -m <subject> -m <trailers>`. They are restated because `--trailer` on top of a conflicted merge's `MERGE_MSG` wrote the block twice: `MERGE_MSG` ends in `# Conflicts:` comment lines, so the `-m` block was not the last paragraph and `interpret-trailers` did not see its own neighbour (measured). A fast-forward makes no commit, so there is nothing to label at the land; the commits it brings carry the second route's stamp.
- **The agent's own commits are stamped by this server after the cycle that made them.** `stampCycleCommits` runs right after the child is gone and before anything reads the branch, and calls `stampBranchCommits`, which re-makes each unlabelled commit with `git interpret-trailers` over `git commit-tree`: the same tree, the same author, committer and dates from the commit's own headers, a parent mapped to its stamped self. Every new commit is written before the branch moves, and the move is `update-ref <new> <old>`, so a commit that arrived meanwhile leaves the branch where it was with nothing half-stamped.

**Why not a hook, and why not at land.** A `prepare-commit-msg` hook was the first candidate and cannot be this app's. `git()` runs with `core.hooksPath=/dev/null` (`git.ts`), so no hook of the repository's reaches a commit the app makes; a hook for the agent's commits means writing into `.git/hooks`, which `gitDirWatch` reports as tampering with the repository; `core.hooksPath` pointed at ours by environment would shadow the repository's own hooks; and every one of them can be undone by the process whose commits it labels. The vault's own note says the same of hooks in general: they live in `$GIT_DIR/hooks`, which is not repository content, and `--no-verify` skips the commit-time ones. The stamp is done by this server after the agent's process has exited, and nothing the agent does inside a cycle can prevent it. **`git interpret-trailers` at land time was the other candidate, and it rewrites a branch that has already been judged.** `run_reviews.head_sha` certifies a SHA (a local branch's land gate compares it with the tip), `verifyRunBranch`'s proof is a SHA (`commitToLeave`), and `squashBase` needs the tip an earlier land recorded to stay an ancestor of the branch, which a rewritten branch need not be. Stamping at land would invalidate the first two and break the third for every chain that landed before this existed. At the end of a cycle nothing has read the tip yet, and the stamp is the same tool.

**What `stampBranchCommits` never rewrites.** Commits reachable from the target (`worktree_base_branch`) or from any tip an earlier run on the same branch landed (`runs.landed_tip`): a branch that merged the target in carries the target's commits, and rewriting one would fork the target's history. A commit that already has a `UF-Run` trailer, which is a continuation's earlier link stamped by its own cycle, so a chain is never relabelled with the last run's id. All or nothing: a commit with a `gpgsig`, `mergetag` or `encoding` header cannot be re-made faithfully, and one in the range stops the whole stamp. More than `STAMP_MAX_COMMITS` (500) commits ahead of the target also stops it.

**What it cannot cover, and what says so.**

- A run that works in the operator's own checkout (`isolation: none`). Its commits go onto the operator's branch, which no run may rewrite. They are unlabelled, and nothing says so.
- A cycle whose stamp was skipped: the run's target was not recorded, the checkout was on another branch, the range was too large or held a signed commit, or the branch moved during the stamp. The run's log says `Run trailers were not added to <branch>: <why>.` and the branch is as the agent left it. If the cause has gone by the next cycle, that cycle's stamp picks the commits up and labels them with its run's id, which is the right run unless a continuation made them.
- Commits that exist from before this: the vault's history, and an unlanded branch's earlier commits. The first are never touched. The second carry no trailer, so the next run that continues the branch labels them as its own.
- A commit the operator makes by hand in a run's checkout, and a commit made by a process that outlives the cycle (a background task the CLI did not wait for).
- `Model` is the model the run was *asked* to use. A run on the CLI's default has no `Model` trailer, because this app does not know what the CLI picked, and a fallback model that answered instead is not named. A merge the app made, and a resolution's, carry none either: no model wrote a clean merge, and the resolver's is not the run's.

**The stamp changes SHAs, so it runs where no SHA has been read.** Anything new that records a run's branch tip during or before a cycle's end has to read it after `stampCycleCommits`, in the same turn of the loop; the three readers that exist (`run_reviews.head_sha`, `verifyInSlot`, `landed_tip`) all come later.
