# The merge queue: a row's turn

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `planItem`, `drainRepo`, `processOne` or `resolveWithClaude` in `src/lib/mergeQueue.ts`, `git()` in `src/lib/land.ts`, or the queue panel that polls `/api/branches/queue`. How the queue is ordered, split across repositories, shown and restarted is in [merge-queue-batches-workers-and-boot.md](merge-queue-batches-workers-and-boot.md).

**A queue tells a branch's problem apart from the checkout's.** `planItem` returns `fail` for the first — the branch behind it is unaffected — and `halt` for the second, which marks every remaining row *in that repository* skipped with one reason instead of scrolling ten identical refusals past. It therefore tests the checkout **before** the conflict, the one place it deliberately disagrees with `landRefusal`'s ordering: that function answers "why can this not be landed", where the conflict is the fact about this branch; this one answers "what should happen next", and paying a model to reconcile a branch into a checkout that will refuse the merge anyway is money spent on nothing. **And it resolves only when the conflict is why the land is refused.** `landRefusal` asks the run's half, `unsettledBranchRefusal`, before the conflict, so a chain link that is not its branch's owner is refused at the land whatever a resolution does to the branch. An auto-resolve batch bought one for it anyway, waited for it, and failed the row with the owner refusal and the resolution's cost beside it. `planItem` therefore fails such a row with `blocked` and spends nothing, as it does with auto-resolve off. A live loop pass is the one refusal of that half the state cannot see, since it depends on the asker, and `resolveConflicts` refuses that one itself before anything is spent. A branch a local model wrote on is the same case from the certification side: its row fails with that gate's sentence, nothing spent, and why it is not resolved and reported as awaiting review is in `local-provider.md`. **A branch the verify gate refuses is the same case.** With `landVerifyCommand` set the gate refuses a land without running anything for an uncommitted path in the run's slot (it counts untracked files, which `resolveCheckout` lets through), a detached slot, or one a live later run holds, and `landRun` asks it only after a resolution has been committed onto the branch. An auto-resolve batch bought one anyway, and the row ended `failed` with the gate's sentence and the resolution's cost beside it, over a merge commit nobody asked for; a merge block with `mergeAutoResolve` in a loop paid that every pass. `landState` therefore reads the gate beside a conflict too, into `resolveGateRefusal`, and `planItem` fails the row with the conflict sentence and the gate's, nothing spent; `startResolution` refuses the same for a batch asker, for a state a poll newer than the plan's. It is not `resolveBlocked`, which the card withholds Resolve on: a person may resolve such a branch and commit what the gate names afterwards, so the field is read only when the asker is a batch, and the card's poll never pays for it. The queue does not bet on a resolver that would commit the untracked path along with its merge: the batch authorised resolving a conflict, not committing an agent's scratch. What the read costs, measured 2026-10-20 by counting git children of one `landState` over a conflicting branch: nothing with no command set or in a slot holding the branch (16 either way), and 13 → 19 in a slot a later run stands in, which is `switchRefusal`'s reads, once per row's turn. **A third answer is neither problem:** a branch whose work reached its target between being queued and its turn — a successor in the same batch carried it, or somebody merged it by hand — is `skip`, recorded `already-landed` with `alreadyOnTargetRefusal`'s sentence. Not `failed`, because a workflow merge block counts a failed row against itself and a loop stops on it over work that is where it belongs; and not `skipped`, because that is the halt's word and a merge block has to go on reading it as a branch that never got there. It is asked apart from `blocked`, since `landRefusal` names a chain's owner before it asks whether the branch is in; ahead of the checkout, which a branch with nothing to merge never needed; and never for a run that can still commit, whose empty branch is an ancestor of its target too. **Two links of one chain in one batch are one row, the owner's.** A workflow merge block wired to both ends of a `continueBranch` link queues both — nothing at Save refuses the graph, and every pass of a loop repeats it — and only the owner may land the ref, so the other link was failed with the owner refusal whenever it came first, and under a squash when it came second as well, because `landed_tip` is written on the owner alone; the block then counted a failed landing over work its owner had carried to the target. `enqueue` therefore drops a link whose chain owner is also selected. That was chosen over having `planItem` skip the link at its turn because at that turn the owner may not have landed yet, and the row would have to claim a landing that had not happened. A link whose owner was *not* selected is queued as asked, and its turn is where the refusal naming the owner belongs, with no resolution bought first whatever the batch authorised — unless the owner already landed the branch in an earlier batch and it has not moved since, which that turn records `already-landed`, because `landedUnchanged` is read across the chain rather than off the link's own `landed_tip`.

**A checkout something else holds is waited for, and never recorded against the row.** A person's own Land or Deliver holds `landing` on the folder for its whole verify command, merge, push and pull request, and a run working in the folder holds it for as long as it works. `landRun` refused a row meeting either with a sentence and nothing more, the drain recorded it `failed`, and the next row met the same hold: measured on `50d60d8` (board task 007f23a2), a repository's whole queue failed within about fifty milliseconds, each row reading as its own fault, and a merge block over it counted failed landings for branches nobody had tried to merge and stopped its loop. That is neither `fail`, since nothing is wrong with the branch, nor `halt`, since it clears without a person. `landRun` now marks both refusals `heldCheckout`, and `drainRepo` puts the row back `queued` saying what holds it — the panel shows that in place of "Next to be landed" — and waits on `checkoutHeld`, a `Set` read and a runs query with no git, once a second, re-reading `isShuttingDown()` and whether the repository still has anything queued on every look, and with no clock on the wait, by the landing-clock rule. Back to `queued` rather than held at `landing`, because `queued` is what Cancel, a shutdown and the boot already reach: a row held `landing` would be out of Cancel's reach and would keep the shutdown's grace waiting on somebody else's land. A resolution paid for on the turn that met the hold stays on the row, which is why `resolve_cost` adds. The cost, stated: a waiting worker keeps its `MAX_MERGE_WORKERS` slot, so a fifth repository waits behind a run working in a fourth's checkout for as long as that run works. `deliverRun` marks nothing, because the queue never calls it; the queue meets its claim through `landRun`.

**Auto-resolution is authorised per batch and recorded per row.** `review.ts` says nothing automatic may reach it, because spend nobody asked for is spend nobody authorised — queueing with the toggle on *is* that authorisation, which is why `auto_resolve` lands on every `merge_queue` row rather than in `settings`, where it could change under a queue already running. `POST` reads it as `=== true` for the same reason `continueAfterDone` does. A refusal that is about the operator's *window* rather than about the branch stops later resolutions being attempted at all: it will refuse every one of them identically, and each attempt costs a full transcript scan to find that out again. A conflict git left no markers in is the other kind: `resolveConflicts` refuses it before its spawn (`conflicts-and-resolution.md`), so the row fails with that sentence at no cost and never reaches `landRun`, and the next branch's resolution is still attempted, because a binary file or a modify/delete in one branch says nothing about the next. Before that refusal the row was the worst case in this file — a resolver that could change nothing recorded `completed`, and the land that followed undid the target's own change with nobody present. Under the install-wide hold the queue refuses a resolution at `processOne`, after `landState`, and again in `startResolution` before `startAssist`, both with `HELD_RESOLUTION_REFUSAL`, and fails the row rather than waiting, for the reason in [a review block is held at its claim and at each review's door, and a merge block only at its conflict resolution](../run-lifecycle/fleet-stop-hold-and-set-aside.md).

**The worker answers the row it took, including when this app is the thing that broke.** `setStatus` is reachable from `drainRepo` and nowhere else — `cancelBatch` and `cancelQueuedFor` touch `queued` rows alone, and `reconcileMergeQueueOnBoot` needs a restart — so a throw escaping that loop was a row stuck on `landing` or `resolving` for the life of the container, and every row behind it stuck on `queued`. Nothing crashed: Next's own `unhandledRejection` handler logs and carries on, so the server went on serving a panel with a spinner on it. And because `queuedRunIds` counts a stranded row as still in the queue, `enqueue` refused that run **by name** for ever, which left the manual Land button as the only retry — it worked, and the queue row went on saying `landing`, which is the whole of the symptom. So each row's work is wrapped: the row is **failed**, never retried, and the message says the merge state is unknown, because the throw can land after `landRun` has merged into the operator's checkout and written `runs.landed_at` — the same sentence the boot reconciler gives a row it caught mid-merge, for the same reason. It **halts the repository** for `planItem`'s reason: a fault in this app will meet the branch behind this one identically, and each rediscovery is another merge attempted into a directory a person owns. `startWorker()` moved inside the `finally`, where a throw from `nextQueuedIn` itself cannot skip it — outside it, a bad drain stranded every repository the `MAX_MERGE_WORKERS` cap was holding back too.

**`git()` never rejects, and that is a contract rather than an observation.** Every caller in `land.ts` reads a `GitResult` and not one of them has a `catch`, so a rejection was the merge queue's stranded row above. `spawn` demotes exactly `EACCES`/`EAGAIN`/`EMFILE`/`ENFILE`/`ENOENT` to the `error` event this already handled and throws every other errno synchronously — `ENOTDIR` from a `cwd` that has become a file, `EPERM` from `childCredentials()`. `EMFILE` and `ENFILE` are worse than a throw: they *return*, having deliberately skipped the stdio wiring, so `child.stdout` is `undefined` and `setEncoding` is what throws — and file descriptors are the resource this app runs closest to spending, at four merge workers of a dozen git children each beside a fleet of agents. A child that could not be started is now the failed call it is, with the errno in `stderr`, where every caller already looks.

**The queue panel polls whatever it last said.** Gating the interval on "something in the last answer was active" made an idle queue an absorbing state: with no interval running nothing fetched a newer answer, so nothing could say the queue had started again, and the only thing that could restart it was a press of Land in *that* tab. A workflow's merge block queues branches directly and so does a second tab, and both advanced, failed and landed with the page frozen on whatever it happened to be showing — the same sentence as above from the other end. One failed read on load froze it identically, the mount effect running once. So the tick is unconditional, slow while idle and every three seconds while working; it is one `GROUP BY` and no git, where the inventory beside it costs a git process per row and is still read only on the edge. `/api/branches/queue` answers through `jsonNoStore` for that helper's own stated reason: `dynamic = "force-dynamic"` governs Next's cache and puts nothing on the wire, and `cache: "no-store"` on the page's `fetch` speaks only to the browser's.
