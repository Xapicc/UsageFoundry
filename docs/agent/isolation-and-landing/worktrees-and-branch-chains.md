# Worktrees, seeding and slots

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `resolveIsolation`, `ensureWorktree`, `seedWorktree`, `probeIsolation` or slot allocation in `src/lib/orchestrator.ts`, `commitPending` in `src/lib/land.ts`, or the prior- and continued-work notices in `src/lib/cycleInvocation.ts`. A run told to carry on its dependency's branch, and the base, claim and notice that go with it, are in [branch-chains.md](branch-chains.md).

**An isolated run works on a branch, and a worktree contains committed work only.** `seedWorktree` copies the gitignored config files named in `settings.isolationCopyGlobs` and nothing else — dependencies are the agent's job, and slot reuse is what makes that cheap. **A pattern names a path, and one list is not fifteen repositories' answer.** The walk was one `readdirSync` of the repository root filtered by `isFile()`, so a monorepo's `apps/web/.env` could not be named by any pattern at all — the setting says globs and what it matched was a bare filename in one directory. `planSeedCopies` is the traversal and it is pure and unit-tested, taking the directory reader as an argument for `normalizeWorkflowInput`'s reason: it descends only where some pattern's own next segment says to, so the default list still costs exactly one `readdir` and no repository is ever walked whole, and `MAX_SEED_DIRS` bounds the one shape that is not bounded by the pattern itself — a wildcard *directory* segment, against a repository this app did not write. A bare filename still matches a top-level file and nothing else, segment counts having to agree, because reading `.env` as "any `.env` anywhere" would silently widen every existing install's list; `..` and a leading `/` are refused rather than resolved, this being a walk of the operator's own checkout that copies into an agent's. `settings.isolationCopyGlobsByRepo` is the per-repository half, keyed by folder — absolute or relative to any mount, longest key winning, so a key on a parent is a default for the tree under it — and it **replaces** the global list rather than adding to it, which is the only way to say that one repository copies nothing. `copyGlobsFor` is that choice and is pure and unit-tested; falling back to the global list is what keeps an existing install's behaviour exactly what it was. And **"nothing to seed" is not "nothing matched"**: those were one log line with the `(copied …)` clause absent, so a checkout that needed configuration and got none read exactly like one that needed none — which costs a billed cycle failing on a file the operator believes is there, or an agent under `acceptEdits` writing a placeholder config and committing it onto the branch. `seedReport` says which, off `git ls-files --others --ignored --directory` asked only when nothing was copied, and the distinction is `regionsRead: false`'s one file over. **What is copied is the operator's own configuration, often credentials, and the checkout does nothing to keep it off the branch**: `git add -f` is git's hint for an ignored path, and `add -A` stages one the repository does not ignore. The exits are where that is refused — Land and Deliver both refuse a branch whose history carries a path the seeding list names (`seededRefusal`, in `deliver.md`) — because no rule inside a checkout an agent owns could hold. The handoff card withholds the `git merge` command entirely while the operator's own checkout is dirty, or while the branch carries a seeded file, rather than showing it with a caveat, because a copyable command gets copied.

**The merge target is recorded, never assumed.** `worktree_base` is a *commit*: it says where a branch started, not where it belongs. `probeIsolation` now also records `worktree_base_branch`, and a detached HEAD stores null rather than the literal `HEAD`. Rows written before that column existed fall back to the branch currently checked out — but only after proving the run's base commit is an ancestor of it, which makes it a deduction, and `targetInferred` says so in the UI.

**Work an agent left uncommitted goes onto its own branch, and nowhere else.** `commitPending` exists because that state is reachable and its symptoms point the wrong way: before `buildArgs` granted `git add`/`git commit` to an isolated run, every such run ended `completed` with a full checkout and an empty branch, which the land card reported as "this branch has no commits of its own" — a run that looks like it did nothing. It is also what frees the slot, since `ensureWorktree` refuses to reuse a checkout with work in it. The decision is `commitRefusal`, and the branch that earns the unit test is the slot one: a slot is reused, so what is uncommitted in it is only this run's while it still has this run's branch checked out — otherwise the commit lands one run's work on another run's branch, authored by nobody. `add -A` rather than the listed paths, because gitignored files stay ignored and a file written since the page loaded belongs to the same work. A seeded file the repository does *not* ignore is staged with the rest, which is why the exits refuse it rather than this button. A failed commit is left **staged** rather than reset: this app's own git runs with hooks off, so the refusal is git's own and re-running is the likely next move, and the agent may have staged part of it itself. `git status --porcelain` is the one output in this app that must not be trimmed — `" M path"` opens with a space that means "unstaged", and `git()` takes `trim: false` for it alone. What is uncommitted is not always work: while a conflict resolution holds the slot, or after one was cut off, it is a half-done merge with its markers in it, and `commitRefusal` refuses both; the reasons are in `conflicts-and-resolution.md`.

**A checkout on the run's branch is adopted as it stands only once git is known to have finished writing it.** `git worktree add` points the new checkout's HEAD at the branch *before* its `reset --hard` writes the files and the index, and cleans up only from a signal handler, so a SIGKILL in between — a container stopped past its grace, an OOM kill — leaves a registered checkout on exactly the run's branch with few or none of its files. Adopted, the restart's Pick up spawned the agent where `git status` reports every tracked file deleted, under the `git add`/`git commit` grant, and told it it was resuming, or for a hand-over that the gap was the predecessor's work: one ordinary `git add -A && git commit` puts the deletion of the repository on a branch an unattended merge can land. `finishCutOffCheckout` asks two questions first. Git's own marker is the lock it writes before the add starts and unlinks when it is done, whose reason is `initializing`, read off `worktree list --porcelain` (a translated string, read as every git this image ships writes it). Finding it, a run nobody can have worked in — no cycle counted, no park, no session id, and not a hand-over — has git's last two steps run for it, `reset --hard` then `worktree unlock`, in git's order so a cut between them is finished again next time, and is then seeded and announced as a new checkout. Anyone else is refused with a sentence naming the slot and the two commands, because what is uncommitted there may be work done since and a reset would destroy it. The session id is there because the counters alone are not enough: a transient retry refunds a cycle that may have worked. The second question is for an unlocked checkout in which nobody has worked: one with changes to tracked paths is refused with the slot's name, because nothing of the run's own can be in it and git no longer vouches that the tree is its own output. Tracked paths only, because an untracked file is what seeding copies in, and a run refused before its first child comes back to exactly that. `cutOffCheckout.test.ts` pins each of those and the control: a run resuming its own finished checkout keeps its uncommitted edits.

**A null `isolation` means isolated-but-not-yet-planned, and every reader of the column takes it that way.** `createRun` writes `plan ? plan.mode : isolate ? null : "none"`, so a run created behind a dependency carries null until `planWorkspace` runs at release — and for ever, if it is `blocked` by a failed dependency or fails at release — and release reads it as `run.isolation !== "none"`. *Start another like this* read it the other way: `seedFromRun` in `src/app/runs/new/formSeed.ts` copied only `"worktree"` as isolated, so a copy of a never-released run landed on "This folder" on a git repository, with no override mark because a seed's own value never is one, and started an agent in the operator's own checkout holding the folder against every other run in its subtree. `"none"` is still copied as none, because it is what the run did — including a run that asked for a worktree on a folder that could not give one, which is the *unavailable* case above — and `canIsolate` re-gates whatever is copied against the folder the copy lands on.

**`repo_root` is the repository a checkout was cut from, and is null on a run that was not given one.** Landing, `checkoutClaim.ts`'s branch key, the merge queue's serialisation key, `review.ts`'s root, `githubTokenFor` and the sandbox all read it that way. The repository a run is *in* is `runs.folder_repo`, written for every run with a plan, and only repository spend reads it; `docs/agent/metering/run-spend-readings.md` says why the two are kept apart.

**A slot outlives the run that worked in it, so anything read from one has to prove the slot still holds that run's branch first.** `allocateSlotPath` hands the lowest clean slot to the next run, which `checkout -b`s its own branch there, so a finished run's `worktree_path` is usually somebody else's checkout within minutes. `headBranchOf` in `git.ts` is the one question asked — `rev-parse --abbrev-ref HEAD`, null for a detached HEAD or a failed read — and three readers compare it with `runs.worktree_branch` before they believe the directory: `slotState` (the land card and the commit door), `reviewCwd` (where a reviewer reads from) and `uncommittedIn` in `diff.ts` (the Changes card, the review and validation prompts, and the Files tab's "left uncommitted"). A reader that skips it does not fail, it reports another run's edits as this run's, and the two cards on one run page then disagree. A new reader of `git status` in `worktree_path` makes the same comparison, and a null on both sides is not a match. A detached HEAD there is the run's only while something ties it to the run — a rebase or bisect naming its branch, or no run outside its chain recorded at that path after it (`laterRunHolds`); a later run's own rebase or `git checkout <commit>` is `detachedByLaterRun`, which reads as taken over, because the sentence for a run's own detached slot tells the operator to switch it back.
