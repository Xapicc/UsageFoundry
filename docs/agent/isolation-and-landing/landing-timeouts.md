# Clocks on the landing path

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `NO_CLOCK` in `src/lib/land.ts`, `RESOLVE_SILENCE_MS` or `startAssist` in `src/lib/review.ts`, or `awaitBatch` in `src/lib/workflows.ts`, and before adding a timeout anywhere on the landing path.

**Nothing on the landing path has a clock on its duration, and that is a rule rather than an omission.** There is no length of time after which merging somebody's work becomes the wrong thing to do, so no timer anywhere decides that a merge has taken too long — a branch that needs ten hours gets ten hours. Five separate ones used to, each a number nobody measured and each failing in the same silent direction: a `SIGKILL`'d `git merge` (two minutes) arrives at `landRun` as `ok: false`, which that function cannot tell from git refusing, so a large repository was told its work conflicted and had it rolled back; a killed `merge-tree` or `status` (twenty) reads as a conflict state that could not be determined or a checkout that could not be read, both of which refuse the land outright; a resolution child killed at ten minutes took the merge with it, since `after` aborts and discards the checkout, so the branch was rolled back with the agent most of the way through; the queue's own twelve-minute wait failed the item and recorded that the branch could not be merged when what had happened was that the loop stopped watching, while the child carried on spending; and a merge block's hour reported its branches as not landed while the queue was still landing them, so the graph carried on past a merge it said had failed. `git()` therefore takes `timeoutMs: 0` — zero is *no clock*, not *kill now* — and `land.ts` passes `NO_CLOCK` at every call that decides or performs a land, `assistTimeoutMs` gives a `resolve` none where a `review` keeps its ten minutes (a review is a card waiting on an answer; a resolution is a step in a merge), and neither `resolveWithClaude` nor `awaitBatch` holds a deadline any more. What the ceilings were protecting against, a wedged child holding its repository's worker, keeps the escapes that are somebody's *decision*: the assist settles on the child's `exit`, `stopInstance` writes a block off and `awaitBatch` tests that on every pass, `cancelBatch` takes the rest of the queue (never the row in flight, and nothing it does signals a running resolution's child), and a restart cancels queued rows and fails the one caught mid-merge. A clock on *duration* cannot tell a wedged child from a large merge, and it was ending the large merges. The one deadline this path now has is on *silence*, which can tell them apart, and the next paragraph is that decision.

**A resolution's child has one deadline, and it is an hour of silence rather than any length of run.** Decided 2026-09-27 on board task 7c5ec794. Until then nothing in this process reached a resolution's child once `startAssist` had spawned it: `assistTimeoutMs` gives a `resolve` no timer, there is no stop on a `run_reviews` row, and `cancelBatch` leaves the row in flight alone, so the two comments that named batch cancellation as a way out described a stop that did not exist. `resolutionBudgetUSD` bounds what one spends; what it cannot bound is a child that spends nothing and never exits, which held one of `maxConcurrentAssists` and its repository's merge worker until a restart, and a restart interrupts every run in flight to free them. `RESOLVE_SILENCE_MS` in `review.ts` ends that child once it has printed nothing on stdout or stderr for sixty minutes, on `maxCycleSilenceMinutes`' reasoning in `budgets-and-guards.md`: every chunk re-arms it, so a merge that is still reporting is never ended however long it runs, which is everything the rule above protects. It lands as `failed`, because nobody decided it, through the same `after` as any failed resolution: the merge is aborted, the checkout discarded, the branch left where it was, and the operator's checkout never touched. `resolutionSilence.test.ts` pins that, and that output re-arms it. **The measurement it rests on.** 79 real resolution transcripts, which is every transcript under `~/.claude/projects` whose first prompt is `resolvePrompt`'s: 8 in throwaway `-resolve-` checkouts and 71 in runs' own worktrees, across 8 repositories, 2026-08-28 to 2026-09-26, written by CLI 2.1.226, 2.1.260 and 2.1.280. The longest gap between consecutive timestamped entries in each ran from 3.7s to 193.5s, median 32.0s, 90th percentile 115.3s. The longest were model turns after a tool result; three of the next four (176s to 184s) were the CLI's own API retries, ending in a synthetic `API Error` and an exit it made by itself. The longest whole resolution took 867.5s, the median 111.6s, and none of the 79 hung. An hour is about eighteen times the worst gap seen. Two caveats: a transcript entry is a proxy for a line on the child's stdout, not a measurement of it; and a verify command granted through `resolveAllowedTools` keeps the stream silent for as long as it runs, where the longest of the 161 `Bash` calls in these transcripts took 20.3s, so a repository whose checks take most of an hour is outside what was measured. **The two alternatives, and why not them.** A Stop on the run page's resolution card would keep this path free of any deadline and put the stop with a person, but the case it exists for is the unattended one, the merge queue's auto-resolve and a workflow's merge block with nobody watching, where a control nobody presses leaves the worker held exactly as before; it would also need a child handle per assist on `globalThis` and a fourth `run_reviews` status. Keeping the status quo was defensible on this evidence, since none of the 79 hung, but its only remedy was a restart that interrupts every run in flight, against a deadline that would have ended none of the 79. The cost of the choice, stated rather than absorbed: a resolution that stays silent for a whole hour and would then have finished is rolled back and has to be asked again, and a stuck one holds its slot for up to an hour rather than until somebody notices.
