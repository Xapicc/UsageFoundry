# Projects: the inventory, Push and Fetch

[← isolation-and-landing index](../isolation-and-landing.md)

Read before editing `src/lib/projects.ts`, `GET /api/projects`, `POST /api/projects/push`, `POST /api/projects/fetch`, or `checkoutHolder`, `claimLanding` or `checkoutOperation` in `src/lib/land.ts`. Added 2026-10-16. Deliver, the other door that sends something to a remote, is in [deliver.md](deliver.md); the credential rules both stand on are in `security/child-uid-and-credentials.md`.

**A project is a git folder the picker's walk finds, and every one is listed — read, refused with its error, or counted as not on this page.** `projectInventory` takes `scanWorkspace`'s folders with `isGitRepo` set, so the picker and this view cannot disagree about what a project is, and mount roots never are one because the walk never lists them. `selectProjectPage` is `selectBranchCandidates`' rule over that list: `MAX_PROJECTS` per request, `offset` to reach the rest, `total` and `notShown` counted over every git folder. A folder whose git fails is a row whose `error` is git's own line and whose git fields are null, never a missing row and never a failed request — `UsageFoundry-local-offload` in this container is a worktree whose `.git` names a host path that does not exist here, and it reads `fatal: not a git repository: …`. Any read of a checkout failing makes the whole row an error rather than a half-filled one, because a row with a branch and no upstream reads as "no upstream", which is a different sentence from "could not tell". Not polled, for `/api/branches`' reason: a page is a few hundred git children and nothing in it changes on its own. The two presses act only on a folder this walk lists (`resolveProject`, one walk per press), never on any directory with a `.git` that the mount happens to hold — a slot under `.uf-worktrees`, a `node_modules`, a checkout deeper than the walk goes.

**What one request reads is decided before any of it is read, and the cap is on the page.** `branchInventory`'s shape, three passes. The checkouts are read under `mapWithLimit` at eight in flight, each checkout's seven children one after another, so a page is at most `MAX_PROJECTS × 7` children whatever the mounts hold. Then, synchronously and before any branch read is dispatched, `selectBranchReads` picks which unmerged branches this request pays for — `MAX_BRANCH_READS` across the page, taken round-robin (every project's newest branch, then every project's second) so one repository holding hundreds of stale branches cannot spend the cap and leave every project after it unread. A branch over the cap is counted in the row's `branchesNotRead` and **not listed**: listing it would mean saying whether it is landed without having asked. That leaves a repository with more unmerged branches than the cap no way to show the rest on this page; `/branches` still reaches every `uf/*` one.

**Ahead and behind are as of the last fetch, and the row says when that was.** They are `git status --porcelain=v2 --branch`'s `branch.ab`, counted against the upstream's local remote-tracking ref, so nothing here contacts a remote to produce them, and `fetchedAt` is `FETCH_HEAD`'s mtime — null for never, which is a different thing from zero. `FETCH_HEAD` is per checkout: measured on git 2.39 on 2026-10-16, a fetch in a linked worktree writes `.git/worktrees/<id>/FETCH_HEAD` and leaves `.git/FETCH_HEAD` alone, while the refs it updates are the repository's. So `fetchedAt` is the newer of the checkout's and the repository's own, which covers fetching from the main checkout; a fetch from a third worktree of the same repository moves the counts without moving either time. An upstream configured but never fetched, or deleted on the remote, has no local ref, `branch.ab` is absent, and ahead and behind are null. A row ahead also names what it is ahead by — `unpushed`, `git log` from the status's own sha to `<branch>@{upstream}`, newest first and at most `MAX_UNPUSHED_LISTED` — so the Push sheet lists the commits a press sends out of the same read as the sha it sends, and says how many of `ahead` it left out. `@{upstream}` rather than `branch.upstream`'s short name, which a local branch called `origin/main` makes ambiguous; the seventh child, spent only on a row that is ahead.

**A mid-operation checkout is read off its git directory's files, the way the run-branch doors read one.** `checkoutOperation` is `operationOn`'s table without the branch name — `rebase-merge/head-name`, `rebase-apply/head-name`, `BISECT_START` — plus `MERGE_HEAD`, in the checkout's own `--absolute-git-dir`, with `readIfPresent`'s rule that only absence reads as idle. Files rather than `rev-parse --verify MERGE_HEAD` so the whole inventory spends no child on it.

**An unmerged branch is one `--no-merged` lists against HEAD, less any squash `isLandedTip` says landed in the current branch.** A squash leaves no ancestry, so `--no-merged` lists a squash-landed `uf/*` branch for ever; the existing rule (`branch-inventory-and-deletion.md`: tip unmoved, the squash's commit still in the target) is asked with the **current branch as the target**, because that is what `--no-merged` was measured against, so a squash and a merge into the branch the operator stands on read the same and a squash into some other branch reads as unmerged here, as a merge into it would. Undo the squash with `reset --hard` and the branch is listed again; `projectPush.test.ts` pins both. A branch is a **run branch** when a run with `isolation = 'worktree'` and this checkout as `repo_root` recorded it, and its row names the chain's owner (`branchOwnerOf`); a `uf/*` ref no run in this repository recorded is an other branch, since there is no run to join it to. Ahead counts are from the shas this request read, not the names, so the count is about the tip the row shows.

**Push sends the commit the page showed, to the current branch's configured upstream, and nothing else.** `git push <remote> <sha>:<upstream's remote ref>`, never the branch's name: what leaves is the commit `planPush` compared against what was shown, whatever HEAD does after the read. Never `--force`, `--force-with-lease`, `--all`, `--mirror` or `--tags`, and never an empty source, so never a deletion. No `--set-upstream`, so `.git/config` is not written and an upstream is neither created nor changed — a branch with none is refused and told to set one by hand. `--no-follow-tags` and `--recurse-submodules=check` are there to overrule config, not decoration: `push.followTags` in the repository or the operator's own config would otherwise send every annotated tag reachable from the commit (`projectPush.test.ts` fails with the flag removed), and `push.recurseSubmodules=on-demand` would push submodules' commits to their remotes. The remote's name is the repository's own `branch.<name>.remote`, so every call that takes it — both `remote get-url`s, the push and the fetch — puts `--end-of-options` in front of it, and a name like `--upload-pack=…` is a remote nobody configured rather than an option. Pushing a sha still updates the local tracking ref, so the row reads level at once (measured, git 2.39).

**A run's branch is never Push's, whatever upstream it has.** Deliver's `push --set-upstream` gives a delivered branch one, so an operator who checks it out would otherwise be offered Push on it — and Push runs none of Deliver's verify gate, seeded-file refusal or certification gate. `planPush` refuses as `run-branch` when a run in this repository recorded the current branch (`runBranchOf`, naming the run), or when it is in the `uf/` namespace and none did, since a run recorded in another install or swept from this one is still a run's.

**Push asks the remote before it pushes, so a branch deleted there is never made again.** The counts are as of the last fetch, and this module's fetch never prunes, so the tracking ref of a branch deleted on the remote survives, the row reads ahead, and a plain push would create the branch again. So the press runs `git ls-remote <push URL> <upstream ref>` first, on the same credential path — after every refusal that needs no remote, so a refused press reaches nothing — and asks `planPush` again with what it said (`RemoteTip`): absent is `upstream-gone`; a commit the pushed one does not contain, which a commit this checkout never fetched cannot be, is `behind` with a sentence saying the remote moved since the last fetch; the pushed commit itself is `nothing-to-push`. Then the checkout is read again and decided once more with both, with nothing awaited between that and the push's spawn. Measured on the scratch remotes: without it the deleted branch was recreated. The inventory never asks the remote, so only the press can say these — the one way its answer may differ from the button's.

**One function decides every refusal, for the button and for the press.** `planPush` is pure and is asked by the inventory for each row's `push` verdict with nothing shown, and by the endpoint with the `branch` and `sha` the operator was shown, so the button and the endpoint cannot disagree about whether a push is possible or why not — `planDelivery` and `deliverHold`'s arrangement for Deliver. Each refusal carries a `code` beside its sentence, in this order, which is what each sentence assumes: `unreadable`; `moved` (HEAD is not that branch at that sha, or the upstream is not the remote and branch the screen named — first, because every later reason describes a state the operator was not shown); `operation` (ahead of `detached`, because a rebase or bisect detaches HEAD and "detached" alone would hide the command that ends it); `run-branch`; `detached`; `no-upstream`; `not-github` (a local upstream, or a URL that is not `https://github.com/…`, or more than one push URL); `no-credential`; `busy`; `nothing-to-push` for a branch with no commits; `uncounted` (no local tracking ref: fetch first); `behind` (pull or rebase by hand — ahead of `nothing-to-push` because a diverged branch is both and the remote would refuse it); `nothing-to-push`; and, from the remote, `upstream-gone`, `behind` and `nothing-to-push`. `planFetch` is push's standing refusals and nothing else. `projects.test.ts` pins every one against a pushable baseline and the orders between those that can hold together. What neither pre-empts is the remote: a remote that moved since the last fetch refuses the non-fast-forward itself, and the endpoint reports it as a 502.

**Push takes `landing`, and refuses on anybody else's.** The same claim `landRun` and `deliverRun` take, taken through `claimLanding` before the fresh read, so no land, delivery or second push starts in the checkout while this one decides and sends; the merge queue already waits on it through `checkoutHeld`, which is why it is that claim rather than a lock of its own. When something already holds it the read still runs and `planPush` states the refusal in its order, so one function says every no. `checkoutHolder` compares held folders by **overlap**, because a push's folder is a repository root and a land's is the run's `folder`, which may be a directory inside one; the reverse is not true — `landRun` and `deliverRun` still test `landing.has(folder)` exactly, so a land whose run folder is a subdirectory does not see a push claimed at the root. That is harmless for what is sent, which is a sha, and was left alone rather than widened into a change to Land. A run working in the folder (`runWorkingIn`) refuses too, naming it, as Deliver does. The decision is made on a read with nothing awaited between it and the push's spawn, and the row the press answers with is read **after** the claim is let go, or it would report the press's own claim as something holding the checkout. `isShuttingDown()` is read in that same turn and `trackLand` holds the shutdown for the push, `deliverRun`'s arrangement.

**There is no verify gate in front of Push, and that is a decision.** Land and Deliver run `landVerifyCommand` because they are where a run's work enters the operator's branch or leaves as a proposal to merge. The commits Push sends are already on the operator's branch: Land put them there, having run that gate in front of the merge, or the operator committed them by hand, which no gate here was ever asked to judge. The command would run in the operator's own checkout, against a tree that may hold uncommitted work the push does not carry — `verifyTreeVerdict`'s reason for refusing such a tree — and a push of hand-made commits would wait on a check nobody configured for them.

**Uncommitted work never blocks a push, and the answer says it stayed home.** `CheckoutFacts` has no uncommitted field, so `planPush` cannot refuse on one; the response's `note` says how many paths were not included, or that the count could not be read.

**The credential is the repository's, and it goes only where every URL git will use is `https://github.com/`.** `githubTokenFor(checkout)`, so a repository whose `UF_GITHUB_TOKENS` entry gives it none refuses (`no-credential`, naming the entry) rather than falling through to the install-wide token, and handed to `git()` through `githubEnv` and the `env` option exactly as `deliverRun` does, with `gitArgs`' `-c` flags keeping hooks and `core.fsmonitor` off. The token is in that child's environment, so the question is which programs git runs there, and the repository's own config — which a work cycle can write — names several: `core.sshCommand` for an ssh URL, `remote.<name>.uploadpack`/`receivepack` for a local path, an unscoped `credential.helper` for a host other than github.com. A review on 2026-10-16 had the token printed by each, through a second `remote.origin.url` (git pushes to all of them, `get-url --push` names the first), a path spelled `git@github.com/o/r` (no colon, so git reads a local path), `ssh://git@github.com:o/r` (which `githubEnv`'s rewrite misses) and `https://elsewhere/@github.com/o/r` — the last three all read as GitHub by `parseRemote` then. So the URLs are read with `get-url --all` (Fetch) and `get-url --push --all` (Push), under `githubEnv`'s rewrites with a placeholder token (`urlReadEnv`), which is exactly what the press's git will use; every one must be `https://` and read by `parseRemote`, whose patterns were tightened to take each form only as git reads it; and Push takes exactly one push URL, the one `ls-remote` asks. An SSH GitHub remote still passes, because the rewrite makes it https. What this does not cover, as Deliver does not: an `http.proxy`, `http.sslVerify` or `http.sslCAInfo` in the repository's config still applies to the https push, and Deliver itself still decides on the first fetch URL (board task "Deliver's credentialed push is checked against the fetch URL").

**Fetch is a press, plain, and asks for what the credential path needs.** `git fetch --no-prune --recurse-submodules=no <remote>`: `--no-prune` because a fetch is asked to bring news, not to delete remote-tracking refs, and the operator's `fetch.prune` would otherwise make it one that does; no submodules, because their remotes need not be GitHub. It requires every fetch URL to be `https://github.com/` and a credential, like Push and for the paragraph above's reason. It takes no claim and is refused by no merge, land or count — it writes remote-tracking refs and `FETCH_HEAD`, never the working tree, the index or HEAD, and nothing a land decides reads either. A rebase or bisect does refuse it, as `detached` with a sentence naming the operation, because the upstream it fetches is the current branch's and they leave none. Nothing polls it and nothing in the run loop calls it. A branch with no commits yet is read too: its ref does not exist, so `for-each-ref` names no upstream, and the branch's `remote`/`merge` config is read instead, so a fresh clone of an empty repository can still fetch.

**Neither has a clock.** `NO_CLOCK`, for `landing-timeouts.md`'s reason: a killed git reads as one that refused, so a push that was merely slow would be reported as not sent when it may have been. The cost is Deliver's too — a push that hangs on the network holds `landing` for that checkout until it ends or the server restarts.

**The wire.** `GET /api/projects?offset=&limit=` answers `ProjectInventoryDTO`. `POST /api/projects/push` takes `{ mountId, folder, branch, sha, remote, remoteRef }` — the row's `branch`, `head` and `upstream.remote`/`upstream.remoteRef` — and `POST /api/projects/fetch` takes `{ mountId, folder }`, each checked by `readPushFields`/`readFetchFields` before anything runs — 400 for a malformed body, 404 for a folder that does not resolve in that mount or has no `.git`, 409 with `code` and the fresh `project` for a refusal, 502 with `code: "remote"` and the `project` when the remote refused or could not be reached, 200 with the `project` as it now stands. Both POSTs go through `auditMutation`. The DTOs are in `apiTypes.ts` under "Projects". URLs on the wire and in sentences go through `redactUrl`, because `get-url` returns credentials exactly as a person wrote them into the URL.
