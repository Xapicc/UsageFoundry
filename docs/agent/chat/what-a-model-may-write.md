# Prompt, agent and order: what a model may write

[← chat index](../chat.md)

Read before editing a proposal's `prompt_override`, `agent_id` or `spec_id`, or `composeTask`, `planApprovalBatch` and `runOrchestratorChild`'s agent argv in `src/lib/chat.ts`.

**Prompt text is the one half of a run a model may write, and it is written down as an exception rather than absorbed.** `chat_proposals.prompt_override` replaces the template's prompt for one run, and `save_template` writes a name, a prompt and a model back for reuse — taking `chatGuards()` for a new template and the row's existing guards for an update, so no argument on that tool can move one. The model is the third thing it writes rather than a hole in that: it is a price, and a template that costs more or less than it did is a change the tool says in the thread rather than only returning. Reasoning effort is a price too, and deliberately **not** a fourth: it is `settings.runEffort` alone, with no column on a proposal, a template, an agent or a node, so nothing this surface writes can move it. The distinction is not cosmetic: guards decide what an agent *may* do and prompts decide what it is *asked* to do, and a chat that cannot adapt a prompt just restates its objections inside the task, which puts the same text in the run with nothing recording that it happened. `composeTask` keeps the two halves in order and separated by a heading, and emits the task alone when there is nothing standing above it — a section marker for a section that is not there is worse than no marker. Every proposal card says which guard set applies, spelling out the untemplated one, and marks a rewritten prompt.

**Who does the work is the third half a model may write, and it is the same act as writing the task.** `chat_proposals.agent_id` and a proposed graph's `agentId` name the saved agent a proposed run would be started as, and neither is an exception to the paragraph above: an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so `planProposal` and `planNode` gain no branch that reads a guard off either. It is an **id** rather than the frozen copy `runs.agent` holds, which is `run_templates`' rule and for its reason — a proposal is form input a person decides on, so it should name the agent as it stands at the click rather than as it stood when the model wrote the card, and the copy is taken where it always is, by `createRun`. A deleted or decayed one is refused **by name** through the same `agentRefusal` at both moments the template is checked at: when the tool records the proposal, where a model can act on the sentence, and again at approval, where the operator can. `list_agents` is what a turn reads first, and it is on the **shared** tool list rather than the chat's: a block names one too, and the alternative is a deciding turn guessing at names out of its system prompt. It grants neither subject anything — the same reason naming one is allowed at all — and it declares the ambient definitions beside the registry, because those reach every run whatever is named and cannot be named at all. The card carries the agent in the line that already carries the folder and the guard set, and *outside* the guard mark: a phrase under the shield would claim it bounds something, which is the one thing about it that is not true however large a fact it is otherwise. `summarizeProposedGraph` says it per block for the same reason it says the fan-out cap.

**Which CLI runs it is a fourth thing a model may write, and the card is what makes that allowed.** `chat_proposals.provider` names the agent CLI a proposed run is spawned as — null is the ordinary Claude run, and stays null on the run rather than becoming `'claude'`, `runs.provider`'s own reading. The new-run form kept this choice with a person on the ground that an option nobody was told the price of is not a choice; the approval card is where this person is told it, so the card states any provider but Claude in warn tone with the form's disclosure in one line, and the operator approving it is the person who picked. It is not a guard — no budget, permission mode or isolation choice reads it — but it does change which of the Claude path's guarantees the run keeps, so the tool refuses the three cards that would say something false: a Codex run whose guard set carries neither a work-cycle nor a time limit (`providerTerminusRefusal`, asked again at the click because a template's guards are read live), a Codex run naming a model (every id the tool offers is a Claude one; `planProposal` also drops a template's model for Codex), and a Codex run started as a saved agent, whose prompt reaches Claude Code only. Only `propose_run` carries it: a workflow block and `emit_runs` still have no provider to name, the second because nobody approves what it starts.

**The chat's own turn is not started as one, and the asymmetry with an orchestrator block is the whole reason.** `runOrchestratorChild` takes one `agent` and a block hands it the one its node names; `runTurn` deliberately hands it none. **The old reason for that is gone, measured, and is replaced rather than kept** — this is exactly the paragraph the singular flag was expected to overturn and did not. It used to rest on a doubt: a `--agents` member carries a system prompt of its own, and whether `--append-system-prompt` also reached the turn it was delegated was not verified against the pin, so this child — the only one in the app whose boundary is *prose* — could not absorb the question the way the others could. That is now measured, and it went the other way: an agent asked to answer with a secret word stated only in the appended text answered with it, so the appended prompt reaches a `--agent` session alongside the agent's own. What stands in its place is the stronger half of the same argument, and it is not a doubt. This child is bounded by `bypassPermissions`, no allowlist, and `systemPrompt()`'s look-do-not-build paragraph carried by `--append-system-prompt`. Selecting an agent here would make some saved prompt the orchestrator's own role — reachable from a registry a chat proposal can name — which is precisely the thing that paragraph exists to fix, and no measurement can make that safe. The second half is unchanged: there is no work here for one to do, since a chat turn looks and proposes, so what an agent would change is how the orchestrator *thinks*. The `@`-mention in the composer is what an operator actually wants from this — it names the agent the proposed *run* will be started as. Nothing in this app parses it back out of the message: it is text, read by a model that has `list_agents`, which is why a name with a space in it is inserted as it stands rather than quoted into a syntax nothing else here speaks. The popover takes **Tab**, the arrows and Esc and never Enter or ⌘↩, because this composer sends on Enter and a list that accepted a completion with it would swallow the send exactly when the operator had finished typing a name.

**Order is the other half of the work a model may write, and it is a label until a person approves it.** `chat_proposals.spec_id` is the chat's own name for a proposal and `depends_on` is what it says that proposal starts after — labels rather than ids, because the model writes several proposals in one turn and has to point one at another before either has an id. They resolve to *run* ids at approval and nowhere else: `planApprovalBatch` is that decision, pure and unit-tested for `planProposal`'s reason with `releasableRuns`' failure modes. A label naming a sibling in the same click resolves to the run this pass is about to create; one naming a proposal of this chat that already became a run resolves to it; anything else **fails that one proposal by name**, and everything behind it fails too with its own sentence naming the one in front of it. Dropping the edge instead is the failure this exists to have none of — a run told to wait and started immediately is bit-for-bit a run that was never told, and the two agents then work in the same checkout in whatever order the queue felt like. The same failure is reachable one step earlier, at the door, and is refused there by name: a `dependsOn` that is present and not a list — the likeliest shape is the list sent as a JSON string, the arrival `normalizeChoices` survives and `idList` refuses — is a tool error at `propose_run`, at each `propose_workflow` block and at `planEmission`, the `emit_runs` door, where nobody reads anything before the runs start. Read as absent, it was a card with no "starts after" line and the run above; missing or `null` still means no dependency. The batch is created in `topologicalOrder`, which moved to `orchestrator.ts` beside `dependencyCycle` for that function's reason: three callers now create runs in one synchronous pass and "every one after what it waits for" has to mean one thing. Without it the order is whatever the page displayed, and a proposal is refused as naming a missing run — an artefact of a render, reported as a fact about the work. Everything `admitDependencies` already decides is deliberately *not* re-decided here — one branch handed over, both ends isolated, no rival continuation, no loop against the live graph — because those need rows and a second copy would be a second set of rules to keep in step; what `propose_run` does check at the door is the subset it can, for the reason it validates everything else there.
