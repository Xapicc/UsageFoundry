# Questions to the operator

[← chat index](../chat.md)

Read before editing `ask_operator`, `sendChatMessage`, `settleQuestions` or `answerChatQuestions` in `src/lib/chat.ts`, `threadItems` in `src/lib/chatThread.ts`, or the question surface of `src/app/chat/page.tsx`.

**The chat can ask the operator a question, and asking is how the turn ends rather than something it waits through.** `CHAT_IDLE_TIMEOUT_MS` is fifteen minutes of **silence** — a turn that keeps producing something is never interrupted, and one that has stopped producing is killed with its answer discarded — so a tool call that blocked on a click is precisely the shape that gets killed: silent for as long as nobody is looking, and then dead with the turn that asked — `ask_operator` therefore records `chat_questions` rows and returns immediately, and the second sentence of what it returns is that no answer is coming back through it. That sentence is load-bearing rather than decorative, and so is the description above it: the tool-calling half of the orchestrator's instructions lives in `/api/mcp`'s descriptions and is deliberately not repeated in `systemPrompt()`, because a description cannot drift from the schema and a prompt can — and a model reading this one as "returns the operator's answer" calls it, gets a receipt, and calls it again until `chatTurnBudgetUSD` stops it. That fact is the single exception the prompt makes to the split: the asking paragraph names `ask_operator`, says it records the questions and ends the turn, and points at the description for the judgement about what is worth asking, which stays where it cannot drift. The pointer is there because a deferred description is only fetched when something names it, and 3 of 98 surveyed conversations fetched this one. The answer arrives on the **next** turn, which is the same conversation to the model (`--resume` against `chat_sessions.session_id`) and a different process to everything else, which is why the answer message quotes each question above the answer to it instead of sending the bare string the operator typed: a fresh child has the thread but not the tool call, and "pnpm" on its own is a referent it has to guess at silently. `chat_questions` holds even less than `chat_proposals` does, and what it holds is nothing — no guard, no permission mode, no budget, no model, no folder claim, no concurrency slot, and nothing derived from `activeRuns()` can see it. A question is a sentence and an answer is a sentence; the only thing answering one starts is another chat turn, and it starts it *through* `sendChatMessage` rather than around it, so every gate a message passes — `dataDirRefusal`, `assistRefusal`, the install limit, the claim, the sweeper — an answer passes unchanged. The bounds on asking are the same shape as `MAX_PENDING_PROPOSALS`' and exist for its reason: at most five questions open on a thread and at most eight choices on one, because past that it is a form rather than a question and a form gets skimmed — and a skimmed answer is worse than none, since the model proposes on it either way and only one of the two is something the operator will remember agreeing to. Three shapes are refused by name rather than repaired, and the reason is the same each time — which of two things the model meant is not something the route can know, and a question repaired into a different question is one the operator answers correctly and the model reads wrongly. A single choice is a decision already taken rather than a choice. A list longer than the cap is counted **after** normalizing, so "twenty options" and "twenty copies of one option" are told apart and the number in the refusal is the number that would have been rendered. And no choices with no typed answer is a card with nothing on it to press — reachable without the model meaning any of it, since `choices` sent as a bare string normalizes to none, which is exactly the arrival shape `normalizeChoices` exists to survive. A fourth bound has a different reason and is not about attention: a question is at most `MAX_QUESTION_CHARS`, 2,000 UTF-16 code units, because `answerMessage` quotes every open question in full and `sendChatMessage` refuses anything past `MAX_CHAT_MESSAGE_BYTES` with a sentence telling the operator to shorten it. Without it one pasted log made Answer refuse on every question in the thread, the short ones beside it included, over words the operator never wrote — and the only way out was an ordinary message, which supersedes them all unanswered. Five at the cap in three-byte characters is under half the message limit, so the rest is left for the answers, the one part of that message the refusal is right about. The refusal names the question by position rather than quoting it, since quoting it is sending the log back, and the cap is stated in the `question` description as well, `comment_on_task`'s reason: a model that learns a limit only by going over it has already written the text. A row asked before the cap existed can still be over it; nothing trims it, and an ordinary message is still its way out.

**A pending question is derived from `chat_questions` and is never a fourth `chat_sessions.status`.** Three reasons, each sufficient on its own, and all three are about paths that already exist. `finishTurn` settles under `WHERE status='thinking' AND turn_seq=?`, which is the settle-once latch every stranded-turn path depends on, so a status meaning "asked and waiting" would have to be written by that same statement — and a turn cancelled or timed out after it had asked would then settle as `failed` and lose the question, or as `asking` and lose the failure. `reconcileChatsOnBoot` fails out `thinking` rows because the child is gone with the process that started it, where a question is a row in a database and survives a restart intact, so a status that meant both would need excluding there by hand — a silent way for a restart to eat every open question. And `sendChatMessage` refuses to send into a `thinking` chat, so a status meaning "waiting for the operator" would sit directly beside the guard that must not refuse the answer it exists to collect. What deriving costs is one query on the poll the proposals already pay for; what it buys is that **nothing about the turn lifecycle changes at all** — a turn that asked ends `idle` like any other, a chat with a question open has no child and an operator who may type anything into the composer, and a question outlives every way a turn can die.

**A question is drawn in the conversation and never in the panel beside it, and *where* it lands is a decision rather than an ordering.** The panel is work waiting to be approved and costs nothing until somebody clicks; a question is a sentence, answering one starts a chat turn and never a run, and it belongs in the half of the page the other sentences are in. It is drawn as an object because it has controls on it, and it is deliberately not a `Card`: `emphasis` carries padding as well as elevation, so a box that changed emphasis inside the scrolled transcript would re-pad the transcript under a reader's hands on a surface that polls — which is the same trap `PROPOSALS_EMPHASIS` records for the conversation card itself. `threadItems` is the placement, pure and unit-tested on the grounds the three functions above it are: every way of getting it wrong produces a *page* rather than an error, and the worst of them is the quietest thing this whole mechanism can do — a question the page never draws leaves the thread waiting on an answer to something the operator was never shown, with no error, no empty state and nothing in the console. The unconditional tail append is what makes that unreachable and is the first case in the file. A question is placed **before the operator's next message** rather than at its own `created_at`: `ask_operator` records the row *during* the turn, so by timestamp alone the card would sit above the reply explaining why it was being asked, and everything between a question and the operator's next message is the rest of the turn that asked it. That is what puts a pending one at the foot of the thread beside the composer and a settled one directly above the message that carried the answer. The comparison is **strict** — `sendChatMessage` appends the message and only then spawns the child that asks, so on `<=` a question would be drawn above the message that provoked it every time the two landed on one millisecond. Only a `user` message closes the placement, because an assistant reply and a `system` failure notice are both the same turn still finishing.

**A settled question keeps its place, and the message beside it is not a duplicate of it however much it reads like one.** A card that vanished when it was answered reads as a question nobody was ever asked, and `answerMessage`'s quoted `Q:`/`A:` block — appearing in the operator's own voice, in words they did not type — then reads as text that arrived from nowhere. Both are drawn, and they are two different facts: the card is the question as it was *asked*, and the message is the text the model was *sent*. Suppressing the message was considered and refused, and the reason is a coupling rather than a preference — the only way for the page to know which message is the generated one is that an `answered` row can only have been settled by `answerChatQuestions`, so a later change letting an ordinary message settle a question as answered would silently eat the operator's real words. `superseded` is drawn as neither an answer nor a failure: saying something else *is* an answer, and danger red would report a redirection as a fault.

**A choice sends on one press only when it is the last question open, and the card says which of the two shapes it is in.** Sending on the press is the entire point of offering buttons, and with nothing else open there is nothing the send can take with it. With siblings still open it cannot: the answer message settles the set and supersedes everything it did not name, so one hasty press would close two questions the operator was still reading — and `answerMessage` would carry them to the model as `(not answered)`, which is the model's cue to stop asking about them. So above one question the choices fill in, `aria-pressed` marks the chosen one, and the row's own button sends them together under a line saying that anything left blank is sent as not answered. The typed answer is an `Input` from the kit and not a hand-written control: below the shell's breakpoint iOS Safari zooms the page in on any text field under 16px and never zooms back out, `CONTROL_BASE` is where that floor lives, and the composer is this app's one hand-written exception rather than a precedent for a second. Enter inside a question's field answers, which is the composer's own chord in the one other field on the page that sends. Every control on the card is out while the chat is `thinking`, with the reason said in words: `ask_operator` returns immediately, so a question can be open while the very turn that asked it is still running, and `sendChatMessage` refuses a second billed child on one conversation.

**The composer beside an open question is neither disabled nor pre-filled, and it says what sending does.** The chat is `idle`, there is no child, and the operator may type anything they like — which is the paragraph above about a pending question not being a status, made visible. What the page owes them is the consequence: an ordinary message is the operator declining and redirecting, and the same statement that records it closes every open question as overtaken. Unsaid, a question answered in prose reads as still waiting and its card stays pressable a week later to start a billed turn about a conversation nothing in the thread is about any more. Pre-filling would be worse than disabling: the words would go out through `/message`, which supersedes rather than answers, so the model would be told nobody answered while the operator watched their own answer being sent.

**A chat waiting on an answer is drawn as waiting, and it stays on the *idle* poll.** The fast cadence exists to catch a turn landing; nothing on the server can produce an answer, so three-second polling would be three times the requests for a row that cannot move until a person clicks. It equally does not stand down, which is the half worth writing down: the answer can arrive from another tab, and the thread list beside it moves for reasons that have nothing to do with this conversation. In the list a waiting thread says `asked you` in the row's own voice rather than in a second accent chip beside `N waiting` — `pendingCount` and `pendingQuestionCount` are kept apart because one is approving work and the other is answering a sentence, and two badges that looked alike would send the reader to the wrong half of the page, which is the confusion not summing them exists to avoid. `thinking` is already drawn that way one span over and the two can legitimately be true at once.

**An ordinary message supersedes every open question, and an answer supersedes the ones it did not name.** Saying something else *is* an answer — it is the operator declining and redirecting — and leaving the question open instead leaves a card that can be clicked a week later to start a billed turn about a conversation nothing in the thread is about any more. The row is marked `superseded` rather than deleted, for `chat_proposals`' reason: the thread has to read as what happened, and a question that vanished reads as one nobody was ever asked. `answered_at` stays null on it, because it is the instant an answer was given and a superseded question was never answered. Both halves are one `UPDATE ... WHERE chat_id=? AND status='pending'` inside `sendChatMessage`'s no-`await` window, so a request that loses the claim settles nothing exactly as it appends nothing, and the pass is idempotent — an id that stopped being open is a no-op rather than a resurrection. The refusal a person can act on is `settleQuestions`, decided before any of it is paid for, and it fails the **whole** call when any id is not open. That is deliberately not the approval route's rule, and the difference is what the ids are: there they are independent, so a stale one is dropped and reported in a sentence; here they compose one message, so a dropped id is the operator's typed answer silently absent from the text the model reads — and the model then answers as though the questions that survived were all it asked. An unanswered question is named in that message rather than left out for the same reason: omitted, it is indistinguishable from one that was never asked, and the next move is to ask it again.
