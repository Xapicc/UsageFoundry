# The chat's MCP tools and its capability

[← chat index](../chat.md)

Read before editing `src/app/api/mcp/route.ts`, `findPastProposals` in `src/lib/chat.ts`, or `chatChildCredentials` in `src/lib/privsep.ts`.

**Two read tools reach past this thread, and neither can move anything.** `list_past_proposals` (chat only) is every *other* conversation's proposals through `findPastProposals`, with the run each approval started read off the run row — `approved` only says a person agreed, and whether the work happened is `status` and `reported_done`. Replaced cards are left out because each is the same work as its replacement, and a rejection is reported as having no reason because `rejectProposal` records none. `list_recurring_failures` is on the **shared** list, since a block writes briefs too: it joins `scanDreaming`'s readout to the Dreaming ledger and hands over a note's absolute path only when `noteStillPresent` proves it is a file inside the vault now. It carries `docs/agent/dreaming.md`'s signature caveat in both its description and its payload.

**The chat's tools run in this process, and that is a correctness requirement rather than a convenience.** `/api/mcp` speaks MCP over HTTP by hand — `initialize`, `tools/list`, `tools/call` — and the handlers call `createRun`, `listTemplates` and `scanWorkspace` directly. A stdio MCP server would be a second process doing check-then-insert against the same SQLite file, which silently permits the two-agents-in-one-directory collision the folder claim exists to prevent. `workspace.ts` exists for the same reason in miniature: the picker and the chat must not be able to disagree about which folders exist or which are busy.

**The chat's child authenticates with a capability, never with `UF_AUTH_TOKEN`.** `middleware.ts` exempts `/api/mcp` because the edge runtime cannot reach SQLite to check a per-turn credential, so the route checks it itself — the exemption and the check must stay together, or the tool surface is public. That check also has to stand **outside** `auditMutation`, and for a reason about the audit log rather than about this route: it *is* the authentication for the whole tool surface, so a request that fails it has passed nothing at all, and auditing that refusal made `request_log`'s 20,000-row cap a lever anyone who could reach the path could pull — twenty thousand refusals and every line naming a run that was started or a sign-in that failed is evicted. Only the handler that already holds a subject is wrapped, which keeps the line the table exists for (a real capability whose tool call was refused, which is the burst somebody comes looking for afterwards); `DELETE` is not audited at all, being a 405 answered before any credential is read; and the refusal goes to stdout, which nothing caps. The capability is minted per turn, written to a 0600 file rather than into argv (where `ps` would show it), and revoked when the child exits. That file is in a per-turn directory of its own under a base the *server* owns, never in `os.tmpdir()`: `/tmp` is 1777, so `ls /tmp/uf-mcp-*.json` found a live capability without guessing its random name and any of the concurrent agents could run it — the name was never the protection, the directory was the leak. Both are removed on every settle path, including the partial-write one inside `writeMcpConfig`, since a directory left behind is a leak in a path nothing else sweeps. The directory closed enumeration and nothing else, and what closes the rest is a **group**: `--mcp-config <path>` is an argv element and `/proc/<pid>/cmdline` is world-readable, so a work-cycle agent read the path off a sibling's command line and opened a file its own uid owned. Under `UF_CHAT_GID` the per-turn directory and file are handed to a group the chat and block child is in and no work cycle is — 0710 and 0040, so a thief fails the owner check, fails the group check, and is left with the "other" bits, which are zero. A gid rather than a second uid because the chat child must stay the uid that owns the mounted `~/.claude`: that credential is what it authenticates and bills with, and a second uid would need a second Claude account. `chatChildCredentials()` is the one place that differs from `childCredentials()`, and `mcpConfigOwnership()` returning null — no `UF_CHAT_GID`, or no privilege separation at all — falls back to the previous arrangement whole rather than half-applying it, because a config the child cannot read is a turn with no tools, which reads as a model that chose not to call any. It names a **subject** rather than a chat id, and that is a discriminated union rather than a bag of optional ids on purpose: the subject is what decides which tool list the caller is offered, and a shape where every id can be absent is a shape where the route can forget to check which it has. It has **three** arms now — a work cycle carries one too, minted per run and revoked with it — and the third is the one whose id is load-bearing rather than descriptive, since a run may complete only the task its own row is claimed by and the whole of that rule's enforcement is that the run id comes from here and never from an argument. That third subject is also why `callTool`'s gate is one membership test against the list `toolsFor` published rather than a refusal per pair: the pairwise shape was correct for two subjects and silently admitted a run asking for a block's tool. `docs/agent/taskboard.md` carries the run's half; nothing about the chat's changed. The subject also *scopes* one tool: `get_run_diff` answers for the runs a chat proposed (`chatOwnsRun`) or the runs of a block's own instance (`instanceOwnsRun`), and refuses the rest with a sentence naming what to use instead. That is the one place blast radius is bounded rather than the theft prevented — a token is its holder's identity, so a stolen one is indistinguishable from the turn that minted it, and patch text was the one thing on this surface a work cycle could not otherwise reach from the folder it was started in. `list_runs` and `get_run` stay install-wide deliberately: "what is already in flight" is the question the orchestrator exists to answer, and a file list is not a patch. `telemetryEnv` used to hand a child `UF_AUTH_TOKEN`, and that precedent was deliberately not followed: that token opens every route for as long as it is set, where this one opens a read-mostly tool surface — the two things it can write are a proposal and a template's prompt, neither of which does anything until a person acts on it — and dies with the turn. That reasoning was an argument for fixing the exception rather than for keeping it, and the exception is gone: the exporter now carries a capability of the same shape, minted per run by `ingestTokenFor`, opening one thing (writes to that run's own telemetry) and revoked when the run's loop ends.
