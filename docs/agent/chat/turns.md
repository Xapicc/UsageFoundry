# A chat turn: settling, ending, bounds and spend

[← chat index](../chat.md)

Read before editing `claimTurn`, `endTurn`, `finishTurn`, `staleTurn`, `keepPartialTurn` or `sweepStuckChats` in `src/lib/chat.ts`, or `src/lib/chatStream.ts`.

**A settle belongs to one turn, and `finishTurn` refuses to settle any other.** `endTurn` writes `failed`, appends the sentence and returns while the child it signalled is still working through an eight-second SIGINT/SIGTERM/SIGKILL ladder — deliberately, because the turns that need ending are the ones whose `close` is not coming, so the row has to be usable before the child is gone. But `failed` is also exactly what invites the retry, so the row is routinely `thinking` again *under a different turn* by the time the old child exits. `chat_sessions.turn_seq` is bumped by the claim in the same statement that writes `status` and `turn_started_at`, never reset, and carried by the child claimed under it; `finishTurn` matches on it as well as on the status, and a settle that matches neither changes nothing. Latched on status alone, a stopped turn's child settled the turn that replaced it: its text appended as the answer to a question it never read, its cost and session id adopted, the live turn left unwatched by a sweeper that reads only `thinking` rows, that turn's own answer later discarded in silence against an `idle` row, and a third billed message admitted by a guard that reads the row rather than the process. A counter rather than `turn_started_at`, which is otherwise written and cleared in all the right places: it is `Date.now()`, two turns claimed inside one millisecond would share it, and the entire value of the latch is that it can never mistake one turn for another. The timeout path is the same sequence with a different first sentence, because `sweepStuckChats` calls the same `endTurn`. What a refused settle costs is a superseded child's own figures, and that is the trade rather than a free win — the CLI reports cost and session id only in the final JSON object a signalled child is not expected to print, but one that does has them dropped rather than charged to a turn the operator is still watching.

**Every way a turn can end writes the ending into the thread, and the row is not a record of it.** There are four — a cancel and a timeout through `endTurn`, a failure through `finishTurn`, and a restart through `reconcileChatsOnBoot` — and each appends a `system` message saying what happened, in the words the row was given. The reason is `claimTurn`: it writes `error=NULL` in the same statement that takes the next turn, and that is right, because `chat_sessions.error` describes the turn the row is on and not the one before it. So the row's copy lasts exactly until the operator retries, which is the *first* thing they do, and a thread whose only record was there reads afterwards as one question followed by another with no reply and no note between them — an answer that never came rather than a turn something killed, which is a different thing to do next. The restart path is the one where this is easiest to leave out and where it is worth the most: it is the only ending nobody is present for, so the sentence is the whole of what the operator finds when they come back. It reads the `thinking` ids *before* the UPDATE, because `status` is the only mark a stranded turn carries and the UPDATE is what removes it. Nothing is resumed on any of the four — a chat turn is a question somebody asked minutes ago, and re-asking it unattended is spend nobody is present to want — so saying so is the entire remedy.

**A turn is bounded by silence and by money, and never by how long it has been going.** `CHAT_IDLE_TIMEOUT_MS` was a wall clock: ten minutes from the claim, whatever the child was doing. What that measured was the wrong thing — a turn asked to read four repositories before proposing anything is a long turn rather than a stuck one, and the bound killed it at its most expensive moment, with the answer discarded, the money spent, and the operator's only move to ask again and buy the same ten minutes. Every failure the bound exists for is *silence*: a child wedged on a socket, a `close` that never comes, a turn nothing in this process can still hear from. So silence is what is measured, in three places that must agree or the bound is enforced twice with different answers. The timer in `runOrchestratorChild` re-arms on every chunk **either** pipe delivers, stderr included, since a child printing only warnings is one this process can plainly still hear from. `recordProgress` stamps `partial_at` on every event — which is why `onProgress` is now called for events that moved nothing, and why the stamp is written on its own when nothing else did, rather than re-writing tens of kilobytes of unchanged `partial_text` twice a second. And `staleTurn`, the backstop for a turn whose child cannot be signalled at all, reads that column with `turn_started_at` behind it for a turn whose first event has not landed, `updated_at` behind that for a row older than the columns, and `STALE_TURN_MARGIN_MS` covering the pacing between the three. Fifteen minutes rather than ten because a single tool call is silent for the whole time it runs and the CLI's own `Bash` allows ten minutes of one — `Optional timeout in milliseconds (default 30000, max 600000)`, read out of the shipped binary rather than guessed — so a bound at or under the longest legitimate silence is the old defect with a new name on it, killing the turns doing the most work and doing it on the tool call rather than on the clock. What is deliberately *not* here is a ceiling on the whole turn: `chatTurnBudgetUSD` bounds a turn in the unit an overrun actually costs in, and the install's rolling ceiling is re-asked while the turn runs, which makes that check the only thing that ends a turn the install cannot afford rather than a way of shortening the wait for a clock. Two things followed the clock out. The capability is minted with no expiry and revoked instead — on the spawn failure, on the exit, and by the idle timer at the moment it decides the turn is over rather than after the SIGTERM/SIGKILL pair that follows it — because a credential expiring on the old bound would be a turn whose tools start answering 401 part-way through, which reads as a model that chose not to call any. And the page cannot say “of up to 15 min” beside a rising clock, because that is the one number on the surface that would be false: it draws the elapsed time and, separately, how long ago the turn last said anything, which is the fact an operator deciding whether to wait can act on.

**A provider refusal is what the turn says went wrong, ahead of anything this app inferred from the wreckage.** Claude Code writes an API error — a 429, an overloaded upstream, a connection dropped mid-response — as an assistant turn attributed to `<synthetic>`, which is how `orchestrator.ts` has read one for as long as the run loop has existed and how `chatStream.ts` reads one now. It is latched on **first** sight and never cleared, because the CLI retries and the retry that finally gives up prints something shorter than the one that said what went wrong. Nothing acts on it while the turn is going: the CLI's own retries are what a transient fault is answered with, a turn that recovers ends with an ordinary `result` this is never consulted for, and re-asking an unattended turn is spend nobody is present to want — the same rule `reconcileChatsOnBoot` follows. What it changes is the sentence a *failed* turn leaves behind. A turn that died without a `result` used to read “The chat produced no readable output (exit 1)”, with the cause sitting unread in the stream; a turn killed for silence said only that it had been killed. Both now name the refusal first, because the operator's next move for an overloaded upstream is to wait and for a revoked credential it is not, and that sentence is the only thing that tells them apart. The refusal stays in the turn's text as well, so it is visible in the row's partial while the turn is still going rather than only after it has ended.

**A chat turn is durable while it is happening, and it was not.** The child runs `--output-format stream-json --verbose` — the run loop's format, for `emit()`'s reason — and every event folds into `chatStream.ts`'s accumulator, which `chat.ts` writes to the row every half-second. Under `--output-format json` the CLI printed **one object when it exited**, so the whole turn existed in one process's memory until it was done: a restart, an OOM or a deploy in the middle lost the assistant's text, the `chat_turn_spend` row and the thread's running total *together*, while the money stayed spent. Four columns carry it — `partial_text`, `turn_tokens`, `turn_cost_est`, and `partial_at` — and all four are **per turn**, cleared by `claimTurn` and by `finishTurn` in the same statement that takes or settles the turn, for `error`'s reason: a value that survived into the next turn is the previous turn's text and the previous turn's money attributed to this one. `partial_text` is a **live view and never the stored message**: a settled turn still appends the CLI's own `result` string, so what a finished thread looks like is unchanged, and the DTO nulls the partial the moment the status does so the answer is never drawn twice. **The two figures are different kinds of number and nothing may merge them.** `turn_tokens` is what the CLI reported and is measured, so a turn that was cut off folds it straight into the thread's count. `turn_cost_est` is this app's own price for those tokens through `guardCostOf`, so it is a **guard** figure: it lands in `cost_usd_est` beside `cost_usd` and never inside it, and the `chat_turn_spend` row it produces carries `estimated = 1` so `installSpend` can put it in `spentGuardUSD` and keep it out of `spentUSD`. That is `runs.spent_usd_est`'s rule one table over, and the page states the split rather than adding the two. **Five endings keep what a turn had produced and none of them gets a `result` event** — a cancel, the silence bound, the install ceiling closing on a live turn, a restart through `reconcileChatsOnBoot`, and a child that died mid-stream. The first four go through `endTurn` and `keepPartialTurn`; the fifth and the *in-closure* half of the second land in `finishTurn` instead, which had none of it — the timer kills the child, the exit settles there rather than in `endTurn`, and the UPDATE cleared `partial_text` with nobody having read it. That is fourteen minutes of billed work discarded because the fifteenth was quiet, so `finishTurn` now appends the partial when the result brought no text of its own. The money was never the half that was lost: its `estimate` branch already recorded it. The half-answer becomes an ordinary assistant message *before* the sentence about how the turn ended, because the note is a footnote to the text above it and the other order reads as an answer that arrived after the failure.

**A chat turn is spend with no `evaluateBudget` behind it.** It passes the same gate a review does — `assistRefusal()`, the operator's own configured ceiling already spent — and nothing else, because there is no per-chat fraction and inventing one would be a threshold nobody set. `settings.chatTurnBudgetUSD` (default $2, null disables) is therefore the only bound on how much one turn may do, and it is enforced *inside* the CLI via `--max-budget-usd` rather than between cycles — `CHAT_IDLE_TIMEOUT_MS` beside it bounds silence rather than work, and stops a turn nothing is left of rather than a turn that is taking a while. `chat_sessions.cost_usd` is displayed on the chat page only: never added to `runs.spent_usd`, never to the meters. The same money also lands as **one dated row per settled turn** in `chat_turn_spend`, and the two are both needed because neither is derivable from the other: the running total answers *what has this thread cost*, which is what the page shows, and the rows answer *what did this install spend on chat inside the window*, which is what the install-wide ceiling reads. Summing the running total bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in, closing every door in the app and stopping the runs already in flight. The row is written inside `finishTurn`'s existing latch and after it, so a late settle that moved no total adds none. `githubEnv()` reaching this child is a real widening of "GitHub credentials reach a work cycle and nothing else" — a chat asked to read issues cannot without it — and is written down rather than absorbed quietly.

**The install's ceiling is asked again while the turn runs, and that is what `chatTurnBudgetUSD` never covered.** It used to be read once, at admission (`sendChatMessage`), so a turn admitted at 99% of a rolling 24-hour window ran past it for as long as the turn lasted, and a turn admitted before three runs finished ran against a figure that had already moved. `--max-budget-usd` bounds *this* turn inside the CLI and always did; what nothing bounded was the install while this turn was going. `recordProgress` re-asks every ten seconds, and only on an event that moved the spend — the ceiling is a scan of three tables and the answer changes slowly, so the overshoot it accepts is ten seconds of one turn. The estimate it has just written is what `installSpend` reads for it, so the check includes the turn asking it. A turn stopped this way ends through `endTurn` like any other, keeping its text and naming the ceiling rather than the symptom.
