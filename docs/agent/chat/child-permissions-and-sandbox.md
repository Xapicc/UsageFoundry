# The chat child's permissions and sandbox

[← chat index](../chat.md)

Read before editing the chat child's argv or sandbox preparation in `runOrchestratorChild` (`src/lib/chat.ts`), or `SEARCH_TOOLS` in `src/lib/cycleInvocation.ts`.

**The chat runs with no tool allowlist that bounds anything, so the system prompt is the boundary.** It runs `--permission-mode bypassPermissions` with no `--disallowedTools` and one `--allowedTools` that grants nothing — `SEARCH_TOOLS`, which is `Grep` and `Glob`, named because the pinned CLI otherwise does not offer them at all and an orchestrator with `Read` and no way to find what to read proposes badly for exactly the reason below. Under `bypassPermissions` there is no prompt for a named tool to skip, so it moves no boundary; what it moves is the tool list. An orchestrator's whole job is to find out enough to propose good work, and the allowlist this replaced — this app's tools, `Read`/`Glob`/`Grep`, read-only `gh`, `git log`/`status`/`branch`, `cd` — refused every question it had not anticipated (a build log, `gh api`, `git -C <path> log`, anything compound), which is a bad proposal an operator then approves believing it was researched. Not `plan`, which refuses MCP tool calls outright (measured: `Cannot call mcp__uf__list_templates while in plan mode`) and would leave the chat able to read GitHub and not this app; not `acceptEdits`, which holds mutating shell for an approval a `-p` child has nobody to give — the same failure `ISOLATED_GIT_TOOLS` exists to fix — so it would reproduce the refusals less predictably. What replaces the allowlist is `systemPrompt()`, which states the role rather than a list of forbidden tools: look, do not build; do not edit, commit, push, or act on GitHub; a task small enough to just fix is a proposal that says it is small. Everything that bounds this child is elsewhere and unchanged — nothing it can call starts a run, `--strict-mcp-config` keeps the mounted `~/.claude`'s MCP servers out, the capability token dies with the turn, `chatTurnBudgetUSD` caps the spend, and `--add-dir` still names only the mounts. The costs are real and are written down rather than absorbed: the chat can write into a checkout the operator also works in, and `githubEnv()`'s token now authenticates writes as well as reads. `permission_denials` is still read and shown in the thread — now because it should be *empty*, so an entry is the CLI declining something on its own.

**The chat's child gets the same sandbox preparation a work cycle does, and deliberately not the git half.** `runOrchestratorChild` calls `ensureSandboxMountPoints` on the turn's working directory and on every `--add-dir` before the spawn — which since 2026-09-13 also fills `$CLAUDE_CONFIG_DIR`, once per call rather than per tree, because that directory is one whatever the child is pointed at — and `sweepSandboxTreeRoot` on that working directory inside `land`; until it did, both failures `sandboxMountPoints.ts` was written for reached this child untouched, because `runIteration` was the only caller of either. Its sandboxed `Bash` calls failed at sandbox *construction* — `bwrap: Can't create file at <tree>/.claude/<name>: Permission denied`, before the command ran, naming a settings file the command never touched, which is the shape of the 255 results this install carried between 2026-08-25 and 2026-09-04 — and the eleven `SANDBOX_TREE_ROOT_NAMES` bwrap binds at the root of the working directory were left behind afterwards as empty `0444` files with nothing sweeping them. **The tree-root half of that was, for a while, the one preparation this child could not have, and the reason was its cwd.** `chatCwd()` returned `WORKSPACE_ROOT` — `/workspace` on this image, `nobody:nogroup` at 0755 — so bwrap's create at the root of the turn's working directory was refused outright and the turn died before its command ran: 18 such failures at `/workspace` and 8 at `/workspace2` between 2026-09-04 and 2026-09-13. Pre-creating was never the answer available, because the server cannot write there either. **The answer was to move the child**, and since 2026-09-14 `chatCwd()` stands a turn that was not pointed at a folder in `/run/uf-chat` — a scratch directory the server makes 0700 and `chownForChild` — root's and the chat group's at 0770 wherever there is a chat group, since board task `7dd5f973` (`../security/chat-child-config-files.md`) — beside `MCP_CONFIG_BASE` and out of `/tmp` for the same reason, falling back to `os.tmpdir()` with a `chat.scratch_cwd_failed` warning when it cannot. A scratch directory rather than a mount, because standing in a mount buys the turn nothing: reach is `--add-dir`'s and not the cwd's, the prompt already forbids relying on a bare `ls` to find folders ("Folder paths must come from list_folders"), and the prompt already tells this child it has a scratch space outside the mounts. It is shared across turns rather than made per turn, which is safe for exactly the reason `/workspace` was not — the directory is writable by the child, so a turn that finds a placeholder swept out from under it by a sibling has bwrap create it, which is the ordinary path and the one that was being refused. Without a chat group, what it does not buy is separation from a work cycle: every child here is one uid. The second is worse here than for a cycle, and that is why the sweep is worth its placement rather than being tidiness: a cycle leaves them in a checkout under `.uf-worktrees` this app is about to throw away, where the chat roams every mount by design, so they land in the operator's **own** checkouts — `.idea` and `.vscode` among them, as files where a checkout wants directories. `cwd` is resolved once above the spawn and both passes are handed that value, because an `existsSync` asked a second time can answer differently and a sweep aimed at the other answer leaves the placeholders exactly where they fell. The sweep is in `land` rather than beside the exit so that no ending can miss it — the spawn failure lands there too, where there is nothing to find and the pass costs eleven `lstat`s — and ahead of `onSettle`, so the operator cannot read a settled turn and still find the tree in the state that turn left it. Both are silent when they worked and warn to `opsLog` when they did not: the chat has no run log, container stdout is the only sink it has, a line per turn for work that succeeded is noise, and a failure is placeholders left in a tree the operator works in that nothing else will mention. **`core.excludesFile` is the one of the three this child deliberately does not get, and the difference is whose repositories these are.** A cycle is ordered to commit and its `git add -A` dies on those eleven — `error: .bash_profile: can only add regular files, symbolic links or git-directories` — so an ignore rule there hides names that could not legitimately be in that tree and rescues a commit that would otherwise fail. Neither half holds here. This turn is told to look and not to build, so there is no `git add -A` to rescue; and `GIT_CONFIG_*` has no scope narrower than the process, so the rule would follow the turn into every repository it visits — which is all of them, by the same roaming that makes `chatEnv` hand it the install-wide GitHub token rather than one scoped to a folder. In the operator's own checkouts an untracked `.vscode`, `.idea` or `.mcp.json` at the root is an ordinary thing to have, and the one thing this child exists to do is look and report to a person who is trusting it to have looked, so a `git status` that quietly under-reports is that trust broken in the direction nobody checks. The failure of *not* having the rule lands instead on a turn that was staging files it was told not to stage, and it lands loudly. It is therefore not something to add silently the day `chatEnv`'s `githubEnv()` grows an argument for it.
