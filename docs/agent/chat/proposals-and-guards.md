# Proposals and their guards

[← chat index](../chat.md)

Read before editing `planProposal`, `approveProposal` or `proposalGuards` in `src/lib/chat.ts`, or `chatGuards` in `src/lib/settings.ts`.

**The orchestrator chat picks what work to do; something a person wrote picks what an agent may do; a person decides whether it happens.** `chat.ts` is a conversation with a read-mostly tool surface, and the two tools that write anything add a `chat_proposals` row or a template's *prompt* — both inert, holding no folder claim and no concurrency slot. `planProposal` is where a proposal becomes a run, and the branch that matters is the one that is *not* in it: no value off a proposal sets a budget, a permission mode or an isolation choice. Those come from the named template, or from `settings.chatDefaultGuards` when it names none. **A proposal may name a `model` of its own, and it is not a fourth guard however much a new field on `ProposalInput` looks like one.** The precedence is stated once and applied once, in `planProposal`: the proposal's model, then the template's — inherited here with the prompt and the guards — then null, which `createRun` turns into `settings.defaultModel`. What licenses the field is `agents.ts`' ground, restated by `templates.ts` and again beside the column: a model moves cost rather than capability, it reaches `--model` and nothing else, and every cost guard already covers whatever it selects, since the run's spend lands on its own `result` event and in its telemetry whatever model produced it. So `propose_run` and `save_template` each grew a field for it and neither grew one for a guard: the budget, the work-cycle limit, the permission mode and the isolation choice still come from the template or from `settings.chatDefaultGuards`, and there is still nothing on the wire that reaches one. Both tool descriptions say that outright, because a model told it may set the model reads the omission as an oversight. `settings.chatDefaultGuards` is a guard set and holds no model, so an untemplated proposal that named none has nothing to inherit and falls straight through — the second one exists because requiring a template made the chat useless on a stock install, and it is a *person's* configuration either way, which is the property that matters. The second is also *frozen onto the proposal* when it is written rather than re-read at the click, for the reason the paragraph below gives. A proposal that names a template that has since been deleted is refused by name rather than falling back to the defaults: the operator approved the card that said "Fix a bug", and a run under different rules than the card stated is what this gate exists to prevent. `--permission-mode` is not something a model should be able to reach for — the same reason `reopenRun` refuses to become a third route to that flag. The approval route takes an explicit list of ids the page displayed, so a proposal the chat added between render and click is not swept into an approval nobody saw, and it approves in one synchronous pass because `createRun`'s folder claim is only atomic inside an event-loop turn. An id that is not pending in *that* chat is dropped rather than approved — and `decisionNote` then has to say which of the two things it was, because "already decided" is a sentence about this thread's proposals and a selection carried over from another one is not. A batch where every id is dropped is a 400 for the same reason an empty list is: a 200 with nothing started is indistinguishable from a batch that worked, and the page clears the selection on `res.ok`. **A click refused by something that will have cleared by the time the operator looks again is a 400 too, and it is refused whole, before anything is decided.** `createRun` throws for five things and two of them are facts about the moment rather than about the proposal — the install limit, whose 24 hours are *rolling*, and another process holding the data-directory lock — so `approveRunBatch` asks both once, up front, and hands the route a sentence rather than a verdict per member. What that avoids is `markProposal(id, "failed")`, which is terminal: `planProposal` refuses anything not `pending`, the route only ever offers what is pending, and the approval loop has no early exit, so one tripped ceiling marked every member of a twenty-proposal click in turn and the only way back to any of them is a billed turn asking the chat to propose it again. The refusal an operator reads says nothing new will start *until spend ages out of the window*, which was true of the install and false of their proposals. Everything else `createRun` refuses for is a property of the proposal — a folder outside every mount, a folder that does not exist, a template or agent since deleted, a rival already continuing the branch — and stays terminal. This is deliberately not a fourth validation pass over what a proposal may be: three doors already re-check those conditions with their own reasons, and `admitDependencies` stays the sole owner of what an edge may be. **There is deliberately no setting that approves a proposal automatically, and the chat itself starts nothing — but auto-start does exist, in one place, and the approval it needs is a different one.** A workflow's orchestrator block starts its runs with nobody clicking anything, because a person saved a graph that had already named that block's folder, its guard set and the most runs it may ever start. The approval moved from the run to the graph; it did not disappear, and everything that made this paragraph's gate worth having survives the move unchanged — see the orchestrator-block invariant below.

**An untemplated proposal's guards are frozen when it is written; a templated one's are read at the click, and the asymmetry is the point.** `chat_proposals.guards_json` holds `chatGuards()` as it stood at the proposal, written server-side by `createProposal` and read back through `proposalGuards` by the only two things that ask — the card and `approveProposal`. The reason the two kinds differ is what each card *promises*. A templated card names a handle, so the operator can go and read the template and see whatever it says today, and reading it live is what lets them fix a bad guard set and have the fix take effect. An untemplated card has no handle and so spells the values out — `plan · own checkout · 3 cycles · $5.00` — and values on a card are a promise about the run that click starts. Both used to be re-derived from `chatGuards()`: the label on every poll, and the run again at the click. So an edit to `chatDefaultGuards` landing in between changed the card under the operator between two renders and started the run under a set no card had ever shown — measured at `plan · own checkout · 3 cycles · $5.00` against a `bypassPermissions` agent in the operator's own folder with no cap on cycles and none on money, and nothing anywhere recording that the two disagreed. That is the same sentence one gate along from the deleted-template refusal, which exists because "a run under different rules than the card stated is what this gate exists to prevent". Freezing removes the window rather than detecting it: there is no fingerprint on the request, no refusal on drift and nothing that tells the operator to reload, **because the card does not go stale**. What null means is a fallback and only ever a fallback — a templated proposal, a workflow one, every proposal already pending across the upgrade that added the column — and it falls back to the live set, which is what every reader did before. A blob that will not parse is null too; a *partial* one is not, and is narrowed by the same `narrowGuards` the settings blob goes through, so an older shape or a hand-edited row resolves to `plan`, a checkout of its own and one work cycle. Every way this can be wrong is narrower than what was asked for, because a guard set arriving from storage may never widen what a run may do. Nothing on the wire can reach the column: `ProposalInput` has no field for it and `propose_run` has no argument, which is `prompt_override`'s rule — prompt text is the half of a run a model may write, and this is exactly what guards are not. The `model` field that now sits two columns over is not a counter-example and carries a comment saying so: it decides what the run costs, which every guard in this blob already measures rather than being set by, and nothing about what the run may do. Since `settings.modelCatalogue`, `propose_run` refuses a model that is not an enabled entry — in the model's own turn, where it can act on the sentence — and the approval deliberately does **not** check it again. That is this file's own classification applied rather than an exception to it: a field read live and refusing the click is one that decides something about the run and could make the run differ from what the card stated, and a model switched off between the write and the press changes what the run costs, which every guard on that card already measures, and nothing about what it may do. So it sits with `task_ids` on the side that never refuses an approval, not with `template_id` on the side that does. The cost of getting that backwards is what makes it worth stating: a refusal here is terminal, `planProposal` refuses anything not `pending` and the approval loop has no early exit, so one retired model would mark every member of a twenty-proposal click failed and the only way back to any of them is a billed turn. The `[1m]` ids reach the row and the argv with their square brackets intact; nothing on that path may normalise the suffix away, because it is a Claude Code construct and the CLI is what reads it. A **workflow** proposal is deliberately outside all of it: approving one saves a graph the operator then presses Run on, and that is a different gate with its own guard set on each block.

**A proposal may name the tasks on the board it is for, and it is the one field that is neither frozen nor a gate.** `chat_proposals.task_ids` holds ids from `list_tasks` and is read **live** at the click — the title and the status on the card are whatever the board says now — which puts it on the opposite side of the paragraph above from the guards and on a different side again from the template and the agent. The guards are frozen because a card that spells values out is a promise about the run this click starts. The template and the agent are read live *and refuse the click*, because both decide something about the run and a card naming one that has gone would start a run under rules or an identity nobody approved. The task decides **nothing about the run**: not a guard, not the folder, not the prompt, not who it is. It is a record of what prompted the work, so what it needs is a handle the operator can go and read — which is what an id resolved at the render buys — and there is nothing about it a click could be wrong about. So a task deleted between the proposal and the press does not refuse the approval: the run still starts, the card and the run page both say *a task since deleted*, and neither links, because the board row they would open is not there. Approving is also not a claim and not a completion — the run claims its tasks when it starts; see `docs/agent/taskboard.md`, which owns the rule that nothing derives a task's status from a run. Unknown at the *tool call* is a different moment and is refused there by name, through `readTaskLinks`, and so is a brief that names an open task the proposal does not list — the chat batching three tasks into one run and linking one is the failure that made this a list, and the taskboard doc has it, on the same ground `propose_run` refuses a deleted template and a deleted agent: a proposal that cannot be believed is otherwise discovered by a person reading a card. `create_task` is the one write on this surface that is not a proposal or a template prompt, and it is on the **chat's** list rather than the shared one — a block's turn is unattended, and the taskboard doc holds the reasoning.
