# `GET /api/chat` and the thread poll

[← chat index](../chat.md)

Read before editing `src/app/api/chat/route.ts`, `src/app/api/chat/[id]/route.ts`, `findChats` in `src/lib/chat.ts` or `mergeMessages` in `src/lib/chatThread.ts`.

**`GET /api/chat` answers two different questions, and which one is decided by whether it was given a parameter at all.** Bare, it is what the page polls: the newest 30 threads *and* the thread to open on, which is `latestChat()` — and that **creates** a thread when the install has none. With `q`, `offset` or `limit` it answers with the list alone, because a search must not do that: an operator looking for a conversation from March would otherwise leave an empty thread behind every time they typed. The 30 stays, and is not the gap — it is the live sidebar list, re-read on every poll while a turn runs, and streaming every thread through that payload would grow it with the install. What was missing was any *other* way to reach a thread, so an approved proposal's reasoning became unreachable the moment thirty conversations had happened since. `findChats` is that way: `LIMIT`/`OFFSET` beside a `COUNT(*)` over the same predicate, and the text matched against the title **or** any message in the thread — a title is written by the model from the opening line, so searching titles alone finds only the conversations somebody already remembers. `EXISTS` rather than a join, so a thread with forty matching messages is one row. The operator's text is a bound parameter and its `%` and `_` are escaped, because unescaped a `%` anywhere in a query matches every thread in the install and a search that returns everything reads exactly like a search that found everything. On the page the results are held apart from the polled list and not for tidiness: that list is overwritten every few seconds, so a result set kept in it would be wiped mid-read.

**The poll asks for the messages it does not have, and that is the only half of the thread a cursor may be right about.** `GET /api/chat/[id]` takes `?after=`, the highest `chat_messages.seq` the page holds, and `chatDTO` answers with the messages past it — the mechanism `/api/runs/[id]/stream` has always used for the run log, arriving here because the chat page re-asked for the whole conversation every three seconds for as long as it was open, so the cost of leaving a chat on screen rose with the chat and never came back down. Measured on a 500-message thread, one poll went from 246,362 bytes of JSON to 1,136, and on a 2,000-message thread from 1,004,522 to 1,137 — the point being the two figures after, not the ratio. **Only the messages ride it.** They are the one store on this page that is written by appending and never touched again; proposals and questions are both updated in place after they are written, so a cursored read of either would leave a decided proposal drawn with its buttons and an answered question still asking. Those two are re-read whole on every poll on purpose, and so is the thirty-thread sidebar above. **The bound is the index, not the parameter.** On `idx_chat_messages_chat (chat_id, ts)` SQLite answers `seq > ?` by visiting every row of the thread and sorting the survivors in a temp B-tree, so the cursor would shrink the *response* and leave the work where it was; `idx_chat_messages_seq (chat_id, seq)`, created in `migrate()` after the column it names, is what turns it into a range scan. The page appends what comes back rather than replacing what it holds — `mergeMessages`, which drops anything at or below the highest `seq` on screen, because the interval fires whether or not the last request has answered and two polls on one cursor are ordinary. `messagesFrom` on the payload is what says which kind of answer it is: a send, a cancel, an answer, a decision, the first load and a `?after=` the page could not have sent all come back as the whole thread, at zero, and replace.
