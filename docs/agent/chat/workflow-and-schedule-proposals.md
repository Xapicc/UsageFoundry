# Workflow and schedule proposals

[← chat index](../chat.md)

Read before editing `planWorkflowProposal` in `src/lib/workflows.ts` or `planScheduleProposal`/`approveScheduleProposal` in `src/lib/schedules.ts`.

**The chat can write a workflow, and approving one saves it rather than starting it.** That asymmetry with `propose_run` is the whole design. An orchestrator block's runs start with nobody looking *because a person fixed its folder, its guard set and its fan-out cap when they saved the graph* — and a graph a model wrote has no such person in it. Saving rather than starting puts one back: the operator reads a card that spells out every guard-shaped fact a canvas would show (`summarizeProposedGraph` — which template supplies each block's guards or the untemplated set written out, where each block runs, how many runs a deciding block may start, whether a merge block may pay to reconcile), then opens the graph, then presses Run. Two separate human decisions stand behind every number in it before an agent exists. `planWorkflowProposal` re-normalizes through the *same* `normalizeWorkflowInput` and the same `folderRefusal` the save route and the validate route call, with the same `currentKnowledge()`, so a template deleted between the proposal and the click is refused by name exactly as `planProposal` refuses one — a second set of rules about what a workflow may be would be confidently wrong about what Approve does the day one of them changed. The **instance budget is not carried**, and there is nothing on the wire that could carry it: no field on the tool, no column on the row, no argument on the plan. That is `startWorkflow`'s "there is nothing to raise it *with*" applied one level up, and its cost is stated rather than absorbed — a proposed workflow runs by hand and `scheduleRefusal` will not let it be scheduled until the operator sets one, which the card says in words. `propose_workflow` requires a `folder` on every non-merge block even though `normalizeWorkflowInput` accepts `""`: the empty string is a real answer from the editor's picker and an *omitted* field is not that answer, and reading one as the other would silently put a block on the mount root — the one selection that blocks every other run in the tree. `propose_run` holds the same line beside a `mountId`, and both doors refuse `null` as they refuse an omitted field, since the normalizer's `?? ""` reads it as the mount root too. `propose_run` also refuses the other half of the pair too: a non-empty `folder` with no `mountId` is refused naming `list_folders`, `list_tasks`' rule, because a templated proposal would otherwise run in the template's folder under a reply that never said the one the model named was dropped. Neither refusal writes a `chat_proposals` row.

**The chat can propose a schedule, and it is the one proposal whose approval leads to spending with nobody present.** `propose_schedule` names a workflow a person already saved and a recurrence; approving it calls `putSchedule`, the schedule form's own write, through `approveScheduleProposal`. What makes that defensible is that the model can name neither half of what bounds it. The workflow must already carry a workflow-wide limit — `scheduleRefusal`, asked at the tool call, on the card and again at the click, because clearing those limits is one edit away and nothing about that edit knows a card is waiting — and every start then runs under that workflow's blocks and limits exactly as a clicked one does. The **recurrence is frozen** on `chat_proposals.schedule` for the untemplated guard set's reason: the card spells a cadence out, and a cadence on a card is a promise about when spending starts. The **workflow is read live** for the template's reason: it is a handle the operator can open, and one deleted or unlimited since refuses the click by name through `planScheduleProposal`, pure and unit-tested. It is stored as `normalizeScheduleInput`'s *input* rather than a spec so an every-N-hours interval is anchored at the approval rather than at the moment a model wrote the card. Approval creates an active schedule, because that is what the form's Save does and the card states what the form states — the first start as an instant in the reader's own time, so a wrong zone is visibly an hour out before anyone agrees to it. A schedule the operator had paused stays paused with its new recurrence, which is `putSchedule`'s rule and is on the card. A second waiting schedule card for one workflow is refused at the tool, since a workflow holds one schedule and approving both in one click would keep whichever the route reached last. `decisionNote` counts schedules apart from saved workflows, because folding them together reads as nothing ever running until somebody presses something.
