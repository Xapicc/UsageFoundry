# A run's spend and the other spend readings

[← metering index](../metering.md)

Read before editing how `src/lib/orchestrator.ts` records a cycle's cost (`cycleSpendOf`, `runs.session_cost_usd`, `reconcileKilledCycle`, `runs.active_iteration`), `telemetryWindow` in `src/lib/otlp.ts`, or `src/lib/repoSpend.ts`. What each repository cost, and what a repository's runs keep re-deriving, are [repository-spend-and-reading.md](repository-spend-and-reading.md).

**Per-iteration spend comes from the CLI's own `result` event** (`total_cost_usd`), not re-derived from tokens. The transcript-derived cost math in `pricing.ts` serves the dashboard; the two are independent on purpose. **A cycle can see more than one `result`, and that event's two figures are not the same kind of number.** `total_cost_usd` is the *session's* running total, so a second one already contains the first and `cycleCostAfterResult` takes the larger rather than adding; `usage` beside it is only that stretch's own and is still summed. One child emits two whenever a turn ends while a background sub-agent is still running and the same session is woken again when it answers — measured on run `075f7959`, where $7.025419 and $9.330155 arrived in the same millisecond and were stored as their sum, 75% above the $9.330155 telemetry recorded across all 110 of that session's requests, on the figure `maxRunCostUSD` is compared against. The fold is scoped to one `IterationResult`, because across children the figure needs the rule in the next paragraph. **`result.usage` is main-thread-only**, so `spent_tokens` understates a delegating cycle by whatever its sub-agents burned — 5,915,907 against telemetry's 8,481,166 on that same run, where three `Explore` sub-agents made 54 of the 110 requests. Not corrected from telemetry, on the rule one table up: that would make `runs.spent_tokens` a mixture of two sources. It is reported beside, never folded in.

**A resumed cycle's `total_cost_usd` is its session's running total, so the run loop banks the increase.** On the pinned CLI a `--resume`d child restores the ledger the previous child saved in the transcript's `cost-state` record and reports from there. This was read off the binary and never run; see `docs/verification/metering-and-cost-run-spend.md`. The loop used to add each figure whole, which charged cycle N for cycles 1..N. One run's `cost-state` climbed 8.415 → 10.34 → 11.97 over three cycles and would have been stored as $30.73. That inflated figure reached `spent_usd`, the pre-cycle `maxRunCostUSD` check, `liveGuardTick` (which builds on the loop's `spentUSD`), `--max-budget-usd`'s remainder and every rollup of the column. `cycleSpendOf` decides what each cycle adds, on the chat's `turnCostOf` rules, measured from `runs.session_cost_usd`, the last figure reported. The whole figure is banked when the cycle resumed nothing (the first cycle, a fresh start, an expired session), when the CLI answered under another session, when there is no earlier figure, or when the total went down. The feed's "cycle done" row and `run.cycle_finished`'s `cost_usd` are measured from the same baseline, because they read the `result` event's `costUSD`, which a resumed child's first result used to fill with the session's total — three cycles of $3, $5 and $2 read $3, $8 and $10 on rows a reader adds up. The loop hands `runIteration` the resume target and `runs.session_cost_usd` as `IterationResult.resumedLedger`, and `handleStreamLine` measures a child's first result against it on the same rules. `IterationResult.costUSD` stays the running total, because `cycleSpendOf` does its own subtraction. The two branches that go back to a session a failed resume left — the resume retry and the fork fallback — restore its figure as well as its id, and `returnToSession` puts both on the row in one statement. The figure used to be restored in the loop's frame only, after the post-cycle UPDATE had stored the failed cycle's null, so a segment that ended before the retry spawned left the row with the session and no baseline, and the next pick-up banked the session's whole total: $3 and $2 of work stored as $8. The earlier sentence here, that a restarted child's accumulator starts at zero so those runs reconciled to the cent, was never recorded against a CLI pin; the 2.1.280 binary saves the ledger at exit even after `error_during_execution`. Two directions are accepted rather than fixed, and both over-count. A run whose row predates the column banks its first resumed cycle whole, once. A child stopped by `SIGINT` still saves its ledger, so the next cycle's increase includes the stopped cycle that `spent_usd_est` already holds. `--max-budget-usd` needs no such correction: the CLI compares it against spend since the restore, so the remainder the loop passes is already per invocation.

**A killed cycle's spend is reconciled, into its own column.** A cycle interrupted mid-flight never emits `result`, so it contributes $0 to `spent_usd`. `reconcileKilledCycle` recovers an estimate from the transcript pipeline — same dedupe key, same price table, same cache-TTL weighting — bounded by session id *and* the cycle's time range, because a resumed session copies earlier turns forward with their original timestamps. A cycle no loop came back for — one the shutdown's grace outlasted, or one a hard stop left open for the next boot — is reconciled the same way by `reconcileInterruptedCycles`, which takes the lower bound from `active_started_at` and charges the cycle to `iterations` in the same statement (`shutdown-and-restart.md`). It lands in `spent_usd_est`/`spent_tokens_est` and **never** in `spent_usd`, which stays a floor of what the CLI itself measured; `RunProgress.spentGuardUSD` is the sum, and only the guard reads it. This is the same display-vs-guard split `costUSD`/`costGuardUSD` already makes for windows. The kill ladder tries `SIGINT` first for the same reason — a CLI that handles it may still print `result`, which is the difference between measured and estimated. This is Claude's half: a Codex cycle killed before `turn.completed` is banked from its rollout instead, in `codex-killed-cycles.md`.

**The cycle in flight is on the row, in its own column, and it is not a count.** `iterations` is written only when a cycle *returns*, or when one no loop came back for is reconciled, because that is what the guard counts — so for the whole of cycle 1, routinely tens of minutes, a working run read `0/N` and `$0.00`, which is bit-for-bit what a run that was marked running and never started reads. `runs.active_iteration` is the same number one tick earlier: stamped beside the `iteration` event at the spawn, cleared in the post-cycle UPDATE and again in `startRun`'s `finally`, so between cycles it is null rather than naming one that has already returned. It is display only — nothing derives a limit from it and `evaluateBudget` is passed exactly what it was before, including the live guard's deliberate `iterations - 1`. `fmtCycleInFlight` is the single reader and it refuses the column on any status but `running`, because nothing clears the row when the container dies mid-cycle and a finished run claiming an open cycle is the same lie pointing the other way. The wording is "cycle N of M **in flight**" for the reason `spent_usd_est` is a separate column: a reading that could be added to the completed count would be worse than no reading. `spent_usd` is untouched by this — it stays a floor of what the CLI measured, and the figure that moves during a cycle is still telemetry's.

**What a run is spending *now* is a third reading on the dashboard, never a correction to the meters.** A cycle's spend lands on `runs.spent_usd` only when the CLI emits `result`, so a cycle in flight contributes $0 there for its whole duration and the page can say nothing about which run is responsible or what it has cost so far. `telemetryWindow(since)` groups `otlp_requests` by `run_id` over the *snapshot's own* `session.startsAt`, so the card covers the same five hours as the meter above it — and the two are still never added, because one is Claude Code's per-request cost for agents this app spawned and the other is our price table over every transcript on the machine, covering overlapping work. Rows with a null `run_id` are excluded: the orchestrator stamps one onto every agent it spawns, so an unattributed record is something else pointed at the ingest route, and the card claims to describe runs. The listed runs are capped at the heaviest few while `runCount` reports the whole set, for the same reason a shortened diff says so. The poll drops from 120s to 60s **only** while `workingRunCount > 0` — `buildSnapshot` re-aggregates the full history on every request and the agent is competing for the same CPU, so a permanently faster dashboard would be paid for by the run it is watching.

**A batch the ingest route read but could not write is answered 503 and logged, never 200.** `otlp_requests` is the live `run_cost`/`run_tokens` guard's only input, and the exporter treats a 200 as delivered and never retries it, so the old blanket `catch` answering 200 lost that spend from the guard for the rest of the cycle with no line anywhere — and the post-cycle "guard was blind" note only fires when *all* telemetry was lost. A body that does not parse is still 200, since no retry fixes it; a retried batch is a no-op through `INSERT OR IGNORE` on `request_id`. The route's own docblock carries the 200/401/413/503 rules, and `src/app/api/otlp/v1/logs/route.test.ts` pins the split.

**Nothing a telemetry record says may lower a spend figure, because whoever posts it is not trusted to be the exporter.** The ingest capability is in the work cycle's environment by design, where `Bash`'s `env` prints it. `telemetrySpendSince` is a plain `SUM` that the live run guard, the install limit and the workflow limit all read, and one record with `cost_usd: -1000` dated in 2100 made it negative for the cycle in flight and for every later cycle: the live `run_cost`/`run_tokens` guard never tripped, other runs' install and workflow figures read less than was spent, and the post-cycle "reported nothing" check saw requests and said nothing. So `parseLogsPayload` skips a record whose cost or any token count is negative, like any other record it cannot use, and clamps a timestamp after the receive time to the receive time. Clamped rather than dropped, so the record still counts in the cycle that received it. A past date needs no bound, because with every figure non-negative it can only leave spend out of a cycle it was not part of. A record that *raises* a figure counts in full for the forging run's own guards, so it stops only the forger. The install and workflow sums judge every other run, so they take a cycle in flight capped at the `--max-budget-usd` it was spawned with (`runs.active_budget_usd`, `inFlightCostForOthers`): the most the CLI lets it spend. That is the smaller of what the run's own `maxRunCostUSD` has left and the tighter of what the install's limit and its workflow's `maxInstanceCostUSD` have left, so a run with a large limit of its own is held to the headroom too. The headroom is no guess and cannot blind either limit, being where the guards would end the run anyway, and [concurrency-and-install-ceiling.md](../budgets-and-guards/concurrency-and-install-ceiling.md) says what it does not close. A Codex or local cycle, or one with no dollar limit to read, is still uncapped.

**A Codex run's spend is tokens wherever a report shows spend, and it is never folded into a dollar figure.** Codex reports no cost and `spent_usd` holds a zero that measures nothing, so every surface that would have read it as a free run carries the run's tokens in their own place instead: the `/runs/live` tile shows finished cycles' `spent_tokens` and the cycle in flight's rollout total (`cycleCodex`, null until something has been read — never zero tokens); the run page's agent split says in a sentence why there is none; the per-repository report counts a Codex run in `runCount` and in its own `codexRunCount`/`codexTokens` and in **none** of the dollar or Claude token columns, which it used to join — Codex tokens summed with Claude's are a figure no instrument produced; and the install report carries `codexRuns`/`codexTokens` over its own window beside the dollar meter, saying the install limit does not bound them. None of these reaches a guard except the run's own `maxRunTokens`, through `codexInFlightSpend` (`budgets-and-guards/enforcement-modes.md`).

**A loop's cost limit is checked on the guard figure and its card shows the floor with the pass blocks' turns added, and the card says so rather than showing the difference.** `loopSpend` reads the guard reading — the members' `spent_usd` plus reconciled estimates for cycles killed before they reported, plus the pass blocks' turns — so that a loop does not take another pass on money it has already spent. The instance page's loop card shows what the rows show: member runs' `spentUSD` plus the reported `costUSD` of the orchestrator and merge members (`loopSpendShown`). It is a floor and can sit well under a limit the loop stopped on; `AggregateDTO.costGuardUSD`'s reading stays unrendered, so under the limit the card says the limit is *checked against a figure that also counts cycles cut short before they reported*, and only when a limit is set. Before the pass blocks were added the card summed runs alone and the gap also included the deciding and merging turns, which are billed and shown on their own rows.
