# What each repository cost, and what its runs keep re-deriving

[← metering index](../metering.md)

Read before editing `src/lib/repoSpend.ts`, `src/lib/repoReading.ts` or `runs.folder_repo`. Split out of [A run's spend and the other spend readings](run-spend-readings.md) on 2026-11-08; its first paragraph here is that page's *fifth reading* of spend, and the other readings are there.

**What each repository cost is a fifth reading, and it is a report rather than a source.** Every spend figure here was scoped to a run, a workflow instance, a chat, or a time window over the whole account — never to the thing an operator organises work by. With fifteen repositories on one subscription, a weekly window at 80% named nothing that could be acted on, and work done for more than one owner had no basis for apportioning what it cost. `repoSpend` groups `runs.spent_usd` by repository over a span and does nothing else. It is **not** a new cost source: it is the CLI's own `total_cost_usd` per cycle, the same figure the run page already shows, so it must never be added to the transcript-derived meters or to telemetry — three routes to overlapping work, and any sum double-counts. It reaches `buildSnapshot()` nowhere, no window meter reads it and `evaluateBudget` has no argument that could carry it; a threshold on a repository is a limit nobody set, which is `buildPeriods`' reason for the period card on the same page. The figure is a **floor** and the card says so in words: a cycle in flight has emitted no `result` and contributes nothing for its whole duration, and `spent_usd_est` rides in its own column rather than being summed in, the same display-versus-guard split `costUSD`/`costGuardUSD` makes. Identity is `conflictKey`'s and not the stored string, because compose defaults `UF_WORKSPACE_2..4` to `${UF_WORKSPACE}` — so `/workspace/repo` and `/workspace3/repo` are routinely one directory and would otherwise be two rows with half the money each — and segments are case-folded for `overlaps`' reason. A run that was not in a git repository lands in an explicit `(not a repository)` bucket rather than being dropped, which is `groupBy()`'s rule with `(main thread)`/`(no skill)`: the columns have to add to the total over the same span or the table cannot apportion anything, and a page of plausible dollar figures says nothing about the ones missing from it. **Membership is `runs.folder_repo`, never `repo_root`.** `folder_repo` is the repository the run's folder is in, as `rev-parse --show-toplevel` answers when the run's plan is made, checkout or not; `repo_root` is the repository a checkout was cut from, and `land.ts`, `checkoutClaim.ts`, the merge queue's key, `review.ts`'s root and the sandbox all read it that way, so writing it for a run without a checkout would change what each of them does to that run. Grouping on `repo_root` put every run without a checkout in the bucket — isolation off, a repository at the mount root, a monorepo package — which on a single-repository mount is every run, measured on 50d60d8 as $12 of $15 filed there, and pinned by `repoSpendAdmission.test.ts`. A row older than the column falls back to `repo_root` and nothing is backfilled: an older run without a checkout stays in the bucket rather than being filed by a guess from what its folder holds today. A waiting run's is written at release with the rest of its plan, so one cancelled while it waited sits in the bucket at $0. A row is labelled by its mount-relative path, by its mount's label when the repository is the mount root, and as `mount / path` only when two rows would otherwise read the same. The span is bounded by `created_at`, `agentSpend`'s bound and for its reason — it is the one instant on a run that never moves, so a run is counted once and in one span — and the cost of that is stated rather than absorbed: a run created before the span and still spending inside it is not in the report, because `runs.spent_usd` is one running total with no per-cycle timestamps behind it and a report that apportioned it would be inventing a figure. Its own route and its own load rather than a field on `/api/usage`, `agentSpend`'s precedent: that one is the dashboard's heartbeat and re-aggregates the whole history every ten seconds.

**What runs on each repository keep re-deriving is a report beside it, and two of its three readings are not money at all.** `repoReading.ts` answers what `proposals/ContinuousImprovement/` found nothing in the app could: what every run on a repository has read, which walls runs keep hitting, and which files they keep colliding in. It inherits `repoSpend`'s refusals whole. It reaches `buildSnapshot()` nowhere, no meter reads it and `evaluateBudget` has no argument that could carry it. Its repository is `COALESCE(folder_repo, repo_root)` under `repoSpend`'s identity — `conflictKey`, case-folded, through the same exported `keyOf`/`labelsOf` — so the two cards name one repository the same way. **The reading is split by whether the run doing it edited the file, and the split is never dropped.** A read is a repeat when its run is not the first by `created_at` to have read that path there, and "edited" is an `Edit`/`Write`/`MultiEdit`/`NotebookEdit` of the path by the same run at any point. In 2026-08 half the repeats were files the run then changed, which it had to open whatever an earlier run knew, so an unsplit share overstates the prize twofold. A path is relativised against the run's checkout, else its repository, else its folder (`repoRelative`); a path outside stays absolute as its own key. **Failures are grouped by Dreaming's `signatureOf`, unchanged, and ordered by distinct runs.** A second normaliser would put two counts of one failure on two pages. `halves-and-write-policy.md` pins that one to a script, and nothing here may edit it to suit this card. It is fed the stored `tool_error` text, so its signatures can differ from Dreaming's transcript-fed ones and the two lists are not joined. The card carries the "a string, not a cause" caveat and links `/dreaming` rather than restating its install-wide list, which has no folder in it. Ordering by rows would rank one run's 214 retries above ten runs failing once. **The one figure in dollars is `run_reviews.cost_usd` of completed resolutions, per repository and never per file.** A resolution names every file it was handed and costs one figure, so a per-file sum is a multiple count: $196.66 against `CLAUDE.md` alone in 2026-08. That money is billed outside work cycles and is in no run's `spent_usd`. It is not added to anything on the page. **No span.** "An earlier run" needs history from before any span's start. The logs are already bounded by `eventRetentionDays`, so the reading and failures cover every kept log and say how far back that is. `run_reviews` is never swept, so contention carries its own first and last dates. Both `run_events` readings come from one full scan — the table has no index on `kind`, so one scan costs half what two would. That is why the route reads on request and the card loads once without polling.
