# What the image carries: the Claude CLI, gh, Playwright and Codex

[← environment index](../environment.md)

Read before editing a pinned `ARG` or a tool install in `Dockerfile`, `CODEX_BIN`, or anything that assumes a tool is on the image's `PATH`.

- The image carries `gh` (`ARG GH_CLI_VERSION`, checksum-verified release tarball rather than an apt source) for the same reason it carries a compiler: an agent asked to open a pull request finds out `gh` is missing halfway through a cycle, inside a tool call, and works around it badly. It is credentialed only by `githubEnv()`, never by a config file in the image — nothing about the image knows a token.

- The image pins `@anthropic-ai/claude-code` (`ARG CLAUDE_CLI_VERSION`) and sets a system-wide git identity. The pin protects a reverse-engineered contract: the `stream-json` parser and the OTLP shapes were captured from one build, and both degrade *quietly* when it moves — an unparsed line becomes a log entry, a missing `result` event understates spend. The identity is not cosmetic: a container hostname has no domain, so git rejects its own auto-detected address under the strict ident every commit uses, and an isolated run — whose preamble orders it to commit — ends with an empty branch.

- **Playwright and one Chromium are in the image, and nothing configures them.** There is no `UF_` variable here and that is the decision: rendering is not a per-install preference the way a gh extension or a Python tool is — an agent working on a web app either can look at the page it built or it cannot, and the failure of the second is silent. It reads its own JSX, curls its own HTML, and never learns that a dialog opened behind its backdrop. `playwright screenshot <url> shot.png` is one tool call and the PNG goes into the transcript as an image the model reads. **The reason it is a `RUN` rather than a boot install** is the one the Go and gh blocks make: a hand `npm install -g` survives `docker restart` and is discarded by `docker compose up --build`, and what an agent meets after that upgrade is `playwright: not found` inside a tool call the run loop reads as the agent deciding not to look. **What it costs is the largest line in the Dockerfile** — ~640 MB Chromium, ~340 MB headless shell, ~250 MB of X, mesa and font packages, against a 1.9 GB image, all measured (`docs/verification.md`). `--only-shell` would drop the first, but the shell is reachable only through `--channel=chromium-headless-shell`, so every screenshot command an agent writes from memory would fail — a saving paid for in failed tool calls. Firefox and WebKit are absent because a second engine answers a rendering-*difference* question and this answers "does it look right at all"; both are one `playwright install` away for a run that needs them. **`/opt/playwright/browsers` rather than the default `$HOME/.cache/ms-playwright`, and that is not cosmetic**: `/home/node` is chowned recursively in the Dockerfile, and a recursive chown over a gigabyte of browser writes a second copy of that gigabyte into the image. It is also the reason the browsers are not a **fifth named volume** — a volume takes its contents from the image exactly once, at creation, so a shipped browser written into one would be masked by whatever an existing volume already held, which is the trap the winnow block records. The directory belongs to `node` while its contents stay root-owned: the shipped build is one every agent reads and none can rewrite, and a repository pinning a different Playwright version can still put its own build alongside rather than meeting EACCES inside a tool call. `docker-entrypoint.sh` chowns that one directory — **not `-R`**, unlike the three cache volumes above, because a recursive chown of a read-only gigabyte would copy it into the writable layer on the first boot after every rebuild. **`.links` is the one exception and is chowned recursively**, because it holds one 67-byte file per installed package and `playwright install` rewrites its own even on a re-install that downloads nothing: root-owned, the command an agent runs to *check* that a browser is there dies with EACCES under the words "Failed to install browsers", which reads as "there is no Playwright here" and sends the run off to fetch a second Chromium somewhere it can write. **That fix reaches only the installs where the sandbox is off**, which is how the image ships. Under `UF_SANDBOX=1` bubblewrap binds everything outside the write allow-list read-only, so the same command answers `Read-only file system` whoever owns the file, and no chown can change it (measured, `docs/verification.md`). Adding the path to the policy's `allowWrite` does reopen it, and is deliberately **not** done: whether the CLI's `allowWrite` merges with or replaces the working-directory defaults it adds was not measured, and a replacement would leave every agent unable to write its own worktree. Running the browser is unaffected either way — only installing is refused. **Chromium's own sandbox does not work here** for the reason `bwrap` does not — `unshare` is EPERM under Docker's default seccomp profile — and does not need to: Playwright defaults `chromiumSandbox` to false, so the CLI and an ordinary `launch()` both work unchanged, and a script that asks for it explicitly is the one thing that will not.

- **The Codex CLI is in the image, and this app spawns it as `CODEX_BIN`.** `npm install -g @openai/codex`, pinned by `CODEX_CLI_VERSION`, on the argument the `gh`, Go and Playwright blocks beside it all make: an install typed into a shell lands in the writable layer, survives `docker restart` and is discarded by the `docker compose up --build` this project is deployed with, so what the next upgrade hands a Codex run is a spawn that fails, and hands a Claude agent reaching for it on PATH `codex: command not found` inside a tool call, which no part of the run loop reads and which ends the cycle looking like the agent decided not to run it. Two things spawn it, both under the agent uid (`childCredentials()`): a work cycle of a run whose `provider` is `codex`, through `CODEX_ADAPTER` in `orchestrator.ts` (`buildCodexArgs`'s `codex exec --json`, read by `handleCodexStreamLine`, its spend unknown rather than zero per `providerRecordsSpend`), and the four commands behind the Settings sign-in panel in `codexAuth.ts` (`login status`, `login --device-auth`, `login --with-api-key`, `logout`). `proposals/ProviderFallback/13-recommendation.md` argued against a second provider; the tree has one anyway, chosen per run and never switched to at a wall (`selectCycleAdapter`). **It arrives signed out, and a sign-in is a file rather than a variable**: `childEnv` and its five byte-identical siblings strip `OPENAI_API_KEY`, `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN`, the Codex CLI's three credential variables, from every child they build (`docs/agent/security.md`), so a Codex cycle authenticates from `$CODEX_HOME/auth.json`, which the panel's `codex login` writes as the agent uid (the panel's own copy, `codexAuthEnv`, strips only the token and says why). Neither `docker-compose.yml` nor the `Dockerfile` sets `CODEX_HOME`, so `config.ts` resolves it to the CLI's own default under the image's `HOME`, `/home/node/.codex`, which is neither the `~/.claude` bind mount nor a named volume. The credential and the `sessions/` threads a Codex run resumes therefore live in the container's writable layer: they survive `docker restart` and are gone when compose recreates the container, so a sign-in lasts until the next rebuild, and making it persist is a volume at that path rather than a line in the Dockerfile. It is the **last** install block in that file so that moving the pin does not invalidate the Playwright layer above it, which is a 640 MB re-download. ~335 MB unpacked on amd64 and ~292 MB on arm64 from a 123 MB download, and the `rg`, `bwrap` and `zsh` it vendors stay under the package's own `vendor/`: the image's own ripgrep and bubblewrap are untouched.
