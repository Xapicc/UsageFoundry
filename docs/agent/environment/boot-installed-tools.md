# Tools installed at boot or build: Go, gh extensions, winnow and Python tools

[← environment index](../environment.md)

Read before editing the Go stack, `UF_GH_EXTENSIONS`, `WINNOW_REF`/`WINNOW_REPO` or `UF_PY_TOOLS` in `Dockerfile`, `docker-compose.yml` or `docker-entrypoint.sh`, or the named volumes they install into.

- **The image no longer carries Go** — it moved to `stacks/go/stack.json` on 2026-09-12, an `archive` step fetching the same `dl.google.com/go/` release against the same published digest, linked into the toolbox already on `PATH`. An operator who works on Go repositories declares it; one who does not stops carrying 265 MB of compiler. **What did not move is the second half**, and that split is the point: `GOPATH=/home/node/go` and `GOCACHE=/home/node/go/build-cache` are stated in the image so that one named volume, `usagefoundry-gocache`, covers both. Without that volume the caches live in the container's writable layer, which `docker compose up --build` discards — so every agent on a Go repository re-downloads every dependency after each upgrade, inside a billed work cycle, and nothing reports it as anything but a slow run. The volume inverts `/data`'s requirement: the *children* are what write it, so the image ships the directory owned by `node` (uid 1000) rather than root 0700, and `docker-entrypoint.sh` chowns it to `UF_AGENT_UID:UF_AGENT_GID` when those are not 1000 — guarded on a `stat` of the volume root, because a populated module cache is tens of thousands of files and an unconditional recursive chown would sit in front of the healthcheck's start period on every restart. `GOTOOLCHAIN` is deliberately left at `auto`: a repository whose `go.mod` demands a newer Go fetches it into that same persisted cache instead of failing the cycle. Moving `GOPATH` into the stack's own `{state}` was considered and refused — it would have orphaned every module an operator had already downloaded, and `BUILD_CACHE_DIRS` reads `$GOPATH` either way. So the toolchain is declared and the cache is the image's, which is the general shape for a stack whose tool caches somewhere the image already wired.

- `UF_GH_EXTENSIONS` names the `gh` extensions an install wants, and `docker-entrypoint.sh` installs them at boot into `usagefoundry-gh`, the **third named volume** — mounted at `/home/node/.local/share/gh`, which is where gh resolves extensions from (`$XDG_DATA_HOME/gh`, `$HOME/.local/share/gh` when that is unset). Boot rather than the image, because which extensions are wanted is the operator's answer and baking one in versions it with the app while still not reaching the next one; and boot rather than a shell, for the reason the Go cache above is a volume at all — gh's default location is the writable layer, so an extension installed by hand survives `docker restart` and is discarded by the `docker compose up --build` this project is deployed with. The symptom of that is `unknown command` inside a tool call, which the run loop reads as the agent deciding not to use the tool. The image creates the directory so a fresh volume inherits `node` rather than root, and the entrypoint chowns it on the same `stat` guard as the Go cache when `UF_AGENT_UID` is not 1000. Every install runs **as that uid** (`setpriv`), never as root: an extension is an executable the children invoke, and root-owned files there leave them unable to upgrade or remove what they run. It is best-effort and never fatal — a refused extension is a degraded install, not a broken one — so each outcome is one `[usagefoundry]` line and nothing else, and the whole block is skipped with a warning naming the variable when `UF_GITHUB_TOKEN` is blank, because gh answers **no** API call unauthenticated, a public repository included, and `UF_GITHUB_TOKENS` cannot stand in for it (those are chosen by the folder a run works in, and this runs before any run exists). An entry already installed is skipped even when its `@tag` has moved, since a restart is the wrong moment to silently replace an executable that holds a token; the operator removes it and restarts. Nothing in `config.ts` reads this variable — it is consumed entirely by the entrypoint, which is what keeps it off the blank-by-default warning surface the bullet above describes. `deployment.test.ts` pins the three files against each other, because a path that moves in one of them leaves a container that boots, installs, reports success and loses everything on the next rebuild — the original defect wearing a variable that says it is fixed.

- `WINNOW_REF` and `WINNOW_REPO` are **build arguments, not environment variables**, and that is the whole difference between them and `UF_PY_TOOLS` beside them. The Dockerfile clones winnow at a pinned commit into `/opt/winnow`, builds it its own virtualenv there, and `contextPruning.ts` runs `/opt/winnow/venv/bin/python -m winnow` from the image layer. Boot-time installation was the obvious alternative and is wrong here for one reason: with `--autocompact` removed this tool is the **only** thing bounding a work cycle's context, so an install where it failed to arrive is an install whose long cycles run to the model's whole window. `UF_PY_TOOLS` installs best-effort and reports it in a line nobody reads; a `RUN` that fails fails the build. `/opt` rather than `/home/node/pytools` for a second reason that is not taste — that path is a named volume, and a volume takes its contents from the image exactly once, at creation, so a build-time install there is masked by whatever the existing volume already holds. Which is precisely the "installed by hand, lost on rebuild" failure the whole mechanism exists to end. Root-owned and 0755: every agent uid reads it and none writes it, because a tool the run loop shells out to on every cycle boundary, sitting where a sibling agent could rewrite it, is a way for one run to put its own code on every other run's transcript. Pinned to a commit on `CLAUDE_CLI_VERSION`'s argument — the run loop measures this tool's effect and prices it, so an unpinned rebuild moves that contract with no announcement. `WINNOW_REF=` empty builds without it, and `winnowAvailable()` then reports the feature unavailable rather than silently pruning nothing. **Nothing in `config.ts` reads either**, which keeps them off the blank-by-default warning surface, and neither is in `docker-compose.yml`'s `environment:` block at all — a build argument in there would be a variable the container carries and nothing consumes.

- `UF_PY_TOOLS` is that mechanism a second time, for Python, and the reason it exists is a *plugin* rather than an agent. `docker-entrypoint.sh` installs each entry at boot with `uv` into `usagefoundry-pytools`, the **fourth named volume** — mounted at `/home/node/pytools`, holding `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR` and `UV_PYTHON_INSTALL_DIR` under one root so one mount covers all three, with the bin directory on the image's `PATH` (which reaches a hook because `childEnv` copies the server's environment and strips only `UF_*`, `OTEL_*` and four named keys). **The failure it prevents is quieter than the gh one.** A plugin registered through `--plugin-dir` reaches the operator only through its hooks, and a hook body conventionally ends in `|| true`, so a command that is not installed produces no error at all: the hook exits 0 having done nothing and a plugin that announces itself on session start keeps announcing itself. Measured here — 213 sessions told a plugin was active against a command that was never present, which is also the run that settled that `--plugin-dir` **does** register hooks (`SessionStart:startup`/`:resume`/`:compact` all fired). The CLI emits a `hook_response` stream event only for `SessionStart` and `Setup` (`zRo`/`JKy` in the pinned bundle, everything else gated behind `CLAUDE_CODE_REMOTE`), so silence from the other events is not evidence they did not run. **`uv` rather than apt's `python3-venv` + `python3-pip`, and that is the decision.** It gives each tool its own environment, so two Python-backed plugins are not each other's resolution problem; and its bin directory holds launchers, where a shared venv's `bin` on `PATH` would shadow `python3` fleet-wide to install one plugin's dependency. `UV_PYTHON_PREFERENCE=system` so the ordinary case uses the 3.11 already in the image and downloads no interpreter; the install dir is on the volume anyway, for the tool that needs a newer one. **An absolute path is a checkout and takes a different branch**: installed `--editable` and exempt from the already-installed test, so it is re-run on every boot. Both halves are the point. Editable makes the container follow the mounted source rather than copy it — measured, `cozempic.__file__` resolves into `/workspace/…` and a host edit reads back changed — and the boot re-run is the only thing that picks up what editable fixes at install time, the dependencies and the console scripts. A tree too broken to build leaves the previous install in place rather than removing it (measured), so an unconditional reinstall cannot lose a working tool. `name@file:///path` is the pinned counterpart and needs no branch: it carries a name, so it copies once and skips thereafter. **The reach this opens is real and is not new**: an editable install runs code out of a mount the agents can write, on every session start, with no restart in between — which is what a `--plugin-dir` directory already is. The pinned form is the one that does not have it. **Split on spaces and `|` but never on commas** — the one place this deviates from its sibling, because a comma is meaningful inside a version specifier and accepting it would turn `pkg>=1,<2` into two unpinnable entries. The entry goes to `uv` verbatim as a PEP 508 requirement; only the *name* is parsed out, and only for the already-installed test, which is **exact** rather than the substring match the gh block uses (`rich` is a substring of `rich-cli`). Everything else is that block's arrangement unchanged: the image creates the directories so a fresh volume inherits `node` rather than root, the entrypoint chowns on the same `stat` guard when `UF_AGENT_UID` is not 1000, every install runs **as that uid** under `setpriv`, it is best-effort and never fatal, an entry already installed is skipped even when its version has moved, and nothing in `config.ts` reads the variable — which is what keeps it off the blank-by-default warning surface. `deployment.test.ts` pins the three files against each other for the same reason it does for gh. **Two things this does not solve and cannot, both the tool's own behaviour rather than the mechanism's.** A tool with an auto-updater re-installs itself past the pin on every session start, so that switch is the operator's (`COZEMPIC_NO_AUTO_UPDATE=1`). And a tool that installs itself into `~/.claude` on first run is writing the operator's **host** file — that path is a bind mount, which is the whole reason `plugins.ts` passes `--plugin-dir` instead of ever running `claude plugin install` — so it reaches every Claude Code session on the machine and not just this app's. Measured: one `cozempic --version` in a throwaway container wrote 7 hooks into `~/.claude/settings.json`. The plugin's own hook bodies already export both switches (`COZEMPIC_NO_AUTO_UPDATE`, `COZEMPIC_NO_GLOBAL_INIT`); what neither covers is an agent, or an operator, invoking the command directly. And the switches cannot go in `.env` — compose reads that for interpolation and this file has no `env_file`, the trap `UF_LOCK_CLAUDE_HOME` is forwarded against — so they belong in a `docker-compose.override.yml`, which is also the right home for one host's answer to a third-party tool this project does not ship.
