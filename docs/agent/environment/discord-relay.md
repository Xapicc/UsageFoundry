# The Discord relay's variables

[← environment index](../environment.md)

Read before editing `DISCORD_WEBHOOK_URL`, `RELAY_PORT` or `RELAY_BIND`, `scripts/discord-relay.mjs`, or the part of `docker-entrypoint.sh` that starts the relay.

**`DISCORD_WEBHOOK_URL` is the one variable in this file that is deliberately absent from the process it configures.** It is the switch that starts `scripts/discord-relay.mjs` from `docker-entrypoint.sh` — set, and the relay boots on loopback inside the container under a restart loop; blank, and nothing starts. The entrypoint then `unset`s it, and the ordering is the whole point: the relay is launched *before* the unset so it inherits the URL, and the unset happens *before* `exec "$@"` so the server never has it. `orchestrator.ts` builds every agent's environment as `{ ...process.env }`, which makes any variable the server holds readable by twenty-five unattended models, and this one posts to a channel on possession alone. A relay process started as root keeps it out of reach of the agent uid's `/proc/<pid>/environ`. `deployment.test.ts` pins all three of those positions, because an edit that reorders them still delivers every notification and is invisible in every other way.

`RELAY_PORT` and `RELAY_BIND` are the relay's own two, and they are forwarded for the reason nothing about them is interesting: the relay is a second process started by the entrypoint with no environment of its own, so it inherits this `environment:` block and nothing else, and until #186 neither name was in it. `scripts/discord-relay.mjs` documented both as operator configuration and `docker-entrypoint.sh` interpolated `${RELAY_PORT:-8787}` into the URL it tells an operator to set, against a variable no operator could give a value to. Blank-by-default is safe for the same reason `UF_LOCK_CLAUDE_HOME`'s is — no `config.ts` read, so no `STRICT_ENV_VARS` entry and no permanent warning — and `optionalEnv` in the relay already treats `""` as unset, which is what makes a key shipped present-and-empty in `.env.example` mean the default rather than port 0. What kept them missing is what kept `UF_LOCK_CLAUDE_HOME` missing one variable earlier: `deployment.test.ts`'s forwarding assertion was a **prefix**, first `UF_SANDBOX` and then `UF_`, and a prefix only covers the names somebody already thought of. It now derives the read set from every `${NAME}` the entrypoint reads outside a comment, subtracts the names the script assigns itself and the names the `Dockerfile`'s `ENV` sets — both derived, so a new local or a new image variable needs no edit — and requires compose to name the rest; a second assertion does the same for the relay's own `requiredEnv`/`optionalEnv` calls, which is the only thing that can see `RELAY_BIND` at all, since the entrypoint never reads it.

The adjacent temptation, refused: the entrypoint does **not** fill in `UF_WEBHOOK_URL` when `DISCORD_WEBHOOK_URL` is set and it is blank. Blank means the notification channel is off, in `notify.ts`, in `webhookConfigured()` and on `/api/status`, and a boot that silently turned one operator variable into another would make "off" a state the operator could no longer express. It warns on the boot log instead — the same asymmetry as everything else here, where only `DATA_DIR` refuses.
