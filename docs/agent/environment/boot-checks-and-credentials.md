# Boot checks, auth and credential variables

[← environment index](../environment.md)

Read before editing `src/lib/config.ts`, `src/lib/configCheck.ts`, `src/lib/authGuard.ts` or `src/instrumentation.ts`, or any variable that carries a credential or decides who can reach the app.

- All process-level config is centralised in `src/lib/config.ts` and fixed at boot. User-editable values belong in the settings table (`src/lib/settings.ts`), not here.

- **The configuration is checked before the server serves, and exactly one check refuses.** `configCheck.ts` runs first in `instrumentation.ts`, before the data directory is claimed and before anything opens the database, because every way of pointing this app at the wrong place used to present identically: a container that starts, answers `/login` and shows an empty dashboard, which is also what a quiet week looks like. `DATA_DIR` **refuses** — a blank value, a path that is not a directory, or one a real write fails in — and the refusal is `process.exit(1)` rather than a thrown `register()`, because Next logs a rejected boot hook and then serves anyway, which for this variable means a container writing every row into the image's writable layer where the next `docker compose up --build` deletes it. Blank is the case worth naming: `env()` reads it as unset, so `DATA_DIR=` is not a request for the default, and the refusal names the path it *would* have used rather than a variable the operator will not find in their own configuration. Everything else **warns** — a mount that is not a directory, a `CLAUDE_HOME` with no `projects/`, any other variable set to the empty string — and the asymmetry is the decision: a workspace is optional by design (four slots mounted unconditionally, a bind source that may not be up yet), `~/.claude/projects` legitimately does not exist until the machine has run Claude Code once, and refusing there would take the dashboard, the run history and the merge queue away from an install that is degraded rather than broken. Warnings are logged and ride on `/api/usage`'s `meta.configProblems` to a banner above the meters — above rather than under, because unlike the notices there they do not explain a number, they say the numbers may describe the wrong machine. Writability is a real write: `mkdirSync(recursive: true)` reports success for a directory it cannot write to, which is why an ownership mismatch used to arrive later as an `EACCES` out of `writeLock`. The variables where blank *is* the answer go through `optionalEnv` and are never reported, and there are two kinds of them: an **off switch** (`UF_AUTH_TOKEN`, `ANTHROPIC_ADMIN_KEY`, `UF_GITHUB_TOKEN`, `UF_GITHUB_TOKENS`, and the notifier's `UF_WEBHOOK_URL`/`UF_WEBHOOK_SECRET`, where blank on either one is a channel that sends nothing) and a **"take the default"** (`UF_ALLOW_NO_AUTH`, `UF_COOKIE_SECURE`, `UF_TRANSCRIPT_CACHE_MAX_ENTRIES`, `UF_TRUSTED_PROXY_HOPS`, and `UF_PUBLIC_URL`/`UF_INSTALL_LABEL`, whose default is an empty field on a body rather than a behaviour), plus `UF_UNMOUNTED_WORKSPACES`, which is not an operator value at all. `STRICT_ENV_VARS` is collected by `env()` as the module runs rather than listed, so a variable added to `config.ts` cannot be forgotten, and the two lists being disjoint is what `configCheck.test.ts` asserts. **What that disjointness cannot see is compose**, and that is the second pin rather than a detail: compose cannot omit an environment key conditionally, so every optional variable is rendered `${VAR:-}` and a correct install has all of them explicitly blank — which makes each one an edit away from a permanent warning on the dashboard of every stock deployment, naming a variable the operator never wrote. Three of them were exactly that, for as long as the block grew and `BLANK_MEANINGFUL_ENV_VARS` did not, and `UF_UNMOUNTED_WORKSPACES` is the one with no floor under the cost: compose *computes* it from the slots it could not mount, blank is its success case and any non-blank value refuses the boot, so there was no `.env` edit that could clear the warning it raised. Nothing else notices — it typechecks, it boots, every page works, and the only symptom is a banner that is always on, which is how a banner stops being read. So `deployment.test.ts` reads the `environment:` block, resolves it as an install that configures nothing gets it, and refuses a blank-by-default key that `config.ts` reads through `env()`; it pins the exported list against what `optionalEnv` actually reads in the same pass, since that list is what the warning's own sentence enumerates. It pins the other direction too, which is the mirror-image failure and just as quiet: there is no `env_file:`, so that block is the whole of what reaches the container, and a `UF_` name added to `config.ts` and not to compose is read as unset on every compose install no matter what the operator wrote in `.env`. For a credential that is a feature that refuses; for a notifier it is silence, which is what a healthy fleet also looks like.

- `UF_AUTH_TOKEN` blank disables auth entirely, and the app now **refuses to boot** in that state unless `UF_ALLOW_NO_AUTH=1` says the operator meant it — `authBootSignal` in `authGuard.ts` is that decision, pure and unit-tested, called from `instrumentation.ts` before the reconcile guard. Acknowledged, it logs a block at boot and `layout.tsx` puts an undismissable banner on every page through `AppShell`'s `authDisabled` prop, read from a server component so no failed request can leave it off. `/api/login` answers **409** rather than a success when there is no token, because a sign-in that checked nothing looked exactly like one that did. The acknowledgement is compared as the exact string `"1"`, `continueAfterDone`'s rule: a value that makes the app stop protecting itself must fail towards refusing to start. `ANTHROPIC_ADMIN_KEY` blank leaves the API-account page in an explicit "not configured" state rather than showing zeros.

- `UF_BIND_ADDRESS` (default `127.0.0.1`) is compose-only — the app never reads it, so it is outside everything `configCheck.ts` can say. It is one setting whose other two halves fail *silently* in opposite directions, which is why the comment beside it names both rather than pointing at a doc: an operator who publishes on `0.0.0.0` without setting `UF_AUTH_TOKEN` (or who leaves `UF_ALLOW_NO_AUTH=1` from a loopback install) exposes every route including the one that starts billed agents against mounted code, and the app cannot tell that state from the one it was told to accept; and `UF_COOKIE_SECURE=1` carried over from a loopback install becomes a sign-in that *succeeds* and issues a cookie the browser will never send back over plain HTTP, so every request after it is anonymous and the only symptom is a redirect to `/login`. Do not add a check for the first here: nothing in this process can see which interface Docker published on, and a guess would refuse correct installs behind a terminator.

- **`UF_TRUSTED_PROXY_HOPS` (default 0) has to describe what is actually in front, and nothing here can check it.** It is how many proxies append to `x-forwarded-for`, and `sourceAddress` reads the client that many entries from the right — the address sign-in's per-source lockout is keyed on and the audit trail records. Zero reads neither forwarding header, which is right for stock compose, where both are the client's writing, and costs only the per-source bucket. Too high reads an entry the client wrote, so a guesser can name the operator's address and lock it out of sign-in; too low makes the outer proxy's address one bucket for everybody, so anybody's ten guesses lock everybody out. Anything but a whole number reads as zero, the direction that hands nobody the operator's bucket. Like `UF_BIND_ADDRESS`, it is a fact about the deployment rather than the app, and this process sees the same headers either way.

- `UF_GITHUB_TOKEN` blank means runs cannot use GitHub at all, and the Settings header says so — the failure otherwise arrives mid-run, inside a tool call nothing here reads. `UF_GITHUB_TOKENS` is the per-repository half beside it (`folder=token` entries, `|`-separated), and the header says which of the three states an install is in, because how *wide* the credential is was the one thing that page could not say. The `UF_` prefix is load-bearing rather than cosmetic: `gitEnv()` and `reviewEnv()` strip that namespace, so both tokens are withheld from every child except the ones `githubEnv()` hands one to — and a second credential shape needing no second exclusion is the whole point of withholding by namespace.

- **Rotating any of these is a container restart, and *which* of them a restart is the only answer for is the part worth knowing.** Nothing outside a process can write that process's environment and nothing in this app writes its own, so `process.env` is fixed for the life of this server — the same sentence `orchestrator.ts` already gives for reading the GitHub credential once per pick-up rather than once per cycle. **Where a value is read therefore decides nothing.** `middleware.ts:41` and `:114` read `UF_AUTH_TOKEN` and `UF_STATUS_TOKEN` out of `process.env` on every single request — measured rather than assumed, the built `.next/server/src/middleware.js` carries both as property accesses, Next inlining neither into the edge bundle because `docker build` has no token to inline — and they rotate exactly as poorly as `AUTH_TOKEN`'s module `const` two files over. So turning a `const` here into a function that reads at use buys nothing observable, and for the GitHub pair it would cost the guarantee `orchestrator.ts` names in words: that a run keeps one credential for the whole of its life, rather than pushing from one cycle and not the next with nothing saying why. **What differs between these values is who issued them**, which is the question an operator actually has at the moment one leaks.
  - **Issued here, so a restart is the only revocation there is.** `UF_AUTH_TOKEN` (`config.ts:328`, the two per-request reads above, `api/login/route.ts:39`, `api/logout/route.ts:102`, `api/status/route.ts:49`) and `UF_STATUS_TOKEN` (`middleware.ts:183` and nowhere else). Nothing outside this container knows either value, so there is no console to revoke them at and a leaked one stays live until the process holding it is replaced. These two are the whole of the rotation problem. The compensation is worth stating because it is the same lever: rotating `UF_AUTH_TOKEN` is also the *only* thing that invalidates a captured session cookie before its own TTL, since the cookie is HMAC'd with the token (`api/login/route.ts:118`) — which is precisely the hole "sign out everywhere" cannot close, the edge gate having no way to read `auth_sessions`.
  - **Issued elsewhere, so the leak closes without this container and the restart only re-arms the install.** `ANTHROPIC_ADMIN_KEY` (`config.ts:350` → `adminApi.ts:45`), `UF_GITHUB_TOKEN` (`:367`) and `UF_GITHUB_TOKENS` (`:407`, both through `githubTokenFor` into `githubEnv()`), `UF_WEBHOOK_URL` (`:509`) and `UF_WEBHOOK_SECRET` (`:517`, both into `notify.ts:389`), `ANTHROPIC_API_KEY` (`:648` → `modelDiscovery.ts:85`, the one place this process sends it itself, to list models; every work cycle still bills against its own inherited copy, so its rotation also reaches runs only through this restart), and `DISCORD_WEBHOOK_URL`, which this process never holds at all — the entrypoint launches the relay with it and `unset`s it before `exec`. Rotating it is still a container restart and not the relay's own: its restart loop is a subshell forked *before* the unset, so it re-execs with the value it was started with, and the server has no copy to update. Revoke each where it was issued — GitHub, the Anthropic console, the webhook's own receiver — and the exposure is over in seconds with nothing restarted and no run ended. What the restart then buys is the *new* value, and in between the install is **degraded rather than exposed**: pushes fail inside a tool call, the API-account panel reports nothing, notifications stop. That is a different decision from the one above and should not be deferred like it.
  - **Not credentials, and on this footing only because they are read the same way.** `UF_PUBLIC_URL` (`:527`, and `middleware.ts:83`, where it is one more origin a signed-in browser may make a change from — a widening, which is a second reason it is environment-only), `UF_INSTALL_LABEL` (`:530`), `UF_NOTIFY_ON_SUCCESS` (`:547`), `UF_MODEL_DECIDER_URL` (`:562` → `modelDecider.ts`, environment-only for the webhook's reason since every request carries a run's task text), `UF_ALLOW_NO_AUTH` (`:340`), `UF_COOKIE_SECURE` (`:347`), `UF_TRUSTED_PROXY_HOPS` (`:404` → `sourceAddress`, which decides whose sign-in bucket a guess fills), `UF_TRANSCRIPT_CACHE_MAX_ENTRIES` (`:93`), and `UF_UNMOUNTED_WORKSPACES` (`:258`), which is compose's output rather than an operator's input. Beside them sit two credentials this app reads **nowhere** and forwards anyway, so they rotate on this same restart and are easy to forget for exactly that reason: `OPENAI_API_KEY`/`CODEX_API_KEY`, stripped from every child except `codexAuth.ts`'s. `ANTHROPIC_API_KEY` was the third until model discovery read it; it is still deliberately not stripped by any of the five child environments, because it is what a work cycle bills against. Every child is spawned from `{ ...process.env }`, so each of them is this process's copy.
  - **What would make one genuinely rotatable, and why none of it is here.** It takes a second source that can change while the process runs, and there are two. The settings table is refused outright at `config.ts:492-508` — `/api/settings` is reachable with the master key, so a repointable webhook target turns one credential into an exfiltration channel — and that refusal covers every value on this list, not just the notifier's. A file is the other, the `*_FILE` convention Docker and Kubernetes secrets use, and it would work for the third-party group; it does **not** work for the one value that most needs it, because `UF_AUTH_TOKEN` is checked in the edge runtime, which has no `node:fs` and must not import `lib/config`, so a file-backed master key means moving the gate off the edge — which `docs/agent/security.md` calls a change to what `middleware.ts` *is*. Neither is a smaller change than the restart it avoids. The restart's real cost is one module over rather than here: `reconcileOnBoot` closes out every live run, and `lastBootReconcile.closed` is the count `README.md` describes as needing picking up by hand.
  - `deployment.test.ts` pins this list against `config.ts` and `middleware.ts`, because the way it went wrong last time was by **growing**: five variables were added to the notification channel, read the same way for the same reason, and nothing anywhere said so.
