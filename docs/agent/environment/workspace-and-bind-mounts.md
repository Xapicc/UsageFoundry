# Workspace mounts, bind mounts and the agent uid

[← environment index](../environment.md)

Read before editing `WORKSPACE_ROOTS` handling or `parseMounts` in `src/lib/config.ts`, the volumes, bind mounts and `UF_AGENT_UID`/`UF_AGENT_GID` in `docker-compose.yml`, or the workspace, data, backup and stacks directory variables in `.env`.

- The app reads `WORKSPACE_ROOTS` (multiple mounts, `Label=/path` entries joined by `|`) and falls back to the single `WORKSPACE_ROOT` when it is unset. `.env` / `.env.example` define `UF_WORKSPACE`, `UF_WORKSPACE_N` and `UF_WORKSPACE_N_NAME`, which are **only** consumed by `docker-compose.yml` — to pick the host mounts and to compose `WORKSPACE_ROOTS`. Running `npm run dev` without either set falls back to `~/workspace`, so `/api/folders` will look empty even though `.env` names a directory.

- An entry in `WORKSPACE_ROOTS` with an *explicitly empty* label (`=/workspace2`) is **skipped**, while a bare path (`/workspace2`) is labelled from its basename. That asymmetry is load-bearing: compose cannot omit a volume conditionally, so all four slots are always mounted and an unset `UF_WORKSPACE_N_NAME` is what switches a slot off. Switching one of the four on or off must stay an `.env` edit, not a compose edit — and the same sentence is why a *fifth* cannot be one: a slot is a hand-written volume line, so `.env` can reach four of them and no more. That ceiling used to be nowhere in the code and silent at the edge of it, which is the one thing it could not be: `UF_WORKSPACE_5_NAME` was interpolated by nothing, so the directory was never mounted and never reached the picker — indistinguishable from a mounted directory with nothing in it, which is what an operator would then go looking for. `MOUNTED_WORKSPACE_SLOTS` names it in `config.ts`, compose forwards the slots past it as `UF_UNMOUNTED_WORKSPACES` (names, never values — a host path is not needed to say which variable is wrong), and `unmountedWorkspaceRefusal` refuses the boot naming them, which is the treatment `${UF_WORKSPACE:?…}` already gets one line over. `parseMounts` itself stays uncapped, because a `docker-compose.override.yml` mounting a fifth slot is the supported route for one and clears that variable to say the mount was really made. `deployment.test.ts` pins the constant against the volume lines, since a fifth line added without bumping it would refuse a slot the deployment does mount — the same silence inverted.

- `UF_WORKSPACE` and `HOME` use compose's `${VAR:?message}` form, so a missing one aborts `docker compose up` instead of substituting. Both previously had defaults, and both failure modes were silent: Docker *creates* a bind source it is handed, so a wrong path yields an empty folder picker and a dashboard of zeros — indistinguishable from a quiet week. Do not restore a default to either. `UF_WORKSPACE_2..4` still fall back to `UF_WORKSPACE`, which is what keeps all four slots mountable.

- `CLAUDE_HOME` (default `~/.claude`) determines which transcripts are parsed; `DATA_DIR` (default `./.data`) holds the SQLite file.

- `UF_BACKUP_DIR` (default `./backups`) is bind-mounted at `/backups`, and being a bind mount rather than the named volume is the whole of it: a snapshot kept inside `usagefoundry-data` is destroyed by the `docker compose down -v` it exists to survive. Nothing writes there on its own — `scripts/backup-db.mjs` is run by hand or by the operator's own cron, which the README states in words rather than shipping a scheduler, because a timer that spends nothing still needs somewhere to put a file that grows without bound. The mechanism is `VACUUM INTO` through a **read-only** connection, never a file copy: the database is in WAL mode, so a copy of `usagefoundry.db` omits every transaction since the last checkpoint and says nothing about it, and read-only is what keeps the second process off the single-writer assumption `db.ts` opens with. The restore refuses while `server.lock` is still beating, for the reason the lock exists at all. **The server now *reads* that directory, and reads it at `/backups` rather than through `UF_BACKUP_DIR`** — `config.ts`'s `BACKUP_DIR`, surfaced as a Backups row on the Storage card and as a path-free reading on `/api/status`. The variable is the bind **source**, a path on the host, so reading it inside the container would point the reading at a directory that does not exist there; forwarding it into the container to make that work would break the mount's one honest meaning, and `deployment.test.ts` catches the attempt, since it is a `UF_` name the `environment:` block does not carry. The refusal above is about **writing** and is unchanged: nothing here schedules a backup. What it closes is that an install backed up nightly and one backed up once in August used to present identically on every page and in every alertable condition. Three states, never two — a directory this process cannot read (a missing bind mount, or one Docker created as root) is reported as unreadable and not as a count of zero, because those need opposite actions.

- `UF_STACKS_DIR` (default `./stacks`) is bind-mounted **read-only** at `/etc/uf-stacks`, and like `UF_BACKUP_DIR` above it is compose's variable and reaches the entrypoint never — so `C8`'s four-files rule does not apply and this mechanism adds no `UF_` variable the container reads. Read-only and off the host is the whole of the choice: `/workspace` is already mounted and would have needed no compose change at all, and it is refused because **agents write there**, which would make a stack declaration a way for one run to install software into every later run. The artifacts go somewhere else entirely — `usagefoundry-stacks` at `/var/lib/uf-stacks` — because the declaration is the durable thing and the volume is a cache: `down -v` destroys it and the next boot reinstalls every stack from the host, at the cost of time and bandwidth and nothing else. **The image ships nothing under that mount point, ever**, and that is the one invariant here whose breach is invisible to whoever commits it: a volume takes its contents from the image exactly once, at creation, so a `mkdir` or a `COPY` there works on a reviewer's fresh install and is masked on every install that already exists. `deployment.test.ts` asserts the `Dockerfile` names no path under it outside the single `ENV PATH` line, which is the only mention that creates nothing. The repository ships `stacks/.gitkeep` so the default works with no setup and deliberately ships no example stack inside — a directory whose presence means "install this" is not something an operator should find already there.

- `UF_AGENT_UID`/`UF_AGENT_GID` in compose exist because the container writes to both bind mounts, and they carry `${UF_UID:-1000}`/`${UF_GID:-1000}` — the same numbers `user:` used to carry for the whole container. macOS Docker Desktop remaps bind-mount ownership onto the container user, which is why uid 1000 was never questioned; Linux preserves the host uid and a mismatch breaks `/login`, transcript writes, and `.uf-worktrees` creation. `user:` is now `"0:0"` and the *server* is the only thing that runs as root — see the privilege-separation invariant below for why the split has to be that way round. The image still sets `HOME`, `DATA_DIR`, `CLAUDE_HOME` and `CLAUDE_CONFIG_DIR` explicitly — required, because a uid with no `/etc/passwd` entry makes `os.homedir()` unreliable. A documented command that has to run as that uid takes it from `docker compose exec -T usagefoundry printenv UF_AGENT_UID` and **never** from `-u "${UF_UID:-1000}"`: that expansion happens in the operator's own shell, and `.env` is compose's input, not an exported environment, so it is 1000 on every install that set `UF_UID` in the file and nothing else — which is every install this page's own instructions produce (#147). `docs/security.md` and `docs/verification.md` were brought to that shape on 2026-09-08; the one `${UF_UID:-1000}` left in the latter is prose about this compose key, where the interpolation genuinely is compose's own.
