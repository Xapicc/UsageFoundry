# Memory, heap and process limits

[← environment index](../environment.md)

Read before editing `mem_limit`, `memswap_limit`, `pids_limit` or `cpus` in `docker-compose.yml`, or `NODE_OPTIONS` or the `MALLOC_*` variables wherever they are set.

- `mem_limit` / `memswap_limit` / `pids_limit` / `cpus` in compose exist because memory here is linear in `maxConcurrentRuns` and `maxConcurrentAssists`: every work cycle is a full Claude Code process — measured 2026-09-16 at 325-407 MB of RSS through one real cycle, and 145 MB of peak RSS for `claude --help` before it holds a conversation at all — that then starts builds and test suites of its own inside the same container, which is the larger half: `next build` peaked at 1,749 MB over 23 processes on this machine. Those two settings bound how many such processes exist; these bound what they may take. Without a limit the kernel's OOM killer picks its victim across the *whole host*, so the process that dies may be an unrelated one; with it the kill is confined, `restart: unless-stopped` brings the container back, and `reconcileOnBoot` closes out the runs with a reason on each. The defaults are sized for the shipped settings — four work cycles plus two other Claude processes — and the arithmetic is in the compose comment and README's *Sizing the container*; raise them **with** the settings, never after. `memswap_limit` matches `mem_limit` because Docker otherwise defaults the swap limit to *twice* it, so the stated ceiling would silently carry that much swap behind it. `cpus` ships as `0` (no quota) because Docker refuses a value larger than the host's CPU count, so any positive default would fail `docker compose up` on a smaller machine.

- `NODE_OPTIONS` states the server's heap ceiling so the term of that arithmetic belonging to this process is a number rather than a property of the host — V8 derives it from the machine's RAM otherwise. It is the one env var here **not** under the `UF_` namespace that every child environment strips (`childEnv`, `chatEnv`, `reviewEnv`, `gitEnv`): `/usr/local/bin/claude` is a symlink straight to a Bun single-file ELF binary on the current pin, so `NODE_OPTIONS` never reaches the CLI process itself — but it does reach every `node` an agent starts inside a cycle, npm and MCP servers and test runners, where inherited it silently becomes their heap ceiling, and a `heap out of memory` part-way through a billed cycle is filed by the loop as the agent crashing. Do not move it into the Dockerfile to save a line — an image-level `ENV` is inherited the same way, and the strip is what makes the compose comment true.

- `MALLOC_MMAP_THRESHOLD_` / `MALLOC_TRIM_THRESHOLD_` sit beside `NODE_OPTIONS` and are the counter-example to it: they are **not** stripped from any child environment, deliberately. Pinning glibc's mmap threshold at 128 KB stops freed transcript-read buffers ratcheting the server's sbrk heap, which is worth 250 MB against 296 MB at idle and — more usefully — a run-to-run spread of 12 MB against 50 MB, measured n=3 on a server built and started beside the running one, 2026-09-16. A heap ceiling inherited by a child is a trap because it is a *limit* and the child's workload is not the server's; an allocator threshold is a hint, and letting it through was measured to cost an agent's `npm test` and `next build` nothing in either RSS or wall time. `MALLOC_ARENA_MAX` is the variable this was proposed as and is deliberately absent: it moved idle RSS by 2 MB and raised `[heap]` from 40 to 54 MB. The CLI process ignores all of them — `claude.exe` is a Bun single-file binary carrying mimalloc. If you are tempted to add another `MALLOC_*`, the question to answer first is not whether it helps the server but what it does to the node children that will inherit it.
