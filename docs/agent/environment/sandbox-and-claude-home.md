# The CLI sandbox and the locked Claude home

[← environment index](../environment.md)

Read before editing `UF_SANDBOX`, `UF_SANDBOX_ENFORCEMENT`, `UF_SANDBOX_ALLOWED_DOMAINS` or `UF_LOCK_CLAUDE_HOME`, or the parts of `docker-entrypoint.sh` that read them.

- `UF_SANDBOX`, `UF_SANDBOX_ENFORCEMENT` and `UF_SANDBOX_ALLOWED_DOMAINS` are the CLI's own Linux sandbox, and all three are consumed **entirely by `docker-entrypoint.sh`** — nothing in `config.ts` reads them, which is what keeps them off the blank-by-default warning surface two bullets up, exactly as `UF_GH_EXTENSIONS` is. Blank is off and off writes **nothing**: no `/etc/claude-code`, no policy, no behaviour change, so a stock `docker compose up --build` is byte-for-byte the install it was before the switch existed. `UF_SANDBOX=1` generates `/etc/claude-code/managed-settings.json` root-owned 0644 — root because the agents are `UF_AGENT_UID` and that is the one policy surface they cannot rewrite, 0644 because the `claude` children that must *read* it are that same uid. **Generated at boot rather than baked into the image, and that is the decision.** The seccomp relaxation it needs lives in `docker-compose.yml`'s commented `security_opt` block — or in a `docker-compose.override.yml`, which is where one host's answer belongs — so an install whose Docker rejects or never applied that profile has no working sandbox, and `failIfUnavailable: true` compiled into an image would then mean every `claude` invocation exits non-zero, fleet-wide, with no off switch short of a rebuild (`git show a74a1bb:"proposals/implemented - Sandboxing/09-implementation-sketch.md"` lines 15–22). `UF_SANDBOX_ENFORCEMENT` is that switch and it is an `.env` edit. **What it does not switch is the failure this install actually had**, and that is the sharpest thing on this page: `failIfUnavailable` is a *startup* gate over an availability check that only asks whether `bwrap` and `socat` exist and are executable — it never runs one. So an installed bubblewrap the kernel refuses passes the check, the gate never fires at either setting, and every command is wrapped in a program that exits 1 before the command does. Measured here the expensive way: 214 failed `Bash` calls across 10 runs over fifteen hours, on runs recording $407 between them, with `UF_SANDBOX_ENFORCEMENT=refuse` set and nothing refused. `sandbox.ts`'s `bwrap-failed` markers exist so the next one is a `sandbox` row on the run's own log instead. **Which is not what happened next**, and the shape of that second failure is worth more than the first: the markers were written from the wording that had just been measured, the profile went on, bubblewrap started getting as far as its *mounts*, and the 714 failed calls it has produced since 2026-08-25 say `bwrap: Can't create file at …` — a sentence the table did not carry, so the detector was silent again for three weeks with the boot line still reading `on`. A marker read off one incident is pinned to that incident. What is on the table now is `bwrap: Can't `, and what an operator sees is a note on the settings page's Sandbox row counting the last day's `sandbox` rows beside the word the policy file earns, because a row that says only `on` is the thing that went unread twice. **Five further things are load-bearing and each fails silently.** The policy carries `enableWeakerNestedSandbox: true` unconditionally, and it is not a confinement: it switches the CLI from mounting a fresh procfs (`--proc /proc`, refused inside Docker's masked `/proc`, measured as `Can't mount proc on /newroot/proc` even as root under the profile) to binding the existing one. Without it the seccomp profile buys a namespace the sandbox still cannot use. It is deliberately **not** counted by `policyNamesSomething`, since a policy naming only it would confine nothing while reading as "on". The policy **can never resolve to nothing**: the CLI hands a command back *unwrapped* when the whole policy names no read deny, no write restriction, no network entry and no credential — and `failIfUnavailable` does not catch that, because a sandbox nothing was asked of is not one that failed — so the credential deny and the two `denyRead` paths are unconditional and are not operator-configurable. It writes `denyRead` and **never** `allowWrite`/`denyWrite`: a write config of any kind makes the CLI bind `/` read-only and rw-bind only the allow set, so a deny-write list with no allow list is a read-only filesystem and a fleet that fails inside its first tool call. Naming `sandbox.filesystem` at all is also what pins `sandbox.filesystem.disabled` to managed settings, which matters because a run that could set that key would drop the credential deny with it. And the file is written to a temp name, parsed, and only then moved into place — a policy the CLI cannot read has its whole `sandbox` block ignored, taking `failIfUnavailable` with it, and a write that fails must leave an operator's own `managed-settings.json` alone. Which is also why the removal on the way back down is gated on `/etc/claude-code/.usagefoundry-owned`: `docker restart` keeps the writable layer, so a policy written under an earlier setting would outlive it, and an off switch that leaves the sandbox on is worse than no switch. The app reads the **file** (`src/lib/sandbox.ts`), never the variable, so an install where the write failed reports no sandbox rather than repeating what `.env` claims — the two are joined by a `[usagefoundry]` line from the entrypoint and nothing else. **Some of it has now been executed, and badly**: an install ran with the policy on and bubblewrap unable to start for fifteen hours, which is where the paragraph above's figures come from and why the `bwrap:` markers exist. What has been measured is that the seccomp profile is what lets a namespace be created (exit 0 at both uids with it, "No permissions to create new namespace" without), that Docker's masked `/proc` refuses the CLI's default bubblewrap shape and accepts the weaker one, and that the availability check does not run what it checks. And, since the seccomp profile and that key went in together, that a `claude` runs a `Bash` command through a sandbox that started (`echo` into `/tmp`, returned, $0.298) and that the credential deny **denies** — a file uid 1000 owns and can `cat` from a plain `docker exec` comes back `Permission denied` through a sandboxed tool call, which is a policy enforced rather than a policy reported. What has **not** been measured is a work cycle doing real work under one: no per-run `--settings` overlay has ever reached a running sandbox, and the `denyRead` paths and the network allowlist are unexercised. `docs/verification.md` carries both the results and the steps still outstanding.

- `UF_LOCK_CLAUDE_HOME` is the other half of that sandbox and a **separate switch on purpose**, also read only by `docker-entrypoint.sh`. `$CLAUDE_CONFIG_DIR/settings.json` is an honored source for `sandbox.*` — the pinned binary resolves the policy from `[...managed, flagSettings, userSettings]` and `filesystem.allowWrite` is documented as *additional* paths — and it is owned by `UF_AGENT_UID`, so until this is on a run appends `{"sandbox":{"filesystem":{"allowWrite":["/"]}}}` and every later session, its own and every sibling's, starts confined to nothing (`git show a74a1bb:"proposals/implemented - Sandboxing/10-validation.md"`, finding 1). Root-owning the *file* does not close it: unlinking is a write to the directory, which the agents own, so the **directory** becomes root's too. Its mode is `1770`, and every bit is load-bearing. **Group-writable**, because CLI 2.1.280 cannot keep a login alive in a directory it only reads: an OAuth refresh first takes `<dir>/.oauth_refresh.lock` and every credential write does `mkdir <dir>/.storage-write.lock`, both beside `.credentials.json`, and both fail with `EACCES` where the agents have no write bit, so the refresh returns `lock_error` before it reaches the token endpoint and the install stops authenticating once the stored access token expires (measured 2026-09-27, `docs/verification.md`; a `0550` stand-in was silent about it, 0 token attempts against 3 in the control). **Sticky**, because that is what makes group-writable safe: the agents can create their own lock and temp files and rename over their own `.credentials.json`, but the kernel refuses them an unlink or a rename over root-owned `settings.json`, so the file the lock exists to protect stays out of reach even though the directory around it is writable — measured deterministic that a uid cannot rename over or `rmdir` a foreign-owned entry in a sticky directory. **No "other" bits**, because on the operator's host this is their own `~/.claude` at 0700. The file stays `0640` — group so the agents can *read* their hooks, permission rules and environment, never write them. Nothing is chowned recursively except an entry found in the wrong hands, so **every entry not on the hand-back list keeps the owner it had**, which on a stock install is the agent's. The list is `projects sessions todos shell-snapshots history.jsonl .credentials.json .claude.json backups`; the last two were measured rather than taken from the sketch (CLI 2.1.226 against a throwaway `CLAUDE_CONFIG_DIR` creates `.claude.json`, `backups/`, `projects/` and `sessions/` before it authenticates, and `.claude.json` lands *inside* the directory precisely because `CLAUDE_CONFIG_DIR` is set). `settings.json` is **not** on that list — it is the one file kept from the agents — and a group-writable directory is what forces a change the `0750` layout never needed: **a missing `settings.json` is created, root-owned, rather than left alone.** Under `0750` the agents could not create one either, so its absence was closed by the same lock; under `1770` a run could create `~/.claude/settings.json`, own it, and put a sandbox policy or a hook in it that every later session reads, so the boot brings an empty `{}` into existence and locks it, and removes it again if the lock does not take. Empty settings are the CLI's own reading of no file, so this decides nothing on the operator's behalf. Five things are load-bearing and each fails silently. It is **all or nothing and hand-backs run first**: a failure leaves metering intact and the hole open, where the reverse order would trade a policy hole for a dashboard of zeros — `projects/` is `transcripts.ts`'s scan and therefore every window, every guard and every spend figure. A missing `projects/` **refuses the boot's whole block** rather than locking, because a root-owned directory is one the CLI cannot create it in; the other entries are named once, on the boot that takes the directory, and not repeated. The post-condition is asked **from the agent's own uid** (`setpriv`, `test -r`/`-w`, and one `rm` of a throwaway root-owned probe for the sticky bit), not from `stat`, because root's own `test -w` says yes to everything and a `fakeowner` bind mount can report a chown that the kernel does not enforce; a `projects/` that came back unwritable undoes the lock, where a `settings.json` a run can still write **or** remove is reported and kept. The directory itself is **not** probed for writability, because under `1770` a writable directory is the point — it is what lets the login renew — and the sticky bit is what keeps that from reaching `settings.json`. And **off undoes it**, from the state rather than a stamp — a stamp in the writable layer would be discarded by `docker compose up --build` while the bind mount kept the ownership, so the boot that most needs to hand the directory back is the one that would have forgotten it did anything; the signature is root owning the directory while the agents own `projects/`, which leaves a `~/.claude` that is root's all the way down (compose under `sudo`) alone. Skipped with a line when `UF_AGENT_UID` is unset, the same condition the chown blocks above skip under, because root is not stopped by an owner. **`docker-compose.yml` forwards it**, and it has to: the `environment:` block names every variable it passes and there is no `env_file`, so until that line existed a `UF_LOCK_CLAUDE_HOME=1` in `.env` was read by compose for interpolation and never reached the container — a security control switched on in a file, never applied, and indistinguishable from one that is off (#125). Forwarding it is safe for the reason nothing else here is forwarded blank: no `config.ts` read means no `STRICT_ENV_VARS` entry, so `${UF_LOCK_CLAUDE_HOME:-}` on a stock install is not a permanent warning. What kept it missing was that `deployment.test.ts`'s forwarding assertion matched the `UF_SANDBOX` prefix, which no more covers this name than it would the next entrypoint-only variable; it now derives the list from every `UF_` the entrypoint reads outside a comment.  **Never executed**: no container has run this, and `docs/verification.md` carries the steps, the branch harness that stands in for them and what that harness does not prove. **What the lock leaves the agents is still loaded**: `plugins/`, `hooks/`, `skills/` and `CLAUDE.md` keep the owner they had, so an enabled plugin's `hooks.json` is a work cycle's to rewrite with the lock on. The chat child, which holds `UF_CHAT_GID`, runs no hooks for that reason (`../security/chat-child-config-files.md`); every other child still runs them, and holds nothing a work cycle does not.
