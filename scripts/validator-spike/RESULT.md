# What the spike measured

`score-report.md` beside this file is the generated tally, regenerated by
`score.mjs --collect`. This is the reading of it, including the parts a
generated table cannot say.

**One number first: 34 of 37, and zero false-finished.**

---

## The numbers

Model **claude-sonnet-4-5**, one call per run, task text + branch diff, no
testimony, no repository access.

| | value |
|---|---|
| agreement, held-out set | **34/37 (91.9%)** |
| agreement, all 40 answered | 35/40 (87.5%) |
| trivial validator that always answers `finished` | 29/37 (78.4%) |
| **false-finished** (said finished, label says not-done) | **0 of 1** held-out; **0 of 2** all-in |
| **false-not-finished** (said not-finished, label says finished) | **0 of 29** held-out; **2 of 31** all-in (cases 18, 24) |
| labelled `unjudgeable` answered `unjudgeable` | 5 of 7 |
| verdicts parsed successfully | 40 of 40 |
| cost per verdict | median $0.125 measured / **≈$0.04 modelled** — see below |
| wall clock per verdict | median 49.5 s (11.9 s – 108.0 s) |
| whole branch diff | median 76.8 kB, max 274 kB; 19 of 40 shortened to fit 60 kB |

"All-in" means every answered case, the three held out included: 40 answered, 31
labelled `finished` and 2 labelled `not-done` (counted from `score-report.md`'s
"Every verdict" table; held-out is 29 and 1). This row first read "1 of 30", which
counted case 18 and missed case 24; both are held out, so the held-out figure was
never affected.

Three cases (2, 18, 24) are held out because this harness cannot vouch that the
model was shown the run's whole diff. The rule is in `score.mjs` and is
label-independent, so it cannot be tuned after the fact — but applying it
honestly costs something: case 2 is one of only two `not-done` rows, so the
held-out detection figure rests on **n = 1**. Both cuts are printed for that
reason, and neither is a rate.

## The two errors, separately

**False-finished: zero.** Both runs the labels call `not-done` were called
`not-finished`, on the same evidence a person used — an empty diff against a
task that plainly required a commit. This is the error the feature exists to
prevent, and there are none to quote.

**False-not-finished: zero on the held-out set, two on the full set** — cases 18
and 24, and both are defects in this harness rather than in the validator. Case
18: the run made three commits; one of its subjects (`Give a rate limit its own
ladder, its own ending, and jitter`) matches more than one commit in the
repository, so `buildCases.mjs` refused to guess and dropped it. The model was
shown two thirds of the work and said so precisely: *"TRANSIENT_BACKOFF_MS (the
#104 retry ladder) is never passed through jitterMs … and only 2 of the required
3 commits exist."* That is the right answer to the input it was given. Case 24:
none of the run's commit subjects resolved, so the model was shown an empty diff
(`unattributed`) for a run labelled `finished` and answered *"branch diff is
empty, so none of it landed"* — again the right answer to the input.

## What it did with the seven `unjudgeable` rows

Five of seven: `unjudgeable`, each for the right reason — a review whose product
is prose, two triage runs forbidden to commit, a read-only audit, a question.
Every one of them names the ambiguity explicitly rather than guessing: *"an empty
diff is consistent with both a completed analysis and a no-op run."*

The other two, cases 8 and 36, it called `finished`. **The label's premise does
not hold for these two rows.** `validator-baseline.md` §3 records their task text
as `Implement WF1` and `Implement WF2` and calls them unjudgeable because the
specification is not in the artefacts. The transcripts say otherwise: the first
user turn of session `a20af8db` is 4,953 characters and of `b7ed0edf` is 6,210,
each carrying a full specification with named deliverables, ordering constraints
and a definition of done — `WF1`/`WF2` appear only as the node's label. The
baseline was describing `runs.task`, the workflow node's own title; a validator
at run end reads the composed prompt, which is what these cases hold.

So the premise is wrong for both rows, and the labels with it. But that does not
make `finished` the right label for both. Each was checked against the repository
with read-only `git show <sha>:<path>` and `git grep <pattern> <sha>` over the
commits its case file lists (`cases/08-a20af8db.json`, `cases/36-b7ed0edf.json`;
the one chain `uf/usagefoundry-1-dd927763` in `/workspace/UsageFoundry`, case 8
`ee8d3c18..918fbf2a` on base `96b558b1`, case 36 `12258cfb..86ab12bf`):

- **Case 8: not `finished`.** The task says *"Uncommitted work goes onto its own
  branch. `commitPending` exists for this"*. At `918fbf2a`, `commitPending` is
  named in `land.ts`, the land route, `CLAUDE.md` and `.gitignore`, which is
  exactly where it is at the base `96b558b1`; no line the five commits added, in
  any file, mentions it, and `stopInstance` in `workflows.ts` does not commit.
  The README the run added says *"the halt never commits, never removes a
  checkout and never touches a branch"*, and `stopInstance`'s own comment says
  the same. So one of the four "what must survive it" items was left out on
  purpose and documented as a choice. Everything else the shipped judge listed is
  there (the `cause` on `stopRun`, `cancelQueuedFor`, the `haltPlan` tests), so
  the evidence supports `partial` at most. I checked this one requirement and
  not the rest of the task. The `prompt.md` run's `finished` is the miss; the
  shipped judge's `not-finished` named exactly this requirement.
- **Case 36: `finished` holds.** At `86ab12bf` the
  task's named deliverables are in the tree: `maxInstanceCostUSD`,
  `maxSessionFraction` and `maxWeeklyFraction` in `InstanceBudgetDTO` and
  `budget.ts`, nullable with `null`/blank/`0` all off (`normalizeInstanceBudget`);
  `evaluateInstanceBudget` sharing `BudgetStopCode` and `readWindowGuard` with
  `evaluateBudget`, with the `no_ceiling` refusal; `enforceInstanceBudget` called
  from `startRun`'s pre-cycle guard and tripping through
  `stopInstance(…, { kind: "guard", … })`; the telemetry door widened by
  `instanceSpend` and written down in `CLAUDE.md`; no live mode, said in the
  README, and in the editor as "checked … never during one"; the limits settable
  only in the workflow editor, with `POST /api/workflows/[id]/run` reading no body; the monotone-terminus
  answer in `CLAUDE.md`; the hatched meter for an unknown figure; and
  `budget.test.ts` carries a test for each of the six scenarios the task lists
  (under the cap, at the cap exactly, in flight, a fraction with no ceiling, a
  window falling back under the guard, an estimate-only instance). Read from the
  source, not run. One clause of the task has nothing to attach to at that commit:
  *"plus any orchestrator-block turns it is responsible for"*. `instanceSpend` sums only
  the rows joined through `workflow_instance_runs`, and `workflow_instance_blocks`,
  the table orchestrator blocks write their cost to, is absent at `86ab12bf` (a
  commit outside that chain adds it, `41b4302de`). At today's head `instanceSpend` does add
  those blocks' `cost_usd` and `cost_usd_est`. So the clause was unmeetable on that
  chain and is met once the work joined, and it does not count against the row.
  The shipped judge flagged the same clause as not visible.

**The labels are left exactly as the measurement run wrote them** and both rows are
still counted as misses above. The "36/37" this section used to quote does not
survive the check: rescoring only what the repository supports (case 36 →
`finished`, case 8 → `partial`, which scores as `not-finished`) gives **35/37**
for `prompt.md`, whose case-8 `finished` stays a miss, and **34/37** for the
shipped preamble, whose case-8 `not-finished` becomes a hit. Neither is an
agreement figure to quote: the new labels were chosen after the verdicts were
known, which is the tuning the held-out rule exists to prevent, and one of them
rests on one requirement checked. They are reported, not applied.

The seventh, case 19, is the one genuine disagreement left. The task asked for
specification documents *and* for six to ten GitHub issues to be filed. The
documents landed; the model called it `unjudgeable` because *"the required 6-10
filed GitHub issues + index cannot be confirmed from a git diff"* — which is
true. The label weighed the visible half. That is a real difference of opinion
about what a partly-off-repository deliverable means, not a failure to read.

## The testimony arm: it changed nothing

`git show a74a1bb:"proposals/implemented - ExternalValidator/external-validator.md"` §1 calls the run's own final message *"the one
artefact that would close the biggest gap"* — the thing that separates a
correct empty diff from a wrong one — and decision 2 recommends giving it to the
validator. That is testable here, so it was tested.

All eight empty-diff cases (1, 2, 6, 10, 15, 24, 31, 34) were re-run with
`--with-testimony`, which appends the run's own last turn marked as its account
of itself. `score-report-testimony.md` is the result:

**Zero of eight verdicts changed.** Six of six on the scored subset, both with
and without — identical verdicts, case for case.

What did change is the reasoning, and it changed in the right direction: given
the testimony, the model names it and declines to lean on it. Case 10:
*"only testimony claims filing, which isn't evidence."* Case 31: *"the final
message is unverifiable testimony."*

The reason it bought nothing is that the discrimination was never in the
testimony. **The task text already carries it.** Every one of the five correctly
`unjudgeable` runs was told in its own prompt not to commit, or asked a question;
both `not-done` runs were told to commit and did not. A reader with the task text
and an empty diff does not need the run's own word for it — and on the two rows
where the task text genuinely cannot settle it, neither can the testimony,
because the testimony is the run's word about exactly the thing in dispute.

This is a negative result against a recommendation the design document makes on
reasoning rather than measurement, on n=8. It is not a reason to strike decision
2 — it is a reason to make M1 measure it before paying for it.

## Cost

Two figures, because only one of them is a measurement.

- **Measured: median $0.125/verdict, $5.27 for all 40.** Priced from the
  sender's own token totals (median 39,875) at Sonnet list. That sender was the
  Claude Code subagent path, which re-sends the prompt once per turn across the
  2–4 turns it takes to `Read` the request and `Write` the reply, and carries its
  own system prompt and tool schemas. It is an upper bound.
- **Modelled: ≈$0.04/verdict.** The median composed prompt is 37,431 characters
  ≈ 11 k tokens of diff-heavy text, plus ~450 output tokens: 11,000 × $3/Mtok +
  450 × $15/Mtok. That is what `validate.mjs --transport api` would actually
  bill, and it could not be measured here because no API key is reachable from
  this container.

Against `git show a74a1bb:"proposals/implemented - ExternalValidator/external-validator.md"` §8's guardrail — median validation cost ≤
10% of the run it validates — even the upper bound clears it comfortably: these
runs cost dollars each, not twelve cents.

## What this did not measure

- **Whether a real `claude` under the pinned CLI answers the same way.** The
  transport that answered these 40 requests was the harness's subagent path, not
  `validate.mjs --transport api` and not `spawnAssist`. Same prompt bytes, same
  model family, different system prompt and a tool loop around it.
- **Testimony on anything but an empty diff.** The `--with-testimony` arm was run
  over the 8 empty-diff cases only, because that is where the design document
  claims it matters. Whether it changes a verdict on a 100 kB patch is untested.
- **Anything about a non-isolated or a `failed`/`blocked`/`cancelled` run.** The
  labelled set is 40 `completed` runs on isolated branches.
- **Whether any of the work is correct.** Every `finished` here means the change
  asked for is present, never that it works.
- **Repeatability.** Each case was judged once. No verdict was sampled twice, so
  none of these numbers carries a variance.

## The shipped preamble on the same 40

Everything above is about `prompt.md`. The prompt that ships is
`buildValidationPrompt` in `src/lib/validation.ts`, whose preamble replaces
"be suspicious rather than generous" with `VERDICT_PREFERENCE`, and it had never
been scored. `score.mjs --shipped` composes each case through that function
(`shippedPrompt.mjs`; the case's `runs.task` as the task body, no history, the
production `diffAsText` rendering the files), `io-shipped/` holds the 40 replies
and `score-report-shipped.md` is the generated tally with the 40-row table.
2026-11-08, judge a Claude Code subagent on **Sonnet 5.5** with no repository
access, one sample per case, composed from `validation.ts` as of `4fd7c103` (last changed
in `9ca987c5`).

| | `prompt.md` (above) | shipped preamble |
|---|---|---|
| agreement, held-out set | **34/37 (91.9%)** | **32/37 (86.5%)** |
| agreement, all 40 | 35/40 (87.5%) | 33/40 (82.5%) |
| trivial validator that always answers `finished` | 29/37 | 29/37 |
| **false-finished** | **0 of 1** held-out; 0 of 2 all-in | **0 of 1** held-out; 0 of 2 all-in |
| **false-not-finished** | 0 of 29 held-out; 2 of 31 all-in (18, 24) | 0 of 29 held-out; 2 of 31 all-in (18, 24) |
| labelled `unjudgeable` answered `unjudgeable` | 5 of 7 | 5 of 7 |
| verdicts parsed | 40 of 40 | 40 of 40 |

**Agreement got worse by two cases; false-finished did not.** Three verdicts
differ between the two runs and no other:

- **7** (`finished`): `finished` → `unjudgeable`. The patch for `settings/page.tsx`,
  where most of the task lives, was dropped to fit; the judge says it cannot check
  the guard-set lead or the save states.
- **20** (`finished`): `finished` → `unjudgeable`. Eight of 22 files' bodies were
  dropped, including `referential.go` and `pr.go`, and the acceptance criteria are
  in issue bodies the judge cannot read.
- **8** (labelled `unjudgeable`, so wrong either way): `finished` → `not-finished`.
  The task requires uncommitted work to go onto its own branch via `commitPending`;
  the README the run added says "the halt never commits", and no visible file calls
  it. `workflows.ts`, where `stopInstance` lives, was among the files dropped from the
  patch. Read afterwards in `/workspace/UsageFoundry` at the case's last commit: that
  file has no `commitPending`, and none of the lines the five commits added, in any
  file, mentions it. So the `not-finished` named a requirement the branch does not
  meet, which is the validator doing its job on a case the label called
  unjudgeable; the earlier run's `finished` is the one that missed it. Whether the
  deviation matters to the operator, the README states it as a choice, was not
  assessed.

**Whether the preamble caused the two lost cases is not shown, and a control says
it probably did not.** Between the two runs the judge model (Sonnet 4.5 → 5.5), the
sender's system prompt and the preamble all changed, with one sample each. So the
three changed cases were re-judged by this run's judge twice more:
`io-control-promptmd/` with `prompt.md` and `io-control-shipped2/` with the shipped
preamble again.

| case | `prompt.md`, Sonnet 4.5 (recorded) | `prompt.md`, this judge | shipped, this judge | shipped, this judge, again |
|---|---|---|---|---|
| 7 | finished | unjudgeable | unjudgeable | unjudgeable |
| 8 | finished | not-finished | not-finished | not-finished |
| 20 | finished | unjudgeable | unjudgeable | **finished** |

With `prompt.md` the present judge gives the same three answers the shipped
preamble gets, so these differences are not attributable to the preamble; the
older run's `finished` on all three is what is out of line, and the likeliest
reasons are the judge model and the sampling. Case 20 flipped under the same
prompt on a second sample, so a single verdict there is a coin the size of the
doubt. This is n = 3 with one or two samples each: it bounds nothing, and it does
not show the preamble is neutral, only that these 40 do not show it is not.

**Repeated since.** `repeat-report-shipped.md` judged all 40 shipped-preamble requests
two more times (80 judges, same model): 38 of 40 cases kept one verdict across the
three samples, held-out agreement was 32, 31 and 32 of 37, and the two cases that moved
(7 and 17, `finished` ↔ `unjudgeable`) both have a shortened patch. Across the
three samples `32/37` moved by one case; the report also says what that does not cover.

**What the 40 do show about the preamble's intent.** `VERDICT_PREFERENCE` routes
unsupported doubt to `unjudgeable`, and where a verdict moved in either run it
was between `finished` and `unjudgeable` on a case whose patch was shortened; in
production `unjudgeable` closes the task without a pickup, so those two would
have closed exactly as `finished` does. Neither run produced a false-finished,
and on 29 held-out `finished` rows neither produced a `not-finished`.

**What this did not measure**, beyond the list above: `spawnAssist`'s child under
`plan` mode (the judge was the harness's subagent path, whose tool access could
not be restricted to the one file it was told to read; the three-call judge for
case 14 and four-call control for case 20 read more than the two-call norm, which
is consistent with paging a large request and is not checked); the board's
title/brief split (the case's `runs.task` stands in for the task body, with a
placeholder title); the "this branch carries more than one run" note `validate.mjs`
adds for the 11 chained cases, which production's evidence does not have and
this run therefore omits; and per-file +/- counts for a file whose patch was
dropped (the `[TRUNCATED]` notice reads `(+? −?)`). 16 of the 40 replies, and 2
of the 3 repeats, reached me in the subagent's chat message and were saved
verbatim by hand (`HAND_SAVED.txt` beside them names which).

## The already-on-main arms

`history.mjs` and `history-report.md` beside this file add one input the 40
cases do not have: an empty branch diff beside commits the server found in the
branch's history (`src/lib/validationHistory.ts`, board task 17be140e). Seven of
the cases above, labelled `finished`, are re-built three ways and judged by the
**shipped** prompt rather than `prompt.md`: with no history, the judge said
`not-finished` for 7 of 7; with the case's own commit, `finished` for 7 of 7;
with another case's commit, `not-finished` for 14 of 14. None of these numbers
extends the 34 of 37, which are about `prompt.md`; the reading, its caveats and
how to re-run are in `docs/agent/taskboard/completion-validation-history.md`.

`history.mjs --arms split` adds the other half of that question, a non-empty branch
diff that is only the later run's share of a task, over six multi-commit cases
(`history-split-report.md`): the later half alone, as today, 0 of 6 `finished`; with
the earlier commits as history, 5 of 6; with another case's commits, 0 of 12; the
rest is in the same document and in `docs/verification/taskboard-board-and-tools.md`.
