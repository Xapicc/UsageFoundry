The task gate

A run is started from a task, does the work, and says it is done. Here is every step between that claim and the board changing — and the four ways it can end.

This models the code, not a proposal. The sibling file external-validator-mockup.html models the design that was pitched — notify-only, a card, a filter segment. What shipped is narrower and stronger: it gates one thing (a run closing its task) and it can spend a work cycle. Where the two disagree, this page is the one that matches src/lib/validation.ts. Off by default.
01

One run, one task, from start to ending

The steps are a real sequence, so they are numbered by when. The blue node is the only new gate.

  1. run starts

    The task is claimed, before the first cycle

    claimTaskForRun runs at the top of startRun — ahead of the worktree, ahead of everything. The board shows claimed while the work is in flight, which is what stops a second agent taking the same brief. This happens whether or not runs can reach the board: the claim is this app writing down what it just did.

  2. cycle 1

    The agent works, and commits

    Its three board tools are list_my_tasks, complete_task and create_task — no list_tasks, so it never sees the rest of your backlog. With the gate on, complete_task's description tells it the branch is what gets read, and to commit before calling.

  3. the claim

    It calls complete_task — and nothing closes yet

    The tool stops being the close and becomes the claim. A run_reviews row opens with kind='validate', carrying the task it is about and the base and head it is judging, and a separate --permission-mode plan child starts on the run's own diff. The agent is told the truth and told not to poll:

    tool“Add jitter to the 429 retry ladder” is not closed yet. What this run has committed to its branch is being read against what the task asks for, and the task closes by itself if that reading finds everything there. Two things follow. Anything you have changed but not committed is not on the branch and cannot be seen, so commit it now if it is part of the work. And if the reading comes back saying something is missing, you will be told what, and the task stays yours — you do not need to call this tool again to find out.

    Asked twice, it answers with the reading already running rather than starting a second one — and rather than closing the task, which is the whole gate defeated by repetition.

  4. ~50s

    What the reader is shown

    The task's own title and brief; the branch diff, up to 60 kB, with the file counts whole even when the patch is cut; the paths that are changed but not committed, named as not delivered; and the run's own prompt underneath, marked context — a run told to do more than the task named is not unfinished for having done it.

    It is never told a run claims to be finished. Agreement bias is directional, and the trigger for this whole path is a claim of completion — so the claim is the one fact kept out of the prompt, and a test asserts against five phrasings of it.

  5. cycle ends

    The boundary waits for the answer

    A run that called complete_task in its last few seconds would otherwise end with the verdict still in flight and no cycle left to act on it — so the boundary waits, polling the row, up to eleven minutes against a measured median of fifty seconds. It holds its own folder and slot, which it was holding anyway; nothing has been released and no dependent is waiting. Press Stop and the wait ends at once.

02

Four endings, and only one of them costs anything

Three of the four close the task. That asymmetry is the design: a gate that failed closed would turn a shortage of assist slots — a memory limit — into billed work.

finished
The task closes

Recorded as completed by this run. The run then ends exactly as it would have — its DONE, or its cycle cap.

costs: one reading
unjudgeable
The task closes

A real answer and a common one: the deliverable never enters the repository, or the specification is somewhere the reader cannot see. A shrug must not buy a cycle.

costs: one reading
no verdict
The task closes

No slot free, no branch of its own, a crash, a timeout, an unreadable reply. Null in the column is its own state and never reads as agreement.

costs: nothing, or one failed reading
not-finished
The task is held open

It stays claimed by this run, and the run gets another work cycle — past the cycle cap it was started with — carrying what the reading could not find.

costs: one reading + one work cycle
The extra cycle extends exactly one limit. maxIterations and maxDurationMinutes are the only two things that guarantee a run ends, so the grant is counted on the row and ceilinged by Extra work cycles a check may buy (default 2). The time limit, the run's spending limit, both window guards and the daily ceiling are all read again at the top of that cycle and still end the run there — a grant is permission to ask for a cycle, never to have one. Set it to zero and the task is still held open and you are still told why; nothing is bought.

04

What you see on the board

Two endings, and the second one is the one worth recognising.

Give the merge queue a head-of-line timeout

claimed

A held-open task stays claimed by a run that is over. That is a stale claim, and this app deliberately has no clock on it — it is left standing and it is yours to release (claimed → open), on a board you are already reading, against a run whose page is one click away. It is not a new state; it is the state a run that died holding a task has always left.

05

The three switches

Under Agents, below Let runs use the taskboard — which has to be on first, since a run that cannot reach the board never claims one.

Check a task before a run closes it
When a run marks its task complete, what it committed to its branch is read against what the task asks for, and the task closes only if that reading finds the work there. If something is missing the task stays open and the run gets another work cycle to finish it. Anything else — a run without its own branch, no slot free, a check that fails, or a reading that cannot tell — closes the task exactly as it does today. Off by default: it is the one child this app starts without being asked
Limit per check
A hard stop inside the CLI, and the only money bound on a check — it fires by itself, so it cannot be left to the window guard that is read once at the door. Measured at about 12c a check on an upper bound. Blank removes it
1.00
Extra work cycles a check may buy
How many further cycles one run may be given when a check finds something missing, past the cycle limit it was started with. Every other limit still ends it — time, run spend, both windows and the daily ceiling — so this extends one bound and not the rest. Zero means the task is still held open and you are still told why, and nothing is bought. There is no blank: a limit that could be removed would be a run nothing ends

06

What is not built, and what is not known

Not built

  • The verdict card and the filter segment the pitch asks for. The action is the product here — the task does not close and the run goes back to work — so the log carries the verdict and nothing was added to the runs list.
  • Anything for an unclaimed task. This gates claimed → done by the run that holds it. A task nobody was started for is still yours to close, and always was.
  • Running your tests. The strong verifier is absent and that is the honest gap — a reading can say the change is present, never that it works.
  • Non-isolated runs. A run in a shared folder has no diff that is only its own work.

Not measured

  • No verdict has ever been produced by a real claude. Nothing in this app has run the assist path against the real CLI, and this is the first thing to make that path automatic.
  • The shipped prompt is not the scored prompt. 34-of-37 agreement with zero false-finished was measured on a text whose be suspicious rather than generous paragraph this change had to replace — because a wrong not-finished now costs a cycle instead of a glance. The figure is inherited.
  • The daily ceiling now counts assists. installSpend reads run_reviews.cost_usd for the first time, so an install with a history of reviews reads higher against its limit immediately, with no run having spent anything new.
It is a weak verifier and the literature is not flattering. A retry loop improves things when an external verifier supplies the signal — Reflexion, 91% against 80%, where the signal is a test runner — and degrades them when a model grades itself: 75.8% → 38.1% on CommonSenseQA after one round. This sits between the two: a separate process reading a diff it did not write. Two of that literature's three rules are met — it is not intrinsic self-correction, and the model does not decide when to stop, a number you set does. The third is the gap above.
