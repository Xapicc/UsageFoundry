Taskboard — a mockup of a decision that has already been taken

This file argues about shape, not about whether the Taskboard should exist. The operator has decided to build it. There are no option files beside this one, no case for it and no case against it, and nothing here is a recommendation. It is a picture to disagree with — about where the pane goes, what a row carries, how the states that are easy to get wrong should look, and what all of that costs.

Every number, name, path, run id and timestamp below is invented, produced by the seeded generator at the foot of this file so that two people opening it see the same board. Nothing here reads the database, a transcript or run_events; there is no task table in this repository and this file does not propose one. Each drawn frame carries its own FABRICATED DATA chip, so a screenshot cropped to one frame still says so.

Throwaway sketch, 2026-09-07, against commit 2d07f09 on uf/usagefoundry-721638d11c0b-2-a0aee284. Colours copied out of src/app/globals.css by hand, so they drift the moment that file changes. Nothing under src/ was touched.

The cost, drawn rather than argued

Six digits move and one pane loses its digit. 02

The board — cross-project by default

Every workspace and folder in one view, grouped by status, priority-ordered inside each group, with Done collapsed rather than absent. Press the Done header to open it; it is a real <details>, and the group header sticks to the top of the scroll area.

FABRICATED DATA1280 × 700 — /taskboard, no filternot a screenshot
What a row carries, and the four things that only became visible once it was drawn

1. The origin badge and the "filed by" link are the same fact. Drawing both put the run id on the row twice. So the badge is the link when a run filed the task, and a plain chip when the operator, the chat or a block did. Origin never takes a status tone — provenance is not health, and docs/agent/conventions.md already keeps status tones off marks that are not statuses.

2. The run that claimed and the run that completed are not always the same run — see in Done, claimed by one run and finished by another after the first ended. That is two links, not one, and it is what makes the links a column rather than a suffix.

3. A task with no folder needs a positive rendering. An empty cell in the location column reads as loading or broken, so an unassigned task draws a dashed No folder pill in that same column. It is a legitimate state — the orchestrator can file work before it knows where it lands.

4. Nesting crosses the grouping. A task a run filed while working another one is drawn under its parent — but the parent is claimed and the child is open, so an open task is rendered inside the Claimed group. The child keeps its own status chip and a filed while working this mark, and the Open group's count does not include it. That means the Open count and the rows visible under the Open header disagree — and so does the summary line above them: the header counts every task, the three group counts do not count a borrowed child, so the header reads one higher than the groups sum to. Both readings are defensible and neither is hidden here. The alternative — put the child in its own status group with a backlink to the parent — is not drawn, and choosing between them is not this file's decision.

No per-row action buttons. The board is a reading surface; the one place an action is drawn is §7, where the action is the point.

The filter — cross-project off, one folder on

Left: the default, every workspace. Right: narrowed to one workspace and one folder.

FABRICATED DATAfilter off
FABRICATED DATAfilter on — Clients › atlas-etl
One decision drawn here

With a filter on, a group with nothing in it still draws its header and a zero — Done reads 0 on the right rather than vanishing. With no filter, an empty group is not drawn at all. The reason is that under a filter the zero is information the operator is looking for, and a group that disappears is indistinguishable from a group that was never there.

The page title stays Taskboard and the scope goes in the summary line under it, not in the heading, so the toolbar title panes.ts:98 would derive stays stable while the filter moves.

What the narrow width settled

At 390 a row is three lines: title, then status · location · origin · age, then the run links. The location is the line most at risk — Clients › northwind-api is already close to the width, so the workspace is drawn faint and the folder in full colour, and the folder is what survives a truncation.

The drawer is 224px of a 390px window and covers most of it, which is why the app opens it as a modal <dialog> rather than pushing the pane. Eleven rows fit without scrolling; a twelfth pane would not.

FABRICATED DATA1280 × 700 — the dense boardnot a screenshot
The honest answer: partly a wall, and here is where

Status grouping and folder grouping cannot both be primary. Priority order inside a status group scatters each folder's tasks the length of the group — at this size the Open group is a column of mono paths in eleven different shapes and no two adjacent rows share one. A reader asking "what is outstanding in atlas-etl" has to use the filter; the board itself cannot answer it.

The sticky header is load-bearing at this size and not at the last one. The Open group alone is taller than the viewport, so without it the reader loses which group they are in about two thirds of the way down. That is a decision this size forced and the eight-row board did not.

What is not drawn: a per-folder sub-heading, a second sort control, or a density toggle. Each is a plausible answer to the paragraph above and each is a shape decision this file deliberately leaves open rather than pre-empting with a sketch.

The three kinds of nothing

docs/agent/dreaming.md:166 already requires this app to keep its kinds of nothing apart, and docs/agent/git-and-review.md names three that may never render as an empty list. These are the Taskboard's three, drawn side by side so they can be compared rather than described.

FABRICATED DATAnothing filed yet
FABRICATED DATAfilter matched none
FABRICATED DATAfetch failed
What makes them three pictures and not one

Empty is a primer and an action. It is the only one of the three that is not a problem, so it takes no tone and it says who else writes here — the point of a board runs and orchestrators write to is lost if a first-time reader thinks only they can file.

Matched none keeps the filter bar, names the filter in the sentence, and says how many tasks exist outside it. It offers Clear, not New task: the operator almost certainly wants the board back, not a task in a folder they were only looking at.

Failed is the only one drawn in the danger tone, and the only one that shows no counts at all — no total, no group headers, no zeroes. A number here would be a claim the app cannot make; it did not read the board, so it does not know that there are none. It names the request and the failure and offers Retry.

07

A claim held by a run that crashed

A claim is a record, not a lease. Nothing expires it, no sweep releases it, and there is no clock on it anywhere. The board has to make that legible without implying the task is stuck — because it is not stuck, it is claimed, and the thing that failed is the run.

FABRICATED DATAtwo claimed rows — a live claim above a crashed one
Where the tone goes

The tone belongs to the run chip, never to the task row. Colouring the row danger says the task is broken; what is broken is a run that finished three days ago. So the row keeps the ordinary Claimed chip, and the failure is a second chip naming the run's own ending.

No word on the row says "stale", "stuck" or "expired". All three assert a rule the app does not have. The row states two facts — when it was claimed, and how that run ended — and lets the operator decide. The one affordance is Release claim, and it is a manual act with a person's name on it rather than a sweep.

Age alone is not the signal. The healthy row above it has been claimed for 6h by a run that is still going; a long claim is ordinary. What distinguishes the two is the run's status, which is why the run's ending is drawn and the elapsed time is not emphasised.

08

Origin, doing visible work

Four origins on four adjacent rows — the operator at their desk, the orchestrator chat, an orchestrator block inside a workflow, and a run that filed something at 03:07 while working on its own task.

FABRICATED DATAthe four origins, adjacent
Why the badge is always present

A board that four writers share is unreadable if the reader has to guess who wrote a row. The badge is on every row, including the operator's — an origin column that is blank for the human and filled for machines makes the human's rows look unattributed rather than obvious.

The 03:07 row is the case the badge exists for: Retire the unused request_log writers looks exactly like something the operator wrote, until the badge says a run filed it in the middle of the night while it was working .

09

Light and dark, drawn at the same time

The toggle at the top of this page switches the whole sheet. These two frames ignore it: each forces its own color-scheme, so the dark side is drawn on every screenshot rather than assumed.

FABRICATED DATAforced light
FABRICATED DATAforced dark
One thing dark made visible

The priority pill is a hairline box with coloured text. In dark, --danger is #ff6961 and the P1 pill reads as a much louder mark than its light-mode counterpart at #d70015, because the dark value is a tint rather than a shade. Three P1 pills down a column is a stripe. Whether priority should be colour at all — rather than position, which the ordering already gives it — is a shape question this file raises and does not settle.

10

What this picture deliberately does not decide

  • Whether it goes after Runs. The brief put it there and the mockup draws the cost. It does not argue the placement, and it does not argue that API account should lose ⌘9.
  • Any schema, route or wire format. There is no task table, no /api/tasks, no polling interval and no statement about who may write what. Four other proposals build the real thing.
  • Nesting versus a backlink when a child's status differs from its parent's — §2 draws one of the two and names the other.
  • What a priority is or who sets it. P1/P2/P3 are placeholders for an ordering, nothing more.
  • Whether Done is terminal, and what reopening one would do to the claim links on it.
  • The icon. The glyph in the sidebar is fabricated for this drawing; src/components/ui/Icon.tsx is untouched.
  • The answer to §5. A per-folder sub-heading, a second sort and a density control are all named there and none is drawn.
